# InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure

InfraRSI Team

###### Abstract

While Recursive Self-Improvement (RSI) has accelerated isolated
algorithm and kernel synthesis, distributed LLM training throughput
depends on tightly coupled launch settings, operator kernels, and
communication schedules, where single edits often hit out-of-memory
(OOM) boundaries, compiler conflicts, measurement jitter, or silent
numerical drift. We present InfraRSI, the agentic harness that turns
open-ended human commands into verified training-system optimizations
through a five-stage workflow: init locks editable scope and a fixed
task contract over workload, loss, and timing invariants to prevent
reward hacking, doctor profiles baseline phases and calibrates cluster
noise, run co-optimizes launch configurations and code patches before
verifying top candidates in back-to-back baseline re-runs and writing
checked findings to a cross-hardware experience bank, and report and
apply audit source paths, account for failed-trial costs, and commit
promoted changes. Rather than stepping greedily from a single
configuration during run, InfraRSI initializes from diverse
experience-seeded configurations and maintains global execution-time and
censored peak-memory models fitted to all trials, including OOM
failures. Using these models, it estimates per-setting memory costs,
revises miscalibrated LLM speed priors from live measurements, and pairs
memory-hungry optimizations with memory-saving settings and verified
code patches. Across four single- and multi-node dense and
Mixture-of-Experts (MoE) LLM training workloads, InfraRSI achieves a
speedup of up to $`2.75\times`$ and lifts mean Model FLOPs Utilization
(MFU) from $`17.4\%`$ to $`30.0\%`$, outperforming existing
configuration tuners and coding agents while transferring experience
across GPU architectures. As it improves training infrastructure
efficiency, InfraRSI forms a two-level Recursive Self-Improvement
loop—revising priors online within runs and distilling experience across
clusters—to push foundation model scaling.

## 1 Introduction

Figure 1: InfraRSI method overview. The five-stage lifecycle defines

Building on classic formulations of self-referential improvement
\[[34](#bib.bib34)\], recent Recursive Self-Improvement (RSI) systems
demonstrate that large language models (LLMs) can discover mathematical
constructions \[[33](#bib.bib33), [25](#bib.bib25)\], synthesize machine
learning pipelines \[[14](#bib.bib14)\], and rewrite agentic scaffolding
\[[45](#bib.bib45)\]. While these systems target isolated algorithms or
single kernels, compute-optimal scaling laws \[[12](#bib.bib12)\]
increasingly bind foundation model progress to the throughput of
distributed training infrastructure \[[36](#bib.bib36),
[24](#bib.bib24), [30](#bib.bib30), [29](#bib.bib29),
[46](#bib.bib46)\]: launch configuration knobs, operator and
training-loop implementations, collective communication schedules, and
device memory limits (Table
[1](#S2.T1 "Table 1 ‣ 2.1 Optimization Objective and Fixed Task Contract ‣ 2 Problem Definition and Empirical Motivation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
In this work, we study how to turn open-ended human commands and
language-model proposals into verified training-system optimizations
through a two-level self-improving loop—revising priors online within
each tuning run while distilling verified runtime evidence into a
cross-cluster experience bank under fixed task contracts. Jointly
optimizing both launch configurations and training source code is
essential because hardware-sensitive mechanisms such as FP8 quantization
\[[23](#bib.bib23), [7](#bib.bib7)\], tensor and expert parallelism,
graph compilation (torch.compile) \[[2](#bib.bib2)\], and FlashAttention
\[[6](#bib.bib6), [35](#bib.bib35)\] interact non-linearly and often
reverse their performance impact across GPU architectures and
interconnect rooflines \[[42](#bib.bib42)\] (Table
[3](#S5.T3 "Table 3 ‣ 5.1 Cross-Hardware Rooflines and Sign Flips ‣ 5 Empirical RSI Loop: Experience Protocol and Cross-Hardware Transfer ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).

Yet applying unconstrained coding agents \[[41](#bib.bib41),
[15](#bib.bib15), [16](#bib.bib16)\] or greedy local search loops
directly to production training repositories exposes four recurring
failure modes (Section
[2](#S2 "2 Problem Definition and Empirical Motivation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
Open-ended code edits frequently introduce reward hacking, numerical
drift, or timing shortcuts, achieving illusory speedups by altering
effective batch sizes, deferring optimizer updates past the timing
window, or applying unstable low-precision casts. At the same time,
distributed clusters exhibit wide-spectrum measurement noise across two
orders of magnitude, causing fixed acceptance thresholds either to
promote random jitter on shared hosts or to discard valid communication
overlaps and incremental code patches on quiet nodes. Guidance from
zero-shot LLM priors is similarly unreliable: predicted speedups
correlate poorly with actual hardware execution and often veto high-gain
compilation or communication settings. Finally, single-incumbent search
loops stall at out-of-memory (OOM) and compiler boundaries whenever a
throughput-boosting setting exceeds device memory on its own and must be
paired simultaneously with memory-saving knobs and compatible kernel
patches.

To address these failure modes, we present InfraRSI (Figure
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"),
Section
[3](#S3 "3 System Architecture: The InfraRSI Harness ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")),
the agentic harness that orchestrates a five-stage optimization workflow
(init $`\to`$ doctor $`\to`$ run $`\to`$ report $`\to`$ apply). In
InfraRSI, init locks editable repository scope and a fixed task contract
over workload, loss, and timing invariants to prevent reward hacking,
while doctor profiles baseline execution phases and calibrates paired
step-time noise on the target cluster. The run stage executes budgeted
compositional search (Section
[4](#S4 "4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")),
a history-aware search controller organized around three mechanisms: (1)
_Multi-Start Initialization and Global Time/Memory Models_
(§[4.1](#S4.SS1 "4.1 Multi-Start Initialization and Global Time/Memory Models ‣ 4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")),

## 2 Problem Definition and Empirical Motivation

### 2.1 Optimization Objective and Fixed Task Contract

Optimizing distributed training infrastructure differs fundamentally
from algorithmic discovery \[[33](#bib.bib33), [25](#bib.bib25),
[14](#bib.bib14)\] and isolated kernel generation \[[26](#bib.bib26),
[16](#bib.bib16)\] (Table
[1](#S2.T1 "Table 1 ‣ 2.1 Optimization Objective and Fixed Task Contract ‣ 2 Problem Definition and Empirical Motivation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
In InfraRSI, each candidate combines launch configuration knobs and
source-code patches to maximize training throughput under a strict
_fixed task contract_: the model architecture, dataset, effective
workload (tokens processed per optimizer update), allowed numerical
precision menu, and optimizer update protocol are held invariant. Each
task contract declares the evaluation window, permitted numerical modes,
and relative loss tolerance, while retaining the full GPU and API search
cost of any failed or rejected candidate.

Evaluating a candidate under this contract separates two distinct
verification questions: _short-horizon loss consistency_ checks that the
candidate’s execution path remains numerically faithful within the
declared precision menu and loss window, whereas _independent
back-to-back verification_ confirms that a candidate’s speedup
reproduces against a fresh reference execution beyond cluster
measurement noise. Because distributed training mechanisms compete for
finite device memory, streaming multiprocessors, and
collective-communication overlap windows, individual optimizations
combine sub-additively and frequently trigger steep feasibility
boundaries, such as compilation and activation-checkpointing conflicts
on Mixture-of-Experts models. Expressing both search cost and projected
runtime savings in common GPU-hour units allows the harness to schedule
and evaluate optimization trials directly.

| Dimension      | Algorithm / Code RSI \[[33](#bib.bib33), [25](#bib.bib25), [14](#bib.bib14)\] | Kernel Synthesis \[[26](#bib.bib26), [16](#bib.bib16)\] | Training Infra RSI (InfraRSI)                        |
| -------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------- |
| Granularity    | Single heuristic or script                                                    | Isolated CUDA/Triton kernel \[[39](#bib.bib39)\]        | Launch knobs & source-code patches (multi-stack)     |
| Cost & Noise   | ms–s; $`10^{3}`$–$`10^{4}`$ runs; low noise                                   | ms/op; $`10^{2}`$–$`10^{3}`$ runs; low noise            | Multi-GPU; 10–20 runs; $`0.04\%`$–$`6\%+`$ noise     |
| Equivalence    | Test suite or val score                                                       | Tensor tolerance ($`L_{\infty}/L_{2}`$)                 | Fixed task contract + source-path audit              |
| Hacking Risk   | Moderate (val overfitting)                                                    | High (caching, skipped sync)                            | Severe (prefetch skew, timer shift, precision drift) |
| HW Sensitivity | Hardware-agnostic logic                                                       | GPU-specific (SM, SRAM)                                 | Roofline/topology-sensitive (H100/H200/H20)          |
| Reusable Asset | Task-specific code pool                                                       | Op kernel library                                       | Cross-hardware priors + audited patch sites          |

Table 1: Comparison of RSI paradigms across algorithmic synthesis,
kernel generation, and training infrastructure.

### 2.2 Evaluation Baselines and System Failure Modes

To evaluate open-code infrastructure search fairly, we compare InfraRSI
against representative autonomous coding agents and configuration
tuners, including Auto-Research \[[15](#bib.bib15)\], the RE-Bench
modular agent scaffold \[[41](#bib.bib41)\], and knob-only OptiCo
\[[3](#bib.bib3)\], under identical task contracts while retaining each
baseline’s native search rules. Across all campaigns, completed trial
counts, GPU execution time, and token consumption are logged along the
search trajectory, including all failed and audit-excluded attempts.

Audited runs across our four dense and MoE LLM workloads (Table
[4](#S6.T4 "Table 4 ‣ 6.1 End-to-End Speedup and MFU Across LLM and MoE Workloads ‣ 6 Experimental Evaluation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"))
expose four recurring failure modes in unconstrained coding agents and
greedy local tuners:

#### 1. Reward hacking and timing-boundary skew.

Without strict contract verification and source-path auditing, open-code
agents frequently achieve illusory speedups via reward gaming
\[[37](#bib.bib37)\] by altering effective work or timing boundaries.
Common failure patterns include unauthorized low-precision casts that
violate the declared precision menu, deferred auxiliary updates that
push work past the timing window while masking runtime import errors
behind a single receipt’s validity flag, step-logging timer shifts that
inflate native reported speed relative to wall-clock time, and
aggressive low-precision or fused cross-entropy edits that degrade
training loss
(§[3](#S3 "3 System Architecture: The InfraRSI Harness ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).

#### 2. Wide-spectrum measurement noise.

Across clusters and workloads, paired step-time noise spans more than
two orders of magnitude, ranging from $`0.04\%`$–$`0.10\%`$ on dedicated
8$`\times`$H100 and 8$`\times`$H200 nodes to over $`6\%`$ on shared
hosts experiencing periodic data-loader or collective stalls. A
hardcoded acceptance threshold (such as a fixed $`2\%`$ gate) is too
coarse on quiet clusters, where it discards valid $`0.5\%`$–$`1.5\%`$
communication overlaps and incremental source-code patches that compound
when stacked, yet still promotes random jitter on noisy hosts unless
governed by calibrated cluster noise gates and independent back-to-back
re-runs
(§[4.1](#S4.SS1 "4.1 Multi-Start Initialization and Global Time/Memory Models ‣ 4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).

#### 3. Miscalibrated LLM quantitative priors.

While frontier LLMs can inspect training repositories and propose
qualitative mechanisms, their zero-shot speedup predictions correlate
negatively with hardware execution (Spearman rank correlation
$`r\in[-0.49,-0.06]`$). In addition, zero-shot priors issue
_false-negative vetoes_ on critical high-impact knobs: on
Gemma-4-26B-A4B MoE (8$`\times`$H200), the prior predicts a negligible
$`+2.0\%`$ gain for graph compilation where empirical execution unlocks
$`+55\%`$; on two-node Qwen3.5-35B-A3B MoE (16$`\times`$H100), it
predicts a slight slowdown for increasing NCCL communication channels
where execution yields a $`+10.2\%`$ gain. A search engine must
therefore combine multi-start initialization with contrarian probing and
empirical prior revision
(§[4.2](#S4.SS2 "4.2 Prior Calibration, Failure Attribution, and Bundle Completion ‣ 4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).

#### 4. Single-incumbent myopia at memory and compiler cliffs.

Optimizing training infrastructure requires coordinating multiple launch
knobs and code patches across steep memory and compatibility boundaries.
Greedy single-incumbent search loops fail in three ways. First, they
discard or repeat failures without attribution, repeatedly triggering
identical out-of-memory crashes or blaming valid launch configurations
when an exploratory source patch fails. Second, they abandon multi-knob
synergies after single-knob OOMs: on Gemma-4-26B-A4B MoE, disabling
activation recomputation alone exhausts device memory
($`+18\text{ GiB}`$ shortfall) and enabling compilation with default
fused kernels hangs, locking out tuners that cannot pair the
memory-hungry optimization with a memory-saving partner
($`-14\text{ GiB}`$) and FlexAttention \[[8](#bib.bib8)\] to reach
$`2.75\times`$ ($`17.6\%`$ MFU). Third, they stall in local optima, as
when Auto-Research plateaus at $`1.29\times`$ on Gemma-4-26B-A4B MoE and
spends its remaining trials circling that local basin
(§[4](#S4 "4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"),
§[5](#S5 "5 Empirical RSI Loop: Experience Protocol and Cross-Hardware Transfer ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).

## 3 System Architecture: The InfraRSI Harness

To address the failure modes in
§[2](#S2 "2 Problem Definition and Empirical Motivation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"),
InfraRSI decouples language-model hypothesis generation from
measurement, verification, search, and experience storage. The harness
pairs a declarative infrarsi.yaml task specification with lightweight
stack adapters ($`<15`$ hook lines) to expose a uniform execution and
receipt interface across major distributed LLM training frameworks,
including Megatron-Core \[[36](#bib.bib36), [24](#bib.bib24)\],
FSDP2/TorchTitan \[[46](#bib.bib46), [18](#bib.bib18)\], DeepSpeed
\[[30](#bib.bib30), [29](#bib.bib29)\], HF Trainer/TRL
\[[43](#bib.bib43)\], and native PyTorch DDP.

### 3.1 Workflow and Multi-Stack Adapters

Every optimization campaign progresses through five deterministic CLI
stages (Figure
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")):

- •
  1. init: Parses target repository ASTs, declares the task scope and
     editable_files, and locks SHA-256 digests of all frozen_files (dataset
     loaders, evaluation scripts, loss definitions, and harness timers).
- • 2. doctor: Executes reference baseline runs, trims warmup steps,
  calibrates cluster step-time noise, profiles execution phase
  breakdowns (forward, backward, optimizer, data loading, and
  collectives), probes interconnect bandwidth, and grades
  experience-bank prior coverage
  (§[5](#S5 "5 Empirical RSI Loop: Experience Protocol and Cross-Hardware Transfer ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
- • 3. run: Executes InfraRSI’s compositional search controller
  (§[4](#S4 "4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"))
  over candidate configurations and source patches, preserving raw
  execution receipts and full resource costs for every attempted
  candidate; at the end of search, it subjects the fastest valid
  candidates to fresh back-to-back verification re-runs against the
  reference baseline on the same GPU allocation, writes verified
  observations and experience packs back to the experience bank
  (§[5](#S5 "5 Empirical RSI Loop: Experience Protocol and Cross-Hardware Transfer ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")),
  and saves result.json, pack.yaml, and REPORT.md.
- • 4. report: Renders and inspects the structured campaign report
  (REPORT.md), invariant verdicts, and resource accounting for candidate
  source-path auditing.
- • 5. apply: Reads the promoted candidate from result.json, checks target
  repository files for post-search working-tree conflicts, and writes
  the validated launch configuration and source diffs (optionally on a
  new git branch).

### 3.2 Measurement and Resource Accounting

InfraRSI represents each candidate as a joint specification of launch
configuration knobs (CLI flags, environment variables, and configuration
keys filtered by algebraic batch-conservation checks) and source-code
patches that synthesize AST-validated unified diffs on editable_files,
such as compiling block-sparse or chunked attention kernels
\[[8](#bib.bib8), [2](#bib.bib2)\], fusing normalization,
rotary-embedding \[[13](#bib.bib13)\], and AdamW \[[21](#bib.bib21)\]
optimizer operators, and bucketing gradient-norm collectives. Every
candidate evaluation and verification run enforces a fixed
optimizer-update count, explicit warmup trimming, and a synchronized
steady-state timing window.

To prevent survivorship bias, the harness tracks GPU hours across
reference, search, promotion, and profiling stages alongside
language-model token consumption, retaining the full GPU and API cost of
every failed or audit-excluded candidate. Incomplete runs from transient
host retries are flagged in the ledger, and migrating a workload to a
new host requires establishing a fresh local baseline.

### 3.3 Semantic, Numerical, and Source-Path Verification

Within each fixed task contract, InfraRSI maximizes log speedup over the
candidate space $`\mathcal{A}`$ subject to 16 deterministic invariants
$`\mathcal{I}_{k}`$ across five verification layers:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\max_{a\in\mathcal{A}}\;y(a)=\ln\!\frac{T_{0}}{T(a)}\quad\text{s.t.}\quad\mathcal{I}_{k}(a)=\mathrm{True},\;\forall k\in\{1,\dots,16\}.
``` |  | (1) |

Task invariants verify execution completion and VRAM caps (L1), model
parameters, sequence length, tokens per update, data digests, and
frozen_files hashes (L2), actual optimizer step counts (L3), permitted
precision menu and relative loss bounds under pre-declared tolerance
regimes ranging from $`0.1\%`$ to $`50\%`$ (L4), and harness-to-script
timing agreement (L5). For numerical verification (L4), all loss
tolerances and adaptation rules are fixed in the task specification
before search begins: by default, L4 bounds relative window-mean loss
deviation within $`\tau`$ (adjusting to $`3\sigma_{\ell}\sqrt{2/k}`$ if
reference repeats vary beyond $`\tau`$, or enforcing per-update maximum
deviation when exact batch order is verified; Table
[8](#A1.T8 "Table 8 ‣ Appendix A Deterministic Five-Layer Verifier Specification ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
Any candidate exceeding these pre-declared bounds is rejected while
retaining its incurred search cost.

Alongside automated receipt checks, InfraRSI performs candidate
source-path auditing before promoting a result. In our open-code
evaluations
(§[6](#S6 "6 Experimental Evaluation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")),
source review excluded candidates that deferred auxiliary parameter
updates to the subsequent step (which omitted the final update from the
timed window and masked a runtime kernel import failure behind a single
receipt’s validity flag) or that introduced unauthorized low-precision
casts outside the task’s permitted precision menu, while confirming that
compliant candidates execute all forward, backward, and optimizer steps
synchronously inside the timed window.

## 4 Budgeted Compositional Search

Under practical multi-GPU search budgets, measurement jitter,
miscalibrated language-model priors, steep memory and compiler-conflict
cliffs, local optima, and late-stage context growth frequently stall
naive proposal loops
(§[2](#S2 "2 Problem Definition and Empirical Motivation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
In each step of the run stage, InfraRSI reads and updates global
execution-time and memory models across all completed trials

(§[4.2](#S4.SS2 "4.2 Prior Calibration, Failure Attribution, and Bundle Completion ‣ 4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")),
and proposes coordinated knob bundles and source patches

### 4.1 Multi-Start Initialization and Global Time/Memory Models

#### Online Noise Calibration and Phase-Headroom Ceiling.

To guard against just-in-time compilation warmup \[[2](#bib.bib2),
[39](#bib.bib39)\] and periodic data-loader or allocator jitter, the
doctor stage trims initial warmup steps and measures each run’s
post-warmup steady-state window mean step time for candidate scoring,
MFU accounting, and final promotion, while using robust median and
split-half statistics inside the search loop so that transient
single-step spikes do not distort surrogate updates. Across runs,
InfraRSI estimates paired log-step-time noise $`\sigma_{\mathrm{pair}}`$
by pooling paired reference re-run differences with within-run
split-half deviations (floored by the within-window white-noise floor),
using $`\max(0.02,\,2\sigma_{\mathrm{pair}})`$ to govern big-knob
selection and stall detection during search and requiring fresh
back-to-back promotion re-runs to exceed the paired relative margin
$`\exp(2\sigma_{\mathrm{pair}})-1`$. This protocol measures paired
baseline noise as low as $`0.04\%\text{--}0.10\%`$ on dedicated
8$`\times`$H100 and 8$`\times`$H200 nodes. Using the doctor stage’s
profiled operator-phase breakdown (forward, backward, optimizer, and
collectives), InfraRSI also caps single-lever log-speedup predictions
via an Amdahl phase-headroom ceiling \[[1](#bib.bib1)\], bounding each
lever’s predicted gain by the profiled time share of the execution
phases it targets.

#### Multi-Start Full-Configuration Initialization.

Infrastructure search spaces partition into disconnected basins
separated by out-of-memory boundaries and compiler incompatibilities.
Starting solely from the unmodified default configuration wastes a large
fraction of the trial budget flipping basic switches one by one, whereas
trusting a single model-proposed bundle risks an immediate crash if any
pair of levers conflicts. InfraRSI therefore dedicates its first three
full trials to probing complementary complete configurations (Figure
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
The first start warm-starts from the best verified full configuration in
the most similar hardware and model environment in the experience bank
via canonical mechanism normalization. The second start probes the prior
model’s highest-rated full configuration that differs from the first
start in at least one high-impact knob, promoting configuration
diversity. The third start executes a uniform random legal configuration
filtered by active conflict rules to anchor global speed and memory
variance, with the first fitting run establishing the memory baseline.
In our Qwen3.5-9B (8$`\times`$H100) run, the experience-seeded first
start reaches $`1.55\times`$ on Trial 1 before subsequent search
advances to $`1.73\times`$.

#### Global Time and Censored Memory Models.

Because configuration knobs and source patches interact
non-monotonically across speed and memory, stepping greedily from only
the latest incumbent deadlocks whenever an early choice blocks a
downstream optimization. InfraRSI instead maintains two global models
fitted across the full trial history and checkpoints search state after
each trial. A Cholesky Bayesian linear time surrogate models log-speedup
over indicator features for non-reference knob settings, verified
source-code patches, and enabling pairs, updating the posterior
precision matrix in closed form while bounding prior variance. In
parallel, a right-censored Tobit memory ledger \[[40](#bib.bib40)\]
models per-GPU peak memory $`\hat{m}(a)`$ (in GiB) for candidate $`a`$
on a device of capacity $`C_{\mathrm{card}}`$ (with observation noise
$`\sigma_{\mathrm{obs}}=0.02\,C_{\mathrm{card}}`$) across three
execution regimes: (i) *exact Gaussian residuals*
$`\hat{m}(a)-m_{\mathrm{peak}}`$ on completed runs with measured peak
memory $`m_{\mathrm{peak}}`$; (ii) *right-censored Tobit likelihoods*
enforcing $`\hat{m}(a)\geq m_{\mathrm{oom}}`$ on out-of-memory trials,
where the failed allocation shortfall establishes the lower bound
$`m_{\mathrm{oom}}`$ on required memory; and (iii) *interval-censored
likelihoods* bounding peak demand within
$`[0.90\,C_{\mathrm{card}},\,C_{\mathrm{card}}]`$ when near-capacity
allocator thrashing occurs. Fitting the posterior memory parameters via
damped Newton steps with Laplace covariance yields calibrated memory
feasibility probabilities and per-setting memory estimates (in GiB) that
distinguish memory spenders from memory savers.

### 4.2 Prior Calibration, Failure Attribution, and Bundle Completion

#### Contrarian Big-Knob Probing and Empirical Prior Revision.

Zero-shot language-model priors correlate poorly with actual multi-GPU
execution (Spearman rank correlation $`r\in[-0.49,-0.06]`$) and
frequently issue false-negative vetoes on high-leverage compiler or
communication flags. To prevent miscalibrated priors from permanently
hiding effective levers, InfraRSI applies empirical-Bayes shrinkage
\[[10](#bib.bib10)\] across both action types: configuration-knob priors
are regularized by their prior spread
($`\sigma_{0}\geq\max(\sigma_{\min},\,0.5|\mu_{0}|)`$) and updated in
closed form by the Cholesky time surrogate as observations arrive, while
language-model code-patch gain predictions are scaled by a conservative
shrinkage factor $`\kappa_{0}`$
($`\mu_{\mathrm{patch}}=\kappa_{0}\hat{\mu}_{\mathrm{LLM}}`$). Alongside
Bayesian posterior updating, InfraRSI actively schedules contrarian
empirical probes whenever a high-impact knob is rated low or vetoed by
the prior yet exhibits high uncertainty whose two-sigma upside clears
the big-knob threshold. InfraRSI tests such levers against the incumbent
by reverting any conflicting setting to reference and automatically
attaching the top estimated memory-saving setting when memory
feasibility is low. After repeated configuration failures or any failure
of a high-confidence setting, InfraRSI also triggers a structured
empirical prior revision carrying measured step times, peak memory, and
out-of-memory shortfalls, directly updating the prior levels
($`\mu_{0},\sigma_{0}`$), refreshing the time surrogate’s prior
parameters and the memory ledger’s declared GiB priors, and re-solving
the posterior in place. As shown in
§[2](#S2 "2 Problem Definition and Empirical Motivation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"),
this probing and revision loop recovers high-gain compilation and
communication settings ($`+55\%`$ and $`+10.2\%`$) that zero-shot priors
initially rate near zero or negative.

#### Failure Blame Attribution Across Memory, Conflicts, and Source Patches.

InfraRSI logs out-of-memory events, numerical violations, and runtime
crashes separately in the ledger. When a non-reference setting triggers
an OOM, it is tagged as requiring a memory-saving partner covering at
least the measured GiB shortfall, and is excluded only if it still fails
across multiple distinct savers. For non-memory crashes, hangs, or
numerical divergence, InfraRSI bans only the minimal conflict tuple (the
smallest co-occurring pair or triple of settings absent from all passing
runs) while keeping each individual setting eligible in other
combinations. Failures during code exploration are attributed to the
candidate patch rather than the underlying launch configuration.

#### Bundle Completion and Conflict Backtracking.

Whenever a configuration fails due to insufficient memory despite high
surrogate-predicted speedup, InfraRSI retains it in a high-upside
failure buffer and performs bundle completion, pairing the configuration
with reference-held memory savers that cover the measured GiB shortfall
while reverting any conflicting knob to reference. For example, on
Gemma-4-26B-A4B MoE, bundle completion pairs disabling activation
recomputation ($`+18\text{ GiB}`$ shortfall) with disabling Liger fused
cross-entropy \[[13](#bib.bib13)\] ($`-14\text{ GiB}`$) and enabling
torch.compile
(§[6.1](#S6.SS1 "6.1 End-to-End Speedup and MFU Across LLM and MoE Workloads ‣ 6 Experimental Evaluation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
Similarly, when a high-prior lever conflicts with an earlier accepted
baseline, conflict backtracking re-evaluates the lever directly on the
clean root reference, migrates the incumbent once verified, and retains
compatible settings on top of the updated baseline.

### 4.3 High-Impact Knob Escape and Code Patch Stacking

#### Focusing Exploration on the Big-Knob Set.

When search needs to backtrack, probe contrarian directions, or jump out
of a local basin, perturbing minor knobs (such as memory pinning or
worker thread counts whose effect is below $`1\%`$) cannot shift the
hardware roofline or free enough memory to unlock major speedups, and
risks attributing gains to sub-noise fluctuations. After every
observation, InfraRSI explicitly partitions the configuration space to
isolate the Big-Knob set $`\mathcal{K}_{\mathrm{big}}`$, defined as all
configuration knobs whose prior ($`\hat{y}_{\mathrm{prior}}`$),
surrogate-posterior ($`\hat{y}_{\mathrm{surr}}`$), or empirical
($`\bar{y}_{\mathrm{emp}}`$) single-knob log-speedup magnitude on at
least one setting clears $`\max(0.02,\,2\sigma_{\mathrm{pair}})`$
($`\approx 2\%`$). All structural exploration operators (initial probe
diversification, contrarian probing, trust-region escape, tabu
deduplication, and warm restarts) operate over
$`\mathcal{K}_{\mathrm{big}}`$.

#### High-Impact Trust-Region Escape and Candidate Deduplication.

Whenever two consecutive full trials fail to improve the incumbent
beyond the noise gate, InfraRSI enters escape mode over
$`\mathcal{K}_{\mathrm{big}}`$. It dynamically expands the minimum
trust-region distance from the incumbent from one to three big knobs to
force multi-knob leaps out of the local basin, extrapolates further
along ordered axes after improving steps, and performs periodic warm
restarts from the best historical run of a distinct configuration class.
To prevent wasted evaluations, InfraRSI also enforces big-knob tabu
filtering and registers every proposed configuration-and-patch signature
in the visited set *before* execution, cleanly separating pre-execution
rejections from completed trials and preventing repetitive proposal
loops.

#### Code Patch Stacking and Trajectory Summarization.

When open-code editing is enabled, late-stage configuration proposals
whose two-sigma upside falls below
$`\max(0.02,2\sigma_{\mathrm{pair}})`$ yield their evaluation slots to
source-code synthesis, and verified patches with small individual gains
are stacked and tested together in the spirit of group testing
\[[9](#bib.bib9)\] once their combined log-gain clears the noise gate.
To keep prompts bounded over long trajectories, InfraRSI retains full
execution traces for the fastest and most recent runs while summarizing
older trials into compact single-line records ($`\sim 28\text{k}`$
characters). In addition, when a candidate refines launch knobs on top
of an already verified patch stack, unmodified inherited diff lines are
not double-counted against the per-step line limit.

### 5.2 Structured Experience Protocol

To make empirical observations portable across heterogeneous
repositories, InfraRSI structures experience records around three core
entities: the Environment, capturing hardware rooflines, node and GPU
topology, interconnect fabric, software versions, model dimensions, and
parallel layout; the Observation, recording complete knob
configurations, step time, peak device memory, numerical verification
conditions, and 16-invariant verdicts alongside explicit out-of-memory
shortfalls and minimal conflict tuples; and the Effect, storing paired
log-speedup, calibrated noise floor, conditioning dependencies, and
physical mechanism class (kernel versus balance). A two-tier normalizer
maps framework-specific flags (such as fused AdamW \[[21](#bib.bib21)\]
or mixed-precision switches) across stacks into 71 canonical mechanisms.

To transfer priors safely across clusters, InfraRSI filters and ranks
each source record against the target environment using a compatibility
scope check and an environmental distance $`d\geq 0`$. The scope check
requires matching training frameworks for all records and grades an
effect as covered when the model family and sequence-length bucket match
(and, for topology-sensitive balance mechanisms, only when the GPU SKU,
node count, per-node GPU count, multi-node interconnect fabric,
parameter-scale bucket, and parallel layout also match), downgrading
partial matches to partial and discarding incompatible records. Eligible
records are then ordered lexicographically by coverage level (covered
before partial), readability, evidence tier, and environmental distance
$`d`$, which sums indicator penalties for GPU SKU and node-count
mismatches, log-ratio differences $`|\ln(a/b)|`$ in parameter count and
sequence length, and $`0.25\times`$ reference-state mismatches.
Environmental similarity is used strictly to *filter and rank prior
evidence* (grading target levers into covered, null, partial, and
unobserved states), whereas *actual target observations* govern
posterior estimates during search via Bayesian surrogate updating and
empirical prior revision \[[10](#bib.bib10)\]
(§[4.2](#S4.SS2 "4.2 Prior Calibration, Failure Attribution, and Bundle Completion ‣ 4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
The corpus statistics in Table

### 5.3 Experience Retrieval and Write-Back

#### Where Experience Enters Search.

Within InfraRSI, retrieved experience packs enter the search loop at two
explicit points: they directly drive the first start of the three-start
initialization

retrieval excludes prior runs from the same workload and GPU SKU so that
warm starts reflect cross-hardware priors rather than self-replay.

At the end of a tuning run, observations that pass all verification

into a new experience pack and written back to the bank. In our
controlled transfer evaluation on Qwen3.5-9B (8$`\times`$H100)

experts). Overall, InfraRSI lifts mean MFU from $`17.4\%`$ to
$`30.0\%`$, pushing compute-bound dense models above $`43\%`$ MFU and
substantially improving utilization on routing- and communication-bound
MoE workloads by jointly eliminating redundant activation recomputation,
kernel launch overhead, and collective communication bottlenecks.

#### (1) Proposal Models.

While the classical Gödel Machine \[[34](#bib.bib34)\] formulated
self-referential modification via formal proof search, recent
code-evolution and agent frameworks (including FunSearch
\[[33](#bib.bib33)\], AlphaEvolve \[[25](#bib.bib25)\], Darwin Gödel
Machine \[[45](#bib.bib45)\], AIDE \[[14](#bib.bib14)\], METR RE-Bench
\[[41](#bib.bib41)\], and autoresearch \[[15](#bib.bib15)\]) rely on the
zero-shot coding priors of frontier LLMs to propose edits. In
distributed LLM training, however, zero-shot speed predictions correlate
poorly with measured hardware throughput and frequently veto high-gain
optimizations
(§[2](#S2 "2 Problem Definition and Empirical Motivation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).
InfraRSI decouples candidate generation from zero-shot model priors
through empirical Bayes prior calibration \[[10](#bib.bib10)\],
contrarian probing, and failure-driven prior revision.

#### (2) Search Controllers.

Existing controllers split into static parallelism planners, fixed
configuration-knob tuners, and single-incumbent free-form code-editing
loops. Across distributed training stacks such as Megatron-LM
\[[36](#bib.bib36), [24](#bib.bib24)\], DeepSpeed \[[30](#bib.bib30),
[29](#bib.bib29)\], PyTorch FSDP \[[46](#bib.bib46)\], and TorchTitan
\[[18](#bib.bib18)\], automatic parallelism planners like Alpa
\[[47](#bib.bib47)\], Galvatron \[[22](#bib.bib22)\], and nnScaler
\[[20](#bib.bib20)\] synthesize distributed execution plans over static
computation graphs, whereas Bayesian optimization \[[38](#bib.bib38)\],
tuning platforms such as Ray Tune \[[19](#bib.bib19)\], and multi-agent
tuners like OptiCo \[[3](#bib.bib3)\] search predefined launch flags;
none of them synthesizes source-level operator patches. Conversely,
free-form coding agents such as autoresearch \[[15](#bib.bib15)\],
RE-Bench agent scaffolds \[[41](#bib.bib41)\], and ResearchBoost-Agent
\[[32](#bib.bib32)\] edit source files directly, but step greedily from
the latest incumbent without a global memory model or combinatorial
failure recovery, often stalling when individual edits trigger
out-of-memory errors or compiler conflicts. InfraRSI coordinates launch
knobs and source patches through multi-point initialization, a global
step-time model paired with a censored memory model
\[[40](#bib.bib40)\], bundle completion, plateau escape, and bounded
context compression
(§[4](#S4 "4 Budgeted Compositional Search ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure");
evaluated under identical contracts in
§[6.1](#S6.SS1 "6.1 End-to-End Speedup and MFU Across LLM and MoE Workloads ‣ 6 Experimental Evaluation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"),

[4](#S6.T4 "Table 4 ‣ 6.1 End-to-End Speedup and MFU Across LLM and MoE Workloads ‣ 6 Experimental Evaluation ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")).

#### (3) Execution and Verification Interfaces.

Kernel compilers, hand-optimized kernel libraries, and kernel-synthesis
benchmarks, including TVM \[[4](#bib.bib4)\], Triton
\[[39](#bib.bib39)\], PyTorch 2 Inductor \[[2](#bib.bib2)\],
FlashAttention-2/3 \[[6](#bib.bib6), [35](#bib.bib35)\], FlexAttention
\[[8](#bib.bib8)\], Liger Kernel \[[13](#bib.bib13)\], FP8 primitives
\[[23](#bib.bib23)\], KernelBench \[[26](#bib.bib26)\], and AI CUDA
Engineer \[[16](#bib.bib16)\], optimize isolated operators against
unit-test shapes, whereas open-code training agents typically judge full
scripts by reading self-reported stdout timers that are vulnerable to
reward gaming \[[37](#bib.bib37), [17](#bib.bib17)\]. InfraRSI treats
compilers and custom kernels as composable primitives within its staged
verification harness
(§[3.4](#S3.SS4 "3.4 Promotion and Delivered Speedups ‣ 3 System Architecture: The InfraRSI Harness ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure")),
combining the 16-item receipt verifier, source-code audits, and
noise-calibrated promotion gates.

#### (4) Experience Memory.

While online agent-serving platforms such as Reef \[[31](#bib.bib31)\]
continually update deployed agents from inference feedback, most
training-time hyperparameter tuners and coding agents either start from
scratch on each cluster, rely on static hand-written skill cards
\[[32](#bib.bib32)\], or append raw execution transcripts until context
windows saturate. InfraRSI records reusable infrastructure findings as
structured experience packs
(§[5](#S5 "5 Empirical RSI Loop: Experience Protocol and Cross-Hardware Transfer ‣ InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure"))
that normalize hardware rooflines, parallel topologies, verified
log-speedups, numerical tolerances, and failure constraints across
canonical optimization mechanisms. Harvested packs from external
hardware SKUs warm-start initialization and seed time and memory priors
while excluding same-task, same-SKU runs

## 8 Conclusion

In this paper, we propose the InfraRSI Harness, a harness that turns
language-model proposals into verified distributed training
optimizations by combining five-stage contract verification,
history-aware compositional search over launch knobs and source patches,
and cross-hardware experience transfer. Across single- and multi-node
dense and Mixture-of-Experts training workloads, InfraRSI consistently
improves end-to-end throughput and hardware utilization over existing
configuration tuners and coding agents while preventing reward hacking.
````
