# SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency

Guan Zheng Huang Affiliation: Railtown AI
Email: [guan@railtown.ai](mailto:)

November 5, 2026

###### Abstract

Methods that repair tool documentation automatically are mostly
evaluated on task accuracy. We report a benchmark that scores them on
cost. Spring-5 is 20 tool families and 344 tasks, each with a
deliberately degraded specification, a hand-written honest one, a
deterministic backend and an answer key, scored on calls charged against
the ideal call path. A wrong answer is charged the full call budget, so
this cost index largely tracks the completion rate, and we report calls
per correct task beside it, which carries no such charge. Over 2,644
baseline sessions, 54% of wrong answers arrive with no rejected call, no
refusal and no retry. The benchmark carries three validity instruments.
A build-time ceiling assertion requires the honest specification to
reach the ideal path and fails systematically on only one family. A dud
rule names the families a stronger model solves cold and catches four. A
directly measured noise floor shows that two evaluations of a
byte-identical specification differ by a 95% factor of 0.64 to 1.56, so
about one comparison in eight crosses a conventional win threshold on
noise alone, and the cheap way of estimating that floor is biased by
which families happen to go unedited. Against these instruments, a
schema-only method closes 1% of the baseline-to-ideal cost gap, an
online self-evolution loop 13%, one batch rewrite over every training
transcript 33%, and a variant given correctness labels 58%. The batch
advantage over the loop is the evidence it reads: held to the loop’s
exposure it is no longer detectable. With five and ten tools in context
the effect survives, the baseline cost does not change, and only
machine-written descriptions sent calls to the wrong tool. On BFCL, 62%
of held-out queries are already answered from the shipped documentation,
which explains a pooled null there. Code, data and runs are released.

## 1 Introduction

A tool specification is the text an agent reads before it calls a
function: what the tool does, what each parameter means, which values
are legal, what the result represents. It is written once, by a human,
usually when the endpoint is built, and then never updated from evidence
even though the agent produces a transcript of every confusion it ever
has.

A growing literature repairs it automatically ([Qu et al.,
2025](#bib.bib1); [Yuan et al., 2025](#bib.bib2); [Fang et al.,
2025](#bib.bib3); [Lu et al., 2026](#bib.bib5)). That work is evaluated
mostly on task success. We argue this is the wrong axis, and the reason
is visible in the failure mode. When documentation is unclear an agent
does not usually fail outright. It makes three calls where one would do
and then answers correctly, or it makes one clean call, receives a
well-formed number that means something other than what was asked, and
reports it with no error anywhere in the transcript. The first costs
money on every request forever and is invisible to an accuracy metric.
The second is scored as a single wrong answer, which understates a
defect that will produce a wrong answer every time it is hit.

Spring-5 measures the first with calls per correct task, and instruments
the second with a per-session census of silent failure. Its headline
cost index charges every wrong answer the full call budget, so on its
own it mostly counts lost completions, and we report it beside both.

#### The measure, in one line.

Every family declares an _ideal call path_: the number of tool calls a
correct solver needs on its held-out tasks. An arm’s cost index is the
calls it was charged divided by that number, so 1 is perfect. The
baselines here sit between 13 and 14, and most of that is the full
budget charged for each wrong answer. Gap closed is the share of the
distance from the baseline’s cost index down to 1 that an arm recovered,
which is the figure quoted throughout.
Section [3.5](#S3.SS5 "3.5 Cost, not accuracy ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
states both formally, together with the charging rule for a task the
agent gets wrong and the third measure, calls per correct task.

#### A benchmark of this kind has a shelf life, and should say so.

The first thing we had to apply to our own dataset is a rule we would
hand any author of another: _a family a stronger model solves from a
cold start is no longer measuring documentation, and must be named
rather than averaged in_. Four of our twenty fail it on the stronger of
the two models we run, while sitting between 4.0 and 18.3 times the
ideal path on the weaker. Documentation defects do not leave production
systems as models improve; they leave our ability to measure them, and a
pooled number that quietly carries four saturated families is diluted by
an amount its reader cannot recover.

_The larger part of this paper is the instrumentation rather than the
dataset._ A benchmark that reports an effect size owes its reader the
resolution behind it, and the three checks of
Section [4](#S4 "4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
are what we built to supply it: what the dataset can reach at best, how
large a difference has to be before it is not noise, and which of its
families have stopped discriminating. The need is not hypothetical. A
recent audit of tool-calling benchmarks ([Bhat et al., 2026](#bib.bib7))
finds evaluators disagreeing with expert reviewers on 18.5% of reviewed
tasks and reports a 57.9–76.8% spread across 23 runs of a single
benchmark, so an improvement of a few points reported without a measured
noise floor is not interpretable. We measure ours, find it wide, and
find that the cheap way of measuring it is biased. _The ceiling
assertion and the noise floor have each changed a conclusion of ours_,
and the dud rule changes how any pooled number should be read, which is
why we recommend all three.

## 2 Related Work

#### Benchmarks for tool use.

BFCL ([Patil et al., 2025](#bib.bib11)), StableToolBench ([Guo et al.,
2024](#bib.bib13)), API-Bank ([Li et al., 2023](#bib.bib14)), WorkBench
([Styles et al., 2024](#bib.bib15)) and $`\tau`$-bench ([Yao et al.,
2025](#bib.bib12)) evaluate whether a model calls the right function
with the right arguments. Documentation is held fixed and treated as
given, although [Hsieh et al. (2023)](#bib.bib10) show that
documentation alone can carry tool use. [Kapoor et al.
(2025)](#bib.bib16) argue that agent evaluations should report cost
beside accuracy, which is the position this benchmark takes for
documentation repair. Trace-Free+ ([Guo et al., 2026](#bib.bib4)) is the
closest to our concern: it categorises interface patterns and reports
that fewer than 12% of real tool documents state parameter constraints
or selection scope, which is the gap our families are built around.

#### Documentation repair.

DRAFT ([Qu et al., 2025](#bib.bib1)), EASYTOOL ([Yuan et al.,
2025](#bib.bib2)) and PLAY2PROMPT ([Fang et al., 2025](#bib.bib3))
rewrite tool descriptions from feedback or self-play; DocsChisel ([Lu et
al., 2026](#bib.bib5)) diagnoses defects from failed execution traces on
queries from WorkBench and API-Bank, with a held-out split, and reports
large gains over the original documentation. Reported gains in this line
shrink as baselines strengthen, and in the comparison of [Guo et al.
(2026)](#bib.bib4) EASYTOOL falls below the original documentation on
single-step StableToolBench, so documentation edits are not safe by
default. All of these are scored on task success.

#### Harness effects.

Harness-Bench ([Yao et al., 2026](#bib.bib6)) measures the system layer
around the model and reports a 23.8-point spread in aggregate score
between harnesses, averaged over eight model backends, while treating
each harness’s tool interface as native rather than as a controlled
factor. It establishes that the layer matters without isolating this
term of it.

#### Benchmark validity.

[Bhat et al. (2026)](#bib.bib7) is the direct motivation for
Section [4](#S4 "4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency").
Our contribution there is narrower and more actionable: three checks
that a benchmark author can run on their own data, and a demonstration
that the cheap way of computing one of them is biased.

## 3 SPRING-5

### 3.1 One family

A family is one tool.
Figure [1](#S3.F1 "Figure 1 ‣ 3.1 One family ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
shows what it contains: a deterministic backend holding the real
convention, a _degraded_ specification carrying exactly one planted
defect, an _honest_ specification that states the rule, an even
train/test split of tasks, and an answer key giving both the expected
value and the ideal number of calls.

Figure 1: One Spring-5 family. Methods start from the degraded
specification and are scored on the held-out tasks. The honest
specification is never given to a method; it exists to assert that the
defect is repairable in principle, and that assertion is checked at
build time.

The parameter set is frozen for every method: names, arity and the
property set cannot change. A proposer that invented a field would
produce a specification that lies about the function signature behind
it, and freezing the set makes every method compete on the same action
space rather than on how much of the interface it is allowed to rewrite.

### 3.2 Selecting the twenty

The twenty were filtered from a hundred candidates on four criteria, and
the first two are the ones that matter.

Rarity. A rule is only worth documenting if a competent engineer would
not guess it. An early candidate planted a mandatory date window and a
both-ends-together pair rule, and the baseline reached the ideal path
anyway, because the model’s prior over API design already encodes those.
Every family was scored on whether the convention is genuinely unusual.

Silence. A confident wrong answer outranks a rejection. A defect that
announces itself through a backend error is repaired by the error
message; a defect that returns a well-formed wrong number is not.
Section [5.1](#S5.SS1 "5.1 Silent failure is a behaviour, not a design property ‣ 5 Results ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
reports how far this intent actually carried.

Separability and spread complete the filter: sixteen families spread
over seven semantic groups (search ranking, time, identity, partial
failure, aggregate statistics, access policy and units) with at most
three per group, the remaining four forming the two matched pairs below,
and no family whose defect could be confused with another’s. The
resulting defect classes are 9 _output semantics_, 5 _cross-parameter
dependency_, 4 _value convention_ and 2 _operational constraint_.

Four of the twenty are two matched pairs, built to isolate mechanisms
rather than to represent a class. regional_index and capability_probe
are identical but for whether the rejection message names a way forward,
which on _luna_ separates a baseline cost index of 25.0$`\times`$ from
11.6$`\times`$. The second pair, aggregate_report and legacy_export,
isolates a refusal made without calling the tool.

### 3.3 Where the defect classes come from

The defects are planted, so the question is whether they are the defects
real documentation has. We did not invent the taxonomy. Two empirical
studies of shipped API documentation supply most of it, and we measure
unplanted instances of the pattern in two third-party benchmarks.

The classes follow two studies of real documentation. [Uddin and
Robillard (2015)](#bib.bib9) surveyed 323 IBM software professionals and
catalogued ten documentation problems, finding that the pressing ones
are about _content_ rather than presentation: incompleteness and
ambiguity together account for 36 problem assignments among 79 example
comments, against 25 for every presentation problem combined. Spring-5
degrades content and never formatting, which is that finding applied.
[Zhong et al. (2020)](#bib.bib8) analysed 5,334 parameters that carry a
rule, across nine libraries and 14,392 source files, and found that
86.2% have the rule only in code, against 10.3% only in documentation
and 3.5% in both. A constraint enforced by the backend and absent from
the text is therefore not an unusual case to construct; it is the
ordinary one. Their category counts map onto ours directly: 18.5% of
rule sentences constrain a parameter’s _format_ (“csvKeyValueDelimiter
must be exactly 1 character”), which is our _value convention_; 5.3%
describe a _relation between parameters_ (“polyLats and polyLons must be
equal length”), which is our _cross-parameter dependency_; and null,
range and legal-value rules account for 69.1%, which is our _operational
constraint_. Our largest class, _output semantics_ at nine families, has
no counterpart in that study, which covers inputs only; we place it with
the content problems of [Uddin and Robillard (2015)](#bib.bib9), which
are not restricted to inputs.

The pattern occurs unplanted in documentation somebody shipped. Two
examples, both measured rather than cited.

_Value convention._ The order-lookup tool in $`\tau`$-bench’s retail
environment ships a description whose author wrote, unprompted, “Be
careful there is a ’#’ symbol at the beginning of the order id.” That is
a maintainer adding exactly the clarification a Spring-5
value-convention defect removes. Deleting that sentence and its example,
and nothing else, takes the family from the ideal call path to
17.4$`\times`$ it. The convention was load-bearing, and the maintainer
knew it.

_A code-only constraint, in its strongest form._ BFCL’s
add_postgres_server is scored against an answer key that requires a
nickname argument, and the published schema does not declare that
parameter at all. The user’s prompt supplies the value in seven of the
eight held-out queries. Neither model we run answers a single one of
them from the shipped schema. This is the 86.2% figure made concrete in
a benchmark built by others, and
Section [7](#S7 "7 Two Third-Party Ports, and What They Cannot Show ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
returns to it, because no method in this paper can repair it: the
parameter set is frozen for every arm, so the call the key wants cannot
be emitted.

What this does and does not establish. It establishes that the defect
classes are drawn from measured properties of real documentation rather
than from our intuition about what would be hard, and that instances of
the pattern survive in third-party artifacts. It does not establish that
our particular twenty are representative in proportion; the class mix
here is chosen for separability and spread, and
Section [3.2](#S3.SS2 "3.2 Selecting the twenty ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
sets out that filter. Effect sizes measured on planted defects remain
effect sizes on planted defects.

### 3.4 How the dataset was built and checked

Every family was written by hand rather than generated. The degraded
text, the honest text, the backend and the answer key were authored per
family, and the defect was chosen from the classes in
Section [3.3](#S3.SS3 "3.3 Where the defect classes come from ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
before the text was written rather than found afterwards.

Three checks ran on top of that. The ceiling assertion of
Section [4.1](#S4.SS1 "4.1 The ceiling assertion ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
is automatic and runs at build time on every family. Every answer key is
recomputed from the backend rather than stored by hand, so a task whose
expected value drifts from its own data fails the build. And every
family, its defect and its honest text were reviewed by two working
engineers besides the dataset’s author, who went through all twenty with
the author to check that each defect is one a competent engineer would
not guess from the interface and that each honest text states the rule
without giving away the task. That review is why the rarity criterion
above is a judgement we are willing to defend: it is not one person’s
intuition about what is hard.

#### Release history.

Three families, event_count, latency_percentile and meter_read, were
expanded from 16 tasks to 24 using parameter combinations the backend
already supported, and every answer recorded before the expansion is
byte-identical afterwards. Five others cannot be expanded without new
backend data that would move recorded answers. Runs made before the
expansion use 320 tasks and three evaluation passes; later runs use the
344 tasks described here and two. Every per-run quantity is computed at
that run’s own pass count, no comparison sets a run on one release
against a run on the other, and the noise estimate of
Section [4.2](#S4.SS2 "4.2 Evaluation noise, and a biased estimator of it ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
pools passes only between evaluations over the same task set.

The complete writer, judge and agent prompts, the schema contract every
method writes through, and the per-family degraded and honest texts are
in the released artifact rather than paraphrased here; the
Reproducibility section at the end says where.

### 3.5 Cost, not accuracy

Write $`s`$ for one evaluation session, $`\mathrm{calls}(s)`$ for the
tool calls it made, $`\mathrm{ok}(s)`$ for whether its final answer was
correct, $`B=25`$ for the call budget, and $`\iota_{f}`$ for family
$`f`$’s declared ideal call path summed over its held-out tasks. Over a
set of families $`F`$ evaluated at $`R`$ passes, an arm $`A`$ is charged

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\mathrm{Charged}(A)\;=\;\sum_{s\in A}\begin{cases}\mathrm{calls}(s)&\mathrm{ok}(s)\\
B&\text{otherwise,}\end{cases}\qquad\mathrm{CostIndex}(A)\;=\;\frac{\mathrm{Charged}(A)}{R\sum_{f\in F}\iota_{f}}.
``` |  | (1) |

Gap closed is the share of the available repair an arm recovered,
against the baseline serving the degraded text and the ideal path as the
floor:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{GapClosed}(A)\;=\;\frac{\mathrm{CostIndex}(\text{baseline})-\mathrm{CostIndex}(A)}{\mathrm{CostIndex}(\text{baseline})-1}.
``` |  | (2) |

Matched cost drops the charging rule entirely. Let $`M`$ be the tasks
every arm in the comparison answered correctly on at least one pass; for
each arm, average its calls over only the passes on which it was right,
then average that over $`M`$:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{Matched}(A)\;=\;\frac{1}{|M|}\sum_{t\in M}\frac{\sum_{s\in A(t),\,\mathrm{ok}(s)}\mathrm{calls}(s)}{|\{s\in A(t):\mathrm{ok}(s)\}|},
``` |  | (3) |

and report it through
Equation [2](#S3.E2 "In 3.5 Cost, not accuracy ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
with $`\mathrm{Matched}`$ in place of $`\mathrm{CostIndex}`$ and the
honest specification’s figure in place of 1.

#### What a wrong answer costs, and why a flat cap.

Equation [1](#S3.E1 "In 3.5 Cost, not accuracy ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
charges the full budget for *any* session that did not end correct,
which includes a session that terminated early with a confident wrong
answer as well as one that exhausted the budget. That is a deliberate
choice, and it makes the index mostly a completion measure, so the
alternatives are worth stating. Charging only the calls actually made
rewards giving up: an arm that abandons an expensive task after two
calls outscores one that solves it in six. Dropping incorrect sessions
conditions the measure on the outcome, which is the selection effect
that makes a method look expensive precisely for finishing the hard
tasks. Charging an unbounded amount is not defined. The budget is a
design choice: it exceeds every correct path in the dataset, and the run
is capped there regardless, so a session is never charged more than it
could have spent. The level of the index scales with it; gap closed
depends on it less, because the same charge enters the baseline and the
arm.

*We do not claim the resulting index is a pure efficiency measure, and
we report the quantity that says how far it is not.* The cap term is
93–97% of every charged total, and the change from baseline in cost
index and in completion rate disagree in sign on none of the twenty
families: *the cost index is largely the completion rate on another
scale*, which is a criticism the reader should be able to make from the
paper rather than against it. This is why matched cost is reported
beside it everywhere and not as an appendix curiosity.
Equation [3](#S3.E3 "In 3.5 Cost, not accuracy ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
contains no cap term and no selection on the outcome, it is the axis on
which an arm is paid only for being cheap on work it actually did, and
Section [5.2](#S5.SS2 "5.2 Five methods ‣ 5 Results ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
shows that the two axes rank the methods differently. A result that
appears on one and not the other is reported as such.

Intervals throughout are a cluster bootstrap over families, since one
specification is served per family and every task in that family is
evaluated against it; resampling tasks would understate the interval by
roughly the family size.

#### Arm names.

Two arms are not methods but the ends of the scale every method is
measured between. baseline serves the degraded specification and never
edits it; optimal serves the hand-written honest specification and
likewise never edits it, so it is the honest text’s own score and the
quantity the ceiling assertion of
Section [4.1](#S4.SS1 "4.1 The ceiling assertion ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
checks. Neither reads a transcript.

The methods are named for what they do with evidence. session-evo is the
online loop, and a *ladder* is that loop run once under each of several
triggers: one session at a time, a writer woken by a trigger, and a
paired trial, in which incumbent and candidate text run on the same
held-back tasks, before anything is served. The trigger decides which
sessions the writer reviews: evidence fires on an error or a retry,
audit on a refusal or a low score from an LLM judge that reads the
session without the answer key, and schedule on every session.
global-observer reads every training transcript and writes once.
labelled-observer is the same with correctness labels and repeated
rounds. easytool rewrites from the declared schema alone and draft
probes the tool and rewrites iteratively; both are reimplementations of
published methods on our write channel, the one contract through which
every method proposes new text. The *writer* is the model call that
proposes that text. A suffix after a slash names the trigger the online
loop ran under, so session-evo/audit is that loop woken by the judge and
session-evo/evidence is the same loop woken by the error-or-retry rule;
a suffix after a hyphen names a variation of a batch arm, so
global-observer-k5 is the batch proposer restricted to five transcripts
per family. *A row naming only a trigger is always the online loop under
that trigger.* The released runs use internal identifiers: self-evo-ab2
is session-evo/evidence (written session-evo where no other trigger is
in play), self-evo-ab2-audit is session-evo/audit, observer is
global-observer, observer-k1, observer-k3 and observer-matched are
global-observer-k1, -k3 and -k5, observer-ab is global-observer-ab, and
toolobserver is labelled-observer.

#### How intervals are written.

Two quantities appear as intervals and they are not the same thing. A
*gap closed* is a share and carries a percent sign on every number, as
in 12.9% \[-2.8%, 32.6%\]. A *contrast* between two arms is a difference
in points and carries pp on the estimate and no percent signs inside the
bracket, as in $`+23.3`$pp \[$`+6.8`$, $`+43.7`$\]. The distinction is
deliberate: a share and a difference of shares are different units.

#### Models.

Two models from OpenAI’s GPT-5.6 family, generally available from 9 July
2026, under a 25-call budget: gpt-5.6-luna at low reasoning effort and
gpt-5.6-sol at medium, referred to throughout as *luna* and *sol*. Both
are called through the OpenAI Responses API with store=False; neither is
fine-tuned, and the dataset was written in September 2026, after both
were released. The API rejects an explicit temperature, so every number
is a draw from the model’s own sampling and single-run figures are
reported with intervals rather than as points.

#### Which ceiling the numbers are against.

Gap closed is computed against each family’s *declared* ideal call path,
the count a correct solver needs. One family, event_count, does not
reach its declared ceiling under *luna*: its honest text advertises a
confirming call the reference solver does not require, so the family
sits at 1.46$`\times`$ the declared ideal in every run with no
unfinished sessions. It is the only family where the declared and the
measured ceiling differ systematically
(Table [1](#S4.T1 "Table 1 ‣ 4.1 The ceiling assertion ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")),
so we report against the declared one throughout.

## 4 Three Instruments for Validity

These are the component of this work we most expect to be reused. Each
answers a question a reader should be able to ask of any benchmark in
this area, and none of the three can be answered from a leaderboard:
what is the best score this dataset admits, how large does a difference
have to be before it is not noise, and which families have stopped
telling methods apart. None is specific to our dataset and all three are
inexpensive to compute.

### 4.1 The ceiling assertion

*The honest specification must reach the declared ideal call path.* If
it does not, the family is not measuring documentation: it is measuring
something the dataset author did not intend, and any method’s failure on
it will be misread as a method failure.

Checked across all six *luna* runs and all four *sol* runs at each run’s
own pass count, six families miss on *luna* and two on *sol*
(Table [1](#S4.T1 "Table 1 ‣ 4.1 The ceiling assertion ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")).
All but one are explained.

#### The instrument has since excluded a dataset.

Before running a replication on Spring-2, an earlier benchmark of ours
that adapts four public APIs, we ran this check, and it failed: with
perfect documentation the agent reached only 343% of the ideal path and
completed 51 of 60 tasks, and an online-loop arm closed 58% of the
baseline-to-ideal distance against the honest specification’s 37%. A
dataset whose declared ceiling is beaten by the methods under test
cannot measure how much of the available repair a method recovered, and
no ladder was run on it. The check cost a baseline and an optimal arm.
*That is the argument for carrying the assertion*: it is inexpensive, it
runs before any claim is made, and it identified an instrument from
which we would otherwise have reported a result.

event_count is a genuine dataset limitation and we disclose it: its
honest text advertises a confirming call the reference solver does not
need, the weaker model makes it about half the time, and the family
therefore cannot reach 100% by construction. Zero unfinished sessions
across six runs of six is the signature of a specification property
rather than a sampling accident.

Every other entry has unfinished sessions, and a 20$`\times`$ violation
from four capped sessions is not a dataset defect but the cost metric’s
known behaviour on a small family. *The instrument is useful precisely
because it separates these two cases*, and a benchmark that reports a
single pass without the unfinished count cannot.

### 4.2 Evaluation noise, and a biased estimator of it

Every contrast in this area is a ratio between two evaluations of a
tool, so how far such a ratio moves when *nothing has changed* decides
what any of them mean. There are two ways to measure it and which one
you can trust depends on something you do not control.

The opportunistic estimator takes every arm that ends a run with a
specification byte-identical to baseline’s: the ratio between their run
totals is pure evaluation noise. It costs nothing, and it is what we
used first.

The direct estimator uses the fact that the degraded specification is
fixed by the dataset, so *every baseline pass ever run is an independent
draw on identical text*. Pooling passes across runs and comparing two
disjoint aggregates the size of a run total gives the same quantity
while conditioning on nothing.

|        | opportunistic       | 188     | 20/20    | 0.625 – 1.339 | 11.7% | 15.4%  |
| *sol*  | direct (180 passes) | 13,122  | 20/20    | 0.712 – 1.405 | 9.2%  | 13.4%  |
|        | opportunistic       | 24      | 11/20    | 0.921 – 1.171 | 0.0%  | 4.2%   |

is close to the direct one where the arms leave every family with a

Table [2](#S4.T2 "Table 2 ‣ 4.2 Evaluation noise, and a biased estimator of it ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
and
Figure [2](#S4.F2 "Figure 2 ‣ 4.2 Evaluation noise, and a biased estimator of it ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
report both estimators at matched aggregation. One comparison in eight
of a byte-identical specification classifies as a win. On *luna*, 11.9%
of same-text comparisons cross the conventional 0.90 threshold and 19.0%
cross 1.05. Any win rate reported against fixed thresholds in this
setting is inflated by about that much and any harm rate by more.

The cheap estimator reports a floor only for the families no arm
happened to edit, and which families those are is decided by the run
rather than by the experimenter. On *luna* all twenty families end some
run unedited and the opportunistic band is close to the direct one. On
*sol* only eleven ever do, and the estimator reports 0.0% of same-spec
comparisons crossing the win threshold against a directly measured 9.2%.
The eleven are not a random eleven: their mean pass-to-pass standard
deviation is 0.026 against 0.134 for the nine that never yield a cell. A
family yields a control cell exactly when no method edited it, a method
edits when something drew its attention, and what draws attention is not
independent of how noisy the family is. *The instrument is conditioned
on the quantity it is measuring, and it fails silently in the direction
that understates variance.*

Our own first analysis used the opportunistic numbers and concluded from
them that the noise floor was a strong property of the model, *sol*’s
band being less than half as wide. Measured directly the bands are
0.642–1.557 and 0.712–1.405, overlapping across most of their range.

Figure 2: Evaluation noise on identical text, by estimator. The

The fix costs nothing. Repeated passes over a fixed specification need
no training, no writer call and no gate, and any harness that stores
per-pass results already has the data. Our recommendation is that a
benchmark in this area report a directly measured noise floor, and that
anyone measuring it opportunistically also report how many families
contributed a control cell, because that number decides whether the
estimate means anything.

### 4.3 The dud rule

The rule stated in
Section [3](#S3 "3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
is that a family a model solves from a cold start has no headroom, so
averaging it into a pooled number dilutes every other family. This
section applies it.
Figure [3](#S4.F3 "Figure 3 ‣ 4.3 The dud rule ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
plots each family’s baseline cost index on the two models.

Figure 3: Baseline cost index per family on both models. Sixteen
families stay above the dud threshold of 1.35$`\times`$ on both, the
closest being account_link at 1.66$`\times`$ on *sol*. Four fall to the

this kind ages.

Four families, effective_access, invoice_total, price_history and
shift_schedule, drop below 1.35$`\times`$ ideal on *sol* while sitting
between 4.0$`\times`$ and 18.3$`\times`$ on *luna*. This is the most
consequential limitation of the instrument. Documentation defects do not
disappear from production systems as models improve; they disappear from
our ability to measure them. Any headline number in this area is
perishable, and a successor dataset will need to be harder rather than
larger. We recommend reporting the dud count alongside any result, and
naming which families it covers.

### 5.1 Silent failure is a behaviour, not a design property

about construction. What the sessions do is a different question and we

### 5.2 Five methods

over every training transcript. labelled-observer is global-observer

the label rather than the method. session-evo is an online loop with a
trigger, a writer and a paired acceptance test.

#### Two arms are not comparable to the others, and we separate them.

The labelled arm carries ground-truth labels. No deployment has those,
so it is not a competing method but a *ceiling*: it prices what a label
is worth, in the role an oracle plays elsewhere in this paper, and its
number should never be quoted alongside the others as though they were
the same kind of thing. global-observer approaches that boundary in a
different way. It retains every training transcript until it writes,
which is a short-lived cache rather than a permanent log, but it is a
stronger data-retention assumption than the online loop makes, and in a
setting where transcripts cannot be retained at all it is simply
unavailable. We report it as a method, with that condition attached.

Four results follow, with labelled-observer read as a ceiling
throughout.

A schema-only method recovers nothing. easytool at 1.0% is the direct
confirmation that a method rewriting from the schema alone cannot state
a convention the schema never contained. draft and the online loop are
indistinguishable from each other and their intervals include zero.

this as a benchmark result rather than a proposed method; its
implications for loop design are outside the scope of this paper.

### 5.3 Is the batch advantage architecture, or just more evidence?

global-observer beats the online loop, and the obvious objection is that
it is not a fair fight. The batch arm reads every training transcript in
one call. The loop’s writer is shown one transcript per review and holds
at most three reviews per family, so over the method run of
Table [4](#S5.T4 "Table 4 ‣ 5.2 Five methods ‣ 5 Results ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
it read 24 transcripts against the batch arm’s 172. If the gap is
exposure rather than architecture, the comparison says nothing about
batch versus online.

We tested it directly with batch arms that read fewer transcripts.
global-observer-k1 reads one per family, about the loop’s total
exposure, and global-observer-k3 reads three, the loop’s per-family
maximum. A second run holds global-observer-k5, at five per family, and
global-observer-ab, the batch proposer with its rewrite put to a paired
trial on tasks held back from the writer.

clear of zero. The paired trial has to hold back 30% of the training
half to have anything disjoint to test on, so it buys an acceptance test
by spending the evidence that made the proposer good. On this dataset
that trade is negative. We report it because a paired trial is easy to
treat as free, and on a batch proposer it is not.

### 5.4 Power

Simulating a family-level test at the between-family spread we measure,
an arm-to-arm difference in cost ratio with standard deviation 0.45
across families, twenty families detect a true difference of 0.10 in
cost ratio 19% of the time and one of 0.20 54% of the time; 80% power
needs about 39 families at 0.20 and 162 at 0.10. We state this because
the field ranks methods at this scale as a matter of course, and because
it explains the shape of
Table [4](#S5.T4 "Table 4 ‣ 5.2 Five methods ‣ 5 Results ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency"):
the contrasts that clear zero are the large ones, and the three arms
clustered between 1% and 13% cannot be separated by this instrument at
this size. A benchmark that cannot separate nearby methods should say so
rather than publish the ordering.

## 6 Catalogue Size

Every number above advertises one tool. Production agents carry many,
and with more tools in context the agent must first find the right one,
so a result measured at one tool does not transfer by assumption. We
re-ran the ladder with the family under test advertised alone, alongside
four others and alongside nine, drawn by rotation through the catalogue,
with every other setting identical and on the current release. The ideal
call path is unchanged by the bundle, so gap closed stays comparable;
what changes is that the agent must first find the tool.

### 6.1 A rewrite can cause misrouting; the shipped and hand-written texts never did

The counter that matters here is calls spent on a tool other than the
one under test.

Across 2,064 baseline and optimal sessions at bundles of five and ten,
there were zero off-target calls. The arms that served a machine-written
specification did not: 10 of 416 calls in one run, 5 of 417 in another,
11 of 388 and 1 of 391 in the third. *Every one of them, in every run,
came from the same family*, and all went to the same neighbour:
regional_index, whose served text drew calls to capability_probe.

That pair is not an accident. regional_index and capability_probe are
the matched pair of
Section [3.2](#S3.SS2 "3.2 Selecting the twenty ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency"),
built to be identical but for their rejection message, and they are
therefore the closest siblings the dataset contains. The mechanism is
visible in the text. The degraded description reads “Search the regional
document index for a region.” The writer replaced it with “Search the
regional document index. The specified region must be entitled for the
current principal; requests for unauthorized regions are rejected by the
backend.” The added clause is accurate and it repairs the defect. It
also introduces entitlement and authorisation vocabulary that was not
there before, and in a catalogue containing a capability-shaped sibling
the agent followed it to the wrong tool.

This is a cost a single-tool benchmark cannot charge. A rewrite is
scored locally, on whether the description now states the rule, and the
paired trial of
Section [5.2](#S5.SS2 "5.2 Five methods ‣ 5 Results ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
compares candidates on the family they belong to. Neither sees a call
that went somewhere else. The effect is small here because our families
were deliberately built to be semantically distant, and it appears only
at the one place where that was relaxed; on a real catalogue, where
near-siblings are the norm rather than a constructed pair,
Section [7](#S7 "7 Two Third-Party Ports, and What They Cannot Show ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")’s
BFCL observation suggests it would be larger. *A tool description is not
a local object, and a documentation-repair method that optimises one
description at a time is optimising an objective that leaves this cost
out.*

## 7 Two Third-Party Ports, and What They Cannot Show

Spring-5 exists because we could not find a public benchmark that both
*executes*, so that calls can be counted, and *leaves documentation
headroom*, so that there is repair to measure. This section reports the
two we ported, because between them they say why that combination is
rare, and because one of them yields a partitioning result we think
anyone evaluating documentation repair should run before quoting a
pooled number. *Neither is a transfer result for this paper’s measure,
and we do not present either as one.*

#### The executing port has no headroom.

A port of $`\tau`$-bench’s retail environment runs under our harness
with the cost index fully computable. With the shipped text the agent
reaches the *ideal call path on seven of seven families*, so the
baseline-to-ideal distance that
Equation [2](#S3.E2 "In 3.5 Cost, not accuracy ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
divides by is zero and no method can be scored. Ablating the spans its
maintainers wrote opens headroom on one family, which is too few to
bootstrap over. The benchmark is not deficient; it is simply
documentation that was written carefully for the model it ships against.

#### The port with headroom does not execute.

BFCL v4 live_multiple is 20 real functions carrying twelve or more
queries each, 637 queries, third-party schemas and a third-party answer
key. Reconstructing a call directly from the key scores 637 of 637, so
our scorer follows the benchmark’s convention. But BFCL scores one
emitted call against a key by structure: nothing executes, there is no
backend, no retry and no call budget, so the cost index cannot be
computed here at all and the comparison necessarily runs on task
accuracy, which cannot see the extra calls a correct answer costs. The
evidence trigger cannot fire either, since with one shot and no
execution there is no error turn and no repeated call for it to read.

*We therefore report BFCL for the two things it can establish*, both of
which are about the instrument rather than about our effect sizes:
whether a benchmark of this sort can be pooled before it is partitioned,
and whether failures on documentation nobody degraded are of the kind we
plant. Readers wanting the cost claim tested off our own dataset will
not find it here, and
Section [8](#S8 "8 Limitations ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
says why we do not have it.

Pooled over every held-out query the result is a null. Against a 59.1%
baseline the audit loop gains $`+3.4`$pp with a 95% interval of
$`[-0.4,+7.4]`$ and a scheduled variant $`+1.9`$ $`[+0.0,+3.9]`$. An
improvement of this size is not negligible on a public leaderboard. It
is, however, barely separable from zero here, and pooling turns out to
be the wrong way to read it.

Running the *stronger* model on the *unmodified* schema partitions the

a capable caller. This is the dud rule of

applied at query level to someone else’s data.

### 7.2 What blocks the hard stratum

We read all 121 held-out queries that neither model answers from the
shipped schema and assigned each a cause, writing every assignment as a
rule so the count reproduces. The 121 are counted over all twenty
families, while the hard stratum of
Table [7](#S7.T7 "Table 7 ‣ 7.1 The benchmark is two populations ‣ 7 Two Third-Party Ports, and What They Cannot Show ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
leaves out the two families carrying an out-of-schema query, which is
why the two figures differ.
Appendix [A](#A1 "Appendix A The BFCL Hard Stratum, Read Query by Query ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
gives the full taxonomy; three figures carry the argument. Routing is
correct on 119 of the 121, so almost none of this is tool selection, and
on 78 of them both models emit a byte-identical call that the key
rejects, which is two independently sampled models agreeing on a reading
of the same text rather than two models guessing. In 72 of the 121,
59.5%, the fix lies in the description of the function under test, which
is the action space every method in this paper is confined to.

One class accounts for 50 of those 72, and it is a class we plant
deliberately. The description tells the caller to pass a sentinel the
declared type will not carry: Music_3_LookupMusic.year is declared
integer and its description reads “Use ’dontcare’ to include songs from
any year”. The advice cannot be followed through a typed function-tool
interface, and omitting the parameter, which the key also accepts in
every such case, is the one action the text never mentions. *That is our
value-convention class occurring unplanted, in a third-party benchmark,
at scale*, and it is the single observation from this transfer that
bears directly on the dataset’s construction. It is also the clearest
case for repairing documentation offline rather than expecting the
caller to cope: the agent gets one shot with no execution and no
feedback, while the contradiction is visible in the schema before any
call is made, since year is declared integer while its own default field
holds the string dontcare.

The remaining 49 are outside what any rewrite here can do: dates the
request never grounds, a key that spells one kind of entity two ways
inside a single family, values the request never states, and the
undeclared parameter of
Section [3.3](#S3.SS3 "3.3 Where the defect classes come from ‣ 3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency").
We record them because *a benchmark’s unreachable fraction is a property
a method’s score should be reported against*, and 40.5% is large enough
to change how a null on the remainder reads.

### 7.3 What we take from the transfer

The honest summary is narrower than either a null or a positive.
*Neither port settles whether this loop transfers*: one has no headroom
to measure against, and on the other 62% of the queries are already
answered from the shipped text while the part that is not supports only
a direction at these counts. We report both because the diagnosis is
reusable and costs one run of a strong model on unmodified
documentation: *any benchmark used to evaluate documentation repair
should be partitioned this way before a pooled number is quoted*. Ours
would fail the same check on four families
(Section [4.3](#S4.SS3 "4.3 The dud rule ‣ 4 Three Instruments for Validity ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")),
which is why the dud rule is stated as an instrument rather than as a
disclosure.

Two further observations from the transfer are worth recording because
Spring-5 cannot see them. An absolute trigger threshold did not port: a
fixed judge-score threshold set on our dataset never fired once here,
because a judge scoring a single call with no tool response sits on a
different part of the scale; a rank-based rule needs no calibration and
does fire. And a tool description is not a local object: BFCL ships
deliberate near-miss siblings, and rewriting one description moved
routing accuracy from 100% to 87.5% on one family, taking task accuracy
down with it even though the new text read better in isolation.
Section [6](#S6 "6 Catalogue Size ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
measures that effect on our own dataset.

## 8 Limitations

- •
  The defects are ours, and the cost claim has never been tested off
  this dataset. Every reported effect size is measured on a dataset
  whose defects we planted, and
  Section [7](#S7 "7 Two Third-Party Ports, and What They Cannot Show ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
  reports the two ports that were meant to fix that and could not:
  $`\tau`$-bench executes but leaves no headroom, BFCL leaves headroom
  but does not execute, so the cost index is computable on one and
  meaningful on neither. *That absence is the reason this dataset
  exists, and it is also the largest open question about it.* The
  instruments, rather than the effect sizes, are the contribution we
  consider best supported.
- •
  Twenty families, low power. A true difference of 0.10 in cost ratio is
  detected 19% of the time
  (Section [5.4](#S5.SS4 "5.4 Power ‣ 5 Results ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")).
  The benchmark does not support separating methods whose true
  difference is small, and no such separation is claimed here.
- •
  Four families are already saturated on the stronger model. The
  instrument ages with the models it is run against, and the families
  whose behaviour is stable across both models are its durable
  component.
- •
  Catalogue realism.
  Section [6](#S6 "6 Catalogue Size ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
  runs the ladder at one, five and ten tools and the effect survives,
  but our families were built to be semantically distant and the one
  constructed near-pair is the only place misrouting appeared. A
  catalogue of genuine near-siblings would stress this harder than we
  can.
- •
  draft and easytool are reimplementations on our channel and action
  space. This supports a controlled comparison of architectures; it does
  not constitute a replication of the originally reported results.
- •
  global-observer assumes the transcripts can be kept. It retains every
  training transcript until it writes, and it reads them all under the
  degraded specification, whereas an online loop discards each
  transcript after its review and edits the text it is also being
  evaluated on.
- •
  Batch observation assumes the tool did not change under it. Spring-5
  serves one version of each tool, so every transcript in an
  global-observer batch was produced against identical behaviour. This
  is the condition a batch method requires, and it is not guaranteed in
  practice: where an endpoint changes mid-window, a batch spanning the
  change mixes two behaviours into one rewrite and cannot tell which
  transcripts describe which, while an online loop at least observes the
  change in order. We verified that no transcript in any arm came from
  the held-out split, so the comparison reported here is sound. *On a
  benchmark with version drift the batch advantage could narrow or
  reverse*, which is the natural next test.

## 9 Conclusion

We built a benchmark for tool-documentation repair scored on cost as
well as accuracy, with calls per correct task beside a cost index that
charges every wrong answer the full budget, and with a census of the
more than half of its failures that produce no error, no refusal and no
retry. The dataset is 20 families and 344 tasks and we release it, but
we expect the three validity instruments to outlast it: a build-time
assertion that the honest specification reaches the ideal path, a dud
rule for families a stronger model solves cold, and a directly measured
noise floor.

The last of those produced the result we least expected. Repeated
evaluations of a byte-identical specification differ by a 95% factor of
0.64 to 1.56, so roughly one comparison in eight crosses a conventional
win threshold on noise alone; and the cheap way of estimating that floor
is biased by its own coverage, reporting zero same-spec wins on one of
our models where the directly measured figure is about one in eleven.
Our own first analysis used the biased version. Anyone reporting a win
rate in this area without a directly measured floor is reporting an
unknown mixture of effect and variance.

## Reproducibility

Dataset, harness, every run directory, the figure-generating scripts and
the JSON file backing every number are released at
[https://github.com/CoronRing/DATE](https://github.com/CoronRing/DATE).

transcribed.

Prompts and contracts are released verbatim, not paraphrased. The agent
system prompt, the writer prompt each method is given, the judge prompt
and trust scale, and the schema contract that fixes what a method may
rewrite are in the harness source at the paths below, so a reader can
check that the methods were held to the same action space rather than
take our word for it.

  arena/agent.py: the agent contract, the answer check, the writer
  contract that freezes the parameter set, and the judge prompt with its
  trust scale.
- •
  arena/methods.py: one function per method, each carrying the
  deviations from its reference implementation in its own docstring.

  arena/spring5/: the twenty families, giving degraded text, honest

### A.1 Why the hard stratum is hard

Of the 121 held-out queries neither model answers from the shipped
schema, routing is correct on 119, so almost none of the failure is tool
selection. On 78 of the 121 both models emit a byte-identical call that
the key rejects, which is two independently sampled models agreeing on a

Classifying each by whether a rewrite could reach it: 111 of the 121 are
in-schema, meaning every parameter the key wants is declared and the
failure is about what the description says about it. Eight are
out-of-schema, and they are the interesting ones. Seven sit in
add_postgres_server, whose answer key requires a nickname argument that
the published schema never declares, while the user’s prompt supplies
the value in seven of eight held-out queries. Neither model answers any
of them. No arm in this paper can: the parameter set is frozen for every
method
(Section [3](#S3 "3 SPRING-5 ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")),
so the call the key wants cannot be emitted at all. That is a
documentation defect of the severest kind occurring in a third-party
benchmark, and it is outside the action space we chose. The eighth sits
in get_service_providers; both families are excluded from the stratified
rows.

and it is worth being precise about what that does and does not mean.*
Across every call either model emitted, a sentinel string appears 721
times in 3,577 string-typed values and zero times in 789 integer, 164
float and 944 boolean ones: the models reach for the sentinel constantly
and the interface refuses it wherever the type forbids it. It does not
follow that the query is unanswerable. Wherever the key names a sentinel
the type forbids it *also* accepts the parameter being absent, and we
checked that a call which simply omits the parameter scores as correct
in every such case. Across the whole held-out split there is no query
without a legal call.

So the defect is not a broken benchmark, and these queries should not be
discarded. It is a description that recommends an action the interface
rejects while never mentioning the one that works, which is a
documentation failure of exactly the kind this paper measures.

Section [7.2](#S7.SS2 "7.2 What blocks the hard stratum ‣ 7 Two Third-Party Ports, and What They Cannot Show ‣ SPRING-5 Measuring Tool Documentation Repair for LLM Agents by Efficiency")
gives the argument this supports. Two details belong here rather than
there. The loop has a correctness signal the caller does not, because a
candidate rewrite is adopted only if it beats the incumbent on held-back
training queries, so a rewrite saying to omit the parameter when the
request names no year is both derivable from the schema alone and
testable before it ships. And the contradiction is why the models fail
consistently rather than randomly: told to pass dontcare into an
integer, they invent a year or send 0 instead of leaving the parameter
out.

A further 20 are an optional parameter supplied unasked. In the
provider-search family, ten queries ask only for a therapist in a named
city. Both models add an insurance_accepted argument set true. The key
lists no such argument, so the call fails on the extra. Nothing in the
description says when to leave a parameter out.

Against that, 49 are outside what any rewrite here can do. Ten are dates
the request never grounds: “find a Music event on March 14th” with no
year anywhere, scored against a 2023 key. Ten more are a key that spells
the same kind of entity two ways inside one family, wanting Vancouver in
one query and Sydney, AU in another, so no single stated convention
satisfies both. Eight want a value the request never states, four want a
value the schema’s own enum excludes, and seven need the parameter that
is not declared.

The arms fix the class we predicted and little else. Of the queries
audit rescued, four of six fall in the sentinel class and schedule three
of seven, against a prior of 41% if rescues were spread evenly. Four in
fifty is also the rate at which the class is repaired, so the reading is
that the defect is real, reachable in principle and mostly missed in
practice. We draw no effect size from counts this small.

### A.3 A correction to our own scorer

An earlier version of this comparison tested an emitted value against
the key by type as well as by value, so an integer 2019 failed a key
entry of "2019" although the schema declares that parameter an integer.
Fifteen calls were scored wrong for obeying the schema. The comparison
now coerces across string, number and boolean spellings, every stored
run was re-scored offline from the recorded calls, and the baseline
moves from 55.1% to 59.1%. We report it because it is the same class of
defect this paper is about, in our own instrument: a convention that one
side of an interface states and the other does not honour.
````
