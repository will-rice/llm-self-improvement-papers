###### Abstract

Building reliable robot capabilities across diverse tasks requires
substantial human effort to develop and maintain skills, design rewards,
and integrate perception with control. We present Reconstruct, Practice,
Go Real (RPG), a framework for autonomous improvement of robot execution
systems without updating model weights. RPG identifies manipulation
capabilities in an offline dataset and constructs related practice tasks
in simulation. During practice, RPG uses execution feedback, privileged
simulator state, and available dataset videos to diagnose failures. It
develops new reusable symbolic skills, refines existing skills, and
revises the system prompt based on these diagnoses. Cross-task
evaluation tests individual candidate changes and merged revisions
before they are retained for reuse. At test time, a multimodal LLM uses
the resulting system prompt and skill library to coordinate perception
and robot control. On held-out initializations of 22 manipulation tasks,
RPG improves task success from 28.6% after the first practice round to
95.0% after 15 rounds, outperforming all evaluated baselines, including
ASPIRE (75.5%) and CaP-Agent0 powered by GPT-6 Astra Pro (60.0%). After
a common calibration and hardware-adaptation procedure, the frozen
system succeeds in all 30 physical trials, with ten trials on each of
three tasks.

## I Introduction

Recent advances in multimodal large language models (MLLMs) have enabled
agents to perceive environments and reason about
tasks \[[1](#bib.bib1)\]. Language-model agents can also generate and
execute code \[[2](#bib.bib2)\] and improve through
feedback \[[3](#bib.bib3)\]. These capabilities offer a way to expand
robot behavior with less task-specific human engineering. In particular,
multimodal coding agents can use visual observations and execution
feedback to construct, refine, and compose executable skills that robots
can retain and reuse across tasks \[[4](#bib.bib4), [5](#bib.bib5),
[6](#bib.bib6)\].

Language-model-based robot control involves a tradeoff between program
execution and online reasoning. _Code-as-Policy_ combines perception and
control primitives into executable programs \[[7](#bib.bib7),
[8](#bib.bib8), [9](#bib.bib9)\]. These programs can execute efficiently
and incorporate feedback loops, but their responses depend on explicit
program logic and perception interfaces. For example, a robust symbolic
check for grasp success can be difficult to specify, while an MLLM can
assess the outcome from images. In _Agent-as-Policy_, the MLLM remains
in the control loop, providing flexible visual and semantic
reasoning \[[1](#bib.bib1), [5](#bib.bib5)\]. However, frequent model
calls can make low-level decisions slow. A scalable system should
combine these strengths by delegating repeatable execution to reusable
code and reserving multimodal reasoning for decisions that benefit from
visual or semantic judgment.

We introduce _Reconstruct, Practice, Go Real_ (RPG), a framework that
develops and refines reusable robot skills through autonomous practice
without updating model weights (Fig. ). RPG improves both the shared
skill library and the system prompt that guides a multimodal agent in
using it. Changes to these shared components persist across episodes and
can benefit other tasks that reuse them.

Given an offline dataset, _Reconstruct_ selects source tasks that expose
useful manipulation capabilities and constructs related practice tasks
in simulation. The resulting practice suite can be expanded by
processing additional tasks from the dataset. A practice task may cover
part of a source task or an analogous manipulation. It need not
reproduce the original trajectory or scene. We use
ABC \[[10](#bib.bib10)\] in this work because it covers 193 diverse
tasks. During _Practice_, RPG compares executions from the Runtime Agent
and the Privileged Agent, which uses the same model and skill library
but additionally receives simulator state. The Video Analyzer uses these
execution records and available dataset videos to diagnose failures. RPG
then develops new reusable symbolic skills, refines existing skills, and
revises the system prompt. It evaluates candidate changes across the
practice tasks and retests merged changes before retaining them.
Finally, _Go Real_ calibrates and freezes the resulting system for
physical deployment, where the Runtime Agent coordinates perception and
control through the shared skill library.

On held-out initializations of 22 manipulation tasks, RPG improves task
success from 28.6% after the first practice round to 95.0% after 15
rounds, outperforming ASPIRE (75.5%) and CaP-Agent0 powered by GPT-6
Astra Pro (60.0%). Through comprehensive ablation experiments, we
demonstrate the benefits of the Privileged Agent, Video Analyzer, and
skill revisions. After a hardware calibration procedure, the frozen RPG
system successfully completes all 30 physical trials, with 10 trials for
each of the three evaluated tasks. These results show that autonomous
practice can develop and refine shared robot skills that support
physical deployment. Our contributions are:

- •
  We introduce RPG, a framework that autonomously selects manipulation
  capabilities from an offline dataset and constructs an expandable
  suite of simulation practice tasks for developing reusable robot
  skills.
- •
  We develop an autonomous practice procedure that uses privileged
  execution and video-based failure diagnosis to revise shared skills
  and the system prompt, validating both individual and merged changes
  across tasks.
- •
  We demonstrate 95.0% success on held-out initializations of 22
  simulated manipulation tasks and 100% success over 30 trials across
  three physical tasks.

## II Related Work

### II-A Robot Programs and Skill Improvement

Code as Policies \[[7](#bib.bib7)\], ProgPrompt \[[8](#bib.bib8)\], and
CaP-X \[[9](#bib.bib9)\] use language models to generate executable
robot programs, while Prompt2Walk \[[11](#bib.bib11)\] generates
low-level locomotion commands. SayCan \[[12](#bib.bib12)\] grounds skill
selection in learned affordances, while VoxPoser \[[13](#bib.bib13)\]
generates 3D value maps for motion planning. Execution feedback also
supports closed-loop reasoning: Inner Monologue \[[14](#bib.bib14)\]
uses success detection and scene descriptions to revise plans, and
REFLECT \[[15](#bib.bib15)\] summarizes multisensory execution records
to explain failures and propose corrections.

Agents can retain execution experience for use beyond the current task.
Voyager \[[16](#bib.bib16)\] accumulates executable skills in Minecraft.
Lifelong Robot Library Learning (LRLL) \[[4](#bib.bib4)\] grows a robot
skill library through simulation exploration and code abstraction with
human guidance. ASPIRE \[[5](#bib.bib5)\] diagnoses failures from
multimodal traces and stores validated strategies as in-context skills.
RATs \[[6](#bib.bib6)\] uses self-directed play to build reusable skills
and failure memories. RHO \[[17](#bib.bib17)\] searches over multi-file
robot policy repositories using execution feedback, paired candidate
tests, and validation. ENPIRE \[[18](#bib.bib18)\] improves robot
policies through autonomous experimentation with physical feedback.
SHAPER \[[19](#bib.bib19)\] evolves reusable skills and a context-code
harness from embodied rollouts without updating model parameters.
HERO \[[20](#bib.bib20)\] autonomously accumulates and consolidates
reusable manipulation behaviors. Outside robotics,
GRASP \[[21](#bib.bib21)\] studies regression-gated updates to
persistent agent skill libraries. RPG combines dataset-guided simulation
practice with failure diagnosis that compares executions from the
Runtime Agent and Privileged Agent, using source videos when available.
It revises shared skill code and the system prompt, then tests both
individual candidates and merged revisions across a fixed practice suite
before retaining them. RPG performs all self-improvement in simulation
and freezes the execution system before physical deployment.

### II-B Offline Data and Simulation Practice

Demo2Code \[[22](#bib.bib22)\] summarizes state-based demonstrations
into task specifications and synthesizes executable code.
Uni-Skill \[[23](#bib.bib23)\] trains a multimodal planner and retrieves
skill-level video examples to implement missing skills. RPG uses videos
and textual descriptions from an offline dataset, here
ABC \[[10](#bib.bib10)\], to identify manipulation capabilities worth
practicing. It constructs related simulation tasks rather than directly
reproducing the source trajectories or their scene geometry. Simulation
can also expand the data and objectives available for robot learning.
MimicGen \[[24](#bib.bib24)\] transforms demonstrations to generate
additional training trajectories, while Re³Sim \[[25](#bib.bib25)\]
reconstructs real scenes to generate simulation data for imitation
learning. Eureka \[[26](#bib.bib26)\] generates reward code for
reinforcement learning. GenSim \[[27](#bib.bib27)\] and
GenSim2 \[[28](#bib.bib28)\] generate simulation tasks and
demonstrations for policy training, with GenSim2 using multimodal
reasoning to construct task solvers. RPG uses simulation to develop and
refine executable skills and the system prompt rather than to train a
neural policy. Model weights, task definitions, and evaluation criteria
remain fixed during practice.

## III Reconstruct, Practice, Go Real

### III-A Agent-as-Policy Setup and Initialization

RPG coordinates six specialized agents across its three stages:
Constructor, Runtime Agent, Privileged Agent, Video Analyzer,
Implementor, and Merger
(Fig. [2](#S1.F2 "Fig. 2 ‣ I Introduction ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")).
It first constructs simulation practice tasks from an offline dataset,
improves a shared robot execution system by practicing these tasks, and
ultimately deploys the resulting system on a physical robot. We
formulate the execution system as _Agent-as-Policy_: a multimodal agent
(the Runtime Agent) follows a system prompt to complete each task by
selecting and composing reusable skills from a shared skill library. The
skills provide generalizable primitives for perception and robot
control, and are constructed and refined through the Reconstruct and
Practice stages described below.

Let $`\mathcal{D}`$ denote the offline dataset. It contains source
tasks, each represented by trajectories with videos and textual
descriptions. In our experiments, $`\mathcal{D}`$ is instantiated with
ABC \[[10](#bib.bib10)\]. Let
$`\mathcal{W}=\{\mathcal{T}_{i}\}_{i=1}^{K}`$ denote the collection of
practice tasks. Each practice task specifies a simulation scene, a goal,
an initial-state distribution, and a binary evaluator $`e_{i}(\tau)`$
that checks completion from an episode trajectory $`\tau`$. Task
specifications remain fixed during practice, while object configurations
vary between episodes according to the specified distribution. The
execution system used in round $`r`$ is
$`S_{r}=(\mathcal{L}_{r},\rho_{r})`$, where $`\mathcal{L}_{r}`$ is the
shared skill library and $`\rho_{r}`$ is the system prompt that
instructs the agent how to use these skills to complete tasks. A skill
takes arguments such as the selected arm and target position, executes
an action sequence, and returns its exit status and measured effects.
The execution system remains fixed within each episode, while the
underlying model weights and agent harness remain unchanged throughout
Practice.

We initialize a base library $`\mathcal{L}_{\mathrm{base}}`$ with nine
low-level tools from CaP-X \[[9](#bib.bib9)\] for state queries,
perception, inverse kinematics, motion, and gripper control. During
Reconstruct, the Constructor examines trajectories from $`\mathcal{D}`$
and builds six higher-level manipulation skills from these tools: pick,
place, pick-and-place, table-supported transfer between arms,
move-above, and push. The resulting initial practice library
$`\mathcal{L}_{0}`$ contains 15 tools and skills. Together with the
initial system prompt $`\rho_{0}`$, this defines
$`S_{0}=(\mathcal{L}_{0},\rho_{0})`$, from which all diagnostic
ablations begin.

### III-B Reconstruct: Build and Freeze the Practice Tasks

The Constructor first selects source tasks from $`\mathcal{D}`$ to cover
useful and diverse manipulation capabilities. For each selected source
task, it chooses 3–8 trajectories and reviews their videos and textual
descriptions. It identifies the manipulation capabilities represented by
the source task and proposes a simulation task for practicing them. We
give the agent a 7.5-minute budget per source task.

The Constructor builds a MuJoCo \[[29](#bib.bib29)\] simulation
environment with the YAM robot model, using available assets and
searching online for additional assets as needed. The practice task may
cover part of the source task or an analogous manipulation, rather than
reproduce the source task or its exact scene geometry. For example,
organizing sunglasses becomes closing a case that starts open and loaded
(Table [I](#S3.T1 "TABLE I ‣ III-B Reconstruct: Build and Freeze the Practice Tasks ‣ III Reconstruct, Practice, Go Real ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")).
Tasks without a corresponding source task in $`\mathcal{D}`$ use
available task specifications.

The Constructor writes a check*success function for each task to
implement $`e*{i}(\tau)`$. Humans check whether it measures the proposed
objective before practice begins. Because the offline dataset contains
many more source tasks than those instantiated in a single practice run,
Reconstruct can continue expanding $`\mathcal{W}`$ by selecting and
processing additional source tasks. We fix the resulting task collection
before Practice begins so that task definitions and evaluators do not
change during self-improvement.

| Organize sunglasses          | Close the case; opening and loading are encoded in the initial state.  |
| Organize makeup              | Close the drawer; preceding manipulation is already satisfied.         |
| Roll towels                  | Fold once; a cloth manipulation analogue with a different final shape. |

### III-C Practice: Improve the System from Execution

Execute tasks. At the start of round $`r`$, the Runtime Agent attempts
to solve each task five times with $`S_{r}`$. It selects skills and
arguments based only on observations available on the deployed robot and
its execution history. In parallel, the Privileged Agent runs separate
episodes from the same initial states using the same model and skill
library. The only difference is that the Privileged Agent also receives
simulator state for selecting skills and arguments: object names, poses,
sizes, velocities, and cloth-corner positions. Both agents invoke the
same skills, which use only sensing and control available on the
deployed robot.

Asymmetric actor-critic learning uses full simulator state to train a
critic while restricting the actor to images \[[30](#bib.bib30)\]. RPG
instead uses privileged state in a separate execution to support failure
diagnosis. With privileged state information, the Privileged Agent may
complete some tasks more reliably than the Runtime Agent using the
current skills. Its successful executions can guide improvements to the
Runtime Agent, while failures shared by both agents can expose defects
in the shared skills.

Analyze failures. On development tasks, which provide task-specific
improvement feedback, the Video Analyzer compares failed Runtime Agent
executions with Privileged Agent executions and related source videos
from $`\mathcal{D}`$ when available. It receives sampled frames, skill
calls and return values, perception results, commanded and measured
robot states, simulator ground truth, and evaluator metrics. It uses
skill calls, gripper events, motion, and annotations from
$`\mathcal{D}`$ to identify manipulation phases, then compares phases
involving the same object role, arm, and operation.

The Video Analyzer identifies the first observed failure and recommends
a concrete change, supporting its diagnosis with frames or traces and
describing the expected physical effect of the change. It does not
modify the execution system. Its diagnosis and recommendation are passed
to the Implementor for revision.

Revise the system. The Implementor receives $`S_{r}`$, the execution
records, and the Video Analyzer’s recommendations. It proposes new
skills, changes to existing skills, and revisions to the system prompt.
For each development task with fewer than five successful Runtime Agent
trials, the Implementor can produce at most one candidate revision. All
candidates branch independently from $`S_{r}`$. Before testing, we check
that each candidate loads, has valid syntax and interfaces, and uses
only observations available at deployment. Validation and
feedback-held-out tasks do not generate task-specific candidate
revisions, but remain part of cross-task validation as regression
checks.

### III-D Validate and Retain System Revisions

A shared-system revision can help one task but hurt another. We
therefore evaluate each candidate using complete Runtime Agent episodes
across $`\mathcal{W}`$, then merge selected revisions and evaluate the
resulting system again.

Test candidates. We compare each candidate $`\widetilde{S}`$ with
$`S_{r}`$ using the Runtime Agent on the same five fixed development
seeds per task. In the reported run, this gives $`22\times 5=110`$
episodes per system. A candidate passes if mean task success increases
and no task loses more than one success out of five. For $`n=5`$, the
observed success rate on task $`i`$ and the mean across tasks are

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\widehat{q}_{i}(S)=\frac{1}{n}\sum_{k=1}^{n}e_{i}(\tau_{ik}(S)),\qquad\widehat{J}(S)=\frac{1}{K}\sum_{i=1}^{K}\widehat{q}_{i}(S).
``` |  | (1) |

Here $`\tau_{ik}(S)`$ is the $`k`$-th Runtime Agent trajectory on task
$`i`$ with execution system $`S`$. Let
$`\Delta\widehat{J}=\widehat{J}(\widetilde{S})-\widehat{J}(S_{r})`$ and
$`\Delta\widehat{q}_{i}=\widehat{q}_{i}(\widetilde{S})-\widehat{q}_{i}(S_{r})`$.
The test is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathsf{Gate}(\widetilde{S};S_{r})=\mathbf{1}\!\left[\Delta\widehat{J}>0\ \land\ \min_{i}\Delta\widehat{q}_{i}\geq-0.20\right].
``` |  | (2) |

A candidate that passes is eligible for merging, but may still be
rejected later based on the execution records.

Merge and retest. The Merger selects eligible revisions and merges them
into $`S^{+}`$. Because edits can conflict, we evaluate $`S^{+}`$ with
the Runtime Agent and apply the same test against $`S_{r}`$. If the
merged system passes and the Merger chooses to retain it,
$`S_{r+1}=S^{+}`$. Otherwise, $`S_{r+1}=S_{r}`$.
Figure [3](#S2.F3 "Fig. 3 ‣ II-B Offline Data and Simulation Practice ‣ II Related Work ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")
illustrates this procedure on Place Bottles in Bin, from failure
diagnosis and skill revision through cross-task validation, merging, and
retention.

We run 15 practice rounds with autonomous revision, validation, merging,
and retention. Humans handle setup, evaluator checks, the decision to
stop practice, and hardware adaptation. After practice ends, we evaluate
the saved round-end systems on separate held-out seeds
(Sec. [IV](#S4 "IV Evaluation ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")).

### III-E Go Real: Adapt and Freeze for Deployment

The final RPG system and CaP-Agent0 are adapted to the physical YAM
robot before evaluation. Both receive the same coordinate calibration
and hardware adaptation, including pad offsets and the empty-gripper
aperture. We do not apply any object- or task-specific tuning. We use
low reasoning effort for all physical evaluations to reduce inference
cost and latency. Beyond these adaptations, we make no behavioral code
changes based on physical feedback. The adapted systems remain fixed
during evaluation. The Privileged Agent and Video Analyzer are not used
during physical deployment.

## IV Evaluation

We organize the evaluation around four questions: Q1, how does task
success change with practice, and how does RPG compare with existing
agents? Q2, how do the diagnostic inputs affect improvement? Q3, can
library changes improve task completion with the surrounding runtime
fixed? Q4, does the resulting system complete physical tasks after
common adaptation?

### IV-A Tasks and Evaluation Protocol

The simulated YAM robot has two 6-DoF arms and two grippers, and
receives RGB-D observations. It accepts 14-dimensional commands
specifying absolute joint-position targets. The practice collection
contains seven CaP-X tasks and fifteen ABC-derived or analogous tasks,
covering transport, sorting, stacking, extraction, insertion,
articulated closing, bimanual manipulation, and cloth folding.

Task specifications identify which bodies are randomized. Default planar
displacement and yaw bounds are $`\pm 3`$ cm and $`\pm 0.5`$ rad for
rigid bodies and $`\pm 4`$ cm and $`\pm 0.3`$ rad for cloth.
Perturbations also include table height ($`\pm 8`$ mm), camera
translation ($`\pm 4`$ mm), camera rotation ($`\pm 0.008`$ rad), and
depth noise and bias. Case and drawer fixtures stay fixed. Development
and evaluation sample the same fixed task distributions, with paired
initializations across methods.

Separate development and evaluation. Practice uses five fixed
development seeds per task for candidate and integration checks. After
the 15-round practice run is complete and its saved systems are frozen,
we retrospectively evaluate each round-end system on the same ten
held-out seeds per task, giving 220 episodes per point in
Fig. [4](#S3.F4 "Fig. 4 ‣ III-E Go Real: Adapt and Freeze for Deployment ‣ III Reconstruct, Practice, Go Real ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents").
These seeds are excluded from improvement and checkpoint selection. The
frozen baselines in
Table [II](#S4.T2 "TABLE II ‣ IV-A Tasks and Evaluation Protocol ‣ IV Evaluation ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")
use the same evaluation initializations. Because each task has the same
number of evaluation episodes, mean task success rate equals pooled
episode success rate.

Success criteria and evaluation budget. Each task is evaluated using its
predefined success condition. Most conditions directly check whether the
target object reaches its specified goal state. Bottle placement
succeeds only when both target bottles are placed correctly among the
distractors. Towel folding succeeds when the final footprint is 42–58%
of its initial area, corresponding corners are within 5 cm, the moved
layer is at least 3 mm above the target corners, and the maximum
thickness is below 5 cm. Each episode has a 20-minute robot-time limit,
in addition to the model-interaction and wall-time limits specified
below.

observation calls, and 1,200 s of wall time.

Self-improvement models. RPG uses Fable 5.1 for offline code revision

to the shared execution system between episodes, while Gemini 3.8 Flash
generates task-level programs during online execution.

Task completion. As shown in

Among the four models evaluated with CaP-Agent0, GPT-6 Astra Pro
performs best with 132/220 successes (60.0%), below RPG’s performance

the remaining three. The improvement spans both task groups: success
increases from 51.4% to 98.6% on CaP-X tasks and from 47.3% to 93.3% on
ABC-derived or analogous tasks.

RPG succeeds in all ten trials on 17 of the 22 tasks. Compared with
ASPIRE, its largest gains come from fixture insertion and bottle
placement, which together account for 15 of its 43 additional successes.
ASPIRE succeeds in one more trial than RPG on serving and standard cube
sorting. Seven of RPG’s 11 failures occur in towel folding, making
deformable manipulation the main remaining failure mode in this
evaluation.

Improvement across rounds. RPG increases from 63/220 successes after
round 1 (28.6%) to 209/220 after round 15 (95.0%). Round 4 exceeds all
four CaP-Agent0 configurations and round 5 reaches 78.2%, exceeding
ASPIRE’s 75.5% endpoint
(Fig. [4](#S3.F4 "Fig. 4 ‣ III-E Go Real: Adapt and Freeze for Deployment ‣ III Reconstruct, Practice, Go Real ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")A).

What changes in the system? Over 15 practice rounds, the skill library
grows from 15 to 38 entries, with 23 new skills and 66 modifications to
existing skills
(Fig. [4](#S3.F4 "Fig. 4 ‣ III-E Go Real: Adapt and Freeze for Deployment ‣ III Reconstruct, Practice, Go Real ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")B).
The system prompt is revised during the first four rounds. The largest
improvement occurs between rounds 3 and 4, when success increases from
43.2% to 73.6%. This round changes the system prompt but records no
skill edit. The new prompt introduces a bounded perception–action loop
and tracks the remaining interaction budget, encouraging the agent to
act on its current estimates instead of repeatedly requesting
observations. Because the same prompt revision also changes how the
agent uses its observation budget, the 30.5-percentage-point gain
reflects the combined behavioral effect of the prompt update rather than
any single instruction.

After the system prompt is fixed, success rises by another 21.4
percentage points between rounds 4 and 15. During this period, the
system makes 60 modifications to existing skills. In rounds 9, 11, 14,
and 15, it modifies existing skills without adding new ones. RPG
therefore improves both by expanding the library and by repairing shared
skill implementations.

The evaluation curve is not strictly monotonic: the number of successes
decreases by one at rounds 6 and 14. These revisions passed the
five-seed development checks but did not improve every result on the ten
held-out evaluation seeds.

### IV-E Q4: Does RPG Transfer to a Physical Robot?

Protocol. We evaluate three physical tasks on a YAM robot: placing a
ball in a drawer and closing it, folding a towel, and transferring a
bowl between hands
(Fig. [5](#S4.F5 "Fig. 5 ‣ IV-C Q2: Which Diagnostic Inputs Drive Improvement? ‣ IV Evaluation ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents")).
Each method receives ten trials per task. We compare the final RPG
system, using Gemini 3.8 Flash, with CaP-Agent0 using either Gemini 3.8
Flash or GPT-6 Astra Pro. All methods use the same calibration and
hardware-adaptation procedure, including a single uniform grasp offset
without object- or task-specific tuning. Each trial uses low reasoning
effort and terminates after 30 VLM calls or 20 minutes, whichever comes
first.

Object positions are randomized, and the same initial arrangements are
manually reproduced across methods. The ball begins outside an open
drawer, the towel lies unfolded on the table, and the bowl starts on the
left side of the workspace. The robot may autonomously retry or recover
within a trial, but no human assistance, manual reset, or system
revision is allowed. We measure both intermediate-stage and
complete-task success within the same trials.

Success criteria. For ball placement and drawer closure, the
intermediate stage succeeds when the ball is placed inside the open
drawer. The complete task succeeds when the ball remains inside after
the drawer is fully closed. Towel folding succeeds when the estimated
final-to-initial footprint ratio is between 0.40 and 0.60 and the folded
towel has approximately parallel sides. For bowl transfer, the
intermediate stage succeeds when the left hand lifts the bowl and moves
it to the center of the workspace. The complete task succeeds when the
right hand alone holds the bowl off the table for at least three seconds
after the left hand releases it. Intermediate support from the table is
allowed. The physical folding criterion is defined independently of the
simulation criterion and is not intended to match its difficulty
exactly.

## V Conclusion

RPG diagnoses failures using privileged execution and validates
revisions across tasks to improve a persistent robot execution system
without updating model weights. Success rises from 28.6% after the first
practice round to 95.0% after 15 rounds on held-out initializations of
22 tasks, outperforming ASPIRE (75.5%) and CaP-Agent0 with GPT-6 Astra
Pro (60.0%). Ablations support combining the Video Analyzer and
Privileged Agent, while a library-only comparison isolates gains from
skill revisions and highlights the importance of task-level validation.
Following the same calibration and hardware-adaptation procedure as the
baselines, the frozen system succeeds in all 30 trials across three
physical tasks. These results show that shared skill code and the system
prompt can serve as practical targets for persistent robot improvement.

Discussion and Limitations. Two bottlenecks limit self-improvement. Each
round collects Runtime Agent and Privileged Agent trajectories across
all 22 tasks, but API rate limits constrain parallel rollouts. As the
task set grows, overlapping revisions to shared skills and dependencies
can also complicate integration. Future work could improve efficiency
through quota-aware rollout scheduling and dependency-aware proposal
integration.

### -A Self-Improvement Protocol

RPG improves a persistent execution system over successive practice
rounds. We denote the system used in Round $`r`$ as
$`S_{r}=(\mathcal{L}_{r},\rho_{r})`$, where $`\mathcal{L}_{r}`$ is the
shared skill library and $`\rho_{r}`$ is the system prompt. Model
weights, task definitions, initial-state distributions, and evaluation
criteria remain fixed throughout Practice. The execution system is also
fixed within an episode and can only be revised between rounds.

#### Practice rollouts.

At the beginning of each round, the Runtime Agent attempts every
practice task on five fixed development initializations. It selects and
composes reusable skills using only observations available at deployment
time and its execution history. In parallel, a Privileged Agent runs
separate episodes from matched initial states using the same runtime
model and the same shared skill library. The Privileged Agent differs
only in its access to simulator state, including object identities,
poses, sizes, velocities, and cloth-corner positions. Both agents invoke
the same deployment-compatible skills. The skills themselves do not
receive privileged state.

#### Failure diagnosis.

Failed executions on development tasks are analyzed by a Video Analyzer.
The analyzer compares executions from the Runtime Agent and Privileged
Agent and, when available, related source videos from the offline
dataset. Its inputs include sampled frames, skill calls and return
values, perception outputs, commanded and measured robot states,
simulator ground truth, and evaluator metrics. It identifies the first
observable failure, attributes a likely cause, and proposes a concrete
correction supported by execution evidence. The analyzer does not
directly modify the execution system. Its diagnosis is passed to the
Implementor.

#### Candidate generation.

The Implementor can revise shared skill implementations and the system
prompt. A development task can generate a candidate only when the
Runtime Agent succeeds on fewer than all five development trials, and at
most one candidate is generated for that task in a round. Validation and
feedback-held-out tasks do not generate task-specific candidate
revisions, but remain in cross-task validation as regression checks.
Development tasks already achieving $`5/5`$ do not generate new
candidates, but remain part of cross-task validation and can therefore
detect regressions in shared components.

#### Cross-task candidate validation.

Because a revision to a shared skill may improve one task while
degrading others, candidates are evaluated on complete Runtime Agent
episodes across the entire 22-task practice suite. The candidate and the
round-start reference system are evaluated on the same five fixed
development initializations for every task, giving $`22\times 5=110`$
episodes per system.

Let $`\hat{q}_{i}(S)`$ denote empirical success on task $`i`$ and let
$`\hat{J}(S)`$ denote mean task success:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\hat{q}_{i}(S)=\frac{1}{5}\sum_{k=1}^{5}e_{i}(\tau_{ik}(S)),\qquad\hat{J}(S)=\frac{1}{K}\sum_{i=1}^{K}\hat{q}_{i}(S),
``` |  | (3) |

where $`K=22`$ and $`e_{i}`$ is the predefined binary task evaluator.
For a candidate $`\tilde{S}`$, define

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\Delta\hat{J}=\hat{J}(\tilde{S})-\hat{J}(S_{r}),\qquad\Delta\hat{q}_{i}=\hat{q}_{i}(\tilde{S})-\hat{q}_{i}(S_{r}).
``` |  | (4) |

A candidate is eligible for integration only if

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\Delta\hat{J}>0\qquad\text{and}\qquad\min_{i}\Delta\hat{q}_{i}\geq-0.20.
``` |  | (5) |

Thus, a candidate must improve mean task completion without reducing any
task’s success count by more than one out of five.

#### Greedy integration of candidate revisions.

Multiple candidates may satisfy the cross-task gate in the same round.
Eligible candidates are ranked by their increase in mean development
success, $`\Delta\hat{J}`$, with deterministic tie breaking. The
highest-ranked candidate initializes the current integrated system. RPG
then considers the remaining eligible candidates in order and greedily
attempts to incorporate them one at a time. The final implementation
permits at most eight such integration attempts in a round; candidates
beyond this budget are not attempted.

Integration is performed only over files modified by the candidate. A
file modified only by the new candidate can be adopted directly. When
both the current integrated system and the new candidate modify the same
file, RPG first performs a three-way merge relative to their common
parent. If the conflict cannot be resolved mechanically, a coding agent
resolves the remaining file-level conflict. The merger is instructed to
preserve compatible additions from both revisions, including newly
introduced reusable skills and their interfaces, while avoiding
unrelated changes, privileged simulator dependencies, or task-specific
hard-coding. Skill-registration metadata is updated only when the
corresponding executable implementation is present.

#### Merged-system validation and retention.

Candidate-level success does not guarantee that individually beneficial
revisions remain effective after integration. The integrated system is
therefore evaluated again with complete Runtime Agent episodes over the
same full development suite and is subjected to the same cross-task
regression criterion relative to the accepted round-start system. If the
integrated revision passes the validation and is retained, it becomes
the next round’s execution system,

|     |                |     |     |
|-----|----------------|-----|-----|
|     |
       ``` math
       S_{r+1}=S^{+}.
       ```             |     | (6) |

Otherwise, RPG preserves the previous accepted system,

|     |                |     |     |
|-----|----------------|-----|-----|
|     |
       ``` math
       S_{r+1}=S_{r}.
       ```             |     | (7) |

This rollback preserves the accepted execution system when a candidate
or merged revision fails validation.

#### One round in summary.

Each practice round therefore follows the sequence

1.  1.
    execute all practice tasks with the current Runtime Agent and
    Privileged Agent;
2.  2.
    diagnose unsuccessful Runtime Agent executions on development tasks;
3.  3.
    propose at most one revision for each development task below $`5/5`$
    success;
4.  4.
    evaluate each revision across all 22 tasks on five paired
    development initializations;
5.  5.
    greedily integrate eligible revisions and retest the combined
    system;
6.  6.
    retain the integrated system only if it passes cross-task
    validation.

The reported experiment repeats this
rollout–diagnose–revise–validate–integrate procedure for 15 rounds.

#### Development versus held-out evaluation.

The five development initializations used for candidate and integration
decisions are separate from the held-out evaluation initializations.
Only after the 15-round practice run is complete and its saved systems
are frozen do we evaluate every saved round-end system retrospectively
on ten held-out initializations per task. Each point on the reported
learning curve therefore contains $`22\times 10=220`$ held-out
evaluation episodes. These held-out initializations are excluded from
candidate generation, acceptance, integration, and checkpoint selection.
Consequently, the held-out round-by-round curve measures the behavior of
the accepted systems on initializations not used to drive
self-improvement.

#### Models and execution budgets.

In simulation, both the Runtime Agent and Privileged Agent use
Gemini 3.8 Flash with xhigh reasoning. Offline failure analysis and code
revision use Fable 5.1 with xhigh reasoning. Each RPG episode is limited
to 30 model turns, 12 model-based observation calls, 1,200 s of wall
time, and 20 minutes of robot execution time. The final runtime
configuration additionally limits an episode to 400 skill calls and
limits an individual generated program execution to 300 s. Model-based
runtime queries and visual observation calls share the same 12-call
observation budget rather than having separate quotas.

### -B Qualitative Examples of Skill Acquisition and Refinement

We present representative examples of how self-improvement changes the
robot’s reusable manipulation behaviors. During self-improvement,
per-task development success is measured on five fixed development
initializations, so these in-loop success rates change in increments of
20 percentage points. Candidate revisions are subsequently evaluated
across the full cross-task validation suite as described in
Appendix [-A](#A0.SS1 "-A Self-Improvement Protocol ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents").
We distinguish these in-loop development measurements from the separate
10-seed held-out evaluations reported in the main experiments.

#### Robust object-in-container placement.

The Place bottles in bin task provides a clear example of acquiring a
previously unreliable manipulation capability. In Round 12, its in-loop
success rate increased from 1/5 (20%) to 5/5 (100%).

Before this improvement, the agent often treated moving the gripper near
the receptacle as sufficient for successful placement. It could commit
to a placement without checking the complete grasp-to-placement
trajectory, continue after an unreachable waypoint, or release a bottle
near the bin without ensuring that the bottle itself had cleared the rim
and entered the opening.

The improved behavior instead localizes the receptacle opening, checks
the complete manipulation route, reasons about the geometry of the
bottle rather than only the fingertip pose, clears the rim before
lowering, and verifies containment after release. In short, the behavior
changes from

> pick $`\rightarrow`$ move near receptacle $`\rightarrow`$ release

to

> localize opening $`\rightarrow`$ check route $`\rightarrow`$ verify
> grasp $`\rightarrow`$ align bottle $`\rightarrow`$ clear rim
> $`\rightarrow`$ lower $`\rightarrow`$ release $`\rightarrow`$ verify
> containment.

This represents a transition from end-effector-centric manipulation to
object-centric manipulation: reaching the commanded gripper pose is no
longer treated as equivalent to achieving the desired physical state.

#### Geometry-aware precision insertion.

The Nut assembly task illustrates how self-improvement can turn generic
object manipulation into a more precise insertion procedure. In the
five-seed development evaluation, success increased from 1/5 (20%) in
Round 4 to 5/5 (100%) in Round 5. The system prompt remained fixed
across this transition. The change came from the reusable manipulation
behavior available to the agent.

Before the improvement, the robot could proceed without confirming that
the nut was actually retained, confuse the graspable handle with nearby
geometry, or align the gripper with the peg without accounting for the
location of the nut’s square hole. It could also release after an
unsuccessful insertion attempt without verifying seating.

The improved behavior first verifies the grasp with a short test lift,
estimates the offset between the gripper and the square hole, aligns the
*hole* rather than the fingertip with the peg, and inserts through small
monitored vertical increments. If insertion stalls, the robot retreats
and re-observes before continuing. Release occurs only after visible
seating.

> grasp handle $`\rightarrow`$ test lift $`\rightarrow`$ verify
> retention $`\rightarrow`$ estimate hole offset $`\rightarrow`$ align
> hole to peg $`\rightarrow`$ incremental insertion $`\rightarrow`$
> verify seating $`\rightarrow`$ release.

#### Closed-loop wiping.

The Spill wipe task demonstrates refinement of an existing physical
capability. In the five-seed development evaluation, performance
increased from 4/5 (80%) in Round 4 to 5/5 (100%) in Round 5.

Earlier wiping behavior was largely open loop. A stroke could miss its
desired endpoint by several centimeters, while the agent continued
without checking which debris remained. The behavior also did not
consistently account for the offset between the fingertip and the actual
wiping surface of the gripper.

The improved behavior turns wiping into a closed-loop coverage
procedure. The robot estimates the support surface, calibrates contact
height, executes short overlapping strokes, retreats to obtain an
unobstructed observation, and selects subsequent strokes according to
the remaining debris.

> estimate patch $`\rightarrow`$ calibrate contact $`\rightarrow`$ short
> pass $`\rightarrow`$ reobserve residuals $`\rightarrow`$ corrective
> pass $`\rightarrow`$ verify clearance.

Thus, self-improvement does not merely tune a pushing trajectory; it
turns a brittle open-loop primitive into an observation-driven wiping
procedure.

#### Verified bimanual lifting.

The Two-arm lift task illustrates improvement in coordinated bimanual
manipulation. In the five-seed development evaluation, success is 3/5
(60%) in Round 11, while later rounds reach 5/5 (100%).

Earlier behavior could treat the two arms almost independently: one arm
might miss its intended approach pose while the system nevertheless
continued toward grasping or lifting. Conversely, an ambiguous
observation could cause the robot to reset even after a plausible
two-handed hold had already been established.

The improved behavior introduces explicit bilateral verification. Each
arm is assigned to the handle on its side, both lifting paths are
checked before the grippers close, both grasps are verified, and the
robot first performs a small synchronized test lift. It then continues
with matched incremental motions while monitoring the object’s rise and
the relative heights of its two sides.

> localize handles $`\rightarrow`$ check both paths $`\rightarrow`$
> verify both grasps $`\rightarrow`$ paired test lift $`\rightarrow`$
> synchronized lift $`\rightarrow`$ verify object rise.

These examples illustrate how self-improvement accumulates reusable
procedural knowledge rather than merely adjusting isolated motion
parameters. Across rounds, the learned behaviors increasingly encode
geometric relationships, preconditions, verification steps, recovery
strategies, and task-level completion criteria.

### -E Failure and Learned-Correction Taxonomy

To characterize what is being accumulated during self-improvement, we
organize the failure analyses into recurring manipulation failure modes
and the corresponding procedural corrections. This taxonomy is
qualitative: it summarizes recurring patterns observed in the analyzer
outputs rather than reporting category frequencies.

|  Failure mode |  Typical failure |  Learned correction |  Representative tasks |
|----|----|----|----|
|  Localization and geometry uncertainty |  The policy acts on a stale, ambiguous, or poorly localized object, receptacle, or support surface. |  Re-observe after scene changes; reconstruct geometry from multiple visible points and depth; invalidate stale targets after contact or failed motion. |  Place bottles in bin, Insert into fixture, Place dish on rack |
|  Grasp identity and retention |  A blocked or object-sized gripper opening is treated as proof that the desired object is held, even when the grasp is empty, mixed, or on the wrong object. |  Combine gripper state with wrist/top observations and a short test lift; require visible target co-motion before transport; preserve uncertain grasps rather than opening blindly. |  Extract from fixture, Nut assembly, Stack blocks |
|  Incomplete path feasibility |  An endpoint is reachable, but an approach, lift, transit, release, or retreat waypoint along the actual manipulation route is not. |  Check the complete manipulation path before committing, including approach, grasp, lift, transport, release, and retreat, using the actual arm configuration and yaw. |  Place bottles in bin, Place dish on rack, Stack blocks |
|  End-effector-centric geometry |  The fingertip reaches the nominal target while the relevant object feature does not: e.g., the bottle misses the opening or the nut hole misses the peg. |  Track the geometry of the manipulated object and its task-relevant feature; estimate object-to-gripper offsets and align the object, hole, bottom surface, or footprint rather than the fingertip. |  Place bottles in bin, Nut assembly, Insert into fixture |
|  Contact and support calibration |  Motion is commanded relative to the fingertip without accounting for pad extension, object extent, table height, or support geometry, causing penetration or ineffective contact. |  Estimate the support surface and relevant tool/object offset; use surface-relative heights and small monitored increments instead of large open-loop contact motions. |  Spill wipe, Fold towel |
|  Multi-effector coordination |  Each arm is controlled locally without verifying that both contacts are valid or that the required relation between the two arms is maintained. |  Verify both grasps, perform a paired test motion, preserve relative geometry, and use synchronized incremental motions with an explicit relation tolerance. |  Two-arm lift |
|  Execution-budget failure |  A physically valid strategy does not finish because repeated staging, recovery, or redundant motion consumes the remaining robot-time budget. |  Plan complete routes using measured execution time; resolve difficult cross-workspace transfers early; reserve explicit time for the final delivery and verification. |  Sort cubes (extended), Sort cubes (standard) |
|  Premature release or completion |  Successful execution of a primitive is treated as task success even though the object is not seated, contained, supported, or geometrically correct. |  Make irreversible actions fail closed; verify physical task state after release; preserve a held object under uncertainty; trigger bounded recovery when the final state is not confirmed. |  Place bottles in bin, Stack blocks, Fold towel |

TABLE VIII: Qualitative taxonomy of recurring manipulation failures and
the reusable corrections learned from them. Many corrections introduce
explicit *preconditions*, *verification*, or *closed-loop recovery*,
rather than merely changing a Cartesian target.

Across these categories, a common trend emerges. Self-improvement
progressively converts implicit assumptions into explicit procedural
checks. A nominally successful motion is no longer sufficient evidence
of a successful grasp, insertion, placement, or coordinated
manipulation. Instead, the evolved procedures increasingly couple action
with observation: they verify preconditions before acting, monitor
execution while acting, and check task-level state before terminating.

This perspective also clarifies why the learned changes can transfer
between tasks. Corrections such as test-lift verification, full-route
reach checking, object-centric alignment, incremental contact motion,
and post-release verification are not tied to a single object instance.
They are reusable manipulation patterns that can be composed in later
tasks.

single missing waypoint. Successful folding requires maintaining thin,
deformable material in both grippers while the geometry of the cloth
changes throughout the motion. Observed failures include uncertain
corner acquisition, loss of one corner during bimanual transport,
insufficient support clearance, incomplete landing reachability, and
termination after a visually plausible but geometrically incorrect
partial fold.

Several of the corrections learned for rigid-object manipulation remain
useful: the robot can verify a corner with a short lift, check the
complete motion path, move the two arms in shorter matched increments,
and re-observe the cloth after a slip. However, these mechanisms still
do not provide sufficiently reliable estimation of layer identity,
persistent cloth contact, and post-fold geometry.

This result exposes an important boundary of the current approach. For
rigid objects, many failures can be converted into reusable procedural
guards around grasping, reachability, alignment, release, and
verification. For deformable objects, the underlying state itself
changes substantially under contact, and visually similar configurations
can correspond to different layering and attachment states. Improving
this regime likely requires richer representations of deformable state
and contact, rather than only additional composition of the existing
rigid-object skills.

### -G Simulation Task Suite

We evaluate RPG on a suite of 22 bimanual manipulation tasks on the YAM
station. Each task specification fixes the simulation scene, language
instruction, execution budget, and a binary evaluator that evaluates the
final outcome from simulator state. The policy’s own success claims are
recorded for diagnostics but never affect the success label.

The suite contains 17 development tasks, one validation task, and four
feedback-held-out tasks. Development tasks provide task-specific failure
feedback and may generate candidate revisions. The validation task,
Restack cubes, does not generate candidate revisions and is used as a
cross-task regression check. It is reported separately from the
feedback-held-out tasks because only the latter are used in the transfer
analysis of
Appendix [-D](#A0.SS4 "-D Transfer without Direct Task-Specific Improvement Feedback ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents").
The four feedback-held-out tasks are Serve onto plate, Two-arm handover,
Transfer object, and Close sunglasses case. They are neither analyzed by
the Video Analyzer nor used to generate task-specific candidate
revisions. They remain in cross-task validation only as regression
checks.

All tasks use the same observation interface: RGB images from the top
and both wrist cameras, top-camera depth, and robot proprioception.
Initial conditions randomize object poses and selected physical
parameters, including friction, mass, table height, camera pose, and
depth noise, followed by a fixed settling period before execution. Each
trial consists of one episode. Task-specific limits on skill calls and
robot execution time are part of the task definition. Unless otherwise
noted, task success is scored from the final simulator state. RATs
follows its native any-time success criterion as reported in
Table [II](#S4.T2 "TABLE II ‣ IV-A Tasks and Evaluation Protocol ‣ IV Evaluation ‣ Reconstruct, Practice, Go Real:Guided Self-Improvement for Embodied Agents").

#### Outcome-based evaluators.

The benchmark uses nine evaluator types that capture different
manipulation objectives. Most placement tasks use an all_in_targets
evaluator, which checks that every required object lies within
task-specific horizontal and vertical tolerances around its target.
Other evaluators check lifting, articulated closure, extraction,
stacking, restacking, level bimanual lifting, debris removal, and cloth
folding. Several evaluators include additional guard conditions to
reject degenerate solutions. For example, moving an entire fixture does
not satisfy extraction, and a pre-stacked scene does not satisfy
restacking unless the base itself is relocated.

#### Representative task definitions.

For Insert into fixture, both pegs must reach their corresponding cups,
with a $`3`$ cm horizontal tolerance. For Two-arm lift, both handle
sites must rise by at least $`6`$ cm while their rise differs by less
than $`3`$ cm, preventing a single-arm tilted lift from passing. For
Spill wipe, at least six of nine debris particles must finish outside
the marked patch, so merely sweeping one portion of the patch is
insufficient.

The Place bottles in bin scene contains six bottles and a central bin,
but only two specified bottles are targets: the black bottle and the
clear bottle with the blue-and-yellow label. The other four are
distractors and need not be moved. Towel folding is evaluated directly
from the cloth mesh: corresponding corners must align within $`5`$ cm,
the moved layer must remain above the receiving layer, the projected
footprint must shrink to $`42`$–$`58\%`$ of its initial area, and the
resulting cloth must remain sufficiently thin.
````
