Junhao Dong, Bryan Kian Hsiang Low, Chenglin Wu, Zhongxiang Dai

###### Abstract

An _agent harness_ is the code that organizes context, maintains state,
and coordinates tool calls for a language model. We study how to improve
the harness under a limited evaluation budget while keeping model
weights fixed. Our method, MESH-Harness, organizes each harness into
functional modules with explicit role-specific interfaces, allowing
alternative implementations of each module to be substituted and
recombined. It uses shared module representations and full-covariance
LinUCB to score candidate combinations based on predicted performance
and exploration value. Mixed-start coordinate ascent selects complete
configurations for evaluation without enumerating the combinatorial
space. Validation traces then guide local code edits, and the resulting
candidates are incorporated into fixed-capacity role-specific pools for
subsequent recombination. On text tasks, retrieval-augmented
mathematical reasoning, code generation, and interactive scientific
tasks, MESH-Harness outperforms Meta-Harness by 5.70, 7.01, 2.00, and
5.00 points, respectively, under matched candidate-evaluation budgets.
Iterative harness optimization improves MESH-Harness by 5.63–7.79 points
over its first-round configurations. For the reported configurations,
aggregate test-time cost is 44.2% lower than that of Meta-Harness, while
total cost including search is 14.6% lower. These results show that
combining module-level design reuse with feedback-driven compositional
search can systematically improve agent harnesses while keeping overall
optimization cost under control.

## 1 Introduction

Large language models (LLMs) can act as agents by retrieving
information, calling tools, and interacting with environments ([Yao
et al., 2023](#bib.bib32)). Their behavior also depends on the external
program that controls memory, context construction, tool use, and
failure recovery. This program is referred to as the _agent harness_.
Unlike a single prompt, a harness specifies how successive model calls
work together to solve a task. For example, harnesses for long-running
agents support this coordination through explicit state handoffs,
progress records, and execution checks ([Young, 2025](#bib.bib34)).
Because the harness governs how model calls work together, optimizing it
offers a way to improve an agent without updating model weights.
AutoHarness synthesizes action validators and policy code through
iterative refinement using environment feedback ([Lou et al.,
2026](#bib.bib21)). Meta-Harness searches over task-specific Python
programs, allowing a proposer agent to inspect previous candidates’
code, scores, and execution traces ([Lee et al., 2026](#bib.bib17)).
Both approaches make the surrounding program an object of optimization
rather than a fixed implementation.

bandit model; new implementations join their respective pools for

The difficulty is that evaluating a harness can be much more expensive
than proposing it. Even a small edit may require an end-to-end
validation run involving many model calls and environment interactions.
Meta-Harness likewise identifies candidate evaluation as its main
computational bottleneck ([Lee et al., 2026](#bib.bib17)). Under a
limited budget, the search must therefore decide not only what to
generate, but what to execute. We study how to use past evaluations to
make these decisions and obtain larger improvements within a fixed
number of candidate evaluations.

We introduce MESH-Harness, a bandit-guided framework for compositional
harness evolution. Contextual bandits use shared features to generalize
from observed rewards and balance predicted performance against
uncertainty ([Li et al., 2010](#bib.bib19); [Chu et al.,
2011](#bib.bib7)). To apply this idea to harnesses, we organize each
harness into functional slots with fixed interfaces, maintain a
candidate pool per slot, and select one implementation per slot. Each
implementation is encoded separately; concatenating the selected
embeddings in slot order represents a complete harness. A shared
surrogate learns from observed harness scores to predict the performance
of untested combinations of module implementations.

Full-covariance LinUCB combines these predictions with an uncertainty
bonus to score module combinations. We approximately maximize this
criterion through mixed-start coordinate ascent, drawing one start per
round from the incumbent, top-$`K`$ archived configurations, or a random
combination and substituting implementations within one slot at a time
rather than enumerating the Cartesian product of candidate pools.
Selection uses only cached representations and surrogate scores; the
chosen complete harness is then executed on the validation tasks. This
separates inexpensive candidate comparison from costly task evaluation.

Selection alone cannot discover implementations absent from the
candidate pools. MASPOB selects prompt combinations using bandit-guided
coordinate ascent but does not update its candidate pools ([Hong et al.,
2026](#bib.bib14)). MESH-Harness instead updates the available
implementations in each slot during search. Validation traces provide
evidence of local failures, such as missing information or repeated
unsuccessful actions, and guide an LLM in editing implementations while
preserving their slot interfaces. New implementations enter their slot’s
fixed-capacity pool for combination with candidates in other slots. Each
execution thus supplies two kinds of feedback: scores update the
selection model, while traces guide module evolution. A new
implementation need not trigger an immediate end-to-end evaluation.

We evaluate MESH-Harness on text tasks, retrieval-augmented mathematical
reasoning, LiveCodeBench ([Jain et al., 2025](#bib.bib15)), and
ScienceWorld ([Wang et al., 2022](#bib.bib29)). Under matched
candidate-evaluation budgets, it improves final test scores over
Meta-Harness by 5.70, 7.01, 2.00, and 5.00 points, respectively.
MESH-Harness improves by 5.63–7.79 points over its first-round
configurations. On ScienceWorld, it starts at 51.90, below the ReAct
reference score of 55.50, and reaches 58.10. Across all four tasks, the
reported configurations reduce aggregate test-time cost by 44.2%
relative to Meta-Harness. Total cost, including search and testing the
reported configurations, is 14.6% lower.

Our contributions are:

- •
  A bandit-guided harness optimizer that allocates a limited evaluation
  budget using shared performance predictions and uncertainty estimates.
- •
  A module-level representation and mixed-start coordinate ascent
  procedure that reuse evaluation feedback across configurations without
  enumerating the full combinatorial space.
- •
  A trace-driven module evolution mechanism, evaluated on four tasks in
  terms of final performance, search gains, and search and test costs.

## 2 Related Work

#### Improving agents through external components.

Recent work improves agents by optimizing the external artifacts that
govern their behavior, ranging from natural-language skill documents to
executable harnesses. ACE ([Zhang et al., 2026c](#bib.bib37))
incrementally curates execution experience into context playbooks, while
SkillOpt ([Yang et al., 2026](#bib.bib31)) refines reusable skill
documents through trajectory-driven edits and validation-gated updates.
MCE ([Ye et al., 2026](#bib.bib33)) co-evolves context artifacts and the
context-engineering skills that produce them. At the code level,
Meta-Harness ([Lee et al., 2026](#bib.bib17)) gives an agentic proposer
access to historical programs, scores, and traces to guide harness
revision. ADIAS ([Jiang et al., 2026](#bib.bib16)) maintains persistent
issue states to direct full-code modifications, and DGM-H ([Zhang
et al., 2026a](#bib.bib35)) makes both the task agent and its
self-improvement procedure editable. AEvo ([Zhang et al.,
2026b](#bib.bib36)) uses accumulated evolution evidence to guide a
meta-agent in editing the search procedure or agent context that governs
subsequent evolution. Closely related to our work, AHE ([Lin et al.,
2026](#bib.bib20)) exposes harness components as editable files and uses
structured trajectory evidence and edit-outcome checks to guide revision
and rollback. Whereas AHE organizes optimization around successive
revisions to a working harness, MESH-Harness maintains alternative
implementations in per-slot pools and learns which complete compositions
to evaluate. Implementations discovered in different iterations can thus
be combined by selecting one per slot, without requiring another LLM
rewrite.

#### Bandit-guided search under limited evaluation budgets.

Feature-based bandits ([Li et al., 2010](#bib.bib19); [Chu et al.,
2011](#bib.bib7)) provide a way to allocate evaluations by sharing
reward information across candidates and balancing exploitation with
uncertainty-driven exploration. TRIPLE ([Shi et al., 2024](#bib.bib28))
casts prompt selection as fixed-budget best-arm identification. For
multi-agent systems, MASPOB ([Hong et al., 2026](#bib.bib14)) combines a
topology-aware GNN surrogate with UCB-guided coordinate search to select
prompt combinations from given candidate domains. MESH-Harness applies
uncertainty-guided selection to configurations with one executable
implementation per functional slot. A shared reward surrogate over
component representations allows past evaluations to inform the ranking
of untested compositions, while coordinate search avoids enumerating the
full combination space. Unlike search over an unchanged candidate
domain, this selection process is interleaved with trace-driven
component evolution, so new implementations can enter the pools as
optimization proceeds.

Together, these choices separate implementation generation from
evaluation allocation. MESH-Harness reuses existing implementations
without additional LLM rewriting, shares feedback across candidate
compositions, and introduces new implementations for existing slots from
execution evidence. This allows search to exploit prior discoveries
without remaining confined to the initial candidate pools.

## 3 Preliminaries

With a fixed execution model $`M`$ and tool set, a _harness_ $`h`$ is a
program that organizes model calls, maintains state, and controls
interaction with the environment. On an instance $`z\sim\mathcal{D}`$,
it produces a trajectory $`\tau\sim\operatorname{Run}(M,h,z)`$ with task
score $`R(z,\tau)`$. Harness optimization seeks to improve expected
performance without changing model weights:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
J(h)=\mathbb{E}_{{\color[rgb]{0,0,0}z\sim\mathcal{D},\;\tau\sim\operatorname{Run}(M,h,z)}}\left[R(z,\tau)\right].
``` |  | (1) |

We organize the harness into $`k`$ functional slots with fixed
interfaces $`\mathcal{I}=\{I_{1},\ldots,I_{k}\}`$. A slot specifies a
fixed functional responsibility, such as retrieval or failure recovery,
rather than a single model call; execution may include branches and
loops. Before round $`t`$, pool $`P_{j,t}`$ contains candidate
implementations satisfying $`I_{j}`$. Substitution occurs within a slot;
each configuration selects one implementation per slot:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
h=(c_{1},\ldots,c_{k}),\quad c_{j}\in P_{j,t},\qquad\mathcal{H}_{t}=\prod_{j=1}^{k}P_{j,t}.
``` |  | (2) |

The executable harness is $`\operatorname{Compose}_{\mathcal{I}}(h)`$;
$`N`$ candidates per slot yield $`N^{k}`$ configurations.

Each round evaluates a complete configuration $`h_{t}`$, yielding a
validation score $`r_{t}`$, traces $`\mathcal{T}_{t}`$, and resource-use
records $`\kappa_{t}`$, all stored in an archive $`\mathcal{A}_{t}`$.
The score is aggregated under the task’s validation protocol and is an
observed estimate rather than the unknown $`J(h_{t})`$. A bandit pull
selects a complete harness: no separate module rewards are observed. We
seek a high-performing configuration within $`T`$ evaluations and select
the final harness from the validation archive. Test data are not used
for generation, selection, or stopping.

### 4.1 Module Pools and Shared Representations

An LLM initializes $`N`$ implementations per slot from the task
description, interfaces, and permitted training information. Candidates
for a retrieval slot, for example, may rank evidence differently. They
must pass their slot’s interface checks and basic execution checks;
duplicates are rejected, and invalid implementations are revised using
error feedback.

A fixed encoder maps each candidate’s role description, interface, and
implementation summary to an embedding, followed by a fixed projection
and normalization to obtain $`e(c)\in\mathbb{R}^{d}`$. The configuration
representation concatenates embeddings in slot order:

|     |                                                    |     |     |
|-----|----------------------------------------------------|-----|-----|
|     |
       ``` math
       x(h)=[e(c_{1});\ldots;e(c_{k})]\in\mathbb{R}^{kd}.
       ```                                                 |     | (3) |

The shared surrogate (i.e., $`\hat{\mu}_{t}(h)`$ in Section
[4.2](#S4.SS2 "4.2 Bandit-Guided Compositional Search ‣ 4 Method ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution"))
predicts harness performance from $`x(h)`$, whose fixed slot order
aligns module implementations by functional role across configurations.
An observation from one configuration can therefore affect the ranking
of other combinations, including those that have not been executed.
Embeddings are cached; newly proposed implementations are encoded in the
same space without resetting the model.

### 4.2 Bandit-Guided Compositional Search

Following linear contextual bandits ([Li et al., 2010](#bib.bib19); [Chu
et al., 2011](#bib.bib7)), we maintain shared reward statistics over
configuration features. Let $`p=kd`$ and $`x_{s}=x(h_{s})`$. Before
round $`t`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
A_{t-1}=\lambda I_{p}+\sum_{s<t}x_{s}x_{s}^{\top},\qquad b_{t-1}=\sum_{s<t}r_{s}x_{s},
``` |  | (4) |

where $`\lambda>0`$, $`A_{0}=\lambda I_{p}`$, and $`b_{0}=0`$. With
$`\hat{\theta}_{t-1}=A_{t-1}^{-1}b_{t-1}`$, the predicted performance
and exploration signal are

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\hat{\mu}_{t}(h)=x(h)^{\top}\hat{\theta}_{t-1},\qquad\sigma_{t}(h)=\sqrt{x(h)^{\top}A_{t-1}^{-1}x(h)}.
``` |  | (5) |

We retain the full information matrix, including cross-slot feature
co-occurrences, for joint parameter estimation and configuration-level
uncertainty. The predicted mean remains additive over slots:
$`\hat{\mu}_{t}(h)=\sum_{j=1}^{k}e(c_{j})^{\top}\hat{\theta}_{j,t-1}`$,
where $`\hat{\theta}_{j,t-1}`$ is the parameter block for slot $`j`$.
The shared reward model and uncertainty estimate guide the selection of
complete configurations; actual performance is determined by end-to-end
execution.
Appendices [A.1](#A1.SS1 "A.1 How one evaluation informs other compositions ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")–[A.2](#A1.SS2 "A.2 The role of full covariance in compositional uncertainty ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")
derive observation transfer and cross-slot uncertainty.

To account for module coverage and lineage reuse as the pools evolve, we
use

|  |  |  |  |
|----|----|----|----|
|  |
``` math
U_{t}(h)=\hat{\mu}_{t}(h)+\alpha g_{t}(h)\sigma_{t}(h)+B_{t}(h)-F_{t}(h),
``` |  | (6) |

with

|  |  |  |  |
|----|----|----|----|
|  |
``` math
B_{t}(h)=\frac{\eta}{k}\sum_{j=1}^{k}\frac{1}{\sqrt{1+n_{t-1}(c_{j})}},\qquad F_{t}(h)=\frac{\gamma}{k}\sum_{j=1}^{k}\log\!\left(1+u_{j,t-1}(f(c_{j}))\right).
``` |  | (7) |

Here, $`n_{t-1}(c)`$ counts prior evaluations containing $`c`$, $`f(c)`$
identifies its lineage family, and $`u_{j,t-1}(f)`$ counts that family’s
uses in slot $`j`$ over the latest $`W`$ evaluations. Thus, *$`B_{t}`$
favors underused modules and $`F_{t}`$ discourages repeated lineage
selection*.

For similarity-aware exploration, set
$`g_{t}(h)=\max\{g_{\min},1-\beta\bar{s}_{t}(h)\}`$. Across slots,
$`\bar{s}_{t}(h)`$ averages each candidate’s maximum nonnegative cosine
similarity to previously evaluated modules in the same slot and its
parent when available; missing references contribute zero. This reduces
the exploration premium for close variants. The coefficients
$`\alpha,\eta,\gamma,\beta\geq 0`$ and $`g_{\min}\in(0,1]`$ control
these terms, which affect selection only, not the reward update.

We approximately maximize $`U_{t}`$ by mixed-start coordinate ascent,
building on the coordinate search used in MASPOB ([Hong et al.,
2026](#bib.bib14)). Each round draws one start from a mixture of the
incumbent, the top-$`K`$ archived configurations restorable by the task
adapter, and a random combination; an empty archive gives a random
start. The incumbent supports local refinement, while archived and
random starts provide alternative search points. We then sweep through
the slots:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
c_{j}\leftarrow\operatorname*{arg\,max}_{c\in P_{j,t}}U_{t}(h_{-j},c),\qquad j=1,\ldots,k,
``` |  | (8) |

where $`(h_{-j},c)`$ substitutes candidate $`c`$ for the implementation
in slot $`j`$ and retains the latest choices elsewhere. Each update
scores a complete configuration. We use two sweeps by default, favor
unevaluated configurations on ties, and use random fallback sampling to
seek a new configuration when the result has already been evaluated. The
$`S`$ sweeps require $`O(S\sum_{j}|P_{j,t}|)`$ surrogate evaluations
(Appendix [A.3](#A1.SS3 "A.3 Monotonicity and computational cost of coordinate search ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")).
Throughout these sweeps, $`U_{t}`$ remains fixed and no harness is
executed. Only the selected $`h_{t}`$ receives a task evaluation, after
which

|  |  |  |  |
|----|----|----|----|
|  |
``` math
A_{t}=A_{t-1}+x_{t}x_{t}^{\top},\qquad b_{t}=b_{t-1}+r_{t}x_{t}.
``` |  | (9) |

We also update the archive, module-use counts, and lineage statistics.

### 4.3 Trace-Driven Module Evolution

After every $`L`$ evaluations, while budget remains, MESH-Harness groups
validation traces by failure type and identifies slots whose
implementations warrant revision. Diagnosis uses current failures,
recurring errors, and previous edits in the relevant lineages. The
proposer mixes failure-guided repair, exploration of less-covered
designs, and local refinement of strong configurations. Each refresh
targets two distinct slots and proposes one child implementation per
slot from its interface, parent code, and execution evidence. Proposals
undergo the checks in
Section [4.1](#S4.SS1 "4.1 Module Pools and Shared Representations ‣ 4 Method ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution"),
with a bounded number of retries for invalid implementations. A child
implements its parent’s slot and can be combined with candidates for
other slots from other rounds.

Each accepted child replaces one candidate in its slot’s pool, keeping
the pool size fixed:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
P_{j,t+1}=(P_{j,t}\cup\{c^{\prime}_{j}\})\setminus\{c_{j}^{-}\}.
``` |  | (10) |

Among eligible candidates, we evict the one with the lowest retention
value: the mean observed reward of configurations containing it.
Unevaluated candidates have value zero and do not inherit parent scores.
Ties favor removing the candidate most similar to others in the pool.
The incumbent’s selected implementations and the newly inserted child
are protected during the update; historical implementations and lineage
records remain archived. Pools without an accepted child are unchanged.

Refreshes preserve $`A_{t}`$ and $`b_{t}`$. A new implementation
receives no immediate task evaluation: subsequent bandit decisions
determine when it is selected and which implementations fill the other
slots. Search therefore learns both which combinations to evaluate and
which implementations to add, without assigning an evaluation to every
proposal. The final harness is chosen by the prespecified validation
criterion and its implementations are frozen for testing. Generation and
embedding costs count toward search expenditure; deployment executes
only the selected harness, without further search.

## 5 Experiments

We evaluate final performance under a limited candidate-evaluation
budget, examine the contributions of selection and module evolution, and
assess the cost and reuse of the resulting harnesses.

### 5.1 Experimental Setup

#### Tasks and evaluation.

We study text tasks on LawBench ([Fei et al., 2024](#bib.bib9)),
USPTO ([Schneider et al., 2016](#bib.bib26)), and Symptom-to-Diagnosis
dataset ([Gretel AI, 2023](#bib.bib11)); retrieval-augmented mathematics
constructed from OlympiadBench ([He et al., 2024](#bib.bib12)) and
MathArena ([Dekoninck et al., 2026](#bib.bib8)); code generation on
LiveCodeBench ([Jain et al., 2025](#bib.bib15)); and interaction in
ScienceWorld ([Wang et al., 2022](#bib.bib29)). We report the
macro-average over the three text datasets, overall Math pass@1 on the
combined test set, LiveCodeBench solve rate under the fixed cap-8
protocol, and mean ScienceWorld progress. Math pass@1 divides the total
number of correct answers across both datasets by their total number of
test instances, weighting each instance equally
(Appendix [C.4](#A3.SS4 "C.4 Metrics and aggregation ‣ Appendix C Implementation Details ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")).
All methods use the same splits
(Appendix [C.1](#A3.SS1 "C.1 Datasets and retrieval resources ‣ Appendix C Implementation Details ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")).
Search and final harness selection use validation data; the selected
implementations are frozen before held-out testing. All reported test
scores are means over three test runs of the same frozen harness.

use the same execution model and a budget of 40 complete candidate

and MESH-Harness evaluates $`40\times 1`$ compositions. Meta-Harness

#### Implementation.

Both optimizers use Claude Code ([Anthropic, 2026a](#bib.bib3)) with
Claude Opus 5 ([Anthropic, 2026b](#bib.bib4)) at medium effort. Unless
stated otherwise, task execution uses DeepSeek V4 Flash ([Xu et al.,
2026](#bib.bib30)) with thinking disabled. MESH-Harness uses
Qwen3-Embedding-8B ([Zhang et al., 2025](#bib.bib38)), 10 candidates per
slot, $`\alpha=0.8`$, and two coordinate-search sweeps per evaluation.
Every five evaluations, while budget remains, it proposes one child
implementation in each of two distinct slots.

## 6 Conclusion

We introduced MESH-Harness, which combines shared module
representations, bandit-guided compositional search, and trace-driven
module evolution to improve agent harnesses without changing model
weights. Across four task domains, it achieves the highest aggregate
scores among the evaluated methods and outperforms Meta-Harness under
matched candidate-evaluation budgets. Text ablations support both guided
selection and module evolution, while further experiments on these tasks
show transfer across execution models and gains from refining a
Meta-Harness solution. For the reported configurations, aggregate
test-time cost is 44.2% lower than that of Meta-Harness, and combined
search-and-test expenditure is 14.6% lower. These results show that
reusing and refining implementations within fixed functional slots can
improve task performance while reducing the execution cost of the
resulting harnesses.

## Appendix A Theoretical Supplements

This section analyzes the mechanisms that make compositional search
useful under a limited evaluation budget: information transfer through a
shared surrogate, uncertainty over module combinations, and inexpensive
coordinate-wise selection. The first two results follow from the ridge
state and the search rule themselves. The final result explicitly states
the additional confidence-envelope assumption needed to relate
acquisition-based selection to the task objective.

### A.1 How one evaluation informs other compositions

Let $`p=kd`$, and fix the embedding map throughout a search run. At a
given round, write

|  |  |  |  |
|----|----|----|----|
|  |
``` math
A=\lambda I+\sum_{s<t}x_{s}x_{s}^{\top},\qquad b=\sum_{s<t}r_{s}x_{s},\qquad\widehat{\theta}=A^{-1}b,
``` |  | (11) |

where $`\lambda>0`$. Since each slot embedding has unit norm,
$`\|x(h)\|_{2}^{2}=k`$. In particular, $`A`$ is positive definite and
$`x(h)^{\top}A^{-1}x(h)\leq k/\lambda`$ for every composition, including
a composition that has not been evaluated.

###### Proposition A.1 (Transfer through the shared ridge state).

Suppose the next evaluated harness has feature vector $`x`$ and reward
$`r`$. Let $`A^{+}=A+xx^{\top}`$ and $`b^{+}=b+rx`$. For any fixed
comparison vector $`v`$, the posterior mean and squared uncertainty
satisfy

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle v^{\top}\widehat{\theta}^{+}-v^{\top}\widehat{\theta}`$ | $`\displaystyle=\frac{v^{\top}A^{-1}x}{1+x^{\top}A^{-1}x}\bigl(r-x^{\top}\widehat{\theta}\bigr),`$ |  | (12) |
|  | $`\displaystyle v^{\top}(A^{+})^{-1}v`$ | $`\displaystyle=v^{\top}A^{-1}v-\frac{(v^{\top}A^{-1}x)^{2}}{1+x^{\top}A^{-1}x}.`$ |  | (13) |

###### Proof.

The Sherman–Morrison identity ([Sherman & Morrison, 1950](#bib.bib27))
gives

|  |  |  |  |
|----|----|----|----|
|  |
``` math
(A+xx^{\top})^{-1}=A^{-1}-\frac{A^{-1}xx^{\top}A^{-1}}{1+x^{\top}A^{-1}x}.
``` |  | (14) |

Multiplying by $`b+rx`$ and using $`A^{-1}b=\widehat{\theta}`$ yields
$`\widehat{\theta}^{+}=\widehat{\theta}+A^{-1}x(r-x^{\top}\widehat{\theta})/(1+x^{\top}A^{-1}x)`$.
Left multiplication by $`v^{\top}`$ proves
Eq. ([12](#A1.E12 "In Proposition A.1 (Transfer through the shared ridge state). ‣ A.1 How one evaluation informs other compositions ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution"));
taking the quadratic form of
Eq. ([14](#A1.E14 "In Proof. ‣ A.1 How one evaluation informs other compositions ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution"))
proves
Eq. ([13](#A1.E13 "In Proposition A.1 (Transfer through the shared ridge state). ‣ A.1 How one evaluation informs other compositions ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")).
∎

These identities make the reuse mechanism explicit. An evaluation
changes another composition’s prediction through its overlap with the
evaluated direction in the $`A^{-1}`$ geometry, not merely through exact
module identity. The update also depends on the prediction residual: a
surprising result has a different effect from one already explained by
the surrogate. Uncertainty cannot increase at a fixed vector after an
observation, and its reduction is largest along directions coupled to
the evaluated composition. This is surrogate-level information transfer;
it is not an assignment of the observed reward to every selected module
as an independent contribution.

The same identities apply after a pool refresh. A new implementation is
encoded in the existing feature space, so it can be scored immediately
with the accumulated $`(A,b)`$. Its creation does not add an
observation, and it receives neither its parent’s reward nor a synthetic
reward. Retiring an implementation changes the feasible set of
compositions but does not invalidate the stored observations. This
separation between the feasible set and the statistical state is what
allows the pools to evolve without restarting the surrogate.

### A.2 The role of full covariance in compositional uncertainty

Partition $`\widehat{\theta}`$ and $`A`$ by functional slot. The mean
prediction remains additive:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{\mu}(h)=\sum_{j=1}^{k}\widehat{\theta}_{j}^{\top}e(c_{j}).
``` |  | (15) |

Full covariance does not introduce explicit pairwise reward features.
Rather, its off-diagonal blocks retain which slot representations have
been observed together:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
A_{ij}=\lambda\,\mathbf{1}\{i=j\}I_{d}+\sum_{s<t}e(c_{i,s})e(c_{j,s})^{\top}.
``` |  | (16) |

These blocks affect both the fitted coefficients and the uncertainty of
a proposed combination.

A two-slot example isolates the distinction. Let $`d=1`$, and suppose
all $`n`$ observations used $`x_{+}=(1,1)^{\top}`$. Then

|  |  |  |  |
|----|----|----|----|
|  |
``` math
A=\lambda I+nx_{+}x_{+}^{\top},\qquad\sigma^{2}(x_{+})=\frac{2}{\lambda+2n},\qquad\sigma^{2}(x_{-})=\frac{2}{\lambda},\quad x_{-}=(1,-1)^{\top}.
``` |  | (17) |

Repeatedly observing the same pairing resolves the common direction but
provides no information about the orthogonal contrast. Replacing $`A`$
by its block diagonal would assign both directions uncertainty
$`2/(\lambda+n)`$ and lose that distinction. In a compositional search,
this matters when modules have repeatedly appeared with the same
partners: frequent exposure of each module need not imply that a
different pairing is well understood.

The distinction is useful for evaluation allocation: exposure to
individual modules and exposure to their joint directions are different
forms of information. The embedding-based mean is a surrogate for
program performance, while end-to-end execution supplies the observed
reward. The selection ablations in
Table [5.3](#S5.SS3.SSS0.Px1 "Selecting which compositions to evaluate matters. ‣ 5.3 Contributions of Selection and Evolution ‣ 5 Experiments ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")
complement this algebraic analysis by measuring the effect of the
acquisition rule under the fixed evaluation cap.

### A.3 Monotonicity and computational cost of coordinate search

During one selection step, the pools, posterior, usage counts, and
lineage statistics are held fixed. Thus the acquisition $`U_{t}(h)`$ is
a fixed function on the current Cartesian product. A coordinate update
enumerates the active candidates for one slot while retaining the other
slots.

###### Proposition A.2 (Monotonic coordinate updates).

If each coordinate update includes the currently selected module among
its choices and selects an acquisition maximizer, the acquisition is
nondecreasing over the coordinate updates. If the procedure is continued
using only strict improving moves, it terminates at a coordinate-wise
maximizer on a finite product space.

###### Proof.

The current composition is feasible in every coordinate subproblem, so
the selected replacement has acquisition at least as large. With strict
improving moves, a composition cannot be revisited. Finiteness therefore
implies termination; at termination no single-coordinate replacement
improves the acquisition. ∎

The implementation uses two sweeps as a bounded local-ascent procedure.
The proposition characterizes each feasible coordinate update;
convergence to a coordinate-wise maximizer would additionally require
continuing strict improvement to termination. Novelty-based tie breaking
preserves nondecrease for equal acquisition values. Duplicate avoidance
is a subsequent selection step, detailed in
Section [B.2](#A2.SS2 "B.2 Mixed-start composition selection ‣ Appendix B Algorithmic Details ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution").

For slot pool sizes $`N_{1},\ldots,N_{k}`$ and $`S`$ sweeps, the
coordinate comparisons require $`S\sum_{j}N_{j}`$ acquisition
evaluations, plus final scoring and any start-selection or
duplicate-handling overhead. Exhaustive comparison would require
$`\prod_{j}N_{j}`$ evaluations. With $`N_{j}=10`$ and $`S=2`$, this is
140 coordinate comparisons instead of $`10^{7}`$ for the seven-slot
tasks, and 100 instead of $`10^{5}`$ for the five-slot ScienceWorld
controller. These counts concern inexpensive surrogate comparisons, not
benchmark executions. Only the selected complete harness consumes a
candidate-evaluation slot.

The dense statistical state occupies $`O(p^{2})`$ space. With a cached
inverse, a rank-one update and a quadratic-form score each require
$`O(p^{2})`$ arithmetic; the agent implementation uses this update. The
text and math implementation instead stores $`(A,b)`$ and evaluates the
corresponding dense linear solves. These implementations realize the
same statistical update with different linear-algebra costs. The
comparison above concerns acquisition-query complexity; embedding newly
proposed modules is accounted for as initialization or refresh work.

### A.4 Decomposing uncertainty and approximate selection

Coverage, lineage, and similarity adjustments modify evaluation
priorities while leaving the observed rewards unchanged. The following
decomposition separates these adjustments from uncertainty and
approximate maximization using the confidence-envelope formulation of
linear bandit analysis ([Abbasi-Yadkori et al., 2011](#bib.bib1)).
Consider a round on which, for some $`q_{t}\geq 0`$, the surrogate
satisfies the uniform envelope

|  |  |  |  |
|----|----|----|----|
|  |
``` math
|J(h)-\widehat{\mu}_{t}(h)|\leq q_{t}\sigma_{t}(h)\quad\text{for all }h\in\mathcal{H}_{t}.
``` |  | (18) |

Write $`V_{t}=\widehat{\mu}_{t}+q_{t}\sigma_{t}`$ and
$`D_{t}=U_{t}-V_{t}`$. Let $`h_{t}^{*}`$ maximize $`J`$ over the current
pools, and define the acquisition-search error
$`\varepsilon_{t}=\max_{h\in\mathcal{H}_{t}}U_{t}(h)-U_{t}(h_{t})\geq 0`$.

###### Proposition A.3 (A conditional one-step decomposition).

Under
Eq. ([18](#A1.E18 "In A.4 Decomposing uncertainty and approximate selection ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")),

|  |  |  |  |
|----|----|----|----|
|  |
``` math
J(h_{t}^{*})-J(h_{t})\leq 2q_{t}\sigma_{t}(h_{t})+\operatorname{osc}_{\mathcal{H}_{t}}(D_{t})+\varepsilon_{t},
``` |  | (19) |

where $`\operatorname{osc}(D)=\max D-\min D`$.

###### Proof.

The envelope gives $`J(h_{t}^{*})\leq V_{t}(h_{t}^{*})`$ and
$`J(h_{t})\geq V_{t}(h_{t})-2q_{t}\sigma_{t}(h_{t})`$. Moreover,
$`V_{t}(h_{t}^{*})-V_{t}(h_{t})=U_{t}(h_{t}^{*})-U_{t}(h_{t})+D_{t}(h_{t})-D_{t}(h_{t}^{*})\leq\varepsilon_{t}+\operatorname{osc}(D_{t})`$.
Combining the inequalities proves the claim. ∎

For MESH-Harness, $`D_{t}=(\alpha g_{t}-q_{t})\sigma_{t}+B_{t}-F_{t}`$.
Equation ([19](#A1.E19 "In Proposition A.3 (A conditional one-step decomposition). ‣ A.4 Decomposing uncertainty and approximate selection ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution"))
separates three sources of selection error: uncertainty in the chosen
composition, the range of the acquisition adjustment, and the gap left
by approximate search. It is a conditional statement under
Eq. ([18](#A1.E18 "In A.4 Decomposing uncertainty and approximate selection ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution"));
the empirical $`\alpha`$ is a search coefficient rather than an asserted
calibrated confidence radius. Coverage and lineage regularize
exploration of an evolving candidate space, while coordinate search
bounds the cost of comparing those candidates.

Pool refresh changes the feasible set without resetting the statistical
state. Protecting the incumbent preserves an already evaluated
configuration, while retaining historical embeddings allows subsequent
selection to reuse all completed observations.
Section [B](#A2 "Appendix B Algorithmic Details ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")
makes these state transitions explicit, including the different roles of
the composition reward, the pool-retention statistic, and the validation
criterion used for final selection.

#### History is selective context, not a new retrieval corpus.

Failure statistics are accumulated over the committed validation
history. The proposer receives a bounded view: up to eight error groups,
at most two representative examples per group, up to six related family
edits, and up to three higher-scoring historical trajectories for
currently failed problems. Contrasts are chosen preferentially from
configurations differing in fewer slots. The additional history context
is limited to 24,000 characters by dropping complete records. Each
record retains its originating evaluation and component identities, so
the proposer can distinguish an observed result from the stated intent
of an untested edit. These contrasts guide a modification hypothesis;
the next complete-harness evaluation supplies its observed reward.

#### Three state transitions have different roles.

A completed evaluation changes $`(A,b)`$, the archive, and usage
statistics. A refresh changes which programs are available while
retaining those statistics. Finalization freezes a validation-selected
composition and removes the optimizer from the execution path. In
particular, the empirical mean $`v(c)`$ is used for pool retention,
whereas the complete-harness reward $`r_{t}`$ is the observation for the
bandit. A new module starts with zero observations and is represented
immediately in the same feature space. This is the operational
counterpart of
Proposition [A.1](#A1.Thmmeshproposition1 "Proposition A.1 (Transfer through the shared ridge state). ‣ A.1 How one evaluation informs other compositions ‣ Appendix A Theoretical Supplements ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution"):
reuse does not require assigning an inherited or synthetic reward to a
new implementation.

#### Evaluation budget.

The default initialization creates 70 modules for the seven-slot tasks
or 50 for ScienceWorld. Seven refreshes can add at most 14 modules while
preserving an active space of $`10^{7}`$ or $`10^{5}`$ compositions. The
budget contains 40 complete-composition evaluations; generation,
embedding, and checks are accounted for separately. Final testing
follows
Algorithm [4](#alg4 "Algorithm 4 ‣ B.4 Admissibility, history construction, and frozen execution ‣ Appendix B Algorithmic Details ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution").

### C.2 Memory and information available to each harness

The optimizer’s validation archive, a harness’s runtime memory, and the
fixed retrieval corpus serve different roles. Validation scores and
traces guide code evolution. Runtime memory supports the current task,
while retrieval supplies external examples. Held-out answers remain with
the evaluator throughout execution.

#### Text.

Each candidate builds a separate memory for each dataset through one
pass over its training examples, receiving the gold label after each
training prediction. Validation and test predictions use this
training-derived memory without adding held-out labels. Memory is
rebuilt for each candidate and each final repetition.

#### Math.

The harness receives the problem, its answer-format instructions, and
access to the fixed retrieval corpus. The evaluator retains the
reference answer and grader. Retrieved solutions belong to the external
corpus; development and test solutions are not added to it. A
candidate’s verifier can inspect and refine an answer using the
available context, but cannot consult the reference answer.

#### LiveCodeBench and ScienceWorld.

Code-generation harnesses receive problem statements, starter-code
interfaces, and public examples. Only public-test results can be used
for repair. ScienceWorld harnesses receive the task description and
observations from their own actions, with memory reset at the start of
every episode. Validation traces from these interactions can guide
subsequent module proposals, as specified in
Section [B.4](#A2.SS4 "B.4 Admissibility, history construction, and frozen execution ‣ Appendix B Algorithmic Details ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution").

### C.4 Metrics and aggregation

Scores are reported on a 0–100 scale. Each selected harness is frozen
and evaluated three times on the same held-out data. For task score
$`S^{(r)}`$ in repetition $`r`$, the reported score is
$`S=\frac{1}{3}\sum_{r=1}^{3}S^{(r)}`$. The cross-task score in
Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")
is the unweighted mean of the four task scores.

#### Text.

Let $`s_{d}^{(r)}`$ be accuracy on dataset $`d`$ in repetition $`r`$.
Text gives equal weight to the three datasets:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
S_{\mathrm{Text}}^{(r)}=\frac{s_{\mathrm{USPTO}}^{(r)}+s_{\mathrm{Symptom}}^{(r)}+s_{\mathrm{Law}}^{(r)}}{3}.
``` |  | (22) |

USPTO uses exact set agreement on normalized precursor strings;
Symptom-to-Diagnosis uses exact diagnosis agreement after case,
whitespace, and punctuation normalization; LawBench requires agreement
on the full set of charges. The same dataset-macro convention defines
the validation reward.

#### Math.

We use the pooled pass@1 protocol shared with Meta-Harness. Let
$`n_{\mathrm{O}}=254`$ and $`n_{\mathrm{A}}=246`$ be the numbers of test
instances from OlympiadBench and MathArena, and let
$`C_{\mathrm{O}}^{(r)}`$ and $`C_{\mathrm{A}}^{(r)}`$ be their
correct-answer counts in repetition $`r`$. Then

|  |  |  |  |
|----|----|----|----|
|  |
``` math
S_{\mathrm{Math}}^{(r)}=100\,\frac{C_{\mathrm{O}}^{(r)}+C_{\mathrm{A}}^{(r)}}{n_{\mathrm{O}}+n_{\mathrm{A}}}.
``` |  | (23) |

Every instance has equal weight, so the two source-level percentages are
weighted by their test-set sizes. Each source’s programmatic grader
evaluates the final extracted answer. Internal retrieval or verification
calls are part of one harness execution; the resulting final answer is
the prediction scored for that instance.

#### LiveCodeBench: cap-8 solve rate.

For each problem, the evaluator concatenates the public and private test
cases, in that order, and retains at most eight. The selected program
solves the problem if it passes every retained case within the
six-second timeout per case. The solve rate is the percentage of test
problems solved. A harness may generate several drafts or use public
feedback for repair, but only its final selected program is scored. The
cap refers to test cases per problem.

#### ScienceWorld.

For episode $`i`$, let $`s_{i,t}^{(r)}`$ be the native environment score
at step $`t`$. The episode contributes its highest attained progress,
clipped to the 0–100 range:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
z_{i}^{(r)}=\min\!\left(100,\max\!\left(0,\max_{t}s_{i,t}^{(r)}\right)\right),\qquad S_{\mathrm{SW}}^{(r)}=\frac{1}{102}\sum_{i=1}^{102}z_{i}^{(r)}.
``` |  | (24) |

Partial progress therefore contributes to the score, while full episode
completion corresponds to 100.

### C.5 Final selection and cost accounting

#### Validation-based selection.

The final harness is selected from the validation archive. Math ranks
candidates by development pass@1, breaking ties by lower mean
input-token use and then by candidate identifier. LiveCodeBench and
ScienceWorld use validation score, then lower total token use and
candidate identifier. Text uses validation accuracy under the strict
component interface. The selected code, executor settings, and retrieval
resources are fixed before testing. Each test repetition starts with
fresh task memory and environment episodes.

#### Search budget.

MESH-Harness evaluates 40 complete compositions; Meta-Harness evaluates
two candidates in each of 20 proposal rounds ([Lee et al.,
2026](#bib.bib17)). Pool initialization, embedding, interface checks,
and coordinate comparisons are optimization work. Reference-harness
evaluations are recorded separately from the 40 new-candidate
evaluations. All initialization and reference-execution expenses are
included in search cost.

#### Reported cost.

The test-only totals in
Table [5.4](#S5.SS4.SSS0.Px1 "Search and execution costs. ‣ 5.4 Cost and Reuse of Optimized Harnesses ‣ 5 Experiments ‣ MESH-Harness: Self-Improving Agent Harnesses via Bandit-Guided Compositional Evolution")
measure execution of the frozen harnesses. Search-plus-test totals
additionally include proposer, executor, and embedding usage during
optimization, with provider-reported cache accounting. At deployment,
only the selected harness and its task resources are required.
Infrastructure interruptions are resumed as the same evaluation; an
executed answer or program that fails the task receives the task’s
failure score.

## Appendix D Analysis of Optimized Harnesses

We analyze the final harnesses selected by validation performance on the
four tasks. Their structures show how MESH turns a pool of reusable
implementations into task-specific programs: modules determine what
information to retain, how to present it to the model, and how to act on
the resulting response. We first examine these decisions within each
task, then relate the selected components to their origins in the pool.
The boxes reproduce prompt or code excerpts from the final
implementations, with only line breaks or outer indentation adjusted for
display.

### D.1 Text: evidence composition with explicit answer contracts

The Text harness separates seven decisions: maintaining training
examples, defining the answer space, retrieving evidence, composing
context, allocating computation, checking the response, and extracting
the final answer. A shared answer contract connects these decisions
across single-label prediction, multi-label prediction, and
structured-string generation. The budget policy identifies the requested
answer type from the input and stored examples, allowing downstream
components to preserve the semantics of each task. Structured strings,
for example, remain open-ended outputs rather than entries in a finite
label inventory.

The selected memory module removes exact input–target duplicates and,
when its pool exceeds capacity, preferentially removes redundant
examples from large signature groups. The retriever ranks examples using
weighted feature overlap, input-length proximity, and script-dependent
features, while suppressing near-duplicates and repeated answer labels.
The composer displays at most four supplied examples and adds a short
“Decisive difference” annotation to each: features shared with the query
but absent from the other displayed cases are identified explicitly.
Retrieval and composition thus serve complementary roles: one selects
examples, while the other exposes the distinctions the model should
consider.

### D.2 Math: compact problem context and exact-answer discipline

allocation, retrieval, context composition, solving, verification, and
answer parsing. The selected combination centers on the requested
mathematical quantity and its output form. Its analyzer distinguishes
counting, finding all solutions, extremal questions, and exact-value
questions, then extracts constraints and corresponding obligations.
These include completeness for a solution set, or an attaining
construction and a matching bound for an extremum.

The selected composer preserves the complete problem and adds compact
planning notes and an exact-answer contract. It does not insert the
retrieved passages, even though retrieval is available through the task
interface. This is a concrete choice within the optimization space: a
component may determine which available information enters the solver
context. Here, the resulting prompt keeps the problem, its constraints,
and the required form of the answer together.

### D.3 LiveCodeBench: complementary drafts and failure-directed repair

The LiveCodeBench harness separates problem analysis, budget selection,
prompt construction, draft generation, public-test feedback, repair
selection, and code parsing. The analyzer extracts the entry-point
contract, requested output, input-size bounds, and boundary conditions.
The prompt distinguishes a function or class method from a
standard-input program and reproduces public examples. The selected
budget requests two drafts with repair enabled. Both drafts use
temperature zero, with different instructions: one models the process
directly; the other is asked to re-derive the requested output quantity
independently, using requirement sentences extracted from the statement
when available.

Each draft is evaluated on the public tests. The repair selector
compares failures across drafts: a failing row is *local* if another
draft passes it, *contested* if the drafts produce different wrong
outputs, and *shared* otherwise. Syntax, timeout, and runtime defects
take precedence when choosing the repair instruction.

### D.4 ScienceWorld: planning with observed preconditions

The ScienceWorld harness uses five slots: evidence memory, goal-phase
planning, action-candidate ranking, a focus guard, and recovery.
Evidence memory records attempted actions, observed changes, score
increments, locations, and focus history. The planner converts this
record into a concrete next subgoal; ranking and guard modules constrain
which actions are proposed and accepted. Recovery uses the same state
and permission interfaces to replace an invalid or repeatedly
ineffective action.

a trace-aware, failure-driven refresh targeting incomplete goals. The

### D.5 Reuse, selection, and evolution in the final programs

The final Text, Math, and LiveCodeBench harnesses each combine seven
implementations from the initial pool; ScienceWorld combines four
initial implementations with the refreshed planner. Their provenance
illustrates the two roles of the pool: preserving alternatives for
combination selection and admitting new implementations during search.
Retention and evolution operate at the level of individual slots, while
evaluation measures the behavior of the assembled program.

Across tasks, the selected programs organize different forms of
evidence: comparisons among examples in Text, mathematical constraints
and answer forms in Math, public-test outcomes in LiveCodeBench, and
observed preconditions in ScienceWorld. Stable interfaces allow these
control policies to be stored and recombined without prescribing a
single reasoning workflow. Together with the main-text ablations, these
cases connect the search design to the concrete programs it produces.
````
