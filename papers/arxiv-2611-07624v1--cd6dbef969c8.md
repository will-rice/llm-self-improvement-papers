###### Abstract

Agent harness evolution enables recursive self-improvement (RSI) without
updating model weights. We examine whether higher benchmark scores yield
reliable, efficient, and transferable improvement. We evaluate four
methods across harnesses, general and coding tasks. Repeated
evaluations, controlled agent expansion, component interventions, and
admission replays reveal recurring patterns. All sixteen evolved agents
gain previously uncovered tasks while losing previously covered ones. In
one general-task case, reliability rises by 5.2 points despite losing
ten previously covered tasks. Most reliability gains also increase
deployment cost. Specific changes usually outperform generic reminders,
but their benefits can change when combined. The highest-scoring agent
does not yield the largest mean improvement in any of our four pools,
and stricter admission can discard useful alternatives. Transfer
selectively preserves gains: coverage usually falls on the general-task
target across both harness types and paradigms, but rises on the coding
target with the outer-layer-only harness. These findings motivate
preservation-aware evaluation, tested decision rules, and explicit
applicability conditions. As a constructive follow-up, EvoAudit turns
these diagnostics into revisions of _select_, _analyze_, _mutate_, and
_gate_, achieving the best performance.

## 1 Introduction

Recursive self-improvement (RSI) studies agents that iteratively revise
their own designs based on experience ([Zelikman et al.,
2024](#bib.bib38); [Hu et al., 2025](#bib.bib25); [Zhang et al.,
2026b](#bib.bib39)). Agent harness evolution offers a concrete form of
this idea for language-model agents: it keeps model weights fixed while
persistently changing the surrounding system that shapes observations
and turns model outputs into actions ([Lin et al., 2026a](#bib.bib6);
[Zhang et al., 2026c](#bib.bib7)). Depending on the harness, these
changes can target prompts, skills, tool interfaces, orchestration, or
source code, going beyond static prompting and memory-based adaptation
([Shinn et al., 2023](#bib.bib17); [Wang et al., 2024](#bib.bib24)).
Recent frameworks close the loop between execution, diagnosis, mutation,
and evaluation, reporting gains on standard benchmarks ([Hu et al.,
2025](#bib.bib25); [Shang et al., 2025](#bib.bib26); [Zhang et al.,
2025a](#bib.bib27)). These benchmark gains suggest that harness
evolution is a promising avenue for pursuing RSI.

However, a higher overall benchmark score do not mean a more useful
agent. It averages over tasks and trials, so newly solved tasks can
conceal lost ones, while deployment cost and performance beyond the
tasks that guided evolution remain unseen ([Gao et al.,
2026](#bib.bib29); [Wang et al., 2026b](#bib.bib30); [Kapoor et al.,
2025](#bib.bib28)). Relying on that score alone can favor brittle or
expensive agent versions and mistake adaptation to the tasks used during
evolution for general improvement. Meaningful progress instead requires
gains that are reliable across tasks, affordable to deploy, and
effective on tasks that did not guide evolution. We aim to explain which
persistent harness changes produce useful gains and how evolution
generates and preserves them.

We organize our empirical investigation around three research questions:

- •
  RQ1 (Phenomenology): Does agent evolution yield reliable and efficient
  improvements, or does it suffer from task-coverage trade-offs and
  hidden costs?
- •
  RQ2 (Generalization): Do the gains achieved during evolving survive
  when the agent is deployed in novel environments or tasks?
- •
  RQ3 (Mechanisms): How do specific evolutionary operators contribute to
  the generation and preservation of beneficial modifications?

We study AHE ([Lin et al., 2026a](#bib.bib6)), HyperAgents ([Zhang et
al., 2026c](#bib.bib7)), A-Evolve ([Lin et al., 2026b](#bib.bib8)), and
GEPA ([Agrawal et al., 2026](#bib.bib9)) with MiniSWE ([Yang et al.,
2024](#bib.bib12)) and Codex ([OpenAI, 2026](#bib.bib13)) on
$`\tau^{3}`$-Banking ([Shi et al., 2026](#bib.bib16)) for general tasks
and Terminal-Bench 2 ([Merrill et al., 2026](#bib.bib10)) for coding
tasks. Repeated evaluations compare evolved and initial agents in
reliability, empirical coverage, regressions, and deployment cost. Split
and cross-benchmark comparisons assess generalization, while controlled
expansion of existing agents, change interventions, and admission
replays trace how gains arise and persist.

Harness evolution redistributes task success, with new coverage
accompanied by regressions across harnesses, task domains, and evolution
paradigms. The practical value of these gains depends on deployment cost
and whether they persist beyond the tasks that guided evolution.
Specific changes usually outperform generic reminders, yet combining
them can alter their value. The strongest existing agent need not offer
the greatest further improvement, and stricter admission can discard
useful alternatives. Useful improvement therefore requires productive
starting points, compatible changes, and search decisions that preserve
gains.

We connect these findings to operator redesign as a constructive
follow-up. Analyses of Phenomenology, Generalization, and Mechanisms
jointly guide revision hypotheses for _select_, _analyze_, _mutate_, and
_gate_. Each hypothesis specifies its supporting evidence, expected
effects, and applicability conditions. We combine these revisions into
_Audit-Guided Evolution_ (AGE) to test their practical value.

Our contributions can be summarized as:

- •
  Revisiting Practical Improvement. We reveal a gap between benchmark
  gains and practical utility, showing that useful improvement in agent
  harness evolution requires preserving useful behavior, managing
  deployment cost, and sustaining gains beyond the tasks that guide
  evolution.
- •
  Understanding the Fragility of Gains. We identify productive agent
  selection, change compatibility, and search retention as central
  challenges. Current performance can misrepresent further improvement
  potential, useful changes can interfere, and admission can discard
  stronger versions.
- •
  Improving Evolution Through Analysis. We translate these findings into
  coordinated revisions of diagnosis, mutation, selection, and
  admission. The resulting AGE algorithm improves reliability and
  coverage over its reference method across both benchmarks and
  harnesses.

## 2 Related Work

Agent Optimization and Evolution. Agent improvement spans inference-time
refinement, optimization of persistent artifacts, and open-ended
self-modification. Reflexion retains linguistic feedback in episodic
memory across trials, whereas Self-Refine iteratively revises the
current output ([Shinn et al., 2023](#bib.bib17); [Madaan et al.,
2023](#bib.bib31)). ReflectEvo trains small language models on
self-generated reflections to improve introspection and reasoning ([Li
et al., 2025](#bib.bib20)). RAM learns from communications to improve an
external memory system ([Li et al., 2024](#bib.bib18)), and The AI
Hippocampus surveys implicit, explicit, and agentic memory mechanisms
([Jia et al., 2025](#bib.bib21)). DSPy optimizes language-model
programs, and TextGrad propagates textual feedback through computational
graphs ([Khattab et al., 2024](#bib.bib32); [Yüksekgönül et al.,
2025](#bib.bib33)). Promptbreeder evolves both task and mutation
prompts, ACE maintains evolving context playbooks, and CoEvoSkills
co-evolves multi-file skill packages with a separate surrogate verifier
([Fernando et al., 2024](#bib.bib34); [Zhang et al., 2025b](#bib.bib35);
[Zhang et al., 2026a](#bib.bib36)). The four approaches examined here
make different choices within this space. AHE exposes editable harness
components and uses distilled execution evidence to guide revisions
([Lin et al., 2026a](#bib.bib6)). HyperAgents makes both the task agent
and its modification procedure editable ([Zhang et al.,
2026c](#bib.bib7)). A-Evolve frames deployment-time adaptation as
goal-directed optimization over persistent system state ([Lin et al.,
2026b](#bib.bib8)). GEPA combines trajectory reflection for prompt
updates with Pareto selection of complementary candidates ([Agrawal et
al., 2026](#bib.bib9)).

Harness and Program Evolution. Related approaches also optimize system
structure and executable code. GPTSwarm optimizes prompt-bearing graph
nodes and orchestration edges, while AgentSquare searches combinations
of planning, reasoning, tool-use, and memory modules ([Zhuge et al.,
2024](#bib.bib37); [Shang et al., 2025](#bib.bib26)). ADAS uses a meta
agent to generate agent programs ([Hu et al., 2025](#bib.bib25)).
Self-modification extends to the improvement procedure itself: STOP
revises optimizer scaffolding, and the Darwin Gödel Machine evolves its
own coding agent ([Zelikman et al., 2024](#bib.bib38); [Zhang et al.,
2026b](#bib.bib39)). AlphaEvolve instead evolves target algorithm
programs using executable evaluation feedback ([Novikov et al.,
2025](#bib.bib40)). Recent work also explores optimizers that construct
their own optimization pipelines ([Xue and Yang, 2026](#bib.bib5)).
RSIHub composes evolution methods from reusable operators and provides
shared evaluation and lineage tracking ([Wang et al.,
2026c](#bib.bib23)). This distinction between improving task solutions,
agent implementations, and optimization procedures motivates separating
what changes from how those changes are generated and retained.

Capability Boundaries and Mechanisms. Empirical studies of reasoning
distinguish improved small-$`k`$ success from expansion of large-$`k`$
task coverage ([Yue et al., 2025](#bib.bib1)). Token-level analyses
identify concentrated learning signals at high-entropy decisions ([Wang
et al., 2025a](#bib.bib2)), while studies of on-policy distillation
examine behavioral compatibility and information novelty ([Li et al.,
2026](#bib.bib3)). Related work also examines the feedback used for
improvement. UAPO introduces uncertainty-aware utility anchors for
preference optimization ([Wang et al., 2025b](#bib.bib19)), and SAVE
uses value-anchored on-policy feedback to update reward models ([Wang et
al., 2026a](#bib.bib22)). We apply a related analytical perspective to
persistent agent-system changes rather than model-weight updates.
Repeated evaluations distinguish reliability from empirical coverage,
common-process Parent expansion tests improvement potential, Component
interventions examine change compatibility, and frozen-pool admission
replays assess retention.

Evaluation of Agent Systems. Agent evaluation must account for cost,
reproducibility, and generalization beyond aggregate success ([Kapoor et
al., 2025](#bib.bib28)). For harness evolution specifically, [Wang et
al. (2026b)](#bib.bib30) find inconsistent advantages over test-time
scaling under comparable feedback and inference budgets, together with
limited held-out generalization. Performance also depends on
interactions among the model, harness, task structure, and coordination
overhead ([Kim et al., 2025](#bib.bib4)). The $`\tau`$-bench family
emphasizes reliable tool-agent-user interaction, while Terminal-Bench 2
evaluates long-horizon execution in terminal environments ([Yao et al.,
2025](#bib.bib11); [Merrill et al., 2026](#bib.bib10)). We study general
and coding tasks through these complementary settings, distinguish task
exposure during evolution, and assess external transfer without further
agent revision. These comparisons connect measured improvement to its
deployment cost and scope of applicability.

## 3 Preliminaries

### 3.1 Definitions

An agent $`A=(M,H)`$ consists of a frozen model $`M`$ and a harness
$`H`$. Following [Lin et al. (2026a)](#bib.bib6); [Agrawal et al.
(2026)](#bib.bib9), an evolution algorithm $`E`$ starts from a _Seed_
$`A_{0}=(M,H_{0})`$ and runs for $`G`$ generations. At generation $`g`$,
a _Parent_ is an eligible existing agent selected for modification, and
$`\mathcal{C}_{g}`$ contains the resulting proposed harnesses. Each
$`H\in\mathcal{C}_{g}`$ defines a _Candidate_ agent $`(M,H)`$. The final
_Champion_ is $`A_{\star}=(M,H_{\star})`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\mathcal{C}_{g}=E(H_{<g},\mathcal{Z}_{<g},\mathcal{D}_{\mathrm{evo}};B_{\mathrm{evo}}),\quad H_{\star}=Q\!\left(\{H_{0}\}\cup\bigcup_{g=1}^{G}\mathcal{C}_{g}\right),
``` |  | (1) |

where $`H_{<g}`$ is the history of harness versions before generation
$`g`$, $`\mathcal{Z}_{<g}`$ is their evaluation evidence,
$`\mathcal{D}_{\mathrm{evo}}`$ is the task set available during
evolution, and $`B_{\mathrm{evo}}`$ is the search budget. The rule $`Q`$
selects the final Champion harness from the archived versions.

### 3.2 Experiment Setup

#### 3.2.1 Evolution Process and Methods

Methods and Harnesses. We evaluate AHE ([Lin et al., 2026a](#bib.bib6)),
HyperAgents ([Zhang et al., 2026c](#bib.bib7)), A-Evolve ([Lin et al.,
2026b](#bib.bib8)), and GEPA ([Agrawal et al., 2026](#bib.bib9)) using
GPT-5.4. AHE and HyperAgents are *implementation-centric* recipes that
emphasize agent engineering, whereas A-Evolve and GEPA are
*reflection-centric* recipes that distill execution feedback into
reusable changes. We run each recipe with two harnesses. MiniSWE 2.4.5
([Yang et al., 2024](#bib.bib12)) is *source-editable* and permits
inner-source changes. Codex 0.143.0 ([OpenAI, 2026](#bib.bib13)) is
*outer-layer-only* and permits changes to prompts, skills,
configuration, and external orchestration. These combinations let us
examine different evolution designs under a common process.
Appendix [A](#A1 "Appendix A Operator Implementations of the Compared Methods ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution")
details their implementations.

In this common process, each recipe specifies how seven operators are
implemented: *select* chooses a Parent, *rollout* collects execution
evidence, *analyze* diagnoses it, and *mutate* proposes a Candidate. The
*validate* operator optionally checks the proposal, *gate* decides
admission, and *record* archives outcomes. We focus the mechanism
analysis on *select*, *analyze*, *mutate*, and *gate* because their
decisions determine which Parents are used, how evidence guides changes,
and which Candidates persist.

Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution")
connects this operator process to the study’s empirical comparisons. The
Phenomenology analysis characterizes gains and regressions through
repeated task evaluations. The Generalization analysis examines how
these gains vary across original splits and external benchmarks. The
Mechanisms analysis examines Parent improvement potential under a common
generation process, Component interactions, and admission decisions on
frozen pools.

#### 3.2.2 Benchmarks and Evaluation Metrics

Benchmarks. General tasks are represented by $`\tau^{3}`$-Banking ([Shi
et al., 2026](#bib.bib16)), with 97 tasks, and coding tasks by
Terminal-Bench 2 ([Merrill et al., 2026](#bib.bib10)), with 89 tasks.
Both are split into Train/Validation/Test. Evolution uses
Train/Validation evidence for search and admission, while Test is
reserved for Seed and Champion evaluation.

Performance. Let $`\mathcal{D}`$ be an evaluation task set with
$`N=|\mathcal{D}|`$ tasks, each executed once per pass over $`k`$
passes. The outcome $`Y_{ni}(A)\in\{0,1\}`$ indicates whether agent
$`A`$ succeeds on task $`n`$ in pass $`i`$. With $`\mathbb{I}[\cdot]`$
an indicator function, *Reliability* (Avg@k) and *Coverage* (Pass@k)
are:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{Avg}@k=\frac{1}{Nk}\sum_{n=1}^{N}\sum_{i=1}^{k}Y_{ni}(A),\quad\mathrm{Pass}@k=\frac{1}{N}\sum_{n=1}^{N}\mathbb{I}\!\left[\max_{1\leq i\leq k}Y_{ni}(A)=1\right].
``` |  | (2) |

*Task turnover* counts coverage gains and losses relative to Seed.
$`\mathrm{Std}@k`$ is the population standard deviation of per-pass
success rates.

Cost. Each model call $`q`$ costs $`c(q)`$. A task execution $`t`$ costs
$`c_{t}`$, the sum of these charges over the agent’s calls. Evolution
cost $`C_{\mathrm{evo}}`$ sums costs over the set of evolution calls
$`\mathcal{L}_{\mathrm{evo}}`$. For deployment, $`\mathcal{T}_{k}`$
contains executions of $`A`$ on $`\mathcal{D}`$ with recorded costs in
the first $`k`$ passes. Their mean cost is
$`\bar{c}_{\mathrm{dep}}^{(k)}`$. Multiplying it by $`k`$ gives the
estimated per-task deployment cost $`C_{\mathrm{dep}}@k`$:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
C_{\mathrm{evo}}=\sum_{q\in\mathcal{L}_{\mathrm{evo}}}c(q),\quad\bar{c}_{\mathrm{dep}}^{(k)}(A;\mathcal{D})=\frac{1}{|\mathcal{T}_{k}|}\sum_{t\in\mathcal{T}_{k}}c_{t},\quad C_{\mathrm{dep}}@k(A;\mathcal{D})=k\,\bar{c}_{\mathrm{dep}}^{(k)}(A;\mathcal{D}).
``` |  | (3) |

### 4.2 Coverage Is a Flow

Evolution Redistributes Success. All sixteen Champions in
Figure [2](#S4.F2 "Figure 2 ‣ 4.2 Coverage Is a Flow ‣ 4 Phenomenology: Revisiting What Has Been Evolved ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution")
gain and lose covered tasks, and increase repeated success on some tasks
while decreasing it on others. This pattern spans both harnesses,
domains, and paradigms: even when both aggregate metrics improve,
coverage does not expand monotonically. Gains and losses should
therefore be reported separately.
Appendix [B.2](#A2.SS2 "B.2 Task-Level Turnover and Pass Stability ‣ Appendix B Phenomenology: Additional Protocols and Analyses ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution")
gives further analysis.

Behavioral Changes Behind Task-Level Gains and Losses. We inspect
contrasting traces for tasks with large success-count changes. Across
the sampled harnesses, domains, and paradigms, recurring differences
concern state preservation, precise grounding, and task completion.
Successful traces preserve recovery files and respect action
dependencies, while failures include incorrect arguments, premature
termination, and solutions that work locally but fail in the required
environment. These contrasts motivate preservation and end-to-end checks
rather than equating every outcome flip with acquired or lost task
knowledge.

### 7.2 AGE Implementation

Recipe and Evidence Flow. AGE installs four fixed operator revisions in
the A-Evolve recipe described in
Appendix [A](#A1 "Appendix A Operator Implementations of the Compared Methods ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution"),
shared across both benchmarks and harnesses. Each generation selects a
Parent, collects fresh Train trajectories, diagnoses behavior, and
proposes one Candidate. Framework scope checks and canonical Validation
evaluation precede admission and recording. The reference *rollout* and
*record* implementations are unchanged, and the optional *validate*
stage is disabled. MiniSWE permits changes to inner source and outer
artifacts, whereas Codex permits only outer-artifact changes. The
evaluator, task partitions, model settings, resource limits, and
evolution operators remain fixed. Online decisions use Train and
Validation evidence.

Run Configuration. Each run uses 20 generations, one proposed Candidate
per generation, and search random seed 0. The target harnesses are
MiniSWE 2.4.5 and Codex 0.143.0, both using GPT-5.4 with high reasoning
effort. Diagnosis and mutation use Codex 0.146.0 with GPT-5.4 and xhigh
effort through Harbor. Every rollout executes the 50 Train tasks afresh.
Canonical scoring executes each Validation task once, using 20 tasks on
$`\tau^{3}`$-Banking and 19 on Terminal-Bench 2. Frozen Champions
receive separate eight-pass reporting evaluations.

Select: Regression-Aware Tie-Breaking. AGE retains the highest-score
objective and revises only exact ties. Let $`\mathcal{P}`$ be the
eligible Parents with finite recorded Validation scores $`s(C)`$, and
let $`\mathcal{T}=\arg\max_{C\in\mathcal{P}}s(C)`$. When comparable
task-level evidence is available, selection minimizes Seed-relative
regressions within $`\mathcal{T}`$:

|  |  |  |
|----|----|----|
|  |
``` math
R(C)=\sum_{t\in\mathcal{D}_{\mathrm{val}}}\mathbb{I}[\bar{r}_{t}(C)<\bar{r}_{t}(A_{0})],\qquad P\sim\operatorname{Uniform}\!\left(\arg\min_{C\in\mathcal{T}}R(C)\right),
``` |  |

where $`\mathcal{D}_{\mathrm{val}}`$ is the Validation task set and
$`\bar{r}_{t}`$ is the mean recorded reward on task $`t`$. Comparable
evidence requires a unique eligible Seed evaluation, matching task-set
hashes and task identities, equal per-task repetition counts, and
completed trials with finite rewards for every tied Candidate and the
Seed. Otherwise, the seeded generator samples uniformly from the
original highest-score tie set. A unique maximizer is selected directly,
and an empty eligible scored set stops selection. The rule reuses
recorded outcomes and preserves the highest-score objective.

Analyze: Behavior-Grounded Diagnosis. The analyzer collects the current
rollout and, when available, one preceding rollout along the selected
lineage, retaining the last 30 records in their stored order. Each judge
input contains chronological tool calls, successful and failed tool
results, and the completion signal. Tool arguments and results are
capped at 600 and 800 characters, respectively. Each rendered trajectory
uses at most 12,000 characters, preserving approximately two-thirds from
its beginning and one-third from its end when truncated. Interrupted
executions can include a bounded termination message. The behavior
bundle excludes benchmark rewards, verifier outputs, hidden tests, raw
task text, and raw-case paths.

The judge returns score, category, outcome, and failure_reason. Scores
0–3 indicate visible breakdown, 4–6 indicate partial or ambiguous
progress, and 7–10 indicate visible completion supported by an
appropriate check or comparably decisive result. Verdicts distinguish
Observed: behavior from Inference: explanations and ground completion
judgments in trajectory evidence. These behavioral scores guide
diagnosis, while benchmark scores drive *select* and *gate*. Each
request permits one attempt with a 600-second timeout. Invalid or failed
responses return an unknown verdict with sentinel score $`-1`$.

The analyzer exports trajectories, behavioral signals, and verdicts in a
structured evidence bundle. The selected text view uses at most 30,000
characters for $`\tau^{3}`$-Banking and 60,000 for Terminal-Bench 2,
omitting trailing whole records beyond these budgets. Mutation consumes
at most a 50,000-character prefix of this view. Both truncation steps
add explicit omission markers.

Mutate: Mechanism-Linked, Dependency-Closed Changes. The mutation agent
receives the selected behavior evidence, Parent workspace, prompt and
skill inventory, and editing contract. Before choosing files, its
instructions require the observed behavior, inferred mechanism,
replacement behavior, activation conditions, and expected trade-off. A
recurring concrete pattern or a single severe, visibly supported
breakdown can motivate a change, while ambiguous evidence favors
preserving current behavior. The agent must inspect affected interfaces
and their producers and consumers, make one coherent intervention,
preserve useful behavior in successful traces, and check for conflicting
or duplicated guidance. Dependency-closed changes may span multiple
files and layers.

The agent is instructed to edit the permitted target directly, inspect
its final diff, run proportionate structural checks, and propose a
validation case for the expected benefit. Outputs retain the patch,
changed-file list, surface-check report, agent response, and usage
record. Structural checks enforce editing surfaces and interfaces, while
the mutation instructions specify evidence grounding, dependency
closure, and behavior preservation. Execution errors stop the operator
and are recorded with their diagnostic information.

Gate: Score-First, Cost-Aware Admission. AGE retains strict
Parent-relative score improvement and adds a cost tie-break. For a
Candidate $`C`$ and its matched Parent $`P`$, with finite Validation
scores, admission is

|  |  |  |
|----|----|----|
|  |
``` math
\operatorname{accept}(C,P)=\mathbb{I}\!\left[s(C)>s(P)\;\lor\;\bigl(s(C)=s(P)\land Q(C,P)\land c(C)<c(P)\bigr)\right].
``` |  |

Here $`c`$ is the recorded USD cost of canonical Validation evaluation.
The comparability predicate $`Q`$ requires matching task-set hashes,
finite strictly positive costs, and a direct Parent evaluation.
Equal-score admission requires a verified, comparable cost reduction.
When cost comparability fails, only the score-improvement branch
applies. A valid matched Parent and finite scores are required, and all
other Candidates are rejected. The operator reuses canonical evaluations
and preserves score improvement as its primary objective.

## 8 Discussion

Feedback Can Be Narrower Than a Change’s Effects. Harness changes affect
many behaviors, while evaluation samples finite executions and
compresses their trade-offs. A prompt, skill, or execution routine can
help the tasks that supply feedback while disrupting behavior elsewhere.
This mismatch offers a common explanation for task regressions,
context-dependent change interactions, and selective transfer. It
suggests that practical evolution depends on how well feedback
represents the consequences of a change, including the resources needed
to deploy it.

Evidence Must Match the Decision. Current performance, improvement
potential, change compatibility, and retention are distinct objectives.
A high-scoring Parent need not yield the greatest subsequent gain, a
useful Component can interfere with other changes, and a conservative
gate can discard alternatives. Together, the diagnostics show why
evidence supporting one decision need not support the next. Evaluation
should test the desired consequence of each decision, rather than reuse
the same aggregate score throughout evolution.

Toward Decision-Specific Feedback. Evaluate *select* through subsequent
gains, ground *analyze* and *mutate* in traces and dependencies, and
assess *gate* through both retained quality and preserved alternatives.
Deployment cost and external evaluation then determine how broadly these
benefits remain useful. EvoAudit and AGE illustrate how these
complementary checks can guide a coordinated redesign while preserving
the reference method’s execution and evaluation contracts.

## 9 Conclusion

Our study shows that harness evolution redistributes observed task
success, bringing both gains and regressions. Across harnesses, task
domains, and evolution paradigms, practical improvement depends on
productive Parents, compatible changes, preservation through search, and
generalization at affordable cost. EvoAudit connects these findings to
operator revisions, and AGE improves reliability and coverage over its
reference method in all four settings. These results motivate evaluating
evolution by the useful behavior it creates and sustains, beyond final
benchmark scores.

### Ethics Statement

Experiments run in isolated benchmark environments rather than live
user-facing services. Evolving agent instructions and code can introduce
regressions and unintended tool use. We retain fixed evaluation
contracts and harness-specific editing permissions, and examine
regressions and transfer alongside aggregate performance. Participants
in the human evaluation provided informed consent. The expert-review
protocol evaluates the evidence, reasoning, and proposed approaches for
operator revisions, as described in
Appendix [E.2](#A5.SS2 "E.2 Human Review Materials and Reporting ‣ Appendix E Operator Redesign: Implementation and Evaluation ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution").
Neither benchmark gains nor expert endorsement establishes safety for
deployment.

## Appendix A Operator Implementations of the Compared Methods

We describe the implementations used in our experiments through the
seven operator stages in
Table [11](#A1.T11 "Table 11 ‣ Appendix A Operator Implementations of the Compared Methods ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution").
All four methods share fixed target-model and evaluator contracts.
MiniSWE permits dependency-closed changes to inner source code as well
as prompts, skills, configuration, and orchestration; Codex permits only
changes outside its immutable executable and source. HyperAgents
additionally permits changes to designated evolution operators.

Evolution Paradigms. Our design-based grouping distinguishes
implementation-centric recipes, AHE and HyperAgents, from
reflection-centric recipes, A-Evolve and GEPA. The former organize
revision around engineering the agent implementation or improvement
machinery; the latter organize it around distilling execution experience
and feedback. Both use evidence and may modify code within the harness’s
legal surface. The grouping follows recipe design, while the harness
determines the permitted editing surface. Codex permits changes to
external orchestration code while keeping its executable and inner
source immutable.

|----|----|----|----|----|
| select |  Newest eligible Parent |  Score-weighted sampling with a child-count penalty |  Highest-scoring eligible Parent |  Per-task Pareto-front sampling |
| rollout |  Reuse Parent evaluation traces |  Reuse Parent evaluation traces |  Fresh Train trajectories |  Fresh Train trajectories |
| analyze |  Per-task debugger reports |  Metrics and browsable raw traces |  Behavior-only trajectory judge |  Focused reflective examples |
| mutate |  One testable target change |  Edit the target and allowed operators |  Distill experience into target changes |  Reflection-guided target revision |
| validate |  $`-`$ |  Python syntax checks |  $`-`$ |  Strict improvement on the Parent’s Train batch |
| gate |  Admit valid completed evaluations |  Admit valid completed evaluations |  Strict improvement over the matched Parent |  Admit valid completed evaluations |
| record |  Outcomes and change evidence |  Lineage experience |  Outcomes and rationale |  Reflection and batch experience |

Search scores use Train tasks for AHE and HyperAgents, and Validation
tasks for A-Evolve and GEPA. The *validate* operator checks proposals,
while the Validation split supplies evaluation tasks. Shared scope and
evaluation-eligibility checks apply to all four methods, including those
that omit the optional *validate* stage. Test outcomes remain excluded
from search.

### A.1 AHE

Selection and Diagnosis. AHE emphasizes observability-grounded
revision ([Lin et al., 2026a](#bib.bib6)). Its *select* operator chooses
the newest eligible Parent, not necessarily the highest-scoring one. The
*rollout* operator reuses that Parent’s evaluation traces. The *analyze*
operator produces task-level debugger reports: failure reports identify
the failure point, possible cause, and corrective lesson, while
successful traces expose reusable strategies and fragile behavior. Mixed
outcomes on a task can therefore inform the diagnosis alongside outright
failures. An overview links these reports to prior changes and their
observed effects.

Revision and Admission. The mutation agent is instructed to make one
coherent, testable change, supported by task evidence and an identified
execution path. It considers whether to retain, revise, or roll back the
preceding change and pursue a different explanation. A change manifest
records the proposed mechanism, affected files, predicted fixes, and
behaviors at risk. Debugger reports supply hypotheses for revision.
There is no separate optional *validate* stage. The *gate* operator
admits a completed, eligible evaluation without requiring a higher
score, so the next Parent can come from a lower-scoring revision. The
*record* operator preserves outcomes and change evidence. Admission and
continuation are thus distinct from final Champion reporting.

### A.2 HyperAgents

Selection and Evidence. HyperAgents permits revision of the improvement
procedure as well as the target agent ([Zhang et al.,
2026c](#bib.bib7)). Its initial *select* policy samples eligible Parents
using a score-dependent weight and a penalty for having many children.
Higher scores increase sampling weight, while the child-count penalty
reduces repeated expansion of the same Parent. The *rollout* operator
reuses Parent evaluation traces. The initial *analyze* operator supplies
metrics and browsable raw traces, leaving their interpretation largely
to the mutation agent rather than first producing AHE-style debugger
reports.

Revision and Admission. Mutation may change the target and permitted
operator implementations while leaving the evaluator and other fixed
contracts unchanged. The mutation instructions favor substantive target
changes but allow an operator-only revision when the evidence supports a
process-level change. An operator revision takes effect at its next
invocation, updating the initial policies in
Table [11](#A1.T11 "Table 11 ‣ Appendix A Operator Implementations of the Compared Methods ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution")
for subsequent Generations. The initial *validate* stage checks Python
syntax in target files and the mutation operator. The initial *gate*
admits completed, eligible evaluations without a Parent-relative score
threshold. The *record* operator stores lineage experience, including
the Parent, outcome, and score. This editable search procedure
distinguishes HyperAgents from target-only revision under fixed
operators.

### A.3 A-Evolve

Selection and Behavioral Feedback. Our A-Evolve implementation
operationalizes experience-driven adaptation ([Lin et al.,
2026b](#bib.bib8)). The *select* operator chooses the highest-scoring
eligible Parent, and *rollout* collects fresh Train trajectories. The
*analyze* operator compresses observable behavior, including tool use,
repeated actions, errors, and completion signals, for a trajectory-only
judge. This judge evaluates behavior without benchmark reward labels.
Its proxy judgments provide feedback for revision, rather than replacing
the benchmark score used for admission.

Revision and Admission. The *mutate* operator distills these
observations into reusable task-solving guidance and executable target
changes. Its instructions emphasize recurrent failure patterns,
self-contained skills with their supporting dependencies, and
preservation of unrelated behavior. Prompt and skill settings organize
revision within the Harness’s legal editing boundary. The optional
*validate* stage is disabled. After canonical evaluation, the strict
*gate* admits a Candidate only if its Validation score exceeds that of
the matched Parent. The *record* operator retains outcomes and the
revision rationale. Unlike AHE and the initial HyperAgents policy,
A-Evolve combines greedy Parent choice with score-improving admission.

### A.4 GEPA

Selection and Reflection. GEPA combines trajectory-based reflection with
per-task Pareto selection ([Agrawal et al., 2026](#bib.bib9)). The
*select* operator identifies eligible Candidates attaining the best
observed score on at least one task, prunes redundant coverage, and
samples according to the remaining per-task memberships. This can
preserve access to task specialists without selecting solely by
aggregate score. The *rollout* operator collects fresh Train
trajectories, and *analyze* assembles task examples, outputs, and
feedback for focused reflection.

Revision Scope. The named reflection units differ by benchmark. On
$`\tau^{3}`$-Banking, MiniSWE focuses on its system-prompt
configuration, while Codex alternates between its prompt and
task-execution skill. On Terminal-Bench 2, both harnesses use the entire
target as the reflection unit. These units guide evidence organization
rather than impose text-only filesystem permissions. The frozen Champion
from MiniSWE with GEPA on Terminal-Bench 2 retains inner-source changes
to task-conditioned guidance and shell execution. Reflection-centric
therefore describes the revision process, not the absence of code
changes. These reflection units are distinct from the post-hoc
Components isolated in our diagnostics.

Validation and Admission. The *validate* operator evaluates the proposal
on the same Train task batch used for the Parent rollout and requires a
complete, scorable comparison with strict improvement. This
feedback-informed proposal filter precedes canonical Validation
evaluation. The subsequent *gate* checks completion and eligibility
without imposing a second Parent-relative improvement threshold. The
*record* operator preserves reflection choices, proposals, and batch
comparisons. Thus, GEPA’s improvement filter lies in *validate*, whereas
A-Evolve’s lies in *gate*, and they use different task evidence.

Implications for the Analysis. These implementations differ in how they
allocate search, summarize evidence, couple target and operator changes,
and filter proposals. Similar final gains can therefore arise through
different processes. These differences motivate diagnostics of
selection, diagnosis, change compatibility, and admission.

Coverage Turnover Across All Settings. All sixteen Champions both gain
and lose covered tasks. Gains range from one to fifteen tasks and losses

combination. A positive net coverage delta therefore represents the
balance of newly covered and lost tasks rather than preservation of the
Seed’s solved set. This shared pattern motivates paired gain/loss
accounting without requiring a specific method to have the largest net
expansion.

Within-Task Reliability Also Redistributes. Every panel contains tasks
on both sides of the success-count diagonal. Evolution can improve
repeated success on already covered tasks, reduce it elsewhere, and
change which tasks are covered at all. The shared combination of these
movements explains why neither a net coverage gain nor a reliability
gain summarizes preservation.

Pass-Half Stability. We compare passes 1–4 with passes 5–8 to assess the

directions differ between halves on $`\tau^{3}`$-Banking, showing
sensitivity to execution variability.

### C.1 Search Exposure and Split Accounting

Task Exposure and External Transfer. Train trajectories supply evolution

### D.1 Select: Parent Choice and Subsequent Improvement

Parent Pools and Common Generation Process. For each benchmark and
harness, we form one pool containing the frozen Champions from AHE,
HyperAgents, A-Evolve, and GEPA. The four pools contain 16 Parents. Each
Parent initializes three separate branches from the same frozen
workspace, producing 48 Candidates in total. Every branch uses the same
original A-Evolve *analyze* and *mutate* implementations, prompts, and
generation allowance. The four methods provide Parent artifacts; the
shared downstream process holds the modification procedure fixed.

Execution Evidence and Evaluation. Each Parent executes the 50 Train
tasks once, and its three branches share this evidence while running
analysis and mutation independently. Canonical Validation uses one pass
over 20 tasks on $`\tau^{3}`$-Banking or 19 on Terminal-Bench 2. Each
Parent and Candidate receives eight Test passes over 27 or 20 tasks,
respectively. Target and mutation models and harness versions follow
Section [3.2.1](#S3.SS2.SSS1 "3.2.1 Evolution Process and Methods ‣ 3.2 Experiment Setup ‣ 3 Preliminaries ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution").
Test outcomes determine the reporting scores and best-Parent labels.
Candidate scores enter this analysis regardless of the original A-Evolve
admission verdict, so the diagnostic measures the changes produced from
each Parent.

Original Selection Rules. We apply the frozen HyperAgents, A-Evolve, and
GEPA *select* rules to each common four-Parent pool. HyperAgents uses
its native score-weighted sampling rule with Train evidence. A-Evolve
uses the one-pass Validation aggregate, and GEPA uses the corresponding
per-task Validation vector. Diagnostic metadata, child-count
initialization, and tie handling are fixed before these rules are
evaluated. AHE’s chronological selector requires a shared lineage order,
so AHE contributes a Parent artifact and the other three rules define
Original. Neither Test outcomes nor sibling Candidate results enter
these selection decisions or the analysis and mutation inputs.

Best Parent and Hit Rate. Let $`\mathcal{P}`$ be a four-Parent pool,
$`C_{P,j}`$ the Candidate from branch $`j`$ of Parent $`P`$, and
$`S(A)`$ the Test $`\mathrm{Avg}@8`$ of agent $`A`$. We define the mean
improvement and the best-Parent set as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\Delta(P)=\frac{1}{3}\sum_{j=1}^{3}S(C_{P,j})-S(P),\qquad\mathcal{B}=\arg\max_{P\in\mathcal{P}}\Delta(P).
``` |  | (4) |

For the three original rules $`\mathcal{S}`$, let $`\pi_{s}(P)`$ be the
probability that rule $`s`$ selects $`P`$.
Table [4](#S6.T4 "Table 4 ‣ 6.1 Select: Choosing Which Agent to Improve ‣ 6 Mechanisms: Tracing How to Discover And Retain The Optimization Gains ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution")
reports

|  |  |  |  |
|----|----|----|----|
|  |
``` math
H_{\mathrm{Original}}=\frac{100}{3}\sum_{s\in\mathcal{S}}\sum_{P\in\mathcal{B}}\pi_{s}(P),\qquad H_{\mathrm{Random}}=100\frac{|\mathcal{B}|}{4}.
``` |  | (5) |

A deterministic rule contributes zero or one before aggregation; a
stochastic rule contributes its probability of selecting a best Parent.
Each pool has a unique maximizer, giving a 25% random baseline.
Improvement remains signed, so the best Parent is the one with the
largest gain or smallest decline.

Current Performance and Improvement Potential. In all four pools, the
Parent with the highest Test score differs from the Parent with the
largest mean improvement. On general tasks, the best-Parent gain is
$`-2.0`$ points for the source-editable harness and $`+19.6`$ for the
outer-layer-only harness; on coding tasks, it is $`+4.0`$ and $`+1.5`$,
respectively. The original rules’ mean hit rate falls below random on
general tasks and exceeds it on coding tasks for both harnesses. These
comparisons motivate assessing selection by subsequent improvement under
a common generation process.

### D.2 Analyze: Component and Reminder Comparisons

Comparison Logic. Applying a Component to the matching Seed measures its
standalone effect; comparing that variant with Champion tests how the
remaining changes affect its benefit. Generic-reminder controls test
whether broad guidance reproduces those effects. These comparisons
inform *analyze* through the specificity of useful guidance and *mutate*
through the composition of changes.

A Recurring Specificity Advantage. Fifteen of sixteen Component variants
have higher reliability than their matching generic-reminder control,
and every Champion case has at least one such Component. The exception
is the isolated shell-adaptation Component in the reflection-centric,
source-editable coding-task case, at 64.0 versus 65.9 for the reminder;
its task-guidance Component instead reaches 67.3. Useful specific
changes are therefore not reproduced by general advice, even though not
every isolated Component helps. Reminders leave source-editable
reliability close to Seed on both task domains and lower
outer-layer-only reliability on both.

Case Composition. The eight Component cases cover both harness types and
task domains. Seven are implementation-centric; the reflection-centric
case uses the source-editable harness on coding tasks. Each case pairs
concrete Champion changes with a generic-reminder intervention on the
matching Seed.

Diagnosis Requirements. The specificity advantage motivates a diagnosis
contract that links failure explanations to execution traces, identifies
useful behavior to preserve, and states when the proposed correction
applies. We assess this contract through the changes and outcomes it
produces.

### D.3 Mutate: Component Effects and Interactions

Complete Revisions Usually Outperform Subsets. Six of eight Champions
have higher reliability than either isolated Component, including two
implementation-centric general-task cases and all four coding-task
cases. The exceptions are two other implementation-centric general-task
cases, one per harness type: the source-editable interface Component
reaches 34.4 versus 32.6 for Champion, and the outer-layer-only
orchestration Component reaches 37.2 versus 36.9. In the latter case,
skills alone also increase coverage to 72.2 versus 66.0, despite
slightly lower reliability. Conversely, an implementation-centric
coding-task Champion with the outer-layer-only harness reaches 72.6
reliability even though both isolated variants, at 69.1 and 68.0, fall
below Seed’s 69.9. These results motivate evaluating combinations
alongside isolated effects.

Interaction Definition and Estimates. For the four completed
$`\tau^{3}`$-Banking decompositions, let $`S_{0}`$, $`S_{A}`$,
$`S_{B}`$, and $`S_{AB}`$ denote $`\mathrm{Avg}@8`$ for Seed, Seed + A,
Seed + B, and Champion. We measure non-additivity by

|     |                                                 |     |
|-----|-------------------------------------------------|-----|
|     |
       ``` math
       I=(S_{AB}-S_{0})-[(S_{A}-S_{0})+(S_{B}-S_{0})].
       ```                                              |     |

A negative value means that the joint gain is smaller than the sum of
the two standalone gains. The Champions from AHE have interactions of
0.0 points for MiniSWE (95% task-paired interval $`[-4.5,4.9]`$) and
$`+2.1`$ for Codex ($`[-2.2,6.2]`$), with both intervals including zero.
The Champions from HyperAgents have negative interactions for MiniSWE
($`-6.3`$; $`[-11.7,-1.2]`$) and Codex ($`-6.6`$; $`[-12.6,-0.6]`$).
These cross-harness observations identify interference as a design risk
in the sampled implementation-centric general-task cases.

Compatibility Checks. Interaction estimates use the four verified
$`\tau^{3}`$-Banking decompositions, while Terminal-Bench 2 provides
targeted subset comparisons. Negative interactions motivate checking
whether a Candidate diff follows its diagnosis, includes necessary
dependencies, and preserves useful behavior. Coupled changes remain
permissible when their dependencies and rationale are explicit.

### D.4 Gate: Size-Normalized Best-Candidate Retention

Candidate Pools. For each benchmark, harness, and method, we freeze four
distinct artifacts from the same evolution lineage: the Seed, historical
Champion, last legal Candidate, and Candidate nearest 50% of cumulative
recorded evolution cost. Predeclared 25% and 75% checkpoints resolve
duplicates. This gives eight pools per benchmark. Each artifact has
eight-pass measurements on separate decision and reporting panels of 20
and 27 tasks for $`\tau^{3}`$-Banking, or 19 and 20 for
Terminal-Bench 2. These task panels follow the canonical diagnostic
splits.

Original Admission Policies. Original gate uses the initial
implementations in
Table [11](#A1.T11 "Table 11 ‣ Appendix A Operator Implementations of the Compared Methods ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution").
AHE, HyperAgents, and GEPA accept all eligible Candidates with completed
evaluations; A-Evolve requires strict mean improvement over its matched
Parent. The comparison supplies four legal, fully evaluated Candidates
to these fixed admission policies, with upstream proposal checks held
outside the replay.

Rules and Replay Contract. Each pool starts with Seed as incumbent and
processes the historical Champion, last legal Candidate, and
cost-indexed checkpoint in the frozen order. This is a diagnostic order,
not the historical generation order. An accepted challenger becomes the
incumbent for subsequent comparisons, while all previously retained
Candidates remain in the set. The constrained rule is unchanged from the
original replay: it requires strict mean improvement over the incumbent
on the same purchased evidence, with ties rejected, and

|  |  |  |  |
|----|----|----|----|
|  |
``` math
L=\frac{1}{|\mathcal{D}_{g}|}\sum_{x\in\mathcal{D}_{g}}\max\{0,\hat{p}_{\mathrm{inc}}(x)-\hat{p}_{\mathrm{cand}}(x)\}\leq 0.05,
``` |  | (6) |

where $`\mathcal{D}_{g}`$ contains 20 decision tasks on
$`\tau^{3}`$-Banking or 19 on Terminal-Bench 2, and each success
fraction uses passes 1–2. All policies receive the same 160 or 152
unique Candidate–task trials, respectively; eligibility-only gates need
not use their numeric scores. For A-Evolve’s original gate, the matched
parent is the current replay incumbent. A separate reporting panel of 27
or 20 tasks, respectively, uses eight passes to identify the empirical
best and never supplies decision evidence. Both benchmarks use the same
fixed order, strict-improvement rule, regression cap, and retained-set
definition.

Metric Definitions. For method $`m`$ and gate $`g`$, let
$`\mathcal{P}_{m}`$ be its four-Candidate input pool,
$`\mathcal{R}_{m,g}`$ the retained set including Seed, and
$`\mathcal{B}_{m}=\arg\max_{c\in\mathcal{P}_{m}}\mathrm{Avg}@8(c)`$ on
the reporting panel. The hit indicator is
$`H_{m,g}=\mathbf{1}[\mathcal{R}_{m,g}\cap\mathcal{B}_{m}\neq\varnothing]`$
and set size is $`N_{m,g}=|\mathcal{R}_{m,g}|`$. Retaining any tied
maximizer counts as a hit. The size-normalized score is
$`H_{m,g}/N_{m,g}`$; Seed ensures a nonempty retained set. Each
main-table cell reports $`100\sum_{m}(H_{m,g}/N_{m,g})/4`$, separately
for each benchmark and harness. This is the mean of per-pool ratios, not
the ratio of mean hit to mean size. Values are rounded to one decimal
place only after aggregation. All sixteen pools have a unique empirical
best. The score therefore equals the chance of drawing that Candidate
uniformly from the retained set; this interpretation does not prescribe
the method’s actual *select* policy.

reporting-panel best in fifteen pools, compared with six under

strong fallback from preservation of evolved gains.

measured scores. The constrained rule combines strict score improvement
with a regression cap. Comparing retained-set quality, size, and
membership motivates admission rules that balance improvement,
preservation, and fallback retention.

## Appendix E Operator Redesign: Implementation and Evaluation

### E.1 Evidence and Implementation Requirements

The analysis agent combines results from the Phenomenology,
Generalization, and Mechanisms analyses with source traces and reference
operators. It identifies recurring patterns across harnesses, task
domains, and evolution paradigms and links each finding to the relevant
comparisons and observed behavior. The resulting evidence report
supplies the rationale and applicability conditions for operator
revision.

Each proposed revision specifies the original rule, observed problem,
implementation change, expected effect, and validation checks. The
implementation agent receives this specification together with the
evidence report, reference code, input/output contract, and permitted
editing surface. It returns versioned code or instructions, evidence
links, applicability conditions, fallback behavior, and validation
records. Interface checks preserve the reference *rollout*, *validate*,
and *record* stages and each harness’s editing contract.

Diagnosis and Mutation Requirements. The *analyze* revision asks
diagnoses to identify the observed failure and useful behavior to
preserve. The *mutate* revision asks Candidate changes to implement that
diagnosis coherently and retain the required dependencies. These
complementary contracts connect execution evidence to the resulting
intervention.

Revision Objectives. The four revisions in
Table [8](#S7.T8 "Table 8 ‣ 7 Recipes: From Empirical Findings to Operator Design ‣ Beneath the Surface: What We Overlook When We Talk About Agent Evolution")
target complementary decisions. Regression-aware *select* uses
preservation evidence to resolve score ties, behavior-grounded *analyze*
links diagnoses to execution traces, dependency-aware *mutate* organizes
coherent changes, and cost-aware *gate* considers resource use at equal
scores. These objectives guide implementation, expert review, and
algorithm evaluation.
