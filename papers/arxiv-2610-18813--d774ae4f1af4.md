###### Abstract

Harness self-evolution revises an agent’s software scaffolding,
including prompts, memory, workflows, and executable components, while
keeping model weights fixed. We formalize a feedback-driven process in
which accepted revisions persist across runs. The framework separates
update targets from proposal and admission mechanisms. It distinguishes
changes to interpreted state from revisions to tools and code,
repository-level control logic, and plugin composition. We characterize
search through evolutionary optimization and examine its reliability
through continual PAC-learning. Under explicit assumptions, the analysis
yields an expected generalization bound, a retention bound conditional
on historical regression budgets, and a high-probability admission rule
using fresh, independent validation data. We examine how persistent
harness revisions affect knowledge sharing and organizational workflows,
with implications for scientific reliability, physical safety, and
institutional accountability. Cases from prior work illustrate
model–harness co-design, distributed execution, and plugin reuse.
Reliable deployment requires continual validation as task distributions
and evaluators change, with independent safeguards for learning, runtime
privileges, and consequential actions. We provide a comprehensive
66-page discussion of related work, theory, algorithms, evaluation,
applications, and the broader impact of Harness RSI, together with
continuously updated code and supplementary materials, at
https://github.com/zgcagi/Harness-RSI.

## 1 Introduction

As tasks and environments change after deployment, agents need
mechanisms for continued adaptation. Harness self-evolution uses
execution feedback to revise instructions, memory, and control logic
while keeping model weights fixed. Later runs load accepted revisions,
and the update mechanism remains available to learn from subsequent
experience
(Section [2](#S2 "2 Definition of Harness Self-Evolution ‣ Self-evolving Agent Harness")).
This process builds on recursive self-improvement and self-referential
problem solving in the context of contemporary
agents (good1965ultraintelligent; schmidhuber2003godel).

Adaptation can revise model weights or the harness governing prompts,
memory, workflows, and tools. Our focus on the latter rests on three
considerations. First, the harness directly shapes a fixed model’s
behavior, while reusable procedures preserve task constraints and
lessons from earlier failures (chan2025mlebench; zhao2024expel;
wang2024voyager). Second, harness revisions reuse an existing model
deployment, avoiding retraining and additional weight checkpoints. This
can reduce adaptation and maintenance costs and permits updates through
proprietary APIs without access to model weights. Third, instructions,
memory records, and code support direct inspection, version comparison,
and change tracking; attributing behavioral differences between model
checkpoints can require additional controlled experiments. We hold the
task model fixed to isolate harness self-evolution, with joint
model–harness evolution addressed in Section .

Existing methods vary in what is modified, how candidates are generated,
and how revisions are admitted (shinn2023reflexion; zhao2024expel;
wang2024voyager; zhang2025aflow; robeyns2025selfimproving). We first
classify the _update target_: the state modified and inherited by later
runs. Interpreted-state updates revise instructions, stored experience,
or task-level coordination over predefined capabilities; executable
revisions change capability implementations, runtime control logic, or
plugin-based service composition
(Section [3](#S3 "3 The Taxonomy of Harness Self-Evolution ‣ Self-evolving Agent Harness");
Figure [1](#S0.F1 "Figure 1 ‣ Self-evolving Agent Harness")). Empirical
selection alone does not establish generalization or retention. Section 
relates candidate search to evolutionary structures, then uses stability
and concentration results to state conditions for expected
generalization, bounded accumulated regressions, and high-probability
admission. Persistent state also determines how revisions propagate and
which consequences software recovery can address, motivating system
design choices, continual validation, and independent safety controls
(Sections –).

This work makes three contributions:

- •
  Definition and Operational Taxonomy
  (Sections [2](#S2 "2 Definition of Harness Self-Evolution ‣ Self-evolving Agent Harness")–[3](#S3 "3 The Taxonomy of Harness Self-Evolution ‣ Self-evolving Agent Harness")).

- •

  (Sections [3](#S3 "3 The Taxonomy of Harness Self-Evolution ‣ Self-evolving Agent Harness")

## 2 Definition of Harness Self-Evolution

#### Harness.

Following the model–harness decomposition (deepseek2026harness), we
define a harness $`H`$ as the software and configuration governing a
model $`M`$’s execution in a task environment $`E`$.
Table [1](#S2.T1 "Table 1 ‣ Harness. ‣ 2 Definition of Harness Self-Evolution ‣ Self-evolving Agent Harness")
summarizes seven runtime functions. Model adapters are part of $`H`$;
learned parameters are part of $`M`$. Execution produces a rollout,
which is scored by $`J`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       \tau\sim\operatorname{Run}(M,H,E),\qquad y=J(\tau).
       ```                                                  |     | (1) |

The final assessment $`J`$ includes scoring, outcome verification, and
the records that determine the result. Candidates may revise internal
critics or provisional checks within $`H`$, but cannot modify $`J`$.

| Component                        | Runtime role                                   | Mechanisms                                                                   |
| -------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------- |
| Agent loop and execution control | Controls execution and termination             | Model and tool calls; continuation, stopping, cancellation, and recovery     |
| Tool and skill orchestration     | Exposes callable capabilities and procedures   | Interfaces and registration; dispatch; skill loading and invocation          |
| Context construction             | Prepares each model input                      | System instructions, tool descriptions, dialogue history, and added context  |
| Memory and state management      | Preserves information across calls or sessions | Retrieval and reusable memory; persistence, resumption, and forking          |
| Context compaction               | Keeps model inputs within context limits       | Summarization; retention and trigger policies; pruning tool outputs          |
| Scheduling and coordination      | Assigns work across execution loops            | Delegation to subagents; task scheduling; background work                    |
| Execution infrastructure         | Enforces boundaries and records activity       | Sandboxes, permissions, approvals, storage, model adapters, logs, and replay |

Table 1: Runtime functions of a harness. An implementation may combine
these functions rather than assign each to a separate module.

#### Harness self-evolution.

Harness self-evolution uses execution experience to iteratively revise
$`H`$, aiming to improve task performance or resource efficiency while
holding $`M`$ fixed. At round $`k\geq 1`$, the incumbent $`H_{k-1}`$
generates a batch of $`b`$ rollouts, each including its trajectory,
outcome, and available feedback:

|     |                                  |                                                                                                       |     |     |
| --- | -------------------------------- | ----------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle\mathcal{B}_{k}`$ | $`\displaystyle=\{\tau_{k,i}\}_{i=1}^{b},\qquad\tau_{k,i}\sim\operatorname{Run}(M,H_{k-1},E_{k,i}),`$ |     | (2) |
|     | $`\displaystyle H_{k}`$          | $`\displaystyle=\operatorname{Update}(H_{k-1},\mathcal{B}_{k}).`$                                     |     | (3) |

The update operator combines diagnosis, proposal, assessment, and
admission. It may draw on historical feedback, archived candidates, and
additional validation rollouts. If no revision is admitted, the
incumbent is retained: $`H_{k}=H_{k-1}`$.

Each retained revision changes the state used for subsequent execution,
whose feedback can guide the next update. This lifecycle requires:

1.  1.  Operational feedback and update continuity. The system uses feedback
        from its own executions to construct or select revisions
        algorithmically, and retains the mechanism for further updates.
        Environments, automated assessors, and people may provide feedback;
        admission may require human approval.
2.  2.  Persistence across runs. Accepted revisions are stored and loaded in
        a subsequent run, allowing experience from one interaction to
        influence later execution.

These requirements concern repeatability: one observed update can
demonstrate the capability if both hold. Appending logs or compacting
context under fixed rules does not revise the harness; learning reusable
procedures or changing memory policies can. Revising the update
mechanism adds another level of recursion.

#### Scope and terminology.

_Self-evolution_ denotes the update process; _self-improvement_ denotes
a gain established by comparison. We use _harness RSI_ (recursive
self-improvement) as the name of the research area, without assuming
that each revision helps. Weight-only adaptation and scaffolds without
an update mechanism fall outside this scope. When a system also trains
weights, we examine its harness updates with the task model held fixed.

## 3 The Taxonomy of Harness Self-Evolution

EURISKO’s heuristic revision and the Gödel Machine’s proof-governed
self-rewriting established distinct antecedents of harness
self-evolution (lenat1983eurisko; schmidhuber2003godel). Contemporary
methods use empirical feedback to revise prompts, consolidate persistent
memory, and search workflow specifications around a fixed
model (agrawal2026gepa; fernando2024promptbreeder; zhao2024expel;
wang2025workflow; zhang2025aflow). The interpreted/executable
distinction concerns the edited artifact’s role, not its programming
language. Workflow revisions remain interpreted when they change
task-level sequencing or routing through fixed coordination interfaces
over predefined operators. This includes code that only composes those
operators; revising operator implementations or the runtime mechanisms
that enact coordination constitutes an executable revision, even under
an unchanged executor.

We organize executable targets into component implementations,
repository-level control logic, and plugin composition. The first two
describe mutation scope; the third describes how components and runtime
services are bound and replaced. Plugin composition can span component
implementations and repository-level logic, so a revision may belong to
more than one category. Classifying the update target does not determine
whether a method satisfies the feedback, continuity, and persistence
requirements in
Section [2](#S2 "2 Definition of Harness Self-Evolution ‣ Self-evolving Agent Harness").

### 3.1 Tools and Code Patches

Component-level revision confines mutation to callable procedures or
designated modules while keeping surrounding orchestration outside the
editable surface. Where entry points and I/O contracts remain fixed,
candidates replace component implementations; tool synthesis may instead
extend the callable interface. Skill libraries retain executable
functions for later retrieval and composition (wang2024voyager;
yu2025polyskill); patch-based architectures, including Self-Harness,
HarnessCompass, and Agentic Harness Engineering, constrain trace-guided
mutation to selected components (zhang2026selfharness;
zhang2026harnesscompass; lin2026agentic). Editing memory-management
functions changes the harness machinery, whereas curating stored entries
changes its interpreted state (zhang2025memevolve). Within this
boundary, candidate archives preserve alternatives for subsequent
search (luo2026harnessbank), while protocol perturbations test whether
an evolved harness’s gain over the initial harness survives changes in
assessment conditions (zhu2026badgenius). Stable interfaces facilitate
replacement and local checks, but changed outputs or shared state can
propagate regressions beyond the edited module.

### 3.2 Repository and Runtime Logic

Repository-level search exposes context construction, orchestration
loops, execution hooks, recovery, and termination to revision. The
boundary concerns control over interactions among harness components,
rather than the number of files edited. Whole-agent synthesis searches
complete control programs, while repository evolution retains
implementation lineages for later selection and
revision (hu2025automated; lee2026metaharness; robeyns2025selfimproving;
zhang2026darwin; zhang2026darwinx; wang2025huxley). Changes to shared
context, scheduling, or recovery can alter the inputs and execution
assumptions of otherwise unchanged components. This coupling motivates
edit constraints, transfer-oriented admission, and deployment
checks (xia2026rrsi; cai2026moss). Archive membership preserves a
candidate for further search; adoption additionally requires promoting
the selected program into the runtime used by later tasks. Extending
mutation to the optimizer’s prompts, hooks, and tools makes the update
mechanism itself evolvable (wang2026verse). An exported program
satisfies the continuing lifecycle only if its deployment retains an
update mechanism.

HarnessOpt extends the SkillOpt-Lite study from skill editing to runtime
revision, improving spreadsheet previews, output checks, and recovery
after tool failures (shen2026skilloptlite). On SpreadsheetBench

### 3.3 Everything Is a Plugin

Plugin architectures organize mutation through declared interfaces,
dependency constraints, and lifecycle operations. The editable object
may be a component implementation or a binding that determines which
implementation supplies a runtime service, such as memory storage, tool
dispatch, or the agent loop. Composition here therefore reaches beyond
task-level routing among fixed operators. Kernel-defined substrates
specify how these services are connected, mounted, and
replaced (deepseek2026harness; shi2026programming); feedback-driven
systems revise typed primitives, versioned resources, or scoped modules
under interface and validation constraints (chen2026harnessx;
li2026argus; zhang2026autogenesis; wu2026modularrsi). This organization
can expose both local capabilities and core runtime services while
retaining explicit constraints on their composition. Everything Is a
Plugin (EIP) extends it to capabilities generated, validated, and
mounted during operation. Interface contracts support compatibility
checks and component replacement; they do not establish behavioral
isolation or safe admission. Adoption still requires validation of the
composed behavior.

Using DSH Everything, a Codex plugin lets the agent generate tools
during execution and retain them for later tasks (shen2026dsheverything;
pan2026eip). In a simulated office workload, spreadsheets from different
company regions vary in language and content but share similar
calculations. Codex creates batch-lookup and summarization tools:
first-task tool calls fall from 13 to 3, while wall time rises by 54.9%
and tokens by 15.7%. A separately reported cumulative series shows
savings from the second task, reaching 110,351 tokens and 22.97 s after
five tasks
(Table [3](#S3.T3 "Table 3 ‣ 3.3 Everything Is a Plugin ‣ 3 The Taxonomy of Harness Self-Evolution ‣ Self-evolving Agent Harness")).
