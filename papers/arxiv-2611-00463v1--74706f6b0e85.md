###### Abstract

Agent harnesses govern how language models act in an environment;
designing their policies by hand is difficult, while automated
techniques require representative datasets and costly executions. We
present Exo, an agent runtime architecture for safe learning during
ongoing work that collapses the optimization loop into task execution,
allowing agents to revise both their harness and their strategies for
further improvement. A minimal protected mechanism layer preserves
execution history and governs policy activation while the harness
evolves through inspectable code changes. On long-running objectives in
an open-world game, Exo reduces model cost by 12–53% relative to Codex
and Pi in standalone runs and 45–82% in transfer runs, while matching
task completion rates. Compared with the same starting policy without
the ability to edit policy, Exo reduces held-out model cost by 35–61% on
AppWorld and SREGym with comparable correctness, cutting AppWorld’s mean
task time by 13% and SREGym’s median diagnosis time by 35%. On Continual
Learning Bench coding tasks, model cost including learning falls by 14%,
with both policies resolving every issue.

## 1 Introduction

Agents have risen rapidly as a new class of application workload, with
wide adoption in developer tools claude-code; codex, personal assistants
openclaw; hermes, and enterprise workflows pace-insurance; resolve-ai;
sierra-siriusxm. These applications combine a language model with a
specialized _harness_ whose policy constructs context, provides tools,
manages memory, and coordinates actions in an environment. Adapting
agents to each domain requires adapting these harness policies: a
network operations agent needs different tools, context, and execution
policies from a coding agent. Harness engineering makes this
specialization possible without changing the model’s weights, but
developers must decide which policies suit each task.

Building effective harness policies requires substantial development
effort. Developers must choose prompts, decide what information to
retain and how to assemble context, and select which tools and skills to
expose. Making these choices by hand is time-consuming and relies on
domain expertise and intuition. Agent-building and optimization tools
aim to automate this process on benchmarks: Meta-Harness searches over
harness implementations lee2026metaharness, GEPA optimizes prompts by
reflecting on execution trajectories agrawal2025gepa, AlphaEvolve and
SkyDiscover support evaluator-guided program optimization and synthesis
skydiscover2026; novikov2025alphaevolve, and industry offers similar
solutions pace2026tempo. These systems organize development into an
external optimization loop that proposes candidate harnesses, executes
them on benchmarks, and uses results to guide subsequent revisions.

However, external optimization depends on evaluation tasks that may be
unavailable and repeated executions that are increasingly costly, while
leaving harness policies fixed during subsequent work. In new domains,
benchmark tasks and faithful evaluation environments are often
unavailable; one study reports that 75% of interviewed teams evaluate
their agents without benchmark sets pan2025map. Even when benchmarks
exist, the trend toward longer task horizons increases the cost of
evaluating candidates through task completion, with some reported
executions already lasting days or weeks openai2025codexmax;
lin2026selfdriving; carlini2026compiler. Benchmarks can also become
outdated as the environment changes. Finally, the resulting harness
policies remain fixed during execution, even when an agent’s runtime
experience may expose a possible gap. Taken together, these challenges
can make external agent-building techniques impractical in real-world
settings or limit their effectiveness.

In this work, we propose an alternative approach to harness adaptation:
equip a minimal agent to inspect and edit its own harness, then let it
use experience from ongoing work to revise and adapt itself at runtime.
As we explain in
[Section 3.1](#S3.SS1 "3.1 Collapsing the Optimization Loop ‣ 3 Approach"),
two properties enable this departure from traditional external adaptive
control: the agent can inspect and reason about the code implementing
its own harness, and it can implement policy revisions with the same
code-editing tools it uses for ordinary task actions. This enables us to
_collapse the optimization loop_: the agent chooses both task actions
and changes to how it acts ([Fig. 1](#S1.F1 "In 1 Introduction")).
Adaptation need not wait for retrospective review of completed execution
traces: with self-editing available as an explicit action, the agent can
explore alternative behaviors, assess their effects, and decide whether
to incorporate them into its harness during the task. This design allows
for the very policy the agent uses to govern its action to evolve at
runtime with experience, including to improve its ability to improve
itself.

agent builds a diagnostic tool and revises context assembly while

However, enabling agents to edit themselves introduces two core systems
challenges. First, the resulting _fate-sharing_ between the optimizer
and the running system means that a faulty edit can disable both the
agent and the logic needed to diagnose and repair it. Second, self-edits
can erase unprotected state – execution history, memory, and task
artifacts – destroying accumulated progress and the record of past
actions, successes, and failures. An agent cannot repair itself if it
cannot execute, nor learn from experience it has lost.

To address these, we present Exo, an agent runtime architecture for
learning and adaptation during ongoing work, with mechanisms to support
safe evolution of an agent’s harness policy. Our key idea is to
partition the agent into an evolvable policy layer and a minimal set of
protected mechanisms necessary for safe operation. As we show in
[Section 4](#S4 "4 Design"), these mechanisms preserve execution history
and prior state across policy revisions and keep recovery authority
outside the editable layer. Inspired by operating systems work on
separating policy from mechanism, particularly exokernels
engler1995exokernel, we expose primitive interfaces that leave as much
policy as possible in the evolvable layer, including how the agent uses
its experience and improves itself. Exo’s architecture makes learning
observable and adaptable while limiting the damage a faulty revision can
cause. The agent can examine its execution history, including outcomes,
model costs, and cache use, to identify improvements grounded in the
environment where it actually works. It can use that evidence to revise
both its task policy and its optimization strategy. Throughout this
process, protected history and snapshots preserve the experience and
recovery points needed to continue learning after a failed revision,
while an independent guardian controls when revised harness policies
take effect ([Section 4](#S4 "4 Design")). The resulting adaptations are
interpretable: they appear as explicit changes to harness code that
developers can inspect.

We evaluate two benefits of runtime learning: improving efficiency
within complex tasks and transferring the resulting specialization to
similar tasks. We study long-task adaptation in RuneScape, a dynamic,
open-world multiplayer role-playing game, across combat, crafting, and
currency objectives. In standalone runs, Exo completes combat and
crafting at 12–53% lower model cost than Codex and Pi and earns 44–125%
more currency per model dollar. In combat transfer runs on fresh
accounts, the cost reduction is 72–82%. We also compare Exo to the same
starting policy without the ability to edit policy on AppWorld, SREGym,
and Continual Learning Bench (CLB) coding tasks
asawa2026continuallearningbench. On AppWorld, Exo reduces held-out cost
by 61% at the same observed 96.9% pass rate and total cost including
learning by 43%. On 20 held-out SREGym incidents, it reduces median
diagnosis time and test cost by 35%, and model rounds by 38%. On CLB, it
uses 15% fewer shell steps and 14% less model cost including reflection,
with matching issue resolution rates across five runs.

In this work, we make three contributions:

- •
  We propose runtime harness self-editing and identify the properties
  that allow the running agent to revise both its task policy and its
  improvement strategy, collapsing the optimization loop.
- •
  We identify the challenges of runtime self-editing and address them
  through an architecture that separates evolvable policy from protected
  mechanisms for preserving state and controlling policy changes.
- •
  We implement and release Exo as open-source software exo2026, and
  evaluate it across open-world objectives and three graded benchmarks,
  demonstrating efficiency gains during ongoing work and reuse of
  learned policies on subsequent tasks.

## 2 Background

We first define agents and their policy, then describe the challenges of
adapting policies to real-world workloads.

### 2.1 Agents and Harnesses

An _agent_ couples language-model inference to an environment through a
repeated interaction loop yao2023react. We view the _harness_ as the
scaffolding surrounding the model that (1) assembles the model’s input
and (2) executes and observes actions on the environment
anthropic2025contextengineering, which is most often a computing
sandbox. A _task_ is a unit of work with an objective and completion
criteria, which may be implicit. Task granularity varies: an SRE agent
might manage one software rollout or a month’s availability SLO across
all rollouts.

Harness policy. We use _policy_ to refer to all of the programmable
rules and procedures governing how an agent uses its model, state, and
environment. These include tool implementations and selection;
prompting; context assembly and compaction; memory and skill indexing
and retrieval; and external integrations, such as service adapters and
task scheduling. These choices are encoded in harness code, prompts,
configuration, and reusable skills. Policy also includes the strategy
for deciding when and how to attempt further improvements.

Though tools in policy and agent-written code in the environment are
similar in spirit (in what they can accomplish), they differ in how they
are managed by the agent. Policy-level tools are often wired directly
into context assembly, whereas code in the environment must be
remembered and managed entirely by model reasoning.

### 2.2 Challenges in Harness Adaptation

Automated optimization methods develop harness policies through an
external loop that proposes candidates, executes them on evaluation
tasks, and uses the results to guide revisions agrawal2025gepa;
lee2026metaharness. Three limitations motivate a different approach.

Evaluation datasets are difficult to obtain and maintain. New domains
often lack representative task sets and faithful evaluation
environments. In a study of production agents, 75% of interviewed teams
evaluated without benchmark sets pan2025map. Constructing a benchmark
requires capturing relevant tasks, expected outcomes, and the
environment in which actions take effect. Even then, changing services,
interfaces, and user requirements can make those tasks and environments
outdated krentsel2026twogaps. An optimizer may consequently improve
performance against a proxy that no longer reflects reality.

Longer tasks increase evaluation cost. Evaluated task horizons are
increasing metr2026horizons, with software-building and theorem-proving
projects already spanning weeks carlini2026compiler;
openai2026navierstokes. As executions lengthen, evaluating successive
candidate policies through complete task runs becomes more expensive.
Waiting for task completion also delays feedback, even when an
inefficient procedure or recurring failure becomes apparent much
earlier.

Fixed harness policies limit runtime adaptation. Even a policy optimized
for a representative workload can encounter new patterns during
execution. A fixed harness can react to observations and retain
memories, but its procedures for constructing context and executing
actions remain unchanged. For example, an agent may recognize that most
diagnostic output is irrelevant while its context-construction policy
continues to include it. Without a path from that observation to a
policy revision, the same inefficiency can recur throughout the task.

## 3 Approach

To address the challenges raised in [Section 2](#S2 "2 Background"), we
propose an alternate method of policy creation: runtime harness
adaptation, where the running agent uses experience from ongoing work to
revise the policy governing that work. This brings task actions and
policy revisions into the same decision process.

### 3.1 Collapsing the Optimization Loop

The external optimization systems described in
[Section 2.2](#S2.SS2 "2.2 Challenges in Harness Adaptation ‣ 2 Background")
can be viewed through the lens of control theory as adaptive control
loops astrom2008feedbacksystems. In a traditional adaptive control
model, shown in [Fig. 2](#S3.F2 "In 3 Approach")(a), the controller
(harness policy) maps an objective $`r`$ and observations of the
environment $`y`$ to task actions $`u`$ (tool calls). An optimizer then
observes the same execution and produces an update $`\theta`$ to the
controller policy.

Harnesses have two special properties that allow us to bring the
optimizer into the core policy itself. First, a harness revision can be
realized in the same action domain as ordinary task work, which we refer
to as optimizer symmetry. More precisely, the update $`\theta`$ can be
produced by a sequence of actions in $`\mathcal{U}^{*}`$: the agent can
inspect source, edit files, run tests, and request activation using
tools already exposed through $`u`$. Revision actions therefore become
choices available to the core policy alongside actions that act directly
on the task.

Second, the harness is _operationally homoiconic_: its policy is code,
and that code is represented as files the agent can observe and
manipulate with its code-editing tools. The object being optimized is
consequently available as data in the optimizer’s environment. Together,
same-domain actions and editable policy representation allow the
optimizer’s proposal logic to move inside the harness, producing the
collapsed loop in [Fig. 2](#S3.F2 "In 3 Approach")(b).

Because the policy governing when and how to revise the harness is
itself editable, the agent can revise both its task behavior and its
strategy for further improvement. Each successor can adopt a new policy
while retaining the ability to revise itself further, independent of
model retraining.

### 3.2 State and Replacement Contracts

Bringing revision into ongoing execution creates two systems challenges.
First, it introduces _fate-sharing_ between core logic and optimizer
logic, meaning a faulty edit can disable both the agent and the logic it
would use to diagnose and repair itself. Second, edits to _unprotected
state_ can erase accumulated progress and execution evidence, including
records of failed revisions.

To address these two critical failure modes, we turn to system
architecture. We first model the system’s runtime state and transitions,
then specify the properties the architecture must enforce as the agent
revises its policy.

State and transitions. We call the replaceable program that implements
the agent’s harness policy the _executor_. We take runtime state at step
$`t`$ to be $`s_{t}`$, and let a protected mechanism $`K`$ apply the
executor’s chosen operation $`a_{t}`$:

|     |                           |                                          |     |     |
| --- | ------------------------- | ---------------------------------------- | --- | --- |
|     | $`\displaystyle s_{t}`$   | $`\displaystyle=(d_{t},e_{t},\pi_{t}),`$ |     | (1) |
|     | $`\displaystyle s_{t+1}`$ | $`\displaystyle=K(s_{t},a_{t}).`$        |     | (2) |

Here $`d_{t}`$ contains durable data, including history, memory, and
artifacts; $`e_{t}`$ contains sandbox files, dependencies, and
processes; and $`\pi_{t}`$ identifies the active executor implementation
and configuration. Operations may update data, act in the sandbox, or
request replacement. In order to stay protected, the storage and
replacement rules in $`K`$ must remain outside the executor’s editing
authority.

Storage contract. Let $`H(d)`$ denote canonical execution history: the
record of messages, tool calls and results, and policy-replacement
events. The storage contract requires this history to be append-only:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       H(d_{t})\preceq H(d_{t+1}),
       ```                          |     | (3) |

where $`\preceq`$ denotes the prefix relation. Existing records cannot
be overwritten or deleted. Memory and task artifacts may have mutable
current values, but updates must retain prior versions for recovery.
These rules preserve evidence without prescribing how the policy uses
it.

Replacement contract. Editing source produces an arbitrary candidate
$`\pi^{\prime}`$, which may have any sort of behavior including
crashing; activating this as the active policy must therefore require a
check that lies outside of the policy itself. We call this mechanism the
guardian $`G(s_{t},\pi^{\prime})`$, which evaluates to $`\{0,1\}`$.
Thus, for a replacement request,

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\pi_{t+1}=\begin{cases}\pi^{\prime},&\text{if }G(s_{t},\pi^{\prime})=1,\\
\pi_{t},&\text{otherwise}.\end{cases}
``` |  | (4) |

Policy replacement preserves durable data and leaves the sandbox
unchanged, while appending replacement events to history; the acceptance
decision may inspect both.

Taken together, these contracts enable the agent to revise its policy
with maximal flexibility while ensuring that edits cannot erase
protected history or bypass replacement checks. Notably, this protection
holds regardless of how the agent chooses its edits, but does not on its
own guarantee improved behavior or continued progress. We give the
preservation proof and discuss these guarantees’ assumptions and limits

The goal of Exo’s architecture is to implement the state and replacement
contracts in
[Section 3.2](#S3.SS2 "3.2 State and Replacement Contracts ‣ 3 Approach")
to provide safety, while enabling the agent to self-edit at runtime with
as much freedom as possible to change how it works. We now describe our
architectural design decisions to enable this.

### 4.1 Partitioning Policy and Mechanism

We consider agent architecture through the lens of a computing system.
The traditional view of harnesses combines two different concerns: the
infrastructure required to serve an agent, including durable history,
privileged resources, and sandboxes; and the policies governing how the
agent thinks and acts, including prompt assembly, compaction, memory,
and tools. This makes self-evolution difficult to do safely, as the
evolvable policy is not distinct from protected resources.

Our key guiding design decision is to partition the harness into two
distinct layers: a protected mechanism layer and an editable policy
layer, akin to the kernel and userspace split in operating system (OS)
design. To determine what functionality should go in each, we draw on
inspiration from Exokernel engler1995exokernel, aiming to isolate the
minimal set of functionality needed for our safety properties, and to
expose it at the lowest level of abstraction to maximize the space of
behaviors that can be expressed above it.

We show our chosen partition in [Fig. 3](#S4.F3 "In 4 Design")(a). Below
the boundary, Exo protects the state and mechanisms needed to preserve
continuity across self-edits. These are the canonical execution history,
which is exposed through an append-only queryable interface annotated
with costs, along with a versioned artifact store that can hold
arbitrary data such as memory, skills, or sandbox snapshots. Finally,
Exo provides the protected mechanisms for credential storage, sandbox
API, and the independent guardian mechanism that controls activation of
replacement executors.

All other harness functionality is expressed in the policy layer, which
we call the executor. These include tool implementations and selection;
context assembly and compaction; prompting; memory and skill indexing
and retrieval; and external integrations, including service adapters and
task scheduling. For example, the protected mechanism preserves
execution history, while the policy decides which parts of that history
are included in the prompt sent to the model. The agent can revise any
policy code above the protected boundary, including its tools, model
calls, compaction, and the procedures governing when and how it attempts
further improvements.

### 4.2 Enabling Runtime Self-Editing

To enable runtime self-editing on this architecture, we take two steps:

1.  (1)
    Mount the executor code in the sandbox, allowing the agent to
    inspect and edit it with its existing tools.
2.  (2)
    Provide a tool to request executor replacement through a protected
    guardian, which builds the candidate and activates it only if it
    passes a guardian function $`G`$.

The agent can thus inspect and edit its own implementation during task
execution, then request activation of the revised policy
([Fig. 3](#S4.F3 "In 4 Design")(b)). The guardian runs independently of
the executor, and replacement requests and outcomes are recorded in the
event history. Our default guardian checks build success; richer
implementations could evaluate candidate behavior over a longer
observation period ().

Independent rollback.  Exo’s split also enables independent rollback of
executor policy, durable agent state, and environment sandboxes.
Executor rollback restores an earlier code version and reactivates it
through the guardian. Append-only history supports forking from an
earlier event, while versioned artifacts retain earlier state for
recovery. The sandbox API separately supports snapshotting and restoring
the task environment. These operations preserve the original execution
record, allowing the agent to retain evidence of what it tried even
after a rollback. Snapshot scope and limits on reversing external
effects are discussed in .

### 4.3 Internal Legibility

To guide self-improvement, an agent needs to inspect both its past
behavior and the costs it incurred. Exo exposes execution history for
retrieval and analysis, annotating model-message events with cost and
token counts, including cached tokens. This makes earlier execution
available for inspection even when it is no longer included in the
model’s context. Policy code can surface these annotations alongside the
messages it retrieves to assemble context, or through tools that
summarize execution statistics. Our implementation provides a reporting
tool covering spending, cached input share, repeated tool calls, and
context composition. For example, the agent can inspect whether a
context revision reduces input tokens while preserving cache reuse.

Implementation and deployment. We have implemented and released Exo as
open-source software exo2026. The core runtime architecture, including
protected mechanisms, totaled $`\sim`$20,000 lines of code, and the base
starting policy comprises $`\sim`$1000 lines. The runtime is deployed in
production, having served O(10k) diverse tasks over O(5m) messages.

## 5 Evaluation

We evaluate two facets of Exo’s runtime learning: (1) whether
specialization improves efficiency within an ongoing task, and (2)
whether the resulting tools and policies remain useful on subsequent
tasks. We first compare Exo with existing harnesses on long-running
open-world objectives, then examine how specialization develops and
transfers. Finally, we evaluate efficiency and correctness across graded
application, infrastructure, and coding tasks.

### 5.1 Experimental Setup

Comparisons. Our open-world experiments compare Exo, Codex
openai2026codexcli, and Pi zechner2026pi using gpt-6.1-sol at medium
reasoning effort across different objectives. For AppWorld, SREGym, and
Continual Learning Bench (CLB) coding, we use gpt-5.6-sol and compare
Exo to the same starting policy without the ability to edit policy. This
control includes standard tools for coding, shell access, subtask
planning, and memory and is labeled *Control* in our figures. We
describe each workload’s task sequence and feedback below.

Metrics. We report task outcomes alongside model cost and time. For
finite game objectives, we measure cost to completion and progress per
model dollar over a fixed window. All costs use common token pricing
that accounts for caching. For graded tasks, we report correctness and
execution efficiency, distinguishing cost on held-out tasks from total
cost including learning and reflection. A *standalone run* starts
without retained agent state; for game objectives, a *transfer run*
repeats the objective on a fresh account while retaining agent state.

### 5.2 Specialization During Open-World Execution

We first examine runtime specialization in a long-running task in an
emulated environment based on RuneScape, an open-world multiplayer
role-playing game runescape. Agents act through the common RS-SDK
interface bittker2026rssdk to pursue objectives, starting from new
accounts. We select three distinct objectives: training all combat stats
to their maximum; accumulating currency through any available strategy;
and directly crafting a challenging item, the adamant platebody, which
requires resource gathering and training, without buying the finished
item. These objectives require hours of coordinated action across a very
large open world with a dynamic environment of monsters and shared
resources. Combat runs were performed on a public server with
1,200-1,500 other players and bots. The other tasks reported were run on
a shared private server due to public server overload. All agents run
concurrently in the same game world.

Exo completes the finite objectives at lower model cost than Codex and
Pi, and earns more currency per model dollar.
[Fig. 4](#S4.F4 "In 4.3 Internal Legibility ‣ 4 Design") compares
standalone and transfer outcomes; provides a tabular view of these
outcomes. In standalone combat, Exo spends \$3.71, versus \$7.26 for
Codex and \$7.95 for Pi; in crafting, it spends \$2.99, versus \$3.90
and \$3.41. Together these yield 12–53% lower completion cost. For
money-making, Exo earns approximately 332k coins per dollar, versus 231k
and 148k, an improvement of 44–125%. All arms finish the finite
objectives.

Much of the early work for Exo builds and revises a reusable combat tool

minutes. We call this early expense the ”specialization cost”, where
self-improvement pays an early premium for improved later performance
within the standalone execution.

Exo’s specialization appears as concrete changes to its tools, action
procedures, and context policy.
[Fig. 5](#S5.F5 "In 5.2.1 Looking Inside Runtime Specialization ‣ 5.2 Specialization During Open-World Execution ‣ 5 Evaluation")(c)
highlights three of the sixteen self-edits Exo made at runtime. At A,
Exo creates train_combat, which batches melee actions and reports
experience gained and observations. After repeated failures to attack a
target, it revises the tool at B to skip stalled targets and retreat
earlier. At C, it builds combat_cycle, which selects the lowest uncapped
melee skill, trains for 180 seconds, collects nearby resources, and
stops on low health. Later, it changes context assembly to retain only
four earlier turn summaries, leaving older strategy in durable memory.
These edits replace repeated model decisions with reusable procedures
and change how the agent presents its experience to the model, which
result in meaningfully more efficient agent behavior.

Specialization may not repay its cost when work offers little reuse. We
selected one additional objective representative of the least repetitive
class of task: completing as many quests as possible. Each quest is
completed once and requires largely distinct steps, items, and
locations. Across three runs per arm, Exo averages \$0.28 per quest
point, versus \$0.24 for Codex and \$0.21 for Pi. Exo builds reusable
dialogue tools, but the quest-specific work leaves little opportunity to
amortize specialization cost. Thus other harnesses without
self-reflection or improvement operate more cheaply for such a task.

### 5.3 Transfer of the Specialized Harness

The tools and policies learned during standalone runs remain useful when
the agent repeats the objectives on fresh accounts. All three arms
retain their history and sandbox state; Exo also carries its
self-modifications. As shown in
[Fig. 4](#S4.F4 "In 4.3 Internal Legibility ‣ 4 Design"), Exo’s combat
cost falls from \$3.71 to \$1.92, versus transfer costs of \$6.87 for
Codex and \$10.89 for Pi. Its crafting cost falls from \$2.99 to \$0.88,
versus \$1.89 and \$1.61. Exo thus completes these transfer objectives
at 45–82% lower model cost than the other harnesses. Its own efficiency
