# Re-executing Coding-Agent Evaluations: Unchanged Decisions and Unresolved Policy Risk

Tianyu Ding Affiliation: Fei Jiang   Lei Yang   Boya Yu    Yaocheng Tong
Affiliation: Independent Researchers    Muzhi Yang
Affiliation: Correspondence: [tid16@pitt.edu](mailto:tid16@pitt.edu)

###### Abstract

Executable tests grade large language model (LLM) coding-agent patches
for leaderboards, rewards and self-improvement. Two preregistered
re-execution studies returned negative results. SWE-bench Pro v1’s
offline option rejected none of 59 accepted Go patches whose grading
configuration changed. Their exploratory, unweighted upper confidence
limit is 4.95% under candidate independence, leaving a 3% exposed-patch
risk unresolved; the preregistered estimator uses inverse
sampling-probability weights. An extension was inconclusive. In a
selected stratum, a reconstructed module cache built from the reference
solution’s dependencies rejected accepted alternatives from four models
that passed with their own dependencies. Re-executing 1,929 selected
agent-version/task evaluations from the Darwin Gödel Machine’s archive
preserved best-agent selection and system-variant ranking, with search
history and scores of evaluations not rerun fixed. Exploratory host,
image and adapted-grader comparisons also preserved them. Seven of 23
disagreements with archived verdicts did not recur on a second host;
rebuilt images changed 16 three-run majority verdicts (0.83%) under
four-CPU execution. We provide an evidence-to-claim summary, lessons for
grader audits and an anonymous replication package. These results
concern accepted patches and fixed-history decisions; general policy
safety and adaptive-learning robustness require broader evaluations.

## 1 Introduction

Executable tests decide whether a large language model (LLM) coding
agent solved a task. Their verdicts feed leaderboards, agentic
reinforcement learning (RL; Du et al., 2026) and self-improvement
selection (Zhang et al., 2026; Wang et al., 2025). Verdicts depend on
patches, grader images, caches, network policy, reference test lists and
execution resources. Network restrictions close routes agents used to
retrieve solutions (Huang et al., 2026b); packaging dependencies removes
reliance on external network state (Du et al., 2026). Passing the
reference (gold) patch validates only that solution: the same
configuration may reject another accepted patch. We test the
consequences for recorded verdicts and decisions.

We preregistered two questions, sealing their protocols, code and inputs
in pushed commits before confirmatory data collection. Study 1 replays
officially accepted SWE-bench Pro v1 patches (Deng et al., 2026) under
its evaluator’s offline option. It tests whether confirmed reversible
losses reach 3% on policy-valid tasks. Study 2 re-executes the SWE-bench
evaluations released with the Darwin Gödel Machine (DGM; Zhang et al.,
2026; Zhang et al., 2025). It tests whether rerun instability or central
processing unit (CPU) contention changes the best recorded agent version
or ranks its three system variants (arms) differently. Both protocols
predicted negative outcomes. Study 1 warned that a negative result would
not establish absence of an effect; Study 2 disclosed a separate
project’s pilot with no verdict flips on 194 evaluations of DGM’s best
agent version.

Study 1 observed no losses among 59 exposed Go patches on 25 tasks; the
other 222 evaluable patches faced identical configurations. The
exposed-sample upper limit is 4.95% under candidate independence; the
extension was inconclusive. A reconstructed gold-bound cache rejected 6
of 15 accepted patches in a selected stratum, all recovered with their
own allowed dependencies. Study 2’s recorded endpoints remained
unchanged; 23 archived verdicts differed from all six original-host
reruns, and seven of those disagreements did not recur on a second host.

We provide an evidence-to-claim summary and replication package. The
selected cache cases provide existence evidence on accepted patches for
the dependency-coverage constraint documented in Lego-RL’s gold-cache
tooling (LegoX, 2026).

## 2 Background and hypotheses

#### Executable tests as rewards

Coding benchmarks and the RL environments built from them score a
solution by applying the agent’s patch to a repository snapshot and
running tests in a container: SWE-bench requires originally failing
tests to pass (FAIL_TO_PASS) and originally passing tests to keep
passing (PASS_TO_PASS) (Jimenez et al., 2024), SWE-rebench validates
tasks in containers with an image per task (Badertdinov et al., 2025),
SWE-bench Pro targets harder, long-horizon problems (Deng et al., 2026),
Multi-SWE-bench adds languages (Zan et al., 2025), and Lego-RL uses the
verdict as a terminal binary reward (Du et al., 2026). The verdict comes
from the tests _and_ from everything around them: the image, the
dependency resolver, the network, and the limits on CPU, memory and
time.

#### Hardened graders and their validation

Two pressures push graders offline. Packages downloaded at grading time
make results depend on mutable external repositories (Silva et al.,
2024a), and open egress lets an agent fetch the upstream fix: DSec
reports agents that used module proxies to retrieve code from
GitHub (Huang et al., 2026b). Lego-RL packages test dependencies into
task images (Du et al., 2026), SWE-rebench V2 pre-builds task
environments (Badertdinov et al., 2026), the SWE-bench Pro evaluator
offers a no-network flag while the maintainers’ latest protocol keeps
network access because some Go tasks fetch modules at test time (Scale
AI, 2026), and SWE-Bench Pro Verified blocks code-hosting domains but
keeps the dependency services builds need (Zheng et al., 2026). Such
designs can be validated by checking that the gold patch still passes
and the empty patch (no agent changes) still fails. A gold-bound
hermetic grader uses the gold patch’s dependencies without network
access; an alternative needing another version can fail to build and
receive a wrong fix’s verdict. Lego-RL’s tooling states this limit for
SWE-bench Pro tasks whose gold patch bumps a Go module: its cache is
resolved from the gold module manifest (go.mod), so “a correct fix that
bumps a module to a different version than gold still cannot download
it” (LegoX, 2026). In RL the same error assigns a failed rollout’s
reward to a solved one. Prior work models false-negative rewards from
imperfect verifiers (Cai et al., 2025); this error is structured,
because it falls on solutions whose dependencies differ from the gold
patch’s.

#### Hypotheses and predictions

Each preregistration fixes a decision rule, called a gate: a complete,
valid result below its thresholds is a KILL (the hypothesis is not
supported), and a result that fails its protocol’s completeness or
validity conditions is INCONCLUSIVE. _H1_ (Study 1): under SWE-bench
Pro v1’s offline option, the weighted rate of confirmed reversible
verdict losses among evaluable accepted candidates on tasks where the
policy is valid is at least 3% (Section 3). The initial protocol
predicted a KILL (subjective probability about 0.85), revised before any
confirmatory data to about 0.65 when the feasibility stage exposed a
memory-limit risk, and predicted that most Go tasks whose gold patch
bumps a module would be ineligible. _H2_ (Study 2): rerun instability or
CPU contention alone reverses a recorded DGM decision, reproducibly
(Section 5). The preregistration predicted a KILL, with instability and
contention each on at most 1% of cells. The extension of Study 1
(Section 4.3) has no kill rule: it dropped the 3% gate, its outcomes are
“no rejection observed”, “rejection observed” or inconclusive, and it
predicted that no rejection would be observed. Table 3 in Appendix G
summarizes the two studies, the extension and the feasibility stratum.

## 3 Study 1 design: offline grading of SWE-bench Pro

#### Units and terminology

An _accepted patch_ passes the benchmark’s tests (_resolved_);
_unresolved_ means those tests were not satisfied. Evaluable patches
reproduce acceptance with complete controls; exposed patches face
different policy configurations. An _artefact_ is an accepted candidate,
gold/empty patch, or officially unresolved control. Study 2’s unit is an
agent-version/task evaluation (Section 5).

#### Policies and arms

A _grader policy_ fixes what the verifier container may reach. The task
image (prepared container environment, pinned by content digest), entry
script, tests, parser, resolution rule and time limit stay fixed.
Official verdicts came from a networked grader that downloads missing Go
modules. Our containers have no network, so baseline arm A0 emulates
that contract. For each artefact it seeds a read-only file module proxy
with the module-checksum entries in go.sum that the image’s cache lacks,
then adds, round by round, every file of each module version the
artefact’s own verification requests. The bytes are fetched on the host
from public module proxies and checked by the Go toolchain against
go.sum. A0 must reproduce the official verdict before a candidate
counts. Arm A1*(BLOCK) (A1 in the confirmatory analysis), the restricted
arm, applies the offline policy P*(BLOCK), which disables networking and
changes nothing else (Scale AI, 2026); it is the single confirmatory
policy. Arm A2, the restored arm, provisions per candidate: it keeps the
shipped image and adds the candidate’s own A0 mirror, excluding the
task’s own module path (the project under repair), whose later versions
could contain the fix. (In the feasibility stage, A2 added the
candidate’s modules to the gold-bound cache, excluding the task’s own
module path.) For Go tasks whose gold patch edits go.mod or go.sum, arm
A1*(LEGO) applies the gold-cache policy P*(LEGO), our reconstruction of
Lego-RL’s gold-bound module cache (LegoX, 2026). It runs the builder’s
Go commands on the gold state offline, against a file mirror seeded from
the gold go.sum and filled request by request until nothing new is
requested; the upstream builder runs them with network access. P\_(LEGO)
is analyzed descriptively. For non-Go tasks the emulation adds nothing,
so A0, A1 and A2 are identical configurations and the design observes
only background disagreement there. Figure 3 (Appendix G) shows the arms
and repetitions.

#### Validity of a policy for a task

A restrictive policy can break a task for every solution. A task is
_eligible_ under a policy only if the gold patch resolves in all three
repetitions under it and the empty patch fails in all three; only
candidates on eligible tasks count.

#### Research questions

The research questions are: RQ1 (validity), on which tasks does
P*(BLOCK) pass the gold patch? RQ2 (incidence): what fraction of
accepted candidates on eligible tasks does P*(BLOCK) reject,
reproducibly and with a network-unavailability signature in its
restricted logs? RQ3 (gold-cache rejection): are accepted alternatives
rejected under P\_(LEGO)? RQ4 (repair): does A2 recover rejected
candidates without newly accepting officially unresolved controls?

#### Corpus and sampling

We use the public split of SWE-bench Pro v1 (Deng et al., 2026) at a
pinned revision, with the official run scripts and parsers at a pinned
commit (Scale AI, 2026). The maintainers publish the patches of nine
agent runs with their verdicts; a _candidate_ is a patch the official
evaluation marked resolved, and we draw from the nine runs (one had no
available patch). The frame contains every task with a resolved
candidate, minus pilot, feasibility and known-broken tasks; tasks are
ordered by a seeded hash, and the confirmatory sample is the first 120,
reserved from metadata before this study fetched any of their candidate
patches. The preregistration discloses a pre-project screen that
downloaded the Go candidate diffs of eight runs and flagged manifest
edits without executing anything; the draw does not use it. Each task
contributes up to four candidates in a frozen round-robin order over
models, its gold and empty patches as controls, and up to one officially
unresolved candidate as a negative control.

#### Outcomes, estimator and gate

Each arm runs three times, in a fresh container with four CPUs, 8
gibibytes (GiB) of memory, no network and the official one-hour timeout,
in a seeded order interleaved across arms. A Study 1 cell is an
(artefact, arm) pair and is _finished_ if all three repetitions
completed the grader invocation, with no launcher error, timeout or
out-of-memory kill and with parser output. A candidate is _evaluable_ if
its task is eligible, its gold-baseline control and candidate A0, A1 and
A2 cells finished, and A0 resolved it three times. It is a _confirmed
reversible loss_ if A1\_(BLOCK) rejects it three times, A2 resolves it
three times, and the restricted logs show the preregistered
network-unavailability signature (NET_RE; Appendix C). Candidates are
weighted by their inverse within-task inclusion probability, estimated
at draw time from availability alone with 20,000 fixed-seed Monte Carlo
draws; the primary quantity is the weighted loss rate, with a one-sided
95% lower bound from a task-cluster bootstrap. The gate requires at
least 200 evaluable candidates from at least two models and passes only
if the rate is at least 3%, the lower bound exceeds 1%, and losses occur
on at least five tasks. A complete, valid sample below these thresholds
is a KILL. The study is invalid, and so inconclusive, if the gold patch
fails any baseline run on an eligible task, if more than 10% of the
drawn tasks have an unfinished control, if more than 10% have finished
gold-baseline cells that do not reproduce the gold verdict, or if its
integrity audit does not accept the execution records as valid (PASS); a
task on which only the restricted arm fails the gold patch is merely
ineligible. In the preregistered simulation, which assumed no attrition,
the design would have passed with probability 0.48 (independent losses)
or 0.40 (clustered losses) at a true rate of 3%, and 0.95 or 0.88 at 5%.
The protocol, code, manifests, seeds, sample reservation, analysis
script and predictions were sealed by a pushed commit before any
confirmatory data; Appendix C gives the sealing, amendment and audit
procedure.

## 4 Study 1 results

The confirmatory run executed all 120 tasks of the reserved prefix: 664
artefacts and 5,997 container runs (93.99 container-hours), with no
interrupted or deadline-truncated cell. Its integrity audit passed on
the fourth round after post-data appendices corrected reporting and
wording, without changing runs.

### 4.1 RQ1: Where the offline policy is valid

Under P\_(BLOCK), the gold patch passed all three restricted runs and the
empty patch failed all three on 113 of the 120 tasks. Four tasks, all
from one JavaScript repository, have incomplete control evidence because
their test workers exceeded the 8 GiB limit. Of the three ineligible
tasks with finished controls, two fail the gold patch in every arm, the
baseline included; the third, a Go task, passes it in all baseline and
restored runs but fails every restricted run with failed module
downloads, so the offline option cannot grade its reference solution.
Both invalidity shares stayed below the preregistered 10%: 4 of 120
tasks with an unfinished control (3.33%) and 2 of 120 whose finished
gold-baseline cells do not reproduce the gold verdict (1.67%).

Of 312 drawn candidates, 281 were evaluable, from seven models on 110
tasks (Table 1); 9 were on ineligible tasks, 11 on tasks with incomplete
controls, and 11 were not reproduced by the baseline arm. No evaluable
candidate lost its verdict or varied across restricted or restored
repetitions. The complete, valid sample returns KILL: H1 is not
supported. A preregistered sensitivity analysis that counts the
unresolved candidates on eligible tasks as losses gives a weighted
3.90%; with eligibility and weights fixed, it covers only the 11
baseline-unreproduced candidates on eligible tasks. It exceeds 3% but
does not establish the registered lower-bound and five-task conditions.
The KILL therefore gives no safety assurance. The 31 unevaluable
candidates may include policy-sensitive cases: baseline emulation can
turn missing inputs into attrition.

Only the 59 evaluable Go patches on 25 tasks faced different
configurations (Figure 1a); all passed with the shipped image alone. The
222 evaluable Python, JavaScript and TypeScript patches faced identical
arms, with no background disagreement. Risk bounds for the exposed
patches were not preregistered. Post hoc and unweighted, the one-sided
95% Clopper-Pearson upper confidence limit is 4.95% on the rejection
rate of these candidates if they are independent, 11.29% on the share of
their 25 tasks with a rejection if tasks are independent, and 27.17% on
the candidate rate if the 13 unevaluable Go draws count as rejections
and candidates are independent. Figure 1b shows the two zero-event
bounds. None excludes 3%; 99 independent exposed candidates without a
rejection would be needed. Under task independence, the same frame
cannot reach 3%: even if all 91 Go tasks of the sampling frame were
eligible and none rejected, the independent-task upper confidence limit
would be 3.24%. This hypothetical limit of that interval does not answer
the registered candidate-level question, and the design did not exercise
package installation at grading time in other ecosystems.

### 4.3 Extension to the remaining Go tasks

A second preregistration, sealed before its data, replayed the 63 Go
tasks that follow the prefix in the reservation order with the same
arms, counting _any_ failed restricted repetition of a reproduced
candidate as a rejection. The extension is _inconclusive_: on one
eligible task the gold patch failed one of its three baseline runs,
which the registered control rule does not allow, and we neither drop
that task nor repeat the run. The registered tally is two rejection
tasks among 59 eligible, one of them that task; because the control
failed, every bound is descriptive and the predicted zero was not
observed. Appendix F gives the tally, the descriptive bounds and the
shared nil-pointer panic behind both failures.

### 4.4 RQ3: Gold-bound caches

The prefix contained one task whose gold patch bumps a Go module, with
no loss under P*(LEGO); the extension added four, the four on which the
gold patch failed P*(BLOCK), and none of their nine evaluable candidates
lost its verdict under the reconstructed cache. The only cache-induced
rejections come from the feasibility stage, which selected 11 such tasks
on purpose and is therefore no prevalence estimate. There, P\_(BLOCK)
failed the gold patch on 8 of the 11 tasks, while the reconstructed
cache passed it on all 11. Of 15 baseline-reproduced accepted candidates
on seven of these tasks, six, on three tasks and from five runs of four
models, failed all three runs under the cache and passed all three once
their own admitted modules were added. On one Flipt task, candidates
from three models each added a version of Masterminds/semver (v3.1.1 or
v1.5.0) that is absent from the gold state’s go.sum; each resolved three
of three baseline and restored runs and none under the cache. Appendix D
describes the reconstruction and the parity checks it passed.

### 4.5 RQ4: Candidate-aware provisioning

Provisioning recovered all six feasibility-stage losses. In the
confirmatory run there was nothing to recover, and the preregistered
safety criterion forbids any restored-arm acceptance when both other
arms reject; it failed: one officially unresolved Python candidate
passed one of three restored runs after failing every other run. Its
restored arm had no mirror and matched the other configurations,
consistent with background flakiness; the cause was not isolated and the
frozen rule counts it. No negative control was observed consuming
provisioned modules (the official run scripts of 5 of the 112 tasks with
a sampled negative control filter out the logged go: downloading
marker), so that zero does not show such use to be absent. The labels
have a limit of their own: 9 of the 112 sampled negative controls, and 3
of the extension’s 63, resolved in every run of every arm, so the replay
does not reproduce the official rejection for them; we did not classify
the cause.

## 5 Study 2: Re-executing a self-improvement archive

A self-improving coding agent compares and promotes its versions using
test verdicts. Study 2 asks whether a released run’s recorded decisions
survive re-execution of frozen patches. A _cell_ is one archived
evaluation of an agent version on a task within a system arm; it can
have multiple reruns. We separate three sources of disagreement: rerun
instability, CPU contention, and drift from the archived grading
environment.

### 5.1 Design

#### Object and decisions

DGM evaluates self-modified coding agents on SWE-bench Verified, up to
200 tasks (Zhang et al., 2026). Its archive (Zhang et al., 2025) holds
245 agent versions (nodes), with 6,006 evaluations on 200 tasks in three
arms: the full system and ablations without open-ended exploration or
self-improvement. The recorded arm bests are 100/200 for the full
system, the 50.0% that DGM reports, 23/59 without self-improvement and
14/60 without open-ended exploration. We reconstruct only decisions that
the released code defines and the archive records. DGM’s score is the
fraction of submitted tasks resolved. _D1_ (best-node selection) chooses
the best of the eight full-system nodes evaluated on the full task set
(197 to 200 submitted tasks each; recorded 100/200 against a runner-up
of 87/200); _D2_ (arm ranking) ranks the three arms by the best score in
each arm’s final archive (the arm bests above, each over its node’s
submitted tasks). A decision reverses if a challenger reaches or exceeds
the incumbent. The staged gate is not reconstructable: recorded history
conflicts with the released threshold (Appendix E).

#### Replay

We re-execute 1,929 recorded cells: every cell of the eight D1 nodes and
of each arm’s top three nodes by recorded score, including ties at the
cutoff, 15 nodes in all. Each cell runs three times with four CPUs
(nominal) and three times with a quarter of a CPU (contention), each run
in a fresh network-isolated container with 8 GiB. Two details affect
replay fidelity, and both surfaced before the seal: DGM grades the patch
after removing its diffs to test files, and the evaluation images
(SWE-bench’s September 2025 v2 tag) commit setup edits the archived runs
left uncommitted. Appendix E gives both checks and the required
regrading agreement.

#### Quantities and rule

A majority verdict is the outcome of at least two of three repetitions.
On each cell, Q1 is rerun instability (non-unanimous nominal verdicts),
Q2 is drift (the recorded verdict differs from the nominal majority),
and Q3 is contention disagreement (the contention majority differs from
the nominal majority). We report counts of cells in each category. Only
Q1- and Q3-type reversals count toward the hypothesis. Starting from
recorded verdicts, each Q1 comparison uses the same repetition index
across all unstable cells; Q3 substitutes contention majorities on cells
without drift. A reversal had to reproduce in a confirmation batch
(Appendix E). Stable drift is reported separately; no drift cell was
also unstable. Nodes not re-executed keep their recorded scores. The
protocol, cell sets and code were sealed before any decision cell ran,
after two rounds of design and code review. We saw the earlier pilot’s
written assessment, not its data.

### 5.2 Results

#### Evaluator and replay

Regrading reproduced 5,999 of the 6,006 archived verdicts (99.88%); all
seven disagreements are on one Astropy task whose reference test list
was revised in the SWE-bench Verified copy used for regrading
(Appendix H). All 11,574 runs completed (68.55 container-hours) without
timeouts or memory kills.

#### Decisions unchanged

Two cells showed rerun instability, and the same two are the only ones
where the contention majority differs from the nominal majority; both
belong to one Sphinx task (sphinx-10466). Under independence the
one-sided 95% upper bound is 0.33% per cell for each quantity, and 2.35%
per task (1 of 200). Neither kind of instability reversed D1 or D2, so
no confirmation batch was needed and the preregistered test returned
KILL. The substitutions narrowed D1’s margin at most from 13 to 12
tasks, and the arm ranking (100/200, 23/59, 14/60) did not move. Post
hoc, reversing D1 would take at least 13 targeted verdict flips among
replayed cells and D2’s top pair at least 7 (Appendix E). The margins
were known before the seal (13 tasks for D1; 0.110 and 0.156 in score
between adjacent arms for D2), so the test asks whether DGM’s recorded
endpoints survive the noise re-execution can expose and says nothing
about close decisions. The result is conditional on unreplayed scores:
with submitted tasks and other scores fixed, an unreplayed retained node
of a lower-ranked arm would need at least 10 more resolved tasks to tie
a higher-ranked arm’s best (initial, unmodified-agent nodes, called
roots, lack recorded submission counts and are excluded). The two
decisions are endpoints: the run’s intermediate selections are not
tested, and one contention profile with three runs each isolates no
causal contention effect.

#### Drift

The recorded verdict and the rerun majority disagreed on 23 cells
(1.19%) of four tasks, and each disagreement held in all six runs of its
cell (Figure 2). Seven follow a revision of the reference test list that
dropped a required test the archived run had not reported as passing.
Nine are on two Sphinx tasks whose required tests fetch an external URL,
which our network-isolated replay cannot reach, whereas the archived
runs were networked. Seven, on one Django task, resolve in every
original-host rerun under both the archived and revised test lists;
their cause was not isolated. Applying all drift at once still leaves D1
and D2 as recorded.

#### Exploratory follow-ups

Seven original drift cells did not reproduce in a second execution.
Rebuilt images changed 16 nominal cell majorities, eight alongside
pytest test-runner and suite-completion differences; causes remain
unisolated. SWE-bench 5.0.2 matched all pinned cell verdicts after
adapting the archived log format. Reconstructed D1/D2 stayed unchanged
in these comparisons. Suite-incompleteness and test-infrastructure
diagnostics use analysis scripts revised after their original seals; we
label them exploratory-unsealed to distinguish them from analyses fixed
before the relevant data. Appendix I gives scope and deviations. These
follow-ups do not recompute the sealed hypothesis gate.

## 6 Implications for grader audits

#### Evidence and scope

Table 2 distinguishes decision stability from grader-policy assurance.
Study 2 fixes history and unreplayed scores; testing intermediate
selections requires adaptive-search replay. The extension’s two
intermittent candidate failures remain unattributed.

| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Study 1             | 0 losses among 59 exposed patches on 25 tasks. Unweighted post-hoc upper bound 4.95% under candidate independence; 3% exposed risk unresolved.                 |
| Study 2             | Best-node selection (D1) and arm ranking (D2) unchanged in the original replay and follow-ups. Original drift partly unreproduced; adaptive learning untested. |

#### Lesson 1: plan around policy-exposed units (Study 1)

For 222 of 281 evaluable patches the arms were identical; only Go
patches faced different dependency configurations. Random task sampling
dilutes this contrast. Even all 91 Go tasks, eligible and
rejection-free, would leave the independent-task bound at 3.24%. At
candidate level, 99 independent exposed candidates with zero rejections
suffice for a 3% upper bound. The extension reproduced 146 candidates,
including two with a failing restricted run; its failed control makes
the tally descriptive. Future audits should sample the policy-exposed
stratum directly and check before data collection whether it contains
enough independent units to resolve the tolerance.

#### Lesson 2: preregister how intermittent crashes are handled (extension)

The extension was inconclusive: one gold baseline run had the
intermittent crash seen in both candidate rejections, and every gold run
was required to pass. A preregistered stability screen could choose a
repetition count $`k`$ and run the gold patch that many times in the
baseline arm before any policy arm to exclude known-flaky tasks. One
training pipeline retries failed gold-patch runs up to ten times (Auras
and Prime Intellect Team, 2026). Such screening changes the conditional
population; a later control failure would still trigger the registered
invalidity rule.

#### Lesson 3: check replay fidelity before re-executing (Study 2)

DGM grades filtered patches, and replay images commit setup edits left
uncommitted in archived runs. Size and checksum comparisons caught the
patch discrepancy; regrading logs applies no patch and misses it, though
it separated reference-label drift. Matching patch and commit records
did not ensure matching verdicts. Re-executions should check patch and
grading inputs and report the runtime environment.

#### Lesson 4: validate hermetic graders on accepted alternatives (feasibility stratum)

The gold patch passed the reconstructed gold-bound cache on all 11
selected tasks, while 6 of 15 accepted alternatives failed it. Replaying
accepted benchmark candidates under a new policy requires container time
but no new labels and detects losses beyond gold-patch validation.
Provisioning each candidate’s own declared dependencies after submission
recovered every such loss. Validating that this policy also keeps
incorrect solutions rejected remains future work; the confirmatory
safety criterion was not met.

## 7 Related work

#### Flaky tests and environmental causes

Network availability (Dietrich et al., 2022), computational
resources (Silva et al., 2024b) and dependency resolution (Ge and Zhang, 2026) affect tests and builds. We measure consequences for accepted
solutions and recorded decisions.

#### Reproducible and offline grading

GitBug-Actions and GitBug-Java capture dependencies so builds re-execute
without network (Saavedra et al., 2024; Silva et al., 2024a), and
maintainers apply the idea to grading: SWE-rebench V2 pre-builds task
environments (Badertdinov et al., 2026), Lego-RL packages dependencies
into task images (Du et al., 2026) and mounts gold-derived Go module
caches (LegoX, 2026), and an open, unmerged SWE-bench pull request (as
of 2026-10-07) grades Multimodal tasks offline with bundles bound to the
gold patch (SWE-bench, 2026). We test SWE-bench Pro v1’s offline option
and a reconstructed Lego-RL gold-bound cache on accepted alternatives.

#### Validity of agent benchmarks and rewards

Inadequate tests admit suspicious patches (Aleithan et al., 2024; Xue
et al., 2026), while test augmentation catches incorrect patches (Yu
et al., 2025; Li et al., 2026). A checklist finds outcome-validity
violations in seven of ten agentic benchmarks and OSWorld checkers
broken by website changes (Zhu et al., 2025). Accepted patches can
diverge from developer intent (Wang et al., 2026b). OpenAI estimates
about 30% of SWE-Bench Pro’s public tasks are broken, including tests
rejecting functionally correct submissions (OpenAI, 2026). SWE-Bench Pro
Verified repairs tasks and audits possible collateral damage in
anti-hacking agent runs (Zheng et al., 2026); we replay fixed accepted
patches under a specified grading policy. Verdicts are compared across
execution substrates (Yuan et al., 2026), and benchmark ports are
validated with parity experiments (Shi et al., 2026). On rewards,
KAT-Coder-V2.5 traces invalid rollouts to sandbox failures (Huang
et al., 2026a), outages can corrupt reward signals (Huang et al.,
2026b), rollout infrastructure carries measurable overhead (Graviet
et al., 2026), code RL environments accept incorrect solutions (Rajan,
2026), and provable false negatives of math answer verifiers trace to
answer forms (Xin, 2026). The math-verifier study measures false
negatives; we measure code acceptance losses under reference-valid
policies. Test augmentation can overfit a reference implementation (Li
et al., 2026); Study 1 instead varies dependency availability with
required tests fixed. Study 2 separates reference-label drift.

#### Re-execution and self-improvement

Independent re-implementations of frozen mechanisms audit idea
reliability in automated research (Ning et al., 2026); Study 2
re-executes fixed evaluated patches and separates execution effects from
reference-label drift. Others audit self-improving agents for edits that
inflate measured performance (Wang et al., 2026a) and argue that
coding-agent failures often originate outside the model (Jarmak, 2026).

## 8 Conclusion

The original and follow-up DGM comparisons preserved fixed-history
endpoints. Seven original drift cells did not reproduce on a second
host; rebuilt images changed 16 nominal majorities (0.83%). The offline
policy rejected none of 59 exposed patches, leaving a 3% risk
unresolved; the extension was inconclusive. Selected cache cases
motivate testing accepted alternatives. Future work should expand
exposed samples and replay adaptive search.

## Limitations

#### Coverage and generalization.

Both preregistered gates returned negative within their tested scope.
Study 1 covers one benchmark and published runs from a few model
families at one time. Its policy contrast is Go-only: 59 of 281
evaluable candidates, on 25 tasks, faced a configuration that the
offline policy changes. The motivating 3% rejection risk remains
unresolved. Study 2 covers one system’s archive on one benchmark, with
cells from three repositories (Appendix E). Broader benchmark and
archive coverage would allow future studies to test how these findings
generalize, including the effects of intermittent failures and adaptive
search. The extension remains inconclusive because its registered
control failed; its tally is descriptive.

#### Acceptance-based evaluation.

Official test acceptance is the operational correctness criterion in
this study. Our claims concern acceptance losses, the quantity a reward
or leaderboard consumes; semantic correctness requires separate
validation. Officially unresolved candidates are negatives under this
test oracle. The baseline emulates the networked contract with a file
mirror, and candidates needing resources beyond that emulation enter
attrition. The reconstructed gold-bound cache matches the needed module
versions in the upstream builder’s cache; file identity was not checked.
Semantic review and file-level cache comparisons would extend the
evaluation of accepted and unresolved patches.

#### Replay controls and selection.

Study 1 uses three repetitions per arm in fresh containers, baseline
reproduction of the official verdict, eligible controls and a
network-unavailability signature. The extension retains the controls but
counts any failed restricted run, a broader rejection rule. Selection
requires baseline reproduction and eligibility. Study 1’s 31 unevaluable
candidates, including out-of-memory kills, enter attrition rather than
the rejection count. A preregistered baseline stability screen could
address intermittent failures in future replays, provided the change in
the eligible population is reported. Replaying excluded cases with
larger resource budgets would help characterize attrition.

#### Statistical resolution.

The preregistered gate decisions are the confirmatory claims. Post-hoc
bounds and secondary analyses are exploratory; the Clopper-Pearson
bounds assume independent units. A tally below a gate does not supply an
upper confidence bound, and repeated runs do not increase the number of
independent tasks. Future sampling plans should target enough
independent, policy-exposed units to resolve the chosen tolerance.
Characterizing rare intermittent failures requires more than the three
runs per profile used here. Network-isolated replays fail
network-dependent tests by construction; we classify these differences
as drift, separately from instability.

#### Prevalence and causal attribution.

The gold-bound cache rejected 6 of 15 accepted candidates in a
deliberately selected feasibility stratum. These cases establish that
the configuration can flip an accepted verdict; prevalence estimation
requires a representative sample. Study 2’s original drift count
describes one execution, and the second execution reproduced only part
of that drift. Controlled host, image and pytest substitutions would
help attribute these differences; the present comparisons identify
neither a host-specific cause nor which verdict is correct. The
suite-incompleteness rules are diagnostic heuristics, and the
test-infrastructure intervention leaves edits already present in an
image intact (Appendix I). Causal tests of those edits require separate
image interventions.

#### Version coverage.

Claims about external systems apply to the tested versions. Appendix H
pairs these pins with upstream releases checked on 2026-10-07. Study 1
tested SWE-bench Pro v1 with its v1 evaluator. The maintainers’ V2,
released 2026-09-22 and now the default configuration, uses a different
harness, a networked verifier and new images; evaluating it is a next
step. Study 2 used DGM’s pinned 2024 grader commit and September 2025
evaluation images. Exploratory follow-ups cover a declared log adapter
for SWE-bench 5.0.2 and a 2026-10-05 snapshot of rebuilt images, with
reference labels held fixed. Extending coverage to current harness,
label and runtime combinations would require new evaluations beyond the
original gate. Appendix H preserves the dated upstream inventory;
Appendix I records the follow-ups.

## Ethical considerations

This work re-executes publicly released evaluation artefacts: a
benchmark’s own task images and tests, officially accepted candidate
patches from public leaderboard runs, and one released self-improvement
archive. It recruits no participants and studies no people; the run
records contain public identifiers from the benchmark repositories:
commit hashes, commit authors’ names and module paths that can include
account names. All candidate code and all benchmark tests run inside
network-isolated containers, because the material is third-party code of
unknown provenance and the experiment must not reach the network.

We release verdicts, identifiers and content hashes, not third-party
artefacts: candidate patches, task files, reference solutions, module
caches and the released archive are not redistributed, so the
replication package neither relicenses other people’s code nor
republishes benchmark solutions that could leak into training data. The
grading code we re-execute is released under MIT (the SWE-bench grader
and the SWE-bench Pro evaluator); DGM and Lego-RL, whose patch filter
and cache builder we reimplement, are Apache-2.0; the benchmark
datasets’ cards state no licence (checked 2026-10-02), and we use them
only to evaluate, as intended.

Our findings concern evaluation infrastructure under the conditions
reported here. The Limitations section defines the scope of each gate;
broader assurances about agent-evaluation reliability require further
evidence. The appendix reports the studies’ compute cost.

host, each pinned to four logical CPUs with 8 GiB (Study 2’s contention
profile caps CPU time at a quarter of one CPU). Study 1’s confirmatory
run took 93.99 container-hours (5,997 runs; Section 4), its extension
101.44 (the sum over its 3,237 run records), the feasibility stage 80.86
(3,315 runs), and Study 2’s replay 68.55 (11,574 runs; Section 5). The
task images for Study 1, its extension and the feasibility stage were
pinned by digest: 245 images, 235 of them pulled (about 352 gigabytes

released artefacts. A reviewer model from a different model family ran
the design and integrity audits (Appendix C).

## Appendix C Sealing, amendments and audits (Study 1)

The protocol, code, manifests, seeds, sample reservation, analysis
script and predictions were sealed by a pushed commit before any
confirmatory data; five amendments are dated appendices committed before
the data they affect, and the runner refuses to start unless the sealed
files match. Four post-data appendices correct the reporting and add a
descriptive bound, and change no run, rule or primary quantity. Design
and integrity audits were run by a reviewer model from a different model
family in separate sessions; they can make a result inconclusive but
cannot pass a gate. A feasibility stage on separate tasks exercised the
harness first; its outcomes did not change the reserved confirmatory

failure in name resolution, ENOTFOUND, EAI_AGAIN, or getaddrinfo. The
supplementary preregistration and classifier retain the exact pattern,
including the lookup-expression syntax.

## Appendix D The reconstructed gold-bound cache

The gold state is the repository after applying the reference patch. Its
go.mod declares module dependencies; go.sum records their checksums. The
reconstruction runs the upstream builder’s go mod download -json all and
go list -deps -test ./... commands on this state, in the same pinned
image with the same toolchain, with a file proxy and checksum lookups
disabled in place of the upstream proxy and checksum database, seeds the
mirror with module metadata files (.mod and .info) for every module
version in the gold go.sum (a registered deviation from the upstream
builder; zips only on request), and repeats until they request nothing
new. On all 11 tasks the last round of both commands ended without error
output, and no request was a query for a module’s latest version. None
of the missing module versions that the six candidates requested is in
these caches or in the gold state’s go.sum. The checks support parity of
the needed module versions with the upstream builder’s cache, not
file-for-file parity, because running that builder requires a networked
task container.

The six rejected candidates come from five leaderboard runs of four
models: one run lost two tasks and each of the other four lost one. The
stratum was selected for exposure, so these counts describe only how the
losses were spread across runs.

## Appendix E Replay-fidelity checks (Study 2)

Study 2’s 1,929 re-executed cells all come from three repositories:
1,399 on Django, 357 on Sphinx and 173 on Astropy. Two details affect
replay fidelity, and both surfaced before the seal. DGM grades the patch
after removing its diffs to test files and the test-environment
configuration file tox.ini, so applying the stored patch would replay
test changes DGM never evaluated; we reimplement the filter, and our
evaluated patch matches the archived one in size and 32-bit cyclic
redundancy check (CRC32) checksum for all 6,006 cells. The replay images
(SWE-bench’s v2-tag evaluation images, distinct from SWE-bench Pro V2
and pinned by image identifier) also commit the harness’s setup edits,
which the archived runs left uncommitted, and each run restores the
archived layout. Grading uses SWE-bench’s grader at the commit DGM’s
README pins (dc4c087c, 2024-10-25); regrading all 6,006 archived logs
had to agree with the archived verdicts on at least 99%.

#### Unreconstructable staged gate

Among 89 retained non-root nodes, 38 have fewer recorded successes on
the first subset than the released threshold requires: four successes on
the first ten-task subset before expanding evaluation. The archive
therefore cannot reconstruct intermediate selections under that rule.

#### Registered substitution and confirmation rules

For rerun instability (Q1), each comparison uses one matched repetition
index across all unstable cells and keeps every other archived verdict
fixed. For contention disagreement (Q3), only cells whose nominal
majority agrees with the archive receive the contention majority. If
either substitution reverses an incumbent/challenger pair, its deciding
cells receive three new nominal and three new contention runs, all
required to finish. Q1 confirmation requires the same pair to reverse in
at least one matched-index panel using deciding cells that are again
unstable. Q3 confirmation requires the same pair to reverse on cells
whose new nominal majority matches the archive and whose new contention
majority repeats the original contention majority. These rules do not
count stable drift as support.

#### How far the decisions were from reversing (post hoc)

With unreplayed scores fixed and root entries excluded, reversing D1
needs at least 13 verdict flips among replayed cells, whether they lower
the incumbent or raise the runner-up, reversing D2’s top pair at least 7
(the best node without self-improvement gaining 7 of its replayed
unresolved cells) and its lower pair at least 10, a tie counting as a
reversal in each case. The registered substitutions changed at most two
cells and narrowed D1’s margin by at most one task. The 23 drift cells
exceed the 7-flip minimum for D2’s top pair, but 22 of them fell on the
eight full-system D1 nodes and one on a node without open-ended
exploration, none on the arm without self-improvement, and they cancel
on the D1 incumbent and runner-up (net change 0 on each). D2 held
because of where drift fell as well as because of its margins. These
distances concern reversing the recorded decisions; they do not show
that such flips would occur. This analysis is exploratory and no gate
uses it.

#### Second-host replay (X1)

A coauthor repeated all 11,574 runs on a second machine, with the
documented host amendment: six four-CPU execution slots, adjusted CPU
affinity (the processors assigned to each run), and scheduler priority.
Both executions have complete outcome ledgers. Verdicts agree at matched
run indices on 11,515 runs (99.49%, descriptive because the repetitions
are independent draws). Nominal and contention majorities each differ on
10 of 1,929 cells. After validity and coverage checks, the registered
reproduction criterion requires at most 1% nominal-majority
disagreement, retention of every original drift cell, and unchanged
reconstructed decisions. A drift cell has a recorded verdict different
from its nominal rerun majority (Q2 in Section 5). The criterion is NOT
MET: seven original drift cells no longer have that disagreement on the
second machine, although nominal disagreement stays below the tolerance
and the reconstructed decisions are unchanged. Those seven django-10097
cells resolve in all 42 original runs and none of the 42 second-machine
runs; the latter contain database errors matching the archived failure
signature. Original-host runtime and logs were not inspected for this
comparison, so the cause remains unisolated. Recorded commits, patch
hashes and patch-application/evaluation exit codes match on all runs;
this does not establish identical runtime environments. The other
differences occurred on Django cache-expiry/cache-touch tests and the
Sphinx task already identified as unstable. The original-host log
reading required for newly gained drift cells could not be completed.

#### Rebuilt-image comparison (X2)

The 2026-10-05 snapshot contains rebuilt container images for all 200
tasks. On the second machine, 5,787 nominal runs cover all 1,929 cells.
Nominal majorities differ from that machine’s original pinned-image runs

registered reporting condition is an endpoint change or more than 1%
nominal-majority disagreement. Neither occurred: reconstructed D1/D2

do not fulfill the registration’s requested explanation for each cell.

#### Grader-version comparison (X3)

With reference test lists fixed at dataset revision 78f471bf, SWE-bench
5.0.2 without adaptation returns not_found on all 6,006 archived logs
because they lack its expected test-output delimiters. The declared
adapter adds \>\>\>\>\> Start Test Output and \>\>\>\>\> End Test Output

no grader code and supplying no test exit code. The adapted logs receive

the parsers or grading rules. The best node and arm ranking are
unchanged, although the score gaps between challengers and the best node
differ from the reconstruction using recorded verdicts. This comparison
reconstructs all 96 nodes with run reports, a larger set than the
final-archive node sets fixed for the original study. The three initial,
unmodified-agent nodes lack recorded submission counts; their task-count
denominators are recovered from their fixed scores. The comparison
neither re-executes tests nor covers logs produced by the current
harness or revised reference test lists.

#### Suite-incompleteness diagnostics (X4)

The scan flags a run if its log meets any of three checks: the pinned
grader’s parser finds no test results; the final pytest summary reports
errors and has at least as many errors as passed tests and no required
FAIL_TO_PASS test has a passed/failed status; or a traceback occurs
after the last result line recognized by the scan’s pattern (or no
result line is recognized). A cell is flagged only when all three
nominal runs are flagged. The stricter variant retains the empty-parser
and error-summary checks but removes the traceback check. A revised
script flags 189 of 1,929 pinned-image cells (9.8%) under the original
checks and 150 (7.8%) under the stricter variant. Thirteen cells are
flagged on pinned images but not rebuilt images; eight become resolved.
These are log-based flags, not a causal classification of environment
failures. The traceback check also flags completed suites, including 15
archived cells recorded as resolved. Neither variant captures the known
django-10097 failure family. Both meet the registered reporting
threshold: at least 1% of cells, with at least two exception signature
families each covering at least three cells. A run’s family is its most
frequent match from a fixed list of exception/warning names, or other; a
cell takes its most common run label. These are text-pattern groups.
Meeting this descriptive threshold establishes neither causal
attribution nor a new defect.

#### Test-infrastructure intervention (X5)

The scan flags files by basename: conftest.py, pytest.ini, setup.cfg,
pyproject.toml, setup.py, .coveragerc, sitecustomize.py,
usercustomize.py, and eval.sh, plus files ending in .pth (Python
path-configuration files). Among 6,006 archive cells, 1,291 have an
evaluated patch that touches one of these files. In 1,203 of those
cells, the only flagged edits match dependency-version pins inserted by
the harness’s pre-install commands. This classification uses strings in
the added lines, rather than establishing that the agent authored those
edits. A revised scan selects 59 of the 769 recorded-resolved replay
cells (7.67%) for one run each after removing the flagged files’ diff
blocks, meaning all patch changes for those files. Fifty-three resolve
and six do not. The registered rule labels the result SUPPORTED when at
least 1% of recorded-resolved replay cells touch flagged files and at
least one complete-suite run becomes unresolved after block removal,
compared with its archived resolved verdict. All six failures also
occurred in full-patch nominal runs on both machines. Comparing against
archived acceptance therefore gives no new evidence that removing a
block caused the failure. Block removal also leaves environment edits
already present in an image intact. This selected, one-run intervention
cannot establish the absence of reward manipulation in the archive.

used for these counts, hashes recorded when the original protocols and
analysis files were fixed, and a manifest identifying changes made to
anonymized export copies. Raw logs and some patch-hunk records are
withheld; the export cannot regenerate every source-level diagnostic.
Recorded run durations sum to 50.51 container-hours for second-host
replay and 12.59 for the image comparison. The infrastructure
intervention adds 59 checks whose durations are not exported. The grader
comparison uses one container to grade archived logs, and the suite
diagnostics scan retained logs. No model was trained or assigned an
experimental verdict.

Internal reviews checked scoped follow-up analyses, claims, statistics
and rejection arguments. A citation-focused check covered five added
references and nine other citation contexts. These checks do not
constitute an independent reproduction of the experiments or
verification of every final file. A separate reproduction check
regenerated ledger summaries and, with pinned dependencies and fonts,
source scalable vector graphics (SVG) figures; its scope did not include
re-executing experiments or certifying the full accompanying package.
Font substitution can change regenerated PDF figures even when source
SVGs match.
