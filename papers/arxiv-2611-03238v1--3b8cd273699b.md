###### Abstract

Computer-use agents for scientific software require application-specific
expertise. Much of this expertise is already documented in
human-authored software manuals and web pages, making them readily
available resources for improving agents’ operational capabilities.
However, turning these resources into executable, reusable skills
remains challenging due to mismatches between documented and deployed
software versions and differences in scope between documentation
coverage and task requirements. To address these challenges, we
introduce ScienceCUA, a two-stage framework combining resource-to-skill
construction with execution-guided skill evolution. First, ScienceCUA
identifies tasks supported by the software from its documentation,
infers operational trajectories, and generalizes them into reusable
Skills. Command catalogs, syntax constraints, and shortcuts are
organized separately as References for on-demand lookup. Then,
ScienceCUA uses execution feedback to drive skill self-evolution by
contrasting successful and failed trajectories for the same task,
identifying deficiencies, revising existing skills or adding new ones,
and updating the skill library only after repeated validation in real
environments. To enable reliable evaluation without benchmark noise or
task leakage, we introduce two improved benchmarks.
ScienceBoard-Verified provides an audited and corrected basis for
measuring task performance, while ScienceBoard-VE separates skill
evolution from final testing through disjoint evolution and test tasks
and further supports native-agent evaluation. Experiments show that the
initial Skills and References improve average task success rate by up to
7.23 percentage points over the base model, while skill self-evolution
increases the total gain over the baseline to as much as 17.12
percentage points. ScienceCUA turns software documentation into an
evolving set of executable skills and queryable references, offering a
practical way for general-purpose agents to use scientific software
reliably and at scale.

## 1 Introduction

Computer-use agents (CUAs) built on foundation models can now execute
multi-step tasks through graphical and command-line interfaces ([Qin
et al., 2025](#bib.bib12); [Sager et al., 2026](#bib.bib13); [Xie
et al., 2024](#bib.bib19)). Most existing benchmarks, including
WebArena, OSWorld, and Windows Agent Arena, focus on general-purpose
web, office, and desktop tasks, while scientific software has received
comparatively less attention ([Xie et al., 2024](#bib.bib19); [Zhou
et al., 2024](#bib.bib23); [Bonatti et al., 2024](#bib.bib3); [Sun
et al., 2026](#bib.bib17)). Scientific software is widely used for
experiments, simulations, and data analysis, but operating these tools
often requires application-specific workflows, commands, syntax, and
parameter constraints ([Sun et al., 2026](#bib.bib17); [Ai et al.,
2026](#bib.bib1)). To complete scientific-software tasks, agents must
use software-specific knowledge to select appropriate operations and
organize them into effective workflows ([Shao et al.,
2026](#bib.bib14)).

We study this problem using ScienceBoard ([Sun et al.,
2026](#bib.bib17)), which evaluates CUAs on six scientific applications.
Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction")(a) shows that each
application provides user manuals or official tutorials containing
application-specific knowledge. However,
Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction")(d) shows that directly
placing these resources in the model context yields only limited gains
in task success while substantially increasing execution time.
Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction")(b) illustrates that
human-authored documentation mixes operational instructions with
conceptual explanations and other narrative content. A particular task,
however, typically depends on only a small fraction of the available
information, as shown in
Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction")(c). The central question
is how to extract task-relevant information from these human-oriented
resources and organize it as structured knowledge that the model can use
effectively.

Prior work has constructed reusable skills from human-created resources
for content creation, gaming, software operation, and related
applications ([Fan et al., 2026](#bib.bib6); [Che et al.,
2026](#bib.bib4); [Jiang et al., 2026](#bib.bib7); [Shen et al.,
2026](#bib.bib15)). For scientific software, these resources must supply
two kinds of knowledge with different lifetimes: procedural guidance for
a specific task, and shared software knowledge queried on demand. We
therefore introduce ScienceCUA, which extracts task-oriented procedural
knowledge and cross-task shared software knowledge from raw software
resources, organizes them as Skills and References, respectively, and
combines them on demand during execution.

However, the initial Skills and References constructed from raw
resources have inherent limitations. First, the available PDF or HTML
resources may not match the version of the software deployed in the
execution environment, since perfectly matched resources are not always
available. Second, for some applications, the resource coverage is
broader than the range of tasks being evaluated, while the task scope is
unknown during construction. The resulting knowledge library therefore
contains many entries that are irrelevant to the evaluation tasks,
reducing the density of useful information. Third, some task
requirements may fall outside the coverage of the resources themselves.

To address these limitations, ScienceCUA drives the continual evolution
of Skills and References through execution feedback. Prior work has used
task feedback and execution trajectories to build reflective memory,
optimize external skills, or adapt agent behavior ([Shinn et al.,
2023](#bib.bib16); [Zhao et al., 2024](#bib.bib22); [Ni et al.,
2026](#bib.bib11); [Liu et al., 2026](#bib.bib8); [Yang et al.,
2026](#bib.bib20); [Chen et al., 2026](#bib.bib5); [Zhang et al.,
2026](#bib.bib21); [Sun et al., 2025](#bib.bib18)). In contrast,
ScienceCUA improves a scientific-software knowledge library initialized
from software resources, using historical failure trajectories to guide
subsequent exploration and help agents avoid repeating failed paths or
continuing to follow potentially erroneous Skills and References; when
knowledge is insufficient, it revisits the original resources to
retrieve and construct task-relevant Skills or References. Combined with
on-demand composition, this design both helps agents bypass ineffective
paths caused by version mismatch and, where the original resources
support it, supplements omitted or overly general knowledge in the
initial library, thereby reducing the mismatch between the resources and
the actual tasks. Candidate updates are added only after independent
validation in the target environment.

To support reliable evaluation, we audit and repair ScienceBoard to
create ScienceBoard-Verified. We also add a set of tasks that do not
overlap with the final test tasks, use them exclusively for skill
evolution, and combine the audited benchmark and the new tasks into
ScienceBoard-VE; in addition, we extend the evaluation framework to
support native agents. Across six scientific applications, the initial
Skills and References improve the average task success rate over the
base model by up to 7.23 percentage points. Execution-guided skill
evolution increases the total gain over the baseline to as much as 17.12
percentage points. Our contributions are:

1.  1.  Resource-to-skill construction for scientific software. We present a
        method for constructing a knowledge library from raw software
        resources. It organizes task-oriented procedural knowledge as Skills
        and cross-task shared software knowledge as References, and supports
        their on-demand composition during execution.
2.  2.  Execution-feedback-driven skill evolution. We use failure
        trajectories to guide exploration and help agents avoid repeatedly
        following erroneous Skills or References. When knowledge is missing
        or an existing entry is inapplicable, the system supplements or
        revises Skills and References from the original resources and
        updates the knowledge library only after validation in the target
        environment.
3.  3.  Reliable evaluation of skill construction and evolution. We audit
        and repair ScienceBoard to create ScienceBoard-Verified, add
        skill-evolution tasks disjoint from the final test set to form
        ScienceBoard-VE, and extend evaluation to native agents.

## 2 Related Work

##### Resource-to-Skill Learning.

Automatically constructing reusable agent knowledge from external
resources is a relatively recent research direction. MMG2Skill [Che
et al. (2026)](#bib.bib4) converts public guides into editable Skills,
but assumes that tasks are paired with relevant guides in advance and
does not realize an end-to-end pipeline for constructing Skills directly
from raw resources. VisualSkill [Jiang et al. (2026)](#bib.bib7)
leverages document images to support GUI element identification and
state verification. However, some HTML documentation contains no images
and thus provides no additional visual evidence; even when screenshots
are available, their interfaces may differ from the current software
version, potentially introducing misleading visual cues.
SkillFoundry [Shen et al. (2026)](#bib.bib15) supports workflow
generation for concrete scientific tasks, but focuses on domain
capability coverage and task workflows rather than on systematically
organizing reusable knowledge for a given scientific software package.
Overall, existing methods differ in their resource formats, task
assumptions, and construction objectives, but systematic investigation
is still lacking into how to automatically discover tasks from raw
scientific-software resources and organize cross-task reusable knowledge
without pre-specified task–resource pairs.

##### Self-Evolving Skills and Experience-Driven Agent Adaptation.

Skill self-evolution improves reusable agent knowledge from execution
experience without modifying model parameters. Early work such as
Reflexion [Shinn et al. (2023)](#bib.bib16) used verbal feedback to
improve subsequent behavior, and SEAgent [Sun et al. (2025)](#bib.bib18)
extended this experience-driven paradigm to computer-use agents. Later
work made such experience explicit and reusable as skills.
EvoSkill [Alzubi et al. (2026)](#bib.bib2) creates or revises skills
from failure feedback and selects candidates through validation, while
Trace2Skill [Ni et al. (2026)](#bib.bib11) distills trajectory-local
lessons into transferable skill catalogs. As skill updates become
central, subsequent studies increasingly focus on their reliability.
SkillOpt [Yang et al. (2026)](#bib.bib20) constrains the scope of skill
edits and accepts only validation-improving updates, while
SkillCAT [Chen et al. (2026)](#bib.bib5) contrasts successful and failed
trajectories for the same task and uses task replay before merging
candidate edits. Most prior methods start from execution experience or
an existing skill library. ScienceCUA instead initializes its library
from scientific-software documentation and addresses version and
task-coverage mismatch through failure-history-guided exploration and
source-grounded additions or revisions.

## 3 Method

### 3.1 Resource-to-Skill Construction

ScienceCUA first transforms software documentation into an initial
library of reusable Skills and queryable References, and then evolves
this library using execution feedback from a disjoint set of evolution
tasks.

#### Decoupling Skills and References

Given PDF/HTML software documentation $`\mathcal{D}`$, we construct an
initial library $`\mathcal{L}_{0}=(\mathcal{S}_{0},\mathcal{R}_{0})`$,
where Skills $`\mathcal{S}_{0}`$ encode reusable task-level operational
procedures and References $`\mathcal{R}_{0}`$ organize cross-task shared
knowledge, such as commands, syntax, and parameter constraints. For
example, KAlgebra’s 2D and 3D plotting workflows form separate Skills,
while syntax for square roots and exponentiation is stored in a
Reference
(Figure [3](#S3.F3 "Figure 3 ‣ Task discovery, trajectory inference, and Skill induction. ‣ Construction Pipeline ‣ 3.1 Resource-to-Skill Construction ‣ 3 Method")).
During execution, the agent selects a Skill for the required workflow
and consults References as needed to incorporate software knowledge into
its actions.

#### Construction Pipeline

We represent a Skill as $`s=(n_{s},d_{s},a_{s},p_{s},b_{s})`$, where
$`n_{s}`$ is its name, $`d_{s}`$ is its capability description,
$`a_{s}`$ specifies its applicability, $`p_{s}`$ lists its
preconditions, and $`b_{s}`$ contains its procedural body, including the
steps needed to accomplish the goal. We represent a Reference as
$`r=(n_{r},d_{r},c_{r})`$, where $`n_{r}`$ is its name, $`d_{r}`$
describes its purpose, and $`c_{r}`$ contains the concrete lookup
content. Construction first organizes the documentation into a shared
evidence corpus. From this corpus, one branch extracts References, while
the other discovers Tasks, infers trajectories, and induces Skills.

##### Traceable evidence organization.

To support all downstream stages and reduce hallucinations, we organize
documentation into traceable evidence. A parser uses authored headings
and navigation to structure text and visual content while retaining
source locations. An agent refines this organization without rewriting
the content. Every downstream Reference, Task, and inferred action or
observation must be grounded in this evidence.

##### Reference extraction.

To make shared software knowledge accessible during execution, the
Reference branch turns relevant evidence into focused lookup entries. A
program first extracts and deduplicates candidate lookup content from
the documentation, including command tables, syntax constraints, and
shortcut descriptions. An agent reviews the remaining candidates to
decide what to retain and how to group them, preserving documented
syntax, parameters, and examples.

##### Task discovery, trajectory inference, and Skill induction.

To ground reusable Skills in concrete operational requirements, the
other branch proceeds from goals to trajectories before induction. An
agent first discovers source-supported user goals without benchmark task
input. For each Task, it infers ordered actions and expected
observations, retaining documented controls. These trajectories make the
required operations explicit before related procedures are grouped into
a coherent Skill, helping preserve actionable detail during abstraction.
After induction, we check whether the operational capability expressed
by each trajectory is included in a Skill and explicitly record any
exclusions.

Each stage produces structured outputs that serve as inputs to
subsequent stages, yielding the initial library
$`\mathcal{L}_{0}=(\mathcal{S}_{0},\mathcal{R}_{0})`$. Reference
extraction, Task discovery, trajectory inference, and Skill induction
are assigned to independent agents, each with its own tools, prompt, and
required output format. A unified description of the Resource-to-Skill
pipeline, including agent roles and tools, prompts, and output schemas,
is provided in
Appendix [F](#A6 "Appendix F Resource-to-Skill Implementation Details").

### 3.2 Execution-Guided Skill Self-Evolution

Differences between documented and deployed software versions, together
with gaps between resource coverage and task requirements, can leave the
initial library misaligned with the target environment or incomplete for
its tasks. ScienceCUA therefore keeps the execution model fixed and
continually evolves Skills and References through two mechanisms:
failure-history-guided exploration and source-grounded knowledge
addition.

##### Evolution setting and overall workflow.

As described in
Section [4.2](#S4.SS2 "4.2 Expanding the Benchmark for Skill Self-Evolution ‣ 4 ScienceBoard-VE: A Verified and Expanded Benchmark for Scientific Computer-Use Agents"),
ScienceBoard-VE contains an evolution set
$`E=\mathrm{Expanded}\setminus\mathrm{Verified}`$ and a held-out test
set $`V=\mathrm{Verified}`$, where $`E\cap V=\emptyset`$. Evolution uses
$`E`$, while $`V`$ remains unseen until final evaluation. Given the
initial library $`\mathcal{L}_{0}=(\mathcal{S}_{0},\mathcal{R}_{0})`$,
ScienceCUA processes each task $`q\in E`$ independently and maintains
its history $`\mathcal{H}_{q}`$. Histories and provisional updates are
not shared across tasks.

Each task uses two types of execution. Task exploration attempts the
task with the frozen initial library, together with any prior failure
records available, to search for a feasible path and collect
environmental feedback. Candidate validation temporarily loads one
modified or newly added Skill or Reference and reruns the task to test
whether that candidate can independently support successful execution.

Each task begins with task exploration. A first-exploration success
requires no update and exits the evolution process. After a failure, the
system either makes no change, revises existing knowledge, or adds
source-supported knowledge according to its diagnosis. Any modified or
newly added Skill or Reference undergoes candidate validation. A
successful candidate enters the candidate pool $`\mathcal{P}`$. A failed
candidate and its validation trajectory enter $`\mathcal{H}_{q}`$ to
guide the next task exploration. If a later exploration succeeds with
the help of failure history, the system contrasts it with earlier
failures, derives a revision candidate when needed, and validates it.
Each task contributes at most one validated candidate to
$`\mathcal{P}`$. These candidates are then consolidated into
$`\mathcal{L}_{\mathrm{final}}`$, merged targets undergo regression
certification, and the library is frozen for evaluation. Further details
are provided in
Appendix [I](#A9 "Appendix I Execution-Guided Skill Self-Evolution: Additional Details").

##### Failure-history-guided exploration.

The first exploration of task $`q`$ performs normal routing over
$`\mathcal{L}_{0}`$ by selecting entries from their names and
descriptions; the routed Skills and References define
$`\mathcal{F}_{q}\subseteq\mathcal{L}_{0}`$. Later task explorations
load the same entries in their initial versions and additionally receive
the accumulated failure history. Formally, the $`i`$-th exploration is
$`\tau_{q}^{(i)}=\operatorname{Execute}_{\theta}(q;\mathcal{L}_{0},\mathcal{F}_{q},\mathcal{H}_{q}^{(i)})`$,
where $`\mathcal{H}_{q}^{(1)}=\emptyset`$. For $`i>1`$,
$`\mathcal{H}_{q}^{(i)}`$ contains the task’s earlier failed task
explorations and candidate validations, including their trajectories,
screenshots, and outcomes. These failure records help the model avoid
paths that failed because of version mismatch, rather than mechanically
follow initial knowledge that conflicts with the deployed software.
Later explorations always start from the same $`\mathcal{L}_{0}`$ and
$`\mathcal{F}_{q}`$: failure history changes exploration behavior,
whereas knowledge changes still require independent validation.
Appendix [I.2](#A9.SS2 "I.2 Complete Execution History and Input Separation ‣ Appendix I Execution-Guided Skill Self-Evolution: Additional Details")
specifies the archived evidence and its input format.

##### Failure diagnosis and candidate construction.

For a failed task exploration, the diagnosis module analyzes its loaded
Skills and References, trajectory, screenshots, and evaluator outcome,
and assigns one primary cause: (1) grounding failure, where interface
perception or manipulation is the main obstacle and no candidate is
produced; (2) modify existing knowledge, where one entry in
$`\mathcal{F}_{q}`$ is relevant but contains an incorrect or incomplete
procedure, condition, parameter, or version-dependent instruction; or
(3) add new knowledge, where the routed knowledge has a genuine coverage
gap and triggers retrieval from the original resources $`\mathcal{D}`$.
The modify branch produces one complete revision candidate
$`\Delta_{q}^{(i)}`$; the add branch produces a new Skill or Reference
candidate only when retrieval finds sufficient source support. Any
resulting candidate is independently validated: success adds it to
$`\mathcal{P}`$ and terminates task $`q`$, whereas failure records it in
$`\mathcal{H}_{q}`$ before task exploration resumes. Separately, only
when a later task exploration itself succeeds does the system contrast
that success with earlier failures and either revise one entry in
$`\mathcal{F}_{q}`$ or make no change; this branch cannot add knowledge.
Details are provided in
Appendices [I.3](#A9.SS3 "I.3 Task Exploration, Failure Diagnosis, and Candidate Validation ‣ Appendix I Execution-Guided Skill Self-Evolution: Additional Details")
and [I.4](#A9.SS4 "I.4 Submission After History-Guided Success ‣ Appendix I Execution-Guided Skill Self-Evolution: Additional Details").

##### Independent candidate validation.

For candidate $`\Delta_{q}^{(i)}`$, ScienceCUA constructs the temporary
library
$`\widetilde{\mathcal{L}}_{q}^{(i)}=\mathcal{L}_{0}\oplus\Delta_{q}^{(i)}`$,
where $`\oplus`$ replaces one initial entry with its revision or inserts
one source-supported new entry. Validation then executes
$`\widetilde{\tau}_{q}^{(i)}=\operatorname{Execute}_{\theta}(q;\widetilde{\mathcal{L}}_{q}^{(i)},\widetilde{\mathcal{F}}_{q}^{(i)},\emptyset)`$
in a reset environment and a fresh session. It fixes the route obtained
by the first task exploration, with the candidate entry substituted or
added, and receives no prior trajectory, diagnosis, or candidate
rationale, thereby testing whether the candidate knowledge itself
supports the task. A successful candidate enters $`\mathcal{P}`$; a
failed candidate remains inactive, and its execution record is added to
the task’s failure history.
Appendix [I.3](#A9.SS3.SSSx1 "Independent Candidate Validation ‣ I.3 Task Exploration, Failure Diagnosis, and Candidate Validation ‣ Appendix I Execution-Guided Skill Self-Evolution: Additional Details")
gives the complete validation protocol.

## 4 ScienceBoard-VE: A Verified and Expanded Benchmark for Scientific Computer-Use Agents

Figure 4: Task distribution in ScienceBoard-VE. The inner ring groups
tasks by application. The outer ring separates verified evaluation tasks
(V) from evolution tasks (E). R+X denotes revised or removed tasks in
the original benchmark. The removed task is excluded from the sector
sizes.

ScienceBoard ([Sun et al., 2026](#bib.bib17)) is a benchmark for
scientific computer-use agents and has been adopted in subsequent
studies on agent evaluation, training, and task expansion ([Lv et al.,
2026](#bib.bib10); [Lu et al., 2026](#bib.bib9)). During reproduction,
we audited all 169 original tasks and identified issues in task
instructions, task statements, reference answers, evaluators, and
execution environments. We therefore construct ScienceBoard-Verified and
add a disjoint set of tasks for skill self-evolution. Together, they
form ScienceBoard-VE. We also extend the evaluation framework to support
native-agent evaluation.
Figure [4](#S4.F4 "Figure 4 ‣ 4 ScienceBoard-VE: A Verified and Expanded Benchmark for Scientific Computer-Use Agents")
summarizes the task distribution and benchmark quality assurance.

### 4.1 ScienceBoard-Verified

We substantively revise 37 tasks and remove one additional task,
yielding 168 executable tasks reserved for final evaluation. We organize
the revisions and supporting repairs into four categories: (1)
Instruction Ambiguity, which covers 15 revised tasks with unclear goals
or omitted completion requirements; (2) Task & Answer Errors, which
covers 12 revised tasks involving incorrect task statements, reference
answers, or expected evaluator results; (3) Evaluator Bias, which covers
10 revised tasks in which unnecessary restrictions exclude valid
execution paths, output representations, or output locations; and (4)
Environment Repairs, which covers application prompts, response
handling, runtime and initialization settings, and unavailable external
dependencies. The fourth category includes shared evaluation-environment
repairs and the removed task; these do not add to the 37 revised tasks.
Appendix [G](#A7 "Appendix G ScienceBoard-Verified: Detailed Repairs")
details all 37 task revisions, the task removal rationale, and the
associated evaluation-environment repairs.

### 4.2 Expanding the Benchmark for Skill Self-Evolution

To separate skill improvement from final evaluation, we add 108 tasks
that do not overlap with the verified test set: 20 each for KAlgebra,
Celestia, GRASS GIS, ChimeraX, and Lean 4, and 8 for TeXstudio. These
tasks are used exclusively for skill self-evolution, while the 168 tasks
in ScienceBoard-Verified remain unseen during skill construction and
evolution and are used only for final evaluation. The resulting
ScienceBoard-VE contains 276 executable tasks in total. The evolution
tasks use the same types of software operations as the test tasks but
differ in their specific targets or requirements, allowing execution
experience to transfer without reusing the test tasks themselves. See
Appendix [H](#A8 "Appendix H Task Construction and Deduplication") for
details.

### 4.3 Native-Agent Evaluation

The original ScienceBoard evaluates models through a unified API-based
interaction loop. We extend it to support native evaluation of Codex and
Grok Build, keeping tasks, software environments, and evaluators
unchanged. In both settings, ScienceBoard supplies screenshots and
accessibility trees, executes the returned action code or control
instructions, and evaluates task outcomes. In the model-based setting,
each API request includes the system prompt, task instruction,
screenshots and accessibility trees from the three most recent steps
together with the model-generated actions for those steps, and the
current screenshot and accessibility tree. For ScienceCUA, we implement
two-stage resource routing through progressive disclosure. Before
execution, the evaluated model selects relevant Skills and References
from their names and descriptions based on the task instruction. The
selected entries are then loaded in full into the system prompt and
included in every subsequent execution request. In the native-agent
setting, each task uses a separate persistent session, to which the
outer evaluation framework appends only the current screenshot and
accessibility tree at each step. The native harness maintains the task
history and compacts context as needed. Skills and References are
registered as independently loadable native resources, which the agent
selects and reads during execution. Each turn concludes with one
ScienceBoard action block for the evaluation framework to execute. To
prevent agents from obtaining additional reference material through web
search, we disable web search for native agents. To preserve task
independence, conversation history and runtime context are maintained
separately for each task and are not shared between tasks.

## 5 Experiments

##### Experimental setup.

We evaluate ScienceCUA on ScienceBoard-Verified. Model-based evaluation
uses Qwen-3.8 Max, GLM-5.2, Grok-4.6, and GPT-5.5. Native-agent
evaluation uses Grok Build with Grok-4.6 and Codex with GPT-5.5. The two
settings follow the respective interaction and resource access protocols
described in
Section [4.3](#S4.SS3 "4.3 Native-Agent Evaluation ‣ 4 ScienceBoard-VE: A Verified and Expanded Benchmark for Scientific Computer-Use Agents").
In model-based ScienceCUA evaluation, at most three Skill and Reference
entries are selected in total before each task. In native-agent
evaluation, the agent autonomously selects and reads resources during
execution, with no limit on the number of Skill and Reference entries it
can access. We report task success rates for each of the six
applications and use their unweighted mean as the overall performance
metric.

Model-based evaluation compares ScienceCUA with Vanilla, direct document
injection, RAG, VisualSkill, and SkillFoundry. Native-agent evaluation
compares Vanilla, VisualSkill, SkillFoundry, and ScienceCUA. ScienceCUA
and VisualSkill use the same documentation inputs. SkillFoundry does not
support direct documentation input and instead automatically searches
for and collects online resources based on the name and version of the
software installed in the execution environment. Implementation details
are provided in
Appendix [B](#A2 "Appendix B Direct Documentation Injection Details")
for direct injection,
Appendix [C](#A3 "Appendix C Retrieval-Augmented Generation Details")
for RAG,
Appendix [D](#A4 "Appendix D SkillFoundry Reproduction Details") for
SkillFoundry, and
Appendix [E](#A5 "Appendix E VisualSkill Reproduction Details") for
VisualSkill.

Skill self-evolution uses the 108 additional tasks in ScienceBoard-VE.
After evolution, the knowledge library is frozen and evaluated on
ScienceBoard-Verified without access to evolution trajectories or
histories.

### 5.1 RQ1: Can ScienceCUA-constructed resources improve task success in scientific software operation?

Table [1](#S5.T1 "Table 1 ‣ Experimental setup. ‣ 5 Experiments") shows
that the initial ScienceCUA library achieves the highest average success
rate in all four model-based settings. ScienceCUA improves over Vanilla
by 5.76–7.23 percentage points, compared with 1.53–3.42 points for
direct document injection, and outperforms RAG, VisualSkill, and
SkillFoundry across all four models. The gains also extend to
native-agent evaluation. ScienceCUA reaches average success rates of
55.41% with Grok Build and 59.82% with Codex, improving over their
respective Vanilla baselines by 9.12 and 5.73 percentage points and
outperforming VisualSkill and SkillFoundry in both settings.
Figure [5](#S5.F5 "Figure 5 ‣ Experimental setup. ‣ 5 Experiments")(a)
shows that ScienceCUA requires 21.1–28.9% less total task execution time
than direct document injection across the four models. ScienceCUA also
reduces total initial library construction time by 62.2% and 34.6%
relative to VisualSkill and SkillFoundry, respectively
(Figure [5](#S5.F5 "Figure 5 ‣ Experimental setup. ‣ 5 Experiments")(b)).
These results support the usefulness of the constructed Skills and
References as initial operational knowledge for scientific software.

### 5.2 RQ2: Do Skills and References make complementary contributions to task success?

We ablate Skills and References separately to assess the individual and
joint contributions of procedural guidance and cross-task shared lookup
knowledge to task success. Skills organize complete operational
procedures around specific goals, while References provide shared
knowledge that is not tied to any single procedure, including syntax
constraints, parameter rules, command and function catalogs, and
keyboard shortcuts. The two resource types have no one-to-one
correspondence that permits direct, equivalent merging. We therefore do
not use a forced merger of the two resource types as an
information-matched control for knowledge organization, and instead use
resource ablations to evaluate the value of providing each knowledge
type individually and both jointly.

Table [2](#S5.T2 "Table 2 ‣ 5.2 RQ2: Do Skills and References make complementary contributions to task success? ‣ 5 Experiments")
shows that providing either resource type alone improves average success
rates over Vanilla, while providing both achieves the best results. In
model-based evaluation with Grok-4.6, the average success rates are
40.09% with Skills alone, 40.62% with References alone, and 44.70% with
both. The corresponding results for native Grok Build are 49.89%,
51.14%, and 55.41%. The relative gains from the two resource types vary
across applications, while providing both further improves overall
performance, supporting the complementary contributions of procedural
guidance and shared lookup knowledge to task execution.

The KAlgebra C-05 comparison in
Appendix [J](#A10 "Appendix J Case Study: Complementary Roles of Skills and References in KAlgebra")
illustrates these roles under the same budget of five interaction turns.
Each condition retains autonomous routing over the permitted resource
types. Reference-only spends its budget locating the script-loading
interface; Skill-only loads the script but leaves the calculation
symbolic. With both types, the agent combines the script-loading Skill’s
guidance with application-specific knowledge from the function-catalog
Reference, then corrects an intermediate vector-valued result using
execution feedback to complete the task.

Figure [5](#S5.F5 "Figure 5 ‣ Experimental setup. ‣ 5 Experiments")(c)
further illustrates actual calls to both resource types during task
execution. Native Grok Build with Grok-4.6 (xhigh) accesses at least one
resource in 156 of the 168 tasks (92.9%). Final task attempts contain
291 completed Skill calls and 543 completed Reference calls, with
repeated calls to the same entry counted separately. These records show
that the agent calls both Skills and References during actual task
execution and, together with the preceding ablation results, support the
contributions of both knowledge types to task completion.

### 5.3 RQ3: Can self-evolution mitigate the limitations of Resource-to-Skill construction?

The initial library may lack task-relevant knowledge or contain
instructions incompatible with the deployed software version. We use
Grok-4.6 (xhigh) and GPT-5.5 (xhigh) to compare the initial library,
Full ScienceCUA, two ablated variants, Trace2Skill ([Ni et al.,
2026](#bib.bib11)), and SkillCAT ([Chen et al., 2026](#bib.bib5)),
examining whether execution-guided self-evolution improves performance
on unseen tasks. The $`-`$Knowledge addition variant only revises
existing entries without adding new Skills or References. The
$`-`$Failure history variant withholds prior exploration and
candidate-validation records from subsequent exploration, leaving the
other mechanisms unchanged. Within each model setting, all evolution
variants use the same initial library, evolution tasks, software
environments, and runtime configurations. Detailed ScienceCUA settings
are provided in
Appendix [I](#A9 "Appendix I Execution-Guided Skill Self-Evolution: Additional Details").

Table [3](#S5.T3 "Table 3 ‣ 5.3 RQ3: Can self-evolution mitigate the limitations of Resource-to-Skill construction? ‣ 5 Experiments")
shows that self-evolution improves the average success rate from 44.70%
to 54.59% for Grok-4.6 and from 57.16% to 65.81% for GPT-5.5, yielding
gains of 9.89 and 8.65 percentage points, respectively. Full ScienceCUA
also outperforms Trace2Skill and SkillCAT, which achieve average success
rates of 46.44% and 53.02% with Grok-4.6, and 60.46% and 63.74% with
GPT-5.5, respectively. These results indicate that knowledge
improvements obtained during evolution transfer to final test tasks not
used during evolution.

Removing either knowledge addition or failure history reduces average
success rates, but the dominant source of improvement varies by
application. KAlgebra and Celestia are particularly sensitive to failure
history: removing it reduces success by 9.68 percentage points for
KAlgebra under both models, and by 9.09 and 6.06 points for Celestia
under Grok-4.6 and GPT-5.5, respectively. Documentation-version
mismatches leave some initial entries with inapplicable capability
constraints or interface paths.
Appendix [K](#A11 "Appendix K Case Study: How Self-Evolve Repairs Resource–Environment Mismatches and Improves Task Performance")
traces how execution feedback repairs such a constraint in KAlgebra,
while
Appendix [M](#A13 "Appendix M Case Study: Outdated Interface Guidance in Celestia")
shows how outdated interface guidance consumes execution steps in an
initial Celestia run. GRASS GIS benefits especially from knowledge
addition: removing it reduces success by 14.71 and 5.89 points under the
two models. Its broad documentation leaves task-relevant module options
underspecified in the initial library;
Appendix [L](#A12 "Appendix L Case Study: Adding a Module-Level Reference for GRASS GIS")
shows how adding a module-level Reference fills this gap and supports
related Verified tasks. Gains are smaller or less consistent for the
other applications. Lean 4 tasks require specialized formal proofs that
the general theorem-proving guide rarely supplies directly, while many
TeXstudio tasks require information from other software beyond the
TeXstudio manual.
Appendix [N](#A14 "Appendix N Task Requirements and Documentation Scope for Lean 4 and TeXstudio")
compares these task requirements with the source documentation.

## 6 Conclusion

We present ScienceCUA, a two-stage framework for computer-use agents
operating scientific software. The first stage extracts source-grounded
operational knowledge from software documentation, distilling task-level
workflows into executable Skills and organizing commands, syntax, and
parameter constraints as queryable References. The second stage refines
Skills and References using execution feedback from the target software
environment. We also construct the audited ScienceBoard-Verified and add
evolution tasks disjoint from the test set to form ScienceBoard-VE,
supporting knowledge evolution and native-agent evaluation. Experiments
across six scientific applications show that the initial Skills and
References improve average task success by up to 7.23 percentage points
over the baseline in model-based evaluation. Knowledge self-evolution
increases the total gain to as much as 17.12 percentage points. These
results suggest that human-authored software resources can be
transformed into executable, verifiable operational knowledge that
continually improves through environmental feedback, enhancing
general-purpose agents’ ability to use scientific software. By
maintaining Skills and References outside the model parameters,
ScienceCUA offers a practical path for agents to adapt to changes in
scientific software environments and task requirements without
retraining the model.

## Appendix A Discussion and Implications

##### Niche and private software are priority settings for our approach.

Knowledge of niche, private, or self-developed software may be
underrepresented during general models’ pre-training and post-training,
leaving gaps in their understanding of specific functions, workflows,
and usage constraints. Extracting knowledge from documentation therefore
has the potential to yield larger performance gains for such software.
Execution feedback can then guide revisions and additions that adapt
this knowledge to the deployed environment and task requirements. For
widely used software whose operational knowledge is well covered during
training, models may already know much of the documented material,
leaving less room for improvement through external knowledge.

##### Knowledge organization should reflect software and task requirements.

Scientific software requires both operational workflows and precise
parameter constraints, syntax rules, and command and function catalogs.
These details are often shared across tasks and consulted only when a
step requires them. ScienceCUA therefore organizes goal-oriented
procedural knowledge as Skills and shared lookup knowledge as
References, allowing agents to follow workflows while accessing specific
rules and details on demand. Other software and scenarios may require
different forms of knowledge organization. Applying our approach to
these settings can retain the process of constructing knowledge from
resources and improving it through execution, while adapting knowledge
organization to the target setting. Such adaptation could include
exploring code-based or visual representations, whose effectiveness we
have not systematically compared within the same framework.

##### Base model capabilities affect the value of external knowledge augmentation.

Recent frontier models, such as GPT-6 Astra, demonstrate stronger
computer-use capabilities. As models become able to complete more
scientific-software tasks on their own, the additional gains from
ScienceCUA’s self-evolved Skills and References may diminish, a pattern
observed in our supplementary experiments
(Appendix [P](#A16 "Appendix P Supplementary Evaluation of Frontier Models")).
Similar effects may arise in other CUA settings: when a base model
already possesses the relevant operational knowledge, the room for
improvement from Skills may shrink; if their guidance is outdated,
inapplicable to the task, or imposes unnecessary constraints on
execution paths, it may even interfere with the model’s own judgment and
lead to worse performance than the base model without Skills. The value
of external knowledge therefore needs to be evaluated in relation to the
base model’s capabilities and the specific task. Practical deployment
must also balance task performance against inference cost. In
budget-constrained settings that call for lower-cost models,
constructing and continually improving external knowledge from software
resources retains practical value. Moreover, the software covered by
ScienceBoard has publicly available documentation, and models may
already have learned some of this operational knowledge. For niche,
private, or self-developed software whose knowledge is underrepresented
during model training, external knowledge may still fill capability gaps
and yield larger gains. This expectation warrants further empirical
validation.

screenshots and accessibility trees from the three most recent steps
together with the model-generated actions for those steps, and the
current screenshot and accessibility tree. Documentation for the
corresponding application is added to every request. ScienceBoard
executes the action code or control instructions returned by the model.

## Appendix C Retrieval-Augmented Generation Details

This appendix describes the retrieval-augmented generation (RAG)
pipeline. Offline preprocessing freezes one corpus per application,
applies structure-preserving chunking and hybrid retrieval, and
materializes task-specific context bundles for deterministic loading at
execution. All tasks of an application share the same corpus. Documents
are never manually paired with tasks.

before retrieval. Bundle generation and benchmark execution use only
these local snapshots, shared across all tasks and evaluated models for

##### PDF normalization.

PDF text is extracted with PyMuPDF from the embedded text layer. OCR is
disabled and raster images are not indexed. Repeated headers and footers
are removed. We infer a hierarchy from chapter, section, appendix, and
numbered headings and retain page ranges as source locators. When a
reliable semantic heading is unavailable, the corresponding page is kept
as a page-level document rather than discarded. This yields 81 semantic
sections and 7 page fallbacks for KAlgebra. The Celestia guide is
retained as 48 page-level documents because its layout does not provide
sufficiently reliable semantic section boundaries.

##### HTML acquisition and freezing.

Each HTML corpus begins at a fixed official documentation root. URLs are
canonicalized and restricted to the documentation scope. The reachable
in-scope link queue is traversed to exhaustion, with no page-count
limit, and every successful response is frozen with its requested URL,
final URL, acquisition time, raw HTML hash, outgoing links, and local
file locator. GRASS GIS contains 1,468 successful pages and ChimeraX
contains 277. Both acquisition queues have zero pending URLs. Images,
video, CSS, JavaScript, PDFs, and pages outside the documentation scope
are excluded. The Lean 4 and TeXstudio documentation trees contain 13
and 9 in-scope pages, respectively, all of which are retained.

##### HTML normalization.

For every retained page, the extractor selects the main, article, or
body content and removes scripts, styles, templates, and navigation
chrome. It segments the remaining content at h1–h6 boundaries.
Paragraphs, lists, tables, and preformatted code are preserved in
reading order, with code represented as fenced blocks. Exact duplicate
pages are removed by content hash. Raw HTML and normalized
Markdown-compatible text are both retained for audit, but only
normalized text is indexed. This procedure is deterministic and uses no
language model.

### C.2 Structure-Preserving Chunking

Chunk boundaries are computed with the tokenizer of BAAI/bge-m3. Each
indexable text is prefixed with its document title and complete section
breadcrumb. The target length is 700 tokens and the hard maximum,
including this prefix, is 1,000 tokens. Text that exceeds the limit is
split preferentially at paragraph, line, or sentence boundaries with an
80-token overlap between consecutive pieces. Chunks never cross
documents or semantic sections. Exact duplicates are removed using the
SHA-256 hash of the complete index text. Near-duplicate removal is not
applied. The counts in
Table [6](#A3.T6 "Table 6 ‣ C.1 Frozen Documentation Corpora ‣ Appendix C Retrieval-Augmented Generation Details")
are post-deduplication, and no resulting chunk exceeds the hard limit.

### C.3 Hybrid Retrieval and Reranking

Retrieval is performed independently for each application. The query is
exactly the stripped task instruction. The software name is used only to
select the corresponding corpus and is not appended to the query.
Cross-application retrieval is disabled.

We retrieve 30 candidates with BM25 and 30 with a dense encoder. BM25
uses $`k_{1}=1.2`$, $`b=0.75`$, binary query term frequency, and a
Unicode-aware tokenizer that preserves compound identifiers. Dense
retrieval uses BAAI/bge-m3 with a maximum input length of 1,024 tokens,
CLS pooling, and L2-normalized embeddings. Encoding uses FP16 on CUDA
with batch size 2. The resulting 1,024-dimensional vectors are stored in
FP32. Similarity is exact cosine similarity, implemented as a dot
product over normalized vectors, without approximate-nearest-neighbor
search.

The two ranked lists are combined by equal-weight reciprocal rank fusion
(RRF):

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\operatorname{RRF}(d)=\sum_{s\in\{\mathrm{BM25},\mathrm{dense}\}}\frac{1}{60+\operatorname{rank}_{s}(d)}.
``` |  | (1) |

The 40 highest-scoring fused candidates are reranked with
BAAI/bge-reranker-v2-m3. The reranker uses a maximum input length of
1,024 tokens, FP16 CUDA inference, batch size 4, and its unnormalized
output score. Ties are resolved deterministically using the fused score
and chunk identifier.

We select up to five reranked chunks whose rendered references fit a
6,000-token context budget. Each numbered reference gives its rank,
document title, section breadcrumb, and chunk text. Retrieval scores are
hidden. The references are enclosed by documentation markers and
prepended to the unmodified original task instruction.

### C.4 Frozen Task Bundles and Runtime Protocol

Offline retrieval produces one frozen bundle per ScienceBoard-Verified
task, storing the query, corpus and index identities, configuration
hash, candidate rankings, final five chunks, and rendered instruction.
The 168 bundles comprise 31 for KAlgebra, 33 for Celestia, 34 for GRASS
GIS, 28 for ChimeraX, 26 for Lean 4, and 16 for TeXstudio. Each is
reused across all evaluated models.

At initialization, hashes and identities are verified. Invalid bundles
fail without live fallback. Runtime uses no retrieval assets or
evaluation data.

### F.1 DSH Child Session Contracts

A DSH child session is defined by more than its prompt. For an Agent
$`a`$, the complete executable contract is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathfrak{C}_{a}=(P_{a},I_{a},T_{a},B_{a},O_{a},V_{a},\tau_{a}),
``` |  | (2) |

where $`P_{a}`$ is the prompt, $`I_{a}`$ is the input scope, $`T_{a}`$

### F.2 Deterministic Validation and Control

All Agent outputs are validated by Python before entering a downstream
stage. A textual citation must contain a quote that exactly matches the
corresponding Evidence text; a visual claim must reference an authorized
and inspected image artifact. Citations cannot point to nonexistent or
out-of-scope Evidence, and downstream objects can reference only
upstream identifiers present in the current frozen snapshot.

Stage-specific validation additionally checks schema constraints,
duplicate candidates, field lengths, step ordering, and cross-object
consistency. For Trajectories, Python verifies that the submitted
task_id matches the dispatched Task, that exactly one acceptable
trajectory is returned, that step ordinals are consecutive, and that
linked References exist and satisfy the reference_guided dependency
rules. For Skills, Python validates Task/Trajectory/Reference relations,
step structure, exact citations, and the coverage protocol over every
dispatched Trajectory.

Pipeline state changes only through structured submission tools.
Ordinary natural-language replies do not commit business results. Key
stages freeze immutable CorpusSnapshot and KnowledgeSnapshot objects so
that downstream child sessions read stable inputs. Attempt/Receipt
bookkeeping, idempotent retry, recovery, and storage details are
implementation mechanisms and are documented in the released code rather
than expanded here.

## Appendix G ScienceBoard-Verified: Detailed Repairs

This appendix documents the 37 task revisions and one task removal made
when constructing ScienceBoard-Verified, corresponding to the 38 revised
or removed tasks summarized in
Figure [4](#S4.F4 "Figure 4 ‣ 4 ScienceBoard-VE: A Verified and Expanded Benchmark for Scientific Computer-Use Agents").
A task may involve multiple issues; we assign it to one category to
avoid double counting and describe secondary changes in the same entry.
The first three categories contain 15, 12, and 10 revised tasks,
respectively. The fourth contains the removed task and shared
evaluation-environment repairs, which are not counted as additional task
revisions.

### G.1 Instruction Ambiguity

These revisions clarify the intended target, information source, or
completion requirements so that the instructions explicitly state what
the evaluator expects.

##### 1. Celestia A-02: Time direction and rate.

The original instruction, “-20x slower,” could be interpreted as running
backward at 20 times normal speed, whereas the evaluator expects a time
scale of 0.05. The revised instruction explicitly requests forward
playback at 0.05x, or 20 times slower than real time.

##### 2. Celestia C-06: Ambiguous G0 star selection.

The instruction asks for the name of the “only” G0 star, but the
software lists multiple stars of this spectral type. We specify the
closest G0 star to identify the intended object unambiguously.

##### 3. Celestia C-10: Unspecified distance convention.

Asking for the globular cluster “farthest from the Milky Way” could
prompt agents to change the distance reference. The revision instead
specifies the cluster with the largest Distance (ly) value in Celestia’s
Deep Sky Objects browser and requests its radius in light-years to two
decimal places.

##### 4. TeXstudio A-01: Angle insertion.

The task asks the agent to measure an angle between specified atoms in
ChimeraX and replace a placeholder in the article. The evaluator checks
the saved file and compilation result, but these requirements were
omitted from the instruction. We explicitly require saving the TeX file
and ensuring successful compilation.

##### 5. TeXstudio A-02: Residue-name insertion.

The task asks for the name of residue /A:6 to be inserted into a table.
We add the previously unstated requirements to save the TeX file and
ensure that it compiles successfully.

##### 6. TeXstudio A-03: DNA sequence correction.

## Appendix I Execution-Guided Skill Self-Evolution: Additional Details

This appendix specifies the execution protocol used in
Section [3.2](#S3.SS2 "3.2 Execution-Guided Skill Self-Evolution ‣ 3 Method").
Evolution uses only $`E=\mathrm{Expanded}\setminus\mathrm{Verified}`$
and the original resources $`\mathcal{D}`$. For new-knowledge creation,
$`\mathcal{D}`$ is accessed through bounded live browsing that starts
from the configured official documentation root for the current
application and follows only in-scope links discovered from fetched
official pages. It does not use a search engine, BM25 retrieval, a saved
Resource-to-Skill snapshot, or model knowledge as source evidence. The
execution model is fixed, and $`V=\mathrm{Verified}`$ is reserved for
final evaluation.

### I.1 Frozen Initial Library and Per-Task State

All evolution tasks start from the same frozen initial library
$`\mathcal{L}_{0}=(\mathcal{S}_{0},\mathcal{R}_{0})`$. A task never
installs a provisional update into the library used by another task.
Instead, it maintains a private execution history and may contribute at
most one independently validated candidate to a global candidate pool
$`\mathcal{P}`$. Candidates are consolidated only after all tasks
terminate.

For each task $`q`$, its first task exploration selects a fixed routed
set $`\mathcal{F}_{q}`$ of Skills and References from
$`\mathcal{L}_{0}`$. Later task explorations use the same routed names
and initial versions, even after the task has produced a failed
candidate. This separates behavioral exploration from candidate
installation: rejected knowledge remains evidence, not active guidance.

Each candidate contains one complete target entry relative to
$`\mathcal{L}_{0}`$. A candidate produced after a failed exploration may
revise one entry in $`\mathcal{F}_{q}`$ or add one Skill or Reference
supported by $`\mathcal{D}`$. A candidate distilled after a later
successful exploration may only revise one existing routed entry. A
rejected candidate is never used as the textual base of a later
candidate.

### I.2 Complete Execution History and Input Separation

Each task has an indexed history archive. For every task exploration and
candidate validation, the archive records the task instruction,
execution type, exact execution-time prompt, raw action–observation
trajectory, evaluator outcome, routed Skill and Reference names, their
complete execution-time contents and version hashes, and every
screenshot mapped to its trajectory step. When applicable, it also
records the diagnosis and the complete candidate entry used in
validation. Screenshots are interpreted as pre-action observations: the
effect of an action is checked in the following screenshot.

The first task exploration receives no history. Every later task
exploration receives all earlier task explorations and candidate
validations for that task, including their exact prompts, raw
trajectories, diagnoses, candidates, outcomes, and screenshots. The
records are explicitly labeled so that the agent can distinguish
exploration from validation, identify which knowledge version was
loaded, and map each screenshot to its execution and step. All
historical screenshots are placed in the first model turn and marked as
evidence; the final live screenshot remains the state on which the agent
must act. The prompt instructs the agent to inspect the complete
history, avoid repeating failed action sequences, and not follow initial
Skills or References mechanically when current GUI evidence suggests a
version mismatch.

Diagnosis and knowledge writing receive the task, loaded entries, exact
prompt, raw trajectory, evaluator result, and complete screenshot
sequence. The analysis agent must inspect every screenshot before
submitting its result. Candidate validation is deliberately separated:
it receives no exploration history, successful trajectory, diagnosis, or
candidate rationale. This prevents the validation agent from succeeding
through transient trajectory memory rather than through the proposed
external knowledge.

### I.3 Task Exploration, Failure Diagnosis, and Candidate Validation

Let $`i\in\{1,\ldots,M_{\mathrm{explore}}\}`$ index task explorations
for task $`q`$. Each exploration begins from the standard initial
environment in a fresh session:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\tau_{q}^{(i)}=\operatorname{Execute}_{\theta}\bigl(q;\mathcal{L}_{0},\mathcal{F}_{q},\mathcal{H}_{q}^{(i)}\bigr),
``` |  | (3) |

where $`\mathcal{H}_{q}^{(1)}=\emptyset`$ and $`\mathcal{H}_{q}^{(i)}`$
for $`i>1`$ contains all earlier exploration and candidate-validation
records for $`q`$. Routing is performed normally only for $`i=1`$; its
result defines $`\mathcal{F}_{q}`$ for subsequent exploration and
validation.

If $`\tau_{q}^{(1)}`$ succeeds, the task exits without proposing an
update. A successful exploration with $`i>1`$ enters the submission
process in
Appendix [I.4](#A9.SS4 "I.4 Submission After History-Guided Success ‣ Appendix I Execution-Guided Skill Self-Evolution: Additional Details").
Each failed exploration is analyzed for one primary root cause.
Exhausting the action budget, stopping early, or failing the evaluator
describes the observed outcome rather than the underlying cause. The
diagnosis uses exactly three categories:

1.  1.
    Grounding failure (grounding_failure). Incorrect interface
    localization, targeting, state reading, or manipulation is the
    principal obstacle. Repeated grounding mistakes that consume the
    action budget can qualify. The counterfactual criterion is whether
    correcting those grounding mistakes would remove the principal
    obstacle; if an independent knowledge deficiency would remain, a
    knowledge category must be selected instead.
2.  2.
    Modify existing knowledge (modify_existing). One loaded Skill or
    Reference is relevant but contains an erroneous or incomplete
    procedure, omitted condition, inappropriate parameter, unsupported
    syntax, or version-dependent instruction. The target must be one
    entry in $`\mathcal{F}_{q}`$.
3.  3.
    Add new knowledge (add_new_knowledge). The routed entries do not
    contain the capability or operational knowledge needed for the task.
    This category is reserved for a genuine coverage gap rather than a
    minor defect in a relevant entry. The new Skill or Reference must be
    supported by task-relevant content in the original resources
    $`\mathcal{D}`$; without sufficient source support, no candidate is
    produced.

Diagnosis and conditional candidate writing occur in the same analysis
session. The diagnosis step fixes the category, evidence, and proposed
repair. For modify_existing, it also fixes the type and name of one
routed target, after which the next step writes its complete replacement
while retaining access to the same trajectory and screenshots. For
add_new_knowledge, the diagnosis deliberately leaves the target type and
name unspecified and describes only the missing reusable knowledge
scope. Only after this diagnosis is accepted does the same session
unlock bounded live access to $`\mathcal{D}`$; the research step
determines whether the supported artifact is a Skill or Reference,
chooses its stable title, and writes one complete new entry. If the
fetched official material is insufficient, no candidate is produced. A
grounding diagnosis likewise produces no candidate and therefore
requires no candidate validation. Either no-candidate outcome consumes
the current exploration attempt. If another exploration remains, the
task continues with its accumulated history. Even after the final
allowed exploration fails, its diagnosis and, when applicable, its one
candidate validation are still completed.

#### Independent Candidate Validation

For a candidate $`\Delta_{q}^{(i)}`$, validation constructs a temporary
library

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widetilde{\mathcal{L}}_{q}^{(i)}=\mathcal{L}_{0}\oplus\Delta_{q}^{(i)},
``` |  | (4) |

where $`\oplus`$ replaces the target’s initial version for a revision or
inserts one source-supported entry for an addition. The validation agent
starts from the task’s standard initial environment in a fresh session.
It force-loads the original entries named by $`\mathcal{F}_{q}`$; for a
revision, the candidate replaces its corresponding original entry, and
for an addition, the candidate is force-loaded in addition to all
original routed entries. Thus every attempt contains at most one
modified or new target.

The validation trajectory is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widetilde{\tau}_{q}^{(i)}=\operatorname{Execute}_{\theta}\bigl(q;\widetilde{\mathcal{L}}_{q}^{(i)},\widetilde{\mathcal{F}}_{q}^{(i)},\emptyset\bigr),
``` |  | (5) |

where the empty history excludes all prior trajectories, screenshots,
diagnoses, and rationales. The task evaluator alone determines success.
A successful candidate is added to $`\mathcal{P}`$ and the task
terminates. A failed candidate, its complete contents, and its
validation record are archived; if another task exploration remains,
that exploration again uses $`\mathcal{L}_{0}`$ and $`\mathcal{F}_{q}`$,
with the failed validation supplied only as history.

### I.4 Submission After History-Guided Success

A task exploration that succeeds at $`i>1`$ may have relied on failure
history unavailable at deployment. The submission agent therefore
contrasts the successful exploration with all earlier failed
explorations, candidate validations, loaded knowledge versions, and
candidate contents. In one response it either concludes that no
knowledge change is warranted or writes a complete revision to one
existing entry in $`\mathcal{F}_{q}`$. This process cannot create a new
Skill or Reference.

At most $`M_{\mathrm{submit}}`$ submission attempts are allowed. Every
revised candidate is generated from the target’s version in
$`\mathcal{L}_{0}`$, not by editing the preceding rejected submission
candidate. On later attempts, the submission agent additionally receives
all previous submission candidates and their validation trajectories so
that it can avoid repeating an ineffective revision. Each candidate is
validated through the history-free protocol in
Equation [5](#A9.E5 "In Independent Candidate Validation ‣ I.3 Task Exploration, Failure Diagnosis, and Candidate Validation ‣ Appendix I Execution-Guided Skill Self-Evolution: Additional Details").
The first successful candidate enters $`\mathcal{P}`$ and ends the task.

When the submission agent attributes a failed validation to grounding,
it may retain the same candidate and validate it again; the unchanged
retry consumes one submission attempt. If no candidate has yet been
proposed, it may instead validate the unchanged initial routed
knowledge. Success of this unchanged validation ends the task without
adding a candidate. If all $`M_{\mathrm{submit}}`$ attempts fail, the
task terminates without an update and does not return to task
exploration.

### I.5 Candidate Consolidation and Final Evaluation

After every evolution task terminates, accepted candidates are grouped
by target Skill or Reference. Revisions are grouped by the identity of
their original entry. For additions, a conservative Grok
semantic-deduplication pass groups candidates only when they have the
same knowledge type and express the same reusable capability at
substantially the same granularity, scope, and intended use; Skills and
References are never grouped together, and uncertain candidates remain
separate. Each group adopts the title of one independently validated
member rather than inventing a new title. If this auxiliary grouping
call is technically unavailable or violates its structured-output
contract, the pipeline fails open to exact type-and-title grouping,
thereby avoiding an unsupported merge. Different targets are
consolidated independently and are never mixed merely because they came
from the same task.

If a target has exactly one accepted candidate, that already validated
candidate is adopted directly without another task execution. If a
target has multiple candidates, the consolidation model receives every
accepted candidate and either the target’s complete initial content for
a revision or an explicit new-entry baseline for an addition. It then
produces one complete entry that preserves the independently validated,
non-conflicting improvements of all candidates. The merged text is not
allowed to discard a candidate-specific capability merely to simplify
the entry.

Because merging can change individually validated content, a
multi-candidate consolidation must pass regression certification. Let
$`Q_{g}`$ contain all tasks that contributed candidates to consolidated
target $`g`$. The same consolidated content and hash are installed for
every replay, and each $`q\in Q_{g}`$ is executed from its standard
initial environment in a fresh, history-free session with its
first-exploration routing fixed. The initial full replay over $`Q_{g}`$
does not consume the reflection budget.

If every replay succeeds, the target is certified. Otherwise, a
reflection agent receives the initial entry, all accepted candidates,
the current consolidation, and every regression prompt, raw trajectory,
evaluator outcome, and screenshot. It chooses between two actions:

1.  1.
    Revise. If the consolidated content caused or contributed to any
    failure, a complete replacement is regenerated from the initial
    entry and all accepted candidates rather than edited cumulatively
    from the failed consolidation. Previously passed results are
    invalidated, and all tasks in $`Q_{g}`$ are replayed.
2.  2.
    Keep. The current consolidation may be retained only when every
    current failure is attributable to grounding and the content itself
    requires no change. Passed tasks remain certified, and only the
    failed tasks are replayed.

Each reflection followed by its required replay consumes one of at most
$`M_{\mathrm{consolidation}}`$ cycles. Infrastructure or API failures
are handled separately and are not treated as task failures. If
certification still fails after the allowance is exhausted, target $`g`$
is rejected: a revised target retains its initial version, while an
uncertified addition is omitted. After all target groups are resolved,
$`\mathcal{L}_{\mathrm{final}}=\operatorname{Consolidate}(\mathcal{L}_{0},\mathcal{P})`$
is frozen and evaluated on $`V`$ with standard initial environments,
fresh sessions, normal routing, and no evolution history. No additional
global regression is performed.

### I.6 Stopping Conditions and Budgets

The default configuration uses

|  |  |  |  |
|----|----|----|----|
|  |
``` math
M_{\mathrm{explore}}=3,\qquad M_{\mathrm{submit}}=3,\qquad M_{\mathrm{consolidation}}=3.
``` |  | (6) |

Only task explorations consume $`M_{\mathrm{explore}}`$; their
diagnosis, candidate writing, and one independent candidate validation
do not. Only submission validations consume $`M_{\mathrm{submit}}`$. The
initial regression of a multi-candidate consolidation does not consume
$`M_{\mathrm{consolidation}}`$; each subsequent reflection-and-replay
cycle does.

Excluding consolidation replay, a conservative execution bound is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
N_{\mathrm{exec}}\leq|E|\bigl(2M_{\mathrm{explore}}+M_{\mathrm{submit}}\bigr),
``` |  | (7) |

which counts at most one candidate validation after each task
exploration and at most $`M_{\mathrm{submit}}`$ submission validations.
This is intentionally loose because a task that enters submission cannot
also fail all task explorations. For a multi-candidate consolidation
group $`g`$, regression adds at most
$`(1+M_{\mathrm{consolidation}})|Q_{g}|`$ task executions; keep
decisions can reduce this by retaining already passed tasks. These
bounds exclude final evaluation, diagnosis and writing calls, source
retrieval, routing, and separately limited infrastructure retries.

Evolution outcomes and consolidation replays are process measurements
and are not substituted for held-out evaluation results.

## Appendix J Case Study: Complementary Roles of Skills and References in KAlgebra

KAlgebra task C-05 illustrates how procedural guidance and shared

### J.1 Task, Routing, and Selected Knowledge

##### Task and initial state.

The task instruction is: *“Load script from ~/script.kal where vector
$`a`$ are defined. Let $`b=(\sqrt{3},2)`$; calculate their inner product
in KAlgebra and store the result in variable p.”* The script contains a
:= vector{-1, root(3, 3)}. Loading it defines $`a=(-1,\sqrt[3]{3})`$, so
the required scalar result is

|     |                                                         |     |
|-----|---------------------------------------------------------|-----|

## Appendix K Case Study: How Self-Evolve Repairs Resource–Environment Mismatches and Improves Task Performance

We use KAlgebra surface-plotting tasks to examine how a mismatch between
available documentation and the deployed software affects the initial
Skills and References, and how Self-Evolve addresses it through
execution feedback. Tasks B-14 and C-19 in Expanded–Verified expose the
initial failures and support Skill revision. We then examine whether the
frozen updated Skill helps previously failed tasks in the disjoint
Verified set succeed. All runs use Grok 4.6 (xhigh).

### K.1 Resource–Environment Mismatch: Why Self-Evolve Is Needed

Resource-to-Skill organizes documented procedures into callable Skills
and References, but their applicability depends on whether the
documentation describes the deployed environment. During resource

### K.2 From Execution Failure to Skill Revision

B-14 and C-19 belong to the Expanded–Verified evolution set. Throughout
exploration, the initial library and each task’s first routed resource
set remain fixed. After failure, the system retains the execution
trajectory, screenshots, evaluator result, diagnosis, and
candidate-validation records. Later explorations receive the accumulated
history for that task, with historical executions explicitly identified
and their mapped screenshots included in the prompt. They can therefore
reconsider unsuccessful actions while still starting from the original
routed resources.

Candidate revisions are tested separately in fresh environments without
exploration history. After a successful exploration, the submission step
uses that trajectory and the earlier failures to revise the original
Skill, followed by another independent validation. The discovered
procedure must thus be written into the Skill and reproduce success
without access to prior trajectories or diagnoses. The following
sections continue from the initial failures shown above.

## Appendix L Case Study: Adding a Module-Level Reference for GRASS GIS

##### Why broad resource coverage leaves a task-relevant gap.

The GRASS GIS Reference Manual organizes software knowledge into twelve
major sections. The benchmark tasks, however, are concentrated in a much
smaller part of this space, primarily the Graphical User Interface
(including Display), General, 3D raster processing, and Database
sections. Resource-to-Skill runs before the downstream task distribution
is known, so its initial construction aims to cover the software
broadly. This coverage-oriented strategy can produce Skills and
References for material that benchmark tasks rarely use, while leaving
frequently needed leaf-level knowledge too general to execute. The
d.vect command illustrates this mismatch: the initial Display catalog
identifies the command but does not provide the syntax and parameter
combinations needed by the recurring vector-styling tasks.

![\[Uncaptioned
image\]](2611.03238v1/Figure/grass_dvect/grass_manual_overview.png)

The manual spans twelve major sections; task demand is concentrated in a
subset. The d.vect command is documented under Display.

Prior Verified runs expose a recurring gap in this task family. B-04
requires an area fill color, B-06 a line width, and B-08 a point-symbol
size. Their initial routed resources contained a broad Display command
catalog, but the corresponding executions did not reach the required
d.vect parameters. These failures motivate adding knowledge at the
module level rather than writing a separate task-specific procedure for
each map.

##### B-18: diagnosing and filling the knowledge gap.

B-18 is an Expanded–Verified task in the evolution set: *“Display
countries@PERMANENT as red boundary lines only in GRASS GIS.”* The
initial resource set exposed the broad Display catalog, but not enough
executable detail to compose the required command. Grok Build examined
the failure evidence and the official GRASS manual, then selected a
Reference rather than a Skill. The diagnosis was that the missing
capability was declarative module knowledge—command syntax, option
semantics, accepted values, defaults, and parameter composition—rather
than an unlearned multi-step workflow. Grok Build browsed three pages
from the same official manual. All 12 retained source-evidence records
passed the later source audit, and the generator did not receive
Verified task prompts or answers.

The resulting module-level Reference, *d.vect Vector Display and
Styling*, generalizes beyond the B-18 map and color. Its relevant
guidance includes:

> color=name controls feature color; fill_color=name controls area fill.
> Areas use fill_color for their fill and color for their outline. Use
> fill_color=none to make areas transparent, or color=none to suppress
> area outlines.
> width=integer sets line width (default: 0).
> size=float sets point-symbol size (default: 5).
> attribute_column=name selects the label column; font, xref, and
> related options control label appearance and placement.

This knowledge is directly relevant to several task families:
independent outline and fill controls support B-18 and B-04; line-width
and symbol-size options support B-06 and B-08; label parameters provide
a reusable route for other vector-styling requests. The Reference
describes reusable d.vect behavior rather than a fixed answer to B-18 in
the evolution set: its options can be composed for other maps, colors,
and styling requests.

##### B-18 validation: applying the added module knowledge.

resource set. Using the command syntax and independent outline and fill
controls provided by the Reference, the agent constructs the command
below and executes it in the Command Console. The map is rendered with
red boundaries and no area fill, and B-18 passes. The added Reference
supplies the parameter knowledge missing from the initial catalog,
enabling the agent to compose the required command.

## Appendix O Research Setting and Baseline Reproduction Constraints of Resource2Skill

### O.1 Research Setting and Knowledge Objectives

Resource2Skill and ScienceCUA both investigate how to transform
human-created resources into reusable skills, but they differ in their
research settings and knowledge objectives.

Resource2Skill primarily addresses authoring tasks across domains such
as PPT, Web, Excel, Blender, CAD, UE5, and audio production. It distills
skills from tutorial videos, repositories, articles, documentation, and
reference artifacts. Its library provides retrievable and composable
authoring techniques, code patterns, and visual references to help
agents create new artifacts, with downstream evaluation primarily
measuring artifact quality.

ScienceCUA aims to improve the ability of models and agents to operate
scientific software. Starting from supplied PDF/HTML software
documentation, it discovers supported operational tasks, derives
task-level procedures, and organizes shared knowledge such as commands,
syntax, and parameter constraints. These forms of knowledge are
represented as Skills and References, respectively, to support agents in
completing user tasks in deployed software environments. Downstream
evaluation primarily measures task success.

Thus, although both approaches investigate resource-to-skill
construction, they differ in how resources are used, how knowledge is
organized, and what downstream evaluation emphasizes.

### O.2 Limitations in Adapting the Released Implementation

At the implementation level, the relevant public interfaces of
Resource2Skill do not directly provide the document-level
knowledge-construction process required for our collections of PDF/HTML
software documentation. Although the paper describes a construction
operator that can generate multiple candidate skills from a single
resource, the two interfaces directly relevant to our documentation
inputs have the following limitations in the public code we inspected.

1.  1.
    StaticArtifactConnector does not directly support PDF manual
    parsing. Its directory mode filters files using domain-specific
    extension lists, covering .xlsx, .html/.htm, .pptx, .blend, and
    selected audio and project formats, but excluding PDF. Consequently,
    the KAlgebra and Celestia PDF manuals used in our experiments cannot
    be directly processed through this mode. Its catalogue mode
    constructs candidates from supplied JSON fields, including
    descriptions and applicability; it does not itself parse the
    referenced manuals, discover knowledge units, or generate
    operational knowledge. [StaticArtifactConnector
    implementation](https://github.com/microsoft/Resource2Skill/blob/main/core/sources/static_artifact.py).
2.  2.
    ArticleConnector uses individual supplied pages as
    candidate-generation units. It accepts a URL list, fetches each
    page, and produces at most one CandidateSkill per URL. Its optional
    model call primarily extracts a title, applicability, tags, and a
    short summary. The interface does not implement recursive
    documentation crawling, cross-page evidence aggregation, or the
    discovery of multiple procedural knowledge units within a page.
    Supplying a documentation homepage or a list of page URLs therefore
    does not directly provide a complete workflow for constructing
    operational knowledge from an entire documentation collection.
    [ArticleConnector
    implementation](https://github.com/microsoft/Resource2Skill/blob/main/core/sources/article.py).

Adapting these interfaces to our setting would require additional
components for PDF parsing, HTML documentation discovery and collection,
knowledge-unit decomposition, cross-page content organization, and
procedural-content generation, before packaging the results as
CandidateSkill records. Resource2Skill’s subsequent candidate processing
and Skill Wiki construction remain reusable. However, the added
components would directly determine the content, granularity, and
coverage of the resulting library—properties central to the evaluation
of resource-to-skill construction.

Such an adaptation would therefore extend beyond input-format conversion
and introduce a knowledge-extraction method designed by us. Its
downstream performance would make the respective contributions of
Resource2Skill and the added extraction procedure difficult to
distinguish. Given these differences in knowledge objectives and the
adaptation requirements of the released implementation, we did not
include Resource2Skill as an original-pipeline baseline alongside
VisualSkill and SkillFoundry under the same evaluation setting.
````
