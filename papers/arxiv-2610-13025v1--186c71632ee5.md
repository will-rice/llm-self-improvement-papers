###### Abstract

Self-evolving agents are increasingly used to improve language model
systems without human intervention through either weight updates or
harness improvements. Existing approaches typically pursue these
directions separately: some methods update model weights using
self-generated experience, while others rewrite the harness that defines
how an agent uses prompts, tools, context, and execution feedback.
However, these approaches overlook the relationship between model
weights and the agent harness. To connect these processes and ensure
effective and smooth agent self-evolving, we propose Evo², a framework
for weight-harness co-evolution. For harness updates, we design a
unified dual-role pipeline that a single policy serves as both a
Proposer, which writes harness edits, and a Reflector, which diagnoses
their effects and guides revision. For weight updates, harness
modifications and their execution outcomes guide the training of both
the Proposer and the Reflector. We further develop EvoTIDE, a training
pipeline that recovers usable trajectories through edit extraction and
prefix continuation, then combines SFT with interleaved GRPO across the
two roles. Extensive experiments across three coding benchmarks
demonstrate that Evo² significantly outperforms existing self-evolution
methods. It achieves 82.1% on Polyglot and 48.3% on SWE-bench Verified,
compared with 62.6% and 41.0% for the strongest baseline, respectively.
We also show that the evolved harnesses transfer to different tasks
without further evolution and rank first in cross-benchmark evaluations.
Our dual-role harness improvement framework is also able to extend to
self-evolution with proprietary models, improving a GPT-5-mini agent’s
performance from 24.4% to 48.3%. In addition, Evo² generalizes to other
tasks smoothly. We extend self-evolution to memory tasks, achieving the
best performance on the LoCoMo and LongMemEval benchmarks. These results
demonstrate the applicability of the framework Evo² across domains and
its broad transferability across models and tasks.

## 1 Introduction

Self-evolving agents offer a way to improve language model systems
through their own experience and without human intervention. Existing
approaches typically follow two directions. The first updates _model
weights_: a model generates solutions, selects useful outputs using task
feedback, and trains on them to improve its ability to solve similar
problems ([Zelikman et al., 2022](#bib.bib10); [Singh et al.,
2024](#bib.bib11)). The second modifies the _agent harness_: a model
inspects and rewrites the program that defines how an agent uses
prompts, tools, context, and execution feedback ([Robeyns et al.,
2025](#bib.bib4); [Zhang et al., 2026](#bib.bib3)). By evaluating these
edits and retaining useful changes, an agent improves its task
performance through modifications to its own code. These approaches
accumulate experience in model parameters and executable programs,
respectively, but typically pursue the two forms of improvement
separately.

Treating these directions separately overlooks the relationship between
model weights and the agent harness. The model’s capabilities shape the
modifications it proposes and how it interprets execution feedback. In
turn, each evaluated modification reveals which changes are useful, why
an edit fails, and how different improvements interact. This experience
can guide the training of the model responsible for evolution. In
particular, proposing edits and diagnosing their effects are skills that
can themselves be learned from earlier evolution attempts, connecting
harness improvement to weight updates.

We introduce Evo², a framework for _weight-harness co-evolution_ in
self-evolving agents (Figure
[1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Evo2: Evolving the Evolver through Weight-Harness Co-Evolution")).
We train the model to become a better _evolver_: to propose useful
harness modifications, interpret their outcomes, and revise them
accordingly. A better evolver builds better harnesses, whose
modifications and execution outcomes provide further experience for
training the evolver. Harness evolution, therefore, supplies training
signals for weight updates, while the updated model guides subsequent
harness search.

Figure 1: Weight-harness co-evolution in Evo². A shared
Proposer–Reflector policy evolves the agent harness. Harness edits and

For harness updates, Evo² uses a unified dual-role pipeline in which a
single policy serves as both a _Proposer_ and a _Reflector_. The
Proposer writes harness edits, while the Reflector examines their
execution outcomes and provides feedback for further revision. Both
roles share parameters and learn from the effects of the modifications
they produce. We organize the search as a tree of harness variants and
introduce _crossover searching_ to combine useful strategies discovered
on different branches. The Reflector identifies a strategy that
addresses a weakness in the current harness, and the Proposer adapts it
to that harness, allowing each branch to build on discoveries made
elsewhere in the tree.

For weight updates, we develop EvoTIDE (Tree-guided Interleaved
Dual-role Evolution) for weight updates, to train the shared policy on
experience collected during harness evolution. We collect trajectories
from both the Proposer and the Reflector, using edit extraction and
prefix continuation to recover usable trajectories from incomplete or
partially invalid rollouts. These trajectories support an SFT warm
start, followed by interleaved GRPO across the two roles. A maintained
parent pool exposes the policy to harnesses at different depths and
performance levels, so it learns both to improve strong candidates and
to repair weaker ones. The updated policy then generates the proposals
and feedback used in subsequent evolution rounds.

Extensive experiments across three coding benchmarks demonstrate that
Evo² outperforms existing self-evolution methods. It achieves 82.1% on
Polyglot and 48.3% on SWE-bench Verified, compared with 62.6% and 41.0%
for the strongest respective baselines. The evolved harnesses also
transfer across benchmarks without further evolution. We further apply
the dual-role harness improvement framework to proprietary models with
fixed weights and extend self-evolution to memory tasks, achieving the
best performance on LoCoMo and LongMemEval. These experiments
demonstrate both the applicability of the framework across domains and
the transferability of its evolved harnesses.

Our contributions are:

- •
  Weight-harness co-evolution: We introduce Evo², which connects harness
  evolution with the training of a unified Proposer–Reflector policy
  through harness modifications and their execution outcomes.
- •
  Crossover searching: We combine reflection and directed editing to
  adapt useful strategies across branches of the harness tree.
- •
  A training pipeline for the evolver: We develop EvoTIDE, which
  combines trajectory recovery, SFT, and interleaved GRPO with a parent
  pool spanning different depths and performance levels.
- •
  A reusable framework and evolved harnesses: We demonstrate
  self-evolution on coding and memory tasks, harness transfer across
  benchmarks, and harness improvement with fixed proprietary models.

## 2 Related Work

##### Self-improving language models.

Self-improvement through training forms an iterative loop: a model
generates experience, learns from feedback, and uses its updated weights
to collect the next round of training data ([Gao et al.,
2025](#bib.bib22); [Fang et al., 2025](#bib.bib23)). STaR and ReST^(EM)
train on successful model outputs ([Zelikman et al., 2022](#bib.bib10);
[Singh et al., 2024](#bib.bib11)), while Absolute Zero and R-Zero
develop tasks and solvers through self-play ([Zhao et al.,
2026](#bib.bib12); [Huang et al., 2026](#bib.bib15)). Other methods
improve training signals through trajectory selection, semantic voting,
or learned evaluators ([Zhong et al., 2026](#bib.bib8); [Jiang et al.,
2026](#bib.bib20); [Wang et al., 2024](#bib.bib16)). EvolveR combines
reusable experience with policy reinforcement ([Wu et al.,
2025](#bib.bib17)). ReVeal, Agent0-VL, and Self-Distillation Zero train
generation together with verification or revision ([Jin et al.,
2026](#bib.bib13); [Liu et al., 2025](#bib.bib6); [He et al.,
2026](#bib.bib14)); EvoLM and CoNL co-train generation and feedback
mechanisms within shared policies ([Li et al., 2026](#bib.bib2); [Sui
and Hooi, 2026](#bib.bib19)). Evo² applies shared-role training to
harness modification: EvoTIDE uses supervised fine-tuning and
interleaved GRPO to train a unified Proposer–Reflector model on
evaluated edits and their outcomes.

##### Self-evolving agent harnesses.

Agents can also accumulate improvements in the harness that manages
their prompts, tools, and control flow. They propose modifications,
evaluate the resulting agent, and use the outcomes to guide further
changes. SICA edits its own implementation ([Robeyns et al.,
2025](#bib.bib4)), DGM maintains an archive for branching
self-modification ([Zhang et al., 2026](#bib.bib3)), and HGM selects
promising parents using estimated descendant performance ([Wang et al.,
2026](#bib.bib5)). Meta-Harness searches over code using prior
candidates and execution traces ([Lee et al., 2026](#bib.bib21)). GEPA
combines reflection with prompt evolution ([Agrawal et al.,
2026](#bib.bib9)), while GEA shares experience across evolving agents
([Weng et al., 2026](#bib.bib18)). The Red Queen Gödel Machine extends
evolution to changing evaluation utilities ([Iacob et al.,
2026](#bib.bib7)). Prior work also demonstrates harness transfer across
tasks and models ([Wang et al., 2026](#bib.bib5); [Lee et al.,
2026](#bib.bib21); [Weng et al., 2026](#bib.bib18)). Evo² makes harness
search a source of self-improvement for the evolver itself: crossover
searching lets the Reflector select a donor strategy and the Proposer
adapt it to a recipient harness, while the resulting experience trains
both roles to guide subsequent search. We evaluate the framework’s
applicability across coding and memory domains as well as the transfer
of its evolved harnesses across benchmarks and executors.

## 3 Method

### 3.1 Overview

Evo² integrates harness evolution with weight evolution (Figure
[2](#S3.F2 "Figure 2 ‣ 3.1 Overview ‣ 3 Method ‣ Evo2: Evolving the Evolver through Weight-Harness Co-Evolution")).
A harness, $`h`$, is the executable program that manages an agent’s
prompts, tools, context, and control flow. A language model policy,
$`\pi_{\theta}`$, serves as the evolver, acting as both Proposer and
Reflector through different role prompts. We train its parameters,
$`\theta`$, on the outcomes of harness modifications. The task executor,
denoted $`M_{\mathrm{exec}}`$, runs inside each candidate harness and
remains fixed during co-evolution, so candidate performance measures the
effect of changing the harness.

Harness evolution proceeds through iterative tree search. Each node
stores a harness and its task evaluation records; an edge records the
edits made to its parent. At each iteration, we sample a parent, use the
Proposer to modify it, and evaluate the resulting candidate. The
Reflector then examines the execution feedback and recommends a
revision, integration of a strategy from another branch, or retention of
the candidate. The Proposer implements any recommended change, which is
evaluated in turn. The resulting harnesses extend the tree, while the
role trajectories and task outcomes provide data for weight evolution.
EvoTIDE uses these data for supervised fine-tuning followed by
interleaved reinforcement learning. Updated weights are used in
subsequent rounds of search and data collection.

### 3.2 Harness evolution through dual-role self-modification

##### Proposer.

The Proposer operates in two modes. In _Type A_, it receives a parent
harness $`h_{p}`$ and its measured task performance, chooses a
modification, and produces edits $`e_{0}`$ to obtain an initial
candidate $`h_{0}`$. In _Type B_, it receives a harness and an explicit
edit directive $`d`$ from the Reflector. It implements that directive
against the current source through edits $`e_{1}`$, producing a revised
candidate $`h_{1}`$. Type A develops the ability to identify
improvements independently; Type B develops the ability to turn feedback
into working code. Both modes can generate a sequence of file edits.

##### Reflector.

The Reflector receives the candidate source, the edits relative to its
parent, the change in task performance, and execution traces from
relevant successes and failures. It identifies the strategy attempted by
the Proposer, diagnoses remaining problems, and chooses one of three
actions: revise provides a directive to improve the candidate; crossover
provides a directive to incorporate a strategy from another branch; and
keep retains the candidate without another edit. A revision directive
describes a concrete change and the execution evidence that motivates
it. Its quality is measured by the performance of the harness produced
when the Proposer follows it. This also allows the Reflector to learn
when an additional modification is unlikely to help.

Let $`z_{p}`$ contain the parent’s evaluation records and $`z_{0}`$
contain the candidate’s edit diff and execution feedback. With available
donor strategies $`\mathcal{S}`$, the shared policy implements the cycle

|     |                          |                                                                               |                         |                                                      |     |     |
| --- | ------------------------ | ----------------------------------------------------------------------------- | ----------------------- | ---------------------------------------------------- | --- | --- |
|     | $`\displaystyle e_{0}`$  | $`\displaystyle\sim\pi_{\theta}(\cdot\mid P_{A},h_{p},z_{p}),`$               | $`\displaystyle h_{0}`$ | $`\displaystyle=\operatorname{Apply}(h_{p},e_{0}),`$ |     | (1) |
|     | $`\displaystyle(m,d,j)`$ | $`\displaystyle\sim\pi_{\theta}(\cdot\mid R,h_{p},h_{0},z_{0},\mathcal{S}),`$ |                         |                                                      |     |     |
|     | $`\displaystyle e_{1}`$  | $`\displaystyle\sim\pi_{\theta}(\cdot\mid P_{B},h_{0},d),`$                   | $`\displaystyle h_{1}`$ | $`\displaystyle=\operatorname{Apply}(h_{0},e_{1}).`$ |     |     |

Here $`P_{A}`$, $`P_{B}`$, and $`R`$ specify role prompts; all calls use
the same model parameters $`\theta`$. We write the Reflector’s decision
compactly as its action $`m`$, directive $`d`$, and donor identifier
$`j`$, which is used only for crossover. The last line is executed for
revision or crossover; for keep, $`h_{1}=h_{0}`$ and no further edit is
sampled. During training, counterpart calls use the frozen snapshot
described in Section
[3.3.3](#S3.SS3.SSS3 "3.3.3 Training process ‣ 3.3 Weight evolution through EvoTIDE ‣ 3 Method ‣ Evo2: Evolving the Evolver through Weight-Harness Co-Evolution").

##### Crossover searching.

Different branches may discover complementary improvements. To make
these discoveries available to the Reflector, we maintain a library
$`\mathcal{S}=\{s_{j}\}`$ of strategies extracted from evaluated
harnesses. Each entry describes a mechanism and its observed effect,
together with whether it is already present in the current candidate.
Given this context, the Reflector can select a donor strategy that
addresses a problem revealed by the candidate’s execution. Its directive
$`d`$ specifies how to integrate the selected $`s_{j}`$ into $`h_{0}`$.
The Type B Proposer then adapts the mechanism to the candidate’s source
and combines it with the existing behavior. We evaluate the combined
harness to determine whether the integration helps. A crossover child
retains the recipient as its tree parent and records the donor strategy,
so it can receive further revision or crossover.

### 3.3 Weight evolution through EvoTIDE

EvoTIDE turns the trajectories generated during harness evolution into
training data for the shared policy. We first collect an initial dataset
and perform supervised fine-tuning (SFT). We then continue collecting
experience from the evolving tree while training both roles with group
relative policy optimization (GRPO) ([Shao et al., 2024](#bib.bib1)).

#### 3.3.1 Data collection

For each evolution attempt, we record the role prompts, model responses,
applied edits, parent and child harnesses, and task evaluation results.
One propose-evaluate-reflect-revise cycle provides an autonomous
Proposer trajectory, a Reflector trajectory, and, when a revision is
requested, a directed Proposer trajectory. The same evaluated harness
can also serve as a parent in a later round or contribute a strategy to
the crossover library.

##### Recovering Proposer trajectories.

An otherwise useful rollout may fail to produce an executable edit
because of how the response is expressed. We use two recovery procedures
during data collection. _Edit extraction_ handles rollouts that end
without an explicit edit action: we search the recorded reasoning and
chat messages for concrete file edits and convert them into the required
action format. _Prefix continuation_ handles a sequence of edits in
which a later edit is invalid, for example because of a malformed tool
call or an incorrect edit format. We truncate the rollout after the last
successfully applied edit, restore the corresponding intermediate
harness, and resume generation from that prefix. This preserves the
valid earlier edits while allowing the model to regenerate the failed
suffix. Recovered proposals pass the same application, startup, and task
evaluation checks as other candidates before entering the training data.

##### Collecting Reflector trajectories.

Evaluated proposals become reflection cases, including edits that
improve performance, leave it unchanged, or cause regressions. For each
case, we generate feedback and evaluate the candidate obtained by
implementing it; a keep response retains the initial candidate. These
outcomes provide supervision for the Reflector’s diagnosis and choice of
action. Connecting strategies from other branches adds crossover cases,
so the dataset includes both local revisions and the integration of
previously discovered mechanisms.

#### 3.3.2 Reward design

Both roles are rewarded by the change in task performance caused by
their decisions. Let $`\widehat{V}(h)\in[0,1]`$ be the mean externally
evaluated task score of harness $`h`$; for tasks with a binary
correctness signal, this is its success rate. For a valid Proposer edit
from $`h`$ to $`h^{\prime}`$, and a valid Reflector intervention from
$`h_{0}`$ to $`h_{1}`$, the execution rewards are

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
r_{P}^{\mathrm{exec}}=\widehat{V}(h^{\prime})-\widehat{V}(h),\qquad r_{R}^{\mathrm{exec}}=\widehat{V}(h_{1})-\widehat{V}(h_{0}).
``` |  | (2) |

For Type A, the Proposer is compared with its sampled parent; for Type
B, it is compared with the candidate it was instructed to revise. A keep
action has $`h_{1}=h_{0}`$ and receives zero execution reward. We
evaluate each comparison on the same tasks under matched execution
conditions, averaging repeated runs when available.

Malformed outputs and edits that cannot be applied or started receive a
negative reward. No-op edits, unusable harnesses, and invalid crossover
directives are also penalized. Type B receives a small additional bonus
or penalty according to whether the edit touches a file named in the
directive. For Reflector interventions, positive gains are credited only
when the traces contain evidence that the added mechanism ran; otherwise
the gain is set to zero.

#### 3.3.3 Training process

##### Supervised fine-tuning.

We initialize the shared policy with a mixture of successful autonomous
edits, directed edits, and Reflector responses selected using their
downstream evaluation results. The model is trained to predict the
recorded response from its role prompt and harness context. We balance
the training mixture across roles and modes to establish both the
editing and reflection behavior needed for online training.

##### Tree maintenance and parent sampling.

During online training, evaluated candidates extend the harness tree and
refresh a bounded parent pool. We retain nodes at multiple depths so the
model encounters both early modifications and harnesses with several
accumulated changes. Within each depth, we reserve part of the pool for
the strongest candidates and sample the remainder from other executable
candidates. This retains weaker harnesses that need repair as well as
strong harnesses that can be improved further. Let $`\mathcal{P}_{r}`$
be the retained pool at round $`r`$, and let
$`\mathcal{N}_{r}=\mathcal{P}_{r}\setminus\{h_{\mathrm{root}}\}`$
contain its non-root harnesses. The root has a permanent place and an
allocated sampling share $`\rho\in(0,1)`$. With weights
$`w(h)=\epsilon_{p}+|\widehat{V}(h)-\tfrac{1}{2}|`$, where
$`\epsilon_{p}>0`$, parent samples follow

|  |  |  |  |
|----|----|----|----|
|  |
``` math
p_{r}(h)=\begin{cases}\rho,&h=h_{\mathrm{root}},\\[2.0pt]
(1-\rho)\dfrac{w(h)}{\sum_{u\in\mathcal{N}_{r}}w(u)},&h\in\mathcal{N}_{r}.\end{cases}
``` |  | (3) |

If $`\mathcal{N}_{r}`$ is empty, we sample only the root. This
distribution gives both high and low-scoring parents more exposure while
keeping every retained parent available. Updating the pool across rounds
lets the training distribution develop with the harnesses produced by
the model.

##### Interleaved role training.

We optimize a single policy for both roles. At the beginning of training
round $`r`$, we set $`\bar{\theta}_{r}=\theta_{r}`$ and freeze
$`\pi_{\bar{\theta}_{r}}`$ to provide the counterpart behavior needed to
evaluate training samples. For Proposer training, this copy provides
Reflector directives for Type B prompts. For Reflector training, it acts
as the Proposer that implements sampled directives. Each optimization
step uses a Proposer group and a Reflector group, with advantages
computed separately for each prompt. Both role updates change the live
parameters $`\theta`$, while $`\bar{\theta}_{r}`$ stays fixed. After the
round yields $`\theta_{r+1}`$, we refresh the snapshot by setting
$`\bar{\theta}_{r+1}=\theta_{r+1}`$ and collect new cases. An improved
Proposer therefore generates new modifications for the Reflector to
learn from, while an improved Reflector generates new directives for the
Proposer. Both skills improve through successive rounds of this
interaction.

##### Balancing modes within each role.

We interleave Type A and Type B Proposer prompts so that training covers
both autonomous improvement and implementation of feedback. For the
Reflector, we sample half of the inputs with an empty strategy set and
half with crossover strategies. We also construct paired SFT prompts:
when a target response is valid in either context, the same response is
used with and without the strategy set. This teaches the model to retain
a useful diagnosis even when donor information is unavailable. Targets
that depend on a specific crossover donor are used only with the
corresponding strategy context. The mixture includes revision,
crossover, and retention decisions, and is refreshed as new trajectories
become available.

##### Policy optimization.

For a role prompt $`q`$, we sample a group of $`G`$ responses
$`y_{1},\ldots,y_{G}`$ from the current policy and compute rewards
$`r_{1},\ldots,r_{G}`$. We use the group mean baseline
$`A_{i}=r_{i}-\frac{1}{G}\sum_{j=1}^{G}r_{j}`$ and normalize the token
losses by a fixed maximum response length $`L_{\max}`$. We average the
losses from the two role groups and take one update per sampled batch.
Truncated responses are masked from the loss. All responses within a
group share the same role and input, so their advantages compare
alternative edits or reflections for the same harness context.

The trained evolver can run the same search procedure on a new initial
harness given an evaluator for its tasks. An evolved harness can also be
deployed directly on new tasks with compatible model and tool
interfaces. These two forms correspond to the outputs of co-evolution:
weights that encode how to improve a harness, and harnesses that
incorporate the improvements found during search.

## 4 Experiments

### 4.1 Experimental Settings

Models. Our main experiments use Qwen3.8-27B, served in FP8 with greedy
decoding, as the fixed task executor. We use the same model as the
evolver: the untrained base model for the baselines and the model
fine-tuned by EvoTIDE for Evo², where a single policy serves as both
Proposer and Reflector. For memory tasks, we additionally use a
Qwen3-Embedding-0.6B retriever. In the proprietary-model experiments,
GPT-5-mini and Claude Haiku 4.5 each serve as both executor and evolver,
with their weights fixed throughout evolution.

Benchmarks and metrics. We evaluate coding harness evolution on
Polyglot, SWE-bench Verified (SWE), and LiveCodeBench (LCB). We report
held-out pass@1 on Polyglot tasks over three evaluation runs, the
resolved rate on SWE-bench Verified instances, and pass@1 on LCB
problems. Proprietary models are evaluated on a 60-task SWE-bench
Verified subset. For memory tasks, we evolve harnesses on LoCoMo and
report mean F1 on three held-out conversations. We also evaluate the
same harnesses on LongMemEval-S using accuracy over 500 instances, with
GPT judging and three evaluation runs.

Baselines. We compare against four representative self-evolving agent
frameworks: SICA ([Robeyns et al., 2025](#bib.bib4)), which edits its
own implementation along a single lineage; DGM ([Zhang et al.,
2026](#bib.bib3)), which maintains an open-ended archive and branches
self-modifications from stored agents; HGM ([Wang et al.,
2026](#bib.bib5)), which selects parents based on the estimated
performance of their descendants; and GEA ([Weng et al.,
2026](#bib.bib18)), which enables concurrently evolving agents to share
experience. All baselines use the untrained model as the evolver and
follow their own selection rules.

### 4.3 Harness Transfer across Benchmarks

For each method and source benchmark, we take the harness reported in
Table

## 5 Conclusion

We presented Evo², a framework for weight-harness co-evolution in
self-evolving agents. A single policy serves as both Proposer and
Reflector, learning from harness modifications and their execution
outcomes to improve its ability to propose edits and guide revision.
Crossover searching combines useful strategies across branches, while
EvoTIDE trains the shared policy through trajectory recovery, SFT, and
interleaved GRPO. Experiments on coding and memory tasks demonstrate
improved task performance and transfer of evolved harnesses across
benchmarks. The dual-role search also supports harness improvement with
fixed proprietary models. Our analyses show that weight evolution
improves search reliability and that crossover searching reduces the
evaluation budget needed to reach strong performance. Evolving the
evolver allows experience to accumulate in both the executable harness
and the policy that guides future evolution.
````
