###### Abstract

Many real-world tasks (e.g., office workflows, scientific
experimentation) require LLM agents to interact repeatedly with their
environments for context-dependent operations. However, such
environments are often not agent-ready. First, information is often
scattered and fragmented across the environment. Second, relevant
evidence in the environment is often mixed with misleading information
and conflicting versions. Third, environments evolve over time,
introducing new noise and more challenging tasks. These challenges can
substantially degrade performance for state-of-the-art AI agents (e.g.,
from 83.9% to 57.6%). To address these challenges, we propose
Env-Rethink (a system with 27B post-trained model) that supports three
main capabilities: (1) It adaptively builds Collection Maps (for
organizing related files) and Event Logs (for contextualizing cross-data
relationships) to supplement necessary context; (2) It further leverages
the post-trained model (through offline trajectory learning) to identify
underlying noise issues in the environment; (3) It ultimately evolves
environments through virtual event histories that alter environmental
states and evidence relationships, producing more tricky ones for
further agent improvement. Experiments show that Env-Rethink can
effectively improve downstream task performance (with over 15.1% rubric
pass rate improvement across nine models on 30 tasks).

## 1  Introduction

Real-world tasks require AI agents to work with source code, data,
configurations, documents, and records of earlier actions. These
materials and their current state form the environment in which the
agent operates. Recent models such as Kimi K3 support extended coding
sessions and multi-step tool use, while advances in agent harnesses
enable increasingly complex autonomous workflows \[[1](#bib.bib14),
[2](#bib.bib16)\]. However, stronger task-solving capabilities do not by
themselves resolve which materials in a persistent environment should be
used: files accumulate, versions conflict, and later corrections can
change the meaning of earlier records.

Current tools improve file access, context management, and continuity
across agent sessions \[[3](#bib.bib9), [4](#bib.bib15),
[5](#bib.bib8)\]. However, access to relevant-looking content is only
part of the problem. An agent also needs to establish whether a file is
the intended source, whether it remains valid, and whether other records
actually corroborate it. These judgments depend on connections across
files that may be absent from the retrieved text or left implicit in the
environment.

Figure [1](#S0.F1 "Figure 1 ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
shows three concrete failures. When asked to summarize a paper, an agent
selects a PDF with the same title as the requested source and copies
altered statistics. When compiling references, it uses a file named
final.bib despite a later withdrawal notice embedded as images in
another document. When preparing an employee profile, it treats several
records repeating one original source as independent confirmation. The
agent can read the files and produce the requested artifact, yet
unresolved relationships among the files lead it to use the wrong
evidence. These cases raise three research challenges.

$`\bullet`$ First, recovering context across files. In the
reference-list example, a filename alone cannot indicate whether the
list remains usable; that decision requires connecting the list to the
later withdrawal. The challenge is to expose such relationships while
retaining the evidence needed to check them, so that agents can locate
relevant materials and interpret them in context.

$`\bullet`$ Second, learning reliable environment judgments. Grouping
files or summarizing them separately does not establish which source
should be trusted. An agent must gather evidence, reconcile conflicting
records, and determine which version applies. These decisions recur
across tasks, but manually specifying them for every environment is
impractical. The challenge is to learn a preparation model that makes
these judgments and prepares useful evidence for different downstream
agents.

$`\bullet`$ Third, creating harder but verifiable environments. A fixed
environment offers limited opportunities to test new judgments.
Returning to the reference-list example, introducing a further revision
or withdrawal could create a harder instance of the same request.
However, the correct reference list would then need to change as well.
Environment evolution must therefore coordinate state changes with
updated reference outcomes and evaluation checks while preserving
sufficient evidence to solve the task. Such instances can test
environment preparation under new conditions and provide material for
subsequent learning.

Our Methodology. To address these challenges, we present Env-Rethink, a
system for preparing and evolving agent environments through three
complementary capabilities. First, we organize existing files with a
_Collection Map_ and an _Event Log_. The map refines directory-based
groups into semantically related collections, while the log reconstructs
synthetic workflows whose revision and provenance relationships are
reviewed against source evidence. Both accompany the original files
during task execution. Second, we learn an environment-preparation model
from qualified tool-using teacher trajectories. Offline fine-tuning
teaches the preparation model to read files and verify their authority
and version relationships; at deployment, it selects files and produces
an evidence report without the downstream request. A separate task agent
uses this prepared environment to execute the request. Finally, we
evolve environments through event-driven state changes that introduce
plausible incorrect choices together with evidence that resolves them.
The evolver jointly generates file changes, updated reference outcomes,
and evaluation checks under an unchanged request. The resulting
instances undergo structural and answer validation, followed by paired
seed–variant runs to assess difficulty. Together, these capabilities
support two workflows: preparing an existing environment for task
execution and generating new environmental states for challenge
evaluation.

## 2  Preliminaries and Motivating Analysis

### 2.1  Model, Harness, and Environment

We distinguish three components of an agent system: the task model, the
harness, and the environment. The task model $`M_{\theta}`$ reasons over
its input context and generates responses or tool-call requests. The
harness $`H`$ manages instructions and context, dispatches tool calls,
returns observations, and controls retries and the execution budget. The
environment comprises the persistent resources and state that the agent
accesses and manipulates through the harness. We represent it as
$`E=(F,S)`$, where $`F`$ comprises the underlying files and service
implementations and $`S`$ denotes their current state.

The task model and harness form the downstream task agent $`A`$, whose
output for a request $`q`$ in environment $`E`$ is denoted by
$`\hat{y}=A(q,E)`$. Environment-side interventions modify the materials
in the environment, their organization, evidence-linked context, or
state, and are distinct from parameter updates to the downstream task
model. An environment-preparation procedure operates upstream of task
execution and may use a trained model to prepare the environment
supplied to the task agent.

### 2.2  Environment Preparation and Evolution

Environment interventions serve two complementary purposes: preparing an
existing task instance for execution and generating new, verifiable
instances under the same task request. We call these operations
_environment preparation_ and _environment evolution_.
Figure [2](#S2.F2 "Figure 2 ‣ 2.2 Environment Preparation and Evolution ‣ 2 Preliminaries and Motivating Analysis ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
summarizes the environment properties they support: organized context
for reliable task execution and changing states that supply new
challenges for subsequent model learning.

![Refer to caption](2609.29773v1/agent-native-env.png)

Figure 2: Two complementary roles of an agent-native environment.
Preparation organizes existing evidence for task execution; evolution
changes environmental states together with their reference outcomes and
evaluators. Both preserve the task request.

_Environment preparation_ makes an existing task instance ready for
execution by improving how an agent accesses, interprets, and uses
evidence. Given an environment $`E`$ and optional preparation-time
information $`c`$, a preparation operator $`C_{\phi}`$ produces a
prepared environment $`\widetilde{E}=C_{\phi}(E;c)`$. Here, $`c`$
denotes auxiliary information available during preparation, such as file
metadata or task-related supervision. The prepared environment supports
three properties: _navigable content_, which makes relevant materials
easy to locate; _explicit relationships_, which expose how records
support, revise, or depend on one another; and _source validity_, which
makes evidence for source authority and version applicability available
for inspection. These properties can be supplied through selected or
organized files and evidence-linked context. Preparation preserves the
task request and the correctness objective of the current instance while
changing how its evidence is exposed and interpreted.

_Environment evolution_ changes the environmental state while retaining
the task request $`q`$ to generate new, verifiable task instances. It
supports _evolving states_, in which files, records, or applicable
conditions change; _new evidence_, which introduces additional records
and relationships to reason over; and _task alignment_, which preserves
the request while updating reference outcomes and evaluation checks to
match the changed state. At generation step $`t`$, let $`y_{t}`$ denote
the reference outcome and $`V_{t}`$ denote the evaluator. We abstract
evolution as
$`(E_{t},y_{t},V_{t})\rightarrow(E_{t+1},y_{t+1},V_{t+1})`$, where
changes to the environment are accompanied by consistent updates to the
reference outcome and evaluation checks, preserving the task objective
and scoring criteria.

The task agent receives the resulting environment and the unchanged
request; reference outcomes and evaluation assets remain with the
generation and validation process. The generated instances can serve as
training data for subsequent model improvement, linking environmental
variation to new learning opportunities.

### 2.3  Limitations of Existing AI Agents

We conduct a motivating experiment on 30 difficult tasks adapted from
Workspace-Bench \[[6](#bib.bib6)\]. For each of nine model–harness
configurations, we compare a _Clean_ environment containing
ground-truth-selected files with a _Noise_ environment containing all
files, while holding the model, harness, and reasoning effort fixed. For
each configuration and condition, pass rate is the number of passed
checks divided by the 1,280 rubric checks across the 30 tasks.
Figure [1](#S0.F1 "Figure 1 ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")(c)
shows lower performance in _Noise_ for all nine configurations.
Averaging their pass rates, the mean falls from 83.9% in Clean to 57.6%
in Noise, a decrease of 26.3 percentage points.

Examining failures in these noisy environments reveals three recurring
behaviors of current agents. (i) *Insufficient search and incomplete
reading.* Agents may stop after an initial search, leave files unopened,
or read documents only partially, missing corrections, constraints, and
supporting evidence. (ii) *Trusting filenames as version indicators.*
Agents may assume that a file containing final in its name is the
required version without checking its validity or applicability. In the
final.bib example in
Figure [1](#S0.F1 "Figure 1 ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")(b),
the agent adopts a reference list despite a later withdrawal notice in
another document. (iii) *Reusing similar files without checking
requirements.* Agents may copy or superficially revise files that
resemble the task goal without verifying the requested scope,
constraints, or outputs, carrying incompatible assumptions and details
into the deliverable.

These behaviors lead to incomplete evidence, incorrect version choices,
and outputs that miss the user’s intent. They motivate environment
preparation that makes related files and their relationships easier to
inspect and provides evidence for judging source validity. Environment
evolution creates further challenges by changing these relationships
under the same request, with corresponding reference outcomes and
evaluation checks.

## 3  System Overview

Env-Rethink is a unified system for preparing and evolving task
environments. It supports two types of requests: (1) task execution,
which provides an existing environment to prepare, and (2) challenge
generation, which specifies a task, seed files, and a generation
direction. The system comprises three complementary modules:
_Environment organization_ recovers collection structure and synthesizes
context linked to source evidence. _Learned preparation_ verifies
candidate files and prepares an environment comprising selected files
and an accompanying preprocessing report. _Environment evolution_
generates more challenging environment states, together with updated
reference outcomes and validation checks.

We illustrate these modules using a composite budget scenario, with all
amounts expressed in thousands of dollars. The channel allocations in
plan_v1.xlsx sum to 35 and are supported by an approval record. A
competing file, plan_FINAL.xlsx, reports a total of 40 despite
containing the same allocations; a notice and its forwarded message both
instruct the reader to use this file. Collection Map separates plan
versions from approval records and messages, while Event Log introduces
source-linked synthetic operations that make their relationships
explicit. The learned verifier cross-checks the numerical values and
approval evidence, selects the supported files, and documents its
judgments in the preprocessing report. A separate downstream task agent
then uses the prepared environment to report the supported total of 35.

For challenge generation, an amendment revises the approved budget to 50. The evolved environment retains the historical version and the
incorrect final copy, and also includes a newer, unapproved draft
totaling 55. The task remains unchanged, but determining the valid
answer now requires resolving version and approval relationships across
a richer evidence history.

### 3.1  Modules and Interfaces

The organization module
(Section [4](#S4 "4 Evidence-Linked Environment Organization ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement"))
constructs Collection Map and Event Log from materials in the
environment. Its EGS and TGS modes differ in the supervision available
during preparation. The Env-Rethink model
(Section [5](#S5 "5 Learning to Prepare Agent-Ready Environments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement"))
reads file collections, selects evidence, and supplies a preprocessing
report for a separate task agent. These are evaluated as distinct
environment-preparation conditions in
Section [7](#S7 "7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement").

The evolution module
(Section [6](#S6 "6 Event-Driven Environment Evolution ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement"))
receives a seed or previous variant, the task request, generation
records, evaluation assets, and available failure feedback. It produces
changed environmental states with corresponding reference outcomes and
checks. Its event history is a generation record, whereas Event Log in
the organization module supplies context to the task agent.

### 3.2  Offline Learning and Task Execution

Offline learning builds structured sub-environments, collects tool-using
teacher trajectories, qualifies and prepares those trajectories, and
fine-tunes the upstream verifier. During deployment, the verifier reads
files in the environment and prepares selected files and an evidence
report. The downstream agent receives the prepared environment and the
original task request. The organization module instead exposes
Collection Map, Event Log, and source files through the environment’s
file-access interface.

### 3.3  Environment Evolution Workflow

The Environment Evolver extends generation histories and materializes
state changes. The pipeline assembles runnable environments, validates
their generation records, executes reference solutions, and compares
seed and variant difficulty across task agents. The workflow also
accepts failure trajectories to guide subsequent changes to state and
evidence dependencies. The Terminal-Bench 2.1 study evaluates seed and
evolved environments across 59 seeds. Accepted instances provide
executable challenges and reference outcomes for subsequent learning;
Appendix [C.1](#A3.SS1 "C.1 Evaluation Settings ‣ Appendix C Event-Driven Generation Protocol ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
specifies the evaluation protocol.

## 4  Evidence-Linked Environment Organization

In a file-based environment, an agent must use documents and records to
produce the deliverable specified by a user. The environment can contain
several versions of a document, corrections recorded in separate files,
and records that repeat information from the same source. Retrieving a
document that matches the request is insufficient if a later revision or
withdrawal changes its validity; the agent must also check the document
against related records.

Directory structure and per-file summaries help locate documents, but do
not necessarily expose these cross-file relationships. Related records
may lie in different directories, and a summary of one file does not say
how it relates to another. Two kinds of information are missing. The
first is which files should be read together, such as a document and its
correction. The second is how those files relate: whether one record
revises another, copies it, or was used to produce it. The second kind
requires inferring relationships from the files available in a static
snapshot.

We supply these two kinds of information through _Collection Map_ and
_Event Log_, both synthesized before task execution without modifying
the source files. Collection Map groups files into collections and
refines the grouping beyond the directory layout. Event Log describes
file use and revision as ordered operations in synthetic workflows
linked to source evidence. Each history is reviewed against the cited
files before inclusion. Both representations can be synthesized from the
environment alone or with task supervision that simulates a
well-organized environment
(Section [4.3](#S4.SS3 "4.3 Preparation Inputs ‣ 4 Evidence-Linked Environment Organization ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
Figure [3](#S4.F3 "Figure 3 ‣ 4 Evidence-Linked Environment Organization ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
shows their synthesis and use.

![Refer to caption](2609.29773v1/stage1-task-ready.png)

Figure 3: Environment organization and task execution. Collection Map is
built by grouping, summarizing, and refining file references. Event Log

### 4.1  Collection Map

Each collection in the map has a card that summarizes its theme,
contents, and representative evidence, with source paths for accessing
the files. Map synthesis begins with deterministic grouping by directory
structure and file-count limits, after which a _Collection Summarizer_
reads each group and writes its card. The cards provide an overview of
the environment’s file collections on which regrouping operates.

Directory-based groups may mix unrelated themes or separate files that
need to be read together. A _Semantic Coordinator_ inspects the cards
and member paths and proposes splits, merges, transfers of file
references, or membership in multiple collections. A deterministic
procedure validates and applies these changes while preserving complete
file coverage, so every file remains in at least one collection and
collections may overlap. A _Collection Refiner_ rereads the affected
groups and updates their cards, which the coordinator uses in the next
round. Regrouping changes only the map.

### 4.2  Event Log

A _History Synthesizer_ reads the files in the environment and proposes
a candidate history composed of sessions such as source review, document
revision, or discussion of a deliverable. Sessions consist of reading,
writing, copying, and exporting events, each recording an actor, action,
time, file path, and provenance. Workflows and timestamps are marked as
synthetic; source-file evidence determines revision relationships and
version validity.

Quoted evidence and the synthesizer’s own inference are kept apart.
Source excerpts must match the cited locations. Review notes written by
the synthesizer are identified as generator inference and appear as
temporary documents that are created, used, and deleted within the
proposed history.

Before a candidate history enters the log, deterministic checks validate
its event structure and file references. An independent _Evidence
Reviewer_ then reads the source files and checks whether quoted excerpts
match the cited files, whether each judgment in the history is supported
by file evidence, whether each recorded action (reading, writing,
copying, or exporting) agrees with the files it cites, and whether the
history is consistent with the files currently present in the
environment. The synthesizer repairs candidates using this feedback; a
candidate that exhausts the repair budget is discarded.

In subsequent synthesis rounds, a subset of previously used files is
hidden from the synthesizer so that new histories cover other materials.
A _Timeline Integrator_ combines the accepted histories into a single
log, reconciling identifiers and timestamps while retaining their event
contents, evidence, and causal order. The task agent can then retrieve
the sessions linked to a file.

### 4.3  Preparation Inputs

Both preparation procedures support two settings with the same output
types and downstream interface. _Environment-Grounded Synthesis (EGS)_
uses files and metadata in the environment: regrouping relies on
collection summaries and member paths, and Event Log synthesis uses the
source files.

_Task-Guided Synthesis (TGS)_ additionally supplies the preparation
process with supervision from the evaluated task. Annotated file labels
distinguish clean files, the ground-truth-selected materials for the
task, from noise files
(Section [2.3](#S2.SS3 "2.3 Limitations of Existing AI Agents ‣ 2 Preliminaries and Motivating Analysis ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
During Collection Map refinement, clean files are brought together into
one collection as far as possible, and noise files are excluded from
that collection. The task request and evaluation rubric guide Event Log
synthesis, but the instructions prohibit copying or restating rubric
entries in the public log.

We compare EGS and TGS to assess downstream task performance under
environment-only and task-guided preparation; results appear in
Section [7.2](#S7.SS2 "7.2 Environment Organization ‣ 7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement").

### 4.4  Task Execution

The completed map and log accompany the original files. The downstream
task agent, the _Task Executor_, uses collection cards to locate
materials, retrieves log sessions by file path, and follows source
references to the underlying evidence. In both EGS and TGS, tool-use
hooks also surface this context during execution. The Task Executor then
uses its native tools to produce the deliverable for the original
request.

## 5  Learning to Prepare Agent-Ready Environments

TGS outperforms EGS in matched comparisons
(Section [7.2](#S7.SS2 "7.2 Environment Organization ‣ 7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")),
motivating a learned preparation model that makes file judgments from
the files alone. We train it on supervised examples. The model reads
file collections and supplies a separate task agent with selected files
and an evidence report.

The central judgment is whether a file’s claims hold up against other
records. A file can claim to be final while another record supersedes
it, or claim authority that its supporting records do not establish.
Grouping and summarizing files alone do not settle such cases; the
preparation model must read the records that support or contradict each
claim. Learning this behavior places requirements on the target and the
data. The target must describe each file’s status relative to other
records without reference to a downstream request. Training examples
must contain the evidence needed for each judgment, but independently
sampled files may omit a necessary predecessor or correction. Final
labels, moreover, specify the judgment but not how the evidence for it
was obtained.

The core of the preparation model is a file verifier. We meet these
requirements with a file-verification target, training sub-environments
built from groups of related records, and teacher trajectories that
supervise file-reading actions together with the final judgments. At
deployment, the verifier’s judgments determine file selection and are
summarized in an evidence report for the downstream agent.
Figure [4](#S5.F4 "Figure 4 ‣ 5.4 Environment Preparation and Deployment ‣ 5 Learning to Prepare Agent-Ready Environments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
shows the procedure.

### 5.1  Verification Task

The verifier receives a file collection, a manifest, file-reading tools,
and an instruction that specifies the output format and requires
individual files to be read. Verification concerns relationships within
the supplied collection; the input does not include the downstream user
request.

The output separates a file’s own claims from its status relative to
other records. For each file, the verifier returns a standard/noise
partition, a category, an observed stage, a family assignment, timeline
information, and supporting evidence. The categories are _authoritative
record_, _false final version_, _fabricated authority_, _misleading
redirection_, _superseded version_, and _out-of-scope file_;
Appendix [A.1](#A1.SS1 "A.1 Label Definitions ‣ Appendix A Data ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
defines them. Observed stage records the status expressed by a file,
whereas category and family judgments interpret that status against
other records in the collection. A claim to be the final version is thus
checked against predecessors, supporting messages, and the authority
chain.

These labels encode authority and provenance within the collection; the
downstream agent determines their relevance to the user request.

### 5.2  Data and Teacher Trajectories

Training sub-environments are constructed from groups of related
records. Attack scenes contain authoritative targets and their decoy
chains; version families retain related records and their order;
redirect groups include pointers and supporting messages. Fillers
provide surrounding file density. Each group keeps the evidence
relationships needed to interpret its annotations.

Teachers from the DeepSeek, GLM, and Gemini families act through Claude
Code in isolated sandboxes. Each teacher receives a sub-environment, the
verification task of
Section [5.1](#S5.SS1 "5.1 Verification Task ‣ 5 Learning to Prepare Agent-Ready Environments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement"),
and a hint whose level is recorded in the generation specification. It
is instructed to read all files and return file classifications. The
resulting trajectory records assistant messages, tool calls, file
observations, and the structured output.

A trajectory is admitted to training only after qualification.
Read-fidelity checks link its file judgments to recorded file access and
observations. Partition judgments, false rejection of authoritative
records, classification of strong decoys, and version order are then
checked against the annotations. When classification errors occur, a
separate agent uses the teacher’s failed trajectory and the ground-truth
annotations to revise the hint. The teacher then repeats the
verification task with the revised hint, with at most two additional
retries. Annotation access is restricted to the revision agent.
Sub-environments whose trajectories still fail are excluded from
training.
Appendix [A.7](#A1.SS7 "A.7 Qualification and Outputs ‣ Appendix A Data ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
gives the thresholds.

The source annotation pool contains 1,597 files from 16 tasks. Fifteen
parent tasks supply the original 209 sub-environments; the collection
and qualification procedure yields 2,116 accepted teacher trajectories
covering 139 of them. Training additionally uses 288 consensus-attack
trajectories.
Appendix [A](#A1 "Appendix A Data ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
describes source selection, annotation, and composition.

Teacher hints can add category features or a checking sequence to the
verification task
(Appendix [A.6](#A1.SS6 "A.6 Teacher Reading ‣ Appendix A Data ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
Student training prompts contain only the verification instruction,
output schema, and reading requirements, without discriminative guidance
about categories and recognition cues. Tool calls are converted to
Qwen-native serialization, and overlong traces are compressed by the
teacher to fit the training context.

````math
## 6  Event-Driven Environment Evolution

Environment evolution changes a seed environment to create harder
instances of the same user request. A seed task consists of an
environment, a user request, a reference solution, and evaluation
checks. A change in the effective date of a record, for example, can
alter which information applies to the same reporting task. The changed
answer must then be determinable from the generated files, and the
reference solution and checks must be updated to match.

Generation is organized around counter-default decision points, which
pair a plausible incorrect choice with evidence that corrects it
(Section [6.1](#S6.SS1 "6.1 Decision Points and Reference Outcomes ‣ 6 Event-Driven Environment Evolution ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
An *Environment Evolver* realizes these points by producing the file
changes, the updated reference outcome, and the evaluator revisions
together, and records file operations as events so that later
generations can build on earlier changes
(Section [6.2](#S6.SS2 "6.2 Event-Driven Environment Generation ‣ 6 Event-Driven Environment Evolution ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
Generated instances are then validated, and their difficulty is measured
separately through matched seed–variant runs.
Figure [5](#S6.F5 "Figure 5 ‣ 6.2 Event-Driven Environment Generation ‣ 6 Event-Driven Environment Evolution ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
shows the procedure.

### 6.1  Decision Points and Reference Outcomes

A *counter-default decision point* specifies an incorrect value or
action in an apparently credible source, another source that uniquely
resolves the conflict, and a check that rejects the incorrect choice.
Accepting the incorrect choice without resolving the evidence leads to a
wrong answer, while the resolving source keeps the decision answerable.
The generation instructions require at least three such points per
variant and evidence chains no shorter than those in the seed.

We use four types of decision point. The *temporal* type concerns
whether a published update has taken effect by the reporting date. For
*exclusion*, a record must be omitted if it was withdrawn, unregistered,
or lacks a required underlying event. An *exception-rule* point concerns
cases that appear similar but are subject to different rules. The
*numerical* type requires recalculating a value from source inputs
despite the presence of a plausible precomputed result.

### 6.2  Event-Driven Environment Generation

The Evolver reads the current task artifacts, generation records, and
available failure examples. It outputs new files, patches to existing
files, an event-history fragment, and revisions to the reference
solution and expected values. The history records file creation,
modification, renaming, and deletion, and references to earlier events
preserve dependencies when a new variant builds on a previous one.

A deterministic merger joins the history fragments and checks event
identifiers, session boundaries, and sequence continuity while
preserving causal links. Assembly then applies the new files and patches
to the previous environment, so each generation starts from the changes
made in earlier variants. Only the assembled files and the unchanged
request are supplied to the task agent. Unlike Event Log in
Section [4](#S4 "4 Evidence-Linked Environment Organization ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement"),
this history serves generation and is not supplied as execution context.

For generation $`t`$, let $`E_{t}`$ be the current environment,
$`V_{t}`$ its evaluator, $`H_{t}`$ the accumulated history, and
$`D_{t}`$ the available failure feedback. With request $`q`$ fixed, the
proposed update is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
(E_{t+1},y_{t+1},V_{t+1},\Delta H_{t+1})=G_{\phi}(E_{t},q,V_{t},H_{t},D_{t};z_{t}),
``` |  | (2) |

where $`z_{t}`$ selects the evolution direction, $`y_{t+1}`$ is the
updated reference outcome, and $`\Delta H_{t+1}`$ records new events.
Expected values and additional checks follow the changed state. Each
update is required to preserve the task objective and existing scoring
criteria.

Figure 5: Environment evolution under a fixed request. Generation events

Appendix [C](#A3 "Appendix C Event-Driven Generation Protocol ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
describes the implementation scope of the checks.

### 6.3  Instance Validation

Instance validation comprises structural checks and answer validation.
Host-side structural checks examine events, file references, assembly,
material placement, and evaluation-asset syntax. They also compare the
task instruction byte for byte with the base and seed to confirm that
the request is unchanged.

Answer validation concerns the updated reference outcome. The Evolver is
instructed to compute the new values in the generated environment and
propagate them to the reference solution and evaluator. Validation
requires the new reference solution to pass the checks and the previous
expected output to fail. Reference execution was optional in the earlier
pilot. The Terminal-Bench 2.1 pipeline requires full-credit reference
execution on both arms before new paired evaluations are launched.
Structural acceptance and answer validation are recorded separately.

Shortcut audits check for generated materials that reveal conclusions
the task requires the agent to infer. Evaluation distinguishes failures
on the seed’s checks from failures on new decision points.
Appendix [C](#A3 "Appendix C Event-Driven Generation Protocol ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
describes the validation procedure, scoring, and validation status of
the evaluated instances.

### 6.4  Difficulty Evaluation and Feedback

Seed and variant are run with matched agent configurations and execution
budgets. The records contain task success and failed-check sets,
separating decision errors from missing outputs and environment
failures. Check-level outcomes provide further information when task
success reaches zero.

When failure summaries are available, they are passed to the Evolver
with the current environment and generation history to guide the next
generation’s decision points. Candidate records retain the seed
identifier, artifacts, checks, and acceptance results, including repair
attempts, so that the generated changes can be related to their
evaluation outcomes.
Section [7.4](#S7.SS4 "7.4 Environment Evolution ‣ 7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")
reports the seed–variant results.

#### 7.2.3  From Context Synthesis to Environment-Understanding Training

The two modes identify the next research question: how can a preparation

reliably generate useful context? Task-guided synthesis outperforms EGS

supervision improves the utility of the prepared context. This motivates
learning to identify relevant evidence and resolve file relationships
from materials in the environment.

Module 2 therefore turns these environmental judgments into training
targets: acquiring evidence, identifying source authority, resolving
version relationships, and preparing environments through file selection
and structured reports, making environment preparation learnable and
reusable.

The same Env-Rethink model prepares environments for all nine downstream

environment layer: file judgments made during preparation determine the
evidence available to each task agent. The consistent improvements
across downstream models show the utility of this shared preparation
step.

Module 2 produces a learned component that can be evaluated and
versioned within an environment. Environment evolution uses virtual
event histories to evolve seed states into harder instances under the
same task request, creating further examples for environment
understanding and downstream work.

### 7.4  Environment Evolution

We apply event-driven evolution to 59 Terminal-Bench 2.1 seed tasks
spanning 14 categories, including software engineering, debugging, model
training, and data processing. The evolved environments extend
generation histories, materialize changed states, and recompute
reference outcomes while retaining the task requests. We compare seed
and evolved environments using DeepSeek-V4.1-Flash, Gemini-3.8-Flash,
Qwen3.8-Flash, and GLM-5.3-Flash, with a nominal three trials per arm
and native binary task-success scoring. The analysis excludes a task
with a failing variant reference run, leaving 55 tasks with paired
results.

gives the aggregation rules, task coverage, and validation scope.

##### Harder environments across tasks and models.

Of the 55 retained tasks with paired results, 32 (58.2%) show lower
success in at least three models, including 21 with decreases in all
four models. Four further tasks show decreases in exactly two models.
These effects span ten categories: 10 of 13 software-engineering tasks,
four of five debugging tasks, and all three model-training tasks meet
the three-model criterion
(Figure [7](#S7.F7 "Figure 7 ‣ 7.4 Environment Evolution ‣ 7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
The category-level changes show that evolution can expose new execution
failures across distinct technical domains under the same task requests.

##### State changes create new execution demands.

The effects are visible at the level of individual tasks. In
log-summary-date-ranges, all four models solve the seed in every trial;
after evolution, success falls to 0/3 for DeepSeek and Gemini and 1/3
for Qwen and GLM. In multi-source-data-merger, all four start at 3/3 and
fall to 2/3, 0/3, 1/3, and 0/3, respectively. In
modernize-scientific-stack, all four fall from 3/3 to 0/3. The unchanged
request now has to be solved against a different state, requiring agents
to recover which records, versions, and operational assumptions govern
the current outcome.

Environment organization and learned preparation help agents recover
valid evidence; environment evolution creates new situations in which
that ability is tested. Together, these studies support environment
preparation and challenge generation as resources for continued
improvement. Execution failures can inform subsequent generation, and
regenerated reference outcomes supply verification targets. This
provides the challenge-generation component of environment-driven
recursive self-improvement.

## 8  Related Work

Agent tools and context management. Agent interfaces determine what
information can be found and carried across sessions. OpenAI provides
file search, computer use, orchestration, and execution tracing
\[[3](#bib.bib9)\]. Anthropic uses selective retrieval, persistent
notes, and structured handoffs \[[4](#bib.bib15), [5](#bib.bib8),
[2](#bib.bib16)\], while SWE-agent designs interfaces for repository
navigation and editing \[[7](#bib.bib5)\]. Together, these systems make
information access and continuity part of agent execution.

Environment adaptation and generation. Constructed environments define
the interactions available to agents and the outcomes that can be
checked. EnvHarness adapts existing environments while preserving their
logic and verifiers \[[8](#bib.bib13)\]. RLVE and AgentScaler generate
training tasks and tool-use simulations \[[9](#bib.bib10),
[10](#bib.bib11)\], while AWM and EvoEnv produce stateful or executable
environments \[[11](#bib.bib2), [12](#bib.bib12)\]. Across these
approaches, environment structure and verifiability are explicit design
choices.

Learning from interaction. Interaction records can turn observations and
corrections into reusable guidance. ReAct grounds decisions in tool
observations, and Reflexion retains textual feedback for later trials
\[[13](#bib.bib7), [14](#bib.bib1)\]. OpenAI and Thrive Holdings’ Tax AI
turns practitioner corrections into evaluated fixes
\[[15](#bib.bib17)\]; Factory’s Signals identifies recurring failures
across agent sessions and proposes code changes \[[16](#bib.bib18)\].
The value of a trace depends on how it informs later decisions.

Feedback-guided environments. Agent performance can guide which
challenges an environment presents next. POET generates challenges
alongside solution optimization and transfers solutions across
environments \[[17](#bib.bib3)\]. PAIRED uses differences in agent
returns to generate solvable challenges \[[18](#bib.bib4)\]. Both link
environment difficulty to observed learner behavior.

## 9  Conclusion

We study environment preparation for agents operating in persistent
file-based environments, motivated by problems with source identity,
version validity, and evidence dependence. Both environment-organization
modes improve task performance over the Noise baselines on the full task
set, with task-guided organization outperforming environment-grounded
synthesis in matched comparisons
(Table [1](#S7.T1 "Table 1 ‣ 7.2.2 Synthesis Results ‣ 7.2 Environment Organization ‣ 7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
The same Env-Rethink model improves performance across nine downstream
models on 30 tasks, comprising 15 training-source tasks and 15 held-out
tasks
(Figure [6](#S7.F6 "Figure 6 ‣ 7.3.2 Downstream Utility ‣ 7.3 Learned Environment Preparation ‣ 7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).
Environment evolution extends this approach from preparing evidence to
generating new challenges: on Terminal-Bench 2.1, 32 of 55 retained
tasks with paired results show lower success in at least three models
under an unchanged task request
(Section [7.4](#S7.SS4 "7.4 Environment Evolution ‣ 7 Experiments ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement")).

Future work will explore transfer to independently collected
environments, joint use of the three modules, and training on validated
evolved instances across repeated rounds. Event-driven generation
supplies changing environmental states, paired execution supplies
failure feedback, and reference solutions supply verification
targets—the components needed to connect environment evolution with
continued agent learning.

## Appendix A Data

This appendix specifies the annotation and collection procedures
supporting the file-verification module.

### A.1  Label Definitions

Each annotation records partition, category, observed stage, family, and
evidence. The six categories describe a file’s authority and
relationships within the supplied collection.

|  Category |  Meaning |
|----|----|
|  *authoritative record* |  The designated authoritative record, supported by source records, content consistency, or archive lineage. |
|  *false final version* |  A purported final or newest version contradicted by the genuine version chain or its own contents. |
|  *fabricated authority* |  Fabricated approvals, messages, or other authority claims lacking supporting records. |
|  *misleading redirection* |  A pointer or instruction conflicting with annotated authority relationships or the timeline. |
|  *superseded version* |  A replaced member of a version family that may still supply historical evidence. |
|  *out-of-scope file* |  A normal file outside the collection’s target scope; task relevance is assessed for the specific downstream task. |

Table 3: File-verification category definitions.

### A.2  Data Manifest

The construction rule allows identical file sets at most twice; file,
family, and semantic overlap are checked across sub-environments.
Repeated teacher trajectories are handled separately through the
retention procedure in
Appendix [B.3](#A2.SS3 "B.3 Trajectory Preparation and Deployment ‣ Appendix B Reproducibility ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement").

### A.3  Selection

Training selection starts from the 30-task, 1,280-rubric
Environment-Hard pool and favors strong clean performance with
substantial noise sensitivity. The record contains 12 core tasks with
1,235 files and four reserve tasks, totaling 16 tasks and 1,597 files.
Task 161 is excluded from the 15-task construction pool, which contains
1,579 files. The original 209 sub-environments and 30 subsequently
generated held-out environments form a collection of 239. Qualified
teacher trajectories cover 139 environments; the 30 additional
environments and the 70-environment teacher-failure pool are excluded
from SFT training. The full-environment module evaluation uses the
remaining 15 tasks, with 617 labeled files, from the 30-task set. These
parent tasks are separate from the 15-task training pool.

Selection uses Clean $`\geq`$90%, a reported Noise$`-`$Clean contrast of
$`-`$38 to $`-`$75 percentage points, and file-level evidence of the
failure mechanism.

### A.4  Annotation

Filename and path rules initialize stage and category; task-analysis
reports supply strong-decoy evidence; teacher labeling covers remaining
files. The process then checks manifests and family constraints. Strong
decoys and disagreements receive human review, while other files receive
category-stratified checks. The construction record reports that all
1,597 labeled files passed consistency checks.

### A.5  Sub-Environments

Attack scenes retain authoritative targets with decoys and fabricated
supporting chains. Version families retain related authoritative and
superseded records with their order. Redirect groups retain pointers,
targets, and supporting messages. Fillers add density around these
relationships. Composition varies the number of authoritative records
and checks whether visible evidence supports each label.

Small batches contain 4–12 files, medium batches 8–30, and large batches
at most 80. The specified mixture is 45%/35%/20%. Size, semantic
composition, and prompt condition accompany each generation and
acceptance record.

### A.6  Teacher Reading

Current generation uses DeepSeek, GLM, and Gemini teacher families
through Claude Code in isolated sandboxes. Complete messages retain
calls, observations, and final judgments. Read-fidelity checks connect
each file judgment to content-access records and supporting
observations.

The generation specification records three hint levels: L0 supplies the
verification task, L1 adds category features and distinguishes claimed
stage from verified category, and L2 supplies a checking sequence. The
current student training prompt contains the verification instruction,
schema, and reading requirements without discriminative guidance. Prompt
provenance records which generation conditions produced each accepted
trajectory and how it entered the final training corpus.

For retries, a separate agent examines the failed teacher trajectory and
the ground-truth annotations to revise the hint. The teacher receives
the revised hint and repeats the verification task.

### A.7  Qualification and Outputs

After read fidelity passes, deterministic qualification requires
partition F1 $`\geq`$0.9, zero false rejections of authoritative
records, correct classification of all strong decoys, and correct order
where a version family occurs. The strong-decoy categories are *false
final version*, *fabricated authority*, and *misleading redirection*.
The generation specification permits at most two additional retries with
hints revised by the separate agent described in
Appendix [A.6](#A1.SS6 "A.6 Teacher Reading ‣ Appendix A Data ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement");
remaining failures are retained for analysis.

The current record reports 2,116 qualified trajectories. The dataset
links their messages and qualification records to file, family, scene,
annotation, and sub-environment manifests.

### A.8  Unseen-Task Extension

The extension contains tasks 72, 75, 78, 85, 100, 146, 159, 171, and
266, none of which entered training, and records annotations for 304
files. Six existing-noise tasks (85, 100, 146, 159, 171, and 266)
contribute 224 files: 70 standard files and 154 noise files across 42
version families. Their annotation record contains 22 entries flagged
for further review. The other three tasks (72, 75, and 78) receive 68
generated noise files across 18 version families. The construction
record includes solvability and task-navigation audits for these tasks.

The extension tasks are included in the unified 30-task downstream
evaluation in
Appendix [B.6](#A2.SS6 "B.6 Thirty-Task Downstream Evaluation ‣ Appendix B Reproducibility ‣ Breaking the Environment Wall: Evolving LLM Agent Environments for Recursive Self-Improvement").

## Appendix C Event-Driven Generation Protocol

The materialized environment and its generation record are represented
separately:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
E_{t}=\langle F_{t},S_{t}\rangle,\qquad R_{t}=\langle L_{t},y_{t},V_{t};\nu_{t}\rangle,
``` |  | (3) |

where $`F_{t}`$ comprises files and service implementations, $`S_{t}`$
is their state, $`L_{t}`$ is the generation history, $`y_{t}`$ is the
reference outcome, $`V_{t}`$ is the evaluator, and $`\nu_{t}`$
identifies the variant. The task agent receives $`E_{t}`$ and the
unchanged request $`q`$; generation and verification retain $`R_{t}`$.

##### Generation and validation.

The Environment Evolver receives the seed or previous variant, its
generation history, and available execution feedback. It produces
environmental changes, causally linked events, and revised reference
outcomes. Assembly applies the changes to produce a runnable
environment. Structural checks verify event links, file references,
evaluation assets, and byte-for-byte preservation of the task request.
Reference execution checks that the new answer passes and the previous
answer fails. Each variant specifies at least three counter-default
decision points, linking a plausible incorrect choice to resolving
evidence and an executable check. Shortcut audits inspect generated
materials for conclusions that would bypass the seed’s reasoning
requirements. Evaluation uses the assembled environment, preserving its
state when files are supplied to the agent.

### C.1  Evaluation Settings

##### Task coverage.

The collection contains 59 Terminal-Bench 2.1 seeds: four easy and 55
medium tasks. We exclude sanitize-git-repo because its variant reference
run fails, leaving 58 seeds, of which 55 have paired results. Among
these, 32 show a success-rate decrease of at least 20 percentage points
in three or more models, four in exactly two models, and 19 in at most
one model. The reported 58.2% uses the 55 retained paired tasks as its
denominator. Category summaries apply the same exclusion. The aggregate
reports observed success-rate changes; reference-validation records are
available for a subset of the retained tasks. A seed-environment fault
is recorded for mteb-retrieve.

##### Scoring and aggregation.

We evaluate DeepSeek-V4.1-Flash, Gemini-3.8-Flash, Qwen3.8-Flash, and
GLM-5.3-Flash with matched configurations and execution budgets across
seed and variant. The target allocation is three independent trials per
arm. Task success requires passing all native checks; check-level pass
rates are used only for diagnosis. For task $`i`$ and model $`m`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\Delta_{i,m}=100\bigl(\hat{p}^{\mathrm{evolved}}_{i,m}-\hat{p}^{\mathrm{seed}}_{i,m}\bigr),\qquad h_{i}=\sum_{m}\mathbf{1}\{\Delta_{i,m}\leq-20\}.
``` |  | (4) |

The main result counts tasks with $`h_{i}\geq 3`$. This is a screening
criterion: one changed outcome in three trials corresponds to 33.3
percentage points. Rates use completed-trial denominators; for example,
GLM’s seed score on largest-eigenval is 1/2 and its variant score is
0/3.

Category means average task-level contrasts, excluding missing pairs and
pairs with zero seed success.
````
