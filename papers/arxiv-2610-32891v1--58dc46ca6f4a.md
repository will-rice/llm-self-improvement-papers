###### Abstract

Large Language Models (LLMs) are increasingly used to optimize code for
performance. This practice often assumes that improvements in execution
speed naturally translate into overall lower energy consumption. We
challenge this assumption empirically by measuring whether
performance-optimized code produced by LLM self-refinement pipelines is
also energy-efficient relative to canonical human reference solutions,
and whether the energy cost of the optimization process can be offset by
subsequent execution-time savings. We evaluate 11 open-source models
across four decoding configurations on all 1,000 problems of EffiBench,
a state-of-the-art performance benchmark, while collecting per-process,
hardware-level energy measurements throughout. Inference energy spans
0.79–8.68 MJ across model-variant pairs, which is roughly equivalent to
the energy of 250–2800 GPT-4.1 queries. Limiting the maximum number of
output tokens has the largest impact, reducing energy use by up to 69%
compared to the default configuration. On the execution side, 42 of 44
configurations produce code that consumes _more_ energy per problem than
the canonical human reference, with overheads ranging from +4% to +886%.
The two exceptions achieve only marginal gains, with break-even points
on the order of $`10^{6}`$–$`10^{7}`$ executions. Mixture-of-Experts
architectures consume substantially less inference energy than
equivalently-sized dense models without sacrificing correctness, making
architectural choice a more consequential sustainability lever than
decoding parameters. Performance optimization and energy efficiency are
not always aligned goals: LLM self-refinement consistently produces
faster-seeking but energy-heavier code relative to what a human engineer
would write. All artifacts are available at
[https://doi.org/10.5281/zenodo.23598170](https://doi.org/10.5281/zenodo.23598170).

## I Introduction

Recent studies indicate that developers routinely integrate Large
Language Models (LLMs) into their daily coding
workflows \[[1](#bib.bib1), [2](#bib.bib6)\]. Beyond code generation,
LLMs are used to iteratively refine code to reduce execution time and
memory usage, tasks that previously required expert manual
effort \[[3](#bib.bib13)\]. This growing practice implicitly assumes
that performance improvements also translate into environmental
benefits: that faster code is greener code. However, each optimization
interaction carries two distinct energy costs: the _inference energy_
consumed when the model produces code \[[4](#bib.bib7),
[5](#bib.bib8)\], and the _execution energy_ consumed when that code is
later run \[[6](#bib.bib9)\]. Both costs are largely invisible to the
developer, yet together determine whether an optimization yields a net
energy benefit. However, it remains unclear whether the execution-time
savings can offset the energy required to generate the optimization, or
whether LLM-optimized code is more energy-efficient than code written by
human developers \[[7](#bib.bib17), [8](#bib.bib27)\].

Coignion et al. \[[9](#bib.bib29)\] introduce the Break-Even Point
(BEP), defined as the number of executions at which cumulative execution
savings offset generation cost, and find that this point ranges from
under 100 to over 200,000 executions depending on the large language
model and the method that is being optimized. However, their analysis
measures savings relative to each model’s own unoptimized output rather
than a canonical human-written solution. This distinction is important
because a model can greatly improve upon its own baseline while still
producing code that is less efficient than a competent human solution.
As a result, it remains unclear whether LLM-optimized code is actually
competitive with what a competent human engineer would produce.

We investigate this question by evaluating the energy consumptioon of
LLM-based code optimization end-to-end. We use
EffiLearner \[[3](#bib.bib13)\], a state-of-the-art iterative
self-refinement pipeline for code performance optimization, to generate
optimized solutions. We evaluate these solutions against the canonical
human-written reference implementations in
EffiBench \[[10](#bib.bib12)\], a benchmark of 1,000 LeetCode problems
paired with top-rated human solutions. We evaluate only open-source
models deployed on-premise. Such deployments are increasingly adopted in
privacy-sensitive environments, while also allowing us to instrument the
underlying hardware and obtain precise, hardware-level measurements of
inference energy rather than relying on estimates or provider-reported
statistics.

Addressing the practical value of LLM-based optimization requires
examining three different aspects. First, the optimization process
itself incurs an energy cost that must be quantified. Second, this cost
may vary substantially across models and decoding strategies,
potentially changing the trade-off between optimization quality and
energy consumption. Finally, the generation investment is worthwhile
only if the resulting code consumes less execution energy than a strong
human-written baseline, allowing the initial energy cost to be recovered
over repeated executions. These considerations motivate the following
research questions:

- •
  RQ1. What is the energy cost of generating performance-optimized code
  using LLMs?
- •
  RQ2. How does the energy cost of generating optimized code vary across
  open-source LLMs and decoding configurations?
  - –
    RQ2a. How do decoding parameters (temperature, context window,
    maximum output tokens) affect energy consumption across models?
  - –
    RQ2b. Which model-configuration pairs offer the most favorable
    trade-off between inference energy and optimization quality?

- •
  RQ3. Does performance-optimized code consume less execution energy
  than canonical human reference solutions, and if so, at what number of
  executions does the generation investment break even?

Contributions.

Our main contributions are as follows:

1.  1.  We present the first end-to-end energy evaluation of iterative
        LLM-based code optimization against canonical human-written
        reference solutions.
2.  2.  We conduct a large-scale empirical study of the energy cost of
        LLM-based code optimization across 11 open-source models and
        multiple decoding configurations, providing a systematic
        characterization of the factors that influence inference energy and
        optimization cost.
3.  3.  We release all experimental artifacts, including repaired EffiBench
        benchmark, to support reproducibility and future research on
        energy-efficient LLM-based code optimization.

Findings in brief. Our results show that inference energy ranges from
0.79 to 8.68 MJ across model–configuration pairs, equivalent to roughly
250–2800 GPT-4.1 queries \[[11](#bib.bib22)\]. Among the evaluated
decoding parameters, limiting the maximum output length has by far the
greatest impact, reducing inference energy by 13–69% relative to the
default configuration.

On the execution side, the optimized code is almost never more
energy-efficient than the canonical human reference: 42 of the 44
evaluated configurations consume between 4% and 886% more execution
energy per problem. Only two configurations outperform the human
baseline, requiring approximately $`3.4\times 10^{6}`$ and
$`6.4\times 10^{7}`$ executions, respectively, to recover the energy
invested in optimization.

## II Related Work

The energy footprint of LLMs has been studied along two axes: the cost
of _operating_ the model, and the cost of _running the code_ the model
produces. Our study sits at the intersection of both.

Luccioni et al. \[[12](#bib.bib18)\] reported that pre-training BLOOM
consumed 433,196 kWh and 24.69 tonnes of CO₂eq. The systematic mapping
by Verdecchia et al. \[[24](#bib.bib19)\] confirmed that the Green AI
literature is heavily skewed toward training, with inconsistent
measurement protocols hampering cross-study comparison. Budennyy et
al. \[[25](#bib.bib20)\] released eco2AI, exposing a 26-fold range in
grid carbon intensity that makes _where_ a model runs nearly as
consequential as how efficiently it runs. These studies establish the
measurement landscape our work builds on, but focus exclusively on
training. The inference cost of iterative optimization pipelines remains
unexamined.

On the inference side, Samsi et al. \[[5](#bib.bib8)\] provide the most
detailed power profile of LLaMA inference across deployments, observing
system draws between 300 W and 1 kW, while a study \[[26](#bib.bib21)\]
estimates that at ChatGPT-scale traffic, inference matches the energy
cost of training in just about 2 days. LASSI-EE \[[22](#bib.bib14)\] is
the closest prior pipeline to ours in spirit: an iterative,
self-correcting LLM loop with runtime power-profile feedback applied to
HPC code, reporting 36% and 34% energy reductions on MI100 and A100
respectively. Like the training-focused studies above, however, it does
not connect inference and execution energy through a break-even
analysis, and targets bespoke HPC kernels rather than a standardised
benchmark like EffiBench. Crucially, no prior work jointly measures
inference and execution energy across a controlled decoding parameter
sweep on a standardised benchmark, which is the gap this paper fills.

### II-B Effect of Model Configuration on Inference Energy

Several recent studies have identified output token length as the
dominant inference energy driver. Poddar et al. \[[13](#bib.bib23)\]
report a Pearson correlation of $`r=0.952`$ between output tokens and
energy, against $`r=0.697`$ for input tokens. Adamska et
al. \[[14](#bib.bib24)\] independently measure $`r=0.9`$ on a separate
corpus and find that prompt phrasing can influence response length. Both
findings emerge as observational correlations across natural output
variation rather than from controlled ablations of the output-token
budget as an independent variable. To our knowledge, no prior study
provides an isolated, controlled measurement of _sampling temperature_,
_context window size_, or _maximum output tokens_ as independent
inference-energy levers while holding the remaining factors constant.
Furthermore, both studies focus on general NLP tasks such as
classification, question answering, and summarization; neither examines
code generation or optimization pipelines, where output structure and
length distributions differ substantially from natural language
responses. Controlled comparisons do exist for the software stack.
Georgiou et al. \[[15](#bib.bib35)\] measure training and inference
energy of six deep learning models under matched configurations in
PyTorch and TensorFlow, and report statistically significant differences
between the frameworks in 94% of the energy and runtime comparisons,
with comparable accuracy and no single framework superior across all
tasks. The factor they vary is the framework, however, and the models
they study are not applied to code generation.

### II-C Runtime Energy of Generated Code and the Break-Even Point

Empirical consensus establishes that LLM-generated code is
systematically less efficient than canonical human solutions.
EffiBench \[[10](#bib.bib12)\], which evaluated 42 models, found that
even the best open-source model (StarCoder2-15B) required 2.59$`\times`$
the execution time and 1.71$`\times`$ the peak memory of human
solutions. Islam et al. \[[7](#bib.bib17)\] extend this picture on 878
EffiBench problems, finding that the best model (DeepSeek-v3) remains
1.17$`\times`$ less energy-efficient than humans, with gaps reaching
449$`\times`$ for dynamic programming and bit-manipulation tasks.
Convergent findings come from Tuttle et al. \[[20](#bib.bib25)\], who
report LLMs outperforming human solutions in only 5.7% of 192 LeetCode
responses. Apsan et al. \[[21](#bib.bib28)\], who show the human–LLM gap
persists across server, PC, and Raspberry Pi platforms. Solovyeva et
al. \[[8](#bib.bib27)\], who find parity only in narrow regimes such as
String and Tree tasks; and Rani et al. \[[23](#bib.bib26)\], who
document that LLM-suggested optimizations on Matlab often
unintentionally increase memory and energy usage. Whether iterative
self-refinement can close this gap, and at what inference cost,
motivates the methodological thread we build on.

The methodological precursor to our pipeline is
EffiLearner \[[3](#bib.bib13)\], which iteratively refines LLM-generated
code by feeding execution-overhead profiles back to the model as
structured prompts, demonstrating consistent reductions in Normalized
Execution Time (NET) and Normalized Total Memory Usage (NTMU) across 22
models, but without measuring inference energy and therefore unable to
answer whether the optimization investment is recovered at execution
time. Coignion et al. \[[9](#bib.bib29)\] first formalised this question
via the BEP ($`BEP=E_{\text{optim}}/(e_{\text{orig}}-e_{\text{opt}})`$),
finding results spanning four orders of magnitude: DeepSeek-R1-14B with
EoH yields 49% per-execution savings but requires 220,324 executions to
break even, while pathologically inefficient code can drop from 318 J to
2.6 J and break even within 100 runs. Critically, their BEP measures
savings relative to each model’s own unoptimized output rather than a
canonical human reference, leaving open the question of whether
LLM-optimized code is competitive with what a human engineer would
write.

### II-D Gap Analysis

Most of the above studies address either (i) the inference energy of
LLMs in general NLP settings, (ii) the runtime efficiency of
LLM-generated code relative to human references, or (iii) the break-even
economics of LLM-based optimization relative to each model’s own
unoptimized output. No prior study jointly measures inference energy
across a controlled decoding parameter sweep, evaluates the resulting
code against canonical human solutions, and applies a break-even
analysis within a multi-epoch self-refinement pipeline on a standardised
benchmark. Our study is designed to fill this intersection.

## III Methods

In this section, we first describe the benchmark dataset and the
self-refinement framework. We then present the evaluated models and
decoding configurations, followed by the hardware platform and
energy-measurement instrumentation. Finally, we explain how this
experimental setup is used to answer each research question.

### III-A Dataset

We evaluate on EffiBench \[[10](#bib.bib12)\], a benchmark of 1,000
efficiency-critical LeetCode problems spanning 171 _Easy_, 589 _Medium_,
and 240 _Hard_ problems. Each entry pairs a problem description with an
executable canonical solution drawn from top-starred LeetCode Discussion
Forum submissions, a test-case generator, and 100 test cases. The
canonical solutions serve as the human reference baseline for our RQ3
break-even analysis. Because they are top-starred submissions, they
represent highly efficient human implementations rather than average
developer code, and we discuss the implications in
Section [VI](#S6 "VI Limitations and Future Work ‣ Green Code or Costly Code? Evaluating the Energy Costs of Iterative LLM-Based Code Optimizations").

EffiBench is particularly well suited to our study because its
algorithmically challenging problems exhibit substantial variation in
execution time, making differences in execution energy measurable.

The EffiBench test cases were generated by GPT-3.5 Turbo, and during our
validation run we found that 122 of the 1,000 problems contained defects
preventing correct execution, all originating in the generated test
cases rather than the solutions themselves. The most common defects were
ordering-sensitive assertions on unordered outputs, missing helper
utilities for tree and linked-list construction, object-address
serialization embedding raw in-memory representations, wrong precomputed
expected values, method-name mismatches, redundant class redefinitions
shadowing the actual implementation, and empty test cases caused by
generator logic that emitted no output. For each defect type we applied
a targeted repair, recomputing expected values from the canonical
solution, injecting missing helpers, rewriting object references as
constructor calls, removing shadowing definitions, and converting
ordering-sensitive assertions to order-independent equivalents. After
repair, all 1,000 canonical solutions pass their respective test cases.

### III-B Self-Refinement Framework

We adopt EffiLearner \[[3](#bib.bib13)\] as our self-refinement pipeline
because it directly targets execution-time and memory efficiency through
line-level profiling feedback, and has been shown to produce
significantly more efficient code across a wide range of model
architectures, achieving state-of-the-art reductions in execution time
and memory usage compared to alternative self-refinement approaches.
EffiLearner structures code optimization as an iterative refinement loop
comprising three stages: code generation, overhead profiling, and code
refinement. Given a task description, the LLM first produces an initial
code candidate.

At each iteration, the current candidate is executed locally against the
set of open test cases provided by the benchmark, and two line-level
overhead profiles are collected: an execution-time profile via
line_profiler and a memory-usage profile via memory_profiler. Each
profiling measurement is repeated 60 times per script, and the reported
Execution Time (ET), Max Memory Usage (MU), and Total Memory Usage (TMU)
values are the averages over those 60 runs. To minimize the influence of
thermal throttling and background load, a cooldown period of 15 seconds
is enforced between consecutive runs. A run is only admitted once CPU
load falls below 50% and the CPU package temperature is within the
50–60 °C range. Both profiles aggregate measurements across all open
test cases and report, per line, the cumulative time and memory
footprint. The current candidate, its overhead profiles, the task
description, and the open test cases are then concatenated into a
refinement prompt and passed back to the LLM, which emits a revised
candidate. The revised candidate is validated for functional correctness
against the open test cases only; if it passes, it replaces the current
candidate as the input to the next iteration. The loop terminates after
a fixed number of iterations. Final evaluation is conducted on a
held-out set of private test cases disjoint from the open test cases,
following the protocol of EffiBench \[[10](#bib.bib12)\].

For each model, we run four configurations that each change at most one
parameter, so that energy differences can be attributed to a single
cause. We vary only deployment levers that practitioners can adjust
without retraining and that act on energy through the number of
generated tokens or the memory provisioned for generation. The _default_
configuration uses temperature 0 (greedy decoding) and a maximum output
length of 2,048 tokens. The _sampling_ variant raises the temperature to
$`0.5`$. In a pilot experiment, temperatures above $`0.5`$ increased
verbosity and inference energy without improving code efficiency, so we
did not sweep higher values. The _reduced-context_ variant caps the
context window at 64k tokens, since all evaluated models support windows
three to four times larger by default. The _reduced-output_ variant
halves the maximum output length to 1,024 tokens to test whether a
shorter generation budget lowers energy without hurting optimization
quality. A full factorial sweep was timely infeasible.

### III-D Experimental Setup

All experiments were conducted on a server equipped with two Intel Xeon
Gold 6438Y+ processors with 128 logical cores in total, 1 TB of system
memory, and two NVIDIA L40 GPUs with 46 GB GDDR6 VRAM each. Simultaneous
Multithreading (SMT) was enabled and the system exposed two Non-Uniform
Memory Access (NUMA) nodes. The server ran Ubuntu 24.04 with Linux
kernel 6.8.0-138, and models were served locally via
vLLM \[[32](#bib.bib10)\]. Processes were pinned to physical cores,
while the frequency governor, turbo boost, C-states, and NUMA policy
remained at their operating system defaults to reflect standard
deployments. The full experimental pipeline required approximately 30
days of continuous execution.

### III-E Energy Measurement

We instrument all experiments with Metrion \[[33](#bib.bib11)\], an
energy measurement tool that attributes energy consumption to processes
at the thread level. Most existing tools neglect the combined effects of
frequency scaling, simultaneous multithreading, and non-uniform memory
access in multi-socket architectures. Utilization-based tools like
CodeCarbon \[[34](#bib.bib15)\] estimate process-level energy from
coarse-grained CPU time and RAPL values without accounting for these
hardware-level effects, while profiling utilities like perf expose RAPL
metrics only at the package level. Metrion overcomes these limitations
by combining Intel RAPL, nvidia-smi, and Hardware Performance Counters
(HWPCs) to attribute CPU, DRAM, and GPU energy at the thread level, with
HWPCs resolving per-thread footprints within each 1-second sampling
window. Metrion does not require a process to span an entire sampling
interval. It uses eBPF and HWPCs to trace when each process is scheduled
on or off the CPU and to count its unhalted cycles, and it allocates the
RAPL package energy, sampled at 1 Hz, to active processes in proportion
to their unhalted cycles in each interval. This attributes energy
correctly even to short-lived processes. Frequency scaling and hardware
topology are handled at attribution time. Metrion weights active cycles
by the APERF/MPERF ratio, which reflects the actual frequency under
Dynamic Voltage and Frequency Scaling (DVFS) and Turbo Boost, scales
overlapping SMT threads by a calibrated contention factor of 1.15, and
attributes energy per socket. Energy is aggregated over all descendant
threads of each solution process, yielding a per-solution breakdown into
CPU, DRAM, and GPU, each decomposed into active and idle components.

#### III-E1 Measurement Protocol

Inference energy and execution energy are measured under different
repetition budgets, reflecting the difference in their computational
cost.

##### Inference energy.

Each _(model, configuration)_ pair is executed six times in full,
covering all 1,000 problems per run. The reported $`E_{\text{total}}`$
($`=E_{\text{gen}}+E_{\text{exec}}`$) is the mean over these six runs.
Running inference six times provides sufficient stability for the
aggregate energy signal while keeping total experiment time feasible
given the cost of a full five-epoch optimization pass. GPU energy
applies only to this inference phase, whose runs last from hours to
days, and is recorded continuously via NVML.

##### Execution energy.

Each solution script is executed 60 times sequentially within one
persistent Python interpreter, and the reported $`E_{\text{exec}}`$ is
the mean over those 60 runs. Keeping the interpreter alive amortizes
startup and import overhead, so the measurement reflects steady-state
energy. Canonical and LLM-generated solutions share an identical
harness, so any residual overhead affects both symmetrically. Individual
executions average more than 0.1 seconds, so the 60 sequential
executions of each solution give cumulative measurement windows well
over one second. The higher repetition count relative to inference is
feasible because individual script executions are cheaper. The same
cooldown protocol applied to resource profiling is used here: a
15-second pause is enforced between consecutive executions, and a run is
only admitted once CPU load is below 50% and the CPU package temperature
is within the 50–60 °C range. These admission criteria prevent
cross-experiment interference and thermal throttling.

### III-F Approaches to the Research Questions

The infrastructure described above produces two complementary energy
measurements at different granularities. For each _(model,
configuration)_ pair, we record the aggregate _generation energy_
$`E_{\text{gen}}`$ expended by the LLM during the entire generation and
optimization run across all 1,000 problems. For each _(model,
configuration, problem)_ triple, it additionally records the per-process
_execution energy_ $`E_{\text{exec}}`$ consumed when running the
resulting solution script. We use these measurements to answer each
research question as follows.

#### III-F1 RQ1 – Energy Cost of Optimization

To quantify the energy cost of generating performance-optimized code, we
report $`E_{\text{gen}}`$ at the granularity at which it is measured:
one aggregate value per _(model, configuration)_ pair, broken down by
hardware component (CPU package, DRAM, GPU) and by dynamic versus idle
contributions, where the dynamic component captures power draw above the
static baseline and the idle component captures the baseline itself.
$`E_{\text{gen}}`$ includes the full generation cost across all five
optimization epochs, including the initial code generation. We report an
aggregate over all 1,000 problems because vLLM batches requests across
problems and our research questions concern model-level and
configuration-level energy budgets.

#### III-F2 RQ2 – Cross-Model and Parameter Variation

RQ2 examines how generation energy varies with model choice and decoding
parameters. We evaluate this along two complementary axes.

##### Parameter sensitivity (RQ2a).

For every model in
Table [II](#S3.T2 "TABLE II ‣ III-C Models and Parameter Configurations ‣ III Methods ‣ Green Code or Costly Code? Evaluating the Energy Costs of Iterative LLM-Based Code Optimizations"),
we compare the energy consumption of each model based on four parameter
configurations defined in
Section [III-C](#S3.SS3 "III-C Models and Parameter Configurations ‣ III Methods ‣ Green Code or Costly Code? Evaluating the Energy Costs of Iterative LLM-Based Code Optimizations").
Holding the model fixed isolates the energy impact of temperature,
context size, and maximum output length.

##### Cross-model comparison (RQ2b).

To identify configurations that simultaneously minimize generation cost
and improve the performance of the optimized code, we plot correctness
efficiency (pass@1/$`E_{\text{total}}`$, in % MJ⁻¹) against the NET of
the last-epoch solutions for each of the four decoding configurations
(default, t0.5, ctx65536, and mt1024), where
$`E_{\text{total}}=E_{\text{gen}}+E_{\text{exec}}`$ is the sum of
generation and execution energy.

#### III-F3 RQ3 – Break-Even of Generation vs. Execution Savings

RQ3 asks whether the energy invested in generating optimized code is
recovered through reduced energy consumption at execution time. We treat
the canonical solution provided by EffiBench as the reference baseline
against which optimized solutions are compared. Each canonical solution
is a top-rated, human-written solution selected from competitive
programming submissions, representing a strong but attainable efficiency
ceiling. We aggregate at the (model, configuration) level rather than
per task because our goal is to characterize the overall energy
trade-off of deploying a given model under a given decoding
configuration, not to identify which individual problems benefit from
refinement.

For each _(model, configuration)_ pair, we compute the mean execution
energy of the optimized solutions $`\bar{E}_{\text{exec}}^{*}`$ and the
mean execution energy of the canonical solutions
$`\bar{E}_{\text{exec}}^{\text{canon}}`$ over the benchmark, and define
the per-run saving as

|     |     |     |
| --- | --- | --- |
|     |

````math
\Delta E=\bar{E}_{\text{exec}}^{\text{canon}}-\bar{E}_{\text{exec}}^{*}.
``` |  |

The break-even point is the number of executions at which the cumulative
execution-time saving offsets the up-front generation cost,

|  |  |  |
|----|----|----|
|  |
``` math
N^{*}=\left\lceil\frac{E_{\text{total}}}{\Delta E}\right\rceil\quad\text{when }\Delta E>0,
``` |  |

where $`E_{\text{total}}`$ is the aggregate generation energy of the
optimization run. $`N^{*}`$ is thus a single scalar per *(model,
configuration)* pair, expressing how many executions of a representative
benchmark problem are required before the energy invested in
optimization is recouped relative to the canonical baseline. When the
mean optimized solution is no more energy-efficient than the canonical
baseline ($`\Delta E\leq 0`$), no break-even point exists and the
optimization constitutes a net energy loss in aggregate. We report this
outcome explicitly where it occurs.

how that cost varies across models and decoding configurations
(Section [IV-B](#S4.SS2 "IV-B RQ2: How does the energy cost of generating optimized code vary across open-source LLMs and decoding configurations? ‣ IV Results ‣ Green Code or Costly Code? Evaluating the Energy Costs of Iterative LLM-Based Code Optimizations")),

each reported in absolute terms and normalized against the profiling
results of the canonical solutions, resulting in NET, Normalized Max
Memory Usage (NMU) and NTMU.

##### Break-even analysis

A break-even point $`N^{*}`$ exists only when the optimized code
consumes less execution energy than the canonical solution on average.
Under this criterion, 42 of the 44 configurations admit *no break-even
point*: the energy invested in generation is never recovered regardless
of how often the resulting code is executed. For the two configurations
where a saving exists, the thresholds are prohibitively large.
Qwen3.5-9B t0.5 requires approximately $`3.4\times 10^{6}`$ executions
per problem to break even, and Nemotron-Cascade mt1024 requires
approximately $`6.4\times 10^{7}`$, thresholds reachable only in
exceptional high-volume deployment scenarios. We discuss the broader
implications for the energy economics of LLM-based code optimization in
Section [V](#S5 "V Discussion ‣ Green Code or Costly Code? Evaluating the Energy Costs of Iterative LLM-Based Code Optimizations").

generation investment of 133 gCO₂eq, yielding
$`N^{*}\approx 3.4\times 10^{6}`$ executions, which is identical to the
energy-denominated result since the conversion is linear in $`\gamma`$.

## V Discussion

We now interpret the results across the three research questions and
their broader implications for practitioners considering LLM-based code
optimization.

### V-A Generation energy as a hidden cost of optimization

A central finding of this study is that the energy consumed during
LLM-based self-optimization is substantial and largely unrecoverable.
Across 42 of the 44 evaluated model-variant configurations, the
optimized code consumes more execution energy per problem than the
canonical human-written reference, and the generation investment
requires millions of executions to break even in the two cases where a
saving exists. Our results suggest that performance optimization and
energy efficiency are not aligned goals: faster code does not
automatically mean greener code when the cost of generation is accounted
for. Coignion et al. \[[9](#bib.bib29)\] reached a similar conclusion on
a different benchmark and pipeline, reporting weak correlation between
performance gains and energy reduction.

### V-B Model and architecture choice matter more than decoding parameters

Our RQ2 analysis shows that the dominant factor in both inference energy
and correctness-efficiency is the choice of model and its architecture,
not decoding configuration. Constraining output length (mt1024)
consistently reduces inference energy across all models, but at the cost
of correctness collapse in several configurations. The MoE architecture
of Qwen3.5-35B-A3B achieves near-identical correctness to the larger
Qwen3.5-27B dense model at less than half the inference energy, owing to
sparse parameter activation, suggesting that architectural choices made
upstream of deployment have a larger sustainability impact than
parameter tuning.

### V-C Self-optimization does not reliably reduce execution energy across epochs

A subtler finding from RQ3 is that the EffiLearner pipeline does not
drive consistent execution-energy reductions even relative to its own
base epoch, with 54.5% of configurations regressing across the
optimization trajectory. Future pipelines should incorporate execution
energy as an explicit selection criterion alongside correctness.

### V-D Practical implications

LLM-based self-optimization is only energetically justified for code
that will be executed at very high volume. For one-off scripts or
lightly used utilities, the generation cost will never be recouped.
Practitioners aiming to reduce overall energy consumption should
restrict optimization to hot-path code with known high execution
frequency and prefer smaller models such as Ministral-3B or Qwen3.5-4B
when correctness requirements allow. The carbon footprint analysis
(Section [IV-D](#S4.SS4 "IV-D Carbon Footprint of the Optimization Loop ‣ IV Results ‣ Green Code or Costly Code? Evaluating the Energy Costs of Iterative LLM-Based Code Optimizations"))
confirms that these differences are non-trivial at scale: the generation
footprint of Qwen3.5-27B is approximately seven times that of
Ministral-3B for the same optimization task.

## VI Limitations and Future Work

The findings reported in this study are bounded by deliberate
experimental choices, each pointing to a concrete direction for future
work.

##### Benchmark scope

EffiBench problems are short, algorithmically dense, and complete in
under a second, which is ideal for energy measurement at scale but
unrepresentative of long-running workloads where break-even would most
plausibly favor optimization. Future work should investigate whether the
pass@1 collapse observed under aggressive decoding constraints persists
on harder, more diverse tasks such as I/O-bound programs or
data-processing pipelines.

##### Human baseline

The canonical EffiBench solutions are top-rated submissions from a
competitive programming forum, so they represent highly efficient human
implementations rather than the code an average practitioner would
write. Our RQ3 comparison therefore measures LLM-optimized code against
a strong reference. We also assign no authoring cost to the canonical
solutions, whereas the generation cost of the LLM is fully counted. This
omission does not affect our main finding. In 42 of 44 configurations
the optimized code consumes more execution energy per run than the
canonical code, so the recurring difference is negative and no authoring
cost for the baseline can turn the generation energy into a net saving
through repeated execution. It could only favor LLM-based optimization
when a solution is executed few times. Future work should compare
against solutions from a broader pool of practitioners and measure human
authoring effort explicitly.

##### Pipeline design

The EffiLearner pipeline replaces solutions with no gate on execution
energy, which explains a significant portion of the regressions we
observed and makes it difficult to attribute results solely to model
capability. Future pipelines should incorporate execution energy as an
explicit selection criterion to isolate its effect.

##### Language and platform coverage

All experiments use Python, whose interpreted execution model shapes the
energy profiles we report. The execution-energy gap between
LLM-generated and canonical solutions may narrow in compiled languages
such as C++ or Rust \[[6](#bib.bib9)\], and a multi-language replication
would establish whether our patterns generalize.

##### Closed-source models

Our open-source-only model selection is required by the need for
hardware-level energy attribution, so our findings do not extend to
frontier models served through commercial APIs. Closing this gap will
require provider-published per-request energy disclosures or
instrumented inference stacks.

##### Broader environmental impact

Our measurements cover operational energy only. Embodied costs of GPU
manufacturing, data-center cooling, model training, and hardware refresh
cycles are not captured yet can outweigh operational savings over the
hardware lifecycle. Future work should adopt a lifecycle perspective
accounting for these indirect impacts.

## VII Conclusion

This paper presented a systematic measurement study of the energy
economics of LLM-based code self-optimization, covering inference and
execution cost across 11 open-source models, four decoding
configurations, and 1,000 EffiBench problems. The central question was
whether performance-optimized code produced by LLM self-refinement is
also energy-efficient relative to canonical solutions.

Optimized code consumes more execution energy than the canonical
reference in 42 of 44 model-variant pairs; the two exceptions achieve
only marginal gains, with break-even points requiring millions of
executions. Performance optimization and energy efficiency are not
aligned even within the refinement trajectory: more than half of all
configurations regress in execution energy relative to their base epoch,
reflecting the absence of any energy-aware selection criterion in the
pipeline.

On the generation side, inference energy varies by nearly an order of
magnitude across models, driven primarily by model size and
architecture. MoE models such as Qwen3.5-35B-A3B offer substantially
lower inference cost than equivalently-sized dense counterparts without
sacrificing correctness, making architectural choice a more
consequential sustainability lever than decoding parameters.
Constraining output tokens (mt1024) is the most effective parameter
adjustment for reducing inference energy, but risks correctness collapse
that must be weighed per model.

Practitioners should restrict LLM-based self-optimization to hot-path
code with reliably high execution frequency, prefer small and MoE-based
models when correctness allows, and treat generation energy as a
first-class cost. Future work should extend this framework to compiled
languages, long-running workloads, and energy-aware refinement
pipelines.
````
