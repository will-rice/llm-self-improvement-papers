###### Abstract

Personal agents increasingly connect to services across the web and
applications by using tools. As the effects of their actions accumulate
and interact across services, unintended or harmful outcomes can arise
when agents fulfill benign user requests. Proactively identifying these
compositional failures requires systematically exploring diverse
cross-service paths. Existing red-teaming methods often simply prompt
LLMs to identify potentially harmful paths from task and environment
descriptions or decompose harmful objectives specified by humans or LLMs
into seemingly benign action combinations. However, generation is biased
toward patterns learned during training, potentially favoring familiar
tool combinations and leaving novel cross-service interactions
underexplored. To address this, we propose X-AgentRed, a self-evolving
red-teaming framework that discovers harmful tool call paths through a
graph of tool dependencies and expands and refines them using execution
feedback. By analyzing each tool’s effects, potential harms, and
preconditions for execution, the red-teaming agent constructs a directed
graph that captures how one tool’s effects can satisfy another’s
execution preconditions. Recipes sampled from this graph are
instantiated as realistic scenarios in which agents can produce harmful
outcomes. Execution feedback enables self-improvement by diversifying
paths that produce harm through tool substitution and refining
preconditions at blocked steps in unsuccessful paths to enable further
execution. Across four frontier agentic models, X-AgentRed achieves
$`1.77\times`$ the harmful path rate of STAC and explores a more diverse
set of tools, yielding $`2.99\times`$ the tool coverage on average.

## 1 Introduction

Recent advances in personal agents, including ChatGPT ([OpenAI,
2026b](#bib.bib19)), Claude ([Anthropic, 2026a](#bib.bib2)), and
Muse ([Meta, 2026](#bib.bib16)), enable users to delegate increasingly
complex tasks across services on the web and in applications. Each
service, such as GitHub or Notion, provides a set of tools that agents
can invoke. Given a user’s goal, these agents coordinate actions across
services for software development, content creation, commerce, and
travel, combining their capabilities into multi-step workflows. These
interconnected services form a multi-service ecosystem whose scope
continues to expand through service integrations and direct interaction
with browser and desktop interfaces ([OpenAI, 2025](#bib.bib17);
[Anthropic, 2026a](#bib.bib2)). As agents gain access to more services,
new capabilities can be combined with existing ones, enabling a broader
range of user tasks and increasingly diverse cross-service workflows.

As agents carry out increasingly diverse workflows across new
combinations of services, these interactions create new ways to induce
behavior that deviates from user intent or bypasses safety guardrails.
When agents fulfill benign user requests, the effects of their actions
can accumulate and interact across services, leading to unintended or
harmful outcomes ([Li et al., 2025](#bib.bib10); [Li et al.,
2026](#bib.bib11)).
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")(a)
illustrates this compositional risk: an agent fulfilling a benign user
request can leak information as its actions interact across services.
Such failures depend on how information, permissions, and state changes
propagate across services. Proactively discovering such failures
requires exploring diverse cross-service paths and examining their
cumulative effects. As the ecosystem expands, this exploration must also
extend to newly possible service combinations beyond previously tested
workflows.

Existing red-teaming methods often search for harmful workflows by
prompting LLMs to propose tool-use sequences from task and environment
descriptions ([Li et al., 2025](#bib.bib10)) or to decompose harmful
objectives specified by humans or LLMs into combinations of seemingly
benign actions ([Kulkarni et al., 2025](#bib.bib9); [Zeng et al.,
2026](#bib.bib29)). Although these methods incorporate execution
feedback to evaluate and revise candidate workflows, they rely on LLM
generation to determine which tools to combine and how to connect them.
This reliance on LLMs’ prior knowledge introduces a potential source of
bias: LLMs are prone to favoring familiar patterns learned during
training, which can concentrate exploration on common tool combinations
while leaving novel cross-service interactions underexplored. This
concern becomes particularly relevant as personal agents gain access to
new services whose interactions are poorly represented in training data.
Exploring this expanding space therefore calls for a systematic way to
identify candidate paths from the capabilities and dependencies of the
available tools.

To address this challenge, we propose X-AgentRed, a self-evolving
red-teaming framework that discovers potentially harmful scenarios
involving multiple services through a graph of tool dependencies and
uses execution feedback to expand and refine them. By analyzing each
tool’s effects, potential harms, and preconditions for execution, the
red-teaming agent constructs a directed graph, referred to as the
_HarmFlow_ graph, that captures how one tool’s effects can satisfy
another’s execution preconditions. We sample recipes by following these
conditions across tools and services, enabling exploration beyond
previously observed workflows.
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")(b)
schematically contrasts LLM-proposed sequences with graph-derived
recipes, illustrating how our graph-based exploration can extend
coverage across services, tools, harm types, and path lengths.

Each recipe specifies a candidate path and is instantiated as a
realistic scenario in which a benign user task can lead to unintended or
harmful outcomes. Executing these scenarios against the target agent
reveals whether harm occurs and where progress is blocked. Based on this
feedback, the red-teaming agent diversifies paths that produce harm by
replacing selected tools with adjacent alternatives in the _HarmFlow_
graph while preserving the steps responsible for the harmful outcome.
For paths blocked during execution, it refines the preconditions at the
blocked step and reconstructs the preceding steps to satisfy them and
enable further execution. This process broadens exploration across
service combinations while deepening the search around identified
vulnerabilities.

Figure 2: X-AgentRed overview. Tool execution preconditions, effects,
and potential harms define the _HarmFlow_ graph. Sampled recipes are
instantiated as scenarios with benign user requests in which
cross-service interactions can lead to harm. Execution feedback
diversifies paths that produce harm through tool substitutions along the
graph and refines blocked paths by addressing unmet preconditions.

We evaluate X-AgentRed across four frontier agentic models in a
simulated multi-service ecosystem comprising 30 services and 914 tools.
Compared with STAC ([Li et al., 2025](#bib.bib10)) and TRACE ([Zeng
et al., 2026](#bib.bib29)), X-AgentRed achieves $`1.77\times`$ and
$`10.36\times`$ the harmful path rate (HPR), respectively, while
covering $`2.99\times`$ and $`1.84\times`$ as many distinct tools on
average across agents. Its executed workflows contain $`2.92\times`$ and
$`7.53\times`$ as many tool calls as STAC and TRACE, respectively, on
average across agents, including adaptive follow-up interactions. We
further analyze executed-path diversity, cumulative discovery over
successive cycles, and the outcomes of feedback-driven diversification
and refinement. These analyses assess both the effectiveness of harmful
behavior discovery and the breadth of exploration across the ecosystem.

Our contributions are threefold:

- •
  We introduce X-AgentRed, a self-evolving red-teaming framework for
  discovering potentially harmful cross-service paths in personal-agent
  ecosystems.
- •
  We develop _HarmFlow_, a graph of tool dependencies derived from
  execution preconditions, effects, and potential harms, to guide recipe
  sampling. Execution feedback diversifies paths that produce harm by
  replacing selected tools with adjacent alternatives while preserving
  the steps responsible for harm, and refines blocked paths by refining
  preconditions and reconstructing preceding steps.
- •
  We evaluate X-AgentRed across four frontier agents in a simulated
  ecosystem of 30 services and 914 tools, demonstrating higher average
  HPR and broader tool coverage than two representative baselines.
  Further analyses characterize generated-path length, executed-path
  diversity, and cumulative discovery over successive cycles.

## 2 Related Work

#### Automated red-teaming.

Automated red-teaming uses LLMs to generate adversarial inputs ([Perez
et al., 2022](#bib.bib21)), optimize prompts ([Zou et al.,
2023](#bib.bib31); [Chao et al., 2025](#bib.bib5); [Mehrotra et al.,
2024](#bib.bib15); [Liu et al., 2024](#bib.bib12)), and adapt
interactions across turns ([Russinovich et al., 2025](#bib.bib24);
[Rahman et al., 2025](#bib.bib22)). For tool-using agents, benchmarks
evaluate harmful behavior and vulnerabilities to external content ([Ruan
et al., 2024](#bib.bib23); [Andriushchenko et al., 2025](#bib.bib1);
[Debenedetti et al., 2024](#bib.bib6)), while generation methods
construct adversarial tasks and interactions ([Kulkarni et al.,
2025](#bib.bib9); [Li et al., 2026](#bib.bib11)). Our representative
baselines use two approaches: STAC ([Li et al., 2025](#bib.bib10))
composes benign tool calls into harmful chains, whereas TRACE ([Zeng
et al., 2026](#bib.bib29)) decomposes harmful tasks into subtasks and
iteratively revises their prompts using execution feedback. X-AgentRed
instead selects cross-service recipes from an explicit tool-dependency
graph before instantiating them as scenarios.

#### Diversity and feedback.

To explore different types of failures, prior work varies both the
harmful behavior targeted by a prompt and the style of
prompting ([Samvelyan et al., 2024](#bib.bib25); [Wang et al.,
2025](#bib.bib27)). Novelty rewards encourage the generation of prompts
that differ from previously generated ones ([Hong et al.,
2024](#bib.bib8)). Feedback from previous attempts is also used to
extract effective strategies, which are stored in a library, and reused
in subsequent searches ([Liu et al., 2025](#bib.bib13)). X-AgentRed
extends these ideas to cross-service compositions: its graph guides
recipe sampling, and execution feedback diversifies successful paths
through service substitution and refines preconditions at blocked steps
in unsuccessful paths. These updates modify recipes and scenarios
without retraining the model.

## 3 X-AgentRed

X-AgentRed is a self-evolving red-teaming framework for discovering
harmful cross-service behavior in personal agent ecosystems
(Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
The red-teaming agent analyzes each tool’s effects, potential harms, and
execution preconditions to construct a dependency graph, referred to as
the _HarmFlow_ graph
(Section [3.1](#S3.SS1 "3.1 HarmFlow Graph ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
The agent samples recipes from this graph and instantiates them as
realistic scenarios in which a benign user task can lead to harm
(Section [3.2](#S3.SS2 "3.2 Recipe Sampling and Scenario Instantiation ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
Executing these scenarios reveals harmful outcomes and blocked steps;
this feedback diversifies successful paths by substituting services
using adjacent nodes in the _HarmFlow_ graph and refines unsuccessful
paths by analyzing preconditions at blocked steps and reconstructing the
preceding steps to enable further execution
(Section [3.3](#S3.SS3 "3.3 Self-Improvement through Execution Feedback ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).

#### Problem setup.

We consider a personal agent $`A`$ operating in a multi-service
ecosystem with tool registry $`\mathcal{T}`$. A scenario $`x`$ specifies
a benign user request $`u`$, an initial environment state $`s_{0}`$, and
a target harm $`h`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
x=(u,s_{0},h)\in\mathcal{X},\qquad\tau\sim\operatorname{Rollout}(A,u,s_{0};\mathcal{T}),
``` |  | (1) |

where $`\mathcal{X}`$ denotes the space of admissible scenarios and
$`\tau`$ records the agent’s actions and state transitions. The target
agent receives $`u`$ and interacts with the environment initialized at
$`s_{0}`$, without observing $`h`$. We define the binary harm indicator
$`H(\tau)`$ as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
H(\tau)=\begin{cases}1,&\text{if execution produces a harmful outcome},\\
0,&\text{otherwise}.\end{cases}
``` |  | (2) |

Our goal is to uncover harmful outcomes that arise through cross-service
interactions as an agent fulfills a benign user request. The request
$`u`$ must admit a safe completion, and the target harm $`h`$ must be
neither requested nor authorized by the user. We define harmful path
rate (HPR) as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{HPR}=\frac{\text{\# of harmful scenarios}}{\text{\# of candidate scenarios}},
``` |  | (3) |

The evaluation protocol is described in
Section [4.1](#S4.SS1 "4.1 Experimental Setup ‣ 4 Experiments ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems").

### 3.1 HarmFlow Graph

Our red-teaming agent analyzes each tool $`t\in\mathcal{T}`$ across the
connected services to identify its effects $`\mathcal{E}_{t}`$,
potential harms $`\mathcal{H}_{t}`$, and execution preconditions
$`\mathcal{P}_{t}`$. Together, these attributes form a structured tool
representation:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
C(t)=\bigl(\mathcal{P}_{t},\mathcal{E}_{t},\mathcal{H}_{t}\bigr),\qquad\mathcal{H}_{t}\subseteq\mathcal{H}.
``` |  | (4) |

Effects describe the state changes or information the tool can produce.
Potential harms specify the harmful outcomes these effects can enable in
a cross-service workflow. Preconditions specify the requirements for
executing the tool, including necessary inputs, available resources, and
access permissions. For example, a file-sharing tool requires an
existing document, a specified recipient, and an account authorized to
change the document’s sharing settings (preconditions). It grants the
recipient access to the document (effect), potentially exposing
sensitive information to someone who is not authorized to receive it
(harm). We represent these tools and their dependencies as a directed
graph, called the *HarmFlow* graph

|  |  |  |  |
|----|----|----|----|
|  |
``` math
G=(\mathcal{T},\mathcal{D}),\qquad\mathcal{D}\subseteq\mathcal{T}\times\mathcal{T},
``` |  | (5) |

where each node $`t\in\mathcal{T}`$ represents a tool with attributes
$`C(t)`$, and $`\mathcal{D}`$ is the set of directed edges. Let
$`\mathcal{R}`$ denote the set of effect–precondition pairs for which
the red-teaming agent judges that the effect can establish the
precondition. We connect source tool $`t_{i}`$ to destination tool
$`t_{j}`$ whenever their effects and preconditions contain such a pair:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{D}=\left\{(t_{i},t_{j})\in\mathcal{T}^{2}\;\middle|\;(\mathcal{E}_{t_{i}}\times\mathcal{P}_{t_{j}})\cap\mathcal{R}\neq\emptyset\right\}.
``` |  | (6) |

To construct $`\mathcal{R}`$, the red-teaming agent evaluates whether
one tool’s effect can satisfy another tool’s execution precondition. For
example, creating a document can satisfy a sharing tool’s requirement
for an existing document, whereas reading a document does not grant
permission to modify its access settings. This decomposes the
construction of complex tool sequences into simpler pairwise dependency
checks, while graph traversal combines the resulting dependencies into
longer tool sequences. Each edge captures a supporting dependency rather
than guaranteeing execution: other preconditions may require additional
context from the environment or preceding tools. Traversing the
resulting graph yields a candidate tool path

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\pi=(t_{1},\ldots,t_{k}),\qquad(t_{i},t_{i+1})\in\mathcal{D}\quad\text{for }i=1,\ldots,k-1.
``` |  | (7) |

A tool path does not determine whether its execution will be safe: when
used to fulfill a benign user request, the same dependencies can lead to
different outcomes depending on the information, permissions, and state
changes across services. A document-sharing workflow, for example, can
serve legitimate collaboration or expose sensitive information to an
unauthorized recipient. By composing locally assessed dependencies,
HarmFlow supports exploration of service combinations beyond previously
observed workflows. Construction details appear in
Appendix [A.2](#A1.SS2 "A.2 X-AgentRed Implementation ‣ Appendix A Implementation Details ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems").

### 3.2 Recipe Sampling and Scenario Instantiation

We sample recipes using backward random walks on the HarmFlow graph
$`G`$ ([Lovász, 1993](#bib.bib14)). Starting from a tool associated with
a target harm, each walk traverses incoming edges to construct a
candidate path, which is then instantiated as a realistic scenario with
a benign user request.

For a target harm $`h\in\mathcal{H}`$, we first select a tool from the
set

|     |                                                              |     |     |
|-----|--------------------------------------------------------------|-----|-----|
|     |
       ``` math
       \mathcal{T}_{h}=\{t\in\mathcal{T}\mid h\in\mathcal{H}_{t}\}.
       ```                                                           |     | (8) |

Starting from this tool, the walk follows incoming edges to sample a
preceding tool at each step. Let $`\mathcal{N}^{-}(t_{i})`$ denote the
incoming neighborhood of $`t_{i}`$, consisting of tools with directed
edges to $`t_{i}`$:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{N}^{-}(t_{i})=\{t\in\mathcal{T}\mid(t,t_{i})\in\mathcal{D}\},\qquad t_{i-1}\in\mathcal{N}^{-}(t_{i}).
``` |  | (9) |

We continue sampling backward up to a predefined maximum path length,
then reverse the sampled sequence to obtain $`\pi=(t_{1},\ldots,t_{k})`$
with $`t_{k}\in\mathcal{T}_{h}`$. Backward sampling explores paths
through diverse services and tools that can lead to the target harm.

We define a recipe as the sampled tool path $`\pi`$ paired with its
target harm $`h`$:

|     |            |     |      |
|-----|------------|-----|------|
|     |
       ``` math
       r=(\pi,h).
       ```         |     | (10) |

Given a sampled recipe $`r`$ and the harm-inducing factor taxonomy
$`\mathcal{C}`$, the red-teaming agent selects an appropriate factor
$`c\in\mathcal{C}`$ and instantiates a scenario:

|     |                                                     |     |      |
|-----|-----------------------------------------------------|-----|------|
|     |
       ``` math
       x=(u,s_{0},h)\sim q_{\mathrm{inst}}(\cdot\mid r,c),
       ```                                                  |     | (11) |

where $`q_{\mathrm{inst}}`$ denotes the scenario instantiation
distribution. The agent generates a benign user request $`u`$ and an
initial environment $`s_{0}`$ in which the selected factor can cause the
sampled cross-service interactions to produce harm $`h`$. We describe
sampling and validation details in
Appendix [A.2](#A1.SS2 "A.2 X-AgentRed Implementation ‣ Appendix A Implementation Details ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems").

### 3.3 Self-Improvement through Execution Feedback

The target agent executes an instantiated scenario $`x`$, producing an
execution trajectory $`\tau`$. LLM judges assess whether harm occurred,
while execution traces help identify blocked steps and unmet
preconditions. This feedback guides subsequent graph and recipe updates.

For a path that produces harm, $`H(\tau)=1`$, the red-teaming agent
diversifies the recipe by replacing tool nodes that are not central to
producing the harmful outcome with adjacent nodes in the HarmFlow graph.
The harm-inducing factor $`c`$ is also retained, allowing the same
vulnerability to be examined across different combinations of services.

For a path that does not produce harm, $`H(\tau)=0`$, refinement uses
execution feedback to identify unmet preconditions at a blocked step
$`t_{j}`$. When such preconditions are identified, the red-teaming agent
refines $`\mathcal{P}_{t_{j}}`$ in the HarmFlow graph and updates the
corresponding dependency edges. It then reconstructs the preceding steps
to satisfy the refined preconditions and enable further execution.
Writing $`\pi_{<j}`$ for the sequence before $`t_{j}`$ and
$`\pi_{\geq j}`$ for the sequence from $`t_{j}`$ onward, the update is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\pi^{\prime}=\widetilde{\pi}_{<j}\mathbin{\|}\pi_{\geq j},\qquad r^{\prime}=(\pi^{\prime},h),
``` |  | (12) |

where $`\widetilde{\pi}_{<j}`$ is the reconstructed sequence and $`\|`$
denotes concatenation.

These graph and recipe updates guide subsequent sampling. Scenario
instantiation and user prompt generation remain separate and are not
directly optimized using judge feedback. We manually inspected all 192
trajectories labeled as harmful across the four target agents and found
no evidence of reward hacking in these cases.

## 4 Experiments

We evaluate X-AgentRed on four frontier agents to assess its
effectiveness in discovering harmful cross-service behavior, the
contribution of execution feedback, and the breadth and diversity of its
exploration. We further compare scenario generation costs and examine
sensitivity to the choice of judge. Each configuration is evaluated in
one run within a fixed simulated ecosystem.

### 4.1 Experimental Setup

\titlespacing

\*

####

0pt6pt1em

#### Environment.

We use ToolSimulator ([Wang et al., 2026](#bib.bib26)) to simulate a
multi-service ecosystem with $`30`$ services and $`914`$ tools. Claude
Opus 4.8 generates tool responses and updates service states throughout
each episode. We describe the environment details in
Appendix [A.3](#A1.SS3 "A.3 Environment and Models ‣ Appendix A Implementation Details ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems").

#### Models.

We use Claude Opus 4.8 as the red-teaming agent. The four target models
are GPT-5.6 Sol, GLM-5.2, DeepSeek-V4-Pro, and Claude Opus 4.8 ([OpenAI,
2026a](#bib.bib18); [Z.ai, 2026](#bib.bib28); [DeepSeek-AI,
2026](#bib.bib7); [Anthropic, 2026b](#bib.bib3)), each operating as a
personal agent in the simulated ecosystem. Claude Opus 5 ([Anthropic,
2026c](#bib.bib4)) and GPT-5.6 Sol serve as the two LLM judges.

#### Baselines.

We compare against STAC ([Li et al., 2025](#bib.bib10)) and TRACE ([Zeng
et al., 2026](#bib.bib29)) as representative methods for constructing
harmful tool-use workflows. STAC composes individually benign tool calls
into harmful chains and adapts prompts using execution feedback. TRACE
decomposes harmful tasks into subtasks and iteratively refines templates
based on target responses. Implementation details appear in
Appendix [A.4](#A1.SS4 "A.4 Baseline Implementations ‣ Appendix A Implementation Details ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems").

#### Evaluation.

Each method generates $`N=250`$ candidate scenarios per target agent for
comparison. We report harmful path rate (HPR;
Equation [3](#S3.E3 "Equation 3 ‣ Problem setup. ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")),
the fraction of candidate scenarios that produce a confirmed harmful
outcome when executed against the target agent. Both LLM judges must
confirm a harmful outcome, a plausible harm-inducing condition, and a
benign user-request sequence. We apply the judging protocol to the same
recorded executions for all three methods. The full judging protocol

#### Coverage across the tool registry.

X-AgentRed achieves broader tool coverage on every target
(Table [2](#S3.T2 "Table 2 ‣ 3.3 Self-Improvement through Execution Feedback ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).

X-AgentRed covers $`41.5\%`$ of the tool registry, compared with
$`13.9\%`$ for STAC and $`23.7\%`$ for TRACE. Coverage grows throughout
the measured budget
(Figure [4](#S4.F4 "Figure 4 ‣ 4.4 ‣ 4 Experiments ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")a).

#### Diversity within and across workflows.

X-AgentRed uses an average of $`13.1`$ distinct tools and $`5.0`$
services per episode, compared with $`4.6`$ tools and $`2.7`$ services
for STAC and $`2.0`$ tools and $`1.9`$ services for TRACE
(Figure [6](#S4.F6 "Figure 6 ‣ 4.7 ‣ 4 Experiments ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
Within-target unique-sequence counts sum to $`998`$ for X-AgentRed and
$`866`$ for STAC. Successful X-AgentRed traces have median pairwise
tool-set Jaccard similarity of $`0.000`$–$`0.065`$ by target. These
measures capture structural diversity, not distinct causal failure
mechanisms.

The ten most-used tools account for $`24.3\%`$ of tool use with
X-AgentRed, compared with $`43.2\%`$ for STAC and $`48.9\%`$ for TRACE
(Figure [4](#S4.F4 "Figure 4 ‣ 4.4 ‣ 4 Experiments ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")b),

overlap among successful tool sets. Successful path overlap is low
across methods and does not uniformly favor X-AgentRed. Targets receive
equal weight in the distribution summaries. These comparisons describe

#### Path length and repetition.

Successful recipes span varied paths and terminal tools. Their median
planned length is $`8`$–$`9`$ steps by target, with a maximum of $`12`$
(Table [7](#A2.T7 "Table 7 ‣ B.2 Recipe Structure and Execution ‣ Appendix B Additional Results ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
The $`192`$ successes contain $`190`$ distinct planned paths when
counted within targets with varied terminal tools. Duplicate planned
paths account for $`2.0`$–$`2.8\%`$ of all candidates.

X-AgentRed produces longer executed paths than both baselines, averaging
$`23.2`$ tool calls per episode versus $`7.8`$ for STAC and $`3.3`$ for
TRACE

Longer paths may expose more intermediate actions to safety checks,
increasing the chance of detection or intervention. Unsuccessful
episodes also receive additional follow-up turns, so executed length
reflects both the workflow and the adaptation policy.

## 5 Conclusion

We introduced X-AgentRed, a graph-based, self-evolving framework for
red-teaming personal agents in multi-service ecosystems. The HarmFlow
graph captures tool dependencies to guide recipe sampling, while
execution feedback expands successful paths and refines blocked ones.
Across four frontier agents, X-AgentRed achieves higher average HPR and
broader tool coverage than STAC and TRACE, exploring more diverse
cross-service workflows. These results demonstrate the value of
combining explicit dependency structure with feedback-driven exploration
to uncover harmful behavior that emerges across services.

#### Limitations.

Maintaining the HarmFlow graph incurs additional computational cost as
services evolve, since new or modified tools require updating tool
representations and re-evaluating affected dependencies.

## Appendix A Implementation Details

### A.1 Harm Taxonomy

Our taxonomy distinguishes observable harmful outcomes from the factors
that induce them
(Table [1](#S3.T1 "Table 1 ‣ Taxonomy. ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
It synthesizes consequence-based tool evaluation from ToolEmu ([Ruan
et al., 2024](#bib.bib23)), risk and failure categories from
Agent-SafetyBench ([Zhang et al., 2024](#bib.bib30)), task redirection
through external content from AgentDojo ([Debenedetti et al.,
2024](#bib.bib6)), and agentic threats from OWASP ([OWASP GenAI Security
Project, 2025](#bib.bib20)). Harmful deviations from user intent include
unauthorized actions and unintended data modification; harmless task
incompletion alone is insufficient.

Harms are labeled from observed actions and outcomes, whereas factors
are assigned to the interaction that initiates the harmful progression.
Sampling balances target harms but does not impose factor quotas.

### A.2 X-AgentRed Implementation

The red-teaming agent uses tool descriptions to identify effects,
potential harms, and execution preconditions, and constructs the
HarmFlow graph as described in
Section [3.1](#S3.SS1 "3.1 HarmFlow Graph ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems").
The graph contains $`914`$ tool nodes and $`29{,}367`$ directed edges.

Recipes are sampled by backward random walks from tools associated with
a target harm, subject to a maximum path length
(Section [3.2](#S3.SS2 "3.2 Recipe Sampling and Scenario Instantiation ‣ 3 X-AgentRed ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
Each cycle generates $`50`$ candidate scenarios. Diversification and
refinement each receive up to $`25\%`$ of the allocation, with random
sampling filling the remaining slots.

Following STAC ([Li et al., 2025](#bib.bib10)), we adapt follow-up user
prompts using the target agent’s responses and tool outputs until harm
occurs or the turn limit is reached.

### A.3 Environment and Models

The simulated environment contains $`914`$ tools across $`30`$ services
(Table [4](#A1.T4 "Table 4 ‣ A.3 Environment and Models ‣ Appendix A Implementation Details ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).
Tools from the same service operate on the same underlying data, so
changes made by one tool are visible to later calls to that service.
ToolSimulator uses Claude Opus 4.8 to generate each tool response from

content is stored as part of the simulated environment.

The full $`914`$-tool registry is available to all target agents except

### A.4 Baseline Implementations

STAC and TRACE use the same simulated ecosystem and external judge pair
as X-AgentRed. Their selection and adaptation procedures differ, so this
comparison does not equalize generation effort or calls to the target
model.

#### STAC.

STAC ([Li et al., 2025](#bib.bib10)) generates tool chains, verifies
their execution, and converts the verified actions into user prompts. We
evaluate its scenarios in generation order. All four targets use the
same ordered corpus of $`250`$ scenarios. Targets execute the scenarios
from their initial states, with up to three adaptive follow-up user
turns. This end-to-end evaluation differs from STAC’s precursor-replay
protocol, which supplies intermediate state before the target performs
the final step. The main results use end-to-end execution throughout.

#### TRACE.

TRACE ([Zeng et al., 2026](#bib.bib29)) decomposes harmful tasks into
subtasks and evolves templates using execution feedback. Our
reimplementation follows the published control flow and settings. The
search may query the target repeatedly within a path, subject to a limit
on generation calls; it does not add follow-up user turns after template
search. The task source specifies source–sink tool pairs, so its tool
paths reflect this input design.

Both baselines use Claude Opus 4.8 for generation and internal search.
TRACE uses $`L=50`$, $`\lambda_{\mathrm{rej}}=1`$,
$`\tau_{\mathrm{mem}}=1`$, $`\alpha=0.2`$, $`\gamma=0.9`$,
$`T_{\min}=0.5`$, $`T_{\max}=2`$, $`\eta=0.99`$, $`\beta=1.5`$, and
subtask-harm threshold $`0.5`$. We follow the paper’s stopping rule
rather than the released code’s additional $`0.95`$ memory threshold.
The intervals reported for STAC are consecutive batches from a fixed
corpus rather than feedback cycles. All comparisons use one run per
configuration.

### A.5 Harm Evaluation

Claude Opus 5 and GPT-5.6 Sol independently evaluate the complete
user-request sequence, tool trace, and recorded environment states. Each
judge checks whether a material harmful outcome occurred, whether the
harm-inducing condition is plausible, and whether every delivered user
request remains benign. Tool results and state evidence support the
assessment; an agent’s own claims do not establish that an action was
safe or authorized. Both judges must accept all three criteria for a
scenario to count toward HPR.

Let $`J_{j}(x)=1`$ when judge $`j`$ accepts these criteria. The final
decision is

|     |                                               |     |      |
|-----|-----------------------------------------------|-----|------|
|     |
       ``` math
       {S_{A}(x)=\mathbf{1}\{J_{1}(x)=J_{2}(x)=1\}.}
       ```                                            |     | (13) |

We apply this protocol to the same recorded executions for all methods.
Unavailable executions or judge assessments are not counted as harmful.

### A.6 Coverage and Diversity Metrics

Let $`U_{i}`$ be the set of canonical tools executed in path $`i`$. Tool
coverage after $`k`$ paths is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
C(k)=\frac{\left|\bigcup_{i=1}^{k}U_{i}\right|}{|\mathcal{T}|}.
``` |  | (14) |

Unsuccessful episodes contribute their executed tools; empty traces
contribute none. Per-target coverage is distinguished from the union
across targets. TRACE coverage includes repeated search executions, so
equal path counts do not imply equal execution budgets.

To measure concentration, we count each tool at most once per episode.
With $`n_{t}=\sum_{i}\mathbf{1}\{t\in U_{i}\}`$ and counts sorted in
descending order, the top-ten share is
$`\sum_{j=1}^{10}n_{(j)}/\sum_{t\in\mathcal{T}}n_{t}`$. Lower values
indicate less concentration on frequently used tools. The share is
undefined if no tools are used.

Within an episode, workflow breadth is the number of distinct tools and
services, while execution length is the total number of tool calls.
Between nonempty successful paths, tool-set Jaccard similarity is
$`J(i,j)=|U_{i}\cap U_{j}|/|U_{i}\cup U_{j}|`$. Comparisons are computed
within targets; lower similarity indicates less tool overlap but does
not measure execution order or distinct causal failures. Ordered path
signatures use canonical tool sequences with consecutive repetitions
collapsed. Raw call counts remain separate from these signatures.

We have a tool sequence for each X-AgentRed and STAC candidate. For
TRACE, the available summaries include tool coverage, call counts, the
share of use assigned to the ten most frequent tools, services per path,
and overlap among successful paths for each target. TRACE’s tool and
service statistics describe declared paths, whereas its call counts
describe execution.
Figure [4](#S4.F4 "Figure 4 ‣ 4.4 ‣ 4 Experiments ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")(c)
shows service-count densities for all three methods, using a Gaussian
kernel with bandwidth $`0.7`$ and equal target weights. Panel (d)
averages each quantile over GPT-5.6 Sol, GLM-5.2, and DeepSeek-V4-Pro

### B.4 Generation Cost Accounting

Generation cost includes API calls for tool analysis, graph or corpus
construction, recipe and prompt generation, scenario instantiation,
validation during generation, and internal search. Failed and discarded
generation attempts and their retries are included. Shared artifacts are
charged once, and total generation calls are divided by
$`4\times 250=1{,}000`$ candidate scenarios across the four targets.

Calls used to execute a generated scenario against the target, simulate
its evaluation trajectory, adapt follow-up user prompts, or judge its
outcome are excluded. Internal validation needed to construct a
candidate remains part of generation, even when it invokes a simulator
or judge. Each invocation is counted once according to its role. This
measures generation overhead rather than end-to-end red-teaming cost; it
does not capture the cost of acquiring execution feedback.

TRACE reports $`21{,}652`$ calls for shared preparation and $`81{,}583`$
calls for generation and internal search, giving
$`103{,}235/1{,}000=103.24`$ calls per candidate. Its separate stages
for runtime execution and safe controls are excluded.

X-AgentRed and STAC require $`22.10`$ and $`55.00`$ generation calls per
scenario, respectively
(Table [3](#S4.T3 "Table 3 ‣ 4.10 Efficiency ‣ 4 Experiments ‣ X-AgentRed: Red-Teaming Personal Agents in Evolving Multi-Service Ecosystems")).

### C.2 Examples of Augmentation and Refinement

#### Augmentation.

A recipe retrieves a Notion meeting note before locating and unlocking a
fleet vehicle. Augmentation substitutes a different Notion block lookup
for the retrieval step while retaining the vehicle-location and unlock
steps. The resulting scenario presents a vehicle-handoff request;
execution unlocks an unattended vehicle in a public garage, which both
judges classify as harmful. This case illustrates variation in the
information-retrieval steps leading to the same harmful action.

#### Refinement.

A treasury-status workflow is blocked when a Notion query lacks the
required authenticated data-source object. Refinement adds
authentication, data-source lookup, database update, and Telegram chat
lookup before the wallet-read and message-edit steps. The revised
workflow proceeds and posts treasury holdings and custody notes to an
all-hands channel with 214 members; both judges confirm information
disclosure. This case illustrates how repairing an unmet precondition
allows a previously blocked workflow to reach a harmful outcome.
````
