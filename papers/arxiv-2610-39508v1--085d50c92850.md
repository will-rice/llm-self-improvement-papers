# Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation

Chengyu Yang¹, Yunxiang Zheng¹, Zongzheng Li¹, Jiamei Li¹, Boxun Lan¹,
Xiaoyu Liu²,  
Xiaoyu Zhang¹, Xiaohong Chen¹, Ming Hu^(1,\*) Affiliation: ¹East China
Normal University, ²China University of Geoscience
Affiliation: ^(\*)Corresponding author

###### Abstract

Self-evolving agent skills enable AI agents to accumulate and refine
reusable procedural knowledge from interaction experience without
updating model parameters. However, since such skills are typically
represented as textual documents and executed through LLM reasoning,
even previously learned procedures must be repeatedly interpreted and
regenerated, introducing avoidable uncertainty into every execution. In
contrast, program execution is deterministic and independently
verifiable. Intuitively, transforming well-specified operations into
executable programs can reduce reliance on LLM reasoning and,
consequently, reduce execution uncertainty. Motivated by this intuition,
we introduce SkillCompiler, a self-evolving skill framework that
integrates programmatic compilation into the skill evolution process.
Specifically, SkillCompiler adopts an executability-aware skill
compilation strategy that decomposes skills into fine-grained
operations, analyzes their executability, and constructs hybrid skill
skeletons that retain LLM reasoning for context-dependent operations
while compiling well-specified ones into validated programs. To avoid
redundant program synthesis and enable executable knowledge to
accumulate across evolving skills, we further design a program asset
reuse mechanism that organizes validated programs as reusable assets,
retrieves existing implementations whenever applicable, and synthesizes
and verifies new programs only when necessary. Extensive experiments on
five benchmarks and six model families demonstrate that SkillCompiler
consistently outperforms state-of-the-art methods, achieving up to
32.33% improvement in task performance.

self-evolving agents, reusable skills, programmatic compilation,

## I Introduction

Large language model (LLM) agents have demonstrated strong capabilities
in reasoning, planning, tool use, and environment interaction, enabling
them to solve increasingly complex tasks, including information
retrieval, Web interaction, and interactive problem
solving \[[1](#bib.bib1), [2](#bib.bib2), [3](#bib.bib3),
[4](#bib.bib4), [5](#bib.bib5)\]. However, agents often need to
rediscover similar task-solving procedures when facing new tasks, even
when related experience has already been acquired. Agent skills provide
a natural way to preserve such experience as reusable procedural
knowledge, allowing agents to reuse previously acquired task-solving
procedures without updating the underlying language
model \[[6](#bib.bib6), [7](#bib.bib7), [8](#bib.bib8), [9](#bib.bib9),
[10](#bib.bib10)\]. Consequently, effectively accumulating and reusing
skills has become an important direction for improving agent
capabilities through interaction experience.

To continuously accumulate and refine reusable skills from interaction
experience, existing work has explored different strategies for skill
evolution. Existing approaches can be broadly classified into two
categories, i.e., skill content evolution and skill execution
augmentation. Specifically, skill content evolution improves reusable
procedural knowledge through trajectory distillation \[[9](#bib.bib9)\],
reflection-based revision \[[12](#bib.bib12)\], and validation-guided
skill optimization \[[10](#bib.bib10)\]. Skill execution augmentation
enhances how acquired skills are applied by reusing learned
workflows \[[17](#bib.bib17), [16](#bib.bib16)\], incorporating external
tool capabilities \[[5](#bib.bib5)\], or constructing executable
procedural representations \[[20](#bib.bib20), [21](#bib.bib21),
[19](#bib.bib19)\]. These methods enable agents to progressively improve
both the knowledge encoded in skills and the way such knowledge is
reused during task execution.

Although existing skill evolution methods can continuously accumulate
and refine reusable task-solving knowledge, they still face two
challenges in reliable and efficient skill reuse, i.e., execution
uncertainty and repeated capability construction. Specifically, ❶
executing an evolved skill still requires the agent to repeatedly
interpret retained knowledge, reconstruct intermediate decisions, and
generate corresponding actions through LLM reasoning. As a result, even
with an unchanged skill, repeated executions may follow different
reasoning paths and produce different outcomes. ❷ Reusable execution
capabilities discovered during skill evolution are often constructed for
individual skills or tasks and are not persistently organized for
subsequent reuse, leading to repeated generation and validation of
similar procedures across evolving skills. Therefore, how to reduce
execution uncertainty while efficiently accumulating and reusing
executable knowledge across skill evolution remains an important
problem.

Typically, LLM reasoning is inherently probabilistic, which makes the
execution of the same skill susceptible to different intermediate
decisions and outcomes across repeated runs. In contrast, executable
programs encode their inputs, control flow, and state transformations
explicitly, so the same operation follows a fixed execution procedure
under the same conditions rather than regenerating intermediate
decisions at each invocation. Intuitively, when an operation has
explicit inputs, well-defined execution logic, and checkable outputs,
its execution no longer needs to be repeatedly regenerated through LLM
reasoning. Instead, such operations can be realized as executable
programs, while LLM reasoning is retained for context-dependent or
difficult-to-formalize decisions. Moreover, once these programs are
validated, they can be persistently accumulated and reused across
evolving skills, avoiding repeated synthesis of the same executable
procedures.

Inspired by the above intuition, we propose SkillCompiler, a
self-evolving skill framework that transforms suitable reasoning
operations into deterministic executable programs as skills evolve.
Specifically, ① SkillCompiler adopts an executability-aware skill
compilation strategy to identify which skill operations can be reliably
transformed into executable programs while retaining LLM reasoning for
context-dependent decisions. ② To avoid redundant program synthesis and
enable executable knowledge to accumulate across evolving skills,
SkillCompiler integrates a program asset reuse mechanism that organizes
validated programs as reusable assets, retrieves compatible
implementations whenever available, and synthesizes and verifies new
programs only when necessary. In this way, SkillCompiler reduces
unnecessary LLM reasoning while preserving the flexibility required for
unresolved operations. The main contributions are summarized as follows.

- •
  We propose SkillCompiler, a self-evolving skill framework that
  progressively transforms suitable skill operations into deterministic
  executable programs. Its executability-aware compilation strategy
  identifies which operations can be reliably programmatized while
  retaining LLM reasoning for context-dependent decisions.
- •
  We design a program asset reuse mechanism that persistently
  accumulates, retrieves, and reuses validated executable programs
  across evolving skills, reducing redundant program synthesis and
  enabling executable knowledge to continuously grow through
  interaction.
- •
  We conduct extensive experiments on five benchmarks and six model
  families. The results show that SkillCompiler outperforms
  state-of-the-art methods, achieving up to 32.33% improvement in task
  performance.

## II Related Work

### II-A Experience Accumulation and Reusable Agent Skills

AI agents can improve subsequent task solving by retaining useful
experience from previous interactions without updating model parameters.
Reflexion \[[6](#bib.bib6)\] stores verbal feedback from previous
attempts to guide future decisions, while ExpeL \[[7](#bib.bib7)\]
extracts generalizable insights from collections of task experiences.
Agent Workflow Memory \[[17](#bib.bib17)\] induces recurring workflows
from trajectories and retrieves them to guide subsequent action
generation. Voyager \[[14](#bib.bib14)\] further accumulates executable
skills from successful environment interactions and refines them through
execution feedback.

### II-B Agent Skills Evolution

Existing work can be classified into _skill content evolution_ and
_skill execution augmentation_. Skill content evolution methods improve
the quality and transferability of reusable procedural knowledge by
refining skill representations from accumulated interaction experience.
For example, Trace2Skill \[[9](#bib.bib9)\] distills reusable lessons
from trajectories. EmbodiSkill \[[12](#bib.bib12)\] revises skills based
on execution evidence. SkillOpt \[[10](#bib.bib10)\] conducts
validation-guided optimization over natural-language skill documents.
Skill execution augmentation methods enhance how acquired skills are
carried out by introducing additional execution structures or
capabilities. For example, Agent Workflow Memory \[[17](#bib.bib17)\]
reuses learned workflows to guide subsequent action generation.
FlowEvo \[[16](#bib.bib16)\] reuses verified workflows as executable
skills. AutoTools \[[5](#bib.bib5)\] augments agent execution with
external tools. NSI \[[20](#bib.bib20)\],
SkillDisCo \[[21](#bib.bib21)\], and Agent Skill
Induction \[[19](#bib.bib19)\] construct more directly executable
procedural representations from interaction experience.

Different from existing skill evolution methods, SkillCompiler does not
merely attach reusable workflows, tools, or executable artifacts to
skill execution. Instead, it explicitly analyzes operation-level
executability within an evolving skill and selectively determines which
operations should remain under LLM reasoning and which should be
transformed into validated programs. To the best of our knowledge,
SkillCompiler is the first self-evolving skill framework that jointly
enables operation-level selective compilation and persistent reuse of
the resulting program assets across skill evolution.

## III Our SkillCompiler Approach

### III-A Overview

Fig. [1](#S2.F1 "Fig. 1 ‣ II-B Agent Skills Evolution ‣ II Related Work ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation")
presents the overall framework of SkillCompiler, which consists of five
major components, including the task analyzer, programmer, executor,
skill optimizer, and program asset manager. Task analyzer decomposes a
task into fine-grained operations, analyzes their executability, and
constructs a hybrid skill skeleton. Programmer realizes programmable
operations by retrieving existing implementations or synthesizing new
programs and validates them before integration. Executor applies the
resulting candidate skill by combining programmatic execution with
decisions from the target agent. Skill optimizer analyzes successful and
failed execution traces to refine the evolving skill. Program asset
manager maintains a program asset bank to support program retrieval,
updating, and reuse across skill evolution.

As shown in
Fig. [1](#S2.F1 "Fig. 1 ‣ II-B Agent Skills Evolution ‣ II Related Work ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation"),
the workflow of SkillCompiler mainly consists of three phases, i.e.,
executability-aware skill compilation, program asset reuse, and skill
optimization. The details of each phase are as follows:

- •
  Phase 1: Executability-aware skill compilation. Given a task, the Task
  Analyzer decomposes it into fine-grained operations, analyzes their
  executability, and organizes both programmatic and agent-guided
  operations into a hybrid skill skeleton. For operations selected for
  programmatic execution, the Programmer obtains validated
  implementations and incorporates them into the skeleton to form a
  candidate skill, while the remaining operations continue to rely on
  LLM reasoning.
- •
  Phase 2: Program asset reuse. Before synthesizing a new
  implementation, the program asset manager retrieves compatible
  programs from the Program Asset Bank and reuses them whenever
  applicable. Newly synthesized and validated programs are persisted as
  reusable assets for subsequent skills.
- •
  Phase 3: Skill optimization. The executor applies the candidate skill
  in the target environment and records the resulting execution traces
  and task feedback. If the skill successfully completes the task, the
  execution result is returned and the validated skill knowledge is
  retained for subsequent reuse. Otherwise, the Skill Optimizer analyzes
  the failed execution trace to identify problematic operations,
  guidance, or dependencies and generates an updated skill skeleton.
  Operations affected by the revision are returned to the preceding
  phases for executability analysis, program retrieval or synthesis, and
  validation before the updated skill is executed again.

### III-B Executability-Aware Skill Compilation

A skill may contain operations with different execution requirements.
Some operations depend on semantic understanding, contextual judgment,
or changing observations, while others follow explicit and repeatable
procedures. Executing all operations through LLM reasoning therefore
introduces unnecessary execution uncertainty, whereas compiling the
entire skill into a program may sacrifice the flexibility required for
context-dependent decisions. To address this issue, SkillCompiler
analyzes executability at the operation level and selectively transforms
suitable operations into executable programs.

#### III-B1 Operation Decomposition.

To identify the appropriate unit for selective compilation, the task
analyzer first decomposes the task and relevant skill knowledge into a
set of fine-grained operations. Each operation represents a locally
coherent capability that can be independently invoked and evaluated. We
represent an operation $`\kappa_{i}`$ using a 6-tuple operation contract
as follows:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\kappa_{i}=\langle I_{i},O_{i},\operatorname{pre}_{i},\operatorname{post}_{i},\operatorname{check}_{i},g_{i}\rangle,
``` |  | (1) |

where $`I_{i}`$ and $`O_{i}`$ denote the required inputs and expected
outputs, $`\operatorname{pre}_{i}`$ specifies the observable
preconditions, $`\operatorname{post}_{i}`$ describes the expected local
effects, $`\operatorname{check}_{i}`$ defines how these effects can be
verified, and $`g_{i}`$ contains reusable execution guidance.
Task-specific entities and values are instantiated only when the
operation is invoked, allowing the same operation to be reused across
different tasks.

#### III-B2 Operation Analysis.

After operation decomposition, the task analyzer determines whether each
operation can be reliably realized through programmatic execution. An
operation is considered programmatic when its inputs and outputs can be
explicitly represented, its execution procedure can be clearly
specified, its preconditions can be observed from the current
environment, and its resulting outputs or local effects can be
independently verified. In addition, the available tool interfaces
should support a bounded implementation of the operation. Operations
satisfying these requirements are selected for programmatic execution,
while operations involving unresolved inputs, context-dependent
decisions, or open-ended semantic reasoning remain agent-guided.

This analysis determines the execution mode of each operation before
constructing the skill. In particular, programmatic operations no longer
require the target agent to repeatedly generate their internal execution
procedures, while agent-guided operations retain LLM reasoning to
accommodate dynamic observations and contextual decisions. In this way,
SkillCompiler selectively moves well-specified operations from
probabilistic reasoning to deterministic execution without restricting
the flexibility of the entire skill.

#### III-B3 Skill Skeleton Construction.

Based on the executability analysis, the task analyzer organizes the
resulting operations into a hybrid skill skeleton. For a task $`x`$, the
instantiated skill skeleton is represented as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
S_{x}=\langle\mathcal{O}_{x},\sigma_{x},\mathcal{E}_{x},\beta_{x}\rangle,
``` |  | (2) |

where $`\mathcal{O}_{x}`$ contains the operation occurrences required by
the task, $`\sigma_{x}`$ specifies their execution order,
$`\mathcal{E}_{x}`$ records the data and prerequisite relations among
operations, and $`\beta_{x}`$ contains the current argument bindings.
Data relations connect the outputs of preceding operations to the inputs
of subsequent operations, while prerequisite relations specify the local
effects that must be established before an operation can be executed.

Both programmatic and agent-guided operations are organized in the same
skill skeleton. During construction, SkillCompilerchecks the
compatibility between operation interfaces and identifies the sources of
required inputs. Task-specific values that are unavailable during
construction remain unresolved in $`\beta_{x}`$ and are instantiated
according to actual observations during execution. Therefore, the skill
skeleton explicitly describes how deterministic programs and LLM
reasoning collaborate to accomplish a task while preserving their
respective execution requirements.

#### III-B4 Programming and Validation.

For each operation selected for programmatic execution,
SkillCompilerneeds to obtain a qualified executable realization before
incorporating it into the candidate skill. The programmer first attempts
to obtain an existing compatible implementation through the program
asset manager. When no qualified implementation is available, it
synthesizes a new program according to the operation contract, permitted
tool interfaces, and available execution evidence.

The synthesized program is validated in an isolated environment before
being used for task execution. Specifically, SkillCompilerchecks whether
the program can be successfully executed, whether its inputs and outputs
conform to $`I_{i}`$ and $`O_{i}`$, and whether the resulting local
effects satisfy $`\operatorname{post}_{i}`$ according to
$`\operatorname{check}_{i}`$. When validation fails, the observed errors
and check discrepancies are returned to the Programmer to guide program
repair. This synthesis, validation, and repair process continues until a
qualified implementation is obtained or the operation remains
agent-guided. Only validated programs are incorporated into the skill
skeleton to form the candidate skill, ensuring that LLM reasoning is
replaced only when the corresponding program can be independently
verified.

### III-C Program Asset Reuse

Although programmatic execution reduces repeated LLM reasoning,
repeatedly synthesizing and validating similar programs can introduce
additional overhead during skill evolution. In practice, different tasks
may contain operations with the same underlying capability, making their
executable implementations reusable across skills. To avoid redundant
program synthesis, SkillCompiler maintains validated programs in the
Program Asset Bank and preferentially reuses existing implementations
whenever compatible operations are encountered.

#### III-C1 Compatibility-Based Program Retrieval.

For each operation selected for programmatic execution, the program
asset manager first retrieves candidate programs according to the
semantic description and execution requirements of the operation.
Lexical similarity is used to identify potentially reusable
implementations, while their applicability is further determined
according to the operation contract. Specifically, compatible Skill
Skeletons are ranked by lexical similarity, while atomic skills are
ranked using lexical Dice similarity, historical utility, and activation
status:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
R(a,o)=\frac{2|\mathcal{T}(o)\cap\mathcal{T}(a)|}{|\mathcal{T}(o)|+|\mathcal{T}(a)|}+0.1\,u(a)+0.05\,\mathbf{1}[\mathrm{active}(a)],
``` |  | (3) |

where $`\mathcal{T}(\cdot)`$ denotes lexical term sets, $`u(a)`$ is the
historical utility of atomic skill $`a`$, and
$`\mathbf{1}[\mathrm{active}(a)]`$ indicates its active status.
Candidates are first filtered by capability and contract compatibility
before ranking.

Program realizations are located through explicit
Skill-Implementation-Program references. A retrieved program can be
reused only when its required inputs can be correctly bound, its
preconditions are satisfied, the current environment provides the
required interfaces, and its existing validation record remains
applicable to the current operation. Formally, the eligible programs are

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathcal{P}_{\mathrm{valid}}(a,x)=\{p\in\mathcal{P}(a):`$ | $`\displaystyle\mathrm{Bind}(p,x)\land\mathrm{Pre}(p,x)`$ |  | (4) |
|  |  | $`\displaystyle\land\mathrm{Env}(p,x)\land\mathrm{Cert}(p,x)\},`$ |  |  |

where $`\mathcal{P}(a)`$ contains the program realizations referenced by
skill $`a`$, and the predicates check argument binding, preconditions,
environment compatibility, and validation applicability, respectively.
Therefore, lexical similarity supports candidate discovery, while
interface and state compatibility determine whether a retrieved program
can be safely invoked.

When multiple implementations correspond to the same capability,
SkillCompiler retains their respective applicability conditions and
validation evidence. The program satisfying the current operation
contract and execution environment is selected for reuse. Automatic
invocation requires a unique eligible or preferred implementation;
otherwise, selection remains agent-guided. If no compatible
implementation is available, the operation is passed to the Programmer
for program synthesis and validation as described in
Section [III-B](#S3.SS2 "III-B Executability-Aware Skill Compilation ‣ III Our SkillCompiler Approach ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation").

### III-D Skill Optimization

After constructing the candidate skill, SkillCompiler executes it in the
target environment to evaluate whether the current skill can
successfully accomplish the task. During execution, the executor invokes
validated programs for programmatic operations and delegates the
remaining operations to the target agent. The resulting actions,
observations, argument bindings, program invocations, local checking
results, and final task feedback are recorded as execution traces for
subsequent skill updating.

#### III-D1 Trace-Based Skill Revision.

When task execution fails, the skill optimizer locates the failure by
comparing the actual execution of each operation with its operation
contract. If an operation produces the expected output and satisfies
$`\operatorname{check}_{i}`$, the operation is retained even when the
final task fails. Otherwise, SkillCompiler revises the corresponding
component according to the observed failure. An unsatisfied or overly
broad invocation condition leads to an update of
$`\operatorname{pre}_{i}`$. Incorrect information passed between
operations leads to changes in argument bindings or dependencies in the
skill skeleton. Incomplete execution guidance results in an update of
$`g_{i}`$. If a program fails to produce the expected effect specified
by $`\operatorname{post}_{i}`$, the corresponding program is sent back
for repair and validation. Therefore, skill revision is performed
locally according to operation-level execution evidence rather than
regenerating the entire skill from the failed task.

#### III-D2 Skill Merging and Updating.

The revised operations are further compared with existing operations in
the skill bank to reduce redundant skill knowledge. SkillCompiler first
determines whether two operations describe the same local capability and
then checks whether their operation contracts are compatible. Operations
with consistent input and output semantics, preconditions, expected
effects, and checking requirements are merged into a shared reusable
operation, while task-specific entities and values are abstracted
through parameterization and argument bindings. Operations with
different capability semantics or conflicting contracts remain separate.

Formally, for two operation contracts $`\kappa_{i}`$ and $`\kappa_{j}`$,
the merging criterion is expressed as

|  |  |  |  |  |
|----|----|----|----|----|
|  |  | $`\displaystyle\mathrm{Mergeable}(\kappa_{i},\kappa_{j})=\mathrm{SameCap}(\kappa_{i},\kappa_{j})`$ |  | (5) |
|  |  | $`\displaystyle\land\ \exists\,\pi:\bigwedge_{f\in\{I,O,\mathrm{pre},\mathrm{post},\mathrm{check}\}}\mathrm{Compat}\bigl(\pi(f_{i}),f_{j}\bigr).`$ |  |  |

Here, $`\mathrm{SameCap}`$ denotes shared capability semantics, $`\pi`$
aligns task-specific parameters, and $`\mathrm{Compat}`$ requires
semantically consistent contract fields under the alignment. Thus,
merging is permitted only when capability identity and contract
compatibility are both satisfied.

The resulting operations are reorganized into an updated skill skeleton.
If the update only changes agent-guided operations, the revised skeleton
can be directly used for the next execution. If the update changes a
programmatic operation, its implementation is retrieved again or
regenerated when necessary and subsequently validated before reuse. The
candidate skill is then executed in the target environment. A successful
execution confirms the current skill update with corresponding skill and
program resources retained, while another failure produces a new
execution trace for the next round of local revision.

## IV Experiments

In this section, we first introduce the experimental setup and evaluate
the performance of SkillCompiler against representative baselines. We
then investigate its execution reliability and resource consumption
through repeated-execution experiments and cost analysis. Finally,
ablation studies are conducted to assess the contributions of the key
components.

### IV-A Experimental Setup

Benchmarks and Models. We conduct experiments on five benchmarks,
including SearchQA \[[28](#bib.bib28)\], OfficeQA \[[29](#bib.bib29)\],
DocVQA \[[30](#bib.bib30)\], LiveMath \[[31](#bib.bib31)\], and
ALFWorld \[[32](#bib.bib32)\]. Specifically,
SearchQA \[[28](#bib.bib28)\] evaluates open-domain question answering,
while OfficeQA \[[29](#bib.bib29)\] and DocVQA \[[30](#bib.bib30)\]
focus on document understanding. LiveMath \[[31](#bib.bib31)\] assesses
mathematical reasoning, and ALFWorld \[[32](#bib.bib32)\] evaluates
long-horizon interactive task solving.
Table [I](#S3.T1 "TABLE I ‣ III-D2 Skill Merging and Updating. ‣ III-D Skill Optimization ‣ III Our SkillCompiler Approach ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation")
summarizes the training, validation, and test partitions of these
benchmarks. Furthermore, we consider six large language models,
including MiniMax-M3, Gemini-3.8-Flash, Qwen3.8-Flash,
DeepSeek-V4.1-Flash, Kimi-K2.6, and GLM-5.3-Flash.

Baselines. We compare our proposed method SkillCompiler with seven
baselines, including No Skill, Human Skill,
Trace2Skill \[[9](#bib.bib9)\], EvoSkill \[[13](#bib.bib13)\],
EmbodiSkill \[[12](#bib.bib12)\], GEPA \[[11](#bib.bib11)\], and
SkillOpt \[[10](#bib.bib10)\].

- •
  No Skill. The agent performs tasks without any skill guidance, relying
  solely on the underlying LLM.
- •
  Human Skill. The agent executes tasks using fixed human-written skills
  provided by SkillOpt without evolution.
- •
  Trace2Skill \[[9](#bib.bib9)\]. It distills reusable knowledge from
  execution trajectories and consolidates trajectory-level lessons into
  transferable skills.
- •
  EvoSkill \[[13](#bib.bib13)\]. It identifies capability gaps through
  failure analysis and iteratively generates or refines skills based on
  validation feedback.
- •
  EmbodiSkill \[[12](#bib.bib12)\]. It employs skill-aware reflection to
  distinguish skill deficiencies from execution failures, enabling
  targeted skill revisions.
- •
  GEPA \[[11](#bib.bib11)\]. It optimizes prompts through
  natural-language reflection on execution feedback and Pareto-based
  candidate selection.
- •
  SKillOpt \[[10](#bib.bib10)\]. It iteratively optimizes
  natural-language skills through bounded textual revisions, accepting
  updates only when validation performance improves.

Evaluation Protocol. All methods use the same task partitions, available
tools, benchmark evaluators, and inference settings within each
model–benchmark configuration. Main performance and cost results are
averaged over three independently seeds (42, 43, and 44). Persistent
skill states are selected before testing and remain frozen throughout
the test evaluation. For repeated-execution and ablation analyses, we
use the seed-42 skill states and execute each test task three times
under the same inputs and environment conditions.

Metrics. Task performance is evaluated using exact match (EM) where
applicable and benchmark-specific scores otherwise, including success
rate (SR) for ALFWorld. Execution reliability is assessed through
outcome instability and execution-path consistency, while resource
consumption is measured by model token usage and the number of model
calls.

### IV-F Discussion

Empirical Implications.  The performance gains vary across benchmarks,
with larger improvements on LiveMath and OfficeQA than on SearchQA and
DocVQA. This suggests that selective compilation is particularly
beneficial when tasks contain recurring operations with explicit inputs,
well-defined procedures, and verifiable effects. In contrast, tasks
dominated by context-dependent interpretation offer fewer opportunities
to replace LLM reasoning with executable procedures.

Limitations. SkillCompiler relies on identifiable operation boundaries,
observable preconditions, and independently checkable effects.
Consequently, ambiguous or context-dependent decisions remain under LLM
control, meaning that compilation reduces rather than eliminates
execution uncertainty. Moreover, local validation establishes
correctness only under the tested inputs and environment states, without
guaranteeing generalization to unseen conditions. The benefits of
persistent program reuse also depend on contract compatibility and
sufficient reuse to amortize synthesis and validation costs. Finally,
our evaluation of SkillCompiler focused primarily on controlled
benchmark environments, and its effectiveness across a broader range of
tasks and in dynamic web environments remains to be investigated.

## V Conclusion

SkillCompiler integrates operation-level compilation into skill
evolution. Its executability-aware strategy combines validated programs
and context-dependent reasoning within hybrid Skill Skeletons, while
persistent program assets support reuse and trace-driven Optimization.
Experiments across five benchmarks and six model families show higher
mean task performance. Fixed-bank repetitions on LiveMath and ALFWorld
additionally show fewer outcome reversals. Resource savings vary by
baseline, while ALFWorld ablations identify the contributions of
programmatic execution, explicit operation dependencies, and
Optimization.

## Appendix A Metric Definitions

Effectiveness and reporting units.  For method $`m`$, learning run
$`s`$, and task $`t`$, let $`z_{m,s,t}`$ be the score returned by the
benchmark evaluator, expressed on $`[0,1]`$ when the native score is
reported as a percentage. The per-run score is

|     |                                                |     |     |
|-----|------------------------------------------------|-----|-----|
|     |
       ``` math
       S_{m,s}=\frac{100}{|T|}\sum_{t\in T}z_{m,s,t}.
       ```                                             |     | (6) |

EM and native binary task-success metrics have $`z\in\{0,1\}`$; any
native continuous score keeps its own name and interpretation. The
four-benchmark main table reports arithmetic means over independent
learning runs. Its Avg column is the unweighted mean of SearchQA,
OfficeQA, DocVQA, and LiveMath, and does not pool tasks across domains.
ALFWorld success rate is reported separately. Repeated evaluations of
one frozen bank form a separate replication axis. Secondary metrics are
not converted into binary accuracy by an added threshold.

Repeated outcomes.  For a fixed bank and a binary correctness or success
signal, let $`y_{t,k}\in\{0,1\}`$ be the outcome of repetition
$`k\in\{1,\ldots,K\}`$ on task $`t`$. The following expressions are
rates; percentages multiply them by 100:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathrm{RSR}@K`$ | $`\displaystyle=\frac{1}{|T|}\sum_{t\in T}\prod_{k=1}^{K}y_{t,k},`$ |  | (7) |
|  | $`\displaystyle\mathrm{EIR}@K`$ | $`\displaystyle=\frac{1}{|T|}\sum_{t\in T}\mathbf{1}\!\left[0<\sum_{k=1}^{K}y_{t,k}<K\right].`$ |  | (8) |

Repeated-run EM or SR averages all $`|T|K`$ binary outcomes. EIR is the
fraction of tasks exhibiting correctness flips; RSR is the supplementary
fraction solved in every repetition. Both use tasks as their
denominator, so the $`K`$ repetitions are not counted as independent
tasks.

Paths.  Let $`A_{t,k}`$ be the canonical sequence of environment
actions. Canonicalization removes method-internal bookkeeping, retains
semantically relevant arguments, and expands environment calls inside
programs. Restoration-discarded actions are excluded from the accepted
path but remain in raw cost. With sequence Levenshtein distance $`d`$,
define

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\operatorname{sim}(A,B)`$ | $`\displaystyle=1-\frac{d(A,B)}{\max\{|A|,|B|,1\}},`$ |  | (9) |
|  | $`\displaystyle\mathrm{APS}@K`$ | $`\displaystyle=\frac{1}{|T|}\sum_{t\in T}\frac{2}{K(K-1)}\sum_{i<j}\operatorname{sim}(A_{t,i},A_{t,j}),`$ |  | (10) |
|  | $`\displaystyle\mathrm{EPR}@K`$ | $`\displaystyle=\frac{1}{|T|}\sum_{t\in T}\mathbf{1}[A_{t,1}=\cdots=A_{t,K}].`$ |  | (11) |

These formulas are applied to workloads with a meaningful action
sequence. A direct answer with no such sequence does not receive an
artificial perfect path score. Success-conditioned APS averages pairs in
which both executions succeed, first within each eligible task and then
across eligible tasks.

Resource variability.  For nonnegative cost quantity $`q_{t,k}`$, let
$`\bar{q}_{t}`$ and $`s_{t}(q)`$ be its mean and sample standard
deviation across repetitions. For $`\bar{q}_{t}>0`$,

|     |                                                       |     |      |
|-----|-------------------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{CV}_{q}(t)=100\,\frac{s_{t}(q)}{\bar{q}_{t}}.
       ```                                                    |     | (12) |

All-zero observed quantities have CV zero and are counted separately;
missing quantities are excluded with their coverage stated. Mean
task-level CV is reported with absolute mean usage. Failed episodes
remain in the resource sample.

Program execution and reuse.  For seed $`s`$, let $`T_{s}`$ denote the
test tasks and $`K_{s}`$ the frozen persistent Bank. Persistent Program
Coverage (PPC) is the fraction of tasks in $`T_{s}`$ with at least one
actually started invocation of a Program from $`K_{s}`$. A Program
mentioned only in a plan, or synthesized temporarily for the current
test task, does not contribute to PPC.

Consumed Program Outputs (CPO) reports a conservative, trace-confirmed
lower bound on downstream consumption of Program results. A result
contributes positive evidence only when its use by a subsequent
operation, output binding, or accepted environment effect can be traced;
a mere invocation or recorded return is insufficient. Cases without a
verifiable consumption link are not inferred to be consumed. The
reported lower bound is calculated within each seed before averaging.

Cross-Skill Reuse (CSR) is the fraction of actually used persistent
Program versions that are invoked by at least two distinct Skill
Skeletons. Multiple task instances of the same Skeleton do not by
themselves establish cross-skill reuse. Program Invocation Success (PIS)
is the number of invocations recorded as successful divided by all
actually started Program invocations; invocation success alone does not
establish final task correctness or universal semantic validity.

Program Action Share (PAS) is the ratio of canonical environment-action
indices executed inside Program spans to all canonical
environment-action indices. Program-internal environment actions are
expanded, and the numerator is a union of indices so that nested
bookkeeping does not double-count an action. Restoration-discarded
actions are excluded from the accepted path but retained in cost
accounting. Computation-only Programs with no environment action are
captured by Program coverage rather than PAS.

For ALFWorld, the numerator/denominator pairs for CSR across seeds 42,
43, and 44 are $`6/11`$, $`7/14`$, and $`6/10`$; for PIS they are
$`690/807`$, $`641/713`$, and $`698/766`$; and for PAS they are
$`1078/1209`$, $`979/1178`$, and $`1034/1163`$, respectively. Each
reported percentage is calculated per seed and then averaged equally
across the three seeds. PPC is $`134/134`$ for each seed; the reported
CPO values are lower bounds.

Graph Construction Coverage (GCC) is the fraction of tasks that enter an
explicit nontrivial reusable or recomposed Skill Skeleton, excluding the
one-node dynamic fallback. An LLM-free task requires no model request
throughout the task execution; a Program identifier in the plan does not
suffice.

Statistical comparisons.  Paired task-level differences use the same
physical task identities. A task bootstrap resamples tasks while keeping
their repeated executions together; it does not treat three executions
of a task as three independent samples. Independent learned banks form a
separate replication axis. Binary paired comparisons can use McNemar’s
test, with a stated multiplicity correction for a family of contrasts.
No significance designation or uncertainty interval is inferred from
rounded aggregate means alone.

## Appendix B Validation and Execution Details

Source-grounded checks.  A reusable program’s test binding identifies
the actual public inputs, source operation, and observed result.
Required inputs are checked against the declared schema and linked to
public fields or executed-operation arguments. Required outputs are
linked to source result fields or independently recorded file effects.
Hidden answer fields and task-identity lookup tables are not program
inputs. An intermediate computation is not reclassified as a complete
answer unless the recorded operation supports that output role. For
validation, a separate environment instance is reset to the source task
and the relevant action prefix is replayed. The program runs through the
permitted interface. The check compares required outputs with the source
reference and, where applicable, verifies the native operation and its
allowed writes. File checks compare the recorded output effect while
retaining the original artifact hash. Parameter variations are applied
only when the source supplies a valid independent reference and the
varied input satisfies the schema. These tests are evidence of local
behavior, not exhaustive branch coverage or semantic equivalence on
arbitrary inputs.

Side effects and failure handling.  Isolated validation avoids changing
the active task. Task-local execution uses a restorable snapshot where
supported, and successful publication occurs only after the associated
output checks. A failed attempt retains its actions, model usage, and
error record. A restored-away interval is not positive evidence for
later skill extraction. Where restoration is unavailable or fails,
subsequent decisions depend on actual state observations; the framework
does not assume arbitrary external operations are reversible.

Retrieval and invocation qualification.  In the ALFWorld execution
protocol, Skill Skeleton and atomic-skill candidates are filtered for
capability and contract compatibility before lexical ranking. Atomic
skills use the Dice-based score in
Eq. ([3](#S3.E3 "In III-C1 Compatibility-Based Program Retrieval. ‣ III-C Program Asset Reuse ‣ III Our SkillCompiler Approach ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation")),
including recorded utility and active status; no embedding-based
retrieval is used. Program realizations are resolved through explicit
Skill–Implementation–Program references rather than independently ranked
by vector similarity. Eligibility requires input binding, preconditions,
environment compatibility, and applicable validation evidence, as
summarized in
Eq. ([4](#S3.E4 "In III-C1 Compatibility-Based Program Retrieval. ‣ III-C Program Asset Reuse ‣ III Our SkillCompiler Approach ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation")).
When no unique eligible or preferred implementation is identified,
execution remains agent-guided.

Asset identity and compatibility.  Operations, program realizations, and
Skill Skeletons are versioned separately. Operations are consolidated
only when they represent the same local capability and have compatible
contracts; matching names or input–output types alone is insufficient.
Program reuse additionally requires compatibility with the current
inputs, preconditions, expected effects, and execution environment. The
Program Asset Manager associates each accepted program version with its
operation contract, applicable execution conditions, and validation
evidence. Changes to the implementation, behavioral contract, or
supported execution conditions require validation of the affected
realization before admission. A failed realization does not invalidate
the operation definition itself. Compatible replacements can serve
existing Skill Skeletons if their operation requirements and parameter
bindings remain satisfied.

## Appendix C Learning, Selection, and Reproducibility

Training and trace-based learning.  Training trajectories provide
evidence for skill induction and revision. The batchwise evolution
process described in
Section [III](#S3 "III Our SkillCompiler Approach ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation")
allows accepted updates to influence subsequent task execution. The
Skill Optimizer analyzes both successful and failed episodes to propose
local changes and consolidate compatible skills. Retained training
trajectories remain associated with the skill state and environmental
observations of their original execution when reused for further
revision. Task outcomes and local operation outcomes are distinguished.
An unsuccessful task may contain independently checked successful
operations that support skill learning. Conversely, overall task success
does not establish that every intermediate program executed correctly.
Failed calls and discarded or rolled-back segments support diagnosis and
revision, while only independently checked, retained execution segments
provide positive evidence for reusable operations.

Local validation and candidate selection.  Local program validation
checks whether a candidate realizes its operation under the tested
inputs and execution conditions, using reference evidence independent of
the candidate’s claimed outputs. Validation-set performance is used to
select among candidate skills or bank snapshots. This selection
evaluates their contribution to task performance and does not replace
local program validation. The selected persistent skill state is fixed
before the corresponding test evaluation.

Independent learning runs.  Main task results and cost comparisons use
seeds $`42`$, $`43`$, and $`44`$. Each learning-based method constructs
a separate bank for each model–benchmark–seed configuration. Task
partitions are shared across methods and runs. Main performance and cost
metrics are calculated within each independent run and then averaged
over the three seeds. Fixed-bank repetition metrics are reported
separately. Learning seeds control training order and supported local
sampling; they do not imply deterministic responses from a hosted
language model. No Skill and Human Skill are evaluated under the same
run settings without model-based skill learning.

Repeated execution.  Stability and ablation analyses use the skill state
learned with seed $`42`$. For each method or condition, the same test
tasks are executed three times with fixed persistent skills, task
inputs, initial environment states, and inference settings. These
repetitions examine variation in executing an established skill rather
than variation between independently learned banks. The LiveMath
analysis uses Gemini-3.8-Flash on 100 tasks, giving 300 task executions.
The ALFWorld analysis uses DeepSeek-V4.1-Flash on 134 tasks, giving 402
task executions. Mean EM or SR summarizes execution outcomes, whereas
EIR@3 counts tasks with both successful and unsuccessful outcomes.
ALFWorld path metrics use canonical environment-action sequences,
including actions executed inside programs. The Full ablation condition
uses the same skill bank and repeated evaluations as the complete
framework in the ALFWorld stability analysis. Metric definitions are
given in
Appendix [A](#A1 "Appendix A Metric Definitions ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation").

Frozen skills and task-local execution.  The persistent learned skill
and Program Asset Bank state remains fixed throughout test evaluation.
Task-local argument grounding, error recovery, and programming permitted
by the corresponding method remain confined to the current task
execution. Temporary programs and intermediate results are not added to
the persistent bank or transferred to later test tasks. Each repeated
execution starts from the same selected bank and reset task-local state.
Test outcomes are used for reporting performance and execution behavior,
not for selecting or revising the bank.

Baselines and textual priors.  Human Skill uses the benchmark-specific
human-written initial.md released by the SkillOpt
authors \[[10](#bib.bib10)\]. This textual skill remains unchanged
during testing and repeated execution. Other baselines retain their own
initialization procedures, learning algorithms, and knowledge
representations under the shared task interface. Within each
model–benchmark comparison, methods use the same task resources, native
tools, evaluators, and inference settings. The reported SkillCompiler
banks are learned through the skill evolution process described in
Section [III](#S3 "III Our SkillCompiler Approach ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation").

Ablation scope.  The three interventions in
Section [IV-E](#S4.SS5 "IV-E Ablation Study ‣ IV Experiments ‣ Compile Away Uncertainty: Self-Evolving Agent Skills via Programmatic Compilation")
are evaluated on ALFWorld with DeepSeek-V4.1-Flash. Each condition
learns independently from an empty bank using seed $`42`$, and its
intervention applies during both learning and testing.

Without Skill Skeleton disables multi-operation skeleton construction
and retrieval while retaining individual operation retrieval,
programmatic execution, and trace-driven learning. Without Programmer
disables program synthesis, qualification, and invocation, including
reuse of stored program realizations, while retaining textual skill
learning, Skill Skeletons, and native tools. Without Skill Optimization
permits the acquisition of new capabilities and an existing textual
operation’s first validated program realization, but prevents subsequent
semantic revision or merging of accepted guidance, contracts, skeletons,
and program realizations. Initial program validation and bounded repair
remain available. All conditions retain runtime grounding and error
recovery within their permitted execution mechanisms, with shared task
partitions, native tools, and budget limits.

Resource accounting.  Learning tokens include training-trajectory
collection, skill construction and revision, feedback, and
validation-based selection. Each model request is counted once, and each
bank’s learning investment is counted once before averaging across
learning runs. Test tokens include input and output tokens from
successful and unsuccessful executions, method-internal model calls, and
retries. Calls/task counts actual model HTTP requests. Retries
contribute to the cost of their original task execution without
increasing the number of evaluated tasks. An execution completed
entirely by programs contributes zero model requests. The main cost
tables average the per-run measurements from seeds $`42`$, $`43`$, and
$`44`$. Ablation costs instead average the three repeated evaluations of
each condition’s seed-42 bank. These summaries characterize resource use
across independently learned banks and during repeated use of a fixed
bank, respectively.

Reproducibility and development history.  Experimental records associate
each run with its model and inference settings, task partition, learning
seed, selected bank version, task outcomes, execution traces, and
learning and test resource usage. Reasoning settings, completion limits,
and retry policies are held consistent within each model–benchmark
comparison. Development included inspection of held-out failure cases;
the reported frozen-bank evaluations prohibit persistent updates from
test outcomes.

Scope of validation.  Programs execute within the permitted benchmark
interfaces and task resources under bounded execution. Local validation
provides evidence for the checked inputs, environment configurations,
and operation effects. Its coverage is limited to those conditions. Task
correctness is determined by the benchmark evaluator, while unresolved
semantics and context-dependent decisions remain under the target
agent’s control.
````
