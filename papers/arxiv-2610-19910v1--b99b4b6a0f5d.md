###### Abstract

Large language model agents increasingly improve by distilling
experience into reusable skills, but errors in that experience can
persist in learned rules and affect later tasks. Existing evaluations
largely examine clean learning or perturbations encountered after skills
are frozen, leaving robustness during self-evolution insufficiently
understood. We introduce RSE-Bench, to our knowledge the first benchmark
for evaluating skill self-evolution under ordinary, non-adversarial
noise. It spans four domains and six benchmarks, with controlled
perturbations to instructions, environmental evidence, execution
records, and outcome–record pairings that preserve the underlying tasks
and native scoring rules. The protocol separates noise during learning
from input-side noise at evaluation, testing frozen skill stores on
held-out tasks. We also introduce RSEClaw, a method-agnostic framework
supporting consistent noise injection and process diagnostics of actual
exposure and skill updates. Across three methods and two backbones,
noisy learning retains only $`25.5\%`$–$`42.1\%`$ of the aggregate gain
achieved by clean self-evolution, depending on the noise type.
Perturbations confined to execution records and outcome–record pairings
cause average losses comparable to input-side noise, despite leaving the
original executions and evaluations intact. Diagnostics further identify
differences in candidate skill text that coexist with small changes in
mean held-out performance.

## 1 Introduction

Large language model (LLM) agents increasingly improve themselves
without weight updates: after completing tasks, they distill execution
experience into persistent, reusable artifacts such as skill libraries
\[17, 30\], natural-language insights \[29, 34\], workflow memory
\[19\], and evolving playbooks \[26, 15\]. Such skill self-evolution can
turn solved tasks into assets for future ones, and recent methods report
substantial gains over skill-free baselines across coding, web, and
office domains \[24, 7\].

These gains are typically measured without systematically perturbing the
experience used for learning. Deployed agents face redundant
instructions, irrelevant and near-duplicate files, fragmented logs, and
outcomes paired with other attempts’ records. For static agents, prior
work primarily measures the execution-time cost of such noise \[18,
12\]. For self-evolving agents, an error can also persist beyond the
episode. An agent might misread an outdated worksheet and distill that
experience into an unreliable rule for choosing templates, affecting
later clean tasks that reuse it. This raises an additional question:
whether noise makes the agent learn the wrong thing and carry it
forward.

Existing evaluations do not directly isolate this effect. Noise
benchmarks for agents inject perturbations at execution time and
evaluate static policies, without updating skills from the perturbed
episodes \[18, 1\]. Robustness probes for evolved skills perturb inputs
after evolution completes, with the skills frozen \[7\]. A parallel
security literature studies malicious corruption of agent memory and
self-evolution, focusing on attack success or safety degradation \[10,
22, 2\]. These lines of work leave open a controlled evaluation of how
ordinary, non-adversarial noise entering the learning loop affects the
reliability of the resulting skills.

We present RSE-Bench, a benchmark for noise-robust skill self-evolution,
together with RSEClaw, the framework that runs it. Two design decisions
organize the benchmark. First, noise is characterized by its entry
point: task instructions (N-Inst), execution-time evidence (N-Evid), the
record visible to the learner (N-Rec), and outcome–record pairings
(N-Bind). Each injection obeys task-preserving constraints that keep
task goals, correct-evidence reachability, ground-truth answers, and
native scoring rules unchanged. Second, learning and evaluation noise
are separated: N-Inst and N-Evid can vary in either phase, while N-Rec
and N-Bind apply only during learning. Clean evaluation measures the
downstream effects of noisy learning; noisy evaluation of cleanly
learned skills measures execution-time sensitivity. Crossing the
applicable conditions further tests whether learning under noise
prepares an agent for the same noise at deployment.

RSE-Bench covers four domains and six benchmarks: spreadsheet
manipulation, document understanding, interactive decision-making, and
skill reuse along ordered task streams. Each uses fixed evolution-train,
selection, and final-test splits, with task identities matched across
conditions. The final-test split is never used for learning and is
evaluated with the skill store frozen. N-Rec and N-Bind transform
learning experience at run time, so task variants alone cannot implement
them. RSEClaw decouples methods from execution, scoring, and noise
injection through a fixed interface. Methods implementing this interface
run without condition-specific modifications. Actual exposure depends on
what each method consumes, so diagnostics track noise exposure, learning
activity, and selected skill versions, supported by optimizer-request
logs and paired-play audits(Appendix D.5).

Our main experiments evaluate ACE, SkillOpt, and RethinkSkill with
GPT-5.2 and DeepSeek-V4.1-Flash. Clean evolution improves the
six-benchmark macro-average by $`2.6`$–$`6.5`$ percentage points, yet
the four noisy-learning conditions retain only $`25.5\%`$–$`42.1\%`$ of
this gain when aggregated across method–backbone pairs. Evidence noise
produces the largest mean loss in both phases. Noise in execution
records and outcome–record pairings causes average losses comparable to
input-side noise, despite leaving the original execution and evaluation
intact. In an ACE ablation on SpreadsheetBench with DeepSeek-V4.1-Flash,
learning under the same noise used at evaluation also fails to improve
performance over clean learning. Our contributions are:

A benchmark for noise-robust skill self-evolution. To our knowledge,
RSE-Bench is the first benchmark evaluating skill self-evolution under
ordinary, non-adversarial noise, with paired conditions separating the
effects of noisy learning from execution-time sensitivity.

The first controlled noise-injection protocol for skill self-evolution.
To our knowledge, this is the first task-preserving protocol jointly
covering non-adversarial noise in instructions, evidence, execution
records, and outcome–record pairings within the skill self-evolution
loop. Instruction and evidence noise are materialized as data; record
and binding noise operate at run time.

RSEClaw, a method-agnostic evaluation framework. A fixed interface
supports consistent execution, scoring, and noise injection across
methods, while process diagnostics and paired-replay audits assess
actual noise exposure and learning activity. We release the framework,
benchmark data, and noise generators.

## 2 Related works

Skill self-evolution in LLM agents. Agents can improve without weight
updates by distilling execution experience into persistent artifacts:
executable skill libraries \[17, 30\], natural-language insights \[29,
13\], workflow memory \[19, 15\], and evolving playbooks \[26\]; recent
methods add optimizer-style discipline with validation-gated skill edits
\[24, 7\]. Unified codebases re-implement many such methods behind one
interface for clean-condition comparison \[20, 25\], and a wave of
benchmarks measures whether evolution helps \[32, 28, 5, 21\]. All of
these train and select skills from noise-free instructions,
environments, and feedback; whether the evolution process itself
survives realistic noise is left unexamined.

Noise robustness of agents. LLMs degrade under irrelevant context
\[12\], and agents are similarly brittle to environmental distraction
\[8, 27\]. AgentNoiseBench \[18\] injects controllable,
solvability-preserving user- and tool-noise into agent benchmarks, and
RethinkSkill \[7\] probes evolved skills with paraphrases and
distractors. However, the former evaluates execution-time robustness of
static agents, and the latter perturbs frozen skills only after
evolution completes. As summarized in Table 1, RSE-Bench extends
evaluation to noise within the learning loop itself, where a noisy
episode can be distilled into persistent skills and affect later tasks
that reuse them.

Contamination of agent memory and experience. A security literature
poisons agent persistence layers, including retrieval stores \[2, 33\]
and self-written memory \[4, 3\]. Recent work shows that self-evolution
itself can be compromised: adversarial task exposure hardens into unsafe
reusable skills \[10\], and biased memory updates degrade agent safety
\[22\]. These works inject deliberately malicious content and measure
attack success, whereas we inject non-adversarial noise – redundant
instructions, irrelevant files, truncated logs, misbound records – and
measure capability on held-out tasks. Relatedly, reward misattribution
across co-retrieved memories has been identified as an inherent flaw to
mitigate \[23, 6\]; our N-Bind instead treats outcome–record pairing as
a controlled, injectable perturbation, measuring its isolated effect on
skill evolution for the first time.

## 3 RSE-Bench

### 3.1 Task Definition

RSE-Bench evaluates noise-robust skill self-evolution: learning
reliable, reusable skills from experience containing non-adversarial
noise. Each noise condition targets one entry point in isolation
(Section 3.2), while preserving task goals, required deliverables,
ground-truth answers, native scoring, and per-task interaction budgets.
Correct task evidence remains intact and accessible.

With the learned skill store frozen, we assess two capabilities on
held-out tasks. _Immunity_ concerns performance on clean tasks after
noisy learning. _Adaptation_ tests whether learning under input-side
noise improves performance under the same noise compared with cleanly
learned skills. Extended design rationale and the corresponding
comparisons are provided in Appendix A.

### 3.2 Task Taxonomy

Every benchmark in RSE-Bench ships in five task conditions: one clean
version and four noisy variants, each corrupting exactly one position of
the learning loop under the task-preserving constraints of Section 3.1.

Instruction noise (N-Inst). Real users rarely hand an agent a minimal
instruction: requests arrive wrapped in organizational background
unrelated to the job, contextual details that do not affect the
solution, and well-meant but unverified advice. N-Inst reproduces these
habits with irrelevant filler that consumes attention,
related-but-unnecessary information that invites false focus, and
misleading non-binding suggestions, such as a hint to reuse a template
that does not apply. The effective request is never altered: an agent
that ignores the additions can solve the task exactly as before. N-Inst
tests whether an agent treats unverified hints as binding constraints,
and whether such hints survive distillation into its reusable rules.

Evidence noise (N-Evid). Real workspaces are cluttered: directories
accumulate outdated workbooks, retrieval returns reports from adjacent
years, and near-duplicates abound. N-Evid injects such material into
what the agent observes during execution: irrelevant files and pages,
topically related but non-decisive evidence, near-miss artifacts that
differ from the correct source in key fields, and redundant presentation
such as repeated results. The correct evidence always remains reachable
within the same interaction budget. N-Evid tests whether an agent can
identify decisive sources amid clutter, and whether the selection habits
it forms there carry into its skills.

Record noise (N-Rec). Between execution and learning, logging failures
can leave gaps in the recorded assistant text and tool outputs. N-Rec
models such fragment loss by randomly selecting and deleting
32-character blocks from these fields, removing approximately 25% of
their characters. Only the record handed to the learner is perturbed;
the execution itself, its outcome, and the environment state remain
untouched. N-Rec tests whether a method can distill reliable skills from
incomplete execution records and keep its reflections calibrated when
the available evidence only partially captures how an outcome was
reached.

Binding noise (N-Bind). In deployed systems, learning is often
asynchronous: outcomes are queued and batched, and delayed feedback can
be attached to the wrong attempt. N-Bind pairs a task’s outcome with
another attempt’s execution record from the same benchmark source and
fit batch. Both the execution records and the outcomes are genuine; only
their correspondence is altered. Applied only when the method itself
decides to update, N-Bind tests whether a method can avoid drawing
incorrect lessons from feedback attributed to the wrong attempt.

The four types differ in where they attach. N-Inst and N-Evid are
materialized as data before a run begins, as noisy instructions and
noisy environments; N-Rec and N-Bind operate at the boundary between
execution and learning, and are applied through the harness at the
moment the learner reads its record or consumes an update. N-Rec and
N-Bind are easily conflated and deliberately separated: under N-Rec the
record of this experience is altered, while under N-Bind the record is
intact but belongs to a different experience. Both corrupt attribution,
but through different mechanisms, and isolated injection lets us measure
which one a given method resists better.

### 3.3 Topic Categories

RSE-Bench spans four domains and six benchmarks: spreadsheet
manipulation (SpreadsheetBench \[9\]), document understanding (SP-DocVQA
\[11\] and MP-DocVQA \[16\]), interactive decision-making (ALFWorld
\[14\]), and sequential skill reuse (SkillFlow \[28\] and
ContinualSkillBench \[5\]). These domains exercise procedural editing,
evidence localization, multi-step planning, and transfer across ordered
tasks, covering both textual and visual evidence. Detailed benchmark
descriptions are provided in Appendix B. All six benchmarks use
deterministic native scoring rules shared by clean and noisy conditions,
avoiding dependence on LLM judges whose interpretation might be affected
by the injected content. The metrics and their application are detailed
in Appendix C.

### 3.4 Dataset Construction

RSE-Bench varies noise along two axes. The first is _where_ noise
enters, one of four entry points of the learning loop, perturbed one at
a time; the second is _which phase_ it applies to, learning or held-out
evaluation. Crossing the two (Table 12) separates what a single noisy
run conflates: whether an agent can still execute in a degraded setting,
and whether what it learned there is sound. All entry points share one
clean-learning, clean-evaluation baseline, against which a degradation
measured under clean evaluation is attributable to learning alone, since
the exam never changed.

Clean base. The clean base imports the original tasks, assets, and
evaluators of the six sources introduced in Section 3.3, and supplies
that baseline. Each source is split into an evolution-train partition on
which self-evolution runs, a selection partition for method-internal
decisions such as accepting a skill update, and a held-out final-test
partition that is never learned from. Task identifiers are fixed, so
noisy variants pair with clean counterparts, ensuring comparisons use
identical tasks.

N-Inst. Each item is its clean counterpart with text inserted into the
user request, in one of three subtypes: content wholly outside the
task’s domain, a true but answer-irrelevant detail of the task’s own
material, and a pointer toward a different concern on that material that
asserts nothing false. The two material-grounded subtypes are generated
with the material in view, so the detail is real rather than invented.
An insert may not change the goal, add binding constraints, or alter
deliverables.

N-Evid. N-Evid adds material to the space the agent searches during
execution: records placed near the answer’s evidence within a workbook
or a page, extra pages in a multi-page task, or repeated genuine
observations in an interactive environment. Generation is answer-aware:
the generator receives the gold answer and the localized original
evidence, because useful distractors live in a narrow margin, close
enough to the question’s topic to compete for attention yet never
supplying a second correct answer or contradicting the real evidence,
and knowing where the answer lives is what makes that margin checkable.
The original evidence always remains intact and accessible, and
distractors are introduced only as additions that never modify or
obscure existing evidence. Benchmark-specific construction procedures
and validity checks are detailed in Appendix E.

N-Rec. N-Rec perturbs the record of an episode after execution and
scoring have completed, leaving both intact: the agent acted in a clean
environment and was scored on what it did, and only the trace handed to
the learner is incomplete. Two operators model loss and duplication
under retry, deleting or repeating spans of assistant reasoning and tool
output at a configurable rate. Deletion leaves no marker, filler, or
cue, since a visible ellipsis would tell the learner exactly where to be
cautious and thereby measure something easier. Evaluator feedback and
citations are preserved verbatim, the episode’s identity, status, and
score are immutable, and so is the condition under which a method
decides to update, so that trajectory noise cannot change how often
learning happens.

N-Bind. N-Bind models a failure of asynchronous learning pipelines in
which feedback returning out of order is paired with execution records
by arrival order rather than by identity, allowing an outcome to be
paired with another attempt’s record. Under this condition, every
execution and evaluation remains genuine; the perturbation affects only
their correspondence. For a misbound attempt, the learner receives the
genuine evaluation result of another attempt from the same benchmark
source and fit batch. Because delays are sampled randomly, the arrival
order within a window may coincide with the original order, so not every
episode is misbound. We record the actual number of misbound episodes in
each batch and report the resulting misbinding rate in Section 5.3.

Table 12 summarizes the conditions and the data behind them. N-Rec and
N-Bind transform the experience consumed by the learner during skill
updates, so these two run only as noisy learning under clean evaluation;
they do not apply during held-out evaluation, when the skill store is
frozen. The invariants above are enforced by automated checks where
mechanically decidable, and otherwise by model review with human audits
of sampled instances. The detailed automated verification pipeline,
model-review prompts, and human audit procedures are provided in
Appendix F.

## 4 The RSEClaw Framework

Two of the four entry points act on the experience a self-evolution
method consumes during learning, so the conditions of Section 3.4 cannot
be run from data alone; they require a framework that applies noise at
consistent points in the evolution loop across methods. RSEClaw meets
this requirement by decoupling the self-evolution method from the
evolution loop: the method under evaluation is a module behind a fixed
interface, while task delivery, native execution, scoring, and noise
injection are managed by the framework. Methods implementing this
interface can run in the same way under every condition without
condition-specific modifications. Whether a particular noise type
reaches a method, however, depends on the information that method
actually consumes: for example, a method that does not read execution
trajectories receives no perturbation under N-Rec. Such cases are
explicitly recorded by the process diagnostics and are not treated as
evidence of robustness.

The evolution loop. RSEClaw follows the fixed cycle shown in Figure 1.
The framework delivers a task from the evolution-train partition, the
method supplies whatever skills it judges relevant, and the framework
executes the agent in the source’s native environment and scores the
outcome with the source’s native evaluator; the resulting episode,
comprising the instruction, the trajectory, and the evaluation, is then
handed to the method, which may reflect on it, revise its skill store,
or decline to update; the updated store is available from the next task
onward. Selection tasks serve the method’s internal decisions, and the
held-out final-test partition is visited only after evolution ends, with
the skill store frozen.

The method interface. A method implements a small contract: retrieve
skills relevant to an incoming task, consume a completed episode, decide
whether to update, and expose its skill store for freezing and
inspection. The contract deliberately excludes everything the experiment
must control, so a method cannot re-score an episode, cannot reach the
final-test partition, and cannot observe which condition it is running
under.

Noise seams. The two run-time conditions attach at seams the interface
itself defines: N-Rec between execution and reflection, N-Bind where
evaluations meet attempts. Their invariants are enforced at run time
rather than by convention, so an implementation that mutates the
original episode, alters an identity, status, or score, or shifts the
method’s update trigger is rejected at the point of violation instead of
being discovered in analysis. The clean condition applies the identity
transformation at the same seams, so clean and noisy runs traverse
identical code paths.

Process diagnostics. Final-test performance alone cannot distinguish a
method that resisted noise from one that never encountered it. RSEClaw
therefore records three types of process information at each
optimization step. First, it records whether noise was applied and its
realized extent: for $`N_{\mathrm{Rec}}`$, whether each episode was
modified, the reason for any unmodified episode (e.g., ineligibility for
learning or a method that does not consume trajectories), and the
fraction of characters deleted; for $`N_{\mathrm{Bind}}`$, the number of
mismatched episodes in each batch. Second, it records which episodes the
method selected for learning. Third, it records whether a skill update
was proposed, whether it passed validation and was accepted, and the
proposed edits. The frozen skill store is supplied with every test task,
so the deployed version determines which updates are available to the
agent during evaluation. For methods that organise skills as individual
rules, such as ACE, the framework also records the rules referenced by
the agent on each test task. Whether a perturbation actually appears in
the method’s inputs is assessed offline. The framework logs every
request received by the optimiser and provides paired-replay audits that
compare clean and noisy optimiser inputs with all other conditions held
fixed. These records help distinguish stable performance despite actual
exposure and learning from cases in which noise never reached the
learner or little learning occurred.

### 5.2 Main Results

Table 2 reports final-test performance averaged over three independent
runs of the complete evolution and evaluation pipeline; standard
deviations are reported in Table 14. The column headers specify the
learning and evaluation conditions, with notation defined in the table
caption. Under clean learning, self-evolution improves the six-benchmark
macro-average for every method–backbone pair, with absolute improvements
of $`2.6`$–$`6.5`$ percentage points over the initial agent.

All four learning-side entry points erode the gain. Of the $`24`$
noisy-learning cells in the Avg block, $`23`$ fall below their
corresponding $`C\!\to\!C`$ baseline. Averaged over the six
method–backbone pairs, relative losses are $`4.9\%`$ under
$`N_{\mathrm{Evid}}`$, $`4.5\%`$ under $`N_{\mathrm{Rec}}`$, $`4.4\%`$
under $`N_{\mathrm{Bind}}`$, and $`3.9\%`$ under $`N_{\mathrm{Inst}}`$.
Measured through differences in the overall macro-average score, these
conditions retain only $`25.5\%`$–$`42.1\%`$ of the improvement achieved
by clean evolution. $`N_{\mathrm{Rec}}`$ and $`N_{\mathrm{Bind}}`$ both
cause larger average losses than $`N_{\mathrm{Inst}}`$, despite
perturbing only the experience passed to the learner. How faithfully an
agent’s own execution is recorded thus matters as much as how clean the
tasks it works on are, a comparison the input-side conditions alone
cannot reveal.

$`N_{\mathrm{Evid}}`$ is most damaging in both phases.
$`N_{\mathrm{Evid}}`$ causes a larger average loss than
$`N_{\mathrm{Inst}}`$ whether injected during learning or evaluation.
Its mean relative loss rises from $`4.9\%`$ during learning to $`6.3\%`$
during evaluation, whereas $`N_{\mathrm{Inst}}`$ causes losses of
$`3.9\%`$ and $`3.6\%`$, respectively. The largest single decline occurs
under evaluation-side $`N_{\mathrm{Evid}}`$: ACE with GPT-5.2 on
SkillFlow falls from $`31.33`$ to $`17.33`$, a relative loss of
$`44.7\%`$.

Relative performance retention depends on the backbone. SkillOpt
achieves the highest clean macro-average on both backbones. On
DeepSeek-V4.1-Flash, it also has the smallest mean relative loss across
all six noisy conditions, combining a clean score of $`77.71`$ with a
loss of $`2.5\%`$. On GPT-5.2, ACE has the smallest relative loss at
$`3.9\%`$, alongside the lowest clean score of $`63.97`$. SkillOpt and
RethinkSkill achieve higher clean scores of $`67.53`$ and $`66.93`$, but
incur losses of $`4.9\%`$ and $`6.6\%`$, respectively. The
clean-performance ranking is therefore consistent across backbones,
while the method that best preserves its clean performance changes.

Degradation varies across benchmarks. Averaged over the $`24`$
noisy-learning cells within each benchmark, the largest losses occur on
SkillFlow ($`10.9\%`$) and SpreadsheetBench ($`5.7\%`$), and the
smallest on SP-DocVQA ($`1.4\%`$): a single-page extractive answer
survives clutter largely intact, whereas a multi-step workbook edit
depends on every cell the agent writes. ContinualSkillBench ($`3.8\%`$),
ALFWorld ($`3.4\%`$), and MP-DocVQA ($`3.1\%`$) fall between.
ContinualSkillBench also contains the largest positive deviations in the
table, where SkillOpt improves by up to $`23.2\%`$ under noise, so an
average over a block does not describe every cell within it. Finally,
self-evolution does not improve every task even without noise: on
GPT-5.2, ACE’s clean evolution on SpreadsheetBench ends below the
initial agent ($`40.83`$ vs. $`45.00`$).

### 5.3 Process Diagnostics

Final-test performance alone cannot distinguish a method that resisted
noise from one that never encountered it. We therefore examine three
process quantities for ACE and RethinkSkill on SpreadsheetBench with
DeepSeek-V4.1-Flash (Table 9): input exposure rate (IER), the skill
version selected on validation for final testing ($`v^{*}`$), and
candidate-to-clean similarity (CCS). IER measures the share of optimiser
inputs containing an injected perturbation across three rounds of $`50`$
fit tasks. CCS measures mean term-frequency cosine similarity between
noisy-run and clean-run candidate skills. Its bracketed reference is
computed over pairs of independent clean runs, and comparisons are made
within each method.

Actual exposure varies across methods and noise types. For ACE, IER is
$`100\%`$ under $`N_{\mathrm{Inst}}`$ and $`N_{\mathrm{Rec}}`$, and
$`97\%`$ under $`N_{\mathrm{Evid}}`$; for RethinkSkill, it is $`100\%`$
under $`N_{\mathrm{Rec}}`$. Binding noise affects a smaller share of
inputs: $`21\%`$ ($`32/150`$) for ACE and $`15\%`$ ($`22/150`$) for
RethinkSkill. These values measure actual mismatches between execution
records and evaluation outcomes. Because random delays can preserve the
original arrival order, some pairings remain unchanged even when binding
noise is enabled. Within this two-method diagnostic subset,
$`N_{\mathrm{Bind}}`$ also produces the smallest mean relative loss
among the four learning-side conditions in Table 10.

Different conditions select different skill versions. Under the same
three-pass learning budget, the validation-selected version varies
across conditions for both methods. ACE selects $`v1`$ under
$`N_{\mathrm{Rec}}`$ and $`v3`$ under $`N_{\mathrm{Evid}}`$, while
RethinkSkill selects $`v1`$ under $`N_{\mathrm{Bind}}`$ and $`v3`$ under
$`N_{\mathrm{Rec}}`$. These differences identify which checkpoint from
each learning trajectory is retained for final testing, providing
additional information about the outcome of evolution.

Lower candidate similarity can accompany a small change in final-test
performance. All eight noisy-to-clean CCS values fall below their
respective clean-to-clean reference means. The largest gap for ACE
occurs under $`N_{\mathrm{Evid}}`$ ($`0.702`$ versus $`0.814`$), and for
RethinkSkill under $`N_{\mathrm{Bind}}`$ ($`0.783`$ versus $`0.901`$).
In the latter case, the mean final-test score changes from $`88.33`$ to
$`89.17`$, a difference of only $`0.84`$ percentage points (Table 10);
the corresponding standard deviations are $`0.72`$ and $`3.15`$ (Table
14). This comparison illustrates that similar mean performance can
coexist with different candidate text. CCS provides a complementary view
of that textual variation, without directly establishing the functional
quality of the selected skills.

### 5.4 Analysis and Ablations

Evaluation noise reverses the benefit of clean evolution. Table 3 and 15
compare the initial agent with an agent carrying a cleanly evolved skill
store. Under clean evaluation, evolution raises the score from $`79.58`$
to $`90.00`$. Under $`N_{\mathrm{Inst}}`$ evaluation, however, the
initial agent scores $`83.75`$, while the cleanly evolved agent scores
$`77.50`$; under $`N_{\mathrm{Evid}}`$, the corresponding scores are
$`82.50`$ and $`78.75`$. The cleanly evolved agent therefore trails the
initial agent by $`6.25`$ and $`3.75`$ percentage points on these noisy
variants, reversing its advantage under clean evaluation.

Additional rounds widen the clean–noisy gap. Appendix Table 16 compares
checkpoints on clean held-out tasks after repeated passes over the same
training set. From one to three rounds, the clean-learning score rises
from $`85.00`$ to $`90.00`$, while the score under $`N_{2}`$ falls from
$`76.25`$ to $`73.75`$. The clean–noisy gap widens monotonically from
$`8.75`$ to $`16.25`$ percentage points.

Learning under matching noise performs worse than clean learning. The
same table compares learning conditions while holding evaluation noise
fixed. Under $`N_{\mathrm{Inst}}`$ evaluation, a store learned under
$`N_{\mathrm{Inst}}`$ scores $`71.25`$, compared with $`77.50`$ for a
cleanly learned store. Under $`N_{\mathrm{Evid}}`$ evaluation, learning
under the matching noise scores $`70.00`$, compared with $`78.75`$ for
clean learning. Matching the learning and evaluation noise thus reduces
performance by $`6.25`$ and $`8.75`$ percentage points, respectively.
For the method we test in this setting, exposure to the deployment noise
during learning does not improve performance under that noise.

GPT-5.5 reduces, but does not eliminate, noise-induced losses. For ACE
on SpreadsheetBench, GPT-5.5 reduces the largest learning-side deficit
from $`15.83`$ to $`6.25`$ percentage points compared with
DeepSeek-V4.1-Flash (Appendix Table 17). All four noisy-learning
conditions nevertheless remain below its clean-learning score of
$`95.00`$, with relative losses of $`1.3\%`$–$`6.6\%`$. These results
show that learning-side degradation is not confined to the weaker
backbone: a stronger model reduces its absolute magnitude in this
setting but does not eliminate it.

Case Studies. Figure 2 illustrates one case, with detailed analyses in
Appendix G. These cases highlight two mechanisms: skills may retain
assumptions or precautions without the conditions that justify them,
making their reuse inappropriate; and reflection may combine useful
content with unsupported corrections, including those inferred from
misbound feedback. Validation assesses each candidate update as a whole,
providing limited evidence about the contribution of individual clauses.
Whether unsupported clauses persist in the deployed skill store
therefore depends on reflection, update acceptance, and version
selection; final-test scores alone cannot establish their presence.

## 6 Conclusion

RSE-Bench evaluates skill self-evolution under non-adversarial noise,
separating learning-side from evaluation-side perturbations.
Learning-side noise erodes a substantial fraction of the aggregate gain
from clean evolution, with record and binding noise causing losses
comparable to those from input-side noise. Candidate skill text can also
diverge despite small changes in mean held-out scores, showing why
performance alone cannot fully characterize learning under noise. We
release RSE-Bench and RSEClaw to support joint evaluation of learning
gains, noise exposure, and changes in learned skills.

## AI Use Statement

Large language models are the subject of study in this work: they serve
as the evaluated actors, as the optimizers inside the ported
self-evolution methods, and as the generator for the N-Inst and N-Evid
noisy releases, all of which is described in the main text. Beyond these
roles, we used LLM-based assistants to search for and locate related
work, to draft and polish text under the authors’ direction, and to help
implement code; all research ideas, experimental designs, and claims are
the authors’ own, and the authors reviewed and take full responsibility
for all text and code in this paper.

## Ethics Statement

RSE-Bench is constructed entirely from publicly available agent
benchmarks used under their respective licenses; it involves no human
subjects, no personally identifiable information, and no newly collected
user data. The injected perturbations are non-adversarial by design:
every noisy instance preserves the task goal, ground truth, scoring, and
evidence reachability of its clean counterpart, so the benchmark
measures robustness to naturally occurring noise rather than providing
recipes for attacking deployed agents. We audited a sample of generated
noisy instances to confirm they contain no harmful or offensive content.
We see no ethical concerns beyond those inherent to evaluating LLM
agents.

## Reproducibility Statement

We release the full benchmark and harness, including the five matched
task releases per source benchmark, the noise-generation and review
pipeline for N-Inst and N-Evid, and the runtime injection modules for
N-Rec and N-Bind, which are deterministic given a recorded seed and make
no model calls. Every run records its resolved configuration, per-phase
noise conditions, model identifiers, budgets, and frozen checkpoint, so
any reported number can be regenerated from the released artifacts.

## Appendix A Design Principles and Evaluation Objectives

Noise characterized by entry point. RSE-Bench distinguishes noise by
where it enters the learning loop: task instructions, environmental
evidence, the execution record consumed by the learner, or the pairing
between a record and its evaluation outcome. These positions represent
different failure modes, including distracting context, cluttered
workspaces, missing log fragments, and misattributed feedback. They are
not levels on a common severity scale. Each condition perturbs one entry
point in isolation, supporting controlled comparisons of how methods
respond to different sources of unreliable experience.

Task-preserving comparisons. Clean and noisy conditions retain the same
task goals, required deliverables, ground-truth answers, and native
evaluators. They also share the same per-task interaction budgets,
including the step, time, and output limits of Appendix D.2. The correct
evidence remains reachable. Noise can increase the difficulty of finding
relevant evidence or interpreting experience without changing what
counts as success. N-Rec and N-Bind additionally preserve the underlying
executions and genuine evaluations, modifying only the records delivered
to the learner or their correspondence with outcomes.

Consequences beyond the learning episode. A local misjudgment may affect
later tasks if it is incorporated into a reusable skill. Evaluating only
the episode in which noise appears can therefore miss its downstream
consequences. RSE-Bench assesses the resulting skill store on held-out
tasks after learning has ended, distinguishing two objectives.

_Immunity_ is assessed by comparing noisy learning followed by clean
evaluation ($`N\!\to\!C`$) with clean learning and clean evaluation
($`C\!\to\!C`$). This comparison measures how well skills learned from
noisy experience retain their usefulness on clean tasks.

_Adaptation_ is assessed by comparing matched noisy learning and
evaluation ($`N\!\to\!N`$) with clean learning under the same noisy
evaluation ($`C\!\to\!N`$). This tests whether exposure during learning
improves performance under that noise. The comparison applies to N-Inst
and N-Evid; N-Rec and N-Bind operate only during learning and therefore
have no noisy-evaluation counterpart.

## Appendix B Benchmark Details

RSE-Bench combines six benchmarks across four domains to evaluate skills
that differ in both their content and their conditions of reuse.
Evidence ranges from structured workbooks and document images to
interactive environment states, while ordered task streams provide
opportunities to examine transfer from earlier learning to later tasks.

Spreadsheet manipulation. The agent modifies real workbooks according to
natural-language requests, including filling formulas, adjusting
formats, merging records, and maintaining cross-sheet references. Useful
skills are procedural, such as inspecting a worksheet’s layout before
editing or checking referenced ranges after modifying a formula. Such
procedures can be reused across workbooks, making it important to
distinguish broadly applicable rules from assumptions specific to one
file. SpreadsheetBench \[9\] provides tasks drawn from real user
requests, with outputs checked against ground-truth workbooks at the
cell level.

Document understanding. The agent answers questions grounded in document
images, requiring it to locate relevant pages and regions and interpret
forms, tables, and layout. Skills concern evidence handling: where to
search, what to cross-check, and when enough evidence has been found.
SP-DocVQA \[11\] poses questions over single document images, whose
answers depend on within-page content and structure. MP-DocVQA \[16\]
extends this setting to multi-page documents, requiring answer-page
localization in addition to reading the relevant content. Together,
these benchmarks evaluate evidence-handling skills across within-page
reading and cross-page search.

Interactive decision-making. The agent acts over multiple steps, with
success determined by its actions and the resulting environment state.
ALFWorld \[14\] provides household tasks in a text environment,
exercising planning over object locations and action sequences. Reusable
skills include behavioral routines such as deciding where to search for
an object, ordering actions to satisfy prerequisites, and verifying that
a subgoal has been completed.

Sequential skill reuse. Ordered task streams provide repeated
opportunities to apply skills acquired from earlier experience.
SkillFlow \[28\] groups tasks into families with shared workflow
structures while varying entities, file formats, and difficulty. Within
each family, tasks follow a fixed order, supporting the reuse of
procedures distilled from earlier tasks. ContinualSkillBench \[5\]
provides longer streams of subtasks ordered by skill-transfer
dependencies and increasing difficulty, one stream per domain (finance
and economics, healthcare, law, and mathematics), so that skills
acquired on earlier subtasks can support later ones that build on them.
This structure supports analyses of how earlier learning relates to
later performance; final-test evaluation in RSE-Bench still follows the
shared protocol with the skill store frozen.

Scoring. Every benchmark is scored by its native evaluator: cell-level
comparison against a ground-truth workbook for SpreadsheetBench, exact
match against the gold answers for SP-DocVQA and MP-DocVQA, the
simulator’s goal-satisfaction flag for ALFWorld, the task’s test suite
for SkillFlow, and test suites, exact match, numerical tolerance, or
token-level F1, depending on the task, for ContinualSkillBench. Clean
and noisy conditions retain the same ground truth and scoring rules. No
language model is involved in scoring, which keeps evaluation
deterministic and avoids an additional source of variation from
LLM-based judging. Benchmark-specific metric definitions are provided in
Appendix C.

## Appendix C Metrics

SpreadsheetBench. The agent submits a path to a workbook. The harness
opens it with openpyxl to reject unreadable files, has LibreOffice
recalculate it so that submitted formulas are compared by their values,
and then calls the native cell-level comparison against the golden

numbers are rounded to two decimals, numeric strings are coerced to

boolean cast to a float in this harness rather than a partial score, and
is therefore not used as one.

SP-DocVQA and MP-DocVQA. Both call the same vendored DocVQA evaluator on
the submitted answer string. Reported accuracy is $`1`$ if the answer,
lowercased and stripped, equals any one of the gold answers, and $`0`$
otherwise. The evaluator also returns ANLS, one minus the normalised
Levenshtein distance to the closest gold answer, floored to $`0`$ below
a similarity of $`0.5`$; it is retained as the soft signal and not
reported. The two benchmarks differ only in what the agent must do to
obtain the answer, not in how the answer is graded: MP-DocVQA supplies
multiple pages, so page localisation is part of the task rather than a
separately scored quantity.

ALFWorld. The episode runs against the native TextWorld PDDL
environment, and won is the environment’s own goal-satisfaction flag
when the episode ends. The environment is constructed deterministically
— fixed seed, no shuffling of admissible commands — so the same action
sequence yields the same verdict. ALFWorld defines no partial credit,
and no reward shaping is added.

SkillFlow. After execution, the harness copies the task’s native test
files into the deployed workspace and runs pytest in the task’s working
directory; reward is $`1`$ if the suite exits zero and $`0`$ otherwise.
Grading is tied to the workspace the harness deployed rather than to
whatever path the agent names in its submission, so an agent that did
the work but answered in prose is still graded on its files. A per-test
pass fraction could be reconstructed from the test report, but it would
be our construct rather than the benchmark’s, so it is neither used nor
reported.

ContinualSkillBench. The native judge grades the JSON output file the
task asked for, and reward is the score it returns. The released pool of
tasks declares four evaluation types and no rubric: one class of
programmatic tasks scored $`1.0/0.0`$ by their pytest suite; one class
of exact-match tasks compared after lowercasing, mapping punctuation to
spaces and collapsing whitespace; one class of numeric tasks compared
under a per-task relative tolerance (default $`10^{-4}`$), falling back
to the string comparison when either side does not parse as a number;
and one class of F1 tasks scored by token-level F1 after lowercasing,
stripping punctuation and dropping articles. The F1 subset is the only
place where a reported score is continuous rather than binary. Because
no task in the pool carries rubrics, the judge’s model-scored branch is
never entered, and it is the only branch in any of the six benchmarks
that would involve a language model in scoring: no LLM judge
participates in any number reported in this paper.

Aggregation. Per-benchmark scores are means of the reported metric over
the tasks of the split, in percent. The macro-average over benchmarks
weights the six equally and is computed before any relative change is
taken, so a rate in Table 2 is the change of the macro-average and not
an average of per-benchmark rates.

## Appendix D Experimental Setup

This appendix specifies the protocol behind every number in Section 5.2
and Section 5.4. Configuration values are those of the released run
configurations; where a value differs between benchmarks, the difference
is stated.

### D.1 Evaluation Protocol

Jobs. A job is one benchmark, one method, one backbone and one learning
condition. Every job starts from the method’s own initial skill store
(empty for RethinkSkill and SkillOpt, an empty two-section playbook for
ACE) and shares no state with any other job, so the five learning
conditions of a method–backbone–benchmark triple are five independent
evolutions over the same tasks.

Partitions. Each benchmark contributes three disjoint partitions (Table
13). The $`50`$ evolution-train tasks are drawn from the benchmark’s
native training split and the $`30`$ selection tasks from its native
validation split, which is never merged into training; both are drawn
once with a fixed seed ($`42`$) and whole groups of tasks that share
material are kept together. The final-test partition is drawn from the
native test split. The evolution-train and selection identifiers are
fixed before any run. All identifiers are identical across methods,
backbones and conditions, so every comparison in the paper is paired at
the task level.

The evolution run. A run makes $`R=3`$ passes over the evolution-train
partition. Before the first pass the initial store is scored on the
selection partition. During a pass the agent executes each training task
with the current store, the episodes are handed to the method, and the
method proposes an update at the points its own algorithm defines (once
per pass for ACE and RethinkSkill, once per batch for SkillOpt; Appendix
D.3). Every proposed store is scored on the selection partition, and the
method’s own gate decides whether it replaces the current one. After the
last pass the harness freezes, among the checkpoints the method
promoted, the one with the highest selection score, breaking ties toward
the earlier version; if no checkpoint is comparable, the initial store
is frozen. The frozen store is then evaluated once on the final-test
partition. No method sees a final-test task before this point, and the
store no longer changes during evaluation.

Learning and evaluation conditions. The column headers of Table 2 name a
learning condition and an evaluation condition.

- •
  _Clean learning_ ($`C\!\to\!\cdot`$) uses the clean evolution-train
  and selection partitions.
- •
  _$`N_{\mathrm{Inst}}`$ and $`N_{\mathrm{Evid}}`$ learning_ replace
  both the evolution-train and the selection partition with the
  corresponding noisy release, task for task, so the method’s gate and
  the frozen-version choice also operate on noisy tasks. The noisy
  releases carry the same gold answers and evaluators as the clean ones
  (Appendix C).
- •
  _$`N_{\mathrm{Rec}}`$ and $`N_{\mathrm{Bind}}`$ learning_ use the
  clean partitions and apply the transformation at the run-time seams of
  Section 4, to training episodes only. Selection episodes and
  final-test episodes are never transformed.
- •
  _Clean evaluation_ ($`\cdot\!\to\!C`$) runs the frozen store on the
  clean final-test partition. _Noisy evaluation_
  ($`C\!\to\!N_{\mathrm{Inst}}`$, $`C\!\to\!N_{\mathrm{Evid}}`$) reloads
  the store frozen by the clean-learning job and runs it on the
  corresponding noisy final-test partition, without any further
  learning.

The _initial agent_ is the same actor with no skill store. For each
benchmark–backbone pair, it is evaluated once per independent run on the
clean final-test partition, and the resulting score is shared by the
three methods within that run. For the noisy-evaluation analyses, it is
also evaluated once per run on each noisy final-test partition
($`\mathrm{Initial}\rightarrow N`$).

Runs. Each cell of Table 2 is the mean over 3 independent runs of the
complete pipeline, evolution and evaluation included; standard
deviations are in Table 14.

### D.2 Agent, Backbones and Budgets

Actor. All methods share one tool-calling actor, which runs in the
benchmark’s native environment through the local executor. It has a
fixed system instruction (“Complete the given benchmark task using
tools. Files use real local paths and persist across tool calls. Finish
by calling submit with the specified submission format.”), receives the
task observation as JSON together with any page images, and acts only
through tool calls: python and command execute code in the task
workspace, read_file and write_file access workspace files, env_step
sends an action to an interactive environment (ALFWorld only), and
submit ends the episode with the benchmark’s native submission object. A
reply without a tool call, or with arguments that are not valid JSON,
receives a one-line reminder of the protocol. The skill store is
inserted as a separate system message after the fixed instruction and
before the task, so it is never mistaken for part of the question; it
carries no version number, so the actor cannot tell how far learning has
progressed. ACE additionally asks the actor to cite the playbook bullets
it relies on, as in the original method.

Per-task limits. Each episode is limited to $`40`$ tool steps, $`60`$ s
per tool call and $`600`$ s of wall-clock time. The standard output and
error of each tool call are truncated to $`16{,}000`$ characters,
keeping head and tail. Because every step resends the transcript, the
three most recent tool results are kept whole and older ones are
shortened to $`500`$ characters by the same head-and-tail rule; the
actor can re-run a call to recover an old result. The current step’s
input is never shortened.

Backbones and roles. Table 5 lists the model settings. Within a job the
same backbone serves as the actor and as the method’s optimizer
(Reflector and Curator for ACE, analysts, merger, ranker and epoch
updater for SkillOpt, rewriter for RethinkSkill), so a backbone column
of Table 2 describes a self-contained system. The $`N_{\mathrm{Inst}}`$
and $`N_{\mathrm{Evid}}`$ variants (Appendix F) are constructed and
reviewed offline by Kimi-K2.8, a model outside the evaluated backbones
that never participates in an evolution run. The generator and both
semantic reviewers use this model with the settings in the lower block
of Table 5; the two reviews are separate requests that do not see each
other’s verdicts. Decoding is deterministic, and every candidate,
including rejected ones, is kept with its review records. No language
model takes part in scoring (Appendix C).

### D.3 Method Configurations

The three methods are reimplemented against their published source,
keeping each method’s update schedule, evidence, prompts and acceptance
rule; only rollout, scoring and noise injection are delegated to the
framework. Table 6 summarizes the differences that matter for noise
exposure.

ACE. After each pass, a Reflector call is made for every training
episode, successes included. It receives the question, the recorded
trajectory truncated to $`6{,}000`$ characters, the submission, the
evaluator feedback and the playbook bullets the actor cited, and returns
a reflection with helpful/harmful/neutral tags for those bullets. The
tags update the bullets’ counters, and a single Curator call then turns
the reflections into operations on the playbook. As in the published
code, only ADD operations are applied, the optional deduplicating
analyzer is disabled, and there is no score-based acceptance gate: every
proposed playbook replaces the current one. The playbook starts with two
empty sections, _general_ and _others_, so that the published rule
redirecting unknown sections to _others_ is meaningful from the first
pass. The selection partition therefore affects ACE only through the
choice of the frozen version.

SkillOpt. SkillOpt updates per step: the $`50`$ training tasks of a pass
are split into steps of $`40`$ and $`10`$ tasks, giving six steps over
three passes. In each step, analyst calls read the trajectories of
failed and of successful episodes in minibatches of $`8`$ and each
proposes at most $`L`$ edits, the proposals are merged hierarchically in
groups of $`8`$, and a ranking call keeps the top $`L`$. The edit budget
$`L`$ follows a cosine schedule from $`4`$ down to $`2`$ over the run.
The patched skill is accepted only if its selection score strictly
exceeds that of the current skill, so a tie is rejected. From the second
pass on, an epoch-end update runs the previous and the current epoch’s
skills on the same $`20`$ training tasks, sampled with a fixed seed, and
uses the paired outcomes to rewrite a reserved slow-update section of
the skill (always accepted, as in the published default) and a
meta-skill that conditions the optimizer’s later prompts without being
shown to the actor. On SP-DocVQA, the gold answers and ANLS of scored
training episodes are appended to the learning record after evaluation,
reproducing the published DocVQA rollout; the actor never sees them and
held-out episodes are not affected.

RethinkSkill. RethinkSkill updates once per pass. Its evidence is the
evaluation ledger of all training episodes: per task a success or
failure label (success only at a hard score of exactly $`1`$), the hard
score, the soft score where the benchmark has one, and the evaluator’s
own reason string where it emits one. A single optimizer call returns
the complete replacement skill as a JSON object with exactly three
string fields (operation, candidate_skill, rationale); any other reply,
and an explicit noop, leaves the skill unchanged. The candidate is
judged by a four-branch gate on the selection partition: it is accepted
if the hard score rises by more than a dead band, rejected if it falls
by more than the band, accepted as a soft rescue if the hard score is
within the band but the soft score rises by at least a rescue margin,
and otherwise left flat. The dead band and rescue margin are the
published per-benchmark values: $`0.01`$ and $`0.02`$ for SP-DocVQA and
MP-DocVQA, $`0.02`$ and $`0.05`$ for SpreadsheetBench, $`0.02`$ with no
rescue for ALFWorld. The published protocol does not cover SkillFlow and
ContinualSkillBench, so a band of $`0`$ with no rescue is used there
instead of an invented value.

### D.4 Run-Time Noise Parameters

$`N_{\mathrm{Rec}}`$. The main experiments use the deletion operator at
severity $`0.25`$ on two channels, the assistant’s text and the tool
outputs, with a fixed seed ($`42`$). Evaluator feedback and bullet
citations are preserved, no marker is left at a deletion, and at most
$`2{,}000`$ characters may be added by any operator. The transformation
is applied to training episodes, including the paired episodes of
SkillOpt’s epoch-end update, and never to selection or final-test
episodes.

$`N_{\mathrm{Bind}}`$. Outcomes are bound to execution records by
arrival order within windows of $`3`$ attempts, with delays drawn
uniformly up to $`6`$ positions from a fixed seed ($`42`$). Binding is
applied within each training batch (a pass for ACE and RethinkSkill, a
step for SkillOpt) and, for SkillOpt, separately to the previous-epoch
and current-epoch sides of the epoch-end comparison, never across them.
Where the sampled arrival order within a window coincides with the
dispatch order, no outcome moves; the binding record of every batch
counts the episodes whose outcome was actually reordered.

### D.5 Analysis Experiments

All analyses use ACE on SpreadsheetBench with DeepSeek-V4.1-Flash, the
same partitions and the same settings as the main experiments, except
where noted below.

Crossed learning and evaluation (Table 15). The initial agent is
evaluated on the clean and on both noisy final-test partitions. Stores
frozen by clean learning are evaluated on the noisy partitions
($`C\!\to\!N`$), and stores frozen by $`N_{\mathrm{Inst}}`$ and
$`N_{\mathrm{Evid}}`$ learning are evaluated on the clean partition
($`N\!\to\!C`$) and on the noisy partition of the same type
($`N\!\to\!N`$). All of these reuse frozen stores; no store is
re-learned for the analysis.

Training rounds (Table 16). This ablation uses one clean-learning run
and one $`N_{2}`$-learning run, each making three passes over the same
evolution-train partition. For each condition, we evaluate the skill
checkpoint at the end of each round $`R\in\{1,2,3\}`$ on the clean
final-test partition, with the skill store frozen during evaluation. The
three columns thus track round-end checkpoints along a single evolution
trajectory within each condition, including the checkpoint at the end of
the third round for $`R=3`$. The gap at each round is the noisy-learning
score minus the clean-learning score, in percentage points.

Backbone (Table 17). The initial agent, clean learning, the four
noisy-learning conditions and the two noisy-evaluation conditions are
repeated with GPT-5.5 as both actor and optimizer, with the settings of
Table 5.

Process diagnostics (Section 5.3). IER, the selected version $`v^{*}`$
and CCS are computed offline from the logged learning inputs, gate
records and candidate skills of the main-experiment runs of ACE and
RethinkSkill; they require no additional model calls.

Optimizer-request logs and paired replay. Every optimizer call is
recorded as it is made: the full prompt, the effective system message,
the request arguments and whether the call returned or failed. These
logs are passive and change nothing the method sends or receives. They
let the analyses check what a method’s optimizer actually received,
rather than inferring it from what the noise seam produced; for example,
an episode modified by $`N_{\mathrm{Rec}}`$ that a method never selects,
or that a method reads only through its evaluation ledger, does not
reach the optimizer. To confirm that the run-time conditions behave as
intended, we additionally run controlled paired replays offline: the
same method state, task order and scripted optimizer replies are
replayed once with the identity transformation and once with
$`N_{\mathrm{Rec}}`$ or $`N_{\mathrm{Bind}}`$, and the corresponding
requests are compared for exact prompt equality. A comparison is counted
only when the system message and request arguments are unchanged and the
number of calls matches; under $`N_{\mathrm{Bind}}`$, whose reordering
can change which episodes a method selects, requests are paired by the
receiving episode before comparison. The replays use no model and no
additional evolution runs; they serve as a check of the harness and of
the logs, not as a separate experiment.

## Appendix E N-Evid Construction Details

This appendix details how the N-Evid releases are built for each
benchmark. Three construction families cover the six sources, chosen by
what the agent actually searches during execution: rendered page images
for the two DocVQA sources, input files in a task workspace for
SpreadsheetBench, SkillFlow and ContinualSkillBench, and the stream of
simulator observations for ALFWorld. Table 7 summarizes the construction
family and gold-answer access for each benchmark.

Shared protocol. All families share four rules. (i) _Group granularity._
Tasks that share the same native material (the same page image, workbook
or environment layout) form a group, and one piece of noise material is
constructed for the whole group, since the agent observes the same
material whichever of the group’s questions it answers. Every question
of the group is checked separately, and the group is published only if
all of them pass; a single rejection withdraws the whole group rather
than a single task. (ii) _Additions only._ The native question, gold
answers, evaluator and train/test assignment are copied unchanged, and
every original asset remains present and byte-identical wherever the
construction does not by design append to it; this is verified by
mechanically replaying each renderer over the untouched original. (iii)
_Separated roles._ Generation and review are separate model calls at
temperature $`0`$; reviewers receive the final rendered material rather
than the generator’s rationale, and a verdict of _uncertain_, a
malformed verdict or a transport failure counts as non-acceptance. (iv)
_Bounded and recorded._ Each group has a fixed ceiling on logical model
calls, all requests, responses, rejections and failures are retained,
and resuming a run never re-draws a rejected group.

### E.1 Answer-Aware Page Edits: SP-DocVQA and MP-DocVQA

Localization. The builder first asks the model to localize the evidence
of every question in the group on the original page images, given the
questions and their gold answers. Each piece of evidence is returned as
a bounding box in original pixel coordinates together with the text
observed inside it, and must include field labels and headers needed to
read the value; the model also lists the _qualifiers_, the conditions
and document identity that select the answer (e.g. a year, an entity, a
form section). Boxes are validated as ordered integer rectangles inside
the image. A question the model cannot localize is marked unresolved and
makes the group inapplicable, rather than letting generation proceed on
a guessed location.

Candidate regions (SP, and MP in-place route). From the localized boxes
the builder enumerates blank regions of the page as placement
candidates. A region is admissible only if it does not overlap any
protected evidence box and lies near one: the gap between rectangle
edges, divided by the page diagonal, is at most $`0.12`$. Each region
carries a conservative character capacity at a fixed font size. Coverage
is recorded per question, and the release does not assume that every
question of a group receives a nearby record.

Generation. Given the localization and the admissible regions, the model
writes one candidate for the whole group. On SP it is a single short
record per edited page: one printable-ASCII paragraph of at most $`320`$
characters and at most the chosen region’s capacity, carrying only a
scoped field and value under a clear heading (e.g. _Prior-year
record:_), so that it reads as a separate record and never fills an
original blank form field or joins an existing table. The scope that
excludes it must already be excluded by the question or by the
established document identity; an alternate value alone, an invented
correction or a “not the answer” disclaimer does not qualify. The model
also returns, for every question, the existing condition, the added
scope and why the addition is excluded. On MP the model takes one of two
routes. By default it writes (a) one independent appended page of the
same genre, describing a clearly different entity, period or scope with
similar fields (title at most $`100`$ characters, body at most
$`2{,}400`$ characters and $`30`$ rendered lines), rendered as a
separate page placed after the original pages. When any question’s
referent is the whole document (its title, author, date, or a count of
its entries), an appended page would join that referent and create a
second valid answer, so the model must instead take (b) the in-place
route above, editing one or more existing pages so that page count and
document identity are untouched, with every question of the group
receiving at least one edited page.

Rendering and delivery checks. Records are drawn at a fixed font size
inside the chosen region; a record that does not fit is rejected, never
shrunk. The renderer is then replayed over the untouched original, and
the candidate is refused if any pixel outside the record’s box differs.
For MP appended pages, the original page files and their order are
byte-identical, and for each task the builder runs the benchmark’s own
preparation step and checks that the number of delivered images equals
the original count plus one, with the new page last.

Review. Two independent reviews, each seeing the final rendered images,
all questions and their gold answers, audit the group. Each returns
group-level checks (natural material, readable, original evidence
preserved, safe placement) and per-question checks (evidence supported,
answer unchanged, no new correct evidence, no answer hint, scope
excluded). Reviewers are instructed to separate a _wrong distractor_,
which is the intended treatment, from an _additional correct answer_,
which is a defect: a question that asks for 1 January 1982 excludes a
clearly labelled 1 January 1981 record, while “the date of this
document” may become ambiguous once a second date appears. Any false
check or uncertainty rejects the candidate. A group may make up to three
generation attempts, bounding its logical calls at $`1+3\times 3`$.

### E.2 Workspace Evidence: SpreadsheetBench, SkillFlow and ContinualSkillBench

On these sources the gold is not a string that can be shown to a
generator: SpreadsheetBench grades against a golden workbook, and
SkillFlow and ContinualSkillBench grade the agent’s files with native
test suites or judges. Generation and review therefore use the public
task and the public input files only, and answer-awareness is replaced
by an explicit, checkable scope: the generator must return a short
_distinction_ string that appears verbatim in the material, together
with the concrete features it shares with the task.

Relation and material. Each group is assigned one of three relations by
a seeded hash of its identifier: _near-miss_ material imitates the topic
and structure of the original input and shares concrete features, but
visibly differs on a question-relevant constraint (e.g. lot codes with
prefix ZX when the task filters for PK); _related non-decisive_ material
shares the domain but supplies no requested evidence or execution
advice; _unrelated_ material has an independent subject. The model
returns a structured note (title, visible scope, columns, rows and
optional paragraphs), never raw file bytes, and must not provide the
answer, a formula, an answer location, a new instruction or an
authoritative correction, nor label the material as irrelevant.

Rendering. A deterministic renderer writes the note into an existing
input file with a format-specific additive operation, selected per group
so that every task of the group has an editable input (Table 7): an
.xlsx workbook gains one final worksheet with a name distinct from every
original sheet, while the original sheets’ XML, cells and formulas
remain byte-identical; a .csv file gains one final column with the
original rows and cell strings unchanged; a .json file gains one new
top-level member with all original keys and values unchanged; .docx,
.txt and .md files gain a trailing titled section with the original
content retained as a prefix. When no input can be edited safely, or the
task has no editable input, a fallback places one separate reference
file in the workspace, always related non-decisive, with $`2`$–$`8`$
columns, $`2`$–$`12`$ rows, $`20`$–$`240`$ words and no executable
formulas; it does not replace any input or claim to be one.

Checks. Before any model review, two mechanical gates run. The renderer
is replayed over the original file and the result must match the
delivered file, which confirms that the original content is intact. A
literal gate then rejects any question that counts or enumerates the
whole container being appended to, such as the number of worksheets in
the workbook, the number of columns in the CSV file, or all top-level
keys of the JSON input, since an addition changes that answer even when
every original value is preserved. The surviving tasks receive two
independent model reviews that see the original and modified excerpts
and the actual before/after structure. The first returns four checks
(answer preserved, scope distinguishable, no instruction, mechanism fit)
and must quote the task’s constraints verbatim; it distinguishes input
constraints from output constraints, so that a requirement for exactly
one output sheet does not forbid an additional input sheet, and it
rejects only an actual input-restriction violation, a loss of answer
identifiability, a new instruction or hint, or a second equally
applicable contradictory fact. The second is an independent ambiguity
audit. A rejection by either review makes the group inapplicable;
uncertainty or an error leaves it unpublished. The generator may
regenerate once after a malformed reply, and a group’s logical calls are
bounded by $`3+2\,|G|`$ for a group of $`|G|`$ tasks.

### E.3 Observation Replay: ALFWorld

In ALFWorld the space the agent searches is the sequence of observations
returned by the simulator, and no text inserted there can be guaranteed
consistent with every future state: a sentence about an object or
location may become false after any action. N-Evid is therefore
constructed without generated content, by replaying genuine public
observations. Each group is assigned one of two operators by a seeded
hash. _Repeat-visible_ appends a copy of lines from the current
observation; _history-excerpt_ appends lines from the immediately
preceding observation. The appended block is labelled _Observation log,
step $`k`$_, with each line quoted, so that it never reads as a
current-state assertion. It is delivered after every non-terminal
observation, including the initial one when the operator has a source,
and is capped at $`900`$ characters of whole lines. Lines that restate
the task goal, instructions or action markup are excluded, so the
operator can only repeat environment evidence the agent has already been
shown.

The simulator is untouched: the native observation text is preserved as
a prefix, and the admissible commands, state transitions, terminal
messages and rewards are identical to the clean episode, which is
checked mechanically. Because the operator’s effect depends on the
trajectory, review is run on real deliveries: the builder records a
native trace for each task, requires at least one non-reset frame on
which the operator actually applied (otherwise the task is marked
uncertain and not published), and passes those frames to the same two
model reviews used for workspace evidence.

## Appendix F Noise Validity Verification

Every noisy condition in RSE-Bench is required to satisfy four
invariants: the task goal is unchanged, the correct evidence remains
reachable within the same interaction budget, the true outcome of every
execution is unchanged, and the scoring semantics are unchanged. This
appendix describes how each invariant is enforced. Verification runs in
three layers of increasing cost and decreasing mechanical decidability.
Automated checks come first and make no model calls; model review
handles the semantic properties that no program can decide; and a human
audit of sampled instances by three independent annotators checks the
two materialized releases, N-Inst and N-Evid. A variant enters a release
only if it passes the automated and model layers that apply to it; the
human audit then re-reviews a random sample of each benchmark’s release,
and a sampled variant that fails is removed. Table 8 gives the mapping.

|                             |                            |                               |                            |                                      |
| --------------------------- | -------------------------- | ----------------------------- | -------------------------- | ------------------------------------ |
| Invariant                   | N-Inst                     | N-Evid                        | N-Rec                      | N-Bind                               |
| Task goal unchanged         | Auto + Model + Human       | Auto + Model + Human          | Auto (question never read) | Auto (question never read)           |
| Correct evidence reachable  | Model + Human              | Auto (replay) + Model + Human | Auto (execution untouched) | Auto (execution untouched)           |
| True outcome unchanged      | Auto (evaluator untouched) | Auto (evaluator untouched)    | Auto (score immutable)     | Auto (payloads permuted, not edited) |
| Scoring semantics unchanged | Auto + Model + Human       | Auto + Model + Human          | Auto                       | Auto                                 |
| No answer leak or hint      | Auto + Model + Human       | Model + Human                 | —                          | —                                    |

Table 8: Where each validity invariant is enforced. _Auto_:
deterministic checks without model calls; _Model_: two-sided model
review of the final material; _Human_: sampled re-review of each
benchmark’s release by three independent annotators, a sampled variant
passing only if all three pass it. N-Rec and N-Bind are deterministic
transformations whose invariants are fully decidable, so they need
neither model nor human review.

### F.1 Automated Verification

Shared release checks. Every noisy release is built from, and checked
against, the clean base of the same source. After the noise field is
removed, each row must be identical to its clean counterpart: same task
identifier, question, target, evaluator reference, split and group.
Evaluators and scoring assets are copied unchanged, and a release that
shadows or rewrites a native scoring asset is refused. Construction and
review always write to a new sibling release and never overwrite an
existing one, so an audit can compare any published variant with the
material it was derived from.

N-Inst. Each variant is the original question with one insert placed
before or after it, the position being fixed by the seed and the task.
Five checks run before any model review. (i) _Verbatim question_: the
original question must occur verbatim in the noisy prompt, so that
nothing of the request is rewritten. (ii) _Non-degenerate insert_: the
remaining span must be nonempty and contain at least one full sentence.
(iii) _No answer string_: no gold answer string may occur in the insert.
For the two DocVQA sources this match respects word boundaries, so that
a one-character or numeric answer does not reject every insert
containing that character. Sources graded by execution have no answer
string and skip this check. (iv) _Source bans_: per-source patterns
reject constructions known to change the product, for example a new
output language, unit or file name. (v) _No output request_: a
deliberately narrow pattern rejects requests to transcribe, copy out,
quote verbatim or report the material’s content “along with your
answer”, which would move the insert into the graded product. The
pattern is narrow on purpose, because unrelated chore requests are the
designed content of this noise and a broad list of imperative verbs
would reject them silently. For ALFWorld, three further checks are
programmatic: any object or receptacle the insert names must appear in
the task’s own reset observation or goal line (scene membership),
statements about listed receptacles may not contradict their presence in
the room, and the insert may not request an action on anything the agent
could act on within its step budget.

N-Evid. The construction-specific checks are detailed in Appendix E; we
summarize the decidable ones here. For image material, the renderer is
replayed over the untouched original and every pixel outside the added
record’s box must be unchanged, protected evidence boxes may not be
overlapped, and for appended pages the original page files and their
order must be byte-identical, with the task’s own preparation step
delivering exactly one more image. For file workspaces, replaying the
renderer over the original input must reproduce the delivered file, the
original sheets, rows, keys or text must be intact, and a literal gate
rejects any question that counts or enumerates the whole container that
received an addition. For ALFWorld, the native observation must remain a
prefix of every delivered observation, the admissible commands,
transitions, terminal messages and rewards must equal those of the clean
episode, and a recorded native trace must contain at least one non-reset
step on which the operator actually applied.

N-Rec. N-Rec runs on a detached copy of each episode after scoring and
never touches the episode that is measured. A configuration is rejected
unless it preserves evaluator feedback and citations. At run time the
transformation (i) applies only to fit-split episodes that are eligible
for learning and appear in the declared task manifest, and passes
held-out episodes through unchanged; (ii) edits only string leaves in
the declared channels, assistant text and tool output, and a structural
comparison of the episode before and after raises an error if any other
field, the trajectory structure, an envelope or the multiset of citation
tokens changed; (iii) for deletion, verifies that exactly the selected
characters were removed and nothing was inserted, with no marker left
behind; (iv) for repetition, caps the added characters; and (v) keeps
the episode’s identity, status, score and learning-eligibility flag
immutable, so the condition under which a method decides to update is
identical to the clean run. Span selection uses a SHA-256 hash of the
seed, source, task and round, so every edit is reproducible and logged
with its coordinates.

N-Bind. N-Bind operates on one fit batch at a time and refuses a batch
that crosses source, split, round or skill version, so a misbound
outcome always comes from a genuine attempt at the same stage of
learning. Before binding, each episode’s score must agree with its
native metrics, and only dedicated trailing evaluation-feedback rows are
treated as movable; an ambiguous row mixing actor content with feedback
is refused rather than moved. Binding must be a one-to-one permutation
of feedback packets, and a post-condition checks that every execution
record and every feedback payload is byte-identical to its original;
only their pairing changes. Methods that consume only native evaluator
feedback cannot acquire gold through a misbound packet. The resulting
mapping records, per slot, the donor attempt and whether the slot is
misbound; the per-batch misbinding counts reported in Section 5.3 are
read from these records rather than from the configured delay
parameters.

Exposure check. For N-Rec and N-Bind, whether the perturbation actually
reached the learner is itself verified. A passive recorder captures
every optimizer request, and for a controlled paired replay, with method
state, task order and stubbed responses held fixed, the clean and noisy
requests are compared call by call. A perturbation counts as exposed
only if the prompt changed while the system message and call arguments
did not. This is a statement about the learner’s inputs, not about model
behaviour.

### F.2 Model Review

Model review decides the properties no program can: whether an insert
changes the product, whether an added fact could also answer the
question, whether a distractor’s scope is visibly excluded. All reviews
run at temperature $`0`$ with thinking disabled, return a fixed JSON
schema that is parsed strictly, and are applied to the final material
exactly as the agent will see it. A malformed reply, a contradictory
verdict (e.g. ok with a failed check), an _uncertain_ verdict or a
transport failure counts as non-acceptance. Reviewers never see any
actor’s score, since a variant must not be selected by how hard it makes
the task. The condensed English renderings below give the decisive
criteria; the verbatim prompts, including source-specific blocks, are
released with the code.

### F.3 Human Audit

Automated checks and model review are run by the same pipeline that
constructs the noise, so we spot-check their output by hand. The audit
covers the two materialized releases, N-Inst and N-Evid, separately for
each of the six benchmarks. It is a sampled re-review of variants that
have already been accepted by the automated and model layers, not an
additional gate applied to every variant.

Sampling. For each benchmark and each of the two noise types, 30
variants are drawn uniformly at random from the accepted releases. For
N-Evid the sampling unit is a group, since one piece of material is
shared by all questions of the group, and every question of a sampled
group is checked.

Review. Each sampled variant is judged by three annotators from the
author team, working independently. Annotators see the clean task, the
noisy variant as the agent would receive it (the noisy prompt for
N-Inst; the modified page images, input files or delivered observations
for N-Evid), and the gold answer where the benchmark has one. They do
not see the model reviewers’ verdicts or any actor’s result on the task.
Each annotator answers one question: does the variant keep the original
task intact, that is, is the goal and deliverable unchanged, is the
correct evidence still present and usable, and does the added content
neither supply the answer, a hint or a second correct answer, nor
contradict the task’s material? A variant passes only if all three
annotators answer yes; a single failing judgment counts as a failure,
and an annotator who is unsure records a failure.

## Appendix G Case Studies

This appendix expands Section 2 into eight classes. Each class is stated
first as a mechanism, independently of any particular cell of the grid,
and is then supported by two concrete cases: one from the ablation
setting used throughout Section 5.4 (SpreadsheetBench,
DeepSeek-V4.1-Flash, ACE) and one from a different source, backbone or
method, so that no class rests on a single cell.

Figures inside the boxes are absolute task counts from the audit of one
complete run of the pipeline, under that run’s per-source scoring key,
and not the run-averaged percentages of Table 2. Counts are therefore
comparable within a case but not across the two cases of a class: the
cross-setting case changes the source, so the scoring key and the number
of tasks change with it (SpreadsheetBench scores a hard restriction over
80 tasks, SkillFlow a reward threshold over 50). Single-task differences
remain inside run-to-run variation (Table 14); every class is claimed at
the level of a set of tasks, and the cases are shown to expose the
mechanism rather than to establish significance on their own. Two
further observations that constrain how the per-cell tables may be read
— that a method can be untouched by a noise position for lack of an
input channel that carries it, and that the same position reverses sign
across source, backbone and method — are reported with the diagnostics
in Section 5.4 rather than as case classes.

### G.1 Learned Skills and Noise Are Mutually Exclusive

A self-evolved skill is a compression of the regularities of the
environment it was learned in, and it inevitably freezes in a set of
premises about that environment’s surface structure. Noise changes
exactly that surface structure while the task goal itself is left
intact, so the premises inside the skill stop holding and the agent goes
on acting on one that is no longer true. This failure differs in form
from the task becoming harder: on the same item, a model carrying no
skill store often still solves it from general competence, and the loss
appears only on the side that enters the noisy environment carrying what
it learned. Such losses should therefore be attributed to a conflict
between the learned prior and the present environment rather than to a
rise in difficulty; where the noise is strong enough, a skill store can
be a net liability.

release; task

### G.2 Precautionary Clauses Consume the Interaction Budget

Noise leads a method to learn cautious discipline of the form “enumerate
first, verify first, only then act”. Such discipline costs almost
nothing in a clean environment, which is why it always looks safe at
learning time; but once it is written down as an unconditional preamble,
it charges a fixed toll on every task. When the environment contains
more objects to be checked — the extra files, sheets and paragraphs all
have to be read first — that toll scales with the number of objects, and
a bounded interaction budget is spent before the real edit is ever
attempted. The failure therefore presents as a step or output limit
rather than as a wrong answer: its cause lies in the skill layer, but it
is recorded as a resource problem in the execution layer.

![](arxiv-2610-19910v1--b99b4b6a0f5d.figures/inline-5.svg)

$`N_{\mathrm{Evid}}`$; task

steps here, ending at step_limit with no submission. This setting also
supplies the third reading the ablation setting cannot: $`9/50`$ tasks
exhaust the budget in this arm against $`3/50`$ in the cleanly evolved
arm, and when the _same_ frozen store (v3, $`6354`$ characters, $`4`$
front-loaded clauses) is re-evaluated on the clean release it still
exhausts $`6/50`$. The proximate cause is thus the precautionary clause
in the store, with the noise only triggering it more often. The class
remains a minority phenomenon — $`6`$ cases in total inside the ablation
setting — and should be read as a visible consequence of unconditional
front-loading, not as the main mechanism of the score drops.

### G.3 Defensive Rules Cross the Noise Boundary

Rules learned in order to resist noise are usually written as
prohibitions — “ignore objects of this kind”, “do not modify anything
the task did not name” — and nothing at write time attaches their
trigger condition: the rule does not know that it holds only while the
noise is present. Retrieval proceeds by semantic proximity, which is
independent of whether the current environment actually contains noise,
so the same prohibition is recalled in clean environments and
reinterprets objects that were supposed to be modified as objects that
must not be touched. The consequence is a loss of immunity: the agent
has already computed the correct result and then declines to write it.
Noise thus leaves a persistent inhibitory residue long after the noise
itself is gone.

![](arxiv-2610-19910v1--b99b4b6a0f5d.figures/inline-6.svg)

$`N_{\mathrm{Inst}}`$, evaluated on the clean release; task 24-23.
Unevolved $`1`$, cleanly evolved $`1`$, and the
$`N_{\mathrm{Inst}}`$-evolved store never submits. The shape reproduces
on a different backbone and a different method, and at larger scale:
$`11`$ tasks in this arm are solved without a store and with a cleanly
learned store, and missed only with the noise-learned one (frozen v3,
$`8075`$ characters, $`1`$ defensive clause). SkillOpt’s store is
continuous prose rather than individually addressable entries, so the
failure can be exhibited only against the defensive clause in the frozen
text, not pinned to one retrieved rule as in ACE. Across both settings
the evidence is “retrieved and then failed”, which is association; a
leave-one-rule-out re-evaluation would be required to make it causal.
The class also does not reproduce everywhere: the ACE arms on SkillFlow
have an empty immunity-loss set in both directions, and that empty set
is reported with the class.

### G.4 Contamination and Useful Experience Share One Rule

A reflection is a narrative account of one complete attempt, in which
the part induced by noise and the part that is genuinely useful are
interleaved, and writing compresses both into the same rule. Retrieval
and curation both operate on whole rules: the useful half-sentence drags
the contaminated half-sentence into the context with it, and any
deletion at rule granularity discards the useful experience along with
the contamination. Contamination is therefore not a separable item that
could be picked out and thrown away, but something that lives
symbiotically with useful knowledge; selective removal would require a
granularity down to the clause, with provenance retained per clause.

![](arxiv-2610-19910v1--b99b4b6a0f5d.figures/inline-7.svg)

distraction from the machine-readable task: its first clause is elicited

the SkillFlow task. It is retrieved on $`44`$ of $`50`$ test items,
$`21`$ of which are still answered correctly. Two caveats travel with
the class. Noise-carrying and piggyback labels come from the keyword
detectors in the diagnostics and carry false positives, for which the
clean arm’s hit rate is the floor; and this particular piggyback is
identified by reading the text — the automatic front-loading-and-guard
detector does not fire on it, so the detector covers only one of the
spellings in which the two clauses can be fused.

### G.5 Misbinding Induces Fabrication That Is Then Frozen In

When the pairing between an outcome and the process that produced it is
broken, the method reads evidence that contradicts itself: the process
shows the work being done, the verdict says it failed. The interface
gives it no way to question the pairing itself, so it instead constructs
an explanation for a failure that never happened and writes that
explanation down as a rule. The error crosses from the feedback layer
into the knowledge layer. If that round happens to pass validation, the
invented rule is deployed and retrieved repeatedly thereafter, and a
one-off perturbation of the binding has been converted into a persistent
false prior.

enters its denominator, so it cannot be traced back to any single rule
even though it is frozen into the store. The two forms should be
reported separately.

### G.6 Attribution Is Displaced from the Error to the Observation Channel

When the record is mutilated, the method loses the basis on which a
failure could be localised, yet it is still required to produce a cause.
The missing evidence does not lead it to delete or shorten steps; it
displaces the attribution onto the only visible anomaly — that the
observation itself cannot be trusted. The rules it then writes are
meta-rules about the credibility of logs and tools, unrelated to task
competence and unable to improve behaviour on later tasks. Such
displacement still looks like learning from the outside, but what is
learned is suspicion of the observation channel, and it goes on
occupying room in the store that task knowledge should hold.

### G.7 The Validation Gate Is the Only Filter

In a pipeline of this shape, curation accepts essentially everything
that is written, and the only real selection happens when a version is
chosen against the validation set. Noise therefore has exactly two
outlets: where the round passes, contamination is deployed together with
the useful rules; where it does not, the whole round is rolled back,
possibly all the way to an empty store. The two outcomes are
indistinguishable in the test score — a score that did not drop may mean
the contamination was resisted, or that nothing was learned at all.
Separating them requires reporting “whether learning happened” and “what
the test score was” as two distinct quantities.

![](arxiv-2610-19910v1--b99b4b6a0f5d.figures/inline-10.svg)
Case 2 — SkillFlow, GPT-5.2, ACE; the same four arms. Here the dichotomy

Freezing at v0 is a fact about whether learning happened and not a
robustness result, which makes reporting the frozen version alongside
any per-position robustness table a requirement rather than a
suggestion.

### G.8 Store Size Drifts Toward Both Extremes

Since filtering happens at that one point, the size of the skill store
drifts along it toward both extremes: where a round is let through, the
store inflates along with its defensive clauses and transfers the cost
to the execution layer; where it is not, the whole round is rolled back
and the store ends smaller than it would have been without noise, or
empty. Whether a skill store grows or shrinks under noise is thus not a
property of the noise position but a consequence of whether that round
passed validation. Reading size in one direction only, as inflation,
hides the more serious failure at the other end: an entire round of
learning is discarded, and it leaves almost no trace in the score.
