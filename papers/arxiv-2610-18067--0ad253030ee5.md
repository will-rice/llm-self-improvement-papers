###### Abstract

Scaling interactive environments has become increasingly important for
training long-horizon agents through reinforcement learning. These
environments often require further testing and refinement after initial
generation, and correcting defects in a task may also require updating
its work context and verifier. However, existing construction pipelines
offer limited support for such iterative refinement while keeping these
components aligned. In this paper, we introduce WorkRover, a framework
for training long-horizon cowork agents through recursive environment
evolution. Its harness-driven synthesis enables construction agents to
jointly build and validate semantically aligned work contexts,
executable tasks, and evidence-grounded verifiers, adapting their
actions to workspace state and execution feedback rather than following
a fixed construction workflow. To support environment evolution, we
introduce Factorial Compatibility Replay (FCR), which uses rollout
feedback to evaluate combinations of component revisions through
dependency-closed replay and selects the smallest validated repair among
tested candidates while preserving task requirements and evaluation
constraints. To provide finer-grained training signals, we propose
Verifier-to-Turn Credit Assignment (VTCA), which augments
trajectory-level GRPO advantages with signals from deterministic
workspace-progress checks and assigns a bounded share of
positive-progress credit to prerequisite turns using recorded
tool-output and artifact dependencies. Using WorkRover, we post-train
Qwen3.5-35B-A3B to obtain WorkRover-35B-A3B and evaluate it on several
cowork-agent benchmarks. Its reported scores exceed those of
Qwen3.5-35B-A3B by 26.27 percentage points on JobBench, 29.32 percentage
points on OfficeQA Pro, and 413.25 Elo points on GDPval v2. These
results suggest that WorkRover offers a promising foundation for
scalable training of long-horizon cowork agents.

## 1 Introduction

Cowork agents powered by large language models (LLMs) perform
professional tasks across files, tools, and applications
\[[15](#bib.bib15)\]. These tasks unfold over long sequences of
dependent actions, requiring agents to locate relevant materials
\[[31](#bib.bib31), [17](#bib.bib17), [37](#bib.bib37)\], track
workspace changes, and maintain consistency across related artifacts
\[[20](#bib.bib20), [33](#bib.bib33), [3](#bib.bib3),
[32](#bib.bib32)\]. Training these agents through reinforcement learning
(RL) depends on environments that support diverse, executable workflows
and provide reliable feedback on task outcomes \[[11](#bib.bib11),
[5](#bib.bib5), [26](#bib.bib26), [10](#bib.bib10), [41](#bib.bib41),
[45](#bib.bib45), [49](#bib.bib49)\]. Recent work has explored automated
environment and task synthesis to expand the range of workspaces and
tasks available for agent training \[[30](#bib.bib30), [2](#bib.bib2),
[18](#bib.bib18)\].

However, expanding the number of synthesized environments does not by
itself ensure reliable training feedback. In a cowork environment, the
work context must support the task’s requirements, and the verifier must
assess the requested outcomes while accepting valid alternative
solutions. Agent rollouts can expose missing dependencies, inconsistent
task specifications, or verification errors that remain after initial
construction \[[47](#bib.bib47)\]. Such defects can make valid behavior
appear unsuccessful or allow incorrect results to be rewarded. Repairing
these defects often requires coordinated revisions within a task
environment: a correction to the work context or task specification may
also require updating the verifier to keep execution and evaluation
aligned. Existing construction pipelines offer limited support for
maintaining this alignment throughout repeated revisions. This motivates
_recursive environment evolution_: repeatedly using execution feedback
to identify defects, coordinate component revisions, and revalidate the
revised environment while preserving the original task requirements and
evaluation constraints. Reliable terminal evaluation also leaves a
credit-assignment challenge: useful steps can occur in failed
trajectories and redundant actions in successful ones, while earlier
information-gathering turns may only contribute through later workspace
changes \[[34](#bib.bib34), [6](#bib.bib6)\].

To this end, we introduce WorkRover, a framework for long-horizon cowork
agent training that integrates harness-driven environment synthesis,
recursive environment evolution, and verifier-grounded policy learning
([Figure
2(b)](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
Its harness tracks component dependencies and enables construction
agents to jointly build and validate semantically aligned work contexts,
executable tasks, and evidence-grounded verifiers. These agents adapt
their construction actions to workspace state and execution feedback
rather than following a fixed workflow. Independent reference executions
from a clean initial workspace establish task feasibility, while
verifier validation tests incorrect outcomes and valid alternatives
against instruction-grounded requirements rather than a prescribed
solution path. For environment evolution, we introduce _Factorial
Compatibility Replay_ (FCR), which evaluates combinations of fixed
repair proposals across the work context, task, harness, and verifier.
Each combination is rebuilt with its dependency-induced updates and
tested under matched rollout conditions. FCR selects the smallest
validated repair among the tested combinations, subject to preserving
task requirements and evaluation constraints and passing regression
checks on affected tasks. Fresh rollouts confirm selected repairs and
provide evidence for subsequent evolution. For policy learning, we
introduce _Verifier-to-Turn Credit Assignment_ (VTCA) to supplement
trajectory-level GRPO advantages with finer-grained feedback. Frozen
deterministic checks measure progress and setbacks in recorded workspace
states, while tool-output and artifact dependencies identify
prerequisite turns eligible for a bounded share of positive-progress
credit. This provides turn-level learning signals without intermediate
judge calls.

We post-train Qwen3.5-35B-A3B with WorkRover and evaluate the resulting
model on five external benchmarks spanning occupational tasks,
professional deliverables, cross-application workflows, and
document-grounded reasoning. WorkRover-35B-A3B exceeds the reported
backbone scores on all five benchmarks, with gains of 26.27 percentage
points on JobBench, 29.32 percentage points on OfficeQA Pro, and 413.25
Elo points on GDPval v2. Controlled experiments further examine the
contributions of environment evolution and verifier-grounded learning.
Under matched repair budget caps, FCR improves task-package synthesis
pass rate by 6.0 percentage points over full regeneration. A separate
maintenance evaluation shows that FCR also resolves naturally occurring
defects more reliably while reducing unintended changes to task intent.
Construction ablations also show that following file dependencies and
matching files with compatible skills improve task yield and
executability, beyond assembling workspaces through topical similarity
alone. With the supervised fine-tuning (SFT) initialization, task and
seed schedules, and rollout budget fixed, VTCA outperforms episode-only
GRPO across all five benchmarks. These findings support improving both
environment reliability and turn-level learning signals for long-horizon
cowork agent training.

Our main contributions are:

1.  1.  Harness-driven construction of semantically aligned environments. We
        introduce a Harness-driven synthesis pipeline that jointly
        constructs _semantically aligned_ work contexts, executable tasks,
        and evidence-grounded verifiers at scale. The Harness explicitly
        _tracks their dependencies_ and validates _task feasibility and
        verifier consistency_.
2.  2.  Recursive environment evolution. We introduce _Factorial
        Compatibility Replay_ (FCR) to support iterative environment repair
        under explicit component dependencies. FCR evaluates coordinated
        revisions, identifies _minimal validated repairs_, and propagates
        changes across affected components while _preserving task intent and
        evaluation constraints_.
3.  3.  Training from verifier-grounded progress. We introduce
        _Verifier-to-Turn Credit Assignment_ (VTCA) to augment
        terminal-reward GRPO with _workspace-grounded advantage shaping_.
        Deterministic checks provide progress proxies, with bounded positive
        allocations to _prerequisite turns_ through recorded tool and
        artifact dependencies, without intermediate Judge calls.

## 2 Related Work

##### Executable environments and verification.

Prior work scales executable environments \[[36](#bib.bib36),
[30](#bib.bib30), [2](#bib.bib2), [7](#bib.bib7), [40](#bib.bib40)\] and
validated task synthesis \[[4](#bib.bib4), [18](#bib.bib18),
[22](#bib.bib22), [12](#bib.bib12)\]. Shared specifications and state
help align tasks and verifiers \[[13](#bib.bib13), [29](#bib.bib29)\],
while adversarial audits test verifier reliability \[[47](#bib.bib47)\].
WorkRover jointly constructs Work Contexts, Tasks, and Verifiers,
tracking their dependencies under a versioned Harness.

##### Environment evolution and repair.

Recent work studies task-bundle revision and execution-driven
environment repair \[[39](#bib.bib39), [23](#bib.bib23),
[10](#bib.bib10)\]. Program repair also studies patch minimization
\[[38](#bib.bib38)\]. FCR replays combinations of fixed repair
proposals, including dependency-induced changes. It selects the smallest
validated repair among those tested, preserving task requirements and
evaluation constraints and checking affected tasks for regressions.

##### Long-horizon learning and progress attribution.

Local credit assignment draws on state comparisons and planning
hierarchies \[[8](#bib.bib8), [24](#bib.bib24)\], progress estimates, or
evidence attribution \[[34](#bib.bib34), [46](#bib.bib46),
[43](#bib.bib43), [9](#bib.bib9), [44](#bib.bib44), [42](#bib.bib42)\].
VTCA shapes GRPO advantages \[[27](#bib.bib27)\] with frozen checks of
workspace progress and setbacks. It assigns a bounded share of positive
credit to prerequisite turns using recorded tool-output and
artifact-version dependencies, without intermediate Judge calls. Checker
coverage \[[48](#bib.bib48)\] and dependency quality limit these
signals. See Appendix
[A](#A1 "Appendix A Extended Related Work ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution").

## 3 Method

In this section, we present WorkRover (Figure
[3](#S3.F3 "Figure 3 ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")),
a framework for training long-horizon cowork agents through recursive
environment evolution. We first introduce harness-driven synthesis of
semantically aligned work contexts, tasks, and verifiers (Sec.
[3.1](#S3.SS1 "3.1 Harness-Driven Environment Synthesis ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
We then present Factorial Compatibility Replay (FCR) for rollout-driven
recursive evolution (Sec.
[3.2](#S3.SS2 "3.2 Recursive Environment Evolution ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution"))
and Verifier-to-Turn Credit Assignment (VTCA) (Sec.
[3.3](#S3.SS3 "3.3 Verifier-to-Turn Credit Assignment ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).

### 3.1 Harness-Driven Environment Synthesis

We organize the training environments into $`N`$ task packages:

|     |     |     |
| --- | --- | --- |
|     |

````math
\mathfrak{L}=\left\{\mathcal{P}_{i}=\left\langle C_{i},T_{i},V_{i}\right\rangle\right\}_{i=1}^{N}.
``` |  |

The Work Context $`C_{i}`$ provides files, capabilities, and application
environments; the Task $`T_{i}`$ specifies goals, deliverables, and
constraints; and the Verifier $`V_{i}`$ checks task completion. The
Harness $`H`$ coordinates construction, tracks dependencies, and manages
execution across the three phases in Figure
[3](#S3.F3 "Figure 3 ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution").

#### 3.1.1 Work Context Construction

Phase I constructs a reusable Work Context $`C_{i}`$ comprising File
Context $`C_{i}^{\mathrm{file}}`$, Capability Context
$`C_{i}^{\mathrm{cap}}`$, and App Context $`C_{i}^{\mathrm{app}}`$. We
collect files from project repositories and DeepResearch trajectories,
along with documents and artifacts. After filtering, we profile their
semantics, cross-file relations, type, and editability to form
general-purpose and domain-specific collections. We package installed
skills and plugins with their MCP interfaces, tools, scripts, and
references. These packages form job, file, and app skill libraries. We
instrument mock and installed applications to create executable App
WorkEnvs with a runtime, UI observation, interaction interfaces, and
reset support. Together, these resources supply the three Contexts used
for WorkEnv assembly and task synthesis in Phase II. Figure
[4](#S3.F4.fig1 "Figure 4 ‣ 3.1.1 Work Context Construction ‣ 3.1 Harness-Driven Environment Synthesis ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
summarizes skill-library coverage. Appendix
[B.1](#A2.SS1 "B.1 Work Context Construction ‣ Appendix B Data Construction and Case Studies ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
provides construction details and complexity analysis; Appendix
[B.2](#A2.SS2 "B.2 Synthesis Resources and Coverage ‣ Appendix B Data Construction and Case Studies ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
reports resource coverage.

#### 3.1.2 Long-Horizon Task Synthesis

Phase II synthesizes task $`T_{i}`$ from the three Contexts in $`C_{i}`$
(Figure
[3](#S3.F3 "Figure 3 ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
A construction profile sets the target edit scope (files), interaction
horizon (turns), skill complexity (number and types of combined skills),
distractor ratio, and cross-environment dependencies (Table
[4](#A2.T4 "Table 4 ‣ B.4 Task Synthesis and Quality Control ‣ Appendix B Data Construction and Case Studies ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution");
Appendix
[B.4](#A2.SS4 "B.4 Task Synthesis and Quality Control ‣ Appendix B Data Construction and Case Studies ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
We profile selected file and app instances for task-relevant semantics,
relations, and executability. The Harness $`H`$ then assembles
compatible files, apps, and capabilities into a WorkEnv. Starting from a
job skill, the Skill Matcher fits the task scope to the WorkEnv’s
available resources and combines job, file, and app skills into an
internal workflow whose stages depend on earlier outputs or state
changes. Its dependency graph guides preparation of the Starter WorkEnv
$`x_{v_{i}}`$, including all required resources and marking editable and
protected state. Task instructions specify goals, materials,
deliverables, and constraints. An independent Demonstrator Agent
executes the task from $`x_{v_{i}}`$; success confirms feasibility and
yields a Reference State $`x_{i}^{\star}`$. The Task Instruction,
Starter WorkEnv, and Reference State form the candidate, with state
differences providing evidence of completion. The workflow and reference
execution must not add requirements or exclude other valid solutions. We
remove inputs to test dependency necessity; independently confirmed
compatibility problems trigger FCR (Section
[3.2](#S3.SS2 "3.2 Recursive Environment Evolution ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
Candidates passing construction checks proceed to Phase III for Verifier
synthesis and validation.

#### 3.1.3 Verifier Synthesis and Validation

Phase III synthesizes and validates the Verifier $`V_{i}`$ (Figure
[3](#S3.F3 "Figure 3 ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
We derive an Evaluation Contract from the task instructions and
agent-visible workspace conditions, fixing its criteria before
inspecting the Reference State. The Contract specifies expected
outcomes, allowed edits, protected state, critical criteria, and
admissible evidence. We use it to generate a rubric and verification
rules, binding each criterion to evidence from files, application
states, or state differences. *Infrastructure Validity* returns
$`\mathit{invalid}`$ when infrastructure faults prevent evaluation;
*Canonical State Diff* checks state changes against the Contract;
*Functional Checks* test artifact content and consistency; and *Semantic
Judge* assesses criteria unresolved by executable checks. Valid
evaluations pass only if the weighted outcome score meets its threshold
and all mandatory checks pass; otherwise they fail. We calibrate
$`V_{i}`$ to reject the Starter State and negative cases that violate
the Contract, while accepting the Reference State and independently
obtained valid alternatives. Independently confirmed compatibility
problems may trigger FCR, followed by recalibration under the same fixed
Contract. We then freeze $`V_{i}`$ for a separate, one-time admission
test; candidates that fail are rejected without feedback for further
repair. Passing candidates become admitted packages $`\mathcal{P}_{i}`$
containing the Task Instruction, Starter WorkEnv, Reference State,
rubric, and evidence, with accepted execution traces $`\tau_{i}`$
retained for training. See Appendix
[C.1](#A3.SS1 "C.1 Verifier Specification and Calibration ‣ Appendix C Verifier, Repair, and Training Details ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
for scoring and validation details.

### 3.2 Recursive Environment Evolution

The Work Context, Task, Harness, and Verifier must work together for a
task to run and be evaluated correctly. *Factorial Compatibility Replay*
(FCR) repairs mismatches revealed during construction or later agent
rollouts. Since changing one component can affect the others, FCR tests
proposed changes both individually and jointly, then selects the
smallest validated repair that preserves the task’s original intent.

##### Diagnosis and proposals.

Independent diagnostics first distinguish environment problems from
mistakes in the agent’s decisions. Agent mistakes alone do not trigger
environment changes. For an environment problem, the Harness records the
affected versions and dependencies, keeps task requirements and
validation checks fixed, and freezes one proposed repair per eligible
component: $`\Delta C`$, $`\Delta T`$, $`\Delta H`$, and $`\Delta V`$ as
applicable. The Evaluation Contract remains fixed once grounded in the
task requirements. Edits visible to the agent must preserve information
boundaries, including keeping hidden evaluation evidence hidden. These
edits must also pass checks by a fixed panel of solvers for unintended
task simplification.

##### Harness screening and replay.

For $`d\leq 4`$ eligible components, each combination
$`\chi\in\{0,1\}^{d}`$ specifies which proposals to apply: $`1`$ applies
a proposal and $`0`$ omits it. This gives $`2^{d}`$ combinations, at
most 16. Before rebuilding packages or running rollouts, the Harness
removes combinations with confirmed conflicts in dependencies, resource
bindings, or requirements; uncertain cases proceed to validation. Each
remaining combination is expanded into a dependency-closed update set
$`\Gamma(\chi)=\operatorname{Close}(\chi)`$. This set includes the
selected repairs and all additional updates needed to keep dependent
components compatible, even if those components were not directly
selected for repair. The rebuilt packages are then replayed with the
same agent policies, execution budgets, and random seeds. Comparing
individual and joint repairs reveals whether some changes work only when
applied together. If only the Verifier changes, all alternatives
evaluate the same recorded evidence.

##### Repair selection.

Independent checks must confirm that the original problem is resolved,
required outcomes and information boundaries are preserved, and the
repair introduces no new problems in affected task packages. These
checks do not use agent success or scores from the proposed Verifier as
evidence of resolution. Once a Verifier exists, the repair must also
pass the fixed Contract checks and tests confirming that the Verifier
rejects known failures and accepts valid alternative solutions. Among
the tested repair combinations that pass these checks, FCR selects
$`\chi^{\star}`$ whose full update set $`\Gamma(\chi^{\star})`$ changes
the fewest component versions, counting updates required by
dependencies. Ties favor fewer rebuilt dependencies, then lower cost.

##### Confirmation and update.

Fresh rollouts with new random seeds confirm the selected repair. A
candidate that has not yet been admitted to the training collection
repeats validation from the earliest affected construction step and must
pass initial admission. For an already admitted package, all validated
changes take effect together after confirmation. If repair selection or
confirmation fails, FCR discards an unadmitted candidate or keeps the
previous admitted version. Later rollouts can reveal new mismatches and
initiate another repair cycle. See Appendices
[C.2](#A3.SS2 "C.2 FCR Mechanics and Promotion ‣ Appendix C Verifier, Repair, and Training Details ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
and
[C.3](#A3.SS3 "C.3 FCR Evaluation Protocol ‣ Appendix C Verifier, Repair, and Training Details ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
for details.

### 3.3 Verifier-to-Turn Credit Assignment

Terminal rewards score an entire rollout but provide little guidance
about which turns made progress. VTCA adds feedback from verified
workspace changes and recorded dependencies (Figure
[5](#S3.F5 "Figure 5 ‣ Confirmation and update. ‣ 3.2 Recursive Environment Evolution ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).

##### Trajectory supervision.

We initialize the policy with verified demonstrations using SFT, then
sample RL rollouts for the same task and initial state. Among rollouts
with valid evaluations, terminal rewards combine Verifier outcome scores
and trace scores. Rewards are zero if any critical criterion or
integrity, protected-state, or safety check fails. We standardize
rewards within each group to obtain the trajectory advantage
$`A^{\mathrm{traj}}_{i,r}`$ for task $`i`$ and rollout $`r`$.

##### Measuring progress.

Frozen deterministic checks \[[34](#bib.bib34)\] score supported
criteria before and after each turn. We subtract the earlier score from
the later one, so increases indicate progress and decreases regression.
If either score is unavailable, we emit no local signal. Missing
observations are never treated as zero completion. Checks run on
recorded states without intermediate Judge calls.

##### Assigning turn credit.

At least half of each positive increment stays with the turn that
produced it. The rest is divided equally among earlier turns whose tool
outputs or exact artifact versions were directly used to produce that
progress, as confirmed by recorded dependencies. For example, a turn
that reads a table may share credit when a later turn uses that returned
table to compute a checked result. Merely opening a file does not
qualify. If no earlier turn qualifies, all credit stays local. Negative
increments remain entirely with the turn that produced them.

##### Policy update.

We combine these allocations using normalized criterion weights
$`\bar{w}_{i,k}`$ to obtain criterion-based credit
$`\delta_{i,r,t}^{\mathrm{crit}}`$ for turn $`t`$. We add this credit to
the trajectory advantage and subtract a local trace cost $`c_{i,r,t}`$
for tool errors or unproductive repetition:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{A}_{i,r,t}=\operatorname{sg}\!\left[A_{i,r}^{\mathrm{traj}}+\alpha H_{i,r}\delta_{i,r,t}^{\mathrm{crit}}-\eta c_{i,r,t}\right],\hskip 18.49988pt\alpha,\eta\geq 0,
``` |  | (1) |

Here $`\alpha`$ and $`\eta`$ weight progress credit and local trace
cost, and $`\operatorname{sg}`$ stops gradients. The gate $`H_{i,r}`$ is
1 only when integrity, protected-state, and safety checks pass. An
unfinished rollout can retain progress credit, while violations disable
it for every turn. Clipped GRPO \[[27](#bib.bib27)\] averages token
contributions within each turn, then turns within each trajectory, so
lengthy turns do not dominate the update. Setting $`\alpha=\eta=0`$
recovers our episode-only baseline. The reliability of this shaping
signal depends on checker coverage and dependency records (Appendix
[C.4](#A3.SS4 "C.4 Verifier-to-Turn Credit Assignment ‣ Appendix C Verifier, Repair, and Training Details ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).

## 4 Experiments

### 4.1 Experimental Setup

##### Model and training data.

We post-train Qwen3.5-35B-A3B \[[25](#bib.bib25)\] to obtain
WorkRover-35B-A3B. Supervised fine-tuning (SFT) uses 30,115 trajectories
generated by Qwen3.5-397B-A17B in synthesized workspaces; all pass task
verification and quality checks. For reinforcement learning (RL), we
independently synthesize 20,000 task–Verifier pairs and screen each pair
with four Qwen3.5-35B-A3B pilot rollouts. Consistency filtering retains
3,200 pairs for training. Starting from the SFT checkpoint, the model
collects online rollouts on these tasks and learns with VTCA-GRPO (Sec.
[3.3](#S3.SS3 "3.3 Verifier-to-Turn Credit Assignment ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
Subset-selection details are in Appendix
[D.1](#A4.SS1 "D.1 Experimental Setup ‣ Appendix D Evaluation Details Referenced in the Main Text ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution").

##### Evaluation.

We evaluate transfer to five external benchmarks: JobBench
\[[16](#bib.bib16)\] for occupational tasks, GDPval \[[1](#bib.bib1)\]
for professional deliverables, AutomationBench \[[28](#bib.bib28)\] for
cross-application workflows, WorkBuddy Bench (Office)
\[[35](#bib.bib35)\] for office workflows, and OfficeQA Pro
\[[21](#bib.bib21)\] for document-grounded question answering. We use
each benchmark’s official evaluator and aggregate metric, reporting
GDPval in Elo and the other four scores as percentages. Table
[1](#S4.T1 "Table 1 ‣ 4.2 Main Results ‣ 4 Experiments ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
compares WorkRover with its backbone, other 27–35B open-weight models,
open-weight models above 400B, and proprietary models. Published
reference scores retain their original task subsets, evaluators, and
harnesses. Our training and evaluation setup is described in Appendix
[D.1](#A4.SS1 "D.1 Experimental Setup ‣ Appendix D Evaluation Details Referenced in the Main Text ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution").

### 4.2 Main Results

WorkRover-35B-A3B improves on its Qwen3.5-35B-A3B backbone across all
five external benchmarks (Table
[1](#S4.T1 "Table 1 ‣ 4.2 Main Results ‣ 4 Experiments ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
Among the percentage-based scores, the largest gains are on OfficeQA Pro
(+29.32 percentage points) and JobBench (+26.27 points), followed by
AutomationBench (+22.67 points) and WorkBuddy Bench (Office) (+13.63
points). GDPval v2 increases from 804.75 to 1218.00 Elo, a gain of

professional deliverables, and application workflows, supporting
transfer beyond the synthesized training workspaces.

Among the listed 27–35B open-weight models, WorkRover has the highest
reported score on every benchmark. Occamy-1.0 has the second-highest
reported score in this group on each benchmark. The largest
percentage-point gap between the two models is on WorkBuddy Bench
(Office): 74.13% versus 66.65%, a margin of 7.48 points. The JobBench

Compared with larger and proprietary models, WorkRover’s relative

### 4.3 Ablations and Analysis

#### 4.3.1 Verifier-to-Turn Credit Assignment

#### 4.3.2 Recursive Environment Evolution

We compare repair methods using Qwen3.5-35B-A3B under matched proposal
and replay budget caps. Safe Resolution Rate (SRR) measures how often a
defect is fixed without causing new failures in related tasks; repairs
must also pass fresh-seed confirmation and a held-out audit. FCR raises
SRR on naturally occurring defects from 60.7% with full regeneration to
70.3% (Figure
[7](#S4.F7 "Figure 7 ‣ Joint repair and repeated evolution. ‣ 4.3.2 Recursive Environment Evolution ‣ 4.3 Ablations and Analysis ‣ 4 Experiments ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")(b)).
It also reduces changes to task intent from 14.3% to 1.3% while using
fewer model tokens (relative cost: 1.00 versus 1.34).

##### Choosing compatible edits.

With repair proposals fixed, Table
[3](#S4.T3 "Table 3 ‣ 4.3.3 Construction Pipeline ‣ 4.3 Ablations and Analysis ‣ 4 Experiments ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
tests selection separately from proposal generation. Compared with
applying all edits (Apply-all), FCR raises SRR by 9.0 percentage points
on natural defects and 10.4 points on injected defects, and reduces
cross-task regression from 7.0% to 0.7%. Testing edit combinations thus
improves repair reliability, at a higher model-token cost (1.00 versus
0.59).

##### Joint repair and repeated evolution.

With proposals fixed, 48–74% of safely resolved cases require joint
edits, depending on the component pair: no smaller subset of the
selected edits passes the same repair checks (Figure
[7](#S4.F7 "Figure 7 ‣ Joint repair and repeated evolution. ‣ 4.3.2 Recursive Environment Evolution ‣ 4.3 Ablations and Analysis ‣ 4 Experiments ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")(a)).
Across three generations, SRR stays at 70.3–72.4% and audit pass rate at
93.8–94.6% (panel c), showing little change in repair quality across
these rounds. FCR’s task success rate also increases over five repair
iterations (panel d).

##### Repairing initial candidates.

FCR also improves initial construction. With the candidate set and
repair budget caps fixed, synthesis pass rate reaches 74.8%, compared
with 49.8% before repair and 68.8% with full regeneration. Repair
therefore recovers more tasks that pass validation from the same initial
pool.

#### 4.3.3 Construction Pipeline

We remove one construction component at a time (Table
[3](#S4.T3 "Table 3 ‣ 4.3.3 Construction Pipeline ‣ 4.3 Ablations and Analysis ‣ 4 Experiments ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")).
Task yield measures the fraction of initial candidates that pass
validation. The largest drops come from removing relation-aware
expansion (74.8% to 52.6%) or validation-guided rewriting (74.8% to
49.8%). These results highlight the value of following file dependencies
and repairing construction errors.

Reference execution and agent success decline as well. Removing
relation-aware expansion lowers them from 95.1% and 58.7% to 77.9% and
41.8%, respectively. Removing file–skill grounding also reduces both
measures, supporting the need to match each file with operations that
can use it. The semantic-only baseline performs worse on all three
measures, suggesting that topical similarity alone is insufficient for
assembling executable workspaces. Success rates use the same frozen
agent but are measured on each variant’s retained workspaces, so they
can also reflect differences in which tasks are admitted.

##### Rewriting on the same initial tasks.

To control for differences in task selection, we compare filtering with
and without rewriting on the same 10,000 initial task intents. Both
variants preserve the required outcomes and use the same frozen agent.
Adding rewriting raises admission from 49.8% to 74.8% and end-to-end
success from 22.2% to 43.9%. Reference execution also rises from 80.0%
to 92.0%, and Verifier validity from 70.0% to 87.0%. Unconstructed,
rejected, and budget-exhausted intents remain in the denominator and
contribute no successful completion. The resulting gains therefore
measure the full pipeline, from initial construction through agent
execution, on the same starting task set.

## 5 Conclusion

WorkRover uses execution feedback to improve both long-horizon cowork
agents and the environments used to train them. The Harness keeps work
contexts, tasks, and verifiers aligned during construction and repair.
FCR revises inconsistent components while preserving task requirements,
and VTCA uses verified workspace progress to guide learning at
individual turns. Experiments show that FCR increases the share of tasks
that pass validation and repairs defects with fewer unintended changes
to task intent and fewer regressions on related tasks. Under matched
rollout budgets, VTCA outperforms episode-only GRPO on all five
benchmarks. These findings support recursive environment evolution as a
practical foundation for reliable long-horizon cowork agent training.

## Appendix A Extended Related Work

##### Executable environments and task synthesis.

Professional agent training requires executable tasks, recoverable
state, and observable outcomes across related artifacts. AppWorld
provides controllable application environments; EnvScaler supports
programmatic environment construction, while ClawGym materializes
workspaces around task and capability requirements \[[36](#bib.bib36),
[30](#bib.bib30), [2](#bib.bib2)\]. Agent-World uses capability
diagnostics to expand tool/database environments \[[7](#bib.bib7)\].
ToolForge constructs virtual-tool tasks, and MetaTask and CLI-Universe
emphasize executable validation \[[4](#bib.bib4), [18](#bib.bib18),
[22](#bib.bib22), [12](#bib.bib12)\]. These approaches organize
synthesis around task bundles, environment expansion, or capability
requirements. WorkRover grounds task construction in file relations and
professional skills, then assembles Tasks and Verifiers within
recoverable Work Contexts under a versioned Harness. Shared contexts
also make dependency tracking and revalidation necessary when one
component changes.

##### Grounded acceptance and verifier reliability.

Acceptance checks must agree with the instruction and the evidence
available in the workspace. ANCHOR constructs instructions,
environments, solutions, and verifiers from a shared workflow
specification \[[13](#bib.bib13)\]. FACET grounds artifacts in shared
state and repairs inconsistencies while preserving source intent
\[[29](#bib.bib29)\]. Hacker–Fixer audits tests and environments with
adversarial cases while checking legitimate solutions
\[[47](#bib.bib47)\]. Stronger rejection checks therefore need to be
considered alongside false rejection of valid alternatives. WorkRover
freezes instruction-grounded requirements and criterion–evidence
bindings, then evaluates implementations using violating mutants and
independently valid solutions. Reference artifacts supply recomputable
anchors without adding requirements. Infrastructure-invalid episodes are
distinguished from policy failures. Validation remains limited to the
declared Contract and the coverage of the controls.

##### Environment evolution and repair selection.

Envs-FORGE studies joint revision of instructions, fixtures, solutions,
tests, and environments, while EchoVerse studies executable environment
evolution \[[39](#bib.bib39), [23](#bib.bib23)\]. FACET routes failed
validation to implicated artifacts and repeats validation from a clean
state \[[29](#bib.bib29)\]. Program repair likewise studies patch
minimization: GenProg reduces test-passing patches through structural
differencing and delta debugging \[[38](#bib.bib38)\]. FCR freezes
component-level proposals over Context, Task, Harness, and Verifier
before replaying their combinations. Materialization includes
dependency-induced changes, and promotion checks affected retained tasks
for regressions under fixed requirements. The selected repair is the
smallest admissible closed edit set among the tested combinations;
bounded enumeration does not establish a global minimum over all
possible repairs. This separates proposal generation, compatibility
selection, and validation of a shared environment revision.

##### Local progress in long-horizon learning.

Methods differ in the evidence used to assign local feedback. GiGPO uses
state comparisons, while HiPER uses a planning hierarchy
\[[8](#bib.bib8), [24](#bib.bib24)\]. TRACE forms temporal differences
in frozen-model reference-answer likelihoods, with bounded look-ahead
for delayed tool effects \[[34](#bib.bib34)\]. TRCA combines
deterministic transition-rubric scores with increments in cumulative
condition coverage \[[46](#bib.bib46)\]. VTCA instead evaluates
successive observable workspace states with frozen checkers. Signed
progress can register both completion and setbacks in persistent,
mutable artifacts. Unsupported or unavailable evidence supplies no local
signal, while terminal evaluation remains applicable to supported task
outcomes. These differences concern the feedback source and its
coverage; they do not by themselves establish the comparative
effectiveness of individual components.

##### Evidence attribution and shaping limits.

STAMP maps verified citations to first-exposure actions; DRACO uses
judge-attributed steps with sign-preserving GRPO advantage
redistribution \[[43](#bib.bib43), [9](#bib.bib9)\]. VTCA follows
recorded direct use of exact tool outputs or artifact versions,
assigning at most half of positive progress to eligible prerequisite
turns and leaving negative increments local. Access alone creates no
dependency edge. Incorrect provenance can misallocate credit, and missed
links leave prerequisites unrepresented. Recorded use therefore does not
establish causal necessity. Potential-based reward shaping preserves
optimal policies under stated assumptions \[[19](#bib.bib19)\]; VTCA is
formulated as workspace-grounded advantage shaping. Conservation of
checker increments before gating, costs, and clipping establishes
neither policy invariance nor an unbiased policy-gradient estimate.

## Appendix B Data Construction and Case Studies

### B.1 Work Context Construction

For each source workspace $`w`$, the index $`I(w)`$ stores a typed graph
$`G_{w}=(V_{w},E_{w})`$ with files or versions as nodes and semantic,
structural, temporal, provenance, and workflow edges. Directory
co-location is only a weak structural signal. A job skill specifies its
professional setting, workflow, materials, and deliverables. The Skill
Matcher retrieves related file regions, then expands them through file
and application skills with compatible inputs, outputs, and interfaces.
The Harness validates dependencies, permissions, bindings, reset,
recovery, and evidence capture. Recorded lineage and derived task
branches stay in one data split.

##### Construction complexity.

Let $`J`$ be the number of job skills, $`W`$ the number of source
workspaces, $`k`$ the number of shortlisted regions per job skill, and
$`M\leq Jk`$ the number of candidates retained for environment assembly.
Let $`C_{\mathrm{index}}`$ and $`C_{\mathrm{retrieve}}`$ denote
per-workspace indexing and per-job-skill retrieval costs;
$`C_{\mathrm{agent}}`$, $`C_{\mathrm{match}}`$, and $`C_{\mathrm{env}}`$
denote per-candidate agent inspection, skill matching, and
environment-assembly costs. Excluding source collection and one-time
pool construction, the total cost of indexed Work Context construction
is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
O(WC_{\mathrm{index}})+O(JC_{\mathrm{retrieve}})+O\!\left(Jk(C_{\mathrm{agent}}+C_{\mathrm{match}})\right)+O(MC_{\mathrm{env}}).
``` |  | (2) |

Agent inspection covers the $`Jk`$ shortlisted candidates, with cost
$`O(JkC_{\mathrm{agent}})`$, whereas exhaustive job–workspace inspection
incurs $`O(JWC_{\mathrm{agent}})`$. This comparison concerns agent
inspection; indexing, retrieval, skill matching, and environment
assembly remain separate costs. The index is reusable across job-skill
queries, so its construction cost is paid once for a fixed source
collection.

##### Inventory and source identity.

Files are inventoried by relative path, format, size, and content hash.
Bounded previews expose headings, workbook sheets, or archive members
for selective reading. Captured sources and independently retained,
readable notes, tables, or reports may enter the Starter State after
relevance and leakage checks. Raw conversations, tool logs, internal
analysis caches, provenance directories, and unsupported web caches are
excluded. The original query informs construction only and is not Solver
evidence. Source pointers support audit; a URL cannot replace a required
local file. Citations in notes must be checked against their sources.
Co-occurrence, retrieval order, and model assertions do not establish
dependencies; missing lineage is unresolved. Freezing files does not
make historical searches or services replayable. Unavailable required
sources lead to revision or rejection; permitted new retrieval follows
the Harness contract and records its evidence separately.

##### Branch plans and answer leakage.

A job skill’s requirements guide eligible-file retrieval within one
source collection. File skills bind the required operations; app skills
bind any instrumented application capabilities. Branches must differ in
professional decisions, operations, or principal products, and cannot
import unselected files or combine source collections. A feasible Branch
Plan becomes a workspace and Task Blueprint specifying file roles,
dependencies, deliverables, and modification/preservation constraints.
Every required outcome has an observable criterion. A write
acknowledgment or readback excerpt alone is not an editable artifact.
Retained notes require evidence for their claims; inputs that already
complete the new task cause revision or rejection. Hidden plans,
solution keys, and evaluation records stay outside Solver inputs and
cannot supply unstated requirements or inaccessible task evidence.

##### Fresh execution, verification, and lineage.

The instruction and selected files/application state define a frozen
Starter State. A fresh Demonstrator establishes feasibility and a
Reference State; historical session completion cannot substitute. The
Contract uses only the instruction and visible invariants, with
independently recomputable anchors. Admission requires rejection of the
Starter State and violating mutants, acceptance of valid Reference
States and alternatives, and protected-state checks. Branches retain
collection, session, and file-version lineage. Sessions, retained
collections, candidates, and admitted tasks are counted separately;
branch count alone does not establish independent diversity.

## Appendix C Verifier, Repair, and Training Details

### C.1 Verifier Specification and Calibration

Criteria derive from the instruction, Starter State, and visible
invariants; Reference artifacts only instantiate independently
recomputable anchors. The frozen Contract specifies editable/protected
state, allowed transitions, and each criterion’s predicate, evidence,
checking mode, weight $`w_{k}`$, threshold $`\gamma_{k}`$, and critical
flag $`b_{k}`$. Unresolved requirements prevent admission. Adapters and
canonical diffs provide stable evidence IDs. Executable checks read both
snapshots; at most one batched Judge call receives frozen
criterion-tagged evidence, has no live tools, and cites evidence or
abstains. For scores $`p_{i,k}\in[0,1]`$, set
$`y_{i,k}=\mathbf{1}[p_{i,k}\geq\gamma_{i,k}]`$ and
$`\bar{w}_{i,k}=w_{i,k}/\sum_{j}w_{i,j}`$:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
S_{B,i}=\sum_{k}\bar{w}_{i,k}p_{i,k},\qquad H_{i}=g_{i}^{\mathrm{integrity}}g_{i}^{\mathrm{protected}}g_{i}^{\mathrm{safety}},\qquad G_{i}=H_{i}\prod_{k:b_{i,k}=1}y_{i,k}.
``` |  | (3) |

Healthy evaluation passes iff $`G_{i}=1`$ and $`S_{B,i}\geq\tau_{B}`$.
Missing required state implies failure; infrastructure-unavailable
evidence implies invalidity. Policy errors under healthy infrastructure
are not invalid. Partial credit cannot offset gates. Auxiliary
$`S_{A}\in[0,1]`$ uses frozen trace checks. Admission requires the
Starter–Reference contrast, protected-state checks, no unresolved
invalid controls, and frozen thresholds for criterion agreement,
worst-family mutant detection, and valid-alternative acceptance.
Task-level negatives must violate the Contract. Calibration, initial
admission, reporting, and promotion use disjoint recipe–seed banks.
Unsupported semantic criteria retain terminal supervision without local
progress signals.

### C.2 FCR Mechanics and Promotion

Freeze one direct proposal per available Context/Task/Harness/Verifier
factor before replay: at most 16 cells, or eight before compilation.
Each cell $`\chi`$ applies the dependency-closed update set
$`\Gamma(\chi)`$, including dependency-induced updates; changed tasks
require fresh execution/compilation, and shared Harness edits require
affected-task checks. Established conflicts make cells unavailable;
uncertain cells proceed to materialization. Candidate repair returns to
the earliest affected gate; maintenance freezes the admitted parent.
Both preserve intent, outcomes, transitions, and applicable Contract
weights, thresholds, flags, and gates. Hidden evidence cannot leak into
visible edits; new tools require separate releases and semantic changes
create new candidates. Blinded equivalence review and a frozen solver
panel apply development-fixed simplification margins.

Matched Context–Task–Harness seeds produce evidence reused by Verifier
variants. Health uses all seeds; outcome contrasts use common healthy
seeds on complete compatible subcubes, without imputation. Verifier
contrasts use sealed label agreement. Selection requires a
proposal-independent defect/health predicate, proposal-disjoint replay,
equivalence, no affected-task regression, and compiled-Verifier
calibration plus a one-use binary promotion shard. Reporting audits
never select repairs. The smallest validated closed edit set
$`\Gamma(\chi^{\star})`$ among tested cells receives fresh-seed
confirmation (Section
[3.2](#S3.SS2 "3.2 Recursive Environment Evolution ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution"));
failure discards candidates or retains maintenance parents and
quarantines unresolved triggers.

### C.3 FCR Evaluation Protocol

Frozen stratified screening of the 10K pool targets 300 natural
mismatches, classified by two blinded reviewers with third-reviewer
adjudication. The separate controlled cohort injects 260 concealed
Contract-preserving defects: 80 single-, 120 pair-, 40 triple-, and 20
four-factor cases. Candidate-controlled comparisons share proposals;
end-to-end comparisons allow independent proposals under matched caps.
Each distinct Context–Task–Harness configuration uses five matched
seeds; compatible Verifiers reuse evidence. Confirmation seeds and
generation-specific promotion shards are disjoint. Joint necessity
excludes passing strict proposal subsets. Triggers are statistical
units; seeds/cells are nested measurements.

### C.4 Verifier-to-Turn Credit Assignment

Canonical traces retain ordering, call/result IDs, tool definitions,
versions, and state metadata. SFT supervises agent tokens; invalid
rollouts receive no training signal. For valid rollout $`r`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
R_{i,r}=G_{i,r}[(1-\lambda)S_{B,i,r}+\lambda S_{A,i,r}],\quad A^{\rm traj}_{i,r}=\frac{R_{i,r}-\bar{R}_{i}}{\max(\operatorname{sd}_{r^{\prime}}R_{i,r^{\prime}},\sigma_{R,\min})},\quad 0\leq\lambda\leq 0.1.
``` |  | (4) |

The denominator floor is development-fixed. Deterministic progress
$`\Delta_{i,r,t,k}=\phi_{i,k}(x_{i,r,t+1})-\phi_{i,k}(x_{i,r,t})`$
requires both endpoints evaluable; otherwise record zero increment and a
missing reason. Missing intervals are not bridged or treated as zero
completion. No intermediate Judge is called. Prerequisite set
$`\mathcal{P}_{i,r,s,k}`$ deduplicates earlier producer turns whose
exact outputs/versions are directly consumed at $`s`$, with
criterion-compatible immutable IDs and call/result links. Stale,
ambiguous, inferred, and unrecorded uses are excluded. With
$`\rho_{i,r,s,k}=\rho\mathbf{1}[|\mathcal{P}_{i,r,s,k}|>0]`$ and
$`0\leq\rho\leq 1/2`$,

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle b_{i,r,s,t,k}`$ | $`\displaystyle=\begin{cases}1-\rho_{i,r,s,k},&t=s,\\
\rho_{i,r,s,k}/|\mathcal{P}_{i,r,s,k}|,&t\in\mathcal{P}_{i,r,s,k},\\
0,&\text{otherwise},\end{cases}`$ |  | (5) |
|  | $`\displaystyle\delta_{i,r,t}^{\mathrm{crit}}`$ | $`\displaystyle=\sum_{k}\bar{w}_{i,k}\left[\sum_{s=t}^{T_{i,r}-1}b_{i,r,s,t,k}\max(\Delta_{i,r,s,k},0)+\min(\Delta_{i,r,t,k},0)\right].`$ |  |  |

Allocation is direct; negatives and empty-set increments stay local.
Weights are not renormalized over observed criteria or centered across
turns. Equation
[1](#S3.E1 "Equation 1 ‣ Policy update. ‣ 3.3 Verifier-to-Turn Credit Assignment ‣ 3 Method ‣ : Scaling Long-Horizon Cowork Agent Training Via Recursive Environment Evolution")
gates progress by $`H`$, terminal reward by $`G`$. Trace cost
$`c_{t}\in[0,1]`$ covers malformed/error calls, redundant
state-preserving actions, and attributable protected-state/safety
violations. GRPO averages tokens within turns, turns within
trajectories, then trajectories within task groups, using fixed behavior
policy, SFT reference, and detached advantages. Before
gating/cost/clipping,
$`\sum_{t}\delta_{i,r,t}^{\mathrm{crit}}=\sum_{k}\bar{w}_{i,k}\sum_{t}\Delta_{i,r,t,k}`$;
only complete observations telescope. Write–revert cycles and wrong
provenance can still alter updates.
````
