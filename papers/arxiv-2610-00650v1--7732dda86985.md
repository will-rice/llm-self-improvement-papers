###### Abstract

The performance of AI coding agents is highly dependent on their
underlying coding rules. However, existing coding rules are typically
hand-crafted and fixed, making the process labor-intensive and often
suboptimal. In this work, we propose _RuleEvolve_ , a self-evolving
framework for coding rules. RuleEvolve maintains a pool of candidate
coding rules and iteratively improves them. In each iteration, it
employs an LLM-powered _mutator module_ to generate variants from
existing candidates, and then uses a _judge module_ to evaluate these
variants and update the pool with the best-performing ones. Extensive
evaluations across two coding-agent frameworks, four backbone LLMs, and
three benchmarks demonstrate that RuleEvolve outperforms both manual
engineering and existing prompt optimization baselines in terms of
functional correctness of the generated code, code length, and/or
generation cost (e.g., tokens used).

## 1 Introduction

The evolution of AI coding agents, such as OpenHands [Wang et al.
(2025)](#bib.bib23), OpenCode [Anomalyco (2025)](#bib.bib24), Claude
Code [Anthropics (2025)](#bib.bib25), and Cursor [Cursor
(2025)](#bib.bib26), has fundamentally redefined code generation tasks
by shifting the focus from manual implementation to high-level
orchestration. Central to the performance of these agents is the coding
rules file, often instantiated as an AGENTS.md document and prepended to
the backbone model’s input context [Agentsmd (2025)](#bib.bib2). These
rules play a critical role in determining the correctness and length of
the generated code, as well as the associated generation cost.

Despite the critical importance of these rules, they are currently
almost exclusively hand-crafted by human developers [PatrickJS
(2025)](#bib.bib1). This manual process is inherently labor-intensive
and suboptimal, as human-written rules often lack task-specific
alignment and can even degrade agent performance [Gloaguen et al.
(2026)](#bib.bib6).

Although automatic techniques [Wu et al. (2025)](#bib.bib12) for prompt
optimization have been developed, these methods remain difficult to
directly apply to self-evolving coding rules. Existing approaches
primarily target short, few-sentence instructions, whereas coding rules
are typically long, well-documented guidance that present a
significantly larger search space. Furthermore, the resource-intensive
nature of coding agents renders previous random mutation strategies
computationally prohibitive. Consequently, there is a critical need for
a framework that can automatically evolve complex coding rules.

To bridge this gap, we propose RuleEvolve, a self-evolving framework for
coding rules. The overall pipeline is illustrated in
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Self-Evolving Coding Rules for AI Coding Agents").
RuleEvolve takes as input a set of coding tasks and aims to evolve
coding rules that can generalize to improve code generation on other
tasks. Specifically, RuleEvolve maintains a pool of $`m`$ candidate
coding rules and iteratively evolves them. In each iteration, it employs
an LLM-powered _mutator module_ to generate $`N`$ mutations from the
current candidates. Each mutation is then evaluated by a _judge module_,
which assesses performance in terms of code correctness, code length,
and generation cost. Based on these evaluations, RuleEvolve updates the
pool by retaining the top-performing $`m`$ candidates.

![Refer to caption](2610.00650v1/RuleEvolve.png)

Figure 1: Pipeline of RuleEvolve.

One challenge is how to allocate the $`N`$ mutations among the $`m`$
candidates in the pool in each iteration. Naive strategies, which
distribute mutations equally or proportionally based on each candidate’s
performance, produce suboptimal results, as demonstrated in our
experiments. To enhance effectiveness, we propose a strategic
mutation-allocation method, which dynamically distributes the $`N`$
mutations by prioritizing candidates with higher performance variance or
those whose mean performance is closer to the current best.

We evaluate RuleEvolve across two coding-agent frameworks, four backbone
LLMs, and three coding benchmarks. Extensive experiments show that the
proposed method consistently maintains or improves functional
correctness measured by pass rate, while significantly reducing code
length and generation cost, as measured by generation time and token
usage. For instance, on the BigCodeBench dataset using the OpenAI SDK
with gpt-5.3-codex, RuleEvolve successfully reduced average code length
by over 60% without sacrificing pass rate.

## 2 Related Works

### 2.1 AI-assisted Code Generation

The landscape of software engineering has been transformed by
AI-assisted code generation. To evaluate these AI-generated code, the
research community has established several coding benchmarks, such as
HumanEval [Chen et al. (2021)](#bib.bib20) and BigCodeBench [Zhuo et al.
(2025)](#bib.bib21), which assess the ability of models to generate
executable and functional code across a variety of programming tasks.
Recent works [Midolo et al. (2026)](#bib.bib3); [Ye et al.
(2025)](#bib.bib4) have sought to enhance the quality of generated code
through prompting strategies. However, these efforts primarily focus on
the performance of the underlying coding LLM in isolation rather than
within the agentic framework. Furthermore, these studies focus on the
optimization of task-specific prompts to the coding LLM, without
considering the self-evolving of the coding rules that guide the code
generation process universally.

### 2.2 Coding Rules for AI Coding Agents

AI coding agents rely on coding rules, typically stored in an AGENTS.md
file, to guide the generation of code. These rules and guidance are
combined with the system and user prompts to serve as input for the
backbone LLM. The specific rules provided influence the structure and
style of the generated code. While recent works [Galster et al.
(2026)](#bib.bib5); [Gloaguen et al. (2026)](#bib.bib6); [Chen et al.
(2026)](#bib.bib7) have explored the impact of these rules on code
generation, these studies primarily focus on measurement without
providing practical insights into how these coding rules can be
systematically improved or evolved.

### 2.3 Self-evolving Agents

Existing studies on self-evolving agents primarily focus on models,
tools, skills, and memory [Yang et al. (2026)](#bib.bib11); [Shao et al.
(2026)](#bib.bib10); [Sun et al. (2026)](#bib.bib9); [Zhang et al.
(2026)](#bib.bib8). While coding rules are central to coding agents,
their self-evolving remains largely unexplored. Automatic prompt
optimization techniques [Wu et al. (2025)](#bib.bib12); [Khattab et al.
(2024)](#bib.bib13); [Tong et al. (2025)](#bib.bib14); [Fernando et al.
(2023)](#bib.bib15); [Nag et al. (2025)](#bib.bib16); [Mehrotra et al.
(2024)](#bib.bib17); [Chao et al. (2025)](#bib.bib18); [Jiang et al.
(2026)](#bib.bib19) can theoretically be applied to optimize coding
rules; however, these methods primarily target short prompts consisting
of only a few sentences. In contrast, coding rules are extensive,
well-documented sets of instructions that create a significantly larger
search space beyond the capability of existing optimizers. Consequently,
applying current prompt optimization techniques directly to coding rules
yields suboptimal performance, as confirmed by our experiments with
Prompt-Ops [Wu et al. (2025)](#bib.bib12).

## 3 Problem Definition

### 3.1 AI Agents for Code Generation

We consider an AI coding agent $`\mathcal{A}_{\theta}`$ powered by a
backbone LLM with parameters $`\theta`$. The agent generates code
conditioned on a specific programming task and underlying coding rules.
In practice, for most modern coding agents, these rules are instantiated
via an AGENTS.md document and prepended to the LLM’s input context.

Let $`x\in\mathcal{X}`$ denote a coding task (i.e., the problem
description), $`r`$ denote the coding rules, and $`y`$ denote the
generated code, where $`\mathcal{X}`$ is the coding task set. Formally,
the coding agent $`\mathcal{A}_{\theta}`$ samples the code $`y`$ from
the conditional distribution:

|     |                                                    |     |     |
| --- | -------------------------------------------------- | --- | --- |
|     | $`\displaystyle y\sim p_{\theta}(\cdot\mid x,r).`$ |     | (1) |

Given a coding task $`x`$ and fixed parameters $`\theta`$, the coding
rules $`r`$ significantly influence the code generation process, thereby
affecting the correctness, length, and inference cost. While correctness
ensures the functional integrity of the code, length and inference cost
are equally critical for real-world deployment. Code length determines
the performance of the generated code, where optimized logic reduces
execution latency and resource consumption. Inference cost directly
affect the scalability of the agentic system; by minimizing token usage
and generation time, developers can substantially lower API expenses and
improve the responsiveness of the development cycle. Formally, we define
two primary goals for the coding rule self-evolving process:

- •
  The generated code $`y`$ should be executable and functionally
  correct.
- •
  The evolved coding rules should reduce the code length as possible and
  minimize inference costs during the generation process.

### 3.2 Objective

To satisfy the first goal, we define a correctness constraint. Let
$`\mathcal{V}(x,y)\in\{0,1\}`$ be a code verifier that determines
whether code $`y`$ is executable and correctly solves the programming
task $`x`$, where $`\mathcal{V}(x,y)=1`$ indicates success. In practice,
$`\mathcal{V}`$ may be implemented by executing $`y`$ against a set of
test cases associated with $`x`$. The evolved coding rules $`r`$ must
satisfy:

|     |                          |             |                                                                                                   |
| --- | ------------------------ | ----------- | ------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle\frac{1}{ | \mathcal{X} | }\sum*{x\in\mathcal{X}}\mathbb{E}*{y\sim p\_{\theta}(\cdot\mid x,r)}[\mathcal{V}(x,y)]\geq\tau,`$ |     | (2) |

where $`\tau`$ is a predefined threshold ensuring that the average
correctness rate of the agent $`\mathcal{A}_{\theta}`$ across the task
set $`\mathcal{X}`$ remains acceptable.

To satisfy the second goal, we define a code-length score $`E(y)`$ and a
cost score $`C(\mathcal{A}_{\theta},x,r)`$. A higher $`E(y)`$ indicates
that the generated code $`y`$ is more concise, while a higher
$`C(\mathcal{A}_{\theta},x,r)`$ indicates lower resource consumption
during the generation process. Formally, the coding rule self-evolving
process is expressed as the following constrained optimization problem:

|     |                                |                          |             |                                                                                                         |
| --- | ------------------------------ | ------------------------ | ----------- | ------------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle\max_{r}\quad`$ | $`\displaystyle\frac{1}{ | \mathcal{X} | }\sum*{x\in\mathcal{X}}\mathbb{E}*{y\sim p*{\theta}(\cdot\mid x,r)}[E(y)+C(\mathcal{A}*{\theta},x,r)]`$ |     |     |
|     | s.t.                           | $`\displaystyle\frac{1}{ | \mathcal{X} | }\sum*{x\in\mathcal{X}}\mathbb{E}*{y\sim p\_{\theta}(\cdot\mid x,r)}[\mathcal{V}(x,y)]\geq\tau.`$       |     | (3) |

## 4 RuleEvolve

### 4.1 Overview

To achieve these objectives, we propose RuleEvolve, a self-evolving
framework for coding rules. As illustrated in
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Self-Evolving Coding Rules for AI Coding Agents"),
RuleEvolve consists of three primary components: a rule pool of fixed
size $`m`$, a _mutator module_ for generating mutated candidates, and a
_judge module_ for evaluation and selection. Given the initial coding
rules $`r`$, RuleEvolve first employs the mutator module to populate the
pool with $`m`$ mutated versions. In each subsequent iteration, $`N`$
newly mutated candidates are generated from $`m`$ candidates in the
current pool. Mutations are strategically allocated based on the
historical mean and variance of the candidates’ scores. Finally, the
$`m+N`$ candidates are evaluated by the judge module; the top $`m`$
candidates are retained for the next iteration, while others are pruned.

Challenge and motivation:  The self-evolving of coding rules presents
two key challenges. First, the generation process in a coding agent
typically involves multi-turn interactions and external tool-calling,
rendering the pipeline non-differentiable and precluding direct
gradient-based optimization. We address this by implementing an
iterative mutation and pruning framework that leverages the mutator
module and the judge module to approximate the optimization process (see
Section [4.2](#S4.SS2 "4.2 Iterative Mutation and Pruning ‣ 4 RuleEvolve ‣ Self-Evolving Coding Rules for AI Coding Agents")).
Second, unlike standard prompt optimization tasks that involve short
targets and low evaluation costs, coding rules are significantly more
resource-intensive to evolve. Each rule set requires full agent
execution and verification, leading to substantial latency and API token
consumption. To avoid resource waste and enhance effectiveness, we
propose a strategic mutation-allocation method that prioritizes mutating
promising candidates, as detailed in
Section [4.3](#S4.SS3 "4.3 Strategic Mutation Allocation ‣ 4 RuleEvolve ‣ Self-Evolving Coding Rules for AI Coding Agents").

### 4.2 Iterative Mutation and Pruning

Mutator $`\mathcal{M}`$:  The mutator module, powered by an LLM, takes
the coding rules $`r`$ and a mutation guidance $`g`$ as input to produce
a mutated candidate $`r_{m}=\mathcal{M}(r,g)`$. The mutation guidance
$`g`$ typically consists of a natural language directive, such as:
_"Mutate the coding rules for an AI coding agent into a new variant by
improving wording, reordering or combining steps, and varying the
style."_

Judge $`\mathcal{J}`$:  The Judge module provides the evaluation
environment for generating code under specific coding rules, executing
the generated code, and assessing performance across the dimensions of
correctness, length, and inference cost. Specifically, the Judge
$`\mathcal{J}`$ takes the coding rules $`r`$, the agent
$`\mathcal{A}_{\theta}`$, and a task set $`\mathcal{X}`$ as input to
produce a score $`S=\mathcal{J}(r,\mathcal{A}_{\theta},\mathcal{X})`$.

As formulated in
Section [3.2](#S3.SS2 "3.2 Objective ‣ 3 Problem Definition ‣ Self-Evolving Coding Rules for AI Coding Agents"),
this score consists of two components. The first is a correctness
penalty designed to ensure that the evolved rules do not degrade the
agent’s functional performance. Given the code verifier $`\mathcal{V}`$,
the penalty is defined as:

|     |                                                                                                                                                          |     |     |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle\mathbb{E}_{x\in\mathcal{X}}\left[\mathcal{V}(x,\mathcal{A}_{\theta}(x,\emptyset))-\mathcal{V}(x,\mathcal{A}_{\theta}(x,r))\right]_{+},`$ |     | (4) |

where $`\mathcal{A}_{\theta}(x,\emptyset)`$ denotes the code generated
by the agent without external coding rules,
$`\mathcal{A}_{\theta}(x,r)`$ denotes the code generated using coding
rules $`r`$, and $`[z]_{+}=\max(z,0)`$.

The second component focuses on the code length and inference cost of
the generation process. As illustrated in Figure , there is a high
correlation between code characters and token usage during generation.
Consequently, we approximate both code length and inference cost using
the number of characters of the generated code, denoted by
$`|\mathcal{A}_{\theta}(x,r)|`$. The overall score $`S`$ is formulated
as:

|     |                     |                            |                                                                                                                                                        |
| --- | ------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --- | --- |
|     | $`\displaystyle S=- | \mathcal{A}\_{\theta}(x,r) | -\lambda\cdot\mathbb{E}_{x\in\mathcal{X}}\left[\mathcal{V}(x,\mathcal{A}_{\theta}(x,\emptyset))-\mathcal{V}(x,\mathcal{A}_{\theta}(x,r))\right]_{+},`$ |     | (5) |

where $`\lambda`$ is a hyperparameter that balances the trade-off
between two components.

Iterative Process:  The complete procedure is summarized in
Algorithm [1](#alg1 "Algorithm 1 ‣ 4.2 Iterative Mutation and Pruning ‣ 4 RuleEvolve ‣ Self-Evolving Coding Rules for AI Coding Agents").
Our approach begins by populating an initial candidate rule pool
$`\mathcal{P}`$ through $`m`$ mutations of the initial coding rules. In
each iteration $`t`$, we strategically distribute $`N`$ mutations among
existing $`m`$ candidates based on their historical scores. This results
in $`N`$ newly mutated candidates by the mutator module $`\mathcal{M}`$,
which are subsequently evaluated by the judge module $`\mathcal{J}`$. To
maintain a manageable search space and focus on high-performing regions,
we employ a pruning step that retains only the top-$`m`$ candidates for
the subsequent iteration. After $`T`$ iterations, the framework returns
the coding rules that achieved the highest average score.

### 4.3 Strategic Mutation Allocation

To avoid meaningless mutations and enhance effectiveness, we employ the
Optimal Computing Budget Allocation [Chen and Lee (2011)](#bib.bib28) to
distribute $`N`$ mutations among $`m`$ candidates wisely. The core
objective is to maximize the probability of correctly identifying the
best-performing candidate while minimizing redundant evaluations of
suboptimal candidates.

For each candidate $`i`$, we maintain a score set $`\mathcal{S}_{i}`$
containing the score from each iteration’s evaluation. To address the
cold-start problem and ensure statistical stability, a newly mutated
candidate inherits the score set from its parent. This inheritance
ensures that all candidates in the rule pool possess the same number of
observations, allowing for a consistent computation of the mean
$`\hat{\mu}_{i}`$ and standard deviation $`\hat{\sigma}_{i}`$ for
candidate $`i`$.

Let $`b`$ be the index of the current best-performing candidate in the
pool, i.e., with the highest average score. We determine the allocation
weights $`w_{i}`$ for all $`i\neq b`$ such that:

|     |                                                                                                      |     |     |
| --- | ---------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle w_{i}\propto\left(\frac{\hat{\sigma}_{i}}{\hat{\mu}_{b}-\hat{\mu}_{i}}\right)^{2}.`$ |     | (6) |

This formulation ensures that more mutations are allocated to candidates
with higher performance variance or those whose mean performance is
closer to the current best. The weight for the best candidate $`w_{b}`$
is then calculated as follows to maintain overall allocation efficiency:

|     |                                                                                                      |     |     |
| --- | ---------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle w_{b}=\hat{\sigma}_{b}\sqrt{\sum_{i\neq b}\frac{w_{i}^{2}}{\hat{\sigma}_{i}^{2}}}.`$ |     | (7) |

Finally, the discrete $`n_{i}`$ mutations for each candidate is
determined by normalizing these weights such that $`\sum n_{i}=N`$. By
iteratively refreshing these statistics, updating allocation weights
$`w_{i}`$, and redistributing the mutations $`n_{i}`$, RuleEvolve
focuses its search on the most promising regions of the coding rule
space, improving the effectiveness of the evolving process. Experimental
results validate this by comparing with naive mutation-allocation
strategies. More details can be found in
Appendix [B](#A2 "Appendix B Justification for Mutation-Allocation Strategy ‣ Self-Evolving Coding Rules for AI Coding Agents").

1: Score sets $`\mathcal{S}_{i}`$ for candidates $`\{1,\dots,m\}`$,
number of mutations $`N`$

2: Compute means $`\hat{\mu}_{i}`$ and standard deviations
$`\hat{\sigma}_{i}`$ from $`\mathcal{S}_{i}`$ for each
$`i\in\{1,\dots,m\}`$

3: $`b\leftarrow\arg\max_{i}\hat{\mu}_{i}`$

4: for $`i=1`$ to $`m,i\neq b`$ do

5:   $`\Delta_{i}\leftarrow\max(\hat{\mu}_{b}-\hat{\mu}_{i},\epsilon)`$

6:   $`w_{i}\leftarrow(\hat{\sigma}_{i}/\Delta_{i})^{2}`$

7: end for

8:
$`w_{b}\leftarrow\hat{\sigma}_{b}\sqrt{\sum_{i\neq b}(w_{i}^{2}/\hat{\sigma}_{i}^{2})}`$

9:
$`\{n_{1},\dots,n_{m}\}\leftarrow\text{round}\left(N\cdot\frac{w_{i}}{\sum_{j}w_{j}}\right)`$

10: return $`\{n_{1},\dots,n_{m}\}`$

## 5 Evaluation

### 5.1 Experimental setup

Datasets:  We utilize the BigCodeBench benchmark [Zhuo et al.
(2025)](#bib.bib21) as our primary dataset for coding rules evolvement.
From this benchmark, we randomly sample 1,000 instances to serve as a
training set. During the self-evolving process, each iteration’s scores
are obtained using mini-batches of size $`B`$, sampled randomly from
this training set. To evaluate the performance of evolved coding rules,
we employ three coding benchmarks: BigCodeBench, BigCodeBench-Hard [Zhuo
et al. (2025)](#bib.bib21), and HumanEval [Chen et al.
(2021)](#bib.bib20). For each of these benchmarks, we randomly select
100 samples as our testing benchmark. Samples drawn from BigCodeBench
for testing are strictly disjoint from the training sets used during
evolvement.

Coding agents:  We evaluate our method using two distinct agentic
frameworks: OpenHands [Wang et al. (2025)](#bib.bib23), a
state-of-the-art open-source autonomous agent, and a custom GPT-based
agent implemented via the OpenAI SDK. For OpenHands, our evolved coding
rules are provided through the AGENTS.md configuration, while for OpenAI
SDK, rules are integrated directly into the system prompt.

Backbone models:  To evaluate the generalizability of coding rules
evolvement approaches, we conduct experiments using both proprietary and
open-weight models. For the proprietary models, we utilize gpt-4.1-mini,
gpt-5-mini, and the state-of-the-art gpt-5.3-codex, all accessed via the
OpenAI API. For the open-weight model, we employ Qwen-Coder-30b [Yang et
al. (2025)](#bib.bib27). We evolve the coding rules for each model
respectively.

Baselines:  We compare RuleEvolve against several baselines to assess
the impact of our coding rules self-evolvement. The _No Rule_ baseline
represents a vanilla setting where the agent receives only the task
description without any coding rules. The _Manual Rule_ baseline
utilizes manually written coding rules sourced from the
awesome-cursorrules repository [PatrickJS (2025)](#bib.bib1); notably,
our experiments indicated that providing coding rules do not
consistently yield performance gains, likely due to a lack of
task-specific alignment. This observation aligns with conclusions
in [Gloaguen et al. (2026)](#bib.bib6). *Prompt-Ops* [Wu et al.
(2025)](#bib.bib12) is a baseline designed for prompt optimization for
LLMs. Our results show that such techniques achieve only a suboptimal
trade-off between correctness and code length, in most cases sacrificing
the functional correctness of the generated code. To demonstrate the
effectiveness of our strategic mutation-allocation method, we also
evaluate two naive mutation-allocation strategies: even and proportional
allocation, which distribute mutations equally or proportionally based
on each candidate’s average score.

Evaluation Metrics:  On testing benchmarks, we evaluate the coding rules
across three dimensions: correctness, code length, and inference cost.
Correctness is measured by the _pass rate_ of the code, defined as the
percentage of generated code that satisfy all provided test cases across
the testing benchmark. Code length is assessed through two metrics:
_code lines_ and _code characters_. Inference cost is measured by
_generation time_ and _token usage_ during the inference process. The
averages of the latter four metrics are computed only on code that is
functionally correct.

Parameter settings:  By default, for our RuleEvolve, we set the number
of iteration $`T`$=10, number of mutations $`N`$=20, pool size $`m`$=5,
coding task batch size $`B`$=10, balance parameter $`\lambda`$=3,000,
and $`\epsilon`$=$`10^{-6}`$. For manual rule, we use the fixed one, as
shown in
Appendix [F](#A6 "Appendix F Manual Rules ‣ Self-Evolving Coding Rules for AI Coding Agents").
For Prompt-Ops, we use their default settings.

the gains in code length or inference cost come at the expense of
functional integrity; in the OpenHands BCB scenario, Prompt-Ops suffers

stress that PR is the most critical metric in autonomous coding; if the
generated code is incorrect, optimizing for code length or inference
cost becomes meaningless. By prioritizing functional correctness,
RuleEvolve ensures that gains in code length or inference cost do not
compromise the agent’s primary utility.

## 6 Conclusion

In this work, we investigate the self-evolvement of coding rules for AI
coding agents. We show that coding rules can be evolved to greatly
reduce code length and minimize inference costs while maintaining the
functional correctness of the generated code. This is achieved by
RuleEvolve, our proposed automatic self-evolving framework for coding
rules. By employing a mutator, judge module, and a strategic
mutation-allocation approach, RuleEvolve successfully evolves coding
rules via iterative mutation and pruning. Extensive evaluations across
two agentic frameworks, four diverse backbone models, and three coding
benchmarks demonstrate that RuleEvolve outperforms both manually crafted
rules and existing baselines, establishing a promising direction for
coding rules self-evolvement.

## Appendix A Limitations

Our work has several limitations. First, while RuleEvolve maintains or
improves functional correctness in most scenarios, the objective of
reducing code length may still lead to a slight decrease in the pass
rate for certain complex tasks where excessive brevity could compromise
logic. Second, our self-evolving process relies on an LLM-powered
mutator and judge module, which introduces inherent stochasticity and
potential biases from the backbone models used during evolving. Third,
our study primarily focuses on optimizing for correctness, code length,
and inference cost through code length approximation. A more
comprehensive exploration of other dimensions, such as code
maintainability or architectural complexity, remains for future work.

## Appendix B Justification for Mutation-Allocation Strategy

In this section, we provide the theoretical justification for the
mutation-allocation strategy used in RuleEvolve. The goal of the Optimal
Computing Budget Allocation \[[5](#bib.bib28)\] is to maximize the
_Probability of Correct Selection (PCS)_, defined as the probability
that the candidate rule set with the highest sample mean is indeed the
true best performer.

Let $`m`$ be the number of candidates in the pool, and let $`J`$ be the
index of the true best candidate such that $`\mu_{J}=\max_{i}\mu_{i}`$.
The PCS is given by:

|     |                                                                                        |     |     |
| --- | -------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle\text{PCS}=P\left(\hat{\mu}_{J}>\hat{\mu}_{i},\forall i\neq J\right).`$ |     | (8) |

Under the assumption that the scores $`\mathcal{S}_{i}`$ are independent
and follow a normal distribution $`N(\mu_{i},\sigma_{i}^{2})`$, for a
large number of mutations $`N`$, the PCS is maximized when the
allocation $`n_{1},n_{2},\dots,n_{m}`$ satisfies the following
asymptotic conditions:

|     |                                                                                                                                         |     |     |
| --- | --------------------------------------------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle\frac{n_{i}}{n_{j}}=\frac{\sigma_{i}^{2}/(\mu_{b}-\mu_{i})^{2}}{\sigma_{j}^{2}/(\mu_{b}-\mu_{j})^{2}},\quad i,j\neq b,`$ |     | (9) |

and

|     |                                                                                          |     |      |
| --- | ---------------------------------------------------------------------------------------- | --- | ---- |
|     | $`\displaystyle n_{b}=\sigma_{b}\sqrt{\sum_{i\neq b}\frac{n_{i}^{2}}{\sigma_{i}^{2}}},`$ |     | (10) |

where $`b`$ is the index of the candidate with the current highest
sample mean.

These conditions provide the following insights into the RuleEvolve
evolvement process:

- •
  Candidates with a smaller performance gap $`(\mu_{b}-\mu_{i})`$
  receive more mutations, as they are the most likely "competitors" to
  the current best.
- •
  Candidates with higher variance $`\sigma_{i}^{2}`$ receive more
  mutations to reduce the uncertainty in their mean estimation.
- •
  The mutations for the best candidate $`n_{b}`$ is scaled based on the
  aggregate noise of all other candidates, ensuring that the comparison
  is sufficiently stable.

By following this allocation, RuleEvolve minimizes the risk of pruning a
potentially superior coding rule due to stochastic noise in mutator
generation, ensuring a more robust and efficient search path than
uniform allocation.

def is_palindrome(string: str) -\> bool:

"""Return True if the given string is a palindrome.

\>\>\> is_palindrome(’a’)

def \_prefix_function(s: str) -\> List\[int\]:

"""Compute prefix-function (a.k.a. failure function) for KMP algorithm.

The prefix-function for a string “s“ is an array “pi“ where “pi\[i\]“

is the length of the longest proper prefix of “s\[:i+1\]“ that is also

a suffix of “s\[:i+1\]“.

This implementation runs in O(n) time and O(n) memory.

Args:

s: Input string.

Returns:

A list of integers representing the prefix-function values for each

position in “s“.

Examples:

\>\>\> \_prefix_function(’ababaca’)

\[0, 0, 1, 2, 3, 0, 1\]

"""

n: int = len(s)

pi: List\[int\] = \[0\] \* n

for i in range(1, n):

j: int = pi\[i - 1\]

while j \> 0 and s\[i\] != s\[j\]:

j = pi\[j - 1\]

if s\[i\] == s\[j\]:

j += 1

pi\[i\] = j

return pi

def make_palindrome(string: str) -\> str:

"""Return the shortest palindrome that begins with "string" by appending

characters to its end.

The function finds the longest palindromic suffix of the input and then

appends the reverse of the remaining prefix. This yields the minimal

number of characters to append so the result is a palindrome that starts

with the original string.

Algorithmic idea:

- Let “rev“ be the reverse of “string“.

- Compute the prefix-function on “rev + ’#’ + string“; the value at the

last position is the length “k“ of the longest prefix of “rev“ that

matches a suffix of “string“ equivalently, the longest palindromic

suffix of “string“.

- Append the reverse of the prefix “string\[:len(string) - k\]“ to the

end of “string“.

This runs in linear time O(n) and linear space O(n).

Args:

string: The input string. May be empty.

Returns:

The shortest palindrome that begins with “string“. If “string“ is

already a palindrome, it is returned unchanged.

Examples:

\>\>\> make_palindrome(”)

”

\>\>\> make_palindrome(’cat’)

’catac’

\>\>\> make_palindrome(’cata’)

’catac’

\>\>\> make_palindrome(’race’)

’racecar’

\>\>\> make_palindrome(’a’)

’a’

"""

n: int = len(string)

if n \<= 1:

return string

rev: str = string\[::-1\]

\# Build a combined string to compute how much of rev matches a suffix
of

\# string (i.e. longest palindromic suffix of string).

combined: str = rev + "#" + string

pi: List\[int\] = \_prefix_function(combined)

k: int = pi\[-1\] if pi else 0 \# length of longest palindromic suffix

\# Append reverse of the prefix that is not part of the palindromic
suffix.

to_append: str = (string\[: n - k\])\[::-1\]

return string + to_append
