# VeriEvolve: Evaluator-First Evolution for Tool-Using Agents

###### Abstract

A central obstacle to self-improving agents is the absence of a reliable
fitness signal for realistic stateful tasks. We introduce VeriEvolve, an
evaluator-first evolution framework that constructs this missing
evaluation layer before optimizing the agent. From each task
instruction, VeriEvolve synthesizes instruction-grounded challenge
states and an executable evaluator that checks them. During each round
of workflow evolution, the evaluator is frozen and serves as the fitness
signal. Between rounds, VeriEvolve revises the evaluator by converting
the end states of strong and weak runs into a pair of counterfactual
test cases.

Across all 30 MCPMark Filesystem tasks, VeriEvolve constructs 30
evaluators with 141 challenge states, achieving 141/141 agreement on the
generated suites and 113/122 agreement on held-out states produced by
executor agents. Evaluator-guided evolution increases externally
verified success from 6/30 to 18/30 for GLM-5.2 and from 27/30 to 30/30
for Claude; refinement removes all three false positives that the weak
executor exposes. Cross-environment studies on PostgreSQL, Playwright,
Notion, and GitHub further expose complementary limits from
observability, state representation, and search/execution capacity.
These results show that executable evaluators can be synthesized and
used to guide search when task success is observable and an external
verifier is available for calibration.

## 1 Introduction

A self-improving agent can optimize only what its evaluator can reliably
measure. In program synthesis, formal reasoning, and scientific
optimization, candidate quality is often supplied through unit tests,
proof checkers, or explicit numerical objectives ([Romera-Paredes et
al., 2024](#bib.bib15); [Novikov et al., 2025](#bib.bib16); [Zhang et
al., 2026a](#bib.bib19); [Wang et al., 2026b](#bib.bib17)). Realistic
tool-use workflows rarely come with an equivalent fitness function.
Instead, agents must translate natural-language instructions into
structured changes across filesystems, databases, repositories,
productivity platforms, and browsers. Extending self-improvement to
these settings therefore requires not only better search but also the
scalable construction of deterministic, machine-checkable evaluators.

This evaluation bottleneck is especially pronounced in stateful,
create–read–update–delete (CRUD) workflows. Correctness is determined by
the resulting environment state rather than the final natural-language
response, and may depend jointly on artifact existence, content,
hierarchy, consistency, preservation, and the absence of unintended side
effects. These constraints are implied by the instruction but are
generally not supplied as a complete executable specification.
Human-authored verification scripts can represent them reliably, but
they are costly to design and validate; MCPMark reports several hours of
expert effort for constructing each task and its verifier ([Wu et al.,
2026](#bib.bib20)). LLM-based judges are easier to scale, but semantic
assessment alone cannot reliably establish that all required properties
of the final state hold.

We study whether this missing evaluation layer can itself be constructed
by agents. Our central question is: _Can an agent synthesize a
task-grounded executable evaluator that is informative enough to guide
workflow improvement without access to an externally authored verifier
during search?_ Our goal is not to reproduce an expert verifier
perfectly in one step. Instead, we ask whether an initially constructed
evaluator can bootstrap useful optimization, and whether the resulting
execution states can subsequently reveal missing constraints and support
sharper evaluation artifacts. We treat this as a feasibility question in
a deliberately favorable setting: task success is observable through the
environment state, and an independent benchmark verifier exists, which
we use only outside the search loop: to admit evaluators, identify false
positives, and measure outcomes.

We introduce VeriEvolve, an evaluator-first framework with four
model-backed roles: a Test-Suite Generator, Verifier Evolver, Workflow
Evolver, and Workflow Executor. In Stage 1, the framework derives
positive, negative, and adversarial challenge states from the task
instruction and observable initial environment. Deterministic category
adapters materialize these specifications, and the Verifier Evolver
constructs a task-specific executable evaluator that is frozen after
passing internal gates. In Stage 2, this evaluator supplies a stationary
fitness signal for evolving a tool-use workflow whose nodes retain
persistent behavioral alternatives. Stage 3 then compares
high-confidence strong-executor states with internally accepted
weak-executor states, mines instruction-grounded differences into paired
counterfactual cases, and promotes a revised evaluator only after
cumulative regression. The revised evaluator is frozen before workflow
search resumes. The external MCPMark verifier is never shown to a
model-backed role and never ranks workflows or edits an evaluator. It is
used outside the loop for three purposes: admitting evaluators to
Stage 2, identifying which accepted states are false positives and
therefore enter Stage 3, and measuring results.

Our primary controlled study covers all 30 MCPMark Filesystem tasks.
Stage 1 constructs 30/30 evaluators with 141 challenge states, including
62 adversarial near-misses, with 141/141 agreement against the external
verifier on the generated suites. On 122 distinct states later produced
by the executor agents, which no evaluator saw during construction,
agreement is 113/122. Under the weaker GLM-5.2 executor, workflow
evolution increases externally verified success from 6/30 at round 0 to
18/30; under Claude, it increases success from 27/30 to 30/30. Three
internally accepted GLM-5.2 states nevertheless fail external
verification, showing that an evaluator can guide effective search while
remaining incomplete. In all three cases, strong–weak state differences
yield regression-verified evaluator revisions that eliminate the
original false positives; for structure_mirror, the weak executor
reaches an externally valid state after a single revision. An expanded
PostgreSQL study covers all 21 standard tasks: 15 synthesized evaluators
meet the Stage 2 admission threshold, and workflow evolution closes
three weak-executor gaps that the strong executor solves at round 0,
while neither executor reaches internal convergence on the remaining 12
eligible tasks within the configured limits. Playwright, Notion, and
GitHub stress tests further expose complementary limits imposed by
observability and state representation.

Our contributions are:

- •
  We identify the scalable construction of deterministic,
  machine-checkable evaluators as a missing prerequisite for
  self-improving agents in realistic stateful tool-use workflows.
- •
  We introduce VeriEvolve, which constructs task-grounded challenge
  states and executable evaluators before evolving persistent
  multi-alternative workflows under a frozen fitness signal, and revises
  an evaluator from differences between strong- and weak-executor final
  states.
- •
  On MCPMark, we show that the synthesized evaluators agree with the
  external verifier on their own challenge states and on held-out
  agent-produced states, that they guide externally measured workflow
  improvement for a strong and a weak executor, and that
  state-difference refinement removes all three false positives the
  external verifier exposed.
- •
  We will release the framework code and the resulting artifacts upon
  publication: challenge states and frozen evaluators for 30 Filesystem
  and 18 PostgreSQL tasks, the 258 agent-produced states with internal
  and external labels used for held-out evaluation, and the evolved
  workflows.

## 2 Related Work

#### Self-improving agents and their evaluators.

Language models are increasingly used as search operators over programs
and agents. FunSearch and AlphaEvolve evolve programs against
automatically computed objectives ([Romera-Paredes et al.,
2024](#bib.bib15); [Novikov et al., 2025](#bib.bib16)); the Darwin and
Huxley Gödel Machines evolve self-modifying coding agents scored on
coding benchmarks ([Zhang et al., 2026a](#bib.bib19); [Wang et al.,
2026b](#bib.bib17)); and HyperAgents jointly represent task-solving and
self-modification roles ([Zhang et al., 2026b](#bib.bib12)). These
systems start from a supplied benchmark or utility. Recent work allows
the evaluation criterion to change: the Red Queen Gödel Machine
co-evolves agents with learned evaluators, freezing each evaluator
within an epoch and promoting challengers against held-out ground-truth
anchors ([Iacob et al., 2026](#bib.bib3)); self-modifying Lean agents
co-evolve their benchmark while keeping Lean as a fixed trusted verifier
([Li et al., 2026](#bib.bib6)); and the Verification Horizon argues that
verification must develop alongside increasingly capable generators
([Wang et al., 2026a](#bib.bib10)). In each case, an improved evaluator
is still validated against an external benchmark, formal verifier,
ground-truth anchor, or human judgment. VeriEvolve shares this
dependence: it builds evaluators for stateful tool-use tasks without the
benchmark’s verifier but uses that verifier afterward to admit
evaluators, select false positives for refinement, and measure their
performance.

#### Evaluation of stateful tool use.

LLM judges scale feedback for open-ended text and dialogue ([Liu et al.,
2023](#bib.bib7); [Zheng et al., 2023](#bib.bib13)), but a semantic
judgment cannot establish that every required state invariant holds.
Agent benchmarks therefore check the resulting artifacts or the
environment state programmatically ([Jimenez et al., 2024](#bib.bib4);
[Yao et al., 2025](#bib.bib18); [Xie et al., 2024](#bib.bib14); [El
Hattami et al., 2025](#bib.bib2); [Wu et al., 2026](#bib.bib20)), and
agent harnesses build on such executable feedback ([Ning et al.,
2026](#bib.bib8)). These checks are written by hand: MCPMark reports
several hours of expert effort per task and verifier ([Wu et al.,
2026](#bib.bib20)). LLMs can generate tests and checks from source code,
formal specifications, or agent traces ([Wang et al., 2025](#bib.bib9);
[Cunha and Macedo, 2026](#bib.bib1); [Kohl et al., 2026](#bib.bib5));
VeriEvolve instead synthesizes evaluators of final environment states
from a task instruction and its initial state, and revises them using
states that agents produce.

## 3 Problem Setting

A stateful tool-use task is a tuple $`\tau=(x,s_{0},\mathcal{O})`$: a
natural-language instruction $`x`$, an initial environment state
$`s_{0}`$, and a read-only observation interface $`\mathcal{O}`$ that
exposes the state available for evaluation. Executing a workflow $`W`$
with the task’s tools yields a final state $`s_{W}`$. The correctness of
$`s_{W}`$ depends on constraints implied by the instruction (existence,
content, structure, consistency, and preservation of artifacts), which
are not given as an executable specification. We consider only tasks
whose success is observable through $`\mathcal{O}`$.

#### Evaluator.

An evaluator $`E`$ is a deterministic program that maps
$`\mathcal{O}(s)`$ to a verdict $`\hat{y}(s)\in\{0,1\}`$, a partial
score $`r(s)\in[0,1]`$, and check-level evidence. VeriEvolve builds
$`E`$ from $`x`$, $`\mathcal{O}(s_{0})`$, a set of synthesized challenge
states with instruction-derived labels,
$`\mathcal{C}=\{(s_{i},y_{i})\}`$, and deterministic execution feedback;
it does not use the benchmark’s verifier. Workflow search maximizes
$`r(s_{W})`$ while $`E`$ is held fixed, and a workflow is _internally
converged_ when $`\hat{y}(s_{W})=1`$.

#### Refinement.

Evaluators are versioned $`E^{(0)},E^{(1)},\ldots`$ together with their
challenge sets $`\mathcal{C}^{(k)}`$. Refinement round $`k`$ compares a
reference state $`F^{+}`$ produced by a strong executor with a
weak-executor state $`F_{k}^{-}`$ that $`E^{(k)}`$ accepts. Their
observable difference
$`\Delta^{(k)}=\mathrm{Diff}\bigl(\mathcal{O}(F^{+}),\mathcal{O}(F_{k}^{-})\bigr)`$
is turned into new labeled challenge states, giving
$`\mathcal{C}^{(k+1)}`$, and into a revised evaluator $`E^{(k+1)}`$;
weak-executor search is then rerun. $`F^{+}`$ is treated as one
high-confidence valid execution, not as a ground-truth oracle, so a
revision may add only instruction-grounded distinctions and must
preserve all earlier verdicts.

### 4.1 Evaluator Construction

The Test-Suite Generator maps the task instruction and observable
initial state to declarative positive, clean-negative, and adversarial
challenge cases. A category-specific deterministic adapter materializes
each specification in an isolated copy of the task environment,
producing executable states with instruction-derived labels.

The Verifier Evolver constructs a sandboxed executable evaluator over
the read-only observation interface $`\mathcal{O}`$. A deterministic
harness runs each evaluator candidate on the materialized challenge
states and returns case-level failures as refinement feedback. Once the
candidate satisfies the construction gate, it is frozen as $`E^{(0)}`$.
The initial output of Stage 1 is therefore the challenge set and

### 4.2 Workflow Evolution under Frozen Evaluation

A workflow contains five functional nodes for task understanding,
planning, ReAct execution, artifact inspection, and post-processing.
Each node maintains a pool of prompt or behavior alternatives, following
the persistent multi-alternative representation of EvoLattice ([Yuksel,
2025](#bib.bib11)), and a candidate path selects one alternative from
every active node. The Workflow Executor runs the selected path in an
isolated task environment and returns the final state and execution
trace.

The frozen evaluator $`E^{(k)}`$ scores the observable final state and
provides partial fitness and check-level evidence. Artifact inspection
separately summarizes execution behavior that may explain the failed
checks. The Workflow Evolver uses these signals to append new node
alternatives for subsequent rounds. Because earlier alternatives remain
available, promising partial behaviors can be retained and recombined
rather than overwritten by each mutation. Throughout a Stage 2 run,
however, $`E^{(k)}`$ is immutable; the search changes how the task is
understood, planned, executed, inspected, or post-processed, but not the
criterion used to compare candidates. The multi-alternative workflow
representation is shown in
Appendix [B.2](#A2.SS2 "B.2 Persistent Multi-Alternative Workflow ‣ Appendix B Implementation and Experimental Configuration ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")
(Figure [3](#A2.F3 "Figure 3 ‣ B.2 Persistent Multi-Alternative Workflow ‣ Appendix B Implementation and Experimental Configuration ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")).

### 4.3 Execution-State Refinement

#### State-difference mining.

At refinement round $`k`$, a deterministic adapter first removes known
environment-specific artifacts symmetrically from $`F^{+}`$ and
$`F_{k}^{-}`$. The State-Diff module then organizes the remaining
observable differences into factual clusters, such as missing or extra
artifacts, content mismatches, and structural deviations. Only clusters
that can be grounded in the task instruction are eligible for
refinement.

#### Counterfactual challenge states.

For each selected cluster, the Test-Suite Generator constructs paired
counterfactual states using $`F^{+}`$ and the current $`F_{k}^{-}`$ as
immutable anchors. The negative state reproduces the selected
difference, while the positive control removes it and holds the
unrelated state fixed. A deterministic label-consistency gate verifies
the expected verdicts, and a coverage gate checks that the pair actually
introduces and removes the targeted difference. Cases that fail either
gate are rejected before evaluator refinement.

#### Evaluator promotion and workflow rerun.

The Verifier Evolver receives the current evaluator, the cumulative
challenge set, and factual observation-level contrasts between the
paired states. It proposes a localized revision targeted at the
uncovered constraint. A candidate is promoted to $`E^{(k+1)}`$ only if
cumulative regression verifies that it accepts $`F^{+}`$, rejects all
prior weak false-positive states, preserves all previous challenge-state
verdicts, and correctly classifies the new cases. The promoted evaluator
is then frozen, and weak-executor workflow evolution is rerun under the
sharper criterion.

A further refinement round is useful only when the new weak state
exposes a novel, instruction-grounded difference that the current
evaluator does not already cover. VeriEvolve terminates when the weak
state matches the reference or no actionable difference remains; when
the evaluator stabilizes on a repeated, already-covered difference; or
when workflow search, evaluator refinement, or the refinement-round
budget is exhausted. Repeated production of an error already detected by
the evaluator is therefore attributed to workflow-search or executor
insufficiency rather than treated as another evaluator gap.

Each accepted refinement round appends paired challenge states, a
strong–weak state contrast, and a new evaluator version, yielding an
ordered and reusable evaluator lineage. The external benchmark verifier
is not part of this loop: its source, verdicts, and diagnostics are
never provided to any model-backed role or used for workflow ranking,
evaluator repair, or termination. In our experiments, however, external
verdicts decide which evaluators enter Stage 2 and which internally
accepted states are false positives that trigger refinement, and the
reference state $`F^{+}`$ is one that the external verifier also
accepts. A deployment without an external verifier would need another
trigger and reference. We evaluate one candidate trigger, executor
disagreement, only retrospectively
(Appendix [E.6](#A5.SS6 "E.6 A Verifier-Free Refinement Trigger ‣ Appendix E Additional Analyses and Ablations ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents"));
a verifier-free reference is not evaluated.

## 5 Experimental Setup

### 5.1 Evaluation Questions and Scope

We evaluate on a subset of the MCPMark standard task suite spanning five
task environments; the complete task and exclusion breakdown is reported
in
Appendix [A](#A1 "Appendix A Task Scope and Evaluation Regimes ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents").
We treat Filesystem as our primary controlled study and the remaining
environments as cross-environment stress tests.

We ask three questions, one per stage. RQ1 (evaluator construction): can
VeriEvolve synthesize challenge states and executable evaluators that
distinguish correct task states from minimally incorrect or adversarial
ones? RQ2 (workflow evolution): do the synthesized evaluators give
feedback informative enough to guide workflow search? RQ3
(execution-state refinement): can differences between strong- and
weak-executor states reveal evaluator constraints not yet covered?

### 5.2 Models and Experimental Budgets

All model-backed roles use Claude Sonnet, except that initial Stage 1
construction ran in interactive Claude Code sessions and the weak
Workflow Executor is GLM-5.2;
Table [7](#A2.T7 "Table 7 ‣ B.1 Model Roles and Invocation Modes ‣ Appendix B Implementation and Experimental Configuration ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")
in
Appendix [B](#A2 "Appendix B Implementation and Experimental Configuration ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")
gives identifiers and invocation modes.

Stage 1 evaluator construction uses only internal gates: positive
acceptance of at least $`0.90`$ and adversarial rejection of at least
$`0.80`$. After an evaluator is frozen, we measure its agreement with
the external MCPMark verifier. For the Stage 2 study, we include frozen
evaluators with at least $`0.85`$ post-hoc external agreement. This
external measurement determines study inclusion and is used for
evaluation; Stage 3 is applied to the internally accepted states that
the external verifier rejects. External labels, diagnostics, and
verifier logic are never routed back into test generation, evaluator
repair, workflow ranking, or workflow evolution.

Unless otherwise noted, Stage 2 runs use five paths per round (three for
the Filesystem Claude campaign), at most 15 workflow rounds (three paths
and at most five rounds for the Playwright and Notion pairs), up to
three evaluator-repair attempts, and at most three refinement rounds. In
the Filesystem GLM-5.2 and the PostgreSQL campaigns, each Stage 2 round
ran as a subprocess with a one-hour timeout; a round that exceeded it
ended the run, which is counted as unsolved. Full per-category gates,
budgets, and timeout settings are listed in
Appendix [B](#A2 "Appendix B Implementation and Experimental Configuration ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents").

We denote acceptance by the internal evaluator and external MCPMark
verifier as $`\mathrm{Int}\checkmark`$ and $`\mathrm{Ext}\checkmark`$,
respectively. Thus, $`\mathrm{Int}\checkmark/\mathrm{Ext}\times`$
denotes an evaluator false positive and
$`\mathrm{Int}\times/\mathrm{Ext}\checkmark`$ an evaluator false
negative. External verdicts are never used as optimization feedback.
Formal exclusions and infrastructure-invalid runs are reported
separately and are not counted as semantic task failures.

Agreement on a finite generated suite does not imply complete coverage.

re-execute each Stage 1 evaluator on the final states that the two
Stage 2 executors produced on Filesystem and label every state post hoc
with the external verifier. These states were produced after the
evaluators were frozen, by other models working on the real task. The
campaigns retained the best state of each round, giving 258 states, 122
of them distinct
(Table [2](#S6.T2 "Table 2 ‣ 6.1 RQ1: Constructing Evaluators ‣ 6 Results ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")).

60 final states, agreement is 57/60, the outcomes in

#### Answer to RQ1.

Where correctness is observable, VeriEvolve built evaluators that agree
with the external verifier on their own suites (141/141 and 115/120) and
on 113/122 held-out Filesystem states. This is external calibration, not
evidence of reliability on its own.

remaining effect of executor capability under the same task-specific
evaluators. Because both comparisons are paired over the same 30 tasks,
we apply an exact McNemar test
(Table [14](#A4.T14 "Table 14 ‣ D.2 Filesystem Stage 2 Results ‣ Appendix D Complete Experimental Results ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")):
GLM-5.2’s external gain (12 tasks gained, none lost) is significant
($`p<0.001`$), whereas Claude’s three gained tasks are not ($`p=0.25`$).

On the 15 admitted PostgreSQL tasks, both executors solve the same three
tasks, and every internally accepted final state is also externally
accepted. The strong executor solves them at round 0; the weak executor
needs 11, 2, and 7 rounds of evolution and 5–32$`\times`$ the strong
executor’s tokens. Neither executor converges on the other 12 tasks
within the configured limits
(Appendix [D.5](#A4.SS5 "D.5 Cross-Environment Results ‣ Appendix D Complete Experimental Results ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")),
which also reports the smaller Playwright and Notion studies.

#### Answer to RQ2.

The evaluators give usable search feedback: evolution triples
weak-executor success on Filesystem and closes three PostgreSQL gaps,
but 12/15 PostgreSQL tasks stay unsolved, so a usable evaluator does not
remove executor and search limits.

## 7 Discussion

Once a calibrated task-specific evaluator is available, the bottleneck
can shift from evaluation to search and execution: neither executor
converges on 12 of the 15 admitted PostgreSQL tasks, and on the three
solved tasks only the weak executor needs evolution. A usable fitness
signal is therefore necessary but not sufficient. Refinement is also
trajectory-dependent: it starts only when search reaches an
evaluator-accepted state that exposes a gap, and in our experiments that
trigger came from the external verifier. A simple verifier-free
alternative, flagging any accepted weak-executor state that differs from
the strong executor’s accepted state, would in retrospect have caught
all three false positives but also flagged 10 of 18 correct states
(Appendix [E.6](#A5.SS6 "E.6 A Verifier-Free Refinement Trigger ‣ Appendix E Additional Analyses and Ablations ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents"));
making such a trigger precise remains open. Because compute is dominated
by candidate execution, future work should devote more capacity to
search and execution, while the accumulated challenge states and
evaluator revisions may support smaller models specialized for test
generation and evaluator repair.

## 8 Conclusion

We introduced VeriEvolve, an evaluator-first framework that constructs
challenge states and executable evaluators before optimizing tool-use
workflows. On MCPMark tasks whose success is observable through the
environment state, the synthesized evaluators agree with the external
verifier on their own challenge states and on most held-out
agent-produced states, guide externally measured workflow improvement,
and can be repaired from strong–weak state differences once a false
positive is identified. Throughout, the external verifier remains the
reference that admits evaluators and exposes their errors; removing that
dependence is the main step toward agents that construct the fitness
signals they require.

## Limitations

#### Dependence on an external verifier.

VeriEvolve never exposes the benchmark verifier to a model or uses it
inside search, but our experiments are not verifier-free. External
agreement decides which evaluators enter Stage 2, external verdicts
identify the false positives that Stage 3 refines, and each reference
state $`F^{+}`$ is externally accepted. Our results therefore show
feasibility under external calibration, not that synthesized evaluators
are reliable, or that refinement can run autonomously, without an
independent verifier.

#### Evidence for evaluator quality.

Calibration on a finite challenge suite does not guarantee complete
evaluator coverage. Test-suite generation and evaluator construction
both used Claude, so the 141 Stage 1 challenge states share their author
with the evaluators they test. The held-out agent-produced states come
from other executors, but only the best state of each round was
retained, so they are selected by the evaluator’s own ranking and are
not independent samples. Initial interactive Stage 1 construction
additionally relied on a procedural verifier-information boundary,
whereas the stronger packet-level technical isolation applies to
Stage 3.

#### Coverage and search.

Our empirical coverage remains uneven across environments. Filesystem is
the only category with complete Stage 1 and Stage 2 coverage together
with execution-state refinement. PostgreSQL provides broader evidence:
all 21 standard tasks receive a Stage 1 disposition, 15 evaluators
qualify for Stage 2, and all 15 matched strong/weak conditions are run
to their configured limits. However, only three of these tasks are
solved by either executor, and no PostgreSQL trajectory produces an
$`\mathrm{Int}\checkmark/\mathrm{Ext}\times`$ state that would trigger
Stage 3. Playwright, Notion, and GitHub remain smaller or incomplete
cross-environment studies. VeriEvolve can evaluate only properties
represented through the observation interface, and several
cross-environment tasks are excluded or caveated because their success
conditions are missing, weakly specified, or distorted by the available
state representation.

Each Filesystem condition was run once, and we compare evolved workflows
with their own round-0 seed rather than with a budget-matched search
baseline, so part of the measured gain may reflect repeated sampling
rather than evaluator guidance. A usable fitness signal does not
guarantee task completion: on most PostgreSQL Stage 2 tasks neither
executor converges, and several weak-executor runs end at the one-hour
round timeout rather than after all 15 rounds. Successful evaluator
repair likewise does not guarantee that a weaker executor can satisfy
the refined criterion. Refinement requires a high-confidence positive
state $`F^{+}`$ from a sufficiently capable executor, and $`F^{+}`$ is
one valid execution, not a complete characterization of all acceptable
solutions. The strong executor provides such a state on 35 of 49 tasks
across environments but on only 3 of 15 PostgreSQL tasks
(Appendix [E.5](#A5.SS5 "E.5 Strong-Executor Reliability ‣ Appendix E Additional Analyses and Ablations ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents"));
one of its internally accepted states is rejected externally, and the
effect of an erroneous $`F^{+}`$ on the revised evaluator is untested.
Repeated workflow execution and refinement remain computationally
expensive, limiting both the present experimental scale and the number
of opportunities for execution-state refinement.

### B.2 Persistent Multi-Alternative Workflow

Figure 3: Persistent multi-alternative workflow used in Stage 2. A
candidate path selects one prompt or behavior alternative from each
active node, producing an artifact and execution trace. Alternatives
persist across rounds, enabling non-destructive reuse and recombination.

Figure [3](#A2.F3 "Figure 3 ‣ B.2 Persistent Multi-Alternative Workflow ‣ Appendix B Implementation and Experimental Configuration ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")
shows the Stage 2 workflow representation. The five active nodes are
task understanding, planning, ReAct execution, artifact inspection, and
post-processing. A fresh workflow contains one seed alternative at each
node except ReAct execution, which contains two. The alternative caps
are $`2,3,5,2,2`$, respectively. The baseline task-understanding
alternative and the disabled post-processing alternative are protected
from eviction.

Alternatives are weighted by their historical mean internal score, with
an uninformed prior of $`0.5`$. Each newly proposed alternative receives
one forced exploration path in the next round; remaining paths use
weighted selection. When a node reaches its cap, the lowest-scoring
non-protected alternative is evicted. The evaluator remains frozen
throughout this process.

## Appendix C End-to-End Case Study: structure_mirror

### C.1 Task and Initial Evaluator

The task asks the agent to reproduce the directory structure of
complex_structure/ under complex_structure_mirror/ without copying file
contents. Each mirrored empty directory must contain a placeholder.txt
file storing its absolute path. Directories containing more than two
direct files are discarded, directory names containing digits receive a
\_processed suffix, and non-digit names are preserved.

Stage 1 synthesized five challenge states

one complete positive case, one clean negative, and three adversarial
near-misses. All five expected labels agree with the external verifier.
The initial evaluator $`E^{(0)}`$ contains five deterministic check
families.

| --------------------- | -------------- | -------------- | -------------------------------------------------------- |

### C.4 An Artifact-Triggered Second Round

The run did not stop at $`F_{1}^{-}`$. Its second refinement round was
triggered by a single extra root-level directory, complex*structure 2,
in the working copy of $`F*{1}^{-}`$. That directory is absent from the
archived $`F*{1}^{-}`$ and from its canonicalization record: it was
created by file synchronization of the working directory after the state
was archived. Re-verifying the archived $`F*{1}^{-}`$ after the fact,
the external verifier and $`E^{(0)}`$, $`E^{(1)}`$, and $`E^{(2)}`$ all
accept it. We therefore exclude the second round from our results. The
$`E^{(2)}`$ it produced adds an absence check learned from the artifact,
and the weak state reached under $`E^{(2)}`$ (score $`0.8333`$, rejected
internally and externally) is reported only for completeness.

### C.5 Separate Controlled Run

A separate controlled run from the same source version also reaches an
$`E^{(1)}`$ and then performs a second round. Its round-2 difference is
mostly genuine: eleven extra placeholder.txt files, mostly in non-empty
directories, and one directory from the discarded subtree, together with
a synchronization-artifact directory complex_structure 3. Its
$`E^{(2)}`$ adds checks against this extra structure, and the weak
executor then produces an internally and externally accepted state with
tree hash 80aeae4e..., the state the primary run reached after one
round. A development run that stopped after one round
(Table [18](#A4.T18 "Table 18 ‣ D.4 Filesystem Stage 3 Lineage ‣ Appendix D Complete Experimental Results ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents"))
confirms that extra structure is a real failure mode: its weak state,
accepted by its $`E^{(1)}`$, contains eleven extra placeholder files and
fails external verification.

### D.3 Held-Out Evaluation on Agent-Produced States

#### Protocol.

For every best-of-round state retained by the two Filesystem Stage 2
campaigns, we copy the snapshot, remove copy-collision duplicates (files
named \<name\> 2 that are byte-identical to \<name\>, created by file
synchronization after the runs), re-execute the task’s Stage 1 frozen
evaluator in the same sandbox used during the campaigns, and run the
external verifier once on the same copy (verdict: exit code 0). No model
is called, and nothing is fed back into any evaluator or workflow.
Identical states (same task and content hash) are counted once in the
“distinct” rows.

#### Data.

Of 320 retained snapshots, 258 are valid campaign states. We exclude 60
Claude snapshots that lie beyond their task’s final round and have no
round record (left over from an earlier run under the same campaign
name) and two Claude file_arrangement states whose recorded internal
verdict does not reproduce, since they may not be the states that were
scored. On the remaining states, every re-executed internal verdict

#### PostgreSQL.

Across all 21 standard PostgreSQL tasks, VeriEvolve successfully
constructs evaluators for 18 tasks. Their 120 post-hoc calibration
states contain 22 external-positive and 98 external-negative cases; the
frozen internal evaluators agree with the external verifier on 115/120
states. Fifteen evaluators satisfy the per-task $`0.85`$
external-agreement threshold and enter Stage 2, three successfully
constructed evaluators remain below threshold, and three tasks are
blocked by limitations of the observation interface. External
calibration is performed only after evaluator construction and is not
routed back into evaluator generation or repair.

All 15 eligible tasks receive matched strong- and weak-executor Stage 2
runs. Both conditions ultimately solve employee_hierarchy_management,
customer_data_migration, and sales_and_music_charts. The strong executor
succeeds at round 0 on all three, whereas the weak executor reaches
externally verified success after 11, 2, and 7 workflow-evolution
rounds, respectively. The weak/strong executor token ratios on these
tasks are $`32.2\times`$, $`5.2\times`$, and $`12.8\times`$. On the
remaining 12 eligible tasks, neither condition reaches internal
convergence. All 12 strong-executor runs use the full 15 rounds; of the
12 weak-executor runs, 4 use all 15 rounds and 8 end earlier, after 4 to
12 rounds, when a round exceeds the one-hour round timeout.

Across the resulting 30 Stage 2 conditions, every internally accepted
final state is also externally accepted: six conditions are
$`\mathrm{Int}\checkmark/\mathrm{Ext}\checkmark`$, while the remaining
24 conditions do not reach internal acceptance. No agent-produced
$`\mathrm{Int}\checkmark/\mathrm{Ext}\times`$ state therefore occurs, so
PostgreSQL does not trigger execution-state refinement. This separates
the existence of evaluator imperfections from their exposure by ordinary
agent trajectories.

#### Playwright.

The extraction_table pair reaches internal and benchmark-external
acceptance under an oracle that primarily validates output format and
row count; this should not be interpreted as a complete
semantic-correctness guarantee. The r1_arxiv pair remains at internal
and external failure under a correctness-calibrated evaluator. The
remaining two tasks are excluded because either independent ground truth
or an observable success state is unavailable.

#### Notion.

The two calibrated Stage 1 evaluators use small suites and are therefore
indicative rather than category-wide evidence. The remove_osaka
historical matched pair exposes an evaluator divergence, but its
evaluator is below the $`0.85`$ admission threshold. Controlled
serialization analysis measures agreement $`0.75`$ under the historical
schema and $`0.50`$ after a live-state serialization change. The latter
decrease is an engineering regression layered on top of the underlying
semantic divergence.

#### GitHub.

The GitHub study remains an incomplete feasibility campaign. A
subsequent audit found that the historical Stage 2 zero scores were
produced by evaluating the live backend inside a short sandbox timeout;
those runs are therefore not used as agent-performance evidence. After
replacing live-backend evaluation with canonical-snapshot scoring, a
strong-executor run on find_salient_file converges at round 0 and passes
post-hoc external verification. The corresponding corrected
weak-executor matched run was not completed, so we make no GitHub
matched-pair or Stage 3 claim.

### E.2 Weak-Executor Context and Model Tier

Removing context truncation substantially changes the weak-executor
result. The truncated GLM-5.2 campaign converges internally on 7/18
completed tasks, whereas the untruncated campaign converges on 21/30.
Twelve tasks previously classified as stalled become internally
converged under full history. The comparison is not denominator-matched,
but the task-level audit supports context truncation as a major source
of the earlier failure mode.

Under identical task-specific evaluators, GLM-4.5 reaches 9/30 internal
and 7/30 external successes, compared with 21/30 and 18/30 for GLM-5.2.
A separate history-accumulating replication reaches 14/30 internally and
12/30 externally, with the same $`85.7\%`$ internal precision as the
primary weak campaign.

### E.3 Paired Contrasts and Localized Evaluator Repair

On debugging, unaided evaluator regeneration fails in four attempts.
Providing an API-visible positive–negative contrast and constraining the
Verifier Evolver to a localized patch yields the required
“fixed-code-present” check in two to three attempts. The corrected
evaluator then assigns full internal fitness to a valid executor state.
This analysis supports the final Stage 3 design choice to expose factual
paired contrasts while requiring minimal, cumulative-regression-checked
evaluator changes.

### E.4 Stagnation and Redundant Refinement

A cap-three replay on uppercase produces identical later weak states and
content-identical evaluator revisions. Two of the three additional
refinement rounds therefore add no new evaluator capability. The final
stagnation gate detects that the remaining state difference is already
covered and terminates all three primary refinement runs without
generating redundant cases.

### E.6 A Verifier-Free Refinement Trigger

In our experiments, Stage 3 is applied to the internally accepted states
that the external verifier rejects. We test retrospectively whether
executor disagreement could replace that signal. For each of the 21
GLM-5.2 final states that its frozen evaluator accepts, we compare it
with the strong executor’s accepted final state on the same task, after
the same canonicalization as in Stage 3, and flag the task under several
rules on the resulting difference. External verdicts are used only to
score the rules
(Table [22](#A5.T22 "Table 22 ‣ E.6 A Verifier-Free Refinement Trigger ‣ Appendix E Additional Analyses and Ablations ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents")).

Flagging any difference catches all three false positives: eight
accepted weak states are identical to the strong state and are correctly
left alone. However, ten of the 18 correct states also differ, mostly in
file content, so only 3 of the 13 flagged tasks are real false
positives. Narrower rules miss some false positives, because the three
differ in different ways: uppercase only in trailing newlines, debugging
in file content, and structure_mirror in missing structure. Such a
trigger is therefore usable only if Stage 3 can dismiss harmless
differences. Its instruction-grounding filter and regression gate are
designed to do this, but they were not exercised on these false alarms,
so whether they would decline them or over-tighten the evaluator is
untested. The analysis also requires a strong-executor state and uses
only three positive cases.

## Appendix G Oracle Isolation, Provenance, and Reproducibility

### G.1 External-Verifier Information Boundary

The external MCPMark verifier is invoked only after an internal
evaluator or workflow trajectory has been frozen. Its verdict is never
used for workflow ranking, alternative credit, evaluator repair,
convergence, or termination. Outside the loop, its verdicts are used for
three decisions: admitting an evaluator to Stage 2 (agreement
$`\geq 0.85`$ on the evaluator’s challenge suite), selecting the
internally accepted but externally rejected states that Stage 3 refines,
and confirming that each reference state $`F^{+}`$ passes. The strength
of this guarantee differs across experimental phases and is reported
explicitly in
Table [25](#A7.T25 "Table 25 ‣ G.1 External-Verifier Information Boundary ‣ Appendix G Oracle Isolation, Provenance, and Reproducibility ‣ VeriEvolve: Evaluator-First Evolution for Tool-Using Agents").

### G.2 Stage 3 Packet Isolation

Each Stage 3 model call receives a small allowlisted packet containing
the task instruction, current evaluator, sanitized challenge cases,
factual state-diff information, and an output contract. State paths,
external verdict fields, and other non-allowlisted values are removed
before packet creation. Every packet is scanned for prohibited tokens,
including references to the external verifier and external verdict
fields.

The model runs from a temporary directory outside the workbench. Most
filesystem and process tools are disabled; read operations are logged.
An attempt to access material outside the approved packet is classified
as an information_boundary_violation and aborts the run. No such
violation occurs in the primary Stage 3 campaign.

### G.3 Provenance and Immutable Artifacts

Each reported run retains its source commit, strategy identifier,
evaluator versions and hashes, workflow-state hashes, per-round
telemetry, and terminal classification. Stage 3 state archives preserve
canonical tree hashes and archive hashes for all retained weak and
reference states. Cumulative regression records whether the candidate
evaluator accepts $`F^{+}`$, rejects all prior false-positive weak
states, preserves previous case verdicts, and handles newly added cases.

Independent reproduction provides additional evidence:

- •
  The uppercase $`E^{(1)}`$ evaluator is byte-identical across three
  independent Verifier-Evolver searches.
- •
  Canonical weak-state tree hashes recur across independent runs for
  uppercase, debugging, and structure_mirror.
- •
  The externally accepted structure_mirror state hash 80aeae4e... is
  reached both by the primary run after one refinement round and by the
  separate controlled run.

### G.4 Run Classification and Intervention Policy

Infrastructure failures are separated from semantic task outcomes.
Provisioning errors, provider aborts, source mismatches, and
unobservable success states are not assigned a semantic score of zero.
The primary campaigns permit deterministic materialization and harness
repair, checkpoint-resume after transient provider failures, and bounded
model repair within the predeclared budget. They do not permit
task-specific manual evaluator logic, external-verifier feedback inside
a loop, or unreported changes to scientific settings.

Development and diagnostic runs are retained for mechanism analysis but
are not pooled with primary outcomes. This distinction is especially
important for the Stage 3 development lineage, the pre-fix GitHub
scoring runs, the Notion serialization diagnostics, and the
pre-provenance Playwright runs.

## Appendix H Prompts and Artifact Schemas

### H.1 Prompt Availability

Exact rendered prompts from the original interactive Stage 1 sessions
were not recorded. We therefore report the role contract, visible
inputs, tools, and output schema rather than reconstructing those
prompts after the fact. Stage 2 and Stage 3 prompt templates are
retained in source, although campaign-era Stage 2 prompt hashes were not
recorded on every early run. A prompt inventory recording available
paths, hashes, invocation modes, and campaign associations will be
released with the code.

### H.2 Role Contracts

#### Initial Test-Suite Generator.

Given the full task instruction and observable initial state, identify
explicit and implicit requirements and generate at least one complete
positive state, one clean negative, and adversarial near-misses. Labels
must be justified from the task instruction alone. The output is a
declarative mutation specification that a deterministic category adapter
materializes.

#### Initial Verifier Evolver.

Given the materialized challenge states and their instruction-derived
labels, write a sandbox-compatible verify(context) function. When the
internal gate fails, revise the evaluator from deterministic case-level
feedback while preserving already-correct checks.

#### Workflow Evolver.

Given the current alternative pool, per-alternative score statistics,
round history, failed checks, and artifact-inspection diagnosis, propose
a small set of new node alternatives. The output is a JSON object
containing a hypothesis and at most one new alternative per selected
node.

#### Refinement Test-Suite Generator.

Given the task instruction, current evaluator, strong–weak difference
clusters, and immutable state anchors, generate paired cases that
reproduce and remove one selected difference while holding unrelated
state fixed.

#### Refinement Verifier Evolver.

Given the current evaluator, cumulative cases, paired factual contrasts,
and deterministic feedback, produce a localized patch targeting the
uncovered constraint. A full rewrite is permitted only when the required
localized edit cannot be expressed safely.

#### Workflow Executors.

Given one selected workflow path and access to the category-specific
tool interface, execute the task in an isolated environment. The
executor does not receive evaluator source, external-verifier
information, or outputs from other candidate paths.

### H.3 Challenge-State Schema

A challenge state contains:

```ltx_verbatim
{
  "case_id": "...",
  "cluster": "...",
  "expected_pass": true | false,
  "adversarial_description": "...", // optional
  "anchor": "f_plus" | "weak",  // refinement only
  "ops": [
    {
      "type": "...",
      "path": "...",
      "content": "...",             // optional
      "from": "..."                 // optional
    }
  ]
}
```

Initial Stage 1 operations are applied to an isolated copy of the
initial environment. Refinement cases may instead be anchored on
$`F^{+}`$ or the current weak state.

### H.4 Evaluator Schema

Evaluators expose one sandboxed function:

```ltx_verbatim
verify(context) -> {
  "passed": bool,
  "checks": [
    {
      "check_id": str,
      "description": str,
      "requirement_ids": [str, ...],
      "passed": bool,
      "evidence": {...},
      "severity": "required" | "optional"
    }
  ],
  "summary": str
}
```

The Filesystem evaluator context provides nine read-only operations for
file existence, directory existence, globbing, directory listing, text,
JSON, and CSV reading, text hashing, and file-size inspection. Imports,
direct file opening, code evaluation, subprocesses, network access, and
filesystem writes are prohibited.

### H.5 Workflow-Alternative Schema

Each active workflow node stores alternatives of the form:

```ltx_verbatim
{
  "alt_id": "...",
  "prompt_template": "...",
  "system_prompt": "...",             // optional
  "max_react_iterations": 20  // ReAct node only
}
```

A workflow stores the ordered node list, alternatives, protected
alternatives, caps, accumulated per-alternative statistics, and path
history. A candidate path selects one alternative from each active node.

### H.6 State-Difference and Counterfactual Schemas

A canonical difference cluster records:

```ltx_verbatim
{
  "kind": "content" | "missing_file" | "extra_file"
          | "missing_dir" | "extra_dir" | "empty_dir"
          | "symlink" | "mode",
  "characteristic": "...",
  "paths": ["...", ...],
  "signature": "..."
}
```

A paired counterfactual uses the same cluster identifier for:

- •
  a negative case that reproduces the selected difference; and
- •
  a positive control that removes only that difference.

The label-consistency gate validates their expected verdicts, while the
coverage gate confirms that the pair actually toggles the targeted
cluster.

### H.7 Cumulative Regression and Loop State

The cumulative regression artifact records:

```ltx_verbatim
{
  "cumulative_freeze_decision":
      "FREEZE" | "REJECT",
  "all_prior_weak_states_rejected": true | false,
  "cumulative_weak_states": [...],
  "added_check_ids": [...],
  "removed_check_ids": [...],
  "case_results": [...]
}
```

The Stage 3 loop state stores evaluator hashes, weak-state tree hashes,
per-round differences and telemetry, the set of seen and covered
clusters, stagnation decisions, and the final terminal reason. The run
manifest binds this lineage to a run identifier, source commit, and
frozen strategy.
