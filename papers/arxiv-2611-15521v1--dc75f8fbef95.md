###### Abstract

Emerging personal AI agents raise fundamental scalability and privacy
concerns for centralized multi-agent systems (MASs), which rely on a
global orchestrator with broad access to agents, resources, and
communication. In decentralized environments, global visibility is
unavailable. Agents need to proactively discover non-local resources
(e.g. tools, skills), and collaborate with other agents to solve tasks.
We study decentralized multi-agent collaboration under graph-constrained
communication, a natural reflection of human structures. Each agent
observes only its local state and can interact only with neighboring
agents. We introduce a benchmark with synthetic scalable distributed
tool calling with 100K+ tools. Our experiments reveal that recent LLM
agents struggle to discover non-local relevant resources and collaborate
in decentralized setting. Moreover, standard reinforcement learning
fails to reliably overcome this limitation, suggesting that
decentralized MAS needs more explicit harness mechanisms for effective
collaboration, even using SOTA LLMs. We then present a strong baseline
GraphHarness, combining topology-aware warmup with self-improving
LLM-based routing. Results show that GraphHarness substantially improves
task success (+48.5) and produces higher quality collaboration (+30.6),
while using fewer costs (+34.0) than baselines.

## 1 Introduction

Personal AI agents are rapidly becoming accessible to a broad
population, such as Meta Muse¹¹ 1
https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/
and OpenClaw.²² 2 https://openclaw.ai/ The proliferation of these
independently operated agents creates a new opportunity for large-scale
decentralized multi-agent collaboration ([Kim et al., 2025](#bib.bib20);
[Mao et al., 2025](#bib.bib35)), through existing organizational
structures such as social networks ([Jiang et al., 2026](#bib.bib18)).

In such multi-agent systems (MASs), agents are naturally organized in a
decentralized manner, without a centralized orchestrator ([Li et al.,
2023](#bib.bib22); [Liu et al., 2024](#bib.bib29)). Individual agents
may differ in their knowledge, capabilities, and access to resources,
making collaboration necessary for solving tasks that no single agent
can complete alone ([Mao and Mirhoseini, 2026](#bib.bib36); [Cheng
et al., 2025](#bib.bib6)). Agents need to discover relevant peers,
exchange information, and coordinate actions autonomously.

Prevailing MASs are mostly centralized, with three major limitations.
_1) Difficult to scale and maintain._ Existing MASs assume that
knowledge is stored in a centralized registry. As multi-agent ecosystems
grow toward web scale, it becomes prohibitively expensive for all
individual agents to access the full capability space, as resources are
continuously added, updated, deprecated, or moved across
organizations ([Grötschla et al., 2025](#bib.bib14); [Zhu et al.,
2025a](#bib.bib68)). _2) Privacy concern._ Many useful skills depend on
private data, restricted information, or specialized runtime, which
cannot always be copied into a shared repository. Even when a resource
can be advertised, its implementation or intermediate states may need to
remain hidden from other parties ([Louck et al., 2025](#bib.bib31); [Zou
et al., 2025](#bib.bib70); [Hu and Rong, 2025](#bib.bib16); [Cheng and
Amiri, 2025](#bib.bib5)). _3) Less collaborative and proactive in
decentralized environment._ Current MASs typically rely on centralized
orchestrators to organize agents and select relevant resources. However,
when no orchestrator exists, individual agents must proactively
coordinate with other agents and discover useful resources through
interaction ([Ma et al., 2025](#bib.bib34); [Davidson et al.,
2026](#bib.bib9); [Pappu et al., 2026](#bib.bib41)).

We study the following research question:

> _Can agents proactively discover external knowledge and solve complex
> tasks in a large-scale decentralized manner?_

![Refer to caption](2611.15521v1/fig1.png)

Figure 1: Illustration of decentralized multi-agent collaboration

We study decentralized multi-agent collaboration, a novel regime to
evaluate MAS on decentralized knowledge discovery and collaboration. In
this setting, each agent only observes its local knowledge and its
immediate neighbors on the communication graph, with zero global
knowledge. Given a query, the originating agent may choose to
proactively search through the network by querying neighbors, forwarding
requests, and deciding whether to terminate or continue the search. A
successful task execution requires involved agents to collectively and
efficiently locate the required capability by the query.

This setting extends multi-agent collaboration from coordination of
centralized orchestrator to discovery over independently operated peers.
Each agent develops a partial, local, and workload-dependent
understanding of the surrounding capability network through interaction.
This extension is necessary when capabilities cross organizational
boundaries, ownership changes over time, and relevant expertise may be
reachable only through intermediate collaborators.

We design a benchmark for the proposed setting with 160 tasks of three
difficulty levels, with 100k+ distributed tools, five network scales and
three topologies. We propose three metrics 1) task success, 2)
collaboration quality, 3) efficiency.

We summarize our contributions as follows.

- •
  A formulation for decentralized knowledge discovery and collaboration.
  We introduce the Graph-Constrained Dec-POMDP setting where knowledge
  are distributed across a network of agents rather than stored in a
  globally searchable registry. Agents must proactively locate relevant
  capabilities through local interaction and access them through either
  knowledge transfer or remote execution.
- •
  Insights on multi-agent behaviors. We discovery when and why agents
  fail in decentralized multi-agent collaboration, which sheds light on
  the future development of agent, including training data and
  evaluation tasks.
- •
  A baseline agent learned proactive collaborate. We design a baseline
  agent that can learn from past experiences and evolve over time.

## 2 Related Work

##### Multi-agent collaboration.

LLM-based multi-agent systems (MAS) have been studied for collaborative
problem solving, where agents specialize, communicate, and reach
consensus ([Guo et al., 2024](#bib.bib15); [Tran et al.,
2025](#bib.bib53)). Prior work examines collaboration under information
asymmetry ([Liu et al., 2024](#bib.bib29)), scientific idea
generation ([Su et al., 2025](#bib.bib50)), self-organizing role
assignment ([Chen et al., 2024](#bib.bib4)), and delegation among agents
and humans ([Tomašev et al., 2026](#bib.bib52); [Zhu et al.,
2026](#bib.bib67)). Yet the benefits of adding more agents are not
guaranteed: several studies show that naive multi-agent teams can
undermine strong individual agents ([Pappu et al., 2026](#bib.bib41)),
fail to explore one another’s knowledge ([Choi et al.,
2026](#bib.bib8)), exhibit collaboration gaps in open-world
settings ([Davidson et al., 2026](#bib.bib9)), and expose weak links
under adversarial prompting ([Arora et al., 2025](#bib.bib1)). This
motivates mechanisms that make collaboration robust rather than merely
larger.

A growing body of work optimizes _how_ agents are connected. Methods
learn or prune communication graphs ([Li et al., 2025](#bib.bib21)) and
jointly optimize prompts and topologies ([Zhou et al.,
2026](#bib.bib66)). Routing approaches decide which agent or context to
invoke ([Liu et al., 2025a](#bib.bib27); [Zhang et al.,
2025b](#bib.bib64); [Shi et al., 2025](#bib.bib49); [Yang et al.,
2026b](#bib.bib57)), including RL-trained routers ([Zhang et al.,
2025a](#bib.bib62)) and decentralized routing policies ([Lozano-Cuadra
et al., 2025](#bib.bib32)). Decentralized designs coordinate agents
without a central controller ([Yang et al., 2025](#bib.bib58); [Mao and
Mirhoseini, 2026](#bib.bib36)), and budget-aware formulations trade off
performance against cost ([Yang et al., 2026a](#bib.bib56)). Our
skill-graph formulation is closest to this line, treating topology as a
first-class, adaptable object.

##### Learning and self-evolution.

Beyond fixed pipelines, agents can be trained to collaborate via
multi-agent reinforcement learning ([Liu et al., 2025b](#bib.bib28);
[Liao et al., 2025](#bib.bib24); [Feng et al., 2026](#bib.bib10); [Liu
et al., 2026a](#bib.bib25)), and can self-improve through shared
experience ([Weng et al., 2026](#bib.bib55)), scaling ([Qian et al.,
2025](#bib.bib44); [Shao et al., 2026](#bib.bib47)), or test-time
adaptation ([Liu et al., 2026b](#bib.bib26)). Most relevant to us,
skill-centric systems co-evolve reusable competencies across
agents ([Pan et al., 2026](#bib.bib39); [Nie et al., 2026](#bib.bib37);
[Zhang et al., 2026](#bib.bib63)).

##### Benchmarks and applications.

MAS are increasingly evaluated on standardized benchmarks spanning
general collaboration and competition ([Zhu et al., 2025a](#bib.bib68)),
cooperative RL tasks ([Papadopoulos et al., 2025](#bib.bib40)), planning
and scheduling ([Geng and Chang, 2026](#bib.bib12)), enterprise
workflows ([Yu et al., 2026](#bib.bib61)), multimodal embodied
settings ([Long et al., 2024](#bib.bib30)), competitive games ([Wang
et al., 2024](#bib.bib54)), swarm intelligence ([Ruan et al.,
2025](#bib.bib45)), and medical tasks ([Zhu et al., 2025b](#bib.bib69));
questions of dependency trust are also raised ([Yao et al.,
2025](#bib.bib60)). Applications range from autonomous scientific
discovery ([Ghareeb et al., 2026](#bib.bib13); [Jin et al.,
2025](#bib.bib19); [Lyu et al., 2026](#bib.bib33)) and infrastructure
management ([Saifullah et al., 2024](#bib.bib46)) to large-scale social,
hospital, and economic simulation ([Li et al., 2024](#bib.bib23); [Mao
et al., 2025](#bib.bib35); [Qi et al., 2026](#bib.bib43)), often built
on general MAS platforms ([Gao et al., 2024](#bib.bib11)).

## 3 DecArena: A Benchmark for Decentralized Multi-Agent Collaboration

We introduce a benchmark for evaluating large-scale decentralized
collaboration among agents, where no agent has access to a global
registry of resources. Instead, resources are distributed, and agents
must solve tasks using only their own local resources and information
obtained through communication. The benchmark therefore tests whether
agents can discover, request, route to, and compose distributed
resources under local observability.

### 3.1 Problem Formulation

##### Decentralized POMDP

A Decentralized Partially Observable Markov Decision Process (Dec-POMDP)
models multiple agents that act under partial observability and optimize
a shared objective ([Bernstein et al., 2002](#bib.bib2); [Oliehoek
et al., 2016](#bib.bib38)). We use the tuple
$`\left(\mathcal{A},\mathcal{S},\{\mathcal{U}_{i}\}_{i=1}^{n},T,R,\{\mathcal{O}_{i}\}_{i=1}^{n},O\right)`$,
where

- •
  $`\mathcal{A}=\{A_{1},\ldots,A_{n}\}`$ is the set of agents
- •
  $`\mathcal{S}`$ is the global environment-state space
- •
  $`\mathcal{U}`$ is the action space
- •
  $`T(s^{\prime}\mid s,\mathbf{u})`$ is the transition model under joint
  action $`\mathbf{u}`$
- •
  $`R(s,\mathbf{u})\in\mathbb{R}`$ is the shared reward
- •
  $`\mathcal{O}_{i}`$ is the local-observation space of agent $`A_{i}`$
- •
  $`O`$ defines the observation distribution after an environment
  transition

The key property is decentralization. There is no controller that
observes the complete state and chooses actions for all agents. Instead,
each agent acts from its own local history
$`h_{i,t}=\left(o_{i,1},u_{i,1},\ldots,o_{i,t-1},u_{i,t-1},o_{i,t}\right)`$
using a local policy
$`u_{i,t}\sim\pi_{i}\left(\cdot\mid h_{i,t}\right)`$

##### Graph-Constrained Dec-POMDP

We extend the Dec-POMDP with a communication graph
$`G=(\mathcal{A},\mathcal{E})`$, where $`(A_{i},A_{j})\in\mathcal{E}`$
means that $`A_{i}`$ and $`A_{j}`$ may communicate directly. The
neighbor set of $`A_{i}`$ is
$`\mathcal{N}_{i}=\left\{A_{j}\in\mathcal{A}:(A_{i},A_{j})\in\mathcal{E}\right\}`$.
An agent can communicate only with its immediate neighbors. A request
for a resource owned by a distant agent must be routed across multiple
edges. Agents do not receive a global resource index, the full network
topology, or the private states of other agents.

##### Local observation.

At round $`t`$, agent $`A_{i}`$ observes only its local view
$`o_{i,t}=\left(x_{i,t},M_{i,t},\mathcal{K}_{i},\mathcal{N}_{i},\mathbf{1}[i=e]q\right)`$,
where $`x_{i,t}`$ is the local execution state, $`M_{i,t}`$ contains
messages received from neighbors, $`\mathcal{K}_{i}`$ is the set of
local resources owned by $`A_{i}`$, $`e`$ is the entry-agent index, and
$`q`$ is the task instruction. Only the entry agent observes the full
task at the start of an episode. Other agents learn about the task only
through messages they receive.

##### Resources.

Let $`\mathcal{K}`$ denote the full set of resources (tools). Each
resource has an owner. A resource remains local unless its owner
explicitly shares its content or executes it and returns the result.

##### Tasks.

A task is represented by
$`\mathcal{T}=(q,z,\mathcal{G}_{\mathcal{T}})`$, where $`q`$ is the
instruction, $`z`$ is the input, and $`\mathcal{G}_{\mathcal{T}}`$ is a
directed acyclic graph of required resources. Each node corresponds to
one resource call, and its input is either the original task input or
the outputs of preceding nodes. Independent resource calls can be
executed in parallel, while dependent calls wait for their required
inputs.

##### Solution

The solution is a collection of local policies
$`\boldsymbol{\pi}=\{\pi_{i}\}_{i=1}^{n}`$. At each node visit, an agent
may reject the request, return local resource content, return an
execution result, or forward the request to one or more neighbors.
Returning content, returning a result, and forwarding may be combined.
Reject is exclusive.

A local policy acts from the agent’s current observation, local
interaction history, and optional persistent memory $`W_{i}`$
$`u_{i,t}\sim\pi_{i}\left(\cdot\mid h_{i,t},W_{i}\right)`$, where
$`h_{i,t}`$ denotes agent $`i`$’s within-task interaction history up to
time $`t`$, and $`W_{i}`$ denotes optional persistent memory accumulated
across tasks.

### 3.2 Task Construction

We use synthetic tool calling as the primary benchmark because it
isolates decentralized collaboration from general language-model
knowledge. Tool execution is deterministic and exactly verifiable, the
construction scales to more than 100k+ tools, and private keyed behavior
prevents an LLM from producing the correct output without accessing the
required tool.

##### Local resources.

The atomic resource is a _tool_. We define two tool types: a _transform_
maps one input string to one output string, while a _merge_ maps two or
more input strings to one output string. To give semantics to the tool
names, we use the OpenAlex ([Priem et al., 2022](#bib.bib42)) hierarchy
of subjects. Each tool is associated with a broad field and a subfield,
such as transform_cs_ml_00123 and merge_math_algebra_00123. Tools that
share ancestors in the taxonomy are semantically related, providing
agents with useful but non-oracle signals for routing. The actual output
of each tool is determined by a private secret key and cannot be
inferred from its semantic name.

##### Tasks.

Each task is a multi-step tool-composition pipeline over a single input
string. Tools within the same step can execute in parallel, while later
steps depend on outputs from earlier steps. Step 1 applies
$`k\in\{1,2,3\}`$ transforms to the raw input, Step 2 optionally merges
their outputs, and Step 3 optionally applies a final transform. We refer
to these as level-1, level-2, and level-3 tasks, respectively. A task
exposes the input, pipeline structure, and required tool names, while
gold intermediate outputs and the final answer remain hidden and are
used only for evaluation.

##### Synthetic construction.

Tools and tasks are generated deterministically
(Appendix [A.1](#A1.SS1.SSS0.Px3 "Private deterministic execution. ‣ A.1 Tool Construction ‣ Appendix A DecArena Benchmark Details ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration")),
making the benchmark fully reproducible and exactly verifiable. Each
tool receives a secret key derived from its identifier. Given its
inputs, the tool canonicalizes and concatenates them, applies a keyed
hash, and returns a fixed-length token. A single input realizes a
transform, while multiple inputs realize a merge. Higher-level tasks
extend lower-level task families, providing controlled compositional
depth while reusing the same underlying tools. Details are presented in
Appendix [A.2](#A1.SS2 "A.2 Task Construction ‣ Appendix A DecArena Benchmark Details ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

##### Task difficulty.

The full tool bank contains more than 100k+ tools distributed throughout
the subject hierarchy. We instantiate 140 evaluation tasks, including 60
level-1, 40 level-2, and 40 level-3 tasks. The remaining tools form a
large set of semantically structured distractors. Many share subjects or
higher-level ancestors with the required tools but are not useful for
the task. Consequently, semantic similarity provides a meaningful
routing signal but does not identify the correct tool or its owner,
requiring agents to perform targeted discovery over a large distributed
capability space.

### 3.3 Decentralized Environment

##### Tool ownership and accessibility.

Each active tool is assigned to exactly one agent. Since the secret key
remains with the owner, a required tool can be executed only by its
owner. The entry agent needs to locate the owner and request the
corresponding result through the communication network.

We ensure that every benchmark task is solvable from every entry point.
Each required tool has an owner in the environment, and the
communication graph is connected. We then stratify entry agents by the
graph distance to required tool owners to measure how collaboration
changes as resources become more remote.

##### Local observability.

Agents observe their own local resources and their immediate neighbors.
There is no global tool registry, global graph view, or centralized
router. Information about remote resources is obtained only through
neighbor-to-neighbor communication. This prevents the benchmark from
reducing to centralized retrieval over a flat tool collection.

##### Network topology and resource placement.

We evaluate three graph families. In a _random graph_, connectivity is
independent of agent capabilities. In a _semantic graph_, agents are
preferentially connected to others with similar capability profiles. In
a _scale-free graph_, preferential attachment creates a small number of
hubs and many low-degree nodes. These topologies expose different
routing challenges while preserving the same local interaction protocol.
Resource distribution over the network and network statistics are
presented in
Appendix [A.9](#A1.SS9 "A.9 Network Construction and Distributed Resource Ownership ‣ Appendix A DecArena Benchmark Details ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

##### Action space.

When an agent receives a request, it chooses actions using only the
request and its local view. The primitive actions are:

- •
  Reject: decline the request and return no result;
- •
  Return: execute a local tool and return its result;
- •
  Forward: send a request to one or more neighbors;
- •
  Submit: stop and submit the final answer.

Return and Forward may be combined. This allows an agent to provide a
local result while continuing to search for other required resources.
Inefficient behavior is not prohibited and is instead reflected in the
efficiency metrics.

### 3.4 Evaluation

We evaluate each run along three complementary dimensions: task success,
collaboration quality, and efficiency. All case-level scores are
aggregated over tasks and reported as percentages.

##### Task success.

Task success measures whether the agent system completes the full
tool-composition pipeline and produces the exact gold output. Because
tool execution is deterministic, final answers can be verified exactly.
We additionally report per-tool output accuracy as a diagnostic of
partial progress on failed tasks, indicating whether the system
successfully discovered and used some required tools even when the final
task was not completed.

##### Collaboration quality.

Collaboration quality measures whether the system successfully
identifies, obtains, and correctly uses the remote resources required by
a task. Specifically, it combines three aspects: whether required remote
tools are queried, whether their execution results are successfully
returned, and whether the returned results are used correctly in the
task pipeline. The collaboration score is the average of these three
components. For tasks whose required tools are all local to the entry
agent, no collaboration is necessary. We therefore report remote-only
collaboration separately to avoid inflating the headline score with
local cases.

##### Efficiency.

Efficiency measures how economically the system explores the network
while solving a task. It combines three normalized components. _Visit
efficiency_ measures how many agent visits are used relative to a
distance-based reference. _Query focus_ measures how selectively
requests are forwarded and penalizes unnecessary fan-out. _Round
efficiency_ measures the number of interaction rounds relative to an
idealized reference that accounts for both tool distance and pipeline
depth. Together, these metrics distinguish targeted collaboration from
success obtained through broad or redundant exploration. Exact
definitions are provided in
Appendix [A.10](#A1.SS10 "A.10 Evaluation Metrics ‣ Appendix A DecArena Benchmark Details ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

## 4 Experiments

We evaluate decentralized collaboration by varying where a task enters
the network and how much routing state an agent can use. Unless
otherwise noted, all methods operate under the same local-observation
and neighbor-communication constraints defined in
Section [3](#S3 "3 DecArena: A Benchmark for Decentralized Multi-Agent Collaboration ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

### 4.1 Evaluation Protocol

##### Entry agents.

For each task, we evaluate every agent as the entry agent. Let
$`\mathcal{T}(q)`$ be the tools required by task $`q`$, let $`o(t)`$ be
the owner of tool $`t`$, and let $`d_{\mathcal{G}}(\cdot,\cdot)`$ denote
shortest-path distance in the communication graph. We define the case
distance as:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
d(q,A_{0})=\max_{t\in\mathcal{T}(q)}d_{\mathcal{G}}\left(A_{0},o(t)\right).
``` |  | (1) |

This measures the distance to the farthest required tool owner and
naturally separates local, one-hop, two-hop, and longer-range cases.
Reporting performance by distance allows us to distinguish local tool
use from increasingly difficult multi-hop collaboration.

##### Coordination protocol.

The main benchmark uses recursive routing. When an agent receives a
request, it may answer using an owned tool, reject the request, or
forward it to selected neighbors. Each receiving agent makes its own
local routing decision. The entry agent therefore does not observe or
control every intermediate hop.

### 4.2 Evaluated Agents

We evaluate the following agents: 1) Reflex Agent ([Jaakkola et al.,
1994](#bib.bib17)), which chooses its next action using only the current
local observation, $`u_{i,t}\sim\pi_{\mathrm{LLM}}(\cdot\mid o_{i,t})`$;
2) Reflex + History ([Yao et al., 2023](#bib.bib59)), which conditions
on the agent’s within-task interaction history,
$`u_{i,t}\sim\pi_{\mathrm{LLM}}(\cdot\mid h_{i,t})`$, including
previously contacted neighbors and returned results; 3)
Experience-Conditioned Agent, which additionally retrieves successful
local experiences from previous tasks,
$`u_{i,t}\sim\pi_{\mathrm{LLM}}(\cdot\mid h_{i,t},\mathcal{H}_{i}^{+})`$;
4) Numerical Q-Routing, a Q-Routing-based baseline ([Boyan and Littman,
1993](#bib.bib3)) in which each agent maintains local scores for
observed resource-neighbor pairs and updates them from routing outcomes;
5) Broadcast, which forwards every resource request to all immediate
neighbors while still allowing locally available results to be returned;
6) Oracle Route, which gives only the entry agent the owner and a
shortest route to each required tool; 7) Oracle Route All, which exposes
the same oracle routing information to every participating agent; 8)
Collaborative Prompting, which augments the Reflex prompt with explicit
instructions to actively seek help, return useful local results, and
forward requests when appropriate; 9) Supervised Fine-Tuning (SFT),
which fine-tunes a shared collaboration policy on high-reward
trajectories collected from the training networks using local
observations and accepted structured decisions; 10) Group Relative
Policy Optimization (GRPO) ([Shao et al., 2024](#bib.bib48)), which
starts from the SFT policy, samples multiple complete collaboration
trajectories per task, and optimizes the policy using rewards based on
correctness, collaboration quality, and efficiency; and 11) On-Policy
Self-Distillation (OPSD) ([Zhao et al., 2026](#bib.bib65)), which
distills a self-teacher with oracle routing information into a student
policy.

Full details are provided in
Appendix [B](#A2 "Appendix B Details of Evaluated Agents ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

## 5 A Strong Baseline: GraphHarness

GraphHarness is a collaboration harness that combines a topology-aware
warmup with experience-adaptive LLM routing. It gives each agent useful
local routing context while preserving decentralized execution. No agent
receives a global resource registry or global graph view.

### 5.1 Topology-Aware Warmup

Before evaluation, agents perform local message passing on auxiliary
tasks that are disjoint from the test tasks. Each agent begins with a
routing state $`W_{i}^{(0)}`$ derived from its own resource metadata. At
warmup layer $`\ell`$, it exchanges compact routing information only
with immediate neighbors and updates its state as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
W_{i}^{(\ell+1)}=\Phi\left(W_{i}^{(\ell)},\operatorname{AGG}\left\{\Psi\left(W_{i}^{(\ell)},W_{j}^{(\ell)}\right):A_{j}\in\mathcal{N}_{i}\right\}\right).
``` |  | (2) |

After $`L`$ rounds, $`W_{i}=W_{i}^{(L)}`$ is fixed and used as
persistent routing context. Information can propagate beyond one hop
across warmup rounds, but every communication step still follows an edge
in the graph.

### 5.2 Experience-Adaptive Routing

During evaluation, each agent combines its warmup state with its current
task history and local experience memory. Let $`M_{i,t}`$ denote the
routing experience stored by agent $`A_{i}`$. For a request involving
resource $`k`$ and candidate neighbor $`A_{j}`$, the LLM produces a
routing score

|  |  |  |  |
|----|----|----|----|
|  |
``` math
s_{i}(k,A_{j},t)=f_{\mathrm{LLM}}\left(k,A_{j},W_{i},M_{i,t},h_{i,t}\right).
``` |  | (3) |

The agent uses these scores to choose one or more neighbors. After
observing the outcome, it updates its local experience memory

|  |  |  |  |
|----|----|----|----|

### 5.3 Results

The results in
Table [1](#S5.T1 "Table 1 ‣ 5.2 Experience-Adaptive Routing ‣ 5 A Strong Baseline: GraphHarness ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration")
show three consistent trends across the memory, tool, and skill tracks.
First, centralized access provides the strongest upper bound on task
success. When the system is given an oracle resource owner or a global
registry, performance is substantially higher than decentralized
alternatives across all tracks. This confirms that the tasks are
solvable when the required resources can be directly identified.
However, centralized settings do not measure collaboration quality,
since agents do not need to discover or negotiate access to remote
resources through the network.

Second, fixed decentralized policies achieve moderate task success but
incur nontrivial communication cost. Policies that always return content
or results improve over metadata-only sharing because they expose more
useful information to the requester. Always-forward policies further
increase collaboration scores by expanding the search over the network,
but this comes at a clear efficiency cost. The strongest fixed baseline
is the policy that both returns content or results and forwards the
request, suggesting that broad sharing and flooding can recover many
required resources. However, its low efficiency indicates that this
success is obtained through excessive communication rather than targeted
collaboration. The budgeted fixed policy improves efficiency but reduces
success, revealing the expected trade-off between resource discovery and
communication cost.

Third, fully decentralized agents are more challenging to coordinate.
The autonomous setting with only tool descriptions performs worst
because agents must infer both the existence and usefulness of neighbor
communication. Explicit network briefing improves task success and
collaboration quality, showing that agents benefit from being told that
useful resources may exist on neighboring nodes. Providing network
metadata further improves success by helping agents route requests more
effectively. Adding visited-node memory improves both success and
efficiency, indicating that agents can avoid redundant exploration when
they remember which nodes or resources have already been queried.
Finally, imposing a communication budget increases efficiency but lowers
success, suggesting that current autonomous agents still rely on
relatively broad exploration to discover useful remote resources.

Across tracks, the skill setting is consistently harder than memory and
tool use. This is expected because skills require not only locating the
correct remote resource, but also understanding when and how to apply
procedural knowledge. Overall, these results highlight the central
challenge of decentralized agent collaboration: centralized registries
offer high success but bypass collaboration, fixed policies provide
useful but costly baselines, and fully decentralized agents must balance
discovery, routing, privacy-preserving access, and communication
efficiency.

### 5.4 Discussion

##### Robustness to Adversarial Agents

Adversarial agents substantially degrade decentralized collaboration.
When $`k`$ adversarial agents deliberately forward requests to the least
promising neighbor, task success drops from 53.7 to 3.2 and
collaboration quality decreases from 57.1 to 25.7. Efficiency also
declines from 71.5 to 33.8. The degradation is most severe when
adversarial agents occupy structurally or semantically important
positions, such as hubs in scale-free networks or nodes connecting
semantically related regions. These results show that decentralized
collaboration is sensitive not only to the presence of adversarial
behavior, but also to where adversarial agents are located in the
network, see
Table [2](#S5.T2 "Table 2 ‣ Robustness to Adversarial Agents ‣ 5.4 Discussion ‣ 5 A Strong Baseline: GraphHarness ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

| 1          | 22.5    | 37.9          | 55.1       |

##### Robustness to Conflicting Information.

We further study decentralized collaboration when agents receive
conflicting routing information ([Cheng et al., 2026](#bib.bib7); [Sun
et al., 2026](#bib.bib51)). We use a ring network so that each agent has
exactly two neighbors, which provides a controlled setting for isolating
conflict resolution. For each resource request, an agent receives two
local knowledge sources that recommend where the request should be
forwarded. In the no-conflict condition, both sources identify the
neighbor that lies on a shortest path to the required resource owner. In
the conflict condition, one source provides the correct direction while
the other recommends the opposite neighbor. We randomize which source is
correct across tasks so that agents cannot resolve conflicts based only
on source identity. Introducing conflicting information reduces task
success from 53.7 to 27.2, collaboration quality from 58.1 to 35.1, and
efficiency from 71.5 to 30.8. The results suggest that decentralized
collaboration degrades substantially when locally available routing
evidence is inconsistent, even when the underlying network remains fully
connected and the required resources remain reachable, see
Table [3](#S5.T3 "Table 3 ‣ Robustness to Conflicting Information. ‣ 5.4 Discussion ‣ 5 A Strong Baseline: GraphHarness ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

|----------------|---------|---------------|------------|
| No Conflicts   | 53.7    | 58.1          | 71.5       |
| With Conflicts | 27.2    | 35.1          | 30.8       |

## 6 Conclusion

We introduce DecArena, a benchmark for evaluating large-scale
decentralized multi-agent collaboration. By formulating
Graph-Constrained Dec-POMDP, DecArena evaluates whether agents can
locate, access, and compose distributed resources without a centralized
orchestrator. Our experiments show that even strong LLM agents struggle
to proactively discover non-local resources using local information
alone. These results suggest that decentralized collaboration remains a
challenging task for existing agents to learn. We propose a strong
baseline, GraphHarness, which is topology-aware, experience-adaptive and
performs efficient and high quality collaboration. DecArena provides a
controlled and scalable testbed for developing agents that can
collaborate effectively in increasingly large and distributed agent
ecosystems.

## Limitations

DecArena intentionally isolates decentralized resource discovery and
routing through synthetic, deterministic tool-calling tasks, which
enables exact verification and controlled scaling but does not capture
the full complexity of real-world collaboration involving ambiguous
requests, heterogeneous APIs, natural-language expertise, changing
permissions, execution failures, or strategic participants.

The headline setting also assumes connected networks, unique resource
ownership, and reachable required resources, so failures measure
discovery and coordination rather than network partition or resource
unavailability.

Our evaluated topologies represent only several stylized network
structures, and experiments at up to 1,000 agents do not fully reproduce
the dynamics of web-scale agent ecosystems.

Finally, performance can depend on the underlying LLM, prompting
strategy, network construction, and persistent routing state, while the
current benchmark emphasizes resource discovery more than other
decentralized challenges such as trust, authentication, incentive
compatibility, asynchronous communication, and evolving ownership.
Extending DecArena to real tools, dynamic networks, heterogeneous
agents, and richer adversarial or privacy-sensitive settings is
therefore an important direction for future work.

## Ethical Considerations

DecArena is designed primarily as a controlled research benchmark and
uses synthetic tools with deterministic execution rather than human
data, reducing risks related to personal information, annotation labor,
or sensitive real-world content. At the same time, advances in
decentralized agent collaboration may have broader societal
implications. Systems that can autonomously discover and invoke
resources across organizational or ownership boundaries could improve
scalability and enable capabilities to remain locally controlled, but
they may also make distributed systems harder to audit and increase the
risk of unauthorized resource access, information leakage, malicious
routing, or propagation of incorrect information. The substantial
degradation observed under adversarial agents and conflicting routing
information further highlights these concerns. Real-world deployment of
such systems should therefore incorporate explicit authorization and
consent, capability-level access control, provenance and logging,
sandboxed execution, communication limits, and mechanisms for detecting
malicious or unreliable participants. We view DecArena as a setting for
studying these challenges rather than evidence that fully autonomous
decentralized agent networks are ready for unrestricted deployment.

## Appendix A DecArena Benchmark Details

This section provides the full construction and evaluation details for
DecArena. The benchmark is designed to isolate a specific capability:
whether agents can discover and use resources that are distributed
across a communication network when no agent has access to a global
resource registry or a global view of the network. We use synthetic tool
calling as the primary task family because it provides exact,
deterministic verification while preserving the central difficulty of
decentralized resource discovery, multi-hop routing, and distributed
execution.

### A.1 Tool Construction

##### Tool bank.

We construct a large synthetic bank containing more than 100k tools. The
bank contains two primitive tool types, *transform* and *merge*. Tool
identifiers are unique across the bank. Only a small fraction of the
full tool bank is required by the benchmark tasks, while the remaining
tools act as semantically plausible distractors.

The large tool space is intentional. If the environment contained only
the tools required by the evaluation tasks, identifying a plausible tool
description would already provide substantial information about the
correct route. Instead, DecArena places each required tool within a much
larger capability ecosystem containing many irrelevant tools with
similar metadata. The resulting problem therefore evaluates targeted
resource discovery rather than enumeration over a small candidate set.

##### Tool types.

A *transform* consumes a single string and produces a single string,

|     |             |     |     |
|-----|-------------|-----|-----|
|     |
       ``` math
       y=f_{t}(x),
       ```          |     | (5) |

while a *merge* consumes two or more strings and produces a single
output,

|     |                                             |     |     |
|-----|---------------------------------------------|-----|-----|
|     |
       ``` math
       y=f_{t}(x_{1},\ldots,x_{m}),\qquad m\geq 2.
       ```                                          |     | (6) |

Both tool types use the same underlying deterministic keyed
transformation. They differ only in the number of inputs they consume.

Each tool is associated with a unique identifier, a semantic category, a
natural-language description, an input schema, an output schema, and a
private execution key. Tool identifiers are deliberately semantically
structured. For example, an identifier may contain lexical cues
associated with its category or function. These cues give an LLM a
meaningful routing signal without revealing the tool output.

##### Private deterministic execution.

Each tool $`t`$ receives a private secret key derived deterministically
from a master seed and the tool identifier:

|     |                                                |     |     |
|-----|------------------------------------------------|-----|-----|
|     |
       ``` math
       \mathrm{key}(t)=\mathrm{HMAC\text{-}SHA256}\\
       (\texttt{master\_seed},\texttt{tool\_id}_{t}).
       ```                                             |     | (7) |

Given input strings $`x_{1},\ldots,x_{m}`$, the execution procedure
first canonicalizes the inputs by sorting them and concatenating them
using a fixed delimiter. The canonicalized input is then processed using
the private key. The resulting digest is Base32 encoded and truncated to
a fixed-length output token.

For a transform, $`m=1`$. For a merge, $`m\geq 2`$. Therefore, the same
deterministic construction supports both primitive types.

This design has four useful properties. First, repeated execution of the
same tool on the same inputs always produces the same output. Second,
all intermediate and final outputs can be reproduced exactly by the
evaluator. Third, outputs cannot be reliably inferred from tool names,
descriptions, or semantic categories because the execution key is
private. Fourth, two semantically similar tools still produce unrelated
outputs because their keys differ.

The private key remains with the tool owner. An agent that does not own
a required tool cannot locally reconstruct its output. It must either
obtain the result from the owner or, in resource-transfer variants of
the benchmark, obtain the transferable resource itself.

### A.2 Task Construction

##### Multi-step pipelines.

Each benchmark task defines a directed acyclic computation graph over
synthetic tools. A task begins with a single raw input string and
requires one or more tools to be executed in a prescribed dependency
structure.

We organize tasks into three levels of compositional depth.

A level-1 task applies $`k\in\{1,2,3\}`$ transform tools independently
to the raw input. These calls can be executed in parallel.

A level-2 task first executes the level-1 transforms and then applies
one merge tool to their outputs.

A level-3 task extends the level-2 pipeline with one additional
transform applied to the output of the merge.

For example:

``` ltx_verbatim
Input: Z4P3

Step 1
  transform_green_river_00368(Z4P3)
  transform_amber_maple_00978(Z4P3)

Step 2
  merge_red_nova_00166(outputs from Step 1)

Step 3
  transform_blue_comet_00392
        (output from Step 2)

Return the output from Step 3.
````

If $`S_{j}`$ denotes the set of tools at pipeline stage $`j`$, tools
within the same stage may be executed independently, while stage $`j+1`$
becomes executable only after all required outputs from stage $`j`$ have
been obtained. The benchmark therefore requires not only resource
discovery but also preservation and composition of intermediate results.

##### Task families.

Tasks are generated in families. A family fixes an input string together
with a pool of tools used across multiple levels. Higher-level tasks
extend lower-level tasks whenever the dependency structure permits.

For example, a level-2 instance may reuse the transforms from a
corresponding level-1 instance and append a merge. A level-3 instance
may further append a final transform. This construction allows
compositional depth to vary while holding much of the underlying
semantic content fixed.

As a result, differences between task levels primarily reflect the
additional collaboration and dependency-management requirements rather
than an unrelated change in tool semantics.

##### Evaluation task set.

The evaluation set contains $`140`$ tasks: $`60`$ level-1 tasks, $`40`$
level-2 tasks, and $`40`$ level-3 tasks. Collectively, these tasks
reference $`186`$ distinct required tools.

The number of benchmark tasks is intentionally much smaller than the
size of the global tool bank. The benchmark therefore evaluates whether
agents can locate a sparse set of relevant capabilities embedded in a
much larger distributed resource space.

##### Required tools and distractors.

For each benchmark environment, every tool required by the selected
evaluation tasks is guaranteed to be present. The remaining resource
slots are filled with distractor tools sampled from the global bank.

Distractors are fully valid tools. They have normal identifiers,
descriptions, categories, schemas, and executable implementations, but
they are not required by the current evaluation tasks. They are
therefore indistinguishable from useful tools based only on their status
in the environment.

The purpose of distractors is to prevent resource discovery from
degenerating into simple category matching. Multiple tools may appear
semantically related to the request even though only one exact tool
produces the required output. As the tool bank grows beyond
$`100{,}000`$ tools, the ratio of relevant to irrelevant resources
becomes increasingly sparse, creating a large-scale discovery problem
similar to realistic capability ecosystems.

##### Semantic categories.

Tools are distributed across semantic categories. Category membership
affects the semantic information available in tool metadata and, in the
semantic network condition, influences both network structure and
resource placement.

A configurable fraction of task families can be constructed so that
their tools share a semantic category. The remaining families contain
tools from multiple categories. This produces both semantically coherent
tasks, for which routing toward a specialized region may be beneficial,
and cross-domain tasks, for which the required resources may be
distributed across different parts of the network.

Importantly, category information never uniquely identifies the required
tool. It provides only a routing prior.

### A.3 Communication Networks and Resource Placement

For each benchmark environment, agents form an undirected communication
graph $`G=(V,E)`$, where each node corresponds to an agent and an edge
indicates that two agents may communicate directly. Every tool is
assigned to exactly one agent. There is no resource replication unless
explicitly introduced as a separate ablation.

We evaluate three network families: random, scale-free, and semantic.
Each topology is paired with a corresponding resource-placement
mechanism. This allows us to vary whether graph structure provides
useful information about resource location.

##### Random networks.

The random condition uses an undirected Erdős–Rényi graph. For $`N`$
agents and target average degree $`d`$, each possible edge is sampled
independently with probability

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       p=\min\left(\frac{d}{N-1},1\right).
       ```                                  |     | (8) |

Unless otherwise specified, we use target average degree $`d=6`$.

Resource ownership is independent of network structure. Let $`M`$ denote
the number of active tools placed in an environment. An initial resource
count is independently sampled for each agent as

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       \tilde{n}_{i}\sim\mathrm{Poisson}\left(\frac{M}{N}\right).
       ```                                                         |     | (9) |

Because independent Poisson draws do not necessarily sum to exactly
$`M`$, we apply an exact-total correction. If the sampled counts contain
fewer than $`M`$ ownership slots, the missing slots are assigned to
uniformly sampled agents. If they contain more than $`M`$, uniformly
sampled ownership slots are removed. The final counts therefore satisfy

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       \sum_{i=1}^{N}n_{i}=M.
       ```                     |     | (10) |

The tools are then randomly permuted and partitioned according to these
counts. Thus, neither graph position nor semantic category provides
information about resource ownership in the random condition.

##### Scale-free networks.

The scale-free condition uses preferential attachment. Let

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
m=\max\left(1,\min\left(\left\lfloor\frac{d}{2}\right\rfloor,N-1\right)\right).
``` |  | (11) |

Construction begins from a clique of $`m+1`$ nodes. Each subsequently
introduced agent creates $`m`$ edges to existing agents, with selection
probability proportional to their current degree. With the default
$`d=6`$, we use $`m=3`$.

This produces a heterogeneous degree distribution with a small number of
highly connected hubs and many lower-degree agents.

Resource placement is also degree-biased. If $`d_{i}`$ is the realized
degree of agent $`i`$, each tool is assigned to agent $`i`$ with
probability

|     |                                                          |     |      |
|-----|----------------------------------------------------------|-----|------|
|     |
       ``` math
       P(o(t)=i)=\frac{d_{i}^{\alpha}}{\sum_{j}d_{j}^{\alpha}},
       ```                                                       |     | (12) |

where we use $`\alpha=1`$ by default.

Consequently, structurally prominent agents are also more likely to own
resources. This configuration models decentralized ecosystems in which
well-connected agents tend to accumulate more capabilities or services.

##### Semantic networks.

The semantic condition introduces correlation between agent
specialization, network structure, and resource ownership.

We initially connect all agents in a ring, which guarantees a connected
backbone. Additional edges are then added until the target average
degree is reached.

When constructing each additional edge, an initial endpoint is sampled
uniformly. With probability $`\rho`$, the second endpoint is sampled
from agents sharing the first endpoint’s semantic category. Otherwise,
it is sampled from the full agent population. We use

|     |           |     |      |
|-----|-----------|-----|------|
|     |
       ``` math
       \rho=0.8.
       ```        |     | (13) |

Resource placement uses a corresponding semantic bias. For a tool $`t`$
with category $`c_{t}`$, let

|     |                            |     |      |
|-----|----------------------------|-----|------|
|     |
       ``` math
       V(c_{t})=\{i:c_{i}=c_{t}\}
       ```                         |     | (14) |

be the set of agents assigned to the same category. With probability
$`q`$, the tool is assigned uniformly to an agent in $`V(c_{t})`$.
Otherwise, its owner is sampled uniformly from the entire network:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
o(t)\sim\begin{cases}\mathrm{Uniform}(V(c_{t})),&\text{with probability }q,\\
\mathrm{Uniform}(V),&\text{otherwise}.\end{cases}
``` |  | (15) |

We use $`q=0.8`$. If no agent represents category $`c_{t}`$, ownership
falls back to uniform sampling.

The resulting graph contains semantic communities but does not provide
an oracle route. A category may contain many agents, tools may be placed
outside their matching communities, and a single task may require tools
from multiple semantic regions.

##### Connectivity.

All headline benchmark networks are connected. Random graph generation
can occasionally produce multiple connected components, particularly at
larger scales. We therefore compute the connected components after graph
generation and, when necessary, connect each disconnected component to
the largest component using one additional edge. If the initial graph
contains $`C`$ components, this procedure introduces exactly $`C-1`$
edges, the minimum number required to produce a connected graph.

Scale-free and semantic graphs are connected by construction under the
default generator, but the same connectivity check is applied to all
topologies.

Connectivity guarantees that every required resource is in principle
reachable from every entry agent. It does not reveal the path to that
resource. Thus, failure reflects discovery or routing behavior rather
than an impossible environment.

##### Unique resource ownership.

Every active tool has exactly one owner. If $`\mathcal{K}_{i}`$ denotes
the set of tools owned by agent $`i`$, then

|     |                                              |     |      |
|-----|----------------------------------------------|-----|------|
|     |
       ``` math
       \mathcal{K}_{i}\cap\mathcal{K}_{j}=\emptyset
       ```                                           |     | (16) |

for all $`i\neq j`$, and

|     |                                               |     |      |
|-----|-----------------------------------------------|-----|------|
|     |
       ``` math
       \bigcup_{i=1}^{N}\mathcal{K}_{i}=\mathcal{K}.
       ```                                            |     | (17) |

This property is important because it prevents an agent from succeeding
by accidentally encountering a duplicate copy of the required tool. A
remote tool must be discovered through its actual owner.

### A.4 Local Observability

The defining constraint of DecArena is local observability. No agent
receives a global resource registry, the full adjacency matrix, or the
mapping from tools to owners.

An agent has direct access only to its own resources and can communicate
directly only with immediate graph neighbors. Information about a remote
agent or resource must therefore propagate through a sequence of local
interactions.

For agent $`A_{i}`$ at interaction step $`t`$, the available local
information includes:

- •
  the request currently received by the agent
- •
  currently available task inputs or intermediate outputs
- •
  the tools locally owned by $`A_{i}`$
- •
  the identities of the immediate neighbors of $`A_{i}`$
- •
  messages and results previously received by $`A_{i}`$
- •
  the within-task interaction history available under the evaluated
  agent design
- •
  optional persistent local routing memory for methods that explicitly
  support cross-task adaptation

Only the entry agent initially receives the complete user task. Other
agents learn about the task only through requests forwarded to them.

Most importantly, the environment does not expose a global function of
the form

|     |                                                 |     |      |
|-----|-------------------------------------------------|-----|------|
|     |
       ``` math
       \texttt{lookup(tool)}\rightarrow\texttt{owner}.
       ```                                              |     | (18) |

Locating a resource is therefore part of the benchmark rather than a
preprocessing step performed by an external retriever.

### A.5 Request and Interaction Protocol

A task begins at an entry agent. The entry agent may already own some of
the required tools, while other required tools may be located several
graph hops away.

When an agent receives a request, it chooses among the following
primitive actions:

- •
  Reject: decline the request and return no result
- •
  Return: execute an owned requested tool and return its output
- •
  Forward: propagate the request to one or more immediate neighbors
- •
  Submit: terminate the task and submit a final answer

Return and Forward may be selected simultaneously. For example, an agent
may provide the result of one locally available resource while
continuing to search for another required resource.

We deliberately do not prohibit inefficient actions. An agent may
forward a request to several neighbors, revisit an earlier node, query
an irrelevant resource, or continue searching after receiving a useful
result. These behaviors are logged and penalized through the efficiency
metrics rather than removed from the action space. This allows the
benchmark to distinguish effective collaboration from success obtained
through indiscriminate flooding.

##### Recursive decentralized routing.

The default evaluation uses recursive routing. Once a request is
forwarded to an intermediate agent, that agent independently chooses
whether to answer, reject, or forward it to its own neighbors. The entry
agent therefore does not centrally control every hop.

For example, if $`A_{1}`$ requests tool $`t`$ from neighbor $`A_{2}`$
and $`A_{2}`$ does not own $`t`$, $`A_{2}`$ may decide to forward the
request to $`A_{5}`$. Agent $`A_{1}`$ need not know that $`A_{5}`$
exists before the request reaches it.

This distinction is central to the benchmark. The problem is not simply
to choose a route over a known graph. The route itself emerges from a
sequence of decisions made under different local observations.

##### Remote execution.

The headline tool benchmark uses remote execution. The owner of a
requested tool executes it locally and returns only the output. The
underlying private key and tool implementation are not transferred.

If agent $`A_{j}`$ owns tool $`t`$, a successful remote call therefore
has the form

|     |                                                                |     |      |
|-----|----------------------------------------------------------------|-----|------|
|     |
       ``` math
       A_{i}\rightarrow\cdots\rightarrow A_{j}:\mathrm{request}(t,x),
       ```                                                             |     | (19) |

followed by

|     |                                                   |     |      |
|-----|---------------------------------------------------|-----|------|
|     |
       ``` math
       A_{j}\rightarrow\cdots\rightarrow A_{i}:f_{t}(x).
       ```                                                |     | (20) |

This models resources that depend on private data, credentials,
proprietary code, or specialized execution environments and therefore
cannot simply be copied to the requester.

##### Intermediate results.

Multi-stage tasks require outputs from earlier tools to be reused as
inputs to later tools. Returned results are therefore added to the task
state and may be included in subsequent requests. A level-3 task may
require several remote discoveries across multiple sequential stages
before the final answer can be produced.

### A.6 Entry Agents and Distance-Based Difficulty

For each task, we evaluate the same resource configuration from
different entry agents. Let $`\mathcal{T}(q)`$ denote the tools required
by task $`q`$, let $`o(t)`$ denote the owner of tool $`t`$, and let
$`d_{G}(\cdot,\cdot)`$ denote shortest-path distance in the
communication graph.

For entry agent $`A_{0}`$, we define task distance as

|     |                                                        |     |      |
|-----|--------------------------------------------------------|-----|------|
|     |
       ``` math
       d(q,A_{0})=\max_{t\in\mathcal{T}(q)}d_{G}(A_{0},o(t)).
       ```                                                     |     | (21) |

The maximum captures the farthest required resource that must be reached
to complete the full task.

We group runs into the following distance buckets:

- •
  Local: $`d(q,A_{0})=0`$
- •
  1-hop: $`d(q,A_{0})=1`$
- •
  2-hop: $`d(q,A_{0})=2`$
- •
  3+-hop: $`d(q,A_{0})\geq 3`$

Local cases measure whether an agent can correctly use resources it
already owns. Increasing-distance cases progressively require more
decentralized discovery and routing.

In the headline benchmark, the communication graph is connected and all
task-required resources are present. Therefore, every task is
theoretically solvable from every entry point. This allows success
degradation with distance to be interpreted as a collaboration failure
rather than lack of reachability.

### A.7 Exact Verification

Because all synthetic tools are deterministic, the benchmark computes
the complete gold execution trace for every task before evaluation. This
includes the expected output of each required tool and the final task
output.

Let $`y^{\star}`$ denote the gold final output and $`\hat{y}`$ the
submitted output. End-to-end task success is

|     |                                                  |     |      |
|-----|--------------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{Success}=\mathbbm{1}[\hat{y}=y^{\star}].
       ```                                               |     | (22) |

No learned evaluator is required.

The evaluator also records intermediate outputs. These diagnostics allow
us to distinguish cases in which an agent found some required resources
but failed to complete the full pipeline from cases in which it never
reached the correct resources.

### A.8 Reproducibility

Tool generation, task generation, topology construction, and resource
placement are seeded and deterministic given the benchmark
configuration. Tool execution is deterministic by construction.

For network generation, topology sampling and resource placement use
separate random-number streams. Given network seed $`s`$, graph
construction uses seed $`s`$, while resource placement uses seed
$`s+1`$. This prevents incidental changes in edge generation from
changing the random sequence used for resource ownership.

All benchmark instances store the resulting graph adjacency, resource
ownership, task specification, and generation configuration. The private
execution information required for verification is retained by the
environment but is not exposed to evaluated agents.

### A.9 Network Construction and Distributed Resource Ownership

GraphHarness separates two aspects of the decentralized environment: the
communication topology determines *who can communicate with whom*, while
resource placement determines *where capabilities are located*. We
construct these two components jointly so that different network
families induce qualitatively different resource-discovery problems
while preserving the same neighbor-to-neighbor interaction protocol.

##### Network configurations.

For the tool benchmark, we construct networks with
$`N\in\{10,50,100,500,1000\}`$ agents. For each network size, we
instantiate three topology families: Random, Scale-Free, and Semantic.
This results in 15 network configurations. Unless otherwise specified,
all networks use target average degree $`\bar{d}=6`$ and random seed
$`0`$.

The full synthetic tool bank contains 100k+ tools, of which 186 distinct
tools are referenced by the benchmark tasks. Every tool has exactly one
owner, so resource ownership forms a partition of the active tool set
and no tool is replicated across agents.

The topology and ownership random variables are generated from separate
deterministic random-number streams. The topology, agent categories, and
connectivity repair use seed $`s`$, while resource placement uses seed
$`s+1`$. This separation prevents incidental random choices made during
graph construction from changing the resource allocation.

#### A.9.1 Random Networks

##### Communication topology.

The random topology is an undirected Erdős-Rényi graph. For $`N>1`$,
every unordered pair of agents is connected independently with
probability

|     |                                           |     |      |
|-----|-------------------------------------------|-----|------|
|     |
       ``` math
       p=\min\left(\frac{\bar{d}}{N-1},1\right).
       ```                                        |     | (23) |

Thus, before connectivity repair, the expected degree of every agent is
approximately $`\bar{d}`$. This topology deliberately contains no
relationship between communication structure and resource semantics.

Because sparse Erdős-Rényi graphs can contain disconnected components,
we subsequently enforce connectivity. If the sampled graph contains
$`C>1`$ connected components, we designate the largest component as the
current main component and connect every remaining component to it with
one additional undirected edge. For each disconnected component, one
endpoint is sampled from that component and the other from the
accumulated main component. The procedure adds exactly $`C-1`$ edges,
which is the minimum number needed to make the graph connected. The
resulting change in average degree is therefore only

|     |                                 |     |      |
|-----|---------------------------------|-----|------|
|     |
       ``` math
       \Delta\bar{d}=\frac{2(C-1)}{N}.
       ```                              |     | (24) |

In practice, this repair is primarily relevant to the larger random
graphs. The semantic and scale-free constructions are connected by
construction.

##### Poisson resource allocation.

Random networks also use a topology-independent resource distribution.
Let $`X_{i}`$ denote the number of tools initially assigned to agent
$`i`$. We first sample

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\tilde{X}_{i}\sim\mathrm{Poisson}(\lambda),\qquad\lambda=\frac{M}{N},
``` |  | (25) |

independently for all agents. This produces natural heterogeneity in
local resource capacity rather than forcing every agent to own exactly
the same number of tools.

Because independent Poisson draws do not necessarily sum exactly to
$`M`$, we apply an exact-total correction. Let

|     |                                       |     |      |
|-----|---------------------------------------|-----|------|
|     |
       ``` math
       \Delta=M-\sum_{i=1}^{N}\tilde{X}_{i}.
       ```                                    |     | (26) |

If $`\Delta>0`$, the missing $`\Delta`$ ownership slots are assigned to
uniformly sampled agents. If $`\Delta<0`$, $`|\Delta|`$ existing
ownership slots are sampled uniformly and removed. This yields final
counts $`X_{i}`$ satisfying

|     |                        |     |      |
|-----|------------------------|-----|------|
|     |
       ``` math
       \sum_{i=1}^{N}X_{i}=M.
       ```                     |     | (27) |

Finally, the $`M`$ tool identifiers are randomly permuted and
partitioned according to these counts. Consequently, random placement
has no dependence on either tool category or graph degree. The
distribution should therefore be interpreted as a Poisson-like
heterogeneous allocation with an exact-total correction, rather than an
unconstrained collection of independent Poisson random variables.

For the tool benchmark, the expected number of tools per agent is
therefore $`37.2`$, $`7.44`$, $`3.72`$, $`0.744`$, and $`0.372`$ for
$`N=10`$, $`50`$, $`100`$, $`500`$, and $`1000`$, respectively. At the
largest scales, many agents intentionally own no local tool. Such nodes
remain useful as communication intermediaries and make resource
discovery distinct from simply querying every node for its local
capability.

#### A.9.2 Scale-Free Networks

##### Communication topology.

The scale-free topology follows preferential attachment. We use

|  |  |  |  |
|----|----|----|----|
|  |
``` math
m=\max\left(1,\min\left(\left\lfloor\frac{\bar{d}}{2}\right\rfloor,N-1\right)\right)
``` |  | (28) |

attachment edges per newly introduced node. With the default
$`\bar{d}=6`$, this gives $`m=3`$ for all benchmark network sizes.

Construction begins with a clique of $`m+1`$ agents. Each subsequent
agent connects to $`m`$ distinct existing agents. The probability of
choosing existing agent $`j`$ is proportional to its current degree,

|     |                                                         |     |      |
|-----|---------------------------------------------------------|-----|------|
|     |
       ``` math
       P(j\mid G_{t})=\frac{d_{j}(t)}{\sum_{\ell}d_{\ell}(t)},
       ```                                                      |     | (29) |

up to a negligible numerical smoothing constant used to avoid zero
probability during implementation. Preferential attachment creates a
heterogeneous degree distribution containing a small number of
high-degree hubs and many lower-degree peripheral agents. The expected
average degree approaches $`2m\approx 6`$ as $`N`$ grows.

##### Degree-biased resource ownership.

Scale-free networks intentionally couple structural centrality with
resource availability. After the graph is generated, tool $`k`$ is
assigned independently to agent $`i`$ with probability

|     |                                                                |     |      |
|-----|----------------------------------------------------------------|-----|------|
|     |
       ``` math
       P(o(k)=i)=\frac{d_{i}^{\alpha}}{\sum_{j=1}^{N}d_{j}^{\alpha}},
       ```                                                             |     | (30) |

where $`d_{i}`$ is the realized degree of agent $`i`$ and $`\alpha`$
controls the strength of the ownership bias. We use $`\alpha=1`$ in the
benchmark.

Thus, high-degree agents are not only easier to reach but also more
likely to own resources. This models ecosystems in which highly
connected or prominent agents accumulate more capabilities, services, or
expertise. Unlike the random construction, the number of resources owned
by an agent is therefore positively correlated with its network
centrality.

The construction creates two competing effects for decentralized
routing. Hubs provide short paths and concentrate useful resources,
which can make successful routes efficient. At the same time,
identifying the appropriate hub from only local information is
non-trivial, and poor routing decisions around high-degree nodes can
induce substantial fan-out.

#### A.9.3 Semantic Networks

##### Agent semantic categories.

Semantic networks introduce local alignment between graph structure and
capability semantics. Each agent is first assigned one of the eight tool
categories. Agent categories are sampled independently and uniformly
from the categories represented in the active tool collection. Let
$`c_{i}`$ denote the category assigned to agent $`i`$.

##### Communication topology.

We first connect all agents in a ring. This guarantees connectivity
while assigning every agent at least two structural neighbors before
additional semantic edges are added.

We then add undirected edges until the graph reaches

|  |  |  |  |
|----|----|----|----|
|  |
``` math
|E|=\min\left(\left\lfloor\frac{N\min(\bar{d},N-1)}{2}\right\rfloor,\frac{N(N-1)}{2}\right).
``` |  | (31) |

For every candidate edge, an endpoint $`i`$ is sampled uniformly. With
probability $`\rho`$, the second endpoint is sampled from another agent
sharing the same category as $`i`$. Otherwise it is sampled from the
complete agent set. Self-loops and duplicate edges are rejected. We use

|     |           |     |      |
|-----|-----------|-----|------|
|     |
       ``` math
       \rho=0.8.
       ```        |     | (32) |

Consequently, most new edges are biased toward semantically similar
agents, while a smaller fraction of cross-category edges maintains
bridges between semantic regions of the network. Because the graph
begins with a ring and then adds edges until the target edge count is
reached, its realized average degree is exactly $`6`$ for the benchmark
sizes considered here, except for trivial finite-size restrictions.

##### Semantic resource allocation.

Tool placement uses the same semantic categories. For a tool $`k`$ with
category $`c_{k}`$, let

|     |                            |     |      |
|-----|----------------------------|-----|------|
|     |
       ``` math
       A(c_{k})=\{i:c_{i}=c_{k}\}
       ```                         |     | (33) |

denote agents assigned to that category. With probability $`q`$, the
tool is assigned uniformly to an agent in $`A(c_{k})`$. With probability
$`1-q`$, it is assigned uniformly to any agent in the network:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
o(k)\sim\begin{cases}\mathrm{Uniform}(A(c_{k})),&\text{with probability }q,\\
\mathrm{Uniform}(\{1,\ldots,N\}),&\text{with probability }1-q.\end{cases}
``` |  | (34) |

We set $`q=0.8`$. If no agent happens to receive the relevant semantic
category, placement falls back to uniform assignment.

This construction creates a noisy but useful correspondence between
network locality and capability semantics. An agent seeking a tool from
a particular category can benefit from routing toward semantically
related neighborhoods, but category information is not an oracle for
exact resource ownership. First, 20% of tools are placed without
semantic matching. Second, multiple agents can share a category. Third,
tasks frequently require several tools, potentially from different
categories. Semantic routing therefore provides a useful inductive bias
without collapsing the problem into deterministic category lookup.

#### A.9.4 Comparison of the Three Network Families

The three constructions independently stress different aspects of
decentralized collaboration. Random networks provide a neutral condition
in which neither graph structure nor ownership conveys semantic routing
information. Scale-free networks introduce strong structural
heterogeneity and correlate resource ownership with degree. Semantic
networks instead introduce local homophily between capability categories
and both communication edges and resource ownership.

Importantly, these conditions modify only the environment. The agent
interaction protocol is identical across all three settings. An agent
observes its own local resources and immediate neighbors, but receives
neither a global adjacency matrix nor a global resource registry. A
distant resource can therefore be discovered only through a sequence of
neighbor-to-neighbor interactions.

##### Reachability versus routing difficulty.

Connectivity is enforced so that benchmark failure cannot be attributed
simply to the absence of a communication path. Every active tool has
exactly one owner, and every owner is reachable from every possible
entry agent. However, connectivity does not make discovery trivial.
Agents do not observe global shortest paths, remote resource locations,
or the full graph. As the number of agents increases, a required tool
may be several hops away, and many intermediate agents may own no
relevant resource. The benchmark therefore evaluates whether an agent
can discover and exploit the existing path using only local routing
decisions rather than whether such a path exists.

### A.10 Evaluation Metrics

We distinguish end-to-end task success from partial progress. This
avoids treating a pipeline with one correct intermediate tool output as
a successful task.

##### Notation.

For one task, let $`T`$ denote the set of required tools. Let $`d_{t}`$
be the shortest-path distance from the entry agent to the owner of tool
$`t`$. The set of required remote tools is

|     |                       |     |      |
|-----|-----------------------|-----|------|
|     |
       ``` math
       R=\{t\in T:d_{t}>0\}.
       ```                    |     | (35) |

Let $`\mathcal{V}=(v_{1},\ldots,v_{N})`$ be the node-visit trajectory
and let $`N=|\mathcal{V}|`$. Let $`K`$ be the set of scored
intermediate-output keys. Each $`k\in K`$ has gold value $`g_{k}`$ and
submitted value $`\hat{s}_{k}`$. The mapping $`\tau:K\rightarrow T`$
associates each output key with the tool that produced it. Let $`Q`$ be
the set of tools queried during the run and let $`\Gamma`$ be the set of
tools for which a result was returned.

##### End-to-end task success.

Let $`y^{\star}`$ be the gold final output and $`\hat{y}`$ the submitted
final output. Case-level success is binary:

|     |                                                  |     |      |
|-----|--------------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{Success}=\mathbbm{1}[\hat{y}=y^{\star}].
       ```                                               |     | (36) |

Dataset-level success is the mean of the case-level indicator and is
reported as a percentage.

##### Per-tool output accuracy.

For each scored tool output, define

|     |                                                        |     |      |
|-----|--------------------------------------------------------|-----|------|
|     |
       ``` math
       a_{t}=\mathbbm{1}[\hat{s}_{k}=g_{k}],\qquad t=\tau(k).
       ```                                                     |     | (37) |

The mean per-tool accuracy is

|     |                                                              |     |      |
|-----|--------------------------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{ToolAcc}=\frac{1}{|\tau(K)|}\sum_{t\in\tau(K)}a_{t}.
       ```                                                           |     | (38) |

If no intermediate outputs are available for scoring, this diagnostic is
undefined. Tool accuracy is reported as partial-credit information and
is not used as a substitute for end-to-end success.

##### Collaboration quality.

For tasks with at least one remote required tool, we measure whether the
run queried the right remote capabilities, obtained their results, and
used them correctly:

|     |                                           |     |      |
|-----|-------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{QueryRate}=\frac{|R\cap Q|}{|R|}.
       ```                                        |     | (39) |

|     |                                                  |     |      |
|-----|--------------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{ResponseRate}=\frac{|R\cap\Gamma|}{|R|}.
       ```                                               |     | (40) |

|     |                                                           |     |      |
|-----|-----------------------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{CorrectUseRate}=\frac{|\{t\in R:a_{t}=1\}|}{|R|}.
       ```                                                        |     | (41) |

The aggregate collaboration score is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{Collaboration}=(\mathrm{QueryRate}+\mathrm{ResponseRate}\\
+\mathrm{CorrectUseRate})/3.
``` |  | (42) |

For tasks with $`R=\varnothing`$, collaboration is not required. The
evaluator assigns these cases a collaboration score of $`100`$ by
convention. We therefore also report collaboration over remote tasks
only, which prevents local-only cases from inflating the interpretation
of decentralized collaborative ability.

##### Visit efficiency.

The current evaluator uses the distance-based reference

|     |                                       |     |      |
|-----|---------------------------------------|-----|------|
|     |
       ``` math
       V_{\mathrm{lb}}=1+\max_{t\in T}d_{t}.
       ```                                    |     | (43) |

This quantity is a lower bound on the number of sequential node
positions needed to reach the farthest required owner. It is not the
exact optimal number of node visits when required tools lie on different
graph branches. We therefore use it only as a normalization reference:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{VisitEff}=100\cdot\frac{V_{\mathrm{lb}}}{\max(V_{\mathrm{lb}},N,1)}.
``` |  | (44) |

This metric rewards compact trajectories while remaining simple to
compute. When comparing systems with substantially different branching
patterns, raw visited-node counts should be reported alongside it.

##### Query focus.

Let $`F`$ be the set of visits that forward to at least one neighbor.
For each $`v\in F`$, let $`f_{v}`$ be the number of neighbors selected
at that visit. Define the mean forwarding fan-out as

|     |                                          |     |      |
|-----|------------------------------------------|-----|------|
|     |
       ``` math
       \bar{f}=\frac{1}{|F|}\sum_{v\in F}f_{v}.
       ```                                       |     | (45) |

When $`F=\varnothing`$, we set $`\bar{f}=1`$. Query focus is

|     |                                          |     |      |
|-----|------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{QueryFocus}=\frac{100}{\bar{f}}.
       ```                                       |     | (46) |

A score of $`100`$ corresponds to single-neighbor forwarding whenever
forwarding occurs. Lower scores indicate broader fan-out. Because narrow
routing can be efficient but incorrect, this metric is interpreted
jointly with success and collaboration quality.

##### Round efficiency.

Partition the required tools into pipeline stages
$`\{S_{1},\ldots,S_{m}\}`$. Under parallel breadth-first propagation
within each stage, we use the following idealized reference round count:

|     |                                                           |     |      |
|-----|-----------------------------------------------------------|-----|------|
|     |
       ``` math
       R_{\mathrm{bfs}}=1+\sum_{j=1}^{m}2\max_{t\in S_{j}}d_{t}.
       ```                                                        |     | (47) |

The factor of two accounts for request propagation to the farthest
required owner in a stage and return of the result. Let

|     |                                                            |     |      |
|-----|------------------------------------------------------------|-----|------|
|     |
       ``` math
       R_{\mathrm{used}}=\max_{v\in\mathcal{V}}\mathrm{round}(v).
       ```                                                         |     | (48) |

Then

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{RoundEff}=100\cdot\min\left(1,\frac{R_{\mathrm{bfs}}}{\max(1,R_{\mathrm{used}})}\right).
``` |  | (49) |

This is a reference-normalized score rather than an exact shortest
schedule for arbitrary asynchronous execution.

##### Aggregate efficiency.

The aggregate efficiency score is the mean of the defined submetrics:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{Efficiency}=\operatorname{mean}(\mathrm{VisitEff},\mathrm{QueryFocus},\\
\mathrm{RoundEff}).
``` |  | (50) |

We report both unconditional efficiency and efficiency conditioned on
successful completion. The conditional score is important because a
failed run may stop early and appear artificially cheap.

### A.11 Additional Diagnostics

The benchmark records additional unscored statistics to support failure
analysis. These include total token usage, wall-clock time, the number
of repeated node visits, and rejection behavior.

Let num_repeated_nodes denote the number of repeated node visits. We
report

|     |                                                              |     |      |
|-----|--------------------------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{RepeatRate}=\frac{\texttt{num\_repeated\_nodes}}{N}.
       ```                                                           |     | (51) |

A visit is *ask-owned* if the request targets a tool owned by the
receiving agent and *ask-unowned* otherwise. We then define

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{RefusalRate}=\frac{\#\{\mathrm{ask\text{-}owned}\land\texttt{Reject}\}}{\#\{\mathrm{ask\text{-}owned}\}}.
``` |  | (52) |

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{DeadEndRate}=\frac{\#\{\mathrm{ask\text{-}unowned}\land\texttt{Reject}\}}{\#\{\mathrm{ask\text{-}unowned}\}}.
``` |  | (53) |

A rate is left undefined when its denominator is zero.

Together, these diagnostics distinguish several sources of failure. An
agent may fail to identify the required capability, route toward the
correct owner, obtain a response, preserve intermediate results, or
synthesize the final pipeline output. Reporting these diagnostics
alongside success, collaboration, and efficiency helps separate routing
quality from favorable resource placement or premature termination.

## Appendix B Details of Evaluated Agents

We compare several agent designs that differ in the information
available to the policy and in how routing decisions are produced or
adapted over time. Unless otherwise specified, all agents use the same
base LLM, local observation space, structured action space, and
neighbor-to-neighbor communication protocol. In particular, changing the
agent design does not change tool ownership, network connectivity, or
the underlying task.

At a visit to agent $`A_{i}`$ at round $`t`$, the agent observes its
current local state $`o_{i,t}`$, including its locally owned tools,
immediate neighbors, received requests or replies, and task information
visible at that node. The policy then selects among the benchmark
actions Reject, Return, Forward, and, for the entry agent, Submit_Final.
Except for the explicitly privileged oracle baselines, agents do not
observe the global graph or the mapping from tools to owners.

### B.1 Reflex Agent

The Reflex agent is the simplest LLM-based decentralized baseline. It
makes each decision solely from the information currently visible at the
node:

|     |                                                              |     |      |
|-----|--------------------------------------------------------------|-----|------|
|     |
       ``` math
       u_{i,t}\sim\pi_{\mathrm{LLM}}\left(\cdot\mid o_{i,t}\right).
       ```                                                           |     | (54) |

The agent does not maintain an explicit memory of earlier decisions. In
particular, its prompt does not include a stored history of previously
contacted nodes, previous forwarding actions, or outcomes from earlier
requests. Any information available to the policy must therefore be
present in the current observation.

This baseline tests whether a pretrained LLM can infer useful
decentralized routing behavior directly from local context. For example,
if an agent does not own a requested tool, it must decide whether to
reject the request or forward it to one of its immediate neighbors
without access to a learned routing table or cross-task experience.

### B.2 Reflex + History

Reflex + History augments the Reflex agent with an explicit record of
its previous interactions. Its decision can therefore condition on a
local interaction history $`h_{i,t}`$:

|     |                                                              |     |      |
|-----|--------------------------------------------------------------|-----|------|
|     |
       ``` math
       u_{i,t}\sim\pi_{\mathrm{LLM}}\left(\cdot\mid h_{i,t}\right).
       ```                                                           |     | (55) |

For each previous visit, the history records the interaction round,
agents from which messages were received, requested tool identifiers,
selected actions, forwarding destinations, tools returned or executed,
and execution or parsing errors when applicable. The history is rendered
into the LLM prompt before the next decision.

The purpose of this baseline is to isolate the value of explicit
interaction memory. In particular, an agent can use its history to avoid
repeatedly forwarding the same request to the same neighbor, recognize
that a previous route did not return a useful result, or retain
information about earlier successful interactions.

Unlike the experience-conditioned methods below, Reflex + History does
not perform explicit retrieval or learn a routing value function. It
simply exposes the recorded interaction trace to the LLM and allows the
model to reason over that trace directly.

### B.3 Collaborative Prompting

Collaborative Prompting tests whether poor decentralized performance is
primarily caused by LLMs being insufficiently willing to seek help. It
uses the same observation, memory, and action space as the Reflex agent,
but strengthens the system prompt with explicit collaboration
instructions.

The prompt encourages an agent to help whenever possible, to return a
local result when it owns a useful tool, and to forward a request when a
neighbor may plausibly help. In particular, the policy is instructed to
strongly prefer collaboration over rejection and to avoid Reject unless
neither the current agent nor any plausible neighbor can contribute.

Importantly, Collaborative Prompting does not specify which neighbor
should be selected. The LLM must still infer the forwarding destination
from its local observation:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
u_{i,t}\sim\pi_{\mathrm{LLM}}\left(\cdot\mid o_{i,t},p_{\mathrm{collab}}\right),
``` |  | (56) |

where $`p_{\mathrm{collab}}`$ denotes the additional collaboration
instruction.

Thus, this baseline changes the agent’s behavioral incentive but
provides no additional information about resource locations or network
topology. It distinguishes failures caused by unwillingness to
collaborate from failures caused by an inability to identify a useful
route.

### B.4 Broadcast

Broadcast provides a high-recall decentralized search baseline. The LLM
is first queried using the standard local policy. The resulting action
is then post-processed so that, whenever the agent has neighbors, the
request is forwarded to all immediate neighbors.

More specifically, if forwarding is possible, Reject is removed from the
final action set and Forward is added. For every tool-specific request
being propagated, an equivalent request is created for each immediate
neighbor. If the LLM has already produced a valid forwarding request,
its requested tool, input, and request type are reused. Otherwise, the
forwarding request is reconstructed from the current incoming request.

Broadcast does not prevent useful local computation. An agent may
simultaneously execute an owned tool and return its result while
forwarding the request to its neighbors. The distinction from the other
agents is that neighbor selection is no longer selective:

|     |                          |     |      |
|-----|--------------------------|-----|------|
|     |
       ``` math
       F_{i,t}=\mathcal{N}_{i},
       ```                       |     | (57) |

whenever forwarding is applicable, where $`\mathcal{N}_{i}`$ is the
immediate-neighbor set of agent $`A_{i}`$.

Broadcast therefore approximates exhaustive graph search while retaining
the same local communication constraint. It provides a useful reference
for the maximum resource coverage obtainable through aggressive
decentralized exploration, while typically incurring substantially
greater communication cost, forwarding fan-out, and redundant node
visits.

### B.5 Oracle Route

Oracle Route provides privileged routing information to the entry agent
while leaving all other agents unchanged. For every tool required by the
task, the benchmark computes a shortest path from the entry agent to an
owner of that tool.

The entry agent receives an additional routing section containing, for
each required tool:

- •
  the tool identifier
- •
  its owner
- •
  a shortest path from the entry agent to that owner
- •
  the first neighbor on that path

If a required tool is already owned by the entry agent, the hint
explicitly identifies it as local.

Let $`o(t)`$ denote the owner of required tool $`t`$ and let

|     |                                     |     |      |
|-----|-------------------------------------|-----|------|
|     |
       ``` math
       P_{t}=(A_{0},A_{p_{1}},\ldots,o(t))
       ```                                  |     | (58) |

be a shortest path from entry agent $`A_{0}`$ to that owner. Oracle
Route reveals $`P_{t}`$ to $`A_{0}`$, including the first-hop
recommendation $`A_{p_{1}}`$.

Only the entry agent receives this privileged information. Intermediate
agents continue to make their own decisions from normal local
observations. Oracle Route therefore removes uncertainty about initial
resource location and route selection while preserving decentralized
behavior after the first forwarding step. It serves as a diagnostic
upper bound on how much performance can improve when the entry agent
knows where the required resources are located.

### B.6 Oracle Route All

Oracle Route All is a stronger privileged baseline. It constructs the
same oracle routing information as Oracle Route, but exposes this
information to every agent that participates in the task.

For each required tool, all visited agents can observe the owner and the
shortest path computed from the original entry agent to that owner.
Thus, an intermediate agent that lies on the supplied route can directly
identify the next node on the oracle path rather than rediscovering the
route from its ordinary local context.

The oracle information is not recomputed into a new globally optimal
route at every intermediate node. Instead, all agents receive the same
entry-originated shortest-path description. This matches the
implementation and preserves a single oracle reference route for each
required resource.

Oracle Route All therefore removes most of the resource-location and
multi-hop routing uncertainty while retaining the benchmark’s
edge-constrained communication mechanism. Messages must still traverse
actual graph edges, tools remain locally owned, and remote tools must
still be executed by their owners. The baseline is intended as a routing
oracle rather than a realistic decentralized agent.

### B.7 Experience-Conditioned Agent

The Experience-Conditioned agent augments the LLM with persistent,
agent-local experience accumulated from previous interactions. Unlike
Reflex + History, which exposes a raw interaction trace, this method
stores structured evidence about successful resource retrieval.

Each agent maintains its own experience memory. When a reply for tool
$`t`$ is observed from agent $`A_{j}`$, the receiving agent records
$`A_{j}`$ as a successful helper for $`t`$. Repeated observations
accumulate a success count. For returned tool results, the agent
additionally caches the exact association between tool identifier, tool
input, returned output, and observed helper. Returned transferable
content can be cached analogously.

For a future request, only experience relevant to the currently
requested tools is retrieved. The memory presented to the LLM contains,
when available:

- •
  previously successful helpers for the requested tool
- •
  the number of successful observations associated with each helper
- •
  whether a helper is currently an immediate neighbor
- •
  exact cached results for matching tool-input pairs
- •
  previously observed transferable tool content
- •
  request-level state indicating whether the current request was
  previously seen, forwarded, or rejected

The implementation retains at most the five highest-count helper entries
and up to five matching cached results per tool when rendering relevant
experience.

The resulting policy can be written as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
u_{i,t}\sim\pi_{\mathrm{LLM}}\left(\cdot\mid h_{i,t},\mathcal{H}_{i}^{+}\right),
``` |  | (59) |

where $`\mathcal{H}_{i}^{+}`$ contains only experience locally observed
by agent $`A_{i}`$. No global trajectory database or centralized
resource map is constructed.

This baseline evaluates whether decentralized routing improves simply by
remembering which agents previously helped with similar tools. It is
particularly useful for distinguishing semantic generalization from
explicit location memorization. A successful helper is evidence about a
useful direction in the network, but it need not be the final tool owner
and may no longer be directly reachable from the current local state.

### B.8 Numerical Q-Routing

We include an online numerical routing baseline inspired by
Q-Routing ([Boyan and Littman, 1993](#bib.bib3)). Each agent maintains
its own routing table indexed by tool and immediate neighbor. The table
estimates the value of forwarding a request for tool $`t`$ from agent
$`A_{i}`$ to neighbor $`A_{j}`$.

For each tool-neighbor pair, the implementation maintains two
quantities. The first, $`\mathrm{resp}_{i}(t,j)`$, measures whether
requests for tool $`t`$ have successfully produced replies through
neighbor $`A_{j}`$. The second estimates the distance from $`A_{i}`$ to
the tool through $`A_{j}`$. The corresponding hop-efficiency term is

|     |                                             |     |      |
|-----|---------------------------------------------|-----|------|
|     |
       ``` math
       \mathrm{eff}_{i}(t,j)=\frac{1}{D_{i}(t,j)}.
       ```                                          |     | (60) |

The routing value exposed to the LLM is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
Q_{i}(t,j)=\frac{1}{2}\left(\mathrm{resp}_{i}(t,j)+\mathrm{eff}_{i}(t,j)\right).
``` |  | (61) |

All unseen tool-neighbor pairs are initialized to zero.

##### Online update.

Learning occurs when an agent observes a reply for tool $`t`$ arriving
from an immediate neighbor $`A_{j}`$. Receiving a reply provides direct
evidence that forwarding through $`A_{j}`$ can reach a responder. The
response estimate is therefore updated toward one:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{resp}_{i}(t,j)\leftarrow(1-\alpha)\mathrm{resp}_{i}(t,j)+\alpha,
``` |  | (62) |

where the default learning rate is $`\alpha=0.2`$.

The distance estimate uses a local bootstrap. Let $`D_{j}^{\star}(t)`$
denote neighbor $`A_{j}`$’s best currently known distance to tool $`t`$.
If $`A_{j}`$ owns the tool, then

|     |                     |     |      |
|-----|---------------------|-----|------|
|     |
       ``` math
       D_{j}^{\star}(t)=0.
       ```                  |     | (63) |

Otherwise, $`D_{j}^{\star}(t)`$ is the smallest previously successful
distance estimate available at $`A_{j}`$, excluding a route immediately
back through $`A_{i}`$. Agent $`A_{i}`$ uses the target

|     |                                      |     |      |
|-----|--------------------------------------|-----|------|
|     |
       ``` math
       \hat{D}_{i}(t,j)=1+D_{j}^{\star}(t).
       ```                                   |     | (64) |

For an existing estimate,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
D_{i}(t,j)\leftarrow(1-\alpha)D_{i}(t,j)+\alpha\hat{D}_{i}(t,j).
``` |  | (65) |

On the first grounded observation, the target distance is assigned
directly.

If the neighbor does not own the requested tool and has no grounded
downstream distance estimate, the response component is still updated
because a reply was observed, but the distance component is left
unchanged. If no reply is ever observed through a neighbor, the
corresponding routing value remains at its initial value.

##### Decentralized routing state.

Every agent owns a separate Q-table. Before each decision, the entries
corresponding to the currently relevant tool are rendered into that
agent’s prompt as a ranking over its immediate neighbors. The LLM then
selects an action using the numerical routing estimates together with
its ordinary local observation.

The implementation uses a shared runtime registry to access the replying
neighbor’s distance estimate during the bootstrap update. This registry
is used only for the estimate of the immediate neighbor from which the
reply was observed. It does not expose the full network topology, remote
resource locations, or arbitrary non-neighbor routing tables to the
policy. Conceptually, it is equivalent to returning the neighbor’s
scalar routing estimate together with the local reply.

The routing table can be updated continuously or frozen after a
specified number of training tasks. Under the frozen condition,
subsequent evaluation tasks can read the learned routing values but
cannot modify them. This permits a clean separation between online
adaptation and evaluation of a fixed learned routing state.

### B.9 Comparison of Agent Information

The evaluated agents can be understood by the additional information
introduced beyond the current local observation. Reflex receives no
additional state. Reflex + History exposes previous interactions.
Collaborative Prompting changes only the behavioral instruction.
Broadcast removes selective neighbor choice by forcing full local
fan-out. Experience-Conditioned routing retrieves structured evidence
from previous successful interactions. Numerical Q-Routing maintains an
explicit learned neighbor-value table. Oracle Route and Oracle Route All
introduce privileged ground-truth routing information and are included
only as diagnostic upper bounds.

Crucially, except for the oracle baselines, none of these methods
receives the global mapping from tools to owners or a globally
searchable representation of the communication graph. Differences in
performance therefore reflect different mechanisms for using local
observations, communication history, and accumulated routing experience
rather than access to a centralized resource registry.

### B.10 Training Learned Collaboration Policies

We study whether decentralized collaboration can be improved through
policy post-training. We consider three complementary approaches:
supervised fine-tuning (SFT), on-policy self-distillation (OPSD), and
group relative policy optimization (GRPO). SFT learns from previously
collected successful collaboration trajectories. OPSD uses a stronger
teacher to supervise states generated by the current student policy.
GRPO directly optimizes the policy using rewards obtained from online
interaction with the decentralized environment.

All three methods train a single shared policy that is used by every
agent in the network. The model is therefore not specialized to a
particular node identity. At each node visit, the shared policy receives
only the local observation available to the acting agent and predicts
the structured decision consumed by the environment. This parameter
sharing allows a policy trained on small networks to be deployed to
previously unseen agents and substantially larger communication graphs.

#### B.10.1 Training and Evaluation Splits

We separate policy training from evaluation along task, network-size,
and topology dimensions. The training environments contain small graphs
with network sizes $`N\in\{10,50\}`$ and use Random and Scale-Free
topologies. Networks with $`N\in\{100,500,1000\}`$ are reserved for size
generalization, while Semantic networks are held out to evaluate
topology generalization.

Within the training environments, we additionally reserve $`10\%`$ of
task identifiers as an in-distribution test set. The holdout is
deterministic and based on a hash of the task identifier, ensuring that
the same task is consistently assigned to the same split across network
configurations and repeated experiments. Held-out task identifiers are
excluded from all SFT examples and from online OPSD and GRPO training.

This produces three evaluation regimes: in-distribution generalization
to unseen tasks, size extrapolation to larger graphs, and topology
transfer to a graph family not used during training. All trained
policies are evaluated by executing them live in the corresponding
held-out environments.

#### B.10.2 Shared Local Policy

A collaboration trajectory contains a sequence of visits to potentially
different agents. At each visit, the acting agent receives a system
instruction together with its current local observation. Depending on
the benchmark configuration, this observation contains the current
request, locally owned tools, immediate neighbors, available
intermediate results, and the interaction history visible to that agent.

The model emits a structured decision specifying the actions to execute,
such as returning a local result or forwarding the request to selected
neighbors. For offline SFT data, we train on the parsed decision
accepted by the environment rather than the teacher model’s unrestricted
natural-language response. Accepted decisions are canonicalized into a
consistent JSON representation. This removes stylistic variation among
data-generating models and focuses learning on the action that changes
the environment.

The same structured action representation is used during online OPSD and
GRPO. Consequently, differences among the three training methods arise
from how training states and learning signals are obtained, rather than
from differences in the underlying agent interface.

#### B.10.3 Training Reward

We use the benchmark evaluator to assign an outcome score to each
complete collaboration trajectory. The reward combines task correctness,
collaboration quality, and efficiency. Let $`S`$, $`C`$, and $`E`$
denote these components normalized to $`[0,1]`$.

For offline trajectory selection, we use

|     |                                        |     |      |
|-----|----------------------------------------|-----|------|
|     |
       ``` math
       r_{\mathrm{offline}}=\frac{S+C+3E}{5}.
       ```                                     |     | (66) |

The larger weight on efficiency discourages flooding. A policy that
forwards every request broadly can often obtain the required resource
and therefore achieve reasonable correctness and collaboration scores,
despite exhibiting poor decentralized routing. Weighting efficiency more
strongly favors trajectories that discover the required resources
selectively.

For online policy optimization, we use a success-gated variant,

|     |                                      |     |      |
|-----|--------------------------------------|-----|------|
|     |
       ``` math
       r_{\mathrm{online}}=S\frac{C+3E}{4}.
       ```                                   |     | (67) |

Gating by correctness prevents the policy from obtaining high reward
merely by terminating early or minimizing communication without solving
the task.

The training correctness signal uses exact per-tool output accuracy,
which provides dense partial credit when only a subset of the required
tools is successfully obtained. This dense signal is used for policy
training only. Headline evaluation continues to use the task success,
collaboration, and efficiency metrics described in
Section [3.4](#S3.SS4 "3.4 Evaluation ‣ 3 DecArena: A Benchmark for Decentralized Multi-Agent Collaboration ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

For a fully local task, no remote collaboration is required. To avoid
granting a constant collaboration reward in such cases, we replace the
collaboration component with the task correctness signal during
training.

#### B.10.4 Supervised Fine-Tuning

SFT provides the initial learned collaboration policy. We construct its
dataset from previously collected trajectories on the training
environments.

##### Trajectory filtering.

Each completed episode is assigned the offline reward defined above. We
retain episodes whose reward is at least $`0.5`$. We exclude
trajectories generated by the Broadcast policy because indiscriminate
forwarding is an undesirable behavior that we do not want to imitate. We
also exclude Oracle Route and Oracle Route All trajectories because
their prompts contain routing information that is unavailable under the
normal decentralized observation model.

Only episodes belonging to the training split are used. The held-out
in-distribution task subset is excluded.

##### Node-level examples.

For every accepted decision in a retained episode, we create one
supervised example. The input contains the system instruction and local
observation seen at that node. The completion is the canonicalized
structured decision executed by the environment.

Thus, an episode visiting several agents contributes several training
examples. All decisions from the same episode inherit its
trajectory-level reward for filtering purposes.

Invalid outputs and attempts that are rejected by the environment are
not used as positive demonstrations.

##### Objective.

Let $`o`$ denote the local observation and $`a=(a_{1},\ldots,a_{L})`$
the serialized structured decision. SFT minimizes the standard
autoregressive negative log-likelihood of the decision tokens:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{L}_{\mathrm{SFT}}=-\sum_{\ell=1}^{L}\log\pi_{\theta}(a_{\ell}\mid o,a_{<\ell}).
``` |  | (68) |

The loss is applied only to the assistant completion containing the
decision. Tokens belonging to the system instruction and local
observation are masked from the training objective.

##### Configuration.

We initialize SFT from Qwen3.5-4B-Instruct. Unless otherwise specified,
we train for two epochs with learning rate $`1\times 10^{-5}`$,
per-device batch size $`8`$, gradient accumulation over $`4`$ batches,
and maximum sequence length $`8192`$. Training uses bfloat16 precision
and gradient checkpointing. The training examples are shuffled before
tokenization.

The default SFT experiment performs full-model fine-tuning. The
implementation additionally supports LoRA with rank $`32`$, scaling
parameter $`64`$, dropout $`0.05`$, and adapters on the query, key,
value, and output projection modules.

#### B.10.5 On-Policy Self-Distillation

SFT learns only from states present in the fixed offline trajectory
corpus. Once deployed, however, the student may make different routing
decisions and reach local states that are rare or absent from this
dataset. OPSD addresses this distribution mismatch by collecting
supervision under the student’s current policy.

##### Initialization.

We initialize the student policy $`\pi_{\theta}`$ from the SFT
checkpoint. OPSD uses the same model as a self-teacher, augmented with
oracle routing information, to provide supervision. The teacher does not
control the trajectory.

In particular, when the student reaches agent $`A_{i}`$, the
self-teacher receives the same local observation $`o_{i,t}`$ together
with oracle routing information for the required resources, including
their owners and shortest routes. The student receives only the standard
local observation and does not have access to this privileged routing
information.

The oracle information provides a stronger supervision signal while
remaining hidden from the student at inference time.

##### On-policy state collection.

At OPSD iteration $`k`$, the current student policy $`\pi_{\theta_{k}}`$
is deployed in the training environments. The student, rather than the
teacher, chooses the actions that determine how the trajectory evolves:

|     |                                                 |     |      |
|-----|-------------------------------------------------|-----|------|
|     |
       ``` math
       a_{i,t}\sim\pi_{\theta_{k}}(\cdot\mid o_{i,t}).
       ```                                              |     | (69) |

The resulting observations therefore follow the state distribution
induced by the current student policy.

For every visited observation $`o_{i,t}`$, we separately query the
teacher using the same local context. The teacher produces a target
decision $`a^{T}_{i,t}`$. The resulting OPSD example is

|     |                        |     |      |
|-----|------------------------|-----|------|
|     |
       ``` math
       (o_{i,t},a^{T}_{i,t}).
       ```                     |     | (70) |

The teacher action is used as a training target but is not used to
advance the environment during data collection. Consequently, subsequent
states remain genuinely on-policy with respect to the student.

##### Distillation objective.

The student is optimized to match the teacher on these student-induced
states. With token-level teacher supervision, the OPSD objective is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{L}_{\mathrm{OPSD}}=-\mathbb{E}_{o\sim d_{\pi_{\theta}}}\left[\sum_{\ell=1}^{L}\log\pi_{\theta}\left(a^{T}_{\ell}\mid o,a^{T}_{<\ell}\right)\right],
``` |  | (71) |

where $`d_{\pi_{\theta}}`$ denotes the observation distribution induced
by the current student policy.

If teacher token probabilities are available, the same procedure can
instead use a token-level KL distillation loss between the teacher and
student distributions. In our structured-action setting, the essential
distinction from SFT is not the particular token-level divergence, but
that supervision is generated on observations sampled from the current
student policy.

##### Iterative training.

OPSD alternates between rollout and optimization. At each iteration, we:

1.  1.
    deploy the current student on the training networks
2.  2.
    collect the local observations encountered by the student
3.  3.
    query the frozen teacher on each collected observation
4.  4.
    canonicalize valid teacher decisions into the benchmark action
    format
5.  5.
    update the student using the newly collected teacher targets

The updated policy is then used to generate the next iteration of
trajectories. Thus, as the student’s routing behavior changes, the
distribution of states receiving teacher supervision changes with it.

##### Why on-policy distillation.

This distinction is particularly important in decentralized routing
because early routing mistakes change all subsequent observations. An
offline dataset may contain strong decisions along successful routes but
provide little supervision for recovery states produced by the student
itself. OPSD exposes the teacher to precisely those states, including
states reached after suboptimal forwarding choices, and teaches the
student how a stronger policy would act from the same locally observable
situation.

OPSD nevertheless remains a distillation method rather than reward
optimization. The target at each state is the teacher’s local decision.
Environment reward can be used to monitor or filter rollouts, but it is
not the direct optimization signal.

##### Configuration.

We initialize OPSD from the same SFT checkpoint used to initialize GRPO.
Student rollouts use only the training networks and training task
identifiers. The self-teacher is frozen throughout training and is
queried deterministically unless otherwise specified. The student is
updated after each collection round using only the teacher completion
tokens.

For a controlled comparison with GRPO, we use the same local observation
format, training environments, maximum context length, and structured
decision representation. OPSD never observes held-out Semantic networks,
larger test networks, or held-out task identifiers during training.

#### B.10.6 Group Relative Policy Optimization

GRPO directly optimizes collaboration outcomes through online
environment interaction. As with OPSD, we initialize the policy from the
SFT checkpoint. Unlike OPSD, no teacher action is provided. Instead, the
policy learns from relative rewards among multiple trajectories sampled
for the same task.

##### Grouped rollouts.

For each training task, the current policy generates a group of $`G`$
complete decentralized trajectories. We use $`G=8`$ by default. Sampling
uses temperature $`1.0`$.

Each rollout executes the normal benchmark environment. All intermediate
routing decisions are therefore made by the current policy using the
same local observations available at evaluation time.

For trajectory $`g`$, the environment produces reward $`r_{g}`$. We
normalize rewards within each rollout group to obtain a group-relative
advantage. Conceptually,

|     |                                                  |     |      |
|-----|--------------------------------------------------|-----|------|
|     |
       ``` math
       A_{g}=\frac{r_{g}-\mu_{r}}{\sigma_{r}+\epsilon},
       ```                                               |     | (72) |

where $`\mu_{r}`$ and $`\sigma_{r}`$ are the mean and standard deviation
of rewards among trajectories generated for the same task.

Every local decision belonging to trajectory $`g`$ receives the
corresponding trajectory-level advantage $`A_{g}`$. This provides credit
to decisions participating in relatively successful collaboration
trajectories and negative signal to decisions participating in poorer
trajectories.

##### Policy objective.

For each collected local decision, we compute the mean log probability
of the completion tokens under the current policy. The GRPO update
increases the likelihood of actions from positive-advantage trajectories
and decreases the likelihood of actions from negative-advantage
trajectories.

We additionally regularize the policy toward the SFT initialization:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{L}_{\mathrm{GRPO}}=-\mathbb{E}\left[A\log\pi_{\theta}(a\mid o)\right]+\beta\mathbb{E}\left[\log\pi_{\theta}(a\mid o)-\log\pi_{\mathrm{ref}}(a\mid o)\right].
``` |  | (73) |

The reference policy $`\pi_{\mathrm{ref}}`$ is the frozen SFT model.

##### Round-based optimization.

Because a benchmark episode contains multi-agent, multi-turn interaction
with an external environment, training uses an explicit
rollout-and-update loop rather than an in-process single-turn GRPO
trainer.

Each training round performs four stages:

1.  1.
    create a servable snapshot of the current policy
2.  2.
    execute grouped rollouts in the training environments
3.  3.
    compute environment rewards and group-relative advantages
4.  4.
    update the policy on the collected local decisions

The updated policy is then used for the next rollout round.

##### Parameter-efficient update.

GRPO applies LoRA to the SFT model. We use rank $`32`$, scaling
parameter $`64`$, and adapters on the query, key, value, and output
projections. The underlying SFT parameters remain frozen. This design
also permits the frozen model with the adapter disabled to serve as the
reference policy for KL regularization without maintaining a second full
model in memory.

##### Configuration.

The default configuration uses $`20`$ GRPO rounds, group size $`8`$,
sampling temperature $`1.0`$, learning rate $`1\times 10^{-6}`$, and KL
coefficient $`\beta=0.02`$. Updates use micro-batch size $`1`$ and a
maximum context length of $`4096`$. Longer contexts are left-truncated
so that the structured completion at the end of the sequence is always
retained.

We use AdamW for optimization and clip the norm of trainable gradients
to $`1.0`$. The online reward uses the success-gated formulation
described in
Section [C.6](#A3.SS6 "C.6 Training Objective for Learned Policies ‣ Appendix C Additional Experimental Details ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration")
to reduce efficiency reward hacking.

#### B.10.7 Comparison of Training Signals

The three methods differ primarily in where their training states and
supervision originate.

SFT uses a fixed offline state distribution generated by previously
collected high-quality trajectories and imitates their accepted actions.
OPSD generates states using the current student policy but obtains the
target action from a self-teacher with oracle routing information. GRPO
also generates states using the current policy, but replaces teacher
supervision with trajectory-level environment reward.

Thus, the progression from SFT to OPSD to GRPO separates three
increasingly interactive forms of policy improvement: offline imitation,
on-policy imitation, and on-policy reward optimization.

## Appendix C Additional Experimental Details

This appendix provides the detailed evaluation protocol, baseline
definitions, ablations, and training objective used in the decentralized
collaboration experiments.

### C.1 Entry-Agent Evaluation by Resource Distance

For each task, we evaluate every agent as the entry agent and group runs
by the distance to the required resources. For a task $`q`$ with
required tool set $`\mathcal{T}(q)`$, we define

|  |  |  |  |
|----|----|----|----|
|  |
``` math
d(q,A_{0})=\max_{t\in\mathcal{T}(q)}d_{\mathcal{G}}\left(A_{0},o(t)\right),
``` |  | (74) |

where $`o(t)`$ is the owner of tool $`t`$. The maximum distance captures
the farthest resource that must be reached to complete the task. We
report four primary buckets:

- •
  Local: $`d(q,A_{0})=0`$, so all required tools are owned by the entry
  agent.
- •
  1-hop: $`d(q,A_{0})=1`$.
- •
  2-hop: $`d(q,A_{0})=2`$.
- •
  3+-hop: $`d(q,A_{0})\geq 3`$.

The headline benchmark uses connected graphs, so every required tool is
reachable from every entry agent. If disconnected graphs are introduced
as a robustness condition, unreachable cases are reported separately and
excluded from headline task success because the task is not solvable
from that entry point.

Evaluating every entry agent makes a separate random-reachable bucket
unnecessary. If exhaustive evaluation becomes too expensive at larger
scales, the same analysis can be approximated by stratified sampling
within these distance buckets.

### C.2 Request Semantics and Within-Task Cache

##### Request semantics.

The headline tool benchmark uses result requests. A queried owner
executes its local tool and returns only the output. This matches the
benchmark action space in which Return exposes a tool result rather than
the private tool implementation.

We additionally support a content-transfer ablation. Under a content
request, an owner may return transferable resource content that the
requester can mount and execute locally. Under a result request,
execution remains delegated to the owner. The request specifies what the
caller prefers, while the queried agent may still reject or forward
according to its policy. This ablation separates open resource sharing
from service-style delegation.

##### Entry-agent cache.

A task may require several resources across multiple pipeline stages. We
therefore distinguish a within-task cache from the cross-task experience
memory used by GraphHarness. The within-task cache may store discovered
resource locations, previous responses, transferred resource bodies when
transfer is enabled, and intermediate execution results.

We compare three cache policies. Under agent, the entry agent decides
what to retain. Under lru, eviction follows a fixed least-recently-used
policy. Under off, no reusable cache is maintained. This ablation
measures whether explicit within-task memory reduces repeated queries
and redundant execution.

### C.3 Routing and Coordination Ablation

We compare two coordination regimes while preserving neighbor-only
communication.

##### Entry-controlled routing.

The entry agent remains the decision maker for the route. Intermediate
agents expose only the local information needed for the entry agent to
choose the next hop and then relay the request along that selected edge.
Intermediate agents do not independently choose where to forward. This
condition tests routing under a single task-level controller without
granting global network access.

##### Recursive routing.

Each receiving agent independently decides whether to answer, reject, or
forward the request to one or more of its own neighbors. The entry agent
may therefore receive a result without observing every intermediate
routing decision.

The first condition isolates the routing ability of the entry agent. The
second evaluates genuinely distributed coordination among multiple local
decision makers. Recursive routing is the default condition in the main
benchmark.

### C.4 Memory and Network Dynamics

Persistent routing information is useful only when it remains
sufficiently aligned with the network. We therefore vary both cross-task
memory and network dynamics.

##### Cross-task memory.

Under none, each task begins with an empty cross-task routing state.
Under persistent, agents retain routing notes, resource-location
estimates, previous outcomes, and neighbor-performance statistics across
tasks. This memory is distinct from the within-task cache in
Section [C.2](#A3.SS2 "C.2 Request Semantics and Within-Task Cache ‣ Appendix C Additional Experimental Details ‣ DecArena: Evaluating Large-Scale Decentralized Multi-Agent Collaboration").

Persistent-memory evaluation is an online adaptation setting. All
methods that retain cross-task state should observe the same task order.
To reduce sensitivity to a particular order, results should be averaged
over multiple task-order permutations.

##### Static graph.

Resource ownership and communication edges remain fixed throughout
evaluation. Persistent memory can therefore accumulate stable routing
information.

##### Dynamic graph between tasks.

Between consecutive tasks, a controlled fraction of communication edges
is perturbed and a controlled fraction of resources migrates to new
owners. This setting tests whether agents learn transferable routing
patterns or only memorize fixed locations.

##### Dynamic graph within tasks.

As a stronger stress test, edges or resource owners may change between
communication rounds while a task is being solved. Each update preserves
graph connectivity and exactly one owner for every active tool. Changes
occur only at round boundaries so that the environment remains well
defined. This condition tests whether agents can detect stale routing
information and recover online.

### C.5 GraphHarness Warmup and Online Adaptation

GraphHarness separates pre-evaluation topology acquisition from online
routing adaptation.

##### Warmup data.

Warmup uses auxiliary tasks that are disjoint from the test tasks.
Agents may exchange compact information about advertised capabilities,
local routing outcomes, and local network structure. Private tool
implementations and secret execution keys remain hidden.

Each agent starts from a local state $`W_{i}^{(0)}`$. One warmup layer
performs

|  |  |  |  |
|----|----|----|----|
|  |
``` math
W_{i}^{(\ell+1)}=\Phi\left(W_{i}^{(\ell)},\operatorname{AGG}\left\{\Psi\left(W_{i}^{(\ell)},W_{j}^{(\ell)}\right):A_{j}\in\mathcal{N}_{i}\right\}\right).
``` |  | (75) |

After $`L`$ rounds, $`W_{i}=W_{i}^{(L)}`$ is fixed for evaluation. The
update is GNN-style in the sense that information propagates through
repeated local aggregation. It does not require a globally materialized
graph representation at any agent.

##### Online routing memory.

During evaluation, agent $`A_{i}`$ maintains local experience memory
$`M_{i,t}`$. For a request involving resource $`k`$ and candidate
neighbor $`A_{j}`$, the LLM computes

|  |  |  |  |
|----|----|----|----|
|  |
``` math
s_{i}(k,A_{j},t)=f_{\mathrm{LLM}}\left(k,A_{j},W_{i},M_{i,t},h_{i,t}\right).
``` |  | (76) |

We use the notation $`s_{i}`$ rather than a Q-value because this score
is generated from contextual routing evidence and is not constrained by
a Bellman update. After observing the local routing outcome, the agent
updates its memory

|  |  |  |  |
|----|----|----|----|
|  |
``` math
M_{i,t+1}=\operatorname{Update}_{\mathrm{LLM}}\left(M_{i,t},k,A_{j},r_{i},o_{i,t+1}\right).
``` |  | (77) |

This distinction separates GraphHarness from the numerical Q-Routing
baseline. Numerical Q-Routing adapts a tabular scalar for each observed
resource-neighbor pair. GraphHarness uses the LLM to generalize from
local routing context and stored experience across semantically related
requests.

### C.6 Training Objective for Learned Policies

For policies trained with reinforcement learning, we use a scalar reward
that combines partial task correctness with interaction cost. Let $`N`$
be the total number of node visits, $`U`$ the number of unique visited
nodes, $`C`$ the number of constraint violations, and $`P`$ the number
of repeated node visits. Let $`\mathrm{ToolAcc}`$ denote mean per-tool
output accuracy. The training reward is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
R=\mathrm{ToolAcc}-\lambda_{N}N-\lambda_{U}U-\lambda_{C}C-\lambda_{P}P.
``` |  | (78) |

The default coefficients are

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\lambda_{N}=0.01,\qquad\lambda_{U}=0,\qquad\lambda_{C}=0.5,\qquad\lambda_{P}=0.05.
``` |  | (79) |

The dense correctness term is used only as a training signal. Headline
evaluation continues to use binary end-to-end task success. The
coefficients are configurable, and individual cost metrics are reported
separately rather than being replaced by this scalar reward.
