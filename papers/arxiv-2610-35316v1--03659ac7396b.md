###### Abstract.

Users often request charts without knowing which database or table holds
the relevant data. Such requests may be ambiguous, and users may ask
follow-up questions to deepen their analysis or iteratively refine
existing charts. A useful assistant must therefore discover relevant
data sources among heterogeneous databases, ask clarifying questions
when needed, and track evolving user intent while preserving constraints
established in earlier turns. Yet recent text-to-visualization agents
typically rely on static agent harnesses that are predefined and remain
unchanged despite recurring failures across tasks. To address this
limitation, we introduce RSIV-Harness, which keeps the language model
weights fixed and applies Recursive Self-Improvement to revise the
surrounding harness from the agent’s own failure traces. To balance
flexible self-improvement with stability, we introduce a four-layer
framework that evaluates proposed harness revisions through anchor and
memory checks, refining those that pass and restoring the best validated
harness otherwise. We further introduce ODAC-Vis, a benchmark with 640
tasks for Open-Domain, Ambiguous, and Conversational
text-to-visualization that jointly evaluates open-domain data discovery,
ambiguity resolution, multi-turn visualization refinement, and
executable chart generation. Experiments show that a single round of
RSIV-Harness improves all six evaluation metrics relative to the seed
harness, with particularly large gains in executability (+28.02 points)
and chart structure (+34.01 points), demonstrating the ability to learn
from task-solving experience and turn recurring failures across tasks
into substantial performance improvements.

While extensive research on natural language interfaces for automated
visualization within the database and data mining community ([Luo et
al., 2021](#bib.bib10); [Chen et al., 2025](#bib.bib11); [Yu et al.,
2019b](#bib.bib16); [Yu et al., 2019a](#bib.bib17); [Deng et al.,
2026](#bib.bib15); [Ouyang et al., 2025](#bib.bib12); [Lu et al.,
2026c](#bib.bib13); [Xu et al., 2025](#bib.bib18)), recent agent systems
increasingly wrap large language models in an *agent harness* ([Lin et
al., 2026](#bib.bib5); [Lee et al., 2026](#bib.bib22); [Liu et al.,
2026](#bib.bib23)): a surrounding layer of system rules, tool
interfaces, and control policies that govern schema access, SQL
generation, and chart rendering. Industrial and academic agents ([Talaei
et al., 2024](#bib.bib9); [Lu et al., 2026b](#bib.bib24)) show that such
harnesses can coordinate retrieval, query planning, execution feedback,
and visualization. Yet most harnesses are authored once and kept fixed
after deployment, while public benchmarks still largely assume a known
target database and a well specified single-turn request ([Luo et al.,
2021](#bib.bib10); [Chen et al., 2025](#bib.bib11); [Yu et al.,
2019b](#bib.bib16)). These gaps limit deployment in enterprise data
lakes and rigorous measurement of open-domain conversational
text-to-visualization.

Benchmark and task coverage. In enterprise data lakes, analysts often
begin without a known target database, must resolve ambiguous requests
through dialogue, and iterate on SQL and charts over multiple turns
before trusting the output
(Figure [1](#acmlabel1 "Figure 1 ‣ 1. Introduction ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")).
Existing benchmarks address these needs only in isolation: open-domain
and cross-database text-to-SQL ([Deng et al., 2026](#bib.bib15); [Xu et
al., 2025](#bib.bib18)), controlled ambiguity in conversational
querying ([Sarwar et al., 2026](#bib.bib21); [Luo et al.,
2025](#bib.bib19)), and multi-turn text-to-visualization ([Luo et al.,
2021](#bib.bib10); [Chen et al., 2025](#bib.bib11); [Song et al.,
2024](#bib.bib14); [Rahman et al., 2025](#bib.bib20)). To our knowledge,
no public benchmark integrates them for end-to-end evaluation with
executable query and chart supervision throughout the dialogue.

Deployment and adaptation. State-of-the-art visualization agents improve
reliability through fixed multi-stage workflows or within-task execution
feedback ([Ouyang et al., 2025](#bib.bib12); [Lu et al.,
2026c](#bib.bib13)). Three adaptation problems therefore remain. First,
recurring failure modes such as premature code generation, schema search
misuse, and cross-database boundary violations persist across tasks
because the harness is not revised from accumulated traces. Second,
improving reliability often requires retraining or replacing the base
model rather than evolving the surrounding harness under fixed weights.
Third, learning from failed tasks may introduce regressions, causing the
harness to fail on tasks it previously solved correctly.

Our solution. We introduce ODAC-Vis and RSIV-Harness as a co-designed
benchmark and method response. RSIV-Harness keeps the language model
weights fixed. It revises only the surrounding harness: the system
surrounding the model, including its prompt, tool, memory, skill, and
middleware. At each turn, an inner loop either clarifies the request or
generates a visualization program, and retries with observed errors
within a bounded budget. An outer loop evaluates failure traces on a
stratified training sample and proposes a revision of the harness.
Rather than following predefined edit rules, the outer loop autonomously
determines which harness components to revise and how, guided by
observed failure patterns. To prevent such open-ended evolution from
degrading previously acquired capabilities, we introduce a four-layer
stability framework that accepts revisions only when they satisfy both
validation-anchor and regression-memory checks, reverting to the best
validated harness otherwise. We establish formal guarantees that
accepted revisions refresh protected records, rejected revisions
preserve those records and restore the champion, the best validation
score remains nondecreasing, and regression on sampled protected records
stays bounded. To evaluate this experience-driven evolution under
realistic open-domain conversational visualization challenges, we
further introduce ODAC-Vis, a benchmark for Open Domain, Ambiguous, and
Conversational text-to-visualization. ODAC-Vis jointly evaluates source
discovery across a fully exposed database collection, ambiguity
resolution, and multi-turn visualization refinement, with
domain-held-out evaluation and executable query-and-chart supervision at
each code-generating turn. Together, ODAC-Vis provides a unified testbed
for these interconnected challenges, while RSIV-Harness enables agents
to learn from recurring task failures and improve their behavior across
tasks.

Contributions. Our work makes four main contributions:

- •
  ODAC-Vis Benchmark. We present the first benchmark in which agents
  must generate visualizations without being given the target database
  or table, clarify ambiguous requests, and support follow-up
  refinement.
- •
  RSIV-Harness Method. We propose a recursive self improvement framework
  that enables agents to evolve from their own task-solving experience.
  An inner ReAct loop handles conversational visualization tasks, while
  an outer loop evaluates execution traces, identifies recurring
  failures across tasks, and autonomously proposes targeted revisions to
  the surrounding harness.
- •
  Stability Rules & Formal Guarantees. We develop a four-layer stability
  rule framework to ensure stable evolution without restricting how
  harness revisions are proposed. We formally guarantee protected-memory
  updates upon acceptance, champion restoration without memory
  modification upon rejection, nondecreasing champion validation scores,
  and bounded regression on sampled protected records.
- •
  Empirical Study. Extensive experiments on held-out domains show that a
  single round of recursive self-improvement improves all six evaluation
  metrics over the seed harness. Cross-backbone transfer and ablation
  studies further examine the generality of these improvements and the
  contributions of individual components. These findings demonstrate
  that agents can turn accumulated task failures into substantial
  improvements on previously unseen tasks.

## 2. Related Work

This work is closely related to conversational text-to-visualization and
to recursive self-improvement of agent harnesses. In this section, we
review the prior literature in these two main directions.

### 2.1. Text-to-Visualization and Conversational Data Access

Natural language (NL) interfaces for visualization (Vis) have progressed
from direct code generation ([Maddigan and Susnjak, 2023](#bib.bib31))
to curated benchmarks and agentic pipelines. Early text-to-vis datasets
such as nvBench and VisEval ([Luo et al., 2021](#bib.bib10); [Chen et
al., 2025](#bib.bib11)) provide large-scale NL-Vis pairs, enabling
automatic validity and readability checks but not source discovery over
a full database collection. Subsequent work extends coverage along three
largely separate axes. Ambiguity-aware benchmarks such as nvBench 2.0
and CLARITY ([Luo et al., 2025](#bib.bib19); [Sarwar et al.,
2026](#bib.bib21)) inject lexical, schema, or value ambiguity into
querying, yet still assume a specified schema and stop at SQL execution.
Complementary models improve robustness to lexical and phrasal
variability ([Lu et al., 2025](#bib.bib42)) and to ambiguity in
interactive text-to-visualization ([Lu et al., 2026d](#bib.bib41); [Xu
et al., 2026b](#bib.bib39)). Multi-turn visualization datasets including
Dial-NVBench, Text2Vis, and PMVisBench ([Song et al., 2024](#bib.bib14);
[Rahman et al., 2025](#bib.bib20); [Xu et al., 2026c](#bib.bib30))
support conversational refinement or progressive intent elaboration, but
provide fixed table or schema context rather than open-domain routing
across heterogeneous sources. CoVis studies neural and LLM-driven
multi-turn interactions for conversational text-to-visualization ([Song
et al., 2026](#bib.bib44)), and FeVisQA studies free-form question
answering over data visualizations ([Song et al., 2025](#bib.bib43)). On
the querying side, cross-domain semantic parsing benchmarks such as
Spider, BIRD, SParC, and CoSQL ([Yu et al., 2018](#bib.bib26); [Li et
al., 2023](#bib.bib27); [Yu et al., 2019b](#bib.bib16); [Yu et al.,
2019a](#bib.bib17)) establish standard splits for schema generalization
and multi-turn SQL dialogue, while TACO ([Deng et al.,
2026](#bib.bib15)) moves toward unspecified databases and cross-database
SQL composition. Text-to-NoSQL translation extends natural-language
querying to non-relational stores ([Lu et al., 2026a](#bib.bib40)). None
of these resources jointly evaluate open-domain source discovery, typed
ambiguity resolution, executable query and chart supervision, and
multi-turn conversational interactions, which motivates our ODAC-Vis
benchmark.

Visualization agents improve reliability through staged workflows and
within-task validation rather than cross-task adaptation. nvAgent
decomposes processing, composition, and validation in a fixed
collaborative workflow ([Ouyang et al., 2025](#bib.bib12)), and
MultiVis-Agent adds logic rules for bounded tool use and cross-modal
refinement ([Lu et al., 2026c](#bib.bib13); [Lu et al.,
2026b](#bib.bib24)). Open-domain SQL systems such as Abacus-SQL combine
retrieval with multi-turn query generation ([Xu et al.,
2025](#bib.bib18)), and recent agentic NL2SQL frameworks employ
multi-agent decomposition, rewriting, and execution-grounded
repair ([Talaei et al., 2024](#bib.bib9); [Wang et al.,
2025](#bib.bib25); [Pourreza and Rafiei, 2023](#bib.bib28); [Cen et al.,
2025](#bib.bib29); [Bogdanov et al., 2026](#bib.bib6); [Luo et al.,
2026](#bib.bib7); [Chen et al., 2026](#bib.bib8)). These systems
nonetheless ship with prompts, tools, and control policies fixed before
deployment and do not revise the surrounding harness from recurring
failures observed across tasks.

### 2.2. Agent Harnesses and Recursive Self-Improvement

LLM agents are increasingly mediated by a surrounding _harness_: system
rules, tool interfaces, middleware, and control policies that govern how
a frozen model interacts with an environment ([Lin et al.,
2026](#bib.bib5); [Lee et al., 2026](#bib.bib22); [Liu et al.,
2026](#bib.bib23)). Industrial and academic text-to-SQL agents
instantiate such harnesses through schema retrieval, query planning,
execution feedback, and validator loops ([Talaei et al.,
2024](#bib.bib9); [Wang et al., 2025](#bib.bib25); [Ouyang et al.,
2025](#bib.bib12); [Lu et al., 2026c](#bib.bib13)), yet most are hand
engineered once and left unchanged after release.

Recursive self-improvement has recently been studied along three
complementary lines. Weight-centric RSI agents such as AREX ([Lu et al.,
2026e](#bib.bib1)) alternate an inner task loop with an outer
audit-and-refine loop, but sustain gains through agentic mid-training
and reinforcement learning over model parameters rather than
deployment-time harness edits. Harness-evolution methods keep the base
model frozen and instead revise prompts, tools, and control programs
from execution traces ([Zhang et al., 2026](#bib.bib2); [Nie et al.,
2026](#bib.bib3); [Guo et al., 2026](#bib.bib4); [Lin et al.,
2026](#bib.bib5); [Zheng et al., 2026](#bib.bib35)), including test-time
program search, weakness-driven proposal with regression testing, and
observability-driven component editing; yet they neither support
clarification over open database collections nor regression-validated
harness commits for coupled query-and-chart execution in multi-turn
dialogue. Inference-time self-correction methods such as Reflexion,
Self-Refine, and DSPy ([Shinn et al., 2023](#bib.bib32); [Madaan et al.,
2023](#bib.bib33); [Khattab et al., 2023](#bib.bib34)) improve
individual trajectories through verbal feedback, iterative drafting, or
compiled prompt pipelines, but do not commit persistent harness
revisions validated across a task distribution. RSIV-Harness addresses
these gaps by learning from recurring failures across tasks to
autonomously evolve the agent harness, while using regression-aware
checks to preserve previously successful behaviors.

## 3. The ODAC-Vis Benchmark

### 3.1. Overview and Motivation

We introduce ODAC-Vis, a benchmark for Open Domain, Ambiguous, and
Conversational text-to-visualization. Each task simulates an analyst who
requests a chart in natural language without naming a target database,
may need to clarify underspecified intent, and may refine the analysis
or the chart over subsequent turns. The benchmark exposes all _206_
SQLite databases from the Spider test collection ([Yu et al.,
2018](#bib.bib26)) and requires a model to discover relevant sources,
compose SQL when multiple databases are needed, and emit executable
Python that queries data and renders a Plotly chart.

Open domain and cross-domain. Unlike prior text-to-vis datasets that
bind each instance to a known table or schema ([Luo et al.,
2021](#bib.bib10); [Chen et al., 2025](#bib.bib11); [Song et al.,
2024](#bib.bib14); [Rahman et al., 2025](#bib.bib20)), ODAC-Vis treats
the full database collection as visible at inference time while keeping
the gold target as one or more specific databases per task. Models must
route to the correct sources without being told which database to open,
and cross-database tasks require SQL-only composition through ATTACH,
temporary tables, joins, semi-joins, unions, or scalar subqueries rather
than post-hoc Python merges. Evaluation uses a _domain-held-out_ split:
domains seen during training never appear in validation or test, so
success requires generalization rather than memorizing a fixed schema
catalog. Complexity is stratified into single-table (30%),
single-database join (50%), and cross-database (20%) tiers within each
split.

Ambiguity. Each task contains one to three ambiguity points drawn from
eight template-defined types. _Data semantics:_

- •
  _Column selection_: “Show revenue” when both gross and net sales
  columns are valid measures.
- •
  _Aggregation granularity_: “Show the trend” when the request can be
  grouped by month or by quarter.
- •
  _Filter logic_: “Top performers” when ranking by revenue or by profit,
  or when conjunctive and disjunctive filters differ.
- •
  _Unit scale_: “Plot sales” when values may be shown in raw units,
  millions, or percentages.

_Visualization semantics:_

- •
  _Chart type_: “Visualize growth” when a line chart (trend) and a bar
  chart (comparison) are both reasonable.
- •
  _Encoding mapping_: “Highlight categories” when color or point size
  could encode the same dimension.
- •
  _Axis label_: “Show enrollment” when the y-axis may label counts or
  normalized rates.
- •
  _Interactivity_: “Make it filterable” when filtering by dropdown
  selection or brush interaction is intended.

Every ambiguity is backed by at least two schema-supported alternatives
that yield distinguishable query or chart outcomes, and each is resolved
through a clarification question followed by a user reply that uniquely
selects one alternative. Dialogues never expose database or table names
during clarification.

Conversational structure. Tasks follow one of two scenarios, which set
the analytical role of the dialogue. In _drilldown_, later requests
deepen the current analysis. In _iterate_, later requests revise the
current chart. Ambiguity is placed independently of that role. Each task
contains one to three ambiguity points on randomly chosen request turns
other than the final turn, so clarification may open the dialogue or
arise during a later drilldown or iteration. A turn that contains an
ambiguity requires the model to ask the user a clarification question on
that turn. On the next turn the user answers the question, and the model
writes the visualization code for user’s intent. A turn without
ambiguity requires the model to write the visualization code directly.
Conversations are capped at eight user–assistant exchanges. The two
scenarios appear in equal proportion within each split.

### 3.2. Dataset Construction Methodology

ODAC-Vis was constructed through a principled, LLM-assisted pipeline
with expert validation, prioritizing quality, coverage, and faithfulness
in open-domain, ambiguity-aware, multi-turn conversational
text-to-visualization scenarios. The detailed construction process of
ODAC-Vis is described below:

Step 1: Cross-domain split. Spider provides 206 independent SQLite
databases and 139 domains. Domains are assigned to splits as atomic
units: roughly 15 domains are held out exclusively for test, while the
remaining domains supply train and validation tasks in a 5:1 ratio.
Within every split we enforce independent quotas over the Cartesian
product of scenario and complexity tier, so evaluation is not skewed
toward a single dialogue pattern or query difficulty. All databases
referenced by a cross-database task belong to domains in the same split.
At inference time the agent may access the full database collection
$`\mathcal{D}=\{d_{1},\ldots,d_{206}\}`$, while task gold specifies a
target subset $`B^{\star}(t)\subseteq\mathcal{D}`$ without naming it in
user dialogue; held-out test domains never appear in train or
validation. The released benchmark contains $`N{=}640`$ tasks. Each
construction slot is indexed by $`u=(s,\sigma,\tau)\in\mathsf{S}`$,
where $`s\in\mathcal{S}`$ is the data split, $`\sigma\in\Sigma`$ the
conversational scenario, and $`\tau\in\mathcal{T}`$ the query-complexity
tier, with

|     |     |     |     |
| --- | --- | --- | --- |
| (1) |     |

````math
\mathsf{S}=\mathcal{S}\times\Sigma\times\mathcal{T},\qquad|\mathsf{S}|=|\mathcal{S}|\cdot|\Sigma|\cdot|\mathcal{T}|.
``` |  |

We target the following marginal proportions over these dimensions:
train:validation:test in $`14{:}3{:}3`$ (approximately 70:15:15,
yielding 448/96/96 tasks at $`N{=}640`$), equal weights on the two
scenarios in $`\Sigma`$, and complexity tiers in $`\mathcal{T}`$ in a
global 3:5:2 ratio (30/50/20% single-table, single-database join, and
cross-database). Slot counts are obtained by nested proportional
rounding:

|  |  |  |  |
|----|----|----|----|
| (2) |  |
``` math
Q[s,\sigma,\tau]=\mathrm{Alloc}\!\left(\mathrm{Alloc}\!\left(\mathrm{Alloc}(N,\;r_{\mathcal{S}})[s],\;r_{\Sigma}\right)[\sigma],\;r_{\mathcal{T}}\right)[\tau],
``` |  |

where $`Q[s,\sigma,\tau]`$ is the number of tasks allocated to slot
$`(s,\sigma,\tau)`$, $`r_{\mathcal{S}}`$, $`r_{\Sigma}`$, and
$`r_{\mathcal{T}}`$ are non-negative integer weight vectors over splits,
scenarios, and tiers, and $`\mathrm{Alloc}(n,r)`$ maps a total $`n`$ and
weights $`r`$ to integer counts that sum to $`n`$ by largest-remainder
rounding. Applying

top-down first fixes the split sizes, then balances scenarios within
each split, and finally assigns complexity tiers within each scenario

Step 2: Cross-database tasks. About 20% of tasks require evidence from
more than one Spider database, yet the collection provides no predefined
links between files. We model the collection as a composability graph
$`G=(\mathcal{D},\Pi)`$ whose nodes are databases and whose edges are
composition plans $`\pi=(\rho,B,\kappa)`$, where $`\rho`$ is a SQL
relation type, $`B\subseteq\mathcal{D}`$ the participating databases,
and $`\kappa`$ an executable program skeleton ([Deng et al.,
2026](#bib.bib15)). Candidate plans are generated from schema overlap
and then filtered in three stages. First, relation-specific generators
produce a candidate set

|  |  |  |  |
|----|----|----|----|
| (3) |  |
``` math
\Pi^{(0)}=\bigcup_{\rho\in\mathcal{R}}\Pi^{(0)}_{\rho},\qquad\mathcal{R}=\{\textsc{equi\_join},\textsc{semi\_join},\textsc{union},\textsc{subq}\}.
``` |  |

Equi-join candidates are retained only if they pass a staged quality
test on name similarity, value overlap, coverage, key uniqueness, and
join expansion:

|  |  |  |  |
|----|----|----|----|
| (4) |  |
``` math
\Pi_{\textsc{equi\_join}}=\bigcup_{\theta\in\Theta}\Bigl\{\pi\in\Pi^{(0)}_{\textsc{equi\_join}}\;\Big|\;\mathrm{Quality}(\pi,\theta)=1\Bigr\},
``` |  |

where $`\Theta=\{\text{strict},\text{relaxed}_{1},\text{relaxed}_{2}\}`$
denotes progressively relaxed thresholds. Next, every candidate must
survive an execution probe that materializes the skeleton on the
reserved databases:

|  |  |  |  |
|----|----|----|----|
| (5) |  |
``` math
\Pi=\Bigl\{\pi\in\Pi^{(0)}\;\Big|\;\mathrm{Probe}(\kappa,B)\neq\bot\Bigr\}.
``` |  |

Finally, only plans whose databases lie in the same split are eligible
for construction in that split:

|  |  |  |  |
|----|----|----|----|
| (6) |  |
``` math
\Pi_{s}=\Bigl\{\pi\in\Pi\;\Big|\;B(\pi)\subseteq\mathcal{D}_{s}\Bigr\},
``` |  |

|  |  |  |  |
|----|----|----|----|
| (7) |  |
``` math
|\Pi_{s}|\;\geq\;\alpha\sum_{\sigma\in\Sigma}Q[s,\sigma,\textsc{cross\_db}],
``` |  |

with $`\mathcal{D}_{s}`$ the databases reachable from domains in
split $`s`$ and $`\alpha{=}3`$ a safety margin used during split
planning. Cross-database gold is sampled as
$`\pi\sim\mathrm{Unif}(\Pi_{s})`$ and realized in SQL via ATTACH;
post-query pandas transforms are restricted to unary cleaning on the
final result set.

This keeps cross-database gold faithful to real schema overlap rather
than hand-written Python merges, and it aligns the benchmark with the
SQL-only composition protocol used in open-domain text-to-SQL
evaluation.

Step 3: Task generation. We build tasks with a chart-centric hybrid of
templates and LLMs. Templates sample query intents, ambiguity points,
and scenario-specific follow-ups from schema metadata, compile each
sample into structured query, cleaning, and chart specifications
together with executable SQL and Plotly code, and discard instances that
fail execution or ambiguity checks. An LLM (DeepSeek-V4.1-Flash ([Xu et
al., 2026a](#bib.bib38))) then paraphrases the verified slots into
natural dialogue. For *drilldown*, templates also sample a follow-up
analysis path after the initial chart; for *iterate*, the target chart
and iteration request are fixed first and clarification turns are
inserted afterward. Each task contains at most eight user–assistant
turns, and ambiguity points are injected at randomly chosen
request-bearing turns. Dialogue length and ambiguity count are coupled
so that one ambiguity uses three or four turns, two use five or six, and
three use seven or eight; adjacent ambiguity turns are separated by at
least one non-ambiguous round:

|  |  |  |  |
|----|----|----|----|
| (8) |  |
``` math
\mathcal{A}(T,k)=\Bigl\{\{a_{1},\ldots,a_{k}\}\subseteq\{1,\ldots,T-1\}\;\Big|\;a_{i+1}-a_{i}\geq 2\Bigr\}.
``` |  |

For each ambiguity turn, templates construct at least two
schema-supported alternatives whose raw-result, cleaned-result, and
chart fingerprints are pairwise distinct, so clarification changes the
downstream gold rather than surface wording alone. Global occurrence
targets over the eight ambiguity types are matched to task schedules by
a unit-capacity bipartite max-flow assignment that fixes one primary
type per task and forbids repeating a type within a dialogue. A final

### 3.4. Dataset Quality Analysis

Benchmark comparisons are only meaningful when the underlying
supervision is faithful to the stated task. We therefore conduct a
controlled quality audit of ODAC-Vis together with two widely used
text-to-visualization resources: Dial-NVBench ([Song et al.,
2024](#bib.bib14)), which models multi-turn visualization dialogue over
a fixed given table or schema, and NVBench 2.0 ([Luo et al.,
2025](#bib.bib19)), which injects ambiguity into the request and retains
multiple valid chart specifications per request.

Each instance receives three independent scores on a 0–100 scale:

- •
  *Relevance*: whether the gold answer targets the analysis implied by
  the request.
- •
  *Plausibility*: whether the answer satisfies stated constraints and
  forms a coherent query or chart specification.
- •
  *Readability*: presentation quality of the answer text and, when
  applicable, the reference chart.

The audit applies this rubric to the gold supervision in each corpus as
follows:

- •
  ODAC-Vis: multi-turn clarification and code turns, with reference
  charts produced from verified executable code.
- •
  Dial-NVBench: conversational question–answer trajectories toward the
  final visualization goal.
- •
  NVBench 2.0: natural-language requests against gold Vega-Lite
  specifications and rendered reference charts when multiple valid
  encodings are annotated.

We randomly sample 100 tasks from each benchmark with a fixed seed so
that both evaluators inspect the same instances. Two experts conduct a
blind review using the shared rubric described above, with dataset
identity and task provenance concealed. An LLM evaluator
(DeepSeek-V4.1-Flash) applies the same dimensions with structured
prompts and returns a score together with a short rationale for each
task. Both protocols score one instance at a time along a single
dimension, yielding three judgments per task.

summarizes the mean scores. ODAC-Vis attains the highest quality across

## 4. RSIV-Harness

ODAC-Vis requires an agent to find the relevant sources in an exposed
database collection. If the request is ambiguous, the agent must resolve
that ambiguity in dialogue before it returns an executable chart.
RSIV-Harness meets that task with a language model whose weights stay
fixed and a harness that is revised from the agent’s own traces.

![Refer to caption](2610.35316v1/method.png)

Figure 4. Architecture of RSIV-Harness. The inner task-solving loop
answers one assistant turn under the deployed harness, and the outer
self-improvement loop revises that harness from traces accumulated
across tasks.

This section proceeds from the architecture to the inner loop, then to
the outer self-improvement loop, and finally to the four-layer stability
rules and the theorems that follow from them.

### 4.1. Design Philosophy and Architecture Overview

Existing visualization systems still face a fundamental limit that
blocks practical deployment. A traditional pipeline fixes its procedure
before the first request, so a failure that keeps recurring can be
removed only by rewriting that procedure or by retraining the model.
Harness agents improve on this design: a frozen model can choose its
next action from the observation it has just received. The harness that
governs the choice is nevertheless fixed at deployment, so the agent
stays rigid and has little flexibility once the scenario grows more
complex than the behavior written for it. To address this limitation, we
propose RSIV-Harness, which keeps the harness as the acting layer of a
frozen model and adds self-improvement that revises the harness from
failures accumulated across tasks.

RSIV-Harness implements a hierarchical, bi-level recursive
self-improvement process, comprising an inner task-solving loop and an
outer self-improvement loop
(Fig. [4](#S4.F4 "Figure 4 ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")).
The inner loop answers one assistant turn by following the harness that
is currently deployed. The outer loop reads the traces of many such
turns and proposes a revision of that harness. A four-layer stability
rule framework then accepts or rejects the revision before it can
replace the deployed harness. The inner loop therefore supplies the
evidence, the outer loop turns that evidence into a candidate, and the
rules decide which harness the next inner loop will use.
Self-improvement starts from a minimal harness, leaves the outer loop
free to choose what to refine and how to refine it, and uses the refine,
restart, anchor check, and memory check rules as the hard constraints
that keep this freedom stable.

### 4.2. Inner Task Loop

The inner loop follows the ReAct pattern ([Yao et al.,
2023](#bib.bib36)) and incrementally constructs an answer by analyzing
the current request, invoking the registered tools, integrating the
returned observations, and determining the next step. The policy is
parameterized by the current harness $`H`$, while the model weights stay
fixed. Consider one assistant turn of a task $`x`$. After $`t`$ steps
the interaction trajectory is

|     |     |                                                  |     |
|-----|-----|--------------------------------------------------|-----|
| (9) |     |
             ``` math
             h_{t}=\bigl[(m_{i},a_{i},o_{i})\bigr]_{i=1}^{t},
             ```                                               |     |

where $`m_{i}`$ is a short decision summary, $`a_{i}`$ is the action,
and $`o_{i}`$ is the observation returned by the environment.

The harness defines a policy $`\pi_{H}`$ and an environment operator
$`\mathcal{T}_{H}`$. Writing $`\bar{h}_{t}`$ for the context shown to
the policy, the next step is

|  |  |  |  |
|----|----|----|----|
| (10) |  |
``` math
(m_{t+1},a_{t+1})=\pi_{H}(x,\bar{h}_{t}),\qquad o_{t+1}=\mathcal{T}_{H}(a_{t+1}),
``` |  |

and the trajectory grows by concatenation,

|      |     |                                               |     |
|------|-----|-----------------------------------------------|-----|
| (11) |     |
              ``` math
              h_{t+1}=h_{t}\oplus(m_{t+1},a_{t+1},o_{t+1}).
              ```                                            |     |

Each step emits one action from a closed set. The action requests one
registered tool, or it terminates the turn with a clarification. A tool
request names one member of the registered set $`\mathcal{T}(H)`$.

The inner loop stops when a legal clarification or a finished program
has been produced, or when $`m(H)`$ policy steps have been used.
Middleware, once a version introduces it, may replace the raw trajectory
by a shorter effective context. If the latest refresh occurred at step
$`\tau\leq t`$,

|  |  |  |  |
|----|----|----|----|
| (12) |  |
``` math
\bar{h}_{t}=z_{\tau}\oplus\bigl[(m_{i},a_{i},o_{i})\bigr]_{i=\tau+1}^{t},\qquad z_{\tau}=f_{H}(h_{\tau}),
``` |  |

and $`\bar{h}_{t}=h_{t}`$ when no refresh has occurred. The refreshed
state retains the observations that later steps still need, including
evidence that ruled a source out. This is the role of autonomous context
update, specialized here to schema evidence and dialogue state. Until
middleware exists, the policy conditions on the raw trajectory.

A clarification ends the turn when it satisfies the dialogue rule. A
chart program is checked and then executed in the sandbox. A failed
execution is kept as the evidence for the next repair. Let $`e_{<j}`$ be
the execution failures observed before the $`j`$-th generation inside
the same turn, and define

|      |     |                                          |     |
|------|-----|------------------------------------------|-----|
| (13) |     |
              ``` math
              p_{j}=\Pr(\mathrm{exec\_ok}\mid e_{<j}).
              ```                                       |     |

The harness allows at most $`K(H)`$ repairs after the first generation,
so the turn may execute the program at most $`K(H)+1`$ times. The
probability that some attempt is executable is

|      |     |                                                  |     |
|------|-----|--------------------------------------------------|-----|
| (14) |     |
              ``` math
              q\bigl(K(H)\bigr)=1-\prod_{j=0}^{K(H)}(1-p_{j}).
              ```                                               |     |

Each repair is conditioned on the concrete error of the previous attempt
and reuses the source evidence already stored in $`h_{t}`$. The repair
rewrites the program attempt and leaves $`H`$ as it was.
Section [4.3](#S4.SS3 "4.3. Outer Self-Improvement Loop ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")
defines the separate map that revises the harness.

### 4.3. Outer Self-Improvement Loop

The outer loop treats the harness as the state of a recursive operator.
Let $`S`$ be a training panel drawn once from the train split,
stratified on the factors reported in
Section [5.1.1](#S5.SS1.SSS1 "5.1.1. Dataset ‣ 5.1. Experimental Setup ‣ 5. Experiments ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"),
and then reused for every round. Let $`V(H)`$ be the task success rate
of $`\pi_{H}`$ on a fixed validation anchor. A task contributes to this
rate only when every assistant turn takes the reference stance and
completes, and every gold-code turn both executes and yields a result
table equivalent to the reference table under the execution-equivalence
comparator
of ([44](#S5.E44 "In 4th item ‣ 5.1.3. Evaluation Metrics ‣ 5.1. Experimental Setup ‣ 5. Experiments ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")).
Because the panel and the anchor stay fixed, a change in $`V`$ is
attributable to the harness.

One round begins from the trace of the current harness,

|      |     |                                       |     |
|------|-----|---------------------------------------|-----|
| (15) |     |
              ``` math
              \tau(H)=\mathrm{Evaluate}(\pi_{H},S).
              ```                                    |     |

Analysis reads $`\tau(H)`$ together with the verdict set $`\mathcal{R}`$
of the candidate rejected in the previous round. It groups traces that
break the same part of the task contract, and only then asks a proposal
model to interpret a bounded sample of each group. We write the
resulting assessment as

|  |  |  |  |
|----|----|----|----|
| (16) |  |
``` math
g(H)=G\bigl(\tau(H),\mathcal{R}\bigr)=\bigl(\mathcal{P},\mathcal{I}\bigr).
``` |  |

Here $`\mathcal{P}`$ is a bounded memory of protected train records
$`(x,t,d,b)`$, consisting of a task, turn, metric, and the baseline
score achieved by a committed harness; $`\mathcal{I}`$ is the set of
unresolved failure clusters. Records are admitted at score 1 for stance,
executability, routing, and execution accuracy, at a positive score for
clarification quality, and at score 0.75 or above for chart structure.
The proposal is

|      |     |                                                |     |
|------|-----|------------------------------------------------|-----|
| (17) |     |
              ``` math
              H^{\prime}=\mathrm{Improve}\bigl(g(H),H\bigr),
              ```                                             |     |

and it contains at most $`E`$ edits. Each edit names the component it
changes and the failure evidence it is meant to address. A legal
proposal is then tested by the stability rules of
Section [4.4](#S4.SS4 "4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization").

The candidate is then submitted to the commit rule of
Section [4.4](#S4.SS4 "4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization").
Let $`H^{\star}`$ be the committed harness with the best anchor score,
and let $`B`$ be that score. Write $`Q`$ for the stratified regression
sample defined below, and abbreviate the commit predicate by

|  |  |  |  |
|----|----|----|----|
| (18) |  |
``` math
\mathrm{Accept}(H^{\prime})=\mathbf{1}\bigl[\mathrm{MC}(H^{\prime})=1\land\mathrm{AC}(H^{\prime})=1\bigr],
``` |  |

where $`\mathrm{MC}`$ is the memory check and $`\mathrm{AC}`$ is the
anchor check defined in
Section [4.4](#S4.SS4 "4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization").
The recursive operator is

|  |  |  |  |
|----|----|----|----|
| (19) |  |
``` math
H_{n+1}=\Phi(H_{n})=\begin{cases}H^{\prime}_{n}&\text{if }\mathrm{Accept}(H^{\prime}_{n})=1,\\
H^{\star}_{n}&\text{otherwise.}\end{cases}
``` |  |

The seed is $`H_{0}`$. On acceptance, eligible protected records from
the new version are folded into the bounded memory after the deployed
harness has been evaluated again on $`S`$,

|  |  |  |  |
|----|----|----|----|
| (20) |  |
``` math
\mathcal{P}_{n+1}=\mathrm{Refresh}_{C}\bigl(\mathcal{P}_{n},\mathcal{A}(H_{n+1})\bigr).
``` |  |

Here $`\mathcal{A}(H)`$ is the set of eligible protected records
observed under $`H`$, and $`C`$ is the memory capacity. The next
analysis can then attend to the clusters that remain in $`\mathcal{I}`$.
On rejection, $`\Phi`$ restores $`H^{\star}_{n}`$. The candidate is
archived with its verdict, and that verdict becomes $`\mathcal{R}`$ for
the following round. A subsequent acceptance clears $`\mathcal{R}`$.
Rejection is the harness-level restart rule: the failed revision is
withdrawn, and the reason for the failure is retained. Acceptance is the
refine rule: verified protected records stay in $`\mathcal{P}`$, and the
next round focuses on what $`\mathcal{I}`$ still contains. The champion
score $`B`$ is replaced only when the accepted anchor score is strictly
larger, so $`B`$ never decreases. A commit inside the factor
$`(1-\varepsilon)`$ still become the current harness.

### 4.4. Stability Rule-Enhanced Evolution

One contribution of the method is to keep self-improvement at its
greatest freedom while using rules to guarantee the stability of that
evolution. We propose a four-layer stability rule framework and provide
the theoretical guarantees that follow from it.

#### 4.4.1. Four-Layer Stability Rule

The framework has four layers, written $`\mathcal{R}=\{RF,RS,AC,MC\}`$.
A candidate that passes the anchor check and the memory check is refined
into the deployed harness. Every other candidate, by contrast, restarts
the deployed harness from the current champion.

##### Refine rules (RF): protected progress.

An accepted candidate stays deployed, its eligible protected records
refresh the bounded memory, and the next round attends to the clusters
that are still open.

| (24) |  |
``` math
\mathcal{R}_{n+1}=\emptyset\qquad\text{if}\qquad\mathrm{Accept}(H^{\prime}_{n})=1,
``` |  |

where $`\mathcal{R}_{n+1}`$ is the verdict set supplied to the next call
of $`G`$.

##### Restart rules (RS).

A rejected candidate is withdrawn from deployment. Its rejection reason
is retained for the next analysis.

###### (i) RS-Rule 1: Champion restoration.

Rejection returns the deployed harness to the champion.

|  |  |  |  |
|----|----|----|----|
| (25) |  |
``` math
H_{n+1}=H_{n}^{\star}\qquad\text{if}\qquad\mathrm{Accept}(H^{\prime}_{n})=0,
``` |  |

where $`H_{n}^{\star}`$ is the committed harness whose anchor score
equals the champion value $`B_{n}`$.

###### (ii) RS-Rule 2: Verdict retention.

The failed check is passed to the next assessment.

|  |  |  |  |
|----|----|----|----|
| (26) |  |
``` math
\mathcal{R}_{n+1}=\{v(H^{\prime}_{n})\}\qquad\text{if}\qquad\mathrm{Accept}(H^{\prime}_{n})=0,
``` |  |

where $`v(H^{\prime})`$ records which predicate failed and which sampled
records regressed.

###### (iii) RS-Rule 3: Frozen memory.

A rejected candidate adds no solved task.

|  |  |  |  |
|----|----|----|----|
| (27) |  |
``` math
\mathcal{P}_{n+1}=\mathcal{P}_{n}\qquad\text{if}\qquad\mathrm{Accept}(H^{\prime}_{n})=0.
``` |  |

##### Anchor check rules (AC): validation floor.

A candidate may be refined only when its score on the fixed validation
anchor stays close to the best committed score.

###### (i) AC-Rule 1: Relative admission.

The anchor test compares the candidate with the current champion.

|  |  |  |  |
|----|----|----|----|
| (28) |  |
``` math
\mathrm{AC}(H^{\prime})=\mathbf{1}\bigl[V(H^{\prime})\geq(1-\varepsilon)\,B\bigr],
``` |  |

where $`V(H)`$ is the task success rate of $`\pi_{H}`$ on the fixed
anchor, $`B`$ is the champion score, and $`\varepsilon\in[0,1]`$ is the
tolerance. Let $`j\in\{1,\ldots,\ell\}`$ index the bounded remediation
cycles within one outer round, where $`\ell`$ is the maximum number of
candidate cycles. An anchor failure returns control to Analyze with its
verdict, and becomes a terminal rejection only in the last cycle:

|  |  |  |  |
|----|----|----|----|
| (29) |  |
``` math
\mathrm{AC}(H^{\prime}_{n,j})=0\implies\begin{cases}g_{n,j+1}=G\bigl(\tau(H_{n}^{\star}),\{v_{\mathrm{AC}}(H^{\prime}_{n,j})\}\bigr),&j<\ell,\\
\mathrm{Reject}_{\mathrm{AC}}(n),&j=\ell.\end{cases}
``` |  |

###### (ii) AC-Rule 2: Strict champion update.

The champion score increases only when an accepted candidate strictly
exceeds it.

|  |  |  |  |
|----|----|----|----|
| (30) |  |
``` math
B_{n}=\begin{cases}V(H^{\prime}_{n})&\text{if }\mathrm{Accept}(H^{\prime}_{n})=1\text{ and }V(H^{\prime}_{n})>B_{n-1},\\
B_{n-1}&\text{otherwise.}\end{cases}
``` |  |

Thus $`H^{\star}`$ changes only in the first branch, while
$`B_{n}\geq B_{n-1}`$.

###### (iii) AC-Rule 3: Band deployment.

An accepted candidate becomes the current harness even when it does not
set a new champion.

|  |  |  |  |
|----|----|----|----|
| (31) |  |
``` math
H_{n+1}=H^{\prime}_{n}\qquad\text{whenever}\qquad\mathrm{Accept}(H^{\prime}_{n})=1,
``` |  |

whereas $`H_{n}^{\star}`$ is updated only
by ([30](#S4.E30 "In (ii) AC-Rule 2: Strict champion update. ‣ Anchor check rules (AC): validation floor. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")).
A later restart therefore returns directly to the champion, which may
itself differ from the harness deployed inside the band.

##### Memory check rules (MC): protected records.

The regression memory blocks a commit that degrades too many sampled
turn–metric achievements of committed harnesses.

###### (i) MC-Rule 1: Stratified sample.

The sample cycles through the groups represented in the memory. Let
$`\Gamma(\mathcal{P})`$ be the set of all nonempty triples of metric
dimension, dialogue scenario, and complexity tier represented in
$`\mathcal{P}`$.

|      |     |                                                              |     |
|------|-----|--------------------------------------------------------------|-----|
| (32) |     |
              ``` math
              Q=\mathrm{Cycle}\bigl(\mathcal{P},\Gamma(\mathcal{P})\bigr),
              ```                                                           |     |

where $`\mathrm{Cycle}`$ takes one record from each group in turn until
the sample budget is filled. A group is visited again only after every
nonempty group has contributed.

###### (ii) MC-Rule 2: Regression bound.

A sampled record $`r=(x,t,d,b)`$ regresses when the candidate’s score
$`s_{d}(H^{\prime};x,t)`$ falls below its stored baseline $`b`$.

|  |  |  |  |
|----|----|----|----|
| (33) |  |
``` math
\mathrm{Reg}_{Q}(H^{\prime})=\sum_{(x,t,d,b)\in Q}\mathbf{1}\bigl[s_{d}(H^{\prime};x,t)<b\bigr],
``` |  |

|  |  |  |  |
|----|----|----|----|
| (34) |  |
``` math
\mathrm{MC}(H^{\prime})=\mathbf{1}\bigl[\mathrm{Reg}_{Q}(H^{\prime})\leq\delta\bigr],
``` |  |

where $`\delta`$ is a nonnegative integer tolerance. The predicate
$`\mathrm{MC}`$ is the memory conjunct
of ([18](#S4.E18 "In 4.3. Outer Self-Improvement Loop ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")).
A memory failure, for its part, follows the same bounded return to
Analyze, with the regressed records included in its verdict:

|  |  |  |  |
|----|----|----|----|
| (35) |  |
``` math
\mathrm{MC}(H^{\prime}_{n,j})=0\implies\begin{cases}g_{n,j+1}=G\bigl(\tau(H_{n}^{\star}),\{v_{\mathrm{MC}}(H^{\prime}_{n,j})\}\bigr),&j<\ell,\\
\mathrm{Reject}_{\mathrm{MC}}(n),&j=\ell.\end{cases}
``` |  |

Thus neither check terminates the round after its first failure. The
round is rejected only if all $`\ell`$ remediation cycles fail.

###### (iii) MC-Rule 3: Seeded growth.

The memory exists before any candidate is proposed, and it is refreshed
only through a refine step.

|  |  |  |  |
|----|----|----|----|
| (36) |  |
``` math
\mathcal{P}_{0}=\mathrm{Cap}_{C}\bigl(\mathcal{A}(H_{0})\bigr),
``` |  |

and $`\mathcal{P}_{n+1}`$
follows ([22](#S4.E22 "In (i) RF-Rule 1: Protected-record refresh. ‣ Refine rules (RF): protected progress. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"))
after acceptance
and ([27](#S4.E27 "In (iii) RS-Rule 3: Frozen memory. ‣ Restart rules (RS). ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"))
after rejection.

#### 4.4.2. Theoretical Guarantees

The stability rules constrain which evolutionary update may be deployed.
Let an evolution context be

|     |                                                        |     |
|-----|--------------------------------------------------------|-----|
|     |
       ``` math
       \mathcal{C}=(H,\mathcal{P},\mathcal{I},B,\mathcal{R}),
       ```                                                     |     |

where $`H`$ is the current harness, $`\mathcal{P}`$ the bounded
protected-record memory, $`\mathcal{I}`$ the open clusters, $`B`$ the
champion score, and $`\mathcal{R}=\{RF,RS,AC,MC\}`$ the rule set.
Throughout, $`V`$ takes values in $`[0,1]`$.

##### Formal theorems.

The framework yields four guarantees.

###### (i) Theorem 1 (Protected-record refresh).

If a candidate is accepted, the bounded memory is refreshed with
eligible records from the deployed harness and the stored rejection is
cleared:

|  |  |  |  |
|----|----|----|----|
| (37) |  |
``` math
\mathrm{Accept}(H^{\prime}_{n})=1\implies\mathcal{P}_{n+1}=\mathrm{Refresh}_{C}\bigl(\mathcal{P}_{n},\mathcal{A}(H_{n+1})\bigr)\;\land\;\mathcal{R}_{n+1}=\emptyset.
``` |  |

Proof sketch. RF-Rule 1
gives ([22](#S4.E22 "In (i) RF-Rule 1: Protected-record refresh. ‣ Refine rules (RF): protected progress. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")).
RF-Rule 3 gives $`\mathcal{R}_{n+1}=\emptyset`$. RF-Rule 2 then
instantiates the next assessment as
$`G(\tau(H_{n+1}),\emptyset)=(\mathcal{P}_{n+1},\mathcal{I}_{n+1})`$, so
the open set passed forward is $`\mathcal{I}_{n+1}`$.

###### (ii) Theorem 2 (Restart invariance).

If a candidate is rejected, deployment returns to the champion, the
protected-record memory is unchanged, and the rejection verdict is
retained:

|  |  |  |  |
|----|----|----|----|
| (38) |  |
``` math
\mathrm{Accept}(H^{\prime}_{n})=0\implies H_{n+1}=H_{n}^{\star}\;\land\;\mathcal{P}_{n+1}=\mathcal{P}_{n}\;\land\;\mathcal{R}_{n+1}=\{v(H^{\prime}_{n})\}.
``` |  |

Proof sketch. RS-Rule 1
is ([25](#S4.E25 "In (i) RS-Rule 1: Champion restoration. ‣ Restart rules (RS). ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")),
hence $`H_{n+1}=H_{n}^{\star}`$. RS-Rule 3
is ([27](#S4.E27 "In (iii) RS-Rule 3: Frozen memory. ‣ Restart rules (RS). ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")),
hence $`\mathcal{P}_{n+1}=\mathcal{P}_{n}`$. RS-Rule 2
is ([26](#S4.E26 "In (ii) RS-Rule 2: Verdict retention. ‣ Restart rules (RS). ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")),
hence $`\mathcal{R}_{n+1}=\{v(H^{\prime}_{n})\}`$. The next call is
therefore $`G(\tau(H_{n}^{\star}),\{v(H^{\prime}_{n})\})`$.

###### (iii) Theorem 3 (Anchor monotonicity).

The champion score is nondecreasing, and the harness left in deployment
stays above the anchor floor of that score:

|  |  |  |  |
|----|----|----|----|
| (39) |  |
``` math
B_{n}\geq B_{n-1}\qquad\text{and}\qquad V(\tilde{H}_{n})\geq(1-\varepsilon)\,B_{n},
``` |  |

where $`\tilde{H}_{n}`$ denotes the harness deployed at the end of round
$`n`$.

Proof sketch.
From ([30](#S4.E30 "In (ii) AC-Rule 2: Strict champion update. ‣ Anchor check rules (AC): validation floor. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")),
the two branches are $`B_{n}=V(H^{\prime}_{n})>B_{n-1}`$ and
$`B_{n}=B_{n-1}`$, so $`B_{n}\geq B_{n-1}`$. Since $`V\in[0,1]`$, the
sequence $`(B_{n})`$ is bounded. Let
$`\mathrm{Accept}(H^{\prime}_{n})=1`$. AC-Rule 1 yields
$`V(H^{\prime}_{n})\geq(1-\varepsilon)B_{n-1}`$,
and ([31](#S4.E31 "In (iii) AC-Rule 3: Band deployment. ‣ Anchor check rules (AC): validation floor. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"))
sets $`\tilde{H}_{n}=H^{\prime}_{n}`$. If $`V(H^{\prime}_{n})>B_{n-1}`$,
then $`B_{n}=V(H^{\prime}_{n})`$ and
$`V(\tilde{H}_{n})=B_{n}\geq(1-\varepsilon)B_{n}`$. If
$`V(H^{\prime}_{n})\leq B_{n-1}`$, then $`B_{n}=B_{n-1}`$ and
$`V(\tilde{H}_{n})\geq(1-\varepsilon)B_{n}`$. Let
$`\mathrm{Accept}(H^{\prime}_{n})=0`$. RS-Rule 1 sets
$`\tilde{H}_{n}=H_{n}^{\star}`$ with $`V(H_{n}^{\star})=B_{n}`$, hence
$`V(\tilde{H}_{n})=B_{n}\geq(1-\varepsilon)B_{n}`$.

###### (iv) Theorem 4 (Anti-oscillation).

Acceptance implies that the stratified regression count does not exceed
the memory tolerance:

|  |  |  |  |
|----|----|----|----|
| (40) |  |
``` math
\mathrm{Accept}(H^{\prime})=1\implies\mathrm{Reg}_{Q}(H^{\prime})\leq\delta.
``` |  |

Proof sketch.
Expand ([18](#S4.E18 "In 4.3. Outer Self-Improvement Loop ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"))
to $`\mathrm{MC}(H^{\prime})=1\land\mathrm{AC}(H^{\prime})=1`$.
Substitute ([34](#S4.E34 "In (ii) MC-Rule 2: Regression bound. ‣ Memory check rules (MC): protected records. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"))
to obtain $`\mathrm{Reg}_{Q}(H^{\prime})\leq\delta`$.
By ([32](#S4.E32 "In (i) MC-Rule 1: Stratified sample. ‣ Memory check rules (MC): protected records. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")),
$`Q=\mathrm{Cycle}(\mathcal{P},\Gamma(\mathcal{P}))`$ emits one element
of each $`\gamma\in\Gamma(\mathcal{P})`$ before repeating any group.
Therefore, whenever $`|\Gamma(\mathcal{P})|>1`$, the count
in ([33](#S4.E33 "In (ii) MC-Rule 2: Regression bound. ‣ Memory check rules (MC): protected records. ‣ 4.4.1. Four-Layer Stability Rule ‣ 4.4. Stability Rule-Enhanced Evolution ‣ 4. RSIV-Harness ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"))
is not computed on a single metric–scenario–tier group. MC-Rule 3
initializes $`\mathcal{P}_{0}=\mathrm{Cap}_{C}(\mathcal{A}(H_{0}))`$
before the first proposal, so the same bound applies to the protected
seed records retained in memory.

## 5. Experiments

### 5.1. Experimental Setup

#### 5.1.1. Dataset

All experiments use ODAC-Vis. We use the train split to drive the outer
loop of RSIV-Harness. The stratified training panel $`S`$ contains 48
tasks from train only domains. Their failure traces are analyzed to
propose harness edits. The anchor check evaluates every candidate on a
panel of 48 validation tasks. Each panel contains one task for every
combination of the three difficulty tiers, the eight ambiguity types,
and the two conversation scenarios. All of the test split is reserved
exclusively for final evaluation. It comprises 96 tasks over 15 held-out
domains that never appear in train or validation, so reported scores
measure open-domain source discovery, ambiguity handling, and multi-turn
chart generation rather than memorization of a fixed schema catalog. All
baselines and evolved harness variants are evaluated on this test split
under model history: each turn conditions on the model’s own prior
assistant outputs within the same task.

#### 5.1.2. Baselines

We compare RSIV-Harness against four progressively more sophisticated
baselines: direct prompting, static harnesses, ReAct, and
MultiVis-Agent:

- •
  Direct Prompt. A single LLM call per turn with no tool access. The
  model receives the full schema catalog together with the conversation
  history and NLQ of this turn.
- •
  Static Harnesses. The minimal seed harness $`H_{0}`$ of RSIV-Harness,
  held fixed and never evolved. A seed already fitted to ODAC-Vis would
  contaminate the attribution of every later edit, since a gain could no
  longer be separated from the seed. The minimal seed forces every
  component the outer loop adds to earn its place against measured
  traces.
- •
  ReAct ([Yao et al., 2023](#bib.bib36)). An ReAct baseline equipped
  with carefully designed, task-specific tools. At each turn, it runs a
  thought-action-observation loop.
- •
  MultiVis-Agent ([Lu et al., 2026c](#bib.bib13)). A state-of-the-art
  multi-agent system for text-to-visualization, adapted to ODAC-Vis task
  with minimal modifications.
- •
  RSIV-Harness (Ours). Our Proposed method. An inner ReAct loop
  clarifies the request or generates a visualization program, while an
  outer loop improves the harness from traces under a four-layer
  stability rule framework.

#### 5.1.3. Evaluation Metrics

To evaluate visualization generation systems, particularly those
handling open-domain, ambiguity-aware, multi-turn conversational tasks
like RSIV-Harness, we adopt the following metrics. Let $`\mathcal{T}`$
be the assistant turns in the evaluation split. For turn $`t`$,
$`y_{t}`$ is the gold stance and $`\hat{y}_{t}`$ is the predicted
stance. Write $`\mathcal{C}=\{t\in\mathcal{T}:y_{t}=\mathrm{code}\}`$
and $`\mathcal{Q}=\{t\in\mathcal{T}:y_{t}=\mathrm{clarify}\}`$.

- •
  Executability tests whether the emitted program can be run to
  completion. It isolates basic viability before asking whether the
  analysis is correct:

  |  |  |  |  |
  |----|----|----|----|
  | (41) |  |
  ``` math
  \mathrm{Exec}=\frac{100}{|\mathcal{C}|}\sum_{t\in\mathcal{C}}\mathbf{1}\!\bigl[\mathrm{Run}(\hat{p}_{t})\bigr],
  ``` |  |

  where $`\hat{p}_{t}`$ is the predicted program and
  $`\mathrm{Run}(\hat{p}_{t})=1`$ when a valid predicted program runs to
  completion.
- •
  Database Routing Accuracy checks whether the program accesses exactly
  the target databases for the task. In an open-domain setting,
  retrieving the wrong source can yield a fluent but irrelevant chart
  even when the code runs successfully. Let $`D(\hat{p}_{t})`$ be the
  set of databases accessed by the prediction, and $`D_{t}^{\star}`$ the
  gold target set:

  |  |  |  |  |
  |----|----|----|----|
  | (42) |  |
  ``` math
  \mathrm{Route}=\frac{100}{|\mathcal{C}|}\sum_{t\in\mathcal{C}}\mathbf{1}\!\bigl[D(\hat{p}_{t})=D_{t}^{\star}\bigr].
  ``` |  |
- •
  Stance Accuracy measures whether an agent chooses the appropriate
  response mode—clarification or executable code—at each assistant turn.
  Because downstream dialogue and prediction depend on this decision,
  stance errors can invalidate an otherwise plausible program or chart:

  |  |  |  |  |
  |----|----|----|----|
  | (43) |  |
  ``` math
  \mathrm{Stance}=\frac{100}{|\mathcal{T}|}\sum_{t\in\mathcal{T}}\mathbf{1}\!\bigl[\hat{y}_{t}=y_{t}\bigr].
  ``` |  |
- •
  Execution Accuracy compares the tabular results pro- duced by the
  ground-truth and predicted programs, determining whether the pre-
  dicted SQL returns the same result as the ground-truth SQL:

  |  |  |  |  |
  |----|----|----|----|
  | (44) |  |
  ``` math
  \mathrm{ExAcc}=\frac{100}{|\mathcal{C}|}\sum_{t\in\mathcal{C}}\mathbf{1}\!\bigl[\exists\,\pi:\;\pi(\hat{R}_{t})\equiv R_{t}^{\star}\bigr],
  ``` |  |

  where $`R_{t}^{\star}`$ and $`\hat{R}_{t}`$ are the gold and predicted
  tables.
- •
  Clarification Quality evaluates how well predicted clarification
  questions recover the intended ambiguity resolution. A completed
  clarification is compared with the gold clarification and any
  annotated alternatives. For each $`n\in\{1,2,3,4\}`$, modified
  $`n`$-gram precision is

  |  |  |  |  |
  |----|----|----|----|
  | (45) |  |
  ``` math
  p_{n}=\frac{\sum_{g\in\mathrm{Gram}_{n}(h)}\min\!\bigl(c_{h}(g),\,c_{\mathcal{R}}^{\max}(g)\bigr)}{\sum_{g\in\mathrm{Gram}_{n}(h)}c_{h}(g)},
  ``` |  |

  where $`h`$ is the predicted clarification, $`\mathcal{R}`$ is the
  reference set, $`c_{h}(g)`$ counts occurrences of $`g`$ in $`h`$, and
  $`c_{\mathcal{R}}^{\max}(g)`$ is the maximum reference count of $`g`$;
  otherwise

  |  |  |  |  |
  |----|----|----|----|
  | (46) |  |
  ``` math
  \mathrm{BLEU\text{-}4}(h,\mathcal{R})=100\cdot\exp\!\Bigl(\tfrac{1}{4}\sum_{n=1}^{4}\log p_{n}\Bigr),
  ``` |  |

  without a brevity penalty. The reported score is the mean turn-level
  BLEU-4,

  |  |  |  |  |
  |----|----|----|----|
  | (47) |  |
  ``` math
  \mathrm{Clarify}=\frac{1}{|\mathcal{Q}|}\sum_{t\in\mathcal{Q}}s_{t},
  ``` |  |

  where $`s_{t}=\mathrm{BLEU\text{-}4}(h_{t},\mathcal{R}_{t})`$ when the
  prediction clarifies and $`s_{t}=0`$ otherwise.
- •
  Chart Structure compares the figure produced by the predicted program
  with the gold figure. Each figure is reduced to a signature
  $`(M,X,Y,c,a_{x},a_{y},I,R)`$: $`M`$ is the mark types; $`X`$ and
  $`Y`$ are the per-trace role sequences of the $`x`$ and $`y`$
  encodings; $`c`$ holds when the figure has multiple traces or a legend
  group; $`a_{x}`$ and $`a_{y}`$ are the axis titles; $`I`$ is the set
  of interaction kinds; and $`R`$ is the multiset of plotted rows.

  |  |  |  |  |  |
  |----|----|----|----|----|
  | (48) |  | $`\displaystyle\mathrm{Struct}`$ | $`\displaystyle=\frac{1}{8}\bigl(\mathbf{1}[M=\hat{M}]+\mathbf{1}[X=\hat{X}]`$ |  |
  |  |  |  | $`\displaystyle+\mathbf{1}[Y=\hat{Y}]+\mathbf{1}[c=\hat{c}]+\alpha_{x}+\alpha_{y}`$ |  |
  |  |  |  | $`\displaystyle+J(I,\hat{I})+\mathbf{1}[R\equiv\hat{R}]\bigr),`$ |  |

  where $`\alpha_{x}=\mathrm{Title}(a_{x},\hat{a}_{x})`$ and
  $`\alpha_{y}=\mathrm{Title}(a_{y},\hat{a}_{y})`$. The reported score
  averages the turn values,

  |      |     |                                                             |     |
  |------|-----|-------------------------------------------------------------|-----|
  | (49) |     |
                ``` math
                \mathrm{Chart}=\frac{100}{|\mathcal{C}|}\sum\mathrm{Struct}
                ```                                                          |     |

### 5.2. Results and Analysis

#### 5.2.1. Overall Results

Table [3](#S5.T3 "Table 3 ‣ 5.1.3. Evaluation Metrics ‣ 5.1. Experimental Setup ‣ 5. Experiments ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")
shows that RSIV-Harness obtains the strongest DeepSeek results on five
of the six metrics. Relative to the best competing method in each
column, it improves executability by 11.68 points, database routing by
4.67 points, stance accuracy by 2.75 points, clarification quality by
0.83 points, and chart structure by 23.24 points. Its execution accuracy
of 31.52 is only 0.39 points below Direct Prompt. The comparison with
the static harness isolates the effect of evolution more directly.
Recursive improvement raises the six metrics by 28.02, 14.01, 15.75,
7.01, 1.43, and 34.01 points in table order. These gains show that
adapting the harness around fixed model weights improves not only
program viability, but also source selection, dialogue decisions, and
the structure of the final chart.

#### 5.2.2. Impact of LLM Backbone

The GPT results test whether a harness evolved only with DeepSeek can
transfer to another backbone without further optimization. Compared with
the static GPT harness, the frozen evolved harness improves five of six
metrics. The gains are 9.34 points in executability, 19.07 in database
routing, 7.50 in stance accuracy, 1.72 in clarification quality, and
8.35 in chart structure. Execution accuracy is 0.78 points lower. The
transferred system is nevertheless slightly below the strongest GPT
baseline on most individual metrics. The deficits are 4.67 points for
executability, 1.55 for routing, 0.25 for stance, 0.78 for execution
accuracy, and 0.01 for chart structure. It achieves the best
clarification score at 3.74. These results demonstrate the applicability
of RSIV-Harness across open-source and proprietary LLM backbones, with
harness improvements learned from one model remaining transferable to
another without adaptation, although some performance gains remain
dependent on the model used during evolution.

#### 5.3.1. Stability Rule Analysis

To isolate the effect of stability rules, we repeat one round of harness
evolution with DeepSeek-V4.1-Flash after removing the stability rule
framework, keeping all other settings unchanged. The resulting harness
is then frozen and evaluated on the test split using the same model. As
shown in
Table [4](#S5.T4 "Table 4 ‣ 5.3. Ablation Study ‣ 5. Experiments ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"),
removing the stability rules leads to performance degradation across all
six metrics: executability drops by 9.73 points, database routing by
3.12, stance accuracy by 2.50, execution accuracy by 3.50, clarification
quality by 2.74, and chart structure by 9.53. The largest declines occur
in executability and chart structure, while the reductions in routing,
stance, and clarification quality indicate that the framework
contributes to multiple aspects of conversational visualization rather
than merely filtering invalid programs. These results highlight the
importance of stability rules in guiding harness evolution, helping
preserve previously successful behaviors while enabling improvements
from accumulated task failures.

#### 5.3.2. Harness Component Analysis

To assess component contributions, we replace each component of the
$`H_{0}`$ with its evolved counterpart—prompt, tool, memory, skill, or
middleware—while keeping the others unchanged.
Table [4](#S5.T4 "Table 4 ‣ 5.3. Ablation Study ‣ 5. Experiments ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization")
reveals complementary strengths. The evolved prompt improves routing
(62.26), clarification (3.76), and chart structure (71.13), while the
tool interface supports routing (62.26) and stance accuracy (65.25).
Memory benefits routing (59.92) and chart structure (67.69), whereas
skills improve execution accuracy (29.18) and chart structure (69.47).
Middleware achieves the best single-component results in executability
(90.66), stance accuracy (66.50), execution accuracy (30.35), and chart
structure (72.41), highlighting the role of control flow and execution
feedback. The complete harness still exceeds every single component
variant in five metrics. The combined result therefore arises from
coordination among components rather than from one isolated edit.

### 5.4. Case Study

We present a cross-database visualization task involving two car-racing
databases joined by driver ID to demonstrate the capabilities of
RSIV-Harness. The user first requests a bar chart of average driver age,
then excludes Kasey Kahne and uses color to encode vehicle make. The
reference chart
(Figure [5(a)](#S5.F5.sf1 "In Figure 5 ‣ 5.1.4. Implementation Details ‣ 5.1. Experimental Setup ‣ 5. Experiments ‣ RSIV-Harness: A Recursive Self-Improvement Harness Framework for Open-Domain Conversational Text-to-Visualization"))
therefore contains nine drivers across three makes. Direct Prompt and
ReAct distort the ages and chart orientation, with ReAct omitting six
drivers. $`H_{0}`$ incorrectly concatenates driver names across sources.
MultiVis-Agent keeps the nine names but shifts the ages, for example
drawing Bobby Labonte at 26.5 rather than 28. In contrast, RSIV-Harness
preserves the correct drivers, ages, and make-based encoding, closely
matching the reference chart. This demonstrates its ability to integrate
cross-database evidence while respecting multi-turn refinements.

## 6. Conclusion

We presented ODAC-Vis and RSIV-Harness as a benchmark and method for
open domain conversational text to visualization. ODAC-Vis evaluates
source discovery, ambiguity resolution, and multi turn chart refinement
under held out domains. RSIV-Harness improves the harness around a fixed
language model through recursive analysis of failure traces. Its
stability rules provide explicit guarantees for protected record
refresh, champion restoration, anchor monotonicity, and bounded
regression. On the test split, a single round of recursive
self-improvement improves the DeepSeek-based harness across all six
evaluation metrics. The same frozen harness also transfers competitively
to GPT-6 Luna. Ablations further show that the stability rules improve
all reported metrics and that the harness components make complementary
contributions. These findings establish harness evolution as a practical
path for improving conversational visualization agents.
````
