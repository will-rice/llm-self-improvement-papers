###### Abstract

Large Language Model (LLM) agents can handle increasingly complex tasks,
navigating long trajectories of observations and actions. As these
trajectories grow, key-value (KV) cache I/O and storage become the
dominant cost. Trajectories can also exceed the LLM’s maximum context
length, requiring control over active cache growth. Prior work uses
context engineering to reduce cache size by trimming or summarizing
history. However, modifying the trajectory prefix invalidates subsequent
cached states and triggers costly re-prefilling of retained context.
Task accuracy can also suffer when too little context is retained to
limit re-prefill costs. We propose cache engineering as a new scheme. It
allows agents to directly control their active KV cache without
modifying the trajectory or re-prefilling retained context.
Specifically, agents can proactively use $`\operatorname{drop}`$ to
exclude selected cache from future attention and
$`\operatorname{repos}`$ to adjust retained keys’ position encodings. We
formalize these cache operations and identify history dependence as a
serving challenge: identical token sequences can yield different cache
states under different cache operation sequences, making prefix matching
insufficient for correct cache reuse. Thus, we co-design the AKV serving
engine. It provides a stateless interface compatible with existing
serving APIs, while internally managing stateful cache reuse, eviction,
and restoration. Experiments show that a tool-response rolling-drop
cache policy improves average benchmark scores by 1.7 points and reduces
average cost by 27.7%, compared with conventional threshold-triggered
summarization. With AKV, it achieves up to $`1.2\times`$ the output
throughput and a $`1.5\times`$ speedup in P95 request latency. Recursive
self-improvement of cache policies further reduces cost by 7.1% over
expert design. Our code is at
[https://github.com/thu-nics/AKV](https://github.com/thu-nics/AKV).

## 1 Introduction

Large Language Model (LLM) agents are capable of increasingly
long-horizon tasks. Agents are generally composed of an LLM for
reasoning and tool calling, and a harness that orchestrates tool
execution and context. Through repeated reasoning, tool use, and
environment interactions, they can carry out complex work spanning
hundreds of rounds ([Ye et al., 2025](#bib.bib7); [Liu et al.,
2025b](#bib.bib39)).

As agent trajectories grow longer, Key-Value (KV) cache growth poses
challenges to both inference cost and task accuracy. In terms of cost,
retaining and repeatedly accessing accumulated KV caches incur
substantial storage and I/O overhead ([Wu et al., 2026](#bib.bib2);
[Anthropic, 2026](#bib.bib3)). As shown in
Figure [14](#A1.F14 "Figure 14 ‣ A.4.2 Cost Breakdown and Active Context Length ‣ A.4 Additional Experiment Results ‣ Appendix A Appendix ‣ Cache Engineering for Agents"),
KV cache reads take up 82.4% of the total API cost. In terms of task
accuracy, agents can suffer severe degradation if either the number of
attended KV states or their positional range exceeds what LLM handles
reliably ([Hsieh et al., 2024](#bib.bib38); [Chen et al.,
2026b](#bib.bib40); [Zhou et al., 2025](#bib.bib41)). Therefore, it
requires delicate control over the active KV cache for efficient and
reliable agent execution.

Prior work reduces the growing cache via context engineering, typically
by trimming or summarizing historical messages. While older messages are
often less useful, editing them changes the trajectory prefix,
invalidates subsequent KV states, and triggers re-prefill. The earlier
the edit, the more retained trajectory suffix that must be re-prefilled.
Common harnesses therefore defer reductions until an active context
length threshold is reached, then trim or summarize most of the
trajectory and retain only a few recent rounds to keep re-prefill
short ([Pi, 2026](#bib.bib53); [OpenAI, 2026](#bib.bib54)). Such
aggressive reductions risk losing useful information from intermediate
rounds, exposing a dilemma between re-prefill cost and task accuracy.

In this paper, we introduce cache engineering, a new scheme for agents
to directly control their active KV cache. As shown in
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Cache Engineering for Agents"),
instead of modifying the text trajectory, it excludes only selected KV
entries from future attention, and reuses all retained KV states without
re-prefill. This allows agents to incrementally drop older KV entries
while retaining more suffix KV within a given cost budget. To support
this control, alongside the usual $`\operatorname{append}`$ operation
that adds KV states for new tokens, we introduce two additional cache
operations. $`\operatorname{Drop}`$ removes selected KV entries from
future attention, and $`\operatorname{repos}`$ adjusts the positions
encoded in retained keys. Throughout execution, the LLM and harness
choose when and how to apply these operations, repeatedly interleaving
them with $`\operatorname{append}`$ to shape the active cache. This
programmable control also enables agents to search, evaluate, and refine
cache engineering strategies through recursive self-improvement (RSI).

Figure 1: Full-context inference, context engineering, and cache
engineering. Full-context inference reuses all historical KV. Context
engineering removes irrelevant text and recomputes the retained history.
Cache engineering keeps the text history but drops selected KV entries,
reusing retained states without recomputation. Nested color blocks
illustrate how retained KV can still carry information from dropped
history.

However, the history-dependent nature of cache engineering challenges
current LLM serving systems. With standard KV caching, the token prefix
fully determines the cached states ([Kwon et al., 2023](#bib.bib52);
[Zheng et al., 2024](#bib.bib20)). In contrast, the same token prefix
and retained positions can result in different cache states under
different cache operation histories. As shown in
Figure [5](#S3.F5 "Figure 5 ‣ 3.3 Cache Operations ‣ 3 Cache Engineering ‣ Cache Engineering for Agents"),
trajectories ① and ② both retain KV entries for B and C, but C’s KV is
computed with attention to A only in ①, due to the different ordering of
drop and append operations. The serving system must therefore account
for both token and cache operation histories to correctly track or reuse
cache states.

Thus, we co-design AKV, a user-friendly and efficient serving system for
cache engineering. It provides a stateless interface compatible with
existing API-based serving, while handling the complexity of stateful
cache management internally. Agents simply submit messages as usual,
accompanied by cache operation instructions, without tracking which KV
states remain resident on the server. The system uses an extended radix
tree for correct reuse and timely eviction of history-dependent cache
states, while segment-batch attention efficiently reconstructs missing
states in a single prefill pass. AKV turns the theoretical efficiency
potential of cache engineering into lower wall-clock latency and higher
throughput for real-world agent workloads.

- •
  Cache engineering formulation. We formalize cache engineering through
  explicit cache operations and their trajectories, providing a clear
  and deterministic description of history-dependent cache states. This
  formulation also provides a programmable interface for agents to
  define and refine their own cache engineering strategies.
- •
  Serving system for cache engineering. We propose the first serving
  system that allows agents to directly control their caches, which were
  previously managed solely by the system. We co-design a stateless
  interface, an extended radix tree, and segment-batch attention to
  support efficient cache reuse, eviction, and restoration.
- •
  Improving efficiency and benchmark performance. Across three LLMs and
  four agent benchmarks, a simple tool-response rolling-drop cache
  policy reduces average cost by 27.7% and improves average benchmark
  scores by 1.7 points, compared with conventional threshold-triggered
  summarization. With AKV server, this translates to $`1.18\times`$ the
  output throughput and a $`1.51\times`$ speedup in P95 request latency.
  An RSI-based policy additionally reduces cost by 7.1% on held-out
  tasks.

## 2 Related Work

Agent context engineering. At the text level, context engineering
summarizes or trims interaction histories to reduce cost and enable
agents to work beyond the LLM’s context window. Existing methods trigger
summarization through heuristics ([Wu et al., 2025](#bib.bib5)) or agent
decisions ([Ye et al., 2025](#bib.bib7); [Sun et al., 2025](#bib.bib9)).
Further work improves summary quality through reinforcement
learning ([Lu et al., 2025](#bib.bib6)) or by optimizing compression
guidelines ([Kang et al., 2025](#bib.bib8)). To avoid the cost and
complexity of summarization, trimming methods ([Lindenbauer et al.,
2025](#bib.bib4); [Zhang et al., 2026](#bib.bib37)) directly remove less
relevant context. However, editing earlier context requires
re-prefilling the retained suffix, creating a dilemma between re-prefill
cost and information retention.

KV cache compression, eviction, and reuse. At the cache level, prior
work reduces cache size or approximately reuses existing states to lower
storage, access, and computation costs. Compression methods use low-rank
representations ([Liu et al., 2024a](#bib.bib12); [Wang et al.,
2024a](#bib.bib57)), quantization ([Liu et al., 2024b](#bib.bib13); [Liu
et al., 2026b](#bib.bib56)), or aggregation ([Fu et al.,
2025b](#bib.bib43); [Wang et al., 2024b](#bib.bib58)) to represent
cached entries more compactly. Eviction methods typically rely on
low-level signals such as token positions ([Xiao et al.,
2024](#bib.bib14)) or attention-based importance ([Zhang et al.,
2023](#bib.bib15); [Li et al., 2024](#bib.bib16); [Fu et al.,
2025a](#bib.bib44); [Yang et al., 2026](#bib.bib55)) to remove less
useful cache entries. Reuse methods adapt cached states to different
positions or context prefixes through position encoding
adjustments ([Gao et al., 2024](#bib.bib22); [Ma et al.,
2026](#bib.bib27); [Ordonez and Parnell, 2026](#bib.bib28)) or partial
recomputation ([Wang et al., 2025](#bib.bib26)). Our work focuses on
eviction and reuse, enabling high-level eviction decisions by agents and
harnesses, while providing a practical serving engine for efficient
cross-request reuse and isolation. We discuss concurrent agent-oriented
eviction work in
Appendix [A.5](#A1.SS5 "A.5 Additional Related Works ‣ Appendix A Appendix ‣ Cache Engineering for Agents").

KV cache management in serving systems. Beyond algorithmic designs,
previous works also explore system optimizations for efficient cache
storage, sharing, and request scheduling. Existing systems use prefix
caching to share KV states across requests with common prefixes while
preserving equivalence to full prefill ([Zheng et al.,
2024](#bib.bib20); [Ye et al., 2024](#bib.bib21)). For agent workloads,
recent systems batch context edits to reduce cache invalidation ([Xu et
al., 2026](#bib.bib10)) or overlap re-prefill with ongoing execution to
hide its latency ([Pan et al., 2026](#bib.bib11)). For cache
engineering, it additionally requires tracking cache operation
histories, since identical token prefixes can produce different states
under different operations.

## 3 Cache Engineering

Cache engineering lets agents directly control their active KV cache
without rewriting the trajectory or re-prefilling retained context. We
introduce basic concepts in
Section [3.1](#S3.SS1 "3.1 Preliminaries ‣ 3 Cache Engineering ‣ Cache Engineering for Agents")
and design motivations in
Section [3.2](#S3.SS2 "3.2 Design Motivation ‣ 3 Cache Engineering ‣ Cache Engineering for Agents"),
then formalize cache operations and their trajectories in
Sections [3.3](#S3.SS3 "3.3 Cache Operations ‣ 3 Cache Engineering ‣ Cache Engineering for Agents")
and [3.4](#S3.SS4 "3.4 Cache Operation Sequence ‣ 3 Cache Engineering ‣ Cache Engineering for Agents").

### 3.1 Preliminaries

An autoregressive LLM predicts the next token conditioned on the
preceding token sequence $`x_{1:t}`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       p_{\theta}(x_{t+1}\mid x_{1:t}).
       ```                               |     | (1) |

Modern LLM serving uses KV caching to avoid recomputing earlier tokens’
states. The next-token prediction is then conditioned on the current
token $`x_{t}`$ and the preceding tokens’ cache:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       p_{\theta}(x_{t+1}\mid x_{t},\mathcal{C}_{1:t-1}),
       ```                                                 |     | (2) |

where $`\mathcal{C}_{1:t-1}`$ denotes the KV states computed from tokens
$`x_{1:t-1}`$.

An agent’s _trajectory_ is the ordered text history used for the
following model computation, including its prompt, assistant messages,
and tool responses. Formally, the trajectory is a _logical token
sequence_ $`x_{1:t}`$, and $`t`$ is its _logical token length_.

In cache engineering, the cache size need not equal the logical token
length. We therefore define the _active cache_ $`\mathcal{C}`$ as the KV
cache states available to subsequent attention. The corresponding token
sequence is the _active context_, whose length equals the number of
token entries in $`\mathcal{C}`$. Note that _active_ refers to
participation in attention at the algorithmic level, not physical cache
residency in the serving engine. A cache entry’s _position encoding
index_ can also be adjusted independently of its token’s _logical index_
in the trajectory.

Context engineering modifies the logical token sequence through trimming
or summarization. In contrast, cache engineering directly modifies the
active cache through cache operations, while keeping the logical token
sequence unchanged.

### 3.2 Design Motivation

The design of cache engineering stems from our thinking about three key
questions: why direct cache modification is needed, which parts of the
cache to retain, and how to manage its encoding positions. We discuss
the motivations and empirical evidence guiding our design decisions
below.

tool responses, averaged over 10 BCP requests.

Figure 3: GPT-OSS-120B accuracy and cost on 100 BCP tasks. Labels
indicate summary thresholds (tokens) or AKV’s retained tool rounds.

Figure 4: Recursive self-improvement on cache engineering policy,
evaluated on the BCP benchmark with MiniMax-M2.7 LLM.

Why modify the cache directly. Cache engineering alleviates the dilemma
between re-prefill cost and task accuracy in context engineering. We
evaluate GPT-OSS-120B on the first 100 BCP tasks, with four trials per
task and at most 100 agent rounds. Trim-based context engineering
(retaining only the latest 12 rounds of tool responses) costs
$`1.85\times`$ as much as the full-context baseline. Summary-based
context engineering (48k threshold) reduces cost by about 7% but lowers
accuracy by 5 percentage points
(Figure [4](#S3.F4 "Figure 4 ‣ 3.2 Design Motivation ‣ 3 Cache Engineering ‣ Cache Engineering for Agents")).
In contrast, directly dropping older tool-response cache can reuse the
remaining cache, simultaneously improving accuracy and reducing cost
(Figure [4](#S3.F4 "Figure 4 ‣ 3.2 Design Motivation ‣ 3 Cache Engineering ‣ Cache Engineering for Agents")).
The retained cache may also preserve information from dropped history
used in its computation ([Xiao et al., 2024](#bib.bib14); [Fu et al.,
2026](#bib.bib1); [Zou et al., 2025](#bib.bib45)), as shown in
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Cache Engineering for Agents").

Which parts of the cache to retain. Cache selection should reflect
message roles, recency, and task needs, beyond token-level importance
heuristics.
Figure [4](#S3.F4 "Figure 4 ‣ 3.2 Design Motivation ‣ 3 Cache Engineering ‣ Cache Engineering for Agents")
shows that older tokens receive less attention than recent ones, and
tool responses receive less attention than assistant messages at
comparable relative positions. We therefore use tool-response rolling
drop as our primary example, retaining cache for all reasoning and
recent tool responses while dropping older tool-response cache. We later
explore alternative policies, including RSI-based cache engineering.

How to manage position encodings. By default, position encoding indices
grow with the logical trajectory, even as the cache is reduced. Dropping
cache neither changes retained position encodings nor resets the next
token’s position index, so indices can reach the model’s limit even with
a small cache. We decouple position encoding indices from logical
indices and cache size, using a separate cache operation to reposition
cached keys with RoPE rotations ([Su et al., 2023](#bib.bib42)) without
re-prefill.

### 3.3 Cache Operations

Figure 5: Cache operation trajectories and history-dependent KV states.
(a) ① appends C to A and B, then drops A’s KV; ② drops A’s KV before
appending C; ③ starts from B alone and appends C. All three retain B and
C. (b) B’s KV is identical in ① and ②, both conditioned on A, but
differs in ③, where B has no prefix. C’s KV differs in all three: ① is
computed with A and B; ② and ③ cannot attend to A but use different B
caches. (c) The extended radix tree shares the A–B prefix of ① and ②,
then branches according to $`\operatorname{drop}`$ timing,
distinguishing the cached states used to generate D.

We define three basic cache operations for cache engineering:
$`\operatorname{append}`$, $`\operatorname{drop}`$, and
$`\operatorname{repos}`$, which directly manipulate cache without
rewriting the existing logical token sequence.

$`\operatorname{Append}`$. Operation $`\operatorname{append}`$ is the
standard cache update in LLM inference. It processes a new token
$`x_{t+1}`$ conditioned on the active cache and appends its cache entry
$`C_{t+1}`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\operatorname{append}(x_{t+1}):\qquad\mathcal{C}\leftarrow[\mathcal{C};\,C_{t+1}].
``` |  | (3) |

We represent $`\mathcal{C}`$ as a sequence of KV entries ordered by
their logical indices, where $`[\cdot;\cdot]`$ denotes concatenation.
The token may come from the prompt, a tool response, or model
generation. Position encoding indices start at zero and advance by one
after each append; $`\operatorname{repos}`$ can reset the next index.

$`\operatorname{Drop}`$. Operation $`\operatorname{drop}`$ removes
selected KV states from subsequent attention, while leaving the retained
states, their position encodings, and the logical token sequence
unchanged
(Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Cache Engineering for Agents")):

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\operatorname{drop}(P):\qquad\mathcal{C}\leftarrow\mathcal{C}\setminus\{C_{i}:i\in P\},
``` |  | (4) |

where $`P`$ is the set of active logical token indices selected for
dropping, and $`\setminus`$ denotes cache removal, preserving the order
of retained entries. Note that $`\operatorname{drop}`$ does not change
the position encoding indices used by subsequent
$`\operatorname{append}`$ operations.

$`\operatorname{Repos}`$. Operation $`\operatorname{repos}`$ updates
cached keys’ position encodings in logical token order, and resets the
position index for subsequent $`\operatorname{append}`$ operations. With
$`r`$ retained cache entries, their position indices become
$`0,\ldots,r-1`$, and the next appended token uses index $`r`$. For
rotary position embeddings (RoPE) ([Su et al., 2023](#bib.bib42)), we
move a cached key $`K`$ from position index $`p`$ to $`q`$ by

|     |                             |     |     |
|-----|-----------------------------|-----|-----|
|     |
       ``` math
       K\leftarrow R(q)R(p)^{-1}K,
       ```                          |     | (5) |

where $`R(p)`$ is the rotation matrix at position $`p`$. Cached values
remain unchanged.

These operations define the cache visible to attention at the
algorithmic level. The serving system handles physical storage,
eviction, and reuse of cache separately in
Section [4](#S4 "4 AKV Serving System ‣ Cache Engineering for Agents").

### 3.4 Cache Operation Sequence

To provide a clear and deterministic description of cache operations, we
use a *cache operation sequence*:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
o_{1:m}=(o_{1},\ldots,o_{m}),\qquad o_{j}\in\{\operatorname{append}(x),\operatorname{drop}(P),\operatorname{repos}\}.
``` |  | (6) |

Here, $`m`$ counts operations, $`x`$ is a token, and $`P`$ contains the
active logical token indices to drop. For a fixed LLM, this sequence
determines the current cache states, starting from an empty cache.

Cache operation sequences are necessary because cache states are
history-dependent: tokens and retained positions alone do not determine
next-token probabilities. For example, in
Figure [5](#S3.F5 "Figure 5 ‣ 3.3 Cache Operations ‣ 3 Cache Engineering ‣ Cache Engineering for Agents"),
all three trajectories retain $`B`$ and $`C`$, but $`A`$’s cache is
available when computing both $`B`$ and $`C`$ in ①, only $`B`$ in ②, and
neither in ③. Thus, $`C`$’s cache states are different in all three
trajectories. Similarly, $`\operatorname{repos}`$ changes the position
encodings used by later $`\operatorname{append}`$ operations, as shown
in
Figure [8](#S4.F8 "Figure 8 ‣ 4.2.3 Reposition-aware Cache Management ‣ 4.2 Cache State Management ‣ 4 AKV Serving System ‣ Cache Engineering for Agents").
Correct cache reuse and restoration therefore require both token and
cache operation histories.

## 4 AKV Serving System

AKV follows the principle of stateless interface, stateful serving.
Agents control the cache used in subsequent attention by specifying
cache operations
(Section [4.1](#S4.SS1 "4.1 Serving Interface ‣ 4 AKV Serving System ‣ Cache Engineering for Agents")),
while the server handles physical cache reuse, eviction, and restoration
internally
(Section [4.2](#S4.SS2 "4.2 Cache State Management ‣ 4 AKV Serving System ‣ Cache Engineering for Agents")).

### 4.1 Serving Interface

|    "messages": \[ |  |
|     {"role": "user", "content": "Search ICLR"}, | $`\triangleright\ \operatorname{append}(m_{0})`$ |
|     {"role": "assistant", "content": "Searching"}, | $`\triangleright\ \operatorname{append}(m_{1})`$ |
|     {"role": "tool", "content": "ICLR is…"} | $`\triangleright\ \operatorname{append}(m_{2})`$ |

|     "drop": {"2": \[1\]}, | $`\triangleright\ \operatorname{drop}(m_{1})`$ |

operations; $`m_{i}`$ denotes message $`i`$.

The serving interface must keep each request’s output distribution
independent of physical cache residency and other requests’ cache
operations. For example, $`\operatorname{drop}`$ must affect only the
issuing request’s attention, leaving other requests’ output
distributions unchanged even when they share the same prefix cache. Each
request must also fully describe the cache states it uses, without
relying on physical cache retained from previous turns. This allows the
server to fully restore missing cache states if memory pressure causes
eviction between turns.

To meet these requirements, AKV extends the standard LLM serving API to
specify both token and cache operation histories. As shown in
Figure [7](#S4.F7 "Figure 7 ‣ 4.1 Serving Interface ‣ 4 AKV Serving System ‣ Cache Engineering for Agents"),
the existing messages field provides the full logical token sequence,
while the optional cache field specifies $`\operatorname{drop}`$ and
$`\operatorname{repos}`$ operation sequence using an operate-after
grammar. Note that all entries in messages implicitly specify
$`\operatorname{append}`$ operations. Each key in drop identifies the
message index after which to apply the operation; its value lists the
message indices whose cache is dropped. The reposition field lists the
message indices after which to apply $`\operatorname{repos}`$. Message
indices are zero-based, and $`\operatorname{drop}`$ precedes
$`\operatorname{repos}`$ when both occur at the same message boundary.
For multi-round agent workloads, clients extend the message and cache
operation histories after each round, following the standard LLM serving
workflow.

### 4.2 Cache State Management

#### 4.2.1 Design Objectives and Challenges

AKV aims to preserve three key properties of conventional LLM serving
systems: (1) reusing cached states if and only if they are equivalent to
the required states, (2) evicting unused cache states without
compromising request isolation, and (3) restoring evicted cache states
within one prefill pass.

Serving systems face three corresponding challenges in preserving these
properties when supporting cache engineering: (1) Token prefixes alone
no longer determine cache states, so ordinary prefix matching can
incorrectly reuse states from different cache operation histories
(Figure [5](#S3.F5 "Figure 5 ‣ 3.3 Cache Operations ‣ 3 Cache Engineering ‣ Cache Engineering for Agents")(b)).
(2) KV cache dropped by one request may still be needed by another, so
evicting it without accounting for other requests can cause unnecessary
recomputation or violate request isolation. (3) Ordinary causal prefill
cannot reproduce cache states resulting from drops and repositions,
while replaying the operation history requires multiple forward passes.
AKV addresses these three challenges with an extended radix tree,
drop-aware eviction, and segment-batch attention, respectively.

#### 4.2.2 Drop-aware Cache Management

Reuse with drop nodes. AKV extends radix-tree prefix matching with drop
nodes. When a request invokes $`\operatorname{drop}`$, AKV inserts a
drop node $`\Delta`$ at the trigger point along the request’s path,
recording the logical token indices whose cache is dropped. Because
$`\operatorname{drop}`$ leaves retained states unchanged but affects
subsequent attention computation, this placement preserves prefix
sharing while distinguishing later states. Prefix matching on the
extended radix tree reuses cache along matched token and operation
prefixes. In
Figure [5](#S3.F5 "Figure 5 ‣ 3.3 Cache Operations ‣ 3 Cache Engineering ‣ Cache Engineering for Agents")(c),
trajectories ① and ② share the $`A`$–$`B`$ prefix but keep distinct
$`C`$ states because they drop $`A`$ at different points, while
trajectory ③ follows a separate branch. When processing $`D`$, each
trajectory directly reuses its corresponding $`B`$ and $`C`$ caches.

Evict with drop-awareness. AKV uses drop information to reclaim unused
cache before requests finish. A cache entry becomes evictable only when
no ongoing computation or restoration needs it. For example, in
Figure [5](#S3.F5 "Figure 5 ‣ 3.3 Cache Operations ‣ 3 Cache Engineering ‣ Cache Engineering for Agents"),
$`A`$’s cache can be freed once both requests ① and ② drop it, even as
they continue generating $`D`$. Eviction frees the physical storage but
leaves the tree node as an empty placeholder, keeping cached descendants
accessible through prefix matching. Among evictable cache entries, AKV
prioritizes evicting dropped cache over cache from completed requests,
since the latter is more likely to be reused in the next round.

Restore with segment-batch attention. AKV uses *segment-batch attention*
to restore missing cache states in a single prefill pass. At each layer,
queries are split at drop trigger points, and each segment attends
causally to its own tokens and to active cache from earlier segments.
Note that dropped cache is excluded from later segments but remains
available to earlier segments that originally used it, as shown in
Figure [10](#A1.F10 "Figure 10 ‣ A.1.1 Restore with Segment-batch Attention ‣ A.1 AKV System Design Details ‣ Appendix A Appendix ‣ Cache Engineering for Agents").
Only attention is segmented, while the FFN processes the full sequence
as one batch. This avoids repeating FFN weight reads, a major source of
memory traffic, for each segment.

#### 4.2.3 Reposition-aware Cache Management

While $`\operatorname{drop}`$ leaves retained cache unchanged,
$`\operatorname{repos}`$ efficiently modifies its keys’ position
encodings. Different requests may therefore need the same cache with
different position encodings. Restoration must also reproduce the
encodings used at each stage of computation.

Figure 8: $`\operatorname{repos}`$ in the KV pool and radix tree. (a)
Two requests share A and B; Request 2 drops A before appending C. (b) B
and C initially occupy positions 1 and 2. (c) $`\operatorname{repos}`$
creates copies at positions 0 and 1 by re-encoding K and copying V. The
original B remains shared with Request 1, while the original C becomes
evictable. The tree branches at B to distinguish positional versions and
records a reposition node after C. Labels $`p`$ denote position $`p`$.

Reuse with key rotation. AKV reuses cache after $`\operatorname{repos}`$
by copying cached states and rotating keys, without recomputing hidden
states. In
Figure [8](#S4.F8 "Figure 8 ‣ 4.2.3 Reposition-aware Cache Management ‣ 4.2 Cache State Management ‣ 4 AKV Serving System ‣ Cache Engineering for Agents")(c),
request 2 copies $`B`$ and $`C`$ from positions 1 and 2 to positions 0
and 1, while request 1 continues using the original $`B`$. In the radix
tree, these copies form a new branch with updated position indices and a
reposition node after $`C`$. Prefix matching checks both token and
operation histories: matching position indices allow direct reuse, while
differing indices require key rotation.
Appendix [A.1.2](#A1.SS1.SSS2 "A.1.2 Reposition Scheme ‣ A.1 AKV System Design Details ‣ Appendix A Appendix ‣ Cache Engineering for Agents")
explains why reposition nodes are necessary and details the matching
rules and position transformations.

Evict positional versions independently. AKV evicts each position
encoding versions independently, when it is no longer in use by any
ongoing computation or restoration. For example, in
Figure [8](#S4.F8 "Figure 8 ‣ 4.2.3 Reposition-aware Cache Management ‣ 4.2 Cache State Management ‣ 4 AKV Serving System ‣ Cache Engineering for Agents")(c),
the original $`B`$ remains in use by Request 1, while the original $`C`$
becomes evictable.

Restore with temporary KV versions. AKV extends segment-batch attention
so each segment uses the position encodings from its original
computation. Queries are also split at $`\operatorname{repos}`$ trigger
points. At each layer, AKV rotates keys and copies values to create
temporary KV versions for segments that require different positions,
which we detail in
Appendix [A.1.1](#A1.SS1.SSS1 "A.1.1 Restore with Segment-batch Attention ‣ A.1 AKV System Design Details ‣ Appendix A Appendix ‣ Cache Engineering for Agents").

### 5.1 Setup

Baselines. We compare AKV with two context engineering baselines that
summarize accumulated history, following common practice in agent
harnesses ([Anthropic, n.d.](#bib.bib24); [OpenAI, n.d.](#bib.bib23)).
Standard uses a higher, model-specific summarization threshold: 96K
tokens for GPT-OSS-120B and MiniMax-M2.7, and 192K tokens for
MiroThinker-1.7-Mini. Text Engineering uses the same summarization
policy with a lower threshold of 48K tokens across all models. For AKV,
we use a tool-response rolling-drop policy that retains the KV states of
the latest 12 tool responses. Its $`\operatorname{repos}`$ threshold
matches Standard’s summarization threshold for each model.

Models and benchmarks. We evaluate AKV across MiniMax-M2.7 ([Chen et
al., 2026a](#bib.bib47)), GPT-OSS-120B ([Agarwal et al.,
2025](#bib.bib48)), and MiroThinker-1.7-Mini ([Team et al.,
2026](#bib.bib46)) LLMs. GPT-OSS-120B is evaluated with high reasoning
effort, while MiniMax-M2.7 and MiroThinker-1.7-Mini are evaluated in
thinking mode. The benchmarks cover various long-horizon agentic tasks,
including BrowseComp-Plus ([Chen et al., 2025](#bib.bib29)) (BCP),
xbench-DeepSearch-2510 ([xbench, 2025](#bib.bib32)) (xbench-DS), and the
text-only 103-task validation subset of GAIA ([Mialon et al.,
2023](#bib.bib30)) (GAIA-Text) for deep research, and
SWE-Verified ([OpenAI, 2024](#bib.bib31)) for software engineering.
Benchmark setup details are provided in
Appendix [A.2.1](#A1.SS2.SSS1 "A.2.1 Evaluation Configurations ‣ A.2 Experimental Details ‣ Appendix A Appendix ‣ Cache Engineering for Agents").

Metrics. We report success rate and mean per-task API cost for the main
agent and its context-summary calls, in US cents unless otherwise
specified. Costs are computed from active input and generated output
tokens using Groq’s rates ([Groq, n.d.](#bib.bib50)) for GPT-OSS-120B
and MiniMax’s official rates for MiniMax-M2.7. For MiroThinker-1.7-Mini,
we use the official rates of its base model, Qwen3-30B-A3B ([Yang et
al., 2025](#bib.bib51)). Detailed token prices are listed in
Table [6](#A1.T6 "Table 6 ‣ A.3 API Cost Accounting for Experiment ‣ Appendix A Appendix ‣ Cache Engineering for Agents").
We additionally charge each token $`\operatorname{repos}`$ by AKV at the
cache-hit rate, deliberately overestimating the cost of key rotation for
a conservative comparison. For serving efficiency, we report request
latency, time to first token (TTFT), and time per output token (TPOT),
together with input and output throughput.

Serving configuration. Baselines run on SGLang ([Zheng et al.,
2024](#bib.bib20)), which is also the base serving system of AKV.
Serving experiments use eight NVIDIA A800-80GB GPUs: four for prefill
and four for decode, with tensor parallelism of four. Since A800 GPU
lacks native MXFP4 support, all LLM weights are set to BF16. Further
details are in
Appendix [A.1.3](#A1.SS1.SSS3 "A.1.3 Serving Configuration ‣ A.1 AKV System Design Details ‣ Appendix A Appendix ‣ Cache Engineering for Agents").

## 6 Conclusion

We introduce cache engineering, enabling agents to directly manage
active KV states while reusing retained caches without recomputation. We
co-design the AKV serving system to support cache engineering through a
stateless interface, an extended radix tree, and segment-batch attention
for efficient cache reuse, eviction, and restoration. Across agent
benchmarks, cache engineering improves average task performance while
reducing inference costs, with AKV translating these efficiency gains
into higher serving throughput and lower latency.

Limitations. Further exploration of cache engineering strategies,
training agents under this scheme, and extending serving support to
linear attention models remain future work.

### A.1 AKV System Design Details

#### A.1.1 Restore with Segment-batch Attention

Segmentation. Building on
Sections [4.2.2](#S4.SS2.SSS2 "4.2.2 Drop-aware Cache Management ‣ 4.2 Cache State Management ‣ 4 AKV Serving System ‣ Cache Engineering for Agents")
and [4.2.3](#S4.SS2.SSS3 "4.2.3 Reposition-aware Cache Management ‣ 4.2 Cache State Management ‣ 4 AKV Serving System ‣ Cache Engineering for Agents"),
AKV restores missing KV states by partitioning queries whenever a
$`\operatorname{drop}`$ or $`\operatorname{repos}`$ operation changes
the visible history or its position mapping. Each segment selects the
corresponding KV pages and applies standard causal attention, encoding
historical visibility without constructing a dense custom mask.

Figure 10: Restore with segment-batch attention. The request in (a)
produces the four attention segments in (b). Numbers denote query/key
positions; colored cells indicate allowed attention.

Example.
Figure [10](#A1.F10 "Figure 10 ‣ A.1.1 Restore with Segment-batch Attention ‣ A.1 AKV System Design Details ‣ Appendix A Appendix ‣ Cache Engineering for Agents")
illustrates a complete restoration, treating each letter as one token
and writing $`X_{p}`$ for token $`X`$ at position $`p`$. Segment 1
computes $`A_{0},B_{1},C_{2}`$ with causal attention. After dropping
$`B`$ and repositioning, Segment 2 computes $`D_{2}`$ using keys
$`(A_{0},C_{1},D_{2})`$. Dropping $`D`$ starts Segment 3: $`E_{3}`$
attends to $`(A_{0},C_{1},E_{3})`$. Although Segments 2 and 3 share a
position mapping, they require separate KV views because $`D`$ is no
longer visible to $`E`$; $`\operatorname{drop}`$ alone does not compact
positions. The second $`\operatorname{repos}`$ moves $`E`$ from position
3 to 2, so Segment 4 computes $`F_{3}`$ using
$`(A_{0},C_{1},E_{2},F_{3})`$.

Batched restoration. Within each layer, AKV writes the newly computed KV
states and constructs the additional position versions, such as
$`C_{1}`$ and $`E_{2}`$, by re-encoding K and copying V. The
segment-specific page lists and query ranges are then submitted together
to batched attention. Thus, all four segments execute within a single
model forward pass, without recomputing hidden states for each position
version or replaying separate forward passes at operation boundaries.

#### A.1.2 Reposition Scheme

Design objective. Reposition-aware cache management must distinguish
positional versions while reusing their shared computational states. We
therefore first identify directly reusable caches via exact matching,
then use retrigger matching to find prefixes that are reusable via
positional transformation, avoiding unnecessary hidden-state
recomputation.

Token-node representation. Each token node is represented as $`T(x,p)`$,
where $`x`$ is the token ID and $`p`$ is the position currently encoded
in its cached K. The position label describes the stored cache, not
necessarily the position at which the token was originally computed. For
example, $`C`$ is initially computed at position 2 in all three
trajectories in
Figure [11](#A1.F11 "Figure 11 ‣ A.1.2 Reposition Scheme ‣ A.1 AKV System Design Details ‣ Appendix A Appendix ‣ Cache Engineering for Agents").
After $`\operatorname{repos}`$, trajectories 1 and 3 use $`(C,0)`$,
while trajectory 2 uses $`(C,1)`$. Operation nodes along the path
preserve the operation history that governs computation.

Why position labels and reposition nodes are needed.

Position labels distinguish cache representations that cannot be used
interchangeably. For example, $`C`$ has the same original computation
history in trajectories 1 and 2, but is repositioned to 0 and 1,
respectively. Its K encodings therefore differ and require positional
transformation before reuse.

Reposition nodes distinguish states that share final positions but arise
from different computations. Trajectories 1 and 3 both drop $`B`$ after
$`ABC`$, but trajectory 3 executes $`R_{C}`$ before computing $`D`$.
When $`D`$ is computed, the positions of $`A`$, $`C`$, and $`D`$ are
respectively $`(0,2,3)`$ and $`(0,1,2)`$. The relative distance between
$`D`$ and $`A`$ changes, while that between $`D`$ and $`C`$ remains
unchanged, potentially producing different hidden states and KV entries
for $`D`$. Both trajectories subsequently drop $`A`$ and execute
$`R_{D}`$ to move $`C`$ and $`D`$ to positions 0 and 1. This later
transformation cannot erase the computational difference already
established in $`D`$. The path must therefore retain $`R_{C}`$ before
$`D`$ to prevent incorrect reuse of $`D`$ and subsequent cached states.

Exact and retrigger matching. Exact matching compares all token-node
fields:

|  |  |  |
|----|----|----|
|  |
``` math
T(x,p)\equiv T(x^{\prime},p^{\prime})\iff x=x^{\prime}\land p=p^{\prime},
``` |  |

and requires identical operation nodes and their parameters. Retrigger
matching ignores only stored position encoding indices while preserving
all operation records:

|     |                                                                  |     |
|-----|------------------------------------------------------------------|-----|
|     |
       ``` math
       \phi(T(x,p))=T(x),\qquad\phi(\Delta P)=\Delta P,\qquad\phi(R)=R.
       ```                                                               |     |

Two prefixes are history-compatible if their projections are identical.

The system initializes the result with the longest valid exact prefix,
then searches compatible branches from the root. A candidate replaces
the current result only if it is valid and matches a strictly longer
prefix, preserving exact matches in a tie. Retrigger matching stops at
the first token or operation mismatch. Selected source caches are copied
and positionally transformed as needed before use.

Correctness of retrigger matching. Under fixed model and position
encoding configurations and exact arithmetic, identical projected
prefixes preserve the token and operation history preceding each token’s
original computation. They therefore produce the same hidden states and
unrotated KV content. $`\operatorname{Repos}`$ operations applied
afterward change only K’s positional representation, allowing a source
version $`s`$ to be transformed into a target version $`t`$ as

|     |                                                      |     |
|-----|------------------------------------------------------|-----|
|     |
       ``` math
       K_{t}=R(p_{t})R(p_{s})^{-1}K_{s},\qquad V_{t}=V_{s},
       ```                                                   |     |

without recomputing hidden states.

Preserving operation nodes prevents this transformation from crossing a
divergence in computational history. For example, trajectories 1 and 3
disagree at $`R_{C}`$ before $`D`$, so retrigger matching cannot reuse
$`D`$ across them. Finite-precision transformations may introduce
rounding error; this correctness argument does not require bitwise
equivalence to recomputation.

#### A.1.4 Workload Replay and Evaluation Protocol

Task selection. To emulate realistic long-horizon agent workloads with
substantial accumulated context, we select the 80 SWE-bench Verified
tasks with the largest context lengths in trajectories, without any
summary operation. These tasks reflect the difficulty of tasks in
long-context reasoning. We rank tasks by this peak length and shuffle
the selected tasks with a fixed seed. All methods use the same tasks and
ordering. Each method replays trajectories collected under its own
context/cache engineering policy, so the number of turns and the output
budgets may differ between methods.

Trajectory replay. For each turn, we reconstruct the output token budget
from the complete recorded message history, including reasoning and
tool-call content, after subtracting the generation prefix already
present in the input. We use temperature 0 and ignore_eos=True to
generate the prescribed number of tokens. The newly generated assistant
response is retained in the history for subsequent turns, while tool
responses are replayed from the recorded trajectory rather than
re-executing the tools. Recorded terminal inputs without an available
assistant response are excluded from replay.

Concurrency and measurement windows. We maintain $`C`$ client task
concurrency and execute turns sequentially within each task. The
task-count target for each measurement window is $`\max(3\times C,30)`$;
measurements include requests from supplemental tasks used to maintain
concurrency. For AKV at $`C\in\{14,16\}`$, we truncate the archived runs
at the completion of the first 30 tasks in completion order, counting
all requests within the resulting window rather than only requests from
those 30 completed tasks. For Standard at large concurrency, KV cache
capacity pressure causes repeated prefill, resulting in severe serving
degradation. We therefore report these two runs over a fixed one-hour
window, with some requests still unfinished at the cutoff.

### A.2 Experimental Details

#### A.2.1 Evaluation Configurations

Evaluation harnesses. We adapt the official BrowseComp-Plus harness,
mini-SWE-agent ([Yang et al., 2024](#bib.bib33)), the browser-agent
scaffold from observation-masking ([Zhang et al., 2026](#bib.bib37)),
and WebExplorer’s evaluation harness ([Liu et al., 2025a](#bib.bib34))
for BCP, SWE-bench Verified, GAIA-Text, and xbench-DeepSearch-2510,
respectively.

Retrieval and webpage reading. BCP evaluation follows the official task
prompts and uses Qwen3-Embedding-8B ([Zhang et al., 2025](#bib.bib35))
to retrieve documents from the benchmark’s fixed corpus. All models and
methods have access to both search and the official optional
get_document tool, which returns the full text of a selected document.
For xbench-DeepSearch-2510, we use GLM-5.2 ([Z.ai, 2026](#bib.bib36)) to
extract information from webpages in response to the agent’s queries.

Answer grading. We use GLM-5.2 as the answer judge for all three
question-answering benchmarks. The grading prompts follow the official
BCP implementation for BCP, observation-masking for GAIA-Text, and
WebExplorer for xbench-DeepSearch-2510. For SWE-bench Verified,
submitted patches are evaluated using the official test scripts and
grading functions; no LLM judge is used.

Agent step limits. The agent step limits are 100 for BCP, 250 for
SWE-bench Verified, 200 for GAIA-Text, and 100 for
xbench-DeepSearch-2510.

#### A.2.2 Context Engineering Baseline Details

Our context engineering baselines adopt Pi’s summarization prompts,
conversation serialization, cut-point selection, and summary-generation
budgets ([earendil-works, 2026](#bib.bib25)), with reserveTokens=16,384
and keepRecentTokens=20,000 across experimental groups. Summarization
uses the agent’s model and reasoning settings, replacing older dialogue
with a summary while preserving system and developer instructions and
the selected recent messages.

Unlike Pi’s native trigger based on the context window minus the
reserve-token budget, we trigger compaction when the exact prompt token
count reaches the threshold specified in
Section [5.1](#S5.SS1 "5.1 Setup ‣ 5 Experiment ‣ Cache Engineering for Agents").
We also reject empty summaries and handle summarization failures
according to the benchmark error protocol without retry.

Pi defines four prompt templates: a shared system prompt, an
initial-summary prompt, an update-summary prompt, and a turn-prefix
prompt. For brevity, we reproduce the shared system and turn-prefix
prompts below. The turn-prefix prompt is appended to the serialized
history in the summary request’s user message.

#### A.4.1 Speedup Breakdown

AKV accelerates decoding primarily by reducing full-attention time. As
shown in

at the same batch size, AKV reduces full-attention time by 59.8% and
total decode-step time by 16.0% relative to Standard. Dropping older
tool-response KV shortens the active context, so subsequent decode steps
load less KV data from GPU memory and perform fewer attention
computations.

Cost breakdown. AKV lowers costs by reducing cache reads and repeated
prefill. As shown in
Figure [14](#A1.F14 "Figure 14 ‣ A.4.2 Cost Breakdown and Active Context Length ‣ A.4 Additional Experiment Results ‣ Appendix A Appendix ‣ Cache Engineering for Agents"),
dropping older tool-response KV reduces the amount of cached history
read by subsequent requests, lowering cache-read costs by approximately
17% relative to Standard. Compared with Text Engineering, AKV reuses
retained KV directly without the re-prefill required when summarization
rewrites the history. This reduces re-prefill computation and lowers
cache-miss input costs by approximately 48%.

Active context length.
Figure [14](#A1.F14 "Figure 14 ‣ A.4.2 Cost Breakdown and Active Context Length ‣ A.4 Additional Experiment Results ‣ Appendix A Appendix ‣ Cache Engineering for Agents")
shows how AKV slows the growth of active context. Once tool responses
exceed the retention budget of $`K`$ rounds, AKV continually drops older
tool-response KV while retaining the most recent $`K`$ rounds and
reasoning KV. The active context therefore continues to grow as
reasoning accumulates, but at a substantially slower rate. In contrast,
Standard accumulates history until summarization triggers a sharp
reduction in context length.

#### A.4.3 Attention Across Message History

![Refer to caption](2610.28577v1/bcp_attention_request37_mean10.png)

per token by layer and message index averaged over 10 selected

To explain why our tool-response rolling-drop policy prioritizes
dropping older tool-response KV entries, we analyze the attention
allocated to different types of historical messages.
Figure [15](#A1.F15 "Figure 15 ‣ A.4.3 Attention Across Message History ‣ A.4 Additional Experiment Results ‣ Appendix A Appendix ‣ Cache Engineering for Agents")
shows attention per token across layers averaged over 10 BrowseComp-Plus
trajectories. Older tool responses receive less attention than older
reasoning in most displayed layers, while recent history generally
receives more attention. This pattern suggests that direct attention to
historical messages depends on both recency and message type, providing
empirical support for retaining recent tool responses and reasoning
while preferentially dropping older tool-response KV entries. Together
with the task performance and cost results reported earlier, this
observation helps explain how AKV reduces KV-cache access while
maintaining task performance.

Compatibility with Harness. To assess whether AKV improves an existing
harness, we integrate it with Pi ([earendil-works, 2026](#bib.bib25))
and evaluate the combination on BCP. For both GPT-OSS-120B and
GPT-OSS-20B, adding AKV improves accuracy by 3% over the native Pi
harness without compaction and 4% over the Pi harness with compaction.

### A.5 Additional Related Works

Concurrent works. Concurrent work adapts KV eviction to the changing
attention needs of agent trajectories. AgentKV ([Liu et al.,
2026a](#bib.bib17)) scores KV entries using query buffers from different
execution phases, retaining information that recency-based scoring can
miss. IntentKV ([Li et al., 2026](#bib.bib18)) combines cross-turn query
memory with learned importance estimates to preserve useful history
under limited KV budgets. SideQuest ([Kariyappa and Suh,
2026](#bib.bib19)) explores model-directed retention through an
auxiliary reasoning branch that identifies stale tool results and issues
cache-deletion commands, but its current strategy is limited to tool
responses, and its serving integration is tailored to this specific
eviction workflow. Context Language Models (CLMs) ([Shao et al.,
2026](#bib.bib49)) primarily study model-driven context management,
treating the live context as an editable file and learning how to
maintain it. CLM also introduces Suffix Cache Reuse to preserve
unchanged downstream KV states after text edits. Its serving support
centers on session-local reuse: relocated states remain in private
buffers outside the shared radix cache, without a unified mechanism for
indexing, managing, and recovering these history-dependent states. AKV
addresses these serving concerns directly by exposing policy-independent
cache operations through a stateless interface and uses an extended
radix tree to track both tokens and cache operation histories,
integrating retained states into shared cache reuse, memory management,
and recovery.
