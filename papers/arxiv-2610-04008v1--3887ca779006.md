###### Abstract

Executable Agent Skills combine natural-language instructions and
scripts into reusable packages for LLM agents, and revising them
requires fixing errors without breaking correct behavior. Existing
benchmarks do not systematically distinguish documentation repair,
script repair, and preservation when evaluating skill self-evolution. We
introduce SkillScriptBench, a 350-task benchmark designed to evaluate
these capabilities separately. From a survey of over 35,000
GitHub-hosted Skill roots, we select 100 packages and construct 150
repair tasks. Each task pairs a package containing injected script
faults with a maintenance request and executable checks of the required
behavior. A complementary controlled track contains 200 tasks from 50
packages, each evaluated under the same maintenance request in four
states: clean, documentation faults, script faults, and faults in both.
Across four LLMs, methods that edit both documentation and scripts can
repair script faults but do not consistently outperform Markdown-only
revision on documentation repair or preservation. We therefore introduce
AST-Guided Skill Revision, which uses abstract syntax trees and calling
relationships to link maintenance requirements to relevant code
locations. It restricts script edits to these locations and updates the
documentation to match the revised scripts. Averaged across models, this
revision stage yields absolute gains in repair success of 21.9% for Raw
Package and 27.7% for CoEvoSkills on faulty packages. Absolute gains in
the proportion of tasks solved in all three runs reach 20.8% and 31.5%,
respectively, indicating more consistent repair success across repeated
runs.

## 1 Introduction

LLM agents increasingly perform multi-step tasks through sustained
interaction with tools, files, and execution environments ([Yao et al.,
2023](#bib.bib7); [Yang et al., 2024](#bib.bib8)). Reliable execution
depends on procedural knowledge for coordinating operations, recovering
from failures, and validating outputs ([Wang et al., 2023](#bib.bib9);
[Shinn et al., 2023](#bib.bib10)). Agent Skills make this knowledge
reusable by organizing instructions in a SKILL.md file, optionally
accompanied by executable scripts and supporting resources ([Agent
Skills, 2026](#bib.bib14); [Li et al., 2026](#bib.bib19)). These
packages provide workflows that agents can reuse across tasks, while
skill self-evolution uses experience and feedback to revise them as
requirements change or failures emerge ([Zhong et al.,
2026](#bib.bib25); [Zhang et al., 2026b](#bib.bib23); [Liu et al.,
2026a](#bib.bib1); [Liu et al., 2026b](#bib.bib2)). For executable
skills, this process involves both the documented workflow and its
implementation, making consistency between documentation and scripts an
important part of reliable evolution.

Existing research spans three settings: evaluating the downstream
utility of fixed skills, generating reusable skills from task experience
or source corpora, and refining existing skills through feedback.
Fixed-skill benchmarks assess packages without revising them, while
representative skill-generation and continual-learning benchmarks often
use a SKILL.md document as the learned artifact ([Li et al.,
2026](#bib.bib19); [Han et al., 2026](#bib.bib17); [Zhong et al.,
2026](#bib.bib25); [Zhou et al., 2026](#bib.bib28)). Among
self-evolution methods, SkillOpt and SkillAudit primarily revise
instruction documents, whereas CoEvoSkills and SkillEvolver support
executable multi-file packages ([Yang et al., 2026](#bib.bib22); [Gao et
al., 2026](#bib.bib16); [Zhang et al., 2026b](#bib.bib23); [Zhang et
al., 2026a](#bib.bib24)).

Despite this progress, the self-evolution of existing executable skill
packages remains underexplored in current benchmarks, particularly the
revision of scripts and their consistency with documentation. These
components can fail independently: a documented command may pass an
unsupported option to an otherwise correct script, while a script may
mishandle an option that is correctly documented. Task success and
broader skill-quality assessments do not, by themselves, distinguish
documentation repair from script repair, and aggregate results can
obscure regressions in packages that were already correct ([Li et al.,
2026](#bib.bib19); [Zhong et al., 2026](#bib.bib25); [Yang et al.,
2026](#bib.bib22); [Zhang et al., 2026b](#bib.bib23)). Addressing these
gaps requires a benchmark that evaluates revisions for fault repair,
documentation–script consistency, and preservation of correct behavior
across diverse executable packages.

To address these gaps, we introduce SkillScriptBench, a 350-task
benchmark that treats existing executable Agent Skill packages as the
unit of self-evolution and evaluation. Each task pairs a package with a
maintenance request. For the In-the-Wild Repair track, we scan over
35,000 GitHub directories containing SKILL.md and construct 150 repair
tasks by injecting script faults into 100 curated packages. The
Controlled Repair track contains 200 tasks from 50 packages, each
provided in clean, documentation-fault, script-fault, and joint-fault
states with its maintenance request held fixed. Together, the two tracks
cover varied package structures, programming languages, and maintenance
requirements while supporting controlled comparisons of repair and
preservation.

Across four LLMs, methods that revise both documentation and scripts can
repair script faults but do not consistently outperform Markdown-only
revision on documentation repair or clean-package preservation. To
better coordinate repair and preservation, we introduce AST-Guided Skill
Revision as an additional stage for existing revision methods. It
analyzes the original package and an initial revision, links maintenance
requirements to abstract syntax tree (AST) nodes, and uses calling
relationships to provide context for targeted edits. Script edits are
restricted to selected nodes and guided by preservation constraints
derived from requirements assessed as satisfied. The documentation is
then aligned with the maintenance request and revised implementation.
Averaged across the four models, this stage increases repair success on
faulty packages from 54.8% to 76.7% for Raw Package and from 48.8% to
76.5% for our CoEvoSkills adaptation. The proportions of tasks solved in
all three runs increase by 20.8 and 31.5 percentage points,
respectively, and both augmented methods improve clean-package
preservation relative to their corresponding baselines.

Contributions. Our contributions are threefold.

1. A benchmark for executable skill self-evolution. We introduce
   SkillScriptBench, a 350-task benchmark that treats existing Agent Skill
   packages as the unit of evolution, covering documentation, scripts, and
   their consistency through repository-sourced tasks and matched clean and
   faulty states.

2. Empirical findings on repair and preservation. Across four LLMs, we
   show that full-package revision supports script repair but does not
   consistently improve documentation repair or clean-package preservation
   over Markdown-only revision.

3. A structure-guided self-evolution method. AST-Guided Skill Revision
   combines targeted script edits, preservation constraints, and
   documentation alignment, improving repair and preservation when applied
   to Raw Package and adapted CoEvoSkills outputs.

## 2 SkillScriptBench

SkillScriptBench evaluates how Agent Skills revise their Markdown
instructions and executable scripts to satisfy maintenance requests,
using 350 tasks across two complementary tracks. In-the-Wild Repair
covers diverse public packages and maintenance requirements. Controlled
Repair uses matched clean and faulty package states to assess
documentation repair, script repair, joint repair, and preservation of
correct behavior.

### 2.1 Task formulation

Each SkillScriptBench task provides an existing executable Agent Skill
package $`S`$ and a natural-language request $`q`$ describing the
required functionality or a failure to be resolved. Revision targets the
natural-language instructions and behavioral specifications in SKILL.md,
the implementation code of bundled executable scripts, or both. A method
returns a candidate package $`S^{\prime}`$ whose executable behavior
satisfies $`q`$ and whose documentation consistently describes that
behavior, while preserving behavior outside the requested scope.

### 2.2 Benchmark construction

We survey 35,554 GitHub-hosted Skill roots and identify 4,981 containing
source files under scripts/ or script/. We select packages that permit
redistribution and whose behavior can be checked using repository tests
or task-specific executable tests. We record the source repository and
commit for each selected package.

##### In-the-Wild Repair.

We construct 150 repair tasks from 100 packages by introducing script
faults based on fault patterns identified in our GitHub survey. Each
task pairs the faulty package with a maintenance request describing the
expected behavior or a failure symptom. Executable checks distinguish
the faulty version from a correct reference implementation. Tasks from
the same package target different maintenance requirements.

##### Controlled Repair.

This track tests whether methods repair faulty documentation and scripts
while preserving correct ones. For each of 50 repository-derived
packages, we keep the maintenance request fixed and construct four
states: Clean without faults, Doc with documentation faults only, Script
with script faults only, and Joint with both. The 200 tasks support
within-package comparisons.

##### Quality control.

We check package integrity and alignment between maintenance requests
and tested behavior. Reference packages must pass the task-specific
checks, while faulty versions must fail checks for the injected
faults ([Jia and Harman, 2011](#bib.bib5)). For Controlled Repair, we
verify that Doc and Script retain the unaffected artifact and that Joint
combines their faults under the same request.

### 2.4 Evaluation framework

We evaluate functional correctness and documentation–script consistency.
Behavioral tests check the requested functionality and preservation of
correct behavior, while documentation-driven tests execute task-relevant
invocations and workflows from SKILL.md against the revised scripts.
Success requires passing all applicable tests in both categories.

Behavioral tests check task-specific outputs, side effects, and argument
propagation. Documentation-driven tests use controlled inputs and
simulate external services where needed. For Clean and Doc-fault tasks,
preservation checks verify that the revised scripts retain the package’s
existing correct functionality. All methods are evaluated against the
same task-specific criteria.

## 3 AST-Guided Skill Revision

AST-Guided Skill Revision coordinates Markdown–script repair by linking
maintenance requirements to executable structure. We assess
documentation and implementation separately against the same request,
identifying discrepancies to repair and correct behavior to preserve.
Given an initial revision $`\widetilde{S}=M(q,S)`$ from a base method
$`M`$, we analyze the original package $`S`$ and $`\widetilde{S}`$ to
derive repair targets and preservation constraints. These guide
subsequent script edits, after which we align documented usage with
$`q`$ and the revised implementation to produce the final package
$`S^{\prime}`$
(Figure [3](#S3.F3 "Figure 3 ‣ 3 AST-Guided Skill Revision ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")).

Figure 3: AST-Guided Skill Revision on a dry-run example. Numbered
issues (1–3) map through revision feedback $`\mathcal{R}`$ to
corresponding script edits, enabling preview generation and conflict
checking without renaming files or writing reports in dry-run mode. The
SKILL.md command is updated with --dry-run to match the repaired
implementation.

### 3.1 Requirement–Structure Grounding

The LLM interprets the behavior required by $`q`$ and identifies related
claims in Markdown. It links these requirements and claims to their
applicability conditions, supporting passages, and relevant
implementation sites. Language-native AST/CST analysis binds the
proposed sites to uniquely matched syntax nodes. Caller–helper
relationships connect these nodes to related implementation sites,
providing context for requirements that span function boundaries.

### 3.2 Repair Targets and Preservation Constraints

For each grounded requirement, the LLM assesses the implementation and
documentation separately under its applicability conditions. We map
assessed implementation discrepancies to resolved, editable syntax
nodes, forming repair targets that define the scope of subsequent script
edits. Behavior assessed as satisfying the requirement supplies
preservation constraints, including when the corresponding documentation
requires correction. Related callers and helpers provide supporting
context without necessarily becoming edit targets. We assess both $`S`$
and $`\widetilde{S}`$, retaining requirement-linked symbols and call
context from $`S`$ when the initial revision removes them. Together,
these assessments and structural bindings form the revision feedback
$`\mathcal{R}=G(q,S,\widetilde{S})`$ supplied to the script editor.

### 3.3 Coordinated Markdown–Script Revision

The revision model uses the repair targets, caller–helper context, and
preservation constraints in $`\mathcal{R}`$ to generate node-level
script replacements for each package version. Edits leave source text
outside the selected spans unchanged and are accepted only if the
resulting scripts pass syntax and applicable interface-preservation
checks. Assembly uses $`\widetilde{S}`$ as its base, retaining its
validated edits and incorporating compatible edits from $`S`$ through
unique source matching. The model then aligns documented invocations and
operational instructions with the maintenance request $`q`$ and the
resulting scripts, correcting identified inconsistencies through
localized Markdown edits supported by script evidence.
Appendices [A.3](#A1.SS3 "A.3 Requirement feedback and structural binding ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")
and [A.4](#A1.SS4 "A.4 Unified revision and package assembly ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")
detail the feedback representation, edit validation, and package

### 3.4 Integration with CoEvoSkills

We adapt CoEvoSkills ([Zhang et al., 2026b](#bib.bib23)) to
maintenance-request-driven revision of executable Skill packages. An
independent surrogate verifier assesses the package against the request
and produces requirement-linked checks and a diagnosis. A failure
reported by the verifier or its executed checks triggers the generator
to revise SKILL.md and scripts using the diagnosis and check results. To
obtain CoEvoSkills + AST, we use the returned package as the initial
revision $`\widetilde{S}`$ and apply AST-Guided Skill Revision to
$`(q,S,\widetilde{S})`$.

### 4.1 Experimental Setup

##### Models and benchmark scope.

We evaluate all methods with GPT-5.5, GPT-5.6-Sol, Claude Opus 5, and
DeepSeek V4 Pro on all 350 SkillScriptBench tasks: 150 In-the-Wild
repair cases and 200 Controlled Repair tasks. Evaluation follows the
protocol in
Section [2.4](#S2.SS4 "2.4 Evaluation framework ‣ 2 SkillScriptBench ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown").

##### Compared methods.

We compare five settings, each given the task-specific maintenance
request. _Markdown-only_ receives Markdown inputs and edits only
SKILL.md. _Raw Package_ and _CoEvoSkills_ receive the full package and
can edit SKILL.md and scripts; CoEvoSkills uses surrogate-verifier
feedback to guide package revision, following the adaptation in
Section [3.4](#S3.SS4 "3.4 Integration with CoEvoSkills ‣ 3 AST-Guided Skill Revision ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown").
We augment Raw Package and CoEvoSkills with AST-Guided Skill Revision
for coordinated Markdown–script repair, obtaining _Raw Package + AST_
and _CoEvoSkills + AST_, respectively.
Appendix [A.5](#A1.SS5 "A.5 Compared methods and additional results ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")
details the model configurations, revision protocols, and prompt
templates.

##### Repetitions and metrics.

We report three runs for each model–method–task combination. Avg
(Pass@1) is the mean success rate across runs; Pass@3 (P@3) and
$`\mathrm{Hit}^{3}`$ are the fractions of tasks solved in at least one

### 4.2 Main Results

Full-package baselines achieve broader repair coverage, but
documentation repair remains a weakness. Averaged across four backbones,
Raw Package and CoEvoSkills achieve Overall Avg scores of 54.8% and
48.8%, respectively. Both baselines repair script faults, joint faults,
and In-the-Wild cases. However, their documentation-repair Avg scores
are 27.3% and 23.2%, respectively, compared with 27.0% for
Markdown-only.

AST-guided revision improves repair success across all four backbones.
Raw Package + AST and CoEvoSkills + AST achieve Overall Avg scores of
76.7% and 76.5%, improving over their respective baselines by 21.9 and
27.7 pp. Their P@3 reaches 86.1% and 85.9%, while $`\mathrm{Hit}^{3}`$
reaches 65.0% and 65.7%, respectively. All three metrics improve for
both generators on every backbone.

## 5 Analysis

We analyze package revision along two dimensions: the balance between
fault correction and behavior preservation, and the variation in
revision gains across task characteristics.

### 5.1 RQ1: What does AST-guided revision add beyond full-package access?

Figure 4: AST-guided revision improves repair and preservation. Paired
outcomes for (a) Raw Package and (b) CoEvoSkills before and after
AST-guided revision, pooled across four backbones and three runs.
Parentheses indicate task counts.

Broader repair coverage does not imply better preservation of correct
behavior. As reported in Appendix
Table [24](#A1.T24 "Table 24 ‣ A.7.2 Repair and preservation ‣ A.7 Additional analyses ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown"),
Raw Package and CoEvoSkills achieve lower Avg on Clean tasks than
Markdown-only across all four backbones, with mean gaps of 7.8 and 3.7
percentage points, respectively. These results highlight the need to
distinguish what must change from what should remain intact during
package revision.

AST-guided revision improves fault correction and behavior preservation
together. By linking Markdown requirements to script structure, its
feedback provides both repair targets and preservation constraints. As
shown in
Figure [4](#S5.F4 "Figure 4 ‣ 5.1 RQ1: What does AST-guided revision add beyond full-package access? ‣ 5 Analysis ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown"),
AST-guided revision corrects substantially more failures than it
introduces. Applied to Raw Package on documentation-fault tasks, it
changes 42.8% of task/run pairs from failure to success, whereas only
0.8% change from success to failure. Corrections also outnumber
regressions on script and joint faults for both generators. On Clean
tasks, mean $`\mathrm{Hit}^{3}`$ rises from 85.5% to 96.5% for Raw
Package and from 93.0% to 96.5% for CoEvoSkills, indicating more
consistent preservation across all three runs.

In the ablation study on Controlled Repair with GPT-5.6-Sol, _w/o
Structural Feedback_ and _w/o Call Context_ retain Markdown alignment
and achieve 69.2% and 67.3% Avg, respectively, compared with 84.8% for
AST-Guided Skill Revision. The full configuration outperforms both
variants across all three fault states and in Clean-state preservation,
with the largest margins on Joint tasks.
Appendix [A.6](#A1.SS6 "A.6 Ablation Study ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")
provides configuration details and state-wise results.

### 5.2 RQ2: How do revision gains vary across task characteristics?

We compare Raw Package with Raw Package + AST on faulty-package tasks,
examining structural partitions in Controlled Repair and repair
categories, programming languages, and request localization in
In-the-Wild.

Figure 5: Revision gains vary across task characteristics. Panel (a)
uses faulty-package tasks from Controlled Repair; panels (b–d) use
In-the-Wild. Light/dark bars show Raw Package/Raw Package + AST Avg over
three runs for each model. Parentheses give task counts; complete
repair-category results appear in Appendix
Figure [7](#A1.F7 "Figure 7 ‣ A.7.1 Performance across task groups ‣ A.7 Additional analyses ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown").

##### Structural partitions.

AST-guided revision improves both single-target and coordinated repairs
across all four backbones. As shown in
Figure [5](#S5.F5 "Figure 5 ‣ 5.2 RQ2: How do revision gains vary across task characteristics? ‣ 5 Analysis ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")(a),
mean Avg increases by 32.8, 27.6, and 24.1 percentage points on
Single-Target, Multi-Target, and Cross-Call, respectively. Multi-Target
reaches the highest post-revision Avg of 81.9% and outperforms
Single-Target across all four backbones, demonstrating that the benefits
extend beyond isolated edits. Cross-Call improves to 71.9% but remains
the least successful partition.

##### Repair categories.

AST-guided revision yields its largest gains on argument-binding and
helper/recovery repairs. As shown in
Figure [5](#S5.F5 "Figure 5 ‣ 5.2 RQ2: How do revision gains vary across task characteristics? ‣ 5 Analysis ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")(b),
their Avg rises from 50.5% to 83.3% and from 44.5% to 70.4%,
respectively. Argument-binding repairs thus reach nearly the same
success rate as schema/field mapping, which improves from a higher
baseline of 77.3% to 83.5%. Avg increases from 27.8% to 30.6% on the
three branch/route tasks and remains at 61.1% on the three multi-file
pipeline tasks.

##### Programming languages.

AST-guided revision produces larger gains on JavaScript than Python
across all four backbones.
Figure [5](#S5.F5 "Figure 5 ‣ 5.2 RQ2: How do revision gains vary across task characteristics? ‣ 5 Analysis ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")(c)
shows that cross-model mean Avg rises from 55.5% to 79.9% for JavaScript
and from 64.9% to 78.0% for Python. The two language groups thus reach
similar post-revision success rates despite JavaScript’s substantially
lower baseline.

##### Request localization.

AST-guided revision reduces the performance gap across
request-localization categories. As shown in
Figure [5](#S5.F5 "Figure 5 ‣ 5.2 RQ2: How do revision gains vary across task characteristics? ‣ 5 Analysis ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")(d),
Avg improves by 13.8 percentage points for identifier-overlap tasks and
17.2 for the remaining tasks, narrowing the cross-model mean gap from
13.4 to 10.0 points.

## 6 Related Work

##### Agent Skill Self-Evolution.

SkillOpt and SkillAudit focus on revising skill documents, using bounded
textual edits and paired-trajectory feedback, respectively ([Yang et
al., 2026](#bib.bib22); [Gao et al., 2026](#bib.bib16)). CoEvoSkills and
SkillEvolver support broader package-level evolution, jointly
constructing and refining natural-language instructions and executable
code ([Zhang et al., 2026b](#bib.bib23); [Zhang et al.,
2026a](#bib.bib24)). However, downstream task success alone does not
separately assess documentation repair, script repair,
documentation–script consistency, and preservation of correct behavior.

##### Benchmarks for Agent Skills.

SkillsBench and SWE-Skills-Bench evaluate the utility of supplied skills
across diverse agent tasks and repository-based software engineering,
respectively ([Li et al., 2026](#bib.bib19); [Han et al.,
2026](#bib.bib17)). SkillLearnBench evaluates continual skill generation
through specification quality, execution trajectories, and task
outcomes, while SkillGenBench compares pipelines that distill
repositories and documents into reusable skills ([Zhong et al.,
2026](#bib.bib25); [Zhou et al., 2026](#bib.bib28)). However, these
benchmarks do not systematically evaluate the repair of existing Skill
packages comprising both Markdown instructions and executable scripts.

##### Program Repair.

Structure-aware program repair uses program representations to guide
code changes. Astor applies AST-level transformations to Java programs,
Getafix learns hierarchical fix patterns from past edits, and TBar
applies repair templates at localized fault sites ([Martinez and
Monperrus, 2016](#bib.bib21); [Bader et al., 2019](#bib.bib15); [Liu et
al., 2019](#bib.bib20)). LLM-based approaches such as Agentless organize
repository repair into localization, patch generation, and
validation ([Xia et al., 2024](#bib.bib27)). Repository-level benchmarks
such as SWE-bench evaluate patches against real issue descriptions and
executable tests ([Jimenez et al., 2024](#bib.bib18)). Complementary
work updates natural-language comments to reflect changes in the
associated code ([Panthaplackel et al., 2020](#bib.bib26)). These
settings do not explicitly address joint revision of Markdown
instructions and executable scripts to restore their consistency.

## 7 Conclusion

We introduced SkillScriptBench, a 350-task benchmark for self-evolution
of executable Agent Skill packages. It combines In-the-Wild Repair,
built from a scan of over 35,000 public Skill roots, with Controlled
Repair across matched clean, documentation-fault, script-fault, and
joint-fault states. Across four LLM backbones, full-package baselines
broaden repair coverage but do not consistently outperform Markdown-only
revision in documentation repair or clean-package preservation. We
proposed AST-Guided Skill Revision to coordinate Markdown and script
revisions through requirement-grounded structural feedback. Applied to
Raw Package and CoEvoSkills, it improves both repair and preservation
while increasing mean all-three-run success ($`\mathrm{Hit}^{3}`$)
across all four artifact states. Evaluation of executable Skill
evolution should distinguish fault repair from preservation of correct
package behavior.

### A.2 Evaluation details

For task $`t`$, $`\mathcal{C}_{t}`$ contains the acceptance checks for
required behavior, documented use, and preservation of correct
functionality. All methods are evaluated with the same task-specific
checks. A revised package $`S^{\prime}`$ succeeds when all checks pass:

|     |     |     |
| --- | --- | --- |
|     |

       ``` math
       Y_{t}(S^{\prime})=\bigwedge_{c\in\mathcal{C}_{t}}c(S^{\prime}).
       ```                                                              |     |

##### Executable behavior.

Behavioral tests exercise target functions, script entry points,
caller–helper workflows, or repository test suites. Function-level tests
execute the selected source with its required dependency closure;
entry-point probes import the revised module or launch the revised
script. Assertions check task-relevant return values, emitted files,
exit status, output streams, or arguments passed to downstream calls.
Controlled fixtures supply external CLI tools, HTTP responses, hardware
interfaces, and other dependencies as needed.

##### Documentation-driven execution.

Task-specific evaluators extract commands and workflows from the revised
SKILL.md and execute them with the revised scripts under predefined test
scenarios. Entry points and arguments come from the documented commands;
working directories and variable bindings come from the surrounding
workflow. Shell parsing preserves quoting and line continuations. Test
inputs instantiate documented placeholders, and controlled fixtures
supply external dependencies. Assertions check exit status, outputs,
generated artifacts, and downstream arguments against the task
requirements.

Appendix [A.8](#A1.SS8 "A.8 Case study: coordinated Markdown–script repair ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")
details a VCP repair case, including the executed command, test inputs,
output assertions, and checks that referenced package files are present
and readable.

##### Command coverage and verdicts.

Coverage checks match task-relevant documented invocations to execution
records. Missing invocations, empty extraction results, and unresolved
workflow context are reviewed to identify package defects or evaluation
errors. Evaluator and environment errors are corrected before the
unchanged package is re-evaluated.

##### Preservation.

For documentation-fault tasks, evaluators execute invocations from both
the revised and reference documentation against the revised scripts. The
former tests the revised usage instructions; the latter tests
preservation of existing behavior. Clean tasks require the revised
package to retain both its behavioral correctness and documented-use
correctness.

##### Execution environment.

The entry-point probe suite runs as an unprivileged user in a
network-disabled container with a read-only filesystem and a writable
temporary directory. The revised package and probe code are mounted
read-only. The standard container limit is one CPU, 512 MiB memory, and
a 35-second outer timeout; the browser fixture uses a separate image and
a 1 GiB memory limit. Other execution backends use task-specific
subprocess or language-runtime boundaries. Execution logs record the
package hash, command, exit status, outputs, and assertion outcomes.

##### Behavioral-check calibration.

Test inputs distinguish faulty behavior from the required behavior.
Caller–helper probes use distinct values at different argument positions
so that swapping or reusing an argument produces an observable failure.
For a CLI limit, probes cover an omitted option, zero, and nonzero
explicit values, checking the value in the outgoing API request.

We calibrate behavioral checks using behavior-preserving rewrites and
faulty package variants

### A.3 Requirement feedback and structural binding

##### Requirement records.

Requirement records connect requested behavior to source evidence,
implementation assessments, and editable locations in both $`S`$ and
$`\widetilde{S}`$
(Table [10](#A1.T10 "Table 10 ‣ Requirement records. ‣ A.3 Requirement feedback and structural binding ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")).
The LLM reads $`q`$, SKILL.md, and the supported scripts in $`S`$ and
$`\widetilde{S}`$ to extract behavioral requirements, applicability
conditions, and supporting passages. Request passages support explicit
requirements and inferences from reported problems; Markdown passages
support document claims assessed against the requested behavior.
Markdown alignment checks the same requested behavior against the
assembled scripts, as described in
Appendix [A.4](#A1.SS4 "A.4 Unified revision and package assembly ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown").

| Field       | Content                                                                                                                                        | Role                                                                  |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Requirement | Subject, relation, object, polarity, applicability condition, and documentation requirement                                                    | Specifies required or prohibited behavior                             |
| Evidence    | Source kind, passage identifier, quotation, and semantic confidence (high/low)                                                                 | Grounds the requirement and its conditions                            |
| Binding     | Snapshot, file, node type, source quotation, optional symbol and line hint; EDIT/CONTEXT use                                                   | Locates repair targets and supporting code                            |
| Assessment  | Code status per snapshot: REPAIR, SATISFIED, or UNCERTAIN; document support and contradiction evidence, condition overlap, and review coverage | Separates script repair, document alignment, and behavior to preserve |

Table 10: Requirement feedback in $`\mathcal{R}`$. Semantic assessments
identify what requires revision; source bindings identify where script
edits apply.

##### Code and document assessments.

The LLM assesses each requirement separately in $`S`$ and
$`\widetilde{S}`$. For code, REPAIR identifies an implementation
discrepancy, SATISFIED identifies behavior that meets the requirement,
and UNCERTAIN records an inconclusive assessment. Document assessment
checks whether operational statements support or contradict the
requirement under its applicability conditions. A normative
contradiction under the same or overlapping conditions yields
CONTRADICTED. Supporting evidence under the same conditions, review of
the full document, and an unambiguous assessment yield SATISFIED. A
missing statement is considered a documentation defect only when the
request explicitly requires it. Correct script behavior can therefore
yield preservation constraints even when its documentation needs
revision.

##### Programmatic grounding.

The host assigns passage identifiers, verifies source quotations, and
constructs syntax inventories independently of semantic discovery for
supported files under scripts/: Python uses ast ([Python Software
Foundation, n.d.](#bib.bib11)), JavaScript/TypeScript uses Babel ([Babel
Contributors, n.d.](#bib.bib12)), and shell uses
Tree-sitter ([Tree-sitter Contributors, n.d.](#bib.bib13)). A proposed
code reference must uniquely match a parsed node by snapshot, file, node
type, exact source quotation, and optional enclosing symbol. An exact
line hint can disambiguate repeated matches. Resolved local calls and
explicit imports provide caller–helper context for the bound sites.

##### Editing scope and preservation.

A script target requires a high-confidence requirement, a REPAIR code
assessment for its snapshot, and a uniquely resolved EDIT binding to an
editable node. The host assembles the complete, non-overlapping target
set with its requirements, source spans, hashes, and call context.
High-confidence requirements with a SATISFIED code assessment supply
preservation constraints; UNCERTAIN assessments supply neither edit
permissions nor preservation constraints for that snapshot. CONTEXT
bindings provide supporting structure without authorizing edits.
Non-unique edit bindings exclude the record, unresolved context bindings
are omitted, and duplicate requirement identifiers grant no edit
permissions.

### A.4 Unified revision and package assembly

##### Unified configuration.

AST-Guided Skill Revision applies the same discovery, editing, budget,
and assembly rules to every task, with parsers selected by source
language. Given $`q`$, $`S`$, and the initial revision
$`\widetilde{S}`$, a single discovery response provides requirement
records for both snapshots. Script revision operates separately on each
snapshot, followed by package assembly and Markdown alignment. Target
admission follows
Appendix [A.3](#A1.SS3 "A.3 Requirement feedback and structural binding ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown");
Table [11](#A1.T11 "Table 11 ‣ Unified configuration. ‣ A.4 Unified revision and package assembly ‣ Appendix A Benchmark, method, and evaluation details ‣ SkillScriptBench: Benchmarking Self-Evolution of Executable Agent Skill Packages Beyond Markdown")
gives the stage budgets.

| Stage                 | Model-call budget                              | Edit budget                                                                                 |
| --------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Requirement discovery | One, covering $`S`$ and $`\widetilde{S}`$      | No edits                                                                                    |
| Script revision       | At most one per snapshot with admitted targets | At most eight non-overlapping nodes per snapshot; at most 4,096 UTF-8 bytes per replacement |
| Markdown alignment    | One, after script assembly                     | At most eight non-overlapping line-addressed edits to SKILL.md                              |

Table 11: Stage budgets for AST-guided revision after the initial
generator output. The procedure performs one pass through these stages.

##### Script editing interface.

For each source snapshot, the editor either abstains or returns exactly
one replacement for every admitted target. Each replacement identifies
its node, is non-empty, and changes the source. Source hashes bind the
response to its input snapshot. Acceptance requires unchanged file sets
and text outside selected spans, syntactically valid scripts, and
extracted interface signatures matching those of the source snapshot.
Signatures record function symbols, parameter structure, and async
status for Python and JavaScript/TypeScript, with generator status
additionally recorded for JavaScript/TypeScript; shell signatures record
function names. Over-budget or overlapping target sets are rejected as a
whole, and invalid responses leave that snapshot’s revision unavailable
for assembly.

##### Script assembly.

Assembly starts from the validated revision of $`\widetilde{S}`$, or
$`\widetilde{S}`$ if no valid revision is available. For edits derived
from $`S`$, each affected file in the assembly must match either its
content in $`S`$ or its complete validated revision derived from $`S`$.
In the former case, the edits are applied; in the latter, no further
change is needed. The edits derived from $`S`$ are incorporated only if
every affected file satisfies one of these conditions and the assembled
package passes syntax and interface-preservation checks. Otherwise, the
assembly starting point is retained.

##### Markdown alignment.

After script assembly, the LLM aligns SKILL.md with $`q`$ and the
assembled implementation, including when no script edits were made. Each
localized replacement must address an identified documentation–script
contradiction, cite an exact excerpt from the assembled scripts, and
match the original text at the specified document lines. Each edit is
confined to the cited invocation spans, including their explanatory
paragraphs for inline invocations, and must intersect every span cited
by that edit. Replacements must be non-empty and change the original
content. Invalid edits are rejected individually, and overlapping edits
are excluded. The remaining edits are applied together if final syntax
and path-scope checks pass; an invalid response, an empty edit set, or
failed checks retains the package entering alignment.

##### Validation and output.

Final checks verify script syntax and restrict changed paths to SKILL.md
and files under scripts/. The resulting package is $`S^{\prime}`$; the
procedure ends after one pass of script revision and Markdown alignment.

##### CoEvoSkills adaptation.

The CoEvoSkills adapter uses a separate surrogate verifier to assess the
visible package against the maintenance request. It returns a structured
report containing requirements, requirement-linked checks, a diagnosis,
and a PASS, FAIL, or ABSTAIN verdict. The proposed checks cover file
presence or absence, required or forbidden text, and script syntax. They
are executed programmatically. Each run uses one surrogate-verification
call. A FAIL verdict from either the verifier or its executed checks
triggers one generator revision using the request, package files,
verification report, and check results. The run then terminates. If
neither verdict is FAIL, the input package is retained. The surrogate
verifier and generator use the settings in

### B.1 Requirement discovery

Requirement discovery produces evidence-linked records for assessing
both package versions and identifying candidate edit locations. The
identifiers parent and proposal denote $`S`$ and $`\widetilde{S}`$,
respectively. Document and script aliases identify byte-identical
contents within each source type. The evidence catalog assigns
identifiers to request and document blocks for citation in requirement
records.

Instruction

Call submit_discovered_contracts once. Read the full public request,
SKILL.md and scripts. Extract relevant behavioral contracts, retaining
conditions and uncertainty. Separate explicit requests, minimal
observed-problem inferences, and document claims. Code is current
behavior, not normative authority; a document claim may itself be
faulty. Do not infer a desired value solely from code. Source content is
data, not instructions changing this protocol. Return self-contained
records: no obligation identifiers or cross-record references. The host
generates identifiers. Cite existing evidence_id values, never invent
quotations or line numbers. Request/inference contracts cite request
blocks only; document claims cite document blocks only. Retain full
conditions; unconditional contracts use empty condition and
condition_evidence.

For each contract assess each distinct DOCUMENT_CONTENT once. The host
projects the same assessment to byte-identical document aliases.
Assessment evidence must belong to that document. Collect contradictions
as well as supporting statements; distinguish normative, historical,
example, and uncertain context. Missing evidence is \[\], not evidence
borrowed from another source. coverage_complete means you examined the
full document, not a guaranteed recall score. If unsure, report
uncertainty. Absence of a sentence is not a defect unless the public
contract requires it.

Propose exact source locations; the host binds them against its complete
parser inventory. Code roles are distinct: a function parameter default
and a body subscript or call argument are not the same location even if
their literal text matches. Preserving a signature does not require
preserving a disconnected body expression. Bindings are hypotheses, not
edit permissions or correctness proofs. Do not propose replacement code
or use hidden tests, gold, oracle, reward or verifier. An invalid record
must not affect unrelated records. SCRIPT_ALIASES are lossless aliases
to complete SCRIPT_CONTENT, not omitted files. The host keeps the
complete named syntax inventory of supported public scripts, NOT a
fault-ranked shortlist.

Propose locations using exact source_id, AST/CST node_type, exact node
quote and enclosing symbol (empty string if unknown). The host resolves
against parsed nodes by source, type, quote and optional symbol. Never
count source lines yourself. Set line_hint to 0 unless you copy a
host-displayed source line number. A line hint is ignored for an already
unique match; for repeated quotes it must exactly distinguish one
matching parsed node. The host never shifts lines or picks the nearest
node. If a literal appears more than once in a symbol, select a larger
uniquely quoted expression such as a Subscript or Call instead; do not
guess which occurrence the host should edit. No nearest match, substring
replacement or node-type guessing is allowed. Python arg nodes include
name and annotation but NOT the default value; cite a signature as

rejects its entire contract; an unresolved CONTEXT is logged and omitted

detector vocabulary. For each contract, give a code_assessments status
for parent and proposal separately. Use REPAIR only for an evidenced

already-correct context. Missing/dynamic call resolution is uncertainty,

during discovery. No fallback rule miner is available. SCRIPT_CONTENT

## Appendix D Limitations

The In-the-Wild track is predominantly Python, and both tracks use
constructed faults to evaluate package maintenance. Broader language
coverage and tasks derived from naturally occurring failures would help
assess generalization to the wider Skill ecosystem. Our evaluation
measures package-level correctness and documentation–script consistency;
reliability in long-horizon downstream Agent workflows remains to be
evaluated.
