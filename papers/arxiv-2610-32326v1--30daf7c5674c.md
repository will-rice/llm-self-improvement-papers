# TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent

Junlin He,  Junzhang Zhu,  Yudong Li,  Yihong Tang, Xuefeng Jiang,  Wei
Ma,  Chengxiang Zhuo,  Zang Li Platform and Content Group, Tencent,
Shenzhen, China The Hong Kong Polytechnic University, Hong Kong, China
McGill University, Montreal, Canada   Independent Researcher, China

###### Abstract

Large Language Model (LLM) agents have enabled automated code evolution,
offering a promising paradigm for algorithm discovery. However, current
recursive self-improvement (RSI) research for sequential recommendation
faces a critical dilemma: general-purpose code evolution frameworks
possess flexible search mechanisms but lack domain-specific feedback,
whereas recommender-specific evolution frameworks utilize rich feedback
but rely on linear evolution. More critically, naively integrating them
fails when applied to Generative Recommendation (GR). Unlike traditional
end-to-end models, GR relies on a module-cascaded training pipeline
(i.e., tokenization, pre-training, and alignment). In this paradigm,
existing naive evolution methods inevitably suffer from _i) cost
blindness:_ squandering budgets by ignoring stage-asymmetric retraining
overheads; and _ii) short-sighted evaluation:_ discarding promising
upstream innovations that temporarily regress metrics before downstream
adaptation. To bridge these gaps, we propose TGR-EvoDAG, a multi-agent
code evolution framework explicitly tailored for GR. TGR-EvoDAG
organizes code evolution as a Directed Acyclic Graph (DAG) that
explicitly maintains multiple evolution branches and merges
complementary innovations, and harmonizes an advanced search mechanism
with rich GR-specific diagnostic feedback. We further introduce
_stage-aware cost planning_ to optimize real-world GPU-hour budgets, and
_active downstream co-adaptation_ to navigate temporary regressions and
unlock deferred cross-stage gains. On public Amazon datasets, TGR-EvoDAG
marks the first autonomous evolution of a complete GR pipeline,
improving offline metrics by up to 37.4% and boosting Agent4Rec
simulated user satisfaction by 19.7% over the strongest GR baseline.
Furthermore, in industrial settings, the evolved GR achieves a 12.16%
relative improvement in offline Hit@1 and, when deployed as an
additional retrieval channel on Tencent’s large-scale commercial media
platform, a statistically significant 0.40% increase in online
click-through rate (CTR).

## 1 Introduction

With the emergence of Large Language Model (LLM) agents, LLM-driven code
evolution has emerged as a promising paradigm, paving the way for
Recursive Self-Improvement ([Romera-Paredes et al., 2024](#bib.bib1);
[Jiang et al., 2025](#bib.bib7); [Chen et al., 2026](#bib.bib47)). This
approach gives agents research-like capabilities: they propose
hypotheses, modify code, run experiments, and collect feedback, enabling
algorithms to self-evolve continuously ([Lu et al., 2024](#bib.bib10);
[Chan et al., 2025](#bib.bib8); [Huang et al., 2024](#bib.bib9); [Liu et
al., 2026](#bib.bib42); [Chen et al., 2021](#bib.bib41)). To accelerate
experimental iterations and reduce labor costs for recommendation
engineers, an increasing number of studies have introduced this paradigm
into the field of sequential recommendation ([Wang et al.,
2026](#bib.bib15); [Kim et al., 2026](#bib.bib16); [Mu et al.,
2026](#bib.bib17)).

While general-purpose code evolution has achieved sophisticated search
mechanisms, such as multi-branch exploration and cross-branch merging,
through population-based approaches ([Romera-Paredes et al.,
2024](#bib.bib1); [Lange et al., 2026](#bib.bib3); [Jiang et al.,
2025](#bib.bib7)) and tree/graph-based architectures ([Jin et al.,
2026](#bib.bib38)), they generally lack the domain-specific feedback
signals essential for recommender systems. Conversely, existing
recommender evolution frameworks invest heavily in feedback quality by
utilizing simulated users and diagnostic probes, yet they predominantly
rely on primitive search mechanisms. For instance, SERS ([Wang et al.,
2026](#bib.bib15)) uses a simple fan-out/fan-in strategy without branch
maintenance; EvoRec performs greedy, round-by-round linear advancement
([Mu et al., 2026](#bib.bib17)); and Self-EvolveRec samples a parent
node from multiple elites ([Kim et al., 2026](#bib.bib16)).

These simple search mechanisms restrict existing recommender evolution
frameworks to traditional end-to-end models, where modifications incur a
uniform full-training cost and produce immediate metric changes ([Kang
and McAuley, 2018](#bib.bib33); [Hidasi et al., 2016](#bib.bib32); [Sun
et al., 2019](#bib.bib34)). They fail on Generative Recommendation (GR),
an increasingly popular paradigm built on a cascaded pipeline
(tokenizer, pre-training, and alignment)([Geng et al.,
2022](#bib.bib19); [Rajput et al., 2023](#bib.bib18); [Wang et al.,
2024](#bib.bib21); [Deng et al., 2025](#bib.bib23); [Pang et al.,
2025](#bib.bib40); [TGR Team et al., 2026](#bib.bib48)), because they
cannot effectively maintain or merge cross-stage innovations. While
explicitly combining advanced general-purpose search mechanisms with
domain-specific feedback seems like a natural solution, this naive
integration still falls short. General-purpose mechanisms fundamentally
rely on two implicit assumptions that a cascaded GR pipeline
structurally violates: 1) Cost Blindness vs. Stage-Dependent Costs.
General-purpose search policies evaluate all candidate nodes uniformly,
ignoring how much retraining an edit requires. In GR, however,
retraining costs are highly asymmetric: modifying the upstream Tokenizer
forces a full-pipeline retraining, whereas editing the downstream
Alignment stage only re-runs the final segment. Being “cost-blind,”
existing frameworks cannot triage edits based on actual overhead,
systematically squandering budgets on expensive upstream explorations. 2) Short-Sighted Evaluation vs. Deferred Gains. General-purpose
frameworks judge modifications by their immediate scores, pruning
candidates that initially regress performance. However, because GR
stages are tightly coupled, modifying an upstream stage almost always
breaks compatibility with the unadapted downstream stage, causing a
temporary performance drop. Lacking structural awareness, existing
frameworks abandon these upstream innovations, missing the opportunity
to actively schedule the necessary downstream adaptations to unlock
“deferred” gains([Liu et al., 2025a](#bib.bib27)).

_short-sighted evaluation_. (c) Capability comparison demonstrating that
TGR-EvoDAG uniquely fulfills the specific demands required to evolve
cascaded GR pipelines.

To this end, we present TGR-EvoDAG, a multi-agent code evolution
framework explicitly built for cascaded GR pipelines. TGR-EvoDAG
seamlessly marries advanced graph search mechanisms with rich
domain-specific feedback. It represents the search space as a Code
Directed Acyclic Graph (Code DAG), driven by a five-stage collaborative
Agent workflow (comprising an Operator Selector, Architect-Critic,
Coder-Reviewer, Distiller, and Pruner) that digests fine-grained
recommendation signals, such as mathematical probes and simulated user
([Zhang et al., 2024](#bib.bib36)). Building upon this foundation,
TGR-EvoDAG tightly integrates the multi-agent workflow with two novel
mechanisms to overcome the inherent blind spots of cascaded pipelines.
First, to address cost blindness, we introduce Stage-Aware Cost Planning
via the Operator Selector. Each DAG node records the exact pipeline
stages its edit touches and the corresponding retraining overhead.
Empowered by this stage-aware schema, our Operator Selector dynamically
balances the expected performance gain against the actual GPU-hour cost,
preventing the framework from blindly exhausting budgets on expensive
upstream explorations. Second, to overcome short-sighted evaluation, we
design Active Downstream Co-Adaptation. Instead of rigidly discarding
candidates that cause immediate performance drops, TGR-EvoDAG explicitly
retains these seemingly “regressed” upstream branches. When the
framework identifies an upstream edit (e.g., Tokenizer) lacking a
corresponding downstream adaptation (e.g., Pre-training), the agents
deliberately schedule a child node to adapt the downstream stage. This
recovers gains from upstream edits that greedy frameworks would discard.

To evaluate our framework fairly, we construct a standardized GR
evolution platform equipped with stage-aware feedback and precise
GPU-hour accounting, ensuring all compared frameworks evolve from an
identical seed codebase. In summary, our core contributions are:

- •
  We identify and formulate the structural mismatch between current code
  evolution frameworks and cascaded GR pipelines. Specifically, we
  expose how cost blindness and short-sighted evaluation cause existing
  methods to systematically misallocate computational budgets and
  discard promising cross-stage innovations.
- •
  We propose TGR-EvoDAG, which harmonizes Code DAG search mechanisms
  with domain-specific feedback via a comprehensive five-stage
  multi-agent workflow. By further introducing stage-aware cost planning
  and active co-adaptation, TGR-EvoDAG enables efficient GR evolution.
- •
  We develop a standardized GR evolution platform. Extensive experiments
  demonstrate that TGR-EvoDAG achieves the fully autonomous evolution of
  a complete GR training pipeline, surpassing both general and
  recommender-specific evolutionary baselines. It improves offline
  metrics by up to 37.4% and boosts user satisfaction in the Agent4Rec
  simulated environment by 19.7% over the strongest GR baseline.
  Moreover, applying the evolved architecture to Tencent’s real-world
  industrial scenarios yields a 12.16% relative improvement in offline
  Hit@1 and a statistically significant 0.40% increase in online
  Click-Through Rate in a 14-day A/B test, demonstrating its practical
  value.

TGR-EvoDAG is part of the TGR series of generative recommendation
research at Tencent ([TGR Team et al., 2026](#bib.bib48)). Beyond this
paper, TGR-EvoDAG has been integrated into Tencent’s internal Uppimo
platform as its implementation backbone, which productizes the recursive
self-improvement (RSI) workflow described here for production
recommendation teams; the platform will be made available for public
trial in the future.

## 2 Related Work

LLM-driven Code Evolution. General-purpose code evolution relies on
three search paradigms. Linear inheritance advances a single thread
(e.g., AIDE, MLE-STAR ([Nam et al., 2025](#bib.bib12); [Yang et al.,
2025](#bib.bib11); [Guo et al., 2024](#bib.bib13))), often stalling at
local optima. Multi-elite sampling draws parents from elite archives to
preserve diversity ([Romera-Paredes et al., 2024](#bib.bib1); [Novikov
et al., 2025](#bib.bib2); [Lange et al., 2026](#bib.bib3); [Liu et al.,
2025b](#bib.bib6); [Liu et al., 2024](#bib.bib4); [Ye et al.,
2024](#bib.bib5)). Explicit tree search maintains multiple branches for
persistent exploration (e.g., SELA, Arbor ([Chi et al.,
2024](#bib.bib14); [Jin et al., 2026](#bib.bib38))); notably, CORAL ([Qu
et al., 2026](#bib.bib39)) even removes fixed strategies and delegates
all search routing to the agent itself. Despite their sophisticated
search, these frameworks fail on Generative Recommendation (GR). First,
they lack the domain-specific feedback (e.g., mathematical probes,
simulated users) essential for GR. Second, facing GR’s cascaded
pipeline, they lack stage-aware cost planning to handle asymmetric
retraining overheads, and cross-stage mechanisms to merge and co-adapt
innovations from upstream tokenization down to alignment.

Generative Recommendation (GR). GR replaces classical ID-based models
([Hidasi et al., 2016](#bib.bib32); [Kang and McAuley,
2018](#bib.bib33); [Sun et al., 2019](#bib.bib34)) with direct
semantic-ID generation ([Tay et al., 2022](#bib.bib31); [Rajput et al.,
2023](#bib.bib18)). Training GR forms a _cascaded three-stage pipeline_:
a Tokenizer quantizes items into hierarchical IDs ([Lee et al.,
2022](#bib.bib28)); Pre-training fits a sequence-to-sequence generator;
and Post-training aligns it with preference signals ([Chen et al.,
2024](#bib.bib30); [Deng et al., 2025](#bib.bib23); [OneRec Team,
2025](#bib.bib24); [Yu et al., 2026](#bib.bib46)). Current manual
research optimizes each stage locally, spanning better tokenizers
([Zheng et al., 2024](#bib.bib20); [Wang et al., 2024](#bib.bib21); [Tan
et al., 2024](#bib.bib25); [Hou et al., 2025](#bib.bib26)), quantization
([Fifty et al., 2025](#bib.bib29)), and architectures ([Zhai et al.,
2024](#bib.bib22)). Because stage-wise improvements are _complementary_,
the global optimum hides in their combinations, a space no
single-threaded search can cover. Furthermore, these stages are tightly
coupled ([Liu et al., 2025a](#bib.bib27)); upstream innovations often
trigger temporary metric drops, requiring downstream re-adaptation to
unlock their _delayed_ value. No prior work autonomously evolves this
complete pipeline.

Self-Evolving Recommender Systems. A nascent line applies code evolution
to recommenders. SERS ([Wang et al., 2026](#bib.bib15)), deployed in
YouTube’s production system, evolves delta edits against a fixed
baseline via a simple fan-out/fan-in strategy. EvoRec ([Mu et al.,
2026](#bib.bib17)) advances the model architecture greedily, round by
round, keeping only the single best variant at each step. Self-EvolveRec
([Kim et al., 2026](#bib.bib16)) employs an LLM-based user simulator
([Park et al., 2023](#bib.bib35); [Zhang et al., 2024](#bib.bib36);
[Wang et al., 2025](#bib.bib37)), and samples a single parent from
multiple elites. These frameworks all introduce recommender-specific
feedback signals, yet adopt a simple search mechanism that maintains and
merges no parallel branches. They fail when evolving a cascaded GR
pipeline: its complementary cross-stage gains must be _merged_ to reach
the global optimum, and its upstream edits pay off only after downstream
re-adaptation. Concurrently, Auto-RecSys ([Li et al., 2026](#bib.bib50))
applies autonomous research agents to industry-scale recommender models.
It focuses on engineering orchestration for long-running experiments
(persistent state, failure recovery, and human-in-the-loop checkpoints),
which is complementary to our work; its search advances each idea
linearly, without explicit GPU-hour budgeting, stage-aware cost
planning, or cross-branch merging.

## 3 Preliminaries

Let $`\mathcal{U}`$ and $`\mathcal{I}`$ denote the sets of users and
items. In sequential recommendation, given a user’s chronological
interaction history $`S_{u}`$, the objective is to predict the next item
$`i_{t+1}`$. Generative Recommendation (GR) reformulates this as a
conditional sequence generation problem. It maps items to discrete
semantic identifiers (SIDs) and autoregressively generates the SID
tokens of $`i_{t+1}`$ conditioned on $`S_{u}`$. Training a GR model
therefore involves three tightly coupled stages: (1) Stage I:
Tokenization. A tokenizer (e.g., RQ-VAE) discretizes item content into
hierarchical semantic IDs. (2) Stage II: Generative Pre-training. A
sequence-to-sequence Transformer is trained to predict the next item’s
tokens via hierarchical cross-entropy. (3) Stage III: Post-training
Alignment. The model is further aligned with desired recommendation
objectives (e.g., exact match or prefix similarity) using preference
optimization or reinforcement learning. We detail the concrete
implementation details and mathematical formulations of these three
stages (e.g., RQ-Kmeans quantization, exact baseline objectives, and
post-training variants) to Appendix
[A.3](#A1.SS3 "A.3 GR Codebase ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent").

## 4 TGR-EvoDAG

We present TGR-EvoDAG, a multi-agent code evolution framework designed
for the cascaded training pipeline of generative recommendation. As
shown in Figure
[2](#S4.F2 "Figure 2 ‣ 4 TGR-EvoDAG ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent"),
TGR-EvoDAG explicitly represents the evolution history as a Code DAG.
This representation enables the framework to preserve multiple promising
branches, revisit earlier pipeline stages, and semantically merge
complementary improvements discovered along different branches.

Figure 2: Workflow of TGR-EvoDAG.

At evolution round $`t`$, the global search state is encapsulated as
$`\mathcal{S}^{(t)}=(\mathcal{G}^{(t)},b^{(t)})`$, where
$`\mathcal{G}^{(t)}=(\mathcal{V}^{(t)},\mathcal{E}^{(t)})`$ is the
current Code DAG, and $`b^{(t)}`$ denotes the remaining evolution
budget. Each node $`v_{i}\in\mathcal{V}^{(t)}`$ acts as a self-contained
experimental record tracking three categories of structured attributes:
(1) Provenance, including the parent set $`\mathcal{P}_{i}`$, applied
search operator
$`o_{i}\in\{\textsc{Explore},\textsc{Mutate},\textsc{Merge}\}`$,
underlying hypothesis $`\mathcal{H}_{i}`$, and branch status
$`\mathcal{Q}_{i}`$; (2) Artifacts, covering the incremental code
modification $`\Delta_{i}`$, executable codebase snapshot
$`\mathcal{B}_{i}`$, and associated artifacts $`\mathcal{A}_{i}`$ (e.g.,
vocabularies, checkpoints); and (3) Empirical Execution, storing the
validation feedback $`\mathcal{F}_{i}`$, distilled lessons
$`\mathcal{D}_{i}`$, and consumed experimental cost $`\mathcal{C}_{i}`$.
The edge set is naturally induced by developmental dependencies,
$`\mathcal{E}^{(t)}=\{(u,v_{i})\mid v_{i}\in\mathcal{V}^{(t)},u\in\mathcal{P}_{i}\}`$.
Because each new node is derived exclusively from previously evaluated
nodes and never modifies its ancestry, $`\mathcal{G}^{(t)}`$ is strictly
guaranteed to be a Directed Acyclic Graph.

### 4.1 Search Operators

TGR-EvoDAG transitions the search state by applying one of three search
operators to generate a new child node $`v_{c}`$. These operators
determine the parent set $`\mathcal{P}_{c}`$ and dictate the semantic
instructions delivered to the multi-agent system.

#### Exploration.

Exploration branches out from a single parent node
($`\mathcal{P}_{c}=\{v_{p}\}`$) to investigate a fundamentally different
direction. Agents formulate a novel hypothesis $`\mathcal{H}_{c}`$
distinct from its ancestry, such as introducing a new training
objective, changing the user-conditioning architecture, or applying a
different post-training algorithm.

#### Mutation.

Mutation performs exploitation and local refinement on a single parent
node ($`\mathcal{P}_{c}=\{v_{p}\}`$). Agents keep the core hypothesis of
$`v_{p}`$ intact while performing localized optimizations, such as
adjusting loss weights, tuning hyperparameters, or modifying sampling
strategies.

#### Merge.

The Merge operator synthesizes complementary improvements discovered
across multiple independent branches
($`\mathcal{P}_{c}=\{v_{p_{1}},\dots,v_{p_{r}}\}`$, $`r\geq 2`$). Unlike
single-parent operators, Merge aggregates a multi-dimensional context.
The framework packages the hypotheses, codebases, and validation
feedback of all parent nodes and forwards them to the pipeline. Agents
are tasked to identify complementary mechanisms, resolve semantic code
conflicts or interface dependencies, and integrate them into a unified
functional codebase $`\mathcal{B}_{c}`$ under a synergized hypothesis
$`\mathcal{H}_{c}`$. To keep the context tractable, we do not inject
full codebase snapshots; instead, each parent is serialized as a unified
diff against the lowest common ancestor in the DAG. Each diff is paired
with its structured hypothesis $`\mathcal{H}`$ and distilled lessons
$`\mathcal{D}`$. This representation stays within the context window
while preserving the information needed to resolve cross-branch
conflicts.

### 4.2 Multi-Agent Pipeline

Each node expansion is executed by a five-stage pipeline instantiated by
seven specialized LLM agents: an Operator Selector, an Architect-Critic
pair, a Coder-Reviewer pair, a Distiller, and a Pruner. To ensure
rigorous evolution, agents communicate through structured intermediate
records (e.g., JSON schemas) rather than unconstrained natural language.
The complete workflow is summarized in Algorithm
[1](#alg1 "Algorithm 1 ‣ Branch-status transition. ‣ A.1 Workflow ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")
(Appendix
[A.1](#A1.SS1 "A.1 Workflow ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")).

#### Stage-Aware Cost Planning via Operator Selector.

Instead of simply counting search iterations, TGR-EvoDAG manages a
realistic GPU-hour budget $`b^{(t)}`$ via empirical cost profiling.
Every evaluated node explicitly records the actual time spent on each
pipeline stage (e.g., Tokenizer, Pre-training, Alignment). Provided with
these historical records, the Operator Selector specifies the
target*stage and training_scope of its intended edit using a structured
JSON schema. This allows the system to estimate the expected GPU-hour
cost $`\mathcal{C}*{c}`$ before execution. By weighing this expected
cost against anticipated performance gains, the Operator Selector makes
strategic budgeting decisions. For instance, it deliberately postpones
expensive upstream edits (which force full-pipeline retraining) until
cheaper downstream architectures fully mature, preventing premature
budget exhaustion.

#### Hypothesis development.

Conditioned on the selected operator $`o_{c}`$ and parents
$`\mathcal{P}_{c}`$, the Architect formulates the hypothesis
$`\mathcal{H}_{c}`$ as a structured blueprint detailing the diagnosed
limitation, proposed mechanism, affected stages, expected diagnostic
changes, and potential risks. The Critic then evaluates this blueprint
against historical lessons and graph ancestry to verify logical
consistency and ensure measurable effects. They engage in an iterative
refinement loop until the hypothesis passes all structural and semantic
checks.

#### Implementation and review.

Guided by $`\mathcal{H}_{c}`$, the Coder implements the codebase
snapshot $`\mathcal{B}_{c}`$ in an isolated workspace initialized from
the parents. The Coder and Reviewer execute a multi-round repair loop
informed by static analysis and peer review. The Reviewer verifies that
the implementation faithfully realizes the blueprint, preserves the
evaluation protocol without data leakage, and maintains cross-stage
compatibility. For Merge nodes, it additionally ensures mechanisms
inherited from all branches remain functionally active. This loop
terminates when the candidate passes all tests or exhausts the repair
budget.

#### Evaluation and lesson distillation.

The standardized environment executes compiled candidates and returns a
comprehensive feedback object $`\mathcal{F}_{c}`$, encapsulating
validation metrics, mathematical probes, user diagnostic reports, and
consumed computational costs. The Distiller then analyzes the hypothesis
$`\mathcal{H}_{c}`$, the code delta $`\Delta_{c}`$, and the empirical
feedback $`\mathcal{F}_{c}`$ to synthesize mechanism-level lessons
$`\mathcal{D}_{c}`$. These lessons explicitly record the tested
mechanism, supporting evidence, applicable conditions, and failure
attributes.

#### Search control and active co-adaptation.

After evaluating $`v_{c}`$, the Pruner acts as a search router rather
than a simple filter. Jointly analyzing quantitative metrics and the
Distiller’s lessons $`\mathcal{D}_{c}`$, the Pruner dynamically dictates
branch state transitions via structured outputs. First, for paths with
irrecoverable collapses, it assigns a \[Pruned\] state, masking them
from the Operator Selector to conserve computation. Second, to address
cascaded pipelines, it enables active downstream co-adaptation. When an
upstream innovation (e.g., Tokenizer edit) causes a metric regression
due to cross-stage incompatibility, the Pruner emits a
\[Needs-Downstream-Adaptation\] tag. Subsequent Operator Selector
prompts are strictly conditioned on these tags, forcing the system to
freeze upstream parameters and mutate the downstream architecture.
Consequently, tightly coupled cross-stage mechanisms are co-evolved
rather than prematurely discarded.

## 5 Experiments

In this section, we conduct numerical experiments to answer five
research questions. (RQ1): Does code-level _DAG_ evolution with
domain-specific feedback beat both general and recommender-specific
evolutionary frameworks? (RQ2): Does _stage-aware cost planning_
overcome _cost blindness_ and budget for expensive upstream (Tokenizer)
innovations? (RQ3): Do _active downstream co-adaptation_ and
_cross-branch merging_ overcome _short-sighted evaluation_? (RQ4): Can
the evolved architecture transfer to real-world industrial scenarios?
(RQ5): Are user diagnosis and mathematical probes _causally_ useful in
driving mutations?

#### Setup and Protocol.

All frameworks evolve on a unified platform under a fixed budget
$`B=24`$ GPU-hours, using Claude CLI ([Liu et al., 2026](#bib.bib42))
with all inference routed to GLM-5.2 ([GLM-5-Team et al.,
2026](#bib.bib43)), starting from an identical TIGER seed codebase (plus
post-training variants SDPO, SPRec, ReReGRPO, APAO) on the Amazon Office
Products dataset. The final champion architecture evolved on this public
dataset is subsequently transferred to Tencent’s large-scale industrial
platform for real-world validation (Section
[5](#S5.SS0.SSS0.Px5 "Real-World Industrial Deployment (RQ4). ‣ 5 Experiments ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")).
We compare against general frameworks (AlphaEvolve ([Novikov et al.,
2025](#bib.bib2)), DeepEvolve ([Liu et al., 2025b](#bib.bib6)), CORAL
([Qu et al., 2026](#bib.bib39)), Arbor ([Jin et al., 2026](#bib.bib38)))
and recommender-specific ones (EvoRec ([Mu et al., 2026](#bib.bib17)),
Self-EvolveRec ([Kim et al., 2026](#bib.bib16))); detailed
configurations of the datasets, codebases, and baselines are provided in
Appendix
[A.2](#A1.SS2 "A.2 Datasets ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent"),
[A.3](#A1.SS3 "A.3 GR Codebase ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent"),
[A.4](#A1.SS4 "A.4 Evolution Baselines ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent").
The platform exposes three feedback channels: (i) offline metrics
(Hit@$`K`$/NDCG@$`K`$), (ii) deterministic mathematical probes, and
(iii) LLM-based user diagnosis (Appendix
[A.5](#A1.SS5 "A.5 Multi-dimension Diagnostics ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")).
Standard general baselines receive only offline metrics channel (i),
whereas recommender-specific frameworks (EvoRec, Self-EvolveRec) and
TGR-EvoDAG access all three channels. To strictly decouple the benefit
of diagnostic feedback from evolutionary search topology, we further
construct two naive integration baselines, namely CORAL + Diag. and
Arbor + Diag., which augment the strongest general search frameworks
with identical multi-channel feedback. Model selection uses offline
validation metrics alone. Both user diagnostic reports and Agent4Rec
simulations are driven by DeepSeek-v4-flash([DeepSeek-AI et al.,
2026](#bib.bib49)) with a temperature of 0 to ensure determinism and
reproducibility. Crucially, evolutionary user diagnosis samples 50
simulated users, whereas post hoc Agent4Rec metrics ([Zhang et al.,
2024](#bib.bib36)) are evaluated on 100 separate simulated users,
keeping the two user cohorts strictly disjoint and non-overlapping to
avoid evaluation leakage (Appendix
[A.6](#A1.SS6 "A.6 Metrics ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")).

#### Analysis of Evolution Trajectory (RQ1-RQ3).

Figure
[3](#S5.F3 "Figure 3 ‣ Main Results. ‣ 5 Experiments ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")
illustrates the 39-round evolution trajectory from the initial TIGER
seed (Hit@10 $`0.0626`$) to the final architecture ($`0.0869`$) across
five distinct phases, directly answering RQ1–RQ3. (Phase 1) The
framework first establishes a robust baseline by injecting both
collaborative and semantic IDs into the TIGER encoder, adjusting InfoNCE
weights, and grid-searching feature fusion and user pooling methods
($`0.0626\!\to\!0.0673`$). (Phase 2) Next, TGR-EvoDAG opens multiple
orthogonal branches based on diagnostic signals. This DAG structure
safely explores and deepens parallel mutations (e.g., recency bias,
user-conditional decoding) without destabilizing the main trunk,
demonstrating a clear advantage over linear frameworks (RQ1). (Phase 3)
It then pairwise merges these independently matured branches and stacks
them with APAO, creating a single-step performance leap to $`0.0824`$
($`+12.3\%`$) and validating the effectiveness of cross-branch merging
(RQ3). (Phase 4) Because modifying the upstream tokenizer requires
expensive full-pipeline retraining, TGR-EvoDAG strategically defers this
to avoid budget waste. It tests the new Repr-LLM encoder on an isolated
branch, where introducing PSRQ initially causes a collapse to
$`0.0599`$. Diagnostics quickly repair it via RMS normalization and
parameter sweeps before trunk integration, demonstrating how stage-aware
cost planning overcomes cost blindness (RQ2). (Phase 5) Finally, when
this repaired tokenizer is merged into the main trunk, performance
initially regresses to $`0.0775`$. Instead of discarding it via greedy
search, TGR-EvoDAG retains the node and actively co-adapts downstream
components by re-tuning the fine-margin loss. This successfully recovers
performance, pushing the model to its final peak of $`0.0869`$ after a
final merge with the APAO branch, thereby overcoming short-sighted
evaluation (RQ3).

#### Ablation of Search Mechanisms (RQ2 & RQ3).

We re-evolve under restricted variants: A (greedy: no multi-branch,
prunes any regression), B (multi-elite but no cross-branch merge), and C
(full search but without cost planning, uniform budget across stages).
As shown in Figure
[4](#S5.F4 "Figure 4 ‣ Ablation of Search Mechanisms (RQ2 & RQ3). ‣ 5 Experiments ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")(a,b),
performance rises monotonically from A to Full TGR-EvoDAG on both
testset and Agent4Rec metrics. A stalls at a local optimum, as its
short-sighted greedy pruning cannot survive the temporary regressions
required for downstream co-adaptation. B tolerates these delayed payoffs
but remains blind to the compounding gains of merging independent
branches, answering RQ3. C adds merging but suffers from cost blindness;
lacking stage-aware planning, it exhausts the budget uniformly and
cannot afford the expensive upstream tokenizer retraining. Full
TGR-EvoDAG finally triages its budget properly to conquer the upstream
stage, unlocking the terminal peak and answering RQ2.

#### Real-World Industrial Deployment (RQ4).

We deploy the champion GR architecture to Tencent’s commercial media
platform with over 10 million daily active users. This deployment is
carried out through Tencent’s internal Uppimo platform, into which
TGR-EvoDAG has been integrated as its core evolution engine. The
production system follows a standard retrieval-pre-ranking-ranking
cascade. Offline Transferability. We train the champion architecture and
the strongest baseline APAO from scratch using 10 days of industrial
logs ($`>`$10 million interactions). As shown in Figure
[4](#S5.F4 "Figure 4 ‣ Ablation of Search Mechanisms (RQ2 & RQ3). ‣ 5 Experiments ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")(c),
our evolved model strictly improves over APAO across all
metrics($`+12.16\%`$ Hit@1, $`+4.83\%`$ Hit@5, $`+0.25\%`$ Hit@50).
Online A/B Testing. We subsequently deployed the evolved model as a
novel retrieval channel for a 14-day A/B test on 5% of live traffic
(serving $`>`$1M users). To ensure strict statistical rigor, we applied
CUPED variance reduction and controlled the false discovery rate via
tiered Benjamini-Hochberg correction ($`q\leq 0.05`$). The online
results reveal a significant overall system CTR increase of $`+0.40\%`$
($`p=0.019`$). Furthermore, the new channel contributes over 10% of
unique exposures (relevant items completely missed by existing channels)
and achieves a channel-specific CTR $`\approx`$13% higher than the
system average.

#### Validation of Diagnostic Signals (RQ5).

To answer whether diagnostic signals are causally useful in driving
mutations, we highlight three critical turning points where offline
metrics alone offered no actionable direction. (i) User Diagnosis: When
performance plateaued, simulated user feedback explicitly reported that
recommendations were “outdated,” motivating the agent to inject an
exponential recency bias. When an initial weak prior ($`\gamma{=}0.9`$)
showed no offline improvement, diagnostics confirmed it was absorbed by
learnable weights, prompting the agent to apply a stronger signal
($`\gamma{=}0.5`$) that successfully broke the plateau. (ii)
Mathematical Probes: Standard metrics only indicate overall correctness,
but mathematical probes isolated a specific “same coarse, wrong fine”
error mode. This directly drove the agent to design a targeted
within-coarse hard-negative contrastive loss that random mutation could
not easily discover. (iii) Distribution Probes: When the new PSRQ
tokenizer caused a catastrophic performance drop, an offline-only search
would have discarded it. However, distribution probes pinpointed a
semantic ID collision spike (to $`65.7\%`$) due to a k-means scale
imbalance. This causal insight guided the agent to apply an RMS
normalization repair, dropping collisions back to $`1.0\%`$ and
unlocking the tokenizer’s potential. Ultimately, while offline metrics
only flag failures, these diagnostics provide the exact causal
mechanisms required for the agent to execute targeted repairs.

## 6 Conclusion

In this paper, we introduce TGR-EvoDAG, a multi-agent code evolution
framework tailored for Generative Recommendation (GR). We observe that
naively integrating existing evolution frameworks fails on GR’s cascaded
pipelines due to two fundamental bottlenecks: cost blindness and
short-sighted evaluation. To bridge this gap, TGR-EvoDAG harmonizes an
advanced Code Directed Acyclic Graph (Code DAG) search mechanism with
rich diagnostic feedback. Building upon this foundation, it introduces
stage-aware cost planning to explicitly triage edits based on actual GPU
overhead, and active downstream co-adaptation to safely navigate
temporary regressions and unlock deferred gains. Extensive evaluations
on a standardized GR platform demonstrate that TGR-EvoDAG achieves
state-of-the-art performance, outperforming the leading non-evolutionary
baseline (APAO) by up to 37.4% in offline metrics and 19.7% in simulated
user satisfaction. In addition, successful migration to Tencent’s
real-world industrial scenarios yields a 12.16% relative improvement in
offline Hit@1 and a statistically significant 0.40% gain in online
Click-Through Rate. Moving forward, building on its integration into
Tencent’s Uppimo platform, we plan to directly evolve GR pipelines
within complex industrial scenarios and to open the platform for public
trial. Moreover, since Large Language Model (LLM) training inherently
involves cascaded stages, we envision our framework can be naturally
extended to optimize multi-stage LLM pipelines.

### A.1 Workflow

Algorithm
[1](#alg1 "Algorithm 1 ‣ Branch-status transition. ‣ A.1 Workflow ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent")
expands a single evolution round of TGR-EvoDAG. We present the round in
the same five stages as Section
[4.2](#S4.SS2 "4.2 Multi-Agent Pipeline ‣ 4 TGR-EvoDAG ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent"),
and use this section to make precise what the main text states only
qualitatively: the records exchanged between the agents, the accounting
of the budget $`b^{(t)}`$, and the transition of the branch status
$`\mathcal{Q}`$.

#### Agent records.

Each agent is invoked as a single call constrained to one structured
record, which the harness parses directly; a response that cannot be
parsed is discarded and the call is repeated rather than repaired, so
that no free-form residue enters the node attributes and every
intermediate decision remains machine-checkable. The Operator Selector
consumes the serialised graph $`\mathcal{G}^{(t)}`$ together with the
remaining budget $`b^{(t)}`$ and returns the operator $`o_{c}`$ and
parent set $`\mathcal{P}_{c}`$; the Architect consumes these and the
ancestral lessons and returns the hypothesis $`\mathcal{H}_{c}`$; the
Coder and Reviewer consume $`\mathcal{H}_{c}`$ and return the codebase
snapshot $`\mathcal{B}_{c}`$ with the delta $`\Delta_{c}`$; the
Distiller consumes $`\mathcal{H}_{c}`$, $`\Delta_{c}`$, and the feedback
$`\mathcal{F}_{c}`$ and returns the lesson $`\mathcal{D}_{c}`$; and the
Pruner consumes $`\mathcal{F}_{c}`$, $`\mathcal{D}_{c}`$, $`o_{c}`$, and
the touched stage and returns the branch status $`\mathcal{Q}_{c}`$. Two
of these choices are deliberate. The Critic is instructed to reject a
blueprint only when it violates a hard invariant, cannot yield an
executable forward pass, is a no-op, or re-proposes a direction already
falsified without addressing the recorded lesson $`\mathcal{D}_{i}`$; a
rejected blueprint costs a full round of agent calls, whereas an
accepted but unpromising one costs only a single evaluation, so the
asymmetry favours acceptance. The Distiller is given the Coder’s
workspace together with $`(\mathcal{H}_{c},\Delta_{c},\mathcal{F}_{c})`$
and inspects $`\Delta_{c}`$ before writing $`\mathcal{D}_{c}`$, so that
a lesson attributes the outcome to a mechanism (a specific layer,
objective, or initialization) instead of restating $`\mathcal{H}_{c}`$.

#### Budget accounting.

A round is charged the GPU-hours measured by the environment,
$`\mathcal{C}_{c}`$, and not the expected cost estimated from the
target*stage and training_scope attributes. That estimate only informs
the Operator Selector’s strategic decision; the decrement
$`b^{(t+1)}\leftarrow b^{(t)}-\mathcal{C}*{c}`$ always uses the measured
value, which is recovered stage by stage and stored on the node, so that
the cost profile available to later rounds reflects the true
stage-asymmetric overheads of the pipeline. A round that fails review or
is interrupted before yielding a usable candidate is charged
$`\tau\_{\text{fail}}`$, the GPU-hours spent before the failure, so that
repeatedly proposing unexecutable candidates cannot be used to explore
at no cost. Token consumption is logged separately and does not draw on
$`b^{(t)}`$.

#### Branch-status transition.

A node that passes review and yields a valid checkpoint, whether or not
it improves on its parent, keeps its default status and remains
selectable, since an immediate regression on an upstream edit is
precisely the signal that downstream co-adaptation is required. Only the
two tagged statuses alter the search: \[Pruned\] is assigned on an
irrecoverable collapse (unexecutable or protocol-violating code, a
broken item$`\leftrightarrow`$code mapping, or a metric collapse with no
diagnostic route) and removes the subtree permanently, masking it from
the Operator Selector; \[Needs-Downstream-Adaptation\] is assigned when
a metric regression is caused by an upstream (tokenization or
pre-training) edit and conditions the subsequent Operator Selector
prompts so that upstream parameters are frozen and the child node must
mutate the downstream stage to restore cross-stage compatibility.

### A.2 Datasets

In this section, we introduce the open-source Amazon Office dataset used
for evolution, as well as the industrial dataset used to verify whether
the evolved GR architecture is effective in real-world industrial
scenarios.

Amazon Office Dataset. Following the evaluation protocol of the initial
codebase ([Yu et al., 2026](#bib.bib46)) and prior generative
recommendation studies ([Rajput et al., 2023](#bib.bib18)), we conduct
all evolution experiments on the Office Products category of the public
Amazon Product Review corpus¹¹ 1
[https://jmcauley.ucsd.edu/data/amazon/links.html](https://jmcauley.ucsd.edu/data/amazon/links.html).
We directly adopt the preprocessed data released by [Yu et al.
(2026)](#bib.bib46). For completeness, we restate the protocol under
which the released data were produced: each review is treated as one
implicit positive interaction, and every user’s interactions are sorted
chronologically into a single behaviour sequence. Five-core filtering
then iteratively discards users and items with fewer than five
interactions. Each history is truncated to the most recent 20 items.
Finally, the data is split with the standard leave-one-out strategy. For
every user, the chronologically last interaction forms the test
instance, the second-to-last forms the validation instance, and the rest
are used for training. All evolutionary frameworks therefore optimise
and are selected on exactly the same validation split, and the test
split is touched only once, for the final checkpoint selected within the
budget $`B`$. Item side information (title, brand, category, price and
description) is concatenated into a textual description and used
exclusively by the item tokenizer. The statistics of the released data

Real-world Industrial Dataset. The industrial data are collected from

### A.3 GR Codebase

In this section, we introduce the codebase provided for the evolutionary
framework.

All frameworks evolve upon an identical seed codebase, which is built
directly on the officially released APAO implementation ([Yu et al.,
2026](#bib.bib46)) together with its preprocessed data and its original
tokenizer configuration. The codebase is organised into four decoupled
modules: (i) item tokenization, (ii) backbone definition, (iii) the
pre-training objective, and (iv) a pluggable post-training objective.
All four share one data loader and one beam-search evaluator. What is
held invariant across all frameworks is the _environment_: the
preprocessed interaction data, the train/validation/test split, the
evaluation protocol and the budget $`B`$. Everything above the data
layer, including the tokenization module, is exposed as mutable code and
may be modified by a candidate during evolution.

Item Tokenization. Every item is represented by a sequence of discrete
semantic tokens rather than a single atomic ID. The seed codebase ships
with the tokenizer configuration of [Yu et al. (2026)](#bib.bib46): a
semantic embedding is first extracted for each item by feeding its
concatenated textual metadata into Llama-3.1-8B-Instruct and taking the
final-layer representation; a 4-level RQ-$`K`$-means quantizer then
residually quantizes each embedding into $`T=4`$ codes
$`(y^{1},y^{2},y^{3},y^{4})`$, one per level. Each level owns an
independent codebook, and a de-duplication suffix is appended whenever
two items collide on all four levels, guaranteeing an injective
item$`\leftrightarrow`$code mapping. A user history
$`x=\{i_{1},\dots,i_{n-1}\}`$ is thus flattened into a token sequence of
length $`4(n-1)`$, and predicting the next item amounts to
autoregressively generating its $`4`$ semantic tokens. Note that the
tokenization module is _not_ frozen: a candidate is free to re-fit or
redesign the quantizer (e.g. changing the number of levels, the codebook
size or the quantization algorithm) as part of its proposed
modification, in which case the downstream backbone is retrained
accordingly. Only the upstream interaction data and the splits are
fixed. The seed baselines reported in the main text all use the original
configuration above.

Backbone. The seed backbone is TIGER ([Rajput et al.,
2023](#bib.bib18)), a T5-style Transformer _encoder-decoder_ operating
entirely in the semantic-token space. The encoder consumes the flattened
history tokens and the decoder autoregressively emits the $`4`$ codes of
the target item; at inference time decoding is performed with
constrained beam search over the valid code trie. Both the encoder and
the decoder consist of $`4`$ layers with $`6`$ self-attention heads of
head dimension $`64`$, ReLU activations in all feed-forward blocks, and
a learnable token embedding dimension of $`128`$, yielding roughly
$`0.01`$B parameters in total. The full architectural and optimisation
configuration is listed in Table
[3](#A1.T3 "Table 3 ‣ A.3 GR Codebase ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent");
all values are inherited from [Yu et al. (2026)](#bib.bib46) without
modification.

````math
Post-training Variants. The seed codebase ships with four post-training
objectives, which together span the mainstream design space of
preference- and reinforcement-based alignment for generative
recommendation. They constitute the algorithmic prior that the
evolutionary frameworks may recombine, ablate or extend.

- •
  SDPO ([Chen et al., 2024](#bib.bib30)) generalises Direct Preference
  Optimization to a multi-negative, softmax-weighted ranking loss. Given
  a positive item $`e_{i,+}`$ and a sampled negative set
  $`\mathcal{N}`$, it optimises

  |  |  |  |  |
  |----|----|----|----|
  |  |
  ``` math
  \mathcal{L}_{\mathrm{SDPO}}=-\log\sigma\!\left(-\log\!\!\sum_{j\in\mathcal{N}}\!\exp\!\Big(\beta\log\tfrac{\pi_{\theta}(e_{j,-}\mid x)}{\pi_{\mathrm{ref}}(e_{j,-}\mid x)}-\beta\log\tfrac{\pi_{\theta}(e_{i,+}\mid x)}{\pi_{\mathrm{ref}}(e_{i,+}\mid x)}\Big)\right),
  ``` |  | (2) |

  where $`\pi_{\mathrm{ref}}`$ is the frozen pre-trained reference
  policy. Crucially, the preference signal is defined at the *complete
  sequence* level, i.e. on the cumulative likelihood of the whole item,
  with a single summation over $`\mathcal{N}`$.
- •
  SPRec ([Gao et al., 2025](#bib.bib44)) is a self-play framework
  designed to suppress the over-recommendation / filter-bubble bias that
  plain DPO induces. Each self-play iteration performs one SFT step on
  the offline interactions followed by one DPO step in which the
  *model’s own predictions from the previous iteration* serve as
  negatives. Because the negative distribution is the current policy’s
  own output, the DPO loss is implicitly re-weighted by the model
  logits, adaptively penalising items the model already over-exposes. No
  extra data or manual intervention is needed.
- •
  ReReGRPO ([Tan et al., 2025](#bib.bib45)) casts post-training as
  reinforcement learning with verifiable rewards on top of GRPO. Two
  domain-specific adaptations make GRPO viable in the constrained item
  space: (i) candidates are sampled by *constrained beam search* rather
  than i.i.d. sampling, which yields a group of valid, distinct and
  on-policy hard negatives in a single pass; and (ii) the sparse binary
  rule reward (exact match with the target) is augmented with a *ranking
  reward* that penalises a generated negative proportionally to its
  probability rank,
  $`r(e_{k})=R_{\mathrm{rule}}(e_{k})+\lambda R_{\mathrm{rank}}(e_{k})`$.
  Advantages are normalised within the group,
  $`\hat{A}_{k}=(r_{k}-\mathrm{mean}(\mathbf{r}))/\mathrm{std}(\mathbf{r})`$,
  and a KL penalty towards the reference policy stabilises the update.
- •
  APAO ([Yu et al., 2026](#bib.bib46)) attacks the training-inference
  inconsistency directly by moving supervision from the sequence level
  to every intermediate *prefix*. Defining the cumulative score of a
  length-$`m`$ prefix as
  $`s^{m}=\sum_{t\leq m}\log\pi_{\theta}(y^{t}\mid x,y^{<t})`$, the
  pairwise variant optimises

  |  |  |  |  |
  |----|----|----|----|
  |  |
  ``` math
  \mathcal{L}_{\mathrm{pair}}=\mathcal{L}_{\mathrm{CE}}+\beta\sum_{m=1}^{T}w_{m}\Big[-\log\sigma\big(-\log\!\!\sum_{j\in\mathcal{N}_{m}}\!\exp(s^{m}_{j,-}-s^{m}_{i,+})\big)\Big],
  ``` |  | (3) |

  while the pointwise variant replaces the bracketed term with the
  negative length-normalised prefix log-likelihood. The prefix weights
  $`\mathbf{w}\in\Delta^{T-1}`$ are *not* fixed but follow an
  exponentiated-gradient update,
  $`w_{m}\!\leftarrow\!w_{m}\exp(\eta\mathcal{L}_{m})`$ followed by
  re-normalisation, which realises *adaptive worst-prefix optimisation*:
  the step whose prefix is currently most likely to fall out of the beam
  receives the largest weight.

### A.4 Evolution Baselines

We compare TGR-EvoDAG against six evolutionary frameworks, grouped into
*general evolutionary frameworks* (domain-agnostic) and
*recommender-specific frameworks* (built for recommendation). Every
baseline is instantiated on the same seed codebase, executed by the same
coding agent (Claude CLI), and constrained by the same budget $`B=24`$
GPU-hours described in the main text, so that the differences reported
stem from the search strategy itself rather than from the environment.

#### General evolutionary frameworks.

- •
  AlphaEvolve ([Novikov et al., 2025](#bib.bib2)) orchestrates an
  autonomous LLM-driven evolutionary pipeline that iteratively evolves
  and optimizes entire algorithmic codebases by directly editing and
  testing code against evaluator feedback. It generalizes the
  FunSearch/Eureka line of LLM-driven code evolution from single
  functions to whole codebases, but is guided primarily by scalar
  metrics and carries no recommendation-specific inductive bias.
- •
  DeepEvolve ([Liu et al., 2025b](#bib.bib6)) extends the evolutionary
  loop with retrieval-augmented generation (RAG): it retrieves external
  scientific knowledge (e.g., academic papers from arXiv) to
  systematically inform hypothesis generation and codebase refinement,
  grounding the evolution in prior work rather than relying on the
  model’s internal knowledge alone.
- •
  CORAL ([Qu et al., 2026](#bib.bib39)) is a multi-agent framework for
  open-ended discovery that replaces rigid control flow with
  long-running agents that explore, reflect, and collaborate through a
  shared persistent memory and asynchronous execution.
- •
  Arbor ([Jin et al., 2026](#bib.bib38)) is a general
  autonomous-research framework built on Hypothesis Tree Refinement : a
  persistent tree links hypotheses, artifacts, evidence, and distilled
  insights across time. A long-lived coordinator manages the global
  strategy over the tree, while short-lived executors implement and test
  individual hypotheses in isolated worktrees; returned results are
  propagated back into the tree as reusable lessons that refine the
  search frontier.

#### Recommender-specific frameworks.

- •
  EvoRec ([Mu et al., 2026](#bib.bib17)) is a multi-agent framework that
  co-evolves both the recommendation model and the optimization
  methodology driving it. Four agents (an Orchestrator, a Research
  Agent, a Code Agent, and a Skill Evolver) run a dual-track loop: the
  Research and Code agents iterate the model each round, while the Skill
  Evolver periodically distills reusable methodology from a persistent
  memory of past experiments into a self-evolving skill library. It is
  domain-aware but is guided primarily by offline metrics, without the
  directional diagnosis.
- •
  Self-EvolveRec ([Kim et al., 2026](#bib.bib16)) introduces
  *directional feedback* for recommender evolution, pairing a *User
  Simulator* that emits natural-language critiques with a *Model
  Diagnosis Tool* that probes internal structure (e.g., embedding
  collapse, ranking margin) and interprets the numbers into a structured
  diagnosis. A *Diagnosis Tool Co-Evolution* mechanism keeps the
  diagnosis tool compatible with the evolving model, and an evolutionary
  archive retains the codebase history.

### A.5 Multi-dimension Diagnostics

During evolution the environment produces, for every executed candidate,
a structured feedback bundle assembled from three complementary
diagnostic channels, following the directional-feedback design of
Self-EvolveRec ([Kim et al., 2026](#bib.bib16)) (which pairs a
qualitative *User Simulator* with a quantitative *Model Diagnosis Tool*)
and specialising it to the 4-layer semantic-ID (SID) generative
recommender. The three channels are: *(i)* offline validation metrics,
giving a macro-level view of ranking quality; *(ii)* deterministic
mathematical probes, exposing internal failure modes that aggregate
metrics cannot express; and *(iii)* qualitative user diagnosis,
surfacing behaviour-level deficiencies in natural language. While
offline metrics in Channel *(i)* are available to every framework,
diagnostic feedback in Channels *(ii)* and *(iii)* is provided
exclusively to domain-specific methods, naive integration variants
(Arbor + Diag. and CORAL + Diag.), and TGR-EvoDAG. For these methods,
the diagnostic content is emitted *stage-aware*: the bundle carries
separate fields for the supervised-fine-tuning stage (sft\_\*) and the
post-training stage (post\_\*), so that multi-stage diagnostics are
produced only if a candidate actually modifies post-training; a
single-stage candidate (e.g., pure TIGER) receives only the sft\_\*
fields.

#### Channel (i): Offline validation metrics.

The environment computes standard ranking metrics (Hit@$`K`$ and
NDCG@$`K`$, $`K\in\{10,20\}`$) on the validation set via constrained
beam search (beam size $`20`$), as formalised in Appendix
[A.6](#A1.SS6 "A.6 Metrics ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent").
These scalars quantify *how well* the candidate ranks, but not *why* it
fails, and are therefore complemented by the two channels below. In the
feedback bundle the metrics appear both as the final-model value
(offline_val) and as the per-stage values (sft_stage_val,
post_stage_val) to enable stage-level credit assignment.

#### Channel (ii): Deterministic mathematical probes.

The probe suite deterministically measures structural and decoding
properties of the trained model, and is grouped into four families
summarised in Table
[4](#A1.T4 "Table 4 ‣ Probe extensibility. ‣ A.5 Multi-dimension Diagnostics ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent").
All values are computed by the environment on the validation split; the
baseline probe set is fixed and cannot be altered by any framework.

#### Probe extensibility.

Although the baseline probe set is fixed, a candidate is permitted to
implement and upload *additional* probe scripts to broaden its own
diagnostic coverage. The environment merges candidate-contributed
metrics into the baseline under an agent.\* namespace and enforces an
additive-only policy (candidate probes may not overwrite baseline
probes), so the official diagnostic surface remains identical across
frameworks while a framework may still monitor candidate-specific
signals. The execution status of any submitted probe is reported back in
the sft_probe_fn_status / post_probe_fn_status fields.

#### Channel (iii): Qualitative user diagnosis.

Following the user-simulator paradigm in Self-EvolveRec ([Kim et al.,
2026](#bib.bib16)), we instantiate an LLM-based simulator to produce
behaviour-level critiques. We construct a population of simulated users,
each governed by a fixed persona spanning three traits (*activity*,
*conformity*, and *diversity*, each ranging from LOW to HIGH).
Conditioned on their individual interaction histories, these simulated
users evaluate the candidate’s top-$`K`$ recommendations via a two-step
protocol:

- •
  Item-level Assessment: The simulator inspects each recommended item to
  predict the user’s reaction. It outputs a binary verdict
  (align/misalign) along with a short causal reasoning for the decision.
- •
  List-level Feedback: Building on the item verdicts, the simulator
  abstracts the overall quality of the top-$`K`$ list. It identifies
  which decision signals the model correctly captured, which patterns
  were overgeneralized, and which user intentions were missed.

Finally, to mitigate individual-user bias and surface systematic flaws,
a global aggregator (prompted as a *Lead Analyst*) synthesizes all
per-user reports. This yields a single, macro-level system critique that
strictly adheres to the unified StandardDiagnosis schema, serving as the
qualitative counterpart to the mathematical probes.

### A.6 Metrics

In this section, we will introduce offline recommendation metrics (Hit
and NDCG) as well as metrics defined in Agent4rec that simulate user
experience.

Offline Recommendation Metrics. Under the leave-one-out protocol each
user $`u`$ has exactly one ground-truth next item $`i_{u}^{\ast}`$.
Given the ranked list $`R_{u}`$ of length $`K`$ produced by constrained
beam search, let $`\mathrm{rank}_{u}\in\{1,\dots,K\}\cup\{\infty\}`$
denote the position of $`i_{u}^{\ast}`$ in $`R_{u}`$
($`\mathrm{rank}_{u}=\infty`$ if it is not retrieved).

*Hit@$`K`$* measures whether the ground-truth item appears in the
top-$`K`$ list:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{Hit}@K=\frac{1}{|\mathcal{U}|}\sum_{u\in\mathcal{U}}\mathbb{I}\!\left(\mathrm{rank}_{u}\leq K\right)=\frac{1}{|\mathcal{U}|}\sum_{u\in\mathcal{U}}\frac{\left|R_{u}^{K}\cap\{i_{u}^{\ast}\}\right|}{\left|\{i_{u}^{\ast}\}\right|}.
``` |  | (4) |

*NDCG@$`K`$* additionally rewards placing the ground-truth item near the
top of the list. With binary relevance
$`\mathrm{rel}_{j}=\mathbb{I}(R_{u}[j]=i_{u}^{\ast})`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{DCG}@K(u)=\sum_{j=1}^{K}\frac{2^{\mathrm{rel}_{j}}-1}{\log_{2}(j+1)}=\frac{\mathbb{I}(\mathrm{rank}_{u}\leq K)}{\log_{2}(\mathrm{rank}_{u}+1)},\qquad\mathrm{IDCG}@K(u)=\frac{1}{\log_{2}2}=1,
``` |  | (5) |

so that

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{NDCG}@K=\frac{1}{|\mathcal{U}|}\sum_{u\in\mathcal{U}}\frac{\mathrm{DCG}@K(u)}{\mathrm{IDCG}@K(u)}=\frac{1}{|\mathcal{U}|}\sum_{u\in\mathcal{U}}\frac{\mathbb{I}(\mathrm{rank}_{u}\leq K)}{\log_{2}(\mathrm{rank}_{u}+1)}.
``` |  | (6) |

We report $`K\in\{10,20\}`$. Since the beam size equals $`20`$, the
top-$`20`$ list is exactly the beam-search output, and the top-$`10`$
list is its truncation.

Agent4Rec Metrics. Offline recommendation metrics summarise a single
next-item prediction and are therefore blind to list-level behavioural
effects such as over-concentration. To complement them, we additionally
report three behaviour-level metrics obtained from the LLM-based user
simulator Agent4Rec ([Zhang et al., 2024](#bib.bib36)). In this
simulator each generative agent is initialised from a real user profile
(activity, conformity and diversity traits) and interacts with the
evaluated recommender *page by page*: four items are displayed per page,
the agent chooses which items to view and rates them on a $`1`$-$`5`$
scale, and then decides whether to request the next page or to exit,
being forced to exit after at most five pages. A rating higher than
$`3`$ is treated as a *like*. Let $`\mathcal{A}`$ denote the evaluation
agent population, and for agent $`a`$ let $`E_{a}`$ be the number of
exposed items, $`L_{a}`$ the number of liked items, and
$`p_{a}\in[1,5]`$ the page index at which $`a`$ exits. We report

|  |  |  |  |  |  |  |  |  |
|----|----|----|----|----|----|----|----|----|
|  | $`\displaystyle\bar{P}_{\mathrm{like}}`$ | $`\displaystyle=\frac{1}{|\mathcal{A}|}\sum_{a\in\mathcal{A}}\frac{L_{a}}{E_{a}},`$ | $`\displaystyle\bar{N}_{\mathrm{like}}`$ | $`\displaystyle=\frac{1}{|\mathcal{A}|}\sum_{a\in\mathcal{A}}L_{a},`$ | $`\displaystyle\bar{N}_{\mathrm{exit}}`$ | $`\displaystyle=\frac{1}{|\mathcal{A}|}\sum_{a\in\mathcal{A}}p_{a}.`$ |  | (7) |

Higher values indicate a better simulated user experience for all three
metrics. $`\bar{P}_{\mathrm{like}}`$ measures the precision of the
exposed list at the behaviour level, $`\bar{N}_{\mathrm{like}}`$
measures the absolute volume of satisfied interests a session delivers,
and $`\bar{N}_{\mathrm{exit}}`$ measures engagement depth: a larger exit
page indicates the agent kept browsing rather than abandoning the
session early.

*Agent4Rec metrics are used strictly for evaluation.* They are computed
only once, on the single checkpoint finally retained under the budget
$`B`$, and serve exclusively to compare the frameworks in the main
results table. They are never computed for intermediate candidates,
never exposed to any evolving framework, and never used for model
selection. Model selection relies solely on the offline validation
metrics defined above. Consequently, no framework can optimise these
numbers directly, and they function as a genuinely held-out behavioural
measurement.

We stress that this evaluation simulator is fully disjoint from the user
simulator that supplies the third feedback channel during evolution. The
latter follows the qualitative-diagnosis design of Self-EvolveRec ([Kim
et al., 2026](#bib.bib16)) and emits natural-language diagnostic reports
(Appendix
[A.5](#A1.SS5 "A.5 Multi-dimension Diagnostics ‣ Appendix A Appendix ‣ TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent"))
rather than scalar scores. The two components are isolated along two
axes: (i) the user populations are drawn from disjoint user sets, so no
agent that participates in evolution-time diagnosis is ever reused for
final measurement; and (ii) their outputs are of different kinds and
consumed by different parties: diagnostic text is consumed by the coding
agent during the search, whereas the three metrics above are consumed
only by us, after the search terminates. This separation rules out any
feedback path from the evaluation protocol back into the evolutionary
process. Within the evaluation simulator itself, the agent population,
the random seeds and the interaction templates are fixed once and shared
by all frameworks, so the reported comparison is deterministic and
paired.
````
