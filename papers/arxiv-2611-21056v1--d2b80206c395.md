###### Abstract

Recent self-improving coding agents have achieved strong benchmark
performance by iteratively modifying their own executable
implementations. A common pattern uses downstream task-derived evidence
to decide which candidates or lineages continue evolving, which we term
_evaluate-and-select_. Obtaining this signal requires repeatedly
executing evolved agents on downstream tasks, so broader exploration
incurs increasing evaluation cost, while repeated optimization against a
fixed evaluation distribution may encourage benchmark-specific
adaptation. We ask a more fundamental question: _can coding agents
self-improve without downstream task evaluation inside the evolution
loop?_ We introduce Explore-then-Integrate (Elite), which integrates
implementation mechanisms rather than selecting a single exploratory
child to continue the lineage. At each generation, Elite proposes
diverse focused improvements, implements them independently from the
same parent, and inspects the resulting programs to identify
complementary, redundant, and conflicting mechanisms before
reimplementing a compatible subset as one coherent descendant. No
downstream task outcomes or task-solving trajectories of evolved
candidates are used to guide evolution; only deterministic checks of
structural and operational validity are used inside the loop. On
SWE-bench Pro, Elite improves the initial agent from 60.0% to 85.6%,
compared with 86.7% for the Darwin Gödel Machine (DGM) and 88.3% for the
Huxley-Gödel Machine (HGM), while using zero candidate task evaluations
and reducing observed wall-clock evolution time by 8.8x and 3.2x,
respectively, under the evaluated configurations. In cross-benchmark
transfer without further adaptation, Elite averages 73.3% on SWE-bench
Verified and 69.3% on Polyglot. Together, these results demonstrate the
feasibility of coding-agent self-improvement without downstream
candidate task evaluation in our setting.

## 1 Introduction

The idea of AI systems improving their capabilities has a long history,
from early informal discussions of machines designing more capable
successors (Good, 1966) to concrete algorithms for recursive
self-improvement (RSI) (Schmidhuber, 1987) and the Gödel machine
(Schmidhuber, 2003). Recent work continues to pursue this goal through
modern agentic systems (Fang et al., 2025; Gao et al., 2025; Ren et al.,
2026a). These systems usually improve either the underlying large
language model (LLM) or its scaffold, where the latter comprises prompts
(Fernando et al., 2023; Yuksekgonul et al., 2024), memory (Xu et al.,
2026b; Zhang et al., 2026d), tools (Cai et al., 2024; Qiu et al., 2025),
and control logic (Zelikman et al., 2023; Yin et al., 2025) that govern
how the model is used. Coding agents provide a practical setting for
studying self-improvement because they can access and modify their own
source code to recursively generate better variants of themselves.
Recent systems have improved coding performance by repeatedly modifying
this software while keeping the LLM fixed (Hu et al., 2025; Zhang et
al., 2025; Robeyns et al., 2025; Zhang et al., 2026b; Wang et al.,
2026a). Since self-improvement can revisit agents retained in an
archive, a central design question is not only how to generate
self-modifications, but also which modifications should be carried
forward during subsequent search.

Existing approaches answer this question in different ways, but most
rely on a common principle that we call _evaluate-and-select_ to decide
which candidates or lineages continue evolving. Although their search
and selection mechanisms differ, downstream task-derived evidence is
used to determine which candidates, groups, or lineages receive
subsequent evolutionary effort. DGM uses benchmark performance to guide
parent selection from an archive of agents (Zhang et al., 2026b). HGM
uses descendant task performance to estimate a lineage’s potential for
further improvement (Wang et al., 2026a). GEA uses group-level search
and task-based novelty (Weng et al., 2026), while MGM shares information
across lineages (Liu et al., 2026). SIFT uses LLM-based comparisons to
rank candidate patches (Fu et al., 2026), while RQGM evolves evaluation
criteria during search (Iacob et al., 2026). This evaluate-and-select
paradigm introduces two limitations. First, obtaining reliable
downstream feedback requires repeatedly executing evolved agents on
target tasks, making broader exploration increasingly expensive (Xu et
al., 2026a; Fu et al., 2026; Wang et al., 2026b; Zeng et al., 2026).
Second, candidate-level performance scores alone do not specify which
implementation mechanisms should be retained or combined. Repeated
optimization against a fixed evaluation distribution may further
encourage benchmark-specific adaptation rather than transferable
improvements (Kapoor et al., 2024; Xia et al., 2026). We therefore ask:
can coding agents decide which changes to carry forward without
downstream candidate task evaluation?

A key insight is that executable exploration can generate
implementation-level evidence for inheritance decisions without
downstream candidate task feedback. Implementing focused modifications
independently from the same parent makes their mechanisms, interfaces,
and dependencies explicit and directly comparable. We can then reason
about which mechanisms are complementary, redundant, or conflicting.
This allows the next descendant to be constructed from compatible
mechanisms without first determining which exploratory child performs
best on downstream tasks. Exploratory children thus serve as
intermediate implementations that inform integration, with their
concrete changes providing the basis for deciding what to inherit. This
suggests a different route to recursive self-improvement: explore
diverse modifications, inspect their implementations, and integrate
compatible mechanisms without using downstream task performance to
decide what is carried forward.

We introduce Elite, an Explore-then-Integrate approach to
self-improvement. Elite first generates a portfolio of focused and
diverse improvement hypotheses grounded in concrete limitations of the
current agent’s runtime source. Each hypothesis is implemented
independently from the same parent, producing multiple executable
alternatives. Elite then inspects all valid alternatives, identifies
mechanisms that are complementary, redundant, conflicting, incomplete,
or unnecessarily complex, and integrates compatible mechanisms into one
coherent descendant. The integrated descendant is accepted only if
deterministic structural and operational checks pass. No downstream task
outcomes or task-solving trajectories of evolved candidates are used to
guide this process. Figure 1 illustrates the difference between ELITE
and existing evaluate-and-select approaches. On the 60-task subset of
SWE-bench Pro, Elite improves the initial agent from 60.0% to 85.6%,
compared with 86.7% for DGM and 88.3% for HGM, while using zero
candidate task evaluations and reducing observed evolution time by
8.8$`\times`$ and 3.2$`\times`$, respectively, under our evaluated
configurations. In cross-benchmark transfer without further adaptation,
the evolved agent achieves 73.3% on SWE-bench Verified and 69.3% on
Polyglot. Ablations further show that successful task-fitness-free
evolution still requires constraints: removing deterministic validity
filtering causes performance to collapse. Post-hoc analyses further
examine how integration exploits mechanisms across exploratory children
and characterize the resulting evolution dynamics. Additional
experiments examine an established mini-swe-agent scaffold, direct joint
implementation of seven proposals, and evaluation-based child selection
in place of mechanism integration.

Our contributions are threefold. (1) We observe that coding agents’
self-modifications are inspectable programs, so which changes to carry
forward can be decided from implementation-level evidence rather than
downstream task outcomes; we formulate this as the problem of
self-improvement without candidate task evaluation. (2) We introduce
Elite, which replaces candidate-level selection with same-parent
executable exploration and compatibility-aware mechanism-level
integration, while using deterministic checks only for operational
validity. (3) We provide empirical evidence that coding-agent
self-improvement without downstream candidate task evaluation is
feasible in our setting, and analyze its evolution dynamics, transfer
behavior, and key design components.

## 2 Related Work

##### Self-improvement in coding agents.

Self-improving agents can modify either the underlying model or the
agent scaffold, including prompts, memory, tools, workflows, and control
logic (Gao et al., 2025; Fang et al., 2025; Ren et al., 2026a).
Software-engineering agents provide infrastructure for interacting with
repositories, development tools, and execution environments (Qian et
al., 2024; Yang et al., 2024; Wang et al., 2025; Hong et al., 2024; Xia
et al., 2025). Automated design methods such as GPTSwarm, ADAS, and
AFlow optimize prompts, graph structures, or code-represented workflows
(Zhuge et al., 2024; Hu et al., 2025; Zhang et al., 2025), while
self-referential approaches such as STOP, Gödel Agent, and SICA modify
their own scaffolds or implementations (Zelikman et al., 2023; Yin et
al., 2025; Robeyns et al., 2025). Coding agents thus provide a concrete
setting for recursive self-improvement because their executable
implementations can be directly modified and used as the basis for
subsequent improvements.

Research on self-improvement has a long history, including
self-referential learning and self-modifying policies (Schmidhuber,
1987; Schmidhuber et al., 1997), as well as the Gödel Machine’s
formulation of self-rewriting under provable utility improvement
(Schmidhuber, 2003). Within this area, evolutionary search offers one
approach to program improvement. Relevant historical foundations include
early evolutionary computation (Barricelli and others, 1954; Holland,
1975), genetic programming (Smith, 1980; Cramer, 1985; Dickmanns et al.,
1987), and meta-evolution of the improvement procedure itself
(Schmidhuber, 1987). Recent LLM-based systems revisit these ideas
through executable self-modification. DGM uses benchmark performance to
guide archive expansion (Zhang et al., 2026b), while HGM estimates
lineage potential from descendant outcomes (Wang et al., 2026a).
Hyperagents combines task solving and meta-level improvement in one
editable program (Zhang et al., 2026c). GEA and MGM share experience or
reuse trajectories and outcomes across groups and lineages (Weng et al.,
2026; Liu et al., 2026); SIFT reduces evaluation cost through LLM-based
ranking (Fu et al., 2026), and RQGM co-evolves evaluation criteria
(Iacob et al., 2026). Despite their different search and evaluation
strategies, these systems retain downstream task-derived evidence to
guide evolution. Elite instead studies whether implementation-level
inspection and mechanism integration can construct the next descendant
without downstream candidate task evaluation.

##### Implementation-level reasoning for code changes.

Recent work in software engineering explores implementation-level
reasoning without executing candidate code. ICE-Score and CodeJudge
assess generated code, while RePaCA reasons over buggy and patched
implementations to assess patch correctness (Zhuo, 2024; Tong and Zhang,
2024; Fuster-Pena et al., 2026). LLM critics assess repository-level
changes, sometimes using reference information such as gold test patches
(Yadavally et al., 2025). Agentic Rubrics scores patches against
repository-specific criteria (Raghavendra et al., 2026), while SWE-RM
learns reward models for fine-grained feedback without unit-test
execution (Shum et al., 2026). ASPIRE uses multiple agents to simulate
runtime behavior and reason about correctness without code execution
(Ramanan et al., 2024). PatchFusion combines edit-level evidence across
repair candidates without test outcomes at decision time (Yang et al.,
2026). These works address feedback, verification, or patch combination
for individual tasks, rather than how an agent’s own implementation
should evolve across generations. Elite draws on the inspectability of
code, using implementation-level reasoning and mechanism integration to
construct the next agent without running candidate agents on downstream
tasks or using evolved-candidate task outcomes to guide evolution.

## 3 Preliminaries

### 3.1 Formalizing Self-Improving Agents

Following prior work (Ren et al., 2026a), we formalize an agent
configuration as $`\mathcal{A}=(\theta,\Sigma)`$, where $`\theta`$
denotes the parameters of the LLM and $`\Sigma`$ denotes the agent
scaffold, including prompts, memory, tools, and control logic.
Self-improvement proceeds over generations $`t=0,1,\ldots,T-1`$, with
updates abstracted as
$`\mathcal{A}_{t+1}=\operatorname{\mathtt{IMPROVE}}(\mathcal{A}_{0:t};S_{t})`$,
where $`S_{t}`$ denotes update-relevant information such as task
outcomes, execution trajectories, critiques, verification signals, or
modifications (Weng et al., 2026; Liu et al., 2026; Zhang et al.,
2026a). Each updated agent persists as a basis for self-modification. We
focus on coding agents with a fixed LLM, so
$`\mathcal{A}_{t}=(\theta,\Sigma_{t})`$ throughout evolution. In our
setting, $`\Sigma_{t}`$ is implemented as a source-code repository
(Appendix A.2), allowing the scaffold and its modifications to be
inspected before downstream evaluation. Such inspection does not
establish downstream capability, but can provide implementation-level
information (Yadavally et al., 2025; Raghavendra et al., 2026; Shum et
al., 2026).

### 3.2 Evaluate-and-Select Self-improvement

Self-improving coding agents organize search differently, but many use
downstream task outcomes to guide evolution. We call this pattern
_evaluate-and-select_. Let $`\mathcal{T}=\{\tau_{1},\ldots,\tau_{N}\}`$
be a downstream evaluation set, and let $`R(\mathcal{A},\tau_{i})`$
denote the outcome of agent $`\mathcal{A}`$ on task $`\tau_{i}`$. Under
evaluate-and-select, these outcomes, or estimates obtained from partial
evaluation, enter $`S_{t}`$ and influence which agents, groups, or
lineages are retained, expanded, or allocated further evaluation. The
selection rule may be deterministic or stochastic, may operate over
retained historical agents, and may combine task outcomes with lineage
statistics, novelty, or resource costs; it need not select a single
highest-scoring winner. This formulation encompasses a range of existing
evaluation-driven strategies for selecting or allocating further effort
across agents, groups, and lineages (Zhang et al., 2026b; Wang et al.,
2026a; Weng et al., 2026; Liu et al., 2026; Fu et al., 2026; Iacob et
al., 2026).

Obtaining this evidence requires task execution: evaluating $`M`$
candidates on $`N`$ tasks costs $`MN`$ rollouts, while adaptive
allocation changes the number of evaluations assigned to each candidate
but does not eliminate this cost (Fu et al., 2026; Dai et al., 2026).
Repeated optimization against a fixed evaluation distribution may
further encourage benchmark-specific adaptation (Kapoor et al., 2024).
Separately, agent-level performance scores do not by themselves specify
how complementary implementation mechanisms should be combined. These
considerations motivate our question: _can coding agents decide which
changes to carry forward without downstream candidate task evaluation?_

## 4 Elite: Explore-then-Integrate Self-Improvement

Under the formalization in Section 3.1, the two paradigms differ in the
information used to update the agent. Evaluate-and-select uses
downstream task-derived evidence in $`S_{t}`$ to guide which agents or
lineages receive further evolutionary effort. Elite instead uses
exploratory implementations and their deterministic validity results;
downstream task outcomes of evolved candidates are not used in $`S_{t}`$
to guide integration or next-agent decisions. Rather than selecting an
entire child based on estimated performance, Elite treats
implementations as evidence and carries forward compatible mechanisms,
shifting the unit of evolutionary decision from whole candidates to
implemented mechanisms.

At each generation, Elite follows two stages. Explore generates a
portfolio of focused improvement hypotheses grounded in limitations of
the current agent, each of which is independently implemented from the
same parent to produce an executable alternative. Integrate then reasons
over the mechanisms realized in these alternatives and reimplements a
compatible subset into a coherent descendant. Deterministic gates are
used only to ensure structural and operational validity; no downstream
benchmark task, task-solving trajectory, or candidate performance score
is used to guide the next-agent decision.

### 4.1 Limitation-Driven Same-Parent Exploration

##### Limitation-driven hypothesis generation.

At generation $`t`$, Elite examines the implementation of the current
agent $`\mathcal{A}_{t}`$ together with a compact evolution history
$`m_{t}`$, which records prior self-modification instructions and their
accompanying code-based rationales. Rather than applying a fixed set of
mutation categories, a proposal operator $`\mathcal{P}`$ jointly
generates $`K`$ focused improvement hypotheses,

```math
\mathcal{H}_{t}=\mathcal{P}(\mathcal{A}_{t},m_{t};K)=\{h_{t}^{(1)},\ldots,h_{t}^{(K)}\}. \tag{1}
```

Each hypothesis specifies the capability to improve, a concrete
limitation in the current implementation, a focused mechanism for
addressing it, and the conditions under which the implementation is
complete (Appendix A.3.1).

##### Same-parent executable exploration.

Each hypothesis is implemented independently against the same parent
$`\mathcal{A}_{t}`$. An implementation operator $`\mathcal{E}`$ produces
a patch $`\Delta_{t}^{(k)}`$, which is applied to $`\mathcal{A}_{t}`$ to
obtain an executable exploratory child:

```math
\Delta_{t}^{(k)}=\mathcal{E}(\mathcal{A}_{t},h_{t}^{(k)}),\qquad\mathcal{A}_{t}^{(k)}=\operatorname{Apply}(\mathcal{A}_{t},\Delta_{t}^{(k)}),\qquad k=1,\ldots,K. \tag{2}
```

Because all exploratory children are independently instantiated from the
same parent, their modifications provide directly comparable
implementation-level alternatives rather than sequentially accumulated
changes. This common reference point also makes it possible to reason
about mechanisms across children before constructing the next
descendant.

##### Deterministic validity filtering.

Before integration, Elite applies a lightweight deterministic gate
$`G_{\mathrm{exp}}(\mathcal{A})\in\{0,1\}`$ to exclude invalid
program-level modifications. The gate checks structural and operational
validity, such as executability, deployability, required agent
interfaces, and permitted modification scope. Python scripts perform
compilation, imports, and predefined assertions; Appendix A.5.2 details
the checks. The valid alternatives form

```math
\mathcal{V}_{t}=\left\{\mathcal{A}_{t}^{(k)}\mid G_{\mathrm{exp}}(\mathcal{A}_{t}^{(k)})=1\right\}. \tag{3}
```

Importantly, $`G_{\mathrm{exp}}`$ is an admissibility check rather than
a measure of downstream capability: it uses no benchmark task outcomes
or candidate performance scores.

##### From exploration to integration.

Exploration therefore produces a set of independently implemented,
operationally valid alternatives rather than a ranked population. Since
no downstream task score identifies a winning child in
$`\mathcal{V}_{t}`$, the remaining decision is not which child should
continue as a whole, but which mechanisms implemented across these
children can be carried forward together. Section 4.2 addresses this
decision through compatibility-aware mechanism integration.

### 4.2 Compatibility-Aware Mechanism Integration

##### From children to mechanisms.

Given the valid alternatives $`\mathcal{V}_{t}`$, Elite shifts the
decision unit from whole children to their implemented mechanisms.
Rather than assigning each child a scalar score or predicting which
child would perform best, the integrator treats the implementations
themselves as evidence. Mechanisms are identified from the intended
improvement $`h_{t}^{(k)}`$ together with its realized implementation,
allowing a mechanism to be considered independently of the child that
contains it and jointly with compatible mechanisms realized by other
children. For each valid child in $`\mathcal{V}_{t}`$, the integrator
receives its hypothesis $`h_{t}^{(k)}`$, a summary of the realized patch
$`\Delta_{t}^{(k)}`$, and the gate results; the full patch remains
available for inspection. The integrator first reviews this evidence
across all valid children and then inspects the full implementations of
a small set of relevant alternatives. The underlying LLM performs
integration through implementation-level reasoning guided by the
structured prompt in Appendix A.3.3, without a separate compatibility
model or task-performance predictor.

##### Compatibility-aware mechanism reasoning.

Using this implementation-level evidence, the integrator reasons about
candidate mechanisms along five dimensions: complementary, when they can
operate together; redundant, when they substantially overlap;
conflicting, when they make incompatible assumptions about interfaces,
state, or control flow; overly complex, when they introduce unnecessary
machinery; and incomplete, when the intended mechanism is only partially
realized. These judgments determine which mechanisms can be carried
forward together, without reducing each child to a single
predicted-quality score. Based on these judgments, an integration
operator $`\mathcal{I}`$ constructs an integrated patch against the
original parent:

```math
\Delta_{t}^{\mathrm{int}}=\mathcal{I}(\mathcal{A}_{t},\mathcal{V}_{t}),\qquad\mathcal{A}_{t}^{\mathrm{int}}=\operatorname{Apply}(\mathcal{A}_{t},\Delta_{t}^{\mathrm{int}}). \tag{4}
```

Importantly, integration operates at the mechanism level rather than by
mechanically concatenating or sequentially applying exploratory patches.
The selected mechanisms are reimplemented as a coherent modification of
the common parent $`\mathcal{A}_{t}`$, allowing shared interfaces,
dependencies, and control flow to be reconciled when mechanisms
interact.

##### Deterministic descendant acceptance.

The integrated descendant is accepted only if it passes a stricter
deterministic gate $`G_{\mathrm{acc}}(\mathcal{A})\in\{0,1\}`$, which
verifies structural and operational validity. It adds smoke tests of the
tool-call protocol and main execution flow. Failure retains the current
parent; details appear in Appendix A.5.2. The next generation is
therefore

```math
\mathcal{A}_{t+1}=\begin{cases}\mathcal{A}_{t}^{\mathrm{int}},&G_{\mathrm{acc}}(\mathcal{A}_{t}^{\mathrm{int}})=1,\\
\mathcal{A}_{t},&\text{otherwise}.\end{cases} \tag{5}
```

As with $`G_{\mathrm{exp}}`$, this gate verifies structural and
operational validity rather than downstream capability. No downstream
benchmark task, task-solving trajectory, or candidate performance score
is used to determine which mechanisms are integrated or whether the
resulting descendant is accepted as the next agent.

##### Downstream evaluation cost.

Unlike the direct evaluate-and-select setting in Section 3.2, Elite
requires no downstream candidate-task rollouts for next-agent decisions.
Its cost instead comes from generating executable alternatives,
inspecting their implementations, and constructing the integrated
descendant; this decision cost is independent of the size of a
downstream evaluation set. The complete procedure is summarized in
Algorithm 1 in Appendix A.6.

## 5 Experiments

### 5.1 Experimental Setup

##### Benchmarks.

We evaluate on SWE-bench Pro, SWE-bench Verified (Deng et al., 2025;
Jimenez et al., 2024), and Polyglot (Paul Gauthier, 2024). We use a
fixed 60-task subset of SWE-bench Pro for the evolution comparison,
while SWE-bench Verified and Polyglot serve as transfer benchmarks.
After evolution, the resulting agents are frozen and evaluated on the
same Pro subset and the two transfer subsets without further adaptation.
Detailed benchmark and task-subset information is provided in
Appendix A.4.

##### Compared methods and evolution protocol.

We compare Elite with DGM (Zhang et al., 2026b) and HGM (Wang et al.,
2026a) using DeepSeek-V4-Flash and Qwen-3.7-Plus. DGM and HGM use
outcomes from the Pro subset as evolutionary feedback, whereas Elite
uses no downstream task outcomes during evolution. For each backbone,
all methods start from the same scaffold and use the same LLM for both
self-modification and task solving, holding the starting agent and model
fixed across methods. All three methods have three independent DeepSeek
evolution runs; Qwen has three Elite runs and one run per baseline. A
full evolution run is the unit of replication. Run-level results and
sample SDs are in Appendix A.1.2; configurations are in Appendix A.5.

##### Metrics.

We report final task success rate as the primary performance metric. To
characterize the resources consumed during self-improvement, we
additionally report downstream task-evaluation count, self-modification
throughput (Self-Mod./h), estimated evolution-stage token usage,
end-to-end wall-clock time, and estimated API cost.

### 5.2 Main Results

##### Performance.

Table 1 summarizes performance across both LLM backbones. Under
DeepSeek-V4-Flash, Elite improves Pro performance from 60.0% to 85.6%,
slightly below DGM and HGM at 86.7% and 88.3%, respectively, which use
downstream task evaluation feedback to guide evolution. However, its
advantage emerges when directly evaluated on SWE-bench Verified and
Polyglot without further evolution, achieving 73.3% and 69.3%,
respectively. These results indicate that the improvements produced by
Elite transfer across benchmarks despite the absence of task-specific
evaluation feedback during evolution. In contrast, DGM and HGM, evolved
on Pro, show limited gains or even regression on these transfer
benchmarks. The same pattern holds under Qwen-3.7-Plus, although the
trade-off becomes more pronounced: evolving without downstream task
feedback is associated with a larger performance gap behind DGM and HGM
on Pro (45.6% vs. 50.0% and 48.3%), while Elite still achieves better
cross-benchmark transfer (56.7% on Verified and 61.3% on Polyglot).

##### Evolution efficiency.

Table 2 reports evolution resource usage. Under DeepSeek-V4-Flash, Elite
completes evolution in a mean of 4.90 hours, compared with 43.15 hours
for DGM and 15.66 hours for HGM, yielding observed wall-clock speedups
of 8.81$`\times`$ and 3.20$`\times`$ under the reported execution
settings. A key source of this efficiency is the elimination of
candidate task evaluations, compared with 810 for DGM and 800 for HGM.
These task rollouts consume additional time, tokens, and API expenditure
during evolution. Elite achieves 16.35 self-modification attempts per
hour, compared with 0.58 for DGM and 3.77 for HGM. Under Qwen-3.7-Plus,
Elite similarly avoids candidate task evaluations, averaging 7.35 hours,
approximately \$20, and 10.89 self-modification attempts per hour, with
lower estimated token usage than both baselines.

### 5.3 Transfer and Evolution Analysis

Figure 2: Cross-backbone scaffold portability. Scaffolds evolved in the

##### Cross-backbone scaffold portability.

We further evaluate cross-backbone scaffold portability by pairing
scaffolds evolved with one backbone with the other backbone, without
additional evolution. All scaffolds are evolved only in the SWE-bench

transferred performance on all three benchmarks under Qwen-3.7-Plus. In
the reverse direction, the Qwen-evolved Elite scaffold likewise achieves
the best or second-best transferred performance across the three
benchmarks. Overall, these results provide evidence that some scaffold
improvements produced by Elite remain useful when transferred across the
two evaluated backbones.

##### Post-hoc evolution dynamics.

We analyze the evolution process after it has concluded; all downstream
task outcomes reported in this analysis are measured post hoc and never
exposed to Elite during evolution. Figure 3(a) compares the seven
exploratory children and the integrated descendant from the first
accepted step on the same 60 SWE-bench Pro tasks. The exploratory
children exhibit substantial outcome variation: six achieve 76.7–83.3%,
while one falls to 3.3%. The integrated descendant reaches 81.7%,
outperforming five of the seven children while remaining below the
highest exploratory score of 83.3%. This comparison illustrates that
Elite can construct a competitive descendant without observing candidate
task performance, although integration does not necessarily recover the
best-performing exploratory alternative.

Figure 3(b) shows the complete $`T=10`$ evolution process. The retained
agent is updated only when an integrated descendant passes the
acceptance gate; otherwise, the current agent is carried forward to the
next generation. Across five accepted updates, post-hoc task performance
improves overall from 60.0% to 86.7%, despite two intermediate
regressions. After the first accepted update reaches 81.7%, subsequent
evolution adds a further 5.0 percentage points. This non-monotonic
trajectory is consistent with the gate’s intended role: it enforces
structural and operational validity without guaranteeing downstream task
improvement. An additional sampling-based comparison between integrated
descendants and exploratory populations is provided in Appendix A.1.3.

##### Mechanism-level integration.

We further inspect the implementations to examine what integration
carries forward. Figure 3(c) presents a representative composition case
in which two same-parent exploratory children independently introduce
complementary mechanisms: one enables complete output reading, while the
other incorporates exit-status feedback. Rather than selecting either
child as the next agent, Elite integrates both mechanisms into a single
coherent descendant. In the analyzed DeepSeek run, integration
incorporates primary mechanisms from 25 of 41 eligible proposals.
Together, the case study and incorporation analysis illustrate how
mechanisms from different exploratory children can be carried forward
into one descendant without ranking children by downstream task
performance. Additional composition and refinement cases are provided in
Appendix A.1.4; proposal diversity, gate outcomes, and repository-level
analyses are reported in Appendix A.1.1.

##### Design ablations.

Table 4 compares Elite with seven variants covering child selection,
exploration and integration, and other components. _Select-one_ retains
$`K=7`$ same-parent exploration but replaces integration with an LLM
decision selecting one child. _SIFT-style Select-one_ instead selects a
child using pairwise LLM judgments aggregated with a Bradley–Terry model
(Fu et al., 2026). _Evaluation-based Select-one_ evaluates the seven
independently implemented children on the same 30 Pro tasks within each
round and selects the highest-scoring child instead of integrating them.
_Single exploration_ sets $`K=1`$ and directly uses the exploratory
child as the next agent, removing both multi-branch exploration and
integration. _Direct joint implementation_ generates seven improvement
proposals and implements them jointly as one child, omitting the
separate exploratory implementations. _w/o hypothesis generation_
removes structured hypothesis generation and directly proposes
self-modifications, retaining $`K=7`$, integration, and both gates. _w/o
deterministic gates_ removes both validity gates, allowing all
exploratory children into integration and accepting the resulting
descendant without deterministic filtering. Further implementation
details and budgets are provided in Appendix A.5.2.

##### Integration versus child selection.

With seven independently implemented children retained, Elite averages
76.1%, exceeding Select-one (71.8%) and SIFT-style Select-one (67.7%).
Evaluation-based Select-one achieves higher target Pro performance
(91.7% versus 85.6%), while Elite has higher cross-benchmark transfer
scores on Verified (73.3% versus 70.0%) and Polyglot (69.3% versus
62.0%). These observed results support mechanism integration as a
competitive alternative to the evaluated selection strategies without
candidate task feedback; the selection comparisons are limited to single
runs.

##### The role of executable exploration.

Direct joint implementation generates seven proposals but implements
them jointly without independent executable children, reducing the
average from 76.1% to 72.1%. This supports obtaining concrete
implementation-level evidence before integration. Single exploration
scores 69.9%, reflecting both reduced exploration breadth and removal of
multi-child integration; it does not match full Elite’s candidate count
or total compute.

##### Other components.

Removing structured hypothesis generation reduces the average to 71.0%,
while removing deterministic gates reduces it to 52.0%. These results
support their complementary roles.

##### Sensitivity to exploration width.

We vary the number of same-parent exploratory children
$`K\in\{3,5,7,9\}`$ while keeping the remaining settings fixed. Table 5
reports three-run means, with $`K=7`$ as the default configuration.
Among the tested widths, $`K=9`$ achieves the highest Pro score of
88.9%, while $`K=7`$ performs best on both transfer benchmarks. Overall,
the average score increases from 70.5% at $`K=3`$ to 76.1% at $`K=7`$
and remains comparable at 75.6% for $`K=9`$, suggesting diminishing
returns from further increasing exploration width rather than a
monotonic benefit from generating more exploratory children.

## 6 Conclusion

We introduced Elite, an Explore-then-Integrate framework for studying
whether coding-agent self-improvement can proceed without downstream
candidate task evaluation. Rather than using task outcomes to rank
evolved candidates, Elite explores multiple executable modifications
from the same parent and constructs the next agent by reasoning over
their implementation mechanisms. Our results provide evidence for the
feasibility of substantial coding-agent self-improvement without
downstream candidate task feedback in the setting studied here.

##### Limitations.

Our evaluation focuses on coding agents and selected benchmark subsets,
with limited repetitions for some comparisons. Broader task coverage and
additional runs would help characterize variability across settings.
Elite relies on implementation-level reasoning and validity checks to
guide evolution; downstream performance can fluctuate across accepted
updates, making longer-term evolution an important subject for further
study. The current implementation also maintains a single lineage.
Extending it with an archive of historical agents could preserve
alternative evolutionary paths and support a broader investigation of
search diversity. Appendix A.7 provides further discussion.

#### A.1.3 Sampled Exploration–Integration Comparison

We use a post-hoc diagnostic on one DeepSeek-V4-Flash evolution run to
compare integrated candidates with their valid exploratory populations.
Evaluations occur after acceptance decisions and never inform evolution.
Figure 7 shows the five accepted updates.

##### Tasks and sampling.

We randomly draw 10 SWE-bench Pro tasks independently of agent outcomes
and keep this subset fixed across all comparisons. Each integrated
candidate is evaluated once per task. Let $`m_{t}\geq 2`$ denote the
number of exploratory children passing the exploration gate at step
$`t`$. Using a fixed random seed, we randomly order tasks and children,
then assign two distinct children to each task using a balanced cyclic
schedule. The resulting 20 distinct child–task pairs cover all valid
children in this study, with evaluation counts differing by at most one
between children. Assignments use neither downstream outcomes nor
integration decisions.

Figure 7: Sampled exploration–integration comparison. Filled markers
show recorded comparisons at accepted rounds 2, 4, 5, 6, and 9. Hollow
markers carry forward the preceding retained agent and its source
exploratory estimate after rejection or failure; they are not outcomes
of the unaccepted children or newly generated exploratory populations.
The Mean column equally averages the five accepted comparisons, counting
each once.

##### Reported quantities and evaluation budget.

The exploration estimate is the mean binary success rate over the 20
sampled child–task outcomes; the integration score is the success rate
on the 10 integrated-agent rollouts. Their difference, in percentage
points, is the integration gap. Each comparison therefore uses
$`20+10=30`$ rollouts. The complete diagnostic covers seven integration
attempts, requiring $`7\times 30=210`$ fresh rollouts; the five accepted
comparisons shown in Figure 7 account for $`5\times 30=150`$ of these.

##### Results and interpretation.

The integrated descendant exceeds the sampled exploratory mean at each
of the five accepted updates, with step-averaged scores of 68.0% and
48.0%, respectively (a 20.0 pp gap). We average these five comparisons
equally. Averaging all ten displayed rounds would instead weight
checkpoints by their retention duration. These are descriptive
comparisons on one fixed subset and one accepted lineage; they do not
establish a general advantage across tasks or runs. Because each child
solves only a subset of the diagnostic tasks, the samples estimate
population-average performance on this subset and cannot identify an
oracle-best child.

### A.2 Initial Agent

#### A.2.1 Repository overview

Figure 14: Initial coding agent repository.

The initial scaffold $`\Sigma_{0}`$ is an executable source-code
repository containing the agent’s prompts, tools, utilities, and control
logic. Given a task description and a working repository, the agent uses
an LLM to inspect the codebase, make changes, and perform local checks.
It exposes two tools: bash executes shell commands, and editor supports
file inspection, creation, and whole-file editing. All methods start
from the same scaffold for a given backbone, and the same initial agent
is evaluated across all three benchmarks. Figure 14 shows the repository
structure.

#### A.2.2 Tools

The initial agent has two tools. Together, they support repository
inspection, code modification, and local verification.

##### Bash.

The bash tool accepts a shell command through its command argument and
executes it in the task environment. The agent can use it to navigate
and search the repository, inspect dependencies and build
configurations, run tests, and review the resulting Git diff. The
implementation collects standard output and filtered standard error and
applies a 120-second command timeout. Each invocation starts a new Bash
session, so commands should explicitly establish their working directory
when necessary. Changes to files remain available to subsequent tool
calls.

##### Edit.

The file-editing tool is implemented in tools/edit.py and exposed to the
model under the name editor. It takes an absolute path and supports
three commands. The view command displays a file with line numbers or
lists a directory to a depth of two levels; file contents are truncated
after 10,000 characters before line numbers are added. The create
command writes the supplied file_text to a new file and rejects an
existing path. The edit command replaces the complete contents of an
existing file with file_text. This initial interface therefore performs
file creation and whole-file editing.

### A.4 Benchmarks and Task Subsets

We evaluate the agents on fixed subsets of SWE-bench Pro, SWE-bench
Verified, and Aider Polyglot, containing 60, 50, and 50 tasks,
respectively. SWE-bench Pro is used to provide evolutionary feedback for
the baselines, whereas SWE-bench Verified and Polyglot are used only for
post-evolution transfer evaluation and never provide feedback during
ELITE evolution. The benchmark referred to as Verified in the main
results is specifically SWE-bench Verified. The task identifiers are
listed in Tables 8–10.

##### Task execution.

Each task is run in a separate container with a fresh agent process and
the benchmark-specified repository state. An agent run may include
multiple model responses, tool calls, and local tests. The resulting
code changes are assessed by the corresponding benchmark evaluator.

##### Evolution feedback.

DGM and HGM use SWE-bench Pro task outcomes during evolution. ELITE does
not use downstream task outcomes from evolved candidates to decide
integration or the next-agent update. Running available tests while
solving an individual task is distinct from returning benchmark
evaluation results to the outer self-improvement procedure.

### A.5 Experimental Settings

#### A.5.1 Evolution Configuration

##### Shared model settings.

We use DeepSeek-V4-Flash and Qwen-3.7-Plus as LLM backbones. All methods
share the same initial scaffold for a given backbone. The maximum output
budget per model response is 16,384 tokens (MAX_OUTPUT_TOKENS=16384);
hypothesis generation uses the same budget (PORTFOLIO_MAX_TOKENS=16384).
Thinking is enabled through DEEPSEEK_THINKING=enabled for DeepSeek and
QWEN_ENABLE_THINKING=1 for Qwen.

##### Controlled execution environment.

Agent execution and deterministic validity checks run inside isolated
Docker sandbox containers built from the experiment runtime image. Each
exploratory or integrated child is executed in a separate containerized
working copy with the timeout shown in Table 11; containers are removed
after the attempt; the host process handles orchestration and records
status and artifacts. This containment isolates child mutations and tool
execution from the host environment.

##### Evolution settings.

Table 11 summarizes the main search parameters. Parallel workers denotes
the configured concurrency limit. ELITE generates $`K=7`$ exploratory
children per valid hypothesis portfolio for both backbones. It uses
eight workers for both backbones; the maximum exploration concurrency is
therefore $`\min(8,7)=7`$. Integration follows exploration. HGM uses the
same search configuration for both backbones, with 20 parallel workers
shared by expansion and evaluation.

##### Search budgets.

Following HGM’s evaluation-budget convention (Wang et al., 2026a), HGM
is configured for 800 task evaluations, and DGM is compared over a
search prefix with approximately the same evaluation count. ELITE
instead uses a fixed ten-generation horizon, since it performs no online
benchmark evaluation of new descendants. These are method-specific
search budgets, not matched compute budgets.

##### Runtime comparison.

All methods run on the same server using the execution settings in
Table 11. Search concurrency and task-evaluation concurrency operate at
different levels. Under the settings in Table 11, DGM uses one
self-modification worker, but evaluates each candidate’s benchmark tasks
with up to eight parallel workers. HGM follows the official 20-worker
configuration, sharing its pool between expansion and evaluation. Elite
uses an eight-worker pool for $`K=7`$ same-parent exploratory children,
followed by integration; its exploration concurrency is therefore at
most seven, even if the pool limit is raised to 20. Increasing candidate
counts to occupy additional workers would change search breadth, while
identical worker limits alone would not ensure equal active concurrency
or resource use. We therefore report practical turnaround for the
evaluated configurations and stopping budgets, including search-time
task evaluation where applicable. The time ratios remain
configuration-dependent; task-evaluation counts and billed API
expenditure provide complementary measures of evolution cost.

##### Repetitions and evaluation budget.

We report three independent evolution runs for Elite with each backbone
and for DGM and HGM with DeepSeek; the Qwen baselines use one run each.
Repeating an evaluation-driven baseline requires rerunning the entire
search, including approximately 800 task evaluations, rather than simply
reevaluating its final agent. Each task evaluation can involve multiple
LLM calls, repository interactions, and test execution, incurring both
runtime and API expenditure. Post-hoc analysis also requires substantial
evaluation beyond the main results: The accepted-lineage analysis in
Figure 3(b) likewise requires full 60-task evaluations of intermediate
checkpoints. Evaluating every integrated candidate over $`T=10`$ rounds
would require at most $`60\times 10=600`$ rollouts for one backbone on
this benchmark. The first-step comparison covers eight agents on 60
tasks (480 agent–task outcomes), while the five-step diagnostic covers
150 outcomes. These analyses examine intermediate and exploratory agents
whose task performance is not observed during Elite evolution. Tables 6
and 7 report individual run results and sample standard deviations.

#### A.5.2 Additional Experimental Settings and Validity Gates

##### Experimental settings.

1.  (1)
    Effectiveness across initial scaffolds. We use mini-swe-agent v2.4.6
    with a fixed Claude-opus-5.5 backbone. Ten evolution rounds yield
    six accepted children, numbered by acceptance order. We evaluate the
    initial agent and accepted child 6 on Pro, Verified, and Polyglot
    using 60, 50, and 50 tasks, respectively. Accepted children 1 and 3
    are also evaluated on the 60 Pro tasks. The retained children are
    evaluated post hoc, without feeding their scores back into
    evolution. Table 3 reports the results.
2.  (2)
    Ablation experiments. All variants use the main DeepSeek
    configuration, initial scaffold, evaluation tasks, and number of
    evolution rounds. Full Elite and the no-gates ablation use three
    independent evolution runs; all other variants use one. Table 4
    reports their scores. Candidate counts and computation follow each
    variant’s pipeline.
    1.  i.
        Alternative selection strategies. These variants retain seven
        independently implemented children and replace mechanism
        integration with child selection. (a) _Select-one (LLM-based)_
        uses an LLM to choose one child as the next agent. (b)
        _SIFT-style Select-one_ uses pairwise LLM judgments aggregated
        with a Bradley–Terry model (Fu et al., 2026). Both LLM-based
        strategies operate without downstream candidate scores. (c)
        _Evaluation-based Select-one_ evaluates all seven children on
        the same 30 Pro tasks within each round and selects the
        highest-scoring child, requiring $`7\times 30=210`$ child–task
        evaluations per round.
    2.  ii.
        Exploration and integration ablations. (a) _Single exploration_
        sets $`K=1`$ and directly retains the valid exploratory child as
        the next agent, removing multi-branch exploration and
        integration. (b) _Direct joint implementation_ generates seven
        improvement proposals and implements them jointly as one child,
        omitting the separate exploratory implementations and their
        subsequent integration.
    3.  iii.
        Other component ablations. (a) _w/o hypothesis generation_
        directly proposes self-modifications without structured
        hypothesis generation, retaining $`K=7`$, integration, and both
        validity gates. (b) _w/o deterministic gates_ removes both
        validity gates, allowing all exploratory children into
        integration and accepting the integrated child without
        deterministic filtering.

predefined program assertions. These checks determine structural and
operational validity without LLM judgments or downstream benchmark
scores. Table 12 summarizes their scope and failure handling. Their

correctness or downstream task performance.

### A.6 Elite Algorithm

Algorithm 1 summarizes the complete Elite self-improvement procedure. At
each generation, valid exploratory children are integrated into a
candidate descendant; if no child passes the exploration gate or the
integrated descendant fails the acceptance gate, the current agent is
retained for the next generation.

### A.7 Mechanism, Scope, and Future Work

##### Implementation-level reasoning.

The underlying LLM parameters remain fixed, while the scaffold controls
tool use, execution feedback, and the problem-solving process. The
model’s programming knowledge and access to source code allow it to
identify concrete limitations, such as missing exit-status feedback,
blocking output reads, or incomplete parsing. Executable exploration
makes the proposed mechanisms, interfaces, and dependencies explicit,
providing evidence for integration to reconcile complementary
functionality, redundancy, and conflicts. For example, the local code
probe in Appendix A.1.4 shows that the integrated implementation
combines exit-status feedback with continuous output reading, returning
all 100,000 output lines and the correct exit code. Deterministic gates
check operational validity, while benchmark evaluations measure the
resulting task performance.

##### Evolution dynamics.

The observed trajectories show overall gains alongside intermediate
variation. In the original DeepSeek run, Pro improves from 81.7% after
the first accepted update to 86.7% at the end, with temporary declines
following two intermediate accepted updates. In the mini-swe-agent run,
ten evolution rounds yield six accepted children. Pro increases from
71.7% initially to 73.3%, 80.0%, and 83.3% for accepted children 1, 3,
and 6, respectively (Table 3). These results illustrate improvement over
multiple accepted updates. Longer evolution runs would help characterize
how progress changes as readily identifiable implementation issues are
resolved and remaining bottlenecks depend increasingly on task behavior
and interactions among mechanisms.

##### Evaluation scope.

Our evaluation focuses on coding tasks, covering two LLM backbones in
the main comparison and an additional scaffold–backbone combination
using mini-swe-agent. The DeepSeek comparison includes three independent
runs per method; Qwen baselines and most ablation variants use one run.
Evaluation uses selected benchmark subsets. Additional repetitions and
broader task coverage would improve the precision of performance
estimates and help characterize how improvement depends on the initial
scaffold and the underlying model’s programming capabilities. Beyond
coding, evaluation could span diverse task domains, interaction
environments, and modalities, including long-horizon tool use (Li et
al., 2026b), memory-dependent tasks (He et al., 2026; Nanbo et al.,
2026; Ren et al., 2026b), web search (Li et al., 2026c; Chen et al.,
2026), and multimodal interaction (Li et al., 2026d), while assessing
safety and robustness across these settings (Li et al., 2026a; Das et
al., 2026).

##### Future work.

A natural extension is to combine same-parent integration with
archive-based search. An archive could retain historical agents, select
a parent for exploration and integration, and add the resulting valid
descendant while preserving alternative lineages. This would allow the
search to revisit intermediate stepping stones and explore multiple
evolutionary paths. Developing archive-retention and parent-scheduling
strategies based on implementation evidence is a promising direction for
extending Elite while preserving its independence from downstream
candidate task feedback.
