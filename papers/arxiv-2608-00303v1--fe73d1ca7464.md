# CrystalMem: Elastic Memory for Self-Evolving LLM Agents via Knowledge Crystallization

Beining Wu    Jun Huang ^(†)^(†)thanks: Beining Wu and Jun Huang are
with the Department of Electrical Engineering and Computer Science,
South Dakota State University, Brookings, SD 57006 USA.  
E-mail: Wu.Beining@jacks.sdstate.edu; Jun.Huang@sdstate.edu

###### Abstract

Memory for self-evolving large language model (LLM) agents is often
provisioned as if its byte budget only grows. Cloud platforms, however,
adjust quotas with load and cost, and we show that capability does not
follow the budget back up: after a squeeze-and-recover cycle, the agent
settles below its pre-squeeze level, a gap we call _memory hysteresis_.
The cause is structural. Deletion and one-way compression discard the
material needed for later rebuilding, and we prove that any policy that
only keeps or drops entries carries a residual-deficit floor. We propose
CrystalMem (Crystallized Memory), an elastic memory sidecar that demotes
entries across four fidelity states under a crystallization-energy
schedule, orders demotions by advantage-weighted influence with
dependency coupling, and recovers capability through verified
recrystallization under explicit compute and byte caps. Across seven
environments, seventeen methods, and six backbones, with multi-tenant
serving and a physical edge–cloud deployment, CrystalMem achieves the
highest restored capability in every setting and closes the loop left
open by every baseline. From a $`50\%`$ byte budget, CrystalMem matches
the strongest budgeted baseline at full provision on every environment;
at equal budgets, it leads by $`+4.6`$ pp on average.

###### Index Terms: 

Agent memory, self-evolving LLM agents, knowledge crystallization,
elastic resource management, cloud computing, LLM serving, memory
management, energy efficiency.

## I Introduction

Self-evolving large language model (LLM) agents improve by accumulating
experience. Trajectories, distilled skills, and facts are written to an
external memory and retrieved for later tasks \[[1](#bib.bib1),
[2](#bib.bib2), [3](#bib.bib3), [4](#bib.bib4), [5](#bib.bib5),
[6](#bib.bib6), [7](#bib.bib7)\]. Production systems now treat this
store as a managed memory plane, with consolidation
pipelines \[[8](#bib.bib8), [9](#bib.bib9), [10](#bib.bib10)\] and
value-based governance \[[11](#bib.bib11), [12](#bib.bib12),
[13](#bib.bib13), [14](#bib.bib14), [15](#bib.bib15)\] deciding what
stays. One layer below, the cloud serving stack already treats resources
as elastic: compute is scheduled \[[16](#bib.bib16), [17](#bib.bib17),
[18](#bib.bib18), [19](#bib.bib19), [20](#bib.bib20), [21](#bib.bib21),
[22](#bib.bib22)\], the key–value cache is paged and
reclaimed \[[23](#bib.bib23)\], and quotas move with load and cost.
Agent memory is the exception. Its byte budget is usually provisioned as
if it could only grow, although a shared cloud offers no such guarantee.

Budgets move in every other tier, but prior work has not asked what a
round trip of the memory budget does to agent capability. Our
measurements show that capability does not simply return with the bytes.
When the quota falls, current stores shed bytes by deleting entries or
by compressing them in one direction; both choices discard material that
would be needed to rebuild the entry later. When the quota returns,
nothing regenerates. The agent settles below its pre-squeeze level even
though the original provision is fully available again
(Figs. [1](#S3.F1 "Fig. 1 ‣ III-B The Memory Hysteresis Phenomenon ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")
and [2](#S3.F2 "Fig. 2 ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")).
We call this gap _memory hysteresis_: the store’s capability depends not
only on the budget it has, but also on the path the budget took.
Retention therefore has to become reversible. Compression ladders that
demote entries into coarser representations \[[24](#bib.bib24)\] keep
more information than deletion, but they only move downward, so each
squeeze leaves a permanent loss. Reversible compression
exists \[[25](#bib.bib25)\], yet reversibility alone does not decide
which entry to demote under a falling budget or whether a later
reconstruction is faithful. Value-based governance chooses better
survivors \[[11](#bib.bib11), [26](#bib.bib26), [27](#bib.bib27),
[28](#bib.bib28)\], but a policy that keeps an entry verbatim or drops
it leaves no residue to rebuild from. Closing the loop requires fidelity
states to demote into, a schedule that moves entries in both directions
as the budget moves, and a gate that verifies what returns.

These requirements sit across three research lines. Agent memory and
self-evolution build stores that grow, consolidate, and retrieve under a
fixed provision \[[29](#bib.bib29), [8](#bib.bib8), [9](#bib.bib9),
[10](#bib.bib10), [30](#bib.bib30)\]. Memory compression and governance
reduce or curate the store through one-way ladders, opportunistic
reversibility, or binary selection \[[31](#bib.bib31), [24](#bib.bib24),
[25](#bib.bib25), [32](#bib.bib32), [11](#bib.bib11),
[33](#bib.bib33)\]. Elastic serving and evaluation reclaim resources
below the memory plane and measure memory at fixed
provisions \[[23](#bib.bib23), [34](#bib.bib34), [16](#bib.bib16),
[17](#bib.bib17), [35](#bib.bib35), [36](#bib.bib36), [37](#bib.bib37),
[38](#bib.bib38), [39](#bib.bib39), [40](#bib.bib40), [41](#bib.bib41),
[42](#bib.bib42), [43](#bib.bib43), [44](#bib.bib44)\]. None treats
fidelity as a two-way function of the byte budget, schedules demotion
and promotion against that budget, or verifies what a promotion brings
back. As a result, no current system closes the capability loop under an
elastic memory budget.

To close this loop, we introduce CrystalMem (Crystallized Memory), an
elastic memory sidecar for self-evolving agents. CrystalMem treats
retention as reversible state assignment through two coupled mechanisms.
First, _knowledge crystallization_ assigns every entry to one of four
fidelity states, from full form down to a minimal trace. A budget-driven
schedule prices each demotion by the utility it forgoes now plus the
compute a later promotion will cost, then takes the cheapest moves first
until the store fits the incoming budget. Entry values come from an
influence estimator that attributes task outcomes to the entries that
served them. Value also flows over a dependency graph, so entries that
anchor other entries sink last. Second, _verified recrystallization_
keeps a residue and a set of invariants for every demoted entry. When
the budget expands, the store regenerates entries from their residues
and admits only reconstructions that pass the invariant check, under an
explicit cap on regeneration compute. Both passes run inside the serving
path with one sorted sweep per stage and no training. Deletion becomes
the last resort instead of the default.

In summary, our main contributions are as follows. They divide into
findings and designs: the phenomenon and its floor are findings; the
crystallization mechanisms are designs; the serving stack and benchmark
environments are adopted from prior work and are not claimed as
contributions.

- •
  We identify and measure _memory hysteresis_ in elastic-budget agent
  memory: a squeeze-and-recover cycle leaves capability below its
  pre-squeeze level even after the budget fully returns. We formalize
  the effect with a loop-area metric and prove a residual-deficit floor
  for keep-or-drop policies.
- •
  We propose CrystalMem: a four-state fidelity ladder scheduled by
  crystallization energy under the live budget, entry values estimated
  from advantage-weighted influence with dependency coupling, and
  verified recrystallization under explicit compute and byte caps. We
  prove feasibility, near-optimality, and loop-closure guarantees.
- •
  We evaluate CrystalMem against seventeen methods across seven
  environments and six backbones, in multi-tenant serving, and on a
  physical edge–cloud testbed. CrystalMem closes the loop left open by
  every baseline, matches full-provision capability at half the byte
  budget, and recovers capability at a fraction of the energy needed to
  re-experience the underlying episodes.

## II Related Work

### II-A Agent Memory and Self-Evolution

A self-evolving large language model (LLM) agent improves without weight
updates by writing experience into external memory and retrieving it at
inference time \[[1](#bib.bib1), [2](#bib.bib2), [45](#bib.bib45),
[46](#bib.bib46), [47](#bib.bib47)\]. One line of work builds the store
itself. Xu et al. \[[29](#bib.bib29)\] propose _A-MEM_, which links and
grows notes for long-horizon recall; *MemGPT* \[[8](#bib.bib8)\] pages
entries between the context window and external storage;
*Mem0* \[[9](#bib.bib9)\] extracts and consolidates long-term memory at
production scale; and *MemoryOS* \[[10](#bib.bib10)\] brings
operating-system structure to storage, update, and retrieval. These
systems make memory larger, better organized, and easier to retrieve.

A second line turns experience into competence.
*Voyager* \[[3](#bib.bib3)\] grows a skill library from open-ended
exploration; *Agent Workflow Memory* \[[48](#bib.bib48)\] and
*ReasoningBank* \[[4](#bib.bib4)\] distill trajectories into reusable
workflows and strategies; *EvolveR* \[[49](#bib.bib49)\] and
*PolySkill* \[[50](#bib.bib50)\] close an experience-driven lifecycle
over skills; *AutoRefine* \[[51](#bib.bib51)\] keeps stored expertise
current; and *MEM1* \[[30](#bib.bib30)\] and
*Memory-as-Action* \[[52](#bib.bib52)\] train the agent to curate its
own context. Across both lines, the store grows and is trimmed under a
fixed provision. The byte budget is treated as a background constraint
rather than a control variable, and neither line asks how capability
changes when the budget shrinks and then returns.

### II-B Memory Compression and Governance

When memory must shrink, one family compresses it.
*MaRS* \[[31](#bib.bib31)\] summarizes episodes into reflections at a
single tier; *RecMem* \[[32](#bib.bib32)\] consolidates recurrently for
long-running agents; _Human-Inspired_ memory \[[24](#bib.bib24)\]
demotes entries through a ladder of representations, but only downward;
and *R³Mem* \[[25](#bib.bib25)\] makes compression reversible, yet
promotes opportunistically, with no budget-driven schedule and no gate
that verifies what returns. A parallel theory line frames memory
compaction as a rate–distortion trade-off over a single compression
event \[[53](#bib.bib53), [54](#bib.bib54), [55](#bib.bib55)\]. In these
systems, fidelity transitions are one-way or unscheduled; none treats
them as a two-way function of a moving byte budget.

Closest to ours, a governance family decides which entries deserve the
bytes. *CURATOR* \[[11](#bib.bib11)\] scores net value per byte and
governs retention under a hard footprint; *A-MAC* \[[33](#bib.bib33)\]
learns what to admit at write time; *AgeMem* \[[12](#bib.bib12)\] learns
a unified long- and short-term management policy; _Darwinian_
memory \[[56](#bib.bib56)\] lets a training-free store regulate itself;
and *BudgetMem* \[[27](#bib.bib27)\] learns selective retention under
explicit cost. These policies identify valuable entries, and the
strongest of them is our binary baseline. However, each policy either
keeps an entry verbatim or drops it. Selection decides which entries
survive a squeeze, but not what fidelity the survivors should occupy or
how evicted capability should return when the budget does.

### II-C Elastic Serving and Evaluation

Elasticity is routine in the serving stack below the memory
store \[[57](#bib.bib57), [58](#bib.bib58), [59](#bib.bib59),
[60](#bib.bib60), [61](#bib.bib61), [62](#bib.bib62),
[63](#bib.bib63)\]. vLLM \[[23](#bib.bib23)\] manages the key–value
cache as a paged, reclaimable resource; sleep-time
compute \[[34](#bib.bib34)\] spends idle cycles preparing context before
queries arrive; and governed shared memory \[[35](#bib.bib35)\]
arbitrates a store written by many agents. These systems reclaim serving
memory or schedule maintenance compute, but they do not tie the fidelity
of an experiential store to the byte budget it receives. CrystalMem
composes with this layer rather than replacing it.

Evaluation is beginning to measure lifecycle effects.
*MemoryAgentBench* \[[36](#bib.bib36)\] measures accumulation and
selective forgetting over incremental interaction; *Reclaim
Eval* \[[37](#bib.bib37)\] finds that lossy retention can leave an agent
worse off than no memory at all; and *Neuromem* \[[64](#bib.bib64)\]
decomposes the streaming lifecycle of an external store into stages.
Each protocol measures at a fixed provision or at a single degradation
point, so capability that fails to return with the budget remains
invisible. To our knowledge, no prior system schedules fidelity movement
in both directions under a byte budget, and no prior protocol measures
what an elastic budget does to agent capability.

## III Preliminaries and Memory Hysteresis Analysis

This section names and formalizes the failure mode: under an elastic
budget, capability lost during a squeeze does not automatically return
when the budget recovers. We model the memory plane and its elastic
budgets
(Sec. [III-A](#S3.SS1 "III-A System Model and Elastic Budgets ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")),
define and measure memory hysteresis
(Sec. [III-B](#S3.SS2 "III-B The Memory Hysteresis Phenomenon ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")),
and show why deletion-based retention cannot close the loop
(Sec. [III-C](#S3.SS3 "III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")).

### III-A System Model and Elastic Budgets

We consider a self-evolving LLM agent hosted in the cloud. Completed
episodes append experiential entries, such as trajectories, distilled
skills, and environment facts, to a memory store. At inference time, the
agent retrieves from this store to condition its policy. The store is a
metered resource, and its provisioned budget changes with cost control,
tenant load, and pricing events. We call this regime an _elastic
budget_, and we call the storage side of the agent the memory plane.

Let $`e`$ denote an entry and $`\mu(e)`$ its serialized size in bytes.
For a store $`M`$, write $`\mu(M)=\sum_{e\in M}\mu(e)`$. The agent
serves an environment $`m`$ with query distribution $`\mathcal{D}_{m}`$.
Time is divided into stages $`s=1,\dots,S`$. During stage $`s`$, the
agent holds store $`M^{s}`$, answers queries, and appends new writes
$`W^{s}`$. A _memory policy_ $`\pi`$ then maps $`(M^{s},W^{s})`$ to the
next store $`M^{s+1}`$ under the byte budget of stage $`s{+}1`$.
Capability is the expected graded outcome
$`C_{m}^{s}=\mathbb{E}_{q\sim\mathcal{D}_{m}}\!\left[g(q,M^{s})\right]`$.
The provider-facing problem is to sustain this capability across the
full budget path:

````math

``` |  | (1) |

Deployed policies fall into two classes. *Binary retention* $`\Pi_{b}`$
keeps an entry verbatim or drops it, so
$`M^{s+1}\subseteq M^{s}\cup W^{s}`$. Recency eviction, expiry, and
learned value governance \[[11](#bib.bib11)\] belong to this class.
*Irreversible ladders* may replace an entry by a lossy transform, but
transitions run in only one direction: once demoted, an entry is never
rebuilt \[[24](#bib.bib24)\]. Both classes share the same structural
property. A squeeze step is a projection, and what it discards re-enters
the store only if the input stream supplies it again.

###### Definition 1 (Elastic budget schedule).

An elastic cycle is the budget path
$`b=(b^{1},\dots,b^{S})=(1,\,0.75,\,0.5,\,0.25,\,0.5,\,0.75,\,1)`$ with
$`S=7`$: a *squeeze* phase $`s\in\{1,\dots,4\}`$ and a *recovery* phase
$`s\in\{4,\dots,7\}`$, with span $`\Delta_{b}=0.75`$. All policies run
under the same path and the same byte accounting (iso-budget).

### III-B The Memory Hysteresis Phenomenon

Elastic budgets turn memory management into a round trip: the store is
squeezed to a quarter of its provision and then restored. If the squeeze
were reversible, capability would retrace the same path during recovery.
We borrow *hysteresis* from magnetism for the failure of this retracing:
the state of the system depends on the path of the control variable, not
only on its current value. The cycle traces a closed path
$`\Gamma=\{(b^{s},C_{m}^{s})\}_{s=1}^{S}`$ in the capability–budget
plane, and the enclosed area measures how much recovery lags the
squeeze.

normalized to each method’s pre-squeeze level (seven environments
$`\times`$ five seeds). After the budget returns to 100%, every baseline
stays below its pre-squeeze capability; CrystalMem returns to the
full-recovery line (red dashed).

### III-C Why Existing Memory Policies Cannot Close the Loop

Fig. 2: Two currencies of hysteresis damage: (a) normalized

Two assumptions isolate what the argument needs.

###### Assumption 1 (Bounded re-observation).

Let $`\bar{M}`$ be the set of entries evicted during the squeeze phase.
Each $`e\in\bar{M}`$ is supplied again by the input stream during the
recovery phase with probability at most $`p_{e}<1`$.

Episodic streams rarely repeat: conversations move on, tasks change, and
drifting environments retire facts. Thus $`p_{e}`$ is small in practice.

###### Assumption 2 (Additive terminal utility).

There exist $`u_{e}\geq 0`$ such that removing any $`A\subseteq M`$ from
a store $`M`$ at the terminal stage lowers capability by at least
$`\sum_{e\in A}u_{e}`$; redundancy is absorbed into the definition of
$`u_{e}`$.

Assumption [2](#Thmassumption2 "Assumption 2 (Additive terminal utility). ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")
applied to $`A=\bar{M}\setminus R`$ yields
$`\tilde{C}-C_{m}^{S}\geq\sum_{e\in\bar{M}\setminus R}u_{e}`$. Taking
expectation over re-observation gives
$`\mathbb{E}\!\left[\tilde{C}-C_{m}^{S}\right]\geq\sum_{e\in\bar{M}}u_{e}\,\mathrm{P}(e\notin R)\geq\sum_{e\in\bar{M}}u_{e}\left(1-p_{e}\right)`$.
∎

The bound is not vacuous: the trough expels at least $`1-b^{4}=75\%`$ of
resident bytes, so the sum in
([4](#S3.E4 "In Proposition 3 (Deficit lower bound for binary retention). ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
covers most of what the agent has learned. We report deficits against
the pre-squeeze anchor $`C_{m}^{1}`$. Value governance operates within
the bound, not beyond it. Choosing which entries to evict reduces the
sum but cannot make it vanish, and the strongest binary baseline still
forfeits $`6.6\pm 1.4`$ pp, compared with $`17.5\pm 4.6`$ pp for recency
eviction
(Fig. [2](#S3.F2 "Fig. 2 ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")(b)).

Lossy tiers relax the binary premise only partially. A single tier fixes
one exchange rate between bytes and fidelity; a $`4\times`$ squeeze
exceeds that rate, so the tier deletes what it cannot hold and inherits
the bound ($`12.4\pm 2.9`$ pp for Mem0). A one-way ladder keeps residues
at several rates but never promotes them, so it serves degraded
representations even after the budget returns ($`10.1\pm 2.2`$ pp). The
measurements separate the two levers: four tiers instead of one buy
$`2.3`$ pp, while the reversible stack of CrystalMem buys another
$`9.0`$ pp ($`1.1\pm 0.4`$ pp). The proof uses only the absence of a
residue from which an entry can be rebuilt. Store such a residue, and
promotion by compute rather than re-observation becomes possible.
Reversibility is the first-order lever; tier count is second-order.

The analysis determines the design. The store must hold entries at
several fidelities and move them in both directions, using a reversible
ladder rather than one-way demotion. Because the sum in
([4](#S3.E4 "In Proposition 3 (Deficit lower bound for binary retention). ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
is weighted by $`u_{e}`$, demotion must track marginal utility, and
entries that anchor others must sink last. Because re-synthesis spends
tokens and can hallucinate, promotion must be budgeted and verified
before it re-enters the store. CrystalMem is built around exactly these
requirements.

## IV CrystalMem Design

### IV-A Overview

The analysis gives three design requirements: a reversible ladder,
utility-aware demotion, and verified promotion. CrystalMem implements
them with a single control loop around the store
(Fig. [3](#S4.F3 "Fig. 3 ‣ IV-A Overview ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")),
executed once per stage in three phases. *Monitor* maintains per-entry
value estimates. *Crystallize* reassigns fidelity states to satisfy the
incoming byte budget. *Recrystallize* buys back capability when the
budget expands. The stage transition factorizes as

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle p\!\left(M^{s+1}\mid M^{s},b^{s+1}\right)=`$ | $`\displaystyle\Bigg[\prod_{e\in M^{s}}\varphi\!\left(f_{e}^{s+1}\mid f_{e}^{s},\eta_{e}\right)\Bigg]`$ |  | (5) |
|  | $`\displaystyle\times`$ | $`\displaystyle\Bigg[\prod_{e\in U^{s}}\mathcal{R}\!\left(e^{\prime}\mid z_{e},M^{s}\right)\mathcal{V}\!\left(v_{e}\mid e^{\prime},h_{e}\right)\Bigg],`$ |  |  |

where the first factor crystallizes: an assignment kernel $`\varphi`$
moves each entry along the fidelity ladder $`f_{e}`$ under a
crystallization energy $`\eta_{e}`$. The second factor recrystallizes: a
generation operator $`\mathcal{R}`$ rebuilds promoted entries from their
residues $`z_{e}`$, and a verification operator $`\mathcal{V}`$ checks
the result against stored invariants $`h_{e}`$. Deletion does not appear
in
([5](#S4.E5 "In IV-A Overview ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")).
It remains only as last-resort eviction of bottom-rung residues.

### IV-B Fidelity Ladder and Crystallization Energy

Observation [2](#Thmobservation2 "Observation 2 (Restoration does not restore). ‣ III-B The Memory Hysteresis Phenomenon ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")
traced open loops to one-way demotion. The ladder replaces deletion with
reversible state assignment.

Every entry occupies one of $`K=4`$ states, $`f_{1}`$ (full) through
$`f_{4}`$ (trace), with compressed and skeletal between. At state $`k`$,
an entry costs $`\mu_{k}(e)`$ bytes and delivers a fraction $`r_{k}`$ of
its utility, with $`\mu_{1}(e)>\dots>\mu_{4}(e)`$ and
$`1=r_{1}>\dots>r_{4}`$; regenerating from state $`k`$ costs $`c_{k}`$
tokens, increasing in $`k`$. From compressed down, each entry keeps a
residue $`z_{e}`$, namely its state-$`k`$ representation, and a set of
invariants $`h_{e}`$: key spans, entity tuples, and outcome facts
distilled at demotion time. These invariants later anchor verification.

A demotion decision trades utility now against compute later. We price
both terms in one score,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\eta_{e}(k)\;=\;\tilde{v}_{e}\left(1-r_{k}\right)\;+\;\tau\,c_{k},
``` |  | (6) |

the utility forgone by holding $`e`$ at state $`k`$ plus the anticipated
cost of buying it back, with $`\tau`$ converting regeneration tokens
into capability cost. Given the incoming budget, Crystallize solves the
constrained assignment

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\varphi^{\star}=\operatorname*{arg\,min}_{\varphi}`$ | $`\displaystyle\sum_{e\in M^{s}}\eta_{e}\!\left(\varphi(e)\right)`$ |  | (7) |
|  | $`\displaystyle\mathrm{s.t.}`$ | $`\displaystyle\sum_{e\in M^{s}}\mu_{\varphi(e)}(e)\;\leq\;b^{s+1}B_{0}.`$ |  |  |

The objective is separable, so the Lagrangian
$`\sum_{e}\eta_{e}(\varphi(e))+\theta\,(\sum_{e}\mu_{\varphi(e)}(e)-b^{s+1}B_{0})`$
is minimized rung by rung: an entry stays at the deepest state whose
marginal price $`\Delta\eta_{e}/\Delta\mu_{e}`$ remains below the
multiplier $`\theta`$ set by the budget. CrystalMem implements this step
as a water-filling descent, demoting one rung at a time in increasing
order of marginal price until the store fits. We call the moving
boundary the crystallization front
(Fig. [3](#S4.F3 "Fig. 3 ‣ IV-A Overview ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")(b)).

### IV-C Influence-Driven Assignment

The bound
([4](#S3.E4 "In Proposition 3 (Deficit lower bound for binary retention). ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
charges a policy for every unit of deleted utility, so demotion order
must track $`u_{e}`$. CrystalMem estimates this value online.

Each retrieval attributes the query outcome back to the entries it
surfaced, baselined against recent outcomes:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
I_{e}\;\leftarrow\;\gamma\,I_{e}+\left(1-\gamma\right)w_{e}\,\frac{g\!\left(q,M\right)-\operatorname*{mean}_{j\in Q}\,g_{j}}{\operatorname*{std}_{j\in Q}\,g_{j}}\,,
``` |  | (8) |

where $`w_{e}`$ is the normalized retrieval weight of $`e`$ in answering
$`q`$, $`Q`$ is a sliding batch of recent queries, and $`\gamma`$ is the
averaging horizon. Entries that repeatedly appear in above-average
outcomes accumulate influence; stale or decorative entries decay toward
zero. The estimator is white-box: it uses only retrieval logs and graded
outcomes, both already produced by the serving path.

Entries are not independent: a skill cites facts, and a trajectory can
ground a distilled rule. CrystalMem maintains a dependency graph over
co-retrieval and reference edges and lets influence flow across it,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\tilde{v}_{e}\;=\;I_{e}+\lambda\!\sum_{e^{\prime}\in N(e)}\frac{x\!\left(e,e^{\prime}\right)}{\sum_{j\in N(e)}x\!\left(e,j\right)}\,I_{e^{\prime}},
``` |  | (9) |

where $`N(e)`$ is the neighborhood of $`e`$, $`x(e,e^{\prime})`$ counts
co-retrievals, and $`\lambda`$ sets the coupling strength. Hub entries
take value from the entries they anchor and therefore sink last,
matching the demotion order required by the analysis. As a hard guard,
an entry is not demoted below skeletal while a full neighbor still cites
its invariants.

### IV-D Recrystallization

Proposition [3](#Thmtheorem3 "Proposition 3 (Deficit lower bound for binary retention). ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")
depends on evictions leaving no residue. Recrystallization removes that
condition.

When the budget expands, Recrystallize selects a promotion set

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle U^{s}=\operatorname*{arg\,max}_{U\subseteq M^{s}}`$ | $`\displaystyle\sum_{e\in U}\tilde{v}_{e}\,\Delta_{e}`$ |  | (10) |
|  | $`\displaystyle\mathrm{s.t.}\;\;\sum_{e\in U}c_{e}\leq\rho\,n^{s},`$ | $`\displaystyle\mu\!\left(M^{s}\right)+\sum_{e\in U}\Delta\mu_{e}\leq b^{s+1}B_{0},`$ |  |  |

where $`\Delta_{e}`$ is the utility regained by lifting $`e`$ one rung,
$`c_{e}`$ is its regeneration cost, $`n^{s}`$ is the serving-token count
of the stage, and $`\rho`$ is the compute cap (default $`10\%`$). The
two constraints make the trade-off explicit: promotion may spend at most
a fixed share of serving compute and may never exceed the byte budget.
Greedy selection by density $`\tilde{v}_{e}\Delta_{e}/c_{e}`$ gives the
standard knapsack approximation for
([10](#S4.E10 "In IV-D Recrystallization ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
and runs in idle windows between queries.

A selected residue is rebuilt by conditioning the host model on
$`z_{e}`$ and its graph neighborhood,
$`e^{\prime}\sim\mathcal{R}(\cdot\mid z_{e},M^{s})`$. The draft is
admitted only if the verification operator confirms it against the
stored invariants, $`\mathcal{V}(e^{\prime},h_{e})=1`$
(Fig. [3](#S4.F3 "Fig. 3 ‣ IV-A Overview ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")(c)):
every key span, entity tuple, and outcome fact recorded at demotion time
must be entailed by $`e^{\prime}`$. A rejected draft leaves the entry at
its current rung, so a failed promotion cannot degrade the store.
Hallucinated reconstructions are filtered before they enter retrieval.
Admission therefore converts serving tokens into recovered capability,
the storage-for-compute exchange the ladder was built to support.

Three properties locate the guarantees of the loop; only the last one is
idealized.

###### Proposition 4 (Feasibility invariance).

Under
Algorithm [1](#alg1 "Algorithm 1 ‣ IV-E System Implementation ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"),
$`\mu(M^{s})\leq b^{s}B_{0}`$ at every stage $`s`$.

###### Proof.

The Crystallize loop demotes, and at the bottom rung evicts, until the
constraint holds. Each step strictly decreases $`\mu(M)`$, so the loop
terminates with a feasible store. Promotions are admitted only within
the byte headroom in
([10](#S4.E10 "In IV-D Recrystallization ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")).
∎

###### Proposition 5 (Near-optimality of the water-filling schedule).

Suppose each entry’s marginal price $`\Delta\eta_{e}/\Delta\mu_{e}`$ is
nondecreasing along the ladder. Then the Phase II schedule is optimal
for the fractional relaxation of
([7](#S4.E7 "In IV-B Fidelity Ladder and Crystallization Energy ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")),
and its energy exceeds the integral optimum by at most
$`\max_{e}\left[\eta_{e}(K)-\eta_{e}(1)\right]`$, the span of one entry.

###### Proof.

Under nondecreasing prices, taking rung moves greedily by price matches
the fractional optimum up to the single boundary move where the byte
constraint becomes tight, by the classical fractional-knapsack argument.
Rounding that move integrally charges at most one entry’s span, and the
fractional optimum lower-bounds the integral one. ∎

The promotion pass in
([10](#S4.E10 "In IV-D Recrystallization ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
admits the same argument per binding cap, losing at most one boundary
entry for each cap.

###### Proposition 6 (Loop closure under exact regeneration).

Suppose no bottom-rung eviction occurs, $`\mathcal{R}`$ restores each
promoted residue to its full utility, and $`\mathcal{V}`$ has no false
rejections. If the caps in
([10](#S4.E10 "In IV-D Recrystallization ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
admit all candidates during the recovery phase, then
$`\mathbb{E}\!\left[D_{m}\right]\to 0`$ and the loop of
Definition [2](#Thmtheorem2 "Definition 2 (Hysteresis area and residual deficit). ‣ III-B The Memory Hysteresis Phenomenon ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")
closes.

###### Proof.

Every squeezed entry retains its residue. Under the stated hypotheses,
each entry is lifted back to $`f_{1}`$ as the budget returns, so the
terminal store matches the counterfactual store of
Proposition [3](#Thmtheorem3 "Proposition 3 (Deficit lower bound for binary retention). ‣ III-C Why Existing Memory Policies Cannot Close the Loop ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")
on the evicted mass. The deficit term vanishes, the recovery branch
retraces the squeeze branch, and the enclosed area of
Definition [2](#Thmtheorem2 "Definition 2 (Hysteresis area and residual deficit). ‣ III-B The Memory Hysteresis Phenomenon ‣ III Preliminaries and Memory Hysteresis Analysis ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")
is zero. ∎

Both greedy passes sort once and sweep once, $`O(|M|\log|M|)`$ per
stage, with no training and no external solver. The loop is cheap enough
to run inside the serving path.

### IV-E System Implementation

CrystalMem runs as a sidecar beside the serving
stack \[[23](#bib.bib23)\]. Monitor hooks the retrieval path and updates
([8](#S4.E8 "In IV-C Influence-Driven Assignment ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
inline; Crystallize fires on budget events; and Recrystallize batches
its generation calls into idle windows, so foreground queries do not
wait on promotion. The store keeps, for each entry, the current rung,
the residue $`z_{e}`$, the invariants $`h_{e}`$, and the graph edges of
([9](#S4.E9 "In IV-C Influence-Driven Assignment ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization")).
Under multi-tenancy, the same schedule runs over the pooled budget with
tenant-weighted values and per-tenant capability floors. On edge hosts,
a small model runs Monitor and Crystallize locally and delegates
$`\mathcal{R}`$ to the hub.

Input: store $`M^{s}`$, incoming budget $`b^{s+1}`$, serving tokens
$`n^{s}`$, compute cap $`\rho`$, rates $`\gamma,\lambda,\tau`$

 on a budget event $`b^{s+1}\neq b^{s}`$, snapshot the loop point
$`\left(b^{s},C_{m}^{s}\right)`$ 3:  on each retrieval, update the
influence $`I_{e}`$ by
([8](#S4.E8 "In IV-C Influence-Driven Assignment ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
4:  refresh the coupled values $`\tilde{v}_{e}`$ by
([9](#S4.E9 "In IV-C Influence-Driven Assignment ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))

5:  Phase II: Crystallize $`\triangleright`$ solve
([7](#S4.E7 "In IV-B Fidelity Ladder and Crystallization Energy ‣ IV CrystalMem Design ‣ CrystalMem: Elastic Memory for Self-EvolvingLLM Agents via Knowledge Crystallization"))
6:  while $`\mu(M)>b^{s+1}B_{0}`$ do 7:   pop the cheapest move
$`e=\operatorname*{arg\,min}_{e}\,\Delta\eta_{e}/\Delta\mu_{e}`$; raise
the multiplier $`\theta`$ to that price 8:   demote $`e`$ one rung,
distilling $`(z_{e},h_{e})`$ at its first demotion; if already trace,

 select the promotion set $`U`$ by

$`e^{\prime}\sim\mathcal{R}(\cdot\mid z_{e},M)`$; admit one rung up iff
$`\mathcal{V}(e^{\prime},h_{e})=1`$ 14:   charge $`c_{e}`$ to the
recrystallization ledger; stop once $`\rho\,n^{s}`$ is spent 15:  end
for

16:  return $`M^{s+1}`$

Algorithm 1 CrystalMem Elastic-Stage Lifecycle (Monitor, Crystallize,
and Recrystallize)

Taken together, CrystalMem turns retention into reversible state
assignment. Advantage-weighted influence and a dependency kernel value
each entry; a crystallization-energy schedule demotes entries along a
four-state ladder to satisfy the budget path; and a
generation–verification operator pair buys capability back under
explicit compute and byte caps, admitting only reconstructions that pass
invariant checks. Deletion becomes the last resort instead of the
default.

$`89\%`$ of the pre-squeeze level. Under binary eviction, the demoted
skills are gone, and success plateaus at $`61\%`$.

## VI Conclusion

In cloud-served self-evolving large language model agents, we identified
*memory hysteresis*: after an experience-store budget is squeezed and
restored, capability settles below the pre-squeeze level. Deletion and
one-way compression cause the gap because they discard the material
needed for later rebuilding; we also prove a residual-deficit floor for
any keep/drop-only policy. CrystalMem closes the loop by replacing
binary memory management with crystallized memory: entries move across
four fidelity states under a crystallization-energy schedule, demotions
are ordered by advantage-weighted influence with dependency coupling,
and verified recrystallization recovers capability under explicit
compute and byte caps. Across seven environments, seventeen methods, and
six backbones, CrystalMem achieves the highest restored capability
everywhere, leaves a residual deficit an order of magnitude below every
binary baseline, and, from half the byte budget, matches the strongest
budgeted baseline at full provision. The advantage carries into
deployment: at the four-tenant operating point, crystallized stores
yield an order of magnitude fewer service-level violations than fair
splitting of binary stores, and on a physical edge–cloud testbed, each
recovered point of capability costs about a fifth of the energy required
to re-experience the underlying episodes.
````
