###### Abstract

Automated harness optimization improves agents by learning from
trajectories and task feedback. Existing offline methods use reference
answers to optimize harnesses for reuse on held-out tasks. However, many
real-world tasks are open-ended, while long runs expose new difficulties
that offline-optimized harnesses may not address. To study harness
optimization in these settings, we introduce PerfRace, a benchmark for
long-running performance optimization of software projects, and
investigate whether agents can use task-specific experience to
recursively improve their harnesses during an ongoing task. To this end,
we introduce BoxBox, which enables agent-triggered harness revision and
kernel-managed hot reloading while preserving execution context. We
evaluate BoxBox on PerfRace under matched test-time budgets, comparing
it with Frozen Harness, offline Harness Evolution, and Harness Scaling.
BoxBox achieves higher speedup with more efficient use of task time and
model cost, reaching a $`\mathrm{Speedup@}4\mathrm{h}`$ of
$`1.70\times`$, compared with $`1.54\times`$ for the strongest baseline.

## 1 Introduction

Large language model (LLM) agents interact with their environment
through harness that determines both the available actions and the
observations they receive ([Yang et al., 2024](#bib.bib2); [Merrill et
al., 2026](#bib.bib49); [Lin et al., 2026](#bib.bib3)). Recent studies
have shown that harness design can substantially affect agent
performance and behavior, even when the underlying model is fixed  ([Lin
et al., 2026](#bib.bib3); [Wang et al., 2026b](#bib.bib35)). These
findings have motivated automatic optimization of agent harness, in
which an optimizer analyzes agent trajectories and evaluation feedback,
proposes modifications to the harness, and evaluates the resulting agent
on benchmark tasks.

Existing offline harness optimization methods ([Park et al.,
2026](#bib.bib18); [Zhang et al., 2026b](#bib.bib11); [Lin et al.,
2026](#bib.bib3); [Wang et al., 2026b](#bib.bib35)) often use reference
answers or task-completion feedback to diagnose failures, and revise
harnesses to improve performance on held-out tasks. This setup aligns
with existing agent benchmarks that evaluate whether an agent completes
a specified task ([Jimenez et al., 2024](#bib.bib40); [Merrill et al.,
2026](#bib.bib49); [Froger et al., 2026](#bib.bib38)).

However, many real-world tasks are open-ended and long-running, making
end-state evaluations alone insufficient to capture how agents progress
throughout these runs. Moreover, this setting poses two challenges for
offline harness optimization. First, open-ended tasks make it difficult
to identify useful harness revisions, as they may lack clear criteria
for diagnosing what needs improvement. Prior evaluations show that
harness evolution does not reliably improve performance without
unit-test feedback ([Wang et al., 2026b](#bib.bib35)). Second, continued
execution exposes new task-specific difficulties that may limit the
generalization of harness revisions learned from other tasks ([Nie et
al., 2026](#bib.bib20); [Wang et al., 2026b](#bib.bib35)).

To study harness optimization in these settings, we introduce PerfRace,
a benchmark for optimizing performance of real-world software projects.
Our experiments show that offline Harness Evolution (HE) underperforms
Frozen Harness on PerfRace
(Figure [1](#S0.F1 "Figure 1 ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")),
with no consistent improvement during training or validation
(Appendix [A.2](#A1.SS2 "A.2 Harness Evolution ‣ Appendix A Experimental Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")),
consistent with prior findings of unreliable gains and limited
generalization ([Wang et al., 2026b](#bib.bib35)).

Nevertheless, the current task’s trajectory can reveal difficulties
encountered during execution and provide task-specific evidence for
harness revision ([Nie et al., 2026](#bib.bib20)). We therefore
investigate whether an agent can use this experience to improve its own
harness during the ongoing task, making harness optimization an online,
task-specific process. Existing methods allocate budget between task
execution and harness optimization through an outer loop, with harness
updates scheduled by predefined triggers or a separate meta-agent ([Wang
et al., 2026b](#bib.bib35); [Liu et al., 2026](#bib.bib14); [Zhang et
al., 2026c](#bib.bib13)). However, external control limits the
task-solving agent’s ability to respond to emerging difficulties. First,
despite observing task progress, the agent cannot decide whether to
spend its remaining budget on task execution or harness revision.
Second, updates occur between task attempts or execution segments,
delaying their use in the ongoing task.

To address these limitations, we introduce BoxBox¹¹ 1 Named after the F1
radio call “box, box,” requesting a pit stop for repairs and adjustments
during the race. to support agent-triggered revision of the full
executable harness through kernel-managed hot reloading. When requested,
the kernel pauses task execution and launches an agent review session to
diagnose difficulties from the trajectory and revise the harness. After
validation, it resumes the task with preserved execution context under
the revised harness, which governs both subsequent execution and future
reviews, enabling recursive harness improvement. We evaluate BoxBox on
PerfRace against Frozen Harness, offline Harness Evolution and
externally controlled Harness Scaling under matched task budgets,
comparing best-so-far correct speedup and model cost. BoxBox achieves a
$`\mathrm{Speedup@}4\mathrm{h}`$ of $`1.70\times`$, compared with
$`1.44\times`$ for Frozen Harness, $`1.28\times`$ for Harness Evolution,
and $`1.54\times`$ for Harness Scaling.

Our main contributions are summarized as follows:

- •
  We introduce PerfRace, a benchmark for evaluating agents on open-ended
  performance optimization tasks, tracking correctness-preserving
  improvements to real-world software throughout task execution.
- •
  We present BoxBox, which combines agent-triggered, full-harness
  revision from task-specific experience with kernel-managed hot
  reloading of the runtime while preserving execution context.
- •
  Our experiments show that BoxBox achieves higher best-so-far correct
  speedup with greater time and cost efficiency than the evaluated
  baselines, supporting harness optimization as part of an agent’s own
  capabilities.

## 2 Related Work

Automated harness optimization. Prior work has extensively studied the
automated optimization of prompts for LLM-based systems ([Zhou et al.,
2023](#bib.bib5); [Pryzant et al., 2023](#bib.bib6); [Yuksekgonul et
al., 2025](#bib.bib7); [Khattab et al., 2024](#bib.bib4); [Agrawal et
al., 2025](#bib.bib8)). Subsequent work extends automated optimization
to agents, using execution trajectories and task feedback to improve
their memory, skills, and workflows ([Zhao et al., 2024](#bib.bib9);
[Zhang et al., 2025](#bib.bib17); [Ni et al., 2026](#bib.bib34); [Hu et
al., 2024](#bib.bib15); [Zhang et al., 2024](#bib.bib16)). Meta-Harness
and AHE further extend automated optimization to executable harness
code, using trajectories and evaluation feedback to guide iterative
revisions ([Lee et al., 2026](#bib.bib10); [Lin et al.,
2026](#bib.bib3)).

Building on this setting, offline methods revise harnesses using
reference answers or task-completion feedback from training tasks,
aiming to improve held-out performance ([Park et al., 2026](#bib.bib18);
[Zhang et al., 2026b](#bib.bib11); [Lin et al., 2026](#bib.bib3)).
However, an evaluation finds unreliable gains without unit-test feedback
and limited transfer from reusable harnesses, but reports gains from
Harness Scaling, which alternates task attempts and harness revisions at
test time ([Wang et al., 2026b](#bib.bib35)).

Following this task-specific direction, JIT-Agent synthesizes a tailored
harness for each task before execution begins ([Zhang et al.,
2026a](#bib.bib19)). TTHE further explores harness optimization without
reference answers, using trajectories and execution-derived feedback to
revise executable harnesses on unlabeled test batches ([Nie et al.,
2026](#bib.bib20)). Continual Harness moves harness optimization into
ongoing task execution through an outer loop that periodically invokes a
refiner while preserving the task state ([Karten et al.,
2026](#bib.bib12)). In BoxBox, the task-solving agent decides when to
allocate its remaining budget to full-harness revision, while a separate
kernel manages runtime hot reloading and preserves execution context.

Long-Horizon and Open-Ended Agent Evaluation. Existing agent benchmarks
cover diverse capabilities but commonly evaluate tasks with explicit end
states, reporting task success, pass rates, or final artifact
quality ([Mialon et al., 2023](#bib.bib37); [Liu et al.,
2024b](#bib.bib39); [Jimenez et al., 2024](#bib.bib40); [Xie et al.,
2024](#bib.bib41); [Merrill et al., 2026](#bib.bib49); [Sun et al.,
2026](#bib.bib42)). Recent iterative optimization benchmarks evaluate
solution quality but still use reference implementations, human
performance, or reference outputs for task construction or
scoring ([Chan et al., 2025](#bib.bib43); [Lyu et al.,
2026](#bib.bib44); [Imajuku et al., 2025](#bib.bib47); [Xu et al.,
2026](#bib.bib32); [Mang et al., 2025](#bib.bib46); [Zhu et al.,
2026](#bib.bib48)). Closer to our setting, Frontier-Eng and FrontierSWE
support iterative optimization of engineering designs and software
projects, with tasks curated from established problems and expert
contributions ([Chi et al., 2026](#bib.bib45); [Chu et al.,
2026](#bib.bib33)).

In contrast, PerfRace constructs long-running performance optimization
tasks from real-world software projects and workloads without requiring
reference optimizations. Its construction pipeline provides a scalable
way to continually source new tasks from public software projects.

Benchmarks for Performance Optimization. [Shypula et al.
(2024)](#bib.bib21) introduce PIE for evaluating LLMs’ ability to make
performance-improving edits to single-file competitive programming
solutions while preserving functional correctness. Subsequent benchmarks
broaden the optimization domains to GPU kernels, general-purpose
numerical programs, and algorithmic redesign, while retaining function-
or file-level optimization tasks ([Du et al., 2024](#bib.bib22); [Huang
et al., 2024](#bib.bib23); [Liu et al., 2024a](#bib.bib24); [Waghjale et
al., 2024](#bib.bib25); [Ouyang et al., 2025](#bib.bib26); [Press et
al., 2025](#bib.bib27)).

GSO and SWE-Perf extend evaluation to repository-level performance
optimization, deriving tasks and human reference optimizations from
GitHub commits and pull requests ([Shetty et al., 2025](#bib.bib28); [He
et al., 2026](#bib.bib29)). SWE-fficiency and FormulaCode further
incorporate a targeted workload per task and multiple
community-maintained workloads, respectively ([Ma et al.,
2026](#bib.bib30); [Sehgal et al., 2026](#bib.bib31)).

These repository-level benchmarks construct tasks around a targeted
performance test, whereas real performance engineering starts from an
end-to-end workload and discovers bottlenecks through profiling.
PerfRace adopts this workload-first formulation, leaving agents to
identify and implement correctness-preserving improvements without a
known target patch.

## 3 PerfRace

PerfRace benchmarks real-world software performance optimization with
three design principles: (1) _Live_: projects are continually sourced
from public GitHub repositories; (2) _Open-ended_: tasks use project
workloads without reference optimizations or known target patches; and
(3) _Long horizon_: agents iteratively optimize code and choose when to
submit for feedback within a fixed budget.

### 3.1 Task Formulation

Each PerfRace task provides the agent with an editable project
workspace, a fixed workload that the agent can run locally, and access
to an external Judge. For official evaluation, the Judge uses a separate
copy of this workload and additional held-out correctness cases.

During the evaluation loop, the agent iteratively modifies the project
and submits changes to the Judge for feedback. Let $`t_{i}`$ denote the
evaluation start time of submission $`i`$ and $`s_{i}`$ its score, with
$`s_{i}=0`$ for incorrect submissions. Scores are attributed
retrospectively to evaluation start times; verification time also counts
toward the task budget. We include the unmodified project as a baseline
submission with $`t_{0}=0`$ and $`s_{0}=1`$. We define the best-so-far
correct speedup as $`S(t)=\max_{i:t_{i}\leq t}s_{i}`$, which the agent
aims to maximize within a fixed task budget $`B`$.

### 3.2 Construction

We construct PerfRace by identifying real projects with optimization
potential and building reliable tasks around realistic workloads
(Figure [2](#S3.F2 "Figure 2 ‣ 3.1 Task Formulation ‣ 3 PerfRace ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")(a)).
Each PerfRace task adopts the Harbor Task Format ([Merrill et al.,
2026](#bib.bib49)), as illustrated in
Figure [2](#S3.F2 "Figure 2 ‣ 3.1 Task Formulation ‣ 3 PerfRace ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")(b).

Discovery. To identify less-explored optimization opportunities beyond
mature, heavily maintained repositories, we search GitHub coding-agent
activity for candidate projects. Specifically, we identified 103,475
candidate projects from public GitHub pull requests and branch pushes
made by known coding agents between May and August 2026
(Appendix [B.3](#A2.SS3 "B.3 Construction and Curation Statistics ‣ Appendix B PerfRace: Benchmark Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).

Filter. We filter candidate projects in two stages. First, deterministic
prechecks verify repository and source-revision accessibility, license
redistributability, and repository size and popularity, retaining 7,257
candidates. We then use GPT-5.6-Luna to assess each candidate’s setup
process, evaluable workload, runtime feasibility, and optimization
potential from its source code. Of these candidates, 239 pass this
assessment and proceed to Pair Verification
(Appendix [B.3](#A2.SS3 "B.3 Construction and Curation Statistics ‣ Appendix B PerfRace: Benchmark Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).

Pair Verification. We use agent–human Pair Verification to construct
runnable tasks and assess their quality against three criteria
(Appendix [B.4](#A2.SS4 "B.4 Pair Verification ‣ Appendix B PerfRace: Benchmark Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")):

- •
  Realism. The workload and metric represent meaningful project use.
- •
  Reliability. Repeated equivalent runs support the same correctness and
  performance conclusions.
- •
  Integrity. The score reflects genuine task completion rather than an
  invalid or shortcut solution.

Specifically, we first let the agent derive workload inputs and scale
from real project use and propose correctness checks, measurement
boundaries, and performance metrics for human review. Second, the agent
configures warmup and runs repeated tests to detect flakiness and
distinguish genuine speedups from noise; the reviewer uses these results
to approve or revise the measurement protocol. Finally, the agent
conducts red-team tests against reward hacking using invalid,
incomplete, hard-coded, and work-skipping solutions; the reviewer
requests verifier fixes as needed before approving the task for
packaging and release. Eventually, we curated 100 tasks, each requiring
an average of 9.1 hours of curation, 12 agent–human interactions, and
\$11.35 in agent cost; detailed statistics are provided in
Appendix [B.3](#A2.SS3 "B.3 Construction and Curation Statistics ‣ Appendix B PerfRace: Benchmark Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization").

### 3.3 Benchmark Composition

The resulting benchmark contains 100 tasks across seven domains
(Figure [3](#S3.F3 "Figure 3 ‣ 3.3 Benchmark Composition ‣ 3 PerfRace ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")):
_developer tools_ (30 tasks) compiles, builds and validates software;
_data systems_ (25 tasks) ingests, indexes and queries data; _scientific
computing_ (15 tasks) runs simulations and numerical solvers; _media
processing_ (9 tasks) renders graphics and audio; _geometry_ (8 tasks)
processes maps and 3D models; _machine learning_ (7 tasks) trains models
and runs inference; and _security_ (6 tasks) encrypts data and analyzes
attack logs. Each task pairs a real project with a fixed workload; for
example, one task optimizes CCC while it compiles SQLite.

### 3.4 Evaluation

In the evaluation loop, the agent chooses when to submit snapshots for
correctness and performance feedback from the Judge
(Figure [2](#S3.F2 "Figure 2 ‣ 3.1 Task Formulation ‣ 3 PerfRace ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")(c)).
The score $`s_{i}`$ is the speedup over the unmodified project for
correct submissions and zero otherwise. Runs without a
correctness-preserving improvement receive a score of $`1\times`$.
During the final five minutes, the agent is prompted to end optimization
and leave the project in a coherent state for the Judge’s final
evaluation.

Prior studies show that agents can inflate scores by tampering with
evaluation code or accessing reference outputs ([Wang et al.,
2026a](#bib.bib50); [Von Arx et al., 2025](#bib.bib51)). We therefore
use _shadow verification_, evaluating project snapshots in separate
containers while keeping verifier code and held-out test data out of the
agent’s workspace. Time spent in shadow verification counts toward
$`B`$.
Appendix [B.5](#A2.SS5 "B.5 Evaluation Protocol ‣ Appendix B PerfRace: Benchmark Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")
provides further details on shadow verification.

## 4 BoxBox

We now present BoxBox for agent-triggered harness revision during
long-running tasks. The following subsections present the problem
formulation, explain the kernel-managed harness update mechanism, and
describe a simple self-review strategy for diagnosis and revision.

### 4.1 Problem Formulation

Consider a fixed language model $`\mathcal{M}`$ and an executable
harness that may change during a task. Let $`H_{k}`$, $`e_{k}`$, and
$`\tau_{k}`$ denote the active harness, environment state, and
accumulated trajectory at interaction step $`k`$, respectively ([Yao et
al., 2023](#bib.bib1)). Task execution follows

|                                        |                                    |                                                                                                   |     |     |
| -------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------- | --- | --- |
|                                        | $`\displaystyle a_{k}`$            | $`\displaystyle\sim p_{\mathcal{M},H_{k}}(\cdot\mid\tau_{k}),\qquad a_{k}\in\mathcal{A}(H_{k}),`$ |     | (1) |
|                                        | $`\displaystyle(e_{k+1},o_{k+1})`$ | $`\displaystyle\leftarrow\operatorname{Execute}_{H_{k}}(e_{k},a_{k}),`$                           |     |     |
|                                        | $`\displaystyle\tau_{k+1}`$        | $`\displaystyle=\tau_{k}\oplus(a_{k},o_{k+1}),`$                                                  |     |     |
|                                        | $`\displaystyle H_{k+1}`$          | $`\displaystyle=\begin{cases}H^{\prime}\_{k},&\text{if a revision is activated},\\                |
| H\_{k},&\text{otherwise}.\end{cases}`$ |                                    |                                                                                                   |

Here, $`a_{k}`$ is a tool call from the action space
$`\mathcal{A}(H_{k})`$ exposed by the active harness, and
$`p_{\mathcal{M},H_{k}}`$ is its distribution induced by $`H_{k}`$
constructing model inputs from $`\tau_{k}`$ and invoking
$`\mathcal{M}`$. $`\operatorname{Execute}_{H_{k}}`$ resolves and
executes $`a_{k}`$ through the harness’s tool implementation, updates
the environment state, and processes the resulting feedback into
$`o_{k+1}`$; $`\oplus`$ appends the action–observation pair to the
history.

When a revision is attempted, the agent revises $`H_{k}`$ based on the
interaction history $`\tau_{k+1}`$, producing a candidate
$`H^{\prime}_{k}`$. If activated, it becomes the active harness for the
next interaction; otherwise, execution continues under $`H_{k}`$.
Subsequent action selection and execution therefore use $`H_{k+1}`$.

### 4.2 Kernel-Managed Harness Updates

BoxBox treats the harness as a task-specific implementation, allowing a
revision to be tailored to the requirements of the ongoing task. To
support such adaptations, BoxBox exposes the full executable harness,
allowing the agent to translate task-specific needs into direct changes
to tools, control flow, and state management. Let $`\mathcal{H}`$ denote
the set of harness implementations compatible with the execution
interface. Methods with predefined editable components restrict
candidate revisions to a subset
$`\mathcal{H}_{\mathrm{bounded}}\subseteq\mathcal{H}`$ ([Zhang et al.,
2026b](#bib.bib11); [Lin et al., 2026](#bib.bib3); [Park et al.,
2026](#bib.bib18)), whereas BoxBox allows revisions
$`H^{\prime}_{k}\in\mathcal{H}`$.

In BoxBox, the harness is the editable agent implementation, while the
runtime is its running version that controls the agent’s execution and
maintains its state. These revisions change the agent’s execution code,
so a faulty update can interrupt the task and make it difficult for the
agent to recover on its own. BoxBox therefore introduces a separate
kernel that manages runtime hot reloading and can safely retain or
restore the previous runtime if an update fails validation or
activation.

Specifically, we register boxbox() as a tool that yields control to the
kernel, with $`\texttt{boxbox()}\in\mathcal{A}(H_{k})`$. When the agent
invokes boxbox(), the kernel suspends task execution and preserves the
agent’s execution context, including the accumulated trajectory,
terminal session, and workspace state. It then launches a review session
for the agent to examine the trajectory, revise the harness as needed,
and commit any changes. After the review session concludes, the kernel
validates any new commits, loads the revised runtime on success, and
otherwise retains the current runtime. During activation, the kernel
transfers the preserved execution context to the new runtime and
reattaches the existing terminal session. On successful activation,
$`H_{k+1}=H^{\prime}_{k}`$, and subsequent interactions follow
Eqn. [1](#S4.E1 "In 4.1 Problem Formulation ‣ 4 BoxBox ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization").
Finally, the kernel returns control to the agent, allowing it to resume
the ongoing task.

Beyond agent-initiated updates, runtime faults also trigger
kernel-managed recovery and review based on the recorded fault evidence.
Appendix [C](#A3 "Appendix C BoxBox: Method Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")
provides further implementation details.

### 4.3 Agent-Controlled Harness Optimization

Based on this mechanism, BoxBox lets the task-solving agent decide when
to request a harness review, so it can adapt its harness in response to
difficulties encountered during task execution. Unlike prior methods
that use an outer loop ([Lee et al., 2026](#bib.bib10); [Karten et al.,
2026](#bib.bib12); [Liu et al., 2026](#bib.bib14)), the agent itself
allocates the shared budget $`B`$ between project-code optimization and
harness revision to maximize $`S(B)`$.

Within the review session, we provide a default skill
(Appendix [D.3](#A4.SS3 "D.3 Self-Review Skill ‣ D.2 Pair Verification Skill ‣ D.1 Filter Prompt ‣ Appendix D Prompts and Skills ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization"))
that guides the agent through a simple self-review strategy based on
diagnosis and harness revision:

- •
  Diagnosis. The agent examines the trajectory for execution failures,
  repeated work, and successful patterns that could be automated or
  reused. It uses these observations to identify limitations of the
  current harness, such as missing capabilities or costly tool
  interactions.
- •
  Revision. The agent selects harness revisions based on their expected
  benefit within the remaining budget, such as adding guidance,
  improving tools, or changing execution logic. For example, repeated
  tool calls can be combined into a reusable tool.

We track harness revisions as Git commits so the agent can inspect prior
changes alongside execution records in subsequent reviews, assess their
effects, and decide whether further revisions are needed.

## 5 Experiments

### 5.1 Experimental Setup

Baselines. We compare BoxBox with three baselines: Frozen Harness
(Frozen) retains the initial harness throughout task execution. Harness
Evolution (HE) optimizes the harness offline on training tasks and
selects it by validation performance, then holds it fixed during
test-task execution. Harness Scaling (HS) uses an external controller to
revise the harness between attempts on the same task, using feedback
from each completed attempt. Both HE and HS are adapted from [Wang et
al. (2026b)](#bib.bib35). Following Meta-Harness ([Lee et al.,
2026](#bib.bib10)), all methods start from the same initial harness
$`H_{0}`$, Terminus-KIRA ([KRAFTON AI and Ludo Robotics,
2026](#bib.bib36)), a simple terminal-based harness that executes shell
commands and returns their outputs to the model.

Evaluation protocol. We split the 100 PerfRace tasks into 40 training
and 10 validation tasks for HE, and 50 held-out test tasks for
evaluating all methods. Both task execution and harness optimization are
performed using GPT-5.6 Luna with high reasoning effort. Each method is
evaluated with three independent runs per test task, each sharing a
four-hour budget ($`B=4\mathrm{h}`$) across task execution, harness
optimization, and evaluation. Detailed configurations are provided in
Appendix [A](#A1 "Appendix A Experimental Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization").

Metrics. To account for randomness, we summarize task $`i`$’s
best-so-far correct speedup across $`R=3`$ runs as
$`\bar{S}_{i}=\left(\prod_{r=1}^{R}S_{i}^{(r)}(B)\right)^{1/R}`$. Let
$`\overline{\mathrm{Cost}}_{i}`$ be its mean model cost in US dollars,
including harness optimization. Across $`N=50`$ tasks, we use harmonic
mean speedup to limit the influence of extreme values ([Shetty et al.,
2025](#bib.bib28)) and arithmetic mean task-level speedup per dollar:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\mathrm{Speedup@}4\mathrm{h}=\frac{N}{\sum_{i=1}^{N}\bar{S}_{i}^{-1}},\qquad\mathrm{Speedup/\$}=\frac{1}{N}\sum_{i=1}^{N}\frac{\bar{S}_{i}}{\overline{\mathrm{Cost}}_{i}}.
``` |  | (2) |

Reported mean model cost averages $`\overline{\mathrm{Cost}}_{i}`$
across tasks. Cost accounting and statistical details appear in
Appendix [A](#A1 "Appendix A Experimental Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization").

Offline harness optimization does not reliably improve performance. HE
reaches $`1.281\times`$ at four hours, below Frozen
(Table [1](#S5.T1 "Table 1 ‣ 5.2 Main Results ‣ 5 Experiments ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).
HE struggles to identify consistently effective harness revisions during
training, while the revisions selected through validation show limited

provides detailed results and failure analysis. HE costs an average of
\$24.56 per test run. Including offline training and validation costs,
shared across the 150 test runs, brings this average to at least
\$33.73. This additional offline expenditure does not translate into
better test performance or greater cost efficiency than Frozen.

Task-specific harness optimization supports continued improvement. Both
HS and BoxBox improve over Frozen, reaching $`1.539\times`$ and
$`1.702\times`$ at four hours, respectively, compared with
$`1.442\times`$ for Frozen
(Table [1](#S5.T1 "Table 1 ‣ 5.2 Main Results ‣ 5 Experiments ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).

$`1.431\times`$ to $`1.539\times`$ and BoxBox from $`1.530\times`$ to
$`1.702\times`$. These trends show that task-specific harness
optimization supports further progress as execution continues.

Agent-controlled harness optimization improves performance and
efficiency.

Whereas HS relies on an external controller to initiate revisions,
BoxBox lets the agent decide when to allocate budget to adapting its

address harness limitations as they arise and apply useful revisions
directly to the ongoing task.

### 5.3 Ablation Studies and Analysis

We further conduct ablation studies on 14 randomly sampled test tasks to
isolate the contributions of key design choices to the effectiveness and
efficiency of harness optimization, then analyze how agents perform
harness optimization during task execution.

Ablation Studies.

|----|----|----|----|
| w/o Agent Triggering | 1.508 | \$21.58 | 0.1338 |
| w/o Full Editing | 1.349 | \$16.07 | 0.1132 |

Table 2: Ablation study of BoxBox. We examine agent-controlled
triggering and full-harness editing in terms of task performance
($`\mathrm{Speedup@}4\mathrm{h}`$), model cost, and cost efficiency
(Speedup/\$).

Agent-controlled triggering. Following the scheduled refinement in
Continual Harness ([Karten et al., 2026](#bib.bib12)), the w/o Agent
Triggering variant schedules reviews every 30 minutes with full-harness
editing. It achieves lower speedup at higher model cost than
agent-triggered BoxBox
(Table [2](#S5.T2 "Table 2 ‣ 5.3 Ablation Studies and Analysis ‣ 5 Experiments ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).
Scheduled reviews can interrupt the process of proposing, implementing,
and evaluating code changes. They also consume model calls even when
they conclude that no harness revision is needed. In contrast, BoxBox
lets the agent decide when to allocate budget to harness optimization
based on the needs of the ongoing task.

Full-harness editing. Following Self-Harness ([Zhang et al.,
2026b](#bib.bib11)), the w/o Full Editing variant retains
agent-controlled triggering but restricts each review to a predefined
scope. It achieves lower speedup than BoxBox
(Table [2](#S5.T2 "Table 2 ‣ 5.3 Ablation Studies and Analysis ‣ 5 Experiments ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).
Predefined editing boundaries can constrain task-specific adaptations
that require changes across components or beyond the permitted scope.
Full-harness editing lets the agent decide what to modify and how
extensively based on the needs of the ongoing task.

Harness Optimization Analysis.

and harness optimization within a shared budget.

## 6 Conclusion

In this work, we introduced PerfRace, a benchmark for long-running
performance optimization of real-world software, and BoxBox, which
combines agent-triggered, full-harness revision from task-specific
experience with kernel-managed hot reloading that preserves execution
context. On PerfRace, offline Harness Evolution yields inconsistent
gains, whereas BoxBox achieves higher best-so-far correct speedup and
greater time and cost efficiency than the evaluated baselines. It
achieves a $`\mathrm{Speedup@}4\mathrm{h}`$ of $`1.70\times`$, compared
with $`1.54\times`$ for the strongest baseline, and reduces mean model
cost by $`29.3\%`$ relative to Frozen Harness. These results support
harness optimization as an agent capability for improving how it solves
a task while continuing its execution.

## Security and Responsible AI Limitations

BoxBox allows an agent to modify executable harness code during an
ongoing task, which introduces security and Responsible AI risks beyond
those of a fixed harness. In particular, the agent executes and modifies
code that may originate from untrusted repositories, and harness
revisions may introduce security regressions, weaken existing
safeguards, or create unintended execution behavior. More generally,
self-modifying agent mechanisms could be misused to alter controls or
expand capabilities in ways not intended by system operators. Our
evaluation is conducted in isolated research environments with
kernel-managed validation and rollback for harness updates and separate
shadow verification for task evaluation. These mechanisms reduce
experimental risk but do not constitute a complete security boundary or
guarantee safe behavior under adversarial conditions. BoxBox should
therefore be viewed as a research prototype rather than a
production-ready self-modifying agent framework. Any production
deployment would require additional sandboxing, access control, security
review, monitoring, and human oversight of agent-generated harness
changes before they are activated.

### A.2 Harness Evolution

Our HE baseline adapts the implementation of [Wang et al.
(2026b)](#bib.bib35) to PerfRace, retaining its core
diagnosis-and-revision workflow. We detail the offline optimization
procedure and examine training progress and the generalization of the
selected harness to held-out tasks.

Setup. We adapt task execution, evaluation, and experiment orchestration
to PerfRace, replacing the task-success objective with best-so-far
correct speedup under a fixed time budget and tailoring the diagnostic
and revision prompts to guide harness improvements that increase speedup
and reduce costs.

The reference HE experiments use full-batch training on Terminal-Bench
2.1 ([Wang et al., 2026b](#bib.bib35)). Publicly released mini-swe-agent
trajectories generated with DeepSeek-V4-Flash on this benchmark ([Kwok
et al., 2026](#bib.bib53)) average 50 agent steps and 12.2 minutes per
run, compared with 965 steps for our Frozen runs under a four-hour
budget on PerfRace. We therefore limit each training run to 45 minutes
and partition the 40 training tasks into mini-batches of five to keep
the volume of trajectory evidence manageable for diagnosis. Across three
reshuffled epochs (24 iterations), we evaluate $`h_{i-1}`$ on one
mini-batch at iteration $`i`$ and use the resulting trajectories and
evaluation outcomes to produce $`h_{i}`$. For validation, we compare
$`h_{8}`$, $`h_{16}`$, and $`h_{24}`$ using fresh baseline measurements.
Table [4](#A1.T4 "Table 4 ‣ A.2 Harness Evolution ‣ Appendix A Experimental Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")
summarizes the HE pipeline and its recorded model costs.

| Validation | 10    | 3 harnesses $`\times`$ 3 runs/task | 2 h            | 1,176.12  |

remaining below its initial level. Validation performance does not

(Table [1](#S5.T1 "Table 1 ‣ 5.2 Main Results ‣ 5 Experiments ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).
These results show that additional offline revisions do not reliably
improve training performance or yield a test-time advantage, consistent
with prior findings of limited transfer ([Wang et al.,
2026b](#bib.bib35)). Including the recorded offline cost raises mean
cost to at least \$33.73 per test run.

Failure analysis. To understand HE’s failure modes, we examine how a
revision introduced during training affected execution on a test task.
At iteration 5, diagnostic reports identified two patterns: (1)
measurements showed faster execution of the baseline code, which had
either remained unchanged or been restored after edits were discarded;
and (2) records of faster execution did not specify which code version
had been measured. These patterns made it difficult to determine whether
measured gains reflected actual code improvements or measurement noise.
HE therefore added a check to the harness to prevent agents from
submitting code without evidence of an actual performance improvement.

Specifically, the agent had to record the current and baseline commits,
at least three timing measurements for each version, and correctness

### A.3 Harness Scaling

Our HS baseline adapts the implementation of [Wang et al.
(2026b)](#bib.bib35) to PerfRace. We describe the execution procedure,
analyze model costs, and examine a failure case.

Setup. We adapt task execution and evaluation to PerfRace, using
best-so-far correct speedup under a fixed time budget as the
optimization objective. Each run shares a four-hour budget across task
execution, harness optimization, and evaluation. An external controller
revises the harness using feedback from each completed attempt and
starts a new agent session, preserving project-code progress and
resetting the execution context.

We record 2,132 HS attempts, with a median of 12 per run. Across 1,983
boundaries, the median interval between one attempt ending and the next
beginning is 3.37 minutes, including harness optimization and runtime
transition.

Model costs. HS’s session resets can lower input-token costs by reducing
the accumulated conversation history. Although project-code progress is
retained, subsequent attempts may need to reconstruct earlier decisions
or repeat experiments whose outcomes are no longer available in the
execution context. BoxBox preserves this context across harness updates,
allowing subsequent optimization to build directly on earlier findings.
This trade-off helps explain why HS’s lower total model cost does not
necessarily translate into greater optimization progress per dollar.

Failure analysis. To examine HS’s optimization process, we trace one
kitops--minilm-pack run
(Figure [8](#A1.F8 "Figure 8 ‣ A.3 Harness Scaling ‣ Appendix A Experimental Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")).
During one harness optimization step, HS’s controller reported that the
agent repeatedly rebuilt the project, ran tests, and reran the workload
on the same code version. It therefore added a repetition check to warn
after three consecutive matching command batches.

Figure 8: HS optimization trajectory on kitops--minilm-pack. Annotations
show selected harness revisions and an agent session containing 113
consecutive checks that produced no new performance measurements.

However, the new repetition check did not stop the agent from performing
the same checks using different command forms. The agent ran 113
consecutive commands repeating the same checks, without modifying code
or collecting new performance measurements. The check only looked for
consecutive repetitions of the same commands, so it could miss repeated
checks written in different ways. The run reached its best correct
speedup of $`1.649\times`$ at checkpoint 5, with no further improvement
in subsequent recorded checkpoints. The repeated checks revealed a need
for further harness revision during execution, yet HS performs harness
optimization only between agent sessions, leaving the current session to
continue under the existing harness.

This case illustrates how session-level external control can delay
harness revisions needed during ongoing task execution. The revised
check missed repeated validation expressed through different commands,
and the agent continued spending task time without making code changes
or collecting new performance measurements. Allowing the agent to
initiate further harness revision when these limitations become apparent
would provide an earlier opportunity to address them.

### B.4 Pair Verification

PerfRace uses Pair Verification to ensure that each task represents
meaningful project use, produces reproducible measurements, and rejects
shortcut solutions; this section describes the agent–human protocol and
analyzes the resulting curation trajectories.

#### B.4.1 Protocol

Pair Verification combines agent-led task construction with human review
to turn each project candidate into an executable task and assess its
realism, reliability, and integrity. The construction skill is provided
in
Appendix [D.2](#A4.SS2 "D.2 Pair Verification Skill ‣ D.1 Filter Prompt ‣ Appendix D Prompts and Skills ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization").
The agent develops the task in stages and pauses for a reviewer decision
after completing the evidence required for each quality criterion.

Figure 18: Pair Verification alternates between agent-led task
construction and human review at the Realism, Reliability, and Integrity
gates.

Explore and Design. The agent first studies the project’s documentation,
examples, code paths, and public usage evidence to understand its
purpose, users, and performance-relevant operations. The agent searches
public release pages for source code, models, and assets, scientific or
government data portals, downstream repositories, production archives,
and real user exports to identify candidate workload inputs. For each
input, the agent records its download location, version, and applicable
terms, and accepts it only when an explicit license, public-domain
designation, or written authorization permits redistribution with the
benchmark.

It uses these materials to identify candidate operations, but grounds
the workload and scale in a real user or downstream application rather
than repository-native tests, benchmarks, examples, or fixtures. The
agent compares plausible workload candidates, then traces the selected
operation from its user-facing entry point through the relevant project
code and demonstrates a small input-to-output execution on the
unmodified revision. During this run, it records dependency
installation, project build, input preparation, and operation time to
check that setup does not dominate the measurement and to estimate
whether complete verification can finish within the 1,200-second budget.
The agent repeats the operation on identical inputs to detect run-to-run
flakiness, including sporadic failures or inconsistent
correctness-relevant outputs, and to identify any dependence of runtime
on random state, network access, or external services. A candidate is
revised or rejected if its stochastic execution remains too variable for
reproducible performance measurement after fixing available random seeds
and aggregating repeated runs.

It then specifies the exact operation, workload and scale available to
the agent, held-out correctness cases, observable correctness utility,
performance metric, and measurement boundary. Before requesting Realism
review, the agent summarizes the project’s purpose and users, the
selected execution path, the basis for the input and scale, and the
alternatives it considered and rejected. The reviewer approves Realism
only when the operation, input, and scale represent meaningful project
use, the metric measures the stated utility, and the workload inputs can
be redistributed as part of the benchmark.

Build and Calibrate. After Realism approval, the agent derives the
installation, build, and run commands from upstream documentation, CI
configuration, and package manifests, and verifies them on the pinned
source revision. The agent implements the verifier, the task’s test
program that measures the performance metric on a separate copy of the
workload and checks additional held-out cases for correctness. It then
constructs the Harbor task files with instruction.md, task.toml, an
environment/ directory containing the editable project and workload, and
a separate tests/ directory containing the verifier code, workload copy,
held-out cases, and expected outputs. The agent pins the project
revision, base image, language toolchain, dependencies, workload assets,
and expected outputs so that the image can be rebuilt and the task rerun
without downloading project source or workload inputs. The task
instruction tells the agent how to build and run the project, what it
may edit, which behavior it must preserve, and which performance metric
to improve.

The agent then builds a fresh image and runs the verifier on the
unmodified project before calibrating performance measurements. The
agent selects the smallest resource profile that completes the workload
without CPU, memory, or storage pressure and sets the verifier timeout
within 1,200 seconds. The agent uses pilot and repeated runs to choose
the workload scale, warmups, repetitions, and aggregation, requiring the
final measurements to have a coefficient of variation below 10% while
keeping build and setup outside the timed operation. The agent checks
that the timing boundary covers the complete operation requested in the
task while excluding one-time environment setup and verifier preparation
that are unrelated to the optimization objective.

For the $`n`$ timed measurements retained after warmup,
$`x_{1},\ldots,x_{n}`$, we compute

|  |  |  |
|----|----|----|
|  |
``` math
\mathrm{CV}=\frac{s}{\bar{x}},\qquad\bar{x}=\frac{1}{n}\sum_{i=1}^{n}x_{i},\qquad s=\sqrt{\frac{1}{n-1}\sum_{i=1}^{n}(x_{i}-\bar{x})^{2}}.
``` |  |

After fixing the workload, correctness checks, resources, and
measurement protocol, the agent builds the final image and evaluates the
unmodified baseline and one optimization candidate under the same
conditions. The reviewer examines the fresh-build correctness results,
repeated measurements and CVs, verification time, resource allocation,
and candidate trajectory. The reviewer approves Reliability only when
fresh builds and repeated runs return the same correctness verdict and
stable performance measurements with the chosen warmups, repetitions,
aggregation, and measurement boundary.

Validate Integrity. To identify reward-hacking paths that could receive
a valid score without completing the task, the agent tests deliberately
incorrect, partial, hard-coded, and work-skipping solutions and checks
that workload inputs, expected outputs, and verifier-owned data cannot
be replaced by agent-controlled files. The agent inspects the evaluation
image for leaked expected outputs, verifier code, or construction notes
that could reveal the hidden checks. For example, in
rust-clippy--cargo-package-lint, removing Cargo dependency tracking made
later runs reuse a cached lint result, which the verifier detects by
touching clippy-driver, running the workload twice against the same warm
target, and requiring each Cargo JSON trace to report a non-fresh
compiler artifact for cargo.

The reviewer approves Integrity only when every requirement in the task
instruction is checked, every verifier check follows from the declared
task, and none of the tested shortcut solutions can receive a valid
score.

Finalize. After all three reviews, the reviewer chooses accept, revise,
or reject; accepted tasks pass final compatibility checks before
publication as a task package comprising an immutable Docker image and
task artifact.

### B.5 Evaluation Protocol

For each submission, the Judge snapshots the agent’s current container
and starts a temporary shadow container from that snapshot. The Judge
creates the snapshot with docker compose commit, launches the shadow
container under a separate Compose project, and removes its container,
local image, and volumes after verification. The agent container remains
paused during verification and resumes from the same workspace state
after the shadow container is removed.

Inside the shadow container, the verifier runs through tests/test.sh and
emits the correctness verdict and performance metric as JSON. The
verifier code, workload copy, held-out cases, and expected outputs are
absent from the agent container and available only inside the shadow
container. Each task declares its warmups, repetition count, aggregation
rule, and required correctness pass rate in task.toml, and its verifier
returns a performance metric only when that pass rate is met.

The task clock continues while the shadow is created, executed, and
removed, so every submission trades part of budget $`B`$ for additional
correctness and performance feedback. After verification, the Judge
returns the correctness verdict and performance metric to the agent as
feedback for subsequent optimization. For a correct submission, the
Judge computes the speedup score by dividing the unmodified baseline
metric by the submission metric. Submissions that fail correctness,
exceed the verifier timeout, or do not produce a valid performance
metric cannot update the best-so-far trajectory $`S(t)`$.

Five minutes before the deadline, the agent receives a final delivery
prompt asking it to leave the project in a coherent state before the
Judge performs one final shadow verification of the current workspace.

### C.1 Effects on Subsequent Interactions

Equation [1](#S4.E1 "In 4.1 Problem Formulation ‣ 4 BoxBox ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")
describes two ways a harness revision can affect subsequent execution
while the language model $`\mathcal{M}`$ remains fixed. Changes to how
the harness constructs model inputs can alter $`p_{\mathcal{M},H_{k}}`$,
influencing the agent’s next action. Changes to
$`\operatorname{Execute}_{H_{k}}`$ can alter how that action is carried
out and how its result is returned as an observation. A revision can
affect either or both, so its influence extends to the trajectory
generated after activation.

The current harness also governs the review loop. Once a revision is
activated, subsequent reviews use the updated implementation and can
examine the experience accumulated under it. Harness changes can
therefore affect both task execution and the process used to produce
later revisions.
Appendix [A.4](#A1.SS4 "A.4 Case Study ‣ Appendix A Experimental Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")
illustrates concrete changes to guidance, measurement, command polling,
and context handling.

### C.2 Review

The task-solving agent requests review through boxbox() without having
to propose a patch. The initial harness requires intervening task
activity and a 30-minute cooldown after each completed review; once
eligible, the agent decides whether and when to request another review.
The kernel preserves the task conversation and launches a separate agent
review session under the current harness. The reviewer can inspect task
trajectories and Git history, but edits only the harness, treating
project code as read-only. It may retain the current harness, add
guidance, or modify executable behavior, committing any changes before
ending review. The default review skill is provided in
Appendix [D.3](#A4.SS3 "D.3 Self-Review Skill ‣ D.2 Pair Verification Skill ‣ D.1 Filter Prompt ‣ Appendix D Prompts and Skills ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization").

### C.3 Execution Context

Execution context includes both runtime-owned state and the existing
task environment. The former includes the task conversation, review
history, and records of which trajectory entries have already been
reviewed. These are exported as a state snapshot. The terminal session
and project workspace remain in place: shell state, ongoing processes,
and project files are preserved through the existing environment
connection.

When the agent calls boxbox(), the runtime yields control to the kernel,
suspending the task interaction loop while review proceeds separately.
This pauses the agent’s task decisions, not the entire container or its
processes. Before importing state into a candidate runtime, the kernel
makes a separate copy, preserving the original snapshot for recovery if
the candidate fails. This separates changing the agent implementation
from restarting its task environment.

### C.4 Hot Reloading

Harness revisions are tracked as Git commits, while the kernel remains
separate from the editable harness. Before switching, the kernel checks
the committed candidate, loads its runtime, and verifies that it
supports task execution and context transfer. The current runtime keeps
its terminal connection until the candidate successfully imports the
copied state. The kernel then transfers the same terminal session to the
candidate and returns control to it, resuming task interaction from the
preserved conversation in the same workspace. If activation fails, the
kernel retains or restores the previous runtime and context. For
agent-requested reviews, the reviewer can leave concise guidance on
using new capabilities and continuing the task. This guidance is
preserved across the update, and the resumed agent is prompted to read
it before continuing. Task execution and review share the same budget
and cost accounting.
Table [12](#A3.T12 "Table 12 ‣ C.4 Hot Reloading ‣ Appendix C BoxBox: Method Details ‣ BoxBox: Recursive Harness Self-Improvement for Long-Running Performance Optimization")
summarizes how execution continues under each outcome.

|  Outcome |  Continuation |
|----|----|
|  No harness change |  Resume the current runtime with the preserved task context. |
|  Successful update |  Continue under the revised harness with transferred context, the existing terminal session, and the same project workspace. |
|  Update fails |  Retain or restore the previous runtime and its preserved context. |
|  Runtime fault |  Enter recovery and review using the retained execution records; restart the terminal while preserving project files. |

### C.5 Recovery

The kernel retains a recovery point across harness updates. A newly
activated runtime remains provisional until it reaches the next
agent-requested review without a runtime fault. If it fails before that
boundary, the kernel restores the previous confirmed harness and state
and initiates a review using the fault evidence. Faults in a confirmed
runtime also trigger review. Runtime-fault recovery starts a fresh
terminal, so shell-local state is lost, but project files, harness
history, and execution records remain available. The retained records
let subsequent reviews examine failed revisions and help the
task-solving agent determine how to continue interrupted work.

The following listing presents the default review skill with
performance-optimization-specific guidance omitted. “Target Agent”
denotes the task-solving agent.

`\iow_now:Ne``¨``\iow_now:Ne``¨# Self-Review``\iow_now:Ne``¨``\iow_now:Ne``¨Act as the macro-level controller of the Target Agent’s task-solving process. Review the trajectory to diagnose the task-solving process, then retain the current harness or select a focused-feedback or reusable-ability adaptation that improves subsequent Target progress within the remaining shared budget.``\iow_now:Ne``¨``\iow_now:Ne``¨## Review the task-solving process``\iow_now:Ne``¨``\iow_now:Ne``¨Treat each review as one iteration in a continuing self-review loop. At the start of every review, examine the accumulated trajectory comprehensively before selecting an intervention.``\iow_now:Ne``¨``\iow_now:Ne``¨Use that broad diagnosis to choose a focused intervention that is supported by the evidence and likely to materially improve subsequent Target progress. Include only the feedback or reusable capabilities justified by the diagnosed problems in task execution and the evidence needed to evaluate their effect.``\iow_now:Ne``¨``\iow_now:Ne``¨Never be satisfied with the current optimization state while task budget remains. Use recorded actions, observations, and measurements to identify all material unsupported links, distinguish evidence from inference, and identify plausible explanations not ruled out. Treat claims that an experiment completed, improved performance, or excluded a direction as unverified until supported by the trajectory. Explain how each unsupported link affects task-execution cost, experiment selection, or progress.``\iow_now:Ne``¨``\iow_now:Ne``¨Critique the Target Agent’s choice of actions, not just candidate outcomes.
````
