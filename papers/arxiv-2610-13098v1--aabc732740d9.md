# VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning

Yingbo Ma Affiliation:  New York University    Kuangshi Ai
Affiliation:  University of Notre Dame    Gordon Dai Affiliation:  New

###### Abstract

Visual agents for symbolic graphics reasoning depend on executable world
representations, yet continued improvement remains bottlenecked by
ambiguous supervision from final renders. Recent agentic systems refine
scenes through repeated interaction, but they lack mechanisms to
recursively extract actionable evidence from execution traces,
overlooking which proposed symbolic edits survived, disappeared, or
interfered during program execution. To address this, we propose VETR
(Verified Execution Trajectories for Refinement), a framework that
enables _agentic recursive self-improvement_ over executable world
representations for symbolic graphics reasoning. Within each task, VETR
retains aligned program/render records with bounded runtime observations
and introduces an _execution refiner_ that compiles observed writes and
state changes into constrained alternative programs. The refiner
validates their endpoints and preservation conditions against captured
runtime state; the ordinary visual verifier then assesses goal
relevance. Repair construction makes no additional language-model calls,
but can require additional executions. Evaluations on BlenderGym (280
tasks) and BlenderBench (27 released tasks) with GPT-5.6-luna and
Qwen3.8-27B show that VETR consistently outperforms existing refinement
strategies, including BlenderAlchemy and VIGA. Controlled ablations
evaluate the contributions of execution refinement and role-asymmetric
evidence organization under fixed generator-interaction caps.

## 1 Introduction

Large Language Model (LLM) agents have made remarkable strides in code
generation, visual reasoning, and interactive editing by equipping LLMs
with tools, planning, and self-refinement capabilities ([Madaan et al.,
2023](#bib.bib10); [Shinn et al., 2023](#bib.bib12); [Gou et al.,
2024](#bib.bib6)). Building on this progress, recent systems for
symbolic graphics reasoning formulate scene understanding and editing as
an iterative process where a generator proposes program modifications
and a verifier evaluates the rendered output ([Yin et al.,
2026](#bib.bib17); [Kuang et al., 2026](#bib.bib21)). These systems
demonstrate that agentic interaction improves over one-shot generation
and that executable programs can serve as world representations
specifying geometry, materials, lighting, and spatial
relationships ([Wang et al., 2026a](#bib.bib27)). However, final-render
feedback alone does not expose edit causality: an image comparison need
not reveal which proposed symbolic edits survived execution, which were
silently overwritten, or which interfered with shared scene resources.

This motivates an execution-evidence interface alongside visual
feedback ([Yin et al., 2026](#bib.bib17); [Kuang et al.,
2026](#bib.bib21)). Additional iterations can supply new proposals, but
do not directly expose effects omitted from the feedback interface.
Logging alone also leaves open how observed values should become
alternative programs ([Wang et al., 2026a](#bib.bib27)). We address this
with supported update operators and explicit runtime preservation
checks. Observed writes supply hypotheses about alternative executions,
while visual verification remains responsible for assessing those
alternatives against the task goal.

To address this, we propose VETR (Verified Execution Trajectories for

execution refiner to construct alternatives from observed writes and
state transitions. The refiner compiles supported numerical changes and
compatible resource bindings, then checks their endpoints and
preservation conditions by fresh execution, without additional
language-model calls. It delivers a runtime-valid alternative when
available, otherwise retaining the raw successful result or the
preceding delivered record after failure. The ordinary visual verifier
assesses the delivered result, and the generator conditions its next
proposal on the available execution outcomes and feedback. This is the
recursive program-revision loop depicted in

We evaluate VETR on BlenderGym (280 editing tasks across five families)
and BlenderBench (27 released tasks at three difficulty levels) with
GPT-5.6-luna and Qwen3.8-27B. VETR is the strongest complete system on
both benchmarks and both backbones, and paired comparisons confirm gains
are not artifacts of completion rates. Ablations isolate the improvement
to the execution refiner (disabling it reduces six-cell BlenderBench
improvement from $`+54.45\%`$ to $`+35.33\%`$ on GPT and $`+56.17\%`$ to
$`+30.09\%`$ on Qwen), and to role asymmetry and execution history (with
GPT on BlenderGym, removing role asymmetry or limiting history raises
$`N\text{-}CLIP`$/$`PL`$ errors by 12.7%/23.7% and 48.5%/79.0%,
respectively). These results support contributions from execution
refinement and evidence organization within the evaluated agent loop;
fixed generator-interaction caps do not imply equal total execution
cost.

Our contributions are summarized as follows:

- •
  Executable world representation for symbolic graphics reasoning. We
  build on scene representation work to establish executable programs as
  the foundation for iterative scene editing, enabling direct
  manipulation of geometry, materials, lighting, and spatial
  relationships.
- •
  Agentic recursive self-improvement with an execution refiner. We
  formulate scene refinement as a propose–execute–observe–verify cycle
  and design a refiner that compiles execution-trace evidence into
  bounded program updates under preservation constraints, without
  additional LLM inference ([Madaan et al., 2023](#bib.bib10); [Shinn et
  al., 2023](#bib.bib12); [Gou et al., 2024](#bib.bib6)).
- •
  Empirical validation on graphics editing benchmarks. We evaluate on
  BlenderGym and BlenderBench across two backbones, showing consistent
  gains over VIGA ([Yin et al., 2026](#bib.bib17)) and BlenderAlchemy,
  with controlled ablations evaluating execution refinement and context
  organization within the host loop.

## 2 Method

VETR refines complete scene programs through a
_propose–execute–observe–verify_ loop. A private execution refiner
constructs alternatives from bounded runtime observations and checks
their realization before ordinary visual verification. Runtime
acceptance and visual goal assessment serve different purposes: the
former checks a candidate’s stated effects and preservation conditions;
the latter guides subsequent editing toward the goal.

### 2.1 Executable World Representation

A task supplies a base scene $`B`$, an editable initial program
$`p_{0}`$, a start image $`r_{0}`$, and a goal image $`y^{\star}`$.
Following code-based scene representations ([Wang et al.,
2026a](#bib.bib27)), the generator submits a complete Python program
$`q_{t}`$, conditioned on the task and its retained interaction history.
Complete means executable relative to the supplied objects and assets in
$`B`$, not a standalone scene constructor. Each submission and repair
executes afresh from $`B`$; the initial program is not run as an extra
preparation step before each submission.

The _raw execution record_ $`z_{t}=(q_{t},r_{t},S_{t},\tau_{t})`$
associates the submitted program with its render, captured state, and
observed writes. The captured state is
$`S_{t}=(\theta_{t},\Pi_{t},G_{t})`$, where $`\theta_{t}`$ stores
supported numerical properties, $`\Pi_{t}`$ stores object-to-resource
references, and $`G_{t}`$ stores captured scene structure. The bounded
write trace is

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\tau_{t}=\bigl[(o_{i},k_{i},v_{i},\ell_{i})\bigr]_{i=1}^{m_{t}},
``` |  | (1) |

where an event records the owner resolved at execution time, a supported
property path, its observed value, and its source location. The observer
covers supported assignments in the submitted source, including local
helpers; imported-library writes and unresolved aliases do not provide
owner-qualified events. Unobserved effects remain unknown. Execution
failures retain available observations and diagnostics, with unavailable
record fields left undefined.

We distinguish $`z_{t}`$ from the *delivered record* $`\bar{z}_{t}`$,
which may contain a repaired program, the raw result, or the preceding
delivered record $`z^{-}`$. Generated program/render pairs retain their
common provenance. Initial observations $`(S_{0},\tau_{0})`$ are
obtained by executing $`p_{0}`$ once without an additional render. We
denote the initial reference by $`z_{0}=(p_{0},r_{0},S_{0},\tau_{0})`$,
marking $`r_{0}`$ as the supplied visual anchor, not a render from that
observation pass. The refiner takes $`z_{0}`$ so that both initial
writes and their final endpoints are available
(Appendix [B](#A2 "Appendix B Execution-refiner implementation details ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).

### 2.2 Execution Refiner

The refiner examines every submitted execution, including successful
proposals whose images already improve. Planning actions do not invoke
it. It uses $`z_{t}`$, the initial observations, and $`z^{-}`$ to
construct and validate alternative complete programs without additional
language-model calls.

#### Candidate effects from execution evidence.

For a supported non-light cell $`(o,k)`$ and source execution
$`s\in\{t,0\}`$, define its *displaced-value indices* in $`\tau_{s}`$ as
the observed writes whose values differ from that source’s final
endpoint. The recovery endpoint is the latest such value:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathcal{I}_{s}(o,k)`$ | $`\displaystyle=\{i:o_{i}=o,\ k_{i}=k,\ v_{i}\not\simeq\theta_{s}(o,k)\},`$ |  | (2) |
|  | $`\displaystyle\widehat{v}_{s}(o,k)`$ | $`\displaystyle=v_{\max\mathcal{I}_{s}(o,k)}\quad\text{when }\mathcal{I}_{s}(o,k)\neq\varnothing.`$ |  |  |

Here $`\simeq`$ denotes the runtime checker’s numerical agreement
predicate. Current and initial traces supply separate recovery
hypotheses, both applied to the current complete program. The
light-recovery channel similarly reconstructs observed owner-local
energy/color requests displaced by later shared writes, resetting
earlier requests after explicit data rebinding. These values are
alternative endpoints, not inferred user intent or proof that a later
assignment was erroneous.

In the ordered controller, if no recovery candidate has been accepted,
the light channel considers eligible full and half effective changes
between $`S^{-}`$, the previous delivered state, and $`S_{t}`$. For
owners in the submitted edit’s supported scope, the *projected light
endpoint* is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
u_{\alpha,o}=\phi(S^{-}(o))+\alpha\bigl[\phi(S_{t}(o))-\phi(S^{-}(o))\bigr],\qquad\alpha\in\{1,\tfrac{1}{2}\},
``` |  | (3) |

where $`\phi(E,c)=Ec`$ is the compiler’s effective-value map for light
energy $`E`$ and color $`c`$. Projection modifies the previous delivered
program, retaining its other captured state. It therefore differs from
recovery, which modifies the raw proposal. The map supplies algebraic
parameter targets, not a guarantee about the rendered image.

#### Compatible values and resource ownership.

Each candidate $`h`$ specifies a reference record
$`z_{h}^{\mathrm{ref}}`$, required endpoints, and permitted changes.
Recovery uses $`z_{h}^{\mathrm{ref}}=z_{t}`$; projection uses
$`z_{h}^{\mathrm{ref}}=z^{-}`$. The compiler appends a patch to that
reference program, producing $`q^{\prime}_{h}`$. It retains reference
values for other captured cells and makes permitted local resource
copies when shared owners require incompatible endpoints. Compatible
sharing is retained. Non-light compilation restores supported values
directly; light compilation uses a bounded reconstruction of $`\phi`$
and compatible owner tuples. Because $`\phi`$ is not one-to-one, its
formula alone does not specify the reconstruction rule
(Appendix [B](#A2 "Appendix B Execution-refiner implementation details ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).

#### Runtime realization and preservation.

The compiled program executes afresh from $`B`$. For the
numerical-property channel, let $`\mathcal{C}_{h}`$ be the reference’s
captured supported cells, $`W_{h}\subseteq\mathcal{C}_{h}`$ the selected
write support, and $`d_{h}`$ its required numerical endpoints. Fresh
readback must satisfy

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\theta^{\prime}_{h}(c)\simeq\begin{cases}d_{h}(c),&c\in W_{h},\\
\theta_{h}^{\mathrm{ref}}(c),&c\in\mathcal{C}_{h}\setminus W_{h}.\end{cases}
``` |  | (4) |

Additional checks cover captured node/mesh structure, protected object
frames, and render context. Light candidates are checked against their
captured owner tuples, effective endpoints, and permitted reference
changes. The captured cells $`\mathcal{C}_{h}\setminus W_{h}`$ are known
values to preserve; properties outside $`\mathcal{C}_{h}`$ are not
covered by this numerical contract. Channel-specific checks constrain
the refiner’s changes relative to its reference, not every change made
by the generator, and are not relaxed after failure.

#### Validation and delivery.

The fixed order is current/initial non-light recovery, current/initial
light recovery, then full-/half-effect projection. Unsupported
alternatives or those lacking required evidence cannot pass the
contract.
Algorithm [1](#alg1 "Algorithm 1 ‣ Execution cap, delivery, and visual feedback. ‣ B.1 Compiling trace evidence into realized edits ‣ Appendix B Execution-refiner implementation details ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
makes the six-additional-execution cap explicit and returns the first
accepted alternative. It also retains endpoint-based skip rules: raw
reuse as full-effect projection requires that candidate’s complete
runtime contract relative to $`z^{-}`$. If the endpoint matches but
those checks fail, the reported branch skips the compiled full-effect
program rather than executing it. Such a skip is not proof of an
equivalent rerender;
Appendix [B](#A2 "Appendix B Execution-refiner implementation details ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
explains its implications. If no alternative is accepted, retain a
successful raw result, otherwise reuse the exact preceding record. Raw
fallback is not certification under a repair contract.

The ordinary visual verifier then evaluates the delivered result against
$`y^{\star}`$. Passing a runtime contract neither requires nor
guarantees lower image error. The recursion is within-task program
revision: subsequent proposals use the delivered result and retained
feedback, without a monotonic-improvement guarantee or a claim that each
program encodes the entire history.

### 2.3 Role-Asymmetric Evidence Organization

The refiner’s internal evidence and the agents’ visible contexts are
distinct. The refiner consumes observed writes, captured endpoints, and
resource bindings. The generator retains its actions and delivered tool
outcomes in a bounded multimodal history, with 24 recent messages by
default and the task/planning inputs pinned separately. The visual
verifier receives the current delivered comparison and returns a
goal-directed critique; its default context is reset rather than sharing
the generator’s accumulated transcript. This organization does not
require either agent to interpret the complete private trace. The
three-message and shared-memory variants change these context policies
(Appendix [G](#A7 "Appendix G Complete context ablations ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).

Algorithm [2](#alg2 "Algorithm 2 ‣ Appendix D Complete refinement procedure ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
places execution refinement inside the host loop and distinguishes the
generator-interaction cap from additional repair executions. At width
$`N>1`$, each executed candidate is refined before the visual tournament
selects a delivered outcome. Final evaluation uses the last successful
selected render from a completed run, not the best historical image;
failures do not replace its associated program. The supplied start image
alone does not constitute a successful generated answer
(Appendix [N](#A14.SS0.SSS0.Px3 "Answer extraction. ‣ Appendix N Execution settings ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).

## 3 Experiments

### 3.1 Experiment Setup

We evaluate the complete VETR system on two established test suites,
BlenderGym ([Gu et al., 2025](#bib.bib8)) and BlenderBench ([Yin et al.,
2026](#bib.bib17)), which evaluate program-based 3D graphics editing
across diverse visual modification tasks. Throughout the main benchmark
results, VETR denotes the full system with execution refinement enabled
by default; the otherwise matched variant with refinement disabled is
reported only in the ablation study.

Tasks and systems. BlenderGym contains 280 editing tasks: 85
blend-shape, 50 placement, 55 geometry, 45 lighting, and 45 material
tasks ([Gu et al., 2025](#bib.bib8)). Each task supplies an initial
program, start image, and goal image. BlenderBench contains 27 released
tasks across three difficulty levels, with nine tasks per level. We
compare One-Shot (direct generation from the initial program and visual
target without iterative feedback), BlenderAlchemy, VIGA, and VETR.
GPT-5.6-luna uses three separate 280-task cohorts: systems, context
ablations, and scene origin/guidance. All GPT-5.6-luna and Qwen3.8-27B
runs use Blender 3.6.0, and every paired task shares a runtime.
VIGA/VETR allow ten generator interactions. Each ablation changes only
its named setting; system comparisons retain each system’s instructions
and execution conventions.
Table [16](#A14.T16 "Table 16 ‣ Appendix N Execution settings ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
maps these cohorts to the full results and configurations.

Measurements. We report negative CLIP similarity
$`N\text{-}CLIP=1-\langle\hat{f}(r),\hat{f}(y^{\star})\rangle`$, using
unit-normalized CLIP ViT-B/32 embeddings, and photometric loss $`PL`$,
the RGB mean squared error in $`[0,1]`$ ([Radford et al.,
2021](#bib.bib11)). Lower is better; tables scale both by 100. The same
stored answer renders also provide PSNR, SSIM, AlexNet LPIPS, Canny edge
F1, and CLIP similarity ([Wang et al., 2004](#bib.bib19); [Zhang et al.,
2018](#bib.bib20)). For PSNR, SSIM, edge F1, and CLIP similarity, higher
is better, whereas for LPIPS, lower is better. PSNR is computed per
image before averaging; CLIP and $`N\text{-}CLIP`$ are algebraically
related. Edge F1 uses thresholds 100/200 on 8-bit grayscale and a
two-pixel Chebyshev matching tolerance. The evaluated iterative wrapper
renders Camera1; the evaluator averages matched views when more than one
is available.
Appendix [L](#A12 "Appendix L Extended image metrics ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
provides all definitions. Paired comparisons use the tasks valid for
both systems. For each, we report a 95% task-level bootstrap confidence
interval (5,000 resamples of tasks with replacement, seed 0) for the
relative reduction in mean error, and an exact two-sided sign test on
per-task wins with ties excluded; a difference is *statistically
significant* when the interval excludes zero and $`p<.05`$
(Appendix [J](#A10 "Appendix J Detailed paired comparisons ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).

### 3.2 BlenderGym

We first evaluate the complete VETR system against one-shot generation
and iterative baselines across diverse editing families. These system
comparisons characterize visual quality under the reported
configurations; the component ablations separately test execution
refinement and evidence organization within the host loop.

Table [2](#S3.T2 "Table 2 ‣ 3.2 BlenderGym ‣ 3 Experiments ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
reports the complete-system results. VETR achieves the strongest overall
performance on both GPT-5.6-luna and Qwen3.8-27B, and consistently
outperforms One-Shot, VIGA, and BlenderAlchemy across the aggregate
metrics and nearly all family-level comparisons. On GPT, VETR attains
the best $`PL`$ and $`N\text{-}CLIP`$ in four of the five editing
families, with material editing as the only exception; on Qwen, it
achieves the best result in every reported family–metric cell. These
results are particularly notable in light of the original VIGA
study ([Yin et al., 2026](#bib.bib17)), which reported substantial gains
over a GPT-4o One-Shot baseline. In our experiments with newer and
stronger backbones, however, the gap between iterative visual refinement
and One-Shot becomes considerably smaller and can even reverse. A
plausible explanation is that improvements in foundation-model
capabilities have substantially strengthened one-shot program
generation, reducing the headroom available to refinement strategies
that rely primarily on rendered visual feedback. In contrast, VETR
continues to improve substantially over these stronger One-Shot outputs.
Rather than depending on an initially weak program that can be corrected
through repeated visual inspection, VETR exploits execution evidence to
identify which symbolic edits were actually realized, overwritten, or
disrupted, and recursively incorporates this information into subsequent
program states. These gains are statistically significant against
One-Shot on both backbones: VETR lowers $`N\text{-}CLIP`$/$`PL`$ by
52.7%/58.8% on GPT and by 28.1%/49.6% on Qwen, and on Qwen it also
improves over VIGA by 40.0%/56.3%. In each case the bootstrap interval
excludes zero and the sign test gives $`p\leq.0043`$
(Appendix [J](#A10 "Appendix J Detailed paired comparisons ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning"),
Table [11](#A10.T11 "Table 11 ‣ Appendix J Detailed paired comparisons ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).

Table [2](#S3.T2 "Table 2 ‣ 3.2 BlenderGym ‣ 3 Experiments ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")

### 3.3 BlenderBench

BlenderBench is a more demanding testbed than BlenderGym, with camera
adjustment, multi-step editing, and compositional tasks that introduce
stronger dependencies between successive scene modifications. These
settings create more opportunities for intermediate errors to propagate,
making them particularly suitable for evaluating whether VETR can
preserve reliable refinement under increasingly entangled execution
trajectories.

Across the 27 released BlenderBench tasks, VETR achieves the best result
in every level–metric cell on both GPT-5.6-luna and Qwen3.8-27B,
outperforming One-Shot and VIGA throughout the benchmark. Relative to
VIGA on the same tasks, VETR reduces $`N\text{-}CLIP`$/$`PL`$ by
55.0%/67.7% on GPT and 27.6%/48.6% on Qwen, showing that its advantage
remains substantial even as task complexity increases.

The strongest separation appears on GPT Level 3, the most compositional
setting, where VETR lowers $`N\text{-}CLIP`$/$`PL`$ by 72.4%/75.2%
relative to VIGA. This is precisely the regime in which
execution-grounded refinement is most useful: when multiple edits
interact, a failure may arise not only from an incorrect visual judgment
but also from symbolic writes that are overwritten, only partially
realized, or otherwise altered during execution. By retaining the
execution trace and converting witnessed state changes into bounded
program updates, VETR can correct these failures before they cascade
into later steps. In contrast, render-only refinement has less direct
evidence about which intermediate edits actually survived execution.

and its unrendered tasks are excluded from its reported means.

### 3.4 Ablation Study

The ablation study examines three design choices: (i) adding the
execution refiner within a fixed generator-interaction cap; (ii) using
separate generator and verifier contexts rather than shared memory; and
(iii) retaining a longer generator history. These interventions test the
refiner and its surrounding evidence interface without assuming that
both agents consume the private runtime trace.

#### Execution refinement.

We first isolate the execution-refiner stage, which converts observed
writes and state transitions into runtime-validated updates. Disabling
only this stage holds prompts, tools, base-scene execution policy,
backbone, and the ten-generator-interaction cap fixed. The enabled stage
can still perform additional repair executions.

Disabling refinement degrades performance in 11 of the 12 level–metric
cells across the two backbones
(Table [4](#S3.T4 "Table 4 ‣ Execution refinement. ‣ 3.4 Ablation Study ‣ 3 Experiments ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")),
often by substantial margins. On GPT, removing refinement increases both
$`PL`$ and $`N\text{-}CLIP`$ errors at every difficulty level, with the
largest degradation on Level 3: $`PL`$ rises from 5.3922 to 11.8475 and
$`N\text{-}CLIP`$ from 6.3201 to 15.2108. The same pattern holds on
Qwen, where disabling refinement substantially increases errors on
Levels 1 and 3 and raises Level 2 $`PL`$ from 0.2585 to 2.9924. Paired
statistics over the 27 GPT tasks confirm the effect: refinement lowers
mean $`PL`$ by 41.8%, which is statistically significant (bootstrap
interval $`[6.7,49.0]`$ excludes zero; sign test 24/3 wins,
$`p=4.9\times 10^{-5}`$), and lowers mean $`N\text{-}CLIP`$ by 32.2%
with a bootstrap interval of $`[14.4,55.5]`$
(Appendix [J](#A10.SS0.SSS0.Px1 "Paired statistics for the execution-refinement ablation. ‣ Appendix J Detailed paired comparisons ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning"),
Table [12](#A10.T12 "Table 12 ‣ Paired statistics for the execution-refinement ablation. ‣ Appendix J Detailed paired comparisons ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).

These results support adding execution refinement within the same
generator-interaction cap. Constructing a repair makes no additional
language-model call, but validation can add up to six execution attempts
per submitted program. The comparison therefore holds the generator
budget fixed, not total computation.

## 4 Discussion and Conclusion

VETR treats executions as evidence for revising an executable scene.
Authoritative records identify the result being refined; observed writes
and state transitions expose how proposed changes become realized
effects. The refiner turns selected observations into executable updates
by jointly choosing supported values and compatible bindings, then
validates the resulting program against runtime contracts before visual
verification. On native BlenderBench, adding this execution stage lowers
aggregate visual error on both evaluated model backbones. Recorded
interventions show how the same evidence-to-program pipeline operates
inside ordinary visual reasoning, while the host-loop studies
characterize the surrounding execution and context interfaces.

#### Scope and transfer.

The BlenderGym history and execution-origin contrasts cover broad
target-view editing; the native BlenderBench comparison evaluates the
complete closed-loop refiner on released tasks. Runtime validation
establishes realization and preservation only for the captured
properties. Goal relevance is assessed by the ordinary visual verifier,
allowing subsequent proposals to build on the delivered result. For
another domain, such as SVG or CAD, the same principle requires
observable program effects, supported update operators, and an explicit
preservation contract. The current refiner operates on a fixed set of
write types derived from the Blender execution model, so extending it to
new domains requires defining additional write grammars and preservation
boundaries. Future work could explore learned preservation models that
infer coupling constraints directly from execution traces.

Generative AI assisted code inspection, literature organization,

renders. The authors are responsible for the final claims, references,

The supplement provides execution and context settings, full paired
tables, metric definitions, and per-task provenance. The supplied

## Appendix A Related Work

#### Executable representations and program revision.

Programs provide compositional control over scene structure: LayoutGPT,
3D-GPT, Holodeck, and SceneCraft generate scenes via language models
([Feng et al., 2023](#bib.bib5); [Sun et al., 2025](#bib.bib13); [Yang
et al., 2024](#bib.bib16); [Hu et al., 2024](#bib.bib9)); Scene Language
unifies programs with semantic and visual representations ([Zhang et
al., 2025](#bib.bib23)); Code-as-World treats executable worlds as
revisable hypotheses ([Wang et al., 2026a](#bib.bib27)). NLI4VolVis
combines language-guided editing with multi-agent control over editable
3D Gaussian representations ([Ai et al., 2026c](#bib.bib1)), while
end-to-end agent harnesses coordinate planning, implementation, and
validation of visual analysis applications ([Miao et al.,
2026](#bib.bib4)). For iterative editing, BlenderAlchemy, VIGA, and
VULCAN combine rendered feedback, visual memory, and geometric
constraints ([Huang et al., 2024](#bib.bib7); [Yin et al.,
2026](#bib.bib17); [Kuang et al., 2026](#bib.bib21)); EZBlender adds
local validation ([Wang et al., 2026b](#bib.bib14)); SEIG imposes stage
budgets and rollback ([He et al., 2026](#bib.bib28)). These systems
establish feedback loops but lack mechanisms to extract alternatives
from execution traces. VETR fills this gap by compiling observed writes
and bindings into bounded updates validated before the next proposal.

#### Agent memory, execution evidence, and preservation.

Feedback-driven refinement is studied by Self-Refine, Reflexion, CRITIC
([Madaan et al., 2023](#bib.bib10); [Shinn et al., 2023](#bib.bib12);
[Gou et al., 2024](#bib.bib6)), Self-Debugging, and CodeAct ([Chen et
al., 2024](#bib.bib25); [Wang et al., 2024](#bib.bib26)); VDebugger
leverages stepwise traces ([Wu et al., 2024](#bib.bib29)); visual unit
tests guide revision ([Panagopoulou et al., 2025](#bib.bib24)); and
agent-memory research examines experience reuse ([Hu et al.,
2026](#bib.bib22); [Xu et al., 2025](#bib.bib15); [Zhang et al.,
2026](#bib.bib18)). HiLSVA combines feedback-driven adaptation with
stepwise provenance ([Ai et al., 2026a](#bib.bib3)), while
SciVisAgentBench evaluates agent performance through task outcomes and
multimodal assessment ([Ai et al., 2026b](#bib.bib2)). Preservation is a
complementary requirement: Prompt-to-Prompt, Plug-and-Play, and MasaCtrl
maintain structure or appearance ([Hertz et al., 2023](#bib.bib32);
[Tumanyan et al., 2023](#bib.bib37); [Cao et al., 2023](#bib.bib36));
PIE-Bench, EditBench, MagicBrush, and ICE-Bench evaluate preservation
alongside editing ([Ju et al., 2024](#bib.bib38); [Wang et al.,
2023](#bib.bib39); [Zhang et al., 2023](#bib.bib40); [Pan et al.,
2025](#bib.bib41)).

#### Execution-guided updates and local reasoning.

SemFix uses symbolic execution for repair synthesis ([Nguyen et al.,
2013](#bib.bib42)); bidirectional evaluation propagates outputs backward
through functional programs ([Mayer et al., 2018](#bib.bib30)). Unlike
these methods targeting internal values, VETR derives candidates from
witnessed imperative executions against an image objective, requiring no
additional model inference. Separation logic and RustBelt motivate local
state reasoning ([Reynolds, 2002](#bib.bib31); [Jung et al.,
2018](#bib.bib34)); we instantiate this as finite runtime checks over
captured properties. Graphics systems like Mitsuba 2 and OpenUSD provide
the foundation of reusable, interacting scene resources ([Nimier-David
et al., 2019](#bib.bib35); [Pixar Animation Studios, 2023](#bib.bib33)),
within which VETR performs recursive within-task program revision using
execution-grounded evidence.

## Appendix B Execution-refiner implementation details

### B.1 Compiling trace evidence into realized edits

The execution refiner converts bounded observations into constrained
executable updates between raw execution and visual verification
(Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).
It constructs candidate effects from earlier writes displaced during
execution or effective changes between runtime states, then compiles
them into parameter updates and permitted resource-ownership changes.
The generator still proposes complete programs with its original prompt
and tool schema. The refiner examines every submitted execution,
including improving raw renders; planning actions do not invoke it. No
additional language model identifies an error or constructs a repair.

#### Observe the write, its owner, and its fate.

Alongside $`\operatorname{Execute}(B,q_{t})`$, the observer records

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\tau_{t}=\bigl[(o_{i},k_{i},v_{i},\ell_{i})\bigr]_{i=1}^{m_{t}},\qquad S_{t}=(\theta_{t},\Pi_{t},G_{t}).
``` |  | (6) |

Here $`o_{i}`$ is the owner bound at the executed statement, $`k_{i}`$ a
supported numerical property path, $`v_{i}`$ its observed value, and
$`\ell_{i}`$ its source location. Final numerical values,
object-to-resource references, and captured structure reside in
$`\theta_{t}`$, $`\Pi_{t}`$, and $`G_{t}`$, respectively. Resolving
owners during execution distinguishes calls to the same submitted helper
that write different objects. The observer covers supported assignments
in submitted source, including local helpers; imported-library writes
and unresolved aliases do not provide owner-qualified candidate
evidence. A supported standalone assignment is read back at the next
eligible Python trace event, observing application-level coercion
without evaluating its right-hand side twice. Unsupported bindings and
incomplete observations remain unknown.

#### Initial reference and required evidence.

The public initial program $`p_{0}`$ is executed once for
$`(S_{0},\tau_{0})`$ without another render. We write
$`z_{0}=(p_{0},r_{0},S_{0},\tau_{0})`$ for this initial reference,
explicitly marking $`r_{0}`$ as the supplied visual anchor rather than
the output of this observation pass. Initial recovery needs both
$`\tau_{0}`$ and the initial endpoint map $`\theta_{0}`$ in $`S_{0}`$;
Algorithm [1](#alg1 "Algorithm 1 ‣ Execution cap, delivery, and visual feedback. ‣ B.1 Compiling trace evidence into realized edits ‣ Appendix B Execution-refiner implementation details ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
therefore takes $`z_{0}`$, matching its caller. Subsequent delivered
program/render pairs retain the provenance of their generated render.
Reusing the initial anchor after failure is not a successful generated
answer.

Recovery requires a source write, its source endpoint, and a resolvable
target in the reference program. Projection requires the in-scope light
observations in both $`S_{t}`$ and $`S^{-}`$. A missing required
observation cannot establish a candidate’s endpoint or preservation
condition; unavailable evidence is not assigned a default value. The
exact supported-path, owner-matching, and missing-data policies remain
implementation details identified in
Section [B.1](#A2.SS1.SSS0.Px10 "Specification boundary. ‣ B.1 Compiling trace evidence into realized edits ‣ Appendix B Execution-refiner implementation details ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning").

#### Lost values become competing hypotheses.

For source execution $`s\in\{t,0\}`$ and a supported non-light cell
$`(o,k)`$, the recovery rule selects

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{v}_{s}(o,k)=v_{i^{\star}},\qquad i^{\star}=\max\{i\text{ in }\tau_{s}:o_{i}=o,\ k_{i}=k,\ v_{i}\not\simeq\theta_{s}(o,k)\},
``` |  | (7) |

when this set is nonempty. The current and initial traces supply
separate source hypotheses. Both propose restoring eligible cells in the
current complete program; initial-source recovery does not rewind the
whole program to $`p_{0}`$. The per-cell rule supplies candidate values,
not by itself a complete definition of how eligible cells are grouped
into a write support.

The light channel reconstructs observed owner-local energy/color
requests displaced by later shared writes, resetting earlier requests
after explicit data rebinding. This reset requires ordered binding
evidence: the final reference map $`\Pi_{s}`$ alone does not describe
when a binding changed. Last-write-wins defines the executed result but
does not identify the program that best matches a new visual goal.
Displaced values remain hypotheses, not inferred intent or proof that a
later assignment was erroneous.

#### Compile values and compatible ownership.

For a recovery hypothesis, let $`W_{h}`$ be the supported cells to
change and $`d_{h}(o,k)`$ their required endpoints; other captured cells
retain their raw endpoints. Shared owners with incompatible requirements
require permitted local copying before writes. Compatible requirements
do not force a split. A shared geometry-node group, for example, cannot
realize two different required radii through one shared value; lamps
with compatible requests may retain shared data.

The light compiler uses the effective-value map $`\phi(E,c)=Ec`$ to
enumerate bounded scalar-write supports and group owners by compatible
required tuples. Non-light compilation restores supported values
directly and detaches conflicting material, mesh, camera, or node-group
references where supported. The map $`\phi`$ does not uniquely determine
the light reconstruction: $`(E,c)`$ and $`(2E,c/2)`$ have the same
effect whenever both are admissible. Consequently, the bounds, selected
tuple components, ordering of feasible reconstructions, and allowed
copying/rebinding must come from the compiler rather than being inferred
from $`\phi`$.

#### Project observed effects into executable updates.

In the ordered controller of
Algorithm [1](#alg1 "Algorithm 1 ‣ Execution cap, delivery, and visual feedback. ‣ B.1 Compiling trace evidence into realized edits ‣ Appendix B Execution-refiner implementation details ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning"),
projection is considered if no recovery candidate has been accepted,
subject to the projection channel’s evidence and scope requirements. For
each in-scope owner $`o`$,
Eq. ([3](#S2.E3 "In Candidate effects from execution evidence. ‣ 2.2 Execution Refiner ‣ 2 Method ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning"))

not hidden target parameters. Projection compiles into the previous
delivered program while retaining its other captured state; recovery
instead uses the raw program. Thus, candidate construction, compilation,
and the decision to execute a compiled program are distinct steps. The
endpoint-based shortcuts below can skip a constructed candidate.

Each compiled program runs afresh from $`B`$, not a scene mutated by a
previous trial. For numerical-property *recovery*, the reference is the
raw record and the check is

#### A single acceptance contract, including raw reuse.

Write $`\mathsf{Valid}_{h}(z^{\prime})`$ for the conjunction of
successful execution, a readable render, realization of all required
endpoints, preservation relative to $`z_{h}^{\mathrm{ref}}`$, and
applicable scope/binding checks. Required unknown values cannot make
this predicate true. It is the same acceptance obligation for a fresh
trial and for reusing the raw record as a projection candidate. In
particular, raw reuse under full-effect projection must satisfy
preservation relative to $`z^{-}`$, not merely agree with its own
numerical endpoints. This notation specifies the contract; it does not
supply undocumented numerical tolerances or an implementation of the
checks.

#### Endpoint shortcuts and the skipped full-effect candidate.

The supplied controller skips a light-recovery trial when its required
endpoint is already realized by the raw record. For full-effect
projection, it returns the raw record only if the endpoint-match test
and $`\mathsf{Valid}_{h}(z)`$ both pass. If the endpoint matches but the
contract fails, it *continues to the next candidate without executing
the compiled full-effect program*.

retains this branch; it is not silently changed to fall through to
execution.

The distinction is substantive. Under the effective-endpoint
interpretation,

|  |  |  |
|----|----|----|
|  |
``` math

``` |  |

repair. A check of a more restrictive required owner tuple is a
different predicate and must be specified explicitly. We do not infer
such a tuple check from the effective-value equation.

As a schematic example, let a previous record have light energy $`1`$
and a protected object position $`x=0`$, with fixed light color. A raw
proposal with energy $`2`$ and $`x=5`$ realizes the full-effect light
target, but violates a projection that must retain $`x=0`$. A compiled
program with energy $`2`$ and $`x=0`$ is not equivalent to the raw

not proof that rerendering would be redundant. The endpoint-match

#### Specification boundary.

The equations and listing above clarify the recorded procedure but do
not fully specify its implementation-dependent selectors. Exact
reproduction still requires the supported-property registry,
source-to-reference owner matching, selection/grouping of $`W_{h}`$, and
the rule selecting projection scope. The light inverse additionally
requires admissible bounds, required tuple components, feasible-solution
ordering, allowed copies/rebindings, and infeasibility handling. Ordered
rebinding observations cannot be recovered from the final $`\Pi_{s}`$
alone; their recording and alignment with numerical writes must be
specified. Finally, the numerical agreement predicate, missing-readback
behavior, shortcut endpoint tests, and recovery-to-projection
eligibility must be tied to the evaluated code. No undocumented values,
selectors, or tie-breaking rules are assumed here. In particular, the
ordered presentation of projection after unaccepted recovery must not be
substituted for a different eligibility gate in the actual controller.

#### Making an edit observable.

Let $`R_{B}(q)`$ denote the rendered result of a complete program.
Distinct programs can satisfy $`q_{1}\neq q_{2}`$ yet
$`R_{B}(q_{1})\simeq R_{B}(q_{2})`$ when execution erases their
differing intermediate values. Their traces may still supply different
alternatives. Conversely, multiple parameterizations of a light effect
can differ in surrounding state. Execution evidence supplies bounded
hypotheses whose realization can be tested; the visual verifier assesses
their goal relevance. An improving raw image does not establish that
every observed request survived, motivating examination of every
submitted execution without asserting that each repair improves the
image.

## Appendix C Execution-interface diagnostics and cost

### C.1 Diagnostic study: consistent realization of proposals

To diagnose execution consistency under the complete-program interface,
this study retains full generator history in both arms and changes the
scene loaded for execution. Rebuild loads the task’s initial scene each
time; persistent scene loads and saves a job-local scene across rounds.
Both use GPT, $`N=1`$, the same verifier, a complete-program interface,
and ten generator interactions. This separate run set completes 278/280
tasks in each arm, with 276 jointly valid answers.

Rebuilding reduces mean $`N\text{-}CLIP`$ by 33.9%, with a 95% interval
of $`[19.8,45.8]`$ and 154 wins, 120 losses, and two ties. The effect is
concentrated in geometry, with a 53.4% reduction;
Appendix [5](#A8.F5 "Figure 5 ‣ Appendix H Scene-origin details and additional trajectories ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
reports every family.

A deterministic replay isolates one mechanism. Executing the same saved
geometry20 program nine times on a persistent scene accumulates nine
modifiers and reduces mesh volume to $`1/256`$ of its first-execution
value. Rebuild keeps one modifier and constant volume. Explicitly
replacing previous modifiers on the persistent scene also prevents
accumulation
(Appendix [P](#A16 "Appendix P Identical-program replay of scene operations ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")).
Thus, the requirement is consistency between a program and its execution
origin; a compatible incremental or replacement interface can also
retain scene state.

### C.2 Refinement cost and candidate breadth

With an interaction cap $`T`$ and candidate width $`N`$, at most $`TN`$
raw candidate programs enter the execution stage. Each submission
permits at most $`R=6`$ additional repair executions, so the
raw-program/repair stage has a worst-case bound of $`(1+R)TN`$ execution
attempts, plus the separate initial-program observation. This is an
upper bound rather than a reconstruction of recorded cost counters.
Planning actions, unsupported candidates, failures, and no-op shortcuts
can reduce execution or render counts. A tournament over $`k`$ available
delivered renders uses $`k-1`$ pairwise comparisons. The refiner itself
makes no additional language-model calls; the generator, ordinary
verifier, and tournament have their own inference costs. The generator’s
visible history is bounded by its message window, while archived
trajectories grow with recorded interactions.

## Appendix K Qwen3.8-27B evaluation: settings and scope

#### Backbone and runtime.

The second-backbone runs use a locally served Qwen endpoint, denoted
Qwen3.8-27B, on all 280 tasks. The run environment uses four H100 80 GB
GPUs, Blender 3.6.0, and BlenderGym’s Infinigen fork, Cycles CUDA
rendering with 512 samples, and the same CLIP ViT-B/32 and RGB-MSE
evaluator. One-Shot, VIGA, and VETR use enabled thinking; VIGA and VETR
have a ten-round budget.

#### Budgets and failures.

VIGA and VETR $`N{=}1`$ have 7,200 s timeouts; $`N{=}4`$ and
BlenderAlchemy have 21,600 s. A timeout remains a failure even if an
intermediate render exists. One-Shot has 29 no-render failures; VIGA has
three timeouts and 12 no-render failures; $`N{=}1`$ has four timeouts;
$`N{=}4`$ has one (geometry37). BlenderAlchemy’s only failure
(material5) produced no candidate render after an upstream planning
error.

#### BlenderAlchemy configuration.

The Qwen line uses the released implementation with family-specific edit
styles and refinement strategies (depth 2, breadth 2, one try). Visual
imagination is disabled because the target render is supplied, and
thinking is disabled to obtain parseable planning responses.

## Appendix L Extended image metrics

#### Definitions.

The extended scorer reads the same stored final-answer images used for
the primary metrics, matches render/goal filenames, and averages
per-image values over available views and then over valid tasks. Images
are loaded as RGB in $`[0,1]`$ at goal resolution; a size mismatch is
resized to that resolution. *PSNR* is $`-10\log_{10}\mathrm{MSE}`$ in
dB, with 100 dB used when $`\mathrm{MSE}\leq 10^{-10}`$. It is computed
per image before averaging. *SSIM* uses
skimage.metrics.structural_similarity, RGB channels, data_range=1, and
the default uniform $`7\times 7`$ window. *LPIPS* uses the AlexNet
backbone with the package's default learned calibration and inputs
scaled to $`[-1,1]`$. *Edge F1* applies OpenCV Canny to both 8-bit
grayscale images with thresholds $`(100,200)`$. Each edge map is dilated
by a $`5\times 5`$ all-ones kernel: a match is within two pixels in
Chebyshev distance. Precision is the fraction of predicted edges matched
to a goal edge, and recall the converse; their harmonic mean is
reported. Both maps empty gives 1; exactly one empty gives 0. *CLIP* is
cosine similarity from ViT-B/32 image embeddings, equal to
$`1-N\text{-}CLIP`$ before the latter’s $`\times 100`$ table scaling.
All CLIP tables derive it from the same canonical per-task
$`N\text{-}CLIP`$ score, so their favorable orderings and ties agree
exactly; separately recomputed cosine scores are retained in the scoring
exports. For a higher-is-better metric, paired relative improvement is
$`(\bar{m}_{\mathrm{first}}-\bar{m}_{\mathrm{second}})/\bar{m}_{\mathrm{second}}`$;
for LPIPS its sign is reversed. Reported percentages multiply these
ratios by 100. Task-bootstrap CIs, wins, and sign tests follow
Appendix [J](#A10 "Appendix J Detailed paired comparisons ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning").

## Appendix M One-Shot editing strategy: statistics behind Section [F](#A6 "Appendix F Editing strategies ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")

#### Measure.

For this program-form analysis, each source line is truncated at its
first \#, whitespace is normalized, and empty lines are removed; thus
inline comments are stripped. *Retention* counts initial-line
occurrences whose normalized text appears anywhere in the generated
program, divided by the initial line count. *Changed lines* counts
initial-line occurrences absent from the generated program plus
generated-line occurrences absent from the initial program. Identical
means equality of the normalized line sequences. A program is
*scene-clearing* if the source contains read_factory_settings,
bpy.ops.object.delete, objects.remove(, or nodes.clear(). A program
*contains a 4.x binding* if it names a Blender identifier introduced in
4.0–4.2 and absent in 3.6 (BLENDER_EEVEE_NEXT, surface_render_method,
the Principled-BSDF sockets Specular IOR Level, Subsurface Weight,
Subsurface Scale, Transmission Weight, Coat Weight, Coat Roughness,
Sheen Weight, Emission Color, and the Noise-Texture socket Lacunarity).
The 100 geometry and material tasks are used because they are the tasks
whose archived GPT One-Shot programs were produced and executed under
Blender 3.6.

Each task/system has one designated source result. The GPT system table
uses one complete Blender 3.6 run set, and the context ablations use one
separately identified run set; failures in every source are retained.
The GPT BlenderAlchemy row uses the same Blender 3.6 environment as the

#### Answer extraction.

All iterative systems are scored using their last successful selected
render from a completed run. A later execution failure contributes
feedback and does not replace that answer. Tasks without a successful
render, and timed-out or incomplete runs, are invalid. Stored renders
are rescored by the same evaluator. Primary comparisons use the
intersection of valid task identities; separate completion counts retain
the information about missing answers.

## Appendix P Identical-program replay of scene operations

We replay the archived first program of geometry20, which is
byte-identical in the two closed-loop trajectories of
Figure [5](#A8.F5 "Figure 5 ‣ Appendix H Scene-origin details and additional trajectories ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")(b).
Its node transform sets scale $`(0.5,1,1)`$ and a $`z`$-rotation of
$`0.35`$ radians, then calls surface.add_geomod. The original base scene
and script are held fixed. We execute it nine times under three
policies: reload the base before each execution; retain the edited
scene; or retain the scene but remove modifiers absent from the initial
base before executing the unchanged script. This last policy supplies a
compatible replacement contract. No language-model requests or rendering
calls are made.

Figure 6: The same program has different repeated-execution semantics.
Measured modifier count and evaluated mesh volume on geometry20.
Persistent appending creates one additional modifier per execution and
halves the current volume each time. Rebuild and explicit modifier
replacement coincide at one modifier and constant volume. All three use
the same archived program and Blender 3.6.0; the volume is normalized by
each policy’s identical first execution.

Persistent execution yields one, three, and nine modifiers at steps 1,
3, and 9; the corresponding measured volumes are approximately 4, 1, and
0.015625 Blender units cubed. Rebuild and replacement both retain one
modifier and volume 4 throughout. The evaluated meshes retain eight
vertices and six faces under all policies: the effect here is repeated
transformation, not growing mesh topology. Object bounds, modifier
identities, script/base/helper hashes, and all 27 observations are
supplied. This single-program intervention explains a concrete
accumulation mechanism and identifies a compatible persistent
alternative; the 280-task closed-loop experiment separately measures the
overall backend policy.

#### Base scene and proposal contract.

The task supplies both blender_file.blend ($`B`$) and start.py
($`p_{0}`$). The latter is the editable reference program shown to the
generator; the runner does not execute it as an extra preparation step
before a proposal. It loads the supplied native scene and executes the
submitted script once. Thus, a complete proposal is complete relative to
the assets and objects already supplied in $`B`$. The answer rule in
Appendix [N](#A14.SS0.SSS0.Px3 "Answer extraction. ‣ Appendix N Execution settings ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
associates the evaluated render with the program in its selected
delivered record, which may be a repaired program rather than the
submitted script. A cached fallback retains the provenance of its
earlier render and does not assign that render to a failed submission.

#### Pinned planning channel.

The BlenderGym planning tool accepts a free-form detailed_plan string
covering visual analysis, code analysis, and intended edits. Its
response is inserted into the second pinned message under Initial plan:;
a subsequent planning call replaces that text in place. Both history
settings use this mechanism.

#### Implementation-to-claim mapping.

agents/generator.py samples and executes candidate actions, selects a
returned outcome, invokes the verifier when requested, appends the
selected interaction, and logs all candidates. agents/prompt_builder.py
pins the initial two messages and applies the role-specific
recent-message window, with tool-boundary handling. The runner sets the
generator window to three for the short-history variant, enables shared
history for the role-asymmetry control, and bypasses verification for
the no-verifier control. The complete-script response field and
latest-render guidance are prompt instructions; the final-answer
evaluator separately selects the last successful render. The $`N{>}1`$
path votes over action types before executing candidates of the selected
type;
Algorithm [2](#alg2 "Algorithm 2 ‣ Appendix D Complete refinement procedure ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning")
explicitly places refinement before the selection of delivered outcomes.

#### Prompt scope and system controls.

The released generator prompts combine shared evidence-use instructions,
Blender binding/API conventions, and family-specific guidance. All
context-window conditions share these instructions. The VIGA runner
saves successful scene updates, whereas the VETR runner loads the task
base scene for each complete-script execution. History and scene-origin
contrasts change individual settings; the same-run prefix analysis holds
initial guidance fixed, and role-prompt/recipe controls are reported in
Appendix [O](#A15 "Appendix O Within-run progress and guidance controls ‣ VETR: Execution-Grounded Self-Improving Agent for Symbolic Graphics Reasoning").
````
