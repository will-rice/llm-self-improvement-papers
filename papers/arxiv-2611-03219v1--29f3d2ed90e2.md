# Can Coding Agents Sustain Continual Evolution without Forgetting?

Jia Li

###### Abstract

Recently, harness self-evolution has emerged as an important paradigm
for improving agent performance. Prior studies show that evolving the
agent harness can effectively enhance agent capabilities without
modifying the foundation model’s parameters. We find that existing
approaches largely study agent evolution on a single task. In practice,
coding agents may need to handle multiple task types over time. Whether
an agent harness can continuously evolve across multiple tasks without
suffering from catastrophic forgetting remains an important open
question.

In this paper, we investigate this open question through a comprehensive
empirical study of continual harness self-evolution. We organize three
software engineering task datasets into six different evolution
directions and apply two representative harness evolution methods to
perform continual evolution along these directions. Our experimental
results show that evolution on a subsequent dataset can substantially
undermine the performance on previously seen datasets. For example, with
DeepSeek-V4-Flash-0731, Meta-Harness improves its performance on
SWE-Bench to 94.0% after evolution. However, after further evolution on
FeatureBench, its performance on SWE-Bench drops to 32.0% by the fifth
round, corresponding to a 66% relative decrease. Finally, based on our
experimental findings, we identify several insights, providing
directions for the continual self-evolution of agent harnesses. Code is
available at
[https://github.com/THU-Agent/continual-harness-evolution](https://github.com/THU-Agent/continual-harness-evolution).

## 1 Introduction

![Refer to caption](2611.03219v1/intro.png)

Figure 1: Overview of our study on continual harness self-evolution.

Coding agents have been increasingly used in software engineering
tasks ([Liu et al., 2024](#bib.bib15)), such as issue solving, feature
addition, and test generation ([Yang et al., 2024](#bib.bib26); [Wang
et al., 2025](#bib.bib24); [Tao et al., 2024](#bib.bib22); [Bouzenia
et al., 2025](#bib.bib3)). A coding agent typically consists of a
foundation model and an agent harness ([Ning et al., 2026](#bib.bib18);
[Yang et al., 2024](#bib.bib26)). The harness coordinates the
interaction between the model, tools, and environment, thereby
influencing how the agent perceives task information, invokes tools, and
executes tasks. Different harnesses can substantially affect agent
performance. In our experiments, with the foundation model fixed,
different harnesses achieve substantially different performance on
SWE-Bench, ranging from 82.0% to 96.0%.

To improve the agent harness, recent studies have explored harness
self-evolution, which enables agents to learn from their own execution
experience by analyzing trajectories, identifying strategies, and using
these insights to automatically improve their runtime systems ([Jiang
et al., 2026](#bib.bib9)). Recently, a number of approaches have been
proposed, demonstrating promising improvements in agent
capabilities ([Agrawal et al., 2026](#bib.bib1); [Zhang et al.,
2026c](#bib.bib30); [Zhou et al., 2025](#bib.bib33); [Chhikara et al.,
2025](#bib.bib6); [Zhang et al., 2026b](#bib.bib29); [Xia et al.,
2026](#bib.bib25); [Lin et al., 2026](#bib.bib14); [Lee et al.,
2026](#bib.bib13); [Zhang et al., 2026a](#bib.bib28); [Chen et al.,
2026](#bib.bib5)). For example, AHE ([Lin et al., 2026](#bib.bib14))
improves the performance of the seed harness $`NexAU_{0}`$ on
Terminal-Bench 2 from 69.7% to 77.0% after ten rounds of evolution.

However, existing harness self-evolution studies primarily focus on
independently evolving harnesses for a single kind of task. In practical
scenarios, coding agents are expected to address various software
engineering tasks. The Stack Overflow Developer Survey 2026 report that
72.9% of developers use AI agents for writing, editing, or generating
code, 62.2% for debugging or troubleshooting, and 50.6% for writing or
maintaining tests [Stack Exchange Inc. (2026)](#bib.bib21). In software
development, a user may first ask a coding agent to add a new feature
and later ask it to write test files. Inspired by this observation, we
propose continual harness self-evolution, which refers to successively
evolving a harness across different task types, in contrast to evolving
a harness independently for a single task. However, to the best of our
knowledge, no existing work has explored continual evolution of coding
agent harnesses across different kinds of tasks.

To bridge the above research gap, we conduct a systematic study of
continual harness self-evolution for coding agents. Our study aims to
answer the following research questions:

RQ1: Can existing harness self-evolution methods sustain continual
evolution across multiple software engineering tasks? Continual harness
self-evolution requires an agent to keep improving on each new tasks
without losing the capabilities it acquired on previous ones. To examine
whether existing methods meet this requirement, we construct a continual
evolution setting in which the harness is evolved on a sequence of
software engineering task types rather than on a single task.
Specifically, we evaluate two representative harness self-evolution
methods, AHE ([Lin et al., 2026](#bib.bib14)) and Meta-Harness ([Lee
et al., 2026](#bib.bib13)), across three software engineering datasets:
SWE-Bench ([Jimenez et al., 2024](#bib.bib10)) for code repair,
SWT-Bench ([Mündler et al., 2024](#bib.bib17)) for test case generation,
and FeatureBench ([Zhou et al., 2026](#bib.bib34)) for feature
generation. Each continual evolution experiment forms a two-stage task
sequence, where the harness first evolves on an earlier dataset and then
continues evolving on a later one, allowing us to track how performance
on the earlier task changes as evolution proceeds. The results reveal
substantial catastrophic forgetting during continual harness
self-evolution, as shown in
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")
(a). For example, Meta-Harness improves SWT-Bench to 100.0%, but its
performance on SWT-Bench drops to 62.0% after further evolution on
FeatureBench.

RQ2: What are the root causes of catastrophic forgetting in the harness?
As shown in
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")
(b), to understand why continual harness self-evolution can lead to
catastrophic forgetting, we collect over 520 agent trajectories and
manually analyze the harness modifications introduced during continual
harness self-evolution. We categorize these modifications into three
major types of harness-level conflicts: verification, workflow, and
budget strategy conflicts. Our ablation experiments show that different
conflict types have substantially different effects on agent
performance. We hope these findings shed light on the design of future
self-evolution methods that are aware of such conflicts, and we call for
more attention to this overlooked yet critical issue.

The main contributions of our work are as follows:

1.  ❶
    Motivated by the practical use of coding agents across diverse
    tasks, we propose the problem of harness continual self-evolution
    and identify catastrophic forgetting as a critical challenge.
2.  ❷
    We evaluate existing harness self-evolution methods under continual
    evolution, revealing catastrophic forgetting on previous acquired
    capabilities.
3.  ❸
    We manually analyze agent trajectories and identify key
    harness-level conflicts that contribute to forgetting phenomena.

## 2 Problem Definition

A coding agent consists of a foundation model and an agent harness that
coordinates its interaction with the software environment ([Ning et al.,
2026](#bib.bib18); [Yang et al., 2024](#bib.bib26)). Recent work has
explored harness self-evolution, which improves agent capabilities by
modifying the harness based on execution experience while keeping the
foundation model parameters fixed ([Jiang et al., 2026](#bib.bib9)).
Formally, an agent is represented as $`A=\langle M,H\rangle`$, where
$`M`$ denotes the foundation model and $`H`$ denotes the harness. Given
execution trajectories $`\mathcal{T}`$ collected from a dataset
$`\mathcal{D}`$, a self-evolution method $`\Omega`$ updates the harness
as $`H^{\prime}=\Omega(H,\mathcal{T})`$.

In practical settings, coding agents may need to evolve across different
software engineering task types, such as issue solving, feature
addition, and test generation. We refer to this setting as continual
harness self-evolution. Given an ordered sequence of datasets
$`\mathcal{D}=(D_{0},D_{1},\ldots,D_{K})`$, where each dataset
represents a kind of software engineering task, the harness is updated
repeatedly as follows:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       H_{i+1}=\Omega\left(H_{i},\mathcal{T}_{i}\right),
       ```                                                |     | (1) |

where $`\mathcal{T}_{i}`$ denotes the execution trajectories collected
from tasks in $`D_{i}`$, and $`i=0,\ldots,K`$.

A central challenge in continual harness self-evolution is to adapt to
the new task type without substantially degrading performance on the
previously encountered one. This challenge is related to the
stability–plasticity dilemma in continual learning ([Carpenter &
Grossberg, 1987](#bib.bib4); [Yang et al., 2026](#bib.bib27)). When
adaptation to new experience compromises previously acquired
capabilities, catastrophic forgetting may occur ([Kirkpatrick et al.,
2016](#bib.bib12)). In this paper, we define catastrophic forgetting as
a substantial performance degradation on the source task after further
harness evolution on the target task.

Ideally, continual harness self-evolution should improve performance on
each new dataset while preserving performance on previously encountered
datasets. Specifically, after evolving on $`D_{i}`$, the resulting
harness $`H_{i+1}`$ should not degrade performance on dataset $`D_{j}`$,
where $`0\leq j<i\leq K`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       \mathrm{Eval}(H_{i+1},D_{i})>\mathrm{Eval}(H_{i},D_{i}),
       ```                                                       |     | (2) |

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       \mathrm{Eval}(H_{i+1},D_{j})\geq\mathrm{Eval}(H_{j+1},D_{j}).
       ```                                                            |     | (3) |

Here, $`\mathrm{Eval}(H,D)`$ denotes the performance of an agent with
harness $`H`$ and a fixed foundation model on dataset $`D`$. The first
condition captures adaptation to the current task, while the second
captures retention of previous-task performance.

To quantify catastrophic forgetting, we measure the absolute and
relative performance drops on the previous dataset:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\Delta_{\mathrm{forget}}=\mathrm{Eval}(H_{j+1},D_{j})-\mathrm{Eval}(H_{i+1},D_{j}),
``` |  | (4) |

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\rho_{\mathrm{forget}}=\frac{\mathrm{Eval}(H_{j+1},D_{j})-\mathrm{Eval}(H_{i+1},D_{j})}{\mathrm{Eval}(H_{j+1},D_{j})}.
``` |  | (5) |

## 3 Experimental Setup

With the problem defined in
Section [2](#S2 "2 Problem Definition ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),
we conduct a study of continual harness self-evolution. In this section,
we introduce the datasets, coding agent framework, self-evolution
methods, and implementation details used in our experiments.

### 3.1 Datasets

We study the continual harness self-evolution between different types of
software engineering tasks, including code repair, test case generation,
and code generation.

SWE-bench Verified ([Jimenez et al., 2024](#bib.bib10)) is one of the
most widely used code repair benchmarks in software engineering. It
contains 500 high-quality instances derived from real-world software
issues collected from GitHub and manually verified by human annotators.
The goal of each task is to identify and resolve the underlying issue by
modifying the corresponding repository.

SWT-Bench ([Mündler et al., 2024](#bib.bib17)) focuses on evaluating
agents’ ability to generate test cases for real-world software issues.
Each task provides the agent with source code and an issue report
collected from GitHub, and the generated tests are expected to fail on
the original implementation but pass after the corresponding fix is
applied. Notably, all task prompts originally follow an identical
sentence structure. To avoid potential shortcuts and improve consistency
with other datasets, we paraphrase this structure while preserving its
semantics, resulting in diverse surface forms across tasks, as discussed
in Appendix
 [B](#A2 "Appendix B Discussion and Case Study for Dataset Settings ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?").

FeatureBench ([Zhou et al., 2026](#bib.bib34)) evaluates agents on
implementing new features in real-world software repositories. Given a
feature requirement and its interface description, the agent is expected
to implement the requested functionality and place the resulting
implementation in the testbed directory. The evaluation considers both
fail-to-pass (F2P) and pass-to-pass (P2P) tests: F2P tests assess
whether the new feature is correctly implemented, while P2P tests verify
that the modification does not break existing functionality.

Due to resource constraints, we randomly sampled a limited number of
instances from each dataset for self-evolution, including 50 instances
from SWE-Bench Verified, 50 from SWT-Bench, and 30 from FeatureBench.

### 3.2 Initial Agent Harness

We initialize the harness with Mini-SWE-Agent ([Yang et al.,
2024](#bib.bib26)), a commonly used agent framework for software
engineering tasks. Its core implementation consists of only around 100
lines of Python code, while achieving a score of over 74% on SWE-bench
Verified. The original implementation provides the agent control flow,
model interface, Bash tool definition, and configurations for both local
and Docker-based environments. To prevent the evolver from modifying the
interface specifications or execution environment, we restrict the scope
of self-evolution to several aspects: modifying the system prompt,
modifying the agent execution logic, and adding or modifying tools.

### 3.3 Evaluated evolution algorithms

We select two representative agent harness self-evolution methods to
evaluate their catastrophic forgetting during continual evolution.

AHE ([Lin et al., 2026](#bib.bib14)) constructs a closed-loop
self-evolution process. The coding agent interacts with the environment
through the current harness and generates trajectories on tasks from the
target dataset. The Agent Debugger then accesses the trajectory files
using general-purpose shell commands and scripting tools, and summarizes
the root causes of successful and failed trajectories. Finally, the
Evolve Agent uses the evidence produced by the Agent Debugger to modify
the harness code, preparing the updated harness for the next round of
evolution.

Meta-harness ([Lee et al., 2026](#bib.bib13)) continuously maintains a
Pareto frontier of harnesses in contrast. In each round of evolution,
the coding agent proposes new modifications by referring to existing
harnesses and accumulated experience. The newly modified harnesses are
then evaluated on tasks from the current dataset, with the evaluation
logs stored in the file system for subsequent evolution.

Since neither method’s publicly available implementation supports the
evolution of Mini-SWE-Agent, we implement the corresponding
functionality based on their original codebases, while aligning our
implementations with the original experimental settings as closely as
possible.

### 3.4 Implementation Details

For the hyperparameters, we set the rollout temperature to 0. For AHE
and Meta-Harness, we follow the settings of their original papers and
perform 9 and 5 rounds of evolution, respectively. In each round, the
same batch of tasks is executed twice, and the resulting trajectories
are analyzed to guide the evolution.

We use DeepSeek-V4-Flash-0731 [DeepSeek-AI (2026)](#bib.bib7) as the
foundation model for both task execution and harness evolution. To
ensure a consistent execution environment across all experiments, we
uniformly use E2B as the sandbox environment. We set the time limit for
each task execution to 1 hour.

### 4.1 RQ1: Catastrophic Forgetting During Continual Harness Self-Evolution

To investigate whether continual harness self-evolution leads to
catastrophic forgetting, we examine how it affects performance on
previously encountered tasks in this RQ.

Setting. In our experiments, we set up continual harness self-evolution
on two datasets of different types. The conclusions obtained from this
experimental setting can also be generalized to multiple sequential
datasets: an evolution method that causes catastrophic forgetting on
adjacent tasks will likewise cause forgetting in continual evolution
across multiple datasets. We first perform self-evolution independently
on SWE-Bench, SWT-Bench, and FeatureBench. After that, we select the
best-performing harness obtained during each evolution process as the
initial harness, transfer it to another dataset for further evolution,
and evaluate its performance degradation on the previous dataset. When
multiple harnesses achieve the same highest score, we select the first
harness that reaches this score. For example, for AHE on FeatureBench,
we select the harness obtained after the third round as an initial for
continual evolution, which achieves a score of 30.0%.

Results. The experimental results derive the following key findings:

❶Both self-evolution methods demonstrate substantial performance
improvements when evolving on a single dataset. As shown in
Figure [2](#S4.F2 "Figure 2 ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),
$`H_{0}`$ denotes the initial harness of Mini-SWE-Agent, while $`H_{i}`$
denotes the harness after the $`i`$-th round of evolution. For example,
AHE improves the performance on SWE-Bench from 82.0% initially to 96.0%
after nine rounds of evolution, while Meta-Harness achieves a final
score of 94.0%. On SWT-Bench, both methods improve the performance from
the initial score of 82.0% to 100.0% on the randomly sampled 50 tasks.
On FeatureBench, both methods eventually achieve an improvement of more
than 10 percentage points. We circle the highest-scoring point in each
line plot in
Figure [2](#S4.F2 "Figure 2 ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),
highlighting the best-performing harness.

❷Existing self-evolution methods struggle to preserve previously
acquired capabilities during continual harness self-evolution. As shown
in
Figure [3](#S4.F3 "Figure 3 ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),
almost every continual harness self-evolution direction results in
substantial performance degradation on previously encountered tasks. For
example, when evolving from SWE-Bench to SWT-Bench, AHE and Meta-Harness
suffer performance degradation of 100% and 98% on SWE-Bench,
respectively, after five rounds of evolution. In other words, after
evolving on SWT-Bench, the resulting agents are almost completely unable
to solve the SWE-Bench tasks. Similarly, in the SWE $`\rightarrow`$
Feature setting, the performance of AHE and Meta-Harness decreases by
29% and 66%, respectively.

❸The extent of catastrophic forgetting varies substantially across
datasets and evolution directions. In the software engineering domain,
SWT-Bench ([Mündler et al., 2024](#bib.bib17)) evaluates agents on test
case generation, whereas SWE-Bench ([Jimenez et al., 2024](#bib.bib10))
and FeatureBench ([Zhou et al., 2026](#bib.bib34)) require agents to
modify the source code of existing repositories. Therefore, SWT-Bench is
relatively less related to the other two datasets, while SWE-Bench and
FeatureBench involve more closely related types of tasks. As shown in
Figure [3](#S4.F3 "Figure 3 ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),
evolution between SWE-Bench and FeatureBench causes relatively smaller
performance degradation on the previously encountered dataset, whereas
evolution between SWT-Bench and the other two datasets leads to
substantially larger degradation. These results suggest that task
relatedness may play an important role in mitigating catastrophic
forgetting during continual harness self-evolution. Evolving on a
substantially different task type can introduce modifications that are
highly detrimental to capabilities acquired from the previous tasks,
resulting in more severe forgetting.

#### 4.2.1 Categorization of Harness Conflicts

In this RQ, we further analyze the reasons why harness modifications
lead to performance degradation on previously encountered tasks.

Setting. To characterize the types of harness conflicts introduced
during continual harness self-evolution, we conduct a two-stage analysis
for each evolution direction in
Figure [3](#S4.F3 "Figure 3 ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?").
First, we extract the code diff between the initial harness and the
harness obtained after five rounds of continual evolution, and manually
examine the modifications to identify the types of conflicts introduced
by the evolution process. We then analyze a total of 520 execution
trajectories and identify the tasks that exhibit a pass-to-fail
transition after continual harness self-evolution. For these cases, we
analyze their execution trajectories in detail and determine which types
of harness conflicts are associated with the observed failures. Finally,
we calculate the proportion of each conflict type among these
pass-to-fail cases to quantify their prevalence in the observed
performance degradation.

Results. We identify three major types of modifications that can
introduce such conflicts: verification conflicts, workflow conflicts and
budget strategy. Among the pass-to-fail cases, verification conflicts
account for 87.1%, workflow conflicts account for 8.2%, and budget
conflicts account for 0.6%. The remaining cases are not associated with
a specific conflict type.

❶Verification conflicts arise when the harness introduces checks,
constraints, or reminders that are tailored to the requirements of a
particular dataset. The harness may determine what evidence should be
inspected, what conditions must be satisfied before submission, or what
artifact should be delivered. These interventions directly influence the
agent’s execution trajectory and can conflict with the requirements of
previously encountered tasks.
Figure [4](#S4.F4 "Figure 4 ‣ 4.2 RQ2: Harness Components Associated with Catastrophic Forgetting ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")
(a) shows a normal example during the continual evolution from
FeatureBench to SWT-Bench. It means that if a newly generated test
already passes on the buggy code, it does not provide fail-to-pass
evidence, and the submission is therefore blocked. This specific
modification of SWT-Bench can negatively affect performance on previous
tasks.

Among the verification conflicts, Artifact conflicts are the most
prominent. When a harness evolves from one type of task to another,
artifact-specific constraints may be incorporated into the harness, such
as enforcing the expected artifact type at submission time. These
modifications can conflict with the requirements of previous tasks,
causing the agent to produce an inappropriate artifact and leading to
task failures. As shown in
Figure [4](#S4.F4 "Figure 4 ‣ 4.2 RQ2: Harness Components Associated with Catastrophic Forgetting ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")
(b), in the evolution from SWT-Bench to SWE-Bench, the required
submission artifact switches from a test-only patch to a source-code
fix, accompanied by a reversal in the polarity of the submission gate.

❷Workflow conflicts arise from differences in the procedures required to
solve different types of tasks. Such differences are typically reflected
in the prompts or workflow-related helpers of the harness. As shown in
Figure [4](#S4.F4 "Figure 4 ‣ 4.2 RQ2: Harness Components Associated with Catastrophic Forgetting ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")
(c), during the evolution from SWE-Bench to SWT-Bench, the prompt is
modified to change the agent’s problem-solving workflow. Instead of
directly modifying the source code after locating the issue, the agent
identifies the relevant test file, writes a regression test, verifies
that it fails before the fix and passes after the fix, and finally
reverts the temporary source-code modifications. While these
modifications may benefit the current task type, they can interfere with
workflows that are more appropriate for previously encountered tasks.

❸Budget strategy concerns how the harness manages the limited time and
computational resources available to the agent. Such strategies include
reminders based on elapsed wall-clock time or the number of steps, as
well as guards for repeated command failures, timeouts, or slow
execution. During continual harness self-evolution, these budget-related
mechanisms may be modified to accommodate the resource requirements of
the current tasks.
Figure [4](#S4.F4 "Figure 4 ‣ 4.2 RQ2: Harness Components Associated with Catastrophic Forgetting ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")
(d) shows a representative modification to the budget strategy
introduced during the evolution from FeatureBench to SWE-Bench. After
repeated command timeouts, the harness prompts the agent to stop
repeatedly retrying the same commands, narrow the scope of testing, and
converge toward a solution more quickly.

The prevalence of different conflict types does not necessarily reflect
their impact on agent performance. To examine their individual effects,
we introduce representative modifications associated with each conflict
type into the harness and evaluate the resulting performance against
that of the original harness. We further analyze failure cases to
understand how each type of conflict leads to task failures.

Setting. We take the AHE evolution from SWE-Bench to FeatureBench as an
example. We add the workflow and time budget-related modifications
identified during continual harness self-evolution to the best
performing harness previously evolved on SWE-Bench, and examine the
resulting performance impact of each modification on SWE-Bench. Since
SWE-Bench and FeatureBench do not differ substantially in terms of their
submission artifacts, we instead use the evolution from SWE-Bench to
SWT-Bench as the source of modifications for verification conflicts.

Results. As shown in
Table [1](#S4.T1 "Table 1 ‣ 4.2.2 Impact and Case Study of Different Harness Conflict Types ‣ 4.2 RQ2: Harness Components Associated with Catastrophic Forgetting ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),
we find that introducing a mandatory artifact constraint immediately
reduces the performance on SWE-Bench to 0.0. During continual harness
self-evolution from SWE-Bench to SWT-Bench, the different deliverable
requirements reverse the submission logic: the evolved harness
automatically checks the agent’s modifications before submission and
rejects any solution that modifies files beyond the test files. This
constraint is suitable for SWT-Bench but incompatible with SWE-Bench,
where source-code modifications are required to fix the issue.

Workflow conflicts also have a substantial impact, reducing the
performance from 96.0 to approximately 66.0. During continuous evolution
from SWE-Bench to FeatureBench, the evolver substantially modified the
agent’s workflow in the system prompt, while also introducing hard
constraints at the harness level to enforce this workflow. In
particular, the evolved harness intercepts network-related commands such
as pip, curl, and git, preventing the agent from accessing external
resources. As a result, the agent loses access to potentially useful
external resources, leading to a substantial degradation in SWE-Bench
performance. Moreover, following the FeatureBench-specific workflow
leads the agent to perform a large number of unnecessary exploratory
operations, increasing the average task execution time by 235%.

In contrast, budget strategies have little impact on task performance,
with their effects mainly reflected in changes in task execution
efficiency. As shown in
Table [1](#S4.T1 "Table 1 ‣ 4.2.2 Impact and Case Study of Different Harness Conflict Types ‣ 4.2 RQ2: Harness Components Associated with Catastrophic Forgetting ‣ 4 Experimental Results ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),

## 5 Related Work

### 5.1 Harness Self-Evolution

Recent work on harness self-evolution focuses on improving the runtime
system surrounding the foundation model ([Lin et al., 2026](#bib.bib14);
[Lee et al., 2026](#bib.bib13); [Zhang et al., 2026a](#bib.bib28); [Chen
et al., 2026](#bib.bib5)). Given a set of tasks, an agent first produces
a collection of execution traces. The evolution process then analyzes
these traces to identify successful behaviors or diagnose the root
causes of failures, and subsequently makes attributable modifications to
the agent’s harness based on the accumulated evidence. A substantial
body of work focuses on evolving individual harness components,
including prompts ([Agrawal et al., 2026](#bib.bib1); [Zhang et al.,
2026c](#bib.bib30)), memory ([Zhou et al., 2025](#bib.bib33); [Chhikara
et al., 2025](#bib.bib6)), and skills ([Zhang et al.,
2026b](#bib.bib29); [Xia et al., 2026](#bib.bib25)), while other
approaches optimize the harness as a whole, such as AHE ([Lin et al.,
2026](#bib.bib14)), Meta-Harness ([Lee et al., 2026](#bib.bib13)),
Self-Harness ([Zhang et al., 2026a](#bib.bib28)) and HarnessX ([Chen
et al., 2026](#bib.bib5)).

However, existing studies on harness self-evolution primarily evaluate
whether the evolution process improves agent capabilities on a single
type of task. This line of work does not explicitly consider whether
existing methods can continuously evolve harnesses across multiple kinds
of tasks.

### 5.2 Continual Learning for Agents

In recent years, research on continual learning has gradually expanded
from continual learning for LLMs to continual learning for LLM-based
agents ([Zheng et al., 2026](#bib.bib32)). For example, Voyager ([Wang
et al., 2024](#bib.bib23)) continuously accumulates and reuses skills
during interaction, while CER ([Liu et al., 2025](#bib.bib16)) and
LifeMem ([Qiu et al., 2026](#bib.bib19)) focus on retaining and
leveraging historical experiences to assist agents in completing current
tasks. Several benchmarks have also been proposed to evaluate continual
learning for agents. LifelongAgentBench ([Zheng et al.,
2025](#bib.bib31)) and EvoAgentBench ([Gao et al., 2026](#bib.bib8))
focus on skill-based agents, while AGENTCL ([Shu et al.,
2026](#bib.bib20)), Continual Learning Bench ([Asawa et al.,
2026](#bib.bib2)), and SWE-Bench-CL ([Joshi et al., 2025](#bib.bib11))
consider task ordering and experience accumulation over time, primarily
evaluating memory-augmented agents.

However, relatively little attention has been paid to the continual
evolution of the agent harness as a whole, where multiple components can
be jointly modified based on accumulated execution experience.

## 6 Conclusion

In this paper, we study continual harness self-evolution and identify
catastrophic forgetting as a central challenge. We evaluate two
representative harness self-evolution methods across three software
engineering benchmarks and six cross-task evolution directions. While
both methods improve performance on individual tasks, their performance
often degrades substantially when evolution spans different tasks.
Further analysis identifies three types of harness-level conflicts that
contribute to catastrophic forgetting: verification, workflow, and
budget-strategy conflicts. These findings highlight the challenges of
evolving coding agents reliably across diverse software engineering
tasks.

## Appendix B Discussion and Case Study for Dataset Settings

In
Section [3](#S3 "3 Experimental Setup ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?"),
we described a specific setting adopted in our experiments: we
paraphrased the fixed linguistic pattern shared by the instances in
SWT-Bench while preserving their original semantics. In this section, we
further discuss and validate the rationale behind this experimental
setting.

If the original SWT-Bench prompts are kept unchanged, as shown in
Figure [5](#A2.F5 "Figure 5 ‣ Appendix B Discussion and Case Study for Dataset Settings ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")(a),
we observe that the Meta-Harness evolution from SWE-Bench to SWT-Bench
introduces a conditional branch for determining the submission artifact,
as shown in
Figure [5](#A2.F5 "Figure 5 ‣ Appendix B Discussion and Case Study for Dataset Settings ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")(c).
Specifically, if the harness identifies the current task as a code
modification task, it requires the agent to submit source code;
otherwise, it requires the agent to submit a test file. This behavior is
a positive signal for mitigating catastrophic forgetting, as it allows
the evolved harness to distinguish between different types of tasks and
preserve the corresponding submission requirements.

However, the condition used to determine test_deliverable is constructed
entirely based on the fixed linguistic template used in SWT-Bench, as
shown in
Figure [5](#A2.F5 "Figure 5 ‣ Appendix B Discussion and Case Study for Dataset Settings ‣ Can Coding Agents Sustain Continual Evolution without Forgetting?")(b).
Such an evolution pattern is clearly unfavorable for generalization, as
the learned condition is closely tied to the surface form of the
SWT-Bench prompts rather than the underlying task semantics.

After paraphrasing the SWT-Bench prompts, we no longer observe similar
template-dependent conditional branches during self-evolution. This
observation suggests that prompt paraphrasing can mitigate the risk of
self-evolution exploiting dataset-specific linguistic patterns,
encouraging the evolved harness to rely more on task-level
characteristics.
