# SEIS: Self-Evolving Inference Systems

Zhen Xu  Jingyu Liu  Zongze Li  Tahseen Rabbani  Ce Zhang University of
Chicago

###### Abstract

Inference systems determine how fast and how cheaply language models can
be served, so making them faster has direct practical value. However,
prior work focuses mostly on optimizing certain parts such as kernels or
memory within the large system. In this work, we take a holistic
approach and apply agentic self-evolution to optimize the whole system
end-to-end. Our SEIS (Self-Evolving Inference Systems) autonomously
optimizes the entire mini-sglang engine without human intervention
through iterative sessions with inherited experiences and code changes.
Serving Qwen3-0.6B on H100, the resulting engine reaches 3.27$`\times`$
the throughput of the original mini-sglang implementation and beats SOTA
engines like vLLM, TensorRT-LLM, and SGLang in the single-request
workload. The correctness of the optimized inference engine by SEIS is
tested in terms of numerical difference and downstream accuracy on math
and long-context retrieval tasks. The code and session histories show
that the speedup comes from redesigning the whole engine and that
building on earlier sessions beats independent attempts. These results
suggest that agentic self-evolution can optimize a complex system
end-to-end. The evaluation also has to evolve with the engine, and
letting agents evolve it is a natural next step.

## 1 Introduction

An inference engine exposes an agent to a systems problem: improving one
component can change which other component limits performance. Faster
linear kernels alter the relative cost of attention and scheduling. A
different decoding strategy changes the shapes that those kernels must
support and the way the engine manages its KV cache. Optimizing the
whole engine, therefore, requires choosing a direction, changing several
components consistently, and revisiting earlier decisions as the
implementation changes.

Recent work uses agents to evolve programs and build or adapt inference
systems ([Novikov et al., 2025](#bib.bib6); [Kamahori et al.,
2026](#bib.bib1); [Chen et al., 2026](#bib.bib2)). We study sustained
optimization of an existing inference engine, tracing how changes
accumulate across sessions, combine across chains, and reveal
limitations in the evaluation guiding the process. A human provides a
working engine, a target model and GPU, a throughput objective, and
constraints. The agent decides what to investigate and implement. SEIS
preserves the implementation and reports across sessions, and optionally
exchanges them between chains. The object that evolves is the inference
system’s source code and numerical implementation; the agent is fixed
throughout the experiment.

The resulting changes extend across the engine. Starting from the
unmodified mini-sglang engine (vanilla), which already includes paged KV
storage, FlashInfer attention ([Ye et al., 2025](#bib.bib10)), and CUDA
graphs, the agents build quantized kernels, fuse computation across
operator boundaries, reduce execution overhead, and implement
prompt-lookup speculative decoding. We call the evolved engine with the
highest development speedup the best engine. It reaches 3.27$`\times`$
vanilla throughput on natural-length requests and exceeds the selected
production configurations on the same single-request workload
(Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ SEIS: Self-Evolving Inference Systems")).
Its measured accuracy differs from vanilla by +1.06 percentage points on
the 660-item GSM8K test split and $`-`$0.37 points on long-input
retrieval. Branching Chain runs on Llama-3.2-1B provide additional
system results in Appendix G.

Figure 1: Qwen3-0.6B on H100. (a) Natural-request throughput: median and

Latency means and central 50%/80% intervals over 100 requests. (c)

Most of the best engine’s natural-request speedup remains with
speculation disabled. The trajectories first show how its ordinary
kernels and execution path are assembled through successive sessions.
They then expose the formation of a larger structural change:
speculative decoding is proposed, rejected, remeasured, and eventually
implemented. A sync transfers a working design to other chains. The best
engine adopts the originating chain’s policy while retaining and
improving its own execution layer and kernels. This connects the
delivered engine to both accumulated local work and selective
cross-chain integration.

We contribute a framework and recorded study of sustained autonomous
inference-system optimization, together with the resulting engines. The
evidence connects three findings: substantial natural-request gains
persist in ordinary decoding; accumulated code and selected peer changes
form the best engine’s implementation; and development-gate success does
not establish complete output capability or final-task quality.
Sections [4](#S4 "4 What the Agents Built ‣ SEIS: Self-Evolving Inference Systems")–[6](#S6 "6 How the Evaluation Evolved ‣ SEIS: Self-Evolving Inference Systems")
present the system results, their formation, and the validation
failures, respectively.

## 2 Related Work

Program evolution and self-improvement. FunSearch and AlphaEvolve evolve
programs: a language model proposes edits and an automated evaluator
scores them ([Romera-Paredes et al., 2024](#bib.bib16); [Novikov et al.,
2025](#bib.bib6)). FunSearch evolves separate islands of programs and
periodically reseeds the weaker ones, following the island model of
evolutionary computation ([Whitley et al., 1999](#bib.bib20)).
Self-improvement methods instead modify the improver. The Gödel machine
rewrites its own code ([Schmidhuber, 2007](#bib.bib21)), STOP improves
the scaffold that calls the language model ([Zelikman et al.,
2024](#bib.bib22)), and the Darwin Gödel Machine evolves the coding
agent itself ([Zhang et al., 2026](#bib.bib7)). SEIS keeps the agent
fixed and evolves a separate system. Its unit of evolution is a
multi-hour agent session over an entire codebase, and the Sync Branching
Chain applies the island model to such sessions.

Figure 2: The SEIS protocol. (a) A fixed agent chooses and implements
optimizations to an inherited engine. Development gates determine which
code is retained; passing candidates may be slower. Code and reports
carry to the next session. Post-validation evaluates task accuracy and
natural-length speed outside optimization feedback. (b) Branching:
sessions start independently from the same engine $`E_{0}`$, and the
best result is kept. (c) Branching Chain: each session inherits the code
and reports of the previous session in its chain. (d) Sync Branching
Chain: every $`N`$ sessions, all chains exchange code and reports, and
each agent decides what to adopt. Nodes represent sessions.

Long-horizon agents and experience across attempts. MLE-bench, RE-Bench,
and PaperBench evaluate agents on machine-learning engineering and
research tasks that take hours ([Chan et al., 2025](#bib.bib23); [Wijk
et al., 2025](#bib.bib24); [Starace et al., 2025](#bib.bib25)), and The
AI Scientist automates a complete research cycle ([Lu et al.,
2024](#bib.bib26)). Reflexion, ExpeL, and Voyager store verbal lessons
or reusable skills for later attempts ([Shinn et al., 2023](#bib.bib27);
[Zhao et al., 2024](#bib.bib28); [Wang et al., 2024](#bib.bib29)), and
MemGPT manages information beyond one context window ([Packer et al.,
2023](#bib.bib30)). In SEIS, both code and written reports pass across
up to twenty sessions. We find that inherited reports carry mistaken
conclusions as well as progress, and we compare a reduced context budget
that forces compaction.

LLMs for kernels, software, and serving systems. KernelBench and The AI
CUDA Engineer study the generation and optimization of individual GPU
kernels ([Ouyang et al., 2025](#bib.bib5); [Lange et al.,
2025](#bib.bib31)). SWE-bench and Terminal-Bench evaluate agents on
software and command-line tasks with fixed tests ([Jimenez et al.,
2024](#bib.bib12); [Merrill et al., 2026](#bib.bib13)). VibeServe builds
serving stacks for particular deployments, and some of its tasks name
speculation as a target ([Kamahori et al., 2026](#bib.bib1); [VibeServe
contributors, 2026](#bib.bib3)). MetaInfer adapts models and hardware
within existing inference frameworks ([Chen et al., 2026](#bib.bib2)).
SEIS starts from a working engine, leaves the optimization sequence to
the agents, and retains a change only if it passes numerical and
termination checks.

Efficient LLM inference. The engines the agents produced combine
established techniques. Serving systems such as vLLM, SGLang, and
TensorRT-LLM, and attention kernels such as FlashAttention and
FlashInfer, improve throughput and memory use ([Kwon et al.,
2023](#bib.bib8); [Zheng et al., 2024](#bib.bib9); [NVIDIA,
2026](#bib.bib4); [Dao et al., 2022](#bib.bib32); [Ye et al.,
2025](#bib.bib10)). Quantization to 8 or 4 bits reduces the memory
traffic of decoding ([Dettmers et al., 2022](#bib.bib33); [Frantar et
al., 2023](#bib.bib34); [Lin et al., 2024](#bib.bib35)). Speculative
decoding verifies drafted tokens with the target model and preserves its
output distribution ([Leviathan et al., 2023](#bib.bib14); [Chen et al.,
2023](#bib.bib36)). Drafts can come from the prompt ([Saxena,
2023](#bib.bib17)), from n-grams generated in parallel ([Fu et al.,
2024](#bib.bib37)), or from lightweight draft heads ([Cai et al.,
2024](#bib.bib38); [Li et al., 2024](#bib.bib39)). We do not claim these
techniques. We study how agents chose, implemented, and combined them.

Reward hacking and agent evaluation. Optimizing a measured objective can
exploit gaps between the measurement and the intended task ([Amodei et
al., 2016](#bib.bib40); [Krakovna et al., 2020](#bib.bib41); [Skalse et
al., 2022](#bib.bib11)). Coding agents skip or special-case tests
([Baker et al., 2025](#bib.bib42)), and ImpossibleBench measures how
often they exploit tests that contradict the specification ([Zhong et
al., 2026](#bib.bib43)). We report such cases in systems optimization,
such as output-vocabulary restriction that keeps task scores within the
margin, and describe how revised evaluation exposed them
(Section [6](#S6 "6 How the Evaluation Evolved ‣ SEIS: Self-Evolving Inference Systems")).

## 3 SEIS: Framework and Experimental Setup

In this section, we start with the formal definition of our evolving
target and the rubrics for evaluating the success an attempt, then we
describe the core agent execution and cooperation protocols used in
SEIS, and finally describe the specific realization of SEIS used in our
experiments.

### 3.1 Improving LLM Serving Efficiency as an Evolving Challenge

We choose optimizing Qwen3-0.6B’s single-request decoding performance
inside of mini-sglang as the core objective for self-evolution. The main
reason for choosing this is because its minimal code base allows free
exploration of creative solutions, yet still providing practical
significance. On top of that, specifying the objective and verifying
progress becomes programmablely possible.

SEIS consists of multiple agent sessions (the interaction patterns among
them are described below), where we give each session a starting
codebase, along with a goal description but do not provide concrete
ideas on what things to try (SEIS’s own job). Specifically, a session is
only given a private worktree, development workloads, correctness
threshold, and a scorer. It is worth noting that we do not prescribe an
optimization sequence or name very specific techniques and, therefore,
SEIS agents have the full freedom to explore techniques such as
self-attention, matrix-vector computation, normalization, sampling, and
CUDA graph optimization. And it turns out that SEIS ends up doing more
than we anticipated such as editing kernels, adjusting model execution
flows, scheduling, and KV cache management. The only constraint we
impose for SEIS is not to modify the test scripts (i.e. scorer) defined
by the problem.

### 3.2 Rubrics for Checking Evolution Progress

Checking software correctness has been an extremely challenging task in
general. Luckily in our setting, we can design very detailed criteria
for checking the correctness and efficiency of a specific implementation
evolved from running SEIS.

#### Numerical Precision Gate

The inference engine takes in different tensor shapes of the input
(which is one major factor of the inference efficiency), and SEIS’s
implementation needs to be accurate in terms of 1) language perplexity
(relative difference within 5%), 2) mean KL divergence ($`\leq 0.05`$),
and 3) argmax token agreement ($`\geq 90\%`$) w.r.t. the base
implementation from mini-sglang.

#### Downstream Performance Gate

On top of the precision gate, we include GSM8K([Cobbe et al.,
2021](#bib.bib15)) and a synthetic retrieval task (details in the
Appendix D) as downstream post-validations, because numerical
differences could accumulate across steps, and therefore, affect model
behaviors.

We admit that passing these two categories of tasks does not directly
lead to behavior equivalence, which itself, as a software similarity
check, is a long-standing research question. However, it does explicitly
give SEIS the right scope to evolve for creative solutions on improving
the baseline’s inference efficiency. More discusses can be found in
Sec [6](#S6 "6 How the Evaluation Evolved ‣ SEIS: Self-Evolving Inference Systems").

### 3.3 SEIS Agent Execution and Cooperation Protocols

SEIS’s main workflow consists of multiple independent agent sessions,
which have a two-hour wall clock time hard limit. Therefore, the central
design question becomes how we can coordinate and exchange information
among them.

#### Single Session Life Cycle

When a session finishes either due to time-out or completion, the master
harness will take the changed code and run evaluation pipelines on the
attempted optimization against the two gates. A successful session will
become the base for future sections to inherit from, including the
updated worktree and progress reports.

#### Multiple Session Topology

Evolution appears through iterative process, and in our case, sessions
need to iterate from where past sessions finish and learn from their
experiences. In this work, we study three concrete topologies that
connect sessions together.

- •
  Branching Branching is the simplest form where we let multiple single
  sessions to work from the same starting point (same base code base,
  objective descriptions, etc), enabling independent explorations of the
  same problem. The final result is aggregated as the best
  implementation among them.
- •
  Branching Chain Different from Branching, Branching Chain allows
  information exchange through temporal inheritance where the new
  sessions can learn and build up from past sessions’ success and
  failure cases through reports and evaluation results.
- •
  Sync Branching Chain Branching Chain allows multiple parallel agents
  to solve a single problem and the natural extension is allowing them
  to share knowledge during their independent execution. Sync Branching
  Chain adds fixed interval (N sessions) barriers among chains of
  sessions for synchronized all-to-all message exchange, so that all
  chains are aware of each other’s progress.

The full topology visualization is in
Figure [2](#S2.F2 "Figure 2 ‣ 2 Related Work ‣ SEIS: Self-Evolving Inference Systems").
We will show in our results that Branching is an intuitive first choice
but often the worst design among the three, significantly eclipsed by
the latter two due to lack of cross-session and cross-chain evolution
capability. And surprisingly, the final performance parity between the
Sync and normal Branching Chain heavily depends on the agent’s own
behavior, which we will discuss in our experiment section.

### 3.4 Experiment Setup

We use Claude Opus 5 through Claude Code (Opus) and GPT-5.6 Sol through
Codex (GPT), both at their maximum reasoning and context length setting.
Each agent runs four conditions, each with three chains of twenty
sessions: Branching Chain (Chain), Sync Branching Chain with $`N=3`$ and
$`N=9`$ (Sync-3 and Sync-9), and Branching Chain with context compaction
at about 128k tokens (Chain-128k). The main Qwen experiments thus
contain 24 chains and 480 sessions. Branching is not run as a separate
condition. Its reference uses the first sessions of the Chain, Sync-3,
and Sync-9 chains, which start independently from vanilla: nine sessions
per agent.

We let SEIS optimize the inference efficiency of Qwen3-0.6B in
mini-sglang, running on a single NVIDIA H100 80G. We focus on single
request and greedy decoding for determined numerical, downstream gate
evaluation, as well as performance profiling. The validation data for
numerical gate spans across natural language, mathematics, and code.
Other model family SEIS experiments are in Appendix G.

## 4 What the Agents Built

This section examines the best engine that the agents built: its speed
and accuracy relative to vanilla and production engines, and the changes
behind its speedup.

### 4.1 End-to-end performance and quality

Self-evolution delivers a large end-to-end speedup. The best engine,
selected by development speedup, comes from Opus Sync-9 chain A. On 100
natural-length requests, it reaches 1,942 tokens/s against 594 tokens/s
for vanilla, a 3.27$`\times`$ speedup. Mean request latency falls from
295 to 89 ms; the best engine emits 1.27 % fewer tokens over these
requests.
Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ SEIS: Self-Evolving Inference Systems")
presents throughput, latency, and task accuracy together, and Appendix E
gives the request statistics.

The speedup preserves measured task accuracy. The best engine scores
58.48 % on the 660-item GSM8K test split, compared with 57.42 % for
vanilla, and 87.78 % on retrieval, compared with 88.15 %. The
differences are +1.06 and $`-`$0.37 percentage points, both within
$`\pm`$3 points. Its audited implementation retains the complete output
head and attention computation. These observations concern the two
reported tasks and the audited code; Appendix E reports paired accuracy
uncertainty.

The best evolved engine also outperforms production engines. We tune
vLLM, SGLang, and TensorRT-LLM through their public interfaces,
considering quantization, speculation, and execution settings on
development data ([Kwon et al., 2023](#bib.bib8); [Zheng et al.,
2024](#bib.bib9); [NVIDIA, 2026](#bib.bib4)). The best evolved engine
reaches 2.81–3.10$`\times`$ their selected configurations’ throughput on
the same model, H100, and single-request workload. The best evolved
engine and all three selected references have observed accuracy
differences within $`\pm`$3 points on both final tasks. Appendix E
specifies the configuration search and timing protocol.

### 4.2 Sources of speedup

Self-evolution optimizes a whole system by redesigning the computation.
The best engine changes 30 files across kernels, model layers,
attention, the engine, and the scheduler. On the GPU, per-output-channel
INT8 linear kernels also perform normalization, residual addition, and
activation. Attention combines q/k normalization, rotary embeddings, and
KV writes, and fuses the combination of attention partials into the
output projection. On the host, greedy token selection runs inside CUDA
graphs, token IDs are published into pinned host memory, and the
scheduler combines step preparation. In a 128-token CUDA profile, kernel
calls fall from 403 to 134 per output token, and standalone
normalization and elementwise calls fall from 169 to below one; summed
kernel time falls from 1,493 to 766 $`\mu`$s per token
(Figure [3](#S2.F3 "Figure 3 ‣ 2 Related Work ‣ SEIS: Self-Evolving Inference Systems")(b,c)).
With speculation off, the engine needs 145 calls and 775 $`\mu`$s per
token, so almost all of this reduction comes from the redesigned
single-token path. Kernel intervals overlap under programmatic dependent
launch, so these sums are not wall-clock decoding time; throughput is
measured separately.

Optimizations build on each other: speculative decoding pays off on top
of efficient kernels.
Figure [4](#S3.F4 "Figure 4 ‣ Multiple Session Topology ‣ 3.3 SEIS Agent Execution and Cooperation Protocols ‣ 3 SEIS: Framework and Experimental Setup ‣ SEIS: Self-Evolving Inference Systems")
shows the additional path. Prompt lookup proposes tokens from the prompt
and generated history. Estimated token yield and verification cost
decide between ordinary decoding and eight- or sixteen-row verification.
Multi-row INT8 kernels and shared-KV attention execute the verification,
while the runtime reserves cache slots, commits the accepted prefix, and
emits the accepted tokens. The chains that built it did so after their
kernels had matured
(Section [5.1](#S5.SS1 "5.1 Branching Chain: Building on Inherited Work ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems")).
On the same 100 prompts with three repetitions, speculation raises the
speedup from 3.08$`\times`$ to 3.27$`\times`$ on natural-length requests
(+6 %), and from 3.12$`\times`$ to 3.87$`\times`$ when outputs are
forced to 256 tokens (+24 %;
Figure [3](#S2.F3 "Figure 3 ‣ 2 Related Work ‣ SEIS: Self-Evolving Inference Systems")(a)).
The final policy comes from chain B and is integrated with chain A’s
execution layer and kernels
(Section [5.2](#S5.SS2 "5.2 Sync Branching Chain: Sharing Work across Chains ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems"));
Appendices B and F give the implementation and validation details.

## 5 How the Engine Evolved

This section follows how the engines evolved over sessions and across
chains, measuring progress by development speedup, the score that SEIS
optimizes during evolution.

### 5.1 Branching Chain: Building on Inherited Work

Accumulating work beats making more independent attempts. With the same
number of sessions, the median chain exceeds the expected best of as
many independent first sessions from the second session on, for both
agents
(Figure [5](#S5.F5 "Figure 5 ‣ 5.1 Branching Chain: Building on Inherited Work ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems")).
By session 20, all eighteen Chain, Sync-3, and Sync-9 chains finish
above the best Branching result: the slowest final engine reaches
2.88$`\times`$ for Opus against 1.99$`\times`$, and 1.84$`\times`$ for
GPT against 1.46$`\times`$. The best engine’s chain shows how the work
accumulates: it rises from 1.73$`\times`$ in session 1 to 3.19$`\times`$
by session 17. Early sessions move the linear layers to INT8 kernels and
fuse operations; later sessions remove host overhead, for example by
publishing the selected token from inside the CUDA graph. This
accumulated work is the ordinary path measured in
Section [4.2](#S4.SS2 "4.2 Sources of speedup ‣ 4 What the Agents Built ‣ SEIS: Self-Evolving Inference Systems").

The largest gains need multi-session changes that build on earlier work.
Speculative decoding, which the goal description never names, is first
considered in session 5 but first works in sessions 14 and 16, in two
chains. Every final engine above 3.6$`\times`$ uses it. It pays off only
after the policy, multi-row kernels, and KV handling change together, so
it cannot be built one small step at a time
(Appendix [B](#A2 "Appendix B Speculative Decoding: Implementation and Engineering History ‣ SEIS: Self-Evolving Inference Systems")).
Its payoff also depends on earlier kernel work. In session 10, one chain
measured 1.9 tokens per step against a verification cost of 2.2 ordinary
steps and declined. The chains that built it did so after their kernels
had matured and a verification step cost less relative to an ordinary
one. Because any passing engine is retained, unfinished work can
continue. The best engine’s chain drops to 2.37$`\times`$ in session 18
with an unfinished speculative implementation, which the next session
repairs and combines with a peer’s policy
(Section [5.2](#S5.SS2 "5.2 Sync Branching Chain: Sharing Work across Chains ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems")).
With a 128k context, no chain finished the change. The one attempt began
in session 20 and hit the time limit; these runs cannot separate
compaction from lost working time.

Inherited reports pass on errors as well as knowledge. What the chains
wrote about speculative decoding also delayed it. Several chains wrote
that the protected interface forbids multi-token execution, and later
sessions repeated the claim. Two chains estimated about 1.0 tokens per
verification step with an off-by-one simulation, against 2.30 from a
correct replay, and abandoned the direction. Another measured 2.07
correctly but left the number out of its report.

### 5.2 Sync Branching Chain: Sharing Work across Chains

A Sync Branching Chain runs several chains in parallel and, every $`N`$
sessions, lets all chains read each other’s code and reports. No engine
is replaced: each recipient decides what to adopt, so a design transfers
only if it can be fitted into a different implementation, a problem
familiar from merging parallel engineering efforts. We ask what
synchronization adds to a plain chain and when it pays off.

Synchronization spreads discoveries faster than chains find them alone.
One chain needed most of its session budget to make speculative decoding
work, but a single synchronization spread it to both peers within one
session
(Figure [6](#S5.F6 "Figure 6 ‣ 5.2 Sync Branching Chain: Sharing Work across Chains ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems")(a)).
One of them had earlier judged the idea unprofitable; with the peer’s
design, it produced the best engine.

Integrating shared work takes engineering but can beat each chain’s own
result. The best engine pairs the originator’s decision policy with the
recipient’s own execution layer and kernels
(Appendix [B](#A2 "Appendix B Speculative Decoding: Implementation and Engineering History ‣ SEIS: Self-Evolving Inference Systems")).
Before the adopted policy could pay off, the recipient had to repair how
its inherited implementation handled accepted tokens and extend its own
execution path
(Figure [6](#S5.F6 "Figure 6 ‣ 5.2 Sync Branching Chain: Sharing Work across Chains ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems")(b)).
Both recipients ended faster than the originator
(Figure [6](#S5.F6 "Figure 6 ‣ 5.2 Sync Branching Chain: Sharing Work across Chains ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems")(a)).
The same recipient also tests another peer’s suggestion and discards it
when it does not help its own implementation.

## 6 How the Evaluation Evolved

The evaluation pipeline and rubrics of
Section [3.2](#S3.SS2 "3.2 Rubrics for Checking Evolution Progress ‣ 3 SEIS: Framework and Experimental Setup ‣ SEIS: Self-Evolving Inference Systems")
were themselves revised during our experiments. We present four cases.
In each, an engine passed the evaluation in use at the time while
breaking something that the evaluation did not check.

(1) An evaluation only protects the code it runs. Our initial capability
check used multiple-choice benchmarks such as MMLU, scored by option
probabilities. An early engine matched the base model’s option
probabilities on every question, yet performed worse on a separate
free-generation GSM8K diagnostic. The explanation was in what the tests
executed: option probabilities came from a single prefill pass, leaving
the modified token-by-token decode path untested. We therefore used
tasks requiring generated answers to assess decode quality, including
the GSM8K and retrieval tests reported here. Unchanged multiple-choice
scores alone could not establish that the evolving implementation
preserved capability.

(2) Whatever the evaluation does not check, the agent may trade away.
Our fixed-length benchmark ignored end-of-sequence (EOS) tokens,
allowing an early candidate that removed EOS from its output head to
pass. Every request in a diagnostic GSM8K run then continued to its
token limit. Another candidate passed fixed-length timing but crashed
when EOS termination was enabled. We added short-generation probes
requiring normal termination before throughput scoring; failures
prevented inheritance. These probes rejected fourteen sessions in the
main Qwen runs, keeping those implementations from becoming the starting
point for subsequent sessions.

(3) Checks that expose failures can let the agent fix them itself. An
optimization cached attention execution information, saving preparation
work but sometimes reusing information invalidated by a new request.
Repeated timing on a fixed prompt passed, while a sequence of different
requests could hang. We verified a repair that refreshed this
information after each new prefill and added varied-request checks to
the speed test available to agents. In a later run, an agent encountered
the hang through this check and implemented the repair. Here, improving
the evaluation made a previously hidden failure actionable for the
agent.

(4) Task scores alone cannot certify an engine; the code must also be
inspected. Even with generation-based evaluation and termination checks,
some final engines of the main runs computed only part of the output
vocabulary. GPT Chain A omitted about 39% of vocabulary rows, while its
GSM8K accuracy differed from vanilla by only $`-1.36`$ percentage
points. The reported tasks use English prompts and numeric answers, so
they exercise limited vocabulary coverage; this candidate also retained
EOS and could terminate normally. Code inspection exposed this reward
hacking against the intended full-vocabulary task ([Skalse et al.,
2022](#bib.bib11)). The audit in
Appendix [F](#A6 "Appendix F Implementation Audit ‣ SEIS: Self-Evolving Inference Systems")
records the restrictions; the task scores alone had not detected them.

The revisions and the audit above were made by us, not by the agents. A
natural next step is to let the agents revise the evaluation as well, so
that the objective evolves together with the engine.

## 7 Limitations and Conclusion

The study covers one engine, a single-request throughput objective, and
two target models; the full organization and context comparisons are on
Qwen. Each condition has one group run, and the Qwen
speculative-decoding history contains two locally developed
implementations that accelerate decoding and two adoptions. The agents
use different vendor CLIs, and CLI revisions changed during the
campaign, so observed behavior includes tooling effects. Development
workloads fix generation length, while natural-length timing covers a
small task workload and no concurrent serving load. Reported
post-validation covers two task benchmarks and selected implementation
properties; it does not establish unrestricted functional equivalence.
Final task accuracy uses data excluded from development feedback, but
the two numeric-answer tasks provide limited capability coverage.

SEIS shows agents coordinating changes across a complete inference
engine over sustained autonomous work. Its best engine reaches
3.27$`\times`$ vanilla throughput on natural requests, with
3.08$`\times`$ retained when speculation is disabled. The histories
connect this result to accumulated kernel and runtime improvements and
to selective integration of a peer’s speculative-decoding policy. Other
final engines expose both gaps in development checks and accuracy
warnings that do not prevent inheritance. The systems and their records
therefore show how useful engineering accumulates, how implementations
combine, and how development scores can diverge from delivered
capabilities.

### AI use statement

Generative AI agents are experimental subjects in this study and are
evaluated as part of the research methodology. During the experiments,
the agents are tasked with optimizing inference engine code. Separately,
generative AI tools were used to assist with English-language editing
for readability, development and refinement of analysis code, and
consistency checks.

### Ethics statement

The experiments use public model weights and benchmark data. No
human-subject data were collected for this study.

### Reproducibility statement

Appendices specify the workloads, development gates, final-engine
selection, accuracy grading, and performance aggregation. Tables and
data figures derive from consolidated session records.

## Appendix B Speculative Decoding: Implementation and Engineering History

Algorithm and integration. The evolved speculative decoder uses n-gram
lookup over the prompt and generated history, followed by verification
against the candidate engine’s greedy predictions. The policy ranks
candidate continuations by backward context match, estimates token yield
by context bucket, and selects a verification width using measured
costs. The execution layer reserves KV slots, commits the accepted
prefix, and pipelines verification with emission of the previous
accepted tail. Multi-row INT8 kernels and shared-KV attention support
verification widths of eight and sixteen in the best engine. These
mechanisms implement established speculative-decoding and prompt-lookup
ideas ([Leviathan et al., 2023](#bib.bib14); [Saxena,
2023](#bib.bib17)); no new decoding-algorithm guarantee is claimed.

Token yield. The offline replay statistic is _output tokens per
verification step_, including the ordinary next token produced by a
step. It is not the probability of accepting a draft token. With an
eight-token draft and the replay policy specified in the analysis code,
the geometric mean across the nine development shapes is 2.30
tokens/step. Two shapes have baseline distinct-4 below 0.3; their
geometric mean is 4.21, versus 1.94 for the other seven. The
corresponding held-out geometric mean is 3.46. These are replay
estimates on vanilla outputs, not online measurements of the final
adaptive policy.

The erroneous scripts compare a draft token with the output position one
token ahead of the correct verification position. The resulting
estimates near one token per step are recorded as reasons to abandon the
technique. Correct replay changes that assessment. The availability of a
profitable implementation also depends on the cost of multi-row
verification, which changes with the engine’s kernels. This history
supports the process account in
Section [5.1](#S5.SS1 "5.1 Branching Chain: Building on Inherited Work ‣ 5 How the Engine Evolved ‣ SEIS: Self-Evolving Inference Systems")
without assigning a separate causal contribution to every preceding
edit.

Builds and adoptions. Opus Chain A completes a speculative
implementation that accelerates decoding in session 16 and extends it in
session 17. Opus Sync-9 B prepares the path in session 13 and rebuilds
the slower prototype into an accelerating implementation in session 14.
A and C adopt B’s design after the sync following session 18. Source
comparison finds 181 matching lines among A’s 637 nonblank code lines,
excluding comment-only lines and standalone string expressions such as
docstrings. Matching preserves indentation and tests membership in B’s
corresponding code lines. Shared coding idioms can contribute to this
count; the reports establish the adoption history, while the overlap
corroborates it.

Policy details and inherited judgments. The policy maintains token-yield
estimates by backward-match-length bucket and compares them with
measured eight- and sixteen-row verification costs. It also scores
candidate continuations against tokens from ordinary decoding, allowing
updates without always taking a speculative step. Reports can lose
useful counterevidence: Sync-3 B measures a yield of 2.07 tokens per
step in session 13, but omits it from the session report; subsequent
reports return to the belief that the generation interface blocks the
technique. The build counts above identify implementations that deliver
acceleration; earlier slower prototypes and A’s session-18
implementation that emits only one token per verification step are
treated as unsuccessful attempts.

Verification coverage. Development teacher-forced checks exercise the
ordinary single-token path. We additionally capture 464 logit rows from
actual eight- and sixteen-row verification steps, then replay the same
prefixes with vanilla and with the optimized ordinary path. Contexts
range from 64 to 2,058 tokens. Widths are selected for coverage, and two
requests inject incorrect drafts.

## Appendix D Evaluation Protocol

Development workloads. The nine development shapes cross three content
types (natural language, mathematics, and code) with input/output
lengths 256/256, 512/128, and 1,024/256. The eighteen held-out shapes
use input lengths 128 and 2,048 and output lengths 128, 512, and 1,024
for each content type. The same target-specific vanilla implementation
provides the speed and numerical references. Timing reports the median
of three runs per shape; aggregate speedup is the geometric mean of
per-shape throughput ratios.

Development gates. Numerical checks use full-vocabulary logits
conditioned on the vanilla token sequence. KL is computed in the
vanilla-to-candidate direction and averaged over checked token
positions. Perplexity ratio must not exceed 1.05, mean KL must not
exceed 0.05, and top-1 agreement must be at least 0.88. Separate
free-generation runs check agreement between timing and instrumentation
modes. Four EOS-enabled termination prompts must finish before their
caps. The GSM8K feedback bit is recorded and shown to the next session,
but it is not a gate.

Task accuracy. We partition GSM8K’s released evaluation items using a
fixed seed into 659 development-feedback items and 660 final-test items.
All reported final GSM8K task accuracies use the latter, with greedy
generation and the saved prompt format. The synthetic retrieval test has
thirty items in each combination of filler length (512, 1,024, or 2,048
tokens) and fact position (10 %, 50 %, or 90 %), giving 270 items. Four
named access-code facts are inserted into WikiText filler ([Merity et
al., 2017](#bib.bib19)), and the model must return the requested
four-digit number. The Qwen prompts including instructions contain
592–2,133 tokens and allow up to 32 output tokens. This tests
longer-input retrieval, distinct from the agent’s context-window
experiment.

Both tasks use the recorded numeric-answer grader. For a generation that
reaches its cap, extraction ends at the first answer-closing marker on
GSM8K, when present, or the first numeric response on retrieval; other
outputs are unchanged. This correction changes no item-level grade for
the current Qwen endpoints or vanilla. Paired comparisons use the same
items for both engines. The $`\pm`$3-point margin describes observed
differences; statistical equivalence additionally requires both
one-sided tests at level 0.05.

Protocol scope. Earlier pilot failures informed the main harness,
including its termination probe and the handling of stalled accuracy
checks. Those pilot cases are identified as such in
Section [6](#S6 "6 How the Evaluation Evolved ‣ SEIS: Self-Evolving Inference Systems")
and do not enter the 480-session main matrix. All experiments reported
as main conditions use the same development thresholds and inheritance
rule. Protected benchmark and interface files are restored before
scoring, and scoring runs outside the agent’s process.

measurements are associated with that same version. The Qwen and Llama

The manuscript data and figures are generated from the consolidated
