###### Abstract

Large language model (LLM) agents tackle complex tasks through reasoning
and interaction with external environments. Agent skills provide
persistent, transferable capabilities that guide task planning, inform
contextual decisions, support tool use, and enable executable
procedures. Yet existing skill-evolution methods largely organize
knowledge around skill artifacts, overlooking the functional
heterogeneity within individual skills and its implications for
knowledge maintenance and use. Inspired by cognitive science, we propose
Cognitive Differentiation in Skill Evolution (CDSE), which evolves a
unified skill through four functionally distinct yet coordinated
components: Meta, Experience, Tool, and Script. CDSE extracts
evidence-grounded semantic gradients from successful and failed
trajectories, consolidates them by functional role, and applies
component-specific updates and validation with cross-component
coordination and adaptive invocation. An analysis of 500 top-ranked
skill packages shows that 96.8% contain knowledge spanning at least two
functional roles. Across six benchmarks, three agent models, and two
execution harnesses, CDSE achieves the highest scores in all 36
settings, improving over the Base agent by 7.6 percentage points and the
strongest competing method in each setting by 2.6 points on average.
Ablation studies further support the importance of functional
differentiation and adaptive invocation.

Large language model (LLM) agents tackle complex tasks through
reasoning, planning, and interaction with external environments ([Yao et
al., 2023](#bib.bib23); [Wang et al., 2024b](#bib.bib31); [Yang et al.,
2024](#bib.bib32)). External skills extend these capabilities by
providing a persistent, reusable knowledge state without modifying model
parameters ([Wang et al., 2024a](#bib.bib8); [Wang et al.,
2025](#bib.bib4); [Zheng et al., 2025](#bib.bib9)). By leveraging
feedback from evaluated execution trajectories, agents can continuously
refine their skills to preserve effective behaviors, address recurring
failures, and improve subsequent task performance. This has motivated
growing research on trajectory-driven skill evolution as a means of
continual agent self-improvement.

Recent studies have explored complementary approaches to transforming
agent execution experience into persistent, reusable capabilities.
Experience- and memory-based methods accumulate workflows, reasoning
strategies, and procedural knowledge from past interactions, enabling
knowledge reuse across tasks ([Wang et al., 2025](#bib.bib4); [Ouyang et
al., 2026](#bib.bib5); [Fang et al., 2026](#bib.bib6)).
Trajectory-to-skill approaches further distill successful and failed
executions into reusable skill artifacts and executable routines ([Zheng
et al., 2025](#bib.bib9); [Ni et al., 2026](#bib.bib12); [Alzubi et al.,
2026](#bib.bib11)). More recent methods focus on refining and managing
evolving skills through evaluation feedback, failure analysis,
behavioral validation, and lifecycle management ([Yang et al.,
2026b](#bib.bib13); [Gautam et al., 2026](#bib.bib14); [Moll et al.,
2026](#bib.bib15); [Zhang et al., 2026a](#bib.bib18); [Lin et al.,
2026](#bib.bib20)). Collectively, these studies have substantially
advanced how agents acquire, refine, and maintain reusable capabilities
from execution experience.

Despite these advances, existing approaches still largely organize
learned knowledge around artifact boundaries, such as skill documents,
memory entries, or skill banks, rather than systematically accounting
for the distinct behavioral functions of individual updates. Yet a
single execution trajectory can yield knowledge serving different
purposes. For example, a spreadsheet task may suggest inspecting
workbook structure before acting, verifying units before comparison,
using a particular library to preserve formulas, or automating repeated
sorting through a reusable script. Although derived from the same
execution, these updates differ in scope, representation, validation
requirements, and when they become useful. Organizing them around
artifact boundaries alone does not determine how each should be
maintained and used. The central challenge is therefore not merely what
knowledge to retain, but how to organize, update, validate, and invoke
it according to its functional role.

Cognitive science offers a useful perspective on how to organize such
functionally diverse knowledge. Atkinson and Shiffrin distinguished
task-dependent control processes from relatively stable memory
structures ([Atkinson and Shiffrin, 1968](#bib.bib27)). For agent
skills, this distinction points to _Meta_ knowledge, which governs
task-level planning, monitoring, verification, and stopping, while other
knowledge supports specific decisions and actions. Yet the knowledge
underlying these actions is itself diverse. Cohen and Squire’s
distinction between knowing how and knowing that ([Cohen and Squire,
1980](#bib.bib28)) highlights differences in how knowledge can be
learned and retained. In agent skills, _Experience_ captures
context-conditioned heuristics and recovery strategies, _Tool_ provides
capability-specific operational guidance, and _Script_ encodes reusable
executable procedures with execution and validation contracts. These
functional categories are tailored to agent execution rather than
directly mapped from human cognitive systems. Finally, Miyake et al.
highlighted the unity and diversity of executive functions ([Miyake et
al., 2000](#bib.bib29)), underscoring the importance of coordination
among specialized functions. Together, these perspectives suggest that
different forms of skill knowledge should be maintained according to
their functional roles while remaining coordinated during task
execution.

To examine these functional distinctions in real-world agent skills, we
analyze 500 widely used skill packages using an expert-derived
annotation scheme
(Appendix [F](#A6 "Appendix F Functional Composition of the Top-500 Skills ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents")).
As shown in
Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents"),
96.8% of the packages contain content spanning at least two functional
roles, with Experience, Meta, and Tool appearing more frequently than
Script. These findings suggest that multiple forms of reusable knowledge
commonly coexist within individual skills, supporting a coordinated yet
functionally differentiated approach to skill evolution.

Building on these cognitive insights and empirical observations, we
propose Cognitive Differentiation in Skill Evolution (CDSE), a framework
that evolves a unified skill through four functionally distinct yet
coordinated components. CDSE first performs _Outcome-Contrastive
Semantic Gradient Discovery_ to extract evidence-grounded directions for
reusable behavioral change from successful and failed trajectories. It
then applies _Cognition-Guided Gradient Consolidation_ to identify which
semantic gradients are worth retaining and assign them to Meta,
Experience, Tool, or Script according to their functional roles.
Finally, _Adaptive Self-Improvement Update_ refines these components
through specialized update and validation mechanisms, while
cross-component coordination and adaptive invocation support their use
as task demands change. In this way, CDSE aligns how knowledge is
learned from trajectories with how it is maintained and used during
subsequent tasks.

Across six benchmarks, three agent models, and two execution harnesses,
CDSE achieves the highest scores in all 36 evaluation settings,
improving over the Base agent by 7.6 percentage points and over the
strongest competing skill-evolution method in each setting by 2.6 points
on average. Component-level analyses further reveal distinct patterns of
contribution, invocation, and transfer. We summarize our main
contributions as follows: (1) identifying and empirically characterizing
functional heterogeneity in real-world agent skills; (2) proposing CDSE
to organize and evolve trajectory-derived knowledge through
function-specific yet coordinated mechanisms; and (3) systematically
evaluating its effectiveness and examining the behavior of
differentiated skill components across diverse tasks, models, and
execution harnesses.

## 2 Related Work

#### Language agents and self-improvement.

LLM agents interleave reasoning, actions, and tool use to solve tasks
through environment interaction ([Yao et al., 2023](#bib.bib23); [Wang
et al., 2024b](#bib.bib31); [Yang et al., 2024](#bib.bib32)).
Self-improvement methods extend this loop by turning execution feedback
into persistent changes, either by retaining feedback, cross-task
insights, and reasoning strategies in context or memory ([Shinn et al.,
2023](#bib.bib1); [Zhao et al., 2024](#bib.bib2); [Fu et al.,
2024](#bib.bib3); [Ouyang et al., 2026](#bib.bib5); [Zhang et al.,
2026d](#bib.bib7)), or by modifying the agent implementation and even
the meta-level adaptation procedure ([Zhang et al., 2026b](#bib.bib26);
[Zhang et al., 2026c](#bib.bib30)). Another line of work jointly evolves
task generation and reasoning or tool-using policies through
reinforcement learning on self-generated curricula ([Zhao et al.,
2025](#bib.bib33); [Huang et al., 2026](#bib.bib34); [Xia et al.,
2026](#bib.bib35)). These works show that improvement can persist at
multiple levels of an agent system. CDSE focuses on a complementary
setting: the base model and improvement protocol remain fixed, while
evaluated trajectories update a persistent external skill state. The
central question is therefore how heterogeneous behavioral updates
should be organized within that evolving state.

#### Agent skills and skill evolution.

Agent skills externalize reusable capabilities as instructions,
workflows, or executable procedures. Prior systems accumulate executable
programs, reusable action routines, or APIs from experience ([Wang et
al., 2024a](#bib.bib8); [Wang et al., 2025](#bib.bib4); [Zheng et al.,
2025](#bib.bib9)). Agent Skills packages broaden this representation to
instructions, linked resources, and scripts loaded through progressive
disclosure ([Zhang et al., 2025](#bib.bib24)), while SkillsBench shows
that skill efficacy depends on the task, model, harness, and package
design ([Li et al., 2026](#bib.bib10)). Recent trajectory-driven methods
create and refine skill artifacts from successful and failed executions
using failure analysis, bounded edits, and evaluation feedback ([Ni et
al., 2026](#bib.bib12); [Alzubi et al., 2026](#bib.bib11); [Yang et al.,
2026b](#bib.bib13); [Gautam et al., 2026](#bib.bib14)), with subsequent
work improving validation, lifecycle management, memory, multi-file
evolution, and skill or meta-skill adaptation ([Moll et al.,
2026](#bib.bib15); [He and Yang, 2026](#bib.bib16); [Zhang et al.,
2026e](#bib.bib17); [Zhang et al., 2026a](#bib.bib18); [Yang et al.,
2026a](#bib.bib19); [Lin et al., 2026](#bib.bib20); [Shen et al.,
2026](#bib.bib21); [Wang et al., 2026](#bib.bib22)). Despite these
advances, the primary unit of organization remains an artifact
boundary—a skill document, folder, or bank entry. Even when the artifact
is hierarchical, multi-file, or memory-enhanced, an update’s execution
function does not explicitly determine its ownership, representation,
update rule, validation contract, or invocation timing. CDSE instead
makes functional ownership the organizing principle, assigning
trajectory-derived updates to Meta, Experience, Tool, or Script and
maintaining them through differentiated but coordinated mechanisms.

## 3 Cognitive Differentiation in Skill Evolution

CDSE evolves a unified skill by discovering semantic gradients from
evaluated trajectories, consolidating them by functional role, and
updating its components through specialized maintenance and
cross-component coordination
(Figure [3](#S2.F3 "Figure 3 ‣ Agent skills and skill evolution. ‣ 2 Related Work ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents")).
The updated components are then invoked adaptively during subsequent
tasks.

### 3.1 Problem Formulation: Trajectory-Driven Skill Self-Evolution

An agent $`\pi_{\theta}`$ solves a task $`x`$ by interacting with an
environment while selectively loading relevant components of a
persistent skill. At evolution round $`t`$, the unified skill state
comprises four functionally differentiated components: Meta, Experience,
Tool, and Script. We denote this state by
$`\mathcal{B}^{(t)}=(\mathcal{M},\mathcal{E},\mathcal{T},\mathcal{S})^{(t)}`$,
with component indices $`\mathcal{K}=\{M,E,T,S\}`$.

Let $`\mathcal{D}^{(t)}=\{(\tau_{i},y_{i})\}_{i=1}^{N_{t}}`$ denote the
evaluated trajectory corpus, where $`\tau_{i}`$ is an execution trace
and $`y_{i}`$ its evaluated outcome. CDSE aims to improve subsequent
task performance by updating the persistent skill state as follows:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\mathcal{B}^{(t+1)}=\mathcal{U}\!\left(\mathcal{B}^{(t)},\mathcal{R}\big(\mathcal{G}(\mathcal{D}^{(t)})\big)\right),
``` |  | (1) |

where $`\mathcal{G}`$ extracts candidate semantic gradients,
$`\mathcal{R}`$ retains and assigns them to functional components, and
$`\mathcal{U}`$ performs the validated skill update detailed in
Section [3.4](#S3.SS4 "3.4 Adaptive Self-Improvement Update ‣ 3 Cognitive Differentiation in Skill Evolution ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents").
This process updates only the external skill state, leaving the model
parameters and update protocol fixed. The formulation also supports
repeated consolidation over a fixed trajectory corpus, as examined in
our multi-round experiments.

### 3.2 Outcome-Contrastive Semantic Gradient Discovery

The discovery stage extracts candidate semantic gradients from evaluated
trajectories, i.e., trace-grounded, reusable directions for behavioral
change ([Shinn et al., 2023](#bib.bib1); [Pryzant et al.,
2023](#bib.bib25)). A deterministic filter $`P`$ removes runtime-only
artifacts while preserving reasoning, tool actions, and observations
relevant to behavioral diagnosis. Successful and failed trajectories are
then analyzed under distinct diagnostic objectives. For successful
trajectories, the analyzer identifies trace-supported behaviors worth
preserving and safeguards for fragile successes. For failed
trajectories, it localizes evidenced decisive errors or missing
transitions and identifies the minimal supported recovery. An observed
outcome alone does not establish the validity of a procedure or
diagnosis; unsupported causes remain unresolved.

Let $`s(y_{i})\in\{+,-\}`$ denote the success/failure label derived from
the evaluated outcome $`y_{i}`$. The corresponding analyzer
$`A_{s(y_{i})}`$ processes the filtered trajectory and its outcome to
produce candidate semantic gradients:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{F}=\mathcal{G}(\mathcal{D}^{(t)})=\bigcup_{i=1}^{N_{t}}A_{s(y_{i})}(P(\tau_{i}),y_{i}).
``` |  | (2) |

Each $`f=(g,e)\in\mathcal{F}`$ pairs a proposed reusable behavioral
update $`g`$ with its supporting trace lines $`e`$. The analyzer
produces a core analysis, reusable lessons, and, when applicable, a
script opportunity. Supporting evidence remains attached to each
candidate, providing the basis for subsequent retention and functional
attribution.

### 3.3 Cognition-Guided Gradient Consolidation

Drawing on cognitive distinctions between control processes and memory
structures, as well as between forms of knowing ([Atkinson and Shiffrin,
1968](#bib.bib27); [Cohen and Squire, 1980](#bib.bib28)), CDSE separates
gradient consolidation into two steps: retention and functional
attribution. Retention determines which candidate gradients are worth
preserving, while attribution identifies the components responsible for
maintaining them.

A retention gate $`r(f)\in\{0,1\}`$ selects evidence-supported,
actionable, and reusable gradients, filtering out generic,
instance-specific, unsupported, or redundant findings. Each retained
gradient is assigned one primary component and, when its evidence
supports an additional functional role, at most one secondary component.
Let $`\rho(f)\subseteq\mathcal{K}`$ denote the set of assigned
components, with $`\rho(f)=\varnothing`$ if $`r(f)=0`$. Consolidation
produces

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathcal{F}_{k}`$ | $`\displaystyle=\{f\in\mathcal{F}:r(f)=1,\ k\in\rho(f)\},`$ |  | (3) |
|  | $`\displaystyle k`$ | $`\displaystyle\in\mathcal{K},\quad 1\leq|\rho(f)|\leq 2\ \text{if }r(f)=1.`$ |  |  |

Functional attribution follows the behavioral role of each gradient.
Meta maintains task-level control policies, including planning,
monitoring, and global verification. Experience maintains
context-conditioned heuristics and recovery strategies activated by
local conditions. Tool maintains capability-specific operational
guidance, while Script receives proposals for reusable executable
procedures and their execution or validation contracts. The primary
assignment is recorded separately, and each gradient retains its
original content and supporting evidence for subsequent
component-specific updates.

### 3.4 Adaptive Self-Improvement Update

Given the consolidated gradient sets
$`\{\mathcal{F}_{k}\}_{k\in\mathcal{K}}`$, the update operator
$`\mathcal{U}`$ in
Equation [1](#S3.E1 "In 3.1 Problem Formulation: Trajectory-Driven Skill Self-Evolution ‣ 3 Cognitive Differentiation in Skill Evolution ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents")
combines component-specific maintenance operators $`U_{k}`$,
cross-component coordination $`C`$, and invocation-description rewriting
$`D`$:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\widehat{\mathcal{B}}_{k}^{(t+1)}`$ | $`\displaystyle=U_{k}(\mathcal{B}_{k}^{(t)},\mathcal{F}_{k}),`$ |  | (4) |
|  | $`\displaystyle\mathcal{B}^{(t+1)}`$ | $`\displaystyle=D\!\left(C(\widehat{\mathcal{B}}^{(t+1)})\right).`$ |  |  |

Here, $`\widehat{\mathcal{B}}_{k}^{(t+1)}`$ denotes the candidate update
to component $`k`$, and $`\widehat{\mathcal{B}}^{(t+1)}`$ collects the
four component updates. Inspired by the unity and diversity of cognitive
functions ([Miyake et al., 2000](#bib.bib29)), this design combines
specialized maintenance with coordination across the unified skill
state.

#### Specialized updates.

Meta and Experience maintain atomic behavioral rules. Both align
incoming gradients with existing rules, aggregate supporting evidence
for revisions, and induce new rules from unmatched gradients. Meta
updates task-level control policies, whereas Experience organizes
heuristics around explicit local activation conditions. Tool assigns
gradients to capability-specific categories and revises or induces
operational rules within each category. Category-level capacity control
preserves coverage across different tools. Script aligns proposals with
existing procedures and screens new proposals for deterministic reuse,
explicit input/output contracts, and feasible tests. Accepted proposals
are implemented or revised, self-tested, and independently verified.
Unverified executable changes are withheld.

#### Cross-component coordination.

After specialized maintenance, the coordinator $`C`$ resolves
conflicting or redundant guidance and residual ownership ambiguity
across components through minimal edits that preserve verified
executable artifacts and component-specific responsibilities.

#### Adaptive invocation.

The description rewriter $`D`$ derives each component’s scope,
applicable conditions, and expected contribution from the coordinated
skill state. Visible before component loading, these descriptions guide
the agent’s selection of relevant components through its ordinary
invocation mechanism as task demands change. The updated skill state is
published only after coordination and description changes pass their
respective validation checks. Details are in
Appendix [G](#A7 "Appendix G Implementation Details of CDSE ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents").

## 4 Experiments

### 4.1 Experimental Setup

We evaluate on six benchmarks: OfficeQA ([Opsahl-Ong et al.,
2026](#bib.bib36)), SpreadsheetBench2 ([Zhu et al., 2026](#bib.bib37)),
SealQA ([Pham et al., 2026](#bib.bib38)), LiveMathBench ([Liu et al.,
2025](#bib.bib39)), SWE-Pro ([Deng et al., 2025](#bib.bib40)), and
AutomationBench ([Shepard and Salimans, 2026](#bib.bib41)), using
GLM-5.2 ([GLM-5-Team and others, 2026](#bib.bib42)),
DeepSeek-V4-Flash ([DeepSeek-AI and others, 2026](#bib.bib43)), and
MiniMax-M3 ([Lai et al., 2026](#bib.bib44)) under both Claude Code and
Codex. Each benchmark collection is split into training and test sets at
a 2:7 ratio. Training trajectories support skill evolution; all reported
results use the test split and benchmark-specific scoring procedures.

We compare CDSE with the same agent without an evolved skill state
(Base), Trace2Skill ([Ni et al., 2026](#bib.bib12)),
SkillOpt-lite ([Yang et al., 2026b](#bib.bib13)), and EvoSkill ([Alzubi
et al., 2026](#bib.bib11)). Within each model–harness block, methods
share the training split, task instances, tool access, and context
limit.
Table [1](#S3.T1 "Table 1 ‣ Adaptive invocation. ‣ 3.4 Adaptive Self-Improvement Update ‣ 3 Cognitive Differentiation in Skill Evolution ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents")
reports results after three evolution rounds for each skill-evolution
method. Task execution is bounded by benchmark-specific per-question
time and turn limits; tasks that remain unfinished when either limit is
reached are counted as failures. Aggregate improvements are

### 4.3 Functional Differentiation and Adaptive Invocation

Figure [4](#S4.F4 "Figure 4 ‣ 4.1 Experimental Setup ‣ 4 Experiments ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents")
examines component-removal effects (a), invocation rates (b), and
first-invocation timing (c). Invocation patterns vary across benchmarks:
all four components are invoked in at least 76.7% of AutomationBench
episodes, whereas Script is invoked in only 6.0% on SpreadsheetBench2.
Invocation timing also differs, with Script loaded later on
SpreadsheetBench2 and SWE-Pro, but Tool and Script loaded early on
AutomationBench.

Component contributions are similarly task-dependent. Removing Tool
reduces performance by 1.2 points on SealQA but 6.5 on SWE-Pro, while
removing any component on AutomationBench causes a 5.0–8.2-point drop.
Notably, despite its low invocation rate, removing Script causes the
largest drop (8.0 points) on SpreadsheetBench2. Component importance
therefore does not directly follow invocation frequency. Under
progressive disclosure, descriptions remain visible before loading, so
even components with zero recorded invocations can influence execution
and exhibit ablation effects.

## 5 Conclusion

CDSE organizes trajectory-derived knowledge into four functionally
distinct components—Meta, Experience, Tool, and Script—using specialized
updates, cross-component coordination, and adaptive invocation. Across
six benchmarks, three models, and two harnesses, it achieves the highest
scores in all 36 settings. Component and transfer analyses reveal
task-dependent contributions and varying transferability, while
ablations highlight the importance of functional differentiation and
adaptive invocation. Token-efficiency analysis further shows that CDSE
achieves greater performance gains per input token. These findings
suggest that effective skill evolution benefits from maintaining and
using knowledge according to its functional role.

## Limitations

Our evaluation covers six benchmarks, three agent models, and two
execution harnesses, leaving generalization to other domains and agent
configurations to future work. Multi-round experiments reuse a fixed
trajectory corpus and therefore do not establish sustained improvement
in continually changing environments. The four-component organization is
supported by our survey and experiments, but alternative decompositions
and their effectiveness remain to be studied.

## Ethical Considerations

CDSE is intended to support research on reliable and reusable LLM
agents. Evolved skills may retain errors or biases from models and
execution trajectories, so improved task performance does not guarantee
safe deployment. Practical use should respect data privacy and
third-party licenses, restrict tool permissions, and retain human
oversight for consequential actions. We encourage responsible use of the
framework and derived artifacts.

The components exhibit distinct but coordinated behavioral roles across
tasks. Their removal effects vary substantially by benchmark, indicating
that different tasks rely on different forms of reusable knowledge.
AutomationBench provides a clear example of coordination: removing Meta,
Experience, Tool, or Script reduces performance by 5.6, 8.2, 6.3, and
5.0 points, respectively, while every component is invoked in at least
76.7% of episodes. In contrast, other benchmarks show more selective
dependence. For example, SealQA relies primarily on Meta and Experience,
whereas SWE-Pro is substantially more sensitive to Meta and Tool. These
heterogeneous contribution profiles support the functional
differentiation of the skill state rather than treating all reusable
knowledge as a homogeneous collection of guidance.

Invocation frequency does not directly reflect functional importance. On
SpreadsheetBench2, Script is invoked in only 6.0% of episodes, yet
removing it causes the largest performance drop on the benchmark, at 8.0
points. This suggests that infrequently activated components can still
be critical when triggered at the appropriate stage of execution.
Invocation timing further reveals task-conditioned specialization. Meta
and Experience are generally selected early, while Script first appears
much later on SpreadsheetBench2 and SWE-Pro, at turns 12.3 and 10.2 on
average. By contrast, Tool and Script are invoked almost immediately on
AutomationBench. Together, these patterns show that the agent does not
follow a fixed component pipeline, but adaptively selects and
coordinates differentiated knowledge according to task demands. This
behavior is consistent with the cognitive-science motivation of unity
and diversity: distinct functional components remain separable in their
roles while cooperating within a unified capability state.

## Appendix D Transfer Evaluation Details

#### Cross-benchmark component transfer.

We take an individual component evolved on SpreadsheetBench2 or
AutomationBench and make it available on a different target benchmark.
Table [2](#S4.T2 "Table 2 ‣ 4.5 Transfer across Tasks, Models, and Harnesses ‣ 4 Experiments ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents")
reports the score change from the target Base on GLM-5.2. The
parenthesized value is the fraction of target episodes that explicitly
load the transferred component. Under progressive disclosure, component
descriptions remain visible to the agent before loading and may affect
execution even when the full component is never loaded. Invocation rate
therefore measures explicit component loading, rather than total
exposure to the component.

The observed transfer differences are consistent with the functional
scopes of the components. Meta stores task-level control policies that
can remain useful across heterogeneous tasks. Experience stores
context-conditioned heuristics, while Tool and Script store
capability-specific instructions and executable procedures,
respectively. These forms of knowledge require progressively closer
alignment between source and target settings, consistent with their more
selective or limited cross-benchmark transfer.

## Appendix E Mechanism Ablation Details

We evaluate four mechanism ablations on SpreadsheetBench2, SWE-Pro, and
AutomationBench using GLM-5.2 under Claude Code. Unlike the
component-removal analysis in
Figure [4](#S4.F4 "Figure 4 ‣ 4.1 Experimental Setup ‣ 4 Experiments ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents"),
these ablations modify the organization, maintenance, coordination, or
invocation of the skill state.

#### Without cognitive differentiation.

The four components are merged into a unified skill maintained by a
generic update mechanism, using the same semantic gradients as full
CDSE.

#### Without specialized updates.

The four-component structure and adaptive invocation are preserved, but
component-specific maintenance operators are replaced by a shared update
strategy.

#### Without cross-component coordination.

Component-specific updates and validation are retained, while
cross-component conflict resolution, deduplication, and ownership
reconciliation are disabled.

#### Without the Adaptive Invocation Interface.

This variant removes the content-aware invocation interface that
describes each component’s scope, when it is useful, and its expected
benefit to guide component selection. Component-specific maintenance and
cross-component coordination are retained. The ablation therefore
evaluates the contribution of this interface to component selection
during execution.

## Appendix G Implementation Details of CDSE

This section specifies the implementation contracts underlying the three
stages in
Section [3](#S3 "3 Cognitive Differentiation in Skill Evolution ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents").
We use the same component state and trajectory notation as the main
text. The following details expand the filtering, evidence selection,
and validation steps summarized there.

### G.1 Trajectory Filtering and Finding Extraction

#### Preserving evidence while filtering logs.

The input to discovery is the evaluated corpus $`\mathcal{D}^{(t)}`$. A
deterministic filter produces $`\bar{\tau}_{i}=P(\tau_{i})`$ by removing
runtime-only heartbeats, retry notifications, lifecycle status,
duplicated terminal metrics, and redundant metadata and wrappers. It
retains ordered reasoning, tool calls and observations, permission
failures, final responses, and termination state, while retaining the
raw trace separately. Analysis operates on filtered execution evidence
rather than a model-generated summary.

#### Outcome-conditioned behavioral diagnosis.

The analyzer uses $`(\bar{\tau}_{i},y_{i})`$ to identify a reusable
direction of behavioral change, or *semantic gradient*. Natural-language
update directions follow the semantic and textual gradient perspective
([Shinn et al., 2023](#bib.bib1); [Pryzant et al., 2023](#bib.bib25)).
Here, outcome-contrastive discovery applies different diagnostic
objectives to successes and failures; it requires neither matched
trajectory pairs nor a numerical gradient. For a success, the analyzer
reconstructs a minimal trace-supported account of how the result was
reached and rates its integrity as valid, fragile, invalid, or unknown.
It extracts behavior worth preserving and safeguards that would
strengthen a fragile success. For a failure, it locates the earliest
clearly evidenced decisive error, missing transition or recovery, or
external obstacle in the inspected trace, together with the smallest
supported recovery. Answer mismatch, timeout, and parse failure are
symptoms whose causes must be supported by the trace. A successful
outcome alone does not establish a sound procedure, and unresolved
causes remain unknown.

#### Functional abstraction into semantic gradients.

Let $`z_{i}=s(y_{i})\in\{+,-\}`$ map the task-specific outcome to its
success/failure label. The two diagnostic paths feed the same functional
abstraction step:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{F}_{i}=A_{z_{i}}(P(\tau_{i}),y_{i}),\qquad f_{ij}=(g_{ij},e_{ij}),
``` |  | (5) |

where $`g_{ij}`$ expresses a reusable behavioral update and $`e_{ij}`$
identifies its supporting trace lines. $`A_{+}`$ seeks behavior to
preserve or strengthen; $`A_{-}`$ seeks an evidenced failure and
supported recovery. Each analysis emits a core finding, up to two
reusable lessons, and at most one script suggestion for a repeated
deterministic operation:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{F}_{i}=\{f_{ij}\}_{j=1}^{m_{i}},\qquad 1\leq m_{i}\leq 4,\quad\mathcal{F}=\bigcup_{i=1}^{N_{t}}\mathcal{F}_{i}.
``` |  | (6) |

Each candidate carries exact trace-line provenance. The analyzer
separates observed evidence from reusable generalization; it does not
reconstruct unavailable ground-truth answers. The output $`\mathcal{F}`$
contains candidate semantic gradients; the next stage determines which
are worth retaining and what function each should serve.

### G.2 Retention and Attribution Rules

Consolidation maps the semantic gradients $`\mathcal{F}`$ to
component-specific update evidence
$`\{\mathcal{F}_{k}\}_{k\in\mathcal{K}}`$. The distinction between
knowledge structures and control processes motivates separating a
finding’s content from its execution role ([Atkinson and Shiffrin,
1968](#bib.bib27)). Evidence for dissociable forms of knowing further
motivates specialized maintenance ([Cohen and Squire,
1980](#bib.bib28)). CDSE instantiates these principles through a
retention gate followed by functional role attribution.

#### Retention gate.

The router first tests whether a candidate is supported, actionable,
reusable, and likely to change execution. It drops generic advice,
unsupported diagnoses, sample-specific answers, and redundant core
analyses already covered by the extracted lessons. For failures,
dropping a redundant core requires the lessons to preserve both the
diagnosis and the recovery. Writing the gate as $`r(f)\in\{0,1\}`$, its
output is $`\mathcal{F}^{\mathrm{keep}}=\{f\in\mathcal{F}:r(f)=1\}`$.
Only retained gradients proceed to attribution.

#### Functional role attribution.

For each retained gradient, the router identifies a primary component
and at most one secondary component. The set $`\rho(f)`$ records
membership in these targets, with primary status stored separately:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\rho(f)`$ | $`\displaystyle\subseteq\mathcal{K},\quad 1\leq|\rho(f)|\leq 2,`$ |  | (7) |
|  | $`\displaystyle\mathcal{F}_{k}`$ | $`\displaystyle=\{f\in\mathcal{F}^{\mathrm{keep}}:k\in\rho(f)\}.`$ |  |  |

A secondary component is included only when the same evidence has
substantial value under another functional responsibility. Meta receives
task-wide control changes; Experience receives heuristics activated by
identifiable local conditions. Tool receives operational guidance whose
validity depends on a named tool or capability; Script receives
proposals for deterministic, testable procedures or their execution
contracts. For example, checking units before comparing values is
contextual experience, whereas a restriction specific to a spreadsheet
library belongs to Tool. A repeatable transformation with explicit
inputs and tests can instead become a Script proposal. The router
neither rewrites the findings nor generates skill content, preserving
the distinction between evidence, ownership, and the subsequent update.

### G.3 Component Maintenance and Validation

Once ownership is established, each component evolves through its own
operator:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{\mathcal{B}}^{(t+1)}_{k}=U_{k}\!\left(\mathcal{B}^{(t)}_{k},\mathcal{F}_{k}\right),\qquad k\in\mathcal{K}.
``` |  | (8) |

Each $`U_{k}`$ produces a component-level candidate. The full operator
$`\mathcal{U}`$ subsequently coordinates and validates these candidates
before returning the next skill state. Specialized maintenance followed
by integration reflects the cognitive principle that differentiated
functions can remain coordinated ([Miyake et al., 2000](#bib.bib29)).

#### Meta and Experience: consolidating behavioral rules.

Both components store ordered atomic rules with stable identifiers. A
finding aligns with at most two existing rules as reinforcing,
extending, or correcting the same knowledge unit; it is split only into
independently actionable parts. Evidence for one rule is aggregated into
one revision, while unaffected rules are preserved. Unaligned findings
with compatible triggers, actions, scope, and constraints induce new
rules, with proposals reconciled across batches. When capacity is
exceeded, the updater shortens rules, merges genuine redundancy, and
finally removes low-value rules. Meta applies this process to task-level
control, whereas Experience requires a local activation condition. Thus,
shared rule machinery maintains distinct behavioral responsibilities.

#### Tool: maintaining capability-grounded knowledge.

Tool organizes operational rules within stable capability categories.
Findings first align with an existing tool or category; unmatched
category proposals are reconciled across batches. Rule alignment,
revision, and induction then occur within each category. Local capacity
control prevents frequently encountered tools from displacing knowledge
about other capabilities.

#### Script: turning suitable feedback into verified procedures.

Script findings first align with existing executable components.
Residual proposals pass a worthiness gate requiring repeatable
deterministic behavior, explicit I/O and error contracts, available
inputs, feasible synthetic tests, and material savings over one-off tool
use. Compatible proposals are grouped; others are deferred. Each work
item selects a documentation update, local modification, replacement,
creation, or deferral. Implementations stay within allocated paths,
declare dependencies, and pass self-tests. An independent verifier then
checks the assembled Script component in a clean environment using
component and full-suite tests. One bounded repair is allowed;
unverified code is withheld. This branch gives procedural changes an
executable acceptance contract.

#### Cross-component coordination.

Component updates produce a candidate skill state
$`\widehat{\mathcal{B}}^{(t+1)}`$. A coordinator $`C`$ reads all four
components and makes minimal edits to resolve concrete conflicts,
duplication, ownership ambiguity, and documentation mismatches. Script
artifacts remain authoritative. A complete Meta, Experience, or Tool
duplicate can be removed when its meaning survives in the appropriate
component; partial overlap is clarified. The coordinator cannot
introduce, renumber, or reorder rules, change Tool category membership,
or alter Script entries or executables. A validator compares the
candidate with its input snapshot and confines changes to the four
component specifications, preserving the previously verified programs.

#### Adaptive invocation and publication.

A description rewriter $`D`$ derives each component’s scope, timing, and
expected benefit from the coordinated content. Only the descriptions
visible before component loading may change; a validator requires
well-formed, distinct descriptions and byte-identical remaining content
and artifacts. Successful coordination and description validation
produce $`\mathcal{B}^{(t+1)}=D(C(\widehat{\mathcal{B}}^{(t+1)}))`$;
$`\mathcal{U}`$ is a partial operator, undefined when either stage fails
validation, in which case no updated state is published. These checks
enforce edit contracts, while task performance is assessed separately in
our experiments. For execution history $`h_{\ell}`$ at step $`\ell`$,
write the agent’s invocation choice as

|  |  |  |  |
|----|----|----|----|
|  |
``` math
I_{\ell}=\operatorname{Select}_{\pi_{\theta}}\!\left(h_{\ell},\{d_{k}^{(t+1)}\}_{k\in\mathcal{K}}\right)\subseteq\mathcal{K},
``` |  | (9) |

where $`d_{k}^{(t+1)}`$ is the revised description of component $`k`$
and $`I_{\ell}`$ contains the components selected for loading at that
step. Selection uses the agent’s ordinary invocation mechanism. As the
task progresses, different components become relevant; their use changes
agent behavior and supplies execution evidence for subsequent skill
evolution.

### H.3 Scoring Rules and Failure Handling

Evaluation depends on the task output: OfficeQA and SealQA score final
answers, SpreadsheetBench2 scores generated workbooks, LiveMathBench
scores selected answer labels, SWE-Pro scores executable test outcomes,
and AutomationBench scores the final environment state. The following
rules specify the reported success rates and distinguish them from
auxiliary partial-credit scores.

#### OfficeQA.

Predicted and reference answers undergo numeric extraction and
normalization, including magnitude units, signs, and thousands
separators. Numeric answers are compared at relative-error tolerances
$`\mathcal{T}=\{0,0.01,0.025,0.05,0.1\}`$, yielding

|  |  |  |
|----|----|----|
|  |
``` math
s=\frac{\sum_{t\in\mathcal{T}}w_{t}\,\mathbf{1}[\text{match at }t]}{\sum_{t\in\mathcal{T}}w_{t}},\qquad w_{t}=\frac{1}{1+20t}.
``` |  |

A match also requires the reference’s nonnumeric text to occur in the
prediction. For a reference containing multiple numbers, every number
must match. Integers from 1900 to 2100 are treated as year candidates
and excluded from numeric matching unless the reference itself is a
year. Purely textual answers use normalized substring or exact matching.
Empty answers receive zero and count as failures in the reported success
rate. Strict success requires $`s\geq 0.8`$; the continuous mean score
is an auxiliary diagnostic. In the Codex evaluation, timeouts and
crashes may be retried at most twice. In Claude Code, reaching the
60-turn limit is counted as a failure without retry.

#### SpreadsheetBench2.

Only the hidden answer regions of the workbook are scored. Comparing the
input workbook with the reference partitions these regions into
unchanged (regression) cells and cells requiring modification. The
output is evaluated separately on both groups. A task succeeds only when
both accuracies are 1.0, after regression accuracy of at least 0.998 is
rounded to 1.0; no partial credit contributes to the reported task
success rate. Numeric cells allow 1% relative error, with absolute
tolerance 0.01 when either value is zero. Numeric strings are parsed and
rounded to two decimal places, and dates are converted to Excel serial
values. Formula comparisons ignore case and absolute-reference markers.
Array formulas use their formula text; recognized financial placeholders
are normalized, as are blank cells and zero where specified by the
evaluator. Excel error values trigger a fallback to formula-text
comparison. Missing outputs fail the task; missing sheets or corrupted
files invalidate the affected scoring regions.

#### SealQA.

A shared offline judge labels each answer Correct, Incorrect, or Not
Attempted; only Correct receives one point. The answer must contain the
reference’s essential information without contradictory claims or
internal inconsistency. Differences in wording, punctuation,
capitalization, and contextually redundant information are ignored.
Uncertain phrasing is allowed when the required information is complete
and consistent; an incomplete or unattempted answer receives zero. All
evaluated models, harnesses, and methods use the same few-shot judging
template and the deepseek-v4-flash-huawei judge with temperature 0 and a
2,048-token output limit. Judging is performed after trajectories are
saved.

#### LiveMathBench.

Our multiple-choice evaluation uses a deterministic scorer. It extracts
the last ANSWER: declaration containing a letter from A to E and
reverses the deterministic option shuffle before comparing with the
reference label. Only the correct option receives one point. The
designated weaker-true option, other incorrect options, missing answer
declarations, exhausted turn budgets, and unresolved execution errors
all receive zero. No language-model judge is used.

#### SWE-Pro.

An instance is resolved only if all tests in both the FAIL_TO_PASS and
PASS_TO_PASS sets pass after the agent’s changes. This binary criterion
requires the intended fix while preserving previously passing behavior;
partial test coverage does not count as task success.

#### AutomationBench.

Rubric assertions evaluate the final world state rather than the agent’s
answer text. The reported metric is binary task completion: every scored
assertion must pass. The fraction of passing assertions provides
auxiliary partial credit. Assertions already satisfied initially and
still satisfied at the end are excluded to avoid rewarding inaction;
initially satisfied assertions that the agent breaks remain failures.
Tasks whose correct behavior is inaction can explicitly retain their
negative assertions. Negative assertions check that prohibited actions
do not occur, and checks marked as unscored or explicitly excluded do
not contribute to the metric.

## Appendix I System Prompt for Gradient Consolidation

This appendix reproduces the system prompt for *Cognition-Guided
Gradient Consolidation*, the second stage of CDSE
(Section [3.3](#S3.SS3 "3.3 Cognition-Guided Gradient Consolidation ‣ 3 Cognitive Differentiation in Skill Evolution ‣ From Trajectories to Differentiated Skills: Cognitive Differentiation for Self-Improving Agents")).
The remaining prompts and implementation code are provided in the
*Software* supplementary material.

You are the routing classifier in a four-skill evolution pipeline. You
receive exactly one completed trajectory-analysis JSON. The original
trajectory, other analyses, existing skills, and external resources are
unavailable and must not be reconstructed. Classify only the supplied
findings; do not rewrite, merge, split, summarize, or create findings.
\## Targets  - \`meta\`: task-level control knowledge, including
priorities, evidence-access boundaries, preservation of user
constraints, phase transitions, search or turn budgets, stopping and
finalization, resolution of known contradictions, and prevention of
answer leakage or unsupported answers.  - \`experience\`:
context-dependent heuristics, anti-patterns, verification practices,
interpretation risks, and recovery tied to a particular data shape,
source situation, or calculation context.  - \`tool\`: actionable
knowledge about using an existing named environment tool, including
selection, sequencing, output interpretation, permissions, limitations,
misuse, inefficient repetition, and recovery.  - \`script\`: a proposed
reusable deterministic operation with defined inputs and outputs that
can be implemented and automatically tested. \## Decision order Evaluate
each finding in this order:  1. Does it control whether the task may
proceed, return to an earlier phase, stop, or finalize? Consider
\`meta\`. 2. Does it give actionable guidance about an existing named
environment tool? Consider \`tool\`. 3. Does it propose a new
deterministic executable capability? Consider \`script\`. 4. Is its
remaining value a local heuristic, anti-pattern, verification practice,
or recovery? Consider \`experience\`. This order guides evaluation but
does not restrict target combinations. \## Boundaries Route by reusable
function, not by words that merely appear in the finding. For \`meta\`,
judge semantic scope rather than observed frequency. A task-level rule
may be routed to \`meta\` from one trajectory; cross-trajectory
frequency and final admission are evaluated later. Do not use
\`experience\` as the default for every useful lesson. Use it for
knowledge that remains local after checking \`meta\`, \`tool\`, and
\`script\`. For \`tool\`, require an explicit named tool and actionable
guidance about how it should or should not be used. Bash, Read, Write,
Edit, Glob, Grep, and other named environment tools count. Merely using
or mentioning a tool is insufficient. Documents, datasets, source
tables, file formats, benchmarks, and domain-specific data sources are
not tools. Prefer \`tool\` when the central rule changes if the named
tool is replaced; prefer \`experience\` when the rule remains fully
tool-independent. A concrete named-tool sequence, usage boundary,
output-handling rule, or recovery has meaningful \`tool\` value even
when it also supports a broader verification or efficiency practice. Use
\`tool\` for guidance about an existing capability and \`script\` for a
new maintained executable capability. A shell snippet or generic
calculation is not a tool finding merely because Bash can run it. For
\`script\`, require a deterministic and testable operation. Do not route
semantic judgment, source-authority selection, business-definition
choice, general planning, or “find the correct answer” capabilities to
\`script\`. \## Keep or drop Drop findings that are generic,
unsupported, purely sample-specific, or unlikely to change future
behavior. Apply the core-specific redundancy rules below. A valid
success may contribute positive behavior. A fragile success should
contribute only supported risks or improvements. An invalid success may
contribute an anti-pattern or recovery, but not a positive pattern. Drop
unknown-success claims whose causal basis is unverified. Drop a
\`success_analysis\` core when its reusable behavior, risk, or
improvement is already captured by \`reusable_lessons\`. A
\`failure_analysis\` core may remain useful because it combines cause
and recovery. Keep it when its failure mechanism, task-control
implication, recovery, or routing value adds material information not
fully preserved by the lessons. Drop it as redundant only when both its
reusable cause and recovery are fully covered; partial overlap is
insufficient. The drop reason must state that both are covered. Do not
keep sample-specific detail alone. \## Output behavior A kept finding
must have one or at most two ordered targets. The first is primary. Use
two targets when a finding has both a concrete tool-specific rule and a
meaningful tool-independent lesson; order them by primary value.
Otherwise add a secondary target only when it has substantial
independent value. Do not generate skill content or reason about
downstream wording. Keep each routing reason to one concise sentence.
Return only JSON matching the supplied schema.
````
