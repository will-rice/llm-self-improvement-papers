# Toward Executable Multi-framework Front-end Code Generation with Self-Correction

Linxiao Li    Haoran Ma    Chenyue Wang Affiliation: The University of
Sydney    Jiaye Lin Affiliation: Meituan    Haochen Sui
Affiliation: University of Michigan    Jiechao Gao Affiliation: Harvard
University Affiliation: Stanford University

###### Abstract

Generating codes from UI screenshots has recently benefited from MLLMs,
yet existing methods centered on HTML targets and transfer poorly to
multi-frameworks such as React, Vue, and Angular. However, unlike HTML,
which does not entail compilation issues, generating executable code in
multi-framework settings is more challenging due to framework-specific
differences in syntax and failure modes, as well as the need to maintain
global consistency across files. To address this problem, we study
executable multi-framework front-end code generation and propose
MESCoder, a tree-structured self-corrective generation framework. Our
method first extracts a structural scaffold from the screenshot and then
constructs sub-trees and assembly relations step by step, transforming
large project generation into a sequence of localized decisions. On top
of this scaffold, we introduce a unified Project Agent that continuously
revises its own partial project under runtime sandbox feedback and
dynamically chooses between local repair and cluster level repair. For
training, we adopt a two-stage strategy that first initializes the
policy offline to learn basic multi-framework generation and repair
priors, and then refines it with online reinforcement learning to
optimize long horizon executability and final page quality. The
resulting framework models multi-framework executability as a
conditioned project state transition process and improves the stability
and quality of complex front end generation through self correction.
Experiments show that our method improves executability, while narrowing
the visual-fidelity gap to HTML-based generation. Codes are available
at: [Link](https://github.com/leo-lilinxiao/MESCoder).

## 1 Introduction

Recent advances in MLLMs have substantially improved the ability to
generate front-end code directly from UI screenshots
 \[[27](#bib.bib27), [16](#bib.bib16), [34](#bib.bib34),
[31](#bib.bib31)\]. This task requires models to jointly perform visual
understanding, structural abstraction, and front-end implementation. As
a result, generation quality depends not only on recognizing local UI
elements, but also on whether the model can transform hierarchical
layout and spatial organization into a coherent implementation
 \[[30](#bib.bib30), [20](#bib.bib20)\].

Existing work has made clear progress on this problem, yet the dominant
formulation remains largely HTML-centered. Recent efforts have scaled
HTML-screenshot training corpora \[[16](#bib.bib16), [34](#bib.bib34),
[9](#bib.bib9)\] and established benchmarks for measuring how faithfully
a generated page reproduces its reference \[[27](#bib.bib27)\]. On the
method side, divide-and-conquer decomposition \[[29](#bib.bib29)\],
layout-guided prompting \[[30](#bib.bib30)\], and structure-aware
fine-tuning \[[20](#bib.bib20)\] further improve element recall and
spatial fidelity. Common to all of these efforts, however, is a shared
assumption: the generation target is a single self-contained HTML file
that renders without compilation and without cross-file reasoning—an
assumption that does not hold in real front-end development, where
production interfaces are assembled from multiple files within
framework-specific project structures and become visible only after the
entire project successfully compiles and runs.

However, extending screenshot-to-code generation from HTML to
multi-frameworks such as React, Vue, and Angular is not merely a matter
of changing prompts or rewriting syntax. Unlike HTML, multi-framework
front-end generation requires models to produce an executable project
within the framework-specific program space, where correctness depends
not only on surface syntax but also on component boundaries, cross-file
dependencies, parent-child assembly, and runtime consistency. Existing
analysis shows that straightforward prompt transfer across frameworks
causes a substantial drop in compilation success and is accompanied by
highly framework-specific error modes \[[33](#bib.bib33)\]. In stricter
frameworks, failures are often no longer limited to local token- or
template-level mistakes, but instead emerge as engineering-level
inconsistencies involving import/export relations, bindings, assembly,
and project-level coherence. Meanwhile, one-shot screenshot-to-project
generation entangles local implementation, global composition, and
framework constraints in a single decoding process, making intermediate
errors difficult to localize and even harder to correct reliably.

Figure 1: Compilation failure rates of six state-of-the-art MLLMs under
one-shot generation on React, Vue, and Angular. Failures are decomposed
into local errors and cluster errors.

To address these challenges, we study executable multi-framework
front-end code generation and propose MESCoder, a tree-structured
self-corrective generation framework. Our key idea is to first extract a
structural scaffold from the input screenshot, converting large project
generation into a sequence of localized subtree expansion and assembly
decisions, and then introduce a unified Project Agent that continuously
revises its own partial project under runtime sandbox feedback. Rather
than treating correction as a post-hoc repair stage, MESCoder integrates
self-correction into the generation loop itself, enabling the model to
dynamically decide whether to continue construction, perform local
repair, or escalate to cluster-level repair when local edits become
insufficient. To stably learn this behavior, we further adopt a
two-stage training strategy: we first initialize the policy offline to
acquire basic multi-framework generation and repair priors, and then
refine it with online reinforcement learning to optimize long-horizon
executability and final page quality. In this way, we formulate
multi-framework front-end generation as a framework-conditioned project
state transition process, with self-correction serving as the key
mechanism for improving cross-framework executability and the stability
of complex front-end generation.

Our contributions are summarized as follows:

- •
  We propose MESCoder, a tree-structured self-corrective generation
  framework that decomposes project construction into localized subtree
  and assembly decisions and equips a unified Project Agent with
  runtime-feedback-driven self-correction.
- •
  We develop a two-stage training strategy that combines offline policy
  initialization with online reinforcement learning, enabling to
  optimize long-horizon executability and generation quality.
- •
  Extensive experiments demonstrate that MESCoder improves code
  executability across multiple frameworks while narrowing visual
  similarity comparable to HTML-based generation.

## 2 Related Work

### 2.1 WebUI Code Generation

Generating front-end code from visual inputs has been studied
extensively. Early methods used classical vision pipelines to
reverse-engineer UI elements \[[23](#bib.bib23), [22](#bib.bib22)\],
while large-scale datasets such as Rico \[[6](#bib.bib6)\] later enabled
data-driven approaches. Beltramelli \[[1](#bib.bib1)\] proposed
pix2code, a CNN-LSTM model that produces code tokens from GUI
screenshots, and Chen et al. \[[2](#bib.bib2)\] concurrently introduced
a neural machine translator for GUI skeletons. The emergence of MLLMs
has shifted this line of work toward fine-tuning on screenshot-code
pairs at scale. WebSight \[[16](#bib.bib16)\] provides two million
synthetic HTML–screenshot pairs, with parallel efforts such as
Sketch2Code \[[19](#bib.bib19)\] extending inputs to hand-drawn
sketches. Design2Code \[[27](#bib.bib27)\] introduces the first
real-world benchmark of 484 webpages with fine-grained visual and
structural metrics, complemented by IW-Bench \[[11](#bib.bib11)\] with
DOM-based element and layout accuracy. Follow-up work scales training
data to over one \[[34](#bib.bib34)\] and 2.56
million \[[9](#bib.bib9)\] instances, introducing TreeBLEU for
structural recall, while Interaction2Code \[[32](#bib.bib32)\] extends
evaluation to dynamic interactions and DesignBench \[[33](#bib.bib33)\]
to React, Vue, and Angular. On the method side, recent approaches
improve generation through divide-and-conquer
decomposition \[[29](#bib.bib29)\], hierarchical
generation \[[10](#bib.bib10)\], modular multi-agent
pipelines \[[14](#bib.bib14)\], layout-guided
prompting \[[30](#bib.bib30)\], and structure-aware
fine-tuning \[[20](#bib.bib20)\]. Closer to our work,
MRWeb \[[28](#bib.bib28)\] extends generation beyond single pages via
explicit resource lists, and DesignCoder \[[4](#bib.bib4)\] couples
hierarchical generation with self-correction. Despite this progress,
existing work remains _HTML-centered_, targeting self-contained pages
that render without compilation. Multi-framework generation for React,
Vue, and Angular instead requires producing multi-file executable
projects whose correctness depends on whether the project as a whole
compiles and runs—a setting that prior methods do not address.

### 2.2 Self-correction in Code Generation

Self-correction has emerged as a central capability for code generation,
allowing models to revise their own outputs based on feedback rather
than committing to a single one-shot prediction \[[24](#bib.bib24)\].
Early prompting-based methods established the basic loop:
Self-Refine \[[21](#bib.bib21)\] iteratively rewrites a program from
natural-language critiques produced by the same model,
Reflexion \[[26](#bib.bib26)\] adds an episodic memory of verbal
reflections distilled from environment feedback, and
Self-Debug \[[3](#bib.bib3)\] grounds the loop in execution traces by
teaching LLMs rubber-duck-style debugging. However, intrinsic
self-correction without external signals has been shown to plateau or
even degrade reasoning quality \[[12](#bib.bib12)\], motivating a shift
toward training-based correction with executable feedback.
CodeRL \[[17](#bib.bib17)\] and StepCoder \[[7](#bib.bib7)\] optimize
generation policies against unit-test or compiler rewards, while
RLEF \[[8](#bib.bib8)\] reinforces multi-turn LLM agents directly with
execution feedback inside the rollout. SCoRe \[[15](#bib.bib15)\]
introduces a two-stage RL recipe to counter behavior collapse and
distribution shift in self-correction, and
$`\mu`$CODE \[[13](#bib.bib13)\] casts multi-turn code generation as a
single-step decision problem with verifier-guided rewards. For small
models, CoCoS \[[5](#bib.bib5)\] aligns reflective revision with
parameter-efficient online RL. On the structural side,
CodeTree \[[18](#bib.bib18)\] performs agent-guided tree search over
generation and refinement, and AlphaCodium \[[25](#bib.bib25)\] reframes
generation as a test-driven flow with iterative public-test refinement,
while DesignCoder \[[4](#bib.bib4)\] couples hierarchical UI generation
with a self-correction loop. Despite this progress, existing
self-correction methods remain _single-file-centric_, treating each
program as a self-contained unit revised in isolation. Multi-framework
front-end projects, in contrast, demand correction over a graph of files
whose compilability depends on cross-file imports, bindings, and
component assembly—a setting where local edits often cannot restore
project-level coherence and that prior methods do not address.

### 3.1 Overview

Given a webpage screenshot $`x`$ and a target front-end framework
$`f\in\{\text{React},\text{Vue},\text{ Angular}\}`$, our goal is to
generate a complete front-end project $`P_{T}`$ that is executable under
$`f`$ and visually consistent with $`x`$. Fig
[2](#S3.F2 "Figure 2 ‣ 3 Methodology ‣ Toward Executable Multi-framework Front-end Code Generation with Self-Correction")
illustrates the learning process of MESCoder, which contains four
components: A fixed scaffold pre-processor extracts a layout tree and a
task queue from the screenshot. A policy module selects a high-level
action according to the current project state. An LLM executor performs
the selected action by generating or patching code. A runtime sandbox
executes the intermediate project, produces diagnostic feedback, and
computes executability-oriented rewards. At step $`t`$, the interaction
is written as

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
m_{t}\sim\pi_{\phi}(\cdot\mid s_{t}),\qquad\Delta_{t}=\mathrm{LLM}(s_{t},m_{t}),\qquad(P_{t+1},d_{t+1},...)=\mathcal{E}(P_{t},\Delta_{t},f),
``` |  | (1) |

where $`s_{t}`$ is the current state, $`m_{t}`$ is the high-level
action, $`\Delta_{t}`$ is the concrete code edit, $`d_{t+1}`$ is the
diagnostic summary, and $`\mathcal{E}`$ denotes the framework-aware
execution environment.

The learning process has two stages. First, we initialize the policy
offline using state-action data. Second, we refine the policy online
with reinforcement learning under sandbox feedback. In the main setting,
the LLM executor is kept fixed, and both offline initialization and
online reinforcement learning optimize only the action policy and its
value estimator.

### 3.2 Tree-Structured Self-Corrective Generation

Front-end pages are naturally hierarchical. A full page is composed of
regions, containers, repeated blocks, and local components, and these
units must eventually be assembled into a coherent project. Directly
generating the entire project in one pass makes intermediate errors
difficult to localize and repair. We therefore first extract a scaffold
from the screenshot $`\mathcal{S}(x)=\{T,U,Q\}`$, where $`T`$ is a
layout tree, $`U`$ is a content slot table, and
$`Q=\{\tau_{1},\tau_{2},\ldots,\tau_{N}\}`$ is a task queue derived from
the tree. The scaffold is fixed and not trained. It provides a
structural interface that localizes generation and correction decisions.

At interaction step $`t`$, the current task pointer is $`i_{t}`$, and
the active task is $`q_{t}=\tau_{i_{t}}\in Q`$. The agent observes

|     |                                              |     |     |
|-----|----------------------------------------------|-----|-----|
|     |
       ``` math
       s_{t}=\{x,f,q_{t},P_{t},d_{t},h_{t},b_{t}\},
       ```                                           |     | (2) |

where $`P_{t}`$ is the current partial project, $`d_{t}`$ is the
diagnostic summary returned by the sandbox, $`h_{t}`$ stores recent
action-feedback history, and $`b_{t}`$ is the remaining budget. The
history term captures whether recent actions have improved the project,
which is important for identifying repeated local failures and deciding
whether broader correction is needed.

The policy selects one action from

|  |  |  |  |
|----|----|----|----|
|  |
``` math
m_{t}\in\{\textsc{Continue},\textsc{PatchLocal},\textsc{PatchCluster},\textsc{Assemble},\textsc{Finish}\}.
``` |  | (3) |

Continue advances the current task when the partial project is
sufficiently healthy. PatchLocal invokes a local repair over a small
scope. PatchCluster invokes a broader repair over a small dependency or
assembly cluster. Assemble integrates completed child units into the
current parent node. Finish terminates the episode when the project is
complete and executable. This action set separates forward construction
from self-correction. Continue and Assemble construct the project, while
PatchLocal and PatchCluster correct intermediate failures. The policy
therefore learns not only whether to repair, but also the appropriate
scope of repair.

The policy is a lightweight neural controller:

|     |                                                                |     |     |
|-----|----------------------------------------------------------------|-----|-----|
|     |
       ``` math
       \pi_{\phi}(m_{t}\mid s_{t})=\mathrm{softmax}(g_{\phi}(z_{t})),
       ```                                                             |     | (4) |

where $`z_{t}`$ is a structured encoding of $`s_{t}`$ and $`g_{\phi}`$
is the actor network. After an action is selected, the LLM executor
generates the concrete code edit:

|     |                                       |     |     |
|-----|---------------------------------------|-----|-----|
|     |
       ``` math
       \Delta_{t}=\mathrm{LLM}(s_{t},m_{t}).
       ```                                    |     | (5) |

The executor is action-conditioned. Under PatchLocal, it is instructed
to modify only a local scope. Under PatchCluster, it may edit several
related files or components. Thus, the LLM handles code realization,
while the policy handles self-corrective control.

### 3.3 Runtime Sandbox and Executability Feedback

The runtime sandbox defines the execution environment. Given the current
project $`P_{t}`$, an executor edit $`\Delta_{t}`$, the selected action
$`m_{t}`$, and the target framework $`f`$, the sandbox applies the edit,
runs framework-specific checks, and returns the updated project together
with compact execution feedback:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
(P_{t+1},d_{t+1},e_{t},e_{t+1},u_{t})=\mathcal{E}(P_{t},\Delta_{t},f).
``` |  | (6) |

Here, $`\mathcal{E}`$ only applies and verifies the edit. The diagnostic
summary $`d_{t+1}`$ is a compact representation of execution feedback.
It records the dominant diagnostic family and the affected files or
components, and is used as part of the next state rather than as a
separate handcrafted reward term. The quantities $`e_{t}`$ and
$`e_{t+1}`$ denote the numbers of sandbox error clusters before and
after applying the edit, measured under the same action-relevant
verification scope $`\Omega_{t}=\Omega(s_{t},m_{t})`$. The scope depends
on the selected action: local repair is verified within the local edit
scope, cluster repair within the related file cluster, assembly within
the parent-child assembly scope, and Finish on the full project. This
avoids penalizing intermediate partial projects for missing future tasks
that have not yet been generated. The binary signal $`u_{t}\in\{0,1\}`$
indicates whether the current action successfully commits a new task.
For example, $`u_{t}=1`$ if a Continue action completes the current
subtree, or if an Assemble action successfully connects a completed
child unit to its parent. Otherwise, $`u_{t}=0`$. Since intermediate
partial projects may not be fully renderable, visual quality is not used
as a dense step-level signal. We compute a terminal quality score
$`Q_{T}`$ only after a final renderable project is produced.

### 3.4 Two-Stage Policy Learning

#### Offline policy initialization.

The offline stage initializes the action policy before online
reinforcement learning. Its goal is not to train the LLM executor or to
teach code generation. Instead, it provides a reasonable action prior
for the policy module $`\pi_{\phi}(m\mid s)`$.

For each clean executable project $`P^{\star}`$, we construct normal
project-construction states by replaying the tree-guided construction
process. These states provide supervision for non-repair actions. If the
current node is unfinished and no critical diagnostic is present, the
label is Continue. If a subtree is completed and should be integrated
into its parent, the label is Assemble. If the root project is complete
and strict checks pass, the label is Finish. Thus, clean replay provides
examples for the forward construction behavior. To initialize repair
decisions, we generate corrupted states from clean projects. Given
$`P^{\star}`$, an automatic corruption operator produces

|     |                                   |     |     |
|-----|-----------------------------------|-----|-----|
|     |
       ``` math
       \tilde{P}=\mathcal{C}(P^{\star}).
       ```                                |     | (7) |

For a corrupted state $`s_{t}`$, we define a candidate repair set
$`\mathcal{M}(s_{t})`$, typically containing PatchLocal and
PatchCluster. For each candidate action $`m\in\mathcal{M}(s_{t})`$, the
LLM executor is called $`K`$ times to generate candidate edits:

|     |                                                         |     |     |
|-----|---------------------------------------------------------|-----|-----|
|     |
       ``` math
       \Delta_{m,k}=\mathrm{LLM}(s_{t},m),\qquad k=1,\ldots,K,
       ```                                                      |     | (8) |

where $`K`$ is the number of executor samples used only for offline
outcome estimation; it reduces labeling noise caused by stochastic LLM
edits. Each candidate edit is evaluated by the sandbox. Let

|     |                                                  |     |     |
|-----|--------------------------------------------------|-----|-----|
|     |
       ``` math
       \hat{R}(s_{t},m)=\max_{k}R(s_{t},m,\Delta_{m,k})
       ```                                               |     | (9) |

be the best outcome score obtained under action $`m`$. The offline
repair label is then

|  |  |  |  |
|----|----|----|----|
|  |
``` math
m_{t}^{\star}=\arg\max_{m\in\mathcal{M}(s_{t})}\hat{R}(s_{t},m).
``` |  | (10) |

This result-driven labeling procedure avoids reducing offline learning
to a predefined error-action rule. It assigns action labels according to
observed outcomes, so the same diagnostic family may still lead to
different repair scopes under different contexts. The policy is
initialized by minimizing

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{L}_{\mathrm{off}}=-\sum_{(s_{t},m_{t}^{\star})\in\mathcal{D}_{\mathrm{off}}}\log\pi_{\phi}(m_{t}^{\star}\mid s_{t}).
``` |  | (11) |

The resulting policy $`\pi_{\phi_{0}}`$ provides an action prior for
subsequent online learning.

#### Online reinforcement learning.

Offline initialization provides a policy prior, but executable project
generation remains a long-horizon decision problem. During real
generation, actions interact with LLM-generated edits,
framework-specific constraints, and accumulated project states. Online
reinforcement learning further optimizes the policy under actual sandbox
feedback.

Starting from $`\pi_{\phi_{0}}`$, the agent interacts with the
environment and collects trajectories $`(s_{t},m_{t},r_{t},s_{t+1}).`$
The online step reward is constructed from the sandbox feedback:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
r_{t}^{\mathrm{step}}=\alpha(e_{t}-e_{t+1})+\beta u_{t}-\gamma c_{t}.
``` |  | (12) |

The first term rewards error reduction in the action-relevant
verification scope. The second term rewards successful task commitment.
The third term penalizes expensive or invalid actions. The cost
$`c_{t}`$ depends on the selected action, edit size, verification scope
size, and whether the edit can be validly applied. At the end of an
episode, the agent receives

|  |  |  |  |
|----|----|----|----|
|  |
``` math
R_{\mathrm{final}}=\begin{cases}r_{\mathrm{pass}}+\mu Q_{T},&\text{SUCCESS},\\
r_{\mathrm{partial}},&m_{T}=\text{FINISH and ERROR},\\
0,&\text{otherwise}.\end{cases}
``` |  | (13) |

The complete optimization objective is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
J(\phi)=\mathbb{E}_{\tau\sim\pi_{\phi}}\left[\sum_{t=0}^{T-1}r_{t}^{\mathrm{step}}+R_{\mathrm{final}}\right].
``` |  | (14) |

We optimize the policy using an actor-critic formulation. The actor is
$`\pi_{\phi}(m\mid s)`$, while the critic estimates the state value
$`V_{\psi}(s)`$. In our implementation, we use PPO-style clipped policy
optimization for stability. The actor and critic parameters, $`\phi`$
and $`\psi`$, are updated during online learning, while the LLM executor
remains fixed in the main setting. This keeps reinforcement learning
focused on high-level self-corrective decision making rather than
token-level code generation.

## 4 Experiment

### 4.1 Experimental Setup

#### Benchmarks and Metrics.

We evaluate on DesignBench \[[33](#bib.bib33)\], the benchmark pairing
real-world webpage screenshots with ground-truth executable
multi-framework projects. Its *design generation* split contains 310
compilation-verified pages across React, Vue, and Angular. We stratify
these by framework and complexity, holding out 200 pages as the test set
and reserving the remaining 110 for training. We report CSR (Compilation
Success Rate), the fraction of projects passing strict compilation and
runtime verification, and CLIP \[[27](#bib.bib27)\], the visual
similarity to the reference image.

#### Training Data.

Our training corpus combines the 110 non-test DesignBench pages
(compilation-verified, multi-framework) with 2,000 projects sampled from
WebCode2M \[[9](#bib.bib9)\] (filtered, decomposed into multi-file
hierarchies, and deduplicated against the test set). All clean projects
are processed by a corruption pipeline $`\mathcal{C}`$
(Appendix [B](#A2 "Appendix B Offline Data Construction ‣ Toward Executable Multi-framework Front-end Code Generation with Self-Correction"))
that injects realistic LLM error modes across varying repair scopes,
yielding a comprehensive offline corpus of 27,430 state-action pairs.

#### Baselines.

We compare MESCoder against four baselines that span from direct
prompting to heuristic and learned self-correction: (1) One-Shot:
Generates the full multi-file project in a single LLM forward pass
without structural decomposition or post-hoc repair, serving as the
vanilla generation reference. (2) Rule Repair: Augments a scaffold-based
generation pipeline with hard-coded, heuristic fix templates for the 20
most frequent compilation errors. This represents state-of-the-art
non-learned execution repair. (3) RLEF (RL from Execution Feedback):
Keeps LLM executor frozen and trains an external controller using
feedback. The controller modulates the executor through generic
generation instructions, but does not use our action space. It serves as
a monolithic RL baseline for testing whether sandbox-feedback
optimization alone can match MESCoder. (4) Offline-Only: An ablation
baseline that uses our exact scaffold representation and MLP policy
trained exclusively on the offline demonstration corpus, omitting the
online PPO exploration stage.

### 4.3 Policy Learning and Behavior

We analyze how the two-stage training procedure shapes the policy’s
self-correction behavior across training dynamics and scope escalation.

#### Training dynamics and action shift.

Figure [3](#S4.F3 "Figure 3 ‣ Training dynamics and action shift. ‣ 4.3 Policy Learning and Behavior ‣ 4 Experiment ‣ Toward Executable Multi-framework Front-end Code Generation with Self-Correction")
illustrates training dynamics and the resulting action distribution
shift. The offline-initialized policy reaches a stable, high-CSR plateau
substantially faster than both random and rule-initialized baselines,
confirming that the behavior-cloning stage provides a meaningful action
prior that makes online RL tractable. The rule-initialized agent
converges more slowly and stabilizes at a lower final CSR, as rigid
heuristic rules cannot capture context-dependent scope decisions. On
*stagnated-cluster* states—where repeated local repair has yielded no
error reduction—the offline-only policy distributes probability nearly
equally between PatchLocal and PatchCluster; after online RL,
PatchCluster rises to a clear dominant position while PatchLocal drops
sharply. Crucially, the shift is selective: this suggests that RL
primarily increases cluster repair on states where local repair has
stagnated, confirming that RL has learned to escalate scope *when and
only when* local repair has demonstrably failed.

## 5 Conclusion

We presented MESCoder, a tree-structured self-corrective generation
framework that addresses the challenge of executable multi-framework
front-end code synthesis. By decomposing project construction into
scaffold-guided subtree expansions and equipping a unified Project Agent
with a learned policy for context-sensitive local and cluster-level
repair under sandbox execution feedback, MESCoder transforms
self-correction from a post-hoc step into an integral part of the
generation loop. Experiments across React, Vue, and Angular with six LLM
executors demonstrate consistent CSR improvements, most pronounced on
Angular, where cross-file dependency failures are prevalent, while
visual fidelity is preserved throughout.

## Appendix B Offline Data Construction

#### Clean project sources.

We use 110 DesignBench training pages plus 2,000 pages from WebCode2M.
The WebCode2M pages are filtered for compilation correctness, decomposed
into multi-file framework hierarchies, and deduplicated against the test
set.

#### Corruption operators.

The corruption pipeline $`\mathcal{C}`$ applies six operators, each
targeting a distinct error family, to generate realistic error-inducing
states from clean projects
(Table [5](#A2.T5 "Table 5 ‣ Corruption operators. ‣ Appendix B Offline Data Construction ‣ Toward Executable Multi-framework Front-end Code Generation with Self-Correction")):

| Operator | Target Family |  Description |
|----|----|----|
| $`\mathcal{C}_{\text{syn}}`$ | Syntax & Template |  Removes closing tags, introduces invalid JSX attribute syntax, or misbalances template braces. |
| $`\mathcal{C}_{\text{bind}}`$ | Local Binding |  Renames a prop or variable reference to an undefined name within a single component. |
| $`\mathcal{C}_{\text{cont}}`$ | Component Contract |  Changes a component’s exported interface without updating its parent call site. |
| $`\mathcal{C}_{\text{asm}}`$ | Assembly & Hierarchy |  Removes or misroutes an import connecting a child component to its parent. |
| $`\mathcal{C}_{\text{mod}}`$ | Module Dep. & Import |  Renames or removes an export without updating downstream import sites, producing missing-export or name-mismatch errors. |
| $`\mathcal{C}_{\text{fw}}`$ | Framework Specific |  Removes an Angular component from @NgModule, or introduces a Vue setup() hook incompatible with Options API. |

Table 5: Corruption operators used in offline data construction.

#### Result-driven repair labeling.

For each corrupted state, the repair label is assigned by calling the
LLM executor $`K{=}4`$ times per candidate action and selecting the
action that achieves the highest sandbox repair score. After filtering,
we retain 27,430 labeled pairs.

## Appendix C Implementation Details

The scaffold preprocessor uses a pretrained visual detector and
rule-based grouping to construct hierarchical layout trees. The
lightweight MLP policy encodes the multimodal state $`s_{t}`$ via frozen
encoders into a latent vector, then outputs an action distribution over
the hierarchical action space. We evaluate across six frozen LLM
executors: GPT-4o, Claude-3.7-Sonnet, Gemini-2.0-Flash, Qwen2.5-VL-72B,
Llama-3.2-90B, and Pixtral-124B. Experiments are run on 8$`\times`$A100
GPUs, and all results are averaged over three independent runs.

## Appendix G LLM Executor Prompt Templates

This appendix provides the complete prompt templates used for each
action category in the MESCoder executor interface. All prompts share a
common system preamble that establishes the task context; per-action
sections then specify the concrete instruction, the project context, and
the expected output format. Identical templates are used across all six
LLM executors; no executor-specific prompt engineering is applied.
Variables enclosed in $`\langle\rangle`$ are filled by the framework at
inference time.

### G.1 System Preamble (Shared Across All Actions)

The following system message is prepended to every LLM call:

> You are a senior front-end engineer specializing in
> $`\langle`$framework$`\rangle`$ (one of React, Vue, Angular). You are
> assisting an automated code-generation agent that constructs a
> multi-file $`\langle`$framework$`\rangle`$ project from a UI
> screenshot. The project is built incrementally: at each step you
> receive a partial project state, the current compilation errors (if
> any), and an action instruction. Your response must follow the
> structured output format exactly: produce only the requested code
> edits, with no surrounding prose, no markdown code fences outside the
> prescribed format, and no commentary. Each edit is a JSON object:
> {‘‘file’’: ‘‘\<path\>’’, ‘‘old’’: ‘‘\<old_content\>’’, ‘‘new’’:
> ‘‘\<new_content\>’’}. If you are generating a new file, set ‘‘old’’ to
> an empty string.

### G.2 Continuation Prompt (Continue Action)

The Continue action advances the current task when the partial project
is sufficiently healthy, generating code for the next scaffold node. The
prompt is structured as follows:

> \[TASK\] Generate the $`\langle`$framework$`\rangle`$ component for
> the UI element described below.
>
> \[SCAFFOLD NODE\]
> - Type: $`\langle`$node_type$`\rangle`$ (e.g., ‘‘Card’’, ‘‘NavBar’’,
> ‘‘DataTable’’)
> - Bounding box (normalized): $`\langle`$x_min, y_min, x_max,
> y_max$`\rangle`$
> - Tree depth: $`\langle`$depth$`\rangle`$
> - Children to generate later: $`\langle`$child_count$`\rangle`$
>
> \[CONTENT SLOTS\]
> $`\langle`$slot_table$`\rangle`$ (Each slot: {node_id, text_content,
> img_crop_description})
>
> \[SCREENSHOT DESCRIPTION\]
> $`\langle`$screenshot image or visual description appended
> here$`\rangle`$
>
> \[EXISTING PROJECT FILES\]
> $`\langle`$list of already-generated files with their current
> content$`\rangle`$
>
> \[INSTRUCTION\]
> Generate the file $`\langle`$target_filename$`\rangle`$ for this
> component. Implement the visual layout faithfully. Use only
> $`\langle`$framework$`\rangle`$-idiomatic patterns. Do not import any
> external UI libraries unless they are already present in package.json.
> Declare all props with correct TypeScript types.
>
> \[OUTPUT FORMAT\]
> {"file": "$`\langle`$target_filename$`\rangle`$", "old": "", "new":
> "\<complete file content\>"}

### G.3 Assembly Prompt (Assemble Action)

The Assemble action integrates completed child units into the current
parent node, resolving imports and type compatibility.

> \[TASK\] Assemble the parent component

## Appendix H Limitations

Our framework improves executable multi-framework front-end generation
through execution feedback and self-correction, but it still has several
limitations. First, the system depends on the quality of the scaffold
preprocessor and the runtime sandbox. Incorrect structure extraction or
incomplete framework-specific checks may mislead the policy and the LLM
executor. Second, although the policy learns high-level corrective
decisions, the actual code edits are still produced by the LLM executor;
when the executor repeatedly fails to generate valid patches, the policy
alone cannot fully recover the project. Third, online reinforcement
learning introduces additional computational cost due to repeated LLM
and sandbox calls, which may limit deployment in latency-sensitive
settings. Finally, our method focuses on syntactic, structural, and
build-time executability, while broader software engineering aspects
such as security, accessibility, maintainability, and long-term code
quality are not fully addressed.

## Appendix I Broader Impacts

This work may have positive societal impacts by reducing the cost of
front-end development, enabling faster prototyping, and making UI
implementation more accessible to designers, small teams, and developers
with limited framework expertise. By explicitly emphasizing executable
multi-framework projects, the method may also reduce debugging burden
and improve the reliability of AI-assisted software generation. At the
same time, the work has potential negative impacts. More capable
automated code generation could contribute to low-quality mass-produced
web interfaces, overreliance on generated code, or deployment of
projects whose security, accessibility, or privacy properties have not
been adequately reviewed. It may also affect demand for certain routine
front-end implementation tasks. Therefore, generated projects should be
treated as developer-assistance outputs rather than fully autonomous
production-ready systems, and should undergo human review, security
checks, and accessibility validation before deployment.
````
