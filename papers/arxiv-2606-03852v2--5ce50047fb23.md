###### Abstract

Large language models often generate code with bugs. Existing methods
revise such code using feedback signals such as test failures and
self-critiques, but these signals are too coarse-grained or too
high-level to tell the model where the code should be revised. We
present Flare, an iterative code generation framework whose lightweight
diagnostic model predicts line-level suspiciousness to guide code
refinement. Given the inherent uncertainty of diagnostic predictions,
Flare searches over the top-k suspicious lines at each step and selects
the next candidate according to execution outcomes. Experiments on
LiveCodeBench and BigCodeBench with five base LLMs show that, even
without candidate search, Flare ($`k`$=1) outperforms the strongest
baseline, NL-Debugging, with an absolute improvement from 1.06% to 9.71%
in 9 of 10 settings. Expanding the search to 10 candidates adds an
average improvement of 8.97%, and Flare keeps an average lead of 3.39%
over the strongest baseline under the same candidate budget. When
evaluated in isolation, our lightweight diagnostic model outperforms
recent fault localization methods, demonstrating that it can provide
reliable fine-grained guidance for code refinement.

## 1 Introduction

Large Language Models (LLMs) have demonstrated remarkable capabilities
in coding ([Jiang et al., 2026](#bib.bib20); [Achiam et al.,
2023](#bib.bib23); [Zhu et al., 2024](#bib.bib22)). Despite this
progress, LLMs remain prone to generating code with bugs ([Jesse et al.,
2023](#bib.bib29); [Wang et al., 2025](#bib.bib35)). Given the challenge
of generating correct code in one pass, existing code generation methods
often perform iterative refinement, where a model generates an initial
program, receives feedback, and then refines the program over multiple
rounds ([Li et al., 2025](#bib.bib12); [Chen et al., 2024](#bib.bib17);
[Madaan et al., 2023](#bib.bib16); [Zhang et al., 2023](#bib.bib21);
[Zhang et al., 2025](#bib.bib19)). However, these methods usually rely
on feedback signals such as test failures and self-critiques to
iteratively refine the generated code. Such signals are either too
coarse-grained or too high-level to tell the model where the code should
be revised.

To address this limitation, we propose Flare, an iterative framework
that uses a lightweight diagnostic model to predict line-level
suspiciousness for targeted refinement during code generation. Given an
initial code solution, Flare aggregates the language model’s
subword-token probabilities over AST-aligned lexical units such as
identifiers, operators, and keywords. The diagnostic model scores these
lexical units and aggregates the scores into line-level suspiciousness
predictions. During refinement, Flare combines the suspicious line with
execution feedback to generate targeted candidate refinements. Given the
inherent uncertainty of fine-grained feedback predictions, Flare is
further equipped with a search procedure over the top-$`k`$ suspicious
lines at each iteration and selects the next candidate based on
execution outcomes. Note that we do not assume that the program contains
only one bug. Instead, Flare addresses one bug at a time and iteratively
refines the program.

Figure 1: Overview of Flare. The framework aligns LLMs’ probability
signals to predict line-level suspiciousness, combines this diagnostic

We evaluate Flare on two code generation benchmarks,
LiveCodeBench ([Jain et al., 2025](#bib.bib18)) and BigCodeBench ([Zhuo
et al., 2025](#bib.bib24)), with five base LLMs and three existing
iterative refinement methods, including NL-Debugging ([Zhang et al.,
2025](#bib.bib19)), Self-Debugging ([Chen et al., 2024](#bib.bib17)),
and Self-Refine ([Madaan et al., 2023](#bib.bib16)). Even without
candidate search ($`k=1`$), Flare outperforms the most competitive
baseline, NL-Debugging, in 9 of 10 settings with an absolute improvement
from 1.06% to 9.71%. Furthermore, searching over 10 candidates
($`k=10`$) yields an absolute average improvement of 8.97% compared with
no candidate search. Under the same $`k=10`$ budget, Flare still
outperforms NL-Debugging and Best-of-N ([Snell et al.,
2024](#bib.bib10)) by 3.39% and 10.45% absolute improvement on average,
respectively. This suggests that diagnostic localization complements
candidate search by using the expanded budget more effectively. Ablation
studies further show that both fine-grained diagnostic feedback and
candidate search contribute significantly to overall gains. When
evaluated in isolation, our diagnostic model achieves 67% Top-1 and 89%
Top-10 localization accuracy, outperforming recent fault localization
methods, including FlexFL ([Xu et al., 2025](#bib.bib9)), LLMAO ([Yang
et al., 2024](#bib.bib26)), and BAP ([Stein et al., 2025](#bib.bib27)).

## 2 Methodology

Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
provides an overview of Flare. Given a code generation task and an
initial program generated by an LLM, Flare predicts ranked suspicious
lines with a lightweight diagnostic model
(Section [2.1](#S2.SS1 "2.1 Fine-Grained Diagnostic Feedback ‣ 2 Methodology ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")).
Flare then prompts the LLM to generate revisions for the top-$`k`$
suspicious lines and selects the next program according to execution
outcomes
(Section [2.2](#S2.SS2 "2.2 Top-𝑘 Candidate Search ‣ 2 Methodology ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")).
The process continues until a program passes all tests or reaches a
maximum iteration budget.

### 2.1 Fine-Grained Diagnostic Feedback

Existing self-refinement methods for code generation often rely on
coarse-grained or high-level feedback, which provides limited guidance
about where the underlying issue resides. Flare introduces a
fine-grained diagnostic model that ranks suspicious lines of the
generated program before each refinement step.¹¹ 1 We evaluate the
diagnostic model and ablate its components in
Section [3.5](#S3.SS5 "3.5 Diagnostic Model Performance ‣ 3 Experiments ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement").
Formally, given a generated program $`\mathcal{C}`$ segmented into $`L`$
lines $`\mathcal{C}=[c_{1},\dots,c_{L}]`$, we train a diagnostic model
$`f_{\theta}`$ that outputs line-level suspiciousness scores:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\mathbf{r}=f_{\theta}(\mathcal{C})\in\mathbb{R}^{L},\qquad\mathbf{r}=[r_{1},\dots,r_{L}],
``` |  | (1) |

where $`r_{i}`$ denotes the suspiciousness score assigned to line
$`c_{i}`$.

#### Training Data Construction.

We train the diagnostic model on the training split of
Collu-Bench ([Jiang et al., 2024](#bib.bib25)), which contains 10504
buggy code solutions generated by 11 diverse LLMs on five datasets,
including HumanEval, MBPP, HumanEval-Java, Defects4J, and SWE-bench.²² 2
None of the benchmarks used in our evaluation is included in
Collu-Bench. Each solution is paired with token probabilities from the
generator LLM and an annotation of the first buggy token. Previous
empirical studies reveal two key insights ([Jiang et al.,
2024](#bib.bib25); [Spiess et al., 2025](#bib.bib36)): LLMs tend to
exhibit lower confidence when generating buggy code, and their errors
are concentrated on certain token categories, such as Keyword,
Identifier, and Type. Motivated by these findings, we represent each
lexical unit by its embeddings, syntactic type, and the LLM’s confidence
signals derived from subword-token probabilities.

To construct these inputs, we first align the LLM’s confidence signals
with the code’s lexical-unit representation. While the LLM assigns
probabilities to subword tokens, program semantics are organized around
syntactic units such as identifiers, operators, and statements. This
mismatch is particularly problematic for code, as standard Byte-Pair
Encoding (BPE) tokenization often splits a single lexical unit into
multiple subword pieces, e.g., max_retries $`\rightarrow`$ $`\{`$max,
\_, retries$`\}`$.

Specifically, we parse $`\mathcal{C}`$ and extract the AST-aligned
lexical sequence

|     |                                                 |     |     |
|-----|-------------------------------------------------|-----|-----|
|     |
       ``` math
       \mathcal{T}(\mathcal{C})=\{t_{1},\dots,t_{M}\},
       ```                                              |     | (2) |

where $`t_{j}`$ corresponds to a lexical unit.

Let $`\{p_{n}\}_{n=1}^{N}`$ denote the probabilities of the $`N`$
subword tokens. For a lexical unit $`t_{j}`$, let
$`\mathcal{S}(j)\subseteq\{1,\dots,N\}`$ contain the indices of its
aligned subword tokens. We define its aggregate confidence

|     |                                                 |     |     |
|-----|-------------------------------------------------|-----|-----|
|     |
       ``` math
       p^{\prime}_{j}=\prod_{n\in\mathcal{S}(j)}p_{n}.
       ```                                              |     | (3) |

$`p^{\prime}_{j}`$ represents the joint probability assigned by the
language model to lexical unit $`t_{j}`$ and serves as a measure of the
model’s confidence in that unit. Because this product may be sensitive
to the number of aligned tokens,
Appendix [B.2](#A2.SS2 "B.2 Length-Aware Confidence Aggregation ‣ Appendix B Additional Experiment Results ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
compares it with alternative aggregation methods that eliminate this
effect.

For each lexical unit $`t_{j}`$ in the program $`\mathcal{C}`$, we
represent it by the tuple

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbf{x}_{j}=\bigl(t_{j},\;\mathrm{Type}(t_{j}),\;p^{\prime}_{j}\bigr),
``` |  | (4) |

where $`\mathrm{Type}(t_{j})`$ denotes the syntactic category of
$`t_{j}`$, such as Keyword, Identifier, or Type.³³ 3 We list type
details in
Appendix [D](#A4 "Appendix D Syntactic Type ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement").

#### Training Objective.

Diagnosing a bug often requires context beyond one lexical unit or line.
For example, a variable update or branch condition may only appear
suspicious when compared with definitions, uses, or constraints
elsewhere in the program. To model these dependencies, we use a
bidirectional transformer encoder to encode the AST-aligned sequence,
allowing each lexical unit to attend to the full program context ([Guo
et al., 2021](#bib.bib28)).

Given the program $`\mathcal{C}`$, we first embed each lexical unit
$`t_{j}`$ in $`\mathcal{C}`$ into an input vector by concatenating its
token embedding, syntactic type, and projected confidence:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathbf{e}_{j}`$ | $`\displaystyle=\bigl[\mathrm{Emb}_{tok}(t_{j});\,\mathrm{Emb}_{type}(\mathrm{Type}(t_{j}));`$ |  | (5) |
|  |  | $`\displaystyle\mathrm{Proj}(p^{\prime}_{j})\bigr],`$ |  |  |

where $`\mathrm{Emb}_{tok}`$ and $`\mathrm{Emb}_{type}`$ are learned
embedding layers, and $`\mathrm{Proj}`$ maps the confidence feature
$`p^{\prime}_{j}`$ to a vector representation.⁴⁴ 4 The implementation
details are provided in
Appendix [A.3](#A1.SS3 "A.3 Experimental Details ‣ Appendix A Implementation Details ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")

We add positional encodings and feed the resulting sequence into the
transformer encoder to obtain contextual representations:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathbf{h}_{1},\dots,\mathbf{h}_{M}`$ | $`\displaystyle=\mathrm{TransformerEnc}\!\bigl(`$ |  | (6) |
|  |  | $`\displaystyle\mathrm{PosEnc}(\mathbf{e}_{1},\dots,\mathbf{e}_{M})\bigr),`$ |  |  |

where $`\mathrm{PosEnc}`$ adds sinusoidal positional encodings to each
input vector as in [Vaswani et al. (2017)](#bib.bib15).

We then apply a linear classifier to each contextualized unit
representation $`\mathbf{h}_{j}`$:

|     |                                          |     |     |
|-----|------------------------------------------|-----|-----|
|     |
       ``` math
       s_{j}=\mathbf{w}^{\top}\mathbf{h}_{j}+b.
       ```                                       |     | (7) |

For each training program, we map the first buggy token annotated by
Collu-Bench to its aligned lexical unit. Let
$`j^{\star}\in\{1,\dots,M\}`$ denote the index of the buggy lexical unit
in the AST-aligned sequence $`\mathcal{T}(\mathcal{C})`$. The diagnostic
model therefore learns to identify the first likely bug rather than to
enumerate every bug in the program. We train the model with
position-level cross-entropy over lexical-unit logits:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{L}_{\text{FL}}=-\log\frac{\exp(s_{j^{\star}})}{\sum_{m=1}^{M}\exp(s_{m})}.
``` |  | (8) |

All trainable components of the diagnostic model are optimized
end-to-end with $`\mathcal{L}_{\text{FL}}`$.

At inference time, we treat each code line as a region composed of
multiple lexical units, analogous to a region in an image, and apply max
pooling over their suspiciousness scores. Specifically, for each line
$`c_{i}`$ containing the lexical units $`\mathcal{T}(c_{i})`$, we define
its line-level suspiciousness score as

|     |                                               |     |     |
|-----|-----------------------------------------------|-----|-----|
|     |
       ``` math
       r_{i}=\max_{t_{j}\in\mathcal{T}(c_{i})}s_{j}.
       ```                                            |     | (9) |

We compare this max pooling design with an alternative design in
Section [3.4](#S3.SS4 "3.4 Alternative Aggregation Design ‣ 3 Experiments ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement").

The diagnostic model ranks lines in descending order of their
suspiciousness scores, yielding $`\mathcal{R}`$. The refinement loop
uses the top-$`k`$ lines in $`\mathcal{R}`$ for targeted refinement.

### 2.2 Top-$`k`$ Candidate Search

Given a code generation task and an initial program
$`\mathcal{C}^{(0)}`$, Flare iteratively refines the candidate program.
At iteration $`t`$, Flare executes the current program
$`\mathcal{C}^{(t)}`$ against the public tests in a sandbox and obtains
execution feedback $`\xi^{(t)}`$. If the program passes all test cases,
the loop terminates and returns the current program as the solution.
Otherwise, the diagnostic model produces a ranking of its suspicious
lines, $`\mathcal{R}^{(t)}`$.

Rather than relying only on the top-ranked line, Flare searches over the
top-$`k`$ suspicious lines. For each selected line, Flare constructs a
targeted refinement prompt containing the code generation task, the
current program, the execution feedback, and that suspicious line. The
language model generates one candidate revision for each prompt,
producing $`k`$ candidate revisions at the current iteration. Thus,
$`k=1`$ uses only the most suspicious line, while larger $`k`$ values
explore multiple plausible fault locations.

We execute all candidate revisions against the public tests⁵⁵ 5 During
refinement, execution feedback and candidate selection use only public
tests. Hidden tests are never used during refinement and are only used
for final evaluation.. If any candidate passes all tests, the loop
terminates and returns a passing candidate as the final solution.
Otherwise, Flare prefers the candidate that passes more tests or
resolves more failures as $`\mathcal{C}^{(t+1)}`$. When candidates pass
the same number of tests, we prefer the shortest candidate for
conciseness. Refinement continues until a candidate passes all public
tests or the maximum iteration budget is reached. Because the diagnostic
model targets the first suspicious location, the language model
generates a complete revised program at each step. Thus, a revision can
modify multiple lines or insert missing code. Flare then reruns
execution and diagnosis, allowing later iterations to address any
remaining errors.

## 3 Experiments

### 3.1 Experimental Setup

#### Benchmarks.

We evaluate Flare on two representative code generation benchmarks.
LiveCodeBench ([Jain et al., 2025](#bib.bib18)) continually incorporates
recent problems from competitive programming platforms, including
LeetCode, AtCoder, and Codeforces, which mitigates contamination risks.
BigCodeBench ([Zhuo et al., 2025](#bib.bib24)) contains practical
programming tasks that require diverse libraries and function calls.
Neither benchmark is included in the source data used to construct the
Collu-Bench training split. We report Pass@1, the percentage of tasks
for which the final generated solution passes all test cases.

#### Base LLMs.

We evaluate Flare with five base LLMs spanning different model families
and scales, including Qwen3-8B ([Yang et al., 2025](#bib.bib32)),
Llama-3.3-70B ([Grattafiori et al., 2024](#bib.bib34)),
GPT-4o-mini ([Hurst et al., 2024](#bib.bib33)), GLM-5.1 ([GLM-5-Team et
al., 2026](#bib.bib14)), and DeepSeek-V4-Flash ([DeepSeek-AI,
2026](#bib.bib13)).

#### Comparison Baselines.

We compare Flare with three iterative refinement methods and two
candidate-search baselines. First, Self-Debugging ([Chen et al.,
2024](#bib.bib17)) generates an explanation of the current program and
combines it with the execution results for refinement. Self-Refine
([Madaan et al., 2023](#bib.bib16)) prompts the model to generate
self-feedback for code refinement. NL-Debugging ([Zhang et al.,
2025](#bib.bib19)) translates the code solution into natural language
and performs debugging in the natural language to guide code refinement.
Best-of-N ([Snell et al., 2024](#bib.bib10)) generates 10 independent
solutions and retains the one that passes the most public tests. We also
equip NL-Debugging with a candidate-search budget of $`k=10`$. At each
iteration, it generates 10 candidate revisions and, following the same
selection rule as Flare, retains the candidate that passes the most
public tests. Following prior work ([Zhang et al., 2025](#bib.bib19);
[Chen et al., 2024](#bib.bib17)), we also include the original LLM
performance as a weak baseline.

#### Implementation Details.

The diagnostic model in Flare is a bidirectional transformer encoder
with 6 layers and 8 attention heads. We train the full diagnostic model
from scratch, including the input embeddings, transformer encoder, and
linear prediction head. Following [Zhang et al. (2025)](#bib.bib19);
[Amini et al. (2025)](#bib.bib8), we use a maximum refinement iteration
budget of $`N`$=5 and a candidate-search budget of $`k`$=10. We also
report the $`k`$=1 variant, which uses only the top-ranked suspicious
region and removes expanded candidate search. Additional details are
provided in
Appendix [A.3](#A1.SS3 "A.3 Experimental Details ‣ Appendix A Implementation Details ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement").

### 3.2 Main Results

Table [1](#S3.T1 "Table 1 ‣ Implementation Details. ‣ 3.1 Experimental Setup ‣ 3 Experiments ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
reports the end-to-end Pass@1 results. Even without candidate search,
Flare ($`k`$=1) already improves on the iterative refinement baselines.
It outperforms Self-Debugging in all settings and surpasses both
Self-Refine and NL-Debugging in 9 of the 10 settings. Specifically,
Flare ($`k`$=1) achieves absolute Pass@1 gains of 1.72% to 9.71% over
the strongest baseline, NL-Debugging, in four of five settings on
LiveCodeBench. On BigCodeBench, Flare ($`k`$=1) provides consistent
gains over NL-Debugging across all five models. These results show that
diagnostic localization improves iterative refinement even before
expanded candidate search is applied.

Expanded candidate search allows Flare to explore multiple plausible
fault regions instead of committing to the highest-ranked one. Compared
with $`k=1`$, Flare with $`k=10`$ improves Pass@1 by 8.97 points on
average, with gains across all settings. The improvements range from
6.84 to 13.42 points on BigCodeBench and from 5.72 to 12.00 points on

performance in most settings, including both smaller and larger models
as well as earlier and more recent ones.

To isolate the contribution of candidate search, we compare Flare
($`k`$=10) with Best-of-N ($`k=10`$) and NL-Debugging ($`k`$=10). Under
the same candidate-search settings, Flare outperforms Best-of-N by 4.11
points on LiveCodeBench and 16.79 points on BigCodeBench on average. It
also outperforms NL-Debugging by 3.20 points on LiveCodeBench and 3.58
points on BigCodeBench.

Overall, these results show that precise diagnostic localization and
candidate search play complementary roles. Localization identifies
likely refinement regions, while expanded search mitigates uncertainty
in the predicted fault location.

### 3.3 Ablation Study

The main results already show that ablating the search procedure by
setting $`k`$ to 1 outperforms other single-candidate baselines. In this
section, we therefore focus the ablation study on the contribution of
each feedback source.
Table [2](#S3.T2 "Table 2 ‣ 3.2 Main Results ‣ 3 Experiments ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
isolates the contributions of diagnostic and execution feedback using
GPT-4o-mini on LiveCodeBench and BigCodeBench. We compare full Flare
with variants that remove one feedback source from the refinement prompt
at both $`k=1`$ and $`k=10`$.

#### Fine-Grained Feedback.

Fine-grained diagnostic feedback improves refinement under both search
budgets. The execution-only variant retains execution feedback in the
refinement prompt but removes the predicted suspicious line. At $`k`$=1,
execution-only refinement reaches 50.29% Pass@1 on LiveCodeBench and
53.77% on BigCodeBench, while full Flare reaches 54.86% and 58.51%. At
$`k`$=10, execution-only refinement reaches 58.29% and 59.47%, while
full Flare reaches 65.14% and 69.65%. The consistent gaps show that
fine-grained feedback provides useful localization guidance on top of
execution feedback in both the single-candidate and expanded-search
settings.

#### Execution Feedback.

Execution feedback also improves refinement under both search budgets.
The diagnostic-only variant includes the predicted suspicious line but
omits execution feedback. At $`k`$=1, diagnostic-only refinement reaches
50.86% Pass@1 on LiveCodeBench and 50.35% on BigCodeBench, below the
full Flare scores of 54.86% and 58.51%. At $`k`$=10, diagnostic-only

and 69.65%. Together, the two ablations show that the signals play
complementary roles: fine-grained feedback identifies where to revise,
while execution feedback describes the observed failure.

### 3.6 Effect of Search Budget

We analyze the effect of two search-budget parameters: the maximum
number of refinement iterations $`N`$ and the number of suspicious lines
$`k`$ explored at each iteration. We vary one budget at a time while
holding the other fixed on LiveCodeBench with GPT-4o-mini.
Figure [2](#S3.F2 "Figure 2 ‣ Execution Feedback. ‣ 3.3 Ablation Study ‣ 3 Experiments ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
shows the results.

Increasing the number of iterations from 3 to 5 improves Pass@1 from
56.57% to 65.14%. Further increasing the budget yields smaller gains,
reaching 65.71% at 7 iterations and 66.86% at 9 iterations. Similarly,
increasing the candidate budget $`k`$ from 4 to 10 improves Pass@1 from
59.43% to 65.14%, while increasing $`k`$ beyond 10 yields smaller
returns relative to the added refinement cost, reaching 66.29% at
$`k=13`$ and 67.43% at $`k=16`$. The default setting ($`N=5`$ and
$`k=10`$) provides the best balance between computational cost and
refinement performance.

### 3.8 Failure Case Analysis

To understand the limitations of Flare, we manually inspected 418 final
solutions that remain incorrect on BigCodeBench and LiveCodeBench and
grouped their failures into three categories.
Appendix [F](#A6 "Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
provides an example of each category.

#### Language Model Reasoning Failures (253/418).

Most failures occur when localization identifies useful regions, but the
language model still lacks the capability to perform the required
reasoning or algorithmic change. For example, in the purchasing problem
in
Table [15](#A6.T15 "Table 15 ‣ Long-Range State and Simulation Errors. ‣ Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement"),
where buying $`k`$ units of product $`i`$ costs $`k^{2}P_{i}`$, the
model incorrectly uses binary search on the target number of units and
validates it with a naive loop. A correct solution instead needs to
reason about marginal costs and purchase units in increasing marginal
cost order. In such cases, the bottleneck is not only where to edit the
program, but also whether the language model can select the right
problem-solving strategy.

#### Misinterpretation of Task Requirements (88/418).

Some failures stem from an incorrect understanding of the problem
specification. The model may implement a plausible algorithmic component
but apply the wrong constraint, formula, or objective in the final
computation. For example, in the stone merging problem in
Table [16](#A6.T16 "Table 16 ‣ Long-Range State and Simulation Errors. ‣ Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement"),
the model applies a linear-basis solution for subset XOR, but the task
requires reasoning about XOR values after whole-bag merge operations.
These errors are difficult to refine through localization alone because
the faulty code often reflects a mistaken interpretation of the task
rather than a localized implementation bug.

#### Long-Range State and Simulation Errors (77/418).

The remaining failures often involve complex state transitions,
multi-stage simulations, or long-range variable dependencies. In these
cases, the model may fix one local transition while breaking a later
dependency. For example, in the simulation problem in
Table [17](#A6.T17 "Table 17 ‣ Long-Range State and Simulation Errors. ‣ Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement"),
the model represents the history of which adults still have stones with
a single global counter, discarding information needed for later years.
This suggests that future work may need feedback from intermediate
program states in addition to line-level localization.

## 4 Related Work

#### Iterative Code Refinement.

Iterative code refinement typically follows a refinement loop in which a
model generates code, receives feedback, and then revises the generated
code. Prior work has explored different forms of feedback for this
process. Self-Debugging ([Chen et al., 2024](#bib.bib17)),
Self-Edit ([Zhang et al., 2023](#bib.bib21)), Cycle ([Ding et al.,
2024](#bib.bib2)), and OpenCodeInterpreter [Zheng et al.
(2024)](#bib.bib4) use execution feedback to guide code revision. By
contrast, Self-Refine ([Madaan et al., 2023](#bib.bib16)) relies on the
model’s own critique to improve its output. [Welleck et al.
(2023)](#bib.bib3) studies self-correction with model-generated
feedback. More recently, NL-Debugging translates the code solution into
natural language and performs debugging in the natural language to guide
code refinement ([Zhang et al., 2025](#bib.bib19)). However, such
signals are either too coarse-grained or too high-level to tell the
model where the code should be revised. Flare addresses this limitation
by augmenting iterative refinement with line-level diagnostic feedback.

#### Fault Localization.

Traditional fault localization (FL) methods often use test coverage
information to predict the fault location. For instance, spectrum-based
FL analyzes runtime spectra from passing and failing test cases and
ranks program entities with suspiciousness metrics such as
Jaccard ([Abreu et al., 2006](#bib.bib7)), Ochiai ([Abreu et al.,
2006](#bib.bib7)), and DStar ([Wong et al., 2014](#bib.bib1)).
Learning-based FL extends this approach by training ranking or
prediction models on execution spectra and other program features, such
as code complexity metrics and error messages ([Li et al.,
2019](#bib.bib6); [Sohn and Yoo, 2017](#bib.bib5)).

More recently, LLM-based FL methods have used language models to reason
about suspicious code regions. AgentFL ([Qin et al., 2024](#bib.bib30))
prompts LLMs with diversified debugging information from failed tests.
FlexFL ([Xu et al., 2025](#bib.bib9)) decomposes localization into two
stages that use LLMs to refine localization results obtained from one or
more existing FL techniques. SOAPFL ([Qin et al., 2025](#bib.bib31))
further standardizes LLM-based localization into structured reasoning
stages, including comprehension, navigation, and confirmation. Another
line of work probes model-internal signals to predict buggy regions.
LLMAO ([Yang et al., 2024](#bib.bib26)) fine-tunes bidirectional
adapters to predict line-level bugginess, while BAP ([Stein et al.,
2025](#bib.bib27)) uses weak supervision to interpret attention patterns
for scalable localization.

Compared with these FL methods, Flare trains a lightweight diagnostic
model to localize suspicious code regions from the language model’s
probabilistic signals. Our evaluation shows that this diagnostic model
outperforms recent methods including FlexFL ([Xu et al.,
2025](#bib.bib9)), LLMAO ([Yang et al., 2024](#bib.bib26)), and
BAP ([Stein et al., 2025](#bib.bib27)).

## 5 Conclusion

We presented Flare, an iterative framework with a lightweight diagnostic
model that predicts line-level suspiciousness signals for bug
localization and refinement. To account for the uncertainty of
diagnostic predictions, Flare searches over the top-$`k`$ suspicious
lines and selects candidate revisions using execution outcomes.
Experiments on LiveCodeBench and BigCodeBench with five base LLMs show
that Flare outperforms existing iterative refinement methods in most
settings, even without candidate search. Ablations confirm that
fine-grained diagnostic feedback and candidate search contribute
significantly to overall gains. These results suggest that fine-grained
localization signals serve as reliable guidance for code refinement.

## Limitations

Our framework has three main limitations. First, the iterative
refinement process introduces overhead. In our efficiency analysis, we
show that this overhead is moderate compared with other iterative
refinement methods. Nevertheless, we acknowledge that the additional
cost may become non-negligible when the number of refinement rounds or
the top-$`k`$ candidate budget is large.

Second, as discussed in our failure-case analysis, the capability of the
language model affects the performance. For example, failures arise from
an incorrect understanding of the problem specification. These errors
are difficult to resolve through localization alone because the faulty
code often reflects a mistaken interpretation of the task rather than a
localized implementation bug.

Third, Flare uses token probabilities produced during code generation as
input to the diagnostic model. These internal signals are used to
predict the bug location. Flare can therefore be applied to any model
that exposes these internal signals, including all models evaluated in
this paper. However, some commercial APIs do not expose these signals,
so the method cannot be applied to them currently.

## Appendix A Implementation Details

### A.1 Model Architecture

#### Embeddings and projection.

We use three learnable modules to embed each lexical unit: (i) a token
embedding layer $`\mathrm{Emb}_{tok}`$, (ii) a type embedding layer
$`\mathrm{Emb}_{type}`$, and (iii) a linear projection $`\mathrm{Proj}`$
for the scalar confidence value. In our implementation, the token
embedding dimension is $`256`$, the syntactic-type embedding dimension
is $`128`$, and the probability projection dimension is $`128`$. The
concatenated vector has dimension $`512`$.

### A.2 Training Setup

We optimize the diagnostic model using AdamW with a learning rate of
$`10^{-4}`$ for $`15`$ epochs and a batch size of $`32`$. Given the
ground-truth buggy unit index $`j^{\star}`$, we minimize a
position-level cross-entropy loss over the logits
$`\{s_{j}\}_{j=1}^{M}`$. We select the best checkpoint according to
validation accuracy (exact match of the predicted index).

### A.3 Experimental Details

We trained our diagnostic model on a single NVIDIA GeForce RTX 4090 GPU.
For training and evaluating the diagnostic model on Collu-Bench, the
dataset contains 13130 samples in total, split into 10504 training
samples and 2626 test samples. We train a single diagnostic model on
this training split and share it across all five base LLMs in our
end-to-end experiments without per-model retraining. Because Collu-Bench
contains programs and token probabilities from 11 different generator
LLMs, the training data does not tie the diagnostic model to any single
generator. The model was trained for 15 epochs, with a total training
time of approximately 10 minutes under this hardware configuration.

As for evaluation benchmarks, we use the code_generation_lite subset
(release_v6) of LiveCodeBench, which contains 175 tasks, and the full
BigCodeBench suite, which contains 1140 tasks.

### A.4 Fault-Localization Evaluation Details

We manually annotated the 100 randomly selected failed LiveCodeBench
programs used in
Section [3.5](#S3.SS5 "3.5 Diagnostic Model Performance ‣ 3 Experiments ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement").
For each program, we inspected the task, the generated code, and the
observed failure, and marked the first line containing the faulty logic
as the reference fault location.

We used official parameter configurations for the fault-localization
baselines whenever they were available. For LLMAO and BAP, we used
Llama 3.2 11B as the backbone. We constructed their fine-tuning examples
from the same Collu-Bench training split used for Flare, following each
method’s original data-construction procedure. Their fine-tuning
configurations follow the corresponding papers and official
repositories. For FlexFL, we used its released prompt with GPT-4o on the
same 100 manually annotated programs.

### B.2 Length-Aware Confidence Aggregation

Equation [3](#S2.E3 "In Training Data Construction. ‣ 2.1 Fine-Grained Diagnostic Feedback ‣ 2 Methodology ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
defines the confidence of lexical unit $`t_{j}`$ as
$`p^{\prime}_{j}=\prod_{n\in\mathcal{S}(j)}p_{n}`$, where
$`\mathcal{S}(j)`$ is the set of BPE-token indices aligned with
$`t_{j}`$. We write this feature in the equivalent log-score space,
$`\ell^{\prime}_{j}=\log p^{\prime}_{j}=\sum_{n\in\mathcal{S}(j)}\log p_{n}`$,
where $`n_{j}=|\mathcal{S}(j)|`$. Because the product is affected by the
number of aligned BPE tokens, we compare the original score with mean
normalization and additive length compensation to remove this length
effect.

| Adjustment | Log-space feature                     | Validation accuracy |
|------------|---------------------------------------|---------------------|
| None       | $`\ell^{\prime}_{j}`$                 | 0.7784              |
| Mean       | $`\ell^{\prime}_{j}/n_{j}`$           | 0.7708              |
| Additive   | $`\ell^{\prime}_{j}+\alpha(n_{j}-1)`$ | 0.7586              |

Table 9: Validation accuracy under alternative lexical-unit confidence
aggregations.

The mean design, $`\ell^{\prime}_{j}/n_{j}`$, uses the average token
log-probability, corresponding to standard length normalization in
sequence scoring ([Murray and Chiang, 2018](#bib.bib11)). The additive
variant adds a fixed reward for each extra BPE token,
$`\alpha(n_{j}-1)`$, following the per-word reward approach [Murray and
Chiang (2018)](#bib.bib11). We set $`\alpha=0.2`$, following the
initialization used in that work.

All three aggregations results are close. The largest gap is only 1.98
validation points, and the original aggregation feature achieves the
best performance. One likely reason is that AST lexical alignment
confines each aggregation to a syntactic lexical unit, which limits the
range of subword lengths under comparison. Another is that the aggregate
confidence is only one scalar input; the model uses lexical identity,
syntactic type, position, and full-program context as inputs.

### B.3 Efficiency

Breaking down the runtime in Section
[5](#S3.T5 "Table 5 ‣ 3.7 Efficiency Analysis ‣ 3 Experiments ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement"),
language model inference accounts for approximately 87% of this runtime

## Appendix C Case Study

To understand how Flare refines programs, we present an example from
LiveCodeBench. The problem gives $`N`$ foods and a calorie budget $`X`$.
Each food has a vitamin type, a vitamin amount, and a calorie cost. The
objective is to maximize the smallest total amount among the three
vitamins. Thus, a correct solution must use one shared food subset that
both stays within budget and balances the three vitamin totals. We
provide complete examples in
Table [18](#A6.T18 "Table 18 ‣ Long-Range State and Simulation Errors. ‣ Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
and
Table [19](#A6.T19 "Table 19 ‣ Long-Range State and Simulation Errors. ‣ Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement").

The initial solution incorrectly defines the dynamic programming (DP)
state as dp = \[\[0\] \* (X + 1) for \_ in range(4)\], using rows 1 to 3
for the three vitamin types and optimizes each vitamin separately. This
design treats each row as an independent knapsack table, which is the
core mistake. Each vitamin row can spend the full calorie budget on a
different subset of foods, so dp\[1\]\[X\], dp\[2\]\[X\], and
dp\[3\]\[X\] may not come from the same food selection. However, the
task requires one shared subset whose total calories are within $`X`$.
The final min computation therefore treats three separately optimized
values as if they were achieved by the same selection, so the reported
answer can be too large.

Execution feedback can show that the output is wrong, but it does not
identify that the abstraction of the DP state is the root cause. Flare’s
diagnostic model ranks the DP initialization line as the most
suspicious. This feedback points directly to the flawed state
abstraction.

Guided by this diagnostic feedback, Flare produces a refined solution
with a different strategy. This solution uses binary search over a
target value $`m`$ and checks whether one subset of foods can make all
three vitamin totals at least $`m`$ within budget $`X`$. This
formulation enforces the shared budget constraint and avoids the
independent-DP mistake.

By contrast, Self-Debugging keeps the three independent DP tables and
adds a binary-search check over a single calorie value. Self-Refine only
makes a minor revision, preserving the original per-vitamin DP tables
and the final min over independently optimized values. NL-Debugging
rewrites the table as dp\[c\]\[v\], but each entry still records only
the best value for one vitamin rather than a joint food selection. All
revisions continue to combine incompatible choices across vitamin types,
reflecting a common refinement failure mode in which the model applies
superficial patches without correcting the underlying abstraction. By
localizing the suspicious DP state, Flare helps refinement to address
the root cause and produce a correct solution strategy.

These examples illustrate what remains difficult after diagnostic
feedback: the language model must still infer the right algorithm,
interpret the task correctly, and maintain long-range program state.

#### Language Model Reasoning Failure.

Table [15](#A6.T15 "Table 15 ‣ Long-Range State and Simulation Errors. ‣ Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
shows a purchasing problem where buying $`k`$ units of product $`i`$
costs $`k^{2}P_{i}`$. A correct solution must reason about marginal
costs and purchase units in increasing marginal-cost order. The
generated solution instead binary searches the target number of units
and uses a naive purchasing loop that does not correctly test whether
that target is achievable. This failure reflects a missing algorithmic
insight rather than a local implementation mistake.

#### Misinterpretation of Task Requirements.

Table [16](#A6.T16 "Table 16 ‣ Long-Range State and Simulation Errors. ‣ Appendix F Detailed Failure Case Analysis ‣ FLARE: Fine-Grained Diagnostic Feedback for LLM Code Refinement")
shows a problem about merging whole bags of stones and counting possible
final XOR values. The generated solution builds a linear basis over the
initial stone counts, which is appropriate for subset-XOR problems but
not for this merge operation. The model recognizes a relevant
mathematical keyword, XOR, but applies the wrong problem formulation.

multiple state transitions.
````
