###### Abstract

LLM-based recommendation agents can search catalogs, inspect products,
ask users, and revise rejected recommendations. However, these behaviors
are often governed by hand-designed workflows, while existing training
methods optimize isolated components such as query rewriting or list
ranking rather than the interaction policy as a whole. We present
SimRec, a reinforcement learning framework that trains the full
interaction policy of a tool-integrated recommendation agent. SimRec
introduces two components. A task-anchored user simulator provides
feedback on every recommendation: conditioned on the current task need
rather than on user profile, and it can be an external LLM or the
recommender itself under self-play. A task-aligned reward optimizes the
whole trajectory with GRPO, crediting natural retrieval quality and
valid tool use alongside the final hit, with training-only target
injection to handle sparse hits over large catalogs. On ESCI and Amazon
C4, SimRec improves the NDCG@100 of a Qwen3-4B agent from 32.23% to
35.42% and from 22.94% to 24.72%, outperforming training-free agents on
far larger backbones and task-aligned baselines on NDCG. Analysis shows
that the trained agent verifies candidates, uses preferences, and
recovers from rejected recommendations far more often than its untrained
counterpart. Our code is available at
[https://github.com/ZJU-REAL/SimRec/](https://github.com/ZJU-REAL/SimRec/).

## 1 Introduction

Recommender systems are moving from one-shot prediction toward
interaction. Built on a large language model (LLM), a recommendation
agent takes a request in natural language, retrieves candidates from the
catalog, inspects those that look plausible, asks the user when the need
is underspecified, and recommends an item; if the user is not satisfied,
it continues from the user’s reaction ([Huang et al.,
2025b](#bib.bib28); [Zhao et al., 2024](#bib.bib39); [Zhang et al.,
2026a](#bib.bib29); [Li et al., 2026](#bib.bib44); [Lin et al.,
2026](#bib.bib40); [Wang et al., 2026](#bib.bib46)). Recommendation
quality in this setting is not the output of a single scoring model but
the result of a sequence of decisions made over the course of the
interaction. A feedback-driven revision is illustrated in
Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction").

Existing agents make these decisions by rules set in advance rather than
by learning from outcomes: a hand-designed workflow prescribes when to
search, when to ask, and when to recommend ([Huang et al.,
2025b](#bib.bib28); [Fang et al., 2024](#bib.bib49); [Wang et al.,
2025b](#bib.bib50)). Where training is used at all, it targets one step
lifted out of the interaction, such as rewriting a query for the
retriever ([Lin et al., 2025](#bib.bib41); [Yoon et al.,
2025](#bib.bib8); [Nguyen et al., 2025](#bib.bib48)), ranking a given
list ([Zhu et al., 2026](#bib.bib42); [Feng et al., 2025b](#bib.bib43)),
or generating a response to a given dialogue ([Xiang et al.,
2026](#bib.bib45); [Cai et al., 2026](#bib.bib56)); the outcome of the
whole interaction never reaches the policy that made the decisions along
the way. These limitations show in behavior. Such agents seldom verify
the candidates they retrieve, seldom consult the user’s history, and
rarely recover once a recommendation is rejected, and a larger backbone
does not make up for it
(Section [4.4](#S4.SS4 "4.4 Analysis ‣ 4 Experiments ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")).
An interaction policy has to be trained on the interaction itself.

Reinforcement learning over complete trajectories trains a policy on
exactly this: the agent acts, the environment responds, and the whole
trajectory is optimized for the final outcome. For search agents the
recipe is well established, with the model interleaving reasoning and
search calls and the trajectory rewarded by the correctness of the final
answer ([Jin et al., 2025](#bib.bib53); [Qian et al., 2025](#bib.bib54);
[Feng et al., 2025a](#bib.bib55)). The search setting, however, comes
with its environment given: the index answers every query the same way,
search is the only tool, and the answer is either right or wrong
(Figure [1](#S0.F1 "Figure 1 ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")).
Recommendation has none of these. The environment is a user who reacts
to each recommended item, the evidence comes from several tools with
different costs, and the outcome is a hit that is rare and does not say
where the failure occurred. Training a recommendation agent on the
interaction itself therefore requires three things to be supplied: the
user, the actions, and the objective.

Interaction with real users cannot supply training signal at the scale
reinforcement learning needs, so the user is played by a
simulator ([Xiang et al., 2026](#bib.bib45)). A simulator that knows the
target item leaks it into the dialogue ([Zhu et al., 2024](#bib.bib51);
[Kim et al., 2025](#bib.bib35)), and one that reconstructs a full user
profile may drift from the actual need over turns ([Zhang et al.,
2024](#bib.bib52); [Meshi et al., 2026](#bib.bib36)); the simulator
should say only what a real user would say after a recommendation,
namely whether the item fits the current need and what it lacks ([Bi et
al., 2019](#bib.bib23)). The actions have to cover the evidence a
recommendation depends on, that is, the candidates, the details of a
single item, and the user’s long-term preferences; each has a cost and
none is always needed, so when to draw on each is left to the
policy ([Li et al., 2025a](#bib.bib21); [Ma et al., 2024](#bib.bib24)).
The objective has to credit what the hit cannot see. A hit is rare, and
a miss does not say whether the target was never retrieved or was
retrieved and not chosen; retrieval quality and tool use therefore have
to be rewarded alongside the final hit, and the reward has to remain
informative when the hit is absent ([Wang et al., 2026](#bib.bib46)).

![Refer to caption](2611.15426v1/case.png)

Figure 2: Case study of SimRec multi-turn recommendation refinement.
SimRec uses user feedback to revise its recommendation.

To meet these requirements, we propose SimRec, a framework that trains a
recommendation agent end-to-end on multi-turn interaction with a
simulated user
(Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")).
The user is a task-anchored simulator: it is conditioned on the current
task need rather than on the target item or a profile, answers each
recommendation with what the item lacks, and never names the target; it
can be an external LLM or the recommender itself under shared-parameter
self-play. The actions are retrieval, item inspection, preference
access, a clarifying question, and a recommendation, in no fixed order;
long-term preferences are thus evidence the agent fetches, not part of
the simulator. The objective is a task-aligned reward over the whole
trajectory that credits natural retrieval quality and valid tool use
alongside the final hit, with training-only target injection so that
candidate comparison can still be learned when retrieval misses. Trained
with GRPO under this objective, the agent learns when to search, when to
inspect, when to ask, and when to recommend.

On ESCI and Amazon C4, SimRec raises the NDCG@100 of its Qwen3-4B
backbone from 32.23% to 35.42% and from 22.94% to 24.72%, above
training-free agents on far larger backbones and above task-aligned
baselines. The gain is in the interaction: the trained agent verifies
candidates and consults preferences where the untrained one almost never
does, recovers from a rejected recommendation, and ranks a fixed
candidate set better in a controlled reranking test. The gains carry
over to a sparse retriever and a smaller backbone, and training leaves
general capabilities intact.

Our contributions are summarized as follows:

- •
  We treat the interaction decisions of a recommendation agent, namely
  when to search, inspect, ask, and recommend, as a policy to be trained
  on the outcome of the whole interaction, and identify what such
  training requires: the user, the actions, and the objective.
- •
  We propose SimRec, which addresses these requirements with a
  task-anchored user simulator, a tool-integrated action space over
  retrieval, item inspection, and preferences, and a task-aligned
  trajectory reward with training-only target injection.
- •
  SimRec outperforms retrieval, training-free, and task-aligned
  baselines on ESCI and Amazon C4, and its gains trace to learned
  interaction behavior: candidate verification, use of preferences,
  recovery after a rejection, and stronger candidate comparison.

## 2 Related Work

### 2.1 Agentic Recommendation Agents

Conversational recommender systems use natural-language interaction to
elicit user needs and support preference understanding and
recommendation [Christakopoulou et al. (2016)](#bib.bib17); [Jannach et
al. (2022)](#bib.bib18). LLM-based methods further improve intent
understanding, candidate analysis, response generation, and multi-turn
planning [Huang et al. (2025a)](#bib.bib19); [Zhang et al.
(2026b)](#bib.bib20); [Li et al. (2025a)](#bib.bib21); [Du et al.
(2025)](#bib.bib22), while conversational product search studies
negative feedback, proactive questioning, query reformulation, and
preference clarification [Bi et al. (2019)](#bib.bib23); [Ma et al.
(2024)](#bib.bib24); [Ye et al. (2025)](#bib.bib25); [Zou et al.
(2025)](#bib.bib26); [Li et al. (2025b)](#bib.bib27). Recent recommender
agents formulate recommendation as sequential observation, reasoning,
and action, often augmented with retrieval, user profiles, and external
knowledge [Huang et al. (2025b)](#bib.bib28); [Zhang et al.
(2026a)](#bib.bib29); [Shang et al. (2026)](#bib.bib30); [Shi et al.
(2025)](#bib.bib37); [Hui et al. (2026)](#bib.bib38). Related work also
explores proactive retrieval, query reformulation, and task-specific
post-training for recommendation and tool decisions [Zhao et al.
(2024)](#bib.bib39); [Lin et al. (2026)](#bib.bib40); [Lin et al.
(2025)](#bib.bib41); [Zhu et al. (2026)](#bib.bib42); [Li et al.
(2026)](#bib.bib44). However, existing multi-turn interaction is still
largely used for need elicitation and information acquisition before
recommendation. SimRec instead models a complete recommendation loop,
where user responses and external evidence continuously update
subsequent recommendation decisions.

### 2.2 User Simulation for Recommendation

User simulation has long supported conversational recommender systems
(CRSs). Early work developed preference-aware and agenda-based
simulators, while UserSimCRS incorporated persona, context,
satisfaction, and conditional response generation [Zhang and Balog
(2020)](#bib.bib14); [Afzali et al. (2023)](#bib.bib13). Subsequent
studies systematize user simulation across information-access tasks and
distinguish its training and evaluation roles [Balog and Zhai
(2023)](#bib.bib12); [Bernard and Balog (2024)](#bib.bib16).

Recent work increasingly uses LLMs to simulate user profiles,
preferences, and conversational behavior [Ni et al. (2026)](#bib.bib31);
[Wang et al. (2025a)](#bib.bib32); [Shi et al. (2025)](#bib.bib37);
[Bougie and Watanabe (2025)](#bib.bib33); [Zhang et al.
(2025b)](#bib.bib34), together with dedicated evaluation protocols and
benchmarks [Yoon et al. (2024)](#bib.bib15); [Kim et al.
(2025)](#bib.bib35); [Meshi et al. (2026)](#bib.bib36). Simulated
interactions have also been used to optimize multi-turn recommendation
policies through preference optimization, self-distillation, and
ranking-based objectives [Xiang et al. (2026)](#bib.bib45); [Wang et al.
(2026)](#bib.bib46); [Feng et al. (2025b)](#bib.bib43); [Zhu et al.
(2026)](#bib.bib42). In contrast, SimRec anchors simulation to the
current task need and generates feedback on recommendation mismatch,
while exposing long-term preferences separately through a tool.

## 3 Method

### 3.1 Problem Formulation

SimRec models recommendation as a finite-horizon interaction among a
recommendation agent, external tools, and a user simulator
(Figure [3](#S3.F3 "Figure 3 ‣ 3.1 Problem Formulation ‣ 3 Method ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")).
Let $`\mathcal{I}`$ be the product catalog, whose items have
identifiers, textual descriptions, and structured attributes. A task is
defined as

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       x=(u_{0},h_{x},z_{x},\mathcal{Y}_{x}),
       ```                                     |     | (1) |

where $`u_{0}`$ is the initial request, $`h_{x}`$ is the user’s
historical interactions, $`z_{x}`$ is the current task need, and
$`\mathcal{Y}_{x}\subseteq\mathcal{I}`$ is the set of target items. The
simulator is conditioned on $`z_{x}`$, and the environment uses
$`\mathcal{Y}_{x}`$ to assess success; neither is directly exposed to
the agent. The agent can access long-term preferences summarized from
$`h_{x}`$ through the preference tool. When training requires one
target, $`y_{x}\in\mathcal{Y}_{x}`$ denotes the selected item; for
single-target tasks, $`|\mathcal{Y}_{x}|=1`$.

At step $`t`$, the state $`s_{t}`$ contains the initial request and
accumulated dialogue, including user responses and tool observations.
The agent selects $`a_{t}\sim\pi_{\theta}(\cdot\mid s_{t})`$ from
clarification, tool-use, and recommendation actions. Tools support
product retrieval, item inspection, and preference access. The
interaction follows

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       s_{t}\rightarrow a_{t}\rightarrow o_{t}\rightarrow s_{t+1},
       ```                                                          |     | (2) |

where $`o_{t}`$ is the resulting user response or tool observation. For
a recommendation $`i_{t}`$, the environment checks whether
$`i_{t}\in\mathcal{Y}_{x}`$, and the simulator generates the
corresponding response. A rejection continues the interaction. The
episode ends upon success, after $`N_{\mathrm{rec}}`$ recommendation
attempts, or at horizon $`T_{\max}`$, yielding a trajectory
$`\tau=(s_{1},a_{1},o_{1},\ldots,s_{T},a_{T},o_{T})`$.

### 3.2 Tool-Augmented Recommendation

SimRec provides three external tools through a unified interface,
covering the three key information needs in recommendation: candidate
discovery, candidate verification, and user preference. Tool outputs are
incorporated into the interaction state as observations.

Product Search. Given a natural-language query, the retriever returns a
relevance-ranked product list. SimRec provides interchangeable retrieval
backends, allowing dense or sparse retrievers to be selected for
different tasks. To limit context length, search results expose compact
product snippets, while full product information is accessed through the
Item Detail tool.

Item Detail. The Item Detail tool returns full product information for a
selected candidate, providing grounded evidence for verifying
constraints such as price, size, compatibility, and functionality and
for distinguishing otherwise similar candidates.

User Preference. For tasks with user history, $`h_{x}`$ is standardized,
deduplicated, chronologically ordered with target items removed, and
LLM-summarized into long-term preferences. The agent accesses this
summary on demand. Preference construction details are provided in the
appendix [C.4](#A3.SS4 "C.4 User Preference Profile Construction ‣ Appendix C Prompts Used in the Recommendation Framework ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction").

Tool use is not governed by a fixed multi-step workflow. Within the
prompt-defined tool budgets and action constraints, the agent decides
when to retrieve, inspect items, access preferences, clarify requests,
or recommend.

### 3.3 Task-Anchored User Simulation

SimRec conditions user simulation on the current task need $`z_{x}`$
rather than a reconstructed long-term user profile. The simulator
generates a response to the agent’s action $`a_{t}`$ as

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
u_{t}\sim\pi_{\mathrm{sim}}(\cdot\mid z_{x},a_{t},\mathcal{H}_{t}),
``` |  | (3) |

where $`\mathcal{H}_{t}`$ is the interaction history. For a
recommendation, $`a_{t}`$ includes the proposed item $`i_{t}`$; for a
clarification turn, it contains the agent’s question. The simulator
receives no hidden target ID and generates feedback grounded in the task
need and interaction history. The environment separately determines
recommendation success by checking whether $`i_{t}\in\mathcal{Y}_{x}`$.
SimRec supports both a fixed external LLM as the simulator and
shared-parameter self-play with role-specific prompts.

### 3.4 Tool-Integrated Policy Optimization

#### 3.4.1 Multi-turn GRPO

We apply Group Relative Policy Optimization (GRPO) [Shao et al.
(2024)](#bib.bib47) over complete multi-turn trajectories. For each task
$`x`$, the old policy samples a group
$`\mathcal{G}(x)=\{\tau_{1},\ldots,\tau_{G}\}`$, where each trajectory
receives reward $`R_{i}=R(\tau_{i})`$. Its group-normalized advantage is
$`\hat{A}_{i}=(R_{i}-\mu_{x})/(\sigma_{x}+\epsilon)`$, where $`\mu_{x}`$
and $`\sigma_{x}`$ are the mean and standard deviation of rewards within
the group. For token $`y_{i,k}`$ generated under context $`c_{i,k}`$, we
define the policy ratio as
$`\rho_{i,k}(\theta)=\pi_{\theta}(y_{i,k}\mid c_{i,k})/\pi_{\theta_{\mathrm{old}}}(y_{i,k}\mid c_{i,k})`$.
The per-token clipped objective is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\begin{split}\ell_{i,k}=\min\bigl\{&\rho_{i,k}\hat{A}_{i},\\
&\operatorname{clip}(\rho_{i,k},1-\epsilon_{c},1+\epsilon_{c})\hat{A}_{i}\bigr\}.\end{split}
``` |  | (4) |

For readability, define the token-wise KL term
$`D_{i,k}^{\mathrm{KL}}=D_{\mathrm{KL}}\bigl(\pi_{\theta}(\cdot\mid c_{i,k})\,\|\,\pi_{\mathrm{ref}}(\cdot\mid c_{i,k})\bigr)`$.
The final optimization objective becomes

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle J(\theta)`$ | $`\displaystyle=\mathbb{E}\Bigl[\frac{1}{|\mathcal{M}|}\sum_{(i,k)\in\mathcal{M}}\bigl(\ell_{i,k}-\beta D_{i,k}^{\mathrm{KL}}\bigr)\Bigr].`$ |  | (5) |

Here, $`\mathcal{M}`$ denotes the optimized tokens; all tokens in a
trajectory share its advantage $`\hat{A}_{i}`$. External-LLM simulation
updates only recommender tokens, while shared-parameter self-play
jointly optimizes both roles for recommendation success.

#### 3.4.2 Task-Aligned Reward

The trajectory reward combines recommendation quality, natural
retrieval, and effective tool use, with a unified penalty for redundant
and overly long interactions:

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle R(\tau)=\operatorname{clip}\bigl(`$ | $`\displaystyle\lambda_{\mathrm{rec}}R_{\mathrm{rec}}+\lambda_{\mathrm{tool}}R_{\mathrm{tool}}`$ |  | (6) |
|  |  | $`\displaystyle+R_{\mathrm{fmt}}-P(\tau),R_{\min},R_{\max}\bigr).`$ |  |  |

Recommendation Reward. We define
$`R_{\mathrm{rec}}=R_{\mathrm{hit}}+R_{\mathrm{ret}}`$, where
$`R_{\mathrm{hit}}=\mathbb{I}[i_{\mathrm{final}}\in\mathcal{Y}_{x}]`$
and is zero if no final recommendation is produced. To provide a denser
retrieval signal, let $`\mathcal{Q}_{\mathrm{nr}}(\tau)`$ denote
non-redundant searches, i.e., previously unseen normalized queries whose
Top-$`K`$ results contain at least one new item. We define

|  |  |  |  |
|----|----|----|----|
|  |
``` math
R_{\mathrm{ret}}(\tau)=\max_{q_{j}\in\mathcal{Q}_{\mathrm{nr}}(\tau)}\operatorname{NDCG}@K(L_{j},\mathcal{Y}_{x}),
``` |  | (7) |

and set $`R_{\mathrm{ret}}=0`$ if no non-redundant search occurs. We use
binary-relevance NDCG@K, computed as the ratio of DCG@K to IDCG@K. For
single-target tasks, it reduces to the discounted gain determined by the
target rank. Retrieval rewards are computed from natural, uninjected
results.

Tool-Use Reward. We reward valid use of each tool category:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\begin{split}R_{\mathrm{tool}}={}&\lambda_{\mathrm{search}}R_{\mathrm{search}}+\lambda_{\mathrm{inspect}}R_{\mathrm{inspect}}\\
&+\lambda_{\mathrm{pref}}R_{\mathrm{pref}}.\end{split}
``` |  | (8) |

where $`R_{a}=\mathbb{I}[N_{a}^{\mathrm{valid}}(\tau)>0]`$ for
$`a\in{\mathrm{search},\mathrm{inspect},\mathrm{pref}}`$. Invalid,
failed, or redundant calls do not count, so each tool type contributes
at most once per trajectory.

Format Reward. $`R_{\mathrm{fmt}}`$ rewards each recommendation
containing a parseable item ID and a nonempty description, regardless of
target match.

Interaction Penalty. Let
$`\delta_{\mathrm{rep}}(\tau)=\mathbb{I}[\operatorname{norm}(q^{+})=\operatorname{norm}(q^{-})]`$
indicate query repetition. The interaction penalty is

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle P(\tau)={}`$ | $`\displaystyle\lambda_{\mathrm{repeat}}\delta_{\mathrm{rep}}(\tau)`$ |  | (9) |
|  |  | $`\displaystyle+\min\bigl\{P_{\max},\,\lambda_{\mathrm{len}}[N_{\mathrm{turn}}(\tau)-T_{\mathrm{free}}]_{+}\bigr\}.`$ |  |  |

Here, $`q^{-}`$ and $`q^{+}`$ are the highest-scoring natural queries
before and after the first corrective feedback. We set
$`\delta_{\mathrm{rep}}=0`$ if either is unavailable, and
$`[a]_{+}=\max(a,0)`$.

#### 3.4.3 Dynamic Retrieval Mechanism

For query $`q_{t}`$, the retriever returns
$`L_{t}=\operatorname{Retrieve}_{K}(q_{t})`$, but the agent sees only
$`V_{t}=L_{t}[:k]`$, where $`k\leq K`$. Reformulating queries across
turns exposes different candidates and expands trajectory-level recall
coverage. To address the sparse training signal over large catalogs,
when a target remains outside the visible list we inject a selected
$`y_{x}\in\mathcal{Y}_{x}`$ after at least $`N`$ user turns:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\begin{gathered}n_{\mathrm{user}}(t)\geq N,\qquad y_{x}\notin V_{t}\\
\Longrightarrow\quad\widetilde{V}_{t}=\operatorname{RandInsert}(V_{t},y_{x}).\end{gathered}
``` |  | (10) |

Here, $`\operatorname{RandInsert}`$ inserts the target at a uniformly
random position in the visible candidate list, avoiding a fixed
positional cue. It preserves learning opportunities for candidate
comparison when retrieval misses the target, following controlled
candidate-construction strategies in agentic recommendation [Wang et al.
(2026)](#bib.bib46). Retrieval rewards are always computed from
uninjected results, and target injection is disabled during evaluation
to prevent information leakage.

## 4 Experiments

### 4.1 Experimental Setup

Datasets. We evaluate SimRec on ESCI [Reddy et al. (2022)](#bib.bib1),
which provides query–product relevance annotations, and Amazon C4 [Hou
et al. (2026)](#bib.bib2), which contains complex shopping requests. We
use five ESCI categories and four Amazon C4 categories. For Amazon C4,
we collect user histories from the original Amazon Reviews 2023 data and
make them available through the preference tool.

Evaluation Metrics. We report instance-weighted NDCG@100 and Recall@100
for retrieval quality, and Hit@1 for the final recommendation. For
agents, retrieval metrics take the maximum across all non-redundant
natural search turns on its Top-100 results, while Hit@1 measures
whether the final recommended item belongs to the target set. For
standalone retrievers, Hit@1 equals Recall@1. Target injection is
disabled during evaluation.

Baselines. We compare SimRec against these baselines: standalone
retrievers (BM25 [Robertson and Zaragoza (2009)](#bib.bib7), Qwen3
Dense [Zhang et al. (2025a)](#bib.bib4), and BLAIR-BASE/LARGE [Hou et
al. (2026)](#bib.bib2)); training-free LLM-based recommenders
(GP-VisualPrompt [Xi et al. (2025)](#bib.bib11) and ChatCRS [Li et al.
(2025a)](#bib.bib21)); trainable LLM-based recommenders (Rec-R1 [Lin et
al. (2025)](#bib.bib41), RetPO [Yoon et al. (2025)](#bib.bib8), and
MiniELM [Nguyen et al. (2025)](#bib.bib48)); and LLM backbone baselines
run within the SimRec framework (Qwen3-4B Base [Yang et al.
(2025)](#bib.bib3), Qwen-Plus¹¹ 1
[https://help.aliyun.com/en/model-studio/qwen-plus](https://help.aliyun.com/en/model-studio/qwen-plus),
DeepSeek-V3.2 [DeepSeek-AI et al. (2025)](#bib.bib9),
DeepSeek-V4-Flash [DeepSeek-AI et al. (2026)](#bib.bib10),
Kimi-K2.6 [Team et al. (2026)](#bib.bib5), and GLM-5.1 [GLM-5-Team et
al. (2026)](#bib.bib6)). Agent-based methods use Qwen3 Dense by default;
BM25 variants assess sparse retrieval.

Implementation Details. SimRec uses Qwen3-4B with Qwen3 Dense as its
default retriever. Each search returns $`K=100`$ items, with the top
$`k=20`$ visible to the agent. During training, target injection is
enabled after at least $`N=2`$ user turns if the selected target remains
absent from the visible candidates. Feedback is generated by a fixed
Qwen3.6-Plus simulator²² 2
[https://help.aliyun.com/en/model-studio/qwen3-6-plus](https://help.aliyun.com/en/model-studio/qwen3-6-plus)
by default; we evaluate shared-parameter self-play separately. GRPO uses
$`G=8`$, a learning rate of $`5\times 10^{-7}`$, clipping coefficient
$`\epsilon_{c}=0.2`$, and KL coefficient $`\beta=10^{-3}`$. Agent

### 4.2 Main Results

Overall Performance. On ESCI
(Table [1](#S4.T1 "Table 1 ‣ 4.1 Experimental Setup ‣ 4 Experiments ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")),
SimRec-4B improves NDCG@100, Recall@100, and Hit@1 from
32.23/72.03/21.20 to 35.42/77.91/24.08, respectively, outperforming
compared training methods. NDCG@100 improves over Qwen3-4B Base in all
five product categories, most strongly in Electronics (+7.66 percentage
points). SimRec also exceeds the strongest alternative backbone’s NDCG
(GLM-5.1, 34.99) and the task-aligned baselines. These results support
the introduction’s distinction between supplying an agent with tools and
learning how to use them over a complete interaction; the behavioral
analyses below examine what changes in the policy.

Retrieval coverage and final choice remain distinct bottlenecks. On
Amazon C4, SimRec reaches the best aggregate NDCG@100 of 24.72 versus
22.94 for Qwen3-4B Base, Recall@100 and Hit@1 increase by 2.97 and 1.45
percentage points respectively. However, BLAIR-LARGE, an Amazon-trained
retriever, achieves higher Recall (63.01 vs. 59.18), while larger LLMs
such as Kimi-K2.6 achieve higher Hit@1. SimRec nevertheless achieves the
highest aggregate NDCG@100 among the compared methods. This suggests
that its main advantage lies in better candidate retrieval rather than
retrieval recall alone.

Different Retrieval Backends. To test robustness to the retriever, we
replace Qwen3 Dense with BM25. SimRec-4B improves NDCG@100/Recall@100
from 19.68/53.94 to 24.02/65.37 on ESCI and from 7.68/21.84 to
15.88/40.77 on Amazon C4 over standalone BM25, showing that its gains
persist with a weaker sparse backend. The larger relative gains further
suggest that interaction can partly compensate for weaker retrieval.
Retrieval gains also extend to the 1.7B backbone
(Appendix [A.4](#A1.SS4 "A.4 Additional 1.7B Results ‣ Appendix A Additional Experimental Details ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction"));
the evaluated general benchmarks show no systematic degradation after
post-training
(Appendix [A.5](#A1.SS5 "A.5 General Benchmark Retention ‣ Appendix A Additional Experimental Details ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")).

Different components address distinct recommendation needs. We conduct
component ablations on Amazon C4
(Table [3](#S4.T3 "Table 3 ‣ 4.3 Ablation Study ‣ 4 Experiments ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")).
Removing user preferences causes the largest NDCG@100 drop (3.55
points), whereas removing item-detail inspection yields the largest
Hit@1 drop(3.72 points). This distinction suggests that preferences help
guide candidate retrieval and ranking, while item details support more
detailed verification before recommendation decision. Disabling
multi-turn feedback further reduces NDCG@100 and Hit@1, respectively.
Thus, even with preference and item-detail tools available, the agent
cannot fully compensate for the absence of corrective user feedback,
which provides task-specific information for revising earlier decisions.
Further domain-level results are provided in
Appendix [B](#A2 "Appendix B Additional Ablation Analyses ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction").

Intermediate rewards and the final hit serve complementary purposes. At
training step 500 on ESCI
(Table [3](#S4.T3 "Table 3 ‣ 4.3 Ablation Study ‣ 4 Experiments ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")),
removing retrieval or tool-use rewards reduces Hit@1 by 2.64 or 2.88
points, despite retaining the final-hit objective. These results suggest
that rewarding evidence acquisition helps improve downstream
recommendation decisions rather than merely encouraging tool use.
Conversely, removing the hit reward lowers NDCG@100 by 6.93 points and
Hit@1 by 2.94 points, indicating that intermediate rewards alone cannot
replace the final outcome signal. Together, these findings support
jointly optimizing evidence acquisition and recommendation accuracy
through trajectory-level rewards.

highlighted in the introduction: useful feedback, recovery after
rejection, tool use, and candidate ranking.

#### 4.4.4 Training Dynamics

Natural retrieval improves while target injection declines. From the
first to the last training window
(Figure [5](#S4.F5 "Figure 5 ‣ 4.4.2 Recovery Analysis ‣ 4.4 Analysis ‣ 4 Experiments ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")),
the Top-10 hit rate rises from 61.81% to 68.52%, indicating that targets
are increasingly ranked near the top. Meanwhile, the Top-100 miss rate
falls from 19.70% to 14.50%, indicating improved retrieval coverage.
Early in training, 38.18% of eligible trajectories require target
injection; even after multiple turns, the target is still absent from
the candidates visible to the agent. The injection rate subsequently
declines to 31.48% as natural retrieval improves. Detailed statistics
are provided in
Appendix [B.3](#A2.SS3 "B.3 Additional Training Diagnostics ‣ Appendix B Additional Ablation Analyses ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction").

SimRec learns a more active tool-use policy. SimRec also exhibits a more
active evidence-seeking policy, with average tool use increasing from
2.43 to 5.19 calls per session. Most of this increase comes from
item-detail inspection (0.58 to 1.83 calls) and preference-tool calls
(0.02 to 0.86), indicating greater use of both product- and
user-specific evidence. Moreover, sessions with more calls have lower
average task reward
(Appendix [B.4](#A2.SS4 "B.4 Tool-Use Behavior Analysis ‣ Appendix B Additional Ablation Analyses ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")),
consistent with harder sessions prompting further investigation.
Together with the component ablations, these results suggest that
training changes how SimRec gathers evidence
(Section [4.3](#S4.SS3 "4.3 Ablation Study ‣ 4 Experiments ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction"))
during interaction.

## 5 Conclusion

We present SimRec, which trains a tool-integrated recommendation agent
over complete interactions using task-anchored feedback and
trajectory-level rewards. SimRec outperforms retrieval, training-free,
and task-aligned baselines in overall NDCG@100 on ESCI and Amazon C4,
while improving over its untrained 4B backbone. Fixed-candidate
reranking and recovery analyses further show better product selection
and more effective revision after rejection. These results demonstrate
the value of learning to gather evidence, recommend, and revise within a
single interaction policy.

## Limitations

SimRec relies on LLM-based user simulation to train multi-turn
recommendation policies. Although feedback is grounded in the current
task need, simulated responses may not fully capture real users’
preferences and behaviors. Improving simulator fidelity and evaluating
SimRec through real-user interactions remain important directions for
future work.

To address sparse recommendation rewards, SimRec employs target
injection during training. Although injection is disabled during
evaluation, this introduces a discrepancy between training and
inference. Developing more effective training strategies without target
injection could further improve the robustness of the learned policy.

Our experiments primarily cover ESCI and Amazon C4 with Qwen3-4B and a
smaller 1.7B backbone. Performance also varies across user simulators
and retrieval backends. Generalization to larger models, broader product
domains, and more diverse interaction settings remains to be explored.

## Appendix A Additional Experimental Details

### A.1 Implementation

The recommender is initialized from Qwen3-4B. The retrieval backend
returns $`K=100`$ items, with the top $`k=20`$ visible by default.
Training-only target injection is enabled after $`N=2`$ user turns if
the target remains absent from the visible list. GRPO uses learning rate
$`5\times 10^{-7}`$, rollout batch size 8, group size $`G=8`$,
temperature 1.0, top-p 1.0, clipping coefficient 0.2, and KL coefficient
$`10^{-3}`$. The external simulator is Qwen3.6-Plus, with temperature
0.2, maximum output length 220 tokens and seed 42. Rewards are clipped
to $`[0,2.5]`$. Duplicate queries receive no additional valid-search
bonus; unchanged feedback queries incur a 0.05 penalty. Length penalties
start after four turns, increase by 0.02 per additional turn and are
capped at 0.20. The recommendation reward weight and retrieval NDCG
scale are both 1.0. The format reward is 0.01; valid search,
item-detail, and preference bonuses are 0.03, 0.01, and 0.01.

### A.3 Controlled Reranking Construction

We construct the ESCI reranking set with BM25 as the only upstream
retriever. BM25 searches the product contents field with $`k_{1}=1.2`$
and $`b=0.75`$, returns the Top-20 candidates, and filters out instances
whose upstream NDCG@20 is zero. We retain the first 16 candidates after
filtering, resulting in 345 valid examples from the 901-instance local
ESCI test set across Baby Products, Office Products, Sports and
Outdoors, Video Games, and Electronics. To prevent the model from
copying the upstream order, each candidate list is shuffled with random
seed 42, while retrieval_score and retrieval_type are hidden. The random
input order serves as the no-reranking baseline.

### B.4 Tool-Use Behavior Analysis

We further analyze the tool-use behavior of SimRec on the test sessions.
We compare against the Qwen3-4B base policy evaluated on the same test
set.

##### Tool-use frequency.

Table [15](#A2.T15 "Table 15 ‣ Tool-use frequency. ‣ B.4 Tool-Use Behavior Analysis ‣ Appendix B Additional Ablation Analyses ‣ SimRec: Learning to Search, Ask, and Recommend from Simulated Interaction")
summarizes the average number of tool calls and interaction turns per
session. SimRec invokes external tools more actively than the base
policy, with 5.19 tool calls per session compared with 2.43 for
Qwen3-4B. The largest increases come from item-detail inspection (1.83
vs. 0.58 calls per session) and preference queries (0.86 vs. 0.02),
while the increase in search calls is more moderate (2.50 vs. 1.83).
SimRec also produces longer interaction trajectories on average (9.05
vs. 6.28 turns).

Importantly, the tool-use reward in SimRec is not assigned independently
to every tool invocation. Instead, it serves as a trajectory-level
binary shaping signal for each tool type: once a tool type has been
invoked validly within a session, subsequent calls to the same tool type
do not provide additional tool-use reward. Multiple calls remain
permissible when they are needed for task completion—for example, the
policy may inspect several different candidate items using the
item-detail tool—but these additional calls do not accumulate extra
$`R_{\mathrm{tool}}`$. The purpose of this reward component is therefore
to encourage the policy to learn valid use of the available tools,
rather than to reward a larger number of calls.

| Item-detail calls / session | 1.83   | 0.58 |

##### Tool-call count and task performance.

To examine whether the higher tool-use frequency could itself provide a
systematic reward advantage, we stratify SimRec trajectories by their
total number of tool calls. The results are shown in

Recommendation quality and final trajectory reward do not increase with
the number of tool calls. Sessions with zero to two calls achieve the
highest NDCG@100, Recall@100, Hit@1, and average reward, whereas
sessions involving five or more calls are substantially more difficult.

| Metric      | 0–2    | 3–4    | $`\geq 5`$ |
|-------------|--------|--------|------------|
| Sessions    | 120    | 268    | 1,334      |

The strong association between longer tool-use trajectories and lower
task performance should not be interpreted as evidence that additional
tool use causes worse recommendations. A more plausible explanation is
selection by task difficulty: easy sessions can often be resolved after
the initial retrieval or a small number of inspections, while difficult
or unresolved sessions trigger further search, item inspection, and
preference consultation. Nevertheless, this analysis rules out a simple
interpretation in which repeatedly invoking tools provides a reliable
way to increase the trajectory-level objective. In particular, repeated
calls to an already used tool type cannot accumulate additional
$`R_{\mathrm{tool}}`$, and empirically the final reward does not
increase with total tool-call count.

Overall, the analysis suggests that post-training changes not only the
final ranking behavior but also the interaction policy: SimRec is more
willing to consult external evidence, especially item details and user
preferences, when the current recommendation remains unresolved. At the
same time, $`R_{\mathrm{tool}}`$ should be understood as a lightweight
tool-validity shaping signal rather than a direct measure of the
marginal utility of each individual tool invocation.
