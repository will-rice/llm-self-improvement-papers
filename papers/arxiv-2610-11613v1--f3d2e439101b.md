# ABSTRACT

An agent can complete a task without improving how it works. Turning task experience into reusable capability requires connecting the changed component to its evaluation and subsequent use. We present AgentEvolver, a system for developing capabilities during task execution while keeping the foundation model fixed. Eight entity families expose reusable operations, methods, agents, control flow, interfaces, and supporting state to revision through a common versioned lifecycle. A shared Runtime coordinates ongoing work, while persistent planning and recoverable context preserve task direction and supporting evidence. We evaluate task outcomes on SWE-bench Pro Public and examine capability changes in six application cases. The team reports an 82.08% resolution rate with evolution, exceeding its reported baseline without evolution. The cases show retained capabilities entering later website, game, and research work, while also documenting incomplete objectives and an unsuccessful strategy. These findings distinguish improvement in a reusable component from success on the final task. AgentEvolver provides a concrete basis for studying capability accumulation through execution; independent-task transfer and total development cost remain open questions.

# 1 INTRODUCTION

Imagine a mind in a glass vessel that knows how a telescope works but cannot adjust its lens. Given a robot body and an observatory to restore, it can act, yet its first image is blurred. A better probe alone will not solve the problem: the instrument interface must supply the right measurements, the calibration method must use them correctly, and specialist robots must coordinate their work. The assignment gradually changes both the observatory and the system repairing it. Figure [1](#page-1-0) illustrates how the branches connect an initial failure to a tested revision and collaborative delivery.

The story leaves two outputs: a repaired observatory and capabilities that can be used again. Software agents face a similar opportunity. Fixing a repository can reveal a missing diagnostic operation; revising a website can expose an inadequate review method; testing a hypothesis can require a more reproducible research environment. A useful response may therefore change the current deliverable, the agent's means of working, or both. This motivates our research question: _how can task execution develop reusable capabilities with inspectable evidence of evaluation and subsequent use?_

Existing agents already turn interaction into retained feedback and executable skills [\(Shinn et al.,](#page-13-0) [2023;](#page-13-0) [Wang et al.,](#page-13-1) [2023\)](#page-13-1). Agent-program search and modification during execution further make the agent's own software an object of adaptation [\(Hu et al.,](#page-12-0) [2025;](#page-12-0) [Zhang et al.,](#page-13-2) [2026a;](#page-13-2) [Xia et al.,](#page-13-3) [2025\)](#page-13-3). These developments motivate a systems question: how should heterogeneous revisions coexist with an unfinished task, its resource budget, and the evidence supporting earlier decisions? AgentEvolver focuses on the interfaces and execution mechanisms needed to maintain those connections.

The challenge is maintaining consistency while work and capabilities change together. A revised interface may invalidate a specialist's assumptions; an evaluation may refer to a version that has since been replaced; a context summary may omit why a candidate was rejected. These problems become

We call the supported scope _global capability evolution_: Tool, Skill, Agent, Workflow, Connector, Environment, Memory, and Plugin can change while the foundation model remains fixed. - A system model for capability evolution during task execution. Eight heterogeneous component families share version identities and an evidence lifecycle linking construction, evaluation, retention, and use.
- Continuity across task and capability changes. A shared Runtime, persistent planning, and recoverable context management coordinate capability development with the original objective, its dependencies, and its resource budget.

# <span id="page-2-0"></span>2 RELATED WORK

Prior work makes experience reusable through several mechanisms: feedback stored for another attempt, executable skills, revised agent programs, and learned model parameters. We organize the comparison around the object of adaptation and the stage at which it changes. AgentEvolver focuses on heterogeneous software components revised during an unfinished task, with a common connection between execution, version identity, and retention evidence.

# 2.1 FEEDBACK AND REUSABLE CAPABILITIES

ReAct [\(Yao et al.,](#page-13-4) [2023\)](#page-13-4) interleaves reasoning and action with environmental observations. Reflexion [\(Shinn et al.,](#page-13-0) [2023\)](#page-13-0) uses retained verbal feedback to influence later attempts, while Voyager [\(Wang](#page-13-1) [et al.,](#page-13-1) [2023\)](#page-13-1) develops an executable skill library through exploration and refinement in Minecraft. These approaches demonstrate that useful experience can reside outside model parameters. AgentEvolver makes the retained object explicit: a task record, an operating method, and an executable operation have different interfaces and evaluation requirements. The component model preserves these distinctions within a common process of development, evaluation, and use.

Toolformer [\(Schick et al.,](#page-13-5) [2023\)](#page-13-5) trains a language model to select and use APIs through self-supervised examples. This changes the model's tool-use behavior. AgentEvolver instead holds the foundation model fixed and permits changes to the surrounding capability system. The distinction concerns the object being adapted: learning when to call an existing API and revising the operation or method exposed to the agent require different evaluations.

# 2.2 AGENT DESIGN AND RUNTIME SELF-MODIFICATION

DSPy [\(Khattab et al.,](#page-12-1) [2023\)](#page-12-1) optimizes modular language-model pipelines, while Automated Design of Agentic Systems [\(Hu et al.,](#page-12-0) [2025\)](#page-12-0) searches over agent programs using an archive and evaluation feedback. The Darwin Gödel Machine [\(Zhang et al.,](#page-13-2) [2026a\)](#page-13-2) develops an expanding archive of modified coding agents. These approaches place different parts of agent software within an optimization process. AgentEvolver emphasizes the infrastructure in which heterogeneous revisions are constructed, evaluated, and consumed during a continuing task. The acting agent supplies the proposal policy, while the framework maintains component identities and evidence throughout development.

Live-SWE-agent [\(Xia et al.,](#page-13-3) [2025\)](#page-13-3) modifies its scaffold while solving software-engineering tasks, making it particularly close in adaptation timing. AgentEvolver studies the coordination requirements of this setting across a broader collection of component interfaces. Process ownership, recoverable task state, and version-specific observations allow several changes to participate in the same continuing task. The contribution concerns how those changes are managed and examined. These experiments do not establish superiority over Live-SWE-agent in a controlled comparison.

Hyperagents [\(Zhang et al.,](#page-13-6) [2026b\)](#page-13-6) combine a task agent and the meta-level modification procedure within an editable program. This extends adaptation to the mechanism that generates future revisions. AgentEvolver's present contribution is complementary: it defines how component changes are executed, identified, assessed, and reused. Its eight-family scope does not establish recursive improvement of the revision procedure; that claim requires a separate longitudinal comparison.

Self-questioning, self-navigating, and self-attributing are the three mechanisms studied in AgentEvolver: Towards Efficient Self-Evolving Agent System [\(Zhai et al.,](#page-13-7) [2025\)](#page-13-7). Its emphasis is task generation, exploration, and differentiated reward assignment. The present report examines versioned software capabilities during execution with a fixed foundation model. These approaches change different parts of an agent, so their evaluation must identify the object of adaptation.

# 2.3 COORDINATION, CONTEXT, AND EVALUATION

AutoGen [\(Wu et al.,](#page-13-8) [2023\)](#page-13-8) organizes configurable multi-agent conversations, while MetaGPT [\(Hong](#page-12-2) [et al.,](#page-12-2) [2024\)](#page-12-2) structures collaboration through roles and operating procedures. These systems establish coordination as an explicit design concern. AgentEvolver connects coordination to capability development: Runtime associates processes and operations with owners, resources, and observable lifecycle states. These mechanisms preserve the relation between delegated work and the candidate version it produces. Ablations are needed to quantify the contribution of each mechanism.

Generative Agents [\(Park et al.,](#page-12-3) [2023\)](#page-12-3) combine memory, reflection, and planning to support continuing behavior. MemGPT [\(Packer et al.,](#page-12-4) [2024\)](#page-12-4) manages information across model context and external storage. Evidence that retrieval performance depends on where information appears in a long context [\(Liu et al.,](#page-12-5) [2023\)](#page-12-5) further motivates evaluating what the agent can recover, rather than considering context length alone. AgentEvolver separates the current Plan, working context, and archived observations so that the agent can recover both its task direction and the observations supporting a capability decision.

# 2.4 TASK EVALUATION AND ADAPTIVE SELECTION

SWE-bench [\(Jimenez et al.,](#page-12-6) [2024\)](#page-12-6) evaluates repository issue resolution, SWE-agent [\(Yang et al.,](#page-13-9) [2024\)](#page-13-9) examines the agent-computer interface, and SWE-bench Pro [\(Deng et al.,](#page-12-7) [2025\)](#page-12-7) extends evaluation to challenging software-engineering tasks. Task identity, available feedback, resource limits, and grading conditions govern what comparisons support. We distinguish our reported internal intervention from external reference values under different conditions. Repeated selection on observed feedback can also bias an evaluation [\(Cawley & Talbot,](#page-12-8) [2010;](#page-12-8) [Dwork et al.,](#page-12-9) [2015\)](#page-12-9); our case analysis therefore separates development comparisons, later use, and independent held-out assessment.

# 3 AGENTEVOLVER

# 3.1 PROBLEM SETTING AND DESIGN REQUIREMENTS

Consider a task q with a deliverable criterion, an initial capability collection, and a finite resource budget. The foundation model remains fixed. An execution changes both the requested artifact and the reusable means of producing it. To describe these changes, we distinguish six parts of the execution state:

<span id="page-3-0"></span>
$$S_t = (D_t, \mathcal{L}_t, A_t, R_t, H_t, b_t). \tag{1}$$

Here D<sup>t</sup> is the deliverable state; L<sup>t</sup> is the archive of admitted component versions; A<sup>t</sup> identifies active versions; R<sup>t</sup> records processes, invocations, and ownership; H<sup>t</sup> contains planning and interaction records; and b<sup>t</sup> is the remaining budget. This notation separates the historical record of a revision from the version currently available for task execution.

Ordinary task actions operate on D<sup>t</sup> using capabilities selected through At. Evolution actions can add an archived version to Lt, change the active selection, or append evaluation and decision records to Ht. Both kinds of work share Runtime and budget accounting. A candidate may become provisionally active before functional evaluation, so archive membership, current availability, and justified retention are distinct properties. The final task is assessed against its deliverable criterion; a capability claim is assessed against a named version, comparison conditions, and observed consumers.

Three design requirements follow. Identity must survive later edits so that an evaluation continues to refer to the component that was tested. Continuity must preserve task direction and execution ownership while the agent develops a candidate. Evidence must connect a retention decision to actual observations and subsequent use. # 3.2 EIGHT EVOLUTION SURFACES AND THE UNIT OF CHANGE

Table [1](#page-4-1) summarizes the eight families. Tool, Skill, Agent, Workflow, Connector, and Plugin participate in the callable capability roster. Environment supplies mounted state and actions, and Memory is supplied internally through its owning subsystem. Their shared identity is a tuple (f, n, v): family, registered name, and version. Common discovery and versioning let an agent find and revise capabilities without requiring every family to behave like a stateless function.

The appropriate change surface depends on the consumer. A bounded operation suggests a Tool; a procedure requiring judgment across observations suggests a Skill. A specialist with separate instructions and context suggests an Agent, while reusable control flow suggests a Workflow. Provider access and shared services motivate Connector and Plugin changes. Environment and Memory change the system's observation or retention mechanisms. These interfaces allow a task to combine revisions without requiring every component to behave like a stateless function.

The component definition, its instances, and its stored content must remain distinguishable. Dispatching another worker from an unchanged definition creates an Agent process; revising its instructions or mounted capabilities changes the reusable Agent. An Agent prompt therefore belongs to that family rather than forming a ninth entity. Likewise, writing a fault record is a Memory-content update, while revising its indexing or retrieval implementation changes the Memory component. Updating today's Plan differs from changing a reusable Workflow. These distinctions prevent ordinary task activity from being counted automatically as capability evolution.

The extension layer archives the bytes admitted for each version and rejects different content submitted under an existing immutable version. Family-specific managers remain responsible for loading the component and its domain state. A Skill retains its manifest, scripts, and references; a service Plugin can retain shared clients and configuration; a Workflow retains its control structure. Version identities make these heterogeneous artifacts addressable by evaluations and later consumers, while preserving the representation appropriate to each family.

# 3.3 RUNTIME: COORDINATING WORK WHILE CAPABILITIES CHANGE

Capability development must coexist with the work that motivated it. Runtime separates persistent Agent processes from bounded component invocations. A process owns its conversation, mailbox, and child work; a component invocation records a particular operation and its result. Workers can complete an assignment, resident services can accept further requests, and subscribers can react to addressed topics. Explicit lifecycle states let a coordinator distinguish completed work from waiting or suspended work before deciding whether a revision is ready to use.

Operations pass through a common invocation boundary that records their owner, parent call, component identity, and execution status. Declared shared and exclusive resource claims control conflicting access. This matters when one branch revises an artifact that another branch is inspecting: concurrency should follow available independence information. The common boundary also lets evaluation records connect observations to the executed component version.

Ownership continues through interruption and cleanup. A parent must stop and join its children before completing its own exit, and an in-flight synchronous operation retains its resource claims until it finishes. Suspension occurs at defined boundaries between steps. These rules keep unfinished activity visible when a task pauses or changes direction. They coordinate declared operations; uncertain external effects still require reconciliation after an interruption.

The root run and its descendants share resource accounting, including later turns of resident processes. Candidate construction, failed attempts, evaluation, and actual consumption therefore belong to the cost of the original task. Reported, estimated, and unknown usage remain distinguishable. This accounting supports a meaningful comparison between evolving and fixed configurations: a faster retained Tool can still be expensive to obtain, and reporting only its final invocation would omit that development cost. Appendix [A](#page-14-0) details these execution contracts.

#### 3.4 PLAN AND CONTEXT: PRESERVING DIRECTION AND EVIDENCE

Planning and memory support continuing agent behavior [\(Park et al.,](#page-12-3) [2023\)](#page-12-3). In our setting, a capability revision is a subproblem within the original assignment. Plan preserves that relationship through a compact current index linked to detailed records of objectives, acceptance criteria, dependencies, and decisions. The latest index is included before model requests; supporting records are retrieved when needed. This division keeps immediate direction accessible without repeatedly placing every historical detail in the working context. A completed plan entry expresses the agent's judgment, while deliverable acceptance remains a separate evaluation.

Hierarchical context management separates the material immediately available to a model from information retained in external storage [\(Packer et al.,](#page-12-4) [2024\)](#page-12-4). AgentEvolver combines stable instructions, a checkpoint summary, and recent complete interactions. Updated Plan and environment observations enter the conversation before request assembly. When older interactions are compacted, the system retains an archive and checks whether the proposed summary reduces the complete request; otherwise it restores the original history. Recent cycles of calls and results remain intact. The design reduces working-context pressure and preserves access to omitted details. The agent must still retrieve and assess the evidence relevant to its next decision.

### 3.5 FROM AN OBSERVED GAP TO A RETAINED CAPABILITY

The acting agent chooses when and how to propose a change under the task's instructions and remaining budget. A proposal identifies a consumer need, the current limitation, and observations that expose it. The acceptance criterion is domain-dependent: an interface may need aligned dates, while a diagnostic operation may need identical outputs at lower latency. Verified-improvement tasks require baseline observations before registration. The system supplies the lifecycle and evidence checks; the agent supplies the proposal policy and substantive comparison criterion.

The candidate is authored in its family's representation and submitted for structural admission. A separate isolated interpreter checks loading, construction, and schema requirements; admitted bytes are archived under their version. Registration may provisionally activate the candidate before functional evaluation. This ordering separates two questions: whether the candidate can enter the system and whether its observed behavior justifies retention. Figure [3](#page-6-0) shows the lifecycle, and Table [2](#page-7-1) summarizes the corresponding operations.

Functional evaluation names the exact family, component, and version, describes the baseline, and records expected and observed results for nonempty test cases. Each case references executed calls. A keep decision requires the evaluated version to match the active archived version and to carry passing evidence with the required run fields. Decisions are appended to history. Rollback and unload have separate state-changing operations, so a review must inspect the resulting active state as well as the recorded intention. Failed candidates and replaced versions remain part of the development history. Retention thus records a revisable engineering decision with observed scope, rather than declaring a component universally reliable.

Actual use answers a further question: did the retained capability participate in the work? Verifiedimprovement tasks require a subsequent successful consumer tied to the retained version, together with the task's comparison or reuse evidence. For a Skill, loading the instructions is only the first step; the observations must show the method being applied. Final deliverable acceptance is evaluated separately. Admission, functional evaluation, adoption, and later use are therefore distinct events. Evidence for one does not establish that the others occurred.

The interfaces compose along task dependencies. In LUMEN, a source Connector emits an evidence packet, a specialist Agent authors an inquiry from that packet, and a review Skill checks the route's claims and measurements. Revising the source contract can therefore require corresponding changes to authoring and review. Version identities and call records make the combined chain inspectable, while the domain criterion determines whether its output is acceptable. This chain illustrates the method in a case whose component families were prescribed by the task.

The comparison itself is domain-dependent. An astronomy interface must preserve relevant dates and reference frames; a voyage review must control the saved starting state; a timing comparison must retain the same input workload. A retained version should carry these applicability conditions forward to its consumers. Reuse can then reveal another limitation and motivate a new revision. This closes the task-level development loop while reserving independent-task transfer for an evaluation that freezes the capability library before exposing new consumer feedback.

# 4.1 SWE-BENCH PRO PUBLIC: TASK-LEVEL COMPARISON

Comparison setup. The current coding configuration pair uses the same model route, initial task interface, planning support, and resource limits. The evolution-enabled condition additionally mounts the adoption Tool and self-evolving Skill; the baseline omits them. Table [3](#page-8-0) summarizes this intended intervention. The declared roster contains one coordinator, so the coding comparison does not test the contribution of multi-agent coordination. Launch-time overrides must be recorded to establish the model and resources actually used for a run.

Evaluation and available evidence. The current launcher submits a frozen patch for host-side grading and withholds final grading feedback during solving. The reported totals come from a separate-machine execution. Its raw per-task results, realized configuration, and complete cost records were not available for this analysis; the configuration in Table [3](#page-8-0) therefore describes the inspected setup rather than a verified execution manifest for those totals. Appendix [C](#page-40-0) details the grading boundary and records needed for reconciliation.

Results. The team reports 600/731 resolved tasks with evolution and 578/731 without evolution. The corresponding rates are 82.08% and 79.07%, an absolute difference of 3.01 percentage points and a net increase of 22 resolved tasks. The top pair in Figure [4](#page-9-0) presents this internal comparison. The reported comparison therefore favors the evolution-enabled condition.

The external rows provide context from the website's frozen 19 September 2026 snapshot, which cites the CodingFleet compilation updated on 11 September 2026.[1](#page-8-1) Their original model and system labels are preserved. Differences in models, harnesses, budgets, and grading conditions prevent these rows from isolating an AgentEvolver effect or establishing a controlled product ranking. The relevant internal contrast for RQ1 is the reported with-evolution versus without-evolution pair.

Interpretation. A net increase of 22 does not reveal how many tasks improved or regressed. If b counts tasks solved only with evolution and c counts those solved only without it, the totals determine b−c = 22 but not either count. Task identities must also be reconciled before assuming exact pairing. Consequently, the aggregates do not support a paired significance test, a gain-per-compute estimate, or attribution to any individual subsystem. The evidence for RQ1 is therefore the aggregate difference between the two reported conditions.

Analysis protocol. The unit is a capability-change episode within a continuing project. For each episode, we reconstruct the task requirement, observed limitation, candidate version, comparison, retention decision, and later consumer, then examine the final task outcome separately. Application design. The four websites explore continued collaboration after an initial release. A user changes a source, requests a new interaction, or asks for a different explanation; the builder must revise the product while preserving earlier work and identifying assumptions that no longer hold. Commonspace applies this idea to community evidence, LUMEN to scientific inquiry, ARKBOUND to comparative play, and ORBITAL to astronomical source data. # 4.2.3 CROSS-CASE FINDINGS AND OPEN QUESTIONS

Three patterns answer RQ2. Semantic failures motivate useful revisions: ORBITAL's source dates, Godot's realized font weight, and LUMEN's interpretation of historical observations expose gaps that syntax or schema validation misses. The later consumer is the connection to task work: impact tracing, route review, engine diagnosis, and frozen replay each enter an identified operation after their initial comparison. Local improvement can coexist with an unmet objective: ORBITAL lacks a required review component, Godot remains an unfinished game, and Signal Foundry's selected strategy fails its comparative criterion. The cases therefore support an analysis of specific capability changes and their use, rather than a success rate for the entire platform.

The cases also identify testable questions for further study. Prescribed component families leave open how an unconstrained agent selects a change surface. Connected-project reuse leaves open whether a frozen capability library helps independent tasks. A local operation speedup leaves open whether its savings recover development cost. Appendix [C](#page-40-0) translates these gaps into matched comparisons, held-out consumer studies, and mechanism-specific ablations.

# <span id="page-11-0"></span>5 DISCUSSION AND LIMITATIONS

Evaluation quality. Versioned calls and observations make claims inspectable but do not validate the evaluator's fixtures, baselines, or judgments, especially when the same agent proposes and evaluates a revision. Repeated selection can also overfit development feedback [\(Cawley & Talbot,](#page-12-8) [2010;](#page-12-8) [Dwork et al.,](#page-12-9) [2015\)](#page-12-9). Stronger conclusions require independent acceptance tests, preserved failed attempts, and a frozen candidate before final evaluation. Feedback used for another revision becomes development evidence. Signal Foundry lacked enforced isolation of final evaluation data.

Coverage, attribution, and cost. The six selected cases, some with prescribed families and connected sessions, do not establish platform-wide success rates or gains across all eight families. Website checks also leave user satisfaction and learning outcomes unmeasured. The SWE comparison remains team reported; its raw run package and paired task outcomes are needed for attribution and uncertainty estimates. Generalization and cost effectiveness require frozen capabilities tested on independent consumers under matched budgets, accounting for regressions, abandoned candidates, and total development cost.

Execution and reproducibility. Resource coordination relies on declared access, summaries can omit facts, and interrupted external operations can leave uncertain effects. Admission may provisionally activate a candidate before functional evaluation, while archived source can depend on changing packages or providers. Reproduction therefore requires inputs, dependency and environment records, and execution history alongside source bytes [\(Sandve et al.,](#page-13-10) [2013\)](#page-13-10). Mechanism-specific ablations and recovery tests should assess how Plan, Runtime, and context management affect final task acceptance under these conditions.

# 6 CONCLUSION

AgentEvolver connects task execution to the development of reusable software capabilities. Its central design separates the deliverable, archived and active component versions, and the observations supporting retention. Eight evolution surfaces share execution, planning, and context mechanisms so that capability changes can participate in continuing work. The reported coding comparison favors evolution, and six application cases show how specific changes are evaluated and consumed, including failures to meet the final objective. Together, these observations motivate evaluating an agent through both what it delivers and what it retains. Establishing when retained capabilities generalize and repay their development cost is the next empirical step.

### A.1 TWO COUPLED FORMS OF PROGRESS

A completed deliverable does not establish that a reusable component improved, and retaining a useful component does not establish task completion.

Equation [1](#page-3-0) distinguishes the deliverable Dt, the archive Lt, and the active version map At. Task actions use the active collection to change the deliverable. A capability revision can add an archived version and alter the active selection, while evaluation and decision records explain why it was retained. Structural admission may provisionally activate a candidate before that judgment. Keeping these states separate prevents availability from being interpreted as demonstrated improvement.

The original task supplies the reason to develop a capability. An expensive operation may motivate a Tool revision; a recurring interpretation error may motivate a Skill; incompatible source semantics may motivate a Connector. The relevant comparison follows from the intended consumer. Faster execution with changed outputs is different from faster execution with matched outputs, just as a stricter rejection rule is different from a higher task completion rate. # A.2 EIGHT FAMILIES, DISTINCT OPERATIONAL ROLES

The eight component families share discovery, identity, and version management but retain different execution semantics. Tool, Skill, Agent, Workflow, Connector, and Plugin appear in the callable capability roster. Environment supplies mounted state and native actions. Memory supplies retained context through its owning subsystem rather than appearing as another operation for the model to select. This separation avoids treating every extension as a stateless function while still making its implementation an explicit object of change.

A Tool packages a bounded operation with an input contract. Its output can be checked directly when the intended behavior is deterministic, or assessed under an explicit task criterion when interpretation remains necessary. A Skill instead describes how to work: which observations to obtain, which alternatives to compare, and which failure conditions to examine. Its value depends on application. Loading a Skill's instructions establishes access to the method, but evidence of use must include subsequent actions that follow that method.

An Agent definition specifies reusable behavior, including its instructions and configuration. Instantiating a second worker from an unchanged definition creates another execution, not another evolved entity. A prompt revision belongs to the Agent's behavior and version rather than to a ninth family. This distinction becomes important when a candidate appears to have improved on paper but the running worker still uses an earlier prompt. Evaluation must connect the admitted definition to the behavior actually invoked. ARKBOUND contains a concrete example of this discrepancy.

Connector and Plugin both support multiple related operations, but emphasize different responsibilities. A Connector provides a provider-facing contract: how a source is requested, normalized, qualified, and returned. A Plugin packages a service implementation and operations that may share configuration or a client. Their effects can depend on external state, so source bytes alone may not reproduce a result. A meaningful record also identifies the inputs, provider observations, and state assumptions under which the operation was evaluated.

Environment and Memory expose a further distinction between implementation and content. Updating the state of a research laboratory is ordinary use of an Environment; changing its materialization or evaluation behavior is a component change. Writing a useful note is a memory-content update; changing how notes are indexed or retrieved is evolution of the Memory implementation. Both forms of activity may improve task execution, but counting them together would obscure what the reusable system actually changed.

The family boundary helps select an appropriate intervention. A missing arithmetic operation can become a Tool, while a multi-step diagnostic procedure can remain a Skill that uses existing Tools. A specialist with its own context can become an Agent; recurring executable handoffs can become

a Workflow. Several families may be needed when an error crosses interfaces. LUMEN's source, route-authoring, and review changes illustrate this composition, whereas the brightness measurement in Godot illustrates a narrowly scoped Tool change.

### A.3 VERSIONED DEVELOPMENT AND RETENTION

A component is identified by its family, registered name, and version. Admission archives the payload associated with that identity and rejects different bytes submitted under an existing immutable version. The purpose is referential stability: an evaluation and a later consumer should refer to the same implementation rather than to a name whose meaning changes silently. Family-specific managers still own loading and domain state. A common identity does not erase differences between a method directory, an Agent definition, and a stateful service.

Structural admission checks whether a candidate can enter the system. An isolated interpreter checks the relevant loading, construction, and schema requirements before the admitted bytes are archived. This stage can provisionally activate the candidate, so structural acceptance precedes the final judgment of usefulness. Such activation makes evaluation possible but creates an obligation to inspect the active version afterward. A candidate that loads successfully may still have incorrect behavior, an unsuitable comparison, or an unfulfilled task-level purpose.

Functional evaluation identifies the candidate and baseline, states expected behavior, and associates observations with executed calls. A passing report requires nonempty passing cases, and the adoption mechanism checks the referenced observations and version consistency. These checks establish that the report concerns identifiable execution. They do not independently determine whether the selected fixtures are representative or whether the evaluator's interpretation is sound. Preserving observations separately from judgment allows those scientific questions to be revisited.

Retention connects a passing evaluation to the currently active archived version and records the decision in history. Rejection, replacement, rollback, and unload remain meaningful alternatives. A recorded intention to roll back is not itself the state change: the corresponding operation must execute, and the resulting active version must be checked. Keeping this distinction explicit is useful when a candidate fails after admission or when several revisions are considered in succession. The failed branch remains evidence about the development process.

Subsequent use provides the link from a retained component back to ongoing work. A later consumer should identify the retained version, the new input or task context, and the observed result. Repeating the original fixture confirms repeatability under that fixture; applying the component to another step in the same project establishes task-local use. Independent-task transfer requires a separate evaluation design with an unexposed consumer. These levels form an evidence hierarchy, not interchangeable labels for successful registration.

Cross-family changes require compatibility as well as local improvement. A stricter source packet can invalidate an author's previous assumptions, and a revised authoring procedure can require a different reviewer. The useful unit of comparison may therefore be a chain of versions rather than one isolated component. The current architecture makes the versions addressable and their calls observable. The application cases provide examples of connected use, while systematic tests of compositional gains and regressions remain a separate empirical question.

# A.5 RESOURCE COORDINATION AND BOUNDED DELEGATION

Component invocations carry an owner, a parent call, timing, state, and declared resource claims. The invocation service coordinates admission across component families while their managers retain responsibility for their own state. Calls are lightweight coroutines, so this service does not imply CPU-level parallel execution. Its role is to decide when declared operations may coexist and to preserve their relationships during completion, failure, and cleanup.

Claims can be shared or exclusive. Shared claims on the same resource may coexist; an exclusive claim conflicts with other access to that resource. Path claims also account for overlap between ancestor and descendant paths, which matters when one operation owns a directory and another targets a file within it. Operations without sufficient independence information retain conservative sequencing. This mechanism is useful for coordinating known access within the runtime, but it cannot infer undeclared writes or enforce a distributed lock across arbitrary external services.

Cancellation preserves the relation between an operation and its claimed resources. If a synchronous operation runs in a thread, requesting cancellation does not stop that thread immediately. The system waits for the operation before releasing its claims, avoiding the appearance that the resource is free while the underlying work continues. Externally executed effects introduce a second question: whether the effect happened before interruption. That question requires observation or reconciliation rather than being answered by the local cancellation flag.

Delegation uses a bounded assignment with a concise task, relevant files, declared read and write sets, and acceptance conditions. The child receives an independent context unless an explicit history fork is requested. Capability allowlists bound what is exposed to that child; an empty allowlist grants no members of the corresponding family. Declared file sets document intended scope, but are not by themselves filesystem enforcement. The distinction matters when interpreting a successful delegation as evidence of either coordination or isolation.

For supported one-shot coding assignments, an isolated worktree can separate the child's edits from its parent's working tree. The runtime owns that worktree, preserves a patch before cleanup, and returns the patch without automatically merging it. If preservation or cleanup fails, the location and error remain available for inspection. This facility supports reviewable concurrent development, within its supported one-shot coding scope.

Explicit history sharing passes portable task context and complete interaction groups rather than implicitly granting a child all of its parent's state. A parent's own permission to receive history does not automatically pass to further descendants. Forked evidence and a resumed native conversation are also different operations: provider-specific opaque state stays with its original conversation. A bounded reference supplies portable evidence rather than native continuation state.

# A.6 BUDGETING ACROSS THE COMPLETE DEVELOPMENT PROCESS

A root run and its descendants share resource accounting, including later turns of resident processes. Candidate construction, evaluation, failed attempts, and subsequent consumption therefore draw on the task's common budget. The root objective remains the relevant unit of cost. Reporting only the retained component's final invocation would omit the work required to obtain it and could make an expensive adaptation appear artificially efficient.

The model layer reserves an estimated input cost and output allowance before framework-visible requests. Shared reservations prevent concurrent children from independently spending the same remaining capacity. Usage receipts then reconcile the reservation with observed usage, and receipt identities prevent duplicate charging when both request-level and turn-level records refer to the same call. The controls depend on observable requests and reported provider usage.

Missing usage remains unknown rather than becoming zero. An interrupted or cancelled request can leave an unreconciled reservation whose estimate continues to count against the budget. Remaining capacity can still support other work, but the unresolved reservation is retained across explicit resume until it is reconciled with evidence. This conservative treatment preserves uncertainty that would otherwise disappear from an apparent cost total. It also separates measured tokens from estimated exposure and monetary prices that may not be available.

A fair comparison between an evolving and fixed system should match the allowed resources and report realized consumption. Equal upper limits alone do not establish equal effort. The evolving arm may spend part of its budget developing a component, while the fixed arm may use that capacity for another task attempt. A useful evaluation reports total tokens, time, failed requests, and unresolved usage alongside accepted tasks. The current coding aggregates do not supply this full paired accounting, so this report does not infer cost efficiency from their accuracy difference.

#### <span id="page-19-0"></span>A.7 PLAN: PERSISTENT DIRECTION FOR CHANGING WORK

The Plan represents the coordinator's evolving understanding of the task. It records what remains to be accomplished, which dependencies are unresolved, and where the evidence for completed work can be found. It is neither another model nor an execution engine. This separation permits the coordinator to revise its approach as observations change while keeping the task objective explicit. Runtime remains responsible for whether work is running or finished; acceptance evidence remains responsible for whether the result satisfies its criterion.

The mechanism separates a compact index from detailed working documents. The index is limited to 2,000 characters and identifies the current objective, progress, blockers, next action, and links to relevant records. Detailed reasoning, acceptance conditions, comparisons, and decisions remain in the plan documents. The agent authors these records with ordinary file operations rather than relying on an additional automatic summarizer. Changes to the index should follow meaningful progress so that its direction and supporting documents stay consistent.

This design manages attention through references. A model request receives a concise account of current work; a decision that depends on an earlier observation can explicitly retrieve the detailed record. The index may omit detail, but it should preserve the route to that detail. If an index is too long, truncation is visible and the original location remains available. Missing or unreadable records are reported as such instead of being filled with inferred progress.

Coordinators own planning and replanning; leaf workers receive bounded assignments and return evidence. A specialist does not automatically become a second owner of the full project plan. In coding tasks, plan records remain outside the submitted business repository so that planning activity

does not contaminate the deliverable patch. Changing the workspace or using a child worktree does not redefine the coordinator's plan as part of that child's output.

When planning and the configured evolution policy are enabled, the detailed plan tracks explicit evolution opportunities. An opportunity records the limitation that motivates it, the reusable operation or method, an intended consumer, expected benefit, relevant capability inspection, and a small comparison or reuse experiment. Its status includes the reason for proceeding or deferring. The record links proposed capability work to a concrete task need.

The configured policy asks qualified opportunities to proceed as background branches when independent product work remains available. Within such a branch, generation, evaluation, and adoption retain their dependency order. Product work that requires the candidate waits for the result, and the coordinator collects outstanding branches before completing. A concrete prerequisite, conflicting write, permission constraint, or resource limit can justify deferral. These are coordination rules for the agent's procedure, not evidence that background execution always improves performance.

Planning support and approval are separate controls. Auto mode supports plan maintenance while allowing authorized execution. Plan mode gates mutating actions until an explicit exit from the review phase. Off mode disables automatic planning support. The effect gate also applies to programmatically composed calls; describing an operation in a plan does not grant permission to execute it. The resulting separation keeps the written approach, the authorization state, and the observed outcome from collapsing into one status label.

After an interruption, the next step may be reconciliation rather than continuation. A plan can say that a source packet was saved even if the corresponding external operation was interrupted before confirmation. The coordinator should inspect the saved artifact or execution record before repeating the action or marking the dependency resolved. The Plan's contribution is to preserve the intended direction and relevant references; it does not independently certify historical claims written into it.

### A.8 CONTEXT ASSEMBLY AND RECOVERABLE COMPRESSION

Long tasks accumulate source material, failed attempts, and decisions. Even when this material fits, a longer context does not ensure reliable retrieval of information at every position [\(Liu et al.,](#page-12-5) [2023\)](#page-12-5). Retaining everything indefinitely increases request size, while discarding history can erase the reason for a constraint or the observation behind a comparison. AgentEvolver addresses this tension by separating stable task anchors from replaceable interaction history, preserving recent complete exchanges, and maintaining references to archived material. Compression manages resources while retaining explicit failure and recovery behavior.

The context envelope distinguishes fixed instructions and task material, a checkpoint, recent interactions, and an optional transient layer. In the current running loop, changed runtime observations and environment images are first recorded in the conversation; the loop does not supply a separate transient layer. The assembler retains that optional interface for other views. This matters for describing the Plan correctly: the current index is refreshed before a request, but its recorded observations can subsequently become part of the history eligible for compression.

Runtime observations are marked as framework observations rather than user feedback or approval. Changed observations enter the history, and repeated unchanged content is not presented as a newly authored user instruction. Environment images are likewise tied to available observations rather than obtained by silently polling during request assembly. These conventions preserve the meaning of what the model sees. They also give an inspection record a basis for distinguishing a newly observed state from a previous image or an agent's own description.

Compaction operates at closed interaction boundaries. Recent assistant calls and their results remain together, avoiding orphan results or requests whose calls have disappeared. The envelope validates call identities and layer consistency before serialization. Keeping complete recent turns is particularly useful when the next decision depends on the exact parameters of a recent failure. Summaries may omit parameters or qualifications preserved in the original exchange.

The pressure decision measures the serialized model request, including fixed instructions, checkpoint content, recent observations, and tool schemas. Measuring only the removable conversation body would miss a large stable prefix or an unexpectedly large native checkpoint. The implementation

Current defaults retain four recent turns, use a full-input trigger of 100,000 tokens, and consider model-window pressure at a fraction of 0.85. The summary generation target is 2,048 tokens. For a conversation bound to a persistent thread, a fold first archives the complete closed conversation, including the previous checkpoint and any opaque provider state. If this archive cannot be written, the original history remains intact and the summarization call is not made. A successful checkpoint retains a locator for that archive, and subsequent archives preserve earlier locators. Thus repeated compression need not remove the route to old evidence, although deleting the containing session would still remove its stored artifacts. The summarization step produces a candidate checkpoint while preserving the fixed task anchors and selected recent complete interactions. Opaque state is not converted automatically between model routes, and explicit resume rejects an incompatible route instead of treating it as interchangeable text.

After constructing the candidate, the loop measures the full request again. If the native representation is less useful for request size or headroom, the already-produced readable companion can be considered without another model call. The smaller valid representation can be selected. If the candidate does not reduce the complete request, the original conversation is restored. This is a size-based acceptance condition for history replacement; it is separate from the soft output-length target used when generating the summary.

The policy seeks headroom below the active limit rather than repeatedly operating at the boundary. A productive reduction with sufficient headroom resets the scheduled retry behavior. Unproductive or inadequate attempts trigger backoff, while actual capacity overflow can request recovery immediately. The implementation also limits repeated unproductive folds. These controls avoid spending another summarization attempt on essentially unchanged pressure at every step, while allowing a long productive run to compact repeatedly as its history grows.

Request savings do not establish semantic completeness. A compacted account can omit a qualification, merge two similar versions, or retain a conclusion without its supporting observation. AgentEvolver does not apply an independent model audit that proves each summary preserves all acceptance conditions. The fixed task anchor, recent exact exchanges, fresh Plan index, and source archive reduce different risks, but none makes compression lossless. A coordinator facing a consequential uncertainty should retrieve the relevant original evidence rather than rely solely on the summary.

Consider a website revision whose checkpoint says that source validation passed but omits that only metadata was available. The Plan can identify the route under revision; the archived source packet resolves the missing qualification. Similarly, a game-development summary may retain a font setting while omitting the engine measurement that motivated it. These illustrative cases explain the distinct roles of a compact task index, a working summary, and recoverable evidence. Their value depends on whether the agent retrieves the relevant detail when the next decision requires it.

A compression evaluation should therefore measure both resource behavior and continuation quality. Resource measurements include full request size, summarization cost, retries, and recovered headroom. Continuation measurements include retained acceptance conditions, correct version references, recovery of a needed source, and avoidance of repeated completed effects. Comparing only summary length would miss the task-level consequence. Conversely, a successful final task without request accounting would not isolate whether the compression policy reduced cost.

### A.9 WORKFLOW AND PROGRAMMATIC COMPOSITION

Plans, Workflows, and one-shot programs express different kinds of structure. A Plan is the coordinator's authored account of current work. A Workflow is a reusable executable control structure with a version and managed continuation. Code Mode is a programmatic interface for composing available operations within a single execution. Treating these as the same mechanism would obscure who chooses the next step, which state is retained, and what a later consumer can reuse. Figure [10](#page-23-0) contrasts the latter two.

A Workflow is represented as a restricted HTML program that can be read and inspected before execution. The compiler admits defined control constructs and input contracts rather than executing arbitrary content embedded in a document. Branches, mappings, and bounded loops support dynamic control; the system is therefore more expressive than a single fixed DAG. Loops require explicit bounds, and limits constrain fan-out, nesting, concurrency, Agent count, and elapsed time. These controls bound the program's operation rather than determine whether its decisions are useful.

Execution separates the static definition from dynamic frames, concrete invocations, and individual attempts. A mapped item or loop round has its own frame; a frame can initiate an invocation; retrying that invocation produces attempts with distinct outcomes. This hierarchy allows the system to identify which part of a reusable procedure failed and which work completed before interruption. Retry attempts remain distinct from independently completed runs.

Workflow state progresses through validation, readiness, execution, and verification to success or failure, with explicit pause and cancellation paths. Checkpoints preserve the executable program identity and completed progress. Resume can reuse completed invocation results while restarting unfinished work, and a changed program cannot silently reuse the same version's checkpoint. However, a checkpoint's local status does not settle whether an interrupted external side effect occurred. The ambiguous effect must be reconciled before retrying it.

The language schema, checkpoint representation, and Workflow behavior have separate versions. A behavior revision can change the procedure while retaining the same language format; a runtime checkpoint change can affect continuation without changing the task procedure. Keeping these identities distinct prevents compatibility claims from being inferred from a single version number.

Evaluation of a Workflow should identify a real terminal run, its inputs, and its outcome rather than merely show that the source document passed parsing.

Code Mode serves a different need: several related operations can be composed in one small program, with intermediate data processed before selected results return to the model. Each run uses a fresh Python child with bindings to available operations. It does not provide a persistent kernel whose hidden state automatically carries into the next program. This makes the program boundary explicit, while authorized external state remains accessible through ordinary operations.

A bound call returns through the ordinary Tool pipeline, preserving policy checks, budget accounting, ownership, and relationships between parent and child calls. Code Mode does not provide an alternate privileged dispatcher. Failures can be handled as program exceptions, and partial output remains available when a program fails or exhausts its allotted execution. Keeping the nested call identities also matters for analysis: these calls were made inside the program and should not be misclassified as separate actions directly emitted by the model.

The fresh child-process boundary is not an operating-system security sandbox. Its permitted filesystem and service access depend on the surrounding execution environment. Similarly, selecting a smaller returned result can reduce material immediately placed in the model context, but does not establish a measured token or latency gain without comparison. The current report presents Code Mode as a controlled composition interface. Quantifying its efficiency would require matched operations, equivalent outputs, and complete request accounting.

A source-review pipeline illustrates the division of labor. The Plan can state that a revised inquiry requires source verification and historical-consistency review. A reusable Workflow can encode the branch that requests a correction after a failed check. A one-shot program can read several packets, apply bound validators, and return a compact table for the next decision. The mechanisms support distinct levels of structure within the same evolving task.

#### A.10 MEMORY, CONVERSATION CONTINUITY, AND HISTORICAL RETRIEVAL

Prior agent architectures combine retained experience with reflection and planning [\(Park et al.,](#page-12-3) [2023;](#page-12-3) [Packer et al.,](#page-12-4) [2024\)](#page-12-4). Our system distinguishes an Agent's conversation from durable notes. A resident process appends new assignments and events to its own conversation, while a one-shot call starts fresh unless continuation is explicitly requested. Notes retain selected facts and references outside that immediate dialogue. Disabling automatic note injection does not erase conversation continuity. Conversation continuity therefore does not require copying every statement into notes.

The default notes interface provides a short index over files that the Agent can read when needed. The memory backend participates in indexing, so a revised Memory implementation can change how entries are ranked or exposed without replacing the Runtime's conversation. Note bodies are not all injected automatically. A compact index can omit complete entries with a notice and a route to the directory, preserving access to omitted material.

Notes are scoped to an actor within a session. Reopening that session can restore its notes, but another actor or session does not automatically acquire the same store. Changing the workspace does not relocate memory into the deliverable. These namespaces organize ownership; they are not themselves a security boundary against unrestricted host filesystem access. They also mean that persistent notes within a session should not be advertised as automatic, validated knowledge transfer across every future project.

An evolved Memory backend can alter retention or retrieval behavior. Demonstrating improvement would require showing which relevant records become available, which are omitted, and how the change affects a later consumer. The present cases do not establish such a controlled Memory improvement. The architectural support belongs in the system description, while the empirical coverage remains concentrated in Tool, Skill, Agent, Connector, and Environment changes. This distinction keeps the eight-family capability claim separate from the number of families actually evidenced in the selected cases.

Notes are fallible references rather than instructions with higher authority. A stored observation should retain its origin and scope, especially when an earlier attempt failed. Repeating a modelwritten claim of success does not create independent evidence, and a note about a passing shell command does not establish that the task's acceptance conditions passed. Useful retention preserves the supporting observation and the conditions under which it was obtained, allowing later work to question an outdated or overly broad interpretation.

Historical retrieval complements the notes interface. Session-level reads can inspect an outline, search prior execution, or retrieve an exact bounded record from the authoritative history. Results report truncation and skipped malformed material rather than presenting a silently complete reconstruction. The route from a concise note or checkpoint to a specific original observation is particularly important when different component versions produced similar-looking results. Retrieval must recover the relevant identity as well as the text of the conclusion.

#### A.11 TRACE, RECOVERY, AND EVIDENCE-PRESERVING VIEWS

Trace records the execution from which evaluations and retrospective analyses are derived. It connects effective model requests, actions, component results, and lifecycle events. A polished interface can show the resulting artifact, but these records establish which version was invoked and what observation was available when a decision was made. Figure [11](#page-25-0) summarizes the relationship between source events and derived views. Traceability improves inspectability without turning a self-authored judgment into an independent acceptance result.

A model-request snapshot records the route actually attempted, effective behavior settings, messages, and complete tool schemas before provider dispatch. This is more informative than a configuration alias alone, because a fallback route or pressure-related excerpt can change what the model actually received. The snapshot has a content-derived identity so that later analyses can refer to the same request. When an observation was shortened for the request, the original result remains distinguishable from the excerpt that reached the model.

Tool results retain execution identity, component version, parent and root call relationships, outcome, timing, and stable error information. A policy-refused operation can still produce a paired result even though its body did not run. This is necessary to distinguish an unavailable operation from an executed failure. Parent-call relationships also preserve the structure of Code Mode and delegated execution, so analyses can distinguish nested work from direct model actions.

The default interactive profile treats Trace as observational: a recording problem can be reported while execution continues. Stricter training and high-risk profiles make required durability a precondition at meaningful boundaries, including before a provider request or a potentially mutating operation. A failure at such a boundary stops progression rather than pretending the missing evidence can be repaired by a model retry. Consequently, the durability guarantee must be stated with its selected profile; it should not be attributed to all runs by default.

Derived views read committed events and preserve a position in the source history. A projection must durably store its output before advancing that position. After a crash, replaying an already applied suffix is preferable to skipping source events whose derived output was never saved. Monotonic positions and versioned projection implementations make this ordering inspectable. The resulting views include operational statistics and training-oriented trajectories, but this report does not claim that training was performed or that those views improved model weights.

Compaction changes the active conversational view without requiring deletion of original events. A replacement identifies the source range it summarizes, while the append-only evidence remains available. The active history and the complete history therefore answer different questions: what context is being continued, and what events occurred. An inspection tool must preserve that distinction. Replaced observations should not be silently counted twice as new evidence, and a summary should not be treated as an independent second measurement of the underlying event.

Recovery also separates kinds of state. A conversation snapshot can restore dialogue under the same bound owner, session, and model route. A mailbox record can preserve queued assignments and acknowledged turn completion. A browser checkpoint can preserve selected browser storage for a fresh page. None of these mechanisms serializes an arbitrary running process graph or proves that an external action completed. The restored record determines what is known locally; the uncertain effect determines what must be checked before execution proceeds.

Possibly executed messages are not blindly replayed. If a process stopped after issuing an operation but before confirming its result, recovery must reconcile that operation using evidence about its external effect. Exactly-once behavior cannot be inferred from a local completed flag when the external service has no corresponding transaction guarantee. This limitation is especially relevant to evolving agents because a repeated registration, write, or evaluation could otherwise alter the version history that the resumed plan expects.

Request and trajectory records contain the material actually used during execution and therefore need the same handling as the original task data. Structured records avoid storing credentials as dedicated metadata fields, and endpoint fingerprints distinguish deployments without exposing complete endpoint addresses. This does not remove sensitive information that may legitimately appear inside task messages or observations. Exporting trajectories or sharing an evidence package requires selecting the relevant records and preserving the appropriate data boundary.

#### A.12 WHAT THE CORE MECHANISMS ENABLE, AND WHAT REMAINS TO MEASURE

The mechanisms form a connected account of execution. Component identities define what can change. Runtime assigns ownership and coordinates declared access. Plan preserves the task's direction and unresolved dependencies. Context management keeps a bounded working history with references to archived evidence. Workflow and Code Mode provide reusable and local forms of composition. Memory and Trace retain different kinds of information for later use and inspection. Together they support capability development without requiring the original objective to disappear into a separate optimization process.

Implementation support is broader than the measured evidence in this report. The six application cases show particular retained changes and consumers, while the coding comparison reports wholesystem task outcomes. Neither isolates every core mechanism. Claims about recovery reliability, compression quality, parallel efficiency, and cross-task library value require targeted controls. The proposed studies specify those controls so that future results can be attributed to a mechanism rather than inferred from the existence of an interface or from a single successful application.

The central design principle is to preserve the connections needed to interpret progress: between a task and an opportunity, between a candidate and its executed version, between an observation and a decision, and between a retained component and a later consumer. Each connection can fail independently. Making them explicit permits useful partial outcomes to be retained while keeping incomplete objectives visible. This is the basis for studying global capability evolution as a process with observable artifacts and decisions, with distinct records of success and failure.

### C.3 FURTHER EXPERIMENTS, EXPLICITLY NOT YET RUN

An evolution ablation should keep task identities, the foundation-model route, initial capabilities, feedback access, and grading protocol fixed. It should report realized cost as well as limits, because candidate search and evaluation consume resources that a fixed baseline may spend differently. Plan and Runtime ablations need targeted long-task or recovery workloads rather than inference from a whole-system score. The experiment plan records these as proposed studies; this draft contains no invented ablation bars or outcomes.

A capability-transfer study should freeze the selected library before revealing final consumer feedback, separating adaptive development from evaluation on new observations [\(Dwork et al.,](#page-12-9) [2015\)](#page-12-9). Development tasks, candidate attempts, and library selection must be logged so that a later gain is not explained by hidden evaluation reuse. Matched consumers can compare the retained library with the initial library and with equivalent task-specific effort, while counting failed attempts and regressions. This protocol tests whether capabilities help beyond their development context, a question the current connected-project receipts cannot settle alone.

A cross-entity study can freeze the LUMEN source, authoring, and review versions, then compare the initial chain, individual replacements, and the full revised chain on the same unseen source and route fixtures. Source identity, evidence availability, route validity, and preservation of historical observations should be scored separately. A missing interface dependency must be distinguished from a valid configuration that performs poorly. Recording both local checks and the final route outcome would reveal whether independently passing components remain compatible when composed. This proposed design extends the current mechanism case without treating its prescribed family coverage as an ablation result.

A separate recovery study should interrupt matched tasks at declared step boundaries, including after context compaction and before confirmation of an external operation. After resumption, it should measure acceptance-condition omissions, recovery of evidence references, duplicate effects, and unfinished child cleanup, alongside time and token cost. Plan variants should share the same tasks, tools, and budgets; Runtime variants should retain the same workers and compare serial with coordinated execution. Deterministic lifecycle checks and model-dependent task outcomes should be reported separately. These proposed controls would locate the value of continuity and coordination more precisely than a whole-system benchmark score.

#### C.4 MECHANISM-SPECIFIC EVALUATION DESIGNS

A planning study should hold the task, model, initial capabilities, and budget fixed while varying the availability of a persistent index and detailed records. Useful tasks include a changed requirement, a deferred dependency, and a continuation after substantial interaction history. Outcomes should include final acceptance, omitted requirements, incorrect completion claims, and retrieval of the evidence needed for the next decision. Human or deterministic assessment should be specified independently of the plan's own status labels.

A context study should expose the same long interaction history to the compared policies and then present continuation tasks whose answers depend on selected historical facts. These facts can include a rejected component version, a source qualification, and a pending external effect. Report request size and summarization cost alongside recovery accuracy and task acceptance. Source-archive availability and explicit retrieval cost should be part of the condition, because a short summary with recoverable references differs from one that permanently discards the evidence.

A Runtime study should separate deterministic contract checks from model-dependent performance. Controlled operations can establish whether conflicting claims serialize, independent claims overlap, and cleanup retains ownership until completion. Long agent tasks can then evaluate the resulting effect on latency and accepted outputs. The study should report the same total work under serial and coordinated conditions, avoiding a comparison where one condition performs fewer checks or omits failed candidates. No outcomes from these proposed controls are included in the present results.

A Memory study should distinguish storing content from changing retrieval behavior. Freeze the source records, revise the indexing or selection implementation, and evaluate later requests with independently specified relevant evidence. Measure useful retrieval, misleading retrieval, omissions, and task consequences rather than counting note creation. Actor and session scope must remain constant across conditions. A separate transfer study can then examine whether deliberately shared, reviewed knowledge helps a new project without silently importing its evaluation answers.

# C.5 VISUAL AND QUANTITATIVE EVIDENCE

Screenshots establish that a particular visual state was recorded. They are useful for tracing a user's path through a product, but generally do not establish the hidden component that caused the state. The case analyses therefore pair visual sequences with versioned execution observations. A synthetic chart or an explanatory video overlay remains an editorial presentation of evidence; its numbers must be reconciled with the original comparison artifact rather than counted as another experiment.

Each quantitative statement has a distinct denominator or workload. The coding rates count tasks; Commonspace counts affected objects in one graph; LUMEN counts issues in one defect fixture; ARKBOUND measures bytes under an acquisition budget; Godot measures invocation time for stated inputs; Signal Foundry reports research artifacts and strategy outcomes. These quantities should not be aggregated into a generic improvement percentage. Keeping their units explicit is necessary for understanding both the strength and the limits of the cross-case synthesis.

Negative and incomplete outcomes are retained in the case record. A missing adopted component, a failed candidate, or a strategy without comparative advantage identifies where the development process stopped or failed its criterion. Excluding such outcomes would overstate the connection between capability activity and task success. Future studies should predefine inclusion criteria, report all eligible attempts, with abandoned attempts, failures, and accepted tasks identified separately.

#### C.7 REPRODUCTION PROCEDURE AND REQUIRED RECORDS

A reproduction first identifies its unit: a coding task, component comparison, or later consumer. Inputs and initial capabilities are fixed before execution, and candidate development preserves failed as well as successful attempts. This record follows the broader principle of retaining the information needed to reproduce a computational result [\(Sandve et al.,](#page-13-10) [2013\)](#page-13-10). The retained version is frozen before final consumer feedback is exposed. Component criteria and task acceptance are then evaluated separately. #### C.8 AMORTIZED COST OF RETAINED CAPABILITIES

A retained capability can reduce later operation cost while remaining expensive to develop. Under a simplified matched-output comparison, let Cdev be the incremental cost of development and evaluation, and let c<sup>0</sup> and c<sup>1</sup> be the per-use costs before and after the change. After n comparable uses, the net saving is

$$\Delta C(n) = n(c_0 - c_1) - C_{\text{dev}}.$$
(2)

Positive amortized savings require c<sup>1</sup> < c<sup>0</sup> and enough later uses to recover the development cost. Each comparison must use one cost unit, such as time or tokens.

This accounting assumes comparable outputs and operating conditions. Maintenance, changed workloads, and regressions can alter the comparison and should be included when observed. The Godot timings estimate a local per-use difference, but the available evidence does not establish the complete development cost or future usage distribution. The report therefore does not infer a break-even point. A prospective study should record development overhead and later consumers together, evaluating acceptance alongside any resource savings.
