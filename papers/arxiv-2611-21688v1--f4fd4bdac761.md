# DeltaHarness: Self-Evolving Harnesses for Resource-Adaptive Tool Execution

###### Abstract

Tool-using agents rely on execution harnesses to organize and schedule
tool operations. The same task and resource description can conceal
runtime conditions that reverse the latency ordering of valid execution
plans. Resolving this uncertainty requires firsthand execution in the
target setting. We introduce DeltaHarness, an execution-guided
policy-search method that adapts agent harnesses from cold-start
measurements. Its QHI loop uses the observed response to update runtime
dispatch, revise physical plans, and select experiments for later
proposals. An independent confirmation panel controls policy
replacement. With fixed dispatch, a revised materialization policy
reduces complete-delivery latency by 30.0% on one video-editing task
across three fresh pairs. On held-out tasks, the evolved policies reduce
latency by 8.2% relative to the best fixed plan in one seed and by 4.6%
relative to the initial proposal in another.

## 1 Introduction

Tool-using language models execute tasks through harnesses that organize
tool operations and control their execution (Lyu et al., 2024; Wu et
al., 2026; Jiang et al., 2026a). Resource-aware execution exposes
choices in dataflow structure, input access, and scheduling (Poms et
al., 2018; Chaudhry et al., 2026). A video composition can run as one
fused render, as parallel output ranges, or through materialized clips
(Yan et al., 2026b; Yan et al., 2026a). Parallel ranges can repeat
decoding and add intermediate traffic. Materializing clips spends local
compute to change later input access. Source layout, cache state, and
interference determine which plan delivers fastest, even across
executions with the same visible task and hardware description. _When
hidden runtime conditions can reverse plan ordering, identifying the
faster plan requires firsthand execution in the target setting._

Execution-guided search uses measured performance to revise systems
algorithms (Cheng et al., 2025; Hamadanian et al., 2025), storage
configurations (Egersdoerfer et al., 2026), and serving policies (Jiang
et al., 2026b). Prior programs and measurements provide an initial cost
estimate; the target setting’s physical response updates it. Under a
fixed measurement budget, adaptation must also choose which comparisons
will inform the next revision.

Experiment selection connects harness evolution to task-aware
exploration, which values information by its effect on downstream
control (Wagenmaker et al., 2023). Active video investigation tests
competing failure explanations before harness revision (Luo et al.,
2026a), while self-improving branches adapt the development cases used
for search (Dong et al., 2026). We study whether selecting task–resource
measurements can improve a successor’s physical execution policy.

DeltaHarness extends this execution-guided loop to physical tool plans
with fixed model weights and tool kernels. For a new device, workload,
or resource setting, cold start combines inherited programs and
experience with measurements of its current physical response. The
physical policy $`H`$ chooses partitioning, concurrency, fusion, and
materialization. The dispatcher $`Q`$ uses measured delivery times to
update admission decisions, and $`I`$ selects task–resource comparisons
for the next proposal. An independent common panel determines incumbent
replacement. Figure 1 shows how experience in the target setting informs
these revisions.

Program-level recursive self-improvement also makes the improver itself
an optimization target (Srikanth et al., 2026). Our recursive variant
rewrites its evidence-analysis program, while policy self-evolution
updates $`H`$. We compare learned experiment allocation with uniform and
balanced panels under matched budgets, followed by frozen held-out
evaluation to assess transfer (Wang et al., 2026b; Xia et al., 2026).

In the fixed-dispatch video-editing case, materializing clips before
fusion reduces latency by 30.0% and raises average active FFmpeg cores
from 0.95 to 1.80. On held-out tasks, the first policy-search seed beats
the best fixed plan and the second improves its initial proposal.
Additional comparisons examine experiment selection, resource response,
and orchestration.

## 2 Related Work

#### Measured Optimization of Computer Systems

Scanner exposes compressed-video access and dataflow execution (Poms et
al., 2018), while Murakkab combines workflow profiling with adaptive
model and hardware configuration (Chaudhry et al., 2026). LLM-driven
systems design builds on measured feedback: ADRS evolves
performance-oriented algorithms (Cheng et al., 2025); Glia coordinates
reasoning, experimentation, and analysis (Hamadanian et al., 2025);
STELLAR reruns applications to tune file systems (Egersdoerfer et al.,
2026); AUTOPOIESIS evolves serving policies under runtime dynamics
(Jiang et al., 2026b); and MaxKernel uses compiler and profiling
feedback for TPU kernels (Wang et al., 2026a). DeltaHarness applies this
measured-optimization principle to physical tool plans, separating
experiment allocation from incumbent confirmation.

#### Learning and Evolving Agent Harnesses

HarnessDev evaluates runnable harness creation and evolution (Wu et al.,
2026); HarnessEvolve diagnoses failures through reference trajectories
(Jiang et al., 2026a); and multi-task self-evolution uses the same
frozen agent as solver and optimizer (Xu, 2026). Specialized harnesses
accumulate diagnosis experience in OpsHarness (Huang et al., 2026),
design feedback in AutoDesign (Luo et al., 2026b), and research
strategies in ScholarEvolve (Yang et al., 2026a). Learned editors
provide another route: Harness Learning trains a proposer from task
feedback (Zhang et al., 2026), Harness-R1 trains an engineer through
target-agent reruns (Shao et al., 2026), and Harness-Zero distills
harness-induced behavior into solver weights (Ye et al., 2026). Our
formulation fixes the model weights and tool kernels while exposing
physical policies and measurement locations to the improver.

#### Active Evidence and Improving Exploration

Task-aware experiment design links observation value to its effect on
the eventual policy, as in nonlinear system identification for
controller optimization (Wagenmaker et al., 2023). VideoHarness-RSI
evolves video-context constructors (Xu and Chen, 2026), and Video-RSI
actively revisits videos to test failure explanations (Luo et al.,
2026a). Exploration also improves through historical replay in Dream-RSI
(Zheng et al., 2026), self-modification records in SelfSearch (Yang et
al., 2026b), shared group experience (Weng et al., 2026), and adaptive
development subsets and proposal guidance (Dong et al., 2026). AIDE2
evaluates rewritten research agents through downstream research
performance (Srikanth et al., 2026). DeltaHarness focuses on fresh
candidate–incumbent task/resource pairs: selected measurements inform a
successor, while a common panel controls replacement.

#### Evaluation and Transfer

RRSI regularizes harness evolution against development-set overfitting
(Xia et al., 2026). Rethinking Harness Evaluation compares evolution
with task-level search under matched feedback and inference budgets
(Wang et al., 2026b). AutoTuneBench studies how baseline choice,
hardware variation, headroom, and infrastructure affect tuning
measurements (Chen, 2026). Controlled agent-scaling experiments further
connect architecture benefits to task structure and coordination
overhead (Kim et al., 2025). These findings motivate our fresh paired
measurements, frozen held-out evaluation, and separate reporting of
execution gains and policy-acquisition cost.

## 3 Problem Formulation

A task $`x`$ specifies a logical composition and its delivery contract.
The visible resource description $`e`$ contains quantities such as CPU
eligibility or an input-response limit; observations $`o`$ describe
measured behavior in the current setting. A harness policy constructs a
physical tool graph

```math
G=H(x,e,o),\qquad G=(V,E). \tag{1}
```

Nodes bind fixed tool operations to arguments and resource requests, and
edges impose dependencies. The dispatcher $`Q`$ schedules ready
operations. The optimization target is complete-delivery time
$`T(Q,H;x,e)`$, including observation, policy evaluation, compilation,
tool execution, and output checks. We write $`T(H;x,e)`$ when the
dispatcher is fixed.

#### Why firsthand evidence is necessary.

Let $`z`$ denote conditions unresolved by $`e`$, such as cache state or
interference. Two plans $`p`$ and $`q`$ can share the same visible
description yet reverse their expected ordering:

```math
\displaystyle\mathbb{E}[T(p)-T(q)\mid x,e,z_{1}] \displaystyle<0, \tag{2}
```

```math
\displaystyle\mathbb{E}[T(p)-T(q)\mid x,e,z_{2}] \displaystyle>0.
```

When both runtime states are compatible with the available prior,
$`(x,e)`$ leaves the current plan ordering unidentified. Cold-start
executions supply observations $`o`$ of the target setting. These
observations update the evidence used for subsequent dispatch, policy
revision, and experiment selection.

Let $`\mathcal{D}_{r}`$ be the information available before proposal
$`r`$, $`H_{0}`$ the common initial policy, and $`H_{r-1}`$ the
incumbent. A fixed model improver $`M`$ proposes

```math
(\widetilde{H}_{r},\widetilde{A}_{r})=M(H_{0},H_{r-1},\mathcal{D}_{r}), \tag{3}
```

where $`\widetilde{A}_{r}`$ names candidate–incumbent comparisons on
development task–environment cells. The measurement rule $`I`$
determines which locations are executed. We compare measurement rules
through the final policy they produce under the same proposal and
execution budgets.

Policy acquisition has a one-time cost $`C_{\mathrm{improve}}`$. Over
$`n`$ deployed tasks, its time cost is

```math
C_{\mathrm{improve}}+\sum_{j=1}^{n}T(Q,H;x_{j},e_{j}). \tag{4}
```

Held-out execution ratios assess the reusable policy; model calls,
development measurements, failures, and waits determine the acquisition
term.

## 4 DeltaHarness

DeltaHarness performs black-box policy optimization with adaptive
experiment allocation. In the full loop, $`H`$ constructs the physical
graph and $`Q`$ decides whether to admit a ready operation or wait for
an active one to finish. Successful workflows supply
decision-to-delivery times for updating $`Q`$. The improver proposes
revisions to $`H`$ and $`I`$ from accumulated outcomes. The
physical-policy and allocation experiments use fixed dispatch.

### 4.1 Representing Physical Policies

A policy maps task and resource observations to a complete physical
plan. The Linux studies implement this map as sandboxed source programs.
The Mac adaptation case uses ordered typed rules with a complete default
branch: conditions test task or environment features and define
missing-value behavior. These are distinct policy interfaces over the
same kinds of physical choices. The compiler and tool kernels are fixed
within each comparison.

For video editing, the plan chooses range count, range concurrency, even
or clip-aware cuts, longest-processing-time ordering, hardware decoding,
clip materialization, materialization concurrency, and audio/video
insertion order (Appendix A). These choices change the physical work.
Materialization creates local inputs for a fused render (Figure 1(c));
scheduling controls when the resulting nodes execute.

### 4.2 Obtaining Firsthand Measurements

Cold start acquires response measurements from the current setting and
combines them with inherited evidence. An observation includes elapsed
time, tool CPU time, input service, work size, and delivery status. Task
preparation supplies observations and reusable artifacts, with its cost
included in each method’s execution. Additional plan comparisons provide
evidence for later decisions.

A comparison cell $`u=(x,e)`$ binds a candidate and incumbent to the
same task and environment. Each policy executes freshly, consecutively,
in randomized order. Even identical plans receive separate executions.
The resulting record contains the common task observation, both
policies, both delivery outcomes, and both costs. Remeasuring the
incumbent controls for drift better than comparison with a stale timing.

Admission limits constrain declared tool pools; FFmpeg retains natural
internal threading. Linux CPU-affinity and FUSE-response controls, and
Mac admission and HTTP-response controls, retain their respective
resource semantics throughout evaluation.

Algorithm 1 Policy evolution with fixed dispatch

#### Measurement allocation.

In the allocation study, the three LLM arms share model, prompt
structure, sampling settings, and proposal count. Uniform samples
development cells without replacement within a panel. Balanced uses a
predefined balanced panel. Selected executes the model’s locations,
including repeats. Invalid locations receive uniform replacement. The
model packet omits arm labels. A $`(1+1)`$-ES baseline mutates
resource-bin plan parameters under the same execution budget, without
additional LLM calls.

All arms begin from one $`H_{0}`$ generated before iterative
candidate–incumbent feedback. They share the prior and pilot, then
receive their own measurements. Each subsequent input retains the
initial policy, incumbent, previous candidates, queries, acceptance
decisions, failures, and costs. Pair records contain both outcomes and
coordinates.

#### Incumbent replacement.

The common panel is revealed after candidate freezing. For paired losses
$`\ell^{\prime}_{rj}`$ and $`\ell_{rj}`$ on $`C_{r}`$, define

```math
\rho_{r}=\exp\left(\frac{1}{|C_{r}|}\sum_{j\in C_{r}}\log\frac{\ell^{\prime}_{rj}}{\ell_{rj}}\right). \tag{5}
```

The plan-search and allocation studies use delivery time as loss for
complete pairs and predefined penalties for failed deliveries.
Replacement requires $`\rho_{r}\leq 0.995`$ and a one-sided 90% upper
bound below 1 from 2,000 cell-bootstrap replicates. In Algorithm 1, only
$`C_{r}`$ enters this decision. Every candidate receives its allocated
measurements, including slower candidates.

#### Feedback and cost.

The eight-round allocation study uses 24 confirmation and 24 selected
pairs per round, totaling 768 executions per arm and 25 LLM proposals
including the common initial proposal. Each proposal receives outcomes
from completed previous rounds. The acquisition cost includes the final
round’s measurements.

After development, policies are frozen and evaluated once on new tasks
and resource conditions. The intended allocation comparisons are
Selected/Uniform and Selected/$`H_{0}`$, with task-clustered uncertainty
and complete delivery.

#### Recursive variant.

Plan search evaluates candidate–incumbent pairs on the full 96-cell
development panel each round. Its recursive variant changes the
improver’s analyze(data) program and method notes every two rounds. That
program summarizes observations for subsequent proposals. Comparison
with a policy-only improver measures the additional recursive layer
(Appendix A).

## 5 Evaluation

We evaluate firsthand policy revision, held-out policy search, recursive
analysis rewriting, and experiment allocation under fixed dispatch. Each
matched comparison fixes the task, resource condition, and tool
implementation. Appendix C gives additional server execution,
orchestration, and scheduling measurements.

#### Firsthand adaptation case.

One fixed 312-frame task runs on a 12-core Mac with stage-pool cap four
and shared HTTP input-response shaping at 4 MiB/s. The valid reference
$`H_{P}`$ uses four clip-aware ranges with LPT ordering. The configured
model, gpt-6.1-terra, receives accumulated execution history, compares
three alternatives, and revises its policy. Three fresh randomized-order
pairs evaluate the frozen revision under the same source bytes,
compiler, and resource condition. The predefined development budget
allows up to three such rounds; this case finishes in the first round.

#### Frozen-policy transfer.

We freeze the Mac policy and reference before evaluating eight
predefined, previously unexecuted edit configurations drawn from known
media. Stage cap four crosses local input and shared HTTP response
limits of 4 and 1.5 MiB/s, with two fresh randomized-order pairs per
task and condition: 48 pairs and 96 executions. The primary panel is
4 MiB/s. The two policies choose the same physical plan on local input,
providing a control for measurement variability. Frame completeness,
latency, video fidelity, and audio duration are reported separately.

#### Plan evolution.

The plan-search study develops policies on six tasks and sixteen
environments: CPU-affinity sizes 2/4/8/16 crossed with local input or
FUSE rates 16/4/2 MiB/s. Eight held-out tasks cross 24 environments,
adding 8/3 MiB/s, for 192 cells per seed. Qwen3.8-27B generates ten
candidates for a _policy-only improver_ with a fixed analysis procedure
or a _recursive improver_ that also rewrites its analysis program and
method notes. Table-based ES uses the same paired evaluator. The first
policy-only proposal is retained for a secondary no-feedback comparison.
Two seeds run under different observed CPU contention.

#### Measurement selection.

The Linux allocation study uses eight search and four
development-validation tasks over sixteen environments. Uniform,
Balanced, Selected, and ES each receive eight rounds with 24
confirmation and 24 selected pairs. LLM arms share Qwen3.8-27B,
temperature 0.6, and a 16,000-token generation limit. Final evaluation
uses sixteen new edit configurations over known media and 24
environments, including new 6/1.5 MiB/s conditions. This experiment uses
source policies; it does not evaluate ES over the Mac typed-rule
interface.

#### Fixed plans and inference.

Range4, range8, K2p2, and fused form the fixed plan bank; K2p2 uses two
ranges with pool two. The bank oracle takes the fastest measured plan
per cell. Ratios below 1 favor the numerator. Held-out intervals use
10,000 task-cluster bootstrap replicates, keeping a task’s environments
together. Delivery failures are counted separately from physical
latency; predefined penalties are used only for search losses. The two
plan-search seeds are analyzed within their respective host conditions.

#### Resource and delivery checks.

FFmpeg retains natural internal threading. Affinity controls CPU
eligibility, and admission controls declared pools, on shared hosts. The
executor checks output properties; full AV decoding follows timing. The
retained quality results and contention-retry protocol are in
Appendix B. Quality coverage includes format, decodability, and selected
source/output comparisons.

## 6 Results

### 6.1 Firsthand Revision Improves a Valid Plan

Firsthand comparisons identify clip materialization followed by local
fusion as an effective alternative to the four-range reference $`H_{P}`$
under constrained input service. The revised policy uses a
materialization pool of four in this setting. Table 1 gives the fresh
confirmation results, and Appendix C reports the three alternatives that
informed the revision.

| --------------------- | -------------- | --------- | ------------- | ----- |
| Trial                 | Order          | $`H`$ (s) | $`H_{P}`$ (s) | Ratio |
| 1                     | $`H\to H_{P}`$ | 9.74      | 14.06         | 0.693 |
| 2                     | $`H\to H_{P}`$ | 9.75      | 14.27         | 0.683 |
| 3                     | $`H_{P}\to H`$ | 9.73      | 13.42         | 0.725 |
| Paired geometric mean |                |           |               | 0.700 |

Table 1: Three fresh paired confirmations on the fixed task. Both
policies deliver all 312 frames with audio; $`H/H_{P}`$ is the
complete-delivery latency ratio.

The updated policy wins all three pairs and reduces complete-delivery
latency by 30.0%. Average active FFmpeg cores, measured as tool CPU
seconds divided by delivery time, rise from 0.95 to 1.80. Cumulative
FFmpeg CPU seconds increase by 32.4%, while source-response payload
falls from 44.7–46.9 MB to 19.9–20.1 MB. Materialization mobilizes local
compute and approximately halves traffic on the constrained input path.

### 6.2 Transfer, Correctness, and Video Fidelity

The frozen-policy evaluation reveals both latency changes and execution
failures (Figure 3). The materialization policy completes 48/48
executions; the reference completes 40/48. Eight reference executions
lose frames under input shaping, leaving the all-task primary speed
comparison undefined. These incomplete outputs are recorded as execution
failures.

Figure 3: Frozen-policy transfer: per-configuration $`H/H_{P}`$ latency,
geometric mean of two fresh pairs. Values below one favor $`H`$. Crosses
in the lower strip mark reference frame deficits, which leave the
full-panel speed ratio undefined. All $`H`$ outputs complete.

Conditional on both outputs being complete, latency reductions range
from 15.7–37.5% at 4 MiB/s and 39.1–55.3% at 1.5 MiB/s. Local input
provides a same-action control: per-configuration ratios span
0.914–1.082, with an aggregate ratio of 1.014 \[0.979, 1.044\]. This
spread shows the measurement variability with two pairs per
configuration.

Materialization adds intermediate re-encoding. On fully aligned
shaped-input pairs, SSIM is 0.9843–0.9956 and PSNR is 32.8–46.4 dB, so
the latency reductions accompany a measurable fidelity loss. Audio
sample counts match in all pairs. Appendix B gives the delivery and
fidelity breakdown.

### 6.3 Policy Evolution Across Two Seeds

The first plan-search seed obtains an 8.2% reduction relative to range4,
the best fixed plan in that run, and a 6.6% reduction on unseen
input-response conditions. The evolved/initial ratio is 0.996 \[0.988,
1.003\] (Figure 4). The evolved and initial policies close 73.0% and
69.0% of the logarithmic bank-oracle gap. The policies select fused
execution at low input-service rates and use task features to condition
the physical plan.

Figure 4: Within-seed latency ratios and task-clustered 95% intervals on
eight held-out tasks and 192 cells per seed. Values below one favor the
numerator. Seed B has higher external CPU contention. Recursive denotes
analysis rewriting; initial denotes the first policy-only proposal.

The second seed runs under higher external CPU occupancy, approximately
0.69 versus 0.01 on assigned cores. Policy-only iteration reduces
latency relative to its initial proposal by 4.6%, with ratio 0.954
\[0.933, 0.976\]. Figure 4 and Table 4 report the policy and
analysis-rewriting comparisons in both seeds. Table 5 gives all
fixed-plan references.

### 6.4 Physical Response and Server Execution

Controlled CPU-affinity measurements reveal different resource responses
for the physical plans (Figure 5). Fused execution benefits from larger
affinity sets beyond the point where staged execution largely flattens.
This plan-dependent response motivates conditioning the harness on both
task structure and available resources.

Figure 5: Physical-plan response to CPU affinity. Each point averages
six compositions, with one observation per composition, plan, and
setting. FFmpeg uses automatic threads under a 128 MiB/s logical
read/write service. Affinity-set size specifies eligible CPUs on a
shared host.

Additional within-host comparisons cover servers equipped with A100,
RTX 3090, and RTX 4090 GPUs. A DAG-aware rule shortens six-task episodes
relative to native concurrency-three execution in five host/resource
conditions (Appendix C). That appendix also separates a model-call
orchestration gain from native rendering time and reports a same-program
feedback comparison.

## 7 Discussion

Cold-start measurements contribute through the execution choices they
change. In the adaptation case, firsthand comparisons lead the improver
to materialize clips before fusion. This reduces source traffic and
exposes more local concurrency, lowering delivery latency as CPU
utilization rises. The transfer measurements also reveal the fidelity
effects of intermediate re-encoding. The scheduling comparison
quantifies the interaction between useful overlap and interference with
active work. These outcomes illustrate how observations from the target
setting guide physical harness decisions.

## 8 Conclusion

DeltaHarness uses cold-start measurements to learn how execution plans
behave under the current task and resource conditions. This information
guides dispatch, physical-policy revision, and further measurement. With
fixed dispatch and tool kernels, a model-selected materialization plan
reduces complete-delivery latency by 30.0% on one task. Held-out policy
search beats the best fixed plan in one seed and improves its initial
policy in another.

## Appendix A Policy Interfaces and Recursive Variant

#### Physical policy interface.

The Mac policy evaluates ordered conditions, assigns missing-value
behavior, and ends with a complete default plan. Task features include
source intervals, clip count, output frames, transitions, and estimated
decode work. The Linux studies use sandboxed source policies. Table 3
lists the physical choices exposed by the executor; each comparison
fixes its compiler and tool implementation.

| Parameter            | Physical choice                |
| -------------------- | ------------------------------ |
| $`K`$                | Number of output ranges, 1–32  |
| Range pool           | Concurrent range operations    |
| Cut mode             | Even or clip-aware cuts        |
| LPT                  | Order ranges by estimated work |
| Hardware decode      | Request when supported         |
| Materialize          | Create intermediate clips      |
| Materialization pool | Concurrent intermediates       |
| Audio first          | Audio/video insertion order    |

Table 3: Typed physical policy parameters. CPU-only experiments fix
hardware decoding off.

#### Recursive analysis rewriting.

The policy-only improver has a fixed method description and analysis
procedure. The recursive improver rewrites both its method description
and a sandboxed analyze(data) function every two rounds. This function
reads the arm’s accumulated task features, resource observations, plan
parameters, wall times, tool CPU times, and I/O counts. Its output
enters later policy prompts. If $`a_{r}`$ is that analysis program, the
additional update is

```math
\displaystyle a_{r+1} \displaystyle=\mathcal{R}(a_{r},\mathcal{D}_{r}), \tag{6}
```

```math
\displaystyle\widetilde{H}_{r+1} \displaystyle=M(H_{r},\mathcal{D}_{r},a_{r+1}(\mathcal{D}_{r})).
```

Model weights and the experiment-selection procedure remain fixed in
this analysis-rewriting comparison. Rewriting the experiment-selection
program $`I`$ would constitute another recursive layer.
