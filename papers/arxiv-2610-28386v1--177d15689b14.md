# VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning

Jiawei Wang    Yucun Li    Xueqi Li    Shenghao Wang    Xinquan Gong   
Dan Zhang    Zheqi Lv    Yuquan Le    Shaozu Yuan    An Zhang    Da Cao
   Tat-Seng Chua

###### Abstract

Visual tool use enables vision-language models (VLMs) to acquire
task-relevant evidence, but its effectiveness can be limited by
predefined visual operations and the tool-use strategies learned during
training. Representing these operations and strategies as reusable
external skills allows them to be refined through self-evolution without
updating model parameters. However, skill refinement can introduce
performance regressions. Meanwhile, inspecting accumulated task
execution trajectories together with skill evolution history may lead to
evolution evidence overload. To address these challenges, we propose
VisualEvolve, a self-evolving framework that evolves executable visual
operations and tool-use strategies for VLMs through a
Select–Execute–Evolve–Evaluate cycle. Skill-Library Snapshot Selection
uses performance on a fixed validation set disjoint from execution tasks
to select an effective historical snapshot for subsequent evolution,
limiting the propagation of performance regressions. Progressive
Evidence Access (PEA) guides capability-gap diagnosis through a
coarse-to-fine hierarchy comprising the Skill-Performance Report,
Evolution Log, Trajectory Summaries, and relevant raw trajectory
segments. Across four VLM backbones and six evaluation sets from three
benchmarks, VisualEvolve improves over the Initial Skill Library in 23
of 24 settings, with a maximum gain of 15.1 percentage points on
VisualProbe Hard using Qwen3.5-Plus. Ablation studies support the
contributions of Snapshot Selection and PEA, while further experiments
show that skills can be improved using experience from different data
settings and directly reused across backbones. Moreover, VisualEvolve
enables effective skill self-evolution with over an order of magnitude
fewer task-solving trajectories than estimated for representative
RL-based methods.

## Introduction

By adopting visual tool use, vision-language models (VLMs) are capable
of inspecting and manipulating images during reasoning ([Wu and Xie,
2024](#bib.bib30); [Wu et al., 2026](#bib.bib29); [Song et al.,
2026](#bib.bib21)). Its effectiveness depends on both the available
visual operations and the strategies that determine when and how to use
them ([Zheng et al., 2026](#bib.bib35); [Lai et al., 2026](#bib.bib9)).
Training-based approaches, such as DeepEyes ([Zheng et al.,
2026](#bib.bib35)) and Mini-o3 ([Lai et al., 2026](#bib.bib9)), learn
these strategies through supervised fine-tuning (SFT) or reinforcement
learning (RL) over predefined visual operations. However, limitations in
available visual operations or their usage strategies may prevent models
from acquiring task-relevant visual evidence ([Lai et al.,
2026](#bib.bib9); [Sun et al., 2026](#bib.bib23); [Wang et al.,
2026b](#bib.bib26)). This motivates adapting both visual operations and
tool-use strategies to the needs revealed during task execution ([Sun
et al., 2026](#bib.bib23); [Huang et al., 2026](#bib.bib6); [Lin et al.,
2026b](#bib.bib13)). Recent work represents reusable task guidance as
external skill – structured instructions for performing a class of
tasks, which can be paired with executable tools ([Sun et al.,
2026](#bib.bib23); [Yu et al., 2026](#bib.bib31)). Stored outside model
parameters, these instructions and associated tools can be refined
without retraining the model ([Sun et al., 2026](#bib.bib23)).

Self-evolution enables an agent to refine its external skill library
through task execution and feedback ([Jiang et al., 2026](#bib.bib7);
[Sun et al., 2026](#bib.bib23)). The goal is to turn experience
accumulated over multiple rounds into reusable visual reasoning
skills ([Jiang et al., 2026](#bib.bib7); [Ni et al., 2026](#bib.bib15);
[Sun et al., 2026](#bib.bib23)). However, skill evolution faces two
challenges. First, skill refinement can introduce performance
regressions, even when it addresses failures observed during task
execution ([Wei et al., 2026](#bib.bib28); [Li and Hu,
2026](#bib.bib11)). Second, skill evolution requires analyzing not only
task execution trajectories, but also the history of skill modifications
and evaluation results ([Li and Hu, 2026](#bib.bib11); [Wei et al.,
2026](#bib.bib28)). As these records accumulate, inspecting them all at
once can cause evolution evidence overload, increasing the context
burden and making capability gaps harder to diagnose ([Lee et al.,
2026](#bib.bib10); [Lin et al., 2026a](#bib.bib12)).

To address these challenges, we propose VisualEvolve, a self-evolving
framework that evolves executable visual operations and tool-use
strategies for VLMs through a Select–Execute–Evolve–Evaluate cycle. Each
cycle comprises four stages: (1) Select. To limit the propagation of
performance regressions, Skill-Library Snapshot Selection guides the
agent to choose a starting library from archived snapshots based on
validation performance; (2) Execute. The selected library is applied to
visual reasoning tasks, producing execution trajectories, correctness
labels, and Trajectory Summaries for capability-gap diagnosis; (3)
Evolve. To address evolution evidence overload, we introduce Progressive
Evidence Access (PEA), which guides capability-gap diagnosis through
coarse-to-fine access to skill evolution history and current execution
evidence. These diagnoses guide revisions to the skill library; (4)
Evaluate. The revised library is assessed on a fixed validation set
disjoint from the execution tasks and archived as a new snapshot. The
resulting validation feedback and updated evolution records support
subsequent snapshot selection and capability-gap diagnosis. Together,
these components enable VisualEvolve to build on effective historical
skill libraries while diagnosing capability gaps through coarse-to-fine
access to execution evidence and evolution history.

As summarized in
Figure [1](#S0.F1 "Figure 1 ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning"),
experiments with four frozen VLM backbones across six evaluation sets
from three benchmarks show that evolving external skills improves visual
reasoning without updating model parameters. VisualEvolve outperforms
the Initial Skill Library in 23 of 24 backbone–evaluation-set
combinations, with the largest gain of 15.1 percentage points (38.1%
relative) on VisualProbe Hard using Qwen3.5-Plus. Ablation studies show
that both selecting the skill-library snapshot for further evolution and
organizing evidence through PEA contribute to these gains. Experiments
under three evolution-data settings further show that VisualEvolve can
improve its skills through self-evolution using execution experience
from different data sources. Finally, we transfer the skill library
evolved with Kimi-K2.5 to three other VLM backbones without
modification. The transferred library improves their average accuracy
over the Initial Skill Library, demonstrating that the evolved skills
can be directly reused across models. Our main contributions can be
summarized as follows:

- •
  We propose VisualEvolve, a self-evolving framework that evolves
  executable visual operations and tool-use strategies for VLMs through
  a Select–Execute–Evolve–Evaluate cycle.
- •
  We introduce Skill-Library Snapshot Selection to select the historical
  snapshot with the highest validation accuracy for subsequent
  evolution, and Progressive Evidence Access to guide capability-gap
  diagnosis through coarse-to-fine access to task execution trajectories
  and skill evolution history.
- •
  We demonstrate that VisualEvolve improves visual reasoning across four
  backbones and three benchmarks without updating model parameters.
  Ablation studies demonstrate the contributions of key stages in the
  evolution cycle and Progressive Evidence Access. Further experiments
  demonstrate effective skill improvement through self-evolution using
  experience from different data sources and direct reuse of evolved
  skills across backbones.

## Related Work

Training-Based Visual Reasoning Agents. Training-based visual reasoning
agents acquire task-relevant evidence through tool use, from invoking
predefined tools such as cropping ([Lai et al., 2026](#bib.bib9); [Zhao
et al., 2026](#bib.bib34); [Chng et al., 2026](#bib.bib3)) to generating
and executing image-processing code ([Zhang et al., 2026](#bib.bib32);
[Song et al., 2026](#bib.bib21); [Guo et al., 2026](#bib.bib4)). These
methods typically optimize when and how to invoke such operations
through SFT, RL, or both ([Su et al., 2025](#bib.bib22); [Lu et al.,
2026](#bib.bib14); [Chen et al., 2026](#bib.bib2)). In contrast,
VisualEvolve keeps the backbone frozen and improves visual reasoning by
evolving external skills.

Skill-Based Agents. External skills encode reusable capabilities ([Yu
et al., 2026](#bib.bib31)) as executable programs ([Wang et al.,
2024](#bib.bib24); [Wang et al., 2026a](#bib.bib25); [Shao et al.,
2026](#bib.bib19)), structured guidance for planning and tool
use ([Jiang et al., 2026](#bib.bib7)), or natural-language instructions
augmented with optional executable and supporting resources ([Ni et al.,
2026](#bib.bib15); [Lin et al., 2026a](#bib.bib12)). VisualEvolve adapts
this paradigm to visual reasoning by representing each skill as a
tool-use strategy paired with an optional visual operation.

Self-Evolving Agents. Self-evolving agents improve over time by
externalizing accumulated experience into reusable artifacts, including
verbal reflections ([Shinn et al., 2023](#bib.bib20)), experiential
knowledge ([Zhao et al., 2024](#bib.bib33); [Ouyang et al.,
2026](#bib.bib16)), and reusable skills ([Wang et al.,
2024](#bib.bib24); [Wei et al., 2026](#bib.bib28); [Ni et al.,
2026](#bib.bib15); [Sun et al., 2026](#bib.bib23)). Recent methods
retain richer evolution histories. SkillHone records diagnoses,
revisions, and feedback to support continual skill refinement ([Li and
Hu, 2026](#bib.bib11)), while Meta-Harness gives its proposer access to
the source code, scores, and traces of prior harness candidates ([Lee
et al., 2026](#bib.bib10)). VisualEvolve focuses on two challenges in
multi-round skill evolution: performance regressions after skill updates
and evidence overload from accumulated evolution history. Snapshot
Selection selects the historical snapshot with the highest validation
accuracy for subsequent evolution, while Progressive Evidence Access
organizes accumulated evidence into a coarse-to-fine hierarchy for
capability-gap diagnosis.

## Method

### Problem Formulation

We study the problem of evolving a skill library to improve performance
on visual reasoning tasks. Given a frozen backbone
$`\mathcal{A}_{\theta}`$, an initial skill library $`\mathcal{L}_{0}`$,
evolution data $`\mathcal{D}_{\mathrm{evo}}`$, and an evolution budget
of $`R`$ rounds, we construct a fixed validation set
$`\mathcal{D}_{\mathrm{val}}\subset\mathcal{D}_{\mathrm{evo}}`$ and
round-specific execution sets
$`\mathcal{D}^{\mathrm{exe}}_{r}\subset\mathcal{D}_{\mathrm{evo}}\setminus\mathcal{D}_{\mathrm{val}}`$
for $`r=1,\ldots,R`$. VisualEvolve iteratively updates the skill library
and obtains a sequence of skill-library snapshots
$`\{\mathcal{L}_{0},\mathcal{L}_{1},\ldots,\mathcal{L}_{R}\}`$. Each
snapshot $`\mathcal{L}_{t}`$ is evaluated on
$`\mathcal{D}_{\mathrm{val}}`$, yielding the validation accuracy
$`a_{t}^{\mathrm{val}}=\mathrm{Acc}(\mathcal{A}_{\theta},\mathcal{L}_{t};\mathcal{D}_{\mathrm{val}})`$.
We select the snapshot with the highest validation accuracy as the final
skill library $`\mathcal{L}^{\star}`$ and assess its performance on
evaluation sets reserved for final testing.

### Framework Overview

As shown in
Figure [2](#S2.F2 "Figure 2 ‣ Related Work ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning"),
VisualEvolve evolves a skill library through multi-round
Select–Execute–Evolve–Evaluate cycles. Skill-Library Snapshot Selection
chooses the starting skill library, Execute applies it to the execution
set to collect execution evidence, Evolve diagnoses capability gaps and
updates the skill library, and Evaluate assesses and archives the
updated skill library. The prompt guiding the evolution process is
provided in
Appendix [F.3](#A6.SS3 "Self-Evolving Agent User Prompt ‣ Appendix F Agent Prompts ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning").

### Skill-Library Snapshot Selection

To limit the propagation of performance regressions across evolution
rounds, each round begins with Skill-Library Snapshot Selection, which
selects a previously archived skill-library snapshot as the starting
point. Formally, we denote a skill library by
$`\mathcal{L}=\{s_{i}\}_{i=1}^{N}`$, where each skill
$`s_{i}=(\pi_{i},u_{i})`$ consists of a textual strategy $`\pi_{i}`$ and
an optional executable visual operation $`u_{i}`$.

In the first round, VisualEvolve starts from the initial skill library
$`\mathcal{L}_{0}`$, which contains a single crop skill and is detailed
in
Appendix [E](#A5 "Appendix E Initial Skill Library ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning").
For each subsequent round $`r>1`$, rather than always evolving from the
latest snapshot, VisualEvolve selects the archived snapshot with the
highest validation accuracy among
$`\mathcal{L}_{0},\ldots,\mathcal{L}_{r-1}`$. The selected snapshot,
denoted by $`\mathcal{L}_{p_{r}}`$, serves as the starting skill library
for round $`r`$.

### Execute

To construct execution evidence for Evolve, Execute applies the selected
starting skill library $`\mathcal{L}_{p_{r}}`$ to the execution set,
producing trajectories, correctness labels, and Trajectory Summaries.

At round $`r`$, the Worker, a task-solving agent instantiated with the
frozen backbone $`\mathcal{A}_{\theta}`$ and equipped with
$`\mathcal{L}_{p_{r}}`$, solves tasks from the execution set
$`\mathcal{D}_{r}^{\mathrm{exe}}`$, producing trajectories that record
the task-solving process and final predictions. To distinguish
successful and failed outcomes for subsequent diagnosis, each trajectory
is assigned a correctness label by comparing its final prediction with
the ground-truth answer. Finally, to reduce the context burden of
trajectory analysis while preserving traceable evidence, each trajectory
is compressed into a source-linked Trajectory Summary, where each
summary comprises multiple findings that capture capability-relevant
behaviors and reference the corresponding supporting spans in the raw
trajectory. Additional details and the Execute instruction are provided
in
Appendices [A.1](#A1.SS1 "Execute Details ‣ Appendix A Method Details ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning")
and [G.1](#A7.SS1 "Execute Meta-Skill ‣ Appendix G Meta-Skills ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning"),
respectively.

### Evolve

Evolve uses execution evidence together with the history of skill
modifications and evaluation results to diagnose capability gaps and
update the starting skill library $`\mathcal{L}_{p_{r}}`$. Since loading
all available evidence at once would incur evolution evidence overload,
we introduce Progressive Evidence Access, which enables the
Self-Evolving Agent, primarily responsible for capability-gap diagnosis
and skill-library updates, to access evidence from coarse to fine. It
first identifies relevant skills through the Skill-Performance Report,
traces their historical modifications through the Evolution Log,
analyzes current-round Trajectory Summaries for recurring failure
patterns, and accesses relevant raw trajectory segments only when
finer-grained evidence is needed.

Skill-Performance Report. Validation accuracy measures the performance
of a skill library but does not indicate which skills are associated
with performance changes. We therefore introduce the Skill-Performance
Report, which estimates each skill’s association with changes in
validation performance through a Skill Performance Score (SPS). The SPS
is defined as the difference in mean correctness between two
skill-library snapshots over the skill-associated validation subset.

Specifically, for two snapshots $`\mathcal{L}_{a}`$ and
$`\mathcal{L}_{b}`$, we define the skill-associated validation subset as

|     |     |     |
| --- | --- | --- |
|     |

````math
\mathcal{D}^{a,b}_{s}=\left\{d_{j}\in\mathcal{D}_{\mathrm{val}}\mid s\in Z_{j}^{(a)}\lor s\in Z_{j}^{(b)}\right\},
``` |  |

where $`Z_{j}^{(a)}`$ and $`Z_{j}^{(b)}`$ denote the sets of skills
loaded while solving validation example $`d_{j}`$ with
$`\mathcal{L}_{a}`$ and $`\mathcal{L}_{b}`$, respectively. Thus,
$`\mathcal{D}^{a,b}_{s}`$ contains all validation examples on which
$`s`$ is loaded under at least one of the two snapshots. For
$`|\mathcal{D}^{a,b}_{s}|>0`$, SPS is computed as the difference in mean
correctness between the two snapshots on this subset:

|  |  |  |
|----|----|----|
|  |
``` math
\operatorname{SPS}_{a\rightarrow b}(s)=\frac{1}{|\mathcal{D}^{a,b}_{s}|}\sum_{d_{j}\in\mathcal{D}^{a,b}_{s}}c^{(b)}(d_{j})-\frac{1}{|\mathcal{D}^{a,b}_{s}|}\sum_{d_{j}\in\mathcal{D}^{a,b}_{s}}c^{(a)}(d_{j}),
``` |  |

where $`c^{(a)}(d_{j}),c^{(b)}(d_{j})\in\{0,1\}`$ indicate whether
$`d_{j}`$ is answered correctly under $`\mathcal{L}_{a}`$ and
$`\mathcal{L}_{b}`$, respectively. The sign of SPS indicates the
direction of the performance difference, while its absolute value
indicates the strength of association. Since multiple skills may be
loaded together, SPS provides only an approximate estimate of an
individual skill’s contribution to the performance change.

At round $`r>1`$, the Self-Evolving Agent uses the report from round
$`r-1`$, which contains SPS values for up to three snapshot pairs:
$`(\mathcal{L}_{p_{r-1}},\mathcal{L}_{r-1})`$,
$`(\mathcal{L}_{0},\mathcal{L}_{r-1})`$, and
$`(\mathcal{L}_{0},\mathcal{L}_{p_{r-1}})`$. The agent considers these
values jointly and prioritizes skills with large absolute SPS for
further inspection.

Evolution Log. The Skill-Performance Report identifies skills associated
with performance changes but does not reveal how these skills have
changed across archived snapshots. We therefore introduce the Evolution
Log, which records each snapshot’s validation accuracy and indexes
per-skill differences between consecutive snapshots. The Self-Evolving
Agent uses the accuracy history to locate improvement or regression
intervals and inspects the corresponding historical changes of the
identified skills, providing references for update directions to reuse
or avoid.

Trajectory Summary. After obtaining historical references for skill
updates, the Self-Evolving Agent turns to current-round execution
evidence. Using the correctness labels, it prioritizes the Trajectory
Summaries associated with incorrect predictions, identifies recurring
failure patterns, and abstracts them into capability gaps, such as
repeatedly revisiting the same image regions and stopping visual search
before sufficient evidence is collected.

Trajectory. When finer-grained evidence is needed, the Self-Evolving
Agent follows the source references in Trajectory Summaries to relevant
segments of trajectories, exposing detailed reasoning and tool-use
behavior behind the identified failures.

Based on the diagnosed capability gaps, Evolve updates the starting
skill library $`\mathcal{L}_{p_{r}}`$ by modifying, adding, or removing
skills, yielding $`\mathcal{L}_{r}`$. For an existing skill
$`s_{i}=(\pi_{i},u_{i})`$, the update can revise its tool-use strategy
$`\pi_{i}`$ or executable visual operation $`u_{i}`$. Before Evaluate,
$`\mathcal{L}_{r}`$ undergoes structural and executability checks. These
checks and the construction of the Skill-Performance Report and
Evolution Log are detailed in
Appendix [A.2](#A1.SS2 "Evolve Details ‣ Appendix A Method Details ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning"),
while the Evolve instruction is provided in
Appendix [G.2](#A7.SS2 "Evolve Meta-Skill ‣ Appendix G Meta-Skills ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning").

### Evaluate

To provide a consistent generalization signal across evolution rounds,
Evaluate assesses the updated skill library $`\mathcal{L}_{r}`$ on the
fixed validation set $`\mathcal{D}_{\mathrm{val}}`$ using the Worker,
yielding the validation accuracy $`a_{r}^{\mathrm{val}}`$. The
Skill-Performance Report and Evolution Log are then updated for use in
the next round’s Evolve stage, while $`\mathcal{L}_{r}`$ is archived as
a new skill-library snapshot for the next round’s Snapshot Selection.
The instruction for Evaluate is provided in
Appendix [G.3](#A7.SS3 "Evaluate Meta-Skill ‣ Appendix G Meta-Skills ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning").

### Evolution Procedure

The complete evolution procedure repeatedly cycles through Skill-Library
Snapshot Selection, Execute, Evolve, and Evaluate until all $`R`$
evolution rounds are completed. All agents use the same frozen VLM
backbone. At each round $`r`$, Snapshot Selection first determines the
starting skill library $`\mathcal{L}_{p_{r}}`$. Execute applies
$`\mathcal{L}_{p_{r}}`$ to a round-specific execution set, producing
trajectories, correctness labels, and Trajectory Summaries. Evolve then
uses Progressive Evidence Access to diagnose capability gaps using the
Skill-Performance Report, Evolution Log, Trajectory Summaries, and, when
needed, relevant raw trajectory segments, and updates the starting skill
library to produce the updated library $`\mathcal{L}_{r}`$. Evaluate
assesses and archives the $`\mathcal{L}_{r}`$, while updating the
Skill-Performance Report and Evolution Log for subsequent rounds. After
all $`R`$ rounds are completed, the archived snapshot with the highest
validation accuracy is returned as the final skill library
$`\mathcal{L}^{\star}`$.

## Experiments

To evaluate VisualEvolve, we conduct comprehensive experiments to
explore the following research questions. RQ1: How does VisualEvolve
improve over Single-Pass inference and the Initial Skill Library, and
how does it compare with representative training-based visual-reasoning
baselines? RQ2: How do the framework stages and the evidence-access
mechanism within Progressive Evidence Access contribute to effective
multi-round skill evolution? RQ3: How does VisualEvolve evolve a skill
library using execution experience from different data sources, and how
well does the evolved skill library transfer across backbones? RQ4: What
is the cost of skill evolution, and what additional inference-time cost
does the evolved skill library introduce?

### Experimental Setup

Evolution Data. We use evolution data $`\mathcal{D}_{\mathrm{evo}}`$ as
the source of execution tasks for skill evolution. In the default
setting, $`\mathcal{D}_{\mathrm{evo}}`$ combines VisualProbe_(train),
with 2.9K samples for challenging visual search ([Lai et al.,
2026](#bib.bib9)), and the Visual Search component of the DeepEyes
training corpus, with approximately 22K samples from the $`V^{*}`$
training set for visual grounding and fine-grained perception ([Wu and
Xie, 2024](#bib.bib30); [Zheng et al., 2026](#bib.bib35)). We retain
only the original image, question, and answer.

Benchmarks. We use separate benchmarks for final evaluation. V^(\*)Bench
contains 191 examples for fine-grained visual search and spatial
reasoning ([Wu and Xie, 2024](#bib.bib30)), HRBench4K and HRBench8K each
contain 800 high-resolution visual-reasoning examples ([Wang et al.,
2025](#bib.bib27)), and VisualProbe Easy, Medium, and Hard contain 141,
268, and 106 examples, respectively, covering increasingly challenging
exploratory visual reasoning ([Lai et al., 2026](#bib.bib9)).

Baselines. We compare VisualEvolve against three types of baselines.
Single-Pass queries the VLM backbone in a single turn without external
tools, serving as the baseline. Initial Skill Library equips each
backbone with $`\mathcal{L}_{0}`$ and serves as the baseline for
measuring gains from evolution. Training-Based Methods include
representative visual-reasoning agents trained with RL, with or without
prior SFT ([Su et al., 2025](#bib.bib22); [Zheng et al.,
2026](#bib.bib35); [Lai et al., 2026](#bib.bib9); [Hong et al.,
2026](#bib.bib5); [Guo et al., 2026](#bib.bib4)).

Implementation Details. We run VisualEvolve for $`R=16`$ evolution
rounds. Before the first round, we sample a fixed 200-example validation
set $`\mathcal{D}_{\mathrm{val}}`$ from $`\mathcal{D}_{\mathrm{evo}}`$.
At each round $`r`$, we sample 32 examples from
$`\mathcal{D}_{\mathrm{evo}}\setminus\mathcal{D}_{\mathrm{val}}`$ to
form $`\mathcal{D}_{r}^{\mathrm{exe}}`$. When
$`\mathcal{D}_{\mathrm{evo}}`$ combines multiple datasets, balanced
sampling is applied to both the validation and execution sets, drawing
an equal number of examples from each dataset. We use
Qwen3.5-Plus ([Qwen Team, 2026a](#bib.bib17)), Qwen3.6-Plus ([Qwen Team,
2026b](#bib.bib18)), Kimi-K2.5 ([Kimi Team et al., 2026](#bib.bib8)),
and Doubao-Seed-2.0-Pro ([Bytedance Seed, 2026](#bib.bib1)), with
temperature $`0`$ and thinking mode enabled.

### Ablation Study (RQ2)

We conduct ablation studies with Qwen3.5-Plus to assess framework stages
and the evidence-access mechanism in Progressive Evidence Access.

For the stage ablations, w/o Skill-Library Snapshot Selection starts
from the latest skill library. w/o Execute removes execution evidence.
w/o Evaluate removes evaluation on the validation set, thereby disabling
Snapshot Selection and leaving the Skill-Performance Report and
Evolution Log empty. For Progressive Evidence Access ablations, w/o
Skill-Performance Report removes skill screening before Evolution Log
analysis, w/o Evolution Log removes the structured association between
historical skill modifications and validation accuracy, and w/o
Trajectory Summary removes trajectory compression. w/o Skill-Performance
Report + Evolution Log removes the hierarchical access provided by these
two components, while w/o Progressive Evidence Access further removes
Trajectory Summaries, so validation-accuracy history, skill-change
history, and raw trajectories are accessed directly without hierarchical
organization.

We make the following observations from
Table [3](#S4.F3 "Figure 3 ‣ Main Results (RQ1) ‣ Experiments ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning")
and
Figure [3](#S4.F3 "Figure 3 ‣ Main Results (RQ1) ‣ Experiments ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning").
(1) All three framework stages contribute substantially to multi-round
skill evolution. Compared with the full framework, removing
Skill-Library Snapshot Selection, Execute, or Evaluate reduces
macro-average accuracy by 5.4, 7.7, and 6.4 percentage points,
respectively. In particular, w/o Execute reaches only 61.5% best-so-far
validation accuracy, highlighting the importance of execution evidence
for effective skill updates. (2) The ablations support the effectiveness
of the coarse-to-fine evidence-access mechanism in Progressive Evidence
Access. Removing any individual component reduces macro-average accuracy
by 2.6–4.6 percentage points. The combined ablations lead to larger
degradation: jointly removing the Skill-Performance Report and Evolution
Log reduces accuracy by 5.8 percentage points, while removing PEA
entirely leads to the largest drop of 6.3 percentage points.

## Conclusion

Self-evolution turns accumulated experience into reusable visual
reasoning skills, but multi-round evolution can suffer from performance
regressions and evolution evidence overload. VisualEvolve addresses
these challenges with Skill-Library Snapshot Selection, which selects
the historical snapshot with the highest validation accuracy, and
Progressive Evidence Access, which organizes evidence into a
coarse-to-fine hierarchy for capability-gap diagnosis. Across four
backbones and six evaluation sets from three benchmarks, VisualEvolve
improves over the Initial Skill Library in 23 of 24
backbone–evaluation-set combinations, with a maximum gain of 15.1
percentage points on VisualProbe Hard. Ablation studies support the
contributions of both Skill-Library Snapshot Selection and Progressive
Evidence Access. Further experiments show that VisualEvolve can improve
skills using execution experience from different data sources, and that
the evolved skill library can be directly reused across VLM backbones.

## Appendix A Method Details

### Execute Details

This section provides additional implementation details for the Execute
stage, including execution set sampling and source references that link
trajectory summaries to supporting spans in the original trajectories.

Balanced Sampling. When the evolution data combine multiple datasets,
VisualEvolve applies balanced sampling to ensure that each dataset
contributes equally to the evolution evidence. Before evolution begins,
VisualEvolve constructs the fixed validation set
$`\mathcal{D}_{\mathrm{val}}`$ using random seed 42 and removes the
selected validation samples from the evolution data. Then, at each
evolution round $`r`$, Execute uses the round index $`r`$ as the random
seed and samples 16 examples from each source, yielding a 32-example
execution set $`\mathcal{D}_{r}^{\mathrm{exe}}`$. Therefore, the
validation set remains fixed across rounds, while the execution set is
resampled with a round-specific seed, and
$`\mathcal{D}_{r}^{\mathrm{exe}}\cap\mathcal{D}_{\mathrm{val}}=\varnothing`$
for every round.

Trajectory Summaries and Source References. For a trajectory
$`T_{r,j}`$, the Memory Agent, a trajectory-processing agent, constructs
the corresponding trajectory summary $`m_{r,j}`$. Each trajectory
summary contains concise, evidence-supported findings that describe
individual behaviors or observations during task execution, including
the skills actually loaded, visual operations invoked, intermediate
observations, verification behavior, failed attempts, and final
prediction. Each finding retains a line-level reference to its
supporting span in the original trajectory. For example,
\[\[trajectory.json\|L3-L16\]\] indicates that the finding is supported
by Lines 3–16 of trajectory.json. The Self-Evolving Agent can follow
this reference through a file-reading command that specifies the
corresponding start and end lines. Trajectory summaries thereby compress
lengthy trajectories while preserving traceable access to the original
evidence. During Evolve, the Self-Evolving Agent reads the summarized
task evidence in
$`\mathcal{M}_{r}=\{m_{r,j}\}_{j=1}^{|\mathcal{D}_{r}^{\mathrm{exe}}|}`$
by default. It follows line-level references to the corresponding
trajectory segments only when a trajectory summary is insufficient for
reliable diagnosis. Complete raw trajectories therefore remain available
as fine-grained evidence but are not loaded by default.

### Evolve Details

This section provides additional implementation details for the Evolve
stage, including post-update structural and executability checks and the
construction of the Skill-Performance Report and Evolution Log.

CheckAndRepair. After the Self-Evolving Agent updates the skill library,
the Orchestrator, a framework-level controller that manages auxiliary
procedures, automatically checks its structural validity and
executability before the library enters the Evaluate stage. Each skill
is stored in a separate directory whose name must match the name field
in the YAML frontmatter of SKILL.md. Optional executable visual
operations are stored in the scripts/ subdirectory and must follow the
prescribed interface. Structural checks verify the directory name, YAML
frontmatter, Markdown format, and referenced file paths. Executability
checks load each optional visual operation through the prescribed
interface and perform a basic invocation. If any check fails,
Orchestrator returns the failure location and diagnostic message for
targeted repair.

Skill-Performance Report Construction. After Evaluate assesses a
skill-library snapshot $`\mathcal{L}_{t}`$ on the fixed validation set,
it records the correctness of each validation example together with the
skills actually loaded. These records form a validation skill-exposure
profile

|  |  |  |
|----|----|----|
|  |
``` math
\mathcal{V}_{t}=\left\{\left(c^{(t)}(d_{j}),Z_{j}^{(t)}\right)\right\}_{d_{j}\in\mathcal{D}_{\mathrm{val}}},
``` |  |

where $`c^{(t)}(d_{j})\in\{0,1\}`$ indicates whether validation example
$`d_{j}`$ is answered correctly under $`\mathcal{L}_{t}`$, and
$`Z_{j}^{(t)}`$ denotes the set of skills loaded while solving
$`d_{j}`$.

At the end of round $`r`$, the Skill-Performance Report
$`\mathrm{SPR}_{r}`$ is constructed from the validation skill-exposure
profiles of the initial snapshot $`\mathcal{V}_{0}`$, the starting
snapshot $`\mathcal{V}_{p_{r}}`$, and the updated snapshot
$`\mathcal{V}_{r}`$. Following the SPS definition in
Section [3.5](#S3.SS5 "Evolve ‣ Method ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning"),
the report considers the snapshot pairs
$`(\mathcal{L}_{p_{r}},\mathcal{L}_{r})`$,
$`(\mathcal{L}_{0},\mathcal{L}_{r})`$, and
$`(\mathcal{L}_{0},\mathcal{L}_{p_{r}})`$. For each pair, SPS is
computed only for skills whose corresponding skill-associated validation
subset is non-empty. When snapshot pairs coincide, the number of
distinct comparisons is smaller than three. The resulting
$`\mathrm{SPR}_{r}`$ replaces the previous report and is used in round
$`r+1`$.

Evolution Log Construction. The Evolution Log $`\mathcal{G}_{r-1}`$
records how the skill library changes across evolution rounds together
with the corresponding validation performance. After evaluating the
evolved library $`\mathcal{L}_{r}`$, the Orchestrator computes the
difference between the skill-library snapshots from two consecutive
rounds, $`\mathcal{L}_{r-1}`$ and $`\mathcal{L}_{r}`$:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\Delta\mathcal{L}_{r}=\operatorname{Diff}\!\left(\mathcal{L}_{r-1},\mathcal{L}_{r}\right).
``` |  | (1) |

The resulting per-skill differences are stored as separate .diff files,
each recording the change to a corresponding skill between the two
snapshots. Let $`\operatorname{Ref}(\Delta\mathcal{L}_{r})`$ denote an
index of references to these files. The Orchestrator then constructs an
evolution record for round $`r`$:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\rho_{r}=\left(r,a_{r}^{\mathrm{val}},\operatorname{Ref}(\Delta\mathcal{L}_{r})\right),
``` |  | (2) |

where $`r`$ is the current round index, $`a_{r}^{\mathrm{val}}`$ is the
validation accuracy of $`\mathcal{L}_{r}`$, and
$`\operatorname{Ref}(\Delta\mathcal{L}_{r})`$ indexes the corresponding
per-skill differences.

The new record $`\rho_{r}`$ is appended to the existing log:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{G}_{r}=\operatorname{Append}(\mathcal{G}_{r-1},\rho_{r}).
``` |  | (3) |

Here, $`\mathcal{G}_{r}`$ denotes the updated Evolution Log.

## Appendix D Trajectory-Budget Estimation and API Cost Calculations

### Trajectory-Budget Estimation

We measure the trajectory budget of VisualEvolve and RL training by the
number of task-solving trajectories.

For VisualEvolve, we count all Worker trajectories generated during
skill evolution, including both Execute and validation-time evaluations.
Before evolution, the Worker evaluates the initial skill library
$`\mathcal{L}_{0}`$ on the fixed 200-example validation set. Each of the
subsequent $`R=16`$ evolution rounds generates 32 trajectories during
Execute and 200 trajectories during Evaluate. The resulting trajectory
budget for one evolution run is

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle N_{\mathrm{VisualEvolve}}`$ | $`\displaystyle=|\mathcal{D}_{\mathrm{val}}|+\sum_{r=1}^{R}\left(|\mathcal{D}_{r}^{\mathrm{exe}}|+|\mathcal{D}_{\mathrm{val}}|\right)`$ |  | (4) |
|  |  | $`\displaystyle=200+(32+200)\times 16=3{,}912.`$ |  |  |

Of these, 512 trajectories come from Execute and 3,400 from validation.
This count excludes final benchmark evaluation and non-Worker model
calls for trajectory summarization and skill evolution.

For training-based methods, we estimate the number of RL rollout
trajectories from the original papers and, when available, official
training configurations. For step-based training, we estimate
$`N_{\mathrm{RL}}\approx SBG`$, where $`S`$ denotes the number of
rollout-collection steps, $`B`$ the number of input questions per step,
and $`G`$ the number of rollouts generated per question. For epoch-based
training, we use $`N_{\mathrm{RL}}\approx EDG`$, where $`E`$ is the
number of passes over an RL dataset containing $`D`$ questions.

### API Cost Calculations

We compute the API cost of VisualEvolve from the input and output tokens
consumed by all model calls during evolution and inference. For each
model $`m`$, let $`p^{m}_{\mathrm{input}}`$ and
$`p^{m}_{\mathrm{output}}`$ denote its official non-cache prices per one
million input and output tokens at the time of our experiments. The
total cost is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathrm{Cost}_{m}=\frac{\mathrm{InputTokens}_{m}}{10^{6}}p^{m}_{\mathrm{input}}+\frac{\mathrm{OutputTokens}_{m}}{10^{6}}p^{m}_{\mathrm{output}}.
``` |  | (5) |

The input/output prices per one million tokens are 0.8/4.8 RMB for
Qwen3.5-Plus, 2.0/12.0 RMB for Qwen3.6-Plus, 4.0/21.0 RMB for Kimi-K2.5,
and 3.2/16.0 RMB for Doubao-Seed-2.0-Pro. We do not apply cache-hit
discounts. All RMB costs are converted to USD using a fixed exchange
rate of 6.82 RMB per USD.

### Evolve Meta-Skill

Listing [G.2](#A7.SS2 "Evolve Meta-Skill ‣ Appendix G Meta-Skills ‣ VisualEvolve: A Skill Self-Evolution Framework for Visual Reasoning")

Listing 7: Meta-Skill for the Evolve stage.

--- name: evolve description: \>- USE WHEN: the evolve stage of an
evolution round, after execute stage. NOT FOR: execute or evaluate
stages. --- \## Evolve Improve Worker performance on the Validation set
by improving Worker skills in \`workplace/skills/\`, focusing on
accuracy. \### Skill Structure  - \*\*YAML frontmatter\*\*:  - \`name\`:
skill identifier. Use lowercase letters, digits, and hyphens, and keep
it identical to the skill directory name.  - \`description\`: load
trigger. The Worker sees only \`name\` and \`description\` before
deciding whether to load a skill, so this field must state what the
skill does and when to use it.  - Use valid YAML. Prefer block scalars
for descriptions: \`\`\`yaml --- name: your-skill-name description: \>-
State what the skill does and when the Worker should load it. --- \`\`\`
If a \`description:\` value is written on the same line, any unquoted
colon inside that value can make the YAML invalid. Use \`description:
\>-\` or quote the whole value instead.  - \*\*Body\*\*: detailed
guidance visible only after the skill is loaded.  - \*\*Optional
scripts\*\*: helper code or utilities used by the skill. \### Inputs
\#### Skills to Evolve  - \`workplace/skills/{name}/SKILL.md\` --
Current skill definition.  - \`workplace/skills/{name}/scripts/\` --
Current skill scripts (if applicable). \#### Current-Round Memories  -
\`workplace/memories/results_index.json\` -- Ordered sample list
(incorrect samples first). Each sample’s \`memory_dir\` field is the
path to its \`summary.md\`.  -
\`workplace/memories/{YYYYMMDD}-{sample_id}/summary.md\` -- Condensed
extraction from \`trajectory.json\` with line citations.  -
\`workplace/memories/{YYYYMMDD}-{sample_id}/trajectory.json\` -- Full
execution trace. \#### Skill-Performance Report  -
\`workplace/memories/evaluation_metrics_report.md\` -- Implementation of
the Skill-Performance Report, used to identify skills associated with
performance changes. \#### Evolution Log  -
\`workplace/evolution_playbook.md\` -- Implementation of the Evolution
Log, which records validation accuracy across rounds and indexes the
corresponding per-skill diff files.  -
\`workplace/history/round-N/skill_diffs/{skill}.diff\` -- Per-skill diff
between the consecutive evaluated snapshots from round \`N-1\` to round
\`N\`. \### Workflow \#### 1. Analyze Skill-Performance Report Read
\`workplace/memories/evaluation_metrics_report.md\`. Use it to identify
skills associated with notable performance changes. \#### 2. Analyze
Evolution Log Read \`workplace/evolution_playbook.md\` to understand
validation-accuracy trends and prior skill changes across rounds.  -
Note which update directions were associated with improvements.  -
Analyze prior round diffs and validation accuracy to avoid repeating
ineffective changes. \#### 3. Analyze Trajectory Summaries Read
\`workplace/memories/results_index.json\` to see the sample list.
Prioritize incorrect samples because they expose skill gaps, but also
review correct samples to understand what already works. Analysis flow:
 1. Read the summary file referenced by \`memory_dir\` first. It gives a
concise view of the run and includes line-range grounding references. 2.
To see the full trajectory details behind the summary, use the line
reference in the summary file to read the corresponding range from
trajectory.json. Example:
\`read_file("workplace/memories/{YYYYMMDD}-{sample_id}/trajectory.json",
offset=41, limit=4)\` for \`\[\[trajectory.json\|L42-L45\]\]\`. If the
cited span is too short, expand to nearby lines or continue reading more
of \`trajectory.json\` for context. For image evidence:  - In step 1,
the original image may appear as \`{"type": "image_path", "path":
"/artifacts/original.jpg"}\`.  - For rendered images, look for the
\`result\` field, e.g., \`\[{"type": "image_path", "path":
"artifacts/read_crop_top_right.jpg"}\]\`.  - You should use
\`read_file\` to inspect these images. \#### 4. Map Failures to Skill
Improvements Map identified issues to targeted changes in
\`workplace/skills/\` (modify, add, delete, split, or merge). Examples:
 - \*\*Load trigger mismatch\*\* -\> refine the YAML frontmatter
\`description\` so it clearly states what the skill does and when the
Worker should load it.  - \*\*Ambiguity\*\* -\> rewrite for clarity and
precision  - \*\*Capability gap\*\* -\> add new skills (with \`mkdir
-p\`) or supporting logic  - \*\*Redundancy / conflict / bloat\*\* -\>
delete overlap, resolve contradictions, tighten verbose skills Skip
low-frequency or uncertain issues to avoid overfitting. \### Evolution
Heuristics  - \*\*Prioritize generalizable patterns:\*\* Because
validation samples differ from the training set, avoid overfitting and
be cautious with blanket rules like "always" as they rarely generalize.
 - \*\*Evidence-driven iteration:\*\* Follow \`Evidence -\> Pattern -\>
Principle -\> Change\`.  - \*\*Balance skill length:\*\* Excessive
length dilutes signal and increases confusion. Overly terse guidance may
miss important nuances. Balance requires cross-round analysis.  -
\*\*Avoid overloading a single skill:\*\* An overloaded skill blurs
trigger boundaries and leads to irrelevant or conflicting guidance.
Instead, add dedicated skills for each question type or scenario, with
clear trigger conditions. \### Outputs  - Updated files in
\`workplace/skills/\`:  - \`SKILL.md\`  - related scripts, if applicable
\### Constraints  - Changes are allowed only in \`workplace/skills/\`.
 - Use:  - \`edit_file\` for targeted edits.  - \`write_file\` for full
rewrites.
````
