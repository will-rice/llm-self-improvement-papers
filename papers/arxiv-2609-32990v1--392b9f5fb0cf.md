###### Abstract

Long horizon agent self-evolution without model weight updates is
essential for enabling deployed agents to accumulate reusable skills and
improve over time. Prior self-evolution work has focused primarily on
short-horizon tasks, while repository-level software engineering remains
unexplored despite being an ideal testbed for long-horizon adaptation.
In this setting, agents are required to solve streams of sequential
tasks, navigate complex dependencies with evolving repositories and
persistently store and reuse experience. Text-based skill optimization
offers an efficient, non-parametric approach for such adaptation.
However, existing methods often suffer from unstable updates,
performance drawdown, and agent collapse over extended deployments. In
this paper, we formalize the concept of in-context self-evolution and
introduce VALVE, a validated-gated framework for long-horizon skill
optimization. We establish finite convergence, provide theoretical
guarantees for future-task gain and drawdown, and derive the validation
and evaluation holdout sizes required for a prescribed tolerance, with
leading-order scaling $`N\gtrsim s^{2}L/\gamma^{2}`$.

Empirically, our pipeline, VALVE achieves stable self-improvement over
evolution horizon spanning more than 1,000 SWE tasks, with average final
and peak gains of $`14.9`$ and $`16.5`$ points across three frontier
models (GPT-5.5, Claude-4.6 and MiniMax-M2.7). The validation gate
reduces average drawdown by 75% and produces an $`\mathbf{11\times}`$
more compact skill bank than ungated evolution. We further present
extensive ablations identifying the design choices most critical to
long-horizon skill evolution.

## 1  Introduction

Long-horizon in-context self-evolution requires an agent to continually
learning throughout deployment while its model weights remain frozen.
Repository-level software engineering is an ideal testbed: a code agent
must process approximately sequential task arrivals (e.g., up to
$`1{,}000`$ requests), navigate complex codebases and dependencies, and
carry experience forward across diverse issues. After solving a task, it
may extract reusable principles and procedures into a persistent skill
bank and recall relevant items for future tasks. This form of test-time
adaptation is attractive because it requires neither model retraining
nor changes to the solver harness. It connects prompt optimization
([Zhou et al., 2023](#bib.bib41); [Pryzant et al., 2023](#bib.bib18);
[Yang et al., 2024a](#bib.bib31); [Yuksekgonul et al.,
2024](#bib.bib37); [Agrawal et al., 2026](#bib.bib1)), context
engineering ([Zhang et al., 2026](#bib.bib39); [Ye et al.,
2026](#bib.bib35)), skill optimization ([Yang et al., 2026](#bib.bib34);
[Shen et al., 2026](#bib.bib20)), and agent self-improvement ([Zhang
et al., 2025](#bib.bib38); [Wang et al., 2025a](#bib.bib26)), all of
which adapt external text through execution feedback. However, most
existing methods are evaluated in bounded optimization settings rather
than over extended task streams. It remains unclear whether repeated
textual updates continue to help when the same persistent memory must
support hundreds of subsequent decisions ([Shridhar et al.,
2021](#bib.bib22); [Dunn et al., 2017](#bib.bib7); [Zhang et al.,
2026](#bib.bib39); [Ye et al., 2026](#bib.bib35)).

Motivated by recent methods ([Yang et al., 2026](#bib.bib34); [Shen
et al., 2026](#bib.bib20)), we study long-horizon self-evolution through
a minimal _Extract-Validate-Retrieve_ formulation. Specifically,
_Extract_ proposes text updates based on completed task trajectories;
_Validate_ decides which proposals are retrained in the memory bank
using held-out tasks; and _Retrieve_ selects the relevant information
from memory for future rollouts. This formulation exposes the central
long-horizon risk. Without selective retention, individually plausible
updates can accumulate, consume context and misguide future
task-sovling. As shown in
[1(b)](#S0.F1.sf2 "1(b) ‣ Figure 1 ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
an ungated agent may improve early yet lose much of its gain as its bank
grows, sometimes finishing below its unevolved counterpart.

This formulation leads directly to a text-space optimization problem.
With the LLM policy and solver harness frozen, the objective is to find
a persisent memory bank that maximizes expected solve probability on the
repository-level task distribution. Moreover, we further derive
theoretical analyses for the corresponding optimization. First, the
positive-margin gate limits the number of accepted bank changes. Under
i.i.d. sampling and stated variance bounds, a disjoint evaluation set
provides high-probability certificates for final population gain and
peak-to-final drawdown. Because the validation set is reused and later
proposals may adapt to earlier verdicts, we additionally derive a
uniform population-loss bound for every accepted update. Second, we
invert the same deviation bounds to determine the required holdout
sizes. For a prescribed tolerance, the valdiation-panel size controls
the certificated population loss of accepted updates.

We instantiate this formation in VALVE (VALidation-gated eVolution for
agEnts) for skill optimization. On each task, the solver LLM samples a
group of attempts. When their outcomes are mixed, the same LLM then
contrasts successful and failed trajectories to propose a set of skills.
The corresponding skill set is only accepted to the memory bank if its
paired rollout on a fixed validation achieves desired improvement. An
embedding-based retriever is used to independently ranks validated
skills for future task solving. Thus, all tasks arrivals belong to the
delopyment horizon, but only validation-approved skills are recorded in
the persistent memory. To validate the effectiveness of our proposed
method and theory, we carry out experiments on four SWE-smith
repositories using three frontier LLMs. Compared with baselines with and
without validation, VALVE achieves the best final gain with minimal
drawdown after $`1000`$ tasks arrivals per repository.

Our contributions are:

- •
  Long-horizon skill optimization for repo-level software engineering.
  We introduce a pipeline that combines mixed-outcome contrastive
  extraction, atomic validation of joint proposals with paired
  executable rollouts, and selective retrieval of rich-text principles
  and skills. Over streams of approximately $`1{,}000`$ task arrivals
  per repository, VALVE achieves both best average final gain and peak
  gain across three frontier models and four repositories.
- •
  Theory for validation-gated evolution. We establish finite
  convergence, provide guarantees on future-task gain and long-horizon
  drawdown, and derive validation and evaluation set size bounds for
  target performance tolerances.
- •
  Evidence for selective retention. Validation reduces average drawdown
  from $`6.1`$ to $`1.5`$ points while producing an $`11\times`$ smaller
  memory bank. Component ablations and item-level analysis show how
  extraction, bank structure, and skill representation affect retained
  improvement.

## 2  Related Work

#### Context, experience, and skill optimization.

A broad line of work studies how agents can improve by optimizing or
accumulating external textual state while keeping model parameters
fixed. Prompt-optimization methods such as APE, ProTeGi, OPRO,
EvoPrompt, TextGrad, and GEPA iteratively propose and evaluate textual
updates ([Zhou et al., 2023](#bib.bib41); [Pryzant et al.,
2023](#bib.bib18); [Yang et al., 2024a](#bib.bib31); [Guo et al.,
2024](#bib.bib9); [Yuksekgonul et al., 2024](#bib.bib37); [Agrawal
et al., 2026](#bib.bib1)). Context- and experience-based methods extend
this idea beyond a single prompt: ACE and MCE evolve richer context
artifacts ([Zhang et al., 2026](#bib.bib39); [Ye et al.,
2026](#bib.bib35)), while Reflexion, ExpeL, AWM, ReasoningBank, and
Voyager distill past trajectories into reusable feedback, strategies,
workflows, or executable knowledge ([Shinn et al., 2023](#bib.bib21);
[Zhao et al., 2024](#bib.bib40); [Wang et al., 2025b](#bib.bib27);
[Ouyang et al., 2025](#bib.bib17); [Wang et al., 2023](#bib.bib25)).
Recent work further formalizes and constructs agent skills from
trajectory evidence ([Jiang et al., 2026](#bib.bib11); [Li et al.,
2026](#bib.bib12); [Ni et al., 2026](#bib.bib15); [Liu et al.,
2026](#bib.bib13)). Most closely related, SkillOpt treats skill text as
trainable external state and accepts edits using held-out performance
([Yang et al., 2026](#bib.bib34)), while SkillOpt-Lite introduces an
independent validation gate for skill updates ([Shen et al.,
2026](#bib.bib20)). We study the same external-state optimization
paradigm but focus on a retrieved bank of individual skills under
repeated long-horizon updates, including which updates to retain and
whether evolution remains stable over time.

#### Self-evolving code agents.

A separate line of work studies self-improvement specifically in
software engineering. SWE-Exp learns experience banks from repair
trajectories ([Chen et al., 2025](#bib.bib6)), and Live-SWE-agent adapts
its scaffold online ([Xia et al., 2025](#bib.bib29)). SICA, the Darwin
Gödel Machine, the Huxley–Gödel Machine, and ARTEMIS optimize agent
implementations, harnesses, or configurations through execution feedback
([Robeyns et al., 2025](#bib.bib19); [Zhang et al., 2025](#bib.bib38);
[Wang et al., 2025a](#bib.bib26); [Brookes et al., 2025](#bib.bib4)),
while Self-play SWE-RL updates model parameters through training ([Wei
et al., 2026](#bib.bib28)). In contrast, VALVE keeps both the LLM and
solver harness fixed and isolates skill-bank evolution, allowing us to
study validation, regression, and convergence over long streams of
project-level software-engineering tasks.

## 3  VALVE: Validation-Gated Evolution for Agents

We first formulate long-horizon in-context self-evolution as
validation-gated text-space optimization. Based on that, we then provide
theoretical guarantees for performance of future tasks, including final
gain and drawdown
(Sec. [3.2](#S3.SS2 "3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")).
We further derive the holdout validation size required for a target
drawdown tolerance
(Sec. [3.3](#S3.SS3 "3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")).
Full proofs are in
Appendix [A](#A1 "Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

### 3.1  Problem setup and VALVE framework

Problem setup. We consider an agent that sequentially encounters tasks
$`x_{1},x_{2},\ldots`$ from a distribution $`\mathcal{D}`$ while its
model weights and solver harness remain fixed. Given a task $`x`$ and
textual context $`c`$, the frozen policy $`\pi`$ produces a trajectory
$`\tau\sim\pi(\cdot\mid x,c)`$ with executable success
$`s(x,\tau)\in\{0,1\}`$. Its solve probability is
$`q(x,c):=\mathbb{E}_{\tau\sim\pi(\cdot\mid x,c)}[s(x,\tau)]`$. The
evolving state is a persistent memory bank $`\mathcal{B}_{t}`$ of
textual artifacts accumulated from previous tasks. Because the full bank
may consume the solver’s context and even misguide its task solving, a
fixed retriever $`R`$ maps each task and bank into a compact context.
Thus, its population performance is
$`F_{\mathcal{D}}(\mathcal{B}):=\mathbb{E}_{x\sim\mathcal{D}}[q(x,R(x,\mathcal{B}))]`$.

#### A minimal framework for stable evolution.

VALVE centers evolution around three operators: _Extract_, _Validate_,
and _Retrieve_. Extract proposes updates from completed experience,
Validate decides which updates persist, and Retrieve maps the persistent
bank to a compact task-relevent solver context. For simplicity, we only
consider optimization on Extract and Validate while Retrieve remains
fixed. This minimal interface allows different extraction, validation,
memory and retrieval mechanisms to instantiate the same framework.
[Figure 2](#S3.F2 "Figure 2 ‣ A minimal framework for stable evolution. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
shows the specific instance for skill optimization.

Figure 2: Overview of VALVE.

Retrieve. As Retrieve is fixed in our evolution, we first briefly
discuss it. Before each task, Retrieve selects a compact subset of
relevant artifacts from the current bank. We independently rank
principles and skills against the issue and inject the highest-scoring
rich-markdown without re-summarization
(Appendix [B.5](#A2.SS5 "B.5 Retrieve: task-conditioned skill composition ‣ Appendix B Implementation details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")).

#### Extract.

On task $`x_{t}`$, the solver samples three attempts under the same
task, repository and retrieved context. Extract is invoked only when
executable outcomes are mixed, enabling a within-task contrast between
successful and failed trajectories. A reflection call proposes at most
three _principles_, which encode transferable reasoning guidance, and
three _skills_, which encode narrow executable procedures. Exact and
near-duplicate items are suppressed before validation
(Appendices [B.2](#A2.SS2 "B.2 Rollout collection and evolution trigger ‣ Appendix B Implementation details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")–[B.4](#A2.SS4 "B.4 Persistent skill state ‣ Appendix B Implementation details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")).

Let $`m`$ denote a proposed bank update. Its population gain is
$`g_{\mathcal{D}}(m\mid\mathcal{B})=F_{\mathcal{D}}(m(\mathcal{B}))-F_{\mathcal{D}}(\mathcal{B})`$.

#### Validate.

A lesson that helps its source task may hurt others. Validate therefore
compares the current and candidate banks on a held-out panel
$`V=\{x_{1},\ldots,x_{n}\}`$ using task-paired executable rollouts. Let
$`F_{V}`$ and $`g_{V}`$ denote the corresponding panel quantities. A
candidate is committed only when

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\mathcal{B}_{t+1}=m_{t}(\mathcal{B}_{t})\ \ \text{if}\ \ \widehat{g}_{V}(m_{t}\mid\mathcal{B}_{t})\geq\rho,\qquad\mathcal{B}_{t+1}=\mathcal{B}_{t}\ \ \text{otherwise.}
``` |  | (1) |

In our implementation, each proposal jointly updates principles and
skills, so the gate evaluates the complete state transition rather than
individual items
(Appendix [B.6](#A2.SS6 "B.6 Validate: paired acceptance on executable outcomes ‣ Appendix B Implementation details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")).
For banks $`\mathcal{B},\mathcal{B}^{\prime}`$ and task $`x`$, we run
$`r`$ paired rollouts and record
$`\widehat{u}_{\mathcal{B}^{\prime},\mathcal{B}}(x):=\frac{1}{r}\sum_{j\leq r}s(x,\tau^{\prime}_{j})-\frac{1}{r}\sum_{j\leq r}s(x,\tau_{j})\in[-1,1]`$.
Finite-rollout noise is absorbed into its variance, bounded by
$`\sigma^{2}`$ on $`V`$ and by $`\sigma_{\mathcal{H}}^{2}`$ on a
disjoint evaluation set $`\mathcal{H}`$.

For an average of $`N`$ i.i.d. summands with variance at most $`s^{2}`$
and upper deviation $`Y-\mathbb{E}Y\leq M`$, the one-sided Bennett
radius
$`b_{M}(N,L,s^{2}):=\frac{s^{2}}{M}\,\mathrm{h}^{-1}\!\Big(\frac{M^{2}L}{Ns^{2}}\Big)\leq\sqrt{\frac{2s^{2}L}{N}}+\frac{2ML}{3N},\qquad\mathrm{h}(v):=(1+v)\ln(1+v)-v`$
is exceeded with probability at most $`e^{-L}`$.

###### Assumption 1 (Sample independence).

For each repository, $`\mathcal{D}`$ denotes its task distribution. The
validation panel $`V`$, held-out evaluation set $`\mathcal{H}`$, and
adaptation stream are disjoint and i.i.d. samples from $`\mathcal{D}`$,
and $`\mathcal{H}`$ is never used by extraction or validation.
Candidates may depend arbitrarily on previous verdicts from $`V`$, and
$`V`$ may be reused throughout evolution.

### 3.2  Stable evolution and certified performance

Here, we show that positive-margin acceptance limits the persistent
state from changing indefinitely.

###### Theorem 1 (Fixed-panel convergence).

Suppose the panel score of the current bank is carried forward rather
than re-estimated after a rejection, and let $`\widehat{F}_{t}`$ denote
the panel score of $`\mathcal{B}_{t}`$ used by
[Equation 1](#S3.E1 "1 ‣ Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").
Then $`\widehat{F}_{t}`$ is non-decreasing,
$`\widehat{F}_{T}=\max_{t}\widehat{F}_{t}`$, and the number $`K`$ of
accepted moves satisfies
$`K\leq\left\lfloor\frac{1-\widehat{F}_{0}}{\rho}\right\rfloor\leq\left\lfloor\frac{1}{\rho}\right\rfloor.`$
The run therefore visits at most $`K+1`$ distinct banks.

The result follows directly from positive-margin ascent on a score
bounded in $`[0,1]`$ and holds for arbitrary history-dependent proposals
and reuse of $`V`$. If improvement is localized to tasks whose baseline
outcomes are unstable, with fraction $`h`$, the bound tightens to
$`K\leq\lfloor h/\rho\rfloor`$
(Appendix [A.4](#A1.SS4 "A.4 Baseline-concentrated headroom ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")).

As validation convergence does not imply population improvement, we
further evaluate frozen checkpoints on a disjoint set $`\mathcal{H}`$.
Let $`\mathcal{B}^{(0)},\ldots,\mathcal{B}^{(J)}`$ be the checkpoints,
$`\mathcal{B}^{(J)}`$ the final bank, and $`A`$ the number of distinct
banks. Denote $`\widehat{\Delta}`$ for the measured final gain over
$`\mathcal{B}^{(0)}`$, and let
$`\mathrm{DD}:=\max_{j}\big[F_{\mathcal{D}}(\mathcal{B}^{(j)})-F_{\mathcal{D}}(\mathcal{B}^{(J)})\big],\widehat{\mathrm{DD}}:=\max_{j}\widehat{D}_{j}.`$

###### Theorem 2 (Certified gain and drawdown).

Under
Assumption [1](#Thmassumption1 "Assumption 1 (Sample independence). ‣ Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
with probability at least $`1-\delta`$,

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle F_{\mathcal{D}}(\mathcal{B}^{(J)})-F_{\mathcal{D}}(\mathcal{B}^{(0)})`$ | $`\displaystyle\geq\widehat{\Delta}-b_{1}\!\left(n_{\mathcal{H}},\ln\tfrac{1}{\delta},\sigma_{\mathcal{H}}^{2}\right),`$ |  | (2) |
|  | $`\displaystyle\mathrm{DD}`$ | $`\displaystyle\leq\widehat{\mathrm{DD}}+b_{1}\!\left(n_{\mathcal{H}},\ln\tfrac{A}{\delta},\sigma_{\mathcal{H}}^{2}\right),`$ |  | (3) |

where
[Equation 2](#S3.E2 "2 ‣ Theorem 2 (Certified gain and drawdown). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
additionally requires its right-hand side to be nonnegative.

Thus a measured held-out gain certifies expected improvement on future
evaluation tasks drawn from $`\mathcal{D}`$, while
equation [3](#S3.E3 "In Theorem 2 (Certified gain and drawdown). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")

gives $`A\leq K+1`$, the drawdown budget depends on accepted changes
rather than the total task horizon. A paired version also certifies

### 3.3  Validation reliability and holdout sizing

Because earlier verdicts from the same validation panel can affect later
updates, we thus further bound the population loss of adaptive
acceptance and then derive the required validation and evaluation set
sizes.

#### Validation reliability.

For an accepted move, define its population loss as
$`\ell_{\mathcal{D}}(m\mid\mathcal{B}):=[-g_{\mathcal{D}}(m\mid\mathcal{B})]_{+}`$.
Because only accepted moves change the bank, only finite states are
reachable under adaptive panel reuse. Conditioning on randomness other
than $`V`$, the number of bank-move pairs that may produce the $`k`$-th
acceptance is at most $`N_{k}:=\sum_{t=1}^{T}\binom{t-1}{k-1},`$ where
$`T`$ is the gate-query horizon fixed in advance.

###### Theorem 3 (Adaptive-validation population-loss guarantee).

Under
Assumption [1](#Thmassumption1 "Assumption 1 (Sample independence). ‣ Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
let $`\delta_{k}:=\delta/(k(k+1))`$ and
$`L_{k}:=\ln(N_{k}/\delta_{k})`$. Then with probability at least
$`1-\delta`$, the $`k`$-th accepted move satisfies, simultaneously for
every $`k`$ and every $`\gamma>0`$ for which the right-hand side is at
least $`-\gamma`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
g_{\mathcal{D}}(m\mid\mathcal{B})\geq\widehat{g}_{V}(m\mid\mathcal{B})-b_{1+\gamma}(n,L_{k},\sigma^{2})\geq\rho-b_{1+\gamma}(n,L_{k},\sigma^{2}).
``` |  | (4) |

The guarantee is anchored at the measured validation gain and remains
valid despite adaptive reuse of the same panel $`V`$.

#### Holdout sizing.

All precedding certificates have the measured quantity where the radius
decreases with the holdout size. Inverting this radius therefore gives
the number of held-out tasks required for a target tolerance.

###### Corollary 1 (Holdout sizing).

Fix $`\gamma>0`$ and write $`a:=2s^{2}L`$ and $`c:=2ML/3`$. Then
$`b_{M}(N,L,s^{2})\leq\gamma`$ whenever

|  |  |  |  |
|----|----|----|----|
|  |
``` math
N\geq\left(\frac{2c}{\sqrt{a+4c\gamma}-\sqrt{a}}\right)^{\!2}=\frac{a}{\gamma^{2}}\big(1+O(\gamma)\big).
``` |  | (5) |

The corollary applies to the two set sizing separately. Setting
$`L=\ln(A/\delta)`$ and $`M=1`$ sizes the evaluation set for a
prescribed drawdown slack $`\gamma`$. For the validation panel, using
$`L=L_{K}`$, $`M=1+\gamma`$, and replacing $`\gamma`$ by
$`\widehat{g}_{V}+\gamma`$ ensures that every accepted update in a run
with at most $`K`$ accepts has population loss at most $`\gamma`$.

The bank count satisfies $`A\leq\lfloor 1/\rho\rfloor+1`$ by
Theorem [1](#Thmtheorem1 "Theorem 1 (Fixed-panel convergence). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").
Baseline rollouts provide a variance proxy. If $`p(x)`$ is the baseline
solve probability,
Assumption [2](#Thmassumption2 "Assumption 2 (Baseline-concentrated gain). ‣ A.4 Baseline-concentrated headroom ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
gives
$`\sigma^{2}\leq(1+\tfrac{2}{r})\mathbb{E}_{x}[p(x)(1-p(x))]+2\varepsilon_{\mathrm{var}}`$,
whose leading term is estimated by
$`\mathrm{vmass}:=\frac{1}{N}\sum_{i=1}^{N}\widehat{p}_{i}(1-\widehat{p}_{i})\frac{r}{r-1}.`$
One can therefore estimate the variance from baseline rollouts, choose
$`\rho`$, $`\gamma`$, and a conservative residual allowance
$`\varepsilon_{\mathrm{var}}`$, and obtain both holdout sizes from
[Equation 5](#S3.E5 "5 ‣ Corollary 1 (Holdout sizing). ‣ Holdout sizing. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

## 4  Experiments

### 4.1  Experimental setup

We implement VALVE using mini-SWE-agent ([SWE-agent Team,
2026](#bib.bib24); [Yang et al., 2024b](#bib.bib32)), where the solver,
extractor, and consumer all are based on the same backbone, using four
SWE-smith repositories ([Yang et al., 2025](#bib.bib33)): pygments,
sqlfluff, pydicom, and deepdiff. Each repository is split into disjoint
partitions
(Appendix [B.1](#A2.SS1 "B.1 Data construction and reference configuration ‣ Appendix B Implementation details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")):
a $`100`$-task evaluation set, a fixed $`50`$-task validation panel
reused for every acceptance decision, and an evolution stream of
approximately $`1{,}000`$ tasks with at most $`100`$ mixed-outcome
evolution steps. All conditions use three rollouts per task,
rich-markdown banks, and the acceptance threshold $`\rho=0.02`$.

### 4.2  Main results

Table [1](#S4.T1 "Table 1 ‣ 4.1 Experimental setup ‣ 4 Experiments ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
shows that VALVE improves final performance across all three backbones.
Across the twelve model-repository runs, the average resolved rate
increases from $`63.9\%`$ to $`78.9\%`$, a gain of $`14.9`$ points, and
every VALVE run outperforms both its unevolved base model and its
counterpart without validation. The model-average gains are
$`6.3,19.0,19.6`$ for MiniMax-M2.7, GPT-5.5, and Claude-4.6,
respectively. VALVE also outperforms SkillOpt in final model average for
all three backbones, although SkillOpt remains best on MiniMax-M2.7
deepdiff and Claude-4.6 pydicom. These results are consistent with our
theoretical analysis and support validaton-gated updates as a practical
mechanism for reliable long-horizon agent evolution.

#### Validation turns transient gains into retained gains.

Table [2](#S4.T2 "Table 2 ‣ 4.1 Experimental setup ‣ 4 Experiments ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
separates peak improvement from the gain retained at the end of
evolution. Overall, SkillOpt reaches a peak gain of $`10.8`$ points and
retains $`7.1`$, with $`3.6`$ points of drawdown. VALVE w/o val reaches
$`7.0`$ points at peak but retains only $`0.9`$, with $`6.1`$ points of
drawdown. VALVE instead reaches $`16.5`$ points at peak and retains
$`14.9`$, reducing average drawdown to $`1.5`$ points.

The contrast is strongest for Claude-4.6: without validation, the
average run peaks at $`+5.6`$ points but ends at $`-6.5`$, whereas VALVE
reaches $`+21.1`$ and retains $`+19.6`$. Three of the four Claude-4.6
runs without validation and the MiniMax-M2.7 pydicom run finish below
baseline.

for fixed variance and log-budget, a larger panel shrinks the deviation

## 6  Conclusion

Long-term self-evolution asks how an agent with a frozen LLM core can
continually improve at test time, and its central obstacle is unstable
updates that cause drawdown and eventual collapse over long horizons. We
distilled the common design of existing in-context evolution methods
into an Extract–Validate–Retrieve pipeline and formulated it as
text-space optimization of a retrieved skill bank. On this formulation,
positive-margin acceptance converges after finitely many bank changes, a
disjoint evaluation set certifies final gain and long-horizon drawdown,
and a uniform pathwise bound controls the population loss of updates
chosen adaptively on a reused validation panel; inverting the same
deviation radius gives sizing rules for both holdouts. Empirically,
VALVE sustains evolution over streams of approximately $`1{,}000`$
software engineering tasks per repository, achieving average final and
peak gains of $`14.9`$ and $`16.5`$ points across three backbones and
four repositories, compared with $`0.9`$ and $`7.0`$ points without a
gate, while cutting average drawdown by $`4.0\times`$ with an
$`11\times`$ more compact skill bank. As agents move toward lifelong
deployment, this work offers practical guidance on validation gating and
a step toward stable, trustworthy continual self-evolution.

### A.1  Online dynamics of the context policy

The solve probability of a context policy $`\mu`$ marginalizes the
context:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbb{P}_{\mu}(\tau\in\mathcal{T}_{x}^{+}\mid x)=\sum_{c}\underbrace{q(x,c)}_{\text{quality}}\underbrace{\mu(c\mid x,\mathcal{E})}_{\text{production probability}}=\mathbb{E}_{c\sim\mu(\cdot\mid x,\mathcal{E})}[q(x,c)],
``` |  | (6) |

where $`\mathcal{T}_{x}^{+}:=\{\tau:s(x,\tau)=1\}`$. The two factors
expose the central design questions behind the population objective
$`F_{\mathcal{D}}`$ of
Sec. [3.1](#S3.SS1 "3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"):
which contexts have high quality, and how should the agent produce them?

Experience is endogenous: the policy shapes the rollouts that
subsequently change the policy. The agent acts causally. At step $`t`$,
it observes only the strictly past experience $`\mathcal{E}_{<t}`$,
draws $`c_{t}\sim\mu(\cdot\mid x_{t},\mathcal{E}_{<t})`$, produces
$`\tau_{t}\sim\pi(\cdot\mid x_{t},c_{t})`$, and observes
$`s_{t}:=s(x_{t},\tau_{t})`$. It then appends the complete interaction
record,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{E}_{<t+1}=\mathcal{E}_{<t}\mathbin{\|}(x_{t},c_{t},\tau_{t},s_{t}),
``` |  | (7) |

where $`\mathbin{\|}`$ denotes sequence concatenation. Thus, although
$`F_{\mathcal{D}}`$
(Sec. [3.1](#S3.SS1 "3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"))
is written as a population objective, its context policy and experience
distribution are coupled through the online rollout process. Over an
evolution horizon of length $`T`$, the corresponding cumulative
objective is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{J}_{T}(\mu):=\mathbb{E}\!\left[\sum_{t=1}^{T}s_{t}\right]=\mathbb{E}\!\left[\sum_{t=1}^{T}q(x_{t},c_{t})\right],
``` |  | (8) |

where the expectation includes task sampling, context selection, and
trajectory generation. A successful evolution rule must therefore
improve future contexts without using information from future
interactions.

### A.2  The deviation radius

###### Lemma 1 (One-sided Bennett radius).

Let $`Y_{1},\ldots,Y_{N}`$ be i.i.d. with mean $`\nu`$, variance at most
$`s^{2}`$, and $`Y_{i}-\nu\leq M`$ almost surely. Then

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbb{P}\left(\frac{1}{N}\sum_{i=1}^{N}Y_{i}-\nu>b_{M}(N,L,s^{2})\right)\;\leq\;e^{-L},
``` |  | (9) |

where $`b_{M}`$ is the one-sided Bennett radius of
Sec. [3.1](#S3.SS1 "3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),

|  |  |  |  |
|----|----|----|----|
|  |
``` math
b_{M}(N,L,s^{2}):=\frac{s^{2}}{M}\,\mathrm{h}^{-1}\!\Big(\frac{M^{2}L}{Ns^{2}}\Big)\leq\sqrt{\frac{2s^{2}L}{N}}+\frac{2ML}{3N},\qquad\mathrm{h}(v):=(1+v)\ln(1+v)-v.
``` |  | (10) |

###### Proof.

Bennett’s inequality for independent summands with the stated variance
and one-sided range gives, for every $`b>0`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbb{P}\left(\frac{1}{N}\sum_{i=1}^{N}Y_{i}-\nu>b\right)\;\leq\;\exp\left(-\frac{Ns^{2}}{M^{2}}\,\mathrm{h}\!\left(\frac{Mb}{s^{2}}\right)\right),\qquad\mathrm{h}(v)=(1+v)\ln(1+v)-v.
``` |  | (11) |

The function $`\mathrm{h}`$ is strictly increasing on $`[0,\infty)`$
with $`\mathrm{h}(0)=0`$, so it is invertible there. Setting the
exponent in
equation [11](#A1.E11 "In Proof. ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
equal to $`-L`$ and solving,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\frac{Ns^{2}}{M^{2}}\,\mathrm{h}\!\left(\frac{Mb}{s^{2}}\right)=L\quad\Longleftrightarrow\quad\frac{Mb}{s^{2}}=\mathrm{h}^{-1}\!\left(\frac{M^{2}L}{Ns^{2}}\right)\quad\Longleftrightarrow\quad b=\frac{s^{2}}{M}\,\mathrm{h}^{-1}\!\left(\frac{M^{2}L}{Ns^{2}}\right),
``` |  | (12) |

which is the first expression in
equation [10](#A1.E10 "In Lemma 1 (One-sided Bennett radius). ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

For the displayed relaxation, use
$`\mathrm{h}(v)\geq v^{2}/(2+\tfrac{2}{3}v)`$, valid for $`v\geq 0`$.
Substituting $`v=Mb/s^{2}`$ turns
equation [11](#A1.E11 "In Proof. ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
into

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\exp\left(-\frac{Ns^{2}}{M^{2}}\cdot\frac{M^{2}b^{2}/s^{4}}{2+\tfrac{2Mb}{3s^{2}}}\right)=\exp\left(-\frac{Nb^{2}}{2s^{2}+\tfrac{2M}{3}b}\right).
``` |  | (13) |

Setting this to $`e^{-L}`$ gives
$`Nb^{2}=L\big(2s^{2}+\tfrac{2M}{3}b\big)`$, that is
$`b^{2}\leq a^{\prime}+c^{\prime}b`$ with $`a^{\prime}=2s^{2}L/N`$ and
$`c^{\prime}=2ML/(3N)`$. Since $`b^{2}\leq a^{\prime}+c^{\prime}b`$
implies $`b\leq\sqrt{a^{\prime}}+c^{\prime}`$, we obtain
$`b\leq\sqrt{2s^{2}L/N}+2ML/(3N)`$. ∎

Every summand below lies in $`[-1,1]`$, for which $`M=2`$ is always
admissible. The following remark identifies the smaller admissible range
in each of our statements.

###### Remark 1 (Effective range).

Each certificate has the form: establish $`\nu\geq c`$ for a population
contrast $`\nu`$, by showing that the empirical mean does not exceed
$`\nu`$ by more than $`b`$, with $`c`$ equal to the empirical value
minus $`b`$. On the failure event $`\nu<c`$, the deviation required is

|     |                                                |     |      |
|-----|------------------------------------------------|-----|------|
|     |
       ``` math
       \frac{1}{N}\sum_{i}Y_{i}-\nu\;\geq\;b+(c-\nu),
       ```                                             |     | (14) |

which grows as $`\nu`$ decreases, while the admissible range $`M=1-\nu`$
also grows. Substituting both into the exponent of
equation [11](#A1.E11 "In Proof. ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
gives

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\frac{Ns^{2}}{(1-\nu)^{2}}\,\mathrm{h}\!\left(\frac{(1-\nu)(b+c-\nu)}{s^{2}}\right).
``` |  | (15) |

For completeness, this exponent is nondecreasing in $`-\nu`$ whenever,
for every $`\nu\in[-1,c]`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\frac{(1-\nu)(b+c+1-2\nu)}{s^{2}}\ln(1+v_{\nu})\;\geq\;2\,\mathrm{h}(v_{\nu}),\qquad v_{\nu}:=\frac{(1-\nu)(b+c-\nu)}{s^{2}}.
``` |  | (16) |

This follows by differentiating the displayed exponent with respect to
$`1-\nu`$ and is directly checkable for any reported $`(N,s^{2},b,c)`$.
We verified
equation [16](#A1.E16 "In Remark 1 (Effective range). ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
over the full interval for the numerical configurations used in this
paper. Under this condition the binding case is $`\nu\to c`$ and the
effective range is $`M=1-c`$. Consequently: for the drawdown
equation [3](#S3.E3 "In Theorem 2 (Certified gain and drawdown). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
only checkpoints with a positive drop can attain the maximum, so $`c=0`$
and $`M=1`$; for the gain
equation [2](#S3.E2 "In Theorem 2 (Certified gain and drawdown). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
and the separation
equation [32](#A1.E32 "In Theorem 4 (Certified separation of retained performance). ‣ A.6 Certified separation between gated and ungated evolution ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
$`c\geq 0`$ whenever the certified floor is nonnegative, so $`M=1`$; and
for the reused panel
equation [4](#S3.E4 "In Theorem 3 (Adaptive-validation population-loss guarantee). ‣ Validation reliability. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
$`c=-\gamma`$ and $`M=1+\gamma`$. If
equation [16](#A1.E16 "In Remark 1 (Effective range). ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
is not verified, the same statements remain valid with the conservative
range $`M=2`$, because every summand lies in $`[-1,1]`$.

### A.3  Proof of fixed-panel convergence

###### Proof of Theorem [1](#Thmtheorem1 "Theorem 1 (Fixed-panel convergence). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

A rejected move leaves both the bank and its recorded panel score
unchanged, so $`\widehat{F}_{t+1}=\widehat{F}_{t}`$. An accepted move at
step $`t`$ replaces the current bank by $`m_{t}(\mathcal{B}_{t})`$ and,
because the accepted candidate’s score is carried forward, replaces
$`\widehat{F}_{t}`$ by the candidate’s score. Hence

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{F}_{t+1}-\widehat{F}_{t}=\widehat{g}_{V}(m_{t}\mid\mathcal{B}_{t})\;\geq\;\rho,
``` |  | (17) |

the inequality being the acceptance rule
equation [1](#S3.E1 "In Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").
In both cases $`\widehat{F}_{t+1}\geq\widehat{F}_{t}`$, so the sequence
is non-decreasing and $`\widehat{F}_{T}=\max_{t}\widehat{F}_{t}`$.

Let $`t_{1}<\cdots<t_{K}`$ be the accepted rounds. Summing
equation [17](#A1.E17 "In Proof of Theorem . ‣ A.3 Proof of fixed-panel convergence ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
over them and telescoping,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{F}_{t_{K}+1}-\widehat{F}_{0}=\sum_{j=1}^{K}\big(\widehat{F}_{t_{j}+1}-\widehat{F}_{t_{j}}\big)=\sum_{j=1}^{K}\widehat{g}_{V}(m_{t_{j}}\mid\mathcal{B}_{t_{j}})\;\geq\;K\rho.
``` |  | (18) |

Since $`\widehat{F}_{t}`$ is an average of quantities in $`[0,1]`$ it
satisfies $`\widehat{F}_{t}\in[0,1]`$, whence

|  |  |  |  |
|----|----|----|----|
|  |
``` math
K\rho\;\leq\;\widehat{F}_{t_{K}+1}-\widehat{F}_{0}\;\leq\;1-\widehat{F}_{0}\;\leq\;1,
``` |  | (19) |

and dividing by $`\rho`$ and taking integer parts gives
equation [1](#Thmtheorem1 "Theorem 1 (Fixed-panel convergence). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").
The bank changes only at accepted rounds, so the number of distinct
banks visited is at most $`K+1`$.

The argument is deterministic. It uses no property of $`V`$ beyond
$`F_{V}`$ being bounded, and in particular permits arbitrary reuse of
$`V`$ and history-dependent proposals. ∎

###### Remark 2.

If the current bank were re-scored with fresh rollouts at every
comparison instead of carried forward,
equation [17](#A1.E17 "In Proof of Theorem . ‣ A.3 Proof of fixed-panel convergence ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
would hold only up to the re-estimation drift. On the event that every
such drift is bounded by $`\eta<\rho/2`$, the same telescoping gives
$`K\leq\lfloor 1/(\rho-2\eta)\rfloor`$.

### A.4  Baseline-concentrated headroom

Let $`p(x)`$ denote the baseline solve probability, let
$`U:=\{x:p(x)\in(0,1)\}`$ be the baseline-unstable set, and let
$`h:=\mathbb{P}_{x\sim\mathcal{D}}(x\in U)`$. With only $`r`$ baseline
rollouts, define the observed unstable panel fraction
$`\widehat{h}:=n^{-1}\sum_{i=1}^{n}\mathbf{1}\{0<\widehat{p}_{i}<1\}`$.
This is generally downward biased for $`h`$: tasks with small but
nonzero $`p(x)`$ can produce only failures in all $`r`$ rollouts.

###### Assumption 2 (Baseline-concentrated gain).

There are residual allowances
$`\varepsilon_{\mathrm{loc}},\varepsilon_{\mathrm{var}}\geq 0`$ such
that every reachable bank satisfies

|  |  |  |  |
|----|----|----|----|
|  |
``` math
F_{V}(\mathcal{B})-F_{V}(\mathcal{B}_{0})\leq\widehat{h}+\varepsilon_{\mathrm{loc}},
``` |  | (20) |

and every reachable move satisfies

|  |  |  |  |  |
|----|----|----|----|----|
|  | $`\displaystyle\mathbb{E}_{x}[u_{m,\mathcal{B}}(x)^{2}]`$ | $`\displaystyle\leq\mathbb{E}_{x}[p(x)(1-p(x))]+\varepsilon_{\mathrm{var}},`$ |  | (21) |
|  | $`\displaystyle\mathbb{E}_{x}[\operatorname{Var}(\widehat{u}\mid x)]`$ | $`\displaystyle\leq\frac{2}{r}\mathbb{E}_{x}[p(x)(1-p(x))]+\varepsilon_{\mathrm{var}}.`$ |  | (22) |

Under
Assumption [2](#Thmassumption2 "Assumption 2 (Baseline-concentrated gain). ‣ A.4 Baseline-concentrated headroom ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
the number of accepted moves satisfies the localized bound

|  |  |  |  |
|----|----|----|----|
|  |
``` math
K\rho\;\leq\;\widehat{h}+\varepsilon_{\mathrm{loc}},\qquad\text{i.e.,}\qquad K\;\leq\;\left\lfloor\frac{\widehat{h}+\varepsilon_{\mathrm{loc}}}{\rho}\right\rfloor.
``` |  | (23) |

###### Proof of equation [23](#A1.E23 "In A.4 Baseline-concentrated headroom ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

Assumption [2](#Thmassumption2 "Assumption 2 (Baseline-concentrated gain). ‣ A.4 Baseline-concentrated headroom ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
directly bounds the realizable panel headroom. Using it in the
telescoping step of
Appendix [A.3](#A1.SS3 "A.3 Proof of fixed-panel convergence ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
gives $`K\rho\leq\widehat{h}+\varepsilon_{\mathrm{loc}}`$, which is
equation [23](#A1.E23 "In A.4 Baseline-concentrated headroom ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").
The idealized zero-residual result is recovered at
$`\varepsilon_{\mathrm{loc}}=0`$, but we do not impose that value on the
experiments. ∎

The variance part of the assumption and the law of total variance give

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\operatorname{Var}\big[\widehat{u}\big]=\operatorname{Var}_{x}\big[u\big]+\mathbb{E}_{x}\big[\operatorname{Var}(\widehat{u}\mid x)\big]\;\leq\;\Big(1+\frac{2}{r}\Big)\mathbb{E}_{x}\big[p(x)(1-p(x))\big]+2\varepsilon_{\mathrm{var}}.
``` |  | (24) |

For $`r`$ independent Bernoulli baseline rollouts on task $`i`$, the
plug-in estimator satisfies

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbb{E}\big[\widehat{p}_{i}(1-\widehat{p}_{i})\big]=\frac{r-1}{r}\,p_{i}(1-p_{i}),
``` |  | (25) |

so multiplying by $`r/(r-1)`$ removes the finite-$`r`$ downward bias,
and averaging over tasks gives
equation [3.3](#S3.SS3.SSS0.Px2 "Holdout sizing. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
as an unbiased estimate of $`\mathbb{E}_{x}[p(1-p)]`$. When $`r=3`$ each
empirically unstable task has $`\widehat{p}\in\{1/3,2/3\}`$ and
contributes $`1/3`$, so empirically $`\mathrm{vmass}=\widehat{h}/3`$.
This identity does not make $`\widehat{h}`$ an unbiased estimate of the
population mass $`h`$.

### A.6  Certified separation between gated and ungated evolution

Write $`\mathcal{B}^{\mathrm{val}}`$ and
$`\mathcal{B}^{\mathrm{noval}}`$ for the final banks produced on a given
repository with and without the gate.

###### Theorem 4 (Certified separation of retained performance).

Fix a repository with task distribution $`\mathcal{D}`$, evaluate both
runs on the same held-out set $`\mathcal{H}`$, and let
$`\sigma_{W}^{2}`$ bound the variance of the per-task cross-condition
contrast

|  |  |  |  |
|----|----|----|----|
|  |
``` math
W(x):=q\big(x,R(x,\mathcal{B}^{\mathrm{val}})\big)-q\big(x,R(x,\mathcal{B}^{\mathrm{noval}})\big).

Then with probability at least $`1-\delta`$,

|  |  |  |  |
|----|----|----|----|

``` |  | (32) |

###### Corollary 2 (Repository average).

If the statement is made for $`G`$ repositories with disjoint evaluation
sets of $`n_{\mathcal{H}}`$ tasks each, then with probability at least
$`1-\delta`$ the average of the $`G`$ repository-level differences
exceeds the average of the $`\widehat{W}_{r}`$ by at most
$`b_{1}\big(G\,n_{\mathcal{H}},\ln\tfrac{1}{\delta},\sigma_{W}^{2}\big)`$.

The contrast is paired: both runs are scored on the same tasks, so task
difficulty cancels within each task and one radius bounds the
difference.

###### Proof of Theorem [4](#Thmtheorem4 "Theorem 4 (Certified separation of retained performance). ‣ A.6 Certified separation between gated and ungated evolution ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

Assumption [1](#Thmassumption1 "Assumption 1 (Sample independence). ‣ Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

|----|----|----|----|

``` |  | (33) |

are i.i.d. in $`[-1,1]`$ with mean
$`F_{\mathcal{D}}(\mathcal{B}^{\mathrm{val}})-F_{\mathcal{D}}(\mathcal{B}^{\mathrm{noval}})`$

### A.7  Proof of the reused-panel population-loss guarantee

Condition on the randomness $`\xi`$ of the run other than the validation
panel: the adaptation task stream, solver sampling, extraction sampling
and retrieval tie-breaking. For an accept pattern $`S\subseteq[T]`$
define recursively

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{B}(S,1)=\mathcal{B}_{0},\qquad m(S,t)=\mathrm{Prop}\big(\xi,\mathcal{B}(S,t),t\big),\qquad\mathcal{B}(S,t+1)=\begin{cases}m(S,t)\big(\mathcal{B}(S,t)\big),&t\in S,\\
\mathcal{B}(S,t),&t\notin S.\end{cases}
``` |  | (35) |

###### Lemma 2 (Path compression).

For every $`S`$ and $`t`$: (i) $`\mathcal{B}(S,t)`$ depends on $`S`$
only through $`S\cap[t-1]`$; (ii) the pair $`(\mathcal{B}(S,t),m(S,t))`$
is $`\xi`$-measurable; (iii) the realized run is the path of
$`S^{\ast}=\{\text{accepted steps}\}`$; and (iv) for each $`k\geq 1`$
the family

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathcal{F}_{k}(\xi):=\Big\{\big(\mathcal{B}(S,t),m(S,t)\big):t\in[T_{\mathrm{gate}}],\;S\subseteq[T_{\mathrm{gate}}],\;t\in S,\;|S\cap[t-1]|=k-1\Big\}
``` |  | (36) |

of pairs that can occur at an accepted step preceded by exactly $`k-1`$
accepts satisfies $`|\mathcal{F}_{k}(\xi)|\leq N_{k}`$ with $`N_{k}`$ as
in
equation [3.3](#S3.SS3.SSS0.Px1 "Validation reliability. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

###### Proof.

(i) The recursion
equation [35](#A1.E35 "In A.7 Proof of the reused-panel population-loss guarantee ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
consults $`S`$ only at indices strictly below $`t`$, so
$`\mathcal{B}(S,t)`$ is unchanged if $`S`$ is modified at indices
$`\geq t`$. (ii) By induction on $`t`$:
$`\mathcal{B}(S,1)=\mathcal{B}_{0}`$ is fixed, and if
$`\mathcal{B}(S,t)`$ is $`\xi`$-measurable then so is
$`m(S,t)=\mathrm{Prop}(\xi,\mathcal{B}(S,t),t)`$, the proposal mechanism
being a deterministic function of $`\xi`$, the current bank and the step
index; hence $`\mathcal{B}(S,t+1)`$ is $`\xi`$-measurable. (iii)
Immediate from the definition of the gate
equation [1](#S3.E1 "In Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
which accepts exactly at the steps in $`S^{\ast}`$. (iv) A pair in
$`\mathcal{F}_{k}`$ is determined by the step $`t`$ at which it occurs
together with the prefix $`S\cap[t-1]`$, by (i). The constraint
$`t\in S`$ and $`|S\cap[t-1]|=k-1`$ means the prefix is a subset of
$`[t-1]`$ of size exactly $`k-1`$, of which there are
$`\binom{t-1}{k-1}`$. Summing over $`t\in[T_{\mathrm{gate}}]`$ gives

|  |  |  |  |
|----|----|----|----|
|  |
``` math
|\mathcal{F}_{k}(\xi)|\;\leq\;\sum_{t=1}^{T_{\mathrm{gate}}}\binom{t-1}{k-1}=N_{k}.\qed
``` |  | (37) |

The family $`\mathcal{F}_{k}(\xi)`$ is defined without reference to the
panel: it enumerates what the optimizer could have produced under every
possible sequence of verdicts. Each of its elements is therefore a fixed
bank-and-move pair against which the panel is an honest i.i.d. sample.

###### Proof of Theorem [3](#Thmtheorem3 "Theorem 3 (Adaptive-validation population-loss guarantee). ‣ Validation reliability. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

Fix $`k\geq 1`$ and work conditionally on $`\xi`$. Let
$`(\mathcal{B},m)\in\mathcal{F}_{k}(\xi)`$. By
Lemma [2](#Thmlemma2 "Lemma 2 (Path compression). ‣ A.7 Proof of the reused-panel population-loss guarantee ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")(ii)
it is $`\xi`$-measurable and hence, by
Assumption [1](#Thmassumption1 "Assumption 1 (Sample independence). ‣ Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
independent of the panel. The panel values

|  |  |  |  |
|----|----|----|----|
|  |
``` math
Y_{i}:=\widehat{u}_{m(\mathcal{B}),\mathcal{B}}(x_{i}),\qquad x_{i}\in V,
``` |  | (38) |

are therefore i.i.d. in $`[-1,1]`$ with mean
$`g_{\mathcal{D}}(m\mid\mathcal{B})`$ and variance at most
$`\sigma^{2}`$, and their average is
$`\widehat{g}_{V}(m\mid\mathcal{B})`$.
Lemma [1](#Thmlemma1 "Lemma 1 (One-sided Bennett radius). ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
with $`L=L_{k}`$ and, by
Remark [1](#Thmremark1 "Remark 1 (Effective range). ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization"),
$`M=1+\gamma`$, gives

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbb{P}\Big(\widehat{g}_{V}(m\mid\mathcal{B})-g_{\mathcal{D}}(m\mid\mathcal{B})>b_{1+\gamma}(n,L_{k},\sigma^{2})\Big)\;\leq\;e^{-L_{k}}=\frac{\delta_{k}}{N_{k}}.
``` |  | (39) |

A union bound over the at most $`N_{k}`$ elements of
$`\mathcal{F}_{k}(\xi)`$ gives

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\mathbb{P}\Big(\exists(\mathcal{B},m)\in\mathcal{F}_{k}(\xi):\;\widehat{g}_{V}-g_{\mathcal{D}}>b_{1+\gamma}(n,L_{k},\sigma^{2})\Big)\;\leq\;\delta_{k}.
``` |  | (40) |

By
Theorem [1](#Thmtheorem1 "Theorem 1 (Fixed-panel convergence). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
the run accepts at most $`\lfloor 1/\rho\rfloor`$ moves surely, so only
finitely many strata are non-empty, and summing
equation [40](#A1.E40 "In Proof of Theorem . ‣ A.7 Proof of the reused-panel population-loss guarantee ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
over $`k\geq 1`$,

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\sum_{k\geq 1}\delta_{k}=\delta\sum_{k\geq 1}\frac{1}{k(k+1)}=\delta\sum_{k\geq 1}\left(\frac{1}{k}-\frac{1}{k+1}\right)=\delta.
``` |  | (41) |

Hence with probability at least $`1-\delta`$ the event in
equation [40](#A1.E40 "In Proof of Theorem . ‣ A.7 Proof of the reused-panel population-loss guarantee ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
fails for every $`k`$ simultaneously. On that event, the $`k`$-th
accepted move of the realized run lies in $`\mathcal{F}_{k}(\xi)`$ by
Lemma [2](#Thmlemma2 "Lemma 2 (Path compression). ‣ A.7 Proof of the reused-panel population-loss guarantee ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")(iii)–(iv),
so

|  |  |  |  |
|----|----|----|----|
|  |
``` math
g_{\mathcal{D}}(m\mid\mathcal{B})\;\geq\;\widehat{g}_{V}(m\mid\mathcal{B})-b_{1+\gamma}(n,L_{k},\sigma^{2})\;\geq\;\rho-b_{1+\gamma}(n,L_{k},\sigma^{2}),
``` |  | (42) |

the last step by the acceptance rule
equation [1](#S3.E1 "In Validate. ‣ 3.1 Problem setup and VALVE framework ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").
The bound holds conditionally on $`\xi`$ with probability at least
$`1-\delta`$ for every $`\xi`$, and therefore unconditionally. ∎

The proof uses no independence between candidates, no freshness of the
panel and no restriction on how proposals react to past verdicts;
reusing the rollouts of the unchanged current bank induces dependence
across the elements of $`\mathcal{F}_{k}(\xi)`$, which a union bound
tolerates. It does require $`T_{\mathrm{gate}}`$ to be fixed in advance,
since it determines $`N_{k}`$.

### A.8  Proof of the sizing rule

###### Proof of Corollary [1](#Thmcorollary1 "Corollary 1 (Holdout sizing). ‣ Holdout sizing. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").

By
Lemma [1](#Thmlemma1 "Lemma 1 (One-sided Bennett radius). ‣ A.2 The deviation radius ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
it suffices to make the displayed relaxation of $`b_{M}`$ at most
$`\gamma`$, that is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\sqrt{\frac{a}{N}}+\frac{c}{N}\;\leq\;\gamma,\qquad a:=2s^{2}L,\quad c:=\frac{2ML}{3}.
``` |  | (43) |

Substituting $`u:=N^{-1/2}>0`$ turns this into the quadratic condition

|     |                                       |     |      |
|-----|---------------------------------------|-----|------|
|     |
       ``` math
       c\,u^{2}+\sqrt{a}\,u-\gamma\;\leq\;0,
       ```                                    |     | (44) |

whose left-hand side is increasing in $`u`$ on $`u>0`$ and vanishes at

|     |                                                   |     |      |
|-----|---------------------------------------------------|-----|------|
|     |
       ``` math
       u^{\star}=\frac{-\sqrt{a}+\sqrt{a+4c\gamma}}{2c}.
       ```                                                |     | (45) |

The condition is therefore $`u\leq u^{\star}`$, i.e.
$`N\geq(u^{\star})^{-2}`$, which is
equation [5](#S3.E5 "In Corollary 1 (Holdout sizing). ‣ Holdout sizing. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization").
Expanding $`\sqrt{a+4c\gamma}=\sqrt{a}\,(1+2c\gamma/a+O(\gamma^{2}))`$
gives $`u^{\star}=\gamma/\sqrt{a}+O(\gamma^{2})`$ and hence
$`N=(2s^{2}L/\gamma^{2})(1+O(\gamma))`$, the stated leading order. All
reported sizes invert the exact radius $`b_{M}`$ rather than its
relaxation, and are therefore no larger. ∎

### B.1  Data construction and reference configuration

We use one common Extract–Retrieve–Validate protocol across
repository-level experiments; only the repository, backbone, or
explicitly ablated component changes.
Table [5](#A2.T5 "Table 5 ‣ B.1 Data construction and reference configuration ‣ Appendix B Implementation details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
summarizes this reference protocol rather than a configuration
specialized to any single repository.

|  Component |  Reference setting |
|----|----|
|  Data |  One repository-level task stream from the SWE-smith training split |
|  Evaluation set |  100 tasks sampled without replacement (seed 42) |
|  Validation panel |  50 tasks sampled from the remaining stream (seed 123); the same fixed panel is used for every acceptance decision |
|  Agent |  Frozen code-agent backbone (MiniMax-M2.7, GPT-5.5, or Claude-4.6-sonnet, according to the run) with an interactive shell environment |
|  Adaptation |  3 independently sampled rollouts per task |

|  Evaluation |  100 held-out tasks at step 0 and every 10 mixed tasks, with 3 rollouts per task |

runs.

#### Repository selection.

We study DeepDiff, Pygments, pydicom, and SQLFluff, selected from the
high-volume SWE-smith repositories using two practical criteria. First,
each provides more than $`1{,}000`$ nonempty tasks to construct
substantial adaptation, validation, and evaluation partitions, and
yields reliable patch-producing agent runs. Second, they exercise
markedly different forms of repository knowledge: recursive object
comparison, syntax highlighting, medical-image processing, and SQL
parsing and linting. This combination lets us test whether persistent
skills help across distinct APIs, test structures, and debugging
patterns rather than within variants of one application domain.

Within each repository, the partition is constructed before adaptation.
We first sample and remove the evaluation set, then reserve 50
validation tasks, and use the remainder as the adaptation stream. Thus
no exact instance appears in more than one partition. The 50 reserved
tasks form one fixed validation panel reused at every comparison rather
than a fresh sample at each update. The prepared order of the adaptation
stream is preserved, and independent fixed seeds make the partitions
reproducible.

### B.2  Rollout collection and evolution trigger

For each adaptation task $`x_{t}`$, the agent receives the issue
description and an interactive repository environment in which it can
inspect files, edit source code, and execute tests. An attempt
terminates when the agent submits a patch or reaches its interaction
budget. The submitted patch is evaluated by the executable task-specific
test harness; this outcome, rather than the agent’s self-assessment,
supplies the binary label.

Before generating attempts, Retrieve selects one memory context
$`M_{t}`$ from the current bank. Three rollouts are then sampled
independently under the same issue and frozen context. Let $`R=3`$ and
let $`z_{t,r}\in\{0,1\}`$ indicate whether attempt $`r`$ passes the
executable tests. We call task $`t`$ *mixed* when

|     |                            |     |      |
|-----|----------------------------|-----|------|
|     |
       ``` math
       0<\sum_{r=1}^{R}z_{t,r}<R.
       ```                         |     | (46) |

Mixed tasks provide a within-task contrast: the issue, repository state,
and retrieved context are held fixed, but the sampled trajectories
contain both successes and failures. The full pipeline applies Extract
only to this subset, avoiding lessons inferred solely from uniformly
successful or uniformly failed experience. All tasks are nevertheless
solved and scored. The evolution index counts mixed tasks, so the
100-step budget can require observing approximately $`1{,}000`$ raw
tasks.

### B.3  Extract: contrastive reflection

Extract maps the labeled rollout set
$`\tau_{t}=\{(h_{t,r},p_{t,r},z_{t,r})\}_{r=1}^{R}`$ to a candidate
update $`\Delta_{t}=(\Delta_{t}^{P},\Delta_{t}^{S})`$, where $`h`$ is
the interaction history and $`p`$ the submitted patch. The reflection
context contains the issue, the three labeled summaries, their final
results, and the names of existing memories. The latter discourages
paraphrased duplicates. Extract returns at most three principles and
three skills.

We distinguish the two memory types semantically. A *principle* captures
a domain-agnostic reasoning strategy—how to reason under uncertainty. A
*skill* captures a narrow, executable software-engineering procedure,
search strategy, testing pattern, or recurring mistake to avoid. The
central system instruction used for same-task contrastive extraction is
shown below; formatting examples are omitted for space.

System prompt: contrastive Extract *You are a learning agent extracting
transferable lessons from multiple attempts at the same software
engineering task. Return strict JSON with exactly three keys:
issue_summary, principles, skills.* *Focus on: what reasoning
distinguished successful attempts from failed ones; mistakes repeated
across failed attempts; concrete techniques that worked.* Principles:
*meta-cognitive, domain-agnostic reasoning strategies. Principles
describe HOW to think and reason, not what to do procedurally. They must
be useful beyond any single language, framework, or task type.* Skills:
*specific, actionable software-engineering techniques. They must be
narrow enough to apply immediately and grounded in what went wrong or
what worked in the trajectories.* *Output only valid JSON. Return at
most three new principles and three new skills; return empty lists if
there are no new insights worth adding.*

The accompanying user message instantiates the following template:

User prompt template *Task: \[issue description\]* *This task was
attempted $`R`$ times: \[number\] succeeded and \[number\] failed.*
*Attempt 1 \[SUCCESS/FAILED\]: \[trajectory summary; final result\]*
*$`\ldots`$* *Attempt $`R`$ \[SUCCESS/FAILED\]: \[trajectory summary;
final result\]* *Already known principles/skills (do not repeat or
closely paraphrase): \[item names\]. Extract at most three new
principles and three new skills.*

Each principle contains a short search sentence and a structured body
with Statement and When to apply. Each skill contains a search sentence,
a scope hint, and a structured body with Scope, Trigger, and a numbered
Procedure. Optional anti-patterns and code examples make the learned
text directly usable by a future solver. The logical output schema is

``` ltx_verbatim
{
  "principles": [{"name": "...", "text": "...",
                  "markdown": "..."}],
  "skills": [{"name": "...", "text": "...",
              "scope_hint": "...", "markdown": "..."}]
}
````

Malformed outputs produce an empty proposal rather than an unconstrained
repair attempt. This conservative choice prevents malformed reflections
from entering the persistent state.

### B.4  Persistent skill state

In the reference configuration, the state $`M=(P,S)`$ consists of
separate append-only banks of principles $`P`$ and skills $`S`$. An item
stores its name, search sentence, rich body, source tasks, support
count, creation step, usage count, and source-outcome statistics; skills
additionally retain a scope hint. These fields support both retrieval
and later inspection of provenance.

Before validation, exact normalized duplicates are merged with their
existing items. A candidate is also suppressed when its token-set
Jaccard similarity to an existing item is at least $`0.45`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

       ``` math
       J(a,b)=\frac{|T_{a}\cap T_{b}|}{|T_{a}\cup T_{b}|}\geq 0.45.
       ```                                                           |     | (47) |

Here $`T`$ includes the search sentence and rich body, as well as the
scope hint for skills. The reference configuration performs no periodic
summarization or LLM-based consolidation, ensuring that accepted updates
remain individually traceable.

### B.5  Retrieve: task-conditioned skill composition

Retrieve independently ranks principles and skills for the current
issue. The query combines the task identifier and issue description. For
item $`i`$, let $`Q`$ denote query tokens, $`C_{i}`$ the item’s
search-text tokens, and $`M_{i}`$ its metadata tokens (the scope hint
for a skill and the empty set for a principle). The score is

|     |                             |                                                                                                                                                         |                        |         |
| --- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ------- | --- | --- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | --- | --- |
|     | $`\displaystyle s(i,q)={}`$ | $`\displaystyle\underbrace{\frac{                                                                                                                       | Q\cap(C*{i}\cup M*{i}) | }{\min( | Q   | ,   | C*{i}\cup M*{i} | )}}_{\text{overlap coefficient}}+\underbrace{\sum_{w\in Q\cap C*{i}}\log*{2}\!\max\!\left(\frac{N}{df(w)},1\right)}\_{\text{text IDF}}`$ |     |     |
|     |                             | $`\displaystyle+0.45\underbrace{\sum_{w\in Q\cap M_{i}}\log_{2}\!\max\!\left(\frac{N}{df(w)},1\right)}_{\text{scope IDF}}+0.5I_{i}+\cos(e_{q},e_{i}),`$ |                        | (48)    |

where $`N`$ is the size of the corresponding bank. The lexical terms
reward direct issue and scope matches, while cosine similarity captures
semantic relatedness between the issue and rich item body. $`I_{i}`$ is
an importance prior derived from source-task outcomes, with support
count as a fallback. Semantic vectors use the Qwen3-Embedding-0.6B model
when available, with a deterministic hashing representation as a
fallback. The ten highest-scoring principles and ten highest-scoring
skills are selected independently.

The selected rich bodies are composed into the solver context rather
than re-summarized. This preserves procedures, triggers, and
anti-patterns exactly as validated. The injected system-prompt block has
the following form:

System-prompt augmentation produced by Retrieve _Learned principles:_ _—
\[principle name\] —_ _\[Statement; when to apply; optional
anti-pattern\]_ _$`\ldots`$_ _Learned skills:_ _— \[skill name\] —_
_\[Scope; trigger; numbered procedure; optional anti-pattern\]_
_$`\ldots`$_ _Use the above when relevant, but do not follow them
blindly if repository evidence contradicts them._

The final instruction treats retrieved memory as defeasible guidance
rather than an authority that can override repository evidence.

### B.6  Validate: paired acceptance on executable outcomes

Extract proposes a _joint_ bank move containing all new principles and
skills from the current mixed task. Validate compares two conditions on
the same fixed 50-task validation set:

- •
  current: task-conditioned retrieval from the current bank $`M`$;
- •
  candidate: the same retrieved context augmented by all items in
  $`\Delta_{t}`$.

Each condition receives three independently sampled and executably
graded rollouts per task. For $`c\in\{\mathrm{cur},\mathrm{cand}\}`$,
the empirical pass rate is

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\widehat{p}_{c}=\frac{1}{50}\sum_{j=1}^{50}\frac{1}{3}\sum_{r=1}^{3}z^{(c)}_{j,r}.
``` |  | (49) |

All reported experiments use the acceptance threshold $`\rho=0.02`$. The
proposed move is committed exactly when

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\widehat{p}_{\mathrm{cand}}\geq\widehat{p}_{\mathrm{cur}}+0.02.
``` |  | (50) |

Thus each condition aggregates 150 binary outcomes, and the threshold
requires at least three net additional successful rollouts on the
$`1/150`$ score grid. The comparison validates the joint state
transition rather than attributing utility to individual items. Results
for the unchanged current state are reused until an accepted update
changes the bank, reducing repeated evaluation without changing the
acceptance rule.

The same 50 tasks are reused for every candidate. They are 50 distinct
task draws with three within-task replications, not 150 independent
population-task samples. Accordingly, $`\rho=0.02`$ is an empirical
acceptance margin rather than a confidence level. A comparison uses up
to $`2\times 50\times 3=300`$ executable rollouts before reuse of the
unchanged current result. Across $`24{,}600`$ task-level paired samples
from the main runs, the candidate-minus-current difference has mean
$`-0.006184`$ and variance $`0.024954`$, rounded to
$`\sigma^{2}=0.025`$.
Theorem [1](#Thmtheorem1 "Theorem 1 (Fixed-panel convergence). ‣ 3.2 Stable evolution and certified performance ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
characterizes fixed-panel convergence with score carry-forward, while
Theorem [3](#Thmtheorem3 "Theorem 3 (Adaptive-validation population-loss guarantee). ‣ Validation reliability. ‣ 3.3 Validation reliability and holdout sizing ‣ 3 VALVE: Validation-Gated Evolution for Agents ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
gives the corresponding uniform population-loss guarantee over the paths
induced by panel reuse.
Table [4](#A1.T4 "Table 4 ‣ A.9 Numerical instantiation ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
and
Figure [7](#A1.F7 "Figure 7 ‣ A.9 Numerical instantiation ‣ Appendix A Proofs and Certification Details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")

### B.7  Evaluation protocol and reported statistic

Before adaptation and every ten mixed tasks, we freeze the current bank
and evaluate it on a disjoint 100-task panel. Each task receives three
independent rollouts. For panel size $`H=100`$, avg@3 is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
\operatorname{avg@3}=100\times\frac{\sum_{j=1}^{H}\sum_{r=1}^{3}z_{j,r}}{3H}.
``` |  | (51) |

The denominator includes all $`3H`$ attempts, including empty or
unsuccessful submissions. The main table reports the final-checkpoint
avg@3 first and the highest observed avg@3 over the trajectory in
parentheses. The latter uses this panel for checkpoint selection and
therefore is not an untouched final-test estimate. When gains are
discussed, final and peak gains are computed relative to the shared
step-0 evaluation. We retain the bank state, extracted proposals,
rollout histories, executable verdicts, validation comparisons, and
periodic evaluation results needed to reconstruct each accepted
transition.

### B.8  Ablation implementations and prompts

Table [6](#A2.T6 "Table 6 ‣ B.8 Ablation implementations and prompts ‣ Appendix B Implementation details ‣ Certified Long-Horizon Code Agent Evolution via Validation-Gated Skill Optimization")
describes each intervention at the method level. Because some
interventions jointly alter representation and control flow, we state
these couplings explicitly rather than treating every command-line
change as a perfectly isolated causal operator.

|  Ablation |  Method-level intervention |
|----|----|
|  Sentence skills |  Replace structured rich bodies with one-sentence principles and scoped skill sentences throughout extraction, storage, and injection. |
|  No principles |  Constrain Extract to return an empty principle set; retrieve and inject skills only. |
|  Single document |  Replace itemized banks with one principle document and one skill document, updated through section-level add/replace/delete operations and injected in full. This also removes item-level retrieval. |
|  Inject all |  Remove task-conditioned ranking and inject every stored item in reverse creation order. |
|  Batch of four |  Buffer four completed tasks and perform one cross-task reflection; use one validation rollout per validation task. |
|  All tasks |  Apply Extract and Validate after all-pass and all-fail tasks as well as mixed tasks; the 100-step horizon consequently counts raw tasks. |

Table 6: Method-level definitions of the ablations.

#### Batch extraction.

For the batch-size ablation, Extract receives four task blocks, each
containing the issue, outcome label, trajectory summary, and final
result. Principles must recur across at least two tasks or be
sufficiently universal to justify retention from one instance; skills
may remain task-specific when reusable. The core system instruction is:

System prompt: batched Extract *You are a learning agent that extracts
transferable lessons by comparing multiple completed software
engineering tasks.* *Principles must appear as a recurring pattern
across at least two tasks in this batch, OR be so universally applicable
that a single instance justifies inclusion. Skills can be task-specific
as long as they are genuinely reusable.*

In mixed-only mode, a batch is reflected upon when it contains at least
one mixed task, but neighboring all-pass or all-fail examples remain
visible to the cross-task reflection. Since this condition also uses one
validation rollout per task, it changes both extraction granularity and
validation noise.

#### Single-document extraction.

The single-document condition represents each memory type as sections
under named headings. Reflection proposes bounded section edits of the
form

Single-document update schema *operation: add, replace, or delete*
*target: existing section name* *name: proposed section name* *text:
one-sentence summary* *markdown: complete replacement body* *scope hint:
where or when a skill applies*

A replacement removes the target section and appends the proposed
version; a missing replacement target becomes an addition, while an
addition that reuses an existing name is ignored. Because the resulting
documents are always injected in full, this condition jointly changes
extraction, storage, and retrieval rather than merely changing the
on-disk format.

#### Interpretive scope.

The remaining couplings are similarly important. All-task evolution
changes both the extraction trigger and the number of raw tasks observed
before stopping; removing validation also removes validation-derived
reflection feedback; and high reasoning changes reflection as well as
solving. Ablation differences should therefore be interpreted as effects
of these operational method variants, not as estimates of perfectly
isolated primitives.

◼  audit_yield_tuple_index_group_consistency.md $`\times`$
audit_yield_tuple_index_group_consistency  Scope: Any lexer callback
method that yields (match.start(N), TokenType, match.group(N)) tuples.
Trigger: A bug report or diff shows that match group indices were
swapped between match.start() and match.group() calls in yield
statements. Procedure: (1) Locate every yield statement in the callback
that uses match.start(N) and match.group(M). (2) For each yield, confirm
that N == M—the position index and the group index must refer to the
same capture group. (3) If they differ (e.g., yield match.start(2),
String, match.group(1)), swap them back so both indices match. (4)
Cross-check against the regex pattern’s group numbering to confirm the
semantic meaning of each group. Anti-pattern: \# Wrong: position from
group 2, value from group 1 yield match.start(2), String, match.group(1)
yield match.start(1), String, match.group(2) \# Correct: position and
value from the same group yield match.start(1), String, match.group(1)
yield match.start(2), String, match.group(2)

◼  enumerate_all_swapped_values_in_buggy_commit.md $`\times`$
enumerate_all_swapped_values_in_buggy_commit  Scope: Functions where a
bug-introducing commit swapped or inverted one or more values (booleans,
string literals, constants, token types). Trigger: You find one swapped
value (e.g., ’ vs. ") in a function and are about to fix only that one.
Procedure: (1) Run git show \<bad-commit\> -- \<file\> and collect
every - (removed) and + (added) line in the affected function. (2) For
each changed line, categorize the change: swap, inversion, constant
change, reorder, deletion. (3) List all changes as a checklist before
writing any fix. (4) Fix each item on the checklist, not just the first
one you noticed. (5) After fixing, re-run git show \<bad-commit\> and
confirm every - line is restored and every + line is removed.
Anti-pattern: \# Bug commit changed: \# char = r’"’if double else
r"’"(correct) \# to: \# char = r"’"if double else r’"’(wrong) \# AND
also changed quantifier ’{3,}’ to ’{2,}’ \# AND also changed state_name
prefix ’t’ to ’d’ \# Fixing only the char swap leaves the other bugs
intact.

Use before assignment can indicate reordered code  Statement: When a
variable is used before it is assigned in a code block, suspect that
lines were reordered or moved during a buggy edit rather than that the
variable is simply missing. When to apply: • You encounter a NameError
or a use-before-assignment pattern in code that previously worked. • A
bug-introducing commit touched the ordering of statements in a function.
• The variable is assigned later in the same function, suggesting it was
moved rather than deleted. Better pattern: Trace the full sequence of
statements in the function and check whether any assignment was
displaced below a use site. Reordering the statements back to their
logical order (assign before use) is often the complete fix.
Anti-pattern: Assuming the variable needs to be initialized at the top
of the function with a default value, when the real fix is restoring the
original statement order.
