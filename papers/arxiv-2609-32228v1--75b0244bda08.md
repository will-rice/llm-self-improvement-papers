###### Abstract

In self-play, a proposer generates verifiable tasks to train a solver.
Proposer rewards often depend on the solver’s success rate, but equally
difficult tasks can differ in their training value. We introduce
CompassPlay, a self-play method that rewards the proposer through
gradient alignment. The reward favors tasks whose solver loss gradients
align with those of reference tasks representing the target
capabilities. It draws on a first-order approximation to learning
progress and scores each eligible task without additional solver
training. Our experiments show gains in performance and training
efficiency. In coding self-play with Qwen2.5-Coder-7B, a small external
reference set guides task generation. CompassPlay improves average
accuracy over AZR’s difficulty reward by 1.5 percentage points on
in-domain coding and 2.7 on out-of-domain mathematics. In Lean 4 theorem
proving, CompassPlay matches the difficulty baseline’s 150-iteration
cumulative coverage with 40% fewer GPU-hours.

## 1 Introduction

Self-play turns task generation into part of reasoning-model training. A
proposer creates problems, a solver attempts them, and a verifier checks
the answers ([Zhao et al., 2025](#bib.bib38); [Bailey et al.,
2026](#bib.bib2)). This loop can expand training beyond a fixed
collection of human-written problems. Its value depends on the tasks
that the proposer learns to generate. The verifier checks whether a
solution is correct, but does not establish how much training on
generated tasks would help the solver. The proposer therefore needs a
reward that connects task generation to progress on the capabilities we
want to improve.

A common strategy favors tasks near the solver’s current ability ([Zhao
et al., 2025](#bib.bib38); [Huang et al., 2025](#bib.bib14)). The
solver’s estimated success rate provides an inexpensive signal for
finding such tasks. This encourages a curriculum that adapts as the
solver improves. However, tasks with the same success rate can exercise
different skills and contribute differently to target performance. A
reward based only on success rate cannot distinguish these
contributions.

One way to estimate training value is to train on candidate tasks and
measure the resulting improvement. SOAR follows this principle
([Sundaram et al., 2026](#bib.bib31)). It trains a copy of the solver on
a group of generated problems and evaluates the copy on reference
problems. The accuracy gain becomes a shared reward for the group. This
measures learning progress directly, but requires additional training
and evaluation for each group. We seek a reward that estimates training
value for individual tasks without these additional solver-training
runs.

Gradient-based signals provide a natural proxy for this purpose. Prior
work uses gradients to estimate training value for data selection ([Xia
et al., 2024](#bib.bib34); [Yang et al., 2026](#bib.bib35)) and
influence-based feedback to guide synthetic-data generation ([Li et al.,
2025b](#bib.bib21); [Fan et al., 2026](#bib.bib8)). Building on these
ideas, we introduce CompassPlay, a self-play method that rewards the
proposer through gradient alignment. For a proposed task with a verified
solution, CompassPlay compares the solver’s loss gradient on that
solution with the gradient of a reference loss for the target
capabilities
(Figure [1](#S0.F1 "Figure 1 ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")a).
To first order, a small gradient step on the task lowers the reference
loss in proportion to the inner product of the two gradients. The inner
product also grows with the task’s gradient norm, which can rise without
better alignment, so CompassPlay rewards the cosine of the two gradients
instead
(§[2.2](#S2.SS2 "2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
Both gradients are taken at the solver’s current parameters, so the
reference direction moves as the solver learns, and each eligible task
receives its own score without additional solver training.

We evaluate CompassPlay on two different domains: coding and theorem
proving. We construct the reference from the supervision available in
each domain. In coding self-play, the reference is a fixed external set
of problems with gold solutions, which is not included in proposer
prompts. In our Lean setup, we use no external gold-proof reference set.
We instead use the solver’s verified proofs of solved seed theorems as
local references. Here, the proposer also sees the seed statement. We
observe that optimizing alignment in this setting encourages renamed
copies of the seed. Weighting alignment by a novelty factor relative to
the seed suppresses this behavior
(§[4.2](#S4.SS2 "4.2 Novelty-weighted alignment ‣ 4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
Whether reference tasks appear in proposer prompts therefore matters for
reward design.

Our contributions are as follows.

- •
  We introduce CompassPlay, a proposer reward based on the cosine

## 2 Method

CompassPlay changes the proposer reward within the self-play loop. We
first describe the self-play setting
(§[2.1](#S2.SS1 "2.1 Self-play with a proposer and a solver ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")),
then present the reward design and reference choices
(§[2.2](#S2.SS2 "2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

### 2.1 Self-play with a proposer and a solver

In a classic self-play setting, a proposer policy $`\pi_{\phi}`$
generates tasks for a solver policy $`\pi_{\theta}`$ to attempt
(Figure [1](#S0.F1 "Figure 1 ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")a).
Their parameter vectors are $`\phi`$ and $`\theta`$, respectively. The
two policies may share weights, as in our coding experiments. We denote
a task by $`x`$ and a solver attempt by $`y`$. Given a conditioning
input $`z`$ (past tasks or a seed theorem), the proposer samples a
candidate task $`\tilde{x}\sim\pi_{\phi}(\cdot\mid z)`$. The solver then
samples $`k`$ attempts
$`y_{1},\ldots,y_{k}\sim\pi_{\theta}(\cdot\mid\tilde{x})`$. A verifier
$`v`$ (a Python executor or the Lean 4 compiler) assigns each attempt a
binary correctness reward $`v(\tilde{x},y_{j})\in\{0,1\}`$. The
resulting solve rate is
$`s(\tilde{x})=\frac{1}{k}\sum_{j=1}^{k}v(\tilde{x},y_{j})`$. The solver
uses $`v`$ as its reward for policy-gradient reinforcement learning
(RL). The proposer maximizes the expectation of its scalar reward
$`r(\tilde{x})`$:

|     |     |     |     |
| --- | --- | --- | --- |
|     |

````math
\max_{\phi}\;\mathbb{E}_{\tilde{x}\sim\pi_{\phi}(\cdot\mid z)}\big[r(\tilde{x})\big].
``` |  | (1) |

A common difficulty reward is $`r(\tilde{x})=1-s(\tilde{x})`$ for tasks
with $`0<s(\tilde{x})<1`$, optionally weighted by a judge score ([Zhao
et al., 2025](#bib.bib38); [Bailey et al., 2026](#bib.bib2)).

### 2.2 CompassPlay: Gradient alignment as the proposer reward

The difficulty term $`1-s(\tilde{x})`$ gives the same score to tasks
with the same solve rate. We propose to assess each task’s training
value through its effect on a reference loss. CompassPlay estimates this
effect using first-order gradients.

#### Candidate utility.

To formalize learning benefit, let
$`\mathcal{L}_{\mathrm{ref}}(\theta)`$ be a reference loss for the
target problems. For a held-out reference set, we use the average loss
on its gold solutions. When no such set is available, we use a local
reference described below. Let $`g(\tilde{x})`$ denote the gradient of
the solver’s loss on a candidate paired with a verified solution. All
gradients are taken with respect to the solver parameters $`\theta`$. We
define the candidate’s *utility* as the decrease in
$`\mathcal{L}_{\mathrm{ref}}`$ under a hypothetical gradient step:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
U(\tilde{x})\;=\;\mathcal{L}_{\mathrm{ref}}(\theta)\;-\;\mathcal{L}_{\mathrm{ref}}\big(\theta-\eta\,g(\tilde{x})\big),\qquad g(\tilde{x})=\nabla_{\theta}\,\ell\big(\tilde{x},y^{\star}(\tilde{x});\theta\big),
``` |  | (2) |

where $`\ell(x,y;\theta)`$ is the solver’s cross-entropy (CE) loss,
averaged over solution tokens. Here, $`y^{\star}(\tilde{x})`$ is a
verified solution of the candidate, and $`\eta`$ is the step size. This
hypothetical loss-gradient step defines the scoring proxy. Actual solver
training uses the policy-gradient objective described above.

#### First-order approximation.

We write $`g_{\mathrm{ref}}`$ for the gradient of the reference loss.
The symbols $`\langle\cdot,\cdot\rangle`$ and $`\lVert\cdot\rVert`$
denote the Euclidean inner product and norm, respectively. For a small
step size $`\eta`$,
equation [2](#S2.E2 "In Candidate utility. ‣ 2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
expands to

|  |  |  |  |
|----|----|----|----|
|  |
``` math
U(\tilde{x})\;=\;\eta\,\big\langle g(\tilde{x}),\;g_{\mathrm{ref}}\big\rangle\;+\;O(\eta^{2}),\qquad g_{\mathrm{ref}}=\nabla_{\theta}\mathcal{L}_{\mathrm{ref}}(\theta).
``` |  | (3) |

This first-order term corresponds to the single-step influence estimate
underlying TracIn ([Pruthi et al., 2020](#bib.bib27)). GradAlign ([Yang
et al., 2026](#bib.bib35)) uses a related gradient-alignment criterion
to select RL training problems. Evaluating this approximation requires
no optimizer step or second-order derivatives. Both gradients are taken
at the solver’s *current* parameters, so the reference direction evolves
as the solver learns.

#### From inner product to cosine.

The inner product in
equation [3](#S2.E3 "In First-order approximation. ‣ 2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
depends on both gradient norms and directional alignment. For positive
alignment, a larger candidate gradient norm can raise the score without
improving that alignment. CompassPlay therefore normalizes both
gradients and uses their cosine similarity as its base proposer reward:

|  |  |  |  |
|----|----|----|----|
|  |
``` math
r_{\cos}(\tilde{x})\;=\;\cos\big(g(\tilde{x}),\,g_{\mathrm{ref}}\big)\;=\;\frac{\langle g(\tilde{x}),g_{\mathrm{ref}}\rangle}{\lVert g(\tilde{x})\rVert\,\lVert g_{\mathrm{ref}}\rVert}.
``` |  | (4) |

The resulting reward is bounded in $`[-1,1]`$ and invariant to positive
rescaling of either gradient. We compare cosine and inner-product
rewards in our coding ablation
(§[3.3](#S3.SS3 "3.3 Ablations ‣ 3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver");
Appendix [C.2](#A3.SS2 "C.2 Cosine vs dot product ‣ Appendix C Ablations on the coding task ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

#### The reference gradient.

CompassPlay constructs $`\mathcal{L}_{\mathrm{ref}}`$ from the reference
data available in each domain. In coding self-play, we use a held-out
*external* reference set
$`\mathcal{D}_{\mathrm{ref}}=\{(x_{j},y_{j}^{\star})\}`$ of problems
with gold solutions, which is not included in proposer prompts
(§[3](#S3 "3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
describes the set). The reference loss is
$`\mathcal{L}_{\mathrm{ref}}(\theta)=\frac{1}{|\mathcal{D}_{\mathrm{ref}}|}\sum_{j}\ell(x_{j},y_{j}^{\star};\theta)`$,
and $`g_{\mathrm{ref}}`$ is its gradient at the current $`\theta`$.

In our theorem-proving setup, we use no external gold-proof reference
set. The solver’s own verified proofs provide the reference supervision.
Each candidate is generated from a seed statement that the solver has
already proved. We use the seed’s verified proof as a *local* reference,
with
$`g_{\mathrm{ref}}=\nabla_{\theta}\ell(x_{\mathrm{seed}},y^{\star}_{\mathrm{seed}};\theta)`$.
The reward favors conjectures whose proof gradients align with this
reference gradient. The key distinction is whether reference tasks
appear in proposer prompts. In the local setting, the proposer sees the
seed statement whose verified proof defines $`g_{\mathrm{ref}}`$. We
leave the dependence of $`g(\tilde{x})`$ and $`g_{\mathrm{ref}}`$ on
$`\theta`$ implicit. For local references, $`g_{\mathrm{ref}}`$ also
depends on the candidate’s seed.

#### The candidate gradient.

CompassPlay computes $`g(\tilde{x})`$ from the solver’s loss on a
candidate paired with a *verified* solution. Unverified attempts are not
used to compute this gradient. In coding self-play, we use the oracle
answer in the solver’s answer format. Depending on the task type, this
answer is the executed output, the input supplied by the proposer, or
the proposer’s program. In theorem proving, we average the loss
gradients over up to $`m`$ verified proofs generated by the solver for
each conjecture, with $`m=4`$ in our experiments. We compute gradients
with respect to all solver parameters and accumulate the cosine in
single precision.

#### Which candidates are rewarded.

CompassPlay applies the alignment reward to candidates solved in some
but not all sampled attempts ($`0<s(\tilde{x})<1`$). In theorem proving,
the base loop also requires $`s(\tilde{x})`$ to be at most the 70th
percentile of solve rates in the batch. Candidates outside these
criteria receive no alignment reward. We handle them as in the base
loop: a fixed penalty in coding and exclusion from the proposer batch in
theorem proving. These rules govern proposer rewards; the solver retains
its domain’s training objective and task filters. The proposer update
retains the base loop’s advantage estimator, reward normalization within
each batch, and KL and clipping terms.

#### Lower computational cost.

CompassPlay is computationally cheaper than measuring learning benefit
through repeated solver training and evaluation. It scores candidates
individually using first-order gradients, without the additional
training runs required by SOAR ([Sundaram et al., 2026](#bib.bib31))
(Appendix [A](#A1 "Appendix A The SOAR baseline ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
The added work consists of forward/backward passes on verified candidate
and reference solutions. A shared reference gradient can be reused
across candidates while the solver parameters remain fixed. Scoring does
not update model parameters, and temporary gradients are discarded
afterward. Relative to difficulty rewards, which reuse the solve-rate
rollouts, the extra cost is the gradient computation. We report measured
costs and training efficiency in
§[3.2](#S3.SS2 "3.2 Comparison with SOAR ‣ 3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver"),
§[4.3](#S4.SS3 "4.3 Coverage and computational cost ‣ 4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver"),
and
Appendix [B](#A2 "Appendix B Per-step cost breakdown ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver").

#### Reward variants.

In coding self-play, CompassPlay uses the cosine reward
$`r_{\cos}(\tilde{x})`$ from
equation [4](#S2.E4 "In From inner product to cosine. ‣ 2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver").
In theorem proving, alignment with a local reference can reward copies
of the seed
(§[4.1](#S4.SS1 "4.1 Copying with a local reference ‣ 4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
We therefore multiply the cosine reward by a novelty factor. Let
$`J(\tilde{x},x_{\mathrm{seed}})\in[0,1]`$ denote the token-Jaccard
similarity between the candidate statement $`\tilde{x}`$ and its seed
$`x_{\mathrm{seed}}`$. The resulting reward is

|  |  |  |  |
|----|----|----|----|
|  |
``` math
r_{\cos\times\mathrm{nov}}(\tilde{x})=r_{\cos}(\tilde{x})\,\bigl(1-J(\tilde{x},x_{\mathrm{seed}})\bigr).
``` |  | (5) |

In the experiments, CompassPlay (cos) uses $`r_{\cos}`$, while
CompassPlay (cos $`\times`$ novelty) uses
$`r_{\cos\times\mathrm{nov}}`$.
Appendix [F](#A6 "Appendix F Instantiation details and pseudocode ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
summarizes both instantiations and gives the self-play loop in
Algorithm [1](#alg1 "Algorithm 1 ‣ Appendix F Instantiation details and pseudocode ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver"),
using the same similarity function $`J`$.

## 3 General reasoning with coding self-play

#### Setup.

We evaluate CompassPlay in the coding self-play setting of AZR ([Zhao
et al., 2025](#bib.bib38)). The proposer and solver share a single
Qwen2.5-Coder-7B model ([Hui et al., 2024](#bib.bib15)). Tasks are built
from Python programs and verified by execution. Task types, the solver
objective, and the training configuration follow AZR. We compare three
configurations:

- •
  solve-only: only the solver objective is optimized. Proposals still
  come from the shared weights, which change as the solver learns.
- •
  AZR (difficulty): the difficulty reward of AZR, $`1-s`$ for $`0<s<1`$.
- •
  CompassPlay (cos): the cosine gradient-alignment reward in
  equation [4](#S2.E4 "In From inner product to cosine. ‣ 2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver").

AZR and CompassPlay differ only in the proposer reward. For CompassPlay,
$`g_{\mathrm{ref}}`$ is the cross-entropy gradient of gold solutions to
32 problems from the MATH training split. This reference set is fixed
throughout training, disjoint from evaluation, and not included in
proposer prompts. Mathematics problems are used only for the reference
gradient; solver-training tasks remain coding problems.

Each configuration runs for 200 steps. We evaluate with greedy decoding
every 5 steps on three coding benchmarks: LiveCodeBench ([Jain et al.,
2025](#bib.bib16)), CRUXEval-I, and CRUXEval-O ([Gu et al.,
2024](#bib.bib10)). We also evaluate on five mathematics benchmarks:
MATH500 ([Lightman et al., 2024](#bib.bib22)), AMC23, GSM8K ([Cobbe
et al., 2021](#bib.bib4)), Minerva Math ([Lewkowycz et al.,
2022](#bib.bib19)), and OlympiadBench ([He et al., 2024](#bib.bib11)).
Mathematics is out of domain with respect to the generated training
tasks. CompassPlay and AZR use the same three random seeds; solve-only
has one run.
Appendix [E](#A5 "Appendix E Experimental details ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
gives benchmark and evaluation details.

### 3.2 Comparison with SOAR

CompassPlay estimates each candidate’s training value from gradient
alignment. SOAR ([Sundaram et al., 2026](#bib.bib31)) instead rewards
candidate groups by the reference-accuracy gain after training a solver
copy on each group. We compare the downstream accuracy and computational
cost of these approaches. No public implementation was available, so we
reimplemented SOAR on our training stack. It shares the base model,
proposer, and outer optimizer with the other methods.
Appendix [A](#A1 "Appendix A The SOAR baseline ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
describes the inner loop, reference set, and deviations from the
original recipe. We ran this baseline once for 20 outer steps.

evaluation checkpoint. GPU-hours are training wall-clock time multiplied
by the number of GPUs, excluding benchmark evaluation.

### 3.3 Ablations

We test the two design choices in
§[2.2](#S2.SS2 "2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver"):
which gradients represent the candidate and the reference, and how the
two gradients are compared. Each configuration is run once.

#### CE and REINFORCE gradients.

The solver is trained with policy-gradient RL, whereas CompassPlay
computes both gradients from the CE loss on verified or gold solutions
(§[2.2](#S2.SS2 "2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
We therefore test whether gradients of the RL objective give a better
reward. We replace CE gradients with REINFORCE estimates of the gradient
of the expected verifier reward on the reference side alone or on both
sides ([Williams, 1992](#bib.bib33)). The CE configuration outperforms
both variants at the CE run’s final compute budget. With a shared seed,
the CE run uses 93 GPU-hours for 200 training steps, versus 161 with
REINFORCE gradients on both sides
(Appendix [C.1](#A3.SS1 "C.1 The reference gradient ‣ Appendix C Ablations on the coding task ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

#### Cosine and dot-product rewards.

The first-order utility in
equation [3](#S2.E3 "In First-order approximation. ‣ 2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
is the inner product, which also grows with the candidate gradient norm.
We test whether normalizing it to the cosine improves training. Cosine
achieves higher mean accuracy than the dot product over the final
quarter of training: 58.31% vs. 55.99% on coding and 48.13% vs. 45.16%
on mathematics.
Appendix [C.2](#A3.SS2 "C.2 Cosine vs dot product ‣ Appendix C Ablations on the coding task ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
gives the settings and learning curves.

## 4 Theorem proving with Lean self-play

#### Setup.

We evaluate CompassPlay on the 3,323 target theorems of SGS ([Bailey
et al., 2026](#bib.bib2)) using separate DeepSeek-Prover-V2-7B models
for the proposer and solver ([Ren et al., 2025](#bib.bib29)). We use
full-parameter updates and check proofs with Lean 4 ([de Moura &
Ullrich, 2021](#bib.bib5)) against mathlib4 ([The mathlib Community,
2020](#bib.bib32)). Our implementation adapts the SGS training framework
to condition conjectures on solved target theorems (seeds); the original
SGS recipe conditions on unsolved targets. For each candidate,
$`g_{\mathrm{ref}}`$ is computed from its seed’s verified proof at the
current solver parameters. We use no external gold-proof reference set.

In each iteration, the solver attempts every unsolved target theorem. We
report cumulative coverage on this target set: the fraction of target
theorems solved at least once. Each method is run once.

#### Methods.

We compare proposer-training strategies within the same adapted setup:

- •
  solve-only: the proposer is frozen, and only the solver is trained.
- •
  SGS reward: the SGS guide score times the difficulty term $`1-s`$.
- •
  difficulty: the solve-rate reward $`1-s`$.
- •
  CompassPlay (cos): the cosine reward in
  equation [4](#S2.E4 "In From inner product to cosine. ‣ 2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver"),
  $`\cos(g(\tilde{x}),g_{\mathrm{ref}})`$, with the local reference.
- •
  CompassPlay (cos $`\times`$ novelty): alignment weighted by novelty
  relative to the seed
  (§[4.2](#S4.SS2 "4.2 Novelty-weighted alignment ‣ 4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

### 4.1 Copying with a local reference

The proposer sees the seed whose proof defines its local reference.
Repeating that seed can therefore offer a shortcut to high alignment
without introducing a new task. We measure copying by the fraction of
eligible conjectures with token-Jaccard similarity above 0.8 to their
seed. In
Figure [4](#S4.F4 "Figure 4 ‣ 4.1 Copying with a local reference ‣ 4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver"),
the copy rate of CompassPlay (cos) reaches 96% at iteration 75, while
difficulty falls below 1% by iteration 40. A separate name-normalization
audit confirms that many conjectures are pure renamings of their seeds
(Appendix [D](#A4 "Appendix D Pure-rename audit ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

### 4.2 Novelty-weighted alignment

To reduce copying in this setting, we multiply the cos reward by novelty
relative to the seed, giving CompassPlay (cos $`\times`$ novelty) in
equation [5](#S2.E5 "In Reward variants. ‣ 2.2 CompassPlay: Gradient alignment as the proposer reward ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver").
The novelty factor is zero at token-Jaccard similarity 1 and shrinks the
alignment score’s magnitude as overlap increases. We retain eligible
candidates in the proposer batch and apply the base loop’s reward
normalization.

With CompassPlay (cos $`\times`$ novelty), the copy rate stays below
0.5% over iterations 60–150
(Figure [4](#S4.F4 "Figure 4 ‣ 4.1 Copying with a local reference ‣ 4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
At the audited checkpoints, the pure-rename rates are 1.0% for
cos $`\times`$ novelty and 77.5% for cos
(Appendix [D](#A4 "Appendix D Pure-rename audit ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

## 5 Related work

#### Proposer rewards in self-play.

Many self-play methods use solver feedback to guide task generation
([Zhao et al., 2025](#bib.bib38); [Bailey et al., 2026](#bib.bib2);
[Dong & Ma, 2025](#bib.bib7); [Poesia et al., 2024](#bib.bib26)). Some
favor tasks near the solver’s current ability using estimates of success
or uncertainty ([Huang et al., 2025](#bib.bib14); [Liu et al.,
2025](#bib.bib23)). Others reward tasks that cause solver failure
([Zhang et al., 2025](#bib.bib37); [Kuba et al., 2025](#bib.bib18)). SGS
supplements difficulty with an LLM guide score ([Bailey et al.,
2026](#bib.bib2)). GASP uses hard goalpost problems to guide generation
([Jana et al., 2026](#bib.bib17)), while [Pu et al. (2026)](#bib.bib28)
study data gating and reward grounding. SOAR rewards task groups by the
gain in reference accuracy after training a solver copy on them
([Sundaram et al., 2026](#bib.bib31)). CompassPlay uses gradient
alignment as a proxy for learning progress. Each eligible candidate
receives a score without these additional solver-training runs.

#### Learnability signals.

Automatic curricula prioritize tasks using intermediate success rates
([Florensa et al., 2018](#bib.bib9)), learning progress ([Matiisen
et al., 2017](#bib.bib24)), or regret ([Dennis et al., 2020](#bib.bib6);
[Parker-Holder et al., 2022](#bib.bib25)). In LLM reinforcement
learning, SEC uses a learnability-based curriculum ([Chen et al.,
2025](#bib.bib3)), and LearnAlign uses gradient alignment for data
selection ([Li et al., 2025a](#bib.bib20)). CompassPlay uses a related
alignment signal to train a proposer to generate tasks.

#### Influence-based data selection and generation.

TracIn estimates data influence by accumulating gradient inner products
across training checkpoints ([Pruthi et al., 2020](#bib.bib27)). LESS
selects instruction data using gradient similarity to target examples
([Xia et al., 2024](#bib.bib34)). MATES learns an influence model for
pretraining data selection ([Yu et al., 2024](#bib.bib36)). GradAlign
uses alignment between candidate and validation gradients for RL data
selection ([Yang et al., 2026](#bib.bib35)). Influence feedback can also
guide generation. Montessori-Instruct trains a teacher using changes in
reference loss for individual training examples and updates the student
between rounds ([Li et al., 2025b](#bib.bib21)). OptimSyn uses
optimizer-aware gradient influence to reward a rubric generator ([Fan
et al., 2026](#bib.bib8)). CompassPlay uses gradient alignment in
self-play with executable or formal verification. Both proposer and
solver learn throughout training, and the reward uses gradients at the
current solver parameters. In Lean, we observe substantial copying when
the proposer sees the seed defining its local reference. Novelty
weighting reduces this behavior
(§[4.2](#S4.SS2 "4.2 Novelty-weighted alignment ‣ 4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
In our coding setup, reference tasks are not included in proposer
prompts and no novelty factor is used.

## 6 Conclusion

CompassPlay rewards proposed tasks through gradient alignment with a
reference objective. It scores each eligible candidate without training
a separate solver copy. In coding self-play, CompassPlay uses an
external reference and improves average accuracy over AZR on both coding
and mathematics. In Lean, the solver’s verified seed proofs provide
local references, but the proposer can learn to copy the seeds it sees.
With novelty weighting, CompassPlay reduces copying and matches the
difficulty baseline’s 150-iteration cumulative coverage with 40% fewer
GPU-hours. These results support gradient alignment as a practical
proposer reward and highlight copying as a concern when reference tasks
are also used to prompt the proposer.

## Appendix A The SOAR baseline

SOAR ([Sundaram et al., 2026](#bib.bib31)) is an asymmetric self-play
method whose proposer reward measures solver learning progress. Our
reimplementation samples $`g=4`$ groups of $`n=64`$ candidate problems
per outer step. It trains a solver copy on each group for $`r=4`$
repeated inner RL runs of 10 steps, evaluates the copy on a held-out
reference set of hard problems, and rolls it back. Every candidate in a
group receives the group’s accuracy gain:

|  |  |  |
|----|----|----|
|  |
``` math
R(X_{k})=\mathrm{Acc}(\theta^{\prime}_{k},Q_{R})-\mathrm{Acc}(\theta,Q_{R}).
``` |  |

Here $`X_{k}`$ is the $`k`$-th group, $`Q_{R}`$ is the reference set,
$`\theta`$ denotes the current solver parameters, and
$`\mathrm{Acc}(\theta^{\prime}_{k},Q_{R})`$ is the reference accuracy
after training on $`X_{k}`$, averaged over the $`r`$ repeated runs.

Each outer step of our reimplementation requires $`g\times r=16`$ inner
RL runs and 17 reference-set evaluations. It produces at most $`g`$
distinct reward values per outer step (2–4 observed in our run), with
each group reward shared by all 64 candidates in that group. CompassPlay
(cos) assigns a score to each eligible candidate individually
(Figure [3](#S3.F3 "Figure 3 ‣ 3.2 Comparison with SOAR ‣ 3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

No public implementation of SOAR was available, so we reimplemented it
from the paper on our training stack, keeping the base model, the
proposer and the outer optimizer the same as for the other methods.
Following the paper, the reference set is drawn from held-out problems
the base model cannot solve (a pool of $`{\sim}370`$ MATH-train problems
with 0/32 successes, 92 resampled every outer step); the reference pool
of cos is drawn from the same held-out MATH-train split but without the
difficulty filter. The recipe could not be followed exactly on a
single-model self-play stack; the five deviations are: the inner loop
uses the outer REINFORCE++ ([Hu et al., 2025](#bib.bib13)) objective
instead of RLOO ([Ahmadian et al., 2024](#bib.bib1)) because the stack
samples one rollout per problem; one problem type per inner step; the
group reward replaces the whole proposer reward rather than only its
difficulty term; promotion updates weights but not the teacher on that
step, and not the optimizer state. SOAR was run once, for 20 outer
steps. Its outer step contains 16 inner RL runs and 17 reference-set
evaluations (measured on a smoke run: about 10.8 s per inner step and
20 s per evaluation); its 20 outer steps cost 109 GPU-hours in total.

## Appendix B Per-step cost breakdown

GPU-hours are training wall-clock hours multiplied by the number of
GPUs. Coding and Lean runs use different GPUs

### C.1 The reference gradient

#### Question.

The reward $`\cos(g(\tilde{x}),g_{\mathrm{ref}})`$ needs a reference
gradient $`g_{\mathrm{ref}}`$ that stands for “progress on the held-out
problems”. The main method uses the cross-entropy (CE) loss gradient on
gold solutions. This is cheap and low-variance, but the solver itself is
trained with RL. Does a REINFORCE loss-gradient estimate give a better
signal, and at what cost?

#### Methods.

We compare three gradient configurations. The reference-sampling
settings also differ;
Appendix [E](#A5 "Appendix E Experimental details ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
gives those used by the REINFORCE variants.

- •
  cos (CE reference): both sides use CE loss gradients of gold
  solutions. The CE loss is averaged over solution tokens. This is the
  main method.
- •
  REINFORCE reference only: we use a REINFORCE ([Williams,
  1992](#bib.bib33)) estimate of $`\nabla_{\theta}\,\mathbb{E}[v(x,y)]`$
  on held-out problems
  (Appendix [E](#A5 "Appendix E Experimental details ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")),
  where $`v(x,y)`$ is the solver’s verifier reward. For alignment, the
  reference gradient is the negative of this estimate. The candidate
  side keeps the CE loss gradient.
- •
  REINFORCE both sides: both sides use the negative of their respective
  REINFORCE reward-gradient estimates, so both are loss gradients.

Each configuration is a single run with the same seed.
Figure [6](#A3.F6 "Figure 6 ‣ Methods. ‣ C.1 The reference gradient ‣ Appendix C Ablations on the coding task ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
has the form of
Figure [3](#S3.F3 "Figure 3 ‣ 3.2 Comparison with SOAR ‣ 3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver").

Figure 6: Reference-gradient ablation: CE reference (the main method)
against REINFORCE reference gradients, accuracy against cumulative
GPU-hours. Single runs with a shared seed.

#### Results.

At the CE run’s final compute budget (93 GPU-hours), cos has higher
in-domain and OOD accuracy than both REINFORCE configurations. The
configuration with REINFORCE gradients on both sides uses 161 GPU-hours
for 200 steps, compared with 93 for cos with the same seed, a factor of
$`1.7\times`$. The reference-only variant combines a REINFORCE
loss-gradient estimate on the reference with CE loss gradients on
candidates. Its OOD accuracy drops below 30% in the first 30 steps and
ends below cos.

### C.2 Cosine vs dot product

#### Question.

The dot product $`\langle g(\tilde{x}),g_{\mathrm{ref}}\rangle`$ in the
first-order approximation depends on both gradient norms and directional
alignment. For positive alignment, a larger candidate gradient norm
$`\|g(\tilde{x})\|`$ can raise the score without changing the gradient
direction. Cosine is invariant to positive rescaling of either gradient.
Does this normalization improve training?

#### Methods.

Two runs that share the seed and differ in one flag, cosine vs dot, both

configuration of

is the cosine member).

## Appendix E Experimental details

#### Hardware.

Coding runs use 8 AMD MI355X GPUs; Lean runs use 8 AMD MI250X GPUs.
GPU-hours are therefore comparable within a domain but not across
domains.

#### Benchmarks (Section [3](#S3 "3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

In-domain: LiveCodeBench ([Jain et al., 2025](#bib.bib16)),
competitive-programming problems collected after the base model’s
training cutoff, scored by hidden tests; CRUXEval-I and CRUXEval-O ([Gu
et al., 2024](#bib.bib10)), predicting the input, respectively the
output, of a short Python function, the two directions of the
code-reasoning task that self-play trains on. Out-of-domain: MATH500
([Lightman et al., 2024](#bib.bib22)), a 500-problem subset of the MATH
competition benchmark ([Hendrycks et al., 2021](#bib.bib12)); AMC23, the
40 problems of the 2023 American Mathematics Competitions; GSM8K ([Cobbe
et al., 2021](#bib.bib4)), grade-school word problems; Minerva Math
([Lewkowycz et al., 2022](#bib.bib19)), undergraduate STEM problems; and
OlympiadBench ([He et al., 2024](#bib.bib11)), olympiad-level
mathematics. Evaluation is greedy (temperature 0, $`k=1`$).

#### Evaluation window.

Tables [1](#S3.T1 "Table 1 ‣ 3.1 Main results ‣ 3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")
and [2](#S3.T2 "Table 2 ‣ 3.1 Main results ‣ 3 General reasoning with coding self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")

one checkpoint to the next

#### REINFORCE reference gradient (Appendix [C](#A3 "Appendix C Ablations on the coding task ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).

The REINFORCE estimator targets $`\nabla_{\theta}\,\mathbb{E}[v(x,y)]`$.
The expectation averages over reference problems $`x`$ and solver
responses $`y\sim\pi_{\theta}(\cdot\mid x)`$; $`v(x,y)`$ is the binary
correctness reward defined in
§[2.1](#S2.SS1 "2.1 Self-play with a proposer and a solver ‣ 2 Method ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver").
For alignment, we use the corresponding loss gradient: the negative of
this reward-gradient estimate. We use 8 samples per problem on a pool of
128 held-out problems, refreshed every 25 steps.

## Appendix F Instantiation details and pseudocode

The coding instantiation uses the AZR training loop ([Zhao et al.,
2025](#bib.bib38)). The Lean instantiation adapts SGS ([Bailey et al.,
2026](#bib.bib2)) to condition conjectures on solved seed theorems
(Section [4](#S4 "4 Theorem proving with Lean self-play ‣ CompassPlay: Rewarding the Proposer for Where It Moves the Solver")).
Within each domain’s setup, the methods share the training loop and
solver objective. They use different proposer rewards, or omit proposer
optimization for solve-only. The coding baseline uses AZR’s difficulty
reward. The Lean baselines include the SGS guide-score-times-difficulty
reward and difficulty, which omits the guide.
````
