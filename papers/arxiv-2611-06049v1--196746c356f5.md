# Reglos: A Self-Evolving Personal Memory Agent with Recursive Self-Improvement

Sen Yang\corresponding Jiaduo Lin Zehong Huang Wen Liu\corresponding
Reglos.ai Reglos.ai Reglos.ai Reglos.ai sen@reglos.ai
jiaduo.lin@reglos.ai zehong.huang@reglos.ai wen@reglos.ai

###### Abstract

Personal agents draw on past conversations to tailor their responses to
each user. Their memory systems store and update what each user says,
and coding agents now also rewrite the harness that turns this memory
into the model’s context. Such patches risk overfitting, because one
tested only on the failures it targets can fix those cases and help
nowhere else. We present Reglos, a training-free personal memory agent
that tests whether harness changes help beyond the failures they were
written to fix. Its self-evolving memory adds to each user’s append-only
record with every conversation, as new preferences supersede old ones
and facts can be forgotten. Its harness improves through recursive
self-improvement, in which a coding agent proposes patches from failure
traces and a critic from a second model family screens each one for
benchmark gaming. After the harness is frozen, a fixed evaluator decides
which further patches to accept. With the same backbone behind every
system, Reglos outperforms state-of-the-art memory systems such as Mem0,
MemOS and EverOS, reaching 61.3% and 84.0% on PersonaMem-v2 and
LongMemEval-S with Qwen3.8-27B, and 57.5% and 87.2% with GPT-5.6 Luna.

Website: https://reglos.ai

## 1 Introduction

A personal assistant that talks with the same user for months has to
keep track of what that user prefers ([Hu et al. 2025](#bib.bib10);
[Jiang et al. 2025b](#bib.bib12)). Some of those preferences change, and
the user may later ask the assistant to forget others. Reading the whole
history handles this poorly, and even frontier models often miss a
preference the user only implied or keep applying one that has changed
([Jiang et al. 2025b](#bib.bib12)). Memory systems keep what each user
says across conversations and recall it when the model answers ([Packer
et al. 2023](#bib.bib26); [Chhikara et al. 2025](#bib.bib4); [Rasmussen
et al. 2025](#bib.bib28); [Li et al. 2025](#bib.bib15); [Hu et al.
2026](#bib.bib9)). How well they work depends on what they store and on
the code that decides what to recall and how to show it to the model,
which we call the _harness_.

Although these systems update what they store as the user talks, the
harness itself is usually written by hand and revised between releases.
Recent work hands that job to coding agents, which evolve memory
programs and pipelines against benchmarks ([Liu et al.
2026b](#bib.bib20); [Chen et al. 2026](#bib.bib3); [Zhang et al.
2025](#bib.bib44)). A benchmark score alone leaves one question open:
does a change help users whose failures nobody inspected while writing
it?

Our own development data show why that question matters. A memory can be
stored correctly and still be used wrongly: in 31% of the failures we
traced, the evidence the model needed was already in its context
(Section [4.1](#S4.SS1 "4.1 PersonaMem-v2 ‣ 4 Results ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).
Those are failures of the harness, and a coding agent can patch them,
but a patch judged on the cases that prompted it can look better than it
is. A prompt-only search over the harness text in the style of GEPA
([Agrawal et al. 2026](#bib.bib1)) gained 3.8 points on the questions it
was selected on and 1.1 on questions it had never seen.

These failures point to two kinds of change with different owners. A
user’s memory changes whenever that user talks, and an error in it is
best fixed then, inside that user’s record. The harness serves every
user at once, so a change to it can help some users and hurt others, and
that is where overfitting happens. We therefore argue that a personal
memory system should improve at two time scales: its memory online as
each user talks, and its harness offline through changes that a fixed
evaluator accepts only after testing them on held-out users.

We present Reglos, a training-free personal memory agent built on this
principle
(Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).
Its inner loop is a self-evolving memory. Each fact enters an
append-only record that stores when it holds and when it was learned, so
a new preference can supersede an old one without erasing it. A request
to forget expires the matching facts, and a nightly pass rewrites the
profile from the user’s current facts. Because these states are
explicit, the harness can tell the model which of two conflicting
preferences is current and what it must not use. Its outer loop improves
the harness through recursive self-improvement. A coding agent reads
failure traces and writes patches, and a critic from a second model
family clusters the same failures and rejects patches that game the
benchmark. After the harness is frozen, a fixed evaluator accepts a
patch only if it helps users held out from development. The two loops
co-evolve. The outer loop learns from the failures of the memory the
inner loop builds, and each accepted patch changes how that memory is
written and read. Qwen3.8-27B writes memory throughout.

With Qwen3.8-27B writing memory for every system, Reglos outperforms
Mem0, MemOS and EverOS on PersonaMem-v2, LongMemEval-S and LoCoMo,
whether Qwen3.8-27B or GPT-5.6 Luna answers
(Figure [1](#S1.F1 "Figure 1 ‣ 1 Introduction ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).
On the official PersonaMem-v2 benchmark split it reaches 61.3%, 7.5
points above the strongest of them; the best published result we found
is 57.2%, obtained with a GPT-4.1-mini reader ([Liu et al.
2026c](#bib.bib21)). On LongMemEval-S it reaches 84.0%, 3.6 points above
EverOS. With GPT-5.6 Luna answering, it scores 57.5% and 87.2% and again
leads both benchmarks. Within the outer loop, the coding agent’s
accepted patches lift the harness from 54.2% to 60.7% on the validation
questions.

## 2 Related Work

#### Memory Systems and Benchmarks.

Early memory for LLM agents paged information in and out of a bounded
context ([Packer et al. 2023](#bib.bib26)) or kept a stream of
observations with periodic reflection ([Park et al. 2023](#bib.bib27)).
Production systems now extract and reconcile facts ([Chhikara et al.
2025](#bib.bib4)), build temporal knowledge graphs ([Rasmussen et al.
2025](#bib.bib28)), link notes ([Xu et al. 2025](#bib.bib37)) or manage
memory as an operating system ([Li et al. 2025](#bib.bib15); [Hu et al.
2026](#bib.bib9)); [Hu et al. (2025)](#bib.bib10) survey the space.
Benchmarks have moved from recalling facts in long dialogues ([Maharana
et al. 2024](#bib.bib23); [Wu et al. 2025](#bib.bib35)) to inferring
implicit, evolving preferences ([Jiang et al. 2025a](#bib.bib11); [Jiang
et al. 2025b](#bib.bib12)) and to long agent trajectories ([Zhao et al.
2026](#bib.bib48)). Two diagnostic studies shape our evaluation. Most
memory systems fall below naive retrieval over the raw history on
PersonaMem-v2 ([He et al. 2026](#bib.bib8)), so we report raw retrieval
with our own answer policy as a control. On LoCoMo, most failures arise
at retrieval (Yuan et al. [2026](#bib.bib41)); on PersonaMem-v2 we find
most reachable failures after retrieval, when the answering model
already holds the evidence
(Section [4](#S4 "4 Results ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).

#### Self-Evolving Agents and Memory.

Self-evolving agents improve from their own interaction data and
feedback ([Gao et al. 2026](#bib.bib7); [Fang et al. 2025](#bib.bib6));
without retraining the underlying model, they reflect on failures
([Shinn et al. 2023](#bib.bib29); [Madaan et al. 2023](#bib.bib22)),
accumulate skills ([Wang et al. 2024](#bib.bib32)), or grow an evolving
context or prompt ([Zhang et al. 2026d](#bib.bib47); [Agrawal et al.
2026](#bib.bib1)). Memory is a common place where this evolution
happens. MemEvolve meta-evolves how experience is encoded, stored and
retrieved ([Zhang et al. 2025](#bib.bib44)), EvolveMem tunes retrieval
configurations from failure logs ([Liu et al. 2026a](#bib.bib19)),
MemSkill and SelfMem evolve memory skills and strategies ([Zhang et al.
2026b](#bib.bib45); [Yang et al. 2026](#bib.bib40)), and MindMemOS
evolves memory schemas and consolidates them by dreaming ([Liang et al.
2026a](#bib.bib16)); Memory-R1, Mem-$`\alpha`$ and Mem-T instead train
the memory manager with reinforcement learning ([Yan et al.
2025](#bib.bib39); [Wang et al. 2025](#bib.bib33); [Yue et al.
2026](#bib.bib42)). Reglos’s inner loop is self-evolution of this kind,
applied per user under fixed rules (supersession that keeps history,
retraction that records the request, and user edits).

#### Recursive Self-Improvement.

In the sense of [Duan et al. (2026)](#bib.bib5), recursive
self-improvement (RSI) is an autonomous, closed loop whose changes
persist and alter later improvement. One line of recent work trains the
model inside that loop ([Lin et al. 2026](#bib.bib18); [Zhang et al.
2026a](#bib.bib43)). Another is training-free and evolves the harness
around a frozen model ([Lee et al. 2026b](#bib.bib14); [Zhang et al.
2026c](#bib.bib46); [Lee et al. 2026a](#bib.bib13)), and some systems
combine the two ([Wei et al. 2026](#bib.bib34); [Su et al.
2026](#bib.bib30)). RSI has also reached memory: MemPro, PrisMem and
ALMA evolve the memory pipeline as code ([Liu et al. 2026b](#bib.bib20);
[Chen et al. 2026](#bib.bib3); [Xiong, Hu, and Clune 2026](#bib.bib36)),
and D²ACCI gates memory changes with statistical tests ([Liu et al.
2026c](#bib.bib21)). Reglos belongs to the training-free harness line,
at the level of strategy autonomy: a coding agent proposes harness code,
the task model stays frozen, and a fixed evaluator decides which changes
to keep.

## 3 Reglos

Reglos pairs an online loop that updates each user’s memory with an
offline loop that recursively improves the harness supplying context to
the frozen model, and the two co-evolve
(Figure [2](#S1.F2 "Figure 2 ‣ 1 Introduction ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).
The same memory service serves our own app, and
Appendix [A](#A1 "Appendix A Implementation Details ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")
gives its thresholds and limits.

### 3.1 Inner Loop: Self-Evolving Memory

#### From conversation to facts.

Each user’s memory grows from what that user says. New messages wait in
a buffer until there are enough to be worth reading, and the task model
then extracts the facts, commitments and requests to forget that they
contain. Before any of this text reaches a model, secrets such as keys
and card numbers are masked. Once extracted, each candidate is compared
with the facts already stored. One batch call then decides whether it is
new, already known, a replacement for an older fact, or extra detail for
one. The accepted facts are kept in the language the user spoke and
indexed for recall.

#### An append-only record.

Every fact keeps the identifiers of its source messages, a perspective
(the user’s own belief, an objective fact, or something the assistant
said) and two times: when the fact holds and when the system learned it.
A fact’s text is never rewritten, so a change of mind closes the old
fact’s validity and leaves it in the record, where the history of a
preference stays readable. A request to forget expires the matching
facts and records the request itself, which the harness later shows the
model with the rule never to rely on it.
Figure [3](#S3.F3 "Figure 3 ‣ An append-only record. ‣ 3.1 Inner Loop: Self-Evolving Memory ‣ 3 Reglos ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")
follows one user through these cases. Users can also inspect, correct,
delete and undo any memory in the app.

Figure 3: One user’s record across three sessions. A change of mind
closes the old fact and keeps it, a request to forget expires the fact
and stays as a rule, and recall shows the model which version holds.

#### Consolidation and recall.

The record is condensed as well as kept. Each night a pass called Dream
summarizes the day’s sessions and rewrites the user’s profile from the
facts that are still current. When a question arrives, recall searches
the facts through six routes at once: three on content (vector, keyword
and entity graph), two anchored on the time and place the question
mentions, and recency. The content routes decide what can come back.
Time, place and recency only raise facts that a content route has found,
unless no content route finds anything, and a fact found by recency
alone is dropped. The routes are fused by reciprocal rank fusion into a
fixed token budget, and an _explain_ call reports which route surfaced
each item.

### 3.2 Engine and Serving

#### A Rust kernel and a Python harness.

The memory kernel is a Rust service. The harness, the benchmark drivers
and the outer loop are written in Python and call it over HTTP. The
split sets what a candidate costs the outer loop. A harness change is
scored on the memories already stored, while an engine change must
re-ingest every history.

#### One database.

The kernel keeps every layer of memory, and the work queue that
maintains it, in a single PostgreSQL 16 database. The indexes behind
recall’s three content routes live there too, as embedding columns
beside the facts, a trigram index and a relational graph table, so no
separate vector store is needed. Recall scans each user’s rows exactly.
One user holds a few hundred to a few thousand facts, and an approximate
index filtered down to one user can silently return fewer of them than
asked. Extraction and Dream run as jobs that workers lease from the same
database, so several instances share the load and a job interrupted by a
crash is picked up when its lease expires.

#### Writes that never lose a fact.

A candidate that matches a stored fact after normalization (case, width,
spacing and punctuation) only confirms the stored row, with no model
call. If the batch adjudication fails, every candidate is kept as new,
so a model error can duplicate a fact but never lose one. Model calls
back off for about three minutes on rate limits and server errors. With
the model’s reasoning disabled, the engine uses a quarter of the output
tokens and 2.6 seconds per model call against 9.3.

### 3.3 The Harness

The harness is the program that sits between the memory kernel and the
frozen task model and determines what the model reads. It receives the
question, together with its answer options where the benchmark provides
them, but has no access to the dataset’s labels. Memory is reachable
only through a narrow interface: recall, the list of stored items, the
user’s profile and the source messages of each fact. Within this
interface the harness may issue several recall queries, filter and rank
the results across memory layers, and decide how the evidence is
organized. These decisions form the search space of the outer loop
(Section [3.4](#S3.SS4 "3.4 Outer Loop: Recursive Self-Improvement ‣ 3 Reglos ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).

Each context opens with a memory-use policy and the user’s requests to
forget, followed by the profile, the recalled facts with superseded ones
marked as no longer true, and a small number of session summaries and
raw excerpts. For multiple-choice questions the harness also retrieves
evidence for each option. The options of a question typically share a
template, so recall on the full option text returns nearly the same
facts for all of them; the harness therefore queries with the terms that
distinguish each option from the others. This per-option retrieval was
the final step accepted by the outer loop
(Section [4.3](#S4.SS3 "4.3 The Outer Loop ‣ 4 Results ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).

The policy specifies how the model should interpret the states that the
record encodes. The model must not rely on facts the user asked to
forget or on preferences that are no longer current, and it must keep
the preferences of other people separate from the user’s own. Further
rules address what the record cannot encode: the memory is incomplete,
preferences must not be inferred from demographic attributes, and
sensitive identifiers must not appear in the answer.
Appendix [A](#A1 "Appendix A Implementation Details ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")
gives the full policy.

#### Setting.

We evolve the harness on PersonaMem-v2 ([Jiang et al.
2025b](#bib.bib12)), whose four-way questions turn on implicit, revised
or retracted preferences, on preferences that belong to someone else,
and on information the user asked not to repeat. Qwen3.8-27B (reasoning
off) writes memory and answers throughout. The loop sees only the
validation split. We report all PersonaMem-v2 results on the official
5,000-question test set. We scored it once after the freeze and never
read its failures
(Appendix [C](#A3 "Appendix C The Outer Loop in Full ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")).

#### Proposer, critic and evaluator.

The proposer is the coding agent Claude Code ([Anthropic
2025](#bib.bib2)) running Claude Opus 5.5. It reads raw failure traces
and writes a patch to the harness, following the finding that raw traces
carry more signal than summaries ([Lee et al. 2026b](#bib.bib14)). The
critic is Codex ([OpenAI 2025](#bib.bib25)) running GPT-6.1 Sol, so the
proposer and the critic come from different model families. The critic
clusters the same failures independently and rejects any patch keyed to
the dataset’s option templates or labels. A fixed evaluator then
decides. After the freeze, every candidate faces the rule of
Figure [4](#S3.F4 "Figure 4 ‣ Proposer, critic and evaluator. ‣ 3.4 Outer Loop: Recursive Self-Improvement ‣ 3 Reglos ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement"):
it must gain on each of two persona-disjoint validation halves (1,317
questions) and may cost a second reader at most one point; GPT-5.6 Luna
is that reader and answers from the same contexts. Humans fix the
objective, the splits and the rule; the proposer decides what to change.
In the taxonomy of [Duan et al. (2026)](#bib.bib5) this is strategy
autonomy (L2), and the inner loop is environment adaptation (L4);
Appendix [C](#A3 "Appendix C The Outer Loop in Full ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")
maps both loops onto their components.

## 4 Results

#### Models.

Qwen3.8-27B runs in non-thinking mode through Alibaba Cloud’s DashScope
API, and qwen3.7-text-embedding supplies every embedding. The EverOS
store for BEAM-100K and the no-memory LoCoMo row with Qwen3.8-27B used
the same unquantized weights served locally. GPT-5.6 Luna answers with
its default reasoning setting.

#### Baselines.

MemOS and EverOS run self-hosted;
Appendix [B](#A2 "Appendix B Controls and Variants on PersonaMem-v2 ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")
describes their PersonaMem-v2 configurations. Mem0 uses its open-source
extraction prompts and retrieval scoring, with its add and search logic
running on an in-process store. Zep runs through its open-source
Graphiti engine. gpt-5.5 judges LongMemEval-S and LoCoMo (categories 1
to 4), and OmniMemEval’s rubric grader with gpt-5.5 scores BEAM.
BEAM-100K and BEAM-500K each use ten sampled conversations with 200
questions. Full context keeps the newest 400k characters of a history.

#### Reglos’s lead comes from sensitive information and forgetting.

Figure [5](#S4.F5 "Figure 5 ‣ Reglos is best on PersonaMem-v2 with both readers. ‣ 4.1 PersonaMem-v2 ‣ 4 Results ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")

#### Forgetting as retraction.

In the seed engine a message such as “please forget that I take
sertraline” was stored as an emphasized memory, because the extraction
prompt read it as a request to remember. On questions that test
forgetting the correct option is the generic one, and the seed answered
none of nine development cases. Retraction with a tombstone, and a
policy line that forbids relying on anything listed as forgotten, raised
this to eight of nine on development and twelve of fourteen on a
held-out slice.

#### Evidence the reader never saw.

Many preferences sat in raw conversation excerpts without being
extracted, and recall driven by the question could not reach them,
because the question does not name the preference. Recall run once per
answer option, with the words that distinguish that option, finds them.
Together with the policy revision between them, the steps from v1 to v3
raised accuracy from 54% to 68% on a 50-question held-out slice.

#### What it costs.

Writing one persona’s 32k-token history to memory costs about 225k to
260k task-model tokens (roughly 7.5 times the history) and 40k embedding
tokens, amortized over 25 questions per persona. Answering costs about
6.0k prompt tokens per question, so judging one candidate on 1,317
questions with two readers takes about 16M prompt tokens. Writing memory
for the 200 test personas took about 50M task-model tokens and six hours
at eight-way concurrency.

## 5 Discussion

#### What the loop found.

Each accepted change, from how a request to forget is recorded to what
recall asks for, began as a failure trace that the coding agent read and
turned into code.

#### The ceiling and the hardest slice.

In our development audit about half of the remaining errors could not be
answered from the history at all, which puts the ceiling for a perfect
reader near 80%, and most of the reachable half are reader decisions
bounded by the task model’s ability ([Zhou 2026](#bib.bib49)).
Preferences that belong to other people stay below chance for every
system: a preference stated about a sister or a colleague is extracted
as the user’s, and every later layer trusts it. The fix belongs in the
write path, with provenance that survives consolidation.

#### Limitations.

One open 27B model writes memory for every system; Reglos remains first
on PersonaMem-v2 and LongMemEval-S when GPT-5.6 Luna answers. The
published number we compare with uses a different reader (GPT-4.1-mini).
The LoCoMo result rests on reading short histories in full, and on BEAM
the systems sit within a few points of each other.

#### Next steps.

The next step in the taxonomy of [Duan et al. (2026)](#bib.bib5) is a
loop that chooses which experience to gather. The product already
records when users correct, delete or undo a memory; turning those
events into the failure traces the proposer reads, behind the same
evaluator, is the step we are taking next ([Liang et al.
2026b](#bib.bib17); [Xue et al. 2026](#bib.bib38)). A second direction
is to stop holding the model fixed. Everything here was gained with a
frozen model, and most errors that memory can still fix are reader
decisions, so training the model that writes and reads memory is the
complementary step. Reinforcement learning on memory construction and
use is an active direction ([Wang et al. 2025](#bib.bib33); [Yan et al.
2025](#bib.bib39)), an RL-trained 4B agentic memory reaches 55.2% on
PersonaMem-v2 ([Jiang et al. 2025b](#bib.bib12)), and harness search can
alternate with training on the policy ([Wei et al. 2026](#bib.bib34)).
Further on, the record’s operations (add, supersede, retract,
consolidate, recall) could become the training objective of a memory
foundation model. A third direction is modality: in our benchmark runs
images enter memory only as captions, and the record, recall and
redaction should extend to images, voice and the screen, under the same
rules for supersession and forgetting.

## 6 Conclusion

We presented Reglos, a personal memory agent whose two loops co-evolve
at two time scales: each user’s memory evolves online in an append-only
record, and the harness that turns memory into context evolves offline
through patches that a coding agent proposes and a fixed evaluator
scores. With one frozen open 27B model and a training-free pipeline,
Reglos outperforms the memory systems we compared on PersonaMem-v2,
LongMemEval-S and LoCoMo with either answering model, and exceeds the
best published result under PersonaMem-v2’s official protocol. Its main
limit is the reader itself: most errors that memory can still fix are
decisions made with the evidence in view. We plan to feed users’ own
corrections back into the outer loop as experience.

## Appendix A Implementation Details

This appendix gives the thresholds and limits behind
Section [3](#S3 "3 Reglos ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement").

#### Services and storage.

The kernel consists of a memory library, a memory service that exposes
it over HTTP, and a model service that presents an OpenAI-compatible
interface and fails over between providers on network errors, rate
limits and server errors. Embeddings are 1024-dimensional columns on
facts, conversation chunks and sessions. An exact scan of one user’s
facts takes milliseconds. Jobs (extraction, re-indexing and Dream) are
rows that workers claim under a ten-minute lease, so several instances
share the work without coordinating.

#### The record.

Every memory is a fact row with a statement, a predicate, the entity it
is about, a perspective (an objective fact, a belief or preference of
the user, or something the assistant said), a confidence, and the
identifiers of its source messages. Two time axes are stored separately:
the interval during which the fact holds (_valid from_, _valid to_) and
the system’s own timeline (_ingested at_, and _expired at_ once the row
is retired). Only the validity and expiry fields of a row ever change.
When a new statement supersedes an old one, the old row receives an end
of validity and stays in the record, so a question about an earlier
period can still be answered. A request to forget expires the matching
facts with a reason, and a tombstone fact records the request so that
recall, summaries and the profile all honor it. A fact matches when its
cosine similarity to the request is at least 0.68 or its trigram overlap
at least 0.6; a request to forget expires at most six facts and a
correction at most two, and background the user entered deliberately is
never expired.

#### The write path.

Incoming turns pass through a buffer and a redaction step that replaces
keys, card numbers and identity numbers with placeholders. The model
then proposes candidate facts, commitments and retractions. A candidate
whose normalized key (case, width, spacing and punctuation) matches a
stored fact only confirms that fact, and a single batch call decides for
each remaining candidate whether it is new, a duplicate, a replacement,
a coexisting fact or an enrichment of an existing one. Facts, summaries
and the profile are stored in the language of the conversation.

#### Recall.

The three content routes are dense vector search, keyword search and
traversal of the entity graph. The two anchor routes match a time
window, interpreted in the configured time zone against both when a fact
was recorded and when its event happened, and a scene or location. A
question that names no time skips the time route. Fusion is weighted
reciprocal rank fusion ($`k=60`$), cut to 45 items and packed in rank
order into 8,100 tokens; both limits widen for questions that ask to
enumerate. Each route has a 2.5-second timeout, and a route that times
out is reported while the others’ results are returned. For every item,
_explain_ returns the routes that found it, its rank on each, its fusion
contribution and its validity state.

#### Consolidation.

Dream flushes the write buffer, summarizes each session, rebuilds the
profile from the user’s current facts and rewrites it. It runs for each
user once a night after an hour of inactivity, and a session pending for
more than thirty hours is scheduled regardless of the hour.
Consolidation never deletes rows of the record; it produces summaries
and the profile, which recall draws on next to the facts and raw
excerpts.

recalled memory

## Appendix C The Outer Loop in Full

#### The two loops as improvement loops.

A self-improving system can be described by its components, with its
autonomy graded in levels ([Duan et al. 2026](#bib.bib5)). The
components include the target the system changes, the experience it
learns from, the improver and the verifier.
Table [8](#A3.T8 "Table 8 ‣ The two loops as improvement loops. ‣ Appendix C The Outer Loop in Full ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")
maps both loops of Reglos onto this framework.

|               | Inner loop (per user, in deployment)                                    | Outer loop (the harness, offline)                                                                       |
| ------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Target        | that user’s record, summaries, profile                                  | harness code and prompts: extraction rules, retraction, recall and evidence construction, answer policy |
| Experience    | the user’s conversations, calendar, corrections                         | failure traces on development splits: context, prediction, gold, recall explanations                    |
| Improver      | the fixed write and consolidation pipeline                              | a proposer coding agent (Claude Code) and a critic from a second family (Codex)                         |
| Strategy      | fixed rules: add-only extraction, merge adjudication, retraction, Dream | cluster failures, form a hypothesis, patch, evaluate                                                    |
| Verifier      | fixed write rules plus user review (inspect, correct, delete, undo)     | frozen evaluator, pre-registered acceptance rule, second reader                                         |
| Inherited     | the record itself (append-only history)                                 | the accepted harness and the log of candidates and decisions                                            |
| Humans decide | what to share, what to correct or delete                                | objective, splits, acceptance rule, when to freeze                                                      |
| Level         | L4, environment adaptation                                              | L2, strategy autonomy                                                                                   |

Table 8: The two loops of Reglos in the self-improvement framework.

#### Inner loop: self-evolving memory (L4).

The inner loop is what the product does for every user every day. Its
target is persistent state, the experience is the user’s own
interaction, and the rules under which the state may change are fixed:
the pipeline deletes nothing (only the user can), supersession keeps
history, forgetting is a retraction with a tombstone, consolidation adds
derived layers and leaves facts unchanged, and the user can override any
of it. In the framework this is environment-adaptation autonomy, and it
is what the broader literature calls a self-evolving memory ([Gao et al.
2026](#bib.bib7); [Fang et al. 2025](#bib.bib6)). The pipeline that
writes memory changes only through the outer loop, which is how the two
loops co-evolve.

#### Outer loop: recursive self-improvement of the harness (L2).

The outer loop changes the code. Its target is everything between the
frozen task model and the kernel: how facts are extracted and merged,
how a request to forget is applied, what recall is asked for, how
evidence is laid out, and what the policy says. The critic is a model
from a different family than the proposer; it clusters the failures
independently and checks every proposal against a shortcut rule: no
logic keyed to the dataset’s option templates, to the labels of who
holds a preference, or to how the generic option is constructed. The
verifier is a frozen script that applies the rule of
Figure [4](#S3.F4 "Figure 4 ‣ Proposer, critic and evaluator. ‣ 3.4 Outer Loop: Recursive Self-Improvement ‣ 3 Reglos ‣ Reglos: A Self-Evolving Personal Memory Agentwith Recursive Self-Improvement")
to every candidate after the freeze.

In the framework this is strategy autonomy, the level of Self-Harness
([Zhang et al. 2026c](#bib.bib46)), and Meta-Harness ([Lee et al.
2026b](#bib.bib14)) works the same way: the coding agent decides what to
change and people decide what counts. The improver and the verifier stay
fixed, so the loop stops short of recursive inheritance (L5), where they
too would be revised.

#### Splits.

During development the loop tuned on small slices of the validation
split and checked progress on a separate slice at milestones. After the
freeze we divided the validation personas into two persona-disjoint
halves and excluded every persona inspected during development, which
leaves 1,317 questions.

#### Acceptance rules.

During development a change was kept when it did not lower accuracy on
the tuning slices, and it replaced the current harness once it gained
about 3 points. This margin proved close to run-to-run noise, so after
the freeze we adopted the stricter rule of
